## 1. 定位

H 层第 7 个锚点（deps：2-5、1-3c）。站点状态口径：**趋势观察**——这一点与 H6 的「面试出现中」不同，必须分清两条线：

- **社区热度高**：官方产品已发布并持续迭代（OpenAI ChatGPT Agent、Anthropic Claude Computer Use），开源方案活跃（Browser Use 等），评测基准（OSWorld、WebVoyager）分数不断刷新，技术对比文铺天盖地。
- **已进面试真题**：截至 2026-09 复核，未检索到确证真题。面试中以**开放讨论题**出现——「了解 Computer Use 类 Agent 吗？什么场景适合用？」，考察的是机制理解与诚实评估可靠性边界，不是背产品参数。

趋势观察期的答题纪律：**讲清循环机制、讲准产品格局、诚实给出可靠性数字与安全边界**。说「已经能替代人工」与说「只是玩具」同为减分项。

三个支柱：

1. **机制层**：感知-行动循环（截图→理解→点击→验证）与步级错误累积。
2. **格局层**：CUA 与 Claude Computer Use 的形态对比；2025-2026 产品线剧变（Operator 关停并入 ChatGPT Agent、OpenAI Agent 工具线整合）。
3. **工程层**：可靠性从 15-38% 到 72-89% 的演进，以及监督式部署三件套。

前置关系：循环节拍就是 2.5 的 ReAct，Observation 的来源从工具返回值变成新截图；有 API 的场景仍走 1.3c 的工具调用——GUI 是无 API 时的兜底而非首选。浏览器/计算机使用 Agent 的入门实操在 4.4（选修），沙箱与执行隔离在 H8 深化。

## 2. 一句话定义

计算机使用 Agent（Computer Use Agent，CUA）是让多模态模型直接操作图形界面的 Agent：截图→视觉理解界面→输出坐标与动作（移动、点击、输入、滚动）→执行→再截图验证，循环推进直到任务完成——不依赖目标软件提供 API，人能点的它就能点。

## 3. 为什么需要

企业自动化的真实痛点是**覆盖率缺口**：绝大多数存量企业软件（ERP、财务系统、内部审批台）没有开放 API，或 API 覆盖不到全流程；RPA（Robotic Process Automation，机器人流程自动化）能录脚本，但界面一改版就断，且每个流程都要单独开发。只要人能用这个软件，CUA 就能操作——它用「看屏幕」换来了近乎 100% 的场景覆盖。

| 维度 | API/工具调用 | RPA（脚本录制回放） | Computer Use Agent |
|---|---|---|---|
| 适用前提 | 系统提供接口 | 界面稳定、流程固定 | 只要人能操作即可 |
| 目标系统改造成本 | 需开发对接 | 流程梳理+脚本开发 | 近零（不改造目标系统） |
| 界面改版适应性 | 不受影响 | 改版即断，需重录 | 视觉理解有一定鲁棒性，仍需监控 |
| 泛化迁移 | 每个接口单独接 | 每个流程单独录 | 同一 Agent 可跨软件换任务 |
| 速度/成本 | 最快最省 | 快 | 慢（每步一次截图推理，秒级） |
| 可靠性 | 高 | 稳定流程下较高 | 最低（概率性点击） |
| 安全面 | 小（权限可收敛） | 中 | 大（够得着界面上所有按钮） |

结论铁律：**有 API 优先 API，RPA 次之，GUI Agent 是最后手段**。它的价值不是替代前两者，而是补上「无 API 老系统」这块覆盖率为零的拼图——架构师的第一反应应是「为什么不用 API/RPA」，再选最重的锤子。

## 4. 核心原理

### 4.1 感知-行动循环

```text
截图（Observe）→ 理解与决策（Think）→ 执行动作（Act）→ 截图验证（Verify）→ 循环
```

四拍拆解：

1. **感知**：整屏截图送入多模态模型；部分方案叠加 DOM 或无障碍树作为辅助感知（4.4 所述「截图 vs DOM」两类感知路线）。
2. **理解**：模型读图定位目标元素，并判断界面状态——有没有弹窗、是否加载中、上一步是否报错。
3. **决策输出**：动作类型+坐标/按键序列。常见动作空间：`click`、`double_click`、`type`、`key`、`scroll`、`screenshot`、`wait`、`terminate`。
4. **验证**：动作后再截图，对照预期确认是否生效。验证是纠错的唯一来源——跳过验证等于让错误单向累积。

与 2.5 ReAct 的对应：截图是 Observation 的来源，动作用户输出是 Action，新截图即下一次 Observation。循环的终止条件、步数上限、死循环检测，全部沿用 2-3/2-5b 的防护设计，只是对象换成了屏幕。

### 4.2 坐标定位与动作空间

坐标输出是 CUA 区别于普通工具调用的关键难点：

- **绝对坐标**：模型直接输出像素坐标——受分辨率、缩放比（DPR）影响，需统一归一化，截图降采样还会吃掉小按钮的定位精度。
- **辅助定位**：Set-of-Marks 类方法在截图上给可交互元素标注编号，模型输出「点击 3 号元素」，把开放视觉定位降级为选择题，单步成功率显著提升。
- **粒度权衡**：粗粒度动作（「点击提交按钮」，由运行时解析）更稳但依赖界面元数据；细粒度动作（纯坐标）通用但脆。

### 4.3 CUA 与 Claude Computer Use 形态对比

两家代表了两种产品形态：OpenAI 把环境托管起来卖服务，Anthropic 把模型能力下放、让开发者自建循环与环境。

| 维度 | OpenAI CUA 线（Operator→ChatGPT Agent） | Anthropic Claude Computer Use |
|---|---|---|
| 提供形态 | 托管 Agent 产品（Operator 能力并入 ChatGPT Agent）；模型能力亦经 API 提供 | 模型能力以 computer use 工具形式经 API 提供（自 beta 起持续迭代），官方提供参考实现 |
| 宿主环境 | 浏览器类任务跑在 OpenAI 托管的虚拟浏览器里 | 开发者自建虚拟机/容器（官方参考实现基于 Docker 容器），可操控完整桌面 |
| 感知输入 | 截图（低分辨率优化吞吐） | 截图为主；配套 bash、文本编辑等辅助工具 |
| 集成方式 | 产品内对话即用；API 侧作为工具接入自有循环 | 自己写感知-行动循环，灵活性高、工程量大 |
| 适合谁 | 面向消费者的通用任务（订票、购物、填表） | 企业内网系统、桌面软件等需要自定义执行环境的场景 |

### 4.4 产品格局剧变（2025-2026）

引用产品案例前先对时间线——这是趋势观察期最容易翻车的地方：

| 时间 | 事件 | 影响 |
|---|---|---|
| 2024-10 | Anthropic 发布 computer use 能力（API beta） | GUI Agent 走进开发者视野 |
| 2025-01 | OpenAI 发布 Operator（CUA 模型驱动） | 托管式浏览器 Agent 面向消费者 |
| 2025-07 | OpenAI 发布 ChatGPT Agent | 通用 Agent 形态上线 |
| 2025-08-31 | Operator 关停，能力并入 ChatGPT Agent | 独立浏览器 Agent 产品线收束 |
| 2026-03 | Anthropic 推出面向消费者的 Claude Computer Use（Mac 桌面直控） | 从开发者 API 走向 C 端 |
| 2026-06-03 | OpenAI 通知弃用 Agent Builder | 低代码 Agent 编排工具线收缩 |
| 2026-08-26 | Assistants API 关停（定档） | OpenAI 工具线整合，新接口体系成为主线 |

读法：格局从「多家独立产品并行」收敛为「少数通用 Agent 主线+模型能力 API」。面试引用案例时以最新格局为准——提 Operator 必须补一句「已并入 ChatGPT Agent」；引用 OpenAI 工具链时注意 Assistants API 已于 2026-08 关停、Agent Builder 已弃用。用 2025 年初的产品格局答题，等于暴露信息过期。

### 4.5 可靠性演进：15-38% 到 72-89%

- 2025 年初：主流模型在 OSWorld（真实操作系统任务基准）上的成绩普遍落在 15%-38% 区间——五分之四的任务做不完。
- 2026 年：头部方案爬升到 72%-89% 区间（含开源方案 Browser Use 宣称 89.1% WebVoyager 的社区口径）。

从严解读三点：

1. **基准分不等于生产可用**：基准任务定义清晰、环境干净；生产任务更长、界面更脏、干扰更多。
2. **分数口径不可横比**：OSWorld 与 WebVoyager 任务集不同，是否 verified 口径不同，产品宣称与第三方复测之间也存在差距——引用时注明基准名。
3. **即便单任务 80%+，完全自主仍不成立**：长任务与高危场景必须保留人工闸，这是各家产品仍设监督机制的共同原因。

演进归因：视觉定位专项训练提升点击精度、推理模型带来的多步规划与自纠错、Set-of-Marks 类辅助感知、computer use 专项后训练。

### 4.6 步级错误累积

CUA 的核心数学：**任务成功率 = 单步成功率的连乘**。

```text
单步 95% →  8 步任务  66% → 30 步任务  21% → 50 步任务 7.7%
单步 99% →  8 步任务  92% → 30 步任务  74% → 50 步任务 60%
```

与 2-9b 的复合失败率（95%^8≈66%）是同一个公式，只是步数被 GUI 任务拉得更长。三个推论：

1. **任务长度是隐形杀手**：单步看着不错，乘到几十步就归零。拆子任务、加检查点是唯一解。
2. **验证步不是开销而是止损**：每步验证把「错误传染」变成「错误拦截」——点错后立刻发现回退，比 10 步之后发现重来便宜一个量级。
3. **步数预算是硬约束**：无上限循环的期望结局是死循环（反复点刷新、关不完的弹窗）。步数+token 双阈值刹车，是 2-3 防护设计在屏幕上的直接应用。

### 4.7 部署模式：监督式而非全自动

| 模式 | 行为 | 适用 |
|---|---|---|
| 全自动 | 无人值守跑完全程 | 仅限只读、可逆、沙箱内任务 |
| 监督式（生产默认） | 每步可观测；危险动作挂起等人确认 | 大多数生产场景 |
| 半自动 | 低风险步骤自动，提交/支付类人工点击 | 资金、数据变更场景 |
| Shadow（影子模式） | 只记录计划动作不执行，人工复核准确率 | 引入期验证 |

安全三件套贯穿所有模式：**危险操作白名单+人工确认、全程录屏留痕、失败自动暂停转人工**。执行环境本身还要隔离（虚拟机/容器、最小权限账号、网络白名单）——那正是 H8 的主题。

## 5. 架构 / 流程

```text
任务（自然语言）
      |
┌─────▼───────────────────────────────┐
│ 执行环境：隔离 VM/容器（H8 主题）      │
│  ├ 浏览器 / 完整桌面                  │
│  ├ 专用最小权限账号（非管理员）        │
│  └ 网络白名单                         │
└─────┬───────────────────────────────┘
      ▼
┌──── 感知-行动循环（ReAct 变体）────────────┐
│  截图 →（可叠加 DOM/无障碍树）             │
│    ↓                                      │
│  多模态模型：理解界面 → 输出动作+坐标       │
│    ↓                                      │
│  安全闸门：命中危险操作白名单？             │
│    ├ 是 → 挂起 → 人工确认 / 拒绝           │
│    └ 否 → 执行 → 再截图验证（对照预期）     │
│    ↓                                      │
│  任务完成？→ 否 → 步数/预算检查 → 继续循环  │
│              （停滞检测：连续 N 步无变化）  │
└──────────────┬───────────────────────────┘
               ▼
┌──── 治理层 ────────────────────────────────┐
│ 录屏留痕 ｜ 每步日志（截图+动作+决策理由）  │
│ 异常告警：界面改版 / 死循环 / 失败暂停      │
│ 复盘：轨迹回放 → bad case → 评估集回归      │
└───────────────────────────────────────────┘
```

### 6.2 computer use 工具风格的循环（Python 简化骨架）

```python
# cu_loop.py —— computer use 工具风格的感知-行动循环（简化示意）
import json

MAX_STEPS = 25

def screenshot_b64(vm) -> str: ...      # 从隔离 VM/容器截屏并编码
def send_to_model(messages): ...        # 调多模态模型，附带 computer use 工具定义
def run_in_vm(vm, action: dict): ...    # 在 VM 里执行 click/type/key/scroll

def run_task(task: str, vm) -> str:
    messages = [{"role": "user", "content": task}]
    for _ in range(MAX_STEPS):
        resp = send_to_model(messages)                    # 模型基于最新截图决策
        for block in resp.content:
            if block["type"] == "tool_use" and block["name"] == "computer":
                action = block["input"]                   # 如 {"action":"click","coordinate":[1120,640]}
                run_in_vm(vm, action)                     # 执行
                messages.append({"role": "assistant", "content": resp.content})
                messages.append({
                    "role": "user",
                    "content": [{
                        "type": "tool_result",
                        "tool_use_id": block["id"],
                        "content": screenshot_b64(vm),    # 新截图作为 Observation 回传
                    }],
                })
            elif block["type"] == "text" and "任务完成" in block.get("text", ""):
                return block["text"]
    return "步数预算耗尽，转人工"

if __name__ == "__main__":
    print(json.dumps({"result": run_task("把附件发票录入报销系统", vm=None)},
                     ensure_ascii=False))
```

## 7. 案例

### 案例 A：无 API 老报销系统的财务自动化

**场景**：某制造企业 3 套老财务系统均无 API，财务每月手工录入约 1200 笔报销单。

**实施**：阶段一 Shadow 模式 4 周——Agent 每步只输出「计划动作序列」，不实际执行，人工逐条复核；计划操作准确率从 71% 提到 93%（补界面锚点提示与示例轨迹）。阶段二半自动——读取、填表自动执行，最终提交动作保留人工点击；执行环境为独立虚拟机+专用只读账号，全程录屏。

**效果**：单笔处理时间从约 11 分钟降到 3 分钟；因提交必须人工确认，上线至今零资金误操作；步数预算耗尽自动转人工的比例约 6%，构成持续改进的 bad case 池。

### 案例 B：电商运营后台批量改价——界面改版翻车与恢复

**场景**：某电商团队用 CUA 每月批量调整约 500 个 SKU 的价格与库存页签。

**过程**：稳定运行 3 个月后运营后台改版，按钮布局变化；首次执行时每步验证截图与预期不符率飙到 100%，停滞告警 3 分钟内触发，系统自动暂停并降级为人工处理——没有错价上线。随后用新截图重校准定位提示（约 2 人日）恢复运行。

**结果**：结论是「界面改版不是事故而是常态」，可观测告警+降级预案必须作为部署的一部分设计，而不是事后补救。

### 案例 C：跨 4 个系统的客服工单流转——拆任务对抗步级错误累积

**场景**：某物流公司客服工单要在 4 个无 API 系统间查询、回填、流转，单任务平均约 47 步。端到端全自动首月任务成功率仅 68%——正是步级错误累积（单步约 99%，47 步连乘约 62%-68%）。

**改造**：把任务拆成 5 段子任务（查单、核对、填单、校验、流转），每段之间设截图检查点，失败从检查点续跑而非从头重试；跨系统提交动作保留人工确认。

**效果**：任务成功率提升到 91%，平均重试成本下降过半。验证了 4.6 的推论：拆任务+检查点是长任务的唯一解。

## 8. 常见坑

1. **有 API 却硬上 GUI**。  
   CUA 慢、脆、安全面大，是兜底不是首选。先穷尽 API/RPA/导出文件三条路。
2. **跳过每步截图验证**。  
   点错了到第 10 步才发现，只能全部重来。每步验证把错误传染变错误拦截。
3. **危险按钮不设闸**。  
   「删除」「支付」被概率性点中就是事故。白名单+人工确认+录屏三件套缺一不可。
4. **界面改版无告警**。  
   改版后静默点错。验证不符率异常即告警，并预置降级人工预案。
5. **坐标不抗分辨率变化**。  
   截图缩放、DPR 不同导致系统性偏移。统一归一化，必要时用 Set-of-Marks 类辅助定位。
6. **循环无步数与预算上限**。  
   弹窗反复出现导致死循环烧钱。步数+token 双阈值，停滞检测强制终止。
7. **把基准分当生产可靠性**。  
   80% 的单任务成功率在 47 步任务上不剩多少。用自己的任务集做 Shadow 实测。
8. **无 Shadow 期直接上生产**。  
   首日就在真实数据上点按钮。先影子模式复核计划准确率，逐级放行。
9. **执行环境不隔离**。  
   直控员工主机等于把管理员权限交给概率模型。独立 VM/容器+最小权限账号+网络白名单。
10. **不留痕无法审计**。  
    出事答不出「Agent 当时看到了什么、为什么点」。截图+动作+理由逐步落盘，全程录屏。
11. **异常态无处理**。  
    弹窗、验证码、多标签页一出现就卡死。识别已知异常态并定义处理策略，未知态暂停转人工。
12. **长任务无检查点**。  
    第 40 步失败从第 1 步重来。拆子任务+检查点续跑。
13. **凭证权限过大**。  
    用管理员账号跑 GUI Agent。专用账号最小权限，敏感页面不进任务范围。
14. **引用产品格局过期**。  
    还在把 Operator 当独立产品讲。Operator 已并入 ChatGPT Agent；Agent Builder 弃用、Assistants API 2026-08 关停。

## 9. 练习

1. 用 Playwright 写最小循环：截图→由人扮演决策者（打印截图给键盘输入）→执行动作，跑通「打开搜索页搜一个词」。
2. 把决策函数接到任意多模态模型，完成一次静态表单填写，统计 20 次的单步成功率与任务成功率，验证连乘公式。
3. 实现危险词白名单+人工确认闸：构造一个「提交」按钮场景，确认命中时流程挂起。
4. 故意把按钮位置改版（改 CSS），验证「验证不符率」告警能触发。
5. 构造一个会反复弹窗的页面，观察无预算上限的循环行为，然后加步数+停滞检测对比。
6. 同一任务分别用截图感知与 DOM 感知（选择器）实现，对比改版后两者的失效模式差异。
7. 复刻 Shadow 模式：让 Agent 输出计划动作序列而不执行，人工标注 50 步的计划准确率，写一份可靠性边界评估备忘（趋势观察口径：明确说明这是开放讨论题素材而非真题背诵）。
8. 给第 2 题的任务加检查点续跑，对比拆分前后任务成功率与平均重试成本。

## 10. 小结

- 定义：**截图→理解→动作→再截图验证**的循环，鼠标键盘为手、多模态视觉为眼——不依赖 API 驱动任何软件。
- 定位铁律：**有 API 优先 API，RPA 次之，GUI Agent 是最后手段**——价值在补覆盖率，不在替代接口。
- 循环节拍就是 2.5 的 ReAct：截图是 Observation，动作是 Action，验证是纠错与止损的唯一来源。
- 形态两分：**OpenAI 托管产品线（Operator 已并入 ChatGPT Agent）vs Anthropic 能力下放（computer use 工具+自建循环）**。
- 格局剧变（2025-2026）：Operator 2025-08-31 关停并入 ChatGPT Agent；OpenAI 弃用 Agent Builder、Assistants API 2026-08-26 关停——引用案例以最新格局为准。
- 可靠性演进：**15-38%（2025 初，OSWorld）→ 72-89%（2026，含社区口径 89.1% WebVoyager）**——基准分不等于生产可用，口径不可横比。
- 核心数学：**任务成功率=单步成功率连乘**（95%^8≈66%）——拆子任务+检查点是长任务唯一解。
- 部署默认：**监督式而非全自动**——每步可观测+危险动作人工确认+录屏留痕+失败转人工。
- 引入路径：**Shadow 复核计划准确率 → 半自动（提交人工）→ 视数据放开**，界面改版告警与降级预案是部署的一部分。
- 状态口径：**趋势观察**——社区热度高但截至 2026-09 未进确证真题，面试答机制+格局+诚实边界，不吹不贬。
