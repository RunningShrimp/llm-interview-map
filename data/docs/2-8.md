## 1. 定位

Agent 核心层第 8 个知识点，属于「分布式智能协作」。  
它解决两个一体两面的问题：**任务复杂到单 Agent 搞不定时，如何用多个各有所长的 Agent 分工协作？反过来，多 Agent 何时真的优于单 Agent？**（前者是搭建问题，后者是决策问题，4.8 集中回答。）

前置是 2.7 单 Agent 架构模式——多 Agent 中的每个成员，内部仍然是 2.5 讲过的执行循环。  
后续承接：4.6 多 Agent 协作系统（实战）、4.7 生产级 Agent 平台（平台化治理）；评估与安全在 2.9 展开。

## 2. 一句话定义

多 Agent 协作（Multi-Agent Collaboration），是把复杂任务分解给多个具有不同角色、能力、视角的 Agent，通过通信、协商、监督等机制协同完成目标的系统架构。

简化公式：

```text
多 Agent 系统（MAS） = 多个单 Agent + 通信机制 + 协调策略 + 共享状态
```

## 3. 为什么需要

单 Agent 的局限：

- **上下文窗口有限** → 一个 Agent 塞不下所有信息，检索噪声还会挤占有效上下文。
- **能力单一** → 一个 Prompt 难以同时擅长检索、分析、写作多个领域。
- **视角单一** → 一个 Agent 容易陷入思维定势，自己很难发现自己的错。
- **无法并行** → 串行执行，三个独立子任务也要排队跑。
- **难以分工** → 复杂任务需要不同专业角色，单 Prompt 反复切换角色会互相干扰。
- **单点故障** → 一个 Agent 挂了，整个任务失败。
- **无法辩论** → 没有对立视角，错误结论缺乏被挑战的机会。

多 Agent 的价值：

| 优势 | 说明 |
|---|---|
| 分工 | 不同 Agent 负责不同子任务，职责单一 |
| 专业化 | 每个 Agent 有专属 Prompt 和工具，上下文干净 |
| 并行 | 独立子任务同时执行，延迟取决于最慢的一个 |
| 多视角 | 不同 Agent 提供不同观点，减少单一偏见 |
| 制衡 | 监督 Agent 检查执行 Agent，生成与审查分离 |
| 容错 | 一个失败，其他可接管或重试 |

类比：

```text
单 Agent = 一人设计工作室：老板什么都会一点，接大单时文案、设计、
           投放全靠自己，每个环节都在切换角色，越忙越乱。
多 Agent = 一个小团队：文案、设计、投放各一人，各干各的，
           最后由项目经理拼成完整交付物——快，但要付协调成本。
```

代价先说清楚：多 Agent 的调用次数、延迟、调试复杂度都成倍增长。它不是「更多 Agent = 更强」的免费升级，而是为特定瓶颈付出的结构成本——什么时候值得，4.8 集中回答。

## 4. 核心原理

### 4.1 多 Agent 的核心要素

```text
┌──────────────────────────────────────────┐
│           多 Agent 系统                   │
│                                          │
│  ┌────────┐  ┌────────┐  ┌────────┐     │
│  │ Agent1 │  │ Agent2 │  │ Agent3 │     │
│  │ 角色A  │  │ 角色B  │  │ 角色C  │     │
│  └───┬────┘  └───┬────┘  └───┬────┘     │
│      │           │           │           │
│      └───────────┼───────────┘           │
│                  ↓                       │
│         ┌────────────────┐               │
│         │  通信与协调层   │               │
│         └────────────────┘               │
│                  ↓                       │
│         ┌────────────────┐               │
│         │  共享状态/记忆  │               │
│         └────────────────┘               │
└──────────────────────────────────────────┘
```

| 要素 | 说明 | 设计问题 |
|---|---|---|
| 角色 | 每个 Agent 的职责和专长 | 谁负责什么、不负责什么 |
| 通信 | Agent 之间如何传递信息 | 传什么、怎么传、传给谁 |
| 协调 | 谁决定谁做什么 | 集中调度还是自主协商 |
| 共享状态 | 共同维护的上下文 | 存什么、怎么解决并发写 |
| 终止 | 何时认为任务完成 | 谁有权宣布结束 |

### 4.2 六种协作范式

**范式 1：流水线（Pipeline）**

```text
Agent A → Agent B → Agent C → 输出
```

每个 Agent 负责一个阶段，串行传递。

- 优点：简单、可控、每段可独立测试。
- 缺点：无法并行，上一段卡住下一段全部等待。
- 适用：文档处理、ETL、代码生成流水线。

**范式 2：分工并行（Parallelization）**

```text
         ┌─ Agent A ─┐
输入 ────┼─ Agent B ─┼──→ 汇总 Agent → 输出
         └─ Agent C ─┘
```

多个 Agent 同时处理不同子任务，最后汇总。

- 优点：快（延迟取决于最慢分支），天然多视角。
- 缺点：需要汇总逻辑，分支结果可能冲突。
- 适用：多源检索、多角度分析、批量处理。

**范式 3：辩论（Debate）**

```text
Agent A ←→ Agent B ←→ Agent C
   ↓          ↓          ↓
        裁决 Agent
           ↓
         输出
```

多个 Agent 提出观点，互相攻击对方论证，裁决者选最优。

- 优点：强制暴露反例，减少单一偏见。
- 缺点：成本高，可能无法收敛。
- 适用：复杂决策、事实核查、高风险方案评审。

**范式 4：监督（Supervisor，主管模式）**

```text
        ┌──────────────┐
        │  Supervisor  │
        │   （主管）    │
        └──────┬───────┘
               │ 分配任务
     ┌─────────┼─────────┐
     ↓         ↓         ↓
  Worker A  Worker B  Worker C
     │         │         │
     └─────────┼─────────┘
               ↓
          汇总结果
```

一个 Supervisor 决定谁做什么，Worker 执行并回报。类比：装修工地的项目经理——水电工、瓦工、木工各干各的，项目经理决定今天谁进场、验收谁的活；没有项目经理的工地，工人互相等对方先干。

- 优点：集中控制，按需动态调度。
- 缺点：Supervisor 是瓶颈和单点。
- 适用：任务分发、动态调度（生产环境最常用的拓扑）。

**范式 5：层级（Hierarchical）**

```text
              Manager
             /       \
        Team Lead A  Team Lead B
        /    \          /    \
    W1      W2      W3      W4
```

多层管理，每层主管只管自己的下属，逐层上报。

- 优点：可扩展，单层复杂度可控。
- 缺点：通信开销随层数放大，底层信息传到顶层已失真。
- 适用：大型任务、组织模拟。

**范式 6：群体（Swarm，群智协作）**

```text
Agent A ←→ Agent B ←→ Agent C
   ↕          ↕          ↕
Agent D ←→ Agent E ←→ Agent F
```

所有 Agent 平等，按规则自由通信，控制权通过交接（Handoff）在成员间流转。

- 优点：灵活，可能涌现出设计外的协作行为。
- 缺点：难控制、难调试、难追责。
- 适用：研究、社会模拟。

**范式对比（含拓扑属性）**：

| 范式 | 拓扑 | 控制权 | 并行度 | 成本 | 主要失败面 | 适用 |
|---|---|---|---|---|---|---|
| 流水线 | 链式 | 集中 | 低 | 低 | 单点阻塞 | 顺序任务 |
| 分工并行 | 扇出-汇聚 | 集中 | 高 | 中 | 汇总冲突 | 独立子任务 |
| 辩论 | 网状+裁决 | 分散 | 中 | 高 | 不收敛 | 决策、核查 |
| 监督 | 星型 | 集中 | 高 | 中高 | 主管瓶颈 | 动态调度 |
| 层级 | 树型 | 分层 | 高 | 高 | 层间失真 | 大型任务 |
| 群体 | 全连接 | 分散 | 高 | 高 | 不可控 | 研究、模拟 |

按控制权归类只有三种拓扑：**中心化**（监督、层级、流水线——有唯一或分层决策点）、**去中心化**（辩论、群体——成员平等协商）、**汇聚式**（分工并行——扇出后必须有一个汇聚点）。先选拓扑，再定范式。

### 4.3 角色设计

**常见角色**：

| 角色 | 职责 | Prompt 要点 |
|---|---|---|
| Planner | 分解任务、制定计划 | 擅长拆解、逻辑 |
| Researcher | 检索信息 | 擅长搜索、注明来源 |
| Executor | 执行操作 | 擅长工具调用 |
| Critic | 审查输出 | 严格、专找问题 |
| Supervisor | 协调调度 | 全局视角 |
| Summarizer | 汇总结果 | 擅长整合 |
| Domain Expert | 领域专长 | 专业知识 |

**角色设计原则**：

- **职责单一**：一个 Agent 只做一件事，角色越多越乱。
- **边界清晰**：知道什么该做、什么该转交别人。
- **能力匹配**：角色需要什么工具就配什么，不多配。
- **Prompt 差异化**：不同角色用不同 System Prompt，语气和关注点分开。

**示例**：

```python
ROLES = {
    "planner": {
        "system": "你是一个任务规划专家。把复杂目标分解为可执行步骤。",
        "tools": [],
    },
    "researcher": {
        "system": "你是一个研究员。根据问题检索信息，返回事实和来源。",
        "tools": ["search_web", "search_docs"],
    },
    "executor": {
        "system": "你是一个执行者。按计划调用工具完成任务。",
        "tools": ["search_orders", "refund", "send_email"],
    },
    "critic": {
        "system": "你是一个严格的审查员。找出输出中的错误、遗漏、不合理之处。",
        "tools": [],
    },
}
```

### 4.4 通信机制

**方式 1：共享状态（Shared State）**

所有 Agent 读写同一个状态对象：

```python
class SharedState:
    def __init__(self):
        self.goal = None
        self.plan = []
        self.results = {}   # 各任务结果，按任务 ID 索引
        self.messages = []  # 简化版消息历史
        self.artifacts = {} # 中间产物（代码、草稿、数据表）
```

- 优点：简单，所有 Agent 看到同一份事实。
- 缺点：并发写冲突；状态变大后每个 Agent 的上下文都被拖累。
- 适用：小规模、同进程。

**方式 2：消息传递（Message Passing）**

Agent 之间点对点或经总线发消息：

```python
class Message:
    def __init__(self, sender: str, receiver: str, content: str, msg_type: str):
        self.sender = sender
        self.receiver = receiver
        self.content = content
        self.type = msg_type  # request / response / notify
        self.timestamp = time.time()
```

- 优点：解耦，可异步、可跨进程；天然留下通信日志。
- 缺点：需要消息队列与投递保证，链路长后难追踪。
- 适用：大规模、跨服务。

**方式 3：黑板（Blackboard）**

所有 Agent 按契约读写同一块结构化区域，写操作触发通知：

```python
class Blackboard:
    def __init__(self):
        self.data = {}
        self.subscribers = []  # 订阅者：谁关心哪些 key 的变更

    def write(self, key: str, value):
        self.data[key] = value
        self._notify(key, value)  # 通知订阅该 key 的 Agent

    def read(self, key: str):
        return self.data.get(key)
```

类比：办公室的白板——谁都可以上来写自己负责的那一格，路过的人看到更新就接着干自己的部分，不需要两两开会。

- 优点：灵活，适合松散协作。
- 缺点：写入契约不严格时难以追踪谁改了什么。
- 适用：复杂协作、中间产物多。

**通信机制对比**：

| 维度 | 共享状态 | 消息传递 | 黑板 |
|---|---|---|---|
| 耦合度 | 高（共享同一对象） | 低（只认消息） | 中（共享契约） |
| 一致性 | 强，但有并发冲突 | 最终一致 | 取决于契约 |
| 可扩展性 | 差（锁竞争） | 好（跨进程） | 中 |
| 可观测性 | 差（改了不知道） | 好（消息即日志） | 中（需变更通知） |
| 适用规模 | 单进程小团队 | 大规模、跨服务 | 中等、产物驱动 |

### 4.5 协调策略

**策略 1：集中式（Centralized，Supervisor 调度）**

```python
class Supervisor:
    async def run(self, goal: str):
        plan = await self.plan(goal)              # 1. 拆解目标
        for task in plan:
            worker = self.select_worker(task)     # 2. 按任务选人
            result = await worker.execute(task)   # 3. 派发并等待
            self.state.results[task.id] = result  # 4. 收集结果
        return self.aggregate(self.state.results) # 5. 汇总输出
```

**策略 2：去中心式（Decentralized，Peer-to-Peer 对等协商）**

```python
class PeerAgent:
    async def run(self, goal: str):
        while not self.done:
            message = await self.receive()          # 等任何同伴的消息
            if message.type == "request":
                result = await self.handle(message) # 自己能办就办
                await self.send(message.sender, result)
            elif message.type == "result":
                self.state.update(message.content)  # 同伴的进展也进我的状态
```

**策略 3：市场式（Market-Based，竞标分配）**

```python
class Market:
    def assign(self, task):
        bids = [(agent, agent.bid(task)) for agent in self.agents]
        # 每个 Agent 按能力、成本、预计耗时出价，取综合最优
        return min(bids, key=lambda x: x[1].cost)
```

### 4.6 终止条件

多 Agent 的终止在单 Agent 终止机制（最大步数、超时、循环检测，见 2.5）之上，多了「轮（Round）」的概念：一轮 = 主管分配 + 工人执行 + 状态更新，熔断必须挂在轮级别，而不是单个 Agent 的步级别。

| 终止条件 | 说明 | 类型 |
|---|---|---|
| 目标完成 | 主管或裁决者判定目标达成 | 业务判定 |
| 最大轮数 | 防协作死循环的硬上限 | 硬熔断 |
| 预算超限 | 多 Agent 是成本放大器，必须设总预算 | 硬熔断 |
| 无进展 | 连续 N 轮没有新结果产生，判定空转 | 软检测 |
| 共识达成 | 辩论模式专用：多数方收敛或裁决者叫停 | 业务判定 |

### 4.7 多 Agent 的失败模式

| 失败 | 原因 | 解法 |
|---|---|---|
| 无限循环 | 无终止条件 | 最大轮数 |
| 通信爆炸 | 消息太多 | 限制通信拓扑 |
| 责任不清 | 角色重叠 | 明确职责 |
| 互相推诿 | 无协调者 | 加 Supervisor |
| 成本失控 | 多 Agent 多调用 | 预算限制 |
| 无法收敛 | 辩论无终点 | 裁决机制 |
| 状态冲突 | 并发写 | 锁 / 版本控制 |
| 信息丢失 | 消息丢失 | 持久化消息 |
| 单点故障 | Supervisor 挂了 | 冗余 / 降级 |
| 调试困难 | 轨迹复杂 | 全链路 trace |

### 4.8 何时真的优于单 Agent（关键问题）

**面试高频问法**：「多 Agent 什么时候真的优于单 Agent？协调开销和错误放大怎么权衡？」

先给共识口径：**多数场景，单 Agent + 一组趁手的工具已经够用。** LangChain 官方博客《How and when to build multi-agent systems》（2025）明确列了「什么时候不该用多 Agent」；业界默认答案是先单 Agent，遇到下面四条判据中的明确瓶颈，再考虑拆。

**判据 1：可并行性。** 子任务相互独立且各自耗时（数十秒以上），并行收益明显大于协调开销（拆分、派发、汇总的额外调用）。三个 20 秒的检索并行跑，延迟 20 秒而非 60 秒——值得；三个 2 秒的查询并行，协调本身可能比查询还贵。

**判据 2：上下文隔离需求。** 两种情况：一是任务所需信息总量超出单上下文窗口；二是不同职责需要「干净上下文」——研究员翻到的几十条检索噪声，不该跟着进写作者的上下文。子 Agent 干完活只把结论带回，等价于一次上下文压缩。类比：律所的案件卷宗——总卷宗太厚没人读得完，按专长拆给不同律师各读一册，每人只交一页摘要汇入总目录，子 Agent 就是那册分卷。

**判据 3：制衡需求。** 生成者和审查者必须是两个独立上下文。「自己检查自己」会把同一个偏见原样带进审查——生成时漏掉的边界条件，自检时大概率还是看不见。Tester / Reviewer / Critic 的价值正来自上下文分离，而不只是多跑一次模型。

**判据 4：成本收益为正（成本阈值）。** 多 Agent 的代价是三重的：调用次数成倍增长（协调本身也要调模型）；延迟叠加（汇总要等最慢分支）；错误沿通信链放大——单步成功率 95% 的组件，串到第 8 次交互，端到端只剩约 66%（复合失败率直觉，详见 2.9）。多 Agent 每加一条通信边就多一条错误放大路径。收益覆盖不了这些成本，就不该上。

**读写准则**：Phil Schmid《Single vs Multi-Agent System?》（2025）给出简明判据——**读多写少的任务（检索、总结、问答）用单 Agent；重写入、复杂流水线、需要并行改多个系统时，才考虑多 Agent。** 原因：写操作的冲突协调成本远高于读，多 Agent 提供的隔离与分工恰好对冲这部分成本。另有实证研究（论文《Single-agent or Multi-agent Systems? Why Not Both?》，arXiv:2505.18286，2025）对比单 Agent 系统（Single-Agent System, SAS）与多 Agent 系统（MAS）在问答类基准上的表现，结论同样是「并非多者恒胜」，两者各有优势区间。

**面试高频追问**：「为什么用子 Agent，而不是把能力做成 Tool？」——Tool 只复用能力，不提供隔离：调用的一切中间结果都堆在同一个上下文里。子 Agent 提供独立上下文、独立循环、独立轨迹，干完只返回摘要。判据：只需要「能力」（查个价格、发封邮件）就做成 Tool；需要「一整套工作过程」（完整调研、反复试错的编码）才拆成子 Agent。

**单 Agent vs 多 Agent 决策表**：

| 判断维度 | 倾向单 Agent | 倾向多 Agent |
|---|---|---|
| 任务结构 | 单线流程，一步接一步 | 可分解为独立子任务 |
| 上下文 | 信息塞得下且互不干扰 | 超窗，或职责间需上下文隔离 |
| 耗时分布 | 串行总时长可接受 | 子任务各自数十秒以上，并行收益大 |
| 质量机制 | 自检 + 重试即可 | 需独立审查 / 辩论等制衡 |
| 读写比例 | 读多写少 | 重写入、多系统协同改状态 |
| 成本敏感度 | 高（接受不了数倍调用） | 可用 2-5 倍成本换质量与延迟 |

**决策树**：

```text
单 Agent 能完成吗？
├─ 能 → 用单 Agent
└─ 不能 → 瓶颈在哪？
    ├─ 上下文不够 → 多 Agent 上下文隔离
    ├─ 能力单一 → 多 Agent 专业化
    ├─ 串行太慢 → 多 Agent 并行
    ├─ 单视角易错 → 多 Agent 辩论 / 制衡
    └─ 只是任务定义不清 → 回去改 Prompt 和工具，别拆 Agent
```

**工程建议**：

> **先单 Agent，遇到四判据中的明确瓶颈再上多 Agent。**  
> 多 Agent 是为特定瓶颈付出的复杂度代价，不是默认选择。

### 4.10 多 Agent 与单 Agent 的关系

```text
单 Agent 是基础，多 Agent 是扩展。
多 Agent 中的每个 Agent 都是一个完整的单 Agent（循环 + 工具 + 记忆）。
多 Agent 的挑战不在单个 Agent，而在协调——通信、状态、终止、追责。
```

## 5. 架构 / 流程

一个监督模式的完整多 Agent 系统，一轮典型执行流：

```text
┌──────────────────────────────────────────┐
│  用户目标                                 │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  Supervisor Agent（唯一决策点）           │
│  ├─ 理解目标、读当前进展                  │
│  ├─ 分解出本轮任务                        │
│  ├─ 选择 Worker（可多选，并行派发）       │
│  └─ 检查终止条件（轮数/预算/完成）        │
└──────────────────────────────────────────┘
                  ↓
     ┌────────────┼────────────┐
     ↓            ↓            ↓
┌─────────┐  ┌─────────┐  ┌─────────┐
│ Worker1 │  │ Worker2 │  │ Worker3 │
│ 研究员  │  │ 分析师  │  │ 写作者  │
│ 独立上下│  │ 独立上下│  │ 独立上下│
└────┬────┘  └────┬────┘  └────┬────┘
     │            │            │
     └────────────┼────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  共享状态 / 黑板                          │
│  ├─ 任务状态（谁在干什么）                │
│  ├─ 中间结果（只存结论，不存过程噪声）    │
│  └─ 消息历史（可追溯）                    │
└──────────────────────────────────────────┘
                  ↓  回到 Supervisor（下一轮或收尾）
┌──────────────────────────────────────────┐
│  Supervisor 汇总                          │
│  ├─ 检查完整性（有没有缺口）              │
│  ├─ 解决冲突（多来源结论打架）            │
│  └─ 生成最终输出                          │
└──────────────────────────────────────────┘
```

要点：Supervisor 是唯一决策点，Worker 之间不直接通信（星型拓扑）；Worker 之间需要交换的信息一律经共享状态中转，这让全链路追踪只需要盯住「Supervisor 决策 + 状态变更」两类事件。

## 6. 代码 / 工具

### 6.1 监督模式最小实现

```python
import asyncio
import json
from openai import AsyncOpenAI

client = AsyncOpenAI(api_key="YOUR_KEY")

class WorkerAgent:
    """工人 Agent：只接收任务描述和必要上下文，独立完成，返回文本结果。"""
    def __init__(self, name: str, system_prompt: str):
        self.name = name
        self.system_prompt = system_prompt

    async def execute(self, task: str, context: str = "") -> str:
        messages = [
            {"role": "system", "content": self.system_prompt},
            {"role": "user", "content": f"上下文：{context}\n\n任务：{task}"},
        ]
        response = await client.chat.completions.create(
            model="gpt-4o-mini", messages=messages, temperature=0.3,
        )
        return response.choices[0].message.content

class SupervisorAgent:
    """主管 Agent：循环「规划 → 并行派发 → 更新状态 → 检查完成」。"""
    def __init__(self, workers: dict[str, WorkerAgent], max_rounds: int = 5):
        self.workers = workers
        self.max_rounds = max_rounds  # 轮级熔断（4.6）
        self.state = {"results": {}}

    async def run(self, goal: str) -> dict:
        for _ in range(self.max_rounds):
            next_tasks = await self._plan_next(goal)   # 1. 本轮任务
            if not next_tasks:
                break                                   # 主管判定无事可做
            coros = []                                  # 2. 并行派发
            for task in next_tasks:
                worker = self.workers.get(task["worker"])
                if worker:
                    coros.append(worker.execute(
                        task["description"], json.dumps(
                            self.state["results"], ensure_ascii=False)))
            results = await asyncio.gather(*coros, return_exceptions=True)
            for task, result in zip(next_tasks, results):
                if not isinstance(result, Exception):   # 3. 更新状态
                    self.state["results"][task["id"]] = result
        return await self._aggregate(goal)              # 4. 汇总输出

    async def _plan_next(self, goal: str) -> list:
        prompt = f"""你是主管。根据目标和当前进展，决定本轮分配哪些任务。

目标：{goal}
已完成：{json.dumps(self.state['results'], ensure_ascii=False)}
可用 Worker：{list(self.workers.keys())}

输出 JSON：{{"tasks": [{{"id": "...", "worker": "...", "description": "..."}}]}}
任务全部完成时 tasks 为空数组。"""
        response = await client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            response_format={"type": "json_object"},  # 强制 JSON 输出
            temperature=0,
        )
        data = json.loads(response.choices[0].message.content)
        return data.get("tasks", [])

    async def _aggregate(self, goal: str) -> dict:
        prompt = f"根据以下结果回答目标。\n目标：{goal}\n结果：{json.dumps(self.state['results'], ensure_ascii=False)}"
        response = await client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            temperature=0.3,
        )
        return {"answer": response.choices[0].message.content, "state": self.state}

# 组装：3 个 Worker + 1 个 Supervisor
workers = {
    "researcher": WorkerAgent("researcher", "你是研究员，负责检索和总结信息。"),
    "analyst": WorkerAgent("analyst", "你是分析师，负责数据分析和推理。"),
    "writer": WorkerAgent("writer", "你是写作者，负责撰写报告。"),
}
supervisor = SupervisorAgent(workers)
result = await supervisor.run("调研 AI Agent 市场并写一份报告")
```

### 6.2 辩论模式实现

```python
class DebateAgent:
    def __init__(self, name: str, position: str):
        self.name = name
        self.position = position  # 立场：支持 / 反对

    async def argue(self, topic: str, history: list) -> str:
        prompt = f"""你是辩论者 {self.name}，立场：{self.position}。

主题：{topic}
历史发言：
{chr(10).join(f"{h['name']}: {h['content']}" for h in history)}

请发表你的观点，必须回应对方上一轮的论点（200 字以内）："""
        response = await client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            temperature=0.7,  # 辩论方要发散，温度调高
        )
        return response.choices[0].message.content

class JudgeAgent:
    async def judge(self, topic: str, history: list) -> str:
        prompt = f"""你是裁决者。根据以下辩论给出最终结论，必须指出双方各哪些论点成立。

主题：{topic}
辩论：
{chr(10).join(f"{h['name']}: {h['content']}" for h in history)}"""
        response = await client.chat.completions.create(
            model="gpt-4o",  # 裁决用更强的模型，温度 0 求稳定
            messages=[{"role": "user", "content": prompt}],
            temperature=0,
        )
        return response.choices[0].message.content

async def debate(topic: str, rounds: int = 3) -> str:
    debaters = [DebateAgent("正方", "支持"), DebateAgent("反方", "反对")]
    history = []
    for _ in range(rounds):              # 固定轮数 = 收敛保证（4.6）
        for debater in debaters:
            argument = await debater.argue(topic, history)
            history.append({"name": debater.name, "content": argument})
    return await JudgeAgent().judge(topic, history)

result = await debate("公司该不该自建多 Agent 客服系统？")
```

### 6.3 并行分工模式

```python
async def parallel_research(topic: str) -> str:
    # 三个研究员并行检索不同来源，互不依赖
    researchers = [
        WorkerAgent("web", "只搜索网页信息，返回要点和来源。"),
        WorkerAgent("papers", "只搜索学术论文，返回结论和出处。"),
        WorkerAgent("news", "只搜索近期新闻，返回事件和时间线。"),
    ]
    results = await asyncio.gather(
        *[r.execute(f"调研：{topic}") for r in researchers]
    )  # 延迟取决于最慢的一个，而不是三者之和

    # 汇总：单独一个 Agent 做整合，上下文只进结论不进噪声
    summarizer = WorkerAgent("summarizer", "整合多源信息，标注冲突之处。")
    combined = "\n\n".join(
        f"来源 {r.name}：\n{res}" for r, res in zip(researchers, results))
    return await summarizer.execute(f"整合以下调研结果：\n{combined}")
```

### 6.5 用 LangGraph 实现监督拓扑（图编排）

```python
from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Annotated
import operator

class MultiAgentState(TypedDict):
    messages: Annotated[list, operator.add]  # 消息按追加合并
    next_agent: str
    task: str
    results: dict

def supervisor_node(state: MultiAgentState):
    # 唯一决策点：决定下一个执行的 Agent（或结束）
    return {"next_agent": decide_next(state)}

def researcher_node(state: MultiAgentState):
    result = researcher_agent(state["task"])
    return {"results": {**state["results"], "research": result},
            "messages": [result]}

def analyst_node(state: MultiAgentState):
    result = analyst_agent(state["results"].get("research", ""))
    return {"results": {**state["results"], "analysis": result},
            "messages": [result]}

def writer_node(state: MultiAgentState):
    result = writer_agent(state["results"])
    return {"results": {**state["results"], "report": result},
            "messages": [result]}

graph = StateGraph(MultiAgentState)
graph.add_node("supervisor", supervisor_node)
graph.add_node("researcher", researcher_node)
graph.add_node("analyst", analyst_node)
graph.add_node("writer", writer_node)

# 截至 2026 年的推荐写法：START 显式连边（set_entry_point 已废弃）
graph.add_edge(START, "supervisor")
graph.add_conditional_edges("supervisor", lambda s: s["next_agent"], {
    "researcher": "researcher",
    "analyst": "analyst",
    "writer": "writer",
    "end": END,
})
graph.add_edge("researcher", "supervisor")  # 每个 Worker 干完回到主管
graph.add_edge("analyst", "supervisor")
graph.add_edge("writer", "supervisor")

app = graph.compile()  # 需要中断恢复时挂 checkpointer，见 2.5
```

## 7. 案例

### 案例 A：市场调研报告（监督模式）

**目标**：「调研 AI Agent 市场并写一份报告。」

**架构**：Supervisor + Researcher / Analyst / Writer（星型拓扑，Worker 并行）。

**做法**：Supervisor 先派 Researcher 三路并行检索（网页、论文、新闻），只回结论；再派 Analyst 基于结论做趋势分析；最后派 Writer 成稿，Supervisor 检查完整性后输出。

**示意数字**（复盘口径）：单 Agent 基线约 6 次模型调用、端到端约 25 分钟（串行检索逐个来，检索噪声全程占着上下文）；多 Agent 版约 18 次调用、成本约 3 倍，但检索三路并行，端到端降到约 9 分钟，报告覆盖维度从 4 个增加到 9 个，5 人盲评 4 人认为多 Agent 版更好。结论：质量与延迟收益明确，代价是成本 3 倍——高频调用要慎重，低频深度报告值得。

### 案例 B：代码生成流水线（制衡模式）

**目标**：「实现一个用户登录功能。」

**架构**：流水线 Planner → Coder → Tester → Reviewer。

**做法**：Planner 拆出接口与测试用例清单；Coder 按清单实现；Tester 写测试并实际运行，失败信息回传 Coder 修复；Reviewer 独立审查边界条件与安全问题，通过才交付。

**示意数字**：引入 Tester + Reviewer 后，一次通过率从约 55% 提升到约 78%，增量主要来自 Tester 拦截的接口错用和 Reviewer 拦截的边界条件遗漏；总成本约增加 40%（多了测试与审查两段）。这正是 4.8 判据 3 的价值：审查者与生成者上下文分离，看见了生成者自己看不见的问题。

### 案例 C：重大决策辩论（辩论模式）

**目标**：「公司该不该进入 AI Agent 市场？」

**架构**：正方 Agent + 反方 Agent + 裁决 Agent，固定 3 轮。

**做法**：正方列机会与先发优势，反方必须逐条回应并补风险，3 轮后裁决 Agent 综合双方成立论点，给出条件性结论。

**示意数字**：单 Agent 起草的同题分析列出风险 5 条；3 轮辩论把风险清单逼到 11 条（反方专门负责找反例），最终结论为「满足两个前提才进入」。成本约为单 Agent 问答的 5 倍——这类季度级决策一年做不了几次，贵一点值得；日常任务用不上这个配置。

## 8. 常见坑

1. **过早多 Agent**。  
   单 Agent 能搞定的任务上了多 Agent，成本翻倍、质量不变。先单后多，对照 4.8 四判据再拆。

2. **角色重叠**。  
   两个 Agent 做同样的事，互相等待、重复产出。每个角色一句话说清「只做什么、不做什么」。

3. **通信爆炸**。  
   所有 Agent 互相通信，消息数随成员数平方增长。限制拓扑：优先星型，Worker 间不直连。

4. **无终止条件**。  
   辩论无限进行、主管反复派发同一任务，成本失控。最大轮数 + 总预算双熔断。

5. **Supervisor 瓶颈与单点**。  
   所有决策都过 Supervisor，延迟堆积；Supervisor 一挂全系统停摆。可并行的任务批量派发，关键路径做冗余或降级。

6. **状态冲突**。  
   多 Agent 并发写同一状态，后写覆盖先写。共享状态加锁或版本控制，或改为消息传递。

7. **调试困难**。  
   多 Agent 轨迹交织，出问题不知道是哪个 Agent 的错。全链路 trace：每个 Agent 的输入、输出、耗时全部落盘。

8. **成本失控**。  
   多 Agent 调用次数是单 Agent 的数倍，无人看账。设总预算，超限即停并报告已花费金额。

9. **辩论无法收敛**。  
   双方各说各话，永远达不成共识。固定轮数 + 独立裁决者，轮数到即裁决。

10. **信息丢失**。  
    Agent 之间传消息，中间结果没有持久化，重跑全丢。消息与中间产物全部持久化。

11. **把该做成 Tool 的能力拆成子 Agent**。  
    查个价格也起一个子 Agent，上下文开销白白翻倍。只借能力用 Tool，要隔离过程才用子 Agent（见 4.8）。

12. **不评估就上线**。  
    不知道多 Agent 是否真的比单 Agent 好，凭感觉拆。同一任务 A/B 对比成本、延迟、质量，拿数字说话。

13. **框架锁定**。  
    深度绑定某个框架的私有抽象，难以迁移。业务层用自有接口包住框架，3.3 的选型方法定期复核。

14. **忽略权限隔离**。  
    所有 Agent 共享全套工具权限，一个被注入就全线失守。每个 Agent 最小权限：Researcher 只读，Executor 才有写权限（安全细节见 2.9）。

7. 分别用共享状态和消息传递实现同一协作任务。验收标准：对比两者的实现复杂度与一致性风险，写出各适用什么规模。
8. 选一个任务同时跑单 Agent 与多 Agent，记录成本、延迟、质量（人工盲评）。验收标准：得出「该不该拆」的量化结论，而不是印象。
9. 设计一个多 Agent 客服系统：分类 → 处理 → 审查 → 升级。验收标准：退款类高风险工单必经审查节点，审查不通过可升级人工。
10. 实现全链路 trace：记录每个 Agent 的输入、输出、耗时、token 消耗。验收标准：只看 trace 就能复原一次完整协作过程并定位失败环节。

## 10. 小结

- 多 Agent = **多个单 Agent + 通信 + 协调 + 共享状态**；每个成员内部仍是 2.5 讲的执行循环。
- 六种范式：**流水线、分工并行、辩论、监督、层级、群体**；按控制权归为**中心化、去中心化、汇聚式**三类拓扑。
- 五要素：**角色、通信、协调、共享状态、终止**；先定拓扑，再定范式，最后配角色。
- 角色设计四原则：**职责单一、边界清晰、能力匹配、Prompt 差异化**。
- 通信三式：**共享状态、消息传递、黑板**——小规模共享状态，大规模消息传递，产物驱动用黑板。
- 协调三策：**集中式、去中心式、市场式**；生产环境默认从集中式（监督模式）起步。
- 何时真的优于单 Agent：**可并行、需上下文隔离、需制衡、成本收益为正**，四条判据逐一过；默认口径是「多数场景单 Agent + 工具已够」，读多写少不拆、重写入复杂流水线才拆。
- 关键工程：**轮级终止条件、总预算、状态一致性、全链路 trace**；每个 Agent 最小权限。
- 核心原则：**先单后多；多 Agent 的挑战在协调，不在单个 Agent。**
- 这些能力直接支撑：4.6 多 Agent 协作系统、4.7 生产级 Agent 平台。
