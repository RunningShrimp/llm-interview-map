# 讲解 2.8 多 Agent 协作

> 说明：2.7 讲完了单 Agent 的四种架构，本篇回答下一步：**什么时候、以及怎么把一个大脑拆成一支团队**——角色分工、结构化通信、监督评审。  
> 「值不值得拆」的判据与代价账本在 2.8b（Anthropic 三条件、15× token）；跨厂商互操作要等 H5 A2A 协议；实战落地在 4.6/4.7。

---

## 1. 定位

S5 关卡的入口。前置是整个单 Agent 体系：2.7 四大架构模式（每个子 Agent 脑子里跑的正是单 Agent 架构）、2.4 记忆（子 Agent 的独立上下文）、2.5 执行循环、2.6 反思。

它回答两个问题：

1. **怎么搭**：主管-工人、流水线、辩论三种协作模式，加上通信与监督的工程纪律。
2. **该不该搭**：多 Agent 是放大器不是替代品——协调开销与错误放大随时可能吃掉并行收益（正面回答在 2.8b）。

后续走向：2.8b 给三条件判据与 15× token 账本；4.6 多 Agent 协作系统实战；4.7 平台化治理；H5 A2A 协议解决跨厂商互操作。

## 2. 一句话定义

多 Agent 协作是把任务交给一支「AI 团队」：**主管（Supervisor）拆活分任务，工人（Worker）分头干，靠结构化消息（格式固定的工单）通信，最后由主管或独立评审把关汇总**——每个成员内部仍是 2.7 的单 Agent 架构，多 Agent 把它放大成一支团队。

拆分的两个正当动机：

1. **上下文隔离**：每个子 Agent 有独立上下文窗口，各自只扛自己那一段，避免单窗口被中间步骤挤爆。
2. **并行加速**：相互独立的子任务分头开工，墙钟时间按并行度下降。

## 3. 为什么需要

单 Agent 有两个结构性上限：

1. **上下文装不下**：一个 Agent 读 100 份文档再写报告，中间过程会把上下文撑爆——lost-in-the-middle（1.5）让中间关键信息被忽略。
2. **串行跑不完**：可并行的任务被一个 Agent 按顺序做，时间与 token 双浪费。

但多 Agent 不是免费午餐，三笔新账：

| 账目 | 内容 | 量级 |
|---|---|---|
| 协调开销 | 拆单、通信、验收都要过模型 | token 成倍增加 |
| 错误放大 | 一个子 Agent 的错误结论被主管当真采信 | 错误顺流而下成为「事实」 |
| 工程复杂度 | 消息格式、失败兜底、trace 归因 | 开发与调试成本显著上升 |

结论先行：**默认单 Agent；先有明确的并行收益与隔离需求，再上多 Agent。**

## 4. 核心原理

### 4.1 模式一：主管-工人（Supervisor-Worker）

一个大脑拆单、多个工人并行执行、主管验收汇总。类比装修队长：看图纸把活拆成水电、瓦工、油漆，工人分头进场，每晚交工单，队长验收。

- 甜点区：任务可拆、子任务相互独立——多路资料搜集、批量摘要、多文件调研。
- 关键：**拆单质量决定全局**。拆得含糊，工人各干各的，最后拼不到一起。
- 翻车点：多个工人同时改一份稿（写入冲突，互相覆盖）；拆单缺交付标准导致汇总失败。

### 4.2 模式二：流水线（Pipeline）

上一站的产出就是下一站的原料：调研→初稿→配图→校对，像传送带逐站加工。类比汽车装配线。

- 甜点区：工序固定的一条龙生产，每站职责单一、易测易换。
- 翻车点：传送带不回头——**上游错误顺流而下、越滚越大**；中途要返工等于整条线倒带。
- 对策：每站出口加校验闸门（2.6 的验证器思想），不合格就地打回，不带病下传。

### 4.3 模式三：辩论（Debate）

多个 Agent 各自给方案，互相挑刺，裁判汇总拍板。类比三方会审。

- 甜点区：没有标准答案的判断题——方案评审、事实核查、风险把关，多角度互评能逼出单视角盲点。
- 翻车点：**人数 × 轮次让 token 成倍烧**；可能吵半天谁也不服谁，还得裁判兜底。
- 对策：限定辩论轮数（通常 1-3 轮）、裁判 Prompt 要求给出结论而非「各有道理」。

三模式对比：

| 维度 | 主管-工人 | 流水线 | 辩论 |
|---|---|---|---|
| 结构 | 星型（主管居中） | 链型（逐站接力） | 网状（互评后裁决） |
| 通信方向 | 双向（下发/回传） | 单向（只传下一站） | 多向（互评） |
| 适用任务 | 可拆且子任务独立 | 工序固定 | 无标准答案的判断 |
| 通信成本 | 中 | 低 | 高（轮次爆炸） |
| 失败模式 | 拆单模糊、写入冲突 | 错误顺流放大 | 争而不决、token 失控 |
| 并行度 | 高 | 无（串行） | 中（同轮可并行） |

### 4.4 结构化消息通信：为什么不能自由群聊

子 Agent 之间不用自由对话，用**结构化消息（工单）**。两个原因：

1. **上下文与 token 膨胀**：群聊里每句话都要过一遍大模型，上下文越聊越长，成本指数上升。
2. **传话失真**：自然语言传话，A 说的到 C 耳朵里已经走样，最后谁也说不清哪个结论是谁给的。

工单四件套（固定格式才能校验、追责、拼装）：

```text
┌─────────────────────────────────────────┐
│  工单（Task Ticket）                     │
│  1. 目标 goal：查什么/做什么             │
│  2. 问题清单 questions：要回答哪几点     │
│  3. 交付格式 deliverable：表格+要点+来源 │
│  4. 回给谁 report_to：supervisor        │
└─────────────────────────────────────────┘
```

格式固定带来三个工程收益：主管不用替工人「翻译」；验收可以按格式逐项核对；各工人的产出能直接拼装成稿。

### 4.5 监督与评审角色

多 Agent 系统里必须有明确的质检角色，原则：**未经检查的产出不直接采信。**

- **主管验收**：主管兼任评审，按工单的交付格式逐项核对，不达标退回重做或补查。
- **独立评审 Agent**：任务质量要求高时，用单独的评审角色按清单打分，与执行角色解耦（2.6 的原则：尽量换模型当 Judge）。
- **硬验证器优先**：交付格式、来源链接可访问性、数值范围——能用规则验的不用模型评。

### 4.6 协调开销与错误放大

多 Agent 的两笔隐性账必须进设计：

1. **协调开销**：拆单调用、工单下发、验收调用、汇总调用，全是过模型的成本。Anthropic 实测多 Agent 研究系统的 token 用量约为单 Agent 对话的 **15 倍**——架构升级前先算这笔账。
2. **错误放大（Error Amplification）**：一个子 Agent 的错误结论（幻觉、检索错）被主管照单全收、写进汇总，错误从「一个人的猜测」升级成「团队的结论」。对策：关键结论要求带来源；评审角色对无来源论断降权；写入侧收口（见下）。

**写入侧纪律**（read-vs-write 判据的工程化）：子 Agent 只读不写，写作收口给主管或单一执笔 Agent——多人同时改同一份稿是写入冲突的根源。

### 4.7 何时真的值得多 Agent

默认单 Agent；三条件满足得越齐，多 Agent 越值得（Anthropic 口径）：

| 条件 | 判断问题 | 反例 |
|---|---|---|
| 任务可并行拆分 | 拆开后互不干扰吗？ | 一步步推导的数学题拆不动 |
| 探索型、读多写少 | 是「翻书多落笔少」还是「都在改同一张卷子」？ | 协作写一份合同（写冲突） |
| 需要专业分工/上下文隔离 | 子任务需要不同专长或信息量超出单窗口？ | 一问一答的客服对话 |

配套判断：

- **LangChain 反向清单**：分支少、路径可预测、信息能装进一个上下文时别上多 Agent——工作流或单 Agent 更便宜、更可控、更好调。
- **拿不准上混合架构**：检索阶段多 Agent 并行（读多写少），写作阶段收口给单 Agent（重写入）。arXiv 2505.18286 报告混合方案可提精度 1.1-12%、同时省约 88% 成本。
- **先跑通再升级**：先做单 Agent 跑通全流程，遇到真瓶颈（上下文装不下、串行太慢）再升级——架构升级是手段不是勋章。

## 5. 架构 / 流程

三种协作模式的结构图：

```text
【主管-工人：星型】                 【流水线：链型】
        ┌────────┐
        │  主管   │拆单↑回传              调研 → 初稿 → 配图 → 校对
        └───┬────┘                        ↓      ↓      ↓      ↓
   ┌────────┼────────┐                 产出即原料，逐站接力；
  工人A    工人B    工人C                每站出口加校验闸门
   │        │        │                 （防错误顺流放大）
  工单↓    工单↓    工单↓
  并行执行，互不通信，写作收口给主管

【辩论：网状】
   顾问A ←→ 顾问B
     ↖     ↗   （限定 1-3 轮互评）
      裁判拍板 → 结论
```

主管-工人完整流程清单：

1. **拆单**：主管把总任务拆成相互独立的子任务，每个写清目标、问题清单、交付格式。
2. **下发**：工单格式固定，工人只看到自己的工单（上下文隔离）。
3. **并行执行**：工人内部跑单 Agent 循环（2.7），只读外部资料、不写共享稿。
4. **回传**：按交付格式回传，工人之间不对话。
5. **验收**：主管或评审按格式核对，不达标退回重做（设退回上限）。
6. **汇总**：收口给主管一人执笔，把验收通过的产出拼成最终稿。

## 6. 代码 / 工具

### 6.1 主管-工人编排示例

```python
"""主管-工人编排：拆单 → 并行执行 → 评审验收 → 收口汇总。
工人之间零通信，只按工单交付；写作收口给主管一人。"""

import json
from concurrent.futures import ThreadPoolExecutor
from openai import OpenAI

client = OpenAI(api_key="YOUR_KEY")
MODEL = "gpt-4o-mini"
PLANNER = "gpt-4o"          # 拆单用更强的模型：拆单质量决定全局

def plan(task: str) -> list:
    resp = client.chat.completions.create(
        model=PLANNER, temperature=0,
        response_format={"type": "json_object"},
        messages=[{"role": "user", "content":
            f"把任务拆成相互独立的子任务（拆开后互不干扰、各查各的）。"
            f"每个子任务给 goal、questions、deliverable。任务：{task}"}])
    return json.loads(resp.choices[0].message.content)["subtasks"]

def run_worker(ticket: dict) -> dict:
    """工人 Agent：内部跑 2.7 的单 Agent 循环（可挂工具/检索），
    这里示意通信接口——工人只看到自己的工单。"""
    system = f"""你是工人 Agent，只处理分给你的工单。
目标：{ticket['goal']}
要回答：{json.dumps(ticket['questions'], ensure_ascii=False)}
交付格式：{ticket['deliverable']}
约束：不得与其他工人交流；只做工单范围内的事；关键结论必须带来源。"""
    resp = client.chat.completions.create(
        model=MODEL, temperature=0,
        messages=[{"role": "system", "content": system},
                  {"role": "user", "content": "开工，按交付格式汇报。"}])
    return {"worker_id": ticket["worker_id"],
            "result": resp.choices[0].message.content}

def review(report: dict, ticket: dict) -> bool:
    """评审：按工单的交付格式验收，不达标退回；未经检查的产出不采信"""
    resp = client.chat.completions.create(
        model=MODEL, temperature=0,
        response_format={"type": "json_object"},
        messages=[{"role": "user", "content":
            f"工单要求：{json.dumps(ticket, ensure_ascii=False)}\n"
            f"工人产出：{report['result']}\n"
            '产出是否达标（覆盖全部问题、格式合规、有来源）？'
            '回 JSON：{"pass": bool, "why": str}'}])
    return json.loads(resp.choices[0].message.content)["pass"]

def supervisor(task: str, max_workers: int = 5,
               max_retry: int = 2) -> str:
    tickets = [{"worker_id": f"w{i}", **s}
               for i, s in enumerate(plan(task))][:max_workers]
    accepted = []
    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        for ticket, report in zip(tickets, pool.map(run_worker, tickets)):
            for attempt in range(max_retry):           # 验收失败退回重做
                if review(report, ticket):
                    accepted.append(report["result"])
                    break
                report = run_worker(ticket)            # 重做后重新验收
    return synthesize(task, accepted)                  # 写作收口：主管执笔

def synthesize(task: str, parts: list) -> str:
    resp = client.chat.completions.create(
        model=PLANNER, temperature=0,
        messages=[{"role": "user", "content":
            f"任务：{task}\n以下是各工人验收通过的产出，"
            f"拼装成一份带来源的最终报告：\n\n" + "\n\n".join(parts)}])
    return resp.choices[0].message.content

print(supervisor("调研智能手表市场的价格带与主打卖点"))
```

### 6.3 流水线中途校验与辩论轮数护栏（配置式清单）

```text

station_1_research:
  gate: 每条结论必须有可访问的来源链接

  rounds: 2                # 人数 x 轮次 = token 预算，2 轮封顶
  judge_must: 给出明确结论与理由，禁止"各有道理"
  budget: {"max_tokens": 50000}
```

## 7. 案例

### 案例 A：百份财报摘要（主管-工人的甜点区）

**场景**：一家金融科技公司的投研支持，要求分析 100 份财报、每份产出固定格式的一页摘要，最后汇总成行业综述。

**架构**：主管把任务拆成 100 个相互独立的工单（每单一编号一份财报、问题清单固定、交付格式为「表格+要点+页码引用」）；8 个工人并行执行、只读不写；评审按格式验收，不合格退回；主管收口执笔综述。

**效果**：墙钟时间从串行的约 6 小时压到约 50 分钟；交付格式合格率 97%；token 总量约为单 Agent 的 9 倍，但换来的时间收益对交付节点不可妥协——这笔账值。

### 案例 B：多 Agent 研究系统（读多写少的标准示范）

**场景**：参照 Anthropic 多 Agent 研究系统的口径：用户问开放性研究问题，系统给出带来源的调研报告。

**架构**：主管（Claude Opus 级）拆解研究计划，3-5 个子 Agent 并行搜索不同角度（典型的读多写少：各查各的、互不覆盖），关键结论必须带来源链接，主管验收后统一执笔成稿。

**效果**：在该系统的内部评估中，多 Agent 方案相对单 Agent 的产出质量有明显提升，代价是 token 用量约 15 倍——因此只对值得深挖的开放问题启用，简单事实问题仍走单 Agent。

### 案例 C：方案评审辩论翻车与修正

**场景**：某电商的技术选型评审 Agent，初期设计为 4 个顾问 Agent 自由辩论 5 轮。

**问题**：单次评审 token 是预期的 20 倍以上，且常吵不出结论，日志里出现顾问 A 重复顾问 B 的论点（传话失真后互相附和）。

**修正**：顾问缩到 2 个、轮数锁 2、裁判 Prompt 强制「给结论+理由，禁止和稀泥」；论点去重后统一喂给裁判。

**效果**：单次评审成本降约 85%，结论明确率从约 60% 升到 92%——辩论制的关键护栏是轮数与裁判纪律。

## 8. 常见坑

1. **自由群聊代替结构化通信**。上下文越滚越长、传话失真、token 失控。对策：工单四件套（目标/问题清单/交付格式/回给谁），子 Agent 间零对话。
2. **拆单模糊、无交付标准**。工人各干各的，回收时拼不成稿。对策：主管拆单时写清每单的目标、问题、交付格式，用强模型做 Planner。
3. **多个工人同时写同一份稿**。写入冲突互相覆盖。对策：子 Agent 只读不写，写作收口给主管或单一执笔。
4. **流水线不设中途校验**。上游错误顺流而下越滚越大。对策：每站出口加闸门，不合格就地打回，不带病下传。
5. **子 Agent 产出不验收直接采信**。错误放大：一个人的幻觉变成团队的结论。对策：主管或独立评审按清单验收，关键结论必须带来源。
6. **辩论不设轮数与预算**。人数 × 轮次让 token 成倍烧，还吵不出结论。对策：轮数锁 1-3，裁判必须给明确结论。
7. **能用工具解决的拆成了子 Agent**。Tool 是单次无状态调用，拆成 Agent 是为循环与上下文隔离付费——不需要就别付。对策：先问「这个子任务需要多轮自治吗」。
8. **主管自己下场干活**。角色混同后拆单、验收全都失守。对策：主管只拆单/验收/汇总，执行一律派工。
9. **失败无兜底**。子 Agent 超时或产出为空，主管照常汇总。对策：每个工单带超时与重试，失败降级为「该部分缺失」并显式标注。
10. **没有 trace 归因**。多 Agent 出错时不知道错在哪一站。对策：全链路留痕（3.4 可观测性），每条消息带 ticket_id 与 worker_id。
11. **忘了上下文隔离这个初心**。把所有中间过程回灌主管上下文，等于回到单窗口。对策：主管只见工单与验收结果，不见工人的完整轨迹。
12. **为了架构而架构**。把「上了多 Agent」当技术亮点写进汇报。对策：用 2.8b 的三条件自查，写不清三条件就退回单 Agent。

## 9. 练习

1. 跑通 6.1 的主管-工人编排，用「调研某品类市场价格带」作任务，观察工单下发与验收回传的完整 trace。
2. 故意把某个工单的 deliverable 删掉，观察验收环节如何失败，再补上格式约束对比效果。
3. 把工人改成并行写同一份共享文档，制造写入冲突，然后改回「只读 + 收口执笔」，记录两种方案的产出质量差异。
4. 实现流水线三站（调研→初稿→校对）加每站出口闸门，构造一条上游错误数据，观察闸门拦截。
5. 搭一个 2 顾问 + 1 裁判的辩论评审，把轮数从 1 调到 4，画出成本与结论明确率的曲线。
6. 用三条件（可并行、读多写少、需分工/隔离）审查你手头的任务，写一段「该不该上多 Agent」的论证。
7. 给 6.1 加预算护栏：全流程 token 超限即熔断，返回已完成部分并标注缺失。
8. 对比单 Agent 串行与主管-工人并行完成同一批量任务，统计墙钟时间、token 总量与失败率三组数字。

## 10. 小结

- 多 Agent = **主管拆活 + 工人并行 + 工单通信 + 评审把关**；每个成员内部仍是 2.7 的单 Agent 架构——多 Agent 是放大不是替代。
- 三模式各管一类任务：**主管-工人（可拆独立）、流水线（固定工序）、辩论（无标准答案的判断）**。
- 子 Agent 间用**结构化工单**（目标/问题清单/交付格式/回给谁），不用自由群聊——防 token 膨胀与传话失真。
- 格式固定的三收益：**可校验、可追责、可直接拼装**。
- 铁律：**未经检查的产出不直接采信**；关键结论必须带来源，否则评审降权。
- 两笔隐性账：**协调开销（Anthropic 实测约 15× token）与错误放大**——升级前先算账。
- 写入纪律：**子 Agent 只读不写，写作收口给一人**（read-vs-write 判据的工程化）。
- 三条件判据：**任务可并行、探索型读多写少、需专业分工/上下文隔离**——越齐越值得。
- 默认单 Agent，先跑通再升级；拿不准上混合架构（检索并行 + 写作收口）。
- Tool 与子 Agent 的分界：**单次无状态调用用 Tool，需要循环与上下文隔离的自治单元才用子 Agent**。
