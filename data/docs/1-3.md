## 1. 定位

S1 应用层第 3 个知识点，回答本锚点的关键问题：**如何让 LLM 安全调用工具？**

前两个锚点解决选型与引导：1.1 选模型、1.1b 调参数、1.2 写提示。本锚点解决**输出形态与行动接口**两个问题：

- 结构化输出（Structured Output）：让模型输出程序可直接解析的 JSON。
- Function Calling（函数调用，下称 FC）：让模型把自然语言翻译成结构化的工具参数，由程序校验后执行、结果回传。

它是 1.4 RAG、1.6 评估、2.1 Agent 定义、2.3 工具使用的直接前置。一句话串起关系：**FC 是平台化的结构化输出**——Schema 从提示词里的手写示例，升级为 API 一等公民的工具定义。

## 2. 一句话定义

结构化输出：让 LLM 按预先约定的 JSON Schema（用 JSON 描述数据结构契约的标准）产出机器可解析的结果。  
Function Calling：在结构化输出之上，让模型判断「该不该调工具、调哪个、参数填什么」，由应用程序校验参数、执行真正的系统调用并把结果回传给模型继续对话的协议——**AI 只填单，程序才办事**。

## 3. 为什么需要

自由文本回答有三个工程硬伤：

1. **不可解析**。「金额大约是三万五」人能懂，程序没法入账——下游系统要的是字段，不是散文。
2. **不稳定**。同一问题两次回答结构不同，正则解析随时崩。
3. **不安全**。让模型直接「办事」，等于把系统权限交给一个概率性输出器。

结构化输出与 FC 分别对应前两个与第三个问题：

| 维度 | 自由文本 | JSON Mode | 严格模式（Structured Outputs） | Function Calling |
|---|---|---|---|---|
| 语法合法性 | 无保证 | 保证（强制合法 JSON） | 保证 | 保证（参数为 JSON） |
| 字段/Schema 合规 | 无保证 | 无保证 | 强保证（Schema 注入解码约束） | 强（配合校验层） |
| 能否触发系统动作 | 否 | 否 | 否 | 是（经程序执行） |
| 权限边界 | 无 | 无 | 无 | 清晰（应用侧把守） |
| 典型用途 | 聊天、创作 | 信息抽取 | 抽取、分类、入库 | 查询、下单、操作类 |

「点餐小票」直觉（站内 1-3b 考点）：应用给模型一份菜单（工具定义），模型按格式填一张小票（参数 JSON），服务员（程序）验单后才送厨房（真正的系统）执行，做好端回来（结果回传）。模型从头到尾没进过厨房。

## 4. 核心原理

### 4.1 结构化输出三道关

```text
第 1 关  提示词层：给 Schema + 示例 + 「只输出 JSON，不要解释、不要代码块」
第 2 关  API 层：JSON Mode / 严格模式，语法层（或 Schema 层）硬保证
第 3 关  代码层：parse + Schema 校验，失败把错误喂回去，带错重试 ≤3 次，仍失败转人工
```

三道关是纵深防御，不是三选一：

- 第 1 关便宜但软——模型可能裹 markdown 代码块、漏字段。
- 第 2 关硬但有限——基础 JSON Mode 只保语法，不保字段内容。
- 第 3 关兜底——任何模型、任何模式都可能有坏输出，校验层是最后防线。

「出货三检」类比（站内 1-3 考点）：订单写清规格（Schema）、生产线按标准模式生产（JSON Mode）、出货验收（校验重试）。缺一道必翻车。

### 4.2 JSON Mode 的两层：语法保证 ≠ 字段保证

| 层 | 机制 | 保证什么 | 不保证什么 |
|---|---|---|---|
| 基础 JSON Mode（response_format=json_object） | 解码时约束输出必须是合法 JSON | 语法可 parse | 字段齐全、类型正确、值合理 |
| 严格模式（Structured Outputs，json_schema+strict） | 把 Schema 注入解码约束，只能产出符合 Schema 的 token 序列 | 字段、类型、必填、枚举 | 语义正确（金额对不对它不知道） |

工程推论：

- 只开基础模式，字段缺失照样发生——必须配第 3 关。
- 严格模式把 Schema 变成解码期硬约束，字段级合规率接近 100%，但「值对不对」仍需业务校验。
- 开基础 JSON Mode 时，提示词里必须出现「JSON」一词（多数实现如此要求），否则 API 报错。

Schema 设计四原则：

1. 枚举代替自由文本（「币种：CNY/USD」远好过一句描述）。
2. 结构浅而稳——嵌套超过 2-3 层，遵守率明显下降。
3. 关键字段允许 null 并写明「找不到填 null，禁止编造」——宁 null 走人工，不收编造。
4. 日期用 ISO 8601（YYYY-MM-DD），金额拆数值与币种两个字段。

### 4.3 Function Calling 的完整回合

```text
1. 注册菜单   应用随请求传入 tools：每个工具的 name / description / parameters
2. 模型填单   模型判断该不该调、调哪个，输出结构化参数 JSON（tool_calls）
3. 程序验单   应用校验：Schema 层（类型/必填/枚举/格式）+ 业务层（存在/归属/限额）
4. 厨房执行   合格则由应用调用真正的系统接口（带应用自己的权限与账号）
5. 结果回传   执行结果以 tool 消息回传，模型组织成自然语言答复用户
```

三个关键认知：

- 模型的输出只是一段结构化文本，**执行者是应用**。模型没有联网、没有碰数据库。
- 验单失败不是异常，是常态——概率性输出必然出错，正确姿势是把错误信息回传让模型自修。
- tool_choice 控制行为：auto（模型可调可不调）、required（必须调）、指定函数（强制调某个）。

### 4.4 工具定义三要素

| 要素 | 内容 | 写烂的后果 |
|---|---|---|
| name | 工具名，动宾结构（get_weather、apply_refund） | 名字含糊，模型选错工具 |
| description | 何时该用、何时不该用、边界与限制 | 选错工具或该调不调——描述是模型的唯一依据 |
| parameters | JSON Schema：类型/必填/枚举/范围/格式 | 填错参数、格式漂移（日期写成「下礼拜三」） |

description 是工具质量的一半：写清正例、反例、边界。例如「仅当用户明确提出退款且订单已完成时使用；只计算可退金额，不触发实际退款」。工具数量也要克制——菜单越长，选错概率越高。

### 4.5 参数双层校验与带错重试

| 层 | 校验什么 | 工具 | 示例 |
|---|---|---|---|
| Schema 层 | 类型、必填、枚举、正则格式、数值范围 | pydantic / jsonschema / zod | order_id 匹配 ^ORD\d{10}$；0<amount≤订单实付 |
| 业务层 | 存在性、归属、状态、限额、频率 | 应用代码 + 数据库 | 订单存在且归属当前登录用户；在 30 天退货期内 |

带错重试协议：

```text
校验失败 → 组装错误反馈：「date 字段格式非法（要求 YYYY-MM-DD），
你填了『明天』，请换算成具体日期后重新输出」
→ 连同原对话回传模型 → 模型自修重填 → 再校验
→ 循环上限 3 次 → 仍失败走人工或降级
```

带错误反馈的重试成功率远高于原样重发：模型知道错在哪个字段、违反什么要求，才有修正方向。静默丢弃会让模型困惑，应用侧猜值执行会引入脏数据——两者都比退回重填差一个量级。

### 4.6 安全原理：填单不办事

「AI 只填单」的结构带来三条安全红利：

1. **最小权限**：执行接口用只读账号、白名单接口，模型永远接触不到凭据。
2. **人类在环**：高危操作（退款、发邮件、删数据）设计成「报价不执行」——模型产出草稿/待确认状态，用户确认才生效。资金类工具的两段式（报价→确认）是行业标准。
3. **可审计**：每次调用留痕（谁、何时、调了什么工具、什么参数、结果如何），出事可追溯。

再加两道闸：限流（单会话高危调用超阈值即转人工，防注入诱导与死循环）、参数边界硬编码在应用侧（模型说金额是多少不算数，代码里的上限才算数）。

### 4.7 不稳定场景与兜底

| 不稳定表现 | 根因 | 兜底手段 |
|---|---|---|
| 输出裹 ```json 代码块 | 模型惯性 | 解析前剥壳（strip 代码围栏）；提示词明令禁止 |
| 字段缺失 / 类型错 | Schema 太松 | 严格模式 + 必填约束 + 校验重试 |
| 枚举值拼错 | 枚举没进 Schema | 枚举写进 Schema，业务层兜底映射 |
| 幻觉字段值（编造日期/金额） | 值无法从输入推出 | 「找不到填 null 禁编造」+ 低置信转人工 |
| 选错工具 | description 烂、工具太多 | 重写描述、给正反例、收窄工具数量 |
| 多次重试仍失败 | 任务超模型能力 | 降级路径：换更强模型 / 简化 Schema / 人工队列 |
| 高危参数（金额、收件人）越界 | 模型被诱导 | 应用侧硬上限 + 人工确认 |

原则：**解析失败是可预期的工程事件，按状态机处理（重试→降级→人工），不按异常崩溃处理。**

## 5. 架构 / 流程

一个带校验与兜底的完整工具调用回合：

```text
用户输入
   ↓
┌───────────────────────────────────────────────┐
│ 应用：组装请求                                  │
│  messages（system + history + user）            │
│  tools = [get_weather, query_order, ...]        │
│  temperature=0~0.2（结构化的隐形搭档，见 1.1b）  │
└───────────────────────────────────────────────┘
   ↓ API 响应
模型决策
   ├─ 不调工具 → 直接文本回答 → 返回用户
   └─ tool_calls（可一次并行多个独立调用）
        ↓
┌───────────────────────────────────────────────┐
│ 应用：验单（对每个 tool_call）                   │
│  1. parse arguments（失败→错误反馈重试）         │
│  2. Schema 校验：类型/必填/枚举/格式             │
│  3. 业务校验：存在/归属/限额                     │
│  失败 → 错误信息回传模型自修（上限 3 次）         │
└───────────────────────────────────────────────┘
   ↓ 全部合格
┌───────────────────────────────────────────────┐
│ 应用：执行                                      │
│  高危操作 → 人工确认闸门（草稿制）                │
│  普通操作 → 用应用自有权限调真实系统              │
│  每次调用写审计日志                              │
└───────────────────────────────────────────────┘
   ↓ tool 消息回传
模型组织语言 → 最终答复 → 下一轮（多步循环的终止与
死循环防护在 2.3 / 2.5 展开）
```

## 6. 代码 / 工具

### 6.1 结构化输出三道关（提示词 + JSON Mode + pydantic 校验带错重试）

```python
import json
from pydantic import BaseModel, ValidationError
from openai import OpenAI

client = OpenAI(api_key="YOUR_KEY")

# 第 1 关：提示词给 Schema 与约束
class Contract(BaseModel):
    party_a: str | None      # 甲方，找不到填 null
    party_b: str | None
    amount: float | None     # 金额（数值）
    currency: str            # 枚举收窄
    expire_date: str | None  # ISO 8601：YYYY-MM-DD

SCHEMA_HINT = """抽取字段：{"甲方": str|null, "乙方": str|null, "金额": number|null,
"币种": "CNY"|"USD", "到期日": "YYYY-MM-DD"|null}
字段在原文找不到时填 null，禁止编造。只输出 JSON，不要解释、不要代码块。"""

def extract(text: str, max_retry: int = 3) -> Contract | None:
    messages = [
        {"role": "system", "content": SCHEMA_HINT},
        {"role": "user", "content": text},
    ]
    for _ in range(max_retry):
        resp = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=messages,
            temperature=0,                            # 低温配结构化
            response_format={"type": "json_object"},  # 第 2 关：JSON Mode
        )
        raw = resp.choices[0].message.content
        # 常见坑兜底：剥掉可能裹上的 markdown 代码围栏
        raw = raw.strip().removeprefix("```json").removeprefix("```").removesuffix("```")
        try:
            return Contract.model_validate_json(raw)  # 第 3 关：校验
        except (json.JSONDecodeError, ValidationError) as e:
            messages.append({"role": "assistant", "content": raw})
            messages.append({"role": "user",
                             "content": f"上次输出未通过校验：{e}\n请修正后重新输出，只输出 JSON。"})
    return None   # 仍失败：转人工复核队列，宁 null 不编造
```

### 6.2 Function Calling 全流程（tools 定义 + 双层校验 + 错误回传自修）

```python
import json
from datetime import date, timedelta
from openai import OpenAI

client = OpenAI(api_key="YOUR_KEY")

tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市某天的天气。当用户询问天气时使用；"
                       "不用于空气质量、机票或穿搭推荐。",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名，如：北京"},
                "date": {"type": "string", "description": "日期，ISO 格式 YYYY-MM-DD"},
            },
            "required": ["city"],
        },
    },
}]

CITY_WHITELIST = {"北京", "上海", "深圳"}   # 业务层白名单

def validate_args(name: str, args: dict) -> str | None:
    """双层校验：返回 None 表示合格，返回字符串即错误反馈。"""
    if name != "get_weather":
        return f"未知工具 {name}"
    if not isinstance(args.get("city"), str) or not args["city"]:
        return "city 必填且为字符串"
    if args["city"] not in CITY_WHITELIST:
        return f"city 仅支持 {sorted(CITY_WHITELIST)}"
    d = args.get("date")
    if d is not None:
        try:
            parsed = date.fromisoformat(d)
        except ValueError:
            return "date 格式非法，要求 YYYY-MM-DD，请把『明天』这类表述换算成具体日期"
        if parsed > date.today() + timedelta(days=7):
            return "date 仅支持未来 7 天内"
    return None

def run_turn(user_msg: str, max_fix: int = 3) -> str:
    messages = [{"role": "system", "content": "你是助手，需要查询信息时调用提供的工具。"},
                {"role": "user", "content": user_msg}]
    for _ in range(max_fix + 1):
        resp = client.chat.completions.create(
            model="gpt-4o-mini", messages=messages,
            tools=tools, tool_choice="auto", temperature=0)
        msg = resp.choices[0].message
        if not msg.tool_calls:                        # 模型选择直接回答
            return msg.content
        messages.append(msg)
        for tc in msg.tool_calls:                     # 支持一次多个并行调用
            try:
                args = json.loads(tc.function.arguments)
                err = validate_args(tc.function.name, args)
            except json.JSONDecodeError as e:
                err = f"参数不是合法 JSON：{e}"
            if err:
                result = {"error": err}               # 错误信息回传，模型自修
            else:
                result = query_weather_api(args)      # 厨房执行：应用自有权限
                audit_log(tc.function.name, args)     # 审计留痕
            messages.append({"role": "tool", "tool_call_id": tc.id,
                             "content": json.dumps(result, ensure_ascii=False)})
    return "抱歉，暂时无法完成查询，已转人工。"          # 重试上限兜底
```

### 6.3 高危工具的「报价不执行」清单

```text
工具描述模板（apply_refund）：
  description: 用户明确提出退款且订单已完成时使用。
               仅计算可退金额并进入待确认状态，不触发实际退款。
  parameters:
    order_id: string，必填，正则 ^ORD\d{10}$
    reason:   enum [质量问题, 未收到, 七天无理由]
    amount:   number，0 < amount <= 订单实付

应用侧五条规则：
  1. Schema 校验：正则 / 枚举 / 金额范围
  2. 业务校验：订单存在、归属当前登录用户、30 天退货期内
  3. 执行策略：生成待确认单据 → 用户点击确认 → 才调真实退款接口
  4. 限流：单会话退款调用超过 2 次即转人工
  5. 审计：全量留痕（用户、时间、参数、结果）
```

## 7. 案例

### 案例 A：合同抽取入库

**场景**：一家金融科技公司从上传的合同 PDF 抽取甲乙方、金额、到期日入库，准确率优先。  
**做法**：Schema 把金额拆成数值与币种两个字段、日期用 ISO 8601、找不到填 null 禁编造；低温加基础 JSON Mode；pydantic 校验类型格式，再加「各分期金额加总等于总额」的业务核验；关键字段为 null 或低置信进人工复核队列；抽样 50 份人工标注对比，按字段统计准确率迭代提示词。  
**效果**：字段级准确率从约 82% 提升到 96%，编造值导致的脏数据接近归零，人工复核比例稳定在 8% 左右。

### 案例 B：客服查订单与防乱退款

**场景**：某电商平台客服 Agent 接 query_order 与 apply_refund 两个工具。  
**做法**：order_id 加正则校验；退款工具 description 写明「仅计算可退金额，不触发实际退款」；业务层校验订单归属当前登录用户与 30 天退货期；两段式「报价→用户确认→执行」；单会话退款调用超 2 次转人工。  
**效果**：一次话术诱导（让 Agent 直接群发补偿券）被应用层阈值与人工确认闸门拦截；退款误操作率降为 0，人工介入集中在真实纠纷。

### 案例 C：日期格式自修

**对话**：用户问「北京明天下雨吗」。  
**过程**：模型填单 `{city: 北京, date: 明天}` → 校验失败（格式非法）→ 错误信息回传 → 模型换算成 `2026-09-17` 重填 → 校验通过 → 天气系统返回小雨 22°C → 模型答复「明天北京有小雨，记得带伞」。  
**要点**：验单失败不是 bug 而是流程；带错重试一轮成功，全程无需人工。

## 8. 常见坑

1. **开了 JSON Mode 就以为稳了**。基础模式只保语法合法，字段缺失照样发生；严格模式或代码校验必须配齐。
2. **校验失败原样重发**。不带错误反馈的盲目重试成功率低；把报错与坏输出一起回传。
3. **重试不设上限**。死循环烧钱；上限 3 次，之后降级或人工。
4. **输出裹 markdown 代码块没处理**。解析前剥壳，提示词同时明令禁止。
5. **Schema 嵌套太深**。超过 2-3 层遵守率明显下降，结构要浅而稳。
6. **自由文本当枚举用**。枚举写进 Schema，拼错率骤降。
7. **只做 Schema 校验不做业务校验**。格式对但订单不存在、金额超限，照样是事故。
8. **description 只写一句话**。模型选错工具多半是描述烂；写清何时用、何时不用的正反例。
9. **把模型参数直接当真值执行**。金额、收件人等高危参数在应用侧硬编码上限。
10. **高危工具给直发权限**。退款、发邮件走「报价不执行 + 人工确认」两段式。
11. **不留审计日志**。出事无法追溯；每次调用记录工具、参数、结果、用户。
12. **温度开太高**。结构化任务用 0-0.2，随机性是解析失败的放大器。
13. **失败只会抛异常**。解析失败是常态，按状态机处理：重试→降级→人工。
14. **混淆本篇与 2.3 的边界**。本篇是单回合内的校验与自修；多步循环的死循环防护、步数与预算阈值在 2.3/2.5 展开。

## 9. 练习

1. 用 pydantic 加基础 JSON Mode 写一个抽取器，故意不给 Schema 示例，统计 10 次输出中字段缺失的次数。
2. 把第 1 题升级为严格模式（json_schema 加 strict），对比字段合规率变化。
3. 实现 validate_args 加带错重试，构造「明天」日期场景，观察模型能否自修为 ISO 格式。
4. 定义两个描述相近的工具，先把 description 写含糊、再写清正反例，对比选错率。
5. 给一个查询工具加业务白名单校验，测试模型填越界值时错误回传与自修的完整路径。
6. 实现退款工具的「报价不执行」两段式，模拟用户确认前后的完整状态流。
7. 对一次批量抽取任务统计三道关的失败分布（语法错/Schema 错/业务错），找出最该加固的一道。
8. 把带错重试上限从 3 改成不设限，观察极端 bad case 下的成本曲线，体会设上限的必要性。

## 10. 小结

- 结构化输出三道关：**提示词 Schema 加示例 → API JSON/严格模式 → 代码校验带错重试**，纵深防御缺一不可。
- JSON Mode 两层：基础模式保语法，严格模式（Structured Outputs）保 Schema；**语法合法 ≠ 字段正确**。
- Schema 设计四原则：枚举收窄、结构浅、允许 null、禁编造——**宁 null 走人工，不收编造**。
- FC 完整回合：**注册菜单 → 模型填单 → 程序验单 → 厨房执行 → 结果回传**；AI 只填单不办事。
- 工具定义三要素：**name / description / parameters**；description 决定选对工具，Schema 决定填对参数。
- 校验两层：**Schema 层（类型/格式）+ 业务层（存在/归属/限额）**；带错重试上限 3 次。
- 安全三红利：**最小权限、高危人工在环、全量审计**——权限锁在应用侧是 Agent 安全的地基。
- 低温（0-0.2）是结构化的隐形搭档（回看 1.1b）。
- 并行调用是免费午餐：一次请求返回多个独立 tool_calls，查三个城市只跑一轮。
- 这些能力直接支撑：1.4 RAG、1.6 评估、2.1 Agent、2.3 工具异常防护、2.3b MCP。
