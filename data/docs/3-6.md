## 1. 定位

AI 工程化层第 6 个知识点，回答大纲里的关键问题：**如何稳定承载真实流量？**

Demo 阶段一条 `uvicorn` 进程加一个 API Key 就能演示；生产阶段的流量有峰谷、任务有长短、连接要保持、会话要迁移、GPU 又贵又少——「能跑」和「能扛」之间隔着一整套部署与扩展工程。

前置依赖 3.1（架构与接口设计）：部署形态是分层架构的落地，容量规划要从架构约束倒推。向后支撑：3.7（成本、延迟与可靠性——单位成本由部署形态与引擎吞吐决定）、3.9（CI/CD 与发布——发布门禁建立在容量与伸缩信号上）、4.9（部署与运维——软故障告警建立在容量水位上）。

划界：本篇管「部署形态与伸缩」——部署在哪、怎么扩、怎么削峰；成本量化与可靠性工程（重试 / 熔断 / 降级链）归 3.7，发布流程归 3.9，值班应急归 4.9。

## 2. 一句话定义

部署与扩展（Deployment & Scaling），是为 Agent 服务选择合适的运行形态（虚拟机 / 容器 / Serverless / 混合），用容量估算定规模、用自动伸缩（Autoscaling）应对峰谷、用队列与缓存削峰填谷（Peak Shaving），使其在服务等级目标（Service Level Objective, SLO）约束内稳定承载真实流量的工程能力。

简化公式：

```text
承载能力 = 部署形态 × 容量估算 × 伸缩策略 × 削峰填谷
```

四项相乘：任何一项为零，整体为零——形态选错（如 Serverless 跑小时级任务），容量算得再准也扛不住。

## 3. 为什么需要

朴素部署（单进程 FastAPI，同步调用 LLM，会话放内存）在真实流量下的问题：

- **流量有峰谷** → 峰值 QPS 常是均值 3–10 倍；按峰值配置闲时浪费，按均值配置高峰宕机。
- **长任务占死连接** → 一次报告生成 5 分钟，同步请求把 worker 与连接占满，新请求排队超时。
- **流式被断流** → 生成到一半，网关默认 60 秒读超时把服务器推送事件（Server-Sent Events, SSE）连接掐断，用户看到截断的回答。
- **扩容即丢会话** → 会话上下文放在进程内存，滚动更新或扩容后请求落到新副本，Agent「失忆」。
- **CPU 指标失灵** → Agent 大部分时间在等 LLM 返回，CPU 利用率很低但并发已打满，按 CPU 伸缩的副本数纹丝不动。
- **冷启动叠加首响** → 无服务器（Serverless）冷启动与首 token 时间（Time To First Token, TTFT）叠加，首响翻倍。
- **GPU 贵且是硬瓶颈** → 云 API 有提供商限流配额，自建 GPU 有显存账，两侧都不能拍脑袋。

**对比**：

| 维度 | Demo 部署 | 生产部署 |
|---|---|---|
| 目标 | 跑通一次演示 | 扛住峰值流量并守住 SLO |
| 流量 | 单用户、无峰谷 | 峰谷 3–10 倍、突发不可预期 |
| 状态 | 进程内存 | 外置存储（Redis / DB），副本可随意增减 |
| 模型接入 | 单一 API Key | 多提供商配额 / 自建推理池 |
| 伸缩 | 无 | 指标驱动自动伸缩 + 定时兜底 |
| 失败处理 | 刷新重试 | 队列重投、背压、降级（见 3.7） |

**类比**：Demo 像在家招待朋友，一桌一灶怎么都行；生产像开餐厅——前厅（接入层）控制入座节奏，后厨（模型侧）决定出餐速度，等位叫号（队列）消化高峰。只扩前厅不扩后厨，排队只会更长——这就是应用层与模型层必须分开做容量规划的原因。

## 4. 核心原理

### 4.1 稳定承载真实流量：三段正面回答

关键问题的完整答案是三段：容量估算定底数，伸缩策略抗波动，削峰填谷保下限。

**第一段：容量估算。** 用利特尔法则（Little's Law）：

```text
平均在途并发数 L = 请求到达率 λ × 平均停留时长 W
```

Agent 服务与普通 Web 服务的差别在 W：普通接口毫秒级，Agent 一次请求常是 5–60 秒（多步循环加生成）。因此 Agent 的第一稀缺资源不是 QPS，而是**并发连接数**。

```text
例：50 QPS × 平均 20 秒/请求 = 1000 并发连接
副本数 = 1000 ÷ 单副本并发上限（压测得出，如 200）× 冗余系数 1.5 ≈ 8 副本
若峰值为均值 5 倍，按峰值重算（5000 并发 → 38 副本），不是把均值结果线性放大
```

**第二段：伸缩策略。** 底数之上用自动伸缩吸收波动：在线层按并发连接数伸缩，异步层按队列深度伸缩，选型与失效模式见 4.4。

**第三段：削峰填谷。** 伸缩有下限（扩容生效需 1–3 分钟）与上限（GPU 扩容以天计），扛不住的瞬时洪峰交给队列：请求先入队，系统按稳定速率消费，见 4.5。

三段的关系：估算告诉你常态要几台，伸缩告诉你波动时几台，削峰告诉你极端时先排队而不是先崩溃。

**面试高频问法**：「流量从 100 QPS 涨到 5000 QPS，你的 Agent 服务怎么扩？瓶颈在模型侧还是编排侧？」共识口径：先拆瓶颈再扩。编排侧（自建服务）是 CPU 与连接密集，加副本并按并发连接数自动伸缩，分钟级见效；模型侧若是云 API，先撞到的是提供商限流配额，解法是多提供商分流或私有化部署；若是自建 GPU，扩容以天计，必须按峰值提前储备。一句话：编排层弹性伸缩，模型层容量前置，洪峰入队列。

### 4.2 部署形态：四种选择与 LLM 应用的特殊约束

| 维度 | 虚拟机（VM） | 容器 + K8s | Serverless | 混合 |
|---|---|---|---|---|
| 启动速度 | 分钟级 | 秒级 | 冷启动毫秒到秒级 | 按层选 |
| 伸缩粒度 | 整机、慢 | 副本级、分钟级 | 请求级、可缩到零 | 按层选 |
| 状态 | 长驻 | 无状态 + 外置存储 | 无状态、执行完即释放 | 按层选 |
| 流式（SSE） | 支持 | 支持 | 截至 2026 年主流平台已支持流式响应，长连接仍受限（趋势观察） | 支持 |
| 长任务 | 无限制 | 无限制 | 主流函数计算平台（Function as a Service, FaaS）单次执行上限为分钟级（约 15 分钟） | 长任务走常驻层 |
| 成本模型 | 包月 | 常驻但密度高 | 按调用计费、闲时为零 | 核心常驻 + 突发弹性 |
| 典型用途 | GPU 推理节点、数据库 | Agent 在线服务、worker | 事件驱动的短任务（文档入库、批量评估） | 生产系统的实际形态 |

Agent 服务的实际答案通常是混合：在线服务（长连接、SSE、会话外置）用容器；事件型短任务用 Serverless；GPU 推理用专用 GPU 节点池或独立推理集群；突发流量溢出到云 API。

### 4.3 长任务与短请求：三类流量，三种部署

| 维度 | 同步短请求 | SSE 流式 | 异步长任务 |
|---|---|---|---|
| 时长 | 秒级 | 首 token 秒级，总时长 10–60 秒以上 | 分钟到小时级 |
| 连接 | 请求-响应即断 | 全程保持到生成结束 | 提交即返回，结果回调或轮询 |
| 超时配置 | 网关 30 秒量级 | 关代理缓冲，读超时 300 秒以上 | 任务级超时，与连接无关 |
| 伸缩信号 | QPS | 并发连接数 | 队列深度 |
| 状态 | 无 | 会话外置 | 任务状态机 + 检查点（见 2.5） |
| 典型部署 | 在线副本池 | 在线副本池 | 队列 + worker 池 |

核心规则：**不要用同步接口承载长任务。** 同步请求把「任务的时长」变成「连接的时长」，网关、负载均衡、客户端每一层的超时都会砍它，任何一层重试还会放大并发。长任务的正确形态是提交-入队-处理-通知（见 4.5），过程中的进度展示用流式或轮询。

### 4.4 伸缩策略：定时、指标、队列深度、预测

K8s 生态的两个主力控件：水平 Pod 自动伸缩器（Horizontal Pod Autoscaler, HPA）与基于事件驱动的伸缩（Kubernetes Event-driven Autoscaling, KEDA），前者看指标扩在线副本，后者看事件（典型是队列长度）扩 worker。

| 策略 | 原理 | 生效延迟 | 适合 | 主要风险 |
|---|---|---|---|---|
| 定时伸缩 | 按业务周期预约扩缩（工作日 9 点扩、21 点缩） | 提前生效 | 周期明显的流量 | 流量不按剧本走 |
| 资源指标 | HPA 默认按 CPU / 内存 | 1–3 分钟 | CPU 密集服务 | Agent 是 IO 密集，CPU 低估失灵 |
| 自定义业务指标 | 按并发连接数、在途请求数、P95 延迟伸缩 | 1–3 分钟 | Agent 在线层 | 需要自定义指标管道 |
| 队列深度 | 按消息积压量伸缩 worker（KEDA） | 秒到分钟 | 异步任务层 | 消费速率受下游限流制约 |
| 预测式 | 按历史流量预测扩容（趋势观察，云厂商能力） | 提前生效 | 大促等已知高峰 | 预测偏差需兜底 |

生产组合拳：在线层用自定义并发指标，异步层用队列深度，两者都设 min/max 副本护栏，再加定时提前扩兜底。伸缩信号的选择原则：**信号要直接反映用户体验受损的原因**——排队变长扩 worker，并发打满扩在线副本，而不是间接的 CPU 百分比。

### 4.5 队列与削峰填谷

类比：没有队列的餐厅，高峰期客人全部挤进门站着等，门口堵死谁也吃不上；有等位叫号，客人按出餐能力分批入座，店外排队但店内秩序不崩。队列对系统做的正是这件事：把「过载崩溃」换成「排队等待」。

异步化链路：

```text
API 接收任务 → 校验与去重 → 写入任务表 → 入队 → worker 消费
→ 更新任务状态（进度 / 结果）→ 完成回调或通知客户端
```

队列在传统后端已验证的能力，在 Agent 场景逐条对上：

| 能力 | 作用 | Agent 场景 |
|---|---|---|
| 削峰 | 瞬时洪峰先入队，系统按稳定速率消费 | 大促客服、定时批量评估的流量尖峰 |
| 解耦 | 生产者与消费者独立部署、独立伸缩、独立发布 | 编排服务与执行 worker 分开扩容 |
| 重试与死信 | 消费失败自动重投，多次失败进死信队列（Dead Letter Queue, DLQ）人工处理 | 工具偶发失败、LLM 超时的自动恢复（机制细节见 3.7） |
| 顺序（分区） | 同一 key 的消息保持有序 | 同一会话的任务按序执行，避免状态竞争 |
| 背压（Backpressure） | 队列水位超限时拒绝或降级新任务 | 水位超过阈值直接返回「稍后再试」，防雪崩 |

两条纪律：队列改变的是失败形态，从「报错」变成「等待」，必须给用户可见的排队位置与预计时长，否则体验只是从崩溃换成无限等待；背压阈值要在压测里校准，太高形同虚设，太低把可服务的流量也拒之门外。

### 4.6 并发模型、SSE 连接保持与有状态 Agent

**并发模型。** 异步框架（FastAPI + uvicorn）下单 worker 可持数千并发连接，瓶颈从 CPU 转移到内存、文件描述符与下游 LLM 并发配额。worker 数由 CPU 密集段（检索重排、JSON 解析）决定，并发上限由压测得出——两个数不要混为一谈。

**SSE 连接保持。** 流式输出要求整条链路不缓冲、不掐断：

```text
反向代理：proxy_buffering off（或响应头 X-Accel-Buffering: no）
读超时：proxy_read_timeout 300 秒以上（默认 60 秒是断流首因）
心跳：服务端每 15–30 秒发一行 SSE 注释（: ping），防中间设备空闲断连
传输：HTTP/1.1 keepalive 或 HTTP/2，避免连接频繁重建
```

**有状态 Agent 的两条路。** Agent 的会话上下文与执行状态是「状态」，与「副本可随意增减」直接冲突：

- 会话亲和（Session Affinity）：负载均衡（Load Balancer）按会话 ID 把请求路由到同一副本。实现快，但副本故障即丢会话，且与自动伸缩相互制约——扩缩容改变路由表。
- 状态外置：会话状态、检查点（见 2.5）、长期记忆（见 2.4）放 Redis / DB，任意副本可接管任何会话。副本无状态，才能自由伸缩与滚动更新。

生产主流是状态外置 + 无状态副本；会话亲和只在状态无法外置时（如本地缓存预热很重的检索副本）作为补充。

### 4.7 GPU 与推理服务边界：云 API 还是自部署

| 维度 | 云 API | 自部署（vLLM 等） |
|---|---|---|
| 启动成本 | 开箱即用 | 需要 GPU 集群与推理运维 |
| 成本曲线 | 按 token 计价，量大后陡增 | 固定投入，利用率打满后单 token 显著更低 |
| 容量上限 | 提供商限流配额，需多 Key 多提供商 | 自己的显存与卡数，可控可扩 |
| 数据合规 | 数据出域 | 可全内网，敏感数据不出机房 |
| 模型迭代 | 换模型改参数即生效 | 换权重需重新压测容量 |

判断口诀：流量小、波动大、快速验证——云 API；流量稳定且大（自建利用率能打满）、合规要求数据不出域、需要深度定制（超长上下文、高频共享前缀）——自部署。

自部署侧的三大推理引擎（截至 2026 年）：

| 维度 | vLLM | TensorRT-LLM | llama.cpp |
|---|---|---|---|
| 定位 | 吞吐与生态平衡，工程默认 | 极致延迟与吞吐上限 | 边缘与端侧 |
| 核心技术 | PagedAttention + 连续批处理 | 按模型编译的 kernel 优化 | GGUF 量化 + CPU/GPU 混合推理 |
| 硬件 | NVIDIA 为主、兼容多卡 | 深度绑定 NVIDIA | CPU / Apple Silicon / 低端 GPU |
| 换模型 | 直接加载新权重 | 重新编译 engine | 转换 GGUF 即可 |
| 典型场景 | 在线 API、Agent 后端、月更模型 | 延迟敏感、模型半年以上稳定 | 本地原型、端侧、离线小任务 |

vLLM 同卡吞吐翻数倍的两个机制：一是连续批处理（Continuous Batching）——静态批处理（Static Batching）像班车，凑满一车才发、先做完的陪等最慢的；连续批处理像网约车拼车，每个解码步结束后动态补位，完成的请求立刻弹出、排队的立刻补进批内空位，GPU 永远满载。二是分页注意力（PagedAttention）——把 KV 缓存（KV Cache）按页管理、消除碎片，同卡并发与吞吐同时上来。

选型三问：延迟敏感还是吞吐敏感？部署环境是 NVIDIA 集群还是笔记本手机？模型迭代频率月更还是半年不动？工程默认答案是 vLLM：性能够用、生态最全、换权重无痛；P99 要压到 500ms 以内、模型长期稳定、且有 NVIDIA 调优人力，三者同时满足才值得迁 TensorRT-LLM。

**面试高频问法**：「为什么 LLM 推理慢且贵？自部署和云 API 怎么选？」共识口径：慢在自回归解码——逐 token 生成受显存带宽限制，每生成一个 token 都要读一遍权重与 KV Cache；贵在 GPU 时间。选型按三个要素回答：流量形态（峰谷比大用云，平稳量大自建）、数据边界（合规要内网则自建）、单位成本拐点（自建利用率打不满就是亏损），而不是比较「哪个技术更先进」。

### 4.8 显存三笔账与容量规划四步（自部署侧）

部署模型像开酒店：只算买楼的钱一定破产，运营的变动成本才是大头。

| 科目 | 公式 | 性质 | 示例（7B，fp16，4K 上下文，16 路并发） |
|---|---|---|---|
| 权重账 | 参数量 × 每参数字节（fp16=2B，INT8=1B，INT4=0.5B） | 固定开销 | 7×2 = 14 GB |
| KV Cache 账 | 2×层数×KV头数×head_dim×序列长×字节×并发 | 随并发与上下文线性增长 | 单路约 2.1 GB，16 路约 34 GB |
| 激活与框架开销 | （权重+KV）× 10%–20% | 随 batch 增大 | 约 7 GB |
| 合计 | 三项相加再留 20%–30% 冗余 | — | 约 55–60 GB |

三个关键数字：7B fp16 权重 14 GB，INT4 后约 3.5 GB；MHA 结构的 7B（32 层、32 头、128 维）fp16 下每 token 约 512 KB，4K 上下文单路吃 2.1 GB，16 路并发时 KV（34 GB）是权重（14 GB）的两倍多——只报「模型 14 GB」是容量规划的经典失分点；分组查询注意力（Grouped-Query Attention, GQA）把 KV 头减到 8 组，KV 账直降为 1/4——选模型时 KV 结构就是成本结构。

量化是显存账本的第一杠杆：

| 精度 | 每参数字节 | 7B 权重 | 说明 |
|---|---|---|---|
| fp16 / bf16 | 2 B | 14 GB | 质量基线 |
| INT8 | 1 B | 7 GB | 近乎无损，省一半 |
| INT4（AWQ/GPTQ） | 0.5 B | 3.5 GB | 主流生产选择 |
| KV Cache 量化（fp8/int8） | — | KV 减半 | 叠加在权重量化之上 |

13B 模型：fp16 权重 26 GB + 8 路 4K KV 约 8 GB + 开销 15% 约 39 GB，单张 40G 卡放不下；换 INT4 后权重 6.5 GB、合计约 20 GB，单张 24G 卡轻松承载。量化的实际意义：同样预算下并发翻倍，或同样并发下卡数减半。

容量规划四步（4.1 的应用侧公式在此落到 GPU）：

```text
第一步 定 SLO        P99 延迟（TTFT / 每 token 间隔）/ 单卡吞吐 / 可用性
第二步 算单卡并发     显存账本算出单卡塞几路，再验算 decode 速度是否满足 P99
第三步 峰值定卡数     峰值 QPS ÷ 单卡 QPS × 冗余系数（1.5–2.5）
第四步 压测校准       真实流量回放压 P99 与吞吐，调副本数与伸缩阈值
```

两条纪律：按峰值设计不按均值——供水系统按高峰人数设计，按均值必炸；延迟约束常比显存约束先到——批越大吞吐越高但单请求延迟也涨，在线对话小 batch 优先、离线跑批大 batch 填满，先定 SLO 再定 batch。

### 4.9 PD 分离、端侧与扩容顺序

**PD 分离（Prefill-Decode Disaggregation）**：把 prefill（算输入，算力密集）与 decode（逐 token 生成，显存带宽密集）拆到不同实例，各自用合适的硬件与批策略，中间靠 KV Cache 传输衔接。Mooncake、DistServe 一类架构已验证长输入场景的 P99 与吞吐同时受益；代价是 KV 传输链路、路由一致性、故障恢复的复杂度——中小规模先用一体机，规模上来再拆。

**端侧与边缘推理（趋势观察）**：把 1B–3B 小模型以 INT4 量化跑在手机、AI PC、车载神经网络处理器（Neural Processing Unit, NPU）上，动机是隐私（数据不出设备）、离线可用、毫秒级本地延迟、边际成本近零。架构核心是端云协同：端侧做意图识别、脱敏、简单任务，复杂任务升级云端。输入法本地续写（高频、轻量、隐私敏感）是端侧教科书场景；通用问答与复杂代码重构留给云端。

**扩容顺序：先软后硬。** 容量告警触发时按性价比逐层加码：

| 层级 | 手段 | 见效速度 | 成本 |
|---|---|---|---|
| 第一层：配额与调度 | 限流排队、降级到小模型、调大批参数、开前缀缓存（Prefix Caching） | 分钟级 | 近零 |
| 第二层：单实例优化 | 量化、调显存利用率与并发上限参数 | 小时级 | 低 |
| 第三层：基础设施 | 加副本、TP 拆分、加卡、PD 分离 | 天级 | 高 |

顺序反了就是事故：流量尖峰先无脑加卡，账单翻倍还可能压不回 P99——先查是不是大量重复请求没走缓存、长系统提示没开前缀共享。软件层的钱省完，再加硬件。（限流与降级的可靠性细节见 3.7。）

## 5. 架构 / 流程

一个能稳定承载真实流量的 Agent 服务部署架构：

```text
┌──────────────────────────────────────────────────┐
│ 客户端（Web / App / API 调用方）                  │
└──────────────────────┬───────────────────────────┘
                       ↓
┌──────────────────────────────────────────────────┐
│ 接入层：负载均衡 → 网关                           │
│   限流 / 鉴权 / 路由 / SSE 不缓冲不掐断（4.6）    │
└───────┬──────────────────────────┬───────────────┘
        ↓ 同步 + 流式               ↓ 长任务提交
┌───────────────────┐    ┌─────────────────────────┐
│ 在线层（无状态）  │    │ 异步层                  │
│  Agent 副本池     │    │  任务队列 ─→ worker 池  │
│  HPA：并发连接数  │    │  KEDA：队列深度         │
└───────┬───────────┘    └──────────┬──────────────┘
        ↓                           ↓
┌──────────────────────────────────────────────────┐
│ 状态层：Redis（会话/检查点）· DB（任务）· 向量库  │
│   状态外置 → 副本无状态、可自由伸缩（4.6）        │
└───────┬──────────────────────────────────────────┘
        ↓
┌──────────────────────────────────────────────────┐
│ 模型层：云 API（多提供商配额）                    │
│        或自建 vLLM GPU 池（规模后 PD 分离）       │
│   扩容顺序：先配额调度，再单机调优，最后加卡      │
└──────────────────────────────────────────────────┘
        ↕ 指标回流：并发连接 / 队列深度 / TTFT / 显存水位
┌──────────────────────────────────────────────────┐
│ 伸缩控制：HPA + KEDA + 定时兜底                  │
│   容量闭环：定 SLO → 算并发 → 峰值×冗余 → 压测校准│
└──────────────────────────────────────────────────┘
```

读图三点：在线层与异步层分开伸缩（信号不同）；状态层全部外置（副本才敢随意增减）；模型层是容量最重的一层，扩容以天计，必须前置规划。

### 6.3 KEDA：按队列深度伸缩异步 worker

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: agent-worker-scaler
spec:
  scaleTargetRef: { name: agent-worker }     # 异步任务 worker Deployment
  minReplicaCount: 2                          # 深夜也留保底消费力
  maxReplicaCount: 30
  cooldownPeriod: 300                         # 队列清空后等 5 分钟再缩，防抖动
  triggers:
  - type: redis
    metadata:
      address: redis-master.default.svc:6379
      listName: agent:tasks                   # 任务队列
      targetListLength: "10"                  # 每个 worker 积压 10 条为目标水位
      enableListLengthApproximation: "true"   # 用近似长度，降低 Redis 压力
```

配套逻辑：入队时写任务表（状态 queued），worker 取任务置 running 并设可见性超时，完成写 done；消费失败重投，超过 3 次进死信队列。队列水位超过背压阈值（如 5000）时入口直接返回「排队人数较多，请稍后」——这是 4.5 背压的落地。

### 6.5 容量估算脚本（应用侧 + 显存侧）

```python
"""部署容量估算：应用侧用 Little's Law 算副本，模型侧算显存三笔账。"""

def app_capacity(qps: float, avg_seconds: float, per_replica_conns: int,
                 peak_factor: float = 5.0, safety: float = 1.5) -> dict:
    """应用侧：在途并发 = QPS × 平均时长；副本数按并发除以单副本上限。"""
    avg_concurrency = qps * avg_seconds
    peak_concurrency = avg_concurrency * peak_factor
    replicas = peak_concurrency / per_replica_conns * safety
    return {
        "平均并发": round(avg_concurrency),
        "峰值并发": round(peak_concurrency),
        "建议副本": round(replicas + 0.5),      # 向上取整
        "单副本并发上限": per_replica_conns,     # 压测得出，不要拍脑袋
    }

BYTES = {"fp16": 2, "int8": 1, "int4": 0.5}

def gpu_memory(params_b: float, layers: int, kv_heads: int, head_dim: int,
               ctx_len: int, concurrency: int,
               weight_dtype="fp16", kv_dtype="fp16") -> None:
    """模型侧：权重 + KV Cache + 开销 三笔账，单位 GB。"""
    weight = params_b * BYTES[weight_dtype]
    # KV：2 份（K 和 V）× 层数 × KV头数 × 头维度 × 字节；Q 不缓存
    kv_per_seq = 2 * layers * kv_heads * head_dim * BYTES[kv_dtype] \
        * ctx_len / 1024**3
    kv_total = kv_per_seq * concurrency
    overhead = (weight + kv_total) * 0.15
    total = weight + kv_total + overhead
    print(f"权重 {weight:.1f} GB｜KV 单路 {kv_per_seq:.2f} × {concurrency} 路 "
          f"= {kv_total:.1f} GB｜开销 {overhead:.1f} GB")
    print(f"运行时合计 {total:.1f} GB，规划建议（含 25% 冗余）{total * 1.25:.1f} GB")

# 例：应用侧 —— 50 QPS、平均 20 秒、单副本 200 并发、峰值 5 倍
print(app_capacity(qps=50, avg_seconds=20, per_replica_conns=200))
# {'平均并发': 1000, '峰值并发': 5000, '建议副本': 38, '单副本并发上限': 200}

# 例：模型侧 —— 7B GQA（8 组 KV 头）INT4 权重 + INT8 KV，4K 上下文，16 路
gpu_memory(params_b=7, layers=32, kv_heads=8, head_dim=128,
           ctx_len=4096, concurrency=16,
           weight_dtype="int4", kv_dtype="int8")
# 权重 3.5 GB｜KV 单路 0.26 × 16 路 = 4.2 GB｜开销 1.2 GB → 单张 24G 卡可承载
```

## 7. 案例

### 案例 A：电商客服 Agent 大促扩容（应用侧）

**场景**：某电商客服 Agent，日常均值 20 QPS、平均 15 秒（平均并发约 300），大促峰值约 30 倍，SLO 要求 P95 首 token 2 秒内。

**做法**：先按 4.1 估算——单副本压测并发上限 300，常态 2 副本起步、min 设 4 留发布冗余；峰值并发约 9000，理论上限 40 副本。HPA 信号从 CPU 换成并发连接数（CPU 版本压测时利用率 30% 不动而排队已爆炸）；低价值高频问题（物流查询）前置规则与缓存拦截约 60% 流量，在线层实际峰值并发降到约 3600，落在 12–18 副本区间（缓存与路由机制见 3.7）；大促前一小时定时预扩到 12 副本，洪峰由 HPA 接管。

**效果（示意）**：大促峰值 6 小时零宕机，P95 首 token 1.8 秒守住 SLO；对比上一季度按 CPU 伸缩的版本，副本响应从滞后 8 分钟到 1 分钟内，超时率从 4.7% 降到 0.3%。

### 案例 B：研究报告 Agent 的异步化改造（削峰填谷）

**场景**：一家金融科技公司的深度研究报告 Agent，单任务 5–10 分钟（检索、多轮分析、写报告），原来走同步 HTTP，网关 60 秒超时，约 30% 请求被中途掐断，客户端重试进一步放大并发。

**做法**：同步改异步三件套——提交接口秒回任务 ID；任务入 Redis 队列，worker 池消费，KEDA 按队列深度在 2–25 副本间伸缩；进度走任务状态轮询，完成推送通知。任务状态机与检查点沿用执行循环的设计（见 2.5），worker 崩溃后任务重投、从断点续跑；队列水位超过 5000 触发背压，入口返回排队预计时长。

**效果（示意）**：交互超时率从 30% 降到 0（提交永远秒回）；任务完成时间中位数仅上升约 40 秒（排队成本）；worker 副本闲时 2 个、忙时 25 个，GPU 与 API 成本随流量近似线性，不再为峰值常备。

### 案例 C：14B 客服模型自部署上线（模型侧）

**场景**：14B 客服模型，日请求 50 万（均值约 6 QPS、峰值数十倍），P99 小于 2 秒，模型月更，数据不能出域——必须自建。

**做法**：选 vLLM（模型月更，TensorRT-LLM 每次重编译不可接受；OpenAI 兼容接口让客服系统零改造迁移）；AWQ-INT4 量化把权重压到约 7 GB，按三笔账规划单卡并发；系统提示长且固定，开前缀缓存（实测命中率 60% 以上）；双副本挂负载均衡，压测目标单卡吞吐达到峰值 1.5 倍留冗余；容量结论写入 Runbook，大促前重放流量更新数字。

**效果（示意）**：单张 80G 卡承载峰值流量，对比朴素 transformers 部署吞吐提升约 3 倍，月度 GPU 成本降约 60%；两次模型月更均为换权重直接上线，无停机。

## 8. 常见坑

1. **同步接口跑长任务**。  
   worker 与连接被占满，网关超时掐断、客户端重试放大并发；长任务一律提交-入队-通知（见 4.3、4.5）。

2. **SSE 被反向代理缓冲或超时断流**。  
   用户看到截断的回答；proxy_buffering off、读超时 300 秒以上、加心跳注释行（见 4.6）。

3. **HPA 只看 CPU**。  
   Agent 等 LLM 返回时 CPU 很低，排队爆炸而副本不动；换并发连接数等自定义业务指标。

4. **会话状态放进程内存**。  
   扩容或滚动更新即「失忆」；状态外置到 Redis，副本无状态（见 4.6）。

5. **按均值容量设计**。  
   峰值一来直接打穿；按峰值乘冗余系数设计，再压测校准（见 4.1、4.8）。

6. **Serverless 跑超时长任务**。  
   任务跑到平台执行上限被硬杀，进度全丢；超分钟级任务进队列 worker（见 4.2）。

7. **队列无背压**。  
   洪峰下积压无限增长，消费延迟雪崩，最终等价于宕机；水位上限加入口快速失败（见 4.5）。

8. **只算权重漏算 KV Cache**。  
   长上下文多并发下 KV 反超权重，容量规划必须算三笔账（见 4.8）。

9. **max-model-len 直接开满**。  
   单路 KV 上限随之暴涨，同卡并发骤降；按业务真实需要收。

10. **月更模型选 TensorRT-LLM**。  
    每次换模型重新编译 engine，维护成本吞掉性能收益；迭代快选 vLLM。

11. **gpu-memory-utilization 拉满**。  
    高峰 OOM 整实例拒绝服务；0.85–0.92 起步压测定。

12. **只看显存不看 P99**。  
    显存塞得下不代表延迟达标，批越大单请求延迟越高；先定 SLO 再定 batch。

13. **容量告警先加卡**。  
    账单翻倍还可能压不回 P99；先软后硬——配额、路由、缓存查完再动硬件（见 4.9）。

14. **量化不回归**。  
    INT4 权重、fp8 KV 都可能伤质量；上线前必须过评估集回归（门禁见 3.5、3.9）。

15. **端侧场景滥用大模型**。  
    输入法续写级任务上云端 LLM，延迟、隐私、成本三项全输；小模型加量化才是正解（见 4.9）。

## 9. 练习

1. 用 Little's Law 估算你项目的容量：给定 QPS、平均请求时长、单副本并发上限，算平均并发、峰值并发与副本数，再用压测验证误差。
2. 打包 Agent 服务镜像并部署，用 nginx 反代 SSE 接口，复现默认配置下的断流，再按 4.6 修复并对比断流点。
3. 部署 CPU 版 HPA，压测观察「排队爆炸而 CPU 不动」的失灵现象；改并发连接自定义指标，记录两种信号的伸缩时间差。
4. 把一个 5 分钟任务异步化：API 提交、Redis 队列、worker 消费、状态轮询；配 KEDA 队列深度伸缩，压一个 10 倍洪峰观察削峰曲线。
5. 会话状态外置改造：把内存会话迁到 Redis，滚动更新验证会话不丢；再人为杀副本验证任意接管。
6. 用 vLLM 部署 7B AWQ 模型，开启前缀缓存，用 vllm bench serve 压出单卡并发与 P99，写进容量 Runbook。
7. 用 6.5 脚本代入你所用模型的层数、KV 头数、head_dim，算 4K 与 32K 上下文的单路 KV，观察 KV 何时反超权重。
8. 给定峰值 50 QPS、P99 2 秒、上下文 8K，写完整容量规划书：应用副本数、GPU 卡型与卡数、冗余与压测方案。
9. 模拟容量告警：把并发压到超限，按「先配额调度、再单机调优、最后加卡」的顺序逐层处置，记录每层处置后的水位变化。

## 10. 小结

- 稳定承载真实流量 = **容量估算（Little's Law：并发 = QPS × 时长）+ 伸缩策略 + 削峰填谷** 三段，缺一段就扛不住某类流量。
- 部署形态四选：**VM（GPU 与数据层）、容器（在线服务主流）、Serverless（事件型短任务）、混合（生产实际形态）**；长任务不上 Serverless。
- 三类流量三种部署：**同步短请求、SSE 流式（不缓冲不掐断）、异步长任务（队列 + worker）**；同步接口不承载长任务。
- 伸缩信号跟着体验走：**在线层看并发连接数，异步层看队列深度**；CPU 对 IO 密集的 Agent 失灵。
- 队列五能力：**削峰、解耦、重试死信、顺序、背压**；队列把崩溃换成排队，必须给用户可见的等待。
- 有状态 Agent：**状态外置优于会话亲和**——无状态副本才配得上自动伸缩。
- 模型侧边界：云 API 撞配额、自建看显存；**流量形态、数据边界、成本拐点**三要素定选型，三引擎默认 vLLM。
- 显存三笔账：**权重 + KV Cache（最高频漏算项）+ 开销**；GQA 与量化（INT4 权重、fp8 KV）是两大杠杆，量化必须过质量回归。
- 容量规划四步：**定 SLO → 算单卡并发 → 峰值 × 冗余定规模 → 压测校准**；按峰值设计不按均值。
- 扩容顺序**先软后硬**：配额与调度（分钟级）→ 单实例优化（小时级）→ 基础设施（天级）；PD 分离与端侧是规模与场景的延伸。
- 这些能力直接支撑：3.7 成本、延迟与可靠性，3.9 CI/CD、版本管理与发布，4.9 部署与运维。
