## 1. 定位

L3 工程层的第 6 个知识点，回答大纲里的关键问题：**如何稳定承载真实流量？**

Demo 阶段一个 `transformers.generate()` 就能交差；生产阶段的推理是另一门学问：GPU 一秒几块钱、显存有限、请求有峰谷、SLO 有 P99 承诺。推理服务化就是把「模型能跑」变成「模型能扛」。

它直接前置依赖 3.1（架构与接口设计）——推理服务是六层架构里「模型侧」的展开，容量规划要从架构约束倒推。它向后支撑：3.7（成本、延迟与可靠性，单位成本由引擎吞吐决定）、3.9（评估门禁与安全发布，deps 含本篇）、4.9（部署与运维，软故障告警建立在容量信号上）。

本篇覆盖三个考点卡：3-6（推理服务化认知）、3-6b（显存估算与容量规划）、3-6c（端侧与边缘推理，趋势观察口径）。

## 2. 一句话定义

推理服务化（LLM Serving）是把模型权重交给推理引擎（Serving Engine），由引擎负责 KV Cache 管理、连续批处理、量化加载与 API 暴露，用最少的 GPU 在 SLO 约束内承载峰值流量的工程体系；容量规划则回答「几张什么卡、怎么扩」。

## 3. 为什么需要

朴素部署（PyTorch + transformers 直接起服务）在真实流量下有四个致命问题：

1. **GPU 空转**：静态批处理（Static Batching）凑满一批才发车，先完成的请求陪着最慢的等，算力利用率常常不到 30%。
2. **显存碎片**：KV Cache 按最大长度预留连续显存，实际利用率低，同卡并发上不去。
3. **没有账本**：不知道一张卡能扛多少并发，扩容靠猜，要么浪费钱要么高峰宕机。
4. **接入成本高**：每个上层应用都要适配私有 API，模型一换全链路改。

推理引擎把这三个问题的解法（连续批处理、PagedAttention、OpenAI 兼容 API）打包成开箱即用的产品；容量规划则用数据替代猜测。一句话：**引擎决定单卡效率，规划决定集群规模，两者共同决定单位 token 成本。**

## 4. 核心原理

### 4.1 推理服务的核心调度：连续批处理

传统静态批处理像班车：凑满一车才发车，先做完的乘客陪等最慢的，车经常空转。连续批处理（Continuous Batching，vLLM/O-RAN 系引擎的标配）像网约车拼车：每个解码步结束后动态补位——完成的请求立刻弹出、排队的请求立刻补进批内空位，GPU 永远满载。同卡吞吐通常提升 2 到 4 倍。

代价是调度复杂度：批内请求序列长度不一，引擎必须做逐请求的状态管理——这正是 PagedAttention 存在的理由（详见 3.7 的原理拆解）。

### 4.2 三大推理引擎对比

| 维度 | vLLM | TensorRT-LLM | llama.cpp |
|---|---|---|---|
| 定位 | 吞吐王者，生态最全 | 极致延迟与吞吐上限 | 边缘与端侧王者 |
| 核心技术 | PagedAttention + 连续批处理 | 按模型编译的 kernel 优化（engine 构建） | GGUF 量化 + CPU/GPU 混合推理 |
| 硬件绑定 | NVIDIA 为主，兼容多卡 | 深度绑定 NVIDIA | CPU/Apple Silicon/低端 GPU 均可 |
| 换模型成本 | 直接加载新权重 | 每次换模型重新编译 engine | 转换 GGUF 即可 |
| 并发能力 | 高（分页显存 + 动态补位） | 最高（调优到位时） | 弱，不适合高并发服务化 |
| API 生态 | OpenAI 兼容，上层零改造 | 需搭配 Triton 等服务层 | 本地单机为主 |
| 典型场景 | 在线 API、Agent 后端、月更模型 | 延迟敏感、模型稳定半年以上 | 本地原型、端侧、离线小任务 |

选型三问定引擎：

1. **延迟敏感还是吞吐敏感？** 在线对话看 TTFT，离线跑批看总吞吐。
2. **部署环境是什么？** 有 NVIDIA 集群、还是笔记本手机车载。
3. **模型迭代频率？** 月更选 vLLM（直接换权重），半年不动才值得为 TRT-LLM 的编译优化买单。

工程默认答案通常是 vLLM：性能够用、生态最全、模型月更无痛。什么时候换 TRT-LLM：P99 要求压到 500ms 以内、模型长期稳定、且有 NVIDIA 调优人力，三者同时满足再迁移。

### 4.3 显存三笔账

部署模型像开酒店：只算买楼钱一定破产，变动成本才是运营大头。

| 科目 | 公式 | 性质 | 示例（7B，fp16，4K 上下文，16 路） |
|---|---|---|---|
| 权重账 | 参数量 × 每参数字节（fp16=2B、INT8=1B、INT4=0.5B） | 固定开销 | 7×2=14 GB |
| KV Cache 账 | 2×层数×KV头数×head_dim×序列长×字节×并发 | 随并发与上下文线性涨 | 单路约 2.1 GB，16 路约 34 GB |
| 激活与框架开销 | 权重+KV 之和的 10%~20% | 随 batch 增大 | 约 7 GB |
| 合计 | 三项相加再留 20%~30% 冗余 | — | 约 55~60 GB |

三个关键数字记牢：

- **7B fp16 权重 14 GB，INT4 约 3.5 GB**——量化是显存账本的第一杠杆。
- **KV Cache 是最高频漏算项**：MHA 结构的 7B（32 层、32 头、128 维）fp16 下每 token 约 512 KB，4K 上下文单路就吃 2.1 GB；16 路并发时 KV（34 GB）是权重（14 GB）的两倍多。只报「模型 14 GB」是容量规划的经典失分点。
- **GQA 直接给 KV 减肥**：8 组 KV 头共享，KV 账降到 1/4；MLA（DeepSeek 系）压缩更狠。选模型时 KV 结构就是成本结构。

### 4.4 容量规划四步

```text
第一步 定 SLO        P99 延迟 / 单卡吞吐目标 / 可用性
第二步 算单卡并发     单请求显存（权重份额+KV+开销）→ 卡的显存上限内能塞几路
                     再验算 decode 速度：TPOT × 输出长度是否满足 P99
第三步 峰值定卡数     峰值 QPS ÷ 单卡 QPS × 冗余系数（1.5~2.5）
第四步 压测校准       真实流量回放压 P99 与吞吐 → 调副本数与 HPA 阈值
```

两条纪律：

- **按峰值设计，不按均值**：供水系统按高峰人数设计，按均值必炸。
- **延迟约束常常比显存约束先到**：显存算得下不代表 P99 达标——批越大吞吐越高但单请求延迟也涨，在线对话小 batch 优先，离线批处理大 batch 填满。先定 SLO 再定 batch。

### 4.5 量化：显存账本的第一杠杆

| 精度 | 每参数字节 | 7B 权重 | 说明 |
|---|---|---|---|
| fp16/bf16 | 2 B | 14 GB | 质量基线 |
| INT8（W8A16） | 1 B | 7 GB | 几乎无损，省一半 |
| INT4（AWQ/GPTQ） | 0.5 B | 3.5 GB | 主流生产选择，质量损失可接受 |
| KV Cache 量化（fp8/int8） | — | KV 减半 | 叠加在权重量化之上 |

13B 模型：fp16 权重 26 GB + 8 路并发 4K KV 约 8 GB + 开销 15% ≈ 39 GB，单张 40G 卡放不下；换 AWQ-INT4 后权重 6.5 GB，合计约 20 GB，单张 24G 卡轻松承载。这就是量化的实际意义：**同样预算下把可用并发翻倍，或同样并发下把卡数减半。**

### 4.6 端侧与边缘推理（趋势观察口径）

端侧推理是把 LLM 跑在手机、AI PC、车载 NPU（Neural Processing Unit）上。诚实标注：硬件生态证据充分，但面试真题尚少，作为 3-6/3-6b 的延伸视角掌握。

四大动机：隐私（数据不出设备）、离线可用、本地毫秒级延迟、边际成本近零。

技术三件套：小模型（1B~3B 端侧特调）+ 激进量化（INT4/W4A16）+ 端侧运行时（llama.cpp、MLC、各厂 NPU SDK）。旗舰手机 NPU 算力已达数十 TOPS，统一内存架构让 CPU/GPU/NPU 共享显存——硬件为端侧 AI 备好了灶。

端云协同是架构核心：端侧小模型做第一道处理（意图识别、脱敏、简单任务），复杂任务才升级云端大模型，路由是分工的关键。典型场景判断：输入法本地续写（高频+轻量+隐私敏感）是端侧教科书场景；通用百科问答、复杂代码重构留给云端。

### 4.7 PD 分离与扩容顺序

**PD 分离（Prefill-Decode Disaggregation）**：把 prefill（算你的问题，compute-bound，吃算力）和 decode（逐字生成，memory-bandwidth-bound，吃显存带宽）拆到不同实例，各自用最合适的硬件形态与批策略，中间靠 KV Cache 传输衔接。业界方案（Mooncake、DistServe 一类架构）已验证：分离后各自填满资源，长输入场景的 P99 与吞吐同时受益。代价是系统复杂度上升——KV 传输链路、路由一致性、故障恢复都要管，中小规模先用一体机，规模上来了再拆。

**扩容顺序：先模型配额，再基础设施。** 容量告警触发时，按性价比从软到硬逐层加码：

| 层级 | 手段 | 见效速度 | 成本 |
|---|---|---|---|
| 第一层：模型配额与调度 | 限流、按优先级排队、降级到小模型、调大批参数、开前缀缓存 | 分钟级 | 零 |
| 第二层：单实例优化 | 量化（INT4 权重/KV fp8）、调 gpu-memory-utilization 与 max-num-seqs | 小时级 | 低 |
| 第三层：基础设施扩容 | 加副本、TP 拆分、加卡、PD 分离 | 天级 | 高 |

顺序反了就是事故：流量尖峰先无脑加卡，账单翻倍还可能压不回 P99——先检查是不是 30% 的重复请求没走缓存、是不是长系统提示没开前缀共享。软件层的钱省完了，再加硬件。

生产推理服务的全景与容量规划闭环：

```text
│    ↓ OpenAI 兼容 API                                │
├────────────────────────────────────────────────────┤
│  接入层：负载均衡 → 限流/配额 → 模型路由              │
```

### 6.2 显存三笔账估算脚本

```python
"""推理显存估算器：权重 + KV Cache + 开销，输入模型结构与业务参数，输出容量规划账本。"""

BYTES_PER_PARAM = {"fp16": 2, "bf16": 2, "int8": 1, "int4": 0.5}


def kv_bytes_per_token(
    num_layers: int, kv_heads: int, head_dim: int, dtype: str = "fp16"
) -> int:
    """单 token 的 KV 显存：2 份（K 和 V）× 层数 × KV 头数 × 头维度 × 字节。Q 不缓存。"""
    return 2 * num_layers * kv_heads * head_dim * int(BYTES_PER_PARAM[dtype] * 2 / 2)


def estimate(
    params_b: float, num_layers: int, kv_heads: int, head_dim: int,
    ctx_len: int, concurrency: int,
    weight_dtype: str = "fp16", kv_dtype: str = "fp16",
    overhead_ratio: float = 0.15, safety_margin: float = 0.25,
):
    weight_gb = params_b * BYTES_PER_PARAM[weight_dtype]
    kv_per_seq_gb = kv_bytes_per_token(num_layers, kv_heads, head_dim, kv_dtype) \
        * ctx_len / 1024**3
    kv_total_gb = kv_per_seq_gb * concurrency
    overhead_gb = (weight_gb + kv_total_gb) * overhead_ratio
    total_gb = weight_gb + kv_total_gb + overhead_gb
    planned_gb = total_gb * (1 + safety_margin)

    print(f"权重账      ：{weight_gb:6.1f} GB（{params_b}B @ {weight_dtype}，固定）")
    print(f"KV Cache 账 ：{kv_total_gb:6.1f} GB（单路 {kv_per_seq_gb:.2f} GB × {concurrency} 路 @ {ctx_len} 上下文）")
    print(f"开销账      ：{overhead_gb:6.1f} GB（激活与框架，按 {overhead_ratio:.0%}）")
    print(f"运行时合计  ：{total_gb:6.1f} GB")
    print(f"规划建议    ：{planned_gb:6.1f} GB（含 {safety_margin:.0%} 冗余）")

    gpu_cards = {"A100 80G": 80, "A100 40G": 40, "A10 24G": 24, "4090 24G": 24}
    for name, mem in gpu_cards.items():
        fit = "可单卡承载" if mem >= planned_gb else "需要量化 / TP 拆分 / 降并发"
        print(f"  {name:10s}：{fit}")


# 例 1：7B MHA（32 层、32 KV 头、128 维）fp16、4K、16 路
estimate(params_b=7, num_layers=32, kv_heads=32, head_dim=128,
         ctx_len=4096, concurrency=16)
# 权重 14 GB；单路 KV 2.1 GB，16 路 33.6 GB；合计约 55 GB → 40G 卡放不下

# 例 2：同模型换 GQA（8 组 KV 头）+ INT4 权重 + KV fp8
estimate(params_b=7, num_layers=32, kv_heads=8, head_dim=128,
         ctx_len=4096, concurrency=16, weight_dtype="int4", kv_dtype="int8")
# 权重 3.5 GB；单路 KV 0.26 GB，16 路 4.2 GB；合计约 9 GB → 单张 24G 卡承载
# 三层优化叠加后，同卡并发能力提升一个数量级——这就是账本的意义
```

### 6.3 多副本容量与扩容判断（伪代码清单）

```yaml
slo:
  ttft_p99_ms: 2000          # 首 token 时间承诺
  tpot_ms: 50                # 每 token 生成时间承诺

  peak_qps: 100              # 峰值流量（按大促/工作日高峰回放取值）

  L1_quota:                  # 分钟级，零成本

    - 权重 INT4 / KV fp8 量化（若尚未开启）
    - max-num-seqs 与 gpu-memory-utilization 调优
  L3_infra:                  # 天级，高成本
    - HPA 按并发水位扩副本
    - 加卡 / TP 拆分 / PD 分离改造
```

## 7. 案例

### 案例 A：14B 客服模型上线（引擎选型）

**场景**：14B 客服模型，日请求 50 万（均值约 6 QPS、峰值数十倍），P99 小于 2 秒，模型月更。

**决策**：选 vLLM。负载形态是吞吐敏感型，vLLM 的连续批处理加 PagedAttention 正是把同卡吞吐做满的方案；模型月更，TensorRT-LLM 每次都要重新编译 engine，维护成本不可接受；OpenAI 兼容接口让客服系统零改造迁移。

**上线方案**：AWQ-INT4 量化（14B 权重约 7 GB），单卡承载较高并发；系统提示长且固定，开前缀缓存（命中率 60% 以上）；双副本挂负载均衡；压测目标 P99 小于 2 秒、单卡吞吐达到峰值的 1.5 倍留冗余。迁移 TRT-LLM 的预留条件写进文档：P99 压到 500ms 以内且模型稳定半年再议。

**效果**：单张 80G 卡承载峰值流量，对比朴素 transformers 部署吞吐提升约 3 倍，月度 GPU 成本降约 60%。

### 案例 B：13B 在线 API 的 GPU 规划

**场景**：峰值 100 QPS、P99 小于 2 秒、上下文 8K。规划 GPU 资源。

**四步走**：

1. **先量化**：fp16 权重 26 GB 起步太高，上 AWQ-INT4 权重约 6.5 GB；KV 每路 8K 约 1~2 GB（GQA 结构取低值）。
2. **算单卡并发**：80G 卡减去权重与开销，可容纳 25~30 路 8K 并发；验算 decode 速度满足 P99，靠连续批处理与前缀缓存把有效吞吐拉到单卡 30~50 QPS。
3. **峰值定卡数**：100 QPS 按 2 倍冗余压到 40 QPS/卡，需要 4~6 副本（或更多 A10 分摊）。
4. **压测校准**：真实流量回放压 P99 与吞吐，按实测调副本数与 HPA 阈值。

**效果**：规划误差从「拍脑袋买卡」收敛到压测偏差 15% 以内；结论写入容量 Runbook，大促前只需重放流量更新数字。

### 案例 C：车载助手的端侧部署（趋势观察）

**场景**：语音交互要求首响 300ms 内、隧道断网可用、乘客对话不上云。

**方案**：三条需求逐条映射——延迟与断网要求推理本地化，隐私要求零上传，纯端侧是必选项。3B 级车载特调模型 INT4 量化跑车机 NPU；任务限定在导航问答、车控指令、闲聊安抚，与小模型能力匹配；少数复杂问题走云端，但仅上传脱敏后的抽象请求；端侧置信低且无网时坦诚降级。

**效果**：首响延迟从云端方案的 800ms 降到 250ms 以内，断网可用率 100%，网络出口抓包验证零原始语音上传。同时向需求方诚实标注取舍：部分复杂请求降级是趋势观察期技术与需求的匹配过程。

## 8. 常见坑

1. **只算权重漏算 KV Cache**。最高频失分点：长上下文多并发下 KV 常反超权重，规划必算三笔账。
2. **按最大上下文开 max-model-len**。上下文上限直接决定单路 KV 上限，按业务真实需要收，不要开满。
3. **静态批处理直接上生产**。GPU 空转严重，吞吐差数倍；生产一律连续批处理。
4. **月更模型选 TRT-LLM**。每次换模型重新编译 engine，迭代快的团队维护成本吞掉性能收益。
5. **把 llama.cpp 用在高并发服务化**。它是端侧与本地王者，并发能力撑不起在线服务。
6. **gpu-memory-utilization 拉满**。留不出激活与碎片余量，高峰 OOM；0.85~0.92 起步压测定。
7. **按均值容量设计**。峰值流量打穿服务；按峰值乘冗余系数设计，再压测校准。
8. **只看显存不看 P99**。显存算得下不代表延迟达标，批越大单请求延迟越高，先定 SLO 再定 batch。
9. **长系统提示不开前缀缓存**。客服类场景命中率 60% 以上，白扔的算力就是白扔的钱。
10. **量化不回归**。INT4 权重、fp8 KV 都可能伤质量，上线前必须过 golden set 回归。
11. **容量告警先加卡**。先查配额、路由、缓存等软件层，30% 的容量问题不用花一分钱硬件。
12. **一体机硬撑长输入场景**。prefill 与 decode 资源画像完全不同，规模上来后 PD 分离收益显著。
13. **端侧场景滥用大模型**。输入法续写级别的任务上云端大模型，延迟、隐私、成本三项全输；小模型加量化才是正解。
14. **没有容量 Runbook**。扩容顺序、压测脚本、SLO 目标不落文档，事故时全靠临场发挥。

## 10. 小结

- 推理服务化 = 引擎（单卡效率）+ 容量规划（集群规模），共同决定单位 token 成本。
- 三引擎定位：**吞吐 vLLM、极致延迟 TRT-LLM、边缘端 llama.cpp**；选型三问：延迟还是吞吐、部署环境、迭代频率。
- vLLM 双杀手锏：**PagedAttention 分页显存 + 连续批处理动态补位**，同卡吞吐翻数倍。
- 显存三笔账：**权重（固定）+ KV Cache（随并发与上下文线性涨，最高频漏算）+ 激活开销（10%~20%）**，再留 20%~30% 冗余。
- KV 公式：**2×层数×KV头数×head_dim×序列长×字节×并发**；GQA 直接砍到 1/4。
- 容量规划四步：**定 SLO → 算单卡并发 → 峰值×冗余定卡数 → 压测校准**，按峰值不按均值。
- 量化是第一杠杆：INT4 让权重账除以四，KV fp8 再减半——每项量化都要过质量回归。
- 端侧推理（趋势观察）：小模型 + 激进量化 + NPU 运行时，四大动机是隐私、离线、延迟、边际成本；架构核心是端云协同路由。
- PD 分离：prefill 吃算力、decode 吃带宽，规模上来后拆开各自填满资源。
- 扩容顺序：**先模型配额与调度（分钟级零成本），再单实例调优，最后才动基础设施**。
- 这些能力向后支撑：3.7 的单位成本分析、3.9 的发布门禁、4.9 的容量告警与软故障防御。
