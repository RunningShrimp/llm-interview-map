# 讲解 4.10 作品集与复盘

> 说明：4.1 的百行 MVP 是这条作品线的起点——从地摊到展厅是同一个项目的两次呈现。  
> 本篇是 L4 收口：把 4.8 的红队结果、4.9 的故障处置、3.5 的指标全部整理成别人能看、能验、能信的证据链。本篇合并本站 4-10、4-10b、4-10c 三张考点卡。

---

## 1. 定位

L4 工程化层最后一个知识点，也是整个学习路线的出口。

它解决一个根本问题：**你确实会做，但如何让别人（面试官、评审、协作方）相信你会做？**

前置依赖：4.1 最小可用 Agent——作品集里的项目从那个 CLI 原型长出来。本篇同时收拢前面所有工程化的产出物：3.5 的评估指标、4.8 的红队报告、4.9 的故障复盘，都是作品集的展品。

本篇覆盖三张考点卡：作品集四件套（4-10）、STAR 讲述法与追问防线（4-10b）、架构师的表达——代价论证与出题能力（4-10c）。

## 2. 一句话定义

作品集是工程能力的证明文件：架构图、指标表、可演示 Demo、复盘文档四件套，外加 STAR 讲项目故事——面试官不信形容词，只信可验证的证据链与诚实的取舍分析。

## 3. 为什么需要

简历上写「精通 Agent 开发、熟悉 RAG」是形容词——面试官每天看 200 遍，默认不信。同一份能力，呈现方式决定可信度：

| 呈现方式 | 典型内容 | 面试官接收到的信号 |
|---|---|---|
| 形容词式 | 「精通」「熟悉」「深入了解」 | 无法验证，默认存疑 |
| 名词堆砌式 | 「用了 vLLM/RAG/MCP/多 Agent」 | 像教程复刻，深挖即露馅 |
| 证据链式 | 架构图带理由 + 指标带测量法 + 能跑的 Demo + 诚实的复盘 | 「决策是他自己做的，数字是真的」 |

三个硬理由：

1. **面试深挖的本质是验证据链**。追问「这个数字怎么来的」就是在敲墙——每句结论必须踩在可复现的证据上，敲到没有地基的地方整面墙塌掉。
2. **作品集替你回答没被问到的问题**。架构图上每个组件旁写着「为什么需要它」，面试官的追问大多已经写在纸上了。
3. **复盘是区分「自己做的」与「教程复刻」的唯一信号**。教程给不出「放弃了语义缓存，因为查询太离散命中率不足 5%」这种句子——它需要真实的假设、实验、数据、结论。

## 4. 核心原理

### 4.1 作品集四件套

展厅类比：进门先看总览图（架构图），每件展品旁立着检测报告（指标表），中间是试用台（Demo），出口挂着开发日记（复盘文档）。

| 件套 | 形式 | 证明什么 | 缺件的后果 |
|---|---|---|---|
| 架构图带理由 | 分层图 + 每个组件一句存在理由与选型依据 | 全局认知：系统是你设计的 | 深挖架构时讲不清全貌 |
| 指标表带测量法 | 评估分/p95 延迟/成本/红队结果，每个数字标测量方法 | 用数据说话，且知道数字怎么来 | 数字被追问一句就塌 |
| 三分钟 Demo | 一镜到底视频或在线链接 | 东西真的存在且能跑 | 只能口头描述可信度骤降 |
| 复盘文档带放弃方案 | 踩坑、取舍（放弃 X 因为 Y）、差距分析 | 思考深度，不是教程复刻 | 只剩成功叙事，像背的 |

逐件展开：

**架构图带「为什么」。** 每个组件旁一句存在理由（删掉它会坏什么）和关键选型依据（如「选混合检索是因为 30% 的查询含产品编号」）。图不是画给面试官看的，是替你回答追问的。

**指标必须带测量法。** 「解决率 76%（人工标注 200 例）」「p95 11s（压测脚本）」——每个数字能回答「怎么测的」才可信。有迭代记录更好：「Recall@5 从 60% 到 89%，三轮切分策略迭代」比一个孤立的 89% 有说服力得多。

**Demo 三分钟一镜到底。** 结构固定：问题 → 架构一瞥 → 演示主流程 → 指标页收尾。在线 Demo 必须有兜底：演示脚本预演 + 录屏备份 + 指标截图。现场翻车是最大事故，但预案本身也是作品——4.9 的运维思维在演示日的投射。

**复盘写取舍与差距。** 有力的复盘不写流水账（「第一周搭框架、第二周调模型」），写两类句子：「放弃了 X 因为 Y」（证明决策过程）、「指标没达预期的原因与后续」（证明诚实与成长性）。全绿的指标反而可疑。

### 4.2 STAR 讲述法：把项目讲成有证据链的故事

STAR = 情境（Situation）- 任务（Task）- 行动（Action）- 结果（Result）。四幕各有要求：

| 要素 | 内容 | 常见错误 | 证据要求 |
|---|---|---|---|
| S 情境 | 业务痛点，一句话带量化 | 铺垫太长、没有数字 | 痛点数据来源 |
| T 任务 | 你的职责边界，目标带数字 | 说「我们」混淆贡献 | 目标达成口径 |
| A 行动 | 关键决策与取舍，挑最有含金量的难点深讲 | 流水账、名词堆砌 | 为什么选 A 不选 B + 失败尝试 |
| R 结果 | 量化影响 + 复用/溢出价值 | 「效果不错」零分 | 测量方法 + 每个数字可复现 |

讲述原则：

1. **有冲突才有故事**。「命中率只有 60%，我怎么通过切分重构提到 85%」是高潮；「我们用了 RAG，效果不错」是噪音。
2. **决策胜过苦劳**。深挖考的是判断力：为什么选 A 不选 B、坑怎么发现怎么填——取舍与反思比技术名词高一个段位。
3. **每个数字备好测量法**。被问「85% 怎么测的」，标准答案是：「300 条标注测试集、Recall@10 口径、与同一基线对比、每周回归」——三层证据：数据来源、对比方式、极端追问的应答。
4. **诚实边界**。不熟的细节坦然承认并给出推理——编造被追两层必穿，诚实加思考力反而加分。

### 4.3 删掉测试自测法

讲之前先自己考自己：把项目里任一组件拿出来，问两个问题——

```text
问 1：删掉它，系统会坏在哪？
问 2：换掉它，要改几处？
```

- 两个都答不上 → 要么组件真冗余（删掉降复杂度），要么你还没真正理解自己的系统（回去补课）。
- 答得出 → 这个组件的存在理由与耦合度就是面试追问的标准答案。

这个自测把作品集从「组件堆砌」里筛出来：每个组件都能说出存在理由，系统才是自己的设计——否则深挖时立刻露馅。

### 4.4 追问防线

深挖不是刁难，是验证据链。常见追问与应答策略：

| 追问类型 | 典型问题 | 应答策略 |
|---|---|---|
| 数字来源 | 「76% 怎么测的？」 | 评估集构成 + 指标口径 + 对比方式，当场可复现 |
| 选型理由 | 「为什么混合检索不用纯向量？」 | 具体问题 + 量化基线 + 干预 + 量化结果 |
| 失败尝试 | 「试过什么不行的方案？」 | 坦承失败 + 失败原因 + 从中得到的约束 |
| 贡献边界 | 「这部分是你做的还是团队的？」 | 说「我」不说「我们」，边界讲清 |
| 反思成长 | 「最大的坑？重来改什么？」 | 早建评估集之类的教训 + 转化成方法论 |

架构师级别的追问是「代价题」：「你的方案有什么代价？什么情况下你会换？」应答用代价三件套：

```text
每个选择说清三件事：
1. 付出的代价 —— 敢说代价，说明你真做过
2. 成立的边界条件 —— 说明你会迁移，不是死记
3. 被放弃的备选方案 —— 说明你思考过全空间
```

示例：「选 RAG 而非微调——代价是检索链路的持续维护、检索错则全错、多了约 200ms 检索延迟；代价在『知识周更且必须溯源』的约束下可接受；微调换来零检索延迟与风格内化，但知识凝固、每次更新重训、无法溯源，在我们的约束下不可接受；如果知识更新频率降到季度以下且不需溯源，会重新评估微调。」

配一条自检：**费曼出题法**——为项目里的技术点出一道能区分「背过」与「掌握」的题（场景 + 两难 + 追问链）。出不出打在核心矛盾上的题，说明还没真懂；面试前给自己出三道，答不顺就回去补。

### 4.5 可复现材料包

别人能不能验证，取决于材料包是否自足：

| 材料 | 内容 | 验证方式 |
|---|---|---|
| README | 项目导览：一图一表三链接（架构/指标/Demo/复盘/运行） | 五分钟读完知道全貌 |
| 评估数据集 | 300 条标注样本 + 口径说明 | 评审可自己跑评测 |
| 评测脚本 | 一条命令复现指标表全部数字 | 数字可复算 |
| Trace 样例 | 3-5 条典型执行 trace（含一次故障处置） | 证明 trace 体系真实存在 |
| 红队报告 | 4.8 的扫描报告 + 修复记录 | 证明安全评估做过 |
| 复盘文档 | 踩坑/取舍/差距分析 | 证明思考深度 |
| commit 历史 | 分阶段的施工记录 | 证明过程真实、渐进 |

## 5. 架构 / 流程

作品集的结构（展厅动线）：

```text
┌────────────────────────────────────────────┐
│ README（导览）                              │
│   一句项目定位 + 一图一表三链接              │
└─────────────┬──────────────────────────────┘
              ↓
┌────────────────────────────────────────────┐
│ 架构图（总览图）                            │
│   分层 + 每组件一句「删掉会坏什么」          │
└─────────────┬──────────────────────────────┘
              ↓
┌────────────────────────────────────────────┐
│ 指标表（检测报告）                          │
│   每个数字带测量法与迭代记录                 │
└─────────────┬──────────────────────────────┘
              ↓
┌────────────────────────────────────────────┐
│ Demo（试用台）                              │
│   3 分钟一镜到底：问题→架构→演示→指标        │
│   兜底：演示脚本 + 录屏 + 截图              │
└─────────────┬──────────────────────────────┘
              ↓
┌────────────────────────────────────────────┐
│ 复盘（开发日记）                            │
│   踩坑 + 放弃的方案（X 因为 Y）+ 差距分析    │
└────────────────────────────────────────────┘
```

三分钟 Demo 的时间轴脚本：

```text
0:00-0:20  问题：一句话痛点 + 一句定位（不要超过 20 秒）
0:20-0:50  架构一瞥：架构图过一遍，只点 3 个关键组件的存在理由
0:50-2:20  主流程演示：一个真实问题从提问到带引用的回答一镜到底
2:20-2:50  指标页：评估分、p95、成本、红队结果各 5 秒，念测量法
2:50-3:00  收尾：复现方式（一条命令）+ 材料包链接
```

## 7. 案例

### 案例 A：知识库问答 Agent 的完整作品集

**场景**：求职者把一个企业知识库项目整理成四件套参加面试。

**做法**：README 五分钟导览；架构图上每个组件标存在理由（Rerank 那条直接写「删掉 Recall@5 掉 18 个点」）；指标表 12 个数字全部带测量法，专设「没达标的指标」诚实区（表格类问题 64%，写明原因与排期）；Demo 三分钟一镜到底加录屏备份；复盘写两条放弃方案（语义缓存命中率不足 5%、全量微调改为 RAG+LoRA）。

**效果**：二面深挖 40 分钟，面试官的五个追问（数字来源、切分迭代、放弃原因、删掉 Rerank 会怎样、故障处置）全部命中材料里已写好的内容——证据链闭合。示意量级：整理前简历过筛率约 1/10，整理后约 1/3。

### 案例 B：一段三分钟 STAR 叙述

**场景**：面试官说「讲一个你最有挑战的项目」。

**叙述**：S——公司 2000 人，制度文档散落 5 个系统，员工日均花 40 分钟找文档（来源：内部调研，n=800）。T——我作为 2 人小组的技术负责人，从 0 到 1 搭建知识库问答，目标 3 个月自助解决率 60%。A——三个关键决策：选 RAG 而非微调（知识周更、必须溯源）；自研切分——通用切分把 Recall@5 卡在 60%，盲调两周后先建评估集，再三轮迭代到 85%；权限做在检索层前置过滤（合规红线）。R——上线 3 个月解决率 68%，日均节省 300 人时，命中率爬到 88%；方案复用到第二条业务线。全部数字可复现，仓库里 `make eval` 一条命令。

**要点**：贡献说「我」；行动只深讲一个难点（切分），并主动暴露「盲调两周才建评估集」的教训；每个数字预判了「怎么测的」追问。

### 案例 C：代价三件套应答「为什么 RAG 不微调」

**场景**：资深岗追问：「你们为什么选 RAG？代价呢？」

**应答**：核心矛盾是知识时效与行为内化的取舍。痛点是知识每周更新且必须可溯源，这是 RAG 的主场。代价如实说三条：检索链路持续维护、事故面变大；检索质量决定答案质量，检索错则全错，所以要持续投 30% 精力在评测调优上；比微调内化的响应多约 200ms 检索延迟（用缓存对冲）。被放弃的微调换来零检索延迟与口吻内化，但知识凝固、每次更新重训、无法溯源——约束下不可接受。边界条件：知识更新频率降到季度以下且不需溯源时，重新评估。

**效果**：没有一句优点背诵，四要素（矛盾、代价、备选、边界）齐备——这是架构师表达的满分模板。

## 8. 常见坑

1. **复盘写成流水账**。「第一周搭框架第二周调模型」零信息量。对策：写取舍与悔恨——「放弃了 X 因为 Y」「没达预期的原因与后续」。
2. **数字不带测量法**。「解决率 76%」被问一句「怎么测的」就塌。对策：每个数字旁标评估集、口径、对比方式。
3. **只讲成功**。全绿指标反而可疑，面试官只能推断没遇困难或没复盘。对策：设「没达标的指标」诚实区，配原因与计划。
4. **Demo 无兜底**。现场网络一抖全场安静。对策：预演脚本 + 本地热备 + 录屏 + 指标截图四层保险。
5. **组件堆砌**。每个组件都答不出删掉会坏什么，深挖立刻露馅。对策：讲之前跑一遍删掉测试自测清单。
6. **贡献说「我们」**。边界模糊，无法评估个人能力。对策：涉及自己的部分说「我」，团队部分明确说「团队」并划清自己那一段。
7. **追逐时髦名词**。多 Agent、MCP 全堆上去，与问题规模不匹配。对策：每个组件过删掉测试——答不出存在理由的砍掉。
8. **材料不可复现**。指标没有脚本佐证，评测集不随仓库提供。对策：一条命令复现全部数字，数据集入库。
9. **作品集与简历数字打架**。简历写 90%，作品集指标表写 76%。对策：所有对外材料同源同版本，统一从 metrics.md 引用。
10. **复盘不写放弃的方案**。丢掉了区分「自己做的」与「教程复刻」的最强信号。对策：至少写两条「放弃 X 因为 Y」，含假设、实验、数据、结论。
11. **被追问时硬撑**。不熟的细节现编，两层追问必穿。对策：诚实承认 + 给出推理过程，诚实边界本身就是加分项。
12. **最后一刻才整理**。作品集是过程产物，trace、红队报告、复盘都要平时留档。对策：把「留证据」做成工程习惯——4.8/4.9 的每份产出都是现成展品。
13. **架构图只画框不写理由**。图成了装饰，追问全靠临场。对策：每个组件旁一行「删掉会坏什么」。
14. **只准备讲述不准备出题**。讲得顺不代表懂。对策：费曼出题法自检——为项目出三道打在核心矛盾上的题，答不顺就补课。

## 9. 练习

1. 选一个你做过的 Agent 项目，列出四件套现状，找出缺失件并补齐。
2. 为架构图上每个组件写一句「删掉会坏什么」，写不出的组件决定删掉或补课。
3. 把指标表里每个数字补上测量法：评估集大小、口径、对比方式、工具。
4. 用 STAR 写一段三分钟项目叙述，为每个数字预写「怎么测的」应答。
5. 用代价三件套重写你最常被问的选型题（RAG vs 微调、单 Agent vs 多 Agent 等）。
6. 实践费曼出题法：为项目里的技术点出三道「场景 + 两难 + 追问链」的题，自己限时作答。
7. 制作可复现材料包：一条命令跑通全部指标复算，评测集随仓库入库。
8. 模拟一次演示日翻车：拔网线/换环境跑你的 Demo 兜底流程，记录恢复时间并改进预案。

## 10. 小结

- 面试官不信形容词，只信证据链；作品集是把「会做」变成「能证明会做」的工程。
- 四件套：架构图带组件存在理由、指标表带测量法、三分钟一镜到底 Demo、复盘带放弃方案——各自堵死一类质疑。
- 复盘里最有说服力的是「放弃 X 因为 Y」：假设、实验、数据、结论的完整决策过程，教程复刻给不出。
- STAR 四要素：情境带量化痛点、任务带职责边界、行动挑最难的决策深讲、结果带测量方法。
- 深挖的本质是敲墙验地基：每个数字备好数据来源、对比方式、极端追问三层证据。
- 删掉测试自测：每个组件答得出「删掉会坏什么」与「换掉改几处」；答不出就删掉或补课。
- 架构师表达三件套：代价、边界条件、被放弃的备选——敢说代价说明真做过。
- 诚实边界是防线也是加分项：不熟就承认并给推理，编造两层追问必穿。
- 费曼出题法自检：出不出打在核心矛盾上的题，说明还没真懂。
- 可复现材料包让一切可验证：README 导览 + 数据集 + 一条命令复现 + trace 样例 + commit 历史。
- 演示日的翻车预案是 4.9 运维思维的投射：热备、固定输入、静态备份。
- 作品集不是最后一刻的包装，而是 3.5/4.8/4.9 全程留档的自然产物——平时留证据，临场讲故事。
