# 讲解 2.1 Agent 定义与范式

> 说明：L1 已经备齐了零件——1.3c 的工具调用与参数校验给了「手」，1.5 的上下文管理给了「记忆」。2.1 把零件组装成 Agent：它是什么、谱系上处在什么位置、边界在哪。规划（2.2）、工具防护（2.3）、记忆机制（2.4）、执行循环（2.5）都在本篇框架上展开。

---

## 1. 定位

L2 第一章，Agent 知识体系的总纲。它回答两个问题：**Agent 到底是什么（定义不清则一切讨论失焦）**，以及**什么时候该用 Agent、什么时候不该（范式选型是 Agent 工程的第一个决策）**。

前置：1.3c（Function Calling——工具是 Agent 的手脚，没有工具调用的「Agent」只是嘴上说说）、1.5（上下文管理——多步执行中不失忆的基础）。后续全部 L2 章节都挂在本篇定义的四件套框架上：2.2 规划展开四件套中的「规划」，2.4 展开记忆，2.5 展开循环，2.7/2.7b 回答本篇留下的选型问题的完整版，2.8 处理一个大脑不够拆成团队的情形。

面试里「讲讲你对 Agent 的理解」考的不是名词解释，而是谱系判断力：能不能一句话说清 Chatbot、Workflow、Agent 的分界，能不能判断一个需求该落在谱系的哪一格。

## 2. 一句话定义

AI Agent = 以 LLM 为大脑的智能体：LLM 负责理解、推理、决策，外加任务清单（规划）、笔记本（记忆）、门禁卡（工具），在感知-思考-行动-观察的循环中**由模型自己决定下一步做什么**，直到目标完成。分水岭只有一条：**下一步由谁决定**——人写死的流程是 Workflow，模型决定的是 Agent。

## 3. 为什么需要

LLM 原生形态是 Chatbot：一问一答，只动嘴。它有三个天然天花板：

1. **不能作用于真实世界**。用户问「帮我订下周三的会议室」，Chatbot 只能输出一段「请登录 OA 系统后……」的操作指南；真正的预订动作它做不了——没有工具，模型只有嘴。
2. **不能处理多步任务**。「把这周数据整理成周报发给老板」需要查数据、做表、写摘要、发送四个动作；一问一答的形态没有跨步骤的状态与推进机制。
3. **不能应变**。真实任务的路径事先未知：查数据发现字段缺失，要回头补；订会议室发现满员，要换时间。固定脚本写不完所有分支，需要有人「边干边决定」。

Agent 对症下药：工具让它能动手，记忆让它跨步不失忆，规划让它拆解目标，循环让它持续推进并应变。**但自主性是能力也是代价**——一旦模型决定下一步，行为就不再完全可预测。所以本篇的另一半是边界：什么时候不该让模型决定。

## 4. 核心原理

### 4.1 三分谱系：谁决定下一步

判断一个系统属于哪一格，只看一个问题：**「下一步做什么」由谁决定**。

| 形态 | 下一步由谁决定 | 路径 | 例 | 成本 | 可预测性 |
|---|---|---|---|---|---|
| Chatbot | 用户（一问一答） | 无路径 | 客服问答、闲聊 | 低 | 完全可预测 |
| Workflow | 开发者（预先编排） | 固定，写死在代码/编排图里 | 每早 8 点日报、固定流水线 | 中 | 高 |
| Agent | 模型（循环中自主决策） | 开放，运行时生成 | 开放式调研、复杂运维排障 | 高 | 低 |

三个判据辅助细分：

1. **分支数量**：分支少且能枚举，画成流程图就是 Workflow；分支爆炸或事先未知，才需要 Agent。
2. **不可预测性**：输入的形态是否高度多变。格式固定的表单处理是 Workflow；自由文本的开放式请求才值得 Agent。
3. **错误代价**：路径错了能不能便宜地纠正。代价高的场景（资金、合规）无论多像 Agent，都要收紧自主性。

谱系是一条自主性递增的线：单轮问答 → 按流程走 → 自主拆解应变。**自主性每上一级，可控性就下一级**——这是选型的根本权衡。

### 4.2 Agent 四件套

Agent = LLM 大脑 + 三件套 + 循环节拍器。用「全能实习生」类比：脑子聪明（LLM 会推理），但干活还需要清单本、笔记本、门禁卡，外加一个持续推进的工作节拍。

| 组件 | 类比 | 职责 | 站内展开 |
|---|---|---|---|
| LLM（大脑） | 聪明的脑子 | 理解意图、推理决策、决定下一步 | 上限由模型能力决定 |
| 规划（Planning） | 任务清单本 | 拆目标、排步骤、按反馈调整 | 2.2 |
| 记忆（Memory） | 工作笔记本 | 存对话历史、中间结果、用户偏好 | 1.5 / 2.4 |
| 工具（Tools） | 门禁卡 | 查库、搜索、发邮件，作用于真实世界 | 1.3c / 2.3 |
| 循环（Loop） | 工作节拍 | 感知→思考→行动→观察，直到完成 | 2.5 |

三点澄清：

1. **四件套缺一不可**。只有 LLM 是 Chatbot；LLM + 固定流程是 Workflow；四者齐备且由模型驱动循环才是 Agent。
2. **Agent 的上限由模型能力决定**，工程侧决定下限——工具定义质量、记忆调度、循环刹车都在工程手里。
3. **循环是最容易被忽视的第四件**。面试里背出「规划记忆工具」三件套只是及格线，补上「循环运转、模型在循环里决定下一步」才是完整定义。

### 4.3 RAG + Chat 算不算 Agent

高频辨析题。判定标准不是「用了什么技术」，而是循环里**有没有模型自主决策**：

| 形态 | 结构 | 判定 |
|---|---|---|
| 朴素 RAG 问答 | 固定链路：检索一次 → 生成一次 | 不是 Agent，是 Workflow 级管道 |
| 带路由的 RAG | 规则判断走检索或直答 | 不是 Agent，规则在决策 |
| Agentic RAG | 模型自己判断「要不要检索、检索什么、结果够不够、要不要再检索」 | 是 Agent（检索成了模型可调用的工具） |

结论：**RAG+Chat 默认不是 Agent**——它是「给 Chatbot 外挂知识库」，路径固定。只有当检索决策本身交给模型、进入「判断-行动-观察」循环时（Agentic RAG，2.7 与 3.4 展开），才跨过 Agent 的门槛。面试答法：「标准 RAG 是固定管道；是否算 Agent 看下一步由谁决定——检索决策交给模型循环就是 Agentic RAG，才算。」

### 4.4 自主性的代价

自主性不是免费午餐，账单有三张：

1. **不可预测**。同样输入可能走出不同路径；路径不确定意味着输出结构、耗时、副作用都不确定。Workflow 的输出可以写死断言，Agent 的输出需要轨迹级评估（2.9b）。
2. **调试难**。Workflow 出错看日志定位到具体节点；Agent 出错是一条包含若干次模型决策的轨迹，得先复现「它当时为什么这么想」。Trace 与可观测性（1.6 的延伸）从加分项变成必需品。
3. **成本**。每一次「决定下一步」都是一次 LLM 调用；多步任务的 token 消耗是单轮问答的数倍到数十倍。自主循环一旦失控（死循环、重复调用），成本和延迟同时爆炸——2.3 的步数与预算双阈值就是为这个准备的。

| 代价 | 根因 | 工程对策 |
|---|---|---|
| 不可预测 | 模型决策非确定性 | 收紧目标、限定工具集、评估轨迹 |
| 调试难 | 失败在轨迹而非单点 | 全量 Trace、逐步决策日志 |
| 成本高 | 每步决策都是一次调用 | 步数/预算双阈值、分级路由 |

### 4.5 何时不该用 Agent

反面清单和正面定义同样重要。出现以下任一信号，退回 Workflow 或纯规则：

1. **路径能画成流程图**。分支可枚举、逻辑可穷举——写死流程更稳、更便宜、更快。
2. **任务高度重复且格式固定**。每天同一时间同一格式的日报，是定时脚本的事。
3. **错误代价不可逆**。资金划转、生产配置变更、合规判定——这些环节要规则与人工拍板，AI 提案人类决策。
4. **延迟预算极紧**。Agent 的多步循环天生慢；毫秒级响应的场景容不下循环。
5. **无法获得反馈信号**。Agent 靠观察结果决定下一步；工具返回不可读、不可验证时，循环就是盲飞。

一个实用的起步形态：**AI 提方案，人类拍板**。语言理解、方案生成交给模型，不可逆执行留给人工或强规则——既吃到模型的语言能力，又把风险锁在确定性一侧。

## 5. 架构 / 流程

谱系与 Agent 循环全景：

```text
自主性递增 ──────────────────────────────────────▶

┌──────────┐      ┌──────────────┐      ┌──────────────────┐
│ Chatbot  │      │  Workflow    │      │      Agent       │
│ 一问一答  │      │ 流程写死      │      │ 模型决定下一步     │
│ 只动嘴    │      │ 按图走        │      │ 四件套+循环       │
└──────────┘      └──────────────┘      └──────────────────┘

Agent 内部（四件套 + 循环）：

              ┌─────────────────────────┐
              │      LLM 大脑            │
              │  理解 / 推理 / 决定下一步  │
              └─────────────────────────┘
                 ▲            │
        观察      │            │  行动（工具调用）
        Observation             ▼
┌──────────────┐          ┌──────────────┐
│ 环境 / 工具   │          │  规划         │
│ 返回执行结果  │◀────────▶│  拆解与调整    │
└──────────────┘          └──────────────┘
       ▲                        ▲
       │        读取/写入        │
       └──────▶ 记忆 ◀──────────┘
              （历史/中间结果/偏好）

循环：感知 → 思考 → 行动 → 观察 → （未完成则继续）
终止：目标完成 / 步数或预算触顶 / 需要人工确认
```

同一个任务在谱系两侧的不同走法：

```text
任务：帮我订下周三下午的会议室

Chatbot：  输出一段「请登录 OA → 选择时间 → 提交申请」的文字指南（说）
Workflow：  走死流程：固定查 3 个常用会议室 → 有空则订 → 无空则报错（按图走）
Agent：    查全部空会议室 → 筛 12 人带屏 → 满员则换周四上午再查 →
           订妥后汇报「泰山厅，周三 14:00-15:00」（做，且能应变）
```

## 6. 代码 / 工具

### 6.1 最小 Agent 循环伪代码

不依赖任何框架，40 行看清四件套如何咬合成循环。生产实现要加上限、预算、审计（见 2.3 与 2.5），这里只保留骨架。

```python
# 最小 Agent 循环：LLM + 工具 + 记忆 + 循环
# 依赖 1.3c 的工具调用约定：模型只填单，程序验单后才执行

TOOLS = {
    "search_meeting_rooms": search_meeting_rooms,   # 查询空会议室
    "book_meeting_room":    book_meeting_room,      # 预订（写操作，需确认）
}

SYSTEM = """你是会议室预订助手。可用工具见 tools 定义。
规则：一次只调用一个工具；根据工具返回结果决定下一步；
任务完成后用自然语言向用户汇报；无法完成时如实说明。"""

def run_agent(goal: str, max_steps: int = 10) -> str:
    messages = [                                  # 记忆：对话与中间结果都在这里
        {"role": "system", "content": SYSTEM},
        {"role": "user",   "content": goal},
    ]

    for step in range(max_steps):                 # 循环：节拍器 + 硬刹车
        resp = llm.chat(
            messages=messages,
            tools=list(TOOL_SCHEMAS.values()),    # 门禁卡：只注册需要的工具
        )

        if resp.content:                          # 模型不再调工具 -> 任务完成
            return resp.content

        call = resp.tool_calls[0]
        if not validate_args(call):               # 1.3c：程序验单，模型只填单
            observation = {"error": "参数校验失败", "detail": call.arguments}
        elif call.name == "book_meeting_room":    # 不可逆写操作：人工闸口
            if not human_confirm(call.arguments):
                observation = {"result": "用户拒绝预订，请给其他方案"}
            else:
                observation = TOOLS[call.name](**call.arguments)
        else:
            observation = TOOLS[call.name](**call.arguments)

        # 记忆追加：行动与观察进入上下文，模型据此决定下一步
        messages.append({"role": "assistant", "tool_calls": [call]})
        messages.append({"role": "tool",
                         "content": json.dumps(observation, ensure_ascii=False)})

    return "已达步数上限，任务未完成。已完成的进展：" + summarize(messages)
```

逐行对照四件套：`llm.chat` 是大脑，`messages` 累积是记忆，`TOOLS` 是门禁卡，`for` 循环 + 「模型决定是否继续调工具」是循环与自主决策。`max_steps` 与 `human_confirm` 是 1.7 成本权限意识在 Agent 里的直接体现。

### 6.2 形态选型判定清单

拿到需求时按顺序过一遍，任何一项命中「是」，先考虑不用 Agent。

```text
[选型判定] 按序回答，命中即停：
  Q1 路径能画成有限流程图吗？            是 -> Workflow / 规则脚本
  Q2 分支可枚举且少于 ~10 个？           是 -> Workflow（switch/编排图）
  Q3 任务格式固定、高度重复？            是 -> 定时任务 + 模板
  Q4 错误代价不可逆（资金/合规/删除）？   是 -> 规则 + 人工拍板，AI 只提方案
  Q5 延迟预算 < 2 秒？                  是 -> 单次调用，不上循环
  Q6 工具返回无法程序化判读？            是 -> 先修反馈信号，再谈自主
  以上全否：
  Q7 需求路径开放、输入形态多变、需跨步骤应变？
                                       是 -> Agent（配齐四件套 + 2.3 的护栏）
```

## 7. 案例

### 案例 A：订会议室——同一需求的三种实现

**场景**：行政助手需求「帮员工订会议室」。第一版做成 Chatbot，输出操作指南，上线一周无人使用。第二版做成固定 Workflow：查 3 个固定会议室，有空就订。第三版上 Agent：全量查询、按人数设备筛选、满员自动改期重查。

**效果对比**：Chatbot 版任务完成率 0%（它只动嘴）；Workflow 版 62%（固定三个厅全满即失败）；Agent 版 89%（会换时间、换楼层、合并条件重查）。但 Agent 版单次任务平均 5 次 LLM 调用、4 秒完成，是 Workflow 版的 6 倍成本。

**结论**：完成率与自主性正相关，成本同样正相关。预订这种高频低价值任务，最终落地是「Workflow 为主 + 失败时升级 Agent」的混合形态。

### 案例 B：售后退货——AI 提案人类拍板

**场景**：一家电商平台要在售后系统加 AI 自动处理退货申请。

**拆解**：理解客户诉求（自由文本转结构化：订单号、退货原因、诉求类型）交给模型；查订单与政策并生成初步方案（符合/不符合/需人工）交给模型；安抚性回复生成交给模型。最终退款执行不交给模型——资金不可逆，走强规则加人工确认；理赔政策最终判定与投诉升级留给人工。

**效果**：上线后 70% 的退货申请由「模型提案 + 一键确认」处理，人工只处理 30% 的边缘与升级 case，单件处理时长从 8 分钟降到 3 分钟；资金操作零事故，因为模型全程没有执行权限。

### 案例 C：日报机器人不该是 Agent

**场景**：团队想用「自主 Agent」实现每早 8 点拉数据、生成日报、发群里。实现后发现：每天路径完全相同，Agent 偶尔「发挥」换了图表类型或摘要顺序，反而造成格式不一致；月成本比定时脚本高 15 倍。

**改造**：降级为 Workflow——cron 定时 + 固定查询 + 模板化生成，LLM 只负责一段固定格式的摘要文字，路径与格式写死。

**效果**：格式 100% 稳定，成本降 93%，故障排查从「翻轨迹」变成「看日志」。判据就是 4.5 清单的第一条：路径能画成流程图，就别上 Agent。

## 8. 常见坑

1. **把用了 LLM 的系统都叫 Agent**。
   判据只有一条：下一步由谁决定。模型决定才是 Agent，否则是 Chatbot 或 Workflow。

2. **背了「规划记忆工具」就漏了循环**。
   三件套只是零件，循环才是把它们转起来的节拍器。完整答案是四件套。

3. **需求没拆就上 Agent**。
   先过 4.5 的判定清单，多数「想要 Agent」的需求其实是 Workflow。

4. **给 Agent 注册全量工具**。
   门禁卡发成一串万能钥匙。按任务注册最小工具集，写操作加确认。

5. **循环不设上限**。
   一次发散就死循环，成本延迟双爆。max_steps 与预算双阈值是硬刹车。

6. **记忆只追加不管理**。
   多步之后上下文膨胀，模型「失忆」且成本飙升。历史压缩与检索注入见 1.5 与 2.4。

7. **把不可逆动作交给模型直接执行**。
   模型会被注入误导。资金、删除、对外发送必须有程序校验或人工闸口。

8. **用评估单轮回答的方式评估 Agent**。
   要评的是整条轨迹：走了哪些步、调了哪些工具、在哪步跑偏（2.9b）。

9. **忽视成本量级差异**。
   Agent 单任务的 LLM 调用是单轮问答的数倍到数十倍，报价和容量规划要按这个量级算。

10. **拿框架当定义**。
    用了 LangChain 不等于有了 Agent；没用框架也不等于不能有——6.1 的 40 行就是 Agent。

11. **用 Agent 追求「显得智能」**。
    自主性的价值在应变，不在炫技。稳定重复的任务上 Agent 是负优化。

12. **多步任务让模型「一口气想完」**。
    目标复杂时一步到位的生成质量骤降。拆目标、循环推进，规划见 2.2。

1. 不用框架实现 6.1 的最小 Agent 循环，接两个真实工具（天气查询、日历查询），跑通一个两步任务。
2. 给循环加 max_steps 与 token 预算刹车，构造一个会死循环的任务（如工具恒返回错误）验证护栏。
3. 把同一个「查库并汇总」需求分别实现为 Workflow 与 Agent 版，对比完成率、成本、延迟。
4. 判定练习：对「邮件自动分类打标」「开放式竞品调研」「每季合规报告」三个需求，用 6.2 清单逐项判定该落谱系哪一格。
5. 实现一个带路由的 RAG 与一个 Agentic RAG（模型决定是否再检索），对比在多跳问题上的表现。
6. 在循环里加入人工确认闸口，测试「用户拒绝预订」后 Agent 能否给出替代方案而非报错。
7. 统计你实现的 Agent 完成一次任务的 LLM 调用次数与 token 消耗，估算月 10 万次任务的账单量级。
8. 写一段向非技术同事解释「Chatbot、Workflow、Agent 区别」的话术，判据必须落在「谁决定下一步」上。

## 10. 小结

- Agent = **LLM 大脑 + 规划 + 记忆 + 工具**，在**感知-思考-行动-观察的循环**里由模型决定下一步。
- 谱系判定只看一条：**下一步由谁决定**——用户是 Chatbot，开发者是 Workflow，模型是 Agent。
- 分支可枚举画得出流程图，就用 Workflow；路径开放、输入多变、需要应变，才上 Agent。
- RAG+Chat 默认是固定管道不是 Agent；检索决策交给模型循环（Agentic RAG）才算跨过门槛。
- 自主性有三张账单：**不可预测、调试难、成本高**——每一步决策都是一次 LLM 调用。
- 反面清单优先：错误不可逆、延迟预算紧、无反馈信号的场景，退回规则与人工。
- 最稳的起步形态：**AI 提方案，人类拍板**——语言环节交给模型，资金与合规留给确定性。
- 循环必须有硬刹车：步数上限与预算阈值，这是 2.3 的正式主题。
- 四件套的深挖顺序：规划在 2.2，工具防护在 2.3，记忆在 2.4，循环与失控恢复在 2.5。
