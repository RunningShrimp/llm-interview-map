实战层第 2 个知识点，属于「知识增强型 Agent」。  
它解决一个核心问题：**如何让 Agent 基于企业私有文档、产品手册、政策文件回答，给出可追溯的引用，并且有一套能证明它好、能定位它差的评估方法？**

## 2. 一句话定义

RAG 知识库 Agent，是在单 Agent 原型上增加「离线索引 + 在线检索 + 引用生成 + 分层评估」能力，使 Agent 能基于私有文档回答、标注来源、按权限隔离，且效果可度量、可定位、可迭代的实战系统。

简化公式（两级）：

```text
RAG 能力          = 文档索引 + 混合检索 + Rerank + 引用生成
RAG 知识库 Agent  = 4.1 单 Agent + RAG 能力 + 权限过滤 + 评估闭环
```

## 3. 为什么需要

4.1 的订单助手只能查结构化数据，但真实业务的大量知识是非结构化的：产品手册、政策文件、FAQ、合同、报告、会议纪要、内部 Wiki。这些知识 LLM 的参数里没有，硬问必幻觉；而要把知识库做成可交付的项目，还会撞上一串工程问题：

- **私有知识进不了模型** → 文档在公司系统里，模型参数里没有，直接问只能编。
- **知识更新要动模型** → 微调更新慢、成本高；RAG 更新文档即更新知识。
- **答案不可信** → 无引用的答案在客服、合规场景不能用；引用（Citation）让每句话可回溯。
- **人人能看到所有文档** → 不做权限过滤的多租户知识库，等于把全公司文档摊开在每个人面前。
- **好坏全凭感觉** → 没有评估闭环，不知道系统是 60 分还是 85 分，更不知道差在检索还是生成——这正是本锚点的关键问题。

单 Agent 与 RAG Agent 的差别（交付视角）：

| 维度 | 4.1 订单助手（无 RAG） | 4.2 知识库 Agent |
|---|---|---|
| 能答的问题 | 结构化数据（订单状态） | 非结构化知识（政策、手册） |
| 知识更新 | 改接口、改提示词 | 更新文档、增量重建索引 |
| 答案可信度 | 依赖 LLM 自由发挥 | 引用可回溯到原文 |
| 权限 | 按工具接口天然隔离 | 必须在检索层做元数据过滤 |
| 评估 | 端到端对错一判 | 检索、生成分层评估 + 坏例归因 |

**类比 1（开卷考试）**：LLM 裸答私有问题，像闭卷考试考了没复习的范围——不会也只能硬写（幻觉）；RAG 是开卷考试：桌上摆着资料（检索），并且要求每道题注明出处（引用），实在没有就写「资料中没有」——「不会答」从冒险编造变成可以光明正大地拒答。

**类比 2（活页手册）**：单 Agent 像一位刚入职的聪明客服，通用问题对答如流，问到公司制度只能靠猜；RAG Agent 是同一位客服，工位上放一本带索引的活页手册——回答前先翻到那一页（检索），答案旁夹上便签写清页码（引用），手册换一页知识就更新（增量更新），不同部门只能翻自己的那几分册（权限过滤）。

## 4. 核心原理

### 4.1 两条链路

```text
离线索引：
文档 → 加载 → 清洗 → 切分 → 嵌入 → 向量库 + BM25

在线问答：
用户问题 → 查询重写 → 混合检索 → 权限过滤 → Rerank
        → 上下文组装 → LLM 生成 → 答案 + 引用
```

每个环节的机制（为什么切 512 token、RRF 为什么有效、Bi-Encoder 与 Cross-Encoder 的差别）见 1.4；本篇只讲**怎么组合、怎么验收**。

### 4.2 在 Agent 中的两种集成方式

方式 1：RAG 作为工具（Agentic 式）

```text
Agent 决策：这个问题需要查知识库吗？
   ├─ 需要 → 调用 search_docs(query) → 检索 → 结果回传 → LLM 生成
   └─ 不需要 → 直接回答
```

方式 2：RAG 作为固定前置（管线式）

```text
用户问题 → 无条件检索 → 拼接上下文 → LLM 生成
```

| 维度 | 方式 1：作为工具 | 方式 2：固定前置 |
|---|---|---|
| 检索时机 | LLM 决定，按需检索 | 每问必检 |
| 延迟 | 多一次决策调用，略高 | 少一跳，更快 |
| 无谓检索 | 可避免（寒暄不查库） | 闲聊也查，浪费 |
| 实现复杂度 | 需要工具注册与循环（4.1 骨架） | 一条链路 |
| 适用 | 多工具复杂 Agent | 纯知识库问答产品 |

推荐：**简单问答用方式 2，复杂 Agent 用方式 1**。本篇代码两种都给（6.4 工具版、6.5 管线版）。

### 4.3 文档处理管道（数据接入）

| 步骤 | 工具 | 交付要点 |
|---|---|---|
| 加载 | LangChain Loaders、LlamaIndex | PDF、Word、Markdown、HTML、Wiki 导出 |
| 清洗 | 正则、Unstructured | 去页眉页脚、去广告、脱敏；保留标题结构 |
| 切分（Chunking） | RecursiveCharacterTextSplitter | 512 token + 10% overlap 起步，评估集回归后再调 |
| 元数据 | 自定义 | 来源、租户、权限、时间、内容哈希（供增量更新） |
| 嵌入（Embedding） | BGE-M3（中文）、OpenAI Embedding | 查询与文档必须同一模型 |
| 索引 | Chroma、Qdrant、pgvector | 向量 + BM25 双索引 |

切分策略谱系与参数推导见 1.4。工程上比选策略更关键的三个问题：

- **文档从哪来**：Wiki 导出、网盘、工单系统；第一批先接 50-100 份高价值文档跑通闭环，再扩量。
- **怎么更新**：以「文件名 + 内容哈希」为键做增量——哈希变了重新嵌入，源里删了就从索引删（代码见 6.2）。
- **怎么验收**：抽样 20 条引用回链原文人工比对；来源对不上，管道再漂亮也不合格。

### 4.4 检索策略：混合检索 + RRF 融合

```text
BM25 Top-20 + 向量 Top-20
→ RRF 融合（按排名倒数求和）
→ 权限过滤（元数据 where）
→ Rerank Top-5
→ 交给 LLM
```

RRF（Reciprocal Rank Fusion，倒数排名融合）实现：

```python
def rrf_fusion(bm25_ids, vector_ids, k=60):
    """两路召回按排名融合：排名越靠前贡献越大，k=60 是惯用平滑常数。"""
    scores = {}
    for rank, doc_id in enumerate(bm25_ids):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (rank + k)
    for rank, doc_id in enumerate(vector_ids):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (rank + k)
    return sorted(scores, key=scores.get, reverse=True)
```

为什么必须混合：编号（「工单 BUG-1024」）、代码、专有名词对向量检索不敏感，BM25 恰好补位；口语化的长问题则靠语义向量。两类机制对比见 1.4。

### 4.5 引用生成

提示词模板：

```text
你是一个知识库问答助手。
只根据以下资料回答。
如果资料中没有答案，说“资料中没有相关信息”。
回答时标注引用编号，如 [1][2]。

资料：
[1] 退货政策：签收后 7 天内可退。
[2] 退款时效：3-5 个工作日到账。

问题：退货后多久能收到退款？
```

输出：

```text
根据资料 [2]，退款需要 3-5 个工作日到账。
```

引用的三层验收：编号指向真实资料（结构化校验）、资料确实支持该句（忠实度评估）、资料能回链到原文档与位置（元数据完整）。

### 4.6 查询重写

多轮对话中，用户说「那退款呢？」，直接拿去检索必失败。用 LLM 结合历史重写（Query Rewriting）：

```python
REWRITE_PROMPT = """根据对话历史，把用户最新问题重写为独立完整的问题。
不要回答问题，只做重写。

历史：
{history}

最新问题：{question}

重写后的问题："""
```

重写后：「退货后多久能收到退款？」——检索命中「退款时效」。  
多轮历史的存储与压缩见 2.4；重写属于「检索前改造查询」的最小动作，进阶还有多查询生成与 HyDE（见 1.4）。

### 4.7 检索与生成的联合评估（关键问题的正面回答）

关键问题：**检索和生成如何联合评估？**

一句话答案：**分层单测 + 端到端合测 + 坏例归因闭环**。只看端到端指标无法定位问题层，只看分层指标无法证明整体可用，两者必须成对出现。

**类比 3（医院会诊）**：联合评估像医院看病——先分科检查（检索科出 Recall@K，生成科出忠实度），再看整体疗效（端到端正确率），疑难病例归档进病历库（坏例进回归集），下次复诊先翻旧病历（回归测试保证不退化）。

四层评估表：

| 层 | 测什么 | 典型指标 | 数据来源 | 跳过会怎样 |
|---|---|---|---|---|
| 1. 检索单测 | 相关文档被召回了吗 | Recall@K、Hit Rate、MRR | 标注 query → 相关文档 ID 的评估集 | 检索坏了却去调提示词，白费功夫 |
| 2. 生成单测 | 给对资料时答得好吗 | 忠实度（Faithfulness）、答案相关性、引用准确率 | 评估集 + LLM-as-Judge（RAGAS 等） | 把生成问题误诊为检索问题 |
| 3. 端到端合测 | 整条链路的最终质量 | 答案正确率、引用命中率、拒答正确率 | golden 问答对 + 抽样人工标注 | 分层都好但整体翻车（Top-K 干扰、组装错误） |
| 4. 线上度量 | 真实用户满意吗 | 会话解决率（Resolution Rate）、点踩率、引用点击率 | 生产 Trace 采样 | 离线指标虚高，与线上分布脱节 |

坏例归因表（联合评估的日常形态）：

| 坏例症状 | 先查哪层 | 常见归因 | 对策 |
|---|---|---|---|
| 答非所问，引用也不相关 | 第 1 层 | 检索没召回 | 混合检索、调切分、查询重写 |
| 引用相关，答案却在编 | 第 2 层 | 生成不忠实 | 强化提示词约束、降温度、换模型 |
| 引用相关、忠实但不完整 | 第 1+3 层 | Top-K 太小或切分太碎 | 加大 K、父子切分（小块检、大块回） |
| 库里没有却硬答 | 第 2 层 | 提示词没给拒答出口 | 明确「资料中没有」话术并测拒答率 |
| 单轮好、多轮坏 | 重写环节 | 指代未消解 | 查询重写（4.6 小节） |
| 离线好、线上差 | 第 4 层 | 评估集分布偏移 | 生产 Trace 回灌回归集 |

归因决策树（拿到坏例的第一动作）：

```text
一个坏例
   ↓
第 1 层：Recall@K 里有没有正确文档？
   ├─ 没有 → 检索问题 → 查切分 / 嵌入 / 重写 / 混合权重
   └─ 有 → 第 2 层：给定这些文档，模型答对了吗？
             ├─ 没答对 → 生成问题 → 查提示词 / 模型 / 温度
             └─ 答对了 → 第 3 层：完整链路为何错？
                          → 查上下文组装 / Top-K 噪音 / 引用错位
   ↓
归因结论写回坏例库 → 进回归集 → 下一轮迭代必须不退化
```

与官方口径对齐：LangChain《Agent Evals》白皮书与 LangSmith 文档（2026）把 Agent 评估分为 Run（单次调用）、Trace（一次请求全链路）、Thread（整段会话）三粒度，并提出「生产 Trace → 回归数据集」闭环——与本篇分层表一一对应：第 1-2 层在 Run 粒度，第 3 层在 Trace 粒度，第 4 层在 Thread 粒度。Trace 的采集与回放见 3.4。

注意：LLM-as-Judge 有偏差且随模型漂移，需用人工标注的小型 golden set 定期校准（评估方法论展开见 1.6 与 3.5）。

面试高频问法：**「RAG 的检索和生成效果分别怎么评估？只看最终答案够吗？」**  
共识口径：不够。只看最终答案分不清「没检索到」和「检索到了没用好」，两者对策完全不同。标准答法：分层单测（检索 Recall@K + 生成忠实度、引用准确率）→ 端到端合测 → 坏例归因闭环，线上再加会话解决率。

面试高频问法（排查版）：**「线上 RAG 项目效果差，怎么排查？」**  
共识口径：按归因树走。先跑检索评估集看召回——不达标先修检索（性价比最高）；召回达标再看忠实度与引用；最后查端到端组装与线上分布。切忌一上来就换更大的生成模型。

### 4.8 权限过滤：在检索层，不在提示层

多租户（Multi-Tenant）场景，过滤必须发生在向量库查询阶段：

```python
results = collection.query(
    query_texts=[query],
    n_results=5,
    where={
        "$and": [
            {"tenant_id": user.tenant_id},
            {"permission": {"$in": user.roles}},
        ]
    },
)
```

为什么不能只写进提示词（「不要回答无权限的内容」）：资料一旦进入上下文就已经泄露，还可能被提示注入（Prompt Injection）利用——恶意文档指示模型复述隔壁租户的内容。提示词约束只能作兜底，不能作边界。  
验收方法：两套账号交叉检索做渗透测试，断言互相查不到对方文档（见案例 D）。  
权限与合规模型展开见 3.8；此处只讲 RAG 的落地点。

### 4.9 坏例驱动迭代：优先级怎么排

评估闭环产出的是带归因的坏例清单，下一步是排期。经验排序：**先检索后生成、先便宜后昂贵**——检索层的改进会同时抬高所有生成模型的上限。

迭代优先级表（数字为示意量级，来自同类项目复盘口径）：

| 措施 | 预期效果 | 成本 | 工作量 | 建议次序 |
|---|---|---|---|---|
| 混合检索（BM25 + 向量） | Recall@5 +10~20pt | 低（CPU） | 1-2 天 | 第一步 |
| 加 Rerank（重排） | Top-5 精度明显提升 | 中（延迟 +50~200ms） | 1 天 | 第二步 |
| 调切分（512 / overlap / 父子切分） | +5~15pt，视语料 | 低 | 2-3 天（含回归） | 第三步 |
| 查询重写 | 多轮场景 +20pt 以上 | 低（多一次 LLM 调用） | 1 天 | 有多轮就必做 |
| 换更大生成模型 | 忠实度 +3~5pt | 高（token 单价成倍） | 0.5 天 | 靠后 |
| GraphRAG / 知识图谱 | 多跳问题改善 | 高（构建 + 持续维护） | 周级 | 最后；生产落地集中于知识结构要求高的场景（趋势观察，见 1.4） |

每一步都要在同一个评估集上回归——没有回归集的调优是玄学。

### 4.10 RAG Agent 的决策循环

```text
用户问题
   ↓
Agent 决策：需要检索吗？
   ├─ 否 → 直接回答
   └─ 是 → 查询重写 → 混合检索 → 权限过滤 → Rerank
              ↓
         上下文组装
              ↓
         LLM 生成答案 + 引用
              ↓
         输出（坏例进入评估闭环）
```

「是否检索、检索什么、结果够不够」由模型自主判断，就是 Agentic RAG 的起点；进一步的自省与纠错式检索（Self-RAG、CRAG）见 2.6 与 1.4。

## 5. 架构 / 流程

系统总架构（四层 + 迭代回流）：

```text
┌────────────────────────────────────────────────────┐
│ 离线索引（数据接入层）                              │
│ 文档源 → 加载 → 清洗 → 切分 → 嵌入 → 向量库 + BM25 │
│   ↓ 元数据：来源、租户、权限、时间、内容哈希        │
│   增量更新：哈希变了重嵌，源删除则同步删            │
```

### 6.2 离线索引（含增量更新）

```python
import hashlib
import chromadb
from pathlib import Path
from langchain.text_splitter import RecursiveCharacterTextSplitter
from sentence_transformers import SentenceTransformer

class KnowledgeIndexer:
    def __init__(self):
        self.client = chromadb.PersistentClient(path="./chroma_db")
        self.collection = self.client.get_or_create_collection("knowledge")
        self.embedder = SentenceTransformer("BAAI/bge-m3")
        self.splitter = RecursiveCharacterTextSplitter(
            chunk_size=512,           # 起步值，评估集回归后再调
            chunk_overlap=64,         # 约 10% overlap
            separators=["\n\n", "\n", "。", "！", "？", " ", ""],
        )

    def index_documents(self, docs_dir: str, tenant_id: str = "default"):
        chunks = []
        for file in Path(docs_dir).rglob("*.md"):
            content = file.read_text(encoding="utf-8")
            for i, chunk in enumerate(self.splitter.split_text(content)):
                chunks.append({
                    "id": f"{file.stem}_{i}",
                    "content": chunk,
                    "metadata": {
                        "source": file.name,
                        "tenant_id": tenant_id,
                        "permission": ["user", "admin"],
                        "content_hash": hashlib.md5(content.encode()).hexdigest(),
                    },
                })

        if not chunks:
            return 0

        embeddings = self.embedder.encode([c["content"] for c in chunks]).tolist()
        self.collection.upsert(           # upsert：同 id 覆盖，支持重复构建
            ids=[c["id"] for c in chunks],
            embeddings=embeddings,
            documents=[c["content"] for c in chunks],
            metadatas=[c["metadata"] for c in chunks],
        )
        return len(chunks)

    def sync_documents(self, docs_dir: str, tenant_id: str = "default"):
        """增量更新：源文件已删除的同步删索引，其余走 upsert。"""
        current_names = {f.stem for f in Path(docs_dir).rglob("*.md")}
        stored = self.collection.get(include=["metadatas"])
        for doc_id, meta in zip(stored["ids"], stored["metadatas"]):
            name = meta["source"].rpartition(".")[0]
            if name not in current_names:          # 源里已删 → 索引同步删
                self.collection.delete(ids=[doc_id])
        return self.index_documents(docs_dir, tenant_id)
```

### 6.3 混合检索 + Rerank

```python
from rank_bm25 import BM25Okapi
import jieba
from sentence_transformers import CrossEncoder

class HybridRetriever:
    def __init__(self, collection, embedder):
        self.collection = collection
        self.embedder = embedder
        self.reranker = CrossEncoder("BAAI/bge-reranker-base")
        self.bm25 = None
        self.documents = []

    def build_bm25(self, docs: list):
        """文档变更后重建 BM25（与向量库同步调用）。"""
        self.documents = docs
        tokenized = [list(jieba.cut(d["content"])) for d in docs]
        self.bm25 = BM25Okapi(tokenized)

    def search(self, query: str, user: dict, top_k: int = 5) -> list:
        # 1. 向量检索（带权限过滤：在检索层，不在提示层）
        query_vec = self.embedder.encode([query]).tolist()
        vec_results = self.collection.query(
            query_embeddings=query_vec,
            n_results=20,
            where={
                "$and": [
                    {"tenant_id": user["tenant_id"]},
                    {"permission": {"$in": user["roles"]}},
                ]
            },
        )

        # 2. BM25 关键词检索（补编号、专有名词的召回）
        tokenized_query = list(jieba.cut(query))
        bm25_scores = self.bm25.get_scores(tokenized_query)
        bm25_top = sorted(range(len(bm25_scores)), key=lambda i: -bm25_scores[i])[:20]

        # 3. RRF 融合（k=60）
        scores = {}
        for rank, doc_id in enumerate(vec_results["ids"][0]):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (rank + 60)
        for rank, idx in enumerate(bm25_top):
            doc_id = self.documents[idx]["id"]
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (rank + 60)
        top_ids = sorted(scores, key=scores.get, reverse=True)[:20]

        # 4. Rerank：CrossEncoder 对（查询, 文档）对精排
        candidates = [
            {"id": did, "content": self._get_content(did)}
            for did in top_ids
        ]
        pairs = [(query, c["content"]) for c in candidates]
        rerank_scores = self.reranker.predict(pairs)
        ranked = sorted(zip(candidates, rerank_scores), key=lambda x: -x[1])

        return [c for c, _ in ranked[:top_k]]
```

### 6.5 RAG 作为固定前置管线（方式 2）

```python
RAG_PROMPT = """你是一个知识库问答助手。
只根据以下资料回答。如果资料中没有答案，说“资料中没有相关信息”。
回答时标注引用编号，如 [1][2]。
不要编造资料外的信息。

资料：
{context}

问题：{question}
"""

async def rag_answer(query: str, retriever, user: dict) -> dict:
    docs = retriever.search(query, user, top_k=5)
    context = "\n".join(
        f"[{i+1}] {d['content']}" for i, d in enumerate(docs)
    )
    answer = await chat([
        {"role": "user", "content": RAG_PROMPT.format(context=context, question=query)}
    ])
    return {
        "answer": answer,
        "sources": [{"id": d["id"], "source": d["metadata"]["source"]} for d in docs],
    }
```

### 6.6 分层评估脚本（联合评估落地）

```python
import json

def eval_retrieval(retriever, eval_set, user: dict, k: int = 5) -> dict:
    """第 1 层：检索单测。不经过生成模型，直接对召回结果打分。"""
    stats = {"hit": 0, "total": len(eval_set), "fail": []}
    for case in eval_set:
        docs = retriever.search(case["query"], user, top_k=k)
        ids = [d["id"] for d in docs]
        if set(case["relevant_ids"]) & set(ids):      # 至少命中一个相关文档
            stats["hit"] += 1
        else:
            stats["fail"].append(case["query"])       # 记坏例，供归因
    stats["hit_rate"] = stats["hit"] / stats["total"]
    return stats

def eval_generation(judge_llm, answer: str, contexts: str) -> dict:
    """第 2 层：生成单测。LLM-as-Judge 判定忠实度与引用正确性。"""
    prompt = f"""判断答案是否只基于资料、引用编号是否指向支持它的资料。
只输出 JSON：{{"faithful": true, "citation_ok": true}}
资料：{contexts}
答案：{answer}"""
    return json.loads(judge_llm(prompt))
    # judge 有偏差且随模型漂移，需用人工标注 golden set 定期校准（见 1.6）

def eval_pipeline(rag_answer_fn, retriever, judge_llm, eval_set, user: dict) -> dict:
    """第 3 层：端到端合测 + 坏例归因。输出分层报告，坏例落盘进回归集。"""
    report = {"total": len(eval_set), "ok": 0, "retrieval_fail": 0, "generation_fail": 0}
    bad_cases = []
    for case in eval_set:
        result = rag_answer_fn(case["query"], user)            # 完整链路
        docs = retriever.search(case["query"], user, top_k=5)  # 同查询复跑检索，用于归因
        ids = [d["id"] for d in docs]
        if not (set(case["relevant_ids"]) & set(ids)):
            report["retrieval_fail"] += 1                      # 归因：检索层
            bad_cases.append({**case, "layer": "retrieval"})
            continue
        contexts = "\n".join(f"[{i+1}] {d['content']}" for i, d in enumerate(docs))
        verdict = eval_generation(judge_llm, result["answer"], contexts)
        if verdict["faithful"] and verdict["citation_ok"]:
            report["ok"] += 1
        else:
            report["generation_fail"] += 1                     # 归因：生成层
            bad_cases.append({**case, "layer": "generation"})
    json.dump(bad_cases, open("eval/bad_cases.json", "w"),
              ensure_ascii=False, indent=2)                     # 坏例进回归集
    return report                                              # 下轮迭代必须不退化

if __name__ == "__main__":
    eval_set = json.load(open("eval/retrieval_eval.json"))
    print(eval_retrieval(retriever, eval_set, user={"tenant_id": "default", "roles": ["user"]}))
    # 输出示例：{'hit': 17, 'total': 20, 'hit_rate': 0.85, 'fail': ['那退款呢？']}
```

## 7. 案例

### 案例 A：某电商客服知识库（从裸检索到生产管道）

**场景**：1000 份内部文档（售后政策、商品 FAQ、操作流程），客服与员工日常提问，答案必须带引用。  
**做法**：按六步主线交付——首批接 100 份高价值文档；递归切分 512 token + 64 overlap；BGE-M3 嵌入 + Chroma/BM25 双索引；RRF 融合后 BGE-Reranker 精排 Top-5；生成端强制引用与拒答话术；建 60 条检索评估集 + 60 条端到端评估集。  
**示意数字效果（复盘口径）**：纯向量 Recall@5 约 62%，换混合检索到 74%，加 Rerank 到 81%；端到端回答准确率从 60% 提升到 85%，幻觉率从 15% 降到 3%（人工抽标 200 条）。复盘结论：收益最大的两步是混合检索与 Rerank，合计不到三天工作量——「先检索后生成」的实证。

### 案例 B：一家金融科技公司的合规问答（权限 + 增量 + 评估闭环）

**场景**：3 个租户（部门），每日约 200 份新文档，答案必须可引用、必须能拒答，审计要求全链路可追溯。  
**做法**：检索层 tenant_id + 角色双条件过滤；增量更新按内容哈希，日级同步；评估闭环每周跑一次，把线上点踩会话采样回灌回归集（对应 4.7 小节第 4 层）。  
**示意数字效果**：首月坏例归因分布为检索层 58%（切分过碎占大头）、生成层 31%、组装层 11%；针对性把 chunk_size 从 512 调到 768 并加父子切分后，四周内会话解决率从 68% 提升到 83%；越权检索渗透测试 50 条全部拦截。

### 案例 C：多轮查询重写（小而关键的一步）

```text
用户：退货政策是什么？
助手：签收后 7 天内可退。
用户：那退款呢？
```

「那退款呢？」直接检索几乎必失败（示意数据：Recall@5 约 35%）；经 4.6 小节的重写模板改写为「退货后多久能收到退款？」后，Recall@5 升到约 72%，命中「退款时效」。多轮场景不加重写，前两层的评估数字都会被这类问题拖垮。

### 案例 D：权限过滤的验收（渗透测试）

```python
where={"$and": [{"tenant_id": "company_a"}, {"permission": {"$in": ["hr"]}}]}
```

验收不靠目测：用 A 公司的 HR 账号与 B 公司账号互相检索对方文档各 50 条，断言结果为空、答案层无泄露——50/50 全部拦截才算通过。确保 A 公司看不到 B 公司文档，是上线前的一票否决项。

## 8. 常见坑

1. **切分太大或太小**。  
   太大噪音多，太小语义碎。512 token + 10% overlap 起步，用评估集回归后调整。

2. **只用向量检索**。  
   编号、代码、专有名词召回差。对策：BM25 + 向量混合，RRF 融合。

3. **不加 Rerank**。  
   向量 Top-K 精度有限。对策：CrossEncoder 精排 Top-5，接受 50-200ms 延迟换精度。

4. **嵌入模型选错**。  
   中文语料用英文嵌入模型，语义空间错位。对策：中文选 BGE、GTE、Cohere。

5. **查询和文档用不同嵌入模型**。  
   向量空间不一致，检索失效。对策：同一模型编码两侧，写入与查询共用一个封装。

6. **不做查询重写**。  
   多轮对话里「那退款呢？」检索必挂。对策：结合历史重写为独立完整问题。

7. **提示词不约束**。  
   不要求「只根据资料回答」，LLM 自由发挥。对策：强制引用 + 拒答话术 + 不编造三条约束。

8. **不标注引用**。  
   答案不可追溯，用户不信任。对策：输出结构化引用（文档 ID + 来源），前端可回链。

9. **不做权限过滤，或只在提示层做**。  
   多租户泄露；资料进了上下文即已泄露，还会被提示注入利用。对策：过滤必须在检索层（metadata where），渗透测试验收。

10. **不评估检索，只看最终答案**。  
    分不清是检索问题还是生成问题。对策：分层评估 + 坏例归因（4.7 小节）。

11. **Top-K 太大**。  
    上下文噪音多、成本高，还容易「中间遗忘」（lost in the middle）。对策：Rerank 后取 3-5 块足够。

12. **不更新索引**。  
    知识库变了，检索还是旧内容。对策：内容哈希增量 upsert + 删除同步（6.2）。

13. **忽略元数据**。  
    来源、权限、时间、哈希都要存。对策：入库前定好元数据 schema，否则无法过滤、无法引用、无法增量。

14. **把 RAG 当万能**。  
    RAG 解决知识问题，不解决计算、实时数据。对策：实时查询交给工具调用（见 4.3、2.3）。

15. **离线评估集与线上分布脱节**。  
    离线指标好看，线上点踩不断。对策：定期把生产 Trace 采样回灌回归集，重算分层指标。

16. **调优不看回归**。  
    每次改动凭感觉，好了坏了说不清。对策：任何改动先跑同一评估集，指标不退化才合入（实验管理见 3.5）。

## 9. 练习

1. 最小闭环：用 Chroma + BGE 搭一个最小 RAG，回答 5 个政策问题。验收：每条答案带 [n] 引用，引用能对上原文。
2. 混合检索：实现 BM25 + 向量 + RRF。验收：同一 20 条评估集上 Hit Rate 高于纯向量至少 5 个百分点，并记录 3 个被 BM25 救回的坏例（编号/专有名词类）。
3. 加 Rerank：用 CrossEncoder 精排。验收：Top-5 人工相关性判定提升，同时记录延迟变化（应在 +50~200ms 量级）。
4. 多轮重写：实现「那退款呢？」场景。验收：给出重写前后 Recall@5 对比表。
5. 权限过滤：建两个租户、两种角色。验收：交叉渗透测试 20 条全部拦截。
6. 建检索评估集：20 条 query → 相关文档 ID。验收：脚本能输出 Hit Rate 与坏例清单。
7. 分层评估：实现 6.6 的三层评估脚本。验收：对 10 个坏例给出「检索层 / 生成层」归因，分别修复后复测通过。
8. 集成回 4.1：把 RAG 做成 search_docs 工具挂进 4.1 原型。验收：Agent 对「查订单」走订单工具、对「退货政策」走知识库。
9. 增量更新：实现哈希比对 upsert + 删除同步。验收：改 1 个文档后能检索到新内容，删 1 个文档后不再出现。
10. 方案对比实验：纯向量 vs 混合 vs 混合 + Rerank 三档。验收：产出含 Recall@5、端到端准确率、p95 延迟、单次成本四列的对比表——这张表就是面试讲项目的素材（见 4.10）。

## 10. 小结

- RAG 知识库 Agent = **4.1 单 Agent + 文档索引 + 混合检索 + Rerank + 引用生成 + 权限过滤 + 评估闭环**。
- 离线主线：**加载 → 清洗 → 切分 → 嵌入 → 索引**；交付关键是元数据完整与增量更新。
- 在线主线：**查询重写 → 混合检索 → 权限过滤 → Rerank → 生成 → 引用**。
- 集成二选一：简单问答用固定前置，复杂 Agent 用 search_docs 工具。
- 引用让答案可追溯；权限过滤必须在检索层完成，提示词约束只能兜底。
- 联合评估 = **分层单测（检索 Recall@K、生成忠实度）+ 端到端合测 + 坏例归因闭环**，只看最终答案无法定位问题层；线上以会话解决率为准，生产 Trace 回灌回归集保证不退化。
- 迭代顺序：**先检索后生成、先便宜后昂贵**——混合检索与 Rerank 几乎总是前两步。
- 核心原则：**先保证检索召回，再优化生成。检索没召回，LLM 再强也白搭。**
- RAG 解决知识问题，不解决计算与实时数据——那些交给工具调用（见 4.3）。
- 这些能力直接支撑：4.7 生产级 Agent 平台、4.8 评估与红队（5.4 阶段 3 是实操落点）。
