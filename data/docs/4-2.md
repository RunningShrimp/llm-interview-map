# 讲解 4.2 RAG 知识库 Agent

> 说明：1.4 RAG 给了直觉，1.4b RAG 最小可用版给了完整链路（解析→切分→向量化→检索→引用生成），1.4c 给了检索优化（混合检索、重排），3.2 补了企业数据管线与权限治理——本篇把这些零件组装成「企业知识库问答 Agent」这个 L4 级全案。  
> 面试中它是出现频率最高的终极综合题：本篇讲骨架与方法论，带数字的终极展开在 4.2b；评估方法论底座在 2.9 与 3.5，可观测在 3.4，成本手段在 3.7c。

---

## 1. 定位

L4 实战层第 2 个锚点，回答关键问题：**检索和生成如何联合评估？以及——给你一个模糊需求，能否像架构师一样走完全程。**

前置依赖：

- 1.4b RAG 最小可用版：两周搭起的解析、切分、嵌入、检索、引用生成链路，是本篇的全部积木。
- 1.4c 检索质量优化：结构感知切分、BM25 双路召回、Cross-Encoder 精排，本篇在线链路的默认配置。
- 2.3 工具使用 Tool Use：知识库 Agent 把「检索」注册为工具时的定义、参数校验与失败处理。
- 3.2 数据与知识工程：多格式接入、增量更新、密级过滤、审计——本篇数据板块的深水区。

下游去向：

- 4.2b 终极架构题：本篇骨架的带数字全案版，10 万文档、部门隔离、当天生效逐条展开到实施细节。
- 4.7b Agent 系统全案：六板块思想向多 Agent 平台题的迁移。

它解决一个根本问题：**面试官给一句「给公司搭个知识库问答」，多数人立刻开始罗列技术栈——而合格答案是一张有议程的图纸：需求、架构、数据、安全、评估、成本按序推进，权限前置，权衡随讲随给。答题骨架保证不漏项，权衡意识体现深度。**

## 2. 一句话定义

RAG 知识库 Agent = 以 RAG 为主线（离线索引 + 在线检索生成）、按六板块（需求澄清 → 总体架构 → 数据链路 → 效果与安全 → 评估上线 → 成本迭代）推进的企业级全案；铁律三条：检索与生成必须**联合评估**，权限必须在**检索层前置过滤**，新知识必须**当天可达**。

## 3. 为什么需要

这道题的常见死法不是「不会」，而是「漏」：讲了半天 Milvus 和 Rerank，权限一句话带过，评估一笔勾销，成本一个字不提。对比两种答题方式：

| 维度 | 零件式答题 | 骨架式答题 |
|---|---|---|
| 开场 | 直接报技术栈（「用 LangChain 加 Milvus」） | 先澄清：用户范围、文档量、权限模型、SLO、预算 |
| 结构 | 想到哪说到哪 | 六板块议程推进，每板块不缺席 |
| 权限 | 事后补一句「可以做权限过滤」 | 检索层前置过滤作为铁律，先于生成讲 |
| 评估 | 「可以加个评估」 | 检索+生成联合评估，指标成对出现 |
| 追问抗性 | 一个「失效了怎么办」就问倒 | 每个设计自带失效分析与对策 |
| 收尾 | 突然结束 | 主动给 MVP→完善的演进路线图 |
| 评分印象 | 会用零件 | 心里有整张图纸 |

为什么必须「联合」评估：只看最终答案分不清责任。检索没召回（Recall@K 低），LLM 再强也只能编；检索召回了但答案不忠实（Faithfulness 低），是生成侧的问题。两种病的药方完全不同——不联合评估，所有优化都是盲猜。

为什么权限必须「前置」到检索层：无权文档一旦进入上下文，模型可能复述（提示词约束是概率性的，复杂问题或诱导下会被忽略），引用编号还会直接暴露文档的存在性。生成后隐藏救不了中间泄露。唯一可靠的位置是检索层：无权文档根本不进候选。这也是站内考点卡的必考选择题，选项把「生成后由 LLM 隐藏」设为干扰项——那一层在原理上就不可靠。

## 4. 核心原理

### 4.1 六板块答题骨架

骨架的价值是**不漏项**。把答题当成一场架构评审会：按议程推进，每节先给结论再给理由，主动暴露权衡（「我在 X 与 Y 之间选了 X，因为……」）。

| 板块 | 要回答的问题 | 采分点 | 常见失分 |
|---|---|---|---|
| 1 需求澄清 | 用户是谁？文档量与格式？更新频率？权限模型？SLO？预算？能否用云 API？ | 以问开场——需求边界决定选型，这一步本身就是采分点 | 不澄清直接报方案，被追问到露馅 |
| 2 总体架构 | RAG 主线：离线（解析→切分→索引）+ 在线（改写→混合检索→重排→引用生成） | 离线/在线两段清晰；是否叠加微调现场论证（缺知识选 RAG，缺能力选微调） | 名词堆砌，讲不出删掉哪层会坏什么 |
| 3 数据链路 | 多格式解析、结构感知切分、元数据（部门/密级/时效/版本）、增量更新流水线 | 「数据质量决定效果上限」 | 只讲模型不讲数据 |
| 4 效果与安全 | 防幻觉三约束、权限前置、注入防护（untrusted 分区）、DLP、拒答转人工 | 权限泄漏是企业场景红线，讲在生成之前 | 权限设计放在生成层 |
| 5 评估上线 | golden set 分层评测、周度回归、灰度→全量、badcase 飞轮、Trace 可观测 | 检索+生成联合评估、上线是运营起点 | 「上线即结束」心态 |
| 6 成本迭代 | 前缀缓存、语义缓存、模型路由、量化；MVP→完善的演进路线 | 给路线图而非一步到位 | 只讲效果不算账 |

其中板块 1 的六个问题背下来：**用户范围、文档规模与格式、更新频率、权限模型、SLO、预算**。规模与权限没问清之前不展开细节——这是「澄清永远放第一步」的纪律。

### 4.2 三条硬约束的设计推演

以站内场景题为基准：**10 万份文档（PDF/Word/Confluence）、全员问答、答案可信可溯源、部门隔离、新文档当天生效**。逐条把约束翻译成设计决策：

| 约束 | 推演 | 设计决策 |
|---|---|---|
| 10 万文档 | 在线向量检索毫秒级无压力；瓶颈在解析与索引吞吐 | 解析服务水平扩展；结构感知切分（300–500 字、约 15% 重叠）；Milvus/Qdrant 与 BM25 双索引 |
| 部门隔离 | 全员使用但部门间文档互不可见 | 每个 chunk 挂元数据（dept/密级/状态/版本）；检索层按用户身份前置过滤（见 4.3） |
| 当天生效 | 「更新了答案还是旧的」是必考追问 | webhook 触发增量流水线（解析→切分→向量化→入库），配新鲜度监控（见 4.4） |
| 可信可溯源 | 引用必须能点回原文 | payload 存来源/页码/段落定位；Prompt 强制标注引用编号 |
| 多格式（PDF/Confluence） | 版式还原与 API 拉取是脏活 | PDF 按标题结构还原；Confluence 走 API 增量拉取；表格转文本+描述 |

注意顺序：**先约束后方案**。面试官没给约束时，第一动作是问（并发量级？允许云 API 吗？数据合规？准确率优先还是成本优先？）。之后所有设计都锚定在澄清结果上——本篇其余部分一律以「已确认内部部署、准确率优先」为前提。

### 4.3 权限前置：一条铁律与三个工程要点

三层失效点分析，说明为什么只有检索层可靠：

```text
生成后隐藏（LLM 判断该不该说）  → 不可靠：模型可能复述，引用编号直接暴露存在性
提示词要求（「不要泄露 A 部门文档」）→ 更不可靠：概率性约束，注入诱导下必被绕过
检索层过滤（无权文档不进候选）   → 可靠：确定性代码，文档根本没进上下文
```

三个工程要点：

1. **过滤条件下推给向量库**（Qdrant Filter / Milvus expr / ES filter），而不是「取回 Top-K 后在应用层丢弃」。丢弃版有两个问题：浪费算力；更严重的是无权文档会挤占 Top-K 名额，导致有权的好结果被挤出去。
2. **ACL 与索引同源**：权限元数据来自文档管理系统这一唯一事实源，权限变更（转岗、文档降密）要触发索引元数据更新，否则出现「转岗三个月还能检索原部门文档」这类审计事故。
3. **全链路留痕**：谁、什么时间、问了什么、命中并返回了哪些文档 ID——审计是事后追责与权限策略调优的唯一依据（见 3.8 最小权限与审计）。

### 4.4 增量索引与原子切换

「当天生效」的技术本质是两句话：**更新链路不断、切换不留空窗。**

增量更新的完整链条：文档系统 webhook → 消息队列 → 解析 → 切分 → 向量化 → 写入。四个工程细节决定它是否真的可靠：

1. **内容寻址去重**：对切分结果做内容哈希，哈希未变的 chunk 不重新嵌入。10 万文档全量重嵌一次的成本是增量模式的两个数量级以上——去重是增量流水线的经济基础。
2. **按文档 ID 整组替换**：文档修改后，旧 chunk 必须先全部删除再写入新 chunk。混存的典型症状是「检索到已废止的政策旧版」，而且新旧并存时 Rerank 也救不回来——两版语义几乎一样，只有版本号不同。
3. **版本化重建 + 原子切换**：大范围重建（换嵌入模型、调切分参数）时，新建 shadow collection 全量灌完、回归评估通过后，把 alias 一次切换到新 collection。用户永远只看到完整可用的索引，不存在「重建到一半」的中间态；旧 collection 保留一段时间用于回滚。
4. **新鲜度监控**：对每篇文档记录「源更新时间 → 索引生效时间」的延迟，超过 SLO（如 4 小时）告警。没有监控的流水线等于没有流水线——webhook 鉴权过期、队列积压这类故障，用户永远比告警先发现。

### 4.5 检索 + 生成联合评估

评估的单位不是「答案好不好」，而是**链路每一段的责任划分**：

| 层 | 指标 | 回答的问题 | 主要手段 |
|---|---|---|---|
| 检索召回 | Recall@K / Hit Rate | 该找到的找到了吗 | golden set 人工标注出处 |
| 检索排序 | MRR / NDCG / Precision@K | 找到的排得靠前吗 | 混合检索、Rerank 调优 |
| 上下文质量 | 上下文相关性 | 注入的资料都相关吗 | RAGAS / LLM-as-Judge |
| 生成忠实度 | Faithfulness | 答案基于检索内容吗 | RAGAS / NLI 模型 |
| 生成相关性 | Answer Relevancy | 答了这个问题吗 | LLM-as-Judge |
| 引用正确性 | Citation Accuracy | 引用指向正确来源吗 | 代码校验 + 抽样人评 |
| 联合 | 分层归因 | 是没检到，还是检到了没答好 | badcase 逐条归因 |

联合评估的判据——golden set 每条带标准出处（文档 ID），逐条走这个决策树：

```text
Recall@5 未命中          → 检索问题：查切分粒度、嵌入模型、混合检索、查询改写
Recall@5 命中且忠实度低  → 生成问题：查 Prompt 约束、上下文排序、模型能力
Recall 低且忠实度也低    → 先修检索：检索不召回，生成优化全是空中楼阁
```

golden set 本身要**分层**：按文档类型（政策/表格/流程图）、问题类型（事实/对比/多跳）、难度分层抽样，各层分别看指标。总分掩盖局部崩塌——「总体忠实度 0.9」可能藏着「表格类问题忠实度 0.4」。规模上 500 条是常见起点，每周回归一次，任何改动（切分参数、Rerank 模型、Prompt 版本）必须跑全集、指标不回退才可发布（对应 3.9 的评估门禁）。

### 4.6 生产闭环：Trace → badcase → 回归集

上线不是终点，是飞轮的起点。3.4 可观测性与 3.5 评估体系的机制在这里合流成一条生产线：

1. **全链路 Trace**：每次问答记录原始查询、改写结果、检索命中的文档与分数、Prompt 快照、生成答案、引用、用户反馈（赞/踩）。缺了任何一段，badcase 都无法归因。
2. **坏例挖掘**：负反馈是显式信号；隐式信号包括拒答率异常、引用缺失、Rerank 分数断崖（第一名 0.9 第二名 0.3 说明检索很不确定）。
3. **周会归因**：每条 badcase 判定层级——检索 / 生成 / 数据（文档本身错或过期）/ 权限（该找到的因过滤被挡）——分类入池。归因错了，修复就打偏。
4. **沉淀回归集**：修一条，就把这条连同标准答案进回归集；下次任何改动跑全集，不回退才放行。
5. **复利**：回归集从 50 条滚到 500 条的过程，就是系统从「改一处抖三处」到「周级迭代敢放量」的过程。

## 6. 代码 / 工具

### 6.1 权限过滤检索

```python
# acl_retrieval.py —— 检索层权限前置：无权文档根本不进候选
from dataclasses import dataclass

@dataclass
class UserCtx:
    user_id: str
    dept: str                # 所属部门
    clearance: int           # 密级：1 内部公开 / 2 部门级 / 3 高管级
    is_admin: bool = False

def build_filter(user: UserCtx) -> dict:
    """过滤条件下推给向量库（Qdrant 风格 Filter / Milvus expr）。
    绝不能「先取 Top-K 再在应用层丢弃」——丢弃版让无权文档挤占名额。"""
    return {"must": [
        {"key": "clearance", "range": {"lte": user.clearance}},
        {"key": "dept", "match": {"any": [user.dept, "ALL"]}},
        {"key": "status", "match": {"value": "published"}},   # 草稿/废止不进候选
    ]}

def search(user: UserCtx, query: str, top_k: int = 5) -> list[dict]:
    hits = qdrant.search(
        collection="kb",
        query_vector=embed(query),            # 嵌入与入库必须同一模型
        query_filter=build_filter(user),      # ① 权限过滤在检索层，先于一切
        limit=top_k,
        with_payload=True,                    # 带来源：doc_id/page/dept
    )
    audit(user_id=user.user_id, query=query,  # ② 全链路留痕（3.8）
          doc_ids=[h.payload["doc_id"] for h in hits])
    out = []
    for h in hits:
        p = h.payload
        out.append({"text": p["text"],
                    "cite": f'[{p["doc_id"]} p{p["page"]}]'})  # ③ 引用可回溯到页
    return out
```

### 6.2 增量索引与原子切换

```python
# incremental_index.py —— webhook 增量更新 + 整组替换 + alias 原子切换
import hashlib

def chunk_hash(text: str) -> str:
    return hashlib.sha1(text.encode()).hexdigest()[:16]

def upsert_document(doc: dict):
    """单文档增量：先删旧 chunk 再写新 chunk，保证整组替换。"""
    old = collection.fetch_all(filter={"doc_id": doc["id"]})
    if old:
        collection.delete(ids=[p["chunk_id"] for p in old])  # ① 删旧：防新旧混存
    for chunk in split_by_structure(doc["content"]):         # 结构感知切分
        h = chunk_hash(chunk["text"])
        if collection.exists(content_hash=h):                # ② 内容寻址：未变不重嵌
            continue
        collection.upsert(
            id=new_chunk_id(),
            vector=embed(chunk["text"]),
            payload={"text": chunk["text"], "doc_id": doc["id"],
                     "dept": doc["dept"], "clearance": doc["clearance"],
                     "status": doc["status"], "version": doc["version"],
                     "content_hash": h})
    freshness_track(doc["id"], stage="indexed")              # ③ 新鲜度打点

def rebuild_with_alias_swap(new_params: dict):
    """换嵌入模型/切分参数：shadow 全量重建，回归通过后原子切换。"""
    shadow = client.create_collection("kb_v2", **new_params)
    for doc in stream_all_documents():     # 全量灌 shadow，线上 kb 不受影响
        write_to(shadow, doc)
    if eval_regression(shadow).passed:     # ④ 回归不过不放行（3.9 评估门禁）
        client.update_aliases(alias="kb", collection="kb_v2")  # ⑤ 原子切换
        client.delete_collection("kb_v1")  # 旧版保留窗口期后再删，支持回滚
```

### 6.3 检索 + 生成联合评估脚本

```python
# joint_eval.py —— 分层归因：先判检索，再判生成
import json, re

def recall_at_k(gold_ids: set, hit_ids: list, k: int = 5) -> float:
    return len(gold_ids & set(hit_ids[:k])) / max(len(gold_ids), 1)

def numeric_faithful(answer: str, context: str) -> bool:
    """忠实度近似校验：答案中的数字必须能在检索内容中找到——专打幻觉数字。"""
    nums = re.findall(r"\d+(?:\.\d+)?[%天元个月周小时]?", answer)
    return all(n in context for n in nums)

def joint_eval(cases_path: str):
    layer = {"retrieval_fail": [], "generation_fail": [], "both_ok": 0}
    for case in map(json.loads, open(cases_path)):
        hits = search(user=case["user"], query=case["q"], top_k=5)
        r = recall_at_k(set(case["gold_doc_ids"]),
                        [h["doc_id"] for h in hits])
        context = "\n".join(h["text"] for h in hits)
        answer = generate(case["q"], context)          # 正常 RAG 生成
        if r < 1.0:                                    # ① 没检到 → 检索问题
            layer["retrieval_fail"].append(case["id"])
        elif not numeric_faithful(answer, context):    # ② 检到了没答好 → 生成问题
            layer["generation_fail"].append(case["id"])
        else:
            layer["both_ok"] += 1
    total = len(layer["retrieval_fail"]) + len(layer["generation_fail"]) + layer["both_ok"]
    print(f"检索未召回 {len(layer['retrieval_fail'])}/{total}"
          f"（修切分/混合检索/查询改写）")
    print(f"生成不忠实 {len(layer['generation_fail'])}/{total}"
          f"（修 Prompt 约束/上下文排序/Rerank）")
    return layer
```

## 7. 案例

### 案例 A：某互联网公司 10 万文档知识库全案

**场景**：全员知识问答，PDF/Word/Confluence 混杂，要求可溯源、部门隔离、当天生效。

**实施**：按本篇架构落地——结构切分 400 字、15% 重叠；BGE-M3 嵌入 + Milvus/Qdrant 与 BM25 双索引；混合检索（RRF）+ BGE-Reranker 精排 Top-5；检索层 ACL 前置过滤；生成三约束 + 引用编号。评估集 500 条按文档类型与问题类型分层。

**效果**（示意量级）：Recall@10 从 0.62 提升到 0.89（主要来自混合检索与重排）；忠实度从 0.71 到 0.93（主要来自 Prompt 三约束与引用校验）；新文档索引生效 P95 从全量日更的 26 小时压缩到 40 分钟；权限类事故 0 起。

### 案例 B：「答案还是旧的」事故复盘

**症状**：差旅政策更新三天，员工仍被引导走旧报销流程，投诉集中爆发。

**排查**：Trace 显示检索命中的仍是旧版本 chunk。根因在增量链路：Confluence webhook 的鉴权 token 过期，更新事件在死信队列里积压两天，无人告警；且旧流水线不做整组替换，同一文档新旧 chunk 并存，Rerank 无法区分版本。

**修复**：webhook 失败重试 + 死信队列告警；新鲜度监控（源更新→索引生效 > 4 小时即告警）；按文档 ID 整组替换；版本号进入元数据并在引用中展示。

**效果**：此后 6 个月时效类投诉为 0。教训一句话：**RAG 的时效是链路属性，不是模型属性——「知识库更新了答案还是旧的」九成是更新流水线断了。**

### 案例 C：回归集从 50 条到 500 条

**场景**：知识库团队要频繁调切分参数与 Rerank 模型，但每次改动都在线上引发「变好这里、弄坏那里」。

**实施**：从 Trace 负反馈与低置信信号里筛 badcase，每周归因 30–50 条；修复一条入集一条，配套评估脚本进 CI。

**效果**：半年后回归集 500+ 条，改版引发的指标回退率从约 20% 降到 4%，迭代节奏从「不敢动」变为周级放量。回归集本身成为团队最有价值的资产——它把「感觉变好了」变成「全集不回退」。

## 8. 常见坑

1. **不澄清需求直接报技术栈**。对策：六个问题背下来先问，规模与权限没清前不展开细节。
2. **权限设计放在生成层**。对策：检索层前置过滤是唯一可靠位置，无权文档不进上下文。
3. **权限过滤在应用层做「取回后丢弃」**。对策：过滤条件下推给向量库，否则无权结果挤占 Top-K 名额。
4. **只看最终答案不看链路**。对策：检索+生成联合评估，先 Recall@K 后忠实度，分层归因再动手。
5. **评估集不分层**。对策：按文档类型/问题类型/难度分层看指标，总分掩盖局部崩塌。
6. **元数据只有文本没有权限字段**。对策：dept/密级/状态/版本四件套从第一天进 payload。
7. **更新靠全量重建**。对策：webhook 增量流水线 + 内容哈希去重，成本差两个数量级。
8. **文档更新不删旧 chunk**。对策：按文档 ID 整组替换，否则新旧混存检索到废止版。
9. **大改动直接在现网索引上重建**。对策：shadow collection + alias 原子切换，回归不过不放行。
10. **更新链路无监控**。对策：新鲜度打点 + 死信队列告警，别让用户当第一个报警的人。
11. **上线即结束**。对策：Trace→badcase→回归集飞轮转起来，系统是养出来的。
12. **Top-K 与上下文越长越好**。对策：Top-5 左右配重排足够，塞满窗口只会噪音干扰加成本。
13. **多轮对话不重写查询**。对策：「那退款呢？」单独检索必失败，先做指代补全。

## 10. 小结

- 这道题考的不是零件，是**整张图纸**：六板块（需求/架构/数据/安全/评估/成本）按序推进，不漏项。
- 需求澄清永远是第一步：**用户范围、文档量与格式、更新频率、权限模型、SLO、预算**——边界决定选型。
- 权限铁律：**检索层前置过滤，无权文档不进候选**；过滤条件下推给向量库，应用层丢弃是错的。
- 「当天生效」= webhook 增量流水线 + 内容哈希去重 + 按文档整组替换 + 新鲜度监控。
- 大范围重建用 **shadow collection + alias 原子切换**，回归不过不放行。
- 评估必须**联合**：检索看 Recall@K/MRR，生成看忠实度/相关性/引用准确率，先归因再优化。
- 「更新了答案还是旧的」九成是增量索引链路故障——RAG 的时效是链路属性，不是模型属性。
- 生产闭环：**Trace 落盘 → badcase 归因 → 回归集沉淀 → 评估门禁**，回归集是系统最值钱的资产。
- 安全三件套：防幻觉三约束、untrusted 分区防注入、输出过 DLP；全链路审计留痕。
- 成本三板斧：前缀缓存、语义缓存、模型路由（详见 3.7c）；收尾必给 MVP→完善的演进路线。
- 数字最全的终极展开在 4.2b；评估方法论在 2.9/3.5，数据管线深水区在 3.2。
