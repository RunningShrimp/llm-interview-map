# 讲解 3.5 评估体系与实验管理

> 说明：1.6「LLM 应用评估与可观测性」教的是怎么跑一次评估，本页把它升级为体系与制度：评估集分层、Judge 对人评校准、单变量 A/B、跑分历史表与发布门禁。

## 1. 定位

L3 工程化层第 5 个知识点，必选锚点（掌握等级「熟练」）。

它回答一个团队治理问题：**每周几十次提示词、模型、参数改动里，哪次真的让系统变好了？半年后还能复现这个结论吗？**

前置依赖：

- 1.6 LLM 应用评估与可观测性：金标集、指标、LLM-as-Judge 入门——本页把这些散点织成制度。
- 3.4 可观测性与追踪：trace 与抽样提供坏例来源与线上验证数据，评估体系是观测的消费端。

后续衔接：

## 2. 一句话定义

评估体系与实验管理（Evaluation System and Experiment Management）是把评估从「事后报告」变成「事前护栏」的一套制度：**评估集分层托管、Judge 定期对人评校准、改动走单变量 A/B 并过显著性判定、跑分沉淀历史表、分数倒退自动阻断发布**——让每一版的好坏永远有据可查。

## 3. 为什么需要

没有体系的团队长这样：

1. **改版靠手感**：提示词今天改、明天改回去，谁也说不清当前版本为什么长这样。
2. **实验不可归因**：同时改提示词、换模型、调 temperature，上线效果好，但不知道功劳归谁，甚至正负抵消。
3. **Judge 悄悄变质**：LLM-as-Judge 上线时和人评一致率 85%，三个月后掉到 60%，而所有人都还在采信它的分数。
4. **坏例重复犯**：线上翻车修完就忘，同类问题下个月换个姿势再翻一次。
5. **离线分与线上表现脱节**：离线评估集涨了 3 分，上线后用户差评率反而升了——没人解释得了。

根因只有一个：评估是「手工作坊」而不是「带质量门禁的流水线」。实验管理的核心不是跑分，是**设计能归因、可复现、有门禁的实验**。

| 手工作坊 | 评估体系 |
|---|---|
| 一套测试集打天下 | 冒烟/回归/坏例库三层各司其职 |
| judge 分数直接采信 | judge 先考证（对人评校准）、证会过期 |
| 多变量一起改看总分 | 单变量 A/B + 显著性判定 |
| 分数散落在聊天记录 | 跑分历史表，版本可追溯 |
| 上线前靠自觉跑评估 | 分数倒退自动阻断合并与发布 |

## 4. 核心原理

### 4.1 评估集分层

一套集打天下，要么跑不动（太大），要么跑不快（每次发版等 1 小时）。分层是解法：

| 层 | 规模 | 跑的时机 | 管什么 | 跑分预算 |
|---|---|---|---|---|
| 冒烟集（Smoke） | 20-50 条关键路径 | 每次提交/发版前 | 快速拦住毁灭性倒退 | 2 分钟内 |
| 回归集（Regression） | 150-500 条全场景 | 大改动、日批、发版前 | 全能力面不退步 | 十分钟到小时级 |
| 坏例库（Bad-case Set） | 持续增长，每条带归因标签 | 并入回归集一起跑 | 犯过的错不再犯 | 随回归集 |

三条运维纪律：

1. **全部进代码仓库版本化**：用例是资产，资产必须有版本、有 review。
2. **坏例自动入库**：线上翻车（点踩、judge 低分）经 3.4 的坏例回放定位后，脱敏、加期望行为，自动转成新用例。
3. **分层不混淆**：冒烟集求快求准，绝不为覆盖率往里塞题；覆盖率诉求归回归集。

### 4.2 LLM-as-Judge 校准

Judge 是「用模型给模型打分」，它本身不可靠，必须当被治理对象。**资格证制度**：

1. **上岗前考证**：抽 30-50 条人工标注好的样本让 judge 判，算与人评的一致率（Agreement Rate）；80% 以上才发证上岗。同时看混淆分布：judge 系统性偏松（人评 3 分它给 4 分）比一致率低更危险，因为它是方向性偏差。
2. **证会过期**：三种情况任一发生都要重考——换了 judge 模型、改了评分 prompt、应用输出分布变化（如从短摘要变成长报告）。上游 API 静默升级也算。
3. **一致率本身是被监控指标**：每月抽 40 条人工标注对齐，一致率跌破阈值先**冻结 judge 分数的采信**，排查原因、必要时重写评分标准再恢复。

校准操作表：

| 步骤 | 做法 | 产出 |
|---|---|---|
| 1. 建锚定集 | 30-50 条覆盖各分数段的人工标注样本，版本化托管 | 校准基准 |
| 2. 算一致率 | judge 分与人类分逐条对比：完全一致率、±1 容差一致率、加权 Kappa | 一致率数字 |
| 3. 查方向偏差 | 按「judge 偏松/偏严」分桶统计 | 偏差画像 |
| 4. 修评分标准 | 把分歧样本喂回评分 prompt 迭代，重跑锚定集 | 新版评分 prompt |
| 5. 挂监控 | 每月复测一致率，跌破 80% 触发冻结与复盘 | 持续可信的 judge |

### 4.3 单变量 A/B 与显著性

归因的前提是控制变量。一次实验只改一个变量（提示词**或**模型，别都改）；其余全部冻结。

标准流程五步：

```text
① 冻结单一变量：本次只改提示词，模型/参数/检索配置全不动
② 分层分流：新旧版本各接 50% 流量，按用户哈希分组，同人体验一致
③ 双指标记录：客观指标（任务成功率）+ judge 主观分（已校准）
④ 显著性判定：差异超出波动范围才下结论，平局如实记录为平局
⑤ 沉淀归档：结果写入历史表，胜出版本成为新基线
```

显著性判定用双比例检验（两个版本的 success/n 各做一个比例）：

- 判定统计量：z = (p1 - p2) / sqrt(p̂(1-p̂)(1/n1 + 1/n2))，p̂ 为合并比例。
- 经验刻度：各 100 条样本时，常见基线率下成功率差要在 12~14 个百分点以上才可能显著；各 500 条时，约 6 个百分点；**平局时如实说平局**——把噪声当胜利是实验管理的头号事故。
- 判定标准（指标、阈值、样本量）在实验开始前写死并留档（预注册），防止事后挑指标。

### 4.4 跑分历史表

每次评测的版本、分数、成本、坏例全部归档。没有它，「我们这一年变好了吗」「哪次改动贡献最大」永远答不出。

| 字段 | 示例 | 用途 |
|---|---|---|
| run_id / 时间 | run-20260916-01 | 唯一定位一次评测 |
| 版本标识 | prompt v17 + gpt-4o-mini + k=5 | 复现实验配置 |
| 评估集 | regression@v42（212 条） | 知道分数是对哪套题的 |
| 核心指标 | 忠实度 0.88 / 相关性 0.91 / 拒绝率 3.2% | 跨版本对比 |
| judge 版本 | judge-v3（一致率 84%） | 分数可信度锚点 |
| 单例成本 | 0.021 元 | 分数与成本的联合决策 |
| 新增坏例 | 3 条（标签：检索未命中） | 与 3.4 坏例闭环联动 |
| 结论 | 显著优于 v16（z=2.6，p<0.01），采纳 | 决策留档 |

纪律：分数必须连同**配置与 judge 版本**一起存——脱离配置的分数没有可比性。

### 4.5 回归门禁与离线分不等于线上赢

**回归门禁**：评估分数接入发布流程——提示词改动必须先过冒烟集，再过回归集，分数写入历史表，倒退超阈值自动阻断合并。评估从「事后报告」变成「事前护栏」。3.9 的 Eval Gate 就是这一思想在 CI/CD 流水线里的工程化。

**离线分不等于线上赢**：评估集再好也是对历史的采样，用户行为会变、场景会漂。离线赢了只拿到灰度资格：

```text
离线评估通过（回归集不倒退）
  → 灰度 5%~10% 真实流量，观察 1-2 周
  → 线上指标：真实解决率、复问率、转人工率、差评率、单次成本
  → 线上不劣化（且业务指标不倒退）才全量放量
  → 线上翻车的新坏例 → 坏例库，下次评估集更接近真实分布
```

线下线上两套指标互为验证：线下管「别退步」，线上管「用户是否真的买账」。

## 6. 代码 / 工具

### 6.1 评估脚本：分层跑批与历史表落档

```python
import json
import time
from dataclasses import dataclass

@dataclass
class EvalCase:
    id: str
    question: str
    expected_keywords: list   # 客观判分用
    label: str = ""           # 坏例库归因标签：retrieval_miss / faithfulness / ...

def keyword_scorer(case: EvalCase, answer: str) -> float:
    hit = sum(1 for kw in case.expected_keywords if kw in answer)
    return hit / len(case.expected_keywords) if case.expected_keywords else 1.0

def run_eval(runner, dataset: list[EvalCase], scorers: dict) -> dict:
    """runner: 把 question 变成 answer 的待测管线（版本 A 或 B）。"""
    per_case = []
    for case in dataset:
        t0 = time.monotonic()
        answer = runner(case.question)
        per_case.append({
            "id": case.id, "label": case.label,
            "scores": {name: fn(case, answer) for name, fn in scorers.items()},
            "latency_ms": int((time.monotonic() - t0) * 1000),
            "answer": answer,
        })
    summary = {
        name: sum(c["scores"][name] for c in per_case) / len(per_case)
        for name in scorers
    }
    return {"per_case": per_case, "summary": summary}

def gate_check(result: dict, baseline: dict, min_delta: float = 0.0) -> bool:
    """发布门禁：任一核心指标倒退超阈值即阻断。"""
    for metric, base in baseline["summary"].items():
        if result["summary"].get(metric, 0) < base - min_delta:
            print(f"[GATE] BLOCKED: {metric} {base:.3f} -> "
                  f"{result['summary'].get(metric, 0):.3f}")
            return False
    print("[GATE] PASSED")
    return True

smoke = [EvalCase(**c) for c in json.load(open("smoke_set.json"))]
result = run_eval(my_rag_runner, smoke, scorers={"kw": keyword_scorer})
gate_check(result, baseline=json.load(open("history/latest.json")))
```

### 6.2 Judge 校准：与人评一致率与漂移监控

```python
def judge_score(judge, question: str, answer: str, rubric: str) -> int:
    """调用 judge 模型按 rubric 打 1-5 分（实现略，须解析为 int）。"""

def calibrate(judge, anchor_set: list, rubric: str, tolerate: int = 1) -> dict:
    """anchor_set: [{"question","answer","human":3}, ...] 人工标注的锚定集。"""
    exact, within, bias = 0, 0, 0
    for item in anchor_set:
        j = judge_score(judge, item["question"], item["answer"], rubric)
        diff = j - item["human"]
        exact += (diff == 0)
        within += (abs(diff) <= tolerate)
        bias += diff                       # 正=judge 偏松，负=偏严
    n = len(anchor_set)
    return {
        "n": n,
        "exact_agreement": exact / n,          # 完全一致率
        "tolerated_agreement": within / n,     # ±1 容差一致率
        "mean_bias": bias / n,                 # 方向性偏差
        "certified": within / n >= 0.80,       # 资格线
    }

# 月度复测 + 漂移监控：跌破阈值冻结 judge 采信
report = calibrate(judge_v3, json.load(open("anchor_set_v2.json")), RUBRIC)
if not report["certified"] or abs(report["mean_bias"]) > 0.5:
    print("[JUDGE] 冻结采信：一致率或方向偏差越线，复写评分标准并重考")
else:
    print(f"[JUDGE] 在岗：±1 一致率 {report['tolerated_agreement']:.0%}，"
          f"平均偏差 {report['mean_bias']:+.2f}")
```

### 6.3 显著性判定：双比例 z 检验

```python
import math

def two_proportion_z(s1: int, n1: int, s2: int, n2: int) -> dict:
    """版本1成功 s1/n1，版本2成功 s2/n2；返回 z 值与是否显著(α=0.05)。"""
    p1, p2 = s1 / n1, s2 / n2
    p = (s1 + s2) / (n1 + n2)
    se = math.sqrt(p * (1 - p) * (1 / n1 + 1 / n2))
    z = (p1 - p2) / se
    return {"z": round(z, 2), "significant": abs(z) >= 1.96}

# 各 100 条、成功率 72% vs 85% → z≈2.24，显著，可采纳
print(two_proportion_z(72, 100, 85, 100))
# 各 100 条、72% vs 78% → z≈0.98，不显著，如实记录平局
print(two_proportion_z(72, 100, 78, 100))
```

## 7. 案例

### 案例 A：提示词改版从「手感」到「门禁」

**场景**：某知识库问答团队每周改十几次提示词，版本越堆越多，无人说清哪次改动有效。

**做法**：整理出冒烟集 30 条、回归集 212 条；坏例自动入库；流水线加门禁——冒烟集 2 分钟、回归集 10 分钟，任一核心指标倒退超 1 个百分点即阻断合并；judge 建锚定集 40 条，月度复测一致率。

**效果**：三个月内门禁拦下 9 次劣化合并；「本版本为什么长这样」的答案永远能在历史表里翻到对应 run。

### 案例 B：一次不可归因的「胜利」

**场景**：某客服 Agent 同时换了新模型、改了系统提示、调高 temperature，上线后满意度从 68% 升到 79%。团队内部争论贡献归属，无解。

**复盘**：回滚后按单变量纪律重做——只换模型：+6 分；只改提示词：+4 分；只调 temperature：-1 分且引入格式错误。三项合并的 11 分与当初 11 分吻合，但 temperature 的负贡献此前被完全掩盖。

**效果**：此后团队实验全部单变量化；「哪个改动贡献最大」从争论变成查表。

### 案例 C：离线 3 分的胜利，线上 2 周的翻车

**场景**：某金融助手的离线评估集忠实度涨 3 分、相关性涨 2 分，直接放量上线。

**后果**：灰度数据两周后发现复问率（用户重复追问同一问题）上升 18%——新版回答更「严谨」但更含糊，离线集没有覆盖这类「正确但没用」的样本。

**修正**：把「复问率」纳入线上灰度必看指标；离线评估集补充 30 条「完整性」用例；从此离线通过只给灰度资格，灰度两周线上不劣化才放量。

## 8. 常见坑

1. **一套评估集打天下**。每次发版跑全量，慢到没人肯跑；冒烟/回归分层后门禁才跑得动。
2. **评估集不进版本管理**。用例散落在表格与聊天记录里，跨版本分数不可比。
3. **judge 不校准直接上岗**。与人评一致率未知就采信 judge 分，等于用未知精度的尺子量一切。
4. **judge 证不过期**。换 judge 模型、改评分 prompt、输出分布漂移后仍用旧一致率背书；任一变化触发重考。
5. **只看一致率不看方向偏差**。judge 系统性偏松会把「普遍变好」读进去；平均偏差要单独监控。
6. **多变量一起改**。三变量同改的实验在方法论上作废，任何归因都是猜；一次只动一个变量。
7. **分流不看人只看请求**。同一用户一半请求走新版一半走旧版，体验错乱还污染统计；按用户哈希分组。
8. **事后挑指标**。实验跑完才选「看起来赢」的指标；判定标准必须实验前预注册。
9. **把噪声当胜利**。各 100 条样本 5 个百分点的差异完全在波动范围内；过显著性判定再下结论。
10. **历史表不存配置**。只有分数没有版本、模型与 judge 版本，三个月后无法复现与对比。
11. **离线分高直接全量**。评估集是对历史的采样，覆盖不了真实分布；离线通过只给灰度资格。
12. **坏例修完不入库**。同一类翻车换个姿势重演；坏例必须脱敏、打标签、转回归用例。
13. **门禁只挡提示词**。模型、检索参数、切分策略的变更同样走门禁，否则护栏有洞。

1. 把现有测试用例整理为冒烟集（30 条）与回归集（200 条），进仓库版本化，写清各自的运行时机。
2. 用 6.1 的 Runner 给你的 RAG 管线跑一次全量回归，输出逐例结果与汇总分。
3. 实现门禁函数：对比新版本与历史基线，任一指标倒退超 1 个百分点即返回阻断，接入一次真实的合并流程。
4. 标注 40 条人工样本建锚定集，用 6.2 校准你的 judge，记录完全一致率、±1 一致率与平均偏差。
5. 人为把 judge 的评分 prompt 改苛刻，重跑校准，观察一致率与方向偏差如何变化，写一段复盘认证「证会过期」。
6. 设计并执行一次单变量 A/B：只改检索 k 值（5 对 8），各采 100 条，用 6.3 判定显著性并写入历史表。
7. 给历史表补一条「judge 版本」字段，然后模拟换 judge 模型，说明为什么跨 judge 版本的分数不能直接比。
8. 找一个「离线分涨、线上翻车」的构造案例（如答案正确但过于简略导致复问），为它设计 5 条补充评估用例。

## 10. 小结

- 评估体系回答的不是「分数多少」，而是「**哪次改动真的让系统变好了，且半年后还能复现**」。
- 评估集三层：**冒烟集管发版速度（2 分钟）、回归集管大改动安全、坏例库管持续进化**，全部进仓库版本化。
- Judge 要考证：**上岗前对人评校准（±1 一致率不低于 80%）**，同时监控方向偏差；证会过期——换 judge 模型、改评分 prompt、输出分布漂移任一发生即重考。
- 一致率本身是被监控指标：跌破阈值先冻结 judge 采信，复盘评分标准后恢复。
- A/B 铁律：**单变量、用户哈希分流、判定标准预注册、过显著性判定、平局如实记录**。
- 历史表必须连**配置与 judge 版本**一起存；脱离配置的分数没有可比性。
- 回归门禁：**分数倒退自动阻断合并与发布**——3.9 的 Eval Gate 是它在 CI/CD 里的落地。
- 离线分不等于线上赢：**离线通过只给灰度资格**，灰度看真实解决率、复问率、转人工率与成本，不劣化才放量。
- 闭环飞轮：线上翻车（3.4 trace 回放）→ 坏例入库 → 回归集更厚 → 下次变更更安全。
- 制度 vs 工具：面试答的是**机制设计**（分层、门禁、预注册、judge 治理），工具名只是机制的实施细节。
