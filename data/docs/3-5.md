# 讲解 3.5 评估体系与实验管理

> 说明：1.6 讲了评估的基本概念、指标体系与 LLM-as-Judge 的打分方式、偏差与校准；2.9 讲了 Agent 的轨迹评估与安全评估；3.4 讲了如何用 trace 还原执行现场。
> 3.5 把这些散件组装成**工程体系**：评估集版本化、指标、实验追踪、A/B 测试、回归测试与评估门禁（Eval Gate）。
> 后续 3.9 讲门禁如何接进 CI/CD 流水线与灰度发布，4.8 讲红队评估与对抗测试。

---

## 1. 定位

AI 工程化层第 5 个知识点，属于「质量基础设施」。
它解决一个核心问题：**如何知道一次改版是变好还是变坏——并且让每次改动都被自动验证，使系统持续变好而不是悄悄变坏。**

前置是 1.6（评估的概念、指标与 LLM-as-Judge 基础）和 3.4（trace 为评估供数：坏例筛选、回归集沉淀）；后续承接 3.9（Eval Gate 接进 CI/CD）与 4.8（评估与红队）。

## 2. 一句话定义

评估体系与实验管理，是通过评估集版本化、指标体系、实验追踪、A/B 测试、回归测试与统计显著性检验，把评估嵌入研发流程，实现持续、自动、可复现的质量保障体系。

简化公式：

```text
评估体系 = 评估集 + 指标 + 实验追踪 + 回归测试 + A/B + Eval Gate
```

## 3. 为什么需要

手工评估的痛点：

- **不可复现** → 上次跑 85 分，这次 82 分，分不清是 Prompt 改了还是评估集变了。
- **无法对比** → 两个版本哪个好？凭感觉拍板。
- **回归发现晚** → 上线一周后从客诉才发现变差。
- **评估集散乱** → Excel、JSON、代码里各一份，版本对不上。
- **实验无记录** → 改了 20 版，说不清哪版最好、为什么好。
- **统计不显著** → 10 个用例提升 5%，大概率只是噪声。
- **CI 无评估** → 代码合并前不跑评估，回归风险全部压到线上。
- **人工评估不可持续** → 每次改动都人工看一遍，成本高、看不过来。

**类比 1（餐饮品控）**：没有评估体系 = 私房菜馆换主厨，出品全凭新主厨的口感，老客流失了才知道不对；有评估体系 = 连锁餐厅每道菜有标准配方卡，换厨师也要过盲测评审，口味偏差在出品前就被拦下。

**类比 2（体检基线）**：单看一次血脂数值没有意义，要和去年的基线比、看变化幅度是否超出误差范围。改版评估同理——分数本身不重要，「与基线的差值 + 是否显著」才重要。

```text
手工评估 = 每次改完手动点几下，凭感觉判断
评估体系 = 自动化测试套件：每次提交自动跑，量化对比，超阈值就阻断
```

## 4. 核心原理

### 4.1 评估体系的四个层次

```text
Level 1: 单元测试（Unit Test）      → 格式、解析、工具函数   → 快、确定、每次提交跑
Level 2: 组件评估（Component Eval） → RAG 检索、工具调用、分类 → 中速、按模块跑
Level 3: 端到端评估（E2E Eval）     → 任务成功率、回答质量   → 慢、贵、按版本跑
Level 4: 在线评估（Online Eval）    → 用户反馈、A/B 测试     → 真实流量、持续跑
```

层次越低越快越便宜，越接近代码细节；层次越高越慢越贵，越接近真实体验。CI 里从低到高逐层跑：低层失败就不必跑高层——这与传统测试金字塔同一逻辑，只是「测试」换成了「评估」。

### 4.2 关键问题的正面回答：变好了还是变坏了

单一证据都有盲区：离线评估集可能与线上分布脱节；线上指标会被运营活动、季节波动干扰；「感觉更好」连证据都算不上。工程共识是**三层证据链**：

```text
第一层：离线回归
  在版本化评估集上与基线对比 + 显著性检验
  回答：在已知场景上，这次改动「大概率」变好还是变坏

第二层：在线 A/B
  真实流量分流对照 + 统计检验
  回答：在真实用户分布上，「确实」变好还是变坏

第三层：发布门禁（Eval Gate）
  回归不通过就阻断合并/发布
  回答：无论谁改了什么，系统「至少不会悄悄变坏」
```

一句话：**离线回答「大概率」，A/B 回答「真的」，门禁兜底「至少不变坏」。**

三种在线前评估方式的取舍：

| 维度 | 离线评估 | 在线 A/B | 影子流量（Shadow Traffic） |
|---|---|---|---|
| 信号真实性 | 低（评估集是历史的采样） | 高（真实用户行为） | 中（真实请求、无真实反馈） |
| 速度 | 分钟级 | 天到周级 | 小时到天级 |
| 成本 | 低（评估集固定、可缓存） | 高（影响用户、有风险） | 中（双份推理成本） |
| 可归因 | 强（变量完全可控） | 中（受运营/季节干扰） | 中 |
| 统计功效 | 受评估集规模限制 | 样本充足 | 样本充足 |
| 适用决策 | 日常迭代筛选 | 重大变更定版 | 高风险变更预演 |

影子流量：新版本接收线上真实请求的镜像副本，输出不返回用户、只做记录对比——相当于替补球员跟着打训练赛：跑的是同一套真实战术，不记正式比分，但教练能看到他每个跑位。

**面试高频问法**：「怎么防止改 A 坏 B？」（优化了 A 场景却弄坏 B 场景）。共识口径三条：一是评估集按场景打标签（tag），对比时**按桶看指标**而不只看总分——总分持平可能掩盖 B 桶大跌；二是回归门禁按桶设阈值，任一桶下降超阈值即阻断；三是动 A 之前，先把 B 的历史坏例固化成用例，改完必须过这道关。

### 4.3 评估集管理

评估集（Eval Set）是评估体系的「考卷」。其中人工标注过期望输出的核心子集叫黄金数据集（Golden Set），用于 judge 校准与指标基准。

**版本化**：评估集当代码管，进 git 或对象存储、带版本号；基线（Baseline）文件记录「哪个评估集版本 × 哪个系统版本 = 哪组分数」。评估集一变，历史分数自动失真，所以版本绑定是对比的前提：

```yaml
# eval/sets/core_v3.yaml —— 评估集与代码同管，评审合入后升版本
name: customer-service-core
version: v3
cases:
  - id: cs-0142
    input: "查一下订单 8837 的物流状态"
    expected: { tool: query_logistics, answer_contains: ["已发货"] }
    tags: [logistics, tool-use]
baseline: baselines/core_v3@agent-2.4.1.json   # 评估集版本 × 系统版本 → 分数
```

**评估集分层**：

| 层 | 规模 | 用途 | 频率 |
|---|---|---|---|
| Smoke（冒烟集） | 10–20 条 | 快速验证 | 每次提交 |
| Core | 50–100 条 | 核心能力 | 每日 |
| Full | 500+ 条 | 全面评估 | 发版前 |
| Red Team（红队） | 50–100 条 | 安全测试 | 发版前 |
| Online | 真实流量 | 线上监控 | 持续 |

**构建原则**：代表性（覆盖真实场景）、多样性（不同问法/长度/难度）、平衡性（简单/中等/困难比例合理）、独立性（与调参样例隔离）、可扩展（bad case 持续补充）、版本化（每次变更留痕）。

独立性最容易被忽视。数据泄漏（Data Leakage）的常见渠道与防范：

| 泄漏渠道 | 典型现象 | 防范 |
|---|---|---|
| 调参集与评估集混用 | 同一批 bad case 反复调 Prompt 后仍留在评估集，分数虚高 | 调参样例单独存放；进评估集前先「冷冻」一段时间 |
| Few-shot 示例与用例重叠 | 模型见过几乎原题 | 示例库与用例库做去重检查 |
| 知识库正文收录评估问题 | RAG「开卷考」，检索指标满分是假象 | 评估问题与语料做相似度扫描，过高者移除 |
| Judge 参与过被评版本的构造 | 既当运动员又当裁判 | judge 模型与被评系统版本解耦 |
| 时间泄漏 | 用 T 时刻之后的数据评估 T 时刻的场景 | 按时间切分，评估只用历史侧数据 |

### 4.4 评估指标

**结果指标**：

| 指标 | 公式 | 适用 |
|---|---|---|
| 准确率 | 正确数 / 总数 | 分类、抽取 |
| 精确率（Precision） | TP / (TP + FP) | 误报代价高 |
| 召回率（Recall） | TP / (TP + FN) | 漏报代价高 |
| F1 | 2PR / (P + R) | 精确召回综合 |
| 任务成功率 | 成功数 / 总数 | Agent 端到端 |
| 格式合规率 | 合法输出数 / 总数 | 结构化输出 |

**过程指标**：

| 指标 | 说明 |
|---|---|
| 工具选择准确率 | 选对工具的比例 |
| 参数准确率 | 参数正确的比例 |
| 步数效率 | 最优步数 / 实际步数 |
| 轨迹合理性 | LLM 或人工按轨迹评分（2.9 展开） |

**效率指标**：

| 指标 | 说明 |
|---|---|
| 平均延迟 | 端到端耗时 |
| P95 / P99 | 长尾延迟 |
| 单次成本 | 每次任务费用 |
| Token 消耗 | 输入 + 输出分列 |
| 缓存命中率 | 缓存复用比例 |

**安全指标**：

| 指标 | 说明 |
|---|---|
| 越权率 | 越权操作比例 |
| 注入抵抗率 | 抵御 Prompt 注入比例 |
| PII 泄露率 | 泄露敏感信息比例 |
| 危险操作拦截率 | 高风险操作被拦截比例 |

四类指标别只盯结果：过程指标定位「坏在哪一步」，效率指标接 3.7 的成本延迟治理，安全指标是 4.8 红队的前置。核心指标控制在少数几个——指标太多等于没有指标。

### 4.5 LLM-as-Judge：从「会用」到「上岗」

回顾：judge 的打分方式（绝对打分 vs 成对比较 Pairwise）、四类偏见（位置/长度/自我/格式）与基本校准方法在 1.6 已展开，轨迹级 judge 在 2.9 讲过。本篇只讲把它变成**可持续运行的基础设施**要补的三件事：

1. **上岗门槛**：judge 先在黄金数据集上与人评对齐，一致率（Agreement Rate）达标才允许批量评估。2025–2026 年「judge 校准与人评对齐」已成为独立考察点（来源：Galtea LLM 评估指南 2026；arXiv《Quantitative LLM Judges》2025——judge 分数经回归对齐人评）。
2. **漂移重校准**：judge 模型升级、被评输出风格变化都会让一致性漂移。定期（如每月）用固定校准集重跑一次，一致率跌破门槛就把 judge 摘下岗。
3. **成本与确定性**：CI 中 temperature=0、固定 judge 模型版本；按（评估集版本， 系统版本）缓存判定结果，避免同一改动反复烧钱。

```python
def calibrate_judge(judge_scores: list[float], human_scores: list[float]) -> dict:
    """judge 上岗校准：与人评的一致率 + 相关系数，达标才允许批量评估"""
    n = len(judge_scores)
    agreement = sum(                          # 5 分制下分差 <= 1 视为一致
        1 for j, h in zip(judge_scores, human_scores) if abs(j - h) <= 1
    ) / n
    correlation = pearsonr(judge_scores, human_scores)[0]
    return {
        "agreement": agreement,               # 门槛示意：>= 0.8 才上岗
        "correlation": correlation,           # 参考线：>= 0.7
        "n": n,                               # 校准集几十条起步，太少无意义
    }
```

**面试高频问法**：「LLM-as-judge 本身不可靠怎么办？」共识口径：黄金数据集对齐人评达标后上岗、定期重校准防漂移、成对比较交换顺序去位置偏差、关键发布决策保留人工抽检兜底。分流设计参考 Maxim AI 2026 年的做法：judge 跑全量（千条/分钟级），人评只抽检——用机器换覆盖、用人工保下限。

### 4.6 实验追踪与实验管理

**为什么要记录**：改了 20 版 Prompt，说不清哪版最好、为什么好——没有配置快照的分数无法归因。实验追踪（Experiment Tracking）的底线是：每个分数都能回答「哪个系统版本 × 哪个评估集版本 × 哪套配置」。

实验管理平台的能力清单：

| 能力 | 说明 | 缺失的后果 |
|---|---|---|
| 实验记录 | 名称、假设、指标、时间 | 无法归因，重复试错 |
| 配置快照 | Prompt/模型/参数/依赖全量快照 | 「当时用的哪版 Prompt」说不清 |
| 数据集版本绑定 | 分数挂到评估集版本 | 评估集一变，历史分数失真 |
| 指标对比 | 跨实验 diff、显著性 | 靠肉眼比数字 |
| trace 关联 | 结果可下钻到单条执行轨迹（3.4） | 只有分数，看不到坏例现场 |
| 协作沉淀 | 实验卡片评论、结论归档 | 结论散落在聊天记录里 |

Prompt 版本化与 A/B 联动是 3.5 与 3.9 的交界题（Crosschq 2026 年 prompt 工程师面试原题即问 prompt versioning 与 A/B testing 怎么做）：Prompt 当代码管理（git + 语义化版本），实验记录引用 Prompt 版本号，A/B 每个组绑定一个版本——归因链条才算闭合。

**工具选型（截至 2026 年，变化快，以官方文档为准）**：

| 工具 | 类型 | 特点 |
|---|---|---|
| MLflow | 开源 | 通用实验追踪 |
| Weights & Biases | 商业 | 可视化强 |
| Langfuse | 开源 | LLM 专用，trace + 评估一体 |
| LangSmith | 商业 | LangChain 生态集成深 |
| Prompt Flow | 开源 | Azure 生态 |
| DeepEval | 开源 | LLM 测试框架，可当门禁用 |
| RAGAS | 开源 | RAG 评估指标 |
| OpenAI Evals | 开源 | OpenAI 生态 |

选型看四件事：能否自托管、团队规模、预算、与现有观测栈（3.4）能否打通。

### 4.7 A/B 测试与统计显著性

**流程**：

```text
1. 定义假设：新 Prompt 比旧 Prompt 准确率高 3 个百分点（预注册主指标）
2. 分流：哈希分桶，同一 user_id 稳定落同一组
3. 收集指标：准确率、延迟、成本、满意度
4. 统计检验：比例用 z 检验，连续值用 t 检验或 Mann-Whitney U
5. 决策：显著优于 → 全量；无差异 → 保留简单版；显著差 → 回滚
```

**分流**：按 user_id 哈希分桶（实现见 6.4），保证同一用户始终落同一组、分流与结果无关。不要用「先来的进 A 组」这类时间分流——时段本身与用户行为强相关。

**统计显著性（Statistical Significance）**：p 值的含义是「若新旧其实没差别，观察到当前差异（或更大）的概率」；p < 0.05 才认为提升可信。两个必须一起检查的约束：

1. **样本量**：基线成功率 0.80、想检出 +3 个百分点的提升，α = 0.05、功效 0.8 时每组约需 2,600 条（功效分析，Power Analysis，示意数量级）。样本不够时「不显著」只是没测出来，不等于没差异。
2. **多重比较（Multiple Comparison）**：同时盯 5 个指标、每个 α = 0.05，纯噪声也会有约四分之一的实验「显著」。对策：预注册 1 个主指标、其余列为观察指标，或做 Bonferroni 校正。

### 4.8 回归测试

回归测试（Regression Testing）回答「这次改动有没有破坏已有能力」。触发点不止改代码：

- 代码提交
- Prompt 变更
- 模型升级（含提供方静默更新）
- 工具变更
- 知识库更新

**流程**：

```text
1. 拉取最新代码/配置
2. 跑 Core 评估集
3. 与基线对比（基线 = 上一稳定版本在同一评估集版本上的分数）
4. 任一指标（或任一 tag 桶）下降超阈值 → 标记失败
5. 阻止合并/发布
6. 输出报告：哪些指标、哪个桶、降了多少
```

完整可跑的回归脚本见 6.2。

### 4.9 评估门禁（Eval Gate）

2026 年 LLMOps 岗位直接考的机制：「Code → Test → Eval Gate → Deploy」——评估分数低于阈值即阻断部署（来源：myengineeringpath《LLMOps — CI/CD, Eval Gates & LLM Deployment》2026；Galtea CI/CD quality gate 指南 2026）。

**类比 3（出厂质检）**：Eval Gate 就是整车厂的出厂质检——制动一项不合格，车就不能下线；确有理由要放行，必须走异常单：写明原因、质量总监签字、记录在案、限期整改。没有异常单流程的「口头放行」就是质检形同虚设。

门禁三个组成部分：

**（1）阈值表**（示意，按业务定）：

| 检查 | 阈值 | 动作 |
|---|---|---|
| Smoke 通过率 | < 100% | 阻断 |
| Core 准确率 | 下降 > 3% | 阻断 |
| 回归测试 | 任一指标下降 > 5% | 阻断 |
| 红队通过率 | < 95% | 阻断 |
| 成本 | 上升 > 20% | 警告（治理见 3.7） |
| 延迟 | P95 上升 > 30% | 警告 |

**（2）分级动作**：质量指标（准确率、安全）默认阻断；成本、延迟先警告后阻断——因为它们有主动换取的空间（见 3.7 的取舍）。指标要分桶：总分持平但某 tag 桶大跌 10%，同样阻断（对应 4.2 的「改 A 坏 B」）。

**（3）豁免（Waiver）流程**：阻断不是死路，是绕行审批。

- 谁提：变更作者，写明理由与关联工单（如「分数下降来自评估集口径更新，非真实回归」）。
- 谁批：评估负责人或值班工程师，不能自己批自己。
- 记什么：豁免理由、补偿措施、到期时间。
- 到期怎么办：豁免自动失效，该指标回到门禁之下。
- 健康指标：豁免率本身要进报表——豁免堆积说明阈值定错或质量在滑坡，月度复盘。

**与 3.9 的划界**：本篇定义门禁规则本身——阈值怎么定、动作怎么分级、豁免怎么走、权责归谁；3.9 讲怎么把门禁接进 CI/CD 流水线，与 Prompt Registry、灰度发布、自动回滚组装成完整发布链路。

### 4.10 评估驱动开发流程

```text
 1. 定义任务和指标（预注册主指标）
 2. 构建评估集（Smoke + Core + Full）
 3. 跑基线，保存结果
 4. 改一个变量（Prompt/模型/工具）——一次只改一个，否则无法归因
 5. 跑 Smoke 快速验证
 6. 跑 Core 详细评估
 7. 对比基线，统计检验
 8. 保留提升，回滚退化，记录实验
 9. 提交 PR，CI 自动跑回归
10. 灰度上线，A/B 测试
11. 在线监控，Bad Case 回流
12. 坏例入评估集 → 回到第 4 步
```

这与传统软件的测试驱动开发同构，只是「测试」换成了「评估集 + 指标 + 门禁」——迭代速度不由写代码多快决定，而由评估回路转多快决定。

## 5. 架构 / 流程

评估驱动迭代闭环——整个体系的价值在于这个环能自动转：

```text
┌────────────────────────────────────────────────────────────┐
│                    评估驱动迭代闭环                          │
│                                                            │
│   ┌──────────┐  评估集+基线  ┌──────────┐   通过  ┌─────────┐
│   │ 变更提出 │─────────────→│ 离线评估 │────────→│Eval Gate│
│   └──────────┘              └──────────┘         └─────────┘ │
│        ▲ 回滚/修改               │ 未通过            │ 通过    │
│        │                        ▼                   ▼        │
│        │                   ┌──────────┐       ┌──────────┐   │
│        │                   │ 修复回归 │       │ 灰度/A/B │   │
│        │                   └──────────┘       └──────────┘   │
│        │                        │                   │        │
│        │                        ▼                   ▼        │
│        │                   ┌──────────┐       ┌──────────┐   │
│        └───────────────────│ 复盘记录 │←──────│ 在线监控 │   │
```

支撑这个闭环的平台分层：

```text

实验管理：  实验记录、配置快照、指标对比、trace 关联（3.4）
```

数据从哪来：3.4 的 trace 是原料——坏例从 trace 平台筛出来，人工补期望输出后沉淀为回归用例（MortalJobs《LLMOps 面试指南》2026 把这条「trace 平台 → 坏例筛选 → 回归数据集 → 评估」闭环列为标准考点）；3.10 的反馈闭环是放大器。没有 3.4，评估集只能靠手工攒，闭环转不起来。

### 6.1 指标函数与评估器

```python
import json

def exact_match(output: str, expected: dict) -> float:
    """完全匹配：适用于有唯一标准答案的抽取/分类任务"""
    return 1.0 if output.strip() == expected["answer"].strip() else 0.0

def contains(output: str, expected: dict) -> float:
    """包含关键词：适用于开放问答的宽松判定"""
    return 1.0 if expected["answer"] in output else 0.0

def json_valid(output: str, expected: dict) -> float:
    """格式合规：结构化输出任务的最低门槛"""
    try:
        json.loads(output)
        return 1.0
    except (ValueError, TypeError):
        return 0.0

def judge_score(output: str, expected: dict) -> float:
    """LLM-as-Judge 打分（0-1 化），judge 需先过 4.5 的上岗校准"""
    result = run_judge(task=expected["task"], output=output,
                       reference=expected["answer"])   # temperature=0
    return result["correctness"] / 5.0
```

```python
import time
from dataclasses import dataclass, field

@dataclass
class EvalResult:
    case_id: str
    metrics: dict          # 每个指标一个分数
    passed: bool
    latency: float
    cost: float

class Evaluator:
    """评估器：跑一个评估集，输出按 tag 分桶的指标（4.2 的「防改 A 坏 B」靠分桶）"""

    def __init__(self, agent, metrics: dict):
        self.agent = agent
        self.metrics = metrics        # {"exact_match": fn, "judge": fn, ...}

    async def evaluate(self, dataset: list[dict]) -> dict:
        results = []
        for case in dataset:
            start = time.time()
            output = await self.agent.run(case["input"])
            latency = time.time() - start
            metrics = {name: fn(output, case["expected"])
                       for name, fn in self.metrics.items()}
            results.append(EvalResult(
                case_id=case["id"], metrics=metrics,
                passed=all(m >= 0.5 for m in metrics.values()),
                latency=latency, cost=output.get("cost", 0.0),
            ))
        return self._summarize(results, dataset)

    def _summarize(self, results: list[EvalResult], dataset: list[dict]) -> dict:
        n = len(results)
        tags_of = {c["id"]: c.get("tags", []) for c in dataset}
        summary = {
            "total": n,
            "pass_rate": sum(r.passed for r in results) / n,
            "metrics": {name: sum(r.metrics[name] for r in results) / n
                        for name in self.metrics},
            "avg_latency": sum(r.latency for r in results) / n,
            "avg_cost": sum(r.cost for r in results) / n,
            "by_tag": {},                       # 指标分桶：门禁按桶看阈值
        }
        for tag in {t for ids in tags_of.values() for t in ids}:
            sub = [r for r in results if tag in tags_of[r.case_id]]
            summary["by_tag"][tag] = {
                "n": len(sub),
                "pass_rate": sum(r.passed for r in sub) / len(sub),
            }
        return summary
```

### 6.2 回归评估脚本（CI 可直接调用）

```python
"""regression.py —— 回归评估脚本：对比基线，超阈值即非零退出，供 CI 门禁调用
用法：python -m eval.regression --agent v2.5.0-rc1 --dataset core_v3 --baseline baselines/core_v3@agent-2.4.1.json
"""
import argparse
import json
import sys

async def run_regression(agent, dataset_path: str, baseline_path: str,
                         threshold: float = 0.05) -> int:
    dataset = load_dataset(dataset_path)          # 带版本号的评估集
    baseline = json.load(open(baseline_path))     # 上一稳定版本的分数

    summary = await Evaluator(agent, METRICS).evaluate(dataset)

    regressions = []
    for metric, value in summary["metrics"].items():
        base = baseline["metrics"].get(metric, 0)
        if value < base * (1 - threshold):
            regressions.append({
                "metric": metric, "baseline": base, "current": value,
                "drop": (base - value) / base,
            })
    # 分桶回归：总分持平但某场景桶大跌，同样算失败（防「改 A 坏 B」）
    for tag, base_tag in baseline.get("by_tag", {}).items():
        cur_tag = summary["by_tag"].get(tag, {}).get("pass_rate", 0)
        if cur_tag < base_tag["pass_rate"] * (1 - threshold):
            regressions.append({"metric": f"tag:{tag}",
                                "baseline": base_tag["pass_rate"],
                                "current": cur_tag,
                                "drop": (base_tag["pass_rate"] - cur_tag) / base_tag["pass_rate"]})

    if regressions:
        print("回归检测失败：")
        for r in regressions:
            print(f"  {r['metric']}: {r['baseline']:.3f} -> {r['current']:.3f}"
                  f"（下降 {r['drop']:.1%}）")
        return 1                      # 非零退出码 → CI 阻断合并

    print(f"回归检测通过：{summary['total']} 条用例，"
          f"通过率 {summary['pass_rate']:.1%}")
    json.dump(summary, open("reports/regression.json", "w"), indent=2)
    return 0

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--agent"); parser.add_argument("--dataset")
    parser.add_argument("--baseline"); parser.add_argument("--threshold", type=float, default=0.05)
    args = parser.parse_args()
    sys.exit(run_regression(load_agent(args.agent), args.dataset,
                            args.baseline, args.threshold))
```

### 6.3 实验记录最小实现

```python
"""experiment.py —— 实验记录最小实现：配置快照 + 指标 + 跨实验对比"""
import json
import uuid
from dataclasses import dataclass, field, asdict

@dataclass
class Experiment:
    id: str
    name: str                      # 实验名，如 "rerank-v2-vs-v1"
    hypothesis: str                # 假设：预期什么指标变好多少
    config: dict                   # 快照：prompt_version / model / 参数 / 依赖
    dataset_version: str           # 评估集版本：分数必须挂到考卷版本
    metrics: dict = field(default_factory=dict)
    conclusion: str = ""           # 结论：采纳/放弃/待定 + 理由
    status: str = "running"

class ExperimentTracker:
    def __init__(self, store_dir: str = "experiments"):
        self.store_dir = store_dir
        self.current: Experiment | None = None

    def start(self, name: str, hypothesis: str, config: dict,
              dataset_version: str) -> str:
        self.current = Experiment(
            id=uuid.uuid4().hex[:8], name=name, hypothesis=hypothesis,
            config=config, dataset_version=dataset_version,
        )
        return self.current.id

    def log(self, key: str, value: float):
        if self.current:
            self.current.metrics[key] = value

    def finish(self, conclusion: str, status: str = "done"):
        self.current.conclusion = conclusion
        self.current.status = status
        path = f"{self.store_dir}/{self.current.id}.json"
        json.dump(asdict(self.current), open(path, "w"),
                  ensure_ascii=False, indent=2)

    def compare(self, id_a: str, id_b: str) -> dict:
        a = json.load(open(f"{self.store_dir}/{id_a}.json"))
        b = json.load(open(f"{self.store_dir}/{id_b}.json"))
        return {
            "config_diff": {k: [a["config"].get(k), b["config"].get(k)]
                            for k in set(a["config"]) ^ set(b["config"])
                            | {k for k in set(a["config"]) & set(b["config"])
                               if a["config"][k] != b["config"][k]}},
            "metrics_diff": {k: round(b["metrics"].get(k, 0)
                                      - a["metrics"].get(k, 0), 4)
                             for k in set(a["metrics"]) | set(b["metrics"])},
            "same_dataset": a["dataset_version"] == b["dataset_version"],
            # 同一评估集版本的对比才有意义；否则直接标红
        }

# 使用
tracker = ExperimentTracker()
tracker.start("rerank-v2", "假设：加 Rerank 使 Core 准确率 +3pp",
              config={"prompt_version": "p-41", "model": "gpt-4o-mini",
                      "rerank": "v2"}, dataset_version="core_v3")
tracker.log("pass_rate", 0.85)
tracker.log("avg_latency", 1.9)
tracker.finish("采纳：+3.2pp 达成，延迟可接受", status="adopted")
```

### 6.4 A/B 分流与显著性检验

```python
import hashlib
from scipy import stats

def assign_variant(user_id: str, variants: list[str]) -> str:
    """哈希分桶：同一 user_id 永远落同一组，分流与用户行为无关"""
    bucket = int(hashlib.md5(user_id.encode()).hexdigest(), 16)
    return variants[bucket % len(variants)]

def is_significant(control: list[float], treatment: list[float],
                   alpha: float = 0.05) -> dict:
    """独立样本 t 检验 + 提升幅度；样本量要先过功效分析（4.7）"""
    t_stat, p_value = stats.ttest_ind(control, treatment)
    lift = (sum(treatment) / len(treatment) - sum(control) / len(control)) \
           / (sum(control) / len(control))
    return {
        "n_control": len(control), "n_treatment": len(treatment),
        "t_stat": round(t_stat, 3), "p_value": round(p_value, 4),
        "significant": p_value < alpha, "lift": round(lift, 4),
    }

# 使用：A/B 两组各 3000 条请求的任务成败（0/1）
report = is_significant(
    control=[0 if bad(i) else 1 for i in group_a],   # 旧版本
    treatment=[0 if bad(i) else 1 for i in group_b], # 新版本
)
if report["significant"] and report["lift"] > 0:
    promote_to_100pct()      # 显著为正才全量；显著为负回滚；不显著延长观察
```

## 7. 案例

### 案例 A：Prompt 改动回归（某电商客服团队）

**场景**：工程师修改了客服 Prompt 以提升退款场景的口径准确，CI 自动跑评估。

**结果**：

```text
Smoke 通过率: 100% → 100%（达标）
Core 准确率:  0.85 → 0.82（下降 3.5%，超过 3% 阈值，阻断）
工具准确率:   0.90 → 0.88（下降 2.2%）
平均步数:     3.2 → 4.1（增加 28%，触发延迟警告）
按桶看：退款桶 +6pp，物流桶 -12pp —— 总分掩盖了物流桶大跌
```

**动作**：CI 阻止合并，报告直接指出物流桶回归。
**修复**：回滚 Prompt；把物流桶坏例固化成 8 条新用例后重新修改，第二次提交双桶达标。
**效果**：若无门禁，这次改动会带着 -12pp 的物流回归上线，约一周后才从客诉发现——修复成本从一次 PR 返工变成一次线上事故。

### 案例 B：A/B 测试模型选型（一家金融科技问答产品）

**假设**：旗舰模型比轻量模型准确率高 3 个百分点以上，值得为其成本升级。

**实验**：

```text
分流：user_id 哈希，A/B 各 50%，每组约 6000 次会话

指标（每组均值）：
A 组（轻量模型）: 准确率 0.82, 延迟 1.2s, 单次成本 $0.0005
B 组（旗舰模型）: 准确率 0.89, 延迟 2.5s, 单次成本 $0.008

统计检验：p = 0.03 < 0.05，提升 +7 个百分点，显著
```

**决策**：准确率确实显著提升，但单次成本 16 倍、延迟翻倍，全量不划算。
**最终**：上路由策略——简单查询走轻量模型，复杂查询走旗舰模型；路由版本本身再过一轮 A/B。离线实验先筛掉 3 个候选，只把 2 个放进线上 A/B——离线便宜、在线贵，先离线后在线就是这个顺序的成本原因。

### 案例 C：Bad Case 回流闭环（某文档问答团队）

**流程**：

```text
1. 用户点踩 → 记录 trace_id（trace 来自 3.4 的观测平台）
2. 每周从点踩样本筛出高价值坏例（去重、去噪）
3. 人工分析根因：检索没召回，问题出在切分过粗
4. 修复：调切分 + 加 Rerank
5. 坏例补上期望输出，合入评估集 core_v4
6. 修复版本在 core_v4 上回归通过后发布
```

**效果**：三个月评估集从 60 条长到 210 条，其中约七成来自线上回流；同类问题重复发生率大幅下降——坏例进评估集后，任何让它退化的改动都会被门禁拦下，而不是等下一次客诉。

## 8. 常见坑

1. **评估集和调参集混用**。
   数据泄漏，评估虚高。调参样例单独存放，进评估集前先隔离一段时间。

2. **评估集太小**。
   10 个用例没有统计意义，涨跌全是噪声。Core 至少 50–100 条，并持续回流扩充。

3. **不做版本管理**。
   评估集悄悄变了，历史分数全部失真。评估集进 git，基线绑定「评估集版本 × 系统版本」。

4. **只跑一次评估，没有基线**。
   单点分数无法判断变好变坏。先固化基线，之后每次都对比。

5. **不做统计检验**。
   小样本差异大概率是噪声。用 t 检验/卡方检验加置信区间，样本量先过功效分析。

6. **CI 不跑评估**。
   回归发现太晚，全部压到线上。每次 PR 至少跑 Smoke，回归脚本挂非零退出码。

7. **只看总分不看分桶**。
   总分持平掩盖某场景大跌（改 A 坏 B）。按 tag 分桶出指标，门禁按桶设阈值。

8. **LLM-as-Judge 不校准就上岗**。
   judge 有偏见且会漂移。黄金数据集一致率达标才上岗，定期重校准，关键决策人工抽检。

9. **不做 A/B 测试**。
   离线变好不等于线上变好，凭感觉全量有风险。重大变更灰度 + A/B + 显著性检验。

10. **实验不记录**。
    改了 20 版说不清哪版最好。配置快照 + 指标 + 数据集版本，缺一不可。

11. **一次改多个变量**。
    指标涨了不知道归谁。一次只改一个变量，否则无法归因。

12. **门禁豁免满天飞**。
    阻断被豁免架空，门禁形同虚设。豁免要审批人（不能自批自）、有期限、进月度报表。

13. **评估成本失控**。
    每次提交跑全量评估，又慢又贵。分层：Smoke 快跑，Full 发版前才跑，judge 结果按版本缓存。

14. **忽略在线评估**。
    离线好不代表线上好。监控真实指标：点踩率、解决率、重试率。

15. **不做安全评估**。
    只测功能不测红队，上线后被注入攻击。红队集纳入发版前必跑（4.8 展开）。

16. **评估和开发脱节**。
    评估被当成独立团队的事，开发不看结果。评估嵌进 PR 和 CI，报告发给变更作者本人。

## 9. 练习

1. 为你的 Agent 构建 Smoke（15 条）+ Core（60 条）+ Full（100 条）三层评估集。验收：每条有输入、期望输出和 tag，入库带版本号。
2. 实现 4 个指标函数：exact_match、contains、json_valid、judge_score。验收：在 20 条手工样例上与人工判断一致不少于 18 条。
3. 实现 LLM-as-Judge 并在 50 条黄金数据集上做上岗校准。验收：与人评一致率不低于 0.8（示意门槛），输出一致率和相关系数。
4. 实现 6.3 的实验记录最小实现并跑三次「改动-评估-记录」。验收：能回答「昨天那次改动改了什么配置、指标变化多少」。
5. 实现哈希分流 assign_variant 和显著性检验 is_significant。验收：同一 user_id 调用 100 次落组不变；构造已知差异的两组数据能检出显著。
6. 用功效分析估算样本量：基线成功率 0.80、目标检出 +3pp、α=0.05、功效 0.8。验收：与在线样本量计算器结果数量级一致（约每组 2,600）。
7. 实现 6.2 回归脚本并接入 PR 流水线。验收：人为把某指标降低 6% 时 PR 被阻断，报告列出下降的指标与分桶。
8. 为你的项目写一页门禁规则文档。验收：包含阈值表、阻断/警告分级、豁免流程（谁提、谁批、记什么、多久到期）。
9. 实现 Bad Case 回流管线：点踩日志 → trace → 人工补期望输出 → 评估集新版本。验收：新用例在下一次回归中生效并参与分桶统计。
10. 用 Langfuse 或 MLflow 管理两周的全部实验。验收：导出跨实验对比报表，并复盘一个失败实验的归因。

## 10. 小结

- 评估体系 = **评估集 + 指标 + 实验追踪 + 回归测试 + A/B + Eval Gate**。
- 「变好还是变坏」的三层答案：**离线回归说大概率，在线 A/B 说真的，发布门禁保证至少不变坏**。
- 评估集分层：**Smoke、Core、Full、Red Team、Online**；版本化并与调参集隔离，防数据泄漏。
- 指标四类：**结果、过程、效率、安全**；按 tag 分桶看，防「改 A 坏 B」。
- LLM-as-Judge 是基础设施：**对齐人评达标才上岗，定期重校准防漂移**，CI 中固定种子并缓存结果。
- 实验追踪的底线：每个分数都能回答「**哪个系统版本 × 哪个评估集版本 × 哪套配置**」。
- A/B 三件套：**稳定分流、统计显著性、足够样本量**；预注册主指标防多重比较假阳性。
- Eval Gate：**阈值阻断 + 分级警告 + 带审批与期限的豁免流程**；豁免率堆积说明门禁失效。
- 闭环飞轮：**坏例回流评估集，评估集守住门禁，门禁保护迭代速度**——不能量化就不能优化，不能自动化就不能持续。
- 这些能力直接支撑：3.9 CI/CD、版本管理与发布（Eval Gate 接进流水线）、4.8 评估与红队。
