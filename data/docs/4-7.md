# 讲解 4.7 生产级 Agent 平台

> 说明：2.8 给出了主管-工人/流水线/辩论三种编排与通信协议栈；4.7 先复述这套多 Agent 系统的骨架，再回答平台化问题——多租户、网关、工具市场与治理，并给出「设计一个 Agent 系统」这类终极架构题的答题框架。  
> 上线后的评估与红队、部署与运维分别在 4.8、4.9 展开。

---

## 1. 定位

L4 应用层第 7 个锚点，分两块：**其一**，多 Agent 平台架构——把多个角色化 Agent 组织成有编排、有通信、有治理的系统（考点 4-7）；**其二**，Agent 系统全案设计题——给定「智能客服 Agent」或「数据分析 Agent」，如何给出六层完整设计（考点 4-7b）。两块共用一条主线：从「一个能跑的 Agent」到「一组能复用、能治理、能算账的 Agent」。

前置依赖：2.8 多 Agent 协作（三模式与通信的原始定义）、3.1 Agent 服务架构（接入→网关→服务的分层底座）；全案题还直接调用 4.2 企业知识库、4.3 数据分析 Agent、4.5 幂等与审计的既有结论。  
后续去向：平台上线前后要被 4.8 评估与红队检验，运行期由 4.9 部署与运维守护。

## 2. 一句话定义

生产级 Agent 平台 = 把多个角色化 Agent 组织成有编排、有通信、有治理的系统：三种编排模式选型、结构化消息协议、多租户权限与数据隔离、AI Gateway 收敛模型密钥、工具市场沉淀复用、全链路审计与成本治理；本质是用组织成本换专业深度与可控性——**用单 Agent 能解决就别上平台**。

## 3. 为什么需要

单个 Agent 应用长成三个、十个之后，必然撞上四堵墙：

| 撞墙现象 | 根因 | 平台的解法 |
|---|---|---|
| 每个 Agent 自带一份模型密钥，散落在配置、代码、镜像里 | 密钥管理无收口 | AI Gateway 统一持钥，Agent 无密钥 |
| 同一个「查订单」「发邮件」工具被三个团队各写一遍 | 无工具沉淀机制 | 工具市场：注册、版本、权限绑定、复用 |
| 租户 A 的检索结果出现在租户 B 的会话里 | 数据隔离缺一层强制 | 租户边界进存储与检索，非应用层自觉 |
| 出了错回答不了「谁、何时、用哪个模型、花了多少钱」 | 无全链路审计与成本账 | 统一 Trace + 成本看板 + 配额 |

这与后端从单体到微服务的演进同构：拆分（按职责拆 Agent）、通信（结构化消息/事件）、治理（注册发现、限流、审计、灰度）。微服务时代的教训同样适用：**拆分是为了解决组织复杂度，不是为了时髦**。

## 4. 核心原理

### 4.1 多 Agent 平台架构：三模式与通信协议栈

**三种编排模式**：

| 模式 | 结构 | 适合 | 代价 |
|---|---|---|---|
| 主管-工人 | 主管拆单派活汇总，专家并行执行 | 目标多变、子任务可并行 | 主管是单点，要做兜底与状态外置 |
| 流水线接力 | 解析→分析→写作→审核→发布 | 固定 SOP 流程 | 一段堵全线堵，扩展性弱 |
| 群聊辩论 | 生成者与批评者多轮对抗 | 关键决策质量优先 | token 成倍增长，轮数必须封顶 |

拆分的判据（继承 4.6 三条件）：上下文隔离、职责专业化、环节可独立测试，三条都成立才拆。

**通信协议栈**（自下而上）：

| 层 | 机制 | 说明 |
|---|---|---|
| 消息层 | 结构化消息卡（任务卡/结果卡） | id、输入、验收标准、状态；消息带上下文防重复询问 |
| 状态层 | 共享黑板 | 项目级中间产物外置，避免长轨迹重复传递 |
| 传输层 | 事件总线 / 消息队列 | 环节解耦，可重放 |
| 跨系统层 | A2A 类跨系统协作协议 | Agent 服务间互调的标准接口 |

### 4.2 多租户：权限、数据隔离、审计

| 隔离级 | 实现 | 适用 |
|---|---|---|
| 行级过滤 | 所有存储带 tenant_id，检索/查询强制 where 过滤 | 绝大多数 SaaS 场景 |
| Schema 隔离 | 每租户独立 schema/namespace | 中大型客户、合规要求高 |
| 独立实例 | 每租户独立向量库/数据库 | 金融、医疗等强隔离客户 |

三条纪律：

1. **租户边界在存储层强制，不靠应用层自觉**：检索函数签名里 tenant_id 是必填参数，缺省即报错。
2. **权限模型 RBAC + ABAC 叠加**：角色决定能用哪些 Agent 与工具，属性（部门、密级、租户）决定能碰哪些数据；Agent 权限 = 发起人权限 ∩ 工作流声明。
3. **全链路审计**：每条请求从入口到每次模型调用、工具调用统一 trace_id 贯穿，落审计日志（谁、何时、哪个租户、哪个 Agent、调了什么、参数摘要、结果、成本），出问题可回放。

### 4.3 AI Gateway：收敛密钥，Agent 无密钥

网关是平台的安全与调度中枢：

| 职责 | 机制 |
|---|---|
| 密钥收敛 | 上游模型密钥只存在网关的密钥管理服务；业务侧 Agent 只持网关签发的短期凭证 |
| 路由 | 按任务类型/成本/可用性路由到不同模型（强模型做规划、小模型做检索） |
| 配额与限流 | 租户级配额、令牌桶限流，防止一个租户打穿全局 |
| 降级与熔断 | 某模型故障自动切备用；错误率超阈值熔断 |
| 计量计费 | 记录每次调用的 token 数与模型单价，按租户出账 |
| 审计与脱敏 | 出网请求统一过敏感信息检测与注入检测 |

关键设计原则：**Agent 侧无密钥**。业务进程被攻破也拿不到模型供应商凭证，泄漏面收敛到网关一处；轮换密钥不用碰业务代码。

### 4.4 工具市场与复用

| 环节 | 要求 |
|---|---|
| 注册 | 工具以声明式 Schema（名称、参数、返回、副作用级别）登记 |
| 版本 | 语义化版本，破坏性变更走灰度 |
| 权限绑定 | 每个工具声明风险级（只读/写入/高危），高危绑定审批闸门 |
| 治理 | 调用量、成功率、延迟、owner 全可见；下线有流程 |

市场化的收益是复用与一致性：一个「查订单」工具写一次，Schema 即文档，权限即配置，三个 Agent 直接挂载。

### 4.5 Agent 系统全案答题框架（六层）

终极架构题（「设计智能客服 Agent / 数据分析 Agent」）的答题主线：**目标 → 架构 → 风险 → 闭环**。六层拆解：

| 层 | 内容 | 客服 Agent 要点 | 数据分析 Agent 要点 |
|---|---|---|---|
| 1 目标与边界 | 量化目标 + 不做什么 | 自助解决率 60%→80%；退款超阈值/法律咨询转人工 | 自助完成 80% 日常取数；只读不写、行数与超时设限 |
| 2 单体四件套 | 大脑/规划/记忆/工具 | 意图理解；固定 SOP 编排；会话内+用户画像；查订单/退款/工单 | 表格解析、SQL、绘图、指标字典；四步 SOP（理解→查询→校验→可视化） |
| 3 编排决策 | 单 Agent 优先，三判据命中才拆 | 售前/售后/投诉分线路由 | 单 Agent + 工具集即可 |
| 4 可靠性 | 重试+熔断、阈值、降级、人在环 | 工具失败重试、步数上限、话术兜底、退款两段式确认 | SQL 报错回传重试（≤3 次）、只读账号、数字自动核对 |
| 5 评测 | 轨迹评估 + 端到端指标 + golden set 回归 | 解决率/转人工率/满意度 | 数值正确率/图表可用率/口径命中率 |
| 6 生产治理 | Trace、安全、成本、灰度 | 全链路 Trace、注入防护、成本看板 | 沙箱执行、行级权限、查询审计 |

答题加分项：**主动交代反过度设计**——如果单 Agent 加提示词分区就能稳定完成，明确说不需要多 Agent；这体现架构判断力，而不是堆组件。

### 4.6 容量与成本治理

| 治理项 | 机制 |
|---|---|
| 容量规划 | 并发上限 = 模型 TPM/RPM 配额 ÷ 单任务消耗；编排深度设上限防级联放大 |
| 配额管理 | 租户级 token 配额 + 优先级队列，超配额排队或降级小模型 |
| 成本看板 | 按租户/Agent/工具三维出账，异常增长告警 |
| 路由降本 | 简单任务路由小模型，缓存高频问答，批处理非实时任务 |
| 护栏 | 单任务 token 上限、步数上限、循环检测，防失控 |

## 5. 架构 / 流程

平台分层与一次请求的穿越：

```text
┌────────────────────────────────────────────────────────┐
│ 接入层   Web / API / IM 渠道，租户鉴权（JWT → tenant_id）│
├────────────────────────────────────────────────────────┤
│ 编排层   主管 Agent（拆单派单）/ 流水线引擎 / 路由       │
│          任务卡下发 → 结果卡回收 → 共享黑板             │
├────────────────────────────────────────────────────────┤
│ 执行层   角色 Agent 池（客服/分析/检索/评审）            │
│          只持网关短期凭证，不持模型密钥                 │
├────────────────────────────────────────────────────────┤
│ AI Gateway  统一持钥 · 路由 · 限流配额 · 熔断降级        │
│             计量计费 · 脱敏与注入检测                    │
├────────────────────────────────────────────────────────┤
│ 工具市场   注册 Schema · 版本 · 风险级 · 审批绑定        │
├────────────────────────────────────────────────────────┤
│ 数据层    向量库/库表：全部带 tenant_id                 │
│           行级过滤强制 → Schema 隔离 → 独立实例分级      │
├────────────────────────────────────────────────────────┤
│ 治理面    全链路 Trace · 审计日志 · 成本看板 · 灰度发布  │
└────────────────────────────────────────────────────────┘

一次客服请求的穿越：
用户提问 → 接入层鉴权并注入 tenant_id=u200
 → 路由到客服 Agent（SOP：理解→检索订单→判断→答复）
 → 检索订单走工具市场「查订单 v2.1」（只读，无需审批）
 → 知识问答走数据层（强制 where tenant_id=u200 行级过滤）
 → 模型调用全部经 Gateway（小模型，配额内，计量入租户 u200 账单）
 → 若触发退款：进入两段式确认，挂起等用户/人工批准
 → 全程 trace_id=t-9f2e 写入审计与成本看板
```

## 6. 代码 / 工具

### 6.1 租户隔离检索（边界在存储层强制）

```python
class TenantIsolationError(PermissionError):
    """缺少租户上下文的检索必须直接失败，而不是默认全局。"""

def tenant_search(vector_client, tenant_id: str, user: dict,
                  query: str, top_k: int = 5) -> list[dict]:
    if not tenant_id:
        raise TenantIsolationError("tenant_id is required")   # 必填，杜绝全局检索
    # ABAC：用户属性决定额外数据边界（部门、密级）
    where_filter = {
        "must": [
            {"key": "tenant_id", "match": {"value": tenant_id}},      # 租户硬边界
            {"key": "dept", "match": {"any": user["depts"]}},          # 部门范围
            {"key": "classification", "match": {"any": user["clearance"]}},  # 密级
        ]
    }
    hits = vector_client.search(
        collection="kb",
        query_vector=embed(query),
        query_filter=where_filter,     # 过滤在存储层执行，检索不到越权数据
        limit=top_k,
    )
    audit_log({                        # 全链路审计：谁查了什么租户的什么
        "event": "vector_search", "tenant": tenant_id, "user": user["id"],
        "query_digest": hash(query), "hits": len(hits), "trace": current_trace(),
    })
    return hits

# 错误示范（禁止）：不传租户的检索会把其他租户文档召回
# vector_client.search(collection="kb", query_vector=embed(query))
```

### 6.2 AI Gateway 路由与配额配置（YAML）

```yaml
gateway:
  upstreams:                       # 模型密钥只存在此处（对接 KMS），业务侧无密钥
    - name: strong-model
      provider: openai
      model: gpt-4o
      key_ref: kms://llm/openai-primary
    - name: fast-model
      provider: openai
      model: gpt-4o-mini
      key_ref: kms://llm/openai-secondary

  routes:
    - match: { agent: orchestrator, task: planning }     # 规划走强模型
      upstream: strong-model
    - match: { agent: worker, task: retrieval }          # 检索走小模型，省钱
      upstream: fast-model
      cache: { enabled: true, ttl: 3600 }                # 高频查询缓存

  quotas:                          # 租户级配额与限流
    - tenant: u200
      tokens_per_day: 2000000
      rpm: 120
      on_exceed: degrade_to_fast_model     # 超配额降级而非拒绝
    - tenant: default
      tokens_per_day: 200000
      rpm: 30
      on_exceed: queue

  resilience:
    circuit_breaker: { error_rate: 0.2, window_s: 60, cooldown_s: 30 }
    fallback_chain: [strong-model, fast-model]   # 故障自动切换

  policy:
    pii_filter: on                 # 出网统一脱敏
    prompt_injection_scan: on      # 注入检测在网关层兜一道
    audit: { log_all_calls: true, sink: "kafka://audit" }
```

## 7. 案例

### 案例 A：智能客服 Agent 全案（答题示范）

**目标与边界**：自助解决率从 60% 提到 80%；退款超阈值、法律咨询、情绪激烈会话强制转人工——边界即安全，也是评测锚点。**架构**：单 Agent + 提示词分区起步（售前/售后/投诉同一模型不同分区），四件套——意图理解与决策为大脑，客服流程确定性高用固定 SOP 编排，记忆分会话上下文与用户长期画像，工具为查订单/查物流/退款/建工单（Function Calling + Schema 校验）。**可靠性**：工具失败把错误回传让模型重试（最多 3 次）后熔断；步数与 token 双阈值；降级路径是规则话术兜底并留人工工单；退款走两段式——Agent 完成信息收集与资格校验后进入待确认，用户或人工确认才执行。**评测**：golden set 300 个历史会话做回归，北极星是自助解决率与转人工率，配合轨迹评估定位是「工具选错」还是「话术偏差」。**治理**：全链路 Trace、高危动作审计、成本看板、灰度两周对比人工组。落地效果（示意量级）：自助解决率 61%→79%，平均响应时长从 4 分钟降到 40 秒，单会话成本约 0.06 元。

### 案例 B：平台化收敛密钥与工具复用

某公司三个 Agent 团队各自持有模型密钥，一次配置仓库泄漏导致密钥外流、账单一夜增长六倍。整改：建 AI Gateway，上游密钥进 KMS，业务侧只持短期凭证；路由按任务分级（规划强模型、检索小模型）并上缓存。三个月后模型成本降约 45%，密钥轮换从「全公司发版」变成「网关改一处配置」。同期工具市场收编了 5 份重复的「查订单」实现，统一为一个 v2.1，带风险级与 owner，调用量与成功率全平台可见。

### 案例 C：多租户数据隔离事故与加固

某 SaaS 知识库 Agent 在检索层用应用代码过滤租户，一次重构漏掉一个入口，A 公司用户在搜索结果里看到 B 公司的制度文档。加固方案：租户过滤下沉到存储层——所有向量与文档强制带 tenant_id 且检索函数签名必填（见 6.1），缺省直接抛错；再配全链路审计与越权检索告警。此后三轮回归测试中隔离性全部通过，事故模式从「靠人记住」变成「结构上不可能」。

## 8. 常见坑

1. **单 Agent 能解决就上多 Agent**。拆分要三判据成立，组织成本（token、调试、延迟）会立刻到账。
2. **租户过滤放在应用层**。漏一个入口就泄露；过滤必须下沉到存储层并在函数签名上强制。
3. **检索函数的 tenant_id 可选**。默认值一旦是「全局」，事故只是时间问题；必填，缺省抛错。
4. **Agent 各持模型密钥**。泄漏面随团队数线性增长；密钥收敛进网关与 KMS，业务侧零密钥。
5. **网关只做转发**。不做配额、降级、计量的网关等于没建；路由降本与租户配额是网关的核心价值。
6. **工具重复实现无版本**。同名工具五个版本，Schema 各异；进市场统一注册、版本化、带 owner。
7. **高危工具不绑审批**。写入与资金类工具必须声明风险级并绑定 4.5 的审批闸门。
8. **审计只记最终答案**。中间的每次模型调用、工具调用、检索都要入 Trace，否则无法回放定位。
9. **成本没有租户维度**。出不了「谁花的钱」的账单，配额与商业化无从谈起。
10. **无编排深度上限**。主管派单、子 Agent 再派单，级联把预算打穿；深度与单任务预算双封顶。
11. **降级路径缺失**。模型故障即全站不可用；fallback 链与规则兜底必须预演过。
12. **辩论模式轮数不封顶**。生成者与批评者互相「礼貌拉扯」到天亮；轮数写死在配置里。
13. **错误在交接链无校验**。流水线越长放大越狠；每个交接点做结构化校验与质控抽查。
14. **全案题只罗列组件**。面试考的是「目标→架构→风险→闭环」的叙事与反过度设计的判断，不是名词堆砌。

## 9. 练习

1. 把 6.1 的租户隔离检索接入 4.2 的知识库示例，构造越权查询用例并验证被拦截。
2. 用真实向量库（Qdrant/pgvector）实现 tenant_id + 部门 + 密级三重过滤，写三个越权回归测试。
3. 依 6.2 写一份网关配置：两个上游、任务路由、租户配额、熔断与 fallback 链，并推演一次上游故障。
4. 给「查订单」工具补全注册信息：Schema、风险级、审批绑定、监控指标，并设计其 v3 的灰度方案。
5. 按 4.5 六层框架写「智能数据分析 Agent」全案，重点写只读约束、数字自动核对与口径管理。
6. 给平台设计成本看板的三张表：按租户、按 Agent、按工具的月度账单 Schema。
7. 推演一次级联失控：主管 Agent 故障循环派单，列出三道护栏（深度上限、预算、循环检测）分别在哪层拦截。
8. 做一次 30 分钟的 mock 面试：让对方任选客服或数据分析 Agent 出题，用「目标→架构→风险→闭环」主线限时作答。

## 10. 小结

- 多 Agent 平台 = **编排 + 通信 + 治理**：拆分解决组织复杂度，能用单 Agent 就别拆。
- 三种编排：**主管-工人（多变目标）、流水线（固定 SOP）、辩论（质量优先、轮数封顶）**。
- 通信协议栈：结构化任务卡/结果卡 + 共享黑板 + 事件总线 + A2A 跨系统协议。
- 多租户三纪律：**隔离在存储层强制（行级→Schema→实例分级）、RBAC+ABAC 叠加、全链路审计可回放**。
- AI Gateway 四件事：**收敛密钥（Agent 无密钥）、路由降本、配额限流熔断、计量与安全过滤**。
- 工具市场：注册 Schema、版本化、风险级绑定审批、owner 与指标全可见，复用消灭重复实现。
- 全案答题主线：**目标 → 架构 → 风险 → 闭环**，六层展开（边界/四件套/编排/可靠性/评测/治理）。
- 可靠性四件套是必问项：重试+熔断、步数与预算阈值、降级路径、高危动作人类在环。
- 评测看北极星业务指标（解决率/正确率）+ 轨迹评估定位问题环节 + golden set 回归。
- 容量与成本治理：并发上限算出来、租户配额管起来、成本看板看得见、级联失控有护栏。
- 反过度设计是架构师的基本素养：单 Agent 稳定完成时，明确说不需要多 Agent。
- 平台上线后由 4.8 评估与红队检验安全，由 4.9 部署与运维保障稳定。
