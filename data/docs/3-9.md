# 讲解 3.9 CI/CD、版本管理与发布

> 说明：3.5 评估体系与实验管理解决「改版是变好还是变坏」，3.6 部署与扩展解决「服务怎么稳定跑起来」，本篇解决「每次变更怎么安全地送到线上、出问题怎么安全退回来」。  
> 聚焦**流水线组装**：四类制品（Prompt、模型、工具、数据）的版本化、CI 测试、灰度发布与回滚机制；评估指标与门禁阈值怎么定归 3.5，本篇只讲怎么把它们接进流水线。后续 4.9 部署与运维在此之上加监控、告警与故障演练。

---

## 1. 定位

AI 工程化层第 9 个知识点，属于「持续交付基础设施」。  
它解决一个核心问题：**Agent 的变更对象比普通软件多（代码、Prompt、模型、工具、数据、配置），如何管理这些变更并自动化、安全地交付？**

依赖链：前置 3.5 评估体系与实验管理、3.6 部署与扩展 → 本篇 → 后续 4.9 部署与运维（安全扫描门禁复用 3.8 的结论，坏例回流见 3.10）。

对关键问题「如何安全发布与回滚」，先给集中的正面回答：

```text
安全发布 = 版本化一切（可追溯）+ 评估门禁（上线前拦住回归）
         + 小步灰度（控制爆炸半径）+ 可观测验证（每步放量有判据）
安全回滚 = 制品版本对齐（版本清单（Manifest）记录全部制品版本）
         + 一键回滚（分钟级切回旧版本）+ 回滚后验证（确认旧版本健康）
```

发布与回滚是同一套机制的两面：能灰度才敢发布，版本对齐才能回滚。§4 逐项展开，§5 串成完整流水线。

## 2. 一句话定义

CI/CD（Continuous Integration / Continuous Delivery，持续集成与持续交付）、版本管理与发布，是对 Agent 系统的所有变更制品进行版本化、自动化测试、灰度发布和快速回滚的工程体系，确保系统持续、安全、可追溯地演进。

简化公式：

```text
Agent CI/CD = 版本化一切 + 自动化测试（含评估门禁） + 灰度发布 + 可回滚
```

## 3. 为什么需要

Agent 系统比普通软件多出一大类「非代码制品」，它们都直接影响行为：

| 变更对象 | 普通软件 | Agent 系统 | 说明 |
|---|---|---|---|
| 代码 / 配置 / 依赖 | 有 | 有 | 传统 CI/CD 已覆盖 |
| 数据库 Schema | 有 | 有 | 迁移脚本需可回滚 |
| Prompt | 无 | 有 | 改一行就可能改变全局行为 |
| 模型（含嵌入模型） | 无 | 有 | 厂商更新快照即行为漂移 |
| 工具定义 | 无 | 有 | 参数 Schema 变了模型不知道 |
| 知识库 | 无 | 有 | 换一批文档检索质量就变 |
| 评估集 | 无 | 有 | 评估集变了分数不可比 |

为什么传统流水线不够用（面试高频，展开见 4.2）：

| 维度 | 传统软件 CI/CD | Agent CI/CD |
|---|---|---|
| 行为确定性 | 输入固定、输出固定 | 同一输入输出带随机性 |
| 测试判定 | 断言「相等」即可 | 概率性评估，只能与基线比分数 |
| 变更来源 | 基本都来自代码仓库 | 代码 + Prompt + 模型 + 数据 |
| 变更发起方 | 团队内部 | 还有厂商模型更新（被动变更） |
| 回归（Regression）形态 | 崩溃或报错，容易发现 | 常常是「变笨了」，不报错 |

没有这套体系会遇到：

- **Prompt 改了没人知道**：谁改的、改了什么、效果如何，无法追溯。
- **模型升级回归**：厂商更新快照，行为变化，上线后才发现。
- **知识库更新出错**：新文档覆盖旧文档，检索质量下降。
- **无法回滚**：出问题只能手动修，恢复以小时计。
- **评估和发布脱节**：「评估通过才发布」靠人工执行，迟早跳过。
- **多环境不一致**：dev 能跑，prod 挂。
- **发布风险高**：全量上线，一出问题全站不可用。

**类比 1（菜谱版本化）**：Prompt 不版本化 = 连锁餐厅的大厨凭记忆改酱料配方，改坏了没人说得清原方子；版本化 = 每版配方编号存档，分店一投诉立刻换回上一版。  
**类比 2（新药上市）**：发布流程 = 新药上市——实验室评估（CI 门禁）、一期临床（Staging 验证）、小范围二期（金丝雀 1%–10%）、上市（全量），每期都有终止标准，任何一期出问题立即停药（回滚），而不是全国铺开后再召回。

## 4. 核心原理

先看全景。截至 2026 年，GenAI/LLMOps 岗位面试对这套管线的共识口径是四段式：**制品版本化 → 评估门禁（Eval Gate）→ 部署 → 回滚路径**，即「Code → Test → Eval Gate → Deploy」，评分低于阈值即阻断部署（多家英文 LLMOps 面试指南口径一致）。划界：评估集怎么建、指标怎么选、LLM-as-judge（用大模型当裁判）怎么校准，见 3.5；本篇讲流水线怎么组装——不达标不放行，放行了也退得回来。

### 4.1 版本化一切

四类核心制品 + 传统对象的版本化方案对比：

| 制品 | 版本标识 | 存储 | 变更频率 | 灰度单位 | 回滚方式 |
|---|---|---|---|---|---|
| 代码 | Git commit / 镜像 tag | Git + 镜像仓库 | 高 | 流量百分比 | 切回旧镜像 |
| Prompt | 语义化版本 v1.2.0 | Git / Prompt Registry | 高 | 流量百分比 | 切回旧版本号 |
| 模型 | 固定快照版本号 | 配置 / 模型注册表 | 低（外部触发） | 流量百分比 | 切回旧快照 |
| 工具 | tool@1.2.0 | Git / 注册表 | 中 | 按 Agent 服务 | 切回旧版本 |
| 数据（知识库） | 内容哈希 + 索引版本 | 对象存储 + DB | 高 | 流量百分比 | 切回旧索引 |
| 评估集 | 数据集版本 | Git / DB | 中 | 不灰度 | 切回旧版本 |
| 配置 / 依赖 | Git + lock 文件哈希 | Git | 中 | 随代码 | 切回旧 commit |

Prompt 目录示例（一版一文件，永不覆盖）：

```text
prompts/
├── classify/
│   ├── v1.0.0.txt
│   ├── v1.1.0.txt
│   └── v1.2.0.txt
├── rag_qa/
│   ├── v1.0.0.txt
│   └── v1.1.0.txt
└── registry.yaml
```

```yaml
# registry.yaml：每个 Prompt 的版本台账，记录当前生效版本与历史指标
classify:
  current: v1.2.0
  versions:
    v1.0.0: { created: 2026-01-05, metrics: { accuracy: 0.82 } }
    v1.1.0: { created: 2026-02-02, metrics: { accuracy: 0.85 } }
    v1.2.0: { created: 2026-03-01, metrics: { accuracy: 0.88 } }
```

**面试高频问法**：「你们的 Prompt 怎么做版本管理？」共识口径——当代码管：Prompt 进 Git、按语义化版本（Semantic Versioning）演进、用 registry 记录当前生效版本与历史指标、每次变更过评估门禁、上线走灰度、出问题按版本号一键回滚。只回答「存在文档里 / 在界面上改」视为没有实践。

### 4.2 CI：持续集成

CI 流程：

```text
代码提交 → 代码检查（Lint）→ 单元测试 → 评估门禁（Smoke → Core）→ 安全扫描 → 构建镜像
```

GitHub Actions 示例（评估分两层：Smoke 快筛、Core 全量比对基线（Baseline））：

```yaml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      - run: pip install ruff
      - run: ruff check src/

  unit-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt   # 版本由 lock 文件锁定
      - run: pytest tests/unit/ -v

  eval-gate:                                   # 评估门禁：本篇的核心差异点
    runs-on: ubuntu-latest
    needs: unit-test
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt
      - run: python -m eval.smoke              # Smoke：几十条，几分钟出结果
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      - run: python -m eval.core --baseline baseline.json  # Core：全量，与基线逐指标比对
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}

  security-scan:                               # 依赖与镜像漏洞扫描（要求见 3.8）
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install pip-audit
      - run: pip-audit --requirement requirements.txt
      - run: |
          docker build -t agent:test .
          trivy image --severity HIGH,CRITICAL agent:test

  build:
    runs-on: ubuntu-latest
    needs: [lint, eval-gate, security-scan]    # 门禁与扫描全过才允许构建
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t myregistry/agent:${{ github.sha }} .
      - run: docker push myregistry/agent:${{ github.sha }}
```

CI 门禁规则（阈值与指标定义见 3.5，本篇负责「不达标不放行」的机制）：

| 检查 | 阈值（示意） | 不达标动作 |
|---|---|---|
| Lint | 无错误 | 阻止合并 |
| 单元测试 | 100% 通过 | 阻止合并 |
| Smoke 评估 | 100% 通过 | 阻止合并 |
| Core 评估 | 相对基线下降 < 3% | 阻止合并 |
| 回归集 | 无已知坏例复发 | 阻止合并 |
| 红队（Red Teaming）样本 | 通过率 > 95% | 阻止合并 |
| 依赖 / 镜像扫描 | 无高危漏洞 | 阻止合并 |

**面试高频问法**：「为什么传统 CI/CD 流水线不足以保证 LLM 应用质量？」共识口径——传统单测靠确定性断言，而 LLM 输出非确定，断言「相等」基本不可行；必须补三样东西：带版本的评估集、基于 judge 或规则的概率性门禁、分数回归检测（与基线比，而不是与固定值比）。红队与安全测试的构建方法见 3.8 与 4.8。

### 4.3 CD：持续部署

CD 流程：

```text
构建镜像 → 推送到镜像仓库 → 部署 Staging → Staging 验证 → 灰度到 Prod → 全量 → 监控
```

部署流水线（打 tag 触发：Staging → 金丝雀 → 全量）：

```yaml
name: CD

on:
  push:
    tags: ['v*']

jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          kubectl set image deployment/agent \
            agent=myregistry/agent:${{ github.ref_name }} -n staging
      - run: kubectl rollout status deployment/agent -n staging
      - run: python -m eval.staging        # Staging 全量评估通过，才进灰度

  deploy-canary:
    needs: deploy-staging
    runs-on: ubuntu-latest
    steps:
      - run: |
          kubectl set image deployment/agent-canary \
            agent=myregistry/agent:${{ github.ref_name }} -n prod
      - run: |
          # 切 5% 流量到金丝雀
          kubectl patch virtualservice agent --type merge \
            -p '{"spec":{"http":[{"route":[{"destination":{"host":"agent","subset":"v1"},"weight":95},{"destination":{"host":"agent","subset":"v2"},"weight":5}]}]}}'
      - run: sleep 600                      # 观察 10 分钟
      - run: python -m eval.canary_metrics  # 线上指标达标才允许全量

  deploy-full:
    needs: deploy-canary
    runs-on: ubuntu-latest
    steps:
      - run: |
          kubectl patch virtualservice agent --type merge \
            -p '{"spec":{"http":[{"route":[{"destination":{"host":"agent","subset":"v2"},"weight":100}]}]}}'
```

### 4.4 发布策略

五种策略对比：

| 策略 | 机制 | 风险暴露 | 额外成本 | 回滚速度 | 适用场景 |
|---|---|---|---|---|---|
| 蓝绿（Blue-Green） | 新旧两套完整环境，切流量 | 低（仅切换瞬间） | 双倍资源 | 快（切回旧环境） | 要求秒级回滚的服务 |
| 金丝雀（Canary） | 小比例流量渐进放量 | 低且可控 | 低 | 快（权重归零） | Agent 服务默认选择 |
| 滚动（Rolling） | 逐实例替换 | 中（新旧共存） | 低 | 中 | 无状态后端 |
| A/B | 按用户特征分流 | 低 | 低 | 快 | 效果对比实验（与 3.5 联动） |
| 影子（Shadow，流量镜像） | 新版本复制流量但不返回结果 | 最低（不影响用户） | 双倍调用成本 | 无需回滚（从未真正上线） | 高风险变更预演 |

金丝雀放量流程：

```text
1. 部署新版本（0 流量），健康检查
2. 切 1% 流量，观察 10 分钟
3. 逐步 5% → 10% → 25% → 50% → 100%，每步观察
4. 每步检查：错误率、P99 延迟、单次成本、抽检评估指标
5. 任一步超阈值 → 权重归零回滚，保留现场排查
```

发布检查清单（Go / No-Go）：

| 检查项 | 标准 | 执行方 |
|---|---|---|
| 版本清单已生成 | 代码 / Prompt / 模型 / 工具 / 数据版本齐备 | 发布系统自动 |
| CI 全绿 | 含 Core 评估与安全扫描 | 发布系统自动 |
| 基线快照已存 | 当前生产版本指标已记录，供放量对比 | 发布系统自动 |
| 回滚路径演练过 | 回滚命令 5 分钟内可执行 | 工程师 |
| 数据迁移兼容 | 新版本可读旧 Schema，或双写已开启 | 工程师 |
| 值班与通知 | 发布通知已发，值班人在线 | 工程师 |

### 4.5 回滚机制

回滚触发规则（实现见 6.4 的 AutoRollback）：

| 信号 | 阈值（示意） | 动作 |
|---|---|---|
| 错误率 | > 1%，持续 2 个采样窗口 | 自动回滚 + 告警 |
| P99 延迟 | > 基线 1.5 倍 | 自动回滚 + 告警 |
| 成功率 | < 95% | 自动回滚 + 告警 |
| 单次成本 | > 基线 2 倍 | 自动回滚 + 告警 |
| 抽检评估分 | 相对基线下降 > 5% | 人工确认后回滚 |

回滚方式：

```bash
# K8s 回滚到上一版本
kubectl rollout undo deployment/agent -n prod

# 回滚到指定版本
kubectl rollout undo deployment/agent --to-revision=5 -n prod

# 金丝雀场景：权重直接归零，切回 stable
kubectl patch virtualservice agent --type merge \
  -p '{"spec":{"http":[{"route":[{"destination":{"host":"agent","subset":"v1"},"weight":100}]}]}}'
```

回滚三原则：

1. **制品版本对齐**：按版本清单整体回退。只回滚代码、不回滚 Prompt 和模型，等于没回。
2. **一键执行**：回滚命令预置、可自动化，不临时翻文档。
3. **回滚后验证**：切回旧版本后立即跑健康检查与抽检评估，确认恢复，而不是回滚完就收工。

数据与 Schema 兼容：

- 新版本不破坏旧数据结构（只加列、不改不删）。
- 迁移遵循 expand-contract：先加新列、双写、确认稳定后再删旧列，迁移脚本可回滚。
- 灰度期间双写，保证新旧版本数据一致。

### 4.6 Prompt 发布流程

```text
1. 修改 Prompt：新增版本文件（不覆盖旧版）
2. 提交 PR
3. CI 自动跑评估门禁（见 4.2）
4. 评估通过 → 合并
5. CD 更新 registry.yaml 的 current → 部署配置
6. 灰度验证 → 全量
```

运行时按 registry 的 current 版本加载，实现见 6.1 的 PromptRegistry（get / promote / rollback）。

### 4.7 模型版本管理

模型版本锁定配置（模型名仅示意，关键是写死到快照版本号）：

```python
MODEL_CONFIG = {
    # 禁止使用不带日期的别名：别名会被厂商指向新快照，行为漂移不可控
    "default":  "gpt-4o-2024-08-06",
    "fast":     "gpt-4o-mini-2024-07-18",
    "powerful": "claude-3-5-sonnet-20241022",
    "fallback": "gpt-4o-mini-2024-07-18",
}
# 嵌入模型同理：换嵌入模型 = 全量重建索引，其版本必须与知识库索引版本绑定
```

模型升级流程：

```text
1. 新快照发布（外部触发，属被动变更）
2. 在评估集上跑离线对比（见 3.5）
3. 提升超过阈值 → 进入灰度
4. 灰度 5% 流量，观察 24 小时
5. 逐步放量到 100%
6. 旧快照保留 1 周，随时可切回
```

### 4.8 知识库版本管理

```python
import hashlib

class KnowledgeVersion:
    """知识库版本 = 内容哈希 + 索引版本，两者绑定，缺一不可"""
    def __init__(self, version: str):
        self.version = version
        self.indexed_at = now()
        self.document_count = 0
        self.chunk_count = 0
        self.hash = ""

    def compute_hash(self, documents: list) -> str:
        content = "".join(sorted(d["content"] for d in documents))
        return hashlib.sha256(content.encode()).hexdigest()
```

知识库发布流程：

```text
1. 采集新文档 → 清洗、切分、建索引（管线细节见 3.2）
2. 新索引打版本号，与内容哈希绑定
3. 在检索评估集上验证（Recall@k 等指标，见 3.5）
4. 指标提升 → 灰度：10% 流量用新索引
5. 观察 24 小时 → 全量切换
6. 旧索引保留 1 周，可一键切回
```

### 4.9 配置管理

多环境分层配置（base 定基线，环境文件只写差异）：

```yaml
# configs/base.yaml —— 全环境共享
agent:
  max_steps: 20
  timeout: 300
  prompts:
    classify: v1.2.0   # Prompt 版本也是配置的一部分
    rag_qa: v1.1.0

# configs/dev.yaml —— 只覆盖差异项
agent:
  llm: { default: gpt-4o-mini-2024-07-18 }
  budget: 0.5

# configs/prod.yaml
agent:
  llm: { default: gpt-4o-2024-08-06 }
  budget: 5.0
```

配置加载（base + 环境覆盖，深合并）：

```python
import os
import yaml

ENV = os.getenv("ENV", "dev")  # dev / staging / prod

def load_config() -> dict:
    base = yaml.safe_load(open("configs/base.yaml"))

config = load_config()
```

### 4.10 CI/CD 工具链

| 类别 | 工具（截至 2026 年主流，示意） |

## 5. 架构 / 流程

一个完整的 Agent CI/CD 流水线。注意回滚是嵌在 CD 里的回路，不是流水线末端的独立环节：

```text
┌──────────────────────────────────────────┐
│  变更来源                                 │
│  ├─ 代码提交                             │
│  ├─ Prompt 修改 / 配置变更               │
│  ├─ 知识库更新                           │
│  └─ 模型快照更新（外部被动触发）         │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  CI（持续集成）                           │
│  ├─ Lint / 单元测试                      │
│  ├─ Smoke 评估 → Core 评估（评估门禁）   │
│  ├─ 回归集 + 红队样本                    │
│  ├─ 安全扫描 / 依赖扫描                  │
│  └─ 构建镜像（随镜像生成版本清单）       │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  CD（持续部署）                           │
│  ├─ 部署 Staging → Staging 验证          │
│  ├─ 金丝雀 1% → 5% → … → 100%            │
│  └─ 每步放量检查指标                      │
└──────────────────────────────────────────┘
                  ↓ 指标异常
┌──────────────────────────────────────────┐
│  回滚（嵌在 CD 里的回路）                 │
│  ├─ 自动触发：错误率 / 延迟 / 成本越限    │
│  ├─ 按版本清单整体回退                   │
│  └─ 回滚后验证                           │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  监控与反馈                               │
│  ├─ Trace / Metrics / Logs（见 3.4）      │
│  ├─ 评估指标 / 用户反馈                  │

```

### 6.1 Prompt Registry

```python
import yaml
from pathlib import Path

class PromptRegistry:
    """Prompt 版本仓库：读取、晋级（promote）、回滚（rollback）"""
    def __init__(self, base_dir: str):
        self.base_dir = Path(base_dir)
        self.registry = yaml.safe_load(
            (self.base_dir / "registry.yaml").read_text()
        )

    def get(self, name: str, version: str = None) -> str:
        if version is None:
            version = self.registry[name]["current"]
        path = self.base_dir / name / f"{version}.txt"
        if not path.exists():
            raise ValueError(f"Prompt {name}@{version} 不存在")
        return path.read_text(encoding="utf-8")

    def list_versions(self, name: str) -> list:
        return list(self.registry[name]["versions"].keys())

    def promote(self, name: str, version: str):
        """发布：把 current 指向新版本（由 CD 在灰度通过后调用）"""
        self.registry[name]["current"] = version
        (self.base_dir / "registry.yaml").write_text(
            yaml.dump(self.registry, allow_unicode=True)
        )

    def rollback(self, name: str):
        """回滚：current 回退到上一个版本"""
        versions = self.list_versions(name)
        current = self.registry[name]["current"]
        idx = versions.index(current)
        if idx > 0:
            self.promote(name, versions[idx - 1])

registry = PromptRegistry("prompts/")
prompt = registry.get("classify")  # 获取当前生效版本
```

### 6.2 评估门禁

```python
import json

async def eval_gate(baseline_path: str, threshold: float = 0.05) -> bool:
    """评估门禁：与基线逐指标比对，任一指标跌超阈值即阻断（指标定义见 3.5）"""
    baseline = json.load(open(baseline_path))
    results = await evaluate_current()

    failures = []
    for metric, value in results["metrics"].items():
        base_value = baseline["metrics"].get(metric, 0)
        if value < base_value * (1 - threshold):  # 与基线比，不是与固定值比
            failures.append({
                "metric": metric,
                "baseline": base_value,
                "current": value,
                "drop": (base_value - value) / base_value,
            })

    if failures:
        print("评估门禁失败：")
        for f in failures:
            print(f"  {f['metric']}: {f['baseline']:.3f} → {f['current']:.3f}")
        return False

    print("评估门禁通过")
    return True
```

### 6.3 灰度发布控制器

```python
import asyncio

class CanaryController:
    """金丝雀控制器：按阶段放量，每步验指标，异常即回滚"""
    def __init__(self, k8s_client, metrics_client):
        self.k8s = k8s_client
        self.metrics = metrics_client
        self.stages = [1, 5, 10, 25, 50, 100]

    async def deploy(self, version: str):
        await self.k8s.deploy_canary(version)

        for weight in self.stages:
            await self.k8s.set_traffic_split(canary=weight, stable=100 - weight)
            await asyncio.sleep(600)  # 每个阶段观察 10 分钟

            health = await self.metrics.check_health()
            if not health["healthy"]:
                await self.rollback()
                raise DeploymentFailed(health["reason"])

        await self.k8s.promote_canary()  # 全部阶段通过，转正

    async def rollback(self):
        await self.k8s.set_traffic_split(canary=0, stable=100)
        await self.k8s.delete_canary()
```

### 6.4 自动回滚

```python
import asyncio
import time

class AutoRollback:
    """发布后监控窗口内指标越限，自动切回旧版本"""
    def __init__(self, k8s_client, metrics_client, thresholds: dict):
        self.k8s = k8s_client
        self.metrics = metrics_client
        self.thresholds = thresholds

    async def monitor(self, duration: int = 3600):
        start = time.time()
        while time.time() - start < duration:
            metrics = await self.metrics.get_current()

            if metrics["error_rate"] > self.thresholds["error_rate"]:
                await self.k8s.rollback()  # 按版本清单整体回退
                await self.alert(f"错误率 {metrics['error_rate']} 超阈值，已回滚")
                return

            if metrics["p99_latency"] > self.thresholds["p99_latency"]:
                await self.k8s.rollback()
                await self.alert(f"P99 延迟 {metrics['p99_latency']} 超阈值，已回滚")
                return

            await asyncio.sleep(60)
```

### 6.5 多环境部署脚本

```bash
#!/bin/bash
set -e

VERSION=$1
ENV=$2

if [ -z "$VERSION" ] || [ -z "$ENV" ]; then
    echo "Usage: $0 <version> <env>"
    exit 1
fi

echo "部署 $VERSION 到 $ENV"

# 1. 构建并推送镜像
docker build -t myregistry/agent:$VERSION .
docker push myregistry/agent:$VERSION

# 2. 更新 K8s 并等待滚动完成
kubectl set image deployment/agent agent=myregistry/agent:$VERSION -n $ENV
kubectl rollout status deployment/agent -n $ENV

# 3. 健康检查：失败立即回滚
sleep 10
curl -f http://agent-$ENV/health || {
    echo "健康检查失败，回滚"
    kubectl rollout undo deployment/agent -n $ENV
    exit 1
}

# 4. 部署后验证评估
python -m eval.run --env $ENV

echo "部署成功: $VERSION → $ENV"
```

## 7. 案例

### 案例 A：Prompt 改动被门禁拦下（某电商客服 Agent）

**场景**：开发者把 classify Prompt 从 v1.2.0 升到 v1.3.0，压缩指令以省 token。  
**做法**：提交 PR，CI 自动跑评估门禁。  
**结果（示意）**：Smoke 20/20 通过；Core 准确率 0.85 → 0.82，相对下降 3.5%，超过 3% 阈值，门禁失败、阻止合并。开发者补充少样本示例后提交 v1.3.1，Core 回到 0.86，合并上线。  
**效果（示意）**：回归在合并前被拦截，线上零影响；引入门禁前，同类问题平均上线 2–3 天后才由客诉发现。

### 案例 B：模型快照升级灰度（一家金融科技公司的问答 Agent）

**场景**：模型厂商发布新快照，直接换有行为漂移风险。  
**做法**：先在 500 条评估集上离线对比，达标后进灰度。  
**结果（示意）**：离线评估准确率 +2.1%，进入灰度；5% 流量观察 24 小时，错误率 0.38%（基线 0.42%）、P99 延迟 2.4s（基线 2.3s）、单次成本 +6%；随后 10% → 25% → 50% → 100% 分一周放量；旧快照保留 1 周。  
**效果（示意）**：升级零事故；成本增量经 3.7 的模型路由策略分流到 fast 通道后回落到 +2%。

### 案例 C：知识库更新触发自动回滚（某企业知识库 RAG）

**场景**：知识库例行更新后，RAG 回答质量下滑。  
**做法**：灰度期间持续抽检检索指标，越限自动回滚。  
**结果（示意）**：灰度 10% 流量的第 2 小时，Recall@5 从 0.90 跌到 0.75，触发自动回滚，流量切回旧索引，从告警到回滚完成 8 分钟，影响面始终锁定在 10% 流量。复盘发现新切分策略把补偿规则表格的关键行切断，修复后 Recall@5 升到 0.91，重新走灰度。  
**效果（示意）**：平均恢复时间从小时级降到分钟级，用户基本无感知。

## 8. 常见坑

1. **Prompt 不版本化**。线上直接改，无法追溯与回退；Prompt 当代码管，进 Git、打版本号。
2. **模型不固定快照版本**。用别名调用，厂商更新即行为漂移；配置写死到带日期的快照版本。
3. **知识库不版本化**。索引一重建就覆盖，出错回不去；记录版本 + 内容哈希，旧索引保留一段时间。
4. **CI 不跑评估**。只有单测，行为回归到线上才暴露；每次 PR 跑 Smoke + Core 评估门禁。
5. **评估门禁太松或没有基线**。分数明显下降照样放行；与版本化基线逐指标比对，跌超阈值阻断。
6. **不做灰度直接全量**。一出问题全站不可用；默认金丝雀渐进放量。
7. **没有自动回滚**。靠人工发现、人工决策，恢复以小时计；指标越限自动切回旧版本。
8. **配置硬编码**。多环境行为不一致；分层配置 + 环境变量注入。
9. **密钥进 Git**。一旦泄露即是事故；用密钥管理服务，CI 用 Secret 注入。
10. **不做版本清单**。出问题说不清生产在跑什么组合；每次部署生成 VersionManifest。
11. **回滚不考虑数据 Schema**。代码回去了、新 Schema 回不去，回滚失败；迁移遵循 expand-contract，保持向后兼容。
12. **多环境不隔离**。dev 与 prod 共用模型 Key、共用索引，互相污染；环境间资源与数据全隔离。
13. **只回滚代码不回滚配套制品**。Prompt、模型、索引仍是新版，回滚不彻底；按版本清单整体回退。
14. **忽略评估集自身的版本**。评估集悄悄变了，历史分数不可比；评估集也打版本，基线与评估集版本绑定。
15. **CI/CD 太慢**。全量评估一次一小时，没人愿意等；分层：PR 跑 Smoke，合并后与夜间跑 Full。
16. **发布无通知无记录**。团队不知道上了什么、何时上的；发布自动通知，留存发布日志。

## 9. 练习

1. 实现 Prompt Registry：版本读取、promote、rollback。验收：promote 到 v1.3.0 后 get 返回新版，rollback 后回到 v1.2.0。
2. 配置 GitHub Actions：PR 时自动跑 Lint + 单元测试 + Smoke 评估。验收：故意改坏一个 Prompt，PR 检查变红并阻止合并。
3. 实现评估门禁：与基线逐指标比对，Core 准确率下降超 3% 时以非 0 退出码失败。验收：门禁在 CI 上真实阻断过一次合并。
4. 实现金丝雀控制器：1% → 5% → 10% → 50% → 100%，每步检查指标、异常即回滚。验收：注入一次模拟故障，控制器在第 2 阶段中止并回滚。
5. 实现自动回滚：错误率连续两个窗口超 1% 触发。验收：模拟指标异常后 5 分钟内完成回滚并发出告警。
6. 实现 VersionManifest：部署时记录代码、Prompt、模型、工具、知识库、配置版本。验收：对任意历史部署能还原「当时跑的是什么」。
7. 设计 base / dev / staging / prod 分层配置并实现深合并加载。验收：同名键按环境正确覆盖，未覆盖键继承 base。
8. 实现知识库版本管理与回滚：内容哈希 + 索引版本，可切回旧索引。验收：切回后对同一批查询的检索命中与旧版完全一致。
9. 实现模型升级流程：离线评估 → 灰度 → 全量 → 旧快照保留期。验收：灰度期间任一时刻可一键切回旧快照。
10. 串成完整流水线：一次 Prompt 变更从 PR 到灰度全量，再完整演练一次回滚。验收：全程无人工执行部署命令。

## 10. 小结

- Agent CI/CD = **版本化一切 + 自动化测试（含评估门禁）+ 灰度发布 + 可回滚**。
- 安全发布 = 版本化（可追溯）+ 门禁（拦回归）+ 小步灰度（控爆炸半径）+ 可观测验证（放量判据）。
- 安全回滚 = 版本清单对齐 + 一键回滚 + 回滚后验证。
- 版本化对象：**代码、Prompt、模型、工具、数据（知识库）、评估集、配置**。
- CI 流程：**Lint → 单元测试 → Smoke 评估 → Core 评估 → 回归与红队 → 安全扫描 → 构建**。
- CD 流程：**Staging 验证 → 金丝雀渐进放量 → 每步验指标 → 全量**。
- 发布策略五选一：**蓝绿、金丝雀、滚动、A/B、影子**；Agent 服务默认金丝雀。
- Prompt 与模型是 Agent 特有重点：**Registry + 语义化版本 + 门禁 + 灰度；快照锁定 + 对比评估 + 灰度升级**。
- 核心原则：**一切变更可版本化、可测试、可灰度、可回滚。**
- 这些能力直接支撑：4.9 部署与运维。
