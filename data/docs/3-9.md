# 讲解 3.9 CI/CD、版本管理与发布

> 说明：3.5 评估体系与实验管理解决了「分数从哪来」，3.6 部署与扩展解决了「服务怎么上线」；本篇把两者接成一条发布流水线——Eval Gate（评估门禁）：评分不过线就阻断上线。  
> 发布后的 7×24 监控告警在 4.9 部署与运维展开；灰度期人工观察产生的反馈如何回流系统，见 3.10 人机协同与反馈闭环。

---

## 1. 定位

L3 工程化层第 9 个锚点，回答关键问题：**如何安全发布与回滚？**

前置依赖：

- 3.5 评估体系与实验管理：Eval Gate 需要的评估集、judge 打分、基线分数都产自那里，本篇只消费分数。
- 3.6 部署与扩展：流水线末端的灰度放量、流量切分依赖那里的部署能力。

下游去向：

- 4.9 部署与运维：发布完成只是开始，发布侧的「变更留痕」延续到运行期的监控告警与故障演练。
- 3.10 人机协同与反馈闭环：灰度期的人工观察与用户反馈，是反馈闭环最重要的数据入口。

它解决一个根本问题：**LLM 应用的「代码」远不止代码——提示词、模型版本、配置、数据都是会被改坏的资产，如何让每一次变更安全发布、可追溯、可回滚？**

## 2. 一句话定义

Eval Gate 发布流水线：在传统 Code→Test 之后加一道评估闸门——评估集跑分低于阈值即阻断部署，通过后分级灰度放量，异常一键回滚；同时把提示词、模型、配置、数据四类资产全部纳入版本管理，让每次线上行为变化都能查到「谁、何时、改了什么、依据什么数据放行的」。

## 3. 为什么需要

四个现实把传统发布流程打穿：

1. **提示词没有版本**。大量团队的系统提示词躺在配置中心或聊天工具里，谁都能随手改，改完直接上线，没有变更说明，没有回滚点。出事后「上周到底改了什么」成了悬案。
2. **模型即依赖，依赖会漂移**。写死 `gpt-4o` 这种浮版本号，厂商某天悄悄更新默认模型行为，应用格式错乱、拒答率上升——依赖变了，代码一行没动，线上照样坏。
3. **非确定性输出让传统断言失效**。单元测试假设「同样输入必得同样输出」，LLM 不吃这一套（详见 4.2）。
4. **没有回滚开关**。出事时的选项只剩通宵裸修提示词，而修复本身又是新的无版本变更——在事故上叠事故。

反过来看，良好发布治理的收益很直接：质量决策从「觉得应该没问题」变成「分数说话」，事故止血从「通宵排查」变成「一行命令切回旧版本」。

## 4. 核心原理

### 4.1 四类资产版本化

只管代码的版本管理是残缺的。LLM 应用有四类「会改坏」的资产，全部要进版本管理：

| 资产 | 具体内容 | 版本载体 | 变更频率 | 典型事故 |
|---|---|---|---|---|
| 提示词 | 系统提示词、few-shot 示例、输出格式模板 | git 仓库 + 语义化版本号 | 天/周级 | 措辞微调引发格式回归，无回滚点 |
| 模型 | 模型名、具体快照版本、参数（temperature 等） | 模型注册表 / 配置文件 | 月级 | 浮版本号遇厂商静默更新，行为漂移 |
| 配置 | 工具 Schema、路由规则、重试策略、阈值 | git + 配置中心快照 | 周级 | 阈值被临时调宽后忘改回 |
| 数据 | 知识库文档、切分参数、嵌入模型、索引版本 | 数据集快照 + 索引版本号 | 周/月级 | 文档更新后向量库不同步，检索旧内容 |

要点：

- **单一事实源**：提示词迁入代码仓库，聊天工具里的「最新版」即刻作废，任何人修改必须走提交。
- **整体快照**：一个线上版本 = 提示词版本 + 模型版本 + 配置版本 + 数据索引版本的组合，回滚要按组合整体切，不能只回滚提示词。
- **钉死版本**（Model Pinning）：配置里写 `model: gpt-4o-mini-2024-07-18`，不写 `gpt-4o-mini`。浮版本号等于把发布权交给厂商。

### 4.2 为什么传统 CI/CD 对 LLM 失效

传统单元测试的逻辑是「同样输入必得同样输出，错了就红」。LLM 输出是概率性的，两种失效模式：

- **误报**：同一输入跑两次，字面完全不同但语义都对——`assert output == expected` 全线飘红。
- **漏报**：输出流畅、与历史答案相似，但事实错误——绿灯放行一个坏版本。

所以 LLM 应用必须换尺子：

| 维度 | 传统 CI/CD | LLM CI/CD（LLMOps） |
|---|---|---|
| 判定方式 | 精确断言 `output == expected` | 语义判定：精确匹配 / 关键规则 / LLM-as-judge |
| 质量载体 | 测试用例 | 评估集（冒烟集 + 回归集）+ 阈值门禁 |
| 产物 | 通过/失败二值 | 分数 + 维度明细（准确性、格式、拒答率） |
| 版本对象 | 只有代码 | 代码 + 提示词 + 模型 + 配置 + 数据 |
| 回滚对象 | 代码部署 | 资产组合整体快照 |
| 发布信心来源 | 测试通过 | 离线分数 + 灰度线上指标 |

面试标准答案框架：「传统 CI/CD 对 LLM 不够用，根子是非确定性输出使断言失效（误报 + 漏报）；解法是在 CI 中加入评估集 + 语义判定 + 阈值门禁，并把提示词、模型版本、数据纳入同一套发布治理。」只说问题不说解法，是半个答案。

### 4.3 Eval Gate 五步流水线

| 步骤 | 动作 | 关键物 | 失败动作 |
|---|---|---|---|
| ① 提交 | 提示词/代码改动进 git，带版本号与改动说明 | commit + registry 记录 | — |
| ② 传统测试 | 单元测试、代码审查照跑 | 测试报告 | 阻断 |
| ③ 评估门禁 | 冒烟集 30 条 → 回归集 200 条，judge 打分 + 指标核算 | 评估报告（归档） | **分数 < 门禁线即阻断** |
| ④ 灰度放量 | 10% 流量观察线上解决率、坏例率 24 小时 | 线上指标看板 | 指标回归即回滚 |
| ⑤ 全量/回滚 | 达标全量；异常一键切回上一版快照 | 版本指针切换 | — |

评估集分两层，职责不同：

| 层 | 规模 | 内容 | 耗时 | 用途 |
|---|---|---|---|---|
| 冒烟集（Smoke） | 约 30 条 | 核心场景 + 高频问题 | 分钟级 | 快速拦截明显坏改动 |
| 回归集（Regression） | 约 200 条 | 全场景 + 历史 bad case 沉淀 | 十分钟级 | 拦截局部优化全局变差的回归 |

门禁线怎么定：以上一个已发布版本的分数为基线（如 88 分），门禁线略低于基线（如 85 分）——既挡住明显劣化，又不至于让正常波动卡死流水线。基线随版本滚动更新，只升不降。

### 4.4 模型厂商行为漂移与回滚快照

模型是外部依赖，依赖会漂移。三类漂移源：

1. **厂商静默更新**：浮版本号被指向新快照，输出风格、格式遵从能力、拒答倾向全变。
2. **API 行为变化**：限流策略、错误码、函数调用格式调整。
3. **主动升级**：团队主动换新模型，新模型在你的评估集上分数更高，但长尾场景可能翻车。

防御分层：

- **事前钉死**：配置写快照版本号；关键应用订阅厂商的变更公告与 deprecation 通知。
- **事中监测**：线上格式错误率、拒答率、空回复率是漂移的黄金信号——行为漂移最先体现在这些软指标上（与 4.9 的软故障监控同源）。
- **事后止血**：每个线上版本都有「资产组合整体快照」（提示词 + 模型 + 配置 + 数据索引），一键切回。止血优先于修复：先恢复服务，再重跑评估集、走正常流程适配新行为。

回滚开关必须演练过才算存在。季度流程里加一项：真的把流量切回上一版快照，验证回滚耗时与完整性。

### 4.5 变更留痕

三个月后有人问「这版为什么这么改」，答案必须是一条可查的记录，而不是聊天记录考古。发布记录的最小字段集：

| 字段 | 示例 | 用途 |
|---|---|---|
| 版本号 | prompt v1.7.0 / release r42 | 定位 |
| 改动说明 | 「压缩退款政策段，减少 token 30%」 | 回答为什么改 |
| 评估报告 | 冒烟 92 / 回归 88.5，报告链接 | 证明为什么能改 |
| 审批人 | tech lead 工号 | 责任链 |
| 线上观察结论 | 灰度 24h 解决率 81%→83%，无回归 | 闭环验证 |
| 回滚指针 | 上一稳定组合：prompt v1.6.2 + model 0718 | 出事时直接用 |

这是 3.5 历史表在发布侧的延续：评估体系记录「实验过程」，发布记录沉淀「上线决策」。

## 5. 架构 / 流程

一条完整的 Eval Gate 发布流水线：

```text
开发者提交（代码 + 提示词 + 配置）
        │
        ▼
┌─────────────────────────────┐
│ ① CI：build + unit test      │  传统闸门照跑：管逻辑正确性
└─────────────────────────────┘
        │ 通过
        ▼
┌─────────────────────────────┐
│ ② Eval Gate（评估门禁）      │
│   冒烟集 30 条 → 回归集 200 条 │  新闸门：管输出质量
│   judge 打分 + 指标核算        │
│   分数 < 门禁线 → 阻断 + 归档  │
└─────────────────────────────┘
        │ 分数 ≥ 门禁线
        ▼
┌─────────────────────────────┐
│ ③ 灰度放量                   │
│   10% 流量 × 24h             │  实弹检验：离线分数好 ≠ 线上好
│   观察：解决率/坏例率/客诉率    │
│   指标回归 → 回滚 → 停止放量   │
└─────────────────────────────┘
        │ 指标达标
        ▼
┌─────────────────────────────┐
│ ④ 全量发布 + 变更留痕         │
│   组合快照入档案库            │  回滚指针永远保留
│   基线分数滚动更新            │
└─────────────────────────────┘
        │
        ▼
发布后 → 4.9 监控告警；灰度观察 → 3.10 反馈回流
```

## 6. 代码 / 工具

### 6.1 GitLab CI 风格的评估门禁 pipeline

```yaml
# .gitlab-ci.yml —— LLM 应用 Eval Gate 发布流水线
stages: [build, test, eval-gate, canary, release]

variables:
  GATE_LINE: "85"     # 门禁线：低于即阻断
  BASELINE: "88"      # 上一个已发布版本的分数（滚动更新）

build:
  stage: build
  script:
    - make build
    - make prompts-bundle        # 打包提示词版本目录（见 6.2）

unit-test:
  stage: test
  script: make unit-test         # 传统闸门照跑：管逻辑，不管输出质量

eval-gate:
  stage: eval-gate
  script:
    - python eval/run.py --suite smoke      --json > artifacts/smoke.json
    - python eval/run.py --suite regression --json > artifacts/regression.json
    - python eval/gate.py --report artifacts/regression.json \
        --gate $GATE_LINE --baseline $BASELINE   # 分数不过线：exit 1，流水线断
  artifacts:
    when: always                 # 失败也要归档分数：变更留痕
    paths: [artifacts/]

canary-10:
  stage: canary
  script:
    - ./deploy.sh route --prompt "$CI_COMMIT_TAG" --ratio 10
    - python ops/canary_watch.py --hours 24 \
        --min-resolve-rate 0.80 --max-badcase-rate 0.02
  when: manual                   # 人工确认后再放灰度（人机协同见 3.10）
  environment: production

release-full:
  stage: release
  script:
    - ./deploy.sh route --prompt "$CI_COMMIT_TAG" --ratio 100
    - ./ops/update_baseline.sh --report artifacts/regression.json
  when: manual

rollback:
  stage: release
  script:
    - ./deploy.sh route --prompt "$(cat .last_stable)" --ratio 100  # 切回上一稳定组合快照
  when: manual
```

配套的门禁判定脚本，核心就一个比较加退出码：

```python
# eval/gate.py —— 分数不过线就阻断，让门禁写进流程而不是靠自觉
import json, sys, argparse

p = argparse.ArgumentParser()
p.add_argument("--report", required=True)
p.add_argument("--gate", type=float, required=True)
p.add_argument("--baseline", type=float, required=True)
args = p.parse_args()

report = json.load(open(args.report))
score = report["overall"]                      # judge 汇总分
failed_dims = [d for d, s in report["dims"].items()
               if s < {"format": 0.95, "refusal": 0.90}.get(d, 0.0)]

print(f"overall={score} gate={args.gate} baseline={args.baseline}")
if failed_dims:
    print(f"硬指标不达标: {failed_dims}"); sys.exit(1)
if score < args.gate:
    print("低于门禁线：阻断部署"); sys.exit(1)
print("通过门禁：放行进入灰度")
```

```text
prompts/
├── VERSION                      # 当前生效版本指针：1.7.0
├── registry.yaml                # 版本注册表：分数、作者、状态

    ├── changelog.md
    └── eval_report.json
```

```yaml
# prompts/registry.yaml —— 每个版本一条记录，回滚时按组合整体切换
versions:
```

## 7. 案例

### 案例 A：客服 Agent 的提示词治理

**场景**：某电商客服 Agent，系统提示词由 3 位工程师各自在聊天工具里维护「最新版」，一次口头同意的改动上线后客诉率从 2.1% 升到 5.8%，没人说得清改了什么。

**改造**：提示词迁入仓库版本化；发布走冒烟集 30 条 + 回归集 200 条的门禁；灰度 10% 流量观察客诉率 24 小时；每版留发布记录与回滚指针。

**效果**：三个月后客诉率稳定在 2% 以下，提示词回归类事故从每月 3 次降到 0；「上周改了什么」从一个问题变成一条记录。

### 案例 B：模型厂商静默更新，快照止血

**场景**：一家金融科技公司的工单 Agent，周五晚开始大量输出错误 JSON 格式。定位：厂商把浮版本号悄悄指向了新快照，格式遵从能力下降。

**处置**：配置里钉的是快照版本，未受影响的实例无感；受影响部分执行回滚预案——路由切回最近验证过的「提示词 + 模型快照」组合，22 分钟恢复服务。随后把新快照跑完整评估集，确认 3 个长尾场景掉分，选择继续钉旧快照并向厂商反馈。

**教训**：止血优先于修复。没有版本化与回滚开关的团队，此刻只剩通宵裸修——而裸修本身又是新的无版本变更。

### 案例 C：知识库数据变更纳入门禁

**场景**：某 SaaS 厂商的知识库团队每周更新文档，某次批量替换文档后，问答准确率从 85% 跌到 71%——旧文档被删，向量索引未同步，检索命中失效条目。

**改造**：数据变更视为一等资产变更：文档更新触发增量重建索引，索引打版本号（`kb_index@2026-09`）；索引版本变更同样过回归集门禁，通过后与提示词、模型版本一起组成新快照发布。

**效果**：数据类回归在门禁阶段被拦截，同类事故归零；知识时效从「更新后听天由命」变成「更新即验证」。

## 8. 常见坑

1. **提示词躺在配置中心或聊天工具里，无版本**。对策：迁入 git，单一事实源，改动必须走提交。
2. **模型用浮版本号**。对策：钉死快照版本号，订阅厂商变更公告。
3. **门禁线靠口头约定**。对策：阈值写进流水线配置，`exit 1` 阻断，不靠自觉。
4. **只跑单元测试不跑评估集**。对策：评估门禁设为流水线的必经 stage，失败归档分数。
5. **评估集一成不变**。对策：线上 bad case 过滤后持续进回归集（见 3.10），回归集只增不减。
6. **离线分数好就直接全量**。对策：离线分数好不等于线上好，灰度是最后一道实弹检验。
7. **灰度没有观察指标**。对策：预先定义解决率、坏例率、客诉率阈值，达标才放量。
8. **回滚只存在于理论上**。对策：回滚开关进季度演练，验证耗时与组合完整性。
9. **回滚只回滚提示词**。对策：按「提示词 + 模型 + 配置 + 数据索引」组合整体切，单回滚一项会拼出从未验证过的组合。
10. **分数不归档**。对策：评估报告作为 CI 产物强制存档，失败也存。
11. **基线不滚动更新**。对策：每次全量发布后更新基线分数，基线只升不降。
12. **把厂商静默更新当不可抗力**。对策：格式错误率、拒答率等软指标进监控（见 4.9），漂移当场发现而不是等用户投诉。

## 9. 练习

1. 给一个现有项目写 `.gitlab-ci.yml`：test 之后加 eval-gate stage，分数低于 85 用非零退出码阻断。
2. 把一段散落在代码里的系统提示词重构进 `prompts/` 版本目录，写 registry.yaml 与 changelog.md。
3. 构造 30 条冒烟集：10 条核心场景 + 10 条格式校验 + 10 条历史 bad case，写自动跑分脚本。
4. 把评估集分数故意改低 3 分，验证流水线确实阻断；再验证分数归档产物仍然生成。
5. 写一个回滚脚本：读 `.last_stable` 文件，把路由切回上一稳定组合（提示词 + 模型 + 索引），并实测耗时。
6. 做一次回滚演练：故意发布一个坏版本到灰度，走一遍「发现 → 回滚 → 复盘」全流程，记录总耗时。
7. 为模型版本漂移设计一个监控指标（如 JSON 解析失败率），写告警规则并推演告警触发后的处置动作。

## 10. 小结

- LLM 应用的「代码」远不止代码：**提示词、模型、配置、数据**四类资产都要版本化。
- Eval Gate 五步：**提交 → 传统测试 → 评估门禁 → 灰度 → 全量/回滚**，评分不过线就阻断上线。
- 传统 CI/CD 对 LLM 失效的根子是**非确定性输出使断言失效**：误报（字面不同都对）+ 漏报（相似但都错）。
- 解法是换尺子：**评估集 + 语义判定 + 阈值门禁**；门禁线写进流水线，不靠自觉。
- 评估集分两层：**冒烟集**快速拦截，**回归集**拦全局回归，线上 bad case 持续回流。
- **模型即依赖，依赖会漂移**：钉快照版本、软指标监测漂移、组合快照一键回滚。
- 止血优先于修复：厂商静默更新时先切回已验证快照，再走流程适配。
- 灰度是标配：**10% 流量 × 24 小时**，离线分数好不等于线上好。
- 变更留痕：改动说明 + 评估分数 + 审批记录 + 线上结论归档，让每次发布可追溯。
- 这条流水线向上接 3.5 的评估分数，向下接 4.9 的运行期监控，灰度期的人工反馈流向 3.10 的反馈闭环。
