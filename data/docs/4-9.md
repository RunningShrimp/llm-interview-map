# 讲解 4.9 部署与运维

> 说明：前置 3.6 部署与扩展、3.7 成本延迟与可靠性、3.9 CI/CD 与发布，讲的是"怎么安全地发上线"；3.4 可观测性与追踪提供了监控的底层设施。  
> 4.9 是**实战收口**：Agent 已经跑在线上，模型变了、Prompt 改了、知识库更新了、工具挂了、成本涨了、被攻击了——怎么办？本篇讲监控大盘、告警响应、SLA 管理、故障处理、值班与 Runbook、故障演练这套**上线后的运维实战**。  
> 沉淀下来的指标、大盘与故障复盘，直接成为 4.10 作品集与复盘里最硬的材料。

---

## 1. 定位

实战层第 9 个知识点，属于"上线与运维实战"。
它解决一个核心问题：**如何把 Agent 从"能跑通"变成"能长期稳定运行"，并具备监控、告警、SLA 管理、故障处理、回滚、成本控制、安全响应的完整运维能力？**

对锚点问题"如何保证线上稳定"的正面回答，是一组能力等式：

```text
线上稳定 = 可观测（看得见） + 可告警（叫得醒） + 可回滚（退得回） + 可演练（练得到）
```

- **可观测**：指标、日志、轨迹（Trace）三层齐全，任何一次请求都能还原（见 3.4）。
- **可告警**：关键指标越限时按分级叫到人；不报错但跑偏的"软故障"也有指标能抓住。
- **可回滚**：代码、Prompt、模型、知识库、配置五类对象都能分钟级退回上一版本（见 3.9）。
- **可演练**：降级、限流、扩容这些纸面预案定期真实演练过，真故障时不靠临场发挥。

与相邻篇的分工：部署形态与伸缩机制见 3.6，缓存/路由/重试等单点可靠性手段见 3.7，CI/CD 流水线与版本管理见 3.9。本篇讲**这些能力在上线之后如何组织成一套运维体系**。它是 4.10 作品集与复盘的直接前置。

## 2. 一句话定义

部署与运维，是把 Agent 系统容器化、编排化、可观测化、可灰度化、可回滚化，并通过监控、告警、SLA 管理、值班、故障演练、成本治理，保证其长期稳定、安全、经济运行的实战体系。

简化公式：

```text
Agent 运维 = 部署 + 监控 + 告警 + SLA + 故障处理 + 回滚 + 成本治理 + 安全响应 + 持续评估
```

## 3. 为什么需要

Agent 上线后比普通服务更难运维：

- **模型会变**：厂商更新模型，行为可能漂移。
- **Prompt 会变**：改一行 Prompt，输出全变。
- **知识库会变**：新文档进、旧文档出、权限变更。
- **工具会挂**：第三方 API 超时、限流、返回格式变化。
- **成本会飘**：多轮 Agent 的 token 消耗按步数复利增长。
- **安全会破**：新注入方式、越权尝试、数据泄露。
- **轨迹复杂**：一次请求几十个 span，出问题难定位。
- **状态难恢复**：任务中断后不知道从哪继续。
- **SLO 难保证**：P99 延迟、成功率、成本三条线都要同时盯。

**有与没有运维体系的对比**：

| 维度 | 没有运维体系 | 有运维体系 |
|---|---|---|
| 故障发现 | 用户投诉了才知道 | 分钟级告警到人 |
| 故障定位 | 翻日志靠猜 | Trace 回放定位到具体 span |
| 故障恢复 | 手忙脚乱改代码 | 降级/回滚分钟级止血 |
| 质量劣化 | 缓慢下滑无人察觉 | 每周评估回归兜住 |
| 成本 | 月底看账单惊吓 | 日预算告警 + 按任务归因 |
| 安全 | 被打很久才发现 | 审计告警 + 红队演练 |

**类比一**：

```text
部署上线 = 把车造好、开上路
运维     = 每天查油量、胎压、故障灯，出事故会走保险，按期年检
          没有运维的车也能开，直到某天在高速上抛锚
```

## 4. 核心原理

### 4.1 Agent 运维的特殊性

| 维度 | 普通服务 | Agent 服务 |
|---|---|---|
| 行为确定性 | 高 | 低（同样的输入可能有不同轨迹） |
| 依赖 | 数据库、缓存 | LLM、向量库、工具、模型厂商 |
| 变更对象 | 代码、配置 | 代码、Prompt、模型、知识库、工具 |
| 故障模式 | 超时、报错 | 幻觉、跑偏、越权、成本爆炸 |
| 调试 | 日志 + 断点 | Trace + 轨迹回放 + 评估 |
| 质量指标 | 成功率、延迟 | 成功率、延迟、成本、忠实度、安全 |
| 回滚 | 代码回滚 | 代码 + Prompt + 模型 + 知识库回滚 |

一句话总结：普通服务运维的对象是"系统"，Agent 运维的对象是"系统 + 行为"。行为由模型、Prompt、知识库共同决定，任何一处变化都相当于一次**隐形发布**——这是 Agent 运维所有特殊性的根源。

### 4.2 部署形态与多环境

部署机制本身（容器、Serverless、伸缩策略）见 3.6，配置与版本管理见 3.9，这里只给选型结论与一条纪律：

| 形态 | 适用 | 特点 |
|---|---|---|
| 单容器 | 小流量、内部工具 | 简单 |
| K8s Deployment | 生产标准 | 可扩展、可灰度 |
| Serverless | 波动流量 | 按需、有冷启动 |
| 混合 | 核心自建 + 弹性上云 | 灵活 |

**Agent 生产推荐**：K8s + HPA + Redis + 队列 + 向量库。环境链路 `dev → staging → canary → prod`，配置分层覆盖：

```yaml
# base.yaml —— 所有环境共享
agent:
  max_steps: 20
  timeout: 300

# prod.yaml —— 生产覆盖：模型必须钉死版本号
agent:
  llm: { default: gpt-4o-2024-08-06 }
  budget: 5.0
```

纪律：**prod 的模型版本必须钉死**（写具体版本号，不写别名）。厂商静默把别名切到新版本，等于没人审批过的一次全量发布。

### 4.3 上线前检查清单

| 检查项 | 通过标准（示意） |
|---|---|
| 功能评估 | Smoke + Core 评估集全部通过（见 3.5） |
| 性能 | P95 延迟、单次成本达标 |
| 红队 | 通过率 > 95%（见 4.8） |
| 鲁棒性 | 异常输入、工具故障注入不崩溃 |
| 权限与审计 | 最小权限 + 审计日志落盘（见 3.8） |
| 可观测 | 指标、日志、Trace 三件套就绪（见 3.4） |
| 灰度与回滚 | 放量计划 + 自动回滚判据就绪 |
| 密钥 | Secret 集中管理，代码零密钥 |
| 容量 | 压测过峰值，HPA 已启用 |
| 应急 | 值班手册、联系人、升级路径就绪 |

十项全绿才放行。缺任何一项的发布，都是在拿用户流量做测试。

### 4.4 监控体系

**四层监控**，下层正常不代表上层正常：

```text
1. 基础设施：CPU、内存、网络、磁盘
2. 服务：QPS、错误率、延迟、饱和度
3. LLM：token 分列消耗（输入/输出）、成本、模型延迟、限流
4. Agent：步数、工具调用、成功率、轨迹质量
```

**LLMOps 黄金信号**：首字延迟（TTFT, Time To First Token）、输入/输出 token 分列消耗、单请求成本、缓存命中率、步数分布——这五项是 LLM 应用区别于普通服务的监控核心。

**关键指标表**：

| 指标 | 目标（示意） |
|---|---|
| 请求成功率 | > 99% |
| P95 / P99 延迟 | < 10s / < 30s |
| 首字延迟 TTFT | P95 < 2s |
| 单次请求成本 | 在分任务预算内 |
| 平均步数 | P95 < 10 步（超限即疑似跑偏） |
| 工具调用成功率 | > 98% |
| 缓存命中率 | > 20% |
| 红队拦截率 | > 95% |
| 错误预算剩余 | > 50% |

**软故障（Silent Failure）监控**：Agent 特有的故障形态——服务返回 200，但回答跑偏、原地循环、越权读数据。聚合指标看不见它，要靠轨迹级指标：步数分布右移、同一工具连续失败、输出长度异常、引用为空率上升；再配合生产 Trace 抽样做语义抽检（抽样进评估集，见 3.5）。

### 4.5 SLA、SLO 与错误预算

- 服务水平协议（SLA, Service Level Agreement）：对客户承诺的可用性底线，违约有赔付责任。
- 服务水平目标（SLO, Service Level Objective）：团队自己设定的、比 SLA 更严的内部目标。
- 错误预算（Error Budget）：`1 − SLO`，即允许出错的总量。它是"稳定"与"迭代速度"之间的调节阀。

**不同 SLO 对应的错误预算**（按 30 天、1 亿次请求折算）：

| SLO | 允许月错误时间 | 允许月失败请求数 | 适用 |
|---|---|---|---|
| 99% | 438 分钟 | 100 万次 | 内部工具 |
| 99.5% | 219 分钟 | 50 万次 | 一般在线服务 |
| 99.9% | 43.8 分钟 | 10 万次 | 生产 Agent 常用基线 |
| 99.99% | 4.38 分钟 | 1 万次 | 需多活 + 全自动止损 |

**类比二**：错误预算 = 手机电量。SLO 定 99.9%，等于每月只给你 43.8 分钟的"出错额度"；额度内的小故障可以容忍、照常发布；电量烧光就得省着用——**冻结功能发布，只修稳定性问题**，等预算回充再恢复迭代。

监控口径用烧穿率（Burn Rate）：`burn rate = 1.0` 表示正以"恰好一个月烧完全部预算"的速度出错。多窗口告警：1 小时窗口 burn rate > 14.4 立即电话（P0），6 小时窗口 > 6 升级处理（P1）——实现见 6.6。

### 4.6 告警设计

**分级告警**——不分级就会"P0 和 P3 混在一个群里，值班麻木，真故障被淹没"：

| 级别 | 触发（示意） | 动作 | 响应时限 |
|---|---|---|---|
| P0 | 服务不可用、burn rate > 14.4 | 电话 + 立即值班 | 5 分钟 |
| P1 | 错误率 > 5%、P99 > 30s | 即时消息 + 值班 | 15 分钟 |
| P2 | 日成本 > 80% 预算、工具失败 > 5% | 群通知 | 当天 |
| P3 | 缓存命中率下滑、日志异常 | 记录周报 | 不打扰 |

两条纪律：每条 P0/P1 告警必须挂对应的 Runbook 链接（见 6.7）；告警必须可行动——收到后不知道下一步做什么的告警，先删掉或降级。Prometheus 规则实现见 6.4。

### 4.7 故障处理

**常见故障与处理**：

| 故障 | 现象 | 处理 |
|---|---|---|
| LLM 限流 | 429 增多 | 退避重试、降级备用模型 |
| LLM 故障 | 5xx / 超时 | 熔断（Circuit Breaker）、降级（Fallback）、缓存兜底 |
| 工具超时 | 延迟高 | 重试、降级、跳过并告知 |
| 向量库慢 | 检索延迟高 | 加缓存、扩副本、降级 BM25 |
| 成本突增 | 账单上涨 | 限流、路由小模型、压缩上下文 |
| 越权尝试 | 审计告警 | 拦截、通知安全 |
| 注入攻击 | 红队告警 | 输入过滤、输出校验 |
| 死循环 | 步数超限 | 最大步数、循环检测（见 2.5） |
| 状态丢失 | 恢复失败 | 检查点、状态外置 |
| 软故障 | 200 但跑偏 | 语义抽检、轨迹质量告警、评估回归 |

**故障处理流程**——先止血，后定位，顺序不能反：

```text
1. 告警触发
2. 值班确认（对照 Runbook）
3. 止血：限流、降级、回滚（不以定位根因为前提）
4. 定位：Trace + Logs + Metrics 三角对照
5. 修复
6. 复盘（Postmortem）：时间线、根因、行动项
7. 行动项落地：坏例进评估集、新模式进监控
```

**软故障四层防御**（从输入到观测层层兜住"不报错的坏结果"）：

```text
1. 输入层：输入校验、注入过滤
2. 执行层：最大步数、循环检测、超时、预算熔断
3. 输出层：输出校验、引用核对、高危动作人工确认
4. 观测层：轨迹质量指标 + 语义告警 + 生产 Trace 抽样评估
```

**面试高频问法**：「Agent 服务半夜挂了怎么办？」「线上不报错但回答跑偏，怎么发现和止损？」共识口径分两段答。硬故障：告警分级叫醒值班 → 照 Runbook 止血（熔断降级、切备用模型、必要时回滚，见案例 A）→ Trace 定位根因 → 复盘进回归集；自动化程度高的系统里，止血这步由熔断器和自动回滚先执行，值班做确认。软故障：靠轨迹质量指标（步数分布、工具失败率、输出异常率）和语义抽检先于用户发现，止损靠步数上限、循环检测和预算熔断这些执行层护栏，根因（Prompt 回归、模型漂移）靠评估集定位。

### 4.8 灰度与回滚

**灰度发布（Canary Release）流程**：

```text
1. 部署新版本（0 流量）
2. 健康检查 + 离线评估通过
3. 切 1% 流量，观察 10 分钟
4. 5% → 10% → 50% → 100% 逐级放量
5. 每级检查：错误率、延迟、成本、在线评估分
6. 任一判据越限 → 自动回滚，人工再复盘
```

**回滚对象**——Agent 的回滚面比普通服务宽得多：

代码、Prompt、模型版本、工具版本、知识库索引、配置，六类都要版本化（见 3.9），任何一类不能退回，等于灰度只保护了一半。

**自动回滚判据**（示意）：

```python
def should_rollback(metrics):
    # 任一判据越限即触发回滚，不等人工确认
    return (
        metrics["error_rate"] > 0.01
        or metrics["p99_latency"] > 30
        or metrics["success_rate"] < 0.95
        or metrics["cost_per_request"] > 0.05
    )
```

### 4.9 成本治理

单点手段（缓存、路由、降级的机制细节）见 3.7，运维侧关注的是**持续盯住 + 快速归因**：

| 手段 | 说明 |
|---|---|
| 模型路由 | 简单任务路由到小模型 |
| 缓存 | 精确缓存 + 语义缓存 |
| 上下文压缩 | 摘要、滑动窗口 |
| 输出限制 | max_tokens 封顶 |
| 预算告警 | 日预算 80% 触发 P2 |
| 租户配额 | 每租户日/月上限 |
| 成本归因 | 按模型、租户、任务类型拆账 |

成本日报（总额、按模型、按租户、Top 消耗任务、预算消耗）的实现见 6.3 的埋点与聚合。

**面试高频问法**：「LLM 账单一个月涨了几倍，要求降下来且不能伤核心场景质量，怎么做？」共识口径：先归因后动手——用成本 Dashboard 按模型/租户/任务把增量拆出来（大多数暴涨来自一两类任务，见案例 B），再上路由、缓存、压缩、配额的组合拳，最后用评估集守住核心场景的质量不回退，而不是一刀切砍模型。

### 4.10 值班、Runbook 与故障演练

**值班手册（Runbook）内容**：系统架构图、关键 Dashboard、常见故障 SOP、回滚步骤、联系人、升级路径。模板见 6.7。

**应急预案**（预写好的止血动作）：

- LLM 全挂：降级备用模型，再降级缓存命中结果。
- 向量库挂：降级 BM25 关键词检索。
- 数据库挂：切只读模式，写操作排队。
- 被攻击：限流、封禁、切备用入口。
- 成本失控：限流、暂停非核心任务。

**故障演练类型表**：

| 演练类型 | 做法 | 验证什么 | 频率（示意） |
|---|---|---|---|
| 依赖故障注入 | 断开 LLM / 向量库 / DB | 熔断、降级链路、缓存兜底 | 每月 |
| 高并发压测 | 逐步加压到峰值 2 倍 | HPA 扩容、限流、排队 | 每季度 |
| 软故障演练 | 注入超长步骤、循环调用请求 | 步数上限、循环检测、语义告警 | 每月 |
| 值班拉练 | 随机触发 P1 演练告警 | 响应时限、Runbook 可用性 | 每季度 |
| 红蓝对抗 | 红队模拟注入与越权（见 4.8） | 拦截率、审计告警、应急流程 | 每季度 |
| 灾难恢复 | 区域级故障模拟 | 备份恢复、多活切换 | 每半年 |

**类比三**：故障演练 = 消防演习。不能等真着火才第一次走疏散路线——降级开关、备用模型、限流阀门必须在平时真实按过一次，真故障时才敢按、会按。没演练过的预案，默认它是坏的。

## 5. 架构 / 流程

**运维视角的全景分层**：

```text
┌──────────────────────────────────────────┐
│  接入层                                   │
│  CDN / WAF / LB / API Gateway             │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  Agent 服务（K8s Deployment + HPA）       │
│  ├─ 多副本                               │
│  ├─ 健康检查 + 就绪检查                  │
│  ├─ 优雅关闭                             │
│  └─ 灰度标签（version 路由）             │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  依赖层                                   │
│  Redis / 队列 / 向量库 / DB / LLM API    │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  运维层                                   │
│  ├─ 监控 Prometheus + Grafana            │
```

### 6.2 健康检查、就绪检查与优雅关闭

liveness 回答"进程要不要重启"，readiness 回答"现在能不能接流量"，两者不能合成一个：

```python
@app.get("/health")
async def health():
    # 存活检查：只看进程本身，不查依赖，避免依赖抖动引发重启风暴
    return {"status": "ok"}

@app.get("/ready")
async def ready():
    # 就绪检查：依赖连通性不满足时摘除流量，但不重启
    if not startup_complete:
        raise HTTPException(503, "not ready")
    if not await check_dependencies():
        raise HTTPException(503, "dependencies unavailable")
    return {"status": "ready"}

async def shutdown():
    # 优雅关闭：滚动更新时先摘流量，再给存量任务最长 60 秒收尾
    await deregister_from_lb()
    await asyncio.wait_for(drain_inflight_tasks(), timeout=60)
    await save_checkpoints()   # 未完成任务落检查点，机制见 2.5
```

### 6.4 告警规则（Prometheus）

```yaml
groups:
- name: agent
  rules:
  - alert: AgentHighErrorRate          # P1：错误率
    expr: rate(agent_requests_total{status="error"}[5m]) / rate(agent_requests_total[5m]) > 0.05
    for: 5m
    labels: { severity: P1 }
    annotations: { summary: "Agent 错误率 > 5%", runbook: "rb-error-rate" }
  - alert: AgentHighP99                # P1：长尾延迟
    expr: histogram_quantile(0.99, agent_request_latency_seconds_bucket) > 30
    for: 5m
    labels: { severity: P1 }
    annotations: { runbook: "rb-latency" }
  - alert: AgentCostHigh               # P2：日预算
    expr: agent_cost_dollars_today > 0.8 * agent_cost_budget
    labels: { severity: P2 }
    annotations: { runbook: "rb-cost" }
  - alert: AgentRunaway                # P1：步数右移 = 疑似跑偏/死循环（软故障）
    expr: histogram_quantile(0.95, agent_steps_bucket) > 20
    for: 10m
    labels: { severity: P1 }
```

### 6.6 错误预算与烧穿率

```python
def error_budget_status(window_hours: float, slo: float = 0.999) -> dict:
    """按请求口径计算 SLI、预算消耗与烧穿率（burn rate）。"""
    total = requests_in_window(window_hours)
    errors = errors_in_window(window_hours)
    sli = 1 - errors / total                    # 服务水平指标
    burn_rate = (1 - sli) / (1 - slo)           # 1.0 = 匀速烧完当月预算
    budget_used = (1 - sli) * window_hours / ((1 - slo) * 730)   # 月预算按 730 小时折算
    return {
        "sli": round(sli, 5),
        "budget_used": round(budget_used, 4),
        "burn_rate": round(burn_rate, 2),
        # 经验阈值（多窗口）：1h 窗口 > 14.4 → P0 电话；6h 窗口 > 6 → P1
        "policy": "冻结发布" if budget_used > 1.0 else "正常迭代",
    }
```

## 7. 案例

### 案例 A：LLM 故障自动降级

**场景**：某内容平台的多 Agent 写作服务，主力模型厂商凌晨区域级故障，补全请求开始大面积超时。

**做法（止血自动化，值班只做确认）**：

```text
00:03  熔断器检测到连续 5 次失败，打开熔断，停止向故障端点发请求
00:03  自动降级到备用模型，写作类任务切换成功
00:05  备用模型限流，长上下文任务降级到缓存命中结果 + 排队
00:07  P1 告警到值班，确认降级链路符合预期，决定不回滚
00:41  厂商恢复，熔断器半开探测成功，自动切回主力模型
```

**示意数字效果**：故障 38 分钟，整体可用性保住 95.2%（引入降级演练前，同类故障可用性约 60%）；降级期间生成质量评估分下降 0.4 分（10 分制），业务可接受。这条降级链路正是月度故障演练验证过的（见 4.10）。

### 案例 B：成本突增定位与复盘

**场景**：某电商客服 Agent，日成本从 $50 涨到 $200（4 倍），80% 预算告警触发。

**复盘时间线**：

| 时间 | 动作 | 发现 |
|---|---|---|
| 09:10 | 成本 Dashboard 下钻 | gpt-4o 通道成本涨 5 倍，其他通道平稳 |
| 09:25 | Trace 抽样对比 | "订单追踪"类请求平均输入 token 从 3k 涨到 25k |
| 09:40 | Logs 关联 | RAG 检索单次返回 50 篇文档全量塞进上下文 |
| 09:50 | 根因确认 | 前日发布把 Top-K 误配成 50（应为 5），灰度期量小未暴露 |

**修复与行动项**：Top-K 改回 5 并加配置校验；"检索量"进入发布检查清单；成本按任务类型的日环比告警阈值从 50% 收紧到 30%。次日成本回落到 $58。这次复盘的关键是**归因链路**（Dashboard → Trace → Logs）三步定位，而不是盲目砍模型。

### 案例 C：灰度拦截 Prompt 回归

**场景**：一家金融科技公司的合规审查 Agent，v2 版本把输出格式 Prompt 从宽松改为严格 JSON。

**流程与示意数字**：

```text
1. v2 上线，切 1% 流量
2. 10 分钟观察窗内错误率 0.1% → 0.5%（自动回滚阈值 0.3%）
3. 触发自动回滚，全程 12 分钟，受影响请求约 1,400 条
4. 复盘：新 Prompt 删掉了"输出前自检 JSON"一句，
   长输入下格式错误率升 4 倍
5. 行动项：Prompt 补回自检指令；500 条失败样本加入评估回归集
6. 一周后重新灰度：错误率 0.08%，逐级放量到 100%
```

**关键**：灰度 + 自动回滚 + 评估回归三件套，把一次潜在的线上事故降级成 12 分钟的小事件，并且坏例沉淀为回归资产。

## 8. 常见坑

1. **只有存活检查，没有就绪检查**。  
   启动未完成（模型、向量库未连上）就接流量，首批请求全挂。liveness 与 readiness 分开实现，语义见 6.2。

2. **没有优雅关闭**。  
   滚动更新时正在执行的多步任务被硬杀，轨迹断在中途。处理 SIGTERM：先摘流量，再给存量任务最长 60 秒收尾或落检查点。

3. **状态写在本地**。  
   Pod 重启，会话与任务状态全丢。状态外置到 Redis/DB，靠检查点恢复（机制见 2.5）。

4. **指标只看 CPU 和内存**。  
   LLM 服务的真正瓶颈在 token、限流、工具失败率，CPU 平稳不代表服务正常。四层监控缺一不可（见 4.4）。

5. **告警不分级**。  
   P0 和 P3 混在一个群里，值班麻木，真故障被淹没。P0–P3 分级 + 分渠道通知（见 4.6）。

6. **告警没有对应的 Runbook**。  
   告警报了但没人知道下一步做什么。每条 P0/P1 告警必须挂 SOP 链接，无 SOP 的告警先删或降级。

7. **只监控硬故障，看不见软故障**。  
   服务返回 200 但回答跑偏、原地循环，用户先于监控发现。加轨迹质量指标（步数分布、工具失败率）与生产 Trace 语义抽检。

8. **没有 Trace**。  
   一次请求几十个 span，只有聚合日志无法定位是哪一步错。全链路 Trace + 轨迹回放（见 3.4）。

9. **只能回滚代码**。  
   Prompt、模型版本、知识库索引没有版本化，出问题退不回去。六类回滚对象全部版本化（见 3.9）。

10. **全量发布不做灰度**。  
    一次坏 Prompt 直接打全量用户。1% 起步逐级放量，每级带自动回滚判据（见 4.8）。

11. **成本没有日预算告警**。  
    月底看账单才发现涨了 4 倍。80% 预算告警 + 按任务日环比监控（对照案例 B）。

12. **错误预算烧穿还在发布**。  
    SLO 已经跌破还继续上新功能，雪上加霜。预算耗尽冻结功能发布，只允许稳定性修复（见 4.5）。

13. **值班手册只在老员工脑子里**。  
    新人值班翻聊天记录找答案。Runbook 文档化，随架构变更同步更新（模板见 6.7）。

14. **预案写了但不演练**。  
    降级开关两年没按过，真故障时不敢按也不会按。按频率表做故障演练（见 4.10）。

15. **不做上线后评估回归**。  
    模型静默更新、Prompt 顺手一改，质量缓慢劣化无人察觉。每周评估集回归 + 生产 Trace 抽样进评估（见 4.8、3.5）。

16. **密钥散落在配置和代码里**。  
    轮换困难、泄露无审计。Secret 集中管理，服务零密钥（见 3.8）。

## 9. 练习

1. 为你的 Agent 写 Dockerfile（非 root + HEALTHCHECK）与 K8s Deployment + HPA。验收：滚动更新期间零失败请求。
2. 实现 /health 与 /ready 双端点，ready 检查 LLM 与向量库连通性。验收：断开依赖后 Pod 自动摘除流量但不重启。
3. 实现 SIGTERM 优雅关闭。验收：滚动更新中存量任务能收尾或落检查点。
4. 用 prometheus_client 埋 6 个指标（请求、延迟、TTFT、成本、步数、工具失败），在 Grafana 出第一块大盘。
5. 配置告警规则：错误率 > 5%（P1）、P99 > 30s（P1）、日成本 > 80% 预算（P2），每条挂 Runbook 链接。
6. 为服务定一个 SLO（如 99.9%），算出月错误预算，实现烧穿率告警（1 小时窗口 > 14.4 触发电话级）。
7. 实现灰度发布：1% → 5% → 10% → 50% → 100%，错误率 > 1% 自动回滚。验收：人为注入坏版本，15 分钟内自动退回。
8. 写一份值班 Runbook（三类故障 SOP、回滚步骤、升级路径），找一位没值过班的同事按手册走完一次 LLM 限流场景。
9. 做一次故障演练：断开 LLM 依赖 10 分钟，记录降级是否生效、告警是否触发、恢复是否自动，输出演练报告与改进项。
10. 实现成本日报（总额/按模型/按租户/Top 任务/预算消耗），人工注入一次"成本突增"（改 Top-K），练习 30 分钟内定位根因。

## 10. 小结

- Agent 运维 = **部署 + 监控 + 告警 + SLA + 故障处理 + 回滚 + 成本 + 安全 + 评估回归**。
- 线上稳定四能力：**可观测、可告警、可回滚、可演练**——这是"如何保证线上稳定"的完整答法。
- 上线前：**功能、性能、红队、鲁棒、权限、监控、灰度、回滚**十项检查全绿才放行。
- 监控：**基础设施、服务、LLM、Agent** 四层；黄金信号盯 TTFT、token 分列、单请求成本、缓存命中率、步数分布；软故障靠轨迹质量指标抓。
- SLA：**SLO 定目标，错误预算管发布**——预算烧穿就冻结变更，只修稳定性。
- 告警：**P0–P3 分级，每条高级别告警挂 Runbook**；不可行动的告警是噪音。
- 故障处理：**先止血（限流/降级/回滚）后定位（Trace+Logs+Metrics）**，复盘产物回流评估集与监控。
- 灰度与回滚：**逐级放量 + 自动回滚判据**，代码/Prompt/模型/工具/知识库/配置六类对象都可退。
- 成本：**归因、路由、缓存、压缩、配额**五板斧，日预算告警兜底。
- 核心原则：**可观测、可灰度、可回滚、可降级、可审计、可恢复**——演练验证过的能力才算数。
- 这些能力直接支撑：4.10 作品集与复盘（大盘、SLO 数据、故障复盘是作品集最硬的材料）、5.5 阶段 4：AI 工程化。
