# 讲解 4.9 部署与运维

> 说明：3.6 讲了推理服务化的性能账（TTFT、吞吐），3.9 讲了上线前的评估门禁——它们守住「发出去的版本是对的」。

## 1. 定位

L4 工程化层第 9 个知识点，线上运维专篇。

它解决一个根本问题：**传统运维靠「报错才告警」，但 Agent 的多数坏事不报错——跑偏、卡死、质量悄悄劣化。怎么办？**

前置依赖：

- 3.6 推理服务化认知：黄金信号里的 TTFT 与吞吐，正是服务化性能账在 Agent 业务侧的延续。
- 3.9 Prompt 即代码：评估门禁守「上线前」，本篇的质量抽检与回归是它的线上版——上线前后同一条护栏。

后续走向：4.10 作品集与复盘——「发现软故障→回放定位→止损→复盘沉淀」是面试里最硬的工程故事。与 4.8 红队的关系：红队发现的整改项进入运维的加固与监控闭环。

## 2. 一句话定义

Agent 运维的核心是防御「软故障」（不报错但跑偏、卡死、质量劣化、假成功）：入口护栏、执行熔断、输出抽检、trace 回放定位四层设防，配合 TTFT、token 分列消耗、单请求成本、缓存命中率、任务成功率五个黄金信号做告警，出事用降级、限流、回滚三板斧先止血再查因。

## 3. 为什么需要

传统服务坏了会喊疼：接口 500、超时、宕机，堆栈在日志里，告警立刻响。Agent 不是。

两类故障的对比：

| 维度 | 硬故障 | 软故障 |
|---|---|---|
| 现象 | 接口 500/超时、进程崩溃、格式解析失败 | 跑偏、循环卡死、质量下滑、假成功（状态完成、结果错误） |
| 有没有报错 | 有，日志有堆栈 | 没有，接口零报错、日志干干净净 |
| 发现信号 | 错误率、重启次数 | 业务信号：抽检分、成功率、成本曲线 |
| 检测手段 | 传统监控即够 | 质量抽检、步数熔断、成本看板 |
| 危害节奏 | 立即可见，马上修 | 悄悄恶化，等发现已扩散（用户默默流失、账单悄悄上涨） |
| 典型例子 | 模型 API 503 | Agent 卡在一步反复调工具空烧 token；任务「假成功」 |

软故障更常见的三个结构性原因：

1. **多步自主放大误差**。10 步任务每步 95% 正确，整链正确率约 0.95^10 ≈ 60%——任何一步悄悄劣化，都会被链条复利放大。
2. **LLM 的失败不抛异常**。模型被问倒了会编一个流畅的答案，循环了会继续流畅地循环——失败是「语义级」的，错误监控看不到。
3. **依赖面大且不可控**。模型、检索源、工具 API、上游知识库，任何一个悄悄变劣（比如换版后正文变乱码），Agent 不会报错，只会产出变差。

类比：硬故障像爆胎，砰一声仪表盘立刻报警；软故障像导航悄悄失灵——车还在跑、没有异响，方向一点点偏了，等你发现已经开出几十公里。所以 Agent 运维的重点不是「坏了才报警」，而是装上「持续比对方向」的装置。

## 4. 核心原理

### 4.1 四层防御

医院分级诊疗式的层层设防，每层兜住一类软故障：

| 层 | 时机 | 手段 | 兜不住的 |
|---|---|---|---|
| L1 输入护栏 | 进门预检 | 输入校验、目标清晰度检查、预算护栏（token/成本上限，超预算先拦） | 执行中的偏航 |
| L2 执行熔断 | 术中监护 | 最大步数、单任务成本熔断、循环检测（同工具同参数重复调用）、超时 | 输出质量劣化 |
| L3 输出抽检 | 术后抽检 | 随机抽样 + Judge 打分、关键任务全检、趋势对比基线 | 已流入用户的个别坏例 |
| L4 回放定位 | 会诊 | trace 分步记录、低分请求回放、与历史 diff 对比 | （不拦截，负责根因） |

设计原则：**坏消息尽早暴露、尽快定位。** L1、L2 是拦截型（不让坏事发生/持续），L3 是发现型（坏事已发生但尽快知道），L4 是定位型（知道之后搞清为什么）。

### 4.2 黄金信号

传统 SRE 四金信号（延迟、流量、错误、饱和度）在 Agent 场景不够用——软故障下错误率是 0。要盯五个仪表盘数字：

| 指标 | 含义 | 为什么重要 | 异常含义 | 采集方式 |
|---|---|---|---|---|
| TTFT（Time To First Token） | 用户等首字多久 | 体验的第一感受；流式服务的门面 | 上游模型/网关劣化、排队 | 网关打点：请求发出到首个 token 到达 |
| token 分列消耗 | 各环节各烧多少（输入/输出/按工具/按轮次） | 成本结构可见；异常模式可定位到环节 | 某环节 token 暴涨=提示词膨胀或循环 | 每次调用按 role/环节埋点上报 |
| 单请求成本 | 一次任务平均多少钱 | 商业健康度；最灵敏的软故障探针 | 飙升=循环卡死或缓存失效 | 成本 = sum(token 分列 × 单价) / 任务数 |
| 缓存命中率 | 重复请求走了多少捷径 | 命中率掉则成本延迟双涨 | 提示词模板改动、缓存键设计错误 | 缓存层打点 |
| 任务成功率 | 多少活真正干成 | 唯一直接反映「干活能力」的业务指标 | 下滑=模型/工具/流程某处劣化 | 端到端任务状态打点（注意甄别假成功） |

记忆口诀：**两个体验（TTFT、成功率）、两个成本（token 分列、单请求成本）、一个效率（缓存命中率）。** 其中单请求成本与任务成功率组合，是软故障最灵敏的探测器。

### 4.3 告警设计

告警要分级，避免「要么不告、告了狼来了」：

| 级别 | 定义 | 示例 | 响应 |
|---|---|---|---|
| P0 | 业务受损，需立即人工介入 | 任务成功率跌破 60%、P0 预算击穿 | 值班拉群，直接上止损三板斧 |
| P1 | 明确劣化，当日处理 | 抽检分环比掉 10 分、单请求成本翻倍 | 定位根因，评估是否降级 |
| P2 | 趋势异常，观察处理 | 缓存命中率连续 3 天缓慢下滑 | 排查近期变更 |
| P3 | 信息记录 | 单条低分请求入队 | 汇入周报与回放样本池 |

两个工程要点：

1. **阈值 + 趋势双触发**。绝对阈值（成功率 < 60%）抓急病，趋势触发（滑窗环比掉 10%）抓慢病——软故障多数是慢病。
2. **防告警风暴**。同类告警聚合、故障期间静默依赖它的下游告警，否则值班在被吵第三次后会把告警群静音，防线形同虚设。

### 4.4 告警与止损：三板斧

**先止血，再查因。** 值班的头等任务不是找根因，是把坏结果掐断：

| 手段 | 触发条件 | 具体动作 | 代价 |
|---|---|---|---|
| 降级 | 某环节劣化但服务还要保 | 切备用模型/备用检索源；上兜底话术；关掉非核心功能 | 质量临时下降但可用性保住 |
| 限流 | 成本失控、下游过载 | 按租户/接口限并发、降配额；超限排队 | 部分用户等待或拒绝 |
| 回滚 | 变更后指标劣化且降级无效 | 退回上一个好版本（Prompt 版本、模型版本、配置） | 丢失新版本的收益 |

顺序上有讲究：运行时问题（外部依赖劣化、成本风暴）用降级/限流；确认与版本相关（发布后开始劣化）用回滚。回滚要快，靠的是 3.9 门禁留下的版本化 Prompt/配置——回滚的是配置不是代码。

### 4.5 故障演练设计

防线装好了不等于防线有效——不演练，永远不知道熔断阈值设对没有、值班会不会用三板斧。借混沌工程的思路打自己的系统：

| 演练场景 | 注入方式 | 预期防线 | 验收标准 |
|---|---|---|---|
| 模型劣化 | 代理层随机返回低质回答/高延迟 | L3 抽检发现 + P1 告警 | 15 分钟内告警触发，值班按预案降级 |
| 工具故障 | 模拟检索工具返回乱码/超时 | L2 超时熔断 + 降级切备用源 | 任务成功率不跌破 P0 线 |
| 循环卡死 | 构造诱导循环的任务 | L2 步数熔断 + 成本熔断 | 单任务步数/成本不超上限 |
| 成本风暴 | 放大请求规模/长上下文请求 | L1 预算护栏 + 限流 | 账单增速被掐断，预算告警触发 |
| 注入攻击 | 重放 4.8 红队高危用例 | 输出检查 + 权限拦截 | 零打穿 |

演练节奏：新防线上线必演练一次；季度全场景轮训；每次真实故障的复盘转化为一个新的演练场景。演练结果写进预案——**预案的价值不在文档，在于值班照着做过。**

## 5. 架构 / 流程

四层防御与黄金信号、止损的关系：

```text
                  用户请求
                     ↓
┌──────────────────────────────────────┐
│ L1 输入护栏：校验 / 目标检查 / 预算    │ ← P3 预算水位告警
└──────────────────┬───────────────────┘
                   ↓
┌──────────────────────────────────────┐     黄金信号
│ Agent 执行（多步循环）                │     TTFT / token 分列
│ L2 熔断：步数 / 成本 / 循环检测 / 超时 │←── 单请求成本
└──────────────────┬───────────────────┘     缓存命中率
                   ↓                        任务成功率
┌──────────────────────────────────────┐
│ 输出 → L3 抽检（Judge 打分）→ 用户     │ ← 抽检分环比告警
└──────────────────┬───────────────────┘
                   ↓ 低分样本
┌──────────────────────────────────────┐
│ L4 trace 回放：分步录像 → 锁定环节     │
└──────────────────┬───────────────────┘
                   ↓
        止损三板斧：降级 / 限流 / 回滚
                   ↓
        复盘：trace 存回归用例 + 演练场景
```

一次软故障的标准处置流：

```text
发现（抽检分/成功率/成本越线）
  → 告警分级（P0/P1）
  → 抽最近 N 条低分请求回放 trace
  → 锁定环节（模型？检索？工具？流程？）
  → 止损（降级切备用 / 限流 / 回滚版本）
  → 验证恢复（抽检分回升、成功率回基线）
  → 复盘沉淀（trace 存回归用例，加依赖质量探测，转演练场景）
```

## 6. 代码 / 工具

### 6.1 质量抽检脚本

```python
# quality_sampler.py — L3 输出质量抽检：采样 → Judge 打分 → 趋势告警
import random
import statistics
from openai import OpenAI

client = OpenAI(api_key="YOUR_KEY")

RUBRIC = """你是质检员。根据「标准答案要点」给助手回答打 0-100 分。
要点覆盖不全扣分；编造要点外的事实直接低于 50 分。
只输出数字。

[用户问题] {query}
[助手回答] {answer}
[标准答案要点] {reference}
"""

def sample_recent_tasks(store, n: int = 30) -> list:
    """从任务日志随机抽 n 条：含 query、answer、reference、trace_id"""
    recent = store.fetch_last_hours(hours=1)
    return random.sample(recent, min(n, len(recent)))

def judge_score(query: str, answer: str, reference: str) -> int:
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user",
                   "content": RUBRIC.format(query=query, answer=answer,
                                            reference=reference)}],
        temperature=0,
    )
    try:
        return int(resp.choices[0].message.content.strip())
    except ValueError:
        return -1  # Judge 异常单独计数，不算入均分也不静默丢弃

def quality_check(store, baseline: float = 85.0, drop_alert: float = 10.0):
    tasks = sample_recent_tasks(store)
    scores = [judge_score(t["query"], t["answer"], t["reference"]) for t in tasks]
    valid = [s for s in scores if s >= 0]
    mean = statistics.mean(valid) if valid else 0.0
    low = [t for t, s in zip(tasks, scores) if 0 <= s < 60]

    report = {
        "window": "1h", "sampled": len(tasks),
        "mean_score": round(mean, 1),
        "low_score_ratio": round(len(low) / max(len(valid), 1), 3),
        "low_samples": [t["trace_id"] for t in low][:10],  # 供 L4 回放
    }
    # 绝对阈值 + 趋势双触发
    if mean < baseline - drop_alert:
        report["alert"] = f"P1 质量下滑：{mean} 低于基线 {baseline} 超 {drop_alert} 分"
    elif mean < baseline:
        report["alert"] = f"P2 质量观察：{mean} 低于基线，关注趋势"
    else:
        report["alert"] = None
    return report

if __name__ == "__main__":
    print(quality_check(store=TaskStore()))
    # 输出示例：{'mean_score': 71.3, 'alert': 'P1 质量下滑：71.3 低于基线 85 超 10 分',
    #            'low_samples': ['tr_881', 'tr_902', ...]}
```

低分样本的 trace_id 直接交给 L4 回放——发现与定位是同一条流水线。

### 6.2 黄金信号监控与告警脚本

```python
# golden_signals.py — 五个黄金信号采集 + 分级告警（可挂 cron 每分钟）
import time
import requests

WEBHOOK = "https://hooks.example.com/alert"   # 值班群机器人
THRESH = {
    "ttft_p95_ms":       {"warn": 3000,  "crit": 8000},
    "cost_per_task_usd": {"warn": 0.05,  "crit": 0.15},
    "cache_hit_rate":    {"warn": 0.60,  "crit": 0.40, "lt": True},
    "task_success_rate": {"warn": 0.75,  "crit": 0.60, "lt": True},
}

def fetch_metrics() -> dict:
    """从监控后端拉最近 5 分钟窗口指标；token 分列用于下钻，不做阈值"""
    m = requests.get("http://metrics.internal/agent/summary?window=5m").json()
    return {
        "ttft_p95_ms": m["ttft_p95_ms"],
        "cost_per_task_usd": m["cost_per_task"],
        "cache_hit_rate": m["cache_hit_rate"],
        "task_success_rate": m["task_success_rate"],
        "token_breakdown": m["token_by_stage"],   # {'input':…, 'output':…, 'tool':…}
    }

def classify(name: str, value: float) -> str:
    cfg = THRESH[name]
    if cfg.get("lt"):                       # 越低越坏的指标
        if value < cfg["crit"]: return "P0"
        if value < cfg["warn"]: return "P1"
    else:
        if value > cfg["crit"]: return "P0"
        if value > cfg["warn"]: return "P1"
    return "OK"

def alert(level: str, msg: str):
    requests.post(WEBHOOK, json={"level": level, "text": msg, "ts": time.time()})

def main():
    m = fetch_metrics()
    fired = []
    for name in THRESH:
        level = classify(name, m[name])
        if level in ("P0", "P1"):
            fired.append(f"{level} {name}={m[name]}")
    # 单请求成本翻倍单独升级：最灵敏的软故障探针
    if m["cost_per_task_usd"] > 2 * THRESH["cost_per_task_usd"]["warn"]:
        fired.append("P1 单请求成本超基线 2 倍，疑似循环卡死/缓存失效，"
                     f"token 分列={m['token_breakdown']}")
    if fired:
        alert("P0" if any(f.startswith("P0") for f in fired) else "P1",
              "；".join(fired))

if __name__ == "__main__":
    main()
```

token 分列不设阈值但要始终打印进告警正文——它是指挥值班去哪个环节下钻的第一线索。

### 6.3 执行层熔断与预算护栏

```python
# circuit_breaker.py — L2 熔断：Agent 主循环里的四道闸
class Budget:
    def __init__(self, max_steps=15, max_cost_usd=0.20, max_seconds=120):
        self.max_steps, self.max_cost_usd, self.max_seconds = (
            max_steps, max_cost_usd, max_seconds)
        self.steps, self.cost, self.t0 = 0, 0.0, time.time()
        self.recent_calls = []          # (tool, args_digest) 用于循环检测

    def check(self, tool: str, args_digest: str, call_cost_usd: float):
        if self.steps >= self.max_steps:
            raise BudgetExceeded(f"步数熔断：{self.steps} 步")
        if self.cost + call_cost_usd > self.max_cost_usd:
            raise BudgetExceeded(f"成本熔断：${self.cost:.2f}")
        if time.time() - self.t0 > self.max_seconds:
            raise BudgetExceeded("超时熔断")
        if self.recent_calls.count((tool, args_digest)) >= 3:
            raise BudgetExceeded(f"循环检测：{tool} 同参数重复调用超限")
        self.steps += 1
        self.cost += call_cost_usd
        self.recent_calls.append((tool, args_digest))

# Agent 主循环中每次调用工具前：budget.check(tool, digest, est_cost)
# 熔断触发后不静默失败：任务标记 status='halted'，trace 保留，进回放样本池
```

熔断的正确姿势是「留全尸」：被熔断的任务保留完整 trace 标记为 halted，它们正是回放定位与复盘的最好样本。

## 7. 案例

### 案例 A：检索依赖悄悄劣化

**场景**：某电商客服 Agent，抽检分长期 92。周一例会发现抽检分掉到 71，客服解决率同步下滑；接口零报错、无异常日志——典型软故障。

**定位**：取最近 50 条低分请求的 trace 回放：模型输出正常、流程正常，问题在第 2 步——检索工具返回内容变了。再 diff 两周前同请求的 trace：上游知识库换版后，旧字段还在、正文变成乱码摘要。故障点不在模型、在工具依赖；trace 分步记录让定位只花了 20 分钟。

**止损与恢复**：按预案把该检索源降级——切备用检索源 + 打开缓存兜底，同时限流防止低质结果继续外流，全程不动模型。回放验证抽检分回到 90+。复盘动作：该次 trace 存成回归用例；给上游知识库加内容质量探测告警——下次它再变劣，先于用户知道。

### 案例 B：成本曲线抓出循环卡死

**场景**：一家 SaaS 公司的运维看板上，单请求成本连续两天缓慢爬升，从 $0.03 到 $0.07，任务成功率反而正常——没人投诉。

**定位**：成本告警（P1）触发后下钻 token 分列：某类任务的 tool 调用 token 占比从 20% 涨到 65%。抽样回放 trace 发现：新接入的一个工具偶发返回空结果，Agent 的自纠错逻辑于是反复重试同一调用，最多 12 轮才罢休——任务最终成功（所以成功率正常），但每单烧掉 4 倍 token。

**止损**：给该工具的调用加「同参数重试上限 3 次，超限即降级到兜底路径」，并把重试计数接入循环检测。成本回到 $0.032。这个案例说明**成本指标常常比质量指标更早报警**：假成功骗过成功率，骗不过账单。

### 案例 C：发布回滚

**场景**：某金融科技公司给审核 Agent 发布新版 Prompt（评估门禁通过）。Canary 放量 10% 后 40 分钟，线上抽检分从 88 掉到 74，任务成功率掉 6 个点——版本相关的劣化。

**处置**：值班按预案直接回滚 Prompt 版本（配置回滚，2 分钟生效），指标 10 分钟内回基线。随后用 3.9 门禁的评估集复现：新版 Prompt 在一批「长合同」样本上漏审关键条款——评估集没覆盖这个分布。补样本、修 Prompt、重跑门禁，三天后再发布。

**复盘要点**：门禁过了不等于万无一失——门禁是抽样证明，Canary + 自动回滚是门禁的线上保险。回滚快的前提是版本化配置，以及值班演练过回滚动作。

## 8. 常见坑

1. **沿用「报错才告警」**。Agent 大多数坏事不报错，错误率长期是 0 给人虚假安全感。对策：围绕业务信号（抽检分、成功率、成本）建告警。
2. **只看平均不看分布**。平均延迟正常但 p95 爆炸；平均分掩盖一撮极差请求。对策：TTFT、抽检分都看 p95 与低分占比。
3. **没有步数/成本熔断**。循环卡死可以无限烧钱。对策：L2 四道闸（步数、成本、循环、超时）是底线配置。
4. **熔断了但静默丢弃**。被熔断任务消失得无影无踪，同类问题反复发生。对策：halted 状态 + trace 保留 + 进回放样本池。
5. **抽检无基线**。只有当次分数，没有环比趋势，慢病发现不了。对策：固定基线 + 滑窗趋势双触发。
6. **黄金信号不分环节**。只记总 token，循环卡死和提示词膨胀分不清。对策：token 按环节/工具分列上报。
7. **告警不分级**。所有告警一个音量，值班疲劳后全局静音。对策：P0-P3 分级 + 聚合静默。
8. **止损先查因**。根因要查，但先止损——用户在持续收到坏结果。对策：预案里写明三板斧的触发条件，值班照做。
9. **回滚回不来**。Prompt/配置没有版本化，想回滚只能现场改代码。对策：发布产物全部版本化，回滚是切配置不是发代码。
10. **降级路径没验证过**。备用模型/备用检索源平时不用，真用的时候发现早坏了。对策：降级路径纳入故障演练，定期真实切换。
11. **假成功计入成功率**。任务状态「完成」不等于结果正确，成功率虚高。对策：成功率口径混入抽检分修正，关键任务全检。
12. **trace 只记模型调用**。检索返回、工具出入参不记，回放到一半断片。对策：分步全量记录，特别是工具返回值——案例 A 的故障点就在那。
13. **防线装好不演练**。熔断阈值拍脑袋设的，值班没走过预案。对策：5 类演练场景轮训，真实故障转演练。
14. **只盯技术指标不盯钱**。成本异常是最早的软故障信号，却常被排除在监控外。对策：单请求成本 + 预算水位进告警体系。

## 9. 练习

1. 给你的 Agent 加一个 Budget 类，跑一个故意构造的循环任务，验证步数与成本熔断都触发。
2. 实现质量抽检脚本：抽 30 条、Judge 打分、输出均分与低分样本 trace_id。
3. 构造一个「工具返回悄悄劣化」的场景（把工具返回值替换成乱码），看你的抽检与告警多久发现。
4. 为你的 Agent 定义五个黄金信号的阈值与告警分级，写成配置并在告警脚本里生效。
5. 做一次降级演练：拔掉主检索源，验证备用源切换与恢复时间。
6. 用一条历史低分请求做 trace 回放，写清楚定位到哪一步、证据是什么。
7. 把你的 Prompt/配置接入版本化，演练一次 2 分钟内完成回滚。
8. 写一份 5 场景的故障演练计划（注入方式 + 预期防线 + 验收标准），跑通其中两个。

## 10. 小结

- Agent 线上故障多数是软故障：不报错但跑偏、卡死、质量劣化、假成功——比硬故障更常见也更难缠。
- 软故障的结构性根源：多步误差复利、LLM 失败不抛异常、依赖面大且会悄悄变劣。
- 四层防御：输入护栏（校验/预算）→ 执行熔断（步数/成本/循环/超时）→ 输出抽检（Judge + 趋势）→ trace 回放定位。
- 黄金信号五个：TTFT、token 分列消耗、单请求成本、缓存命中率、任务成功率；单请求成本常是最早报警的探针。
- 告警要分级（P0-P3）且阈值 + 趋势双触发，防告警风暴。
- 止损三板斧：降级、限流、回滚——先止血再查因；回滚的前提是版本化配置。
- trace 分步记录是定位底座：软故障靠回放定位，不靠猜。
- 熔断任务留 trace 标记 halted，它们是最好的回放与复盘样本。
- 防线要演练：模型劣化、工具故障、循环卡死、成本风暴、注入重放五类场景轮训。
- 门禁守上线前，抽检与 Canary 守上线后；上线前后是同一条护栏的两段。
- 一次完整的软故障处置（发现→回放→止损→复盘沉淀）就是 4.10 作品集里最硬的故事素材。
