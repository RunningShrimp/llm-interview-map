# 讲解 3.10 人机协同与反馈闭环

> 说明：3.4 可观测性与追踪记录了系统每一步行为，3.5 评估体系给出了质量分数；本篇把「人」放进流程——高风险动作挂起等人审批，人工修正过滤后流回评估集，让系统越用越好。  
> 权限模型决定「能不能做」在 3.8 展开；审批门、幂等与审计组合成完整企业方案在 4.5 工作流自动化 Agent；本篇闭环产出的回归集如何把关发布，回到 3.9 的 Eval Gate。

---

## 1. 定位

L3 工程化层第 10 个锚点，回答关键问题：**人在哪些节点介入最有效？**

前置依赖：

- 3.4 可观测性与追踪：审批单据里的上下文、事后抽检的抽样对象，都来自全链路轨迹。
- 3.5 评估体系与实验管理：人工确认的真坏例要进回归集才有意义，回流后的效果靠评估体系验证。

下游去向：

- 4.5 工作流自动化 Agent：审批门、幂等、审计三者组合成企业级自动化方案。
- 3.9 Eval Gate：反馈闭环的出口——确认的坏例变成回归集，下一轮门禁生效。

定位补充：这是**趋势性考点**。2026 年设计模式的资料已经成熟（审批工作流、反馈数据流），但专项面试题库仍在成形中——面试多以「你怎么设计人审节点」这类场景追问出现，考设计判断而非名词背诵。

## 2. 一句话定义

人机协同（HITL，Human-in-the-Loop）：按「风险 × 置信度」把人放进 Agent 流程的刀刃节点——高风险动作前挂起审批、低置信输出路由给人工、产出事后抽检；人的每一次修正与驳回都过滤确认为真坏例，回流成回归集与迭代依据，形成「越用越好」的反馈闭环。

## 3. 为什么需要

两个极端都不可行：

- **每步都人审**：系统退化成人力工具，成本爆炸，自动化收益归零。一个发票 Agent 每张发票都等人批，等于没有 Agent。
- **全自动驾驶**：一次不可逆事故（错付一笔 50 万、误发一封对外邮件）就毁掉用户信任，而信任重建的成本远高于事前拦截。

根本原因：Agent 的能力边界与错误代价分布不均匀。检索、摘要、分类出错可逆且代价低；对外发送、付款、删除出错不可逆且代价高。介入点必须跟着代价走，而不是均匀撒在流程里。

同时，人是最高质量的数据源。用户点「踩」、审批时的修改意见、标注员的质检结论，都是带真实分布的监督信号——不回流就是浪费，乱回流就是喂噪声。人机协同的完整命题是两件事：**介入点设计**（让人审在刀刃上）与**反馈闭环**（让人审产出变成系统能力）。

## 4. 核心原理

### 4.1 风险 × 置信度矩阵定介入点

介入点由两个变量共同决定：操作风险（出错代价 × 可逆性）与 Agent 置信度（模型自报置信 + 规则校验通过度 + 历史同类成功率）。

| 组合 | 典型场景 | 协同模式 | 理由 |
|---|---|---|---|
| 低风险 + 高置信 | 知识检索、摘要、分类、写日志 | 全自动执行 | 出错可逆，抽检兜底即可 |
| 低风险 + 低置信 | 冷门领域分类、模糊查询解析 | 自动执行 + 事后抽检 | 代价低，不值得实时打断 |
| 高风险 + 高置信 | 成熟供应商的小额付款、常规模板邮件 | 执行 + 事后抽检 | 信任由数据支撑，但保留抽检 |
| 高风险 + 低置信 | 首次合作供应商付款、大额操作、对外发送 | **挂起等人批** | 不可逆 + 不确定，必须人担责 |
| 新场景首跑 | 新上线工作流的前 N 单 | 强制人审 | 无历史数据支撑置信度 |

三个介入刀刃：**高影响动作**（不可逆、涉资金、对外）、**低置信输出**（模型自己不确定）、**新场景首跑**（无数据背书）。介入点不在多，在准。

落到工程上，两个变量都要可量化：

- **风险分级**：按出错代价（资金损失、法律责任、声誉伤害）与可逆性（能否撤销、能否补偿）打分，产出一张全动作清单的风险表——这张表本身就是设计文档，评审时逐行动过一遍。
- **置信度估计**：模型自报置信度往往校准很差（嘴上说 90%，实际对一半），要叠加程序侧信号——规则校验是否通过、检索命中的相关度分数、历史同类任务的成功率。三者加权比裸信自报可靠得多。
- **阈值随数据演化**：新场景首跑强制人审，积累 N 单全对之后才降级为抽检；反过来，抽检发现坏例率上升时立即升回强制人审。介入边界不是一次画死的，是被数据养出来的。

### 4.2 审批门三要素

审批门（Approval Gate）不是「发个消息等人点同意」，三个要素缺一不可：

| 要素 | 内容 | 缺失后果 |
|---|---|---|
| 带上下文 | 审批单据写清：改什么/做什么、金额与对象、影响谁、Agent 的依据与置信度、原文链接（轨迹见 3.4） | 审批人无据可判，只能盲批，审批门形同虚设 |
| 超时升级 | 超时未审批自动升级到上一级（如 24h 升财务主管），再超时走兜底 | 任务永远挂着，业务停滞且无人知晓 |
| 默认拒绝 | 最终超时未处理的动作默认拒绝执行（付款不付、邮件不发），宁可不办不可错办 | 默认放行 = 无人审批等于全自动，安全底线失守 |

原则一句话：**审批带上下文让人批得快，超时升级让流程不停摆，默认拒绝让底线不失守。**

两条配套纪律：

- **职责分离**：Agent 不能自审、发起人不能审批自己的单据、审批人不能是提单受益人——财务场景的合规硬要求，工程上就是审批人字段的校验规则。
- **审批也是留痕**：谁在什么时间基于什么单据批准了什么动作，全量入审计日志（对接 3.4 轨迹与 3.8 审计），复盘时能还原「当时 Agent 看到了什么、审批人看到了什么」。

### 4.3 反馈过滤回流

用户反馈是燃料，但不能直接倒进油箱。点「踩」的原因五花八门：答案对但用户没细看、答案对但不喜欢措辞、答案确实错了——不过滤直接微调，等于把噪声当信号，模型会学到错误模式，系统「越改越差」。

标准链路五段：

```text
用户反馈 / 人工修正
   → ① 沉淀：反馈结构化入库（对话 ID、轨迹、反馈类型、原文）
   → ② 过滤：标注员/规则确认真坏例（排除误点与偏好分歧）
   → ③ 入库：真坏例进回归集或微调数据（统一结构、去重、标注根因）
   → ④ 修正：改提示词 / 换检索 / 补数据（按持续学习三级选层级）
   → ⑤ 生效：下一轮评估门禁把关，达标才上线（接 3.9 Eval Gate）
```

关键在 ②：确认环节是质量闸门，宁可漏收不可错收——回归集里混进一条标注错误的样本，它会在每次发布时反复制造假回归。

过滤要识别三类「假坏例」：

1. **误点**：用户点错、手滑，反馈内容与对话内容对不上。
2. **偏好分歧**：答案事实正确，用户只是不喜欢措辞或详略——这类不进回归集，量大时可沉淀为风格偏好数据。
3. **需求误解**：用户的问题本身表述有歧义，模型按常见理解作答并没有错——这类改写成澄清题更有价值。

标注员的裁决动作是结构化的：是否真坏例（是/否）、根因归类（检索缺失/提示词缺陷/模型能力/数据过期）、建议去向（回归集/训练数据/丢弃）。裁决入 库后可统计标注员之间的分歧率，分歧率走高说明规范要修订。

### 4.4 标注即资产

人工修正与质检结论是最高质量的标注数据（真实分布 + 专家判断），要按资产管理：

- **统一结构存库**：每条标注含输入、模型输出、人工修正、根因分类（检索缺失/提示词缺陷/模型能力/数据过期）、标注人、时间。
- **标注规范文档化**：什么算坏例、根因怎么归类，写成规范并随案例更新，减少标注员之间的分歧。
- **定期复盘分歧案例**：标注不一致的地方往往正是规范模糊或模型边界不清的地方，每月复盘一次，分歧率是标注质量的量化指标。

标注工作流四步：抽样或全量领取 → 按规范逐条裁决 → 交叉抽检（10% 二人背对背标注，算一致率）→ 分歧案例进周会裁定并回写规范。没有交叉抽检的标注团队，无法回答「你的标签可信吗」这个问题。

这批资产的复利在 4.5 节展开：多数迭代根本不需要重训模型。

### 4.5 持续学习三级

拿到确认的真坏例后，按成本从低到高选层级：

| 层级 | 动作 | 周期 | 适用根因 | 占收益比 |
|---|---|---|---|---|
| 一级：提示词/知识库 | 改提示词、补 few-shot、更新文档与检索规则 | 天级 | 格式不稳、口径错误、知识缺失 | 大多数 |
| 二级：RAG 与小模型 | 换检索策略、加 Rerank、微调分类/路由小模型 | 周级 | 检索召回不足、意图分类边界不清 | 中等 |
| 三级：全量再训练 | 大模型领域微调 | 月级以上 | 系统性能力缺口，前两级确实验不动 | 极少数 |

工程纪律：绝大多数收益在前两级；动三级之前必须证明一、二级已到天花板，且重训后的版本照样要过 3.9 的评估门禁——「训练完成」不等于「可以上线」。

### 4.6 趋势口径

2026 现状的两句话总结：**设计模式已成熟，专项题库成形中。** 审批工作流、反馈数据流的工程资料已经充分（工作流平台、评估平台都有标准做法），但面试侧还没有像 RAG、ReAct 那样的固定题库——出题方式是场景追问：「你们的 Agent 哪些动作要人审？怎么定的线？反馈怎么用？」答好靠的是能画出自己项目的矩阵与链路，而不是背名词。

## 5. 架构 / 流程

审批门 + 反馈闭环的完整数据流：

```text
                ┌────────────────────────────────────┐
                │            Agent 执行流             │
                │                                    │
 用户任务 ──→ 规划/工具调用 ──→ 风险×置信度判定          │
                │        │                           │
                │   低风险高置信                       │
                │        ├──→ 自动执行 ──→ 产出        │
                │        │               │           │
                │   高风险/低置信          ▼           │
                │        ├──→ 审批门 ──→ 放行 ──→ 产出 │
                │        │      │                    │
                │        │   拒绝/超时 → 默认拒绝 → 终止
                │        │                           │
                │        └──→ 全程轨迹留痕（3.4）       │
                └────────────────────────────────────┘
                          │                │
              事后抽检样本 │                │ 用户反馈/审批驳回/人工修正
                          ▼                ▼
                ┌────────────────────────────────────┐
                │            反馈闭环流               │
                │  反馈沉淀 → 标注确认真坏例 → 结构化入库 │
                │      → 回归集 / 微调数据             │
                │      → 提示词/RAG/重训 三级修正       │
                │      → 评估门禁把关（3.9）→ 新版本上线 │
                └────────────────────────────────────┘
```

## 6. 代码 / 工具

### 6.1 审批工作流状态机

```python
# approval_gate.py —— 审批门状态机：上下文单据 + 超时升级 + 默认拒绝
import time, enum

class State(enum.Enum):
    PENDING = "pending"          # 等待审批
    ESCALATED = "escalated"      # 超时升级到上级
    APPROVED = "approved"        # 放行
    DENIED = "denied"            # 人工拒绝 / 超时默认拒绝

class ApprovalGate:
    def __init__(self, action, context, approver,
                 primary_timeout=86400, escalate_timeout=86400):
        self.action = action                    # 待执行的高风险动作
        self.context = context                  # 要素一：带上下文的审批单据
        self.approver = approver
        self.deadline = time.time() + primary_timeout
        self.escalate_deadline = None
        self.state = State.PENDING
        self.audit = []                         # 全程留痕（对接 3.8/3.4）

    def _log(self, event):
        self.audit.append({"t": time.time(), "state": self.state.value, "event": event})

    def submit(self):
        self._log(f"提交审批：{self.context['summary']}，审批人 {self.approver}")

    def decide(self, approver, approve: bool, comment=""):
        if self.state not in (State.PENDING, State.ESCALATED):
            raise RuntimeError("审批已关闭")
        self.state = State.APPROVED if approve else State.DENIED
        self._log(f"{'批准' if approve else '驳回'} by {approver}: {comment}")

    def tick(self):                             # 由后台定时任务驱动
        now = time.time()
        if self.state == State.PENDING and now > self.deadline:
            self.state = State.ESCALATED        # 要素二：超时升级
            self.escalate_deadline = now + 86400
            self._log("24h 未审批，升级至财务主管")
        elif self.state == State.ESCALATED and now > self.escalate_deadline:
            self.state = State.DENIED           # 要素三：默认拒绝，宁可不办不可错办
            self._log("48h 未处理，默认拒绝付款")

    def execute(self, runner):
        if self.state is not State.APPROVED:
            self._log("未获批准，动作不执行")
            return {"ok": False, "reason": self.state.value}
        self._log("执行动作")
        return runner(self.action)              # 审批通过才真正触达外部系统

# 用法：发票付款 Agent 的审批门
gate = ApprovalGate(
    action={"type": "pay_invoice", "id": "INV-2026-0918", "amount": 52000},
    context={"summary": "新供应商首笔付款 5.2 万元",
             "match": "三单匹配失败：PO 金额差 200 元",
             "confidence": 0.62, "trace_url": "https://obs/trace/abc"},
    approver="finance.l1",
)
gate.submit()
# ... 审批人裁决 gate.decide(...) 或超时后 gate.tick() 自动升级/拒绝
```

### 6.2 反馈过滤回流 pipeline

```python
# feedback_loop.py —— 反馈 → 确认真坏例 → 回归集 → 门禁生效
import json, hashlib

def ingest(raw_feedback, session):
    """① 沉淀：反馈结构化入库，带轨迹指针（3.4）"""
    return {
        "session_id": session["id"],
        "trace_url": session["trace_url"],
        "type": raw_feedback["kind"],        # thumbs_down / correction / rejection
        "user_comment": raw_feedback.get("comment", ""),
        "model_output": session["final_answer"],
        "status": "unreviewed",
    }

def confirm(sample, reviewer_verdict):
    """② 过滤：标注员裁决——只有确认真坏例才往下走，宁可漏收不可错收"""
    if not reviewer_verdict["is_real_badcase"]:
        sample["status"] = "discarded"       # 误点/偏好分歧：丢弃并留档
        return sample
    sample.update(status="confirmed",
                  root_cause=reviewer_verdict["root_cause"],  # 检索缺失/提示词缺陷/…
                  reviewer=reviewer_verdict["by"])
    return sample

def promote(sample, regression_set_path="data/regression_set.jsonl"):
    """③ 入库：去重后写入回归集（只增不减）"""
    key = hashlib.sha1(sample["user_comment"].encode()).hexdigest()[:12]
    existing = {json.loads(l)["dedup_key"] for l in open(regression_set_path)}
    if key in existing:
        return False
    with open(regression_set_path, "a") as f:
        f.write(json.dumps({**sample, "dedup_key": key}, ensure_ascii=False) + "\n")
    return True

# ④ 修正：按根因选持续学习层级——
#    检索缺失 → 补文档/调切分；提示词缺陷 → 改提示词；系统性缺口 → 才考虑微调
# ⑤ 生效：回归集并入下一轮 Eval Gate（3.9），分数达标才发布
```

## 7. 案例

### 案例 A：供应商发票审批 Agent

**场景**：一家制造企业的财务部门要上线「自动处理供应商发票并安排付款」的 Agent，日均 400 张发票。

**划线**（风险 × 置信度）：OCR 识别、三单匹配、金额一致性校验——规则清晰、可验证、出错可拦截，全自动；首合作供应商付款、超 5 万元付款、三单匹配失败或字段置信度低的单据——挂起人审，审批单据带发票影像、匹配结果、供应商资质。上线后约 88% 发票全自动通过，12% 进审批队列。

**兜底与闭环**：审批超时 24 小时升级财务主管，48 小时未处理默认拒绝付款——宁可不付，不可错付。审批人的每次驳回与修改结构化留痕；每周复盘发现「某类发票总被拒」的模式，回流成提取规则的修正，先小流量验证再全量。

**效果**：单张发票处理成本从 18 元降到 3 元，错误付款零发生，付款周期从 7 天缩到 2 天。

### 案例 B：客服 Agent 的分级介入

**场景**：某电商客服 Agent 初版对所有会话末尾都要求人工复核，20 名客服疲于奔命，复核形同点确认。

**改造**：按风险 × 置信度重新划线——退款政策问答、物流查询全自动；退款确认短信（涉及真实资金承诺）挂审批；分类置信度低于 0.7 的会话转人工；其余按 5% 随机抽检。

**效果**：人工介入率从 100% 降到 9%，转人工响应时间中位数从 11 分钟降到 40 秒；抽检发现的问题集中在知识库过期条目，成为回归集的重要来源。

### 案例 C：标注资产驱动迭代

**场景**：一家 SaaS 公司的工单 Agent，三个月积累了 1200 条用户点「踩」，此前从未使用。

**改造**：2 名标注员按规范过滤，确认 430 条真坏例，根因分布：检索缺失 52%、提示词缺陷 31%、模型能力不足 17%。按持续学习三级处理：补文档与调切分（一级）解决六成检索类坏例，改提示词（一级）解决格式与口径问题，仅意图路由（二级）微调了一个小模型。

**效果**：回归集从 200 条扩到 630 条，坏例复发率从 35% 降到 8%；没有动过大模型训练——印证「绝大多数收益在前两级」。

## 8. 常见坑

1. **每步都人审**。对策：按风险 × 置信度划线，只在高影响、低置信、新场景设门。
2. **全自动无抽检**。对策：低风险场景保留 5% 左右随机抽检，作为漂移探针。
3. **审批单据没有上下文**。对策：单据写清动作、对象、金额、依据、置信度与轨迹链接，让人批得快。
4. **审批无限期挂起**。对策：超时升级到上级，最终超时默认拒绝，流程不停摆。
5. **超时默认放行**。对策：默认拒绝是安全底线——无人审批等于没人担保，动作就不该发生。
6. **置信度只信模型自报**。对策：自报置信度校准差，用规则校验通过度与历史同类成功率加权。
7. **用户反馈直接拿去微调**。对策：先过滤确认真坏例——把噪声当信号，模型会越改越差。
8. **标注无规范、无存档**。对策：统一结构存库，根因分类，规范文档化。
9. **回归集只进不出且不复盘**。对策：定期复盘标注分歧与失效样本，分歧率是质量指标。
10. **一坏例就上重训**。对策：先走提示词与 RAG 两级，重训前必须证明前两级到顶。
11. **反馈闭环缺出口**。对策：回流数据必须接进评估门禁（3.9）才生效，否则只是存了个寂寞。
12. **审批记录与轨迹割裂**。对策：审批审计对接全链路 trace（3.4），复盘时能还原当时上下文。

## 9. 练习

1. 给自己项目的 Agent 动作清单逐项打分（出错代价、可逆性、置信度可得性），画出你的风险 × 置信度矩阵。
2. 实现一个简化审批状态机：PENDING → APPROVED/DENIED，含 24 小时升级与 48 小时默认拒绝，用单测覆盖全部转移。
3. 设计发票审批单据的 JSON Schema：动作、金额、匹配结果、置信度、轨迹链接、审批人与结论。
4. 收集 50 条真实（或模拟）用户反馈，写过滤规则与标注规范，统计真坏例比例与根因分布。
5. 把确认的坏例写成回归集条目，跑一次基线评估，观察哪些现有用例与它重叠。
6. 选一条真坏例，分别尝试一级（改提示词）与二级（改检索）两种修法，对比回归集分数变化。
7. 为「超时默认拒绝」写一条压力测试：模拟审批人 72 小时不响应，验证动作确实未触达外部系统。

## 10. 小结

- 人机协同的两个极端都不可行：**每步人审成本爆炸，全自动驾驶事故不可控**。
- 介入点 = **风险 × 置信度矩阵**：高影响动作、低置信输出、新场景首跑三个刀刃。
- 审批门三要素：**带上下文的单据、超时升级、默认拒绝**——批得快、不停摆、不失守。
- 判断依据是「出错代价 × 可逆性」：对外发送、付款、删除类必须人审；检索、摘要抽检兜底。
- 用户反馈不能直接用：**反馈 → 确认真坏例 → 回归集 → 门禁生效**，跳过过滤就是喂噪声。
- **标注即资产**：统一存库、规范文档化、定期复盘分歧，分歧率是质量指标。
- 持续学习三级：**提示词/知识库（天级）→ RAG/小模型（周级）→ 全量重训（月级以上）**，收益绝大多数在前两级。
- 审批记录要对接全链路轨迹，复盘时能还原「当时 Agent 看到了什么」。
- 趋势口径：**设计模式已成熟，专项题库成形中**——面试考场景设计判断，不考名词。
- 闭环的出口是 3.9 的 Eval Gate：反馈只有变成回归集并通过门禁，才算真正让系统越用越好。
