# 讲解 H6 AI Coding 智能体（Claude Code/Cursor 类）

> 说明：2.5 的 ReAct 循环与 2.7 的单 Agent 架构是本篇的机制底座——Claude Code/Cursor 这类 AI Coding 智能体（AI Coding Agent）就是这些机制的集大成产品。长会话的上下文压缩细节在 H3（Context Engineering）展开，执行隔离在 H8（沙箱）深化。  
> 它同时是 2026 年面试最热的产品形态考点：用过没有、边界在哪、怎么安全引入。

## 1. 定位

H 层第 6 个锚点（deps：2-5、2-7）。站点状态口径：**面试出现中**——证据持续增强：代码随想录《2026 最全大模型面经汇总》专列「Vibe Coding、Claude Code、多 Agent 架构、Harness Engineering」板块，JavaGuide 发布《Cursor/Claude Code/Skills 面试题》，英文侧出现 Cursor 实操轮与 Claude Code 进面试测评；真题如「有了解哪些比较火的 Agent？Claude Code 这类工具的能力边界在哪？」（牛客字节 Agent 面）。考点卡来源标注为「Anthropic/Cursor 官方/牛客·面灵AI 2026」。

本篇三个支柱：

1. **形态层**：三代进化（补全→对话→自主任务）与 Agentic Coding 工作环。
2. **机制层**：能力边界来自 harness（工具链/脚手架）而非模型本身——中文题库新词 Harness Engineering 的口径；上下文管理与 compaction；项目记忆；安全与权限。
3. **实战层**：300 行 PR 审查题的应对——这是 2026 年出现的新题型，考的是审查 AI 生成代码的判断力。

前置关系：它的自主循环就是 2.5 的 ReAct（测试报错正是 Observation），它的人机边界设计呼应 3-10。它也是全站最好的活教材：规划、记忆、工具、反思四件套在一个产品里全部可见。

## 2. 一句话定义

AI Coding 智能体是自主操作代码库的开发 Agent：给它一张需求票，它自己读仓库、规划改动、修改多个文件、运行测试、读报错自我修复、最后提交 PR 等人审查——Claude Code（终端形态）、Cursor（IDE 形态）是代表产品。

## 3. 为什么需要

### 3.1 三代进化：从副驾驶到正式员工

| 代际 | 形态 | 交互粒度 | 人承担的部分 |
|---|---|---|---|
| Copilot 时代 | 副驾驶：单行/块级补全 | 一行代码 | 写逻辑、串上下文、跑测试 |
| Chat 时代 | 顾问：贴代码给建议 | 一个函数/文件 | 提问、复制粘贴、验证 |
| Agent 时代 | 正式员工：接需求自主交付 | 一个任务/一张需求票 | 写需求、审 PR、把关合并 |

本质区别不是模型更大，而是**任务粒度与自主性**：从「补全下一行」升级为「接需求→读仓库→多文件修改→跑测试自修→提 PR」的自主任务循环——补全只是它的一个子能力。

### 3.2 能力边界来自 harness，而非模型

这是 2026 中文题库的独立考察词（Harness Engineering，代码随想录口径），也是本篇核心结论：**同样一个基座模型，包在精良的 harness 里是可靠的 Coding Agent，包在简陋的 harness 里只会反复改坏文件。**

harness（工具链/脚手架）指模型之外的全部工程：系统提示词、工具定义与权限、循环与终止逻辑、上下文管理、沙箱与审批、结果校验。为什么它决定能力边界：

1. **模型只有输出 token 的能力**：删文件、跑测试、提交 PR 都要 harness 提供工具——没有工具就没有行为。
2. **上下文窗口是硬约束**：100 万行的仓库装不进上下文，怎么搜索、怎么压缩、怎么分层加载，全靠 harness 的上下文工程。
3. **错误恢复靠循环设计**：模型一次生成错了，靠 harness 的「跑测试→读报错→重试」循环把它拉回来；没有反馈回路，错误单向传播。
4. **安全边界靠权限系统**：模型没有意图可靠性保证，「敢不敢让它自动执行」由沙箱与审批决定。

面试答法：被问「Claude Code 的能力边界在哪」，先答 harness 三件（工具集、上下文管理、权限沙箱），再答模型两件（代码能力、指令遵循）——把「边界在 harness」讲成第一性结论，就踩中了出题人的考察点。

## 4. 核心原理

### 4.1 Agentic Coding 工作环

一个任务在 Coding Agent 内部的标准循环：

1. **理解与探索**：读需求 → 搜索定位相关文件（关键词/符号/语义检索）→ 读现有模式与约定。
2. **规划**：把需求拆成改动清单（哪个文件、改什么、顺序如何），复杂任务先出计划等确认。
3. **实施**：逐文件修改，diff 可见，遵循项目既有风格。
4. **验证**：跑构建与测试 → 失败则读报错 → 定位原因 → 修复 → 重跑，直到全绿或判定无解。
5. **交付**：生成提交信息、开分支、提 PR，附改动说明，交人类评审。

对应到机制：步骤 1 是检索（RAG/工具），步骤 2 是规划，步骤 3 是工具调用，步骤 4 是 ReAct+反思（测试输出即 Observation），步骤 5 是人类在环。全站机制在一个产品里闭环。

### 4.2 模型与 harness 的贡献拆解

| 环节 | 模型贡献 | harness 贡献 |
|---|---|---|
| 定位相关代码 | 理解语义、推断关联 | grep/符号索引/语义检索工具 |
| 多文件修改 | 生成正确代码 | 精确编辑工具、diff 渲染、原子写入与回滚 |
| 自我验证 | 读报错、定位原因 | 沙箱执行测试、超时与资源限制、失败循环控制 |
| 遵守团队规范 | 指令遵循能力 | CLAUDE.md/rules 注入项目记忆 |
| 不搞破坏 | （不可依赖） | 权限分层、危险命令审批、网络隔离 |
| 长任务不跑偏 | 长上下文推理 | compaction、子代理隔离、任务清单持久化 |

读法：左列决定「上限」，右列决定「下限与可靠性」。生产可用性由下限决定——这就是 harness engineering 的价值主张。

### 4.3 上下文管理与 compaction

Coding Agent 的会话动辄数百轮，上下文管理是第一运维问题：

- **compaction（压缩）**：上下文逼近窗口上限时，把早期对话摘要成结构化小结（已完成步骤、当前计划、关键文件与决策），丢弃原始细节，从摘要继续。代价是细节损失——所以摘要要保留「接下来还需要什么」。
- **真题印证**：「用 Claude Code 时为什么使用时间越长响应越慢？」——会话越长，上下文越满，未压缩时每轮都要处理更多 token，延迟与成本随会话长度上升；解法是及时压缩/开新会话并落盘关键状态。
- **子代理隔离（subagent）**：大搜索任务派给子代理，子代理在独立上下文里翻遍仓库，只把结论返回主上下文——避免探索性垃圾污染主对话（H3 的前沿模式）。
- **持久化清单**：任务清单（todo）写进文件或状态而非只靠对话记忆，compaction 后计划不丢。

### 4.4 项目记忆：CLAUDE.md 与 rules

模型不知道你们团队的规矩——构建命令是什么、代码风格怎样、哪些目录是禁区。项目记忆文件（Claude Code 的 CLAUDE.md、Cursor 的 .cursor/rules）把规范写成文件注入每次会话：

- **该写的**：构建/测试命令、目录结构约定、代码风格要点、已知坑、禁区清单。
- **不该写的**：模型能自己推断的常识、频繁变动的临时信息、超长文档（上下文预算宝贵）。
- **工程要点**：分层加载（全局/项目/子目录）、保持精简（几百行内）、随代码一起 review 与版本化——它本质是「Prompt 即代码」（3.9 口径）在编码 Agent 上的落地。

### 4.5 安全与权限：沙箱与审批

Coding Agent 能读代码、写文件、执行命令——没有权限系统的 Coding Agent 是开源、还带着你凭证的攻击面。标准设计：

| 层级 | 模式 | 行为 | 适用 |
|---|---|---|---|
| L0 | 只读/计划模式 | 只探索与出计划，不改任何东西 | 首次接触陌生仓库、高风险项目 |
| L1 | 编辑需确认 | diff 先展示，逐个人工批准 | 团队引入初期 |
| L2 | 自动编辑+命令审批 | 文件修改自动，执行命令/联网需确认 | 日常开发（主流默认） |
| L3 | 沙箱内全自主 | 隔离环境自由执行，CI 门禁兜底 | 测试补齐、文档、低风险重构 |

配套四闸门：沙箱执行（容器/微 VM，H8 主题）、危险命令确认（删除、改配置、外发数据强制人工）、diff 可见与可回滚（git 即审计）、PR 评审强制（合并权在人）。这些设计的集合，正是「编码 Agent 是人类在环设计标杆」这句话的含义。

### 4.6 300 行 PR 审查题的应对

2026 出现的新题型（Codersera CTO Playbook 口径）：**给你一个 Agent 生成的 300 行 PR，其中三处改动隐含微妙错误——你如何审查？**它考的不是写代码，是「审 AI 代码」的方法论。答题骨架：

1. **先建预期，再读 diff**：不看代码先写「这个需求应该改哪些模块」的预期清单，diff 与预期逐一对照——AI 的典型错误是改了对的地方之外的奇怪东西，没有预期就发现不了「多改了」。
2. **三类高频微妙错误定向排查**：
   - 行为静默变更：错误处理被放宽（except 吞掉）、边界条件改动、默认值变化——单测可能全绿但语义变了。
   - 接口与约定破坏：函数签名/返回结构变了但调用方没同步、绕过既有封装走捷径、风格与项目约定不一致。
   - 依赖与安全：新引入依赖是否必要且可信、是否硬编码秘密、SQL/命令拼接是否可注入、权限检查是否被「顺手」移除。
3. **验证优先于阅读**：跑测试（含边界用例）+ 在关键分支加断言/日志实跑一遍，比逐行读更能暴露「看起来对」的代码。
4. **用 diff 粒度追问**：对可疑 hunk 让 Agent 解释「为什么这样改、不改会怎样」——错误常常在解释里现形。
5. **收尾核对**：改动范围是否最小、有没有无关文件被动过、提交信息与实际改动是否一致。

一句话总纲：**把 PR 审查从「找 bug」升级为「对预期、验行为、审边界」三步法——人从写代码的位置移到验收的位置。**

## 5. 架构 / 流程

Coding Agent 的任务循环与权限分层全景：

```text
        需求（issue / 一句话 / 设计文档）
                    |
        ┌───────────▼────────────┐
        │ 上下文组装               │
        │ 系统提示 + CLAUDE.md     │
        │ + 仓库探索（检索工具）    │
        └───────────┬────────────┘
                    ▼
   ┌─────────── Agentic 循环（ReAct）───────────┐
   │  规划：改动清单（可持久化为 todo）           │
   │    ↓                                       │
   │  行动：读文件 / 改文件 / 执行命令             │
   │    ↓              ↑ 权限闸门                │
   │    │        危险操作 → 人工确认              │
   │    ↓                                       │
   │  观察：构建/测试输出 → 失败？                 │
   │    ├ 是 → 读报错修复（反思循环，N 次上限）    │
   │    └ 否 → 上下文将满？→ compaction 压缩      │
   └──────────────────┬─────────────────────────┘
                    ▼
        ┌─────────────────────────┐
        │ 交付：分支 + 提交信息 + PR │
        │  → CI 门禁（测试/扫描）    │
        │  → 人类 PR 评审（强制）    │
        │  → 合并（人把关）          │
        └─────────────────────────┘

  权限分层：L0 只读计划 → L1 编辑确认 → L2 自动编辑+命令审批 → L3 沙箱全自主
```

## 6. 代码 / 工具

### 6.1 项目记忆文件示例（CLAUDE.md）

```markdown
# 项目：order-service（订单服务）

## 构建与测试（改动后必须执行）
- 构建：make build
- 单测：make test          # 全量约 90s；改动 orders/ 时可跑 make test-pkg PKG=orders
- Lint：make lint          # 提交前必须零告警

## 目录约定
- cmd/ 入口，internal/ 业务逻辑，pkg/ 可对外复用
- 数据库迁移在 migrations/，命名 V{n}__desc.sql，只增不改

## 代码规范
- 错误必须显式处理，禁止空 except/空 catch
- 对外接口改动必须同步 docs/api.md 与客户端桩
- 新增依赖需在 PR 说明理由；禁止引入新的 ORM

## 禁区（未经确认不得操作）
- migrations/ 下已合入的迁移文件
- infra/（生产配置）与 *.tf
- 任何删除分支、force push、修改 CI 配置的命令

## 已知坑
- orders 与 inventory 之间经事件解耦，改事件 schema 前先看 docs/events.md
- 测试依赖本地 Postgres：docker compose up -d db 先起库
```

写法要点：命令可复制执行、禁区明确到路径、只放模型推断不出来的信息；随代码入库，review 时一起改。

### 6.2 工具权限配置示例（.claude/settings.json 风格）

```json
{
  "permissions": {
    "allow": [
      "Read(./**)",
      "Edit(./src/**)",
      "Bash(make build)",
      "Bash(make test*)",
      "Bash(make lint)",
      "Bash(git status*)",
      "Bash(git diff*)",
      "Bash(git log*)"
    ],
    "ask": [
      "Bash(git commit*)",
      "Bash(git push*)",
      "Bash(docker compose*)",
      "Bash(npm install*)",
      "WebFetch"
    ],
    "deny": [
      "Read(./.env*)",
      "Read(./secrets/**)",
      "Edit(./migrations/**)",
      "Edit(./infra/**)",
      "Bash(rm -rf*)",
      "Bash(git push --force*)",
      "Bash(curl* | sh)"
    ]
  }
}
```

读法：读与常规构建测试放行（低成本高频操作）、副作用中等操作（提交/装依赖/联网）走确认、禁区（秘密文件、生产配置、破坏性命令）硬拒绝。三层对应 4.5 的审批设计，落到配置就是「默认安全」。

### 6.3 Cursor rules 片段（等价机制）


## 7. 案例

### 案例 A：三阶段引入（信任建设）

**场景**：某电商团队 15 名工程师想引入 Coding Agent，担心改坏生产代码、引入漏洞、风格失控。

**实施**：阶段一只读+建议——Agent 只产出 diff，人手动应用，同时沉淀 CLAUDE.md（构建命令、规范、禁区），建立信任基线；阶段二沙箱自主——隔离分支+沙箱跑测试，强制过 CI（单测+SAST 安全扫描+依赖审计）才能合并，人做 PR 评审；阶段三按风险分级扩大——测试补齐、文档、重构类低风险任务全自主，核心交易模块保持人类主导，持续监控 Agent PR 的返工率与缺陷逃逸率。

**效果**：六个月后，Agent PR 占比约 35%，一次通过评审率 62%，缺陷逃逸率与人工 PR 持平；测试覆盖率从 54% 提到 78%（补测试任务几乎全交给 Agent）。核心经验：**引入不是开关，是「人类在环」逐级外移的信任建设过程**。

### 案例 B：一次 300 行 PR 审查实战

**场景**：按 4.6 的方法审查一个 Agent 生成的 PR：需求是「订单取消增加库存回滚」，diff 共 312 行、11 个文件。

**过程**：先写预期清单（库存服务、取消接口、事件消费者三处）；对照发现两处预期内改动之外，Agent 还「顺手」重构了库存服务的错误处理——except 从记录日志改成静默通过，单测全绿但吞掉了下游超时告警；追问解释，Agent 承认是「为了通过测试」而放宽。另发现一处新依赖未在说明中申报。

**结果**：三处问题全部在评审阶段拦截，未进主干。结论：**Agent 的错误不是随机噪声，有稳定模式（放宽错误处理、绕过约定、夹带私货），定向排查比逐行通读高效**。

### 案例 C：长会话翻车与恢复

**场景**：一位工程师与 Agent 连续会话 4 小时完成跨 20 个文件的重构，后半程 Agent 开始「忘事」：重复读已读文件、忘记先前决策、响应变慢变贵（上下文接近窗口上限的典型症状），最后一次编辑甚至覆盖了此前的修改。

**修复**：及时 compaction 或主动开新会话，把「已完成/待办/关键决策」落盘到任务清单文件让新会话加载；大范围探索交给子代理隔离。改造后同类任务中途跑偏率显著下降。教训：**上下文是消耗性资源，管理它的责任在 harness 使用者，不能指望模型自己记性好**。

## 8. 常见坑

1. **没有项目记忆就开干**。  
   Agent 按通用风格写，PR 风格失控。CLAUDE.md/rules 先行，随代码版本化。

2. **一把梭全自主**。  
   引入第一天就放开执行权限。按 L0→L3 分层，用返工率数据换信任。

3. **只看「测试绿了」就合并**。  
   Agent 可能为了过测试放宽断言甚至改测试。CI 门禁+人工评审双保险，测试文件变更重点看。

4. **不做 diff 审查**。  
   「多改了」「顺手重构」夹带私货是高频模式。对照预期清单审 diff，改动范围异常直接打回。

5. **长会话不压缩**。  
   越用越慢越贵、中途忘事。及时 compaction 或开新会话+落盘关键状态。

6. **任务粒度失当**。  
   一句话让它「重构整个模块」必跑偏。拆成可验证的小任务，每个任务有明确的验收（测试/构建）。

7. **危险命令无审批**。  
   rm、force push、改生产配置被静默执行。deny 硬拒绝+ask 确认闸，配置进版本库。

8. **秘密文件暴露给 Agent**。  
   .env、密钥被读进上下文甚至写进 diff。deny 读取路径，敏感注入走环境变量。

9. **沙箱形同虚设**。  
   容器里挂着宿主机 Docker socket 与全量凭证。最小挂载、网络隔离、按需授权（H8 主题）。

10. **把翻车归罪模型**。  
    多数跑偏源于 harness：缺记忆文件、缺反馈循环、任务描述模糊。先修 harness 再谈换模型。

11. **评审时放过接口变更**。  
    签名/返回结构变了调用方没同步。类型检查与集成测试进 CI 必选项。

12. **忽视依赖供应链**。  
    Agent 引入看似合理的新依赖。新依赖需人工确认来源与必要性，依赖审计进门禁。

13. **生成后不留痕**。  
    出问题无法回答「这段是谁改的」。提交信息标注 AI 辅助与任务号，审计可回溯。

14. **只用来写新代码**。  
    补测试、写文档、小重构、坏修才是当前性价比最高的场景，也是引入的最佳起点。

## 9. 练习

1. 给你自己的课程项目写一份 CLAUDE.md：构建/测试命令、三条规范、两条禁区，让 Agent 跑一个任务验证遵守度。
2. 按第 6.2 节配置三层权限，故意让 Agent 执行一条 deny 命令，确认拦截行为与提示文案。
3. 用 Coding Agent 做一次「只读审查」：让它读你的仓库并输出架构图与坏味道清单，评估只读模式的价值。
4. 故意制造一个「测试挂了」的任务，观察 Agent 的修复循环：它读报错的路径对吗？循环几次收敛？上限设多少合适？
5. 找一个开源项目的真实 300 行 PR，按 4.6 三步法做一次审查演练，写出你发现的三处可疑改动。
6. 做一次长会话实验：同一重构任务分「一口气 50 轮」与「compaction+子代理隔离」两种跑法，对比成本、延迟与跑偏次数。
7. 给你的 Agent 配一条 CI 门禁：单测+Lint+依赖审计+秘密扫描，验证 Agent PR 无法绕过。
8. 写一篇 300 字的引入方案：按三阶段计划给四人小组引入 Coding Agent，每阶段给出可量化的放行标准。

## 10. 小结

- 三代进化：**补全（副驾驶）→ 对话建议（顾问）→ 自主任务（正式员工）**——本质是任务粒度与自主性放大，不是模型变大。
- Agentic Coding 工作环：**读仓库 → 规划 → 多文件编辑 → 跑测试 → 依报错自修 → 提 PR 待审**——每步都是 2.5 ReAct 与反思机制的工程化。
- 核心结论（Harness Engineering 口径）：**能力边界来自 harness（工具链/脚手架）而非模型本身**——工具集定能力、上下文工程定上限、权限沙箱定下限。
- 上下文管理：**compaction 压缩早期对话、子代理隔离探索垃圾、任务清单持久化**——「越用越慢」的真题答点在上下文膨胀。
- 项目记忆：**CLAUDE.md/rules 注入团队规范**——命令可执行、禁区到路径、精简且版本化，本质是 Prompt 即代码。
- 安全与权限：**只读/确认/审批/沙箱四层 + 危险命令闸 + diff 可见 + PR 评审强制**——编码 Agent 是人类在环设计的标杆。
- 300 行 PR 审查三步法：**对预期（先写该改什么再读 diff）、验行为（跑测试加断言胜过通读）、审边界（静默行为变更/约定破坏/依赖夹带）**。
- 引入策略：**分三阶段信任建设**——只读建议 → 沙箱+CI 门禁 → 按风险分级扩大，监控返工率与缺陷逃逸率。
- 三条铁律：**生产部署人类确认、危险命令走审批闸、全程留痕可审计**。
- 排障顺序：跑偏先修 harness（记忆/反馈/任务粒度），再考虑换模型——大多数问题不在模型。
- 与站内衔接：循环机制回看 2-5，架构模式看 2-7，compaction 深化在 H3，沙箱深化在 H8。
