# 讲解 4.1 单 Agent 原型

> 说明：前置是 1 层（LLM 应用层，1.1-1.7）与 2.1-2.3（Agent 定义、规划、工具使用）；阅读顺序上 3 层工程化（3.1-3.10）在前，但动手的最小前置只到 2.3。  
> 本篇聚焦「最小可用闭环」：从约 40 行的 v0 最小 Agent 写起，逐步加工具注册表（Tool Registry）、记忆、轨迹（Trajectory）与评估集（Eval Set），长成可调试、可扩展的单 Agent 原型。  
> 同一副骨架由 4.2-4.10 实战系列逐场景加固，最终汇入 4.10 作品集与复盘。

---

## 1. 定位

实战层第 1 个知识点，属于「从知识到能力的第一次落地」。  
它解决一个核心问题：**学了这么多概念，如何真正动手做出一个能用的 Agent？**

浓缩版回答：**最小可用 Agent = LLM + 工具 + 循环 + 终止条件 + 输出**，要素清单与边界见 4.1 小节的正面展开。

本篇产出的原型是 4.2-4.10 全部实战项目的公共骨架，也是 5.3 阶段实操的落点。直接前置：1 层（LLM API、提示词、工具调用、记忆、评估）与 2.1-2.3（定义、规划、工具）；循环细节回查 2.5，记忆细节回查 2.4。

## 2. 一句话定义

单 Agent 原型，是一个具备「目标理解 → 规划 → 工具调用（Tool Calling）→ 记忆（Memory）→ 循环（Loop）→ 输出」完整闭环，代码结构清晰、可调试、可扩展的最小可用 Agent 系统。

简化公式（两级）：

```text
最小可用 Agent = LLM + 工具 + 循环 + 终止条件 + 输出
单 Agent 原型  = 最小可用 Agent + 记忆 + 轨迹日志 + 评估集
```

## 3. 为什么需要

不亲自动手，知识永远是别人的：

- **概念懂了，代码写不出** → 能复述 ReAct（Reason + Act）的 Thought-Action-Observation，落不到一个 while 循环。
- **组件孤立** → 工具、记忆、循环单独都懂，不知道怎么组装进同一个进程。
- **踩不到真坑** → 工具返回 error 时该重试、回传还是熔断，只有写过才知道。
- **无法评估** → 没有可运行的系统，就没有可对照的评估集，好坏全凭感觉。
- **无法演进** → 没有最小闭环，每次改动都是推倒重来。

只读不写与亲手做原型，差别落在每一行：

| 维度 | 只读文档 | 亲手做原型 |
|---|---|---|
| 工具调用失败 | 背「要有错误处理」 | 现场决定：重试、把错误回传模型、还是熔断 |
| 记忆窗口截断 | 知道「滑动窗口」这个词 | 亲测截断后第三轮的指代会不会断 |
| 面试讲项目 | 复述别人的架构 | 拿自己的轨迹和评估数字讲取舍 |
| 迭代速度 | 改不动，越读越焦虑 | 加一个工具十分钟见效 |

**类比 1（学技能）**：学游泳——看一百个教学视频也学不会换气，呛两次水就会了；学 Agent 同理，工具失败的边界处理读文档学不会，写一个原型踩一次坑就懂了。

**类比 2（小步快跑）**：开餐馆——先支一个档口只卖一道招牌菜（v0），卖得动再加两道菜（v1），再加会员卡和流水账（v2）；一上来就装修旗舰店、印二十页菜单，大概率撑不到开业。入门就做「通用助手」，就是那家旗舰店。

## 4. 核心原理

### 4.1 最小可用 Agent 长什么样（关键问题的正面回答）

必须有，且只需有五个要素：

| 要素 | 作用 | 缺了会怎样 | 本篇代码落点 |
|---|---|---|---|
| LLM（大脑） | 决策下一步做什么 | 沦为写死分支的脚本 | v0 的 chat 调用 |
| 工具（手脚） | 触达模型外的真实数据 | 只能靠参数内知识编答案 | v0 的 get_order |
| 循环（Loop，推进） | 把「决策-行动-观察」串成多步 | 一次问答，多步任务必挂 | v0 的 for 循环 |
| 终止条件（刹车） | 知道何时停 | 死循环烧钱、撑爆上下文 | v0 的 5 步上限 + 无工具调用即停 |
| 输出（交付） | 给用户可读结果 | 轨迹一堆，用户拿不到答案 | 返回最终回复 |

以下都不是第一天的必需品：

- 多 Agent：通信与协调成本高，何时值得见 4.6。
- 复杂规划器：Plan-Execute（先规划后执行）是 2.2 的进阶形态，最小原型用 ReAct 式单循环足够。
- 数据库/向量库：内存字典即可起步，知识库场景见 4.2。
- 编排框架：LangGraph 等见 3.3；先手写循环再上框架，才知道框架替你做了什么。
- 生产部署与全链路可观测：见 4.7 与 3.4。
- 权限、审批与沙箱：见 3.8，出现高危操作再加。

用三档水位对齐预期：

| 维度 | 玩具级（脚本 Demo） | 原型级（本篇目标） | 生产级（见 4.7） |
|---|---|---|---|
| 代码组织 | 单文件、过程式 | 分层模块、组件可替换 | 服务化、多租户 |
| 工具 | 1 个、参数不校验 | 2-3 个、Pydantic 参数校验 | 权限、审批、沙箱 |
| 循环与终止 | 无上限，能跑就行 | 最大步数 + 超时熔断 | 预算 + 循环检测 + 降级 |
| 记忆 | 无，或全量拼接 | 滑动窗口（Sliding Window）+ 工作记忆 | 分层记忆 + 持久化 |
| 日志 | print | 结构化 JSON + 轨迹 | 全链路追踪（见 3.4） |
| 评估 | 目测 | 10 条左右评估集 + 指标 | 离线回归 + 在线监控 |
| 价值 | 验证 API 通不通 | 验证闭环与选型 | 承接真实流量 |

**面试高频问法**：「Chatbot、Workflow 和 Agent 有什么区别？给 Chatbot 加上插件是不是就变成 Agent 了？」共识口径：判据是**下一步是否由模型自己决定**——Chatbot 从输入到输出一次成型；Workflow 的分支由代码写死；Agent 在循环中由模型自主选工具、看结果、决定继续还是停止。加插件只给了「手脚」，没有「模型自主决策的循环」，就还不是 Agent（范式辨析见 2.1）。

### 4.2 原型的目标边界

**要做**：

- 完整闭环：目标 → 规划 → 执行 → 输出
- 工具调用：至少 2-3 个工具
- 记忆：短期 + 工作记忆
- 循环：ReAct 或 Plan-Execute
- 日志：每步可追踪
- 评估：至少 10 条评估集

**不做**：

- 不做多 Agent
- 不做生产级部署
- 不做复杂权限
- 不做高并发
- 不做完整可观测性

**原则**：

> **先跑通，再优化。先单 Agent，再多 Agent。先原型，后工程化。**

### 4.3 迭代路线：v0 → v1 → v2

「可跟着做」的关键是小步交付，每步有验收标准：

| 版本 | 增量 | 交付物 | 验收标准 |
|---|---|---|---|
| v0 最小版 | LLM + 1 个工具 + 循环 + 终止 | 单文件约 40 行 | 问「订单 12345 发货了吗」答对，步数不超过 5 |
| v1 加工具 | 工具注册表（Registry）+ 2 个工具 + 参数校验 | registry + order 模块 | 故意传错参数不崩溃，错误能转述给用户 |
| v2 加控制 | 记忆 + 轨迹 + 日志 + 熔断 + 评估 | memory / agent / logger / eval | 10 条评估集跑出三个指标 |

v0 停在玩具级，v1、v2 把它抬到原型级；生产级的完整清单见 4.7 与 3.6。

### 4.4 项目选题

选一个**真实、有边界、可验证**的任务：

| 选题 | 工具 | 难度 | 适合阶段 |
|---|---|---|---|
| 天气查询助手 | 天气 API | 低 | 入门练手首选 |
| 订单查询助手 | 数据库 | 低到中 | 入门推荐（本篇主线） |
| 知识库问答 | 向量库 | 中 | 推荐（衔接 4.2） |
| 数据分析助手 | Python 沙箱 | 中到高 | 进阶（衔接 4.3） |
| 代码助手 | 代码执行 | 中到高 | 进阶 |
| 网页操作助手 | 浏览器 | 高 | 挑战（衔接 4.4） |

**本篇推荐选题：订单查询助手**。理由：

- 有明确工具：查订单、查物流、查商品
- 有记忆需求：用户 ID、历史查询
- 有评估标准：是否查到正确订单
- 不涉及高风险操作，失败也无代价

### 4.5 三个关键机制

**机制 1：工具靠描述被选中**。每个工具暴露给模型的只有三件套：name、description、parameters（JSON Schema）。模型不执行代码，只读描述做选择——描述含糊，选择必错。这是 2.3 的结论在本篇的直接体现：工具描述是写给模型看的接口文档，不是写给人看的注释。

**机制 2：终止有两条路**。自然终止：模型判断信息够了，不再发起工具调用，直接给出答案。熔断终止：达到最大步数或超时，强制收尾并返回部分结果。两条都必须有——只有自然终止，遇到「固执」的模型就死循环；只有熔断，正常任务也会被硬生生截断。终止条件的系统设计见 2.5。

**机制 3：错误当作观察结果回传**。工具失败不抛异常终止整个 Agent，而是把 `{"success": false, "error": ...}` 作为工具消息回传，让模型自己决定重试、换工具还是告知用户。错误不回传，模型永远不知道自己错了。错误分类与自我修正见 2.6。

**面试高频问法**：「手写一个最小可用 Agent，循环里必须处理什么？」共识口径至少五件事：解析工具调用、参数校验、工具错误作为观察结果回传、终止条件（模型不再调用工具 + 步数熔断）、轨迹记录。本篇 v0 覆盖前四件，v2 补齐轨迹。

### 4.6 评估集设计

评估集按三类用例配平：

| 用例类型 | 验证什么 | 示例 |
|---|---|---|
| 正常路径 | 主链路选对工具、答对信息 | 「帮我查一下我的订单」→ search_orders |
| 边界 | 参数筛选、多轮指代 | 「我有哪些已发货的订单」→ 带状态筛选 |
| 失败 | 错误处理不编造 | 「订单 99999 在哪」→ 应回答不存在 |

三个基础指标：**工具准确率**（该调的工具调没调）、**答案准确率**（关键信息是否出现在回复里）、**平均步数**（效率与成本的代理指标）。系统化的评估体系见 3.5，Agent 专项评估与安全见 2.9。

### 6.2 v0：约 40 行的最小可用 Agent

先装依赖、配密钥（v0 只需要 openai 一个包）：

```bash
pip install openai
export OPENAI_API_KEY=<你的密钥>   # 或写入 .env 后用 python-dotenv 加载
```

完整代码（`v0_min_agent.py`，故意用同步客户端，把行数压到最少）：

```python
import json
from openai import OpenAI

client = OpenAI()  # 密钥从环境变量读取

# 工具：一个普通 Python 函数 + 一份给模型看的描述
def get_order(order_id: str) -> dict:
    orders = {"12345": {"id": "12345", "status": "shipped", "amount": 299.0}}
    return orders.get(order_id, {"error": f"订单 {order_id} 不存在"})

TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_order",
        "description": "根据订单 ID 查询订单详情",
        "parameters": {
            "type": "object",
            "properties": {"order_id": {"type": "string", "description": "订单 ID"}},
            "required": ["order_id"],
        },
    },
}]

def run(user_input: str) -> str:
    messages = [
        {"role": "system", "content": "你是订单助手，只根据工具返回的数据回答。"},
        {"role": "user", "content": user_input},
    ]
    for step in range(5):                      # 终止 1：最大步数熔断
        msg = client.chat.completions.create(
            model="gpt-4o-mini",               # 示例值，替换为所用厂商的模型名
            messages=messages,
            tools=TOOLS,
        ).choices[0].message
        if not msg.tool_calls:                 # 终止 2：模型不再调用工具，自然终止
            return msg.content
        messages.append(msg)
        for tc in msg.tool_calls:
            args = json.loads(tc.function.arguments)
            result = get_order(**args)         # 错误也作为观察结果回传，不抛异常
            messages.append({
                "role": "tool",
                "tool_call_id": tc.id,
                "content": json.dumps(result, ensure_ascii=False),
            })
    return "已达最大步数，任务终止。"

if __name__ == "__main__":
    print(run("订单 12345 发货了吗？"))
```

截至 2026 年，主流厂商的对话补全类接口（OpenAI、Anthropic 等）均原生支持工具调用，换厂商只改 client 构造与 model 两处。LLM、工具、循环、终止、输出五要素各就各位——这就是最小可用 Agent。

### 6.3 v1：工具注册表与参数校验

v0 的两个问题：工具写死在循环里，加第二个工具就要改主流程；参数不校验，模型传错类型直接崩。v1 引入注册表（Registry）与 Pydantic 校验。

配置（`src/config.py`）：

```python
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env")

    openai_api_key: str
    model: str = "gpt-4o-mini"    # 示例值，以 .env 配置为准
    temperature: float = 0.0      # Agent 决策要稳定，固定低温
    max_steps: int = 10           # 步数熔断
    timeout: int = 60             # 单次 LLM 调用超时（秒）

settings = Settings()
```

LLM 客户端（`src/llm.py`）：

```python
from openai import AsyncOpenAI
from config import settings

client = AsyncOpenAI(api_key=settings.openai_api_key)

async def chat(messages: list[dict], tools: list[dict] = None) -> dict:
    response = await client.chat.completions.create(
        model=settings.model,
        messages=messages,
        tools=tools,
        temperature=settings.temperature,
    )
    return response.choices[0].message
```

工具注册表（`src/tools/registry.py`）：工具 = 名称 + 描述 + 函数 + 参数模型，四件套缺一不可：

```python
from pydantic import BaseModel
from typing import Callable

class Tool:
    def __init__(self, name: str, description: str, func: Callable, args_model: type[BaseModel]):
        self.name = name
        self.description = description
        self.func = func
        self.args_model = args_model

    def to_schema(self) -> dict:
        # 暴露给模型的三件套：name / description / parameters
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": self.args_model.model_json_schema(),
            },
        }

class ToolRegistry:
    def __init__(self):
        self.tools = {}

    def register(self, tool: Tool):
        self.tools[tool.name] = tool

    def get_schemas(self) -> list[dict]:
        return [t.to_schema() for t in self.tools.values()]

    async def execute(self, name: str, args: dict) -> dict:
        tool = self.tools.get(name)
        if not tool:
            return {"success": False, "error": f"工具 {name} 不存在"}
        try:
            validated = tool.args_model(**args)          # 参数校验
            result = await tool.func(**validated.model_dump())
            return {"success": True, "data": result}
        except Exception as e:
            return {"success": False, "error": str(e)}   # 错误回传，不抛出
```

```python
ORDERS = {
    "12345": {"id": "12345", "user_id": "u1", "status": "shipped", "amount": 299.0, "items": ["耳机"]},
    "12346": {"id": "12346", "user_id": "u1", "status": "delivered", "amount": 599.0, "items": ["键盘"]},
    "12347": {"id": "12347", "user_id": "u2", "status": "pending", "amount": 199.0, "items": ["鼠标"]},
}

class SearchOrdersArgs(BaseModel):
    user_id: str = Field(description="用户 ID")
    status: str | None = Field(default=None, description="订单状态筛选，可空")

async def search_orders(user_id: str, status: str = None) -> list:
    results = [o for o in ORDERS.values() if o["user_id"] == user_id]
    if status:
        results = [o for o in results if o["status"] == status]
    return results

class GetOrderArgs(BaseModel):
    order_id: str = Field(description="订单 ID")

async def get_order(order_id: str) -> dict:
    order = ORDERS.get(order_id)
    if not order:
        return {"error": f"订单 {order_id} 不存在"}
    return order

def register_order_tools(registry: ToolRegistry):
    registry.register(Tool(
        name="search_orders",
        description="根据用户 ID 查询订单列表。当用户询问'我的订单'时使用。",
        func=search_orders,
        args_model=SearchOrdersArgs,
    ))
    registry.register(Tool(
        name="get_order",
        description="根据订单 ID 查询订单详情。当用户提供具体订单号时使用。",
        func=get_order,
        args_model=GetOrderArgs,
    ))
```

注意两处描述里的「当用户……时使用」——这正是机制 1 的落点：描述是模型的路由依据。

记忆（`src/memory.py`）：对话历史用滑动窗口，工作记忆放本轮关键变量：

```python
from collections import deque

class Memory:
    def __init__(self, max_turns: int = 10):
        # deque 自带 maxlen：超过窗口自动丢最旧一轮（2 条消息）
        self.history = deque(maxlen=max_turns * 2)
        self.working = {}

    def add_message(self, role: str, content: str):
        self.history.append({"role": role, "content": content})

    def set_working(self, key: str, value):
        self.working[key] = value

    def get_working(self) -> dict:
        return self.working

    def get_messages(self) -> list[dict]:
        return list(self.history)
```

Agent 主循环（`src/agent.py`）：v0 的循环加上记忆、轨迹与双路终止：

```python
import json
import logging
from llm import chat
from memory import Memory
from tools.registry import ToolRegistry
from config import settings

logger = logging.getLogger("agent")

SYSTEM_PROMPT = """你是一个电商订单助手。
你可以使用工具查询订单信息。
规则：
1. 只使用工具返回的数据回答，不要编造。
2. 如果工具返回错误，告知用户。
3. 回答要简洁、友好。
4. 如果用户没提供用户 ID，先询问。
"""

class Agent:
    def __init__(self, registry: ToolRegistry, memory: Memory = None):
        self.registry = registry
        self.memory = memory or Memory()
        self.trajectory = []

    async def run(self, user_input: str, user_id: str = None) -> dict:
        messages = [{"role": "system", "content": SYSTEM_PROMPT}]
        if user_id:
            messages.append({"role": "system", "content": f"当前用户 ID: {user_id}"})
        messages.extend(self.memory.get_messages())   # 加载记忆
        messages.append({"role": "user", "content": user_input})

        self.memory.add_message("user", user_input)
        self.trajectory = []

        for step in range(settings.max_steps):        # 熔断终止
            logger.info(f"Step {step + 1}")

            msg = await chat(messages, tools=self.registry.get_schemas())

            if not msg.tool_calls:                    # 自然终止
                answer = msg.content
                self.memory.add_message("assistant", answer)
                return {
                    "answer": answer,
                    "steps": step + 1,
                    "trajectory": self.trajectory,
                }

            messages.append(msg)

            for tc in msg.tool_calls:
                tool_name = tc.function.name
                args = json.loads(tc.function.arguments)

                logger.info(f"工具调用: {tool_name}({args})")

                result = await self.registry.execute(tool_name, args)

                self.trajectory.append({              # 轨迹：可离线复盘
                    "step": step + 1,
                    "tool": tool_name,
                    "args": args,
                    "result": result,
                })

                messages.append({
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": json.dumps(result, ensure_ascii=False),
                })

        return {
            "answer": "抱歉，我无法在限定步数内完成这个任务。",
            "steps": settings.max_steps,
            "trajectory": self.trajectory,
        }
```

评估脚本（`eval/run_eval.py`）：跑两个准确率加平均步数：

```python
import json
import asyncio
from agent import Agent
from tools.registry import ToolRegistry
from tools.order import register_order_tools

async def evaluate():
    registry = ToolRegistry()
    register_order_tools(registry)
    agent = Agent(registry)

    eval_set = json.load(open("eval/eval_set.json"))

    results = []
    for case in eval_set:
        result = await agent.run(case["input"], user_id="u1")

        # 工具准确率：该调的工具调了没有
        actual_tools = [t["tool"] for t in result["trajectory"]]
        tool_correct = all(t in actual_tools for t in case["expected_tools"])

        # 答案准确率：关键信息是否出现在回复里
        answer_correct = all(
            kw in result["answer"] for kw in case["expected_contains"]
        )

        results.append({
            "input": case["input"],
            "tool_correct": tool_correct,
            "answer_correct": answer_correct,
            "steps": result["steps"],
        })

    n = len(results)
    print(f"总数: {n}")
    print(f"工具准确率: {sum(r['tool_correct'] for r in results) / n:.2%}")
    print(f"答案准确率: {sum(r['answer_correct'] for r in results) / n:.2%}")
    print(f"平均步数: {sum(r['steps'] for r in results) / n:.1f}")

if __name__ == "__main__":
    asyncio.run(evaluate())
```

## 7. 案例

### 案例 A：订单助手从 v0 到 v2（本篇主线复盘）

**场景**：某电商内部工具，客服同学手工查订单再回复用户，想用 CLI 助手替代高频查询。

**做法**：按 4.3 的路线三步走——v0 单文件验证 API 通；v1 加 search_orders、get_order 两个工具与参数校验；v2 加滑动窗口记忆、JSON 日志与轨迹。

**示意数字**（复盘口径）：v0 约 40 行、当天跑通；v2 约 300 行（含测试与评估）。4 条评估集上工具准确率 100%，答案准确率 75%——失分点是把 get_order 的描述写得太短，模型在「我有哪些已发货的订单」上误调它；把描述改成「当用户提供具体订单号时使用」、评估集扩到 10 条后，答案准确率稳定在 90% 上下，平均步数 2.0。

### 案例 B：天气助手——多轮指代逼出记忆

**场景**：个人练手项目，工具只有 `get_weather(city)`。

**评估集**两条即可暴露问题：

```json
[
  {"input": "北京天气怎么样？", "expected_tools": ["get_weather"], "expected_contains": ["北京"]},
  {"input": "上海呢？", "expected_tools": ["get_weather"], "expected_contains": ["上海"]}
]
```

**关键**：「上海呢？」省略了主语，没有记忆的 Agent 只能反问「请问你要查哪个城市」。加上 6.4 的滑动窗口记忆后，第二轮把历史带上，指代即可解析。

**示意数字**：10 轮指代问句测试，无记忆版 6 次反问、2 次答错城市；加记忆后 10 次全部直接命中工具，平均步数从 2.8 降到 1.2（少了一轮反问）。

### 案例 C：从原型到生产的演进路径

```text

阶段 2：加 RAG（4.2）       检索工具 + 引用与忠实度指标
阶段 3：加数据分析（4.3）   沙箱执行 + 安全边界
```

**教训**：先跑通，再优化；不要一开始就追求生产级。每往上走一个阶段，都拿同一套评估集做回归——评估集是演进路上唯一的安全带。

## 8. 常见坑

1. **选题太大**。  
   一上来就做「通用助手」，什么都做不好。选有边界的任务。

2. **工具太多**。  
   一开始就上 20 个工具，选择准确率骤降、调试困难。从 2-3 个开始。

3. **不做日志**。  
   出问题不知道哪一步错。每步都记录，JSON 结构化最省事。

4. **不做评估**。  
   改一版不知道是好是坏。至少 10 条评估集。

5. **没有最大步数**。  
   Agent 死循环烧钱。步数与超时熔断必须有。

6. **工具描述不清**。  
   LLM 选错工具。描述写清「什么时候用这个工具」。

7. **参数不校验**。  
   LLM 传错参数，工具直接崩。用 Pydantic 在入口校验。

8. **错误不处理**。  
   工具失败整个任务卡死。捕获后把错误回传模型，让它自纠。

9. **记忆不管理**。  
   历史无限增长，撑爆上下文。用滑动窗口截断。

10. **提示词硬编码**。  
    改一句提示词要改代码发版。存文件或配置。

11. **不做类型提示**。  
    代码难维护、难重构。Type Hints + Pydantic 全程带上。

12. **同步阻塞**。  
    工具调用串行等待，延迟叠加。用 asyncio 并发。

13. **不做版本管理**。  
    Prompt、配置、代码散乱，无法回滚。全部进 Git。

14. **不写 README**。  
    别人不知道怎么跑。安装、配置、运行三段写清。

15. **不写测试**。  
    改了工具不知道是否影响 Agent。工具单测 + 用假 LLM 测循环。

## 9. 练习

1. 跑通 v0：不改一行运行 6.2 的最小 Agent，记录一次完整轨迹（工具名、参数、返回）。验收：能贴出轨迹文本。
2. 换一个工具：把 get_order 换成 get_weather(city)（接公开天气 API 或模拟数据）。验收：三句不同问法全部选对工具。
3. 完成 v1：实现 Tool 与 ToolRegistry，参数用 Pydantic 校验。验收：故意传错类型，Agent 能把校验错误转述给用户而不是崩溃。
4. 完成 v2 的记忆：加滑动窗口，支持「上海呢？」式多轮指代。验收：连续两轮指代问句都答对。
5. 加轨迹与 JSON 日志。验收：离线回答「第几步调了什么工具、返回什么」，不用重跑。
6. 构建 10 条评估集（正常、边界、失败至少各 2 条），跑通评估脚本。验收：输出工具准确率、答案准确率、平均步数三个数。
7. 加熔断与循环检测：max_steps 之外，再加「最近 3 步动作指纹相同即终止」（方法见 2.5）。验收：构造一个诱导死循环的输入，Agent 能在限制步数内停住。
8. 写单元测试：覆盖参数校验与注册表，用假 LLM（stub 返回写死的工具调用）测循环。验收：pytest 全绿，且不产生 API 费用。
9. A/B 工具描述：同一评估集对比两版 description。验收：写出量化结论（如 75% 对 90%）并解释原因。
10. 写 README 并初始化 Git 仓库：安装、配置、运行、扩展四段。验收：同伴按 README 十分钟内跑通。

## 10. 小结

- 单 Agent 原型 = **LLM + 工具 + 记忆 + 循环 + 日志 + 评估**；最小可用只需 LLM + 工具 + 循环 + 终止 + 输出。
- 选题原则：**真实、有边界、可验证**。
- 迭代路线：**v0 最小闭环 → v1 工具注册与校验 → v2 记忆、轨迹、熔断与评估**，每步有验收标准。
- 核心组件：**配置、LLM 客户端、工具注册表、记忆、Agent 循环**。
- 工具设计：**命名清晰、描述写清何时使用、参数校验、错误回传**。
- 终止设计：**自然终止 + 步数熔断，两条路都必须有**。
- 评估：**至少 10 条，覆盖正常、边界、失败**，从工具准确率、答案准确率、平均步数起步。
- 工程习惯：**日志、类型提示、测试、README、版本管理**，从第一天带上。
- 核心原则：**先跑通，再优化；先单 Agent，再多 Agent；先原型，后工程化。**
- 这些能力直接支撑：4.2 RAG 知识库 Agent、4.3 数据分析 Agent、4.4 浏览器与计算机使用 Agent、4.5 工作流自动化 Agent、4.6 多 Agent 协作系统、4.7 生产级 Agent 平台，以及 4.10 作品集与复盘。
