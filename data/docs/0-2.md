## 1. 定位

L0 基础层第 2 个锚点，对应大纲核心问题：**能否写出可维护、可测试的脚本和服务？**

掌握档位是「会用」：不背理论，要求能上手写出正确姿势的代码。AI 应用岗的工程主考法是 **async/await 与流式**；Git 与测试是素养底线——面试聊项目时，这两项是「工程靠谱」的最直接信号。

## 2. 一句话定义

从脚本到服务的工程四件套：用虚拟环境（venv）隔离依赖并照单复刻；用 async/await 把「等模型响应」的时间重叠起来；用 FastAPI + SSE 让用户 1 秒看到首字而不是干等 30 秒；用超时 + 指数退避重试 + 幂等意识兜住网络抖动；再用 Git 小步提交和 pytest 测试守住协作底线。

## 3. 为什么需要

LLM 应用和普通 CRUD 服务有一个决定性差异：**每次调模型，90% 的时间在等对方吐字**。这决定了两件事：

1. **等待是主要成本**——谁能让等待重叠，谁就能用一个进程扛住几十路并发（异步的价值）。
2. **网络是常态故障源**——超时、限流、抖动不是事故而是日常，容错必须内建（重试的价值）。

脚本和服务是两个世界：

| 维度 | 脚本思维 | 服务思维 |
|---|---|---|
| 运行方式 | 本机跑一次就完 | 7x24 接请求，必须活得久 |
| 依赖管理 | 装在全局，能跑就行 | 每项目隔离，清单可复刻 |
| 失败处理 | 报错就崩，人工重跑 | 超时/重试/降级自动兜底 |
| 响应方式 | 跑完一次性给结果 | 流式边生成边推送 |
| 质量保障 | 肉眼验一次 | 测试覆盖核心逻辑 |
| 协作方式 | 文件传来传去 | Git 分支、提交、评审 |

面试官问 async、问重试，实际在问：**你的代码能不能从「我电脑上能跑」进化成「线上稳得住」。**

## 4. 核心原理

### 4.1 venv 与依赖管理

venv（virtual environment，虚拟环境）= 每个项目一个独立工具箱。项目 A 要 2.1 版的库、项目 B 要 2.3 版的，堆在一个全局抽屉里迟早打架。标准动作三步：建环境、装包、导清单；同事拿到 requirements.txt 照单复刻。

```bash
# 建环境：在项目根目录生成 .venv 文件夹
python3 -m venv .venv

# 激活（macOS/Linux）
source .venv/bin/activate
# 激活（Windows PowerShell）
.venv\Scripts\Activate.ps1

# 装包：只装进当前环境
pip install fastapi uvicorn httpx pytest

# 导出与复刻
pip freeze > requirements.txt      # 锁定当前版本清单
pip install -r requirements.txt    # 同事照单复刻

# 退出环境
deactivate
```

依赖管理方式对比：

| 方式 | 做法 | 问题 / 价值 |
|---|---|---|
| 全局 pip install | 所有包装系统环境 | 版本打架、污染系统，「我电脑能跑」重灾区 |
| venv + requirements.txt | 环境隔离 + 版本清单 | 团队最低标配，够用 |
| venv + 锁文件（uv/poetry） | 连间接依赖的精确版本一起锁 | 复刻更彻底，团队大了值得上 |
| 直接打包 .venv 发同事 | 压缩环境文件夹 | 路径绑定本机，换机器通常失效 |

两个纪律：`.venv` 目录必须写进 `.gitignore`（环境不入库，清单入库）；requirements.txt 尽量带版本号（`fastapi==0.115.*` 之类），裸装 `fastapi` 半年后复刻出来的可能已经是另一个世界。

### 4.2 async/await 与事件循环

类比：同步服务员点完一桌单，杵在厨房门口等这一桌出锅、端上桌，才去招呼下一桌——一单做完才做下一单。异步服务员点完单把小票丢给厨房，转身就去招呼下一桌，哪桌好了端哪桌。调 LLM 就是典型的「等菜」。

三个机制点：

1. **事件循环（Event Loop）**：那只不停扫「谁好了就处理谁」的眼睛。所有协程注册在循环里，循环在等待间隙切换执行。
2. **await 是让出点**：代码执行到 `await` 才把控制权还给事件循环，别人才能插进来跑。写了 async 却全程没有 await（或被同步阻塞），等于单车道上贴了「可超车」的标志——没用。
3. **收益只属于 IO 密集**：等网络、等磁盘时 CPU 闲着，异步把这段闲时填满。纯计算任务（大规模循环、训练）CPU 本来就满负荷，异步帮不上忙，该上多进程就上多进程。

| 任务类型 | 等的是什么 | 异步收益 | 正确工具 |
|---|---|---|---|
| 调 LLM API | 网络响应 | 极大 | async/await |
| 读数据库、读文件 | IO | 大 | async/await（异步驱动） |
| 大规模数值循环 | CPU | 无 | 多进程 / numpy 向量化 |
| 训练模型 | GPU 计算 | 无 | 框架自己调度 |

并发控制与常见错误：

- `asyncio.gather(*tasks)`：把一堆协程一起发出去，等待重叠，总耗时约等于最慢的那个。
- `asyncio.Semaphore(n)`：限流阀。LLM API 有并发/限流配额，100 个请求裸发出去只会换来一堆 429，要用信号量限制同时在途的请求数。
- 高频错误：在 async 函数里写 `time.sleep()`、同步 `requests`、重 CPU 计算——这些不会让出控制权，整个事件循环被卡死，所有请求一起等它。异步世界里等待用 `asyncio.sleep`、HTTP 用 `httpx.AsyncClient`。

### 4.3 FastAPI + SSE 流式

SSE（Server-Sent Events，服务器单向推送）：HTTP 连接保持打开，服务器一截一截往外吐 `data: ...` 行，浏览器 `EventSource` 或 fetch 流式读取。LLM 逐 token 生成，天然匹配 SSE 的「有就推、推完关」。

FastAPI 是 AI 应用后端首选，三个卖点：原生 async 支持（等 LLM 时不占线程）、自动生成交付式接口文档（/docs）、依赖注入便于管理客户端与配置。

流式 vs 非流式的体验差距：

| 维度 | 一次性返回 | SSE 流式 |
|---|---|---|
| 首字出现时间 | 等全部生成完（长答 10-30 秒） | 1 秒内 |
| 用户感知 | 转圈，像死机 | 在打字，愿意等 |
| 中断成本 | 断了全重來 | 已收到部分可保留 |
| 实现复杂度 | 低 | 略高（生成器 + 响应头） |

服务端实现要点：接口返回 `StreamingResponse`，内部用 async 生成器一段一段 `yield`；响应头 `text/event-stream`；每条消息按 SSE 格式包成 `data: ...\n\n`；结束时推一个约定好的结束标记（如 `data: [DONE]`）。

### 4.4 超时、重试与指数退避

类比：快递没送到就再约一次，而且越失败等得越久（1 秒、2 秒、4 秒）——免得人家正忙你还在疯狂敲门。四要素口诀：**设超时、指数退避、次数封顶、只重试幂等操作**。

- **超时（Timeout）**：每次调用必须设，到点就断。不设超时的调用，用户转圈 30 秒的元凶多半就是它。
- **指数退避（Exponential Backoff）**：第 n 次重试前等 `base * 2^(n-1)` 秒（1s、2s、4s…），再叠加随机抖动（jitter）避免所有客户端同一时刻重试踩踏。
- **次数封顶**：通常 3 次。网络长期故障时，无限重试只会让请求越堆越多，把自己服务拖垮。
- **幂等（Idempotency）**：重复执行不产生重复后果的操作才敢盲重试。查询安全；「扣款一次」不安全——要么不重试，要么带幂等键让服务端去重。

哪些错误值得重试：

| 错误 | 含义 | 是否重试 | 策略 |
|---|---|---|---|
| 超时 / 网络错误 | 没等到响应 | 重试 | 退避重试 |
| 429 Too Many Requests | 触发限流 | 重试 | 拉长退避，看 Retry-After 头 |
| 500 / 502 / 503 / 504 | 服务端临时故障 | 重试 | 标准退避 |
| 400 参数错误 | 请求本身错 | 不重试 | 改请求 |
| 401 / 403 | 认证授权问题 | 不重试 | 修密钥/权限 |
| 402 欠费 / 配额耗尽 | 账户问题 | 不重试 | 充值或降级 |

重试封顶之后要**友好降级**：返回「系统繁忙，请稍后再试」、切换备用模型、或进异步队列——总之不能让用户看着报错栈。

### 4.5 Git 与测试素养

Git 底线动作：小步提交（一个提交一件事）、提交说明写清「为什么」、功能分支开发后合回主干、`.gitignore` 排除 `.venv`、密钥与数据文件。面试聊项目时，「提交历史是否干净、能不能讲清每次改动」是隐性打分项。

测试底线动作：核心逻辑配 pytest 单测；外部 API 一律 mock（测试不花钱、不抖、跑得快）；异步代码用 pytest-asyncio。测什么：参数校验、重试逻辑（mock 前两次失败第三次成功）、SSE 输出格式、边界条件。

## 5. 架构 / 流程

一次「用户发消息到模型回话」的完整服务链路，容错内建于每一环：

```text
用户消息
   |
   v
+----------------------------------------------+
| FastAPI 服务（async）                          |
|  1. 参数校验（pydantic：不合法直接 4xx，不重试） |
|  2. 组装 prompt，取 httpx.AsyncClient          |
+----------------------------------------------+
   |
   v
+----------------------------------------------+
| 调 LLM API（流式）                             |
|  超时 10s --> 到点就断                         |
|  失败? 判断类型:                               |
|    429/5xx/超时 --> 指数退避重试（1s,2s,4s）    |
|                    + jitter，最多 3 次         |
|    400/401/403  --> 不重试，直接报给上层       |
|  并发限制: Semaphore(20) 在途请求封顶           |
|  3 次全败 --> 降级: "稍后再试" / 备用模型       |
+----------------------------------------------+
   |
   v  逐 token yield
+----------------------------------------------+
| StreamingResponse（SSE）                       |
|  data: {"delta": "你"} \n\n                   |
|  data: {"delta": "好"} \n\n                   |
|  data: [DONE] \n\n   --> 连接关闭              |
+----------------------------------------------+
   |
   v
浏览器 1 秒内看到首字，边生成边渲染
```

## 6. 代码 / 工具

### 6.1 FastAPI 异步 SSE 流式接口

```python
# app/main.py
import json
import asyncio
import httpx
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

app = FastAPI()

API_URL = "https://api.openai.com/v1/chat/completions"
semaphore = asyncio.Semaphore(20)          # 在途请求封顶，防打爆配额


class ChatRequest(BaseModel):
    message: str


async def stream_from_llm(message: str):
    """调模型并逐段 yield SSE 格式的数据。"""
    payload = {
        "model": "gpt-4o-mini",
        "messages": [{"role": "user", "content": message}],
        "stream": True,                     # 关键：要求模型流式返回
    }
    headers = {"Authorization": "Bearer YOUR_KEY"}

    async with semaphore:                   # 限并发
        async with httpx.AsyncClient(timeout=10.0) as client:   # 超时必设
            async with client.stream("POST", API_URL, json=payload,
                                     headers=headers) as resp:
                resp.raise_for_status()
                async for line in resp.aiter_lines():
                    if not line.startswith("data: "):
                        continue
                    chunk = line[len("data: "):]
                    if chunk == "[DONE]":
                        break
                    delta = json.loads(chunk)["choices"][0]["delta"].get("content")
                    if delta:
                        yield f"data: {json.dumps({'delta': delta}, ensure_ascii=False)}\n\n"
    yield "data: [DONE]\n\n"


@app.post("/chat")
async def chat(req: ChatRequest):
    return StreamingResponse(
        stream_from_llm(req.message),
        media_type="text/event-stream",     # SSE 响应头
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )

# 运行: uvicorn app.main:app --reload
# 测试: curl -N -X POST localhost:8000/chat -H "Content-Type: application/json" \
#       -d '{"message": "用一句话介绍 RAG"}'
```

### 6.2 指数退避重试（async 版）

```python
# app/llm.py —— 重试策略单独封装，调用方无感知
import asyncio
import random
import httpx

RETRYABLE_STATUS = {429, 500, 502, 503, 504}
MAX_RETRIES = 3


async def call_with_retry(url: str, payload: dict, headers: dict) -> dict:
    """带超时、指数退避、次数封顶的 API 调用。只重试临时性错误。"""
    last_exc: Exception | None = None

    for attempt in range(1, MAX_RETRIES + 1):
        try:
            async with httpx.AsyncClient(timeout=10.0) as client:
                resp = await client.post(url, json=payload, headers=headers)
            if resp.status_code < 400:
                return resp.json()
            if resp.status_code not in RETRYABLE_STATUS:
                resp.raise_for_status()      # 400/401 等：重试无意义，直接抛
        except (httpx.TimeoutException, httpx.TransportError,
                httpx.HTTPStatusError) as exc:
            last_exc = exc

        if attempt == MAX_RETRIES:
            break
        backoff = 2 ** (attempt - 1) + random.uniform(0, 0.5)   # 1s/2s/4s + 抖动
        await asyncio.sleep(backoff)

    raise RuntimeError(f"重试 {MAX_RETRIES} 次后仍失败") from last_exc
```

生产上也可以直接用 tenacity 库替掉手写循环：`@retry(wait=wait_exponential(multiplier=1, max=10), stop=stop_after_attempt(3), retry=retry_if_exception_type(httpx.TimeoutException))`，语义等价。但手写一遍是面试基本功。

### 6.3 pytest：不花钱的测试

```python
# tests/test_llm.py
import pytest
from httpx import AsyncClient, Response, Request
from app.main import app


@pytest.mark.asyncio
async def test_chat_streams_sse(mocker):
    """mock 模型 API，验证 SSE 输出格式——测试不依赖真实网络。"""
    fake_chunks = [
        'data: {"choices":[{"delta":{"content":"你"}}]}',
        'data: {"choices":[{"delta":{"content":"好"}}]}',
        "data: [DONE]",
    ]

    async def fake_aiter_lines(self):
        for line in fake_chunks:
            yield line

    mocker.patch("httpx.AsyncClient.stream", return_value=None)

    async with AsyncClient(app=app, base_url="http://test") as client:
        resp = await client.post("/chat", json={"message": "hi"})

    assert resp.status_code == 200
    assert "text/event-stream" in resp.headers["content-type"]
    assert resp.text.count("data: ") >= 3


@pytest.mark.asyncio
async def test_call_with_retry_gives_up_after_max(mocker):
    """前 N 次都超时：验证封顶后抛错，而不是无限重试。"""
    from app.llm import call_with_retry, MAX_RETRIES

    calls = {"n": 0}

    class FlakyClient:
        def __init__(self, *a, **k): pass
        async def __aenter__(self): return self
        async def __aexit__(self, *a): return False
        async def post(self, *a, **k):
            calls["n"] += 1
            raise httpx.TimeoutException("timeout")

    mocker.patch("app.llm.httpx.AsyncClient", FlakyClient)
    with pytest.raises(RuntimeError):
        await call_with_retry("http://x", {}, {})
    assert calls["n"] == MAX_RETRIES        # 恰好封顶次数，不多不少
```

## 7. 案例

### 案例 A：批量摘要从 200 秒到 12 秒

某内容团队要给 100 篇文章批量生成摘要，v1 用同步 requests 串行调模型，每篇约 2 秒，总耗时 200 秒，运营等到失去耐心。v2 改为 `asyncio.gather` + `Semaphore(10)` 并发（并发再高就触发 429），总耗时约 12 秒——等待全部重叠，瓶颈只剩最慢的那几个请求。注意加速的是「等待重叠」：单次调用本身还是 2 秒，异步没有让模型变快。

### 案例 B：SSE 把首字延迟从 25 秒压到 1 秒内

一家金融科技公司的投研问答，长回答完整生成要 25 秒，界面一直转圈，用户大量中途放弃。改造成 FastAPI + StreamingResponse 的 SSE 流式：模型 `stream=True`，服务端逐 token 转发，首字 1 秒内出现，用户看到在打字就愿意等，会话放弃率明显下降。顺带解决了中断问题：用户关页面时服务端检测到连接断开就停止生成，省下无效 token 成本。

### 案例 C：一次上线事故与重试策略

某电商客服服务上线一周后，高峰期偶发「转圈 30 秒后报错」。排查两个根因：模型调用没设超时（偶发挂死），以及 429 限流被当成致命错误直接抛给用户。治理：全部调用加 10 秒超时；429/5xx/超时走指数退避重试最多 3 次；封顶后降级为「稍后再试」话术并切换备用模型；非幂等工单创建接口加幂等键。上线后接口失败率从约 8% 降到 0.5% 以内，「疯狂敲门」式雪崩再未出现。

## 8. 常见坑

1. **全局装包污染系统环境**。多项目版本打架、系统工具被搞坏。对策：新项目第一件事建 venv。
2. **把 .venv 提交进 Git**。仓库膨胀、路径绑定本机。对策：.gitignore 写上 `.venv/`，入库的是 requirements.txt。
3. **async 里写阻塞调用**。`time.sleep`、同步 requests、重 CPU 循环会卡死整个事件循环。对策：异步等费用 `asyncio.sleep`，HTTP 用 `httpx.AsyncClient`。
4. **定义了 async 却没有 await**。协程从不让出控制权，并发退化成串行，还自以为在并发。对策：检查每个 async 函数是否真有 await 点。
5. **裸发并发打爆 API**。100 个请求同时出去换来满屏 429。对策：Semaphore 限在途数量，配合退避。
6. **调用不设超时**。偶发挂死让用户无限转圈。对策：每次外部调用显式 timeout。
7. **无限重试**。故障期请求越堆越多，自己拖垮自己。对策：3 次封顶 + 退避 + 降级。
8. **重试非幂等操作**。重复请求导致重复扣款、重复建单。对策：重试前先问幂等；不幂等就带幂等键或不重试。
9. **SSE 被中间层缓冲**。nginx 或代理把流攒成一坨一次性吐出，流式白做。对策：关代理缓冲（如 X-Accel-Buffering: no），本地 curl -N 验证。
10. **requirements 不锁版本**。半年后 `pip install -r` 装出另一个世界。对策：freeze 导出带版本，或上锁文件。
11. **测试依赖真实 API**。慢、贵、不稳定，没人愿意跑。对策：mock 外部调用，只测自己的逻辑（6.3 模板）。
12. **提交大杂烩**。一个 commit 混着功能、格式、密钥改动，回滚无从下手。对策：小步提交，密钥走环境变量永不入库。

## 9. 练习

1. 建一个 venv，装 fastapi/httpx/pytest，freeze 导出 requirements.txt；删掉环境后照单复刻一遍。
2. 写同步版和 asyncio 版各一份「并发调 10 次模拟 API」的脚本（用 asyncio.sleep(2) 模拟等待），实测总耗时对比。
3. 给练习 2 加 Semaphore(3)，观察总耗时的变化，解释为什么不是「并发越大越好」。
4. 跑通 6.1 的 SSE 接口（模型可先换成假数据生成器），用 curl -N 观察逐段输出，再故意在响应头里去掉 media_type 看会怎样。
5. 在 6.2 的基础上改造：429 时读取响应头 Retry-After 并按它等待；写一个 mock 测试验证。
6. 把 6.3 的两个测试跑绿；故意把 MAX_RETRIES 改成 0，看测试如何失败。
7. 给自己的项目补一份 .gitignore（.venv、.env、__pycache__、数据目录），并检查 git log 的提交说明是否说清了「为什么」。
8. 用一句话向室友解释：为什么你的异步服务在「帮用户算斐波那契第 10^9 项」这个接口上毫无加速效果。

## 10. 小结

- venv 先行：**新项目先建环境再装包**，清单入库、环境不入库。
- LLM 调用九成时间在等：**async/await 让等待重叠**，一个进程扛几十路并发。
- 事件循环是那只「谁好了就处理谁」的眼睛；**有 await 才让出控制权**。
- 收益只属于 **IO 密集**；CPU 密集该上多进程，异步帮不上忙。
- 并发要限流：**Semaphore 封顶在途请求**，裸发并发等于自己制造 429。
- FastAPI 三卖点：**原生 async、自动文档、依赖注入**；SSE 用 StreamingResponse 逐段 yield。
- 流式是体验分水岭：**首字 1 秒** vs 干等 30 秒。
- 容错口诀：**设超时、指数退避、次数封顶、只重试幂等操作**，封顶后友好降级。
- 400/401/403 不重试，**429/5xx/超时**才值得重试。
- Git 小步提交 + pytest mock 外部依赖，是「工程靠谱」的素养底线。
- 这套底座直接支撑：0-3 的训练代码、2.x 的 Agent 服务化、4-1 的最小可用 Agent。
