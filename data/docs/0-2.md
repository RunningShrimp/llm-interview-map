## 2. 一句话定义

Python 工程基础，是用 Python 把 LLM/Agent 逻辑组织成**可维护、可测试、可部署服务**的最小工程能力集合。

注意关键词：不是"会写 Python 语法"，而是"**工程化地写 Python**"。

```text
简化公式：
Python 工程基础 = 类型与校验（Type Hints / Pydantic）
              + 异步并发（asyncio / httpx）
              + 异常与重试（超时、指数退避）
              + 配置与日志（环境变量、结构化日志）
              + 测试（pytest）
              + 项目与依赖管理（uv / Git 工作流）
```

## 3. 为什么需要

做 AI Agent，你每天都在做这些事：

- 调用 LLM API（HTTP、异步、超时、重试）
- 定义工具（函数签名、参数校验、错误处理）
- 管理状态（会话、记忆、任务队列）
- 处理结构化数据（JSON、Schema、Pydantic）
- 读配置（API Key、模型名、超参数）
- 写测试（Prompt 改动后回归验证）
- 打包部署（Docker、依赖管理）

这些全是 Python 工程问题，而且每个都对应一个具体痛点：

- **LLM 输出不可控** → 返回的 JSON 缺字段、类型漂移，没有校验就是埋在下游的定时炸弹
- **接口不稳定** → 超时、限流（429）、5xx 是调用 LLM 的日常，不重试就直接失败
- **延迟以秒计** → 一次 LLM 调用秒级起步，串行等待会把多步 Agent 拖到不可用
- **改动频繁** → Prompt、模型、工具天天调，没有回归测试等于每次上线赌一次
- **链路难排查** → 多步调用环环相扣，没有日志就不知道错在哪一环
- **环境与协作** → 依赖不锁版本、Key 硬编码，换台机器、上个线就出事

**Agent 开发 80% 的时间在写工程代码，20% 在调 Prompt。**

脚本式写法与工程化写法的差距：

| 维度 | 脚本式写法 | 工程化写法 |
|---|---|---|
| LLM 返回坏 JSON | 深处抛 KeyError，深夜报警 | 入口校验拦截，带错误信息重试 |
| 换模型 / 换供应商 | 全文件搜索替换 | 改一行配置 |
| 并发调用 3 个接口 | 串行 1500ms | 并发约 500ms |
| 线上出错 | 靠猜 | 日志定位到具体一步 |
| 新人接手 | 读三天代码 | 看项目结构半小时上手 |
| Prompt 改动 | 祈祷没坏 | 回归测试全绿再合并 |

类比：脚本式写法像家里做私房菜——一个厨师从头做到尾，味道靠手感，换个人掌勺就变味；工程化写法像中央厨房——备菜、烹饪、质检、出餐各有工序和标准，谁来操作、出多少份，结果都稳定。LLM 应用要交付给真实用户，走的是中央厨房路线。

## 4. 核心原理

### 4.1 类型提示（Type Hints）

让代码"自解释"，也是工具调用和结构化输出（Structured Output）的基础。

```python
def search_docs(query: str, top_k: int = 5) -> list[dict]:
    ...
```

为什么重要：

- IDE 能补全、能查错
- Pydantic / FastAPI / Function Calling 都依赖类型
- 团队协作可读性大幅提升

机制上要注意：Python 的类型提示**运行时不强制**（传错类型不会立刻报错），它的价值分两层——静态检查（mypy / pyright 在写代码阶段抓错）和运行时校验（Pydantic 把类型变成真正的数据契约）。Agent 工具的函数签名，本质上就是给 LLM 看的接口文档（见 2.3 工具使用）。

| 场景 | 无类型 | 有类型 |
|---|---|---|
| IDE 补全与重构 | 靠猜 | 精准跳转、安全重命名 |
| 参数传错 | 跑到那一行才炸 | 静态检查阶段即报 |
| 定义工具 Schema | 手写 JSON | 从签名与文档字符串生成 |
| 代码评审 | 逐行读语义 | 签名即契约 |

### 4.2 Pydantic：数据校验与结构化

Agent 里到处都是"不确定的 LLM 输出"，Pydantic 是你的**守门员**。

```python
from pydantic import BaseModel, Field

class ToolCall(BaseModel):
    tool_name: str = Field(description="要调用的工具名")
    arguments: dict = Field(default_factory=dict)
    reason: str | None = None
```

校验流水线：

```text
LLM 原始输出（字符串）
  → json.loads 解析
  → Pydantic 按 Schema 校验（字段名 / 类型 / 必填 / 约束）
  → 通过：得到带类型的对象，安全进入业务代码
  → 失败：抛 ValidationError（指明哪个字段、什么原因）
        → 把错误信息拼回 Prompt，让 LLM 重新生成
```

作用：

- 校验 LLM 返回的 JSON 是否符合 Schema
- 自动类型转换、报错清晰
- 和 OpenAI Function Calling、LangChain、FastAPI 无缝配合

截至 2026 年，Pydantic v2 是事实主流（校验核心用 Rust 重写，比 v1 快一个量级），新项目直接按 v2 语法写。

### 4.3 异步编程（async/await）

Agent 常要并发调用：多个工具、多个模型、多个检索。  
同步代码会串行等待，异步可以并发。

先看机制：同步代码发起网络请求后，线程干等着；异步代码 `await` 挂起当前协程（Coroutine），**事件循环（Event Loop）**转去执行别的协程，等回包了再切回来。一句话：等待不再占用执行权。

```text
同步（串行）：
调用A █████████ (500ms)
                   调用B █████████ (500ms)
                                    调用C █████████ (500ms)
总耗时 ≈ 1500ms，线程大部分时间在空等网络回包

异步（并发）：
调用A █████████
调用B    █████████
调用C       █████████
总耗时 ≈ 500ms（由最慢的一个决定）
```

类比：同步像一桌配一位专属服务员，从点单到上菜全程站在桌边干等；异步像正常餐厅——服务员点完单就去下一桌，后厨出菜铃一响再回来端菜。事件循环就是那个"铃"。

```python
import asyncio
import httpx

async def call_llm(prompt: str) -> str:
    async with httpx.AsyncClient(timeout=30) as client:
        r = await client.post("https://api.example.com/chat", json={"prompt": prompt})
        return r.json()["text"]

async def main():
    results = await asyncio.gather(
        call_llm("问题A"),
        call_llm("问题B"),
        call_llm("问题C"),
    )
    print(results)

asyncio.run(main())
```

关键概念：

- `async def` 定义协程
- `await` 等待异步结果，等待期间让出执行权
- `asyncio.gather` 并发执行
- `asyncio.Semaphore` 控制并发数

```python
# 用信号量（Semaphore）把并发压在上限内：LLM API 普遍按并发限流
sem = asyncio.Semaphore(5)  # 最多 5 个请求同时在飞

async def bounded_call(prompt: str) -> str:
    async with sem:
        return await call_llm(prompt)
```

为什么 LLM 应用偏偏吃异步这一套？答案是 GIL（Global Interpreter Lock，全局解释器锁）：CPython 同一时刻只允许一个线程执行字节码，多线程无法并行 CPU 计算；但网络 IO 等待会释放 GIL，所以**IO 密集的 LLM API 调用、向量检索正是协程的最佳场景**。

| 任务类型 | 典型例子 | 选型 |
|---|---|---|
| IO 密集、高并发 | 调 LLM API、向量检索、批量爬取 | asyncio 协程 |
| IO 密集、小脚本 | 一次性批量下载 | 线程池，或干脆同步 |
| CPU 密集 | 本地 Embedding、大规模文本清洗 | 多进程或任务队列 |
| 混合负载 | Agent 服务（少量计算 + 大量 IO） | 异步框架 + 计算丢进程池 |

流式输出（Streaming，常用 SSE 即 Server-Sent Events）是异步的另一主战场：LLM 逐 token 吐字，服务端用异步生成器把增量推给前端，用户看到的首字延迟从"整段生成完"降到"第一个 token 到达"。实现细节在 1.1 展开。

**面试高频问法**（业界共识口径）：「async def 什么时候该用、什么时候不该用？」——等待 IO（网络、数据库）时用；纯 CPU 计算不收益反而添复杂度；且 async 函数里绝不能调用阻塞库（requests、time.sleep），否则事件循环整体卡死，所有请求一起停。

**面试高频问法**：「FastAPI 为什么适合做 LLM 服务？」——原生基于 asyncio（天然匹配 IO 密集负载）、请求/响应用 Pydantic 校验、对流式响应支持好，三件事正好对上 LLM 服务的形状。

### 4.4 异常处理与重试

LLM API 会超时、限流、返回 5xx。工程代码必须能扛。

```python
import asyncio
import random
import httpx

async def call_with_retry(url: str, payload: dict, max_retries: int = 3):
    for attempt in range(max_retries):
        try:
            async with httpx.AsyncClient(timeout=30) as client:
                r = await client.post(url, json=payload)
                r.raise_for_status()
                return r.json()
        except (httpx.TimeoutException, httpx.HTTPStatusError):
            if attempt == max_retries - 1:
                raise  # 最后一次仍失败：向上抛，交给调用方降级
            wait = 2 ** attempt + random.random()  # 指数退避 + 抖动（Jitter）
            await asyncio.sleep(wait)
```

先分类再重试：

| 状态码 | 性质 | 对策 |
|---|---|---|
| 408 / 超时 | 可重试 | 指数退避后重试 |
| 429 | 可重试 | 读 Retry-After 头，退避后重试 |
| 5xx | 可重试 | 退避重试，连续失败则熔断（Circuit Breaker）降级 |
| 400 | 不可重试 | 请求体本身错了，改请求 |
| 401 / 403 | 不可重试 | 查 Key 与权限 |
| 422 | 不可重试 | 格式不符 Schema，改请求 |

指数退避（Exponential Backoff）的推导：每次失败后等待时长翻倍——1s、2s、4s。三次重试总等待约 7s 而不是固定间隔的 3s，看似更慢，实际是给过载的服务端留恢复窗口，整体成功率更高；加抖动是为了避免多个客户端同步重试，形成新的流量尖峰。

原则：

- 区分**可重试**（超时、429、5xx）和**不可重试**（400、401）
- 指数退避 + 抖动
- 设置最大重试次数，避免无限循环

### 4.5 配置管理

不要把 API Key 写死在代码里。

```python
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    # 敏感项与可变项全部走环境变量，代码零硬编码
    openai_api_key: str
    model_name: str = "gpt-4o-mini"
    temperature: float = 0.0
    max_tokens: int = 1024

    model_config = SettingsConfigDict(env_file=".env")  # Pydantic v2 写法

settings = Settings()  # 启动即校验：缺 Key 直接快速失败，而不是跑到一半才崩
```

原则：

- 敏感信息放环境变量 / `.env`
- `.env` 加入 `.gitignore`
- 配置用类型校验，启动时快速失败（Fail Fast）

### 4.6 日志与追踪

Agent 是多步系统，没有日志等于盲人摸象。

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s | %(levelname)s | %(name)s | %(message)s"
)
logger = logging.getLogger("agent")

logger.info("tool_call", extra={"tool": "search", "query": "退货政策"})
```

原则：

- 结构化日志（JSON）便于检索
- 记录关键事件：请求、工具调用、错误、耗时
- 不要打印敏感信息（API Key、PII）

一次 Agent 请求的日志至少要能回答：进来了什么、走了哪几步、每步花了多久、哪一步失败、用了多少 token。完整的追踪（trace / span）体系在 3.4 展开。

### 4.7 测试

Prompt 改动后，怎么知道没变坏？靠测试。

```python
import pytest
from my_agent import extract_json

def test_extract_json_valid():
    result = extract_json('{"name": "张三", "age": 30}')
    assert result["name"] == "张三"

def test_extract_json_invalid():
    with pytest.raises(ValueError):
        extract_json("这不是 JSON")
```

测试层次：

| 层次 | 测什么 | 例子 | 速度 |
|---|---|---|---|
| 单元测试 | 纯函数逻辑 | JSON 解析、Schema 校验、退避时长计算 | 毫秒级 |
| 集成测试 | 带依赖的链路 | LLM API 调用、检索链路（用 Mock / 录制回放） | 秒级 |
| 评估测试 | LLM 输出质量 | golden set 通过率、结构化输出合法率 | 分钟级 |

集成测试不要每次真打 LLM API：慢、贵、不稳定，用 Mock 或录制的响应回放；输出质量评估在 1.6 / 3.5 展开。

### 4.9 Git 工作流

Agent 项目的 Git 纪律与传统后端一致，但多了几类"资产"必须进版本管理：

- **Prompt 模板、评估集、配置样例都是代码** → 全部进 Git，变更可追溯、可回滚（与 3.9 的 CI/CD 直接衔接）
- **`.env` 永不提交** → 只提交 `.env.example`
- **小步提交 + 约定式提交信息**（feat / fix / test）→ 出问题时能二分定位到具体提交
- **分支模型**：main 保持随时可运行，功能在 feature 分支开发，测试通过后合并

## 5. 架构 / 流程

一个典型 Agent 项目的 Python 工程分层：

```text
┌─────────────────────────────────────┐
│  入口层 (CLI / FastAPI / 定时任务)   │
├─────────────────────────────────────┤
│  Agent 编排层 (循环 / 状态机)        │
├─────────────────────────────────────┤
│  能力层 (LLM 调用 / 工具 / 检索)     │
├─────────────────────────────────────┤
│  基础设施层 (HTTP / 日志 / 配置 / DB) │
└─────────────────────────────────────┘
```

一次请求在分层里的完整旅程：

```text
用户输入
  ↓ [入口层]    校验入参、生成请求 ID
  ↓ [编排层]    Agent 循环：组装上下文 → 决定下一步动作
  ↓ [能力层]    LLM 调用 / 工具调用 / 检索（全是 IO，一律 async）
  ↓ [基础设施层] httpx 发请求、写日志、读配置、落库
  ↓ 返回结果（沿途每层写日志，全程携带同一请求 ID）
```

原则：

- **每层只依赖下层**，不要交叉
- LLM 调用封装成独立模块，方便替换模型
- 工具用统一接口，方便注册和测试
- 配置、日志、异常处理横切所有层

## 6. 代码 / 工具

一个最小可用的 Agent 工程骨架（对应 4.8 的目录结构，逐文件可拼装运行）：

```python
# schemas.py —— 数据契约：消息与工具结果
from pydantic import BaseModel

class Message(BaseModel):
    role: str
    content: str

class ToolResult(BaseModel):
    success: bool
    data: dict | None = None
    error: str | None = None

# config.py —— 配置集中读取，Key 不落代码
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    api_key: str
    model_name: str = "gpt-4o-mini"
    model_config = SettingsConfigDict(env_file=".env")

settings = Settings()

# llm.py —— LLM 调用封装：换模型只改这里
import httpx
from schemas import Message
from config import settings

async def chat(messages: list[Message]) -> str:
    async with httpx.AsyncClient(timeout=60) as client:
        r = await client.post(
            "https://api.openai.com/v1/chat/completions",
            headers={"Authorization": f"Bearer {settings.api_key}"},  # 从配置读，不硬编码
            json={
                "model": settings.model_name,
                "messages": [m.model_dump() for m in messages],
            },
        )
        r.raise_for_status()
        return r.json()["choices"][0]["message"]["content"]

# tools.py —— 工具统一返回 ToolResult，失败不抛异常、由上层兜底
from schemas import ToolResult

async def search_docs(query: str, top_k: int = 5) -> ToolResult:
    try:
        # 这里接你的检索逻辑
        docs = [{"title": "退货政策", "content": "..."}]
        return ToolResult(success=True, data={"docs": docs[:top_k]})
    except Exception as e:
        return ToolResult(success=False, error=str(e))

# agent.py —— 主循环：只做编排，不做杂活
import logging
from schemas import Message
from llm import chat

logger = logging.getLogger("agent")

async def run_agent(user_input: str) -> str:
    messages = [Message(role="user", content=user_input)]
    logger.info("agent_start", extra={"input": user_input})

    response = await chat(messages)
    logger.info("agent_response", extra={"chars": len(response)})
    return response
```

这个骨架虽小，但已经具备：类型、异步、校验、日志、分层、配置外置。逐条对照第 4 节，每项能力都落在一个具体文件里——这就是"工程化"的可检验形态。

## 7. 案例

### 案例 A：工具调用参数校验

场景：某电商客服 Agent，LLM 负责生成工具调用参数。内部测试 200 次调用里，约 6% 出现格式偏差——`top_k` 传中文数字、字段缺失、类型漂移。

LLM 返回：

```json
{"tool": "search", "args": {"query": "退货", "top_k": "五"}}
```

`top_k` 是字符串 `"五"`，不是整数。  
没有 Pydantic 校验，这类错误约三分之一会沉到下游才崩溃，且栈信息指向无关位置，排查一小时起步。  
加上校验后，错误在工具调用前被拦截，把 ValidationError 信息拼回 Prompt 让 LLM 重出一次参数，最终调用成功率回到 99% 以上。

### 案例 B：并发检索提速

场景：一个 RAG（检索增强生成）型问答 Agent（见 1.4），每步要查 3 个检索源（向量库、BM25、配置库），单源约 500ms。

串行：3 × 500ms = 1500ms。  
用 `asyncio.gather` 并发：约 500ms（等最慢的那个）。  
一个 5 步任务、每步 3 路检索：串行 5 × 1500ms = 7.5s，并发 5 × 500ms ≈ 2.5s。用户体感从"卡住"变成"可用"，且差距随步数继续放大。

### 案例 C：没有日志的调试地狱

场景：某团队 Agent 回答错误，但没人知道错在哪一环：

- 是检索没召回？
- 是 LLM 幻觉？
- 是工具调用失败？

无日志时排查一天没有结论；补上结构化日志（每步输入摘要、耗时、结果状态）后，同类问题约 10 分钟定位——那次是第 2 步工具参数被截断导致的空结果。复盘口径：多步系统里，日志写在哪，排查能力就在哪。

### 案例 D：依赖不锁版本的代价

场景：某小团队用无版本号的 requirements.txt，CI 某天突然全红——一个传递依赖升级，把 pydantic 从 v1 行为带到 v2，旧写法失效。  
修复：迁移到 uv + uv.lock 锁定全量依赖版本，新机器 `uv sync` 一键复现；此后三个月 CI 零环境故障。原则：依赖图必须整体锁定，"我机器上能跑"不是环境管理。

## 8. 常见坑

1. **不用类型和 Pydantic**。  
   LLM 输出不可控，没有校验就是定时炸弹。对策：入口处全部过 Pydantic，失败带原因重试。

2. **同步代码硬扛并发**。  
   Agent 多步调用，串行会慢到不可用。对策：IO 密集路径一律 async + httpx.AsyncClient。

3. **API Key 写死在代码里**。  
   泄露风险极高。对策：环境变量 + pydantic-settings，`.env` 进 `.gitignore`。

4. **不写测试**。  
   Prompt 一改，旧功能悄悄坏掉，回归成本极高。对策：纯函数上单元测试，输出质量上评估集（见 1.6）。

5. **异常处理太粗**。  
   `except Exception: pass` 会吞掉关键错误。对策：按异常类型分叉处理，兜底分支必须记日志再抛出或降级。

6. **没有超时设置**。  
   LLM 调用可能挂几十秒，拖垮整个服务。对策：client 层统一设 timeout，外层再配总时长预算。

7. **日志打印敏感信息**。  
   PII、Key、用户数据不能进日志。对策：落盘前过滤字段，日志里只留摘要与 ID。

8. **项目结构混乱**。  
   所有代码堆一个文件，后期无法维护。对策：按 4.8 的骨架分层，模块职责单一。

9. **依赖不锁定版本**。  
   今天能跑，明天 `pip install` 就崩。对策：uv / poetry 锁全量依赖，部署按锁文件还原。

10. **async 函数里调用阻塞库**。  
    requests、time.sleep 会卡死事件循环，整个服务的请求一起停。对策：换 httpx.AsyncClient 与 asyncio.sleep，CPU 重活丢进程池。

11. **重试不分错误类型**。  
    对 401、400 也重试，白白烧时间和配额。对策：按 4.4 的状态码表分类，可重试才退避。

12. **并发不加信号量**。  
    gather 几百个请求直接触发 429 甚至封 Key。对策：Semaphore 限并发，429 时读 Retry-After 再退避。

## 10. 小结

- Python 工程基础 = 类型 + Pydantic + 异步 + 异常 + 配置 + 日志 + 测试 + 项目结构 + Git。
- 核心目标：**可维护、可测试、可部署**。
- Agent 开发中，工程代码占大头，Prompt 只是其中一环。
- LLM 应用是 IO 密集负载：asyncio + httpx 是标配，阻塞库是事件循环的毒药。
- 校验前置：LLM 输出必须过 Pydantic，失败把错误信息带回重试，不让坏数据流向下游。
- 重试先分类：可重试（超时 / 429 / 5xx）才退避，指数退避加抖动、设上限。
- 配置走环境变量并启动即校验；日志结构化、带请求 ID、不含敏感信息。
- 测试分层：单元测纯函数、集成就用 Mock、质量交给评估集。
- 依赖整体锁版本，任何机器一键复现环境。
- 这些能力直接支撑：0.3 训练评估脚本、1.1 LLM API 与模型选型、1.3 结构化输出与 Function Calling、2.3 工具使用、2.5 执行循环与状态机、3.4 可观测性与追踪、3.9 CI/CD 与版本管理，以及全部实战层（4.1-4.10）。
