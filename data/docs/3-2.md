# 讲解 3.2 数据与知识工程

> 说明：1.4 搭了单机 RAG 最小链路，1.4c 用切分、混合检索与重排优化了检索质量——那些是「一次性的管道」。  
> 本篇把数据面升级成**持续运转的生产管线**：采集→清洗→切分→嵌入→索引五站、增量更新与新鲜度 SLA、权限标签、版本血缘、坏例回流运营，并延伸到合成数据前沿（考点 3-2b）。数据面放进完整知识库全案在 4.2/4.2b，权限与审计的合规视角在 3.8。

---

## 1. 定位

AI 工程化阶段的数据课。1.4 回答「RAG 怎么搭」，本篇回答三个生产级问题：

1. **知识在变**：制度下周改版、产品今晚上线，新文档什么时候可检索？（增量更新与新鲜度）
2. **知识有密级**：工资制度只有 HR 能查，权限在哪一层生效？（元数据与权限标签、前置过滤）
3. **知识要负责**：答案错了要能追到「哪份文件哪一版」，数据从哪来、被谁改过？（版本与血缘）

再往前沿走一步（考点 3-2b）：当真实数据不够，**用模型造数据**（self-instruct、蒸馏、自博弈）已是面试出现中的方向题；以及被多数人忽略的长期工作——知识库运营，让 badcase 回流变成数据资产的飞轮。模型与检索算法决定上限，**数据管线决定能不能稳定发挥出上限**。

## 2. 一句话定义

数据与知识工程，是把企业分散在 PDF、Confluence、表格、邮件里的知识，经**采集→清洗→切分→嵌入→索引**五站流水线持续转化为可检索资产，以元数据五件套（部门/密级/时间/版本/血缘）支撑权限前置过滤与全链路追溯，以事件驱动增量更新保障新鲜度 SLA（如 15 分钟内可检索），并用坏例回流与合成数据（self-instruct/蒸馏/自博弈）持续供给数据质量与数量——demo RAG 是烧水壶，企业 RAG 是自来水厂。

## 3. 为什么需要

demo 与企业级的数据面差距：

| 维度 | demo RAG | 企业级 RAG 数据面 |
|---|---|---|
| 数据源 | 一个文件夹几十份 PDF | 十万级文档，PDF/Confluence/邮件/表格多格式 |
| 更新方式 | 手工重跑全量索引 | webhook 事件驱动增量更新，分钟级生效 |
| 权限 | 无 | ACL/密级元数据，检索层前置过滤 |
| 可追溯 | 无 | 每块带版本与血缘，答案可追到文件与版本 |
| 质量保障 | 人工看几条 | 解析成功率/新鲜度/坏例回流，管线即 SLA |
| 失败处理 | 重跑脚本 | 失败队列 + 告警 + 重试幂等 |

三个具体动机：

1. **稳定性**：用户不关心你的检索算法多先进，只关心「问新制度能不能查到、工资制度会不会被别人查到」——前者靠更新流水线，后者靠权限前置。
2. **合规**：删除权、审计（谁在何时查了什么）、答案可追溯，都要求数据面从第一块元数据起就设计好。
3. **规模**：十万文档全量重建索引动辄数小时，增量更新不是优化项而是可用性前提。

## 4. 核心原理

### 4.1 数据管线五站

```text
采集 → 清洗 → 切分 → 嵌入 → 索引
```

| 站 | 做什么 | 关键点 | 失败模式 | SLA 指标 |
|---|---|---|---|---|
| 采集 | 连接器拉取各格式数据源 | webhook/轮询事件化，统一事件总线 | 连接器断连、权限变更未感知 | 采集延迟、事件丢失率 |
| 清洗 | 解析还原、去重去噪、脱敏 | PDF 版式还原、表格转键值、扫描件 OCR、PII 脱敏 | 表格解析错乱、重复文档 | 解析成功率 |
| 切分 | 结构感知切块 | 300~500 字 + 10%~15% 重叠，保留标题路径 | 切碎语义、切块丢失上下文 | 块大小分布 |
| 嵌入 | 向量化 | 批量嵌入、查询与文档同模型 | 模型变更未重建全库 | 嵌入吞吐 |
| 索引 | 向量 + 元数据入库，旧版下架 | 原子替换、按部门分区 | 半新半旧状态、下架遗漏 | 索引新鲜度 |

五站里最被低估的是清洗与采集：企业真实语料里，PDF 表格解析错误率和连接器断连造成的「静默缺文档」，比切块参数调优影响大一个量级。

### 4.2 增量更新与新鲜度约束

全量重建是 demo 思维，生产用**事件驱动的增量流水线**：文档创建/更新/删除都产生事件，webhook 触发「解析→切块→向量化→替换旧版」，端到端延迟即新鲜度 SLA。

以「新文档 15 分钟内可检索」为例做新鲜度预算：

| 阶段 | 预算 | 说明 |
|---|---|---|
| 采集（webhook 到达 + 队列排队） | 2 min | 队列要有积压告警 |
| 解析 + 清洗 | 3 min | PDF 大文件是长尾，超时走慢通道 |
| 切分 | 1 min | 纯 CPU，快 |
| 批量嵌入 | 4 min | 受嵌入 API 吞吐限制，可并发 |
| 索引写入 + 旧版下架 | 2 min | 原子替换，不留半新半旧 |
| 副本/缓存失效传播 | 2 min | 检索缓存按文档版本失效 |
| 余量 | 1 min | 长尾重试 |
| 合计 | 15 min | 端到端监控，超时告警 |

三个工程要点：

1. **变更检测**：不是每个事件都值得重嵌入——对文档内容做哈希，内容没变（仅元数据变动）只更新元数据；变了才走全管线。省下大量嵌入费用。
2. **幂等与原子替换**：同一文档事件重复投递不产生重复块；新块写入与旧块下架在一个事务语义内完成，任何时刻检索不出现新旧混杂。
3. **新鲜度是 SLA 不是口号**：端到端延迟打点监控，超时告警到人；「当天生效」是及格线，「15 分钟」要求把每一站的预算算清楚并持续监控。

### 4.3 元数据与权限标签

每个 chunk 入库时打**元数据五件套**：

| 字段 | 作用 | 缺失后果 |
|---|---|---|
| dept（部门） | 命名空间隔离 + ACL 过滤 | 跨部门数据互见 |
| level（密级） | 公开/内部/秘密分级过滤 | 密件出现在普通问答 |
| effective_time（生效/失效时间） | 只检索现行有效版本 | 已废止制度仍被引用 |
| doc_version（版本） | 增量替换与回滚 | 新旧版本混杂 |
| lineage（血缘：来源文件、页码、父文档） | 答案追溯、审计、删除权 | 无法回答「这答案哪来的」 |

**权限前置过滤是企业 RAG 第一铁律**：权限在检索层生效——无权文档根本不进入候选集。如果文档进了上下文再叮嘱模型「别说出去」，引用链接早已泄露，且注入攻击可直接诱导复述。「不进上下文就无密可泄」是唯一可靠的防线；这要求权限信息在入库时（而不是检索时）就已经结构化好。

### 4.4 版本与血缘

三层版本设计：

1. **文档版本**：每次更新版本号 +1，旧版本块**逻辑下架**（标记失效而非物理删除），保留供审计与回滚。
2. **chunk 血缘**：块记录「来自哪份文件的哪个版本哪一页」，引用（citation）直接落到页级。
3. **索引版本**：全量重建（如换嵌入模型）时建新索引、双跑验证、灰度切换，而非原地覆盖——数据层也有自己的「发布流程」。

血缘的三个用途：答案追溯（用户/审计问「依据是什么」，直接给出文件+版本+页）；删除权合规（用户要求删除某文档，沿血缘清除所有块与缓存）；坏例归因（答案错了，先看检索到的是哪个版本，是不是「旧版没下架」这类管线问题）。

### 4.5 合成数据前沿（self-instruct / 蒸馏 / 自博弈）

真实数据有墙：互联网语料被反复挖过（数据墙），企业标注贵且慢。解法是「用 AI 造 AI 的粮食」——用模型生成训练数据再喂给模型，三条主流生产线：

| 生产线 | 做法 | 代表渊源 | 质检要点 |
|---|---|---|---|
| Self-Instruct 自举 | 少量种子指令让强模型自扩成大规模指令-回答对，去重过滤后训练 | Alpaca 的起家技术 | 种子覆盖度、去重与多样性度量 |
| 强模型蒸馏 | 推理模型生成长思维链，小模型学「怎么想」而非只学答案 | R1 蒸馏小模型 | 过程保真、口吻与知识边界即天花板 |
| 自博弈 / 可验证自进化 | 模型自出题，程序判卷（代码跑测试、数学对答案），只保留验证通过的样本 | AlphaZero 式自我对弈思想 + RLVR 数据引擎 | 判卷器本身要可信，防 reward hacking |

口径提示：这是**前沿方向级考点，面试中出现中**，考的是认知框架而非细节——能说出三条生产线、说清最大风险、给出落地配方，就是满分答卷。

最大风险是**模型崩塌（model collapse）**：用模型生成数据反复自训，几代之后多样性坍塌、错误被逐代放大——照镜子式的近亲繁殖。工业级配方因此是：**合成 + 真实数据混炼**（掺 20%~30% 真实标注当「锚」）、控制自训代数、优先选可验证领域（数学/代码有程序判卷员，质量有保底）。另一条红线是法律：多数模型厂商服务条款禁止用其输出训练竞品模型，商用前必须过法务确认授权链；合成数据混入测试集还会造成评测污染。

### 4.6 知识库运营：坏例回流

管线建完只是开始，知识库是运营出来的：

1. **坏例回流**：线上 badcase（答错、检索错、引用错版本）经归因后转成三样资产——评测集新用例、管线修复项、文档补录任务。回归飞轮与 2.9 的评测闭环、3.5 的评估体系共用同一套机制。
2. **管线即 SLA**：新鲜度（端到端更新延迟）、解析成功率、失败队列深度、检索零命中率查询占比，都是需要看板与告警的运营指标。
3. **零命中与低分查询**：检索不到或得分很低的查询是「知识缺口清单」，定期交给内容运营补文档——知识库的边界由运营持续外推。

## 5. 架构 / 流程

企业数据面四层与一次增量更新的旅程：

```text
┌───────────────────────────────────────────────────────────┐
│ 接入层  连接器池: Confluence API / 网盘监听 / 邮件网关        │
│         统一事件总线: 创建/更新/删除 → 事件(带文档ID+版本)    │
└────────────────────────┬──────────────────────────────────┘
                         ↓ webhook 事件
┌───────────────────────────────────────────────────────────┐
│ 处理层  内容哈希变更检测 →(没变)只更新元数据                  │
│         ↓(变了)                                            │
│   按格式路由解析: PDF版式还原 / 表格转键值 / OCR / HTML      │
│   清洗脱敏(PII/密钥) → 结构化切块(300~500字,15%重叠)         │
│   每块打元数据五件套: {dept, level, time, version, lineage} │
└────────────────────────┬──────────────────────────────────┘
                         ↓ 新块 + 元数据
┌───────────────────────────────────────────────────────────┐
│ 索引层  批量嵌入 → 向量库按部门分区写入                       │
│         旧版本块逻辑下架(保血缘供审计) —— 原子替换            │
└────────────────────────┬──────────────────────────────────┘
                         ↓ 可检索 (SLA: 15 分钟内)
┌───────────────────────────────────────────────────────────┐
│ 服务层  检索前权限前置过滤: 用户身份 → {dept 白名单, 密级上限} │
│         查询审计: 谁何时检索/引用了哪份文件                   │
└────────────────────────┬──────────────────────────────────┘
                         ↓ badcase / 零命中查询
┌───────────────────────────────────────────────────────────┐
│ 运营层  管线看板: 新鲜度/解析成功率/失败队列                  │
│         坏例回流 → 评测集 + 修复项 + 补录任务                 │
└───────────────────────────────────────────────────────────┘
```

## 6. 代码 / 工具

### 6.1 增量索引流水线

事件驱动的增量更新：变更检测、重嵌入、旧版原子下架。

```python
"""incremental_index.py — webhook 驱动的增量索引（示意）"""
import hashlib

CHROMA = ...  # 向量库客户端（Chroma/Qdrant/pgvector 均可），略


def content_hash(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8")).hexdigest()


def on_doc_event(event: dict):
    """事件: {"doc_id", "version", "text", "meta": {dept, level, effective_at}}"""
    doc_id, version, meta = event["doc_id"], event["version"], event["meta"]

    # 1) 变更检测：内容没变只更新元数据，省嵌入费用
    h = content_hash(event["text"])
    old = CHROMA.get(where={"doc_id": doc_id, "is_current": True})
    if old["ids"] and old["metadatas"][0][0].get("content_hash") == h:
        update_metadata_only(doc_id, meta)
        return

    # 2) 清洗 + 切分（结构感知切块的简化版）
    blocks = [b.strip() for b in split_by_heading(event["text"]) if b.strip()]

    # 3) 嵌入（批量，生产加并发与限流）
    vectors = embed_batch(blocks)

    # 4) 原子替换：写新块 → 旧块逻辑下架（保留血缘供审计）
    new_ids = [f"{doc_id}:v{version}:{i}" for i in range(len(blocks))]
    CHROMA.add(
        ids=new_ids,
        embeddings=vectors,
        documents=blocks,
        metadatas=[{
            "doc_id": doc_id, "doc_version": version,
            "dept": meta["dept"], "level": meta["level"],
            "effective_at": meta["effective_at"],
            "content_hash": h, "is_current": True,
            "lineage": f"{doc_id}#v{version}#block{i}",
        } for i in range(len(blocks))],
    )
    CHROMA.update(ids=old["ids"],
                  metadatas=[{**m, "is_current": False} for m in old["metadatas"][0]])
    record_pipeline_latency(event["received_at"])  # 打新鲜度 SLA 点
```

### 6.2 检索层权限前置过滤

用户身份转成过滤器，无权文档根本不进候选：

```python
"""permission_search.py — 权限前置过滤检索"""
LEVEL_ORDER = {"public": 0, "internal": 1, "secret": 2}


def build_acl_filter(user: dict) -> dict:
    """用户身份 → 检索过滤器：部门白名单 + 密级上限"""
    return {"$and": [
        {"dept": {"$in": user["depts"]}},                      # 部门白名单
        {"level": {"$in": [lv for lv in LEVEL_ORDER
                           if LEVEL_ORDER[lv] <= LEVEL_ORDER[user["max_level"]]]}},
        {"is_current": True},                                   # 只检索现行版本
    ]}


def search(user: dict, query: str, top_k: int = 5):
    # 无权文档在向量库阶段就被过滤——不进上下文就无密可泄
    res = CHROMA.query(query_texts=[query], n_results=top_k,
                       where=build_acl_filter(user))
    audit_log(user["id"], query, [m["lineage"] for m in res["metadatas"][0]])
    return res["documents"][0]


# HR 用户可查工资制度
search({"id": "u1", "depts": ["hr", "public"], "max_level": "secret"},
       "工资制度里年假顺延怎么规定？")
# 普通研发用户：工资制度(dept=hr, level=secret)根本不在候选集
search({"id": "u2", "depts": ["rd", "public"], "max_level": "internal"},
       "工资制度里年假顺延怎么规定？")   # → 返回空或不相关的一般资料
```

### 6.3 Self-Instruct 合成数据小样

前沿生产线 1 的最小示意（种子扩展 + 去重过滤）：

```python
"""self_instruct.py — 指令自举的骨架示意"""
SEEDS = [
    "帮我总结这份退货政策的要点",
    "对比 A、B 两个套餐的流量与价格差异",
]

def synthesize(seeds, n=50):
    out = []
    for i in range(n):
        seed = seeds[i % len(seeds)]
        # 生产中用强模型做：改写任务 + 变换领域 + 生成回答，三段式自扩
        new_instr = llm(f"基于任务改写出一个新任务（换场景/换约束）: {seed}")
        new_answer = llm(new_instr)
        out.append({"instruction": new_instr, "answer": new_answer})
    return out


def dedup_and_filter(samples, sim_threshold=0.9):
    """去重（嵌入余弦相似度）+ 规则质检，控制多样性坍塌"""
    keep, seen_vecs = [], []
    for s in samples:
        v = embed(s["instruction"])
        if all(cosine(v, w) < sim_threshold for w in seen_vecs):
            if passes_quality_check(s):          # 规则/裁判模型质检
                keep.append(s)
                seen_vecs.append(v)
    return keep
# 落地提醒：混入 20%~30% 真实标注数据；商用前确认上游模型服务条款
```

## 7. 案例

### 案例 A：10 万文档企业知识库数据面

某制造企业 10 万份文档（PDF 6 万、Confluence 3 万、表格 1 万），要求部门隔离、密级分级、新文档当天生效。数据面按第 5 节四层落地：连接器池统一事件总线；PDF 走版式还原（解析成功率 91%→98% 是首轮攻坚重点）；切块 400 字 + 15% 重叠，全量打元数据五件套；向量库按部门分区，检索层 ACL + 密级前置过滤。上线半年零越权事件；一次审计追溯到「某答案引用了已废止的 v3 版制度」，顺血缘发现旧版下架逻辑的并发漏洞并修复——血缘设计直接把一次潜在合规事故变成一行修复。

### 案例 B：15 分钟新鲜度 SLA 达成

一家金融科技公司的制度知识库要求「新制度上传 15 分钟内可检索」。初始全量重建需 6 小时，完全不达标。改造为增量流水线并按 4.2 拆预算：webhook 触发、内容哈希变更检测（消掉 60% 的无效重嵌入）、嵌入批量并发、旧版原子下架、检索缓存按文档版本失效。端到端 p95 从 6 小时压到 9 分钟，新鲜度达标率 99.2%；管线看板上「失败队列深度」告警让一次 Confluence 连接器断连在 20 分钟内被发现修复，而不是等到用户投诉「查不到新制度」。

### 案例 C：合成数据微调客服小模型

某电商想用 8B 小模型替代部分客服问答。方案：以 3 个月真实客服日志的问题分布为骨架，用强模型生成 20 万条「问题-回答」候选（self-instruct 变体），规则引擎 + 抽检做质检（生成回答约 12% 违反业务规则被过滤），掺 25% 真实人工标注数据混炼训练。效果：领域问答准确率从基座 61% 升到 84%，标注成本约为纯人工方案的三分之一。同时踩过坑：第一版未混真数据，模型对「超出强模型知识边界」的内部政策一律编造，混入真数据并按知识缺口补生成后才收敛。商用前法务确认了上游服务的输出使用条款。

## 8. 常见坑

1. **全量重建当更新手段**。  
   十万文档重建数小时，知识永远滞后；事件驱动增量更新 + 新鲜度 SLA 才是生产形态。

2. **新鲜度没有打点**。  
   「当天生效」靠感觉；端到端延迟必须监控告警，15 分钟 SLA 要拆到每一站的预算。

3. **权限靠 prompt 约束**。  
   文档进了上下文再叮嘱「别泄露」必泄露；权限必须在检索层前置过滤，无权不进候选。

4. **元数据不存权限与时间**。  
   部门、密级、生效时间缺失，过滤无从谈起；五件套在入库时就要结构化好。

5. **旧版本物理删除**。  
   审计与回滚无据可查；旧版块逻辑下架、保留血缘。

6. **切块丢失结构信息**。  
   标题路径不进块，检索到孤立段落无法理解语境；切块要携带「章节路径」。

7. **换嵌入模型不重建索引**。  
   新旧向量空间不一致，检索静默劣化；换模型 = 新索引双跑验证后灰度切换。

8. **变更检测缺失**。  
   每个事件都重嵌入，费用翻倍；内容哈希不变只更新元数据。

9. **管线静默失败**。  
   连接器断连、解析失败没人知道；失败队列 + 积压告警是管线 SLA 的一部分。

10. **合成数据直接全量训练**。  
    不混真数据导致分布单一、边界外一律编造；混 20%~30% 真实数据当锚，控自训代数防模型崩塌。

11. **拿上游输出训练不管条款**。  
    多数厂商禁止用于竞品模型训练；商用前过法务确认授权链。

12. **合成数据混进测试集**。  
    评估分数虚高（评测污染）；训练集与评测集物理隔离。

13. **badcase 修完即弃**。  
    同样的失败换个皮再来；坏例必须回流成评测用例与补录任务，形成飞轮。

14. **只盯着算法调优**。  
    企业场景里 PDF 表格解析错误与连接器断连的影响远大于切块参数；先把管线稳定性做好。

## 9. 练习

1. 给 1.4b 你搭的 RAG 加增量更新：webhook 事件触发，内容哈希检测变更，旧版本逻辑下架。
2. 为你的向量库实现元数据五件套（dept/level/time/version/lineage），并写一个权限前置过滤的检索函数。
3. 设计一份「15 分钟可检索」的新鲜度预算表，给每一站定预算并说明超时后的降级策略。
4. 构造一份多格式小语料（PDF/HTML/表格各 3 份），统计解析成功率，找出失败模式并修复。
5. 用 self-instruct 思路生成 50 条客服指令数据，做去重与质检，统计被过滤的比例与原因。
6. 写一段模型崩塌的验证小实验：用模型输出迭代训练（或模拟）两代，度量输出多样性变化。
7. 建一个知识库运营看板：新鲜度、解析成功率、零命中查询 Top10，每周导出一次。
8. 从线上收集 5 条 badcase，按「检索问题 / 版本问题 / 生成问题」归因，并各转成一条评测集用例。

## 10. 小结

- 数据管线五站：**采集 → 清洗 → 切分 → 嵌入 → 索引**，清洗与采集的稳定性比切块调优更影响生产质量。
- 增量更新三件：**事件驱动流水线、内容哈希变更检测、原子替换旧版下架**；新鲜度是 SLA，15 分钟可检索靠逐站预算与监控。
- 元数据五件套：**部门、密级、时间、版本、血缘**——权限前置过滤与全链路追溯的地基。
- 权限铁律：**检索层前置过滤，无权文档不进候选**；不进上下文就无密可泄。
- 版本与血缘支撑三件事：答案追溯、删除权合规、坏例归因；换嵌入模型 = 新索引双跑灰度切换。
- 合成数据三条生产线：**self-instruct 自举、强模型蒸馏、自博弈/可验证自进化**；最大风险是模型崩塌，配方是混真数据 + 控代数 + 优先可验证领域；商用先过法务。
- 知识库是运营出来的：**坏例回流评测集、零命中查询补文档、管线指标看板化**。
- 数据面放进完整知识库全案在 4.2/4.2b，权限合规视角在 3.8，评测飞轮与 2.9/3.5 同一机制。
