## 1. 定位

AI 工程化层第 2 个知识点，属于「数据基础设施」。  
它解决一个核心问题：**如何把原始、杂乱、分散的数据，变成 Agent 可用、高质量、可维护的知识资产？**  
并正面回答贯穿本篇的关键问题：**知识如何持续更新且可追溯？**（4.9 集中回答）

与 1.4 的分工：1.4 讲 RAG 系统内「切分/检索/重排」的机制与取舍；本篇讲知识资产本身的工程化管理——数据源管理、清洗流水线、标注体系、版本与血缘（Data Lineage）、权限与合规、持续更新机制。切分策略的机制细节收敛到 1.4，本篇只保留工程选型视角。

直接前置是 1.4（RAG 组件机制已就位）；后续承接 3.5（评估数据集从哪来）与 4.2（RAG 实战的知识底座）；2.4 的长期记忆同样消费这里的知识供给。

## 2. 一句话定义

数据与知识工程，是对数据的采集、清洗、切分、标注、索引、版本管理、权限控制和持续更新进行系统化管理，为 AI 系统提供可靠知识供给的工程体系。

简化公式：

```text
知识工程 = 采集 + 清洗 + 切分 + 标注 + 索引 + 版本 + 权限 + 更新
```

## 3. 为什么需要

RAG 效果不好，业内复盘的共识量级是八成出在数据上：

- **数据源杂乱**：PDF、Word、HTML、数据库、API，格式各异。
- **质量参差**：过时、错误、重复、矛盾的内容混在一起。
- **切分不当**：太大噪音多，太小语义碎。
- **无版本管理**：知识更新了，不知道哪些变了。
- **无权限控制**：A 部门能看 B 部门的机密文档。
- **无更新机制**：知识库半年没更新，回答过时。
- **无评估反馈**：不知道哪些文档被检索、哪些没用。
- **无溯源**：答案错了，不知道来自哪篇文档。

没有知识工程 vs 有知识工程：

| 维度 | 没有知识工程 | 有知识工程 |
|---|---|---|
| 新鲜度 | 半年不更新，答过时政策 | 定时/事件/CDC 增量，分钟到小时级新鲜 |
| 出错追溯 | 答案错了查不到来源 | 版本 + 血缘定位到具体 chunk 与源文档 |
| 权限 | 跨部门、跨租户泄露 | 检索层强制过滤，零泄露 |
| 评估复现 | 换一版数据，结果不可比 | 数据集带版本，结果可比 |
| 成本 | 每次全量重建 | 增量更新，嵌入调用降一个量级 |

**类比**：

```text
LLM    = 一个聪明的学生
数据   = 学生读的教材
RAG    = 开卷考试
教材质量差 → 再聪明的学生也考不好
```

## 4. 核心原理

### 4.1 数据来源分类

| 来源 | 格式 | 特点 | 处理难点 |
|---|---|---|---|
| 文档 | PDF、Word、Markdown | 结构化好 | 解析、表格、图片 |
| 网页 | HTML | 内容丰富 | 去广告、动态内容 |
| 数据库 | SQL | 结构化 | Schema 理解、关联 |
| API | JSON | 实时 | 限流、格式变化 |
| 对话 | 文本 | 口语化 | 噪音、隐私 |
| 代码 | 多语言 | 结构化 | 语法树、注释 |
| 邮件/IM | 文本 | 非正式 | 线程、引用 |

不同来源的「变更信号」不同：文件靠 mtime 与内容哈希，网页靠爬虫 diff，数据库靠 updated_at 或 CDC，API 靠游标/分页。变更信号决定了 4.9 更新触发的选型。

### 4.2 数据采集

**原则**：

- **全量 vs 增量**：首次全量，后续增量。
- **定时 vs 实时**：文档定时，API 实时。
- **拉取 vs 推送**：主动拉取或订阅变更。
- **去重**：内容哈希（Content Hash）、URL 去重。

**采集管道**：

```python
import re  # 清洗会用到
from pathlib import Path

class DataCollector:
    async def collect(self, source: dict) -> list[dict]:
        if source["type"] == "file":
            return await self._collect_files(source["path"])
        elif source["type"] == "web":
            return await self._crawl(source["urls"])
        elif source["type"] == "database":
            return await self._query_db(source["connection"], source["query"])
        elif source["type"] == "api":
            return await self._call_api(source["endpoint"])

    async def _collect_files(self, path: str) -> list[dict]:
        documents = []
        for file in Path(path).rglob("*"):
            if file.suffix in [".pdf", ".docx", ".md", ".txt"]:
                content = await parse_file(file)
                documents.append({
                    "content": content,
                    "source": str(file),
                    "type": file.suffix,
                    "mtime": file.stat().st_mtime,  # 增量检测信号
                })
        return documents
```

### 4.3 数据清洗

**清洗内容**：

| 问题 | 处理 |
|---|---|
| 页眉页脚 | 正则去除 |
| 广告 | 规则 + 模型过滤 |
| 乱码 | 编码统一 UTF-8 |
| 重复 | 哈希去重、语义去重 |
| 空白 | 规范化 |
| 敏感信息 | 脱敏（个人敏感信息，PII） |
| 过时内容 | 时间过滤 |
| 错误内容 | 人工审核 |

**清洗管道**：

```python
import re

class DataCleaner:
    def clean(self, doc: dict) -> dict:
        text = doc["content"]

        # 1. 去除页眉页脚
        text = re.sub(r"第 \d+ 页.*?\n", "", text)

        # 2. 去除多余空白
        text = re.sub(r"\n{3,}", "\n\n", text)
        text = re.sub(r" {2,}", " ", text)

        # 3. 去除广告
        text = self._remove_ads(text)

        # 4. 脱敏
        text = self._mask_pii(text)

        # 5. 去重（与已有文档对比）
        if self._is_duplicate(text):
            return None

        doc["content"] = text
        doc["cleaned_at"] = now()
        return doc

    def _mask_pii(self, text: str) -> str:
        text = re.sub(r"\d{11}", "[手机]", text)
        text = re.sub(r"\d{18}", "[身份证]", text)
        return text
```

### 4.4 切分与元数据

切分策略的机制推导（为什么递归切分是默认、语义切分何时值得、父子块如何工作）在 1.4 详解，向量与嵌入基础见 0.7。本篇只保留工程选型速查：

| 策略 | 实现 | 适用 |
|---|---|---|
| 固定长度 | 按 token 数切 | 通用 |
| 递归切分 | 按段落→句子→词 | 推荐默认 |
| 语义切分 | 嵌入相似度断点 | 高质量 |
| 结构切分 | 按标题/章节 | 结构化文档 |
| 父子切分 | 小块检索，大块返回 | RAG 推荐 |

**面试高频问法**：「如何设计 RAG 知识库的构建方案？切分策略怎么定？」共识口径：按文档结构选策略——结构化文档优先按标题/章节切，通用文本用递归切分兜底，块大小 256–1024 token、重叠 10%–20% 起步，最后用评估集（见 3.5）验证，而不是拍脑袋定参数。

### 4.5 数据标注（Annotation）

**标注类型**：

| 类型 | 说明 | 用途 |
|---|---|---|
| 分类标注 | 文档分类 | 路由、过滤 |
| 质量标注 | 好/坏 | 数据清洗 |
| 相关性标注 | 查询-文档相关性 | RAG 评估 |
| 问答标注 | 问题-答案对 | 评估集 |
| 偏好标注 | A/B 哪个好 | 微调、评估 |

**标注方式对比**（截至 2026 年，LLM 预标注 + 人工复核已是标注流水线的主流起点，趋势观察）：

| 方式 | 做法 | 单条成本 | 吞吐 | 一致性 |
|---|---|---|---|---|
| 纯人工 | 人逐条标 | 高 | 低 | 依赖规范与培训 |
| LLM 预标注 + 人工复核 | 模型先标，人只改错 | 中 | 中高 | 高，复核纠正模型漂移 |
| 主动学习（Active Learning） | 模型挑最不确定的样本送人标 | 中（总量下降） | 中 | 高 |
| 规则/弱监督 | 正则与启发式自动标 | 低 | 高 | 低，必须抽检 |

**标注流程**：

```text
1. 定义标注规范
2. 抽样
3. 多人标注
4. 计算一致性（Cohen's Kappa，标注者间一致性系数）
5. 解决分歧
6. 形成金标准
```

**标注工具**：Label Studio、Argilla、Prodigy（以各自官方文档为准），以及自建。

### 4.7 版本管理与数据血缘（Data Lineage）

**为什么需要版本**：

- 知识更新了，要知道变了什么。
- 出问题要回滚。
- 评估要可复现。
- 合规要可追溯。

**版本对象**：

| 对象 | 版本方式 |
|---|---|
| 文档 | 内容哈希 + 时间戳 |
| 索引 | 索引版本号 |
| 嵌入模型 | 模型版本 |
| 切分策略 | 策略版本 |
| 评估集 | 数据集版本 |

**数据版本方案对比**：

| 方案 | 思路 | 优点 | 局限 |
|---|---|---|---|
| 自建元数据（内容哈希 + 版本号入库） | 每次入库记录哈希、时间、来源 | 与检索栈天然集成，可按 chunk 追溯 | diff 与回滚要自己实现 |
| Git + DVC | 大文件用内容指针管理 | 与代码、切分策略同仓，版本语义成熟 | 面向文件而非向量索引 |
| lakeFS 一类数据湖分支 | 数据湖上的 Git 分支模型 | 支持大规模文件、分支隔离实验 | 引入新组件，有运维成本 |

选型口径：要按 chunk 追溯、检索栈自研 → 自建元数据；语料以文件形态管理、团队已有 Git 流程 → DVC；多环境隔离做数据实验 → lakeFS。三者不互斥，常见组合是「向量索引自建元数据 + 语料仓走 DVC」。

**数据血缘**：一条从检索结果反推回源头的链路：

```text
chunk_005 ──→ doc_123（v2.1，内容哈希 ab12…）
                  │
                  ├──→ source：Confluence 空间「售后政策」
                  └──→ 处理链：清洗规则 v5 · 切分策略 v3 · 嵌入模型 v2
```

答案出错时，沿这条链能回答「这条内容来自哪篇文档哪个版本、被哪套处理规则加工过」。

**类比**：没有版本与血缘的知识库 = 没有编目卡的图书馆——任何人都能往里塞书，没人知道某本书是第几版、谁捐的、有没有被换过页；有版本与血缘 = 每本书有版次、采购单、修订记录，馆长随时能回答「第 2 版改了什么、什么时候进的馆」。

**最小实现**：

```python
class KnowledgeVersion:
    def __init__(self, version: str):
        self.version = version
        self.documents = {}
        self.created_at = now()
        self.changes = []

    def add_document(self, doc_id: str, content: str):
        old = self.documents.get(doc_id)
        if old != content:
            self.changes.append({
                "doc_id": doc_id,
                "action": "update" if old else "add",
                "timestamp": now(),  # 变更审计的最小记录
            })
        self.documents[doc_id] = content

    def diff(self, other: "KnowledgeVersion") -> dict:
        added = set(other.documents) - set(self.documents)
        removed = set(self.documents) - set(other.documents)
        changed = {
            k for k in set(self.documents) & set(other.documents)
            if self.documents[k] != other.documents[k]
        }
        return {"added": added, "removed": removed, "changed": changed}
```

### 4.9 知识更新：持续更新且可追溯

本篇关键问题的正面回答，拆成两半：怎么持续更新（触发 + 策略），怎么可追溯（版本 + 血缘 + 审计）。

**更新触发方式对比**：

| 触发方式 | 机制 | 典型新鲜度 | 复杂度 | 适用 |
|---|---|---|---|---|
| 定时调度 | 调度器周期性拉取 | 小时～天 | 低 | 文档类、变更低频 |
| 事件推送（Webhook） | 源系统变更时回调 | 分钟级 | 中 | Confluence、SharePoint、Git |
| 变更数据捕获（Change Data Capture，CDC） | 订阅数据库 binlog（如 Debezium 一类 CDC 中间件） | 秒～分钟 | 高 | 数据库为主的源 |

**更新策略对比**：

| 策略 | 做法 | 新鲜度 | 成本 | 适用 |
|---|---|---|---|---|
| 全量重建 | 重新索引所有内容 | 低 | 最高 | 嵌入模型或切分策略变更后 |
| 增量更新（Incremental Update） | 只处理变更文档 | 高 | 低 | 日常默认 |
| 实时更新 | 变更立即索引 | 最高 | 高 | 有分钟级新鲜度约束 |
| 定时批量 | 每天固定窗口跑 | 中 | 低 | 容忍天级滞后 |

**可追溯三件套**：

- **版本**：内容哈希 + 版本号，回答「变了什么」（见 4.7）。
- **血缘**：chunk → 文档 → 源 → 处理链，回答「内容从哪来」（见 4.7）。
- **变更审计**：每次更新记录谁、何时、改了哪些文档、影响哪些 chunk、评估结果如何，回答「谁动的、能不能回滚」。

三者合起来，才敢说知识库「持续更新且可追溯」：更新可增量、可灰度、可回滚，出错可定位到 chunk 级。

**防污染**：更新不是直接覆盖线上索引。正确姿势是「影子索引 → 评估门禁 → 灰度切换」（评估门禁机制见 3.9），否则就是案例 B 的事故。

**类比**：城市导航地图——新路通车后，地图厂商靠众包轨迹与市政数据触发更新（事件/CDC），只重算受影响的路段（增量），并保留历史版本可回退；而不是每隔半年把全国地图推倒重画一遍（全量重建）。

**面试高频问法**：「知识库每天有几万篇新文档，怎么保证 15 分钟内可检索且不污染旧答案？」（一线大厂系统设计真题约束的转写）共识口径分三层：触发层用事件推送或 CDC 而非定时轮询，把变更检测延迟压到分钟级；摄入层只做增量——内容哈希判重、只嵌入变更文档、只替换受影响的 chunk；质量层先入影子索引过评估门禁再灰度切换，版本与血缘落账，出问题可回滚。

**增量更新实现**：

```python
async def incremental_update(source: str):
    # 1. 获取变更（定时/事件/CDC 触发后调用）
    changes = await detect_changes(source)

    # 2. 删除旧索引
    for doc_id in changes["removed"]:
        await vector_store.delete(doc_id)
        await bm25_index.delete(doc_id)

    # 3. 添加新索引
    for doc in changes["added"] + changes["changed"]:
        chunks = split(doc)
        await index_chunks(chunks)

    # 4. 记录版本与审计
    await version_store.record(changes)
```

## 5. 架构 / 流程

知识不是一次性灌进去的静态资产，而是一条带更新闭环的生命周期：

```text
┌──────────────────────────────────────────────┐
│ 管理面（贯穿全生命周期）                      │
│ 版本与血缘 ｜ 权限与合规 ｜ 质量监控 ｜ 审计   │
└──────────────────────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ ① 采集层                                     │
│ ├─ 全量/增量、定时/实时（定时/事件/CDC）      │
│ └─ 去重                                      │
└──────────────────────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ ② 清洗层：格式解析｜去噪｜脱敏｜质量检查      │
└──────────────────────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ ③ 切分层：结构/递归切分（机制见 1.4）        │
│            + 元数据打标                       │
└──────────────────────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ ④ 标注层（可选）：分类/质量/相关性｜人工审核  │
└──────────────────────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ ⑤ 索引层：向量｜BM25｜元数据｜图（可选）      │
└──────────────────────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ ⑥ 服务层：检索/更新/管理 API                 │
│            权限过滤、审计日志                  │
└──────────────────────────────────────────────┘
       ↓ 检索日志 / 用户反馈 / 源系统变更
┌──────────────────────────────────────────────┐
│ ⑦ 更新闭环：变更触发 → 检测变更 → 增量摄入    │
│    → 评估门禁 → 灰度切换 → 版本落账           │
└──────────────────────────────────────────────┘
        │
        └──→ 回到 ①，知识生命周期循环
```

### 6.1 完整数据管道

```python
import hashlib
import re
from pathlib import Path
from datetime import datetime
# from langchain.text_splitter import RecursiveCharacterTextSplitter

class KnowledgePipeline:
    def __init__(self, vector_store, bm25_index, metadata_store):
        self.vector_store = vector_store
        self.bm25_index = bm25_index
        self.metadata_store = metadata_store
        self.splitter = RecursiveCharacterTextSplitter(
            chunk_size=512,
            chunk_overlap=64,
            separators=["\n\n", "\n", "。", "！", "？", " ", ""],
        )

    async def ingest(self, source: dict, tenant_id: str):
        # 1. 采集
        documents = await self._collect(source)

        # 2. 清洗
        cleaned = []
        for doc in documents:
            cleaned_doc = self._clean(doc)
            if cleaned_doc and not self._is_duplicate(cleaned_doc):
                cleaned.append(cleaned_doc)

        # 3. 切分
        chunks = []
        for doc in cleaned:
            for i, chunk in enumerate(self.splitter.split_text(doc["content"])):
                chunks.append({
                    "id": f"{doc['id']}_chunk{i}",
                    "content": chunk,
                    "metadata": {
                        "source": doc["source"],
                        "tenant_id": tenant_id,
                        "created_at": datetime.now().isoformat(),
                        **doc.get("metadata", {}),
                    },
                })

        # 4. 索引
        await self._index(chunks)

        return {"documents": len(cleaned), "chunks": len(chunks)}

    async def _index(self, chunks: list[dict]):
        # 向量索引
        embeddings = await embed_batch([c["content"] for c in chunks])
        await self.vector_store.upsert(
            ids=[c["id"] for c in chunks],
            embeddings=embeddings,
            documents=[c["content"] for c in chunks],
            metadatas=[c["metadata"] for c in chunks],
        )

        # BM25
        await self.bm25_index.add(chunks)

        # 元数据
        await self.metadata_store.add(chunks)

    def _clean(self, doc: dict) -> dict:
        text = doc["content"]
        text = re.sub(r"第 \d+ 页.*?\n", "", text)
        text = re.sub(r"\n{3,}", "\n\n", text)
        text = re.sub(r"\d{11}", "[手机]", text)
        if len(text.strip()) < 50:
            return None  # 太短的块没有检索价值
        doc["content"] = text
        return doc

    def _is_duplicate(self, doc: dict) -> bool:
        content_hash = hashlib.md5(doc["content"].encode()).hexdigest()
        return self.metadata_store.exists_hash(content_hash)
```

### 6.2 增量更新

```python
class IncrementalUpdater:
    def __init__(self, pipeline, version_store):
        self.pipeline = pipeline
        self.version_store = version_store

    async def update(self, source: str, tenant_id: str):
        # 1. 获取当前版本
        current = await self.version_store.get_latest(source)

        # 2. 检测变更
        changes = await self._detect_changes(source, current)

        # 3. 删除
        for doc_id in changes["removed"]:
            await self.pipeline.delete(doc_id)

        # 4. 添加/更新
        for doc in changes["added"] + changes["changed"]:
            await self.pipeline.ingest(doc, tenant_id)

        # 5. 记录版本与审计
        await self.version_store.record(source, changes)

        return changes

    async def _detect_changes(self, source: str, current) -> dict:
        new_docs = await self.pipeline._collect(source)
        new_ids = {d["id"] for d in new_docs}
        old_ids = set(current.documents.keys())

        return {
            "added": [d for d in new_docs if d["id"] not in old_ids],
            "removed": list(old_ids - new_ids),
            "changed": [
                d for d in new_docs
                if d["id"] in old_ids and current.documents[d["id"]] != d["content"]
            ],
        }
```

```python
class KnowledgeMonitor:
    def __init__(self, metadata_store):
        self.store = metadata_store

    async def report(self, tenant_id: str) -> dict:
        docs = await self.store.list(tenant_id=tenant_id)

        return {
            "total_docs": len(docs),
            "stale_docs": sum(1 for d in docs if self._is_stale(d)),
            "empty_docs": sum(1 for d in docs if len(d["content"]) < 50),
            "duplicate_docs": self._count_duplicates(docs),
            "avg_length": sum(len(d["content"]) for d in docs) / len(docs),

        }

        updated = datetime.fromisoformat(doc["updated_at"])
```

### 案例 A：企业知识库建设

**需求**：某制造企业，约 10000 份内部文档，5 个部门，多租户隔离。

**管道**：

```text
1. 采集：从 Confluence、SharePoint、文件系统
2. 清洗：去页眉、脱敏、去重
3. 切分：按标题结构 + 递归切分
4. 元数据：部门、权限、时间、来源
5. 索引：向量 + BM25
6. 权限：按部门和角色过滤
7. 更新：每天增量更新（事件推送，平均 20 分钟内入库）
```

**效果**（示意量级）：检索召回率约 90%，权限渗透测试零泄露；每日更新从「全量重建 4 小时」压到「增量 20 分钟」，嵌入调用量下降约 95%——只有变更文档重新嵌入。

### 案例 B：知识更新导致回归

**问题**：知识库例行更新后，RAG 回答质量下降，用户投诉增多。

**排查**：

1. 对比新旧版本 diff（4.7 的版本机制在此发挥作用）。
2. 评估集 300 题：首轮命中率从 82% 掉到 71%（示意量级）。
3. 发现某文档切分位置变了，一张价格表被从中间切断，关键数字与上下文分家。
4. 定位：切分策略升了版本，但没有重新评估就全量切换。

**修复**：

1. 固定切分策略版本，切换前先在影子索引跑评估集。
2. 更新后强制过评估门禁，回归超阈值自动阻断（机制见 3.9）。
3. 灰度更新，监控指标。修复后命中率回到 83%（示意量级）。

### 案例 D：高新鲜度知识库（15 分钟可检索）

**需求**：某资讯平台，日增约 3 万篇文章，要求新内容 15 分钟内可检索，且不能让低质、重复内容污染已有答案。

**做法**：

1. 触发：CMS 发布事件经消息队列推送（事件驱动），不做定时轮询。
2. 摄入：内容哈希判重，拦截约 30% 的转载与重复（示意量级）；LLM 预标注质量分，低于阈值进人工队列。
3. 索引：增量只嵌入新文档，新内容平均 8 分钟可检索。
4. 防污染：新内容先进影子索引，抽 5% 流量灰度验证无回归后切换；每次切换落版本与审计。

**效果**（示意量级）：新鲜度从天级提升到分钟级；一次坏数据投放被评估门禁拦下，10 分钟内回滚，线上无感。

## 8. 常见坑

1. **不清洗直接索引**。  
   噪音多，检索质量差。清洗规则可以先粗后细，但不能没有。

2. **切分策略随意**。  
   不按文档结构调整，语义断裂。用递归 + 结构切分（机制见 1.4）。

3. **无元数据**。  
   无法过滤、无法溯源、无法引用。入库前必须打标签。

4. **无版本管理**。  
   知识更新后无法回滚，评估无法复现。内容哈希 + 版本号是最低配置。

5. **无权限控制**。  
   多租户场景数据泄露。检索层强制行级过滤，不能靠前端隐藏。

6. **不做去重**。  
   重复内容降低检索质量，浪费存储。哈希去重打底，重点场景加语义去重。

7. **不做增量更新**。  
   每次全量重建，成本高、延迟大。日常更新走增量，全量只留给模型/策略变更。

8. **不监控质量**。  
   不知道知识库健康度，问题累积。定期输出重复率、过期率、命中率报表。

9. **不处理 PII**。  
   合规风险。入库前脱敏，日志侧同样要脱敏。

10. **不记录来源**。  
    答案错了无法追溯。必须存 source，最好到 chunk 级血缘。

11. **不评估检索**。  
    不知道检索质量，无法优化。评估集建设见 3.5。

12. **忽略嵌入模型版本**。  
    换模型后旧向量失效，混用两种向量空间。必须整体重建索引。

13. **不做数据血缘**。  
    不知道数据从哪来、经过了什么处理。记录 chunk → 文档 → 源 → 处理链。

14. **不区分冷热数据**。  
    所有数据同样处理，成本高。冷数据降频更新、可压缩，热数据保持新鲜。

15. **不做人工审核**。  
    自动采集可能引入错误内容。关键知识（政策、价格、合规）要人工审核后入库。

## 10. 小结

- 知识工程 = **采集 + 清洗 + 切分 + 标注 + 索引 + 版本 + 权限 + 更新**。
- 采集：**全量/增量、定时/事件/CDC、去重**，变更信号按源类型选。
- 清洗：**去噪、脱敏、格式统一、质量检查**。
- 切分：**递归/语义/结构/父子，256–1024 token + 10%–20% overlap**，机制详见 1.4。
- 标注：**人工/LLM 预标注/主动学习按成本与吞吐组合**，Kappa 验一致性。
- 元数据：**来源、权限、时间、部门、版本、语言**——过滤、血缘、审计的地基。
- 索引：**向量 + BM25 + 元数据 + 图**。
- 版本：**内容哈希、索引版本、模型版本、策略版本**；血缘打通 chunk 到源头。
- 权限：**RBAC/ABAC、行级过滤、多租户隔离**。
- 关键问题答案：**持续更新 = 触发（定时/事件/CDC）+ 增量策略 + 评估门禁灰度；可追溯 = 版本 + 血缘 + 变更审计**。
- 核心原则：**数据质量决定 AI 效果上限；知识工程是长期工程，不是一次性任务。**
- 这些能力直接支撑：3.5 评估体系与实验管理、4.2 RAG 知识库 Agent。
