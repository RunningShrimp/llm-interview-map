# 讲解 1.1 LLM API 与模型选型

> 说明：前置是 0.5 LLM 基础——能力、幻觉与上下文窗口从哪来，决定了什么任务配什么模型。  
> 本篇是 L1 应用层的起点：后续 1.1b/1.1c 深入解码参数与 API 工程实务，1.3 结构化输出与 Function Calling 建立在 OpenAI 兼容接口之上，1.6 评估与 3.7 成本优化消费本篇的选型框架。

---

## 1. 定位

L1「LLM 应用入门」第 1 个锚点，对应大纲核心问题：**什么任务该选什么模型？**

掌握档位是「会用」：能按任务形态在模型家族与具体模型之间做有依据的选择，能用 OpenAI 兼容 SDK 稳定调用（参数、流式、限流重试），能说清 Decoder-only 胜出的原因——这是大模型面试的高频第一问。

上下游关系：

| 方向 | 锚点 | 关系 |
|---|---|---|
| 前置 | 0.5 LLM 基础 | 能力边界与幻觉机理是选型的前提 |
| 前置 | 0.4b token | 计费与上下文窗口的计量单位 |
| 后续 | 1.1b / 1.1c | 解码参数实操与采样机制的数学 |
| 后续 | 1.3 / 1.3b | 结构化输出与工具调用，都走 OpenAI 兼容接口 |
| 后续 | 1.6 / 1.7 | 评估与安全、成本、延迟——选型后如何验证与兜底 |
| 后续 | 3.7 成本优化 | 本篇的模型路由思想在系统级展开 |

## 2. 一句话定义

LLM API 是厂商把大模型封装成的标准服务：应用按「消息列表进、生成文本出」的契约调用，按 token 计费；模型选型则是在能力、成本、延迟、上下文长度、合规五个维度上，为具体任务挑出性价比最高的模型与架构家族。

## 3. 为什么需要

选型错误的代价是双向的：

1. **小题大做**：10 万条评论打情感标签用最大的旗舰模型——单条成本高出一个量级，账单爆炸，而 Encoder 级小模型又快又准。
2. **大材小用**：复杂多跳推理、长文档分析用入门小模型——错误率高，返工与用户流失的成本远超省下的 token 钱。
3. **架构错配**：给生成任务配 Encoder 模型、给语义匹配任务配 Decoder 旗舰——方向性浪费。
4. **合规踩雷**：数据出境、行业监管、私有化要求没提前确认，项目推倒重来。

一张表看清楚「架构家族」这一层的选型逻辑：

| 架构 | 代表 | 看家能力 | 典型任务 | 今天的状态 |
|---|---|---|---|---|
| Encoder-only | BERT 系 | 双向通读、输出理解表示 | 分类、相似度、聚类 | 转行做 Embedding 模型（0.7 的主力） |
| Decoder-only | GPT/LLaMA/Qwen | 逐词生成、指令跟随 | 对话、创作、代码、Agent | 事实标准，几乎垄断生成场景 |
| Encoder-Decoder | T5 系 | 先懂后写 | 翻译、摘要 | 经典场景，多被 Decoder+提示词替代 |

选型口诀：**做生成找 Decoder，做语义匹配找 Encoder，结构化转换先试大模型+提示词，量大再评估专用模型。**

## 4. 核心原理

### 4.1 Decoder-only 为何胜出

三种架构的注意力方向与训练目标不同，命运也不同。Decoder-only 赢在今天的大模型竞赛，有四个工程与科学层面的原因：

**1. 训练目标简单且可无限扩展。** 预测下一个词（Next Token Prediction）不需要人工标注：互联网上任何文本都是训练样本。Encoder 系的掩码填空（Masked LM）信号也可以扩展，但「接着往下写」这个目标与几乎所有下游任务（对话、写作、代码、推理都是某种续写）天然同构，预训练到下游任务的迁移损耗最小。

**2. 信号密度高。** 填空任务里模型只对被掩码的少量位置计算损失；自回归生成对每个位置都计算损失——同样一份语料，学习信号更密集。

**3. 推理天然高效。** 因果掩码（Causal Mask）让生成第 t 个词只依赖前 t-1 个词的中间结果，配合 KV Cache（缓存已计算过的 Key/Value），每生成一个 token 只做增量计算，复杂度与已生成长度无关。Encoder-Decoder 需要先完整编码再解码，两段式在通用对话场景没有优势。

**4. Scaling 行为被验证。** 从 GPT-2 到 GPT-4 一路验证了「参数、数据、算力堆下去能力持续上涨」。工程上「一条路走到底」比「每类任务维护一套架构」的迭代成本低得多。Encoder 没有消失，而是找到了自己的生态位——Embedding（0.7）与廉价分类。

面试作答骨架：**注意力方向 → 训练目标 → 迁移同构性 → 推理效率（KV Cache）→ scaling 验证**，五步收尾补一句「Encoder 转行做 Embedding」。

### 4.2 主流模型家族速览

截至本站大纲时效，应用层常打交道的主流家族（能力边界持续演进，具体排名以最新评测与自有实测为准）：

| 家族 | 厂商 | 特点与生态位 | 常见用途 |
|---|---|---|---|
| GPT 系列 | OpenAI | 生态最成熟，API 事实标准的定义者，多模态与工具调用完善 | 通用对话、Agent、复杂推理 |
| Claude 系列 | Anthropic | 长上下文与代码能力强，指令跟随稳，Agentic 场景表现突出 | 代码、Agent、长文档分析 |
| Gemini 系列 | Google | 多模态原生，长上下文版本激进（百万级 token 量级） | 多模态、超长文档 |
| DeepSeek 系列 | 深度求索 | 开源路线代表，推理模型性价比高，MoE 架构压低推理成本 | 推理、代码、私有化部署 |
| Qwen 系列 | 阿里通义 | 开源矩阵全（0.5B 到百亿级），中文生态好 | 中文应用、私有化、微调底座 |
| GLM 系列 | 智谱 | 中文能力扎实，开源与商用 API 双线 | 中文对话、Agent、国产合规场景 |

两个横向维度值得记住：

- **闭源 API vs 开源权重**：闭源省事、能力天花板高；开源（DeepSeek/Qwen/GLM/LLaMA）可私有化、可微调、可控成本，数据不出域是硬需求的唯一解。
- **旗舰 vs 小模型**：同一家族内通常有旗舰（复杂推理）、中档（通用）、mini 级（简单任务）三档。**简单任务路由到小模型是成本优化的第一杠杆**（3.7 系统级展开）。

### 4.3 选型五维度

| 维度 | 关键问题 | 评估方法 |
|---|---|---|
| 能力 | 复杂推理、指令跟随、中文、代码、多模态够不够 | 用自己的任务建 50~200 条评测集实测，别只看榜单 |
| 成本 | 输入/输出单价、缓存折扣、批处理折扣 | 按预估流量算月账单；输出单价通常是输入的数倍 |
| 延迟 | 首 token 时间（TTFT）、生成速度、P99 | 流式压测；对话类应用 TTFT 比 total time 更影响体感 |
| 上下文 | 窗口多大、长文下注意力是否衰减 | lost-in-the-middle（1.5）：窗口大不等于长文用得好 |
| 合规 | 数据出境、行业监管、私有化、审计留痕 | 前置确认，一票否决项 |

决策顺序建议：**合规先一票否决 → 能力用评测集卡及格线 → 及格者里按成本与延迟排序 → 用路由把「够用的小模型」吃掉大头流量。**

### 4.4 OpenAI 兼容 API：事实标准契约

OpenAI 的 Chat Completions 接口已成为行业事实标准：国内外主流厂商（DeepSeek、Qwen、GLM、Moonshot 等）几乎都提供 OpenAI 兼容端点，推理框架（vLLM、Ollama）也以它为默认接口。**兼容的含义是：换厂商只改 base_url 和 model 名，业务代码不动。**

核心契约：

```text
POST {base_url}/chat/completions
请求：model + messages[] + 参数（temperature / top_p / max_tokens / stream / tools ...）
messages 角色三件套：system（设定与规则）、user（用户输入）、assistant（历史回复）
响应：choices[0].message.content + usage（prompt_tokens / completion_tokens，计费依据）
```

常用参数速查：

| 参数 | 作用 | 经验值 |
|---|---|---|
| temperature | 随机性（1.1b 细讲） | 抽取/代码 0~0.3，对话 0.5~0.8，创意 0.9+ |
| top_p | 候选池截断 | 0.9 常用；与 temperature 二选一大调 |
| max_tokens | 输出长度上限 | 按业务设，防跑飞也控成本 |
| stream | 是否流式 | 交互场景必开 |
| stop | 停止序列 | 控制截断点 |
| tools / tool_choice | 工具调用（1.3） | Function Calling 用 |

### 4.5 限流、重试与流式

生产调用绕不开三件事：

**限流（429 Too Many Requests）**：厂商按账号/模型设 TPM、RPM 配额，高峰期必然撞上。标准姿势：**指数退避 + 随机抖动 + 最大重试次数**；再往上：申请提额、多 key/多厂商池分摊、关键链路配降级模型。

**超时与降级**：网络慢或上游故障时，设请求超时；超时/连续失败后切换备用模型或返回兜底话术——可用性靠预案不靠祈祷。

**流式（Streaming，SSE）**：服务端逐 token 推送，首字延迟（TTFT）从「整段生成完的秒级」降到几百毫秒，交互体验质变。工程要点：客户端增量拼接 delta、处理断线与 done 帧、最后一个 chunk 里通常带 usage 用于计费。

### 4.6 网关与多模型路由

当应用接的模型从一个变成多个（主模型 + 降级模型 + 小模型分摊流量），就需要一层 LLM 网关（Gateway）统一收口：

```text
业务代码 ─→ 网关层
            ├─ 鉴权与配额（按团队/用户限额）
            ├─ 路由（按任务/难度/成本选择模型）
            ├─ 重试与降级（429 退避、故障切换备用厂商）
            ├─ 缓存（相同请求/前缀命中直接返回）
            ├─ 观测（延迟、token、失败率、成本打点）
            └─ 审计（日志留存、敏感信息脱敏）
         ─→ 多家厂商 API（OpenAI / Claude / DeepSeek / Qwen / GLM ...）
```

路由的三个常见依据：**按任务**（分类、简单摘要走小模型；推理、写作走旗舰）、**按难度**（先小模型后验证，失败升级——即模型级 cascade）、**按成本预算**（预算紧张时段降档）。自建或采用开源网关/商用 LLM 网关产品均可，概念层先建立即可，落地在 3.7 与 4.x 工程化章节展开。

## 5. 架构 / 流程

一次生产级调用的完整链路：

```text
┌─────────────────────────────────────────────┐
│ 应用层                                       │
│ 组装 messages（system + 上下文 + 用户输入）    │
│ 选择参数（temperature / max_tokens / stream） │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│ 网关层（可自建或用现成产品）                   │
│ ① 路由：简单任务→mini 级，复杂任务→旗舰       │
│ ② 限流：本地令牌桶，先挡再发                  │
│ ③ 调用：请求发出                             │
│ ④ 失败处理：429/超时 → 指数退避重试            │
│    连续失败 → 切降级模型/备用厂商              │
│ ⑤ 观测：记 latency / tokens / cost / 状态码   │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│ 厂商 API                                     │
│ 非流式：等完整响应 → 解析 content + usage     │
│ 流式：SSE 逐 delta 推送 → 客户端拼接 → done 帧 │
└─────────────────────────────────────────────┘
```

调用决策清单（新功能上线前过一遍）：

1. 任务形态是什么？生成（Decoder 旗舰/中档）还是理解分类（Encoder 小模型或 mini 级 API）？
2. 合规有没有一票否决项？数据能否出域？
3. 用什么参数组合？低温抽取还是高温创意？
4. 流式开不开？超时设多少？
5. 429 与故障的退避、降级预案是什么？
6. token 成本估算与预算告警在哪？（1.7 展开三笔账）

## 6. 代码 / 工具

### 6.1 OpenAI 兼容调用：一份代码切换多家厂商

```python
from openai import OpenAI

# 唯一的厂商耦合点：base_url + model 名。
# 换厂商只需改这两行，业务代码零改动。
client = OpenAI(
    api_key="YOUR_KEY",
    base_url="https://api.deepseek.com/v1",   # 任一 OpenAI 兼容端点
)

resp = client.chat.completions.create(
    model="deepseek-chat",
    messages=[
        {"role": "system", "content": "你是电商客服助手，只依据资料回答，不编造。"},
        {"role": "user", "content": "退货后多久能收到退款？"},
    ],
    temperature=0.2,     # 抽取/事实类低温
    max_tokens=512,      # 控长度、控成本
)

print(resp.choices[0].message.content)
print(resp.usage)        # prompt_tokens / completion_tokens —— 计费依据
```

### 6.2 流式输出：逐 token 推送降低首字延迟

```python
stream = client.chat.completions.create(
    model="deepseek-chat",
    messages=[
        {"role": "system", "content": "你是客服助手。"},
        {"role": "user", "content": "讲讲退货流程。"},
    ],
    stream=True,                      # 打开流式
)

full = []
for chunk in stream:                  # SSE：每个 chunk 带一小段 delta
    delta = chunk.choices[0].delta.content
    if delta:
        full.append(delta)
        print(delta, end="", flush=True)   # 用户立刻看到首字
# 生产要点：断线重连、done 帧处理、最后一个 chunk 的 usage 落库计费
print("\n总长:", len("".join(full)))
```

### 6.3 429 指数退避重试 + 故障降级

```python
import random
import time
from openai import APITimeoutError, RateLimitError

def call_with_backoff(make_request, max_retries: int = 5, base_delay: float = 1.0):
    """指数退避 + 随机抖动；重试耗尽后抛出，由上层走降级。"""
    for attempt in range(max_retries):
        try:
            return make_request()
        except RateLimitError:                      # 429
            if attempt == max_retries - 1:
                raise
            delay = base_delay * (2 ** attempt)     # 1s, 2s, 4s, 8s, 16s
            delay += random.uniform(0, 0.5)         # 抖动：防止多客户端同步重试踩踏
            time.sleep(delay)
        except APITimeoutError:                     # 超时同策略，可更快放弃
            if attempt == max_retries - 1:
                raise
            time.sleep(base_delay * (2 ** attempt))

def ask(messages, prefer_fast: bool = True):
    """主模型 + 降级模型：关键链路可用性靠预案。"""
    primary = {"model": "deepseek-chat"}
    fallback = {"model": "deepseek-chat-lite"}      # 示意的降级型号，按厂商实际填
    try:
        return call_with_backoff(
            lambda: client.chat.completions.create(
                **(primary if prefer_fast else fallback),
                messages=messages,
                temperature=0.2,
            )
        )
    except Exception:
        # 连续失败：切备用型号或直接返回兜底话术 + 告警
        return client.chat.completions.create(
            **fallback, messages=messages, temperature=0.2
        )
```

配套建议：SDK 自带 `max_retries` 参数可兜底简单场景；自写重试的价值在于与降级、观测、熔断联动。批量离线任务改用厂商 Batch 接口，通常半价（1.1c 成本三招之一）。

## 7. 案例

### 案例 A：三需求混合选型

**场景**：某电商公司同时有三个需求：客服对话机器人、10 万条商品评论打情感标签、商品描述批量翻译。

**方案**：需求一走 Decoder 旗舰 API（对话是它的本行），流式输出 + 低温 0.5；需求二用开源 Encoder 级小模型微调（10 万条标注数据充足），单条成本只有大模型的几十分之一；需求三先试大模型 + 翻译提示词跑通，日量上千万字后评估换专用翻译模型控制成本。

**效果**：三线并行，LLM 月成本比「全用旗舰 API」的初始方案下降约七成，情感标签准确率反而更高（小模型 + 领域微调 > 通用大模型零样本）。

### 案例 B：高峰期 429 风暴治理

**场景**：某 SaaS 助手产品晚高峰大量 429，用户侧表现为转圈与报错，投诉量当日翻倍。

**方案**：接入层本地令牌桶先把并发压到配额以下；429 按指数退避加抖动重试（上限 5 次）；申请配额提升 + 双厂商池分摊；客服问答链路配降级模型，连续失败自动切换。

**效果**：429 穿透到用户的比例降到千分之一以下；观测面板显示重试成功率集中在第二次退避后，据此把初始并发再下调 20%，稳定性进一步收敛。

### 案例 C：路由砍掉六成账单

**场景**：某知识库问答产品统一用旗舰模型，月账单超预算 3 倍。日志分析发现 60% 请求是「改写这句更礼貌」类的简单任务。

**方案**：网关加轻量意图路由——规则先行（长度、任务类型字段），规则不确定时用 mini 级模型判难度；简单任务走 mini 级，复杂任务才升旗舰；系统提示固定前缀开启 prompt 缓存。

**效果**：月成本下降约 60%，简单任务响应延迟下降一半，复杂任务质量不回退（抽样评测 200 条对照验证）。

## 8. 常见坑

1. **只看榜单选型**。榜单能力不等于自家任务表现。对策：用自己的 50~200 条评测集实测（1.6）。
2. **把历史对话无限塞进上下文**。输入 token 线性上涨、注意力被稀释。对策：滑动窗口 + 摘要（1.5）。
3. **不改 temperature 一套参数通吃**。低温写创意干瘪，高温做抽取漂移。对策：按任务分入口配参（1.1b）。
4. **没设 max_tokens**。模型跑飞时账单和延迟一起爆炸。对策：按业务上限设值。
5. **裸调不处理 429**。高峰期整链路雪崩。对策：指数退避 + 抖动 + 最大次数，三件套缺一不可。
6. **重试无抖动**。大量客户端同时重试，形成重试风暴。对策：随机抖动打散。
7. **只配主模型不配降级**。上游故障即全站不可用。对策：备用模型 + 兜底话术 + 告警。
8. **非交互场景不开流式**。用户体感延迟数秒。对策：对话类一律流式，TTFT 是体感关键。
9. **忽略 usage 字段**。不知道成本去向，优化无从下手。对策：每次调用落库 tokens 与成本打点。
10. **把「OpenAI 兼容」当成完全等价**。不同厂商对参数、结构化输出、工具调用支持有差异。对策：网关层做兼容性测试，关键功能逐家验证。
11. **合规后置**。先上线后补合规，返工成本极高。对策：数据出境、私有化要求在选型第一轮就一票否决。
12. **小模型大用或大模型小用**。方向性浪费。对策：路由思想——简单任务吃小模型流量，复杂任务升旗舰。

## 9. 练习

1. 用同一份业务代码分别接两家 OpenAI 兼容端点（如 DeepSeek 与 Qwen 的兼容接口），只改 base_url 与 model，验证回答质量差异。
2. 给 6.1 加上参数化配置：从环境变量读取 base_url/model/temperature，做成可切换的多厂商客户端。
3. 对同一问题分别在 temperature=0 与 0.9 下生成 5 次，对比输出方差，体会随机性参数的作用。
4. 实现流式输出到命令行（6.2），统计首字延迟与总时长，对比非流式版本的体感差异。
5. 用 mock 或限流测试环境触发 429，验证 6.3 的退避重试次数与延迟序列（1s/2s/4s/8s/16s + 抖动）。
6. 给 ask() 补一个降级告警日志（时间、原因、切换目标），模拟主模型连续失败三次的场景。
7. 写一个 50 条样本的迷你评测集，对旗舰与 mini 级模型各跑一遍，统计正确率与成本，算出「mini 够用」的任务占比。
8. 画出自家（或假想）产品的路由决策图：哪些任务走小模型、哪些走旗舰、降级链路怎么走，并标注每个分支的成本量级。

## 10. 小结

- 三种架构：**Encoder 会读、Decoder 会写、Enc-Dec 先懂后写**；生成场景 Decoder-only 事实垄断，Encoder 转行做 Embedding。
- Decoder-only 胜出五步答：**训练目标可无限扩展、信号密度高、任务同构、KV Cache 推理高效、scaling 被验证**。
- 主流家族：**GPT/Claude/Gemini 闭源天花板高，DeepSeek/Qwen/GLM 开源可私有化**；按合规、能力、成本三步收敛。
- 选型五维：**能力（自建评测集）、成本、延迟（看 TTFT）、上下文（警惕长文衰减）、合规（一票否决）**。
- OpenAI 兼容接口是事实标准：**换厂商只改 base_url 与 model**，业务代码不动。
- 生产三件套：**流式降首字延迟、指数退避+抖动治 429、降级模型保可用**。
- 网关与路由：**按任务/难度/预算把流量分给够用的最便宜模型**——这是系统级成本优化的第一杠杆。
- 这些直接支撑：1.1b/1.1c 参数与实务、1.3 结构化输出、1.6 评估验证、3.7 成本工程。
