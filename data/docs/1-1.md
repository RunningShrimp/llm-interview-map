# 讲解 1.1 LLM API 与模型选型

> 说明：0.5 讲清了 LLM 的能力边界从哪来（预训练、SFT、RLHF、token、上下文、采样），0.2 提供了异步、包管理、测试这些 Python 工程底座，1.1 把两者接通：在成本、延迟、能力、隐私的约束下选对模型，并工程化地稳定调用它。  
> 后续 1.2–1.7 的提示词、结构化输出、RAG、记忆、评估、安全全部跑在这一层之上；成本与延迟的体系化治理在 3.7 展开。

---

## 1. 定位

LLM 应用层第 1 个知识点，属于“工程入口”。  
基础层让你理解模型“是什么、能什么、不能什么”，1.1 让你学会**把 LLM 接进真实系统**：调用、选型、参数、错误处理、成本控制、流式输出。

一句话：**1.1 之前，LLM 是一个概念；1.1 之后，LLM 是你系统里一个可运维的组件。**

直接前置是 0.5（能力边界）与 0.2（工程底座）；它是后续 1.2–1.7 全部应用能力的工程底座，也是 3.7 成本、延迟与可靠性的应用侧起点。

## 2. 一句话定义

LLM API 与模型选型，是在成本、延迟、能力、隐私约束下，选择合适模型并稳定调用其 API 的工程决策与实现方法。

```text
简化公式：
合适模型（能力 ≥ 任务要求，且成本 / 延迟 / 风险可接受）
+ 稳定调用（参数受控、错误可处理、用量可观测）
= 生产可用的 LLM 接入层
```

## 3. 为什么需要

Demo 阶段你只需要 `client.chat.completions.create(...)`。  
生产阶段你会遇到：

- **模型太多** → GPT、Claude、Gemini、Qwen、Llama、DeepSeek……没有选型标准，全靠拍脑袋。
- **成本失控** → 多轮 Agent 的 token 消耗随轮数复利增长，一个月账单几万。
- **延迟波动** → P99（99 分位）延迟 10 秒，用户直接流失。
- **限流（Rate Limiting）** → 429 错误频发，请求被拒。
- **超时** → LLM 调用挂住，拖垮整个服务。
- **格式不一致** → 不同厂商 API 参数、返回结构不同，换模型等于重写一遍。
- **模型升级** → 厂商悄悄更新模型，行为变化，回归失败。
- **隐私合规** → 数据不能出域，必须本地部署。

类比：模型选型像医院分诊台——感冒发烧去社区门诊（小模型，便宜、快），疑难杂症挂专家号（大模型，强、贵），急诊先稳住再转专科（先降级保可用，再补质量）。**全院只有一个专家号，等于所有任务都用旗舰模型：挂号费（成本）和排队（延迟）双爆炸。**

“不做会怎样”对照：

| 维度 | Demo 写法（不做会怎样） | 生产做法（1.1 教的） |
|---|---|---|
| 调用 | 裸 SDK 直连，挂了就挂了 | 统一封装 + 重试 + 超时 + 降级 |
| 选型 | 全用旗舰模型 | 分层路由，什么活派什么模型 |
| 成本 | 不看账单，月底吓一跳 | 记录 token 用量 + 预算告警 |
| 延迟 | 只看平均值 | 盯 TTFT 和 P99 |
| 模型版本 | 跟随默认最新版 | 固定版本 + 评估后灰度升级 |

这些问题的答案，都在 1.1。

## 4. 核心原理

### 4.1 LLM API 的基本形态

主流 API 分两类。

**1. Chat Completions（消息列表）**

```json
{
  "model": "gpt-4o-mini",
  "messages": [
    {"role": "system", "content": "你是助手"},
    {"role": "user", "content": "你好"}
  ],
  "temperature": 0.7,
  "max_tokens": 1024
}
```

**2. Responses / Completions（直接给提示词）**

```json
{
  "model": "gpt-4o-mini",
  "input": "你好",
  "temperature": 0.7
}
```

区别在输入组织方式：Chat Completions 以消息（messages）列表组织 system / user / assistant 多轮对话；Responses 风格直接接收一段提示词（Prompt）。当前事实标准是 **Chat Completions 风格**：OpenAI、Anthropic、Google、DeepSeek、Qwen 都提供兼容或类似接口，且多数厂商提供 **OpenAI 兼容（OpenAI-compatible）端点**——SDK 只换 `base_url` 就能切换厂商，这是 4.11 多厂商抽象能成立的基础。

```python
from openai import OpenAI

# OpenAI 兼容端点：换 base_url 即可切换厂商（DeepSeek、Qwen、GLM 等普遍兼容）
client = OpenAI(
    api_key="YOUR_API_KEY",                     # 从环境变量读取，严禁写死或放前端
    base_url="https://api.your-vendor.com/v1",  # 厂商兼容端点（示意）
)

resp = client.chat.completions.create(
    model="vendor-model-name",   # 以当期可用模型名为准
    messages=[{"role": "user", "content": "用一句话解释什么是 token"}],
    temperature=0.7,
    max_tokens=256,
)
print(resp.choices[0].message.content)
```

### 4.2 核心参数与采样策略

| 参数 | 作用 | 建议 |
|---|---|---|
| model | 模型名 | 按任务选（见 4.4 决策表） |
| messages | 对话消息 | system + user + assistant 交替 |
| temperature | 随机性（分布锐度） | 工具 / 抽取 0，创意 0.7–1.0 |
| top_p | 核采样（Nucleus Sampling） | 通常 0.9–0.95 |
| max_tokens | 最大输出 | 必设，控制成本和延迟 |
| stream | 流式输出（Streaming） | 长回答开启（见 4.10） |
| stop | 停止序列 | 控制输出边界 |
| frequency_penalty | 频率惩罚 | 减少重复 |
| presence_penalty | 存在惩罚 | 鼓励新话题 |
| seed | 随机种子 | 可复现（部分模型支持） |
| response_format | 输出格式 | JSON 模式 / 结构化输出（见 1.3） |

采样三件套的权衡：

- **temperature**：对整个概率分布做缩放，越低分布越尖，输出越确定。
- **top_p**：只从累积概率前 p 的候选词里采样，截掉长尾。
- **top_k**：只保留概率前 k 个候选，再归一化采样。
- 共识：**一次只调一个**——同时大改 temperature 和 top_p，调参效果无法归因；推理型模型（见 4.3）通常建议保持默认采样参数。

### 4.3 模型格局（截至 2026 年）

| 阵营 | 代表 | 特点 | 适合 |
|---|---|---|---|
| 闭源商用 API | OpenAI（GPT / o 系列）、Anthropic（Claude）、Google（Gemini） | 能力天花板高、开箱即用；数据出域、按 token 计费 | 快速上线、非敏感数据 |
| 开放权重（Open-Weight） | Meta Llama、阿里 Qwen、DeepSeek、智谱 GLM、Mistral | 可自部署也可托管；单价低、可固定版本 | 成本敏感、中等敏感数据 |
| 推理型模型（Reasoning Model） | o 系列、DeepSeek-R1 一类 | 先显式生成思维链（Chain-of-Thought）再作答，数学 / 代码 / 规划显著更强；思考 token 也计费、延迟更高 | 复杂推理与规划任务 |

三点补充：

- **上下文窗口（Context Window）**：截至 2026 年，主流模型普遍在 128K token 量级，部分提供 1M 级别；但“窗口大”不等于“中间不忘”，长上下文的注意力衰减问题在 1.5 展开。
- **自部署推理框架**：vLLM、SGLang、llama.cpp 是开放权重自部署的主流选择，吞吐与延迟调优在 3.6 展开。
- **趋势观察**：上下文缓存（Prompt Caching）已在主流厂商普及，命中缓存的输入 token 计费大幅降低，多轮 Agent 与 RAG（Retrieval-Augmented Generation，详见 1.4）场景收益显著。

### 4.4 模型选型维度

选模型不是“越贵越好”，而是多维权衡：

| 维度 | 说明 |
|---|---|
| 能力 | 推理、代码、多语言、长上下文 |
| 成本 | 输入 / 输出 token 单价（量级对比即可） |
| 延迟 | TTFT、总延迟、P99 |
| 上下文窗口 | 4K / 128K / 1M 量级是否够用 |
| 隐私 | 数据是否出域、是否可自部署 |
| 可控性 | 是否支持微调、系统提示、工具调用（Function Calling） |
| 稳定性 | 厂商 SLA、限流额度、版本策略 |
| 生态 | SDK、文档、社区、OpenAI 兼容性 |
| 合规 | 是否符合行业 / 地区法规 |

任务到档位的选型决策表：

| 任务类型 | 推荐档位 | 参数建议 |
|---|---|---|
| 意图分类、信息抽取、改写 | 轻量小模型 | temperature=0 |
| RAG 问答、总结、翻译 | 中档通用模型 | temperature=0–0.3 |
| 复杂推理、规划、代码 | 旗舰或推理型模型 | 放宽 max_tokens |
| 强合规 / 数据不出域 | 自部署开放权重 | 固定权重版本 |

> 面试高频问法：“你们项目为什么选这个模型？成本、延迟、效果怎么权衡？换模型要改多少代码？”  
> 共识答法：先给选型维度（任务难度、成本、延迟、隐私），再讲分层路由与评估集验证（见 1.6），最后落到统一封装——换模型只改配置，不改业务代码。

### 4.5 部署方式：闭源 API / 开放权重托管 / 自部署

| 维度 | 闭源商用 API | 开放权重托管 API | 自部署（本地 / 私有云） |
|---|---|---|---|
| 能力天花板 | 高 | 中到高 | 取决于模型与显卡 |
| 计费 | 按 token，量级最高 | 按 token，量级更低 | 固定算力成本，高并发摊薄 |
| 启动成本 | 低（一个 Key） | 低 | 高（GPU、推理框架、运维） |
| 数据隐私 | 数据出域 | 托管方可见 | 数据不出域 |
| 可控性 | 受厂商版本策略约束 | 可固定权重版本 | 完全可控、可微调 |
| 延迟 | 受网络与厂商负载影响 | 同左 | 可就近部署、按需调优 |
| 适合 | 快速上线、验证期 | 成本敏感的规模化 | 强合规、超高并发、深度定制 |

演进顺序的经验共识：**验证期用闭源 API 快速跑通；规模化后把高频简单任务切到便宜档位或开放权重托管；合规红线内的场景自部署。**

### 4.6 模型分层策略

生产系统通常不只用一个大模型，而是**分层路由**：

```text
简单任务（分类、抽取、改写） → 小模型（便宜、快）
中等任务（总结、问答、RAG） → 中模型（平衡）
复杂任务（推理、规划、代码） → 大模型（强、贵）
```

示例路由：

```python
def route_model(task_type: str) -> str:
    """按任务类型路由到不同档位的模型（模型名以当期可用为准）"""
    if task_type in ["classify", "extract", "rewrite"]:
        return "gpt-4o-mini"        # 轻量档：分类、抽取足够用
    elif task_type in ["qa", "summarize", "rag"]:
        return "gpt-4o"             # 中档：RAG 问答的主力
    else:
        return "reasoning-model"    # 推理档：复杂推理与规划
```

好处：成本可降 5–10 倍，延迟也更优。

### 4.7 成本模型

成本 = 输入 token × 输入单价 + 输出 token × 输出单价。

单价量级（示意，用于算术演示，实际以厂商当期定价为准）：

```text
旗舰档：输入约 $2.5 / 1M token，输出约 $10 / 1M token
轻量档：输入约 $0.15 / 1M token，输出约 $0.6 / 1M token
```

一次 RAG 问答：

- 输入：system 200 + 检索上下文 2000 + 问题 50 = 2250 token
- 输出：300 token

用旗舰档：

```text
输入: 2250 / 1M × $2.50 = $0.005625
输出:  300 / 1M × $10.00 = $0.003
单次成本 ≈ $0.0086
```

一天 1 万次 → $86/天 → $2580/月。

用轻量档：

```text
输入: 2250 / 1M × $0.15 = $0.0003375
输出:  300 / 1M × $0.60 = $0.00018
单次成本 ≈ $0.0005
一天 1 万次 → $5/天 → $150/月
```

差距 17 倍。**模型选型直接决定商业模式是否成立。**

Agent 场景还有隐性复利：每轮都携带全量历史上下文，输入 token 随轮数线性增长，总消耗近似平方级：

```text
10 轮循环、每轮上下文 3K token：
总输入 ≈ 3K × (1 + 2 + … + 10) = 3K × 55 = 165K token（单次会话）
```

治理手段（缓存、上下文压缩、路由）在 1.7 与 3.7 展开。

### 4.8 延迟模型

两个关键指标：

- **TTFT（Time To First Token，首 token 延迟）**：用户看到第一个字要等多久。
- **总延迟**：完整回答生成完毕的时间。

粗略推导：

```text
总延迟 ≈ 排队 + 预填充（与输入长度正相关）+ 输出 token 数 × 单 token 生成时间
例：输出 500 token、生成速度 50 token/s → 生成段约 10 秒
```

影响因素：模型大小、输入长度、输出长度、网络、并发、推理硬件。

优化手段：

- 流式输出（降低感知延迟，见 4.10）
- 缓存（相同请求直接返回）
- 路由（简单任务小模型，见 4.6）
- 并行调用（多工具并发）
- 压缩上下文（减少输入 token，见 1.5）

### 4.9 错误处理与重试

常见错误：

| 错误 | 原因 | 处理 |
|---|---|---|
| 429 | 限流 | 指数退避重试 |
| 500 / 502 / 503 | 服务端错误 | 重试 |
| 400 | 参数错误 | 不重试，修参数 |
| 401 | 认证失败 | 检查 Key |
| timeout | 网络 / 服务慢 | 重试 + 降级 |
| context_length_exceeded | 超上下文窗口 | 截断 / 压缩（见 1.5） |

重试原则：

- 先区分可重试（429、5xx、超时）和不可重试（400、401）——对不可重试的错误盲目重试只会雪上加霜。
- 指数退避（Exponential Backoff）+ 抖动（Jitter）：等待 1s、2s、4s，叠加随机量，避免所有实例同时重试造成惊群。
- 设最大重试次数（一般 3 次）。
- 重试耗尽后熔断（Circuit Breaker）+ 降级（Fallback）到备用模型或缓存结果。

### 4.10 流式输出

```python
stream = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "写一篇短文"}],
    stream=True,   # 开启流式：服务端边生成边推送
)

for chunk in stream:
    delta = chunk.choices[0].delta.content   # 每个 chunk 只带增量内容
    if delta:
        print(delta, end="", flush=True)    # 立刻上屏，不等完整回答
```

同步 vs 流式对比：

| 维度 | 同步（一次性返回） | 流式（Streaming，Server-Sent Events 分块） |
|---|---|---|
| 首 token 可见 | 等全部生成完 | 生成即推送，TTFT 大幅下降 |
| 感知延迟 | 高 | 低 |
| 完整输出校验 | 容易，拿到全量再解析 | 难，需拼接完成后再校验 |
| 中断 | 只能整体超时 | 可提前中断，省 token |
| 工具调用 | 简单 | 需处理增量参数拼接（见 1.3） |
| 实现复杂度 | 低 | 需处理分块、断连、顺序保证 |

类比餐厅上菜：同步是“一桌菜全做好才一起端上来”，流式是“凉菜先上、热菜跟上”——总做饭时间没变，但客人先动筷，等待感完全不同。

### 4.11 多厂商抽象与 LLM 网关

不同厂商 API 有差异，工程上通常做一层统一封装，即 LLM 网关（LLM Gateway）：

```text
业务代码 → LLM 网关（路由 / 重试 / 缓存 / 计费 / 日志）→ OpenAI / Anthropic / Google / 本地模型
```

类比：LLM 网关像写字楼总机前台——访客（请求）先登记（鉴权），前台看会议室容量（限流），按来访目的分流到不同楼层（模型路由），没约上自动改期（重试），月底统一记账（成本统计）。

好处：

- 切换模型不改业务代码。
- 统一日志、重试、成本统计。
- 方便 A/B 测试（见 1.6）。

工具：

- LiteLLM：开源统一代理，一家 SDK 调多家模型。
- OpenRouter：一个 Key 访问多家模型。
- LangChain / LlamaIndex：更高层抽象，取舍讨论见 3.3。
- 自研封装：最可控，中大型团队的主流选择。

> 面试高频问法：“LLM 网关和传统 API 网关有什么区别？为什么要多模型统一接入？”  
> 共识答法：传统网关管通用流量治理（路由、鉴权、限流）；LLM 网关在此之上多了模型语义——按任务路由到不同模型、token 级计费与配额、Prompt 缓存、模型版本灰度。核心价值是“换模型不改业务代码 + 用量可观测”。

### 4.12 模型版本管理

厂商会更新模型：

- `gpt-4o` 这类别名可能随时指向新的快照版本。
- 行为可能变化，输出格式漂移。
- 回归测试可能失败。

工程建议：

- 固定模型版本（使用带日期后缀的快照名，以厂商支持为准）。
- 记录每次调用实际使用的模型版本，出问题可回溯。
- 升级前先跑评估集（见 1.6）。
- 灰度发布：先切 5% 流量，确认无回归再全量。

## 5. 架构 / 流程

模型选型决策树：

```text
                      ┌── 数据不能出域？ ── 是 ──→ 自部署开放权重（vLLM / SGLang）
                      │
  新任务进入选型 ──────┼── 任务复杂度？
                      │    ├─ 简单（分类 / 抽取 / 改写）→ 轻量模型，temperature=0
                      │    ├─ 中等（问答 / 总结 / RAG）→ 中档模型，temperature=0–0.3
                      │    └─ 复杂（推理 / 规划 / 代码）→ 旗舰或推理型模型
                      │
                      ├── 上下文超窗？ ── 是 ──→ 压缩 / 切分（见 1.5）或换长窗口模型
                      │
                      └── 成本 / 延迟超预算？ ── 是 ──→ 先缓存 → 再降档 → 最后才加档
```

一个生产级 LLM 调用层：

```text
业务请求
   ↓
┌─────────────────────────┐
│  LLM 网关层              │
│  ├─ 模型路由             │
│  ├─ 参数校验             │
│  ├─ 缓存查询             │
│  ├─ 限流/配额            │
│  ├─ 重试/熔断            │
│  ├─ 成本统计             │
│  └─ 日志/trace           │
```

### 6.1 统一封装层（重试 + 超时 + 日志）

```python
import asyncio
import logging
import random

from openai import AsyncOpenAI

logger = logging.getLogger("llm")

RETRYABLE_STATUS = {429, 500, 502, 503}   # 可重试：限流与服务端错误


class LLMClient:
    def __init__(self, api_key: str, timeout: float = 30.0):
        # SDK 自带重试关掉（max_retries=0），统一走下面的重试逻辑便于观测
        self.client = AsyncOpenAI(api_key=api_key, timeout=timeout, max_retries=0)
        self.model_map = {
            "fast": "gpt-4o-mini",       # 轻量档
            "balanced": "gpt-4o",        # 中档
            "powerful": "o1-mini",       # 推理档（以当期可用为准）
        }

    def _resolve_model(self, tier: str) -> str:
        return self.model_map.get(tier, "gpt-4o-mini")

    async def chat(
        self,
        messages: list[dict],
        tier: str = "fast",
        temperature: float = 0.7,
        max_tokens: int = 1024,
        max_retries: int = 3,
    ) -> str:
        model = self._resolve_model(tier)

        for attempt in range(max_retries):
            try:
                response = await self.client.chat.completions.create(
                    model=model,
                    messages=messages,
                    temperature=temperature,
                    max_tokens=max_tokens,
                    timeout=30.0,        # 单次请求超时，防止挂死拖垮服务
                )
                usage = response.usage
                logger.info(
                    "llm_call",
                    extra={
                        "model": model,
                        "input_tokens": usage.prompt_tokens,
                        "output_tokens": usage.completion_tokens,
                        "attempt": attempt + 1,
                    },
                )
                return response.choices[0].message.content
            except Exception as e:
                status = getattr(e, "status_code", None)
                retryable = status in RETRYABLE_STATUS or isinstance(e, TimeoutError)
                if not retryable or attempt == max_retries - 1:
                    raise               # 不可重试，或重试耗尽：抛给上层降级
                # 指数退避 + 抖动：约 1s / 2s / 4s 为基数，叠加随机量避免惊群
                wait = min(2 ** attempt + random.random(), 30)
                logger.warning(f"retry in {wait:.1f}s: {e}")
                await asyncio.sleep(wait)
```

### 6.2 模型路由

```python
def choose_tier(task: str, input_len: int) -> str:
    """按任务类型与输入长度选档位，配合 6.1 的 model_map 使用"""
    if task in ["classify", "extract"]:
        return "fast"                   # 简单任务：便宜快
    if input_len > 8000:
        return "balanced"               # 长输入：需要较大上下文能力
    if task in ["reason", "plan", "code"]:
        return "powerful"               # 复杂任务：上推理档
    return "balanced"
```

### 6.3 成本统计

```python
PRICING = {
    # 示意单价（美元 / 1M token），实际以厂商当期定价为准
    "gpt-4o-mini": {"input": 0.15, "output": 0.60},
    "gpt-4o": {"input": 2.50, "output": 10.00},
}

def estimate_cost(model: str, input_tokens: int, output_tokens: int) -> float:
    p = PRICING.get(model, {"input": 0, "output": 0})
    return (input_tokens * p["input"] + output_tokens * p["output"]) / 1_000_000
```

### 6.4 缓存

```python
import hashlib
import json

def cache_key(model: str, messages: list[dict], temperature: float) -> str:
    payload = json.dumps({"model": model, "messages": messages, "temperature": temperature}, sort_keys=True)
    return hashlib.sha256(payload.encode()).hexdigest()

cache = {}   # 演示用进程内字典，生产换 Redis 并加 TTL

async def cached_chat(client, messages, model="gpt-4o-mini", temperature=0.0):
    key = cache_key(model, messages, temperature)
    if key in cache:
        return cache[key]
    result = await client.chat(messages=messages, tier="fast", temperature=temperature)
    cache[key] = result
    return result
```

适合缓存：FAQ、分类、抽取、固定提示词（Prompt）、temperature=0 的确定性请求。  
不适合：需要实时数据、创意生成。

## 7. 案例

### 案例 A：客服 Agent 的模型分层

**场景**：某电商客服 Agent，日均 5 万次对话（示意数字）。

**做法**：

1. 意图分类：轻量档，temperature=0。
2. 知识库问答：中档，temperature=0.2。
3. 复杂投诉处理：旗舰 / Claude，temperature=0.3。
4. 敏感操作（如大额退款）：转人工审批。

**效果**：约 70% 流量被分类与简单问答消化，综合成本降到全用旗舰模型的 1/5，P50 首 token 从约 2 秒降到 0.8 秒（示意数字）。

### 案例 B：429 限流处理

**场景**：晚高峰厂商限流，429 占比约 8%，直接失败率飙升。

**做法**：

1. 指数退避重试（1s、2s、4s）。
2. 加抖动，避免所有实例同时重试。
3. 超过重试次数，降级到备用模型。
4. 记录限流指标，触发扩容。

**效果**：最终失败率从 8% 降到 0.2%（示意数字），高峰期无用户可感知故障。

### 案例 C：模型升级导致回归

**场景**：厂商把模型别名指向新快照，JSON 输出偶尔多一句解释，解析失败率从 0.5% 升到 3%。

**做法**：

1. 固定模型版本号，先止血。
2. 升级前跑评估集，把该 case 纳入回归。
3. 灰度 5% 流量观察一周。
4. 确认无回归再全量。

**效果**：解析失败率回到 0.5% 以下；此后所有模型变更都有评估门禁（见 1.6）。

## 8. 常见坑

1. **所有任务都用最贵模型**。  
   成本爆炸；简单任务用轻量档就够，按 4.6 分层路由。

2. **不设 max_tokens**。  
   模型可能生成超长回答，成本和延迟失控；每次调用都显式设置。

3. **不处理 429**。  
   高峰期大量失败；指数退避 + 抖动 + 降级备用模型。

4. **不设超时**。  
   LLM 调用挂住拖垮整个服务；客户端层面设连接与读取超时。

5. **不记录 token 使用**。  
   无法做成本分析和优化；每次调用记录模型、输入输出 token、耗时（见 1.6）。

6. **不固定模型版本**。  
   厂商更新导致行为变化、回归失败；固定快照版本 + 升级前跑评估集。

7. **忽略 TTFT**。  
   总延迟不差但首 token 慢，体验照样差；长输出开流式，简单任务路由到小模型。

8. **不做缓存**。  
   相同请求反复调用浪费钱；FAQ、分类、抽取、固定提示词场景加缓存。

9. **把 API Key 放前端**。  
   泄露风险极高；必须服务端调用，Key 走环境变量或密钥管理。

10. **不做降级方案**。  
    主模型挂了整个系统不可用；备用模型 + 缓存兜底 + 熔断。

11. **忽略隐私合规**。  
    敏感数据发到境外 API 可能违规；先做数据分级，红线内自部署（见 1.7、3.8）。

12. **不做 A/B 测试就换模型**。  
    换模型不评估可能悄悄变差；变更走评估集 + 灰度（见 1.6）。

3. 封装一个 LLMClient，支持模型分层、指数退避重试、超时、日志。验收：模拟 429 后能自动恢复。
4. 实现一个基于 Redis 的 LLM 缓存层（精确匹配即可）。验收：相同请求第二次不再打厂商 API。
5. 用 LiteLLM 调用 OpenAI 和 Anthropic，对比返回结构差异。验收：同一业务函数不感知厂商。

7. 设计一个模型路由策略，覆盖分类、问答、推理三类任务。验收：用 4.4 的决策表说明每条路由的理由。

## 10. 小结

- LLM API = 消息列表 + 参数（temperature、max_tokens、stream）；Chat Completions 是事实标准，OpenAI 兼容端点是切换厂商的钥匙。
- 采样一次只调一个旋钮：temperature 或 top_p 二选一；推理型模型保持默认采样参数。
- 选型维度：**能力、成本、延迟、上下文、隐私、可控性、稳定性、生态、合规**，多维权衡，不迷信“最贵”。
- 部署三选：闭源 API 起步、开放权重托管降本、自部署保合规，按“验证期 → 规模化 → 合规红线”逐级演进。
- 生产策略：**模型分层 + 路由 + 缓存 + 重试 + 降级**，一套组合拳。
- 成本公式：**输入 token × 输入单价 + 输出 token × 输出单价**；Agent 多轮场景总消耗近似平方级增长。
- 延迟关键：**TTFT 和 P99，不只看平均**；长输出开流式。
- 错误处理先分类：**可重试（429/5xx/超时）才重试**，指数退避 + 抖动，耗尽后熔断降级。
- 工程原则：**统一封装（网关）、固定版本、记录用量、灰度升级**。
- 这些能力直接支撑：1.2–1.7 全部应用层（提示词、结构化输出、RAG、记忆、评估、安全），以及 3.7 成本、延迟与可靠性。
