# 讲解 3.4 可观测性与追踪

> 说明：1.6「LLM 应用评估与可观测性」讲了评估入门与指标概念，本页把可观测性做成生产体系：Trace/Span 数据模型、最小记录集、LangSmith/Langfuse/OTel 选型三分法、质量指标与坏例沉淀。

## 1. 定位

L3 工程化层第 4 个知识点，必选锚点（掌握等级「熟练」）。

它回答一个运维问题：**线上一次回答出错时，能不能在 5 分钟内还原完整轨迹，分清是检索找错了、提示拼错了、还是模型答偏了？**

前置依赖：

- 1.6 LLM 应用评估与可观测性：金标集、judge、指标概念——本页把「跑一次评估」升级为「常开的观测系统」。
- 3.1 架构与接口设计：观测层是六层架构中的一层，trace 埋点决定各层的可诊断性。

后续衔接：

- 3.5 评估体系：坏例从 trace 里来，回归集从坏例里沉淀——没有 trace 的评估是无源之水。
- 3.9 CI/CD 与发布：回归门禁消费本页沉淀的评估集。

## 2. 一句话定义

LLM 可观测性（LLM Observability）是给「不确定的输出」装仪表盘：用全链路追踪（输入/输出/token/延迟/成本）还原每次请求的完整轨迹，配合性能、成本、质量三类指标与回归灰度机制，让调优有据可依。没有可观测性，一切优化都是猜。

## 3. 为什么需要

LLM 应用与传统应用有两个本质差异，使传统 APM（Application Performance Monitoring）不够用：

1. **输出是概率性的**。服务「正常返回 200」不等于「回答正确」。CPU、QPS、错误码全绿，回答可能已经在悄悄变差——模型升级、供应商侧变更、检索库漂移，都可能在不报错的情况下劣化质量。
2. **一次请求是一条多步链路**。检索 → 重排 → 提示拼装 → LLM 调用 → 工具调用 → 输出校验，任何一步都能拖慢、拖贵、拖错最终结果。

于是 LLM 可观测性必须新增两个维度：

| 维度 | 传统 APM | LLM 应用必须新增 |
|---|---|---|
| 性能 | 响应时间、错误率 | TTFT（Time To First Token）、每步链路耗时分解 |
| 成本 | 基本不涉及 | token 用量、单次成本、日预算燃尽 |
| 质量 | 不涉及 | 差评率、幻觉抽样命中率、拒绝率、格式合规率、转人工率 |
| 轨迹 | 调用栈 | 每步的输入输出摘要，可逐帧回放 |

「回答慢，是 LLM 2.1 秒是大头，还是检索拖了后腿？」「成本超支，是系统提示该缓存了，还是检索塞了太多块？」「质量差，是召回相关分低，还是模型问题？」——这三个问题只有 trace 能回答。

## 4. 核心原理

### 4.1 Trace/Span 三层数据模型

主流方案（LangSmith、Langfuse、OTel）共用同一套分层模型：

| 层级 | 对象 | 内容 | 类比 |
|---|---|---|---|
| 第 1 层 | Trace（轨迹） | 一次完整请求的根对象：用户输入、最终输出、总耗时、总 token、总成本、session_id | 一次航班全程 |
| 第 2 层 | Span（跨度） | 链路中的一步：retrieve / rerank / prompt_build / llm_call / tool_call / validate，各自有耗时与属性 | 一段航段 |
| 第 3 层 | Generation（LLM 调用明细） | Span 的特例：模型名、完整 messages、参数（temperature）、输入输出 token、finish_reason | 机长操作记录 |

关键字段约定：

- **父子关系**：Span 记 `parent_span_id`，构成树；树根是 Trace。
- **成本归集**：Generation 记单次 token，Trace 层汇总为总成本，按模型单价表换算。
- **会话聚合**：多轮对话用 `session_id`/`thread_id` 把多条 Trace 聚成会话，才能看「第 3 轮开始答非所问」这类问题。

### 4.2 最小 trace 记录集

不是所有字段都值得记，但缺了下面任何一个，回放都会断链。每一步（Span）至少记：

| 字段 | 说明 | 用来回答 |
|---|---|---|
| `step` / `span_name` | 步骤名（retrieve/llm/tool/validate） | 卡在哪一步 |
| `started_at` / `duration_ms` | 开始时间与耗时 | 慢在哪一步 |
| `input_summary` | 输入摘要（查询词、消息数、输入 token 数） | 喂进去什么 |
| `output_summary` | 输出摘要（结果条数、输出文本截断、输出 token 数） | 吐出来什么 |
| `tool_calls` | 工具名、参数摘要、返回码 | 工具错没错 |
| `tokens` | 输入/输出 token 数 | 钱花在哪 |
| `status` | ok / error / degraded | 哪步坏了 |
| `retrieval_meta` | 召回条数、Top1 相关分、命中文档 ID（检索步专用） | 检索质量问题 |
| `model` / `params` | 模型名、temperature | 复现与归因 |
| `trace_id` / `parent_span_id` / `session_id` | 关联三键 | 拼出完整链路 |

原则：**全文输入输出只在 LLM Generation 层留档（且有脱敏与保留期策略），Span 层记摘要即可**——既保证可回放，又控制存储与合规风险。

### 4.3 三类核心指标

质量指标是 LLM 特有的新增项，也是最容易漏掉的一类：

| 类别 | 指标 | 说明 |
|---|---|---|
| 性能 | TTFT、TPOT、P50/P95/P99 延迟、吞吐 | 分位看长尾，均值会骗人 |
| 成本 | 日 token、单次成本、单会话成本、预算燃尽进度 | 成本要能按功能/租户下钻 |
| 质量 | 拒绝率、差评率、转人工率、幻觉抽样命中率、格式合规率 | 「正常返回」不等于「回答正确」 |

三个质量指标的解释：

- **拒绝率（Refusal Rate）**：模型以「我无法回答」收尾的比例。突然升高通常意味着提示词过严、安全策略收紧或检索空转。
- **幻觉抽样命中率**：每周抽固定条数（如 100 条），用 LLM-as-Judge 批量初判「回答是否忠于检索内容」，人工复核 judge 标记的可疑样本，算出幻觉比例。全量人评不现实，全信 judge 又不牢靠——抽样人评加 judge 初筛是性价比组合。
- **人工抽检**：分层抽样（好评/差评/长尾场景各抽）比纯随机更能暴露问题；差评全看，好评抽看。

### 4.4 高 QPS 采样

全量记录在开发期可行，线上高 QPS 不可行：存储成本、写入压力、敏感数据暴露面都会爆炸。采样策略：

| 策略 | 规则 | 适用 |
|---|---|---|
| 全量 | 100% 记录 | 开发、灰度期、低 QPS 内部工具 |
| 均匀采样 | 按比例（如 10%）随机丢 | 稳定期基线观测 |
| 尾部采样 | 错误、超时、超长延迟必采 | 与均匀采样叠加 |
| 质量触发采样 | 用户点踩、转人工、judge 低分的 trace 必采且不删 | 坏例沉淀（见 4.5） |
| 新版本提额 | 新模型/新提示词灰度期临时提到 100% | 变更观察窗口 |

要点：**采样丢的只能是「正常样本」，错误与坏例永远不丢**；被丢样本仍要留一行无内容的计数（如按步骤聚合计数），保证吞吐指标不失真。

### 4.5 坏例回放与回归集沉淀

可观测性的终局不是「看」，是「闭环」：

```text
线上 trace → 坏例识别（点踩/转人工/judge 低分）
  → 带完整轨迹回放：逐步定位是检索/提示/模型哪一步的锅
  → 修复后，把该例脱敏、加上期望行为，转成回归集新用例
  → 3.5 的评估体系在每次变更时重放回归集，防止复发
```

工程要点：

1. **回放要可复现**：trace 里记了模型名、参数、检索命中文档 ID 与提示全文（Generation 层），坏例才能原样重放；缺一项就只能「凭记忆修」。
2. **坏例入库要归因标签**：`retrieval_miss` / `faithfulness` / `format_error` / `tool_failure`，按标签统计才知道该优先修哪层。
3. **脱敏后再入库**：用户手机号、订单地址在入库前清洗；评估集进代码仓库，合规审查同样看它。
4. **闭环有节奏**：每周固定「坏例评审会」，入库的坏例当周转用例，否则坏例库变垃圾场。

## 5. 架构 / 流程

生产可观测性系统的一条数据流：

```text
应用进程（埋点 SDK / 结构化日志）
  │  每步 Span：retrieve/llm/tool/validate
  ▼
采集通道（OTel Collector / 平台 SDK 直传）
  │  采样过滤：错误必采、坏例必采、正常按比例
  ▼
存储（Trace 存储 + 生成明细留档 + 脱敏管道）
  │
  ├──▶ 性能面板：TTFT / P99 延迟 / 吞吐
  ├──▶ 成本面板：日 token / 单会话成本 / 预算燃尽
  ├──▶ 质量面板：差评率 / 拒绝率 / 转人工率 / 幻觉抽样
  └──▶ 告警：预算超 80%、P99 破线、质量突降 → 值班响应
        │
        └─▶ 坏例回放 → 回归集沉淀 → 3.5 评估闭环
```

## 6. 代码 / 工具

### 6.1 结构化 trace 日志实现（零依赖核心）

不依赖任何观测平台，先用结构化日志把记录集立起来——这正是「核心自持」的做法，日志按行输出 JSON，任何后端都能消费：

```python
import json
import time
import uuid
import logging

log = logging.getLogger("llm.trace")

class TraceRecorder:
    """最小 trace 记录集：Trace → Span → Generation 三层。"""

    def __init__(self, session_id: str):
        self.session_id = session_id
        self.trace_id = uuid.uuid4().hex
        self.trace_start = time.monotonic()
        self.total_in = 0
        self.total_out = 0

    def span(self, name: str, parent_id: str | None = None):
        return _Span(self, name, parent_id)

    def finish(self, output_summary: str, status: str = "ok"):
        rec = {
            "type": "trace", "trace_id": self.trace_id,
            "session_id": self.session_id, "status": status,
            "duration_ms": int((time.monotonic() - self.trace_start) * 1000),
            "tokens_in": self.total_in, "tokens_out": self.total_out,
            "output_summary": output_summary[:200],
        }
        log.info(json.dumps(rec, ensure_ascii=False))

class _Span:
    def __init__(self, trace: TraceRecorder, name: str, parent_id: str | None):
        self.t, self.name = trace, name
        self.span_id = uuid.uuid4().hex[:16]
        self.parent_id = parent_id
        self.attrs: dict = {}
        self.t0 = time.monotonic()

    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc, tb):
        status = "error" if exc else "ok"
        rec = {
            "type": "span", "trace_id": self.t.trace_id,
            "span_id": self.span_id, "parent_span_id": self.parent_id,
            "span_name": self.name, "duration_ms": int(
                (time.monotonic() - self.t0) * 1000),
            "status": status,
        }
        rec.update(self.attrs)   # input_summary/output_summary/tool_calls/...
        log.info(json.dumps(rec, ensure_ascii=False))

# —— 在 RAG 管线中使用 ——
def rag_answer(query: str, session_id: str) -> str:
    tr = TraceRecorder(session_id)
    with tr.span("retrieve") as s:
        docs = retriever.search(query, top_k=5)
        s.attrs = {"input_summary": query, "output_summary": f"{len(docs)} 条",
                   "retrieval_meta": {"top1_score": docs[0].score}}
    with tr.span("llm_call", parent_id=s.span_id) as s:
        prompt = build_prompt(query, docs)
        resp = llm.chat(prompt)
        s.attrs = {"input_summary": f"messages=2, chars={len(prompt)}",
                   "output_summary": resp.text[:200], "model": llm.model,
                   "tool_calls": [], "tokens_in": resp.usage.input,
                   "tokens_out": resp.usage.output}
        tr.total_in += resp.usage.input
        tr.total_out += resp.usage.output
    tr.finish(output_summary=resp.text)
    return resp.text
```

每行日志形如：

```json
{"type": "span", "trace_id": "a1b2", "span_name": "llm_call", "duration_ms": 2103, "status": "ok", "model": "gpt-4o-mini", "tokens_in": 3420, "tokens_out": 480, "input_summary": "messages=2", "output_summary": "退款需要3-5个工作日…"}
```

### 6.2 OTel `gen_ai.*` 语义约定示例

把同一次 LLM 调用按 OpenTelemetry 生成式 AI 语义约定导出（约定仍在演进，以官方最新版为准）：

```json
{
  "span_name": "chat gpt-4o-mini",
  "span_kind": "client",
  "attributes": {
    "gen_ai.system": "openai",
    "gen_ai.request.model": "gpt-4o-mini",
    "gen_ai.request.temperature": 0.2,
    "gen_ai.usage.input_tokens": 3420,
    "gen_ai.usage.output_tokens": 480,
    "gen_ai.response.finish_reasons": ["stop"]
  },
  "events": [
    { "name": "gen_ai.system.message", "attrs": { "content": "<系统提示摘要>" } },
    { "name": "gen_ai.choice", "attrs": { "content": "<输出文本摘要>" } }
  ]
}
```

选型三分法：

| 方案 | 定位 | 优点 | 局限 | 适用 |
|---|---|---|---|---|
| LangSmith | LangChain 官方全托管平台 | 与 LangChain/LangGraph 深度集成、评估数据集联动 | 生态绑定深、按量收费 | 已在 LangChain 生态、要快速起步 |
| Langfuse | 开源自托管 LLM 观测 | 可私有化部署、成本可控、会话聚合好用 | 要自己运维、SDK 覆盖需自接 | 数据不能出内网、成本敏感 |
| OTel `gen_ai.*` | 开放语义约定（非平台） | 后端可换、与既有 APM 融合、防锁定 | 面板与 LLM 专用功能要自建 | 已有 OTel 体系、强防锁定诉求 |

三分法口诀：**托管平台求快、自托管求控、开放约定求不被绑**；三者可叠加——应用按 OTel 约定打点，Langfuse 等后端兼收 OTel 数据。

## 7. 案例

### 案例 A：AI 客服的「效果怎么样、钱花得值不值」

**场景**：某电商平台 AI 客服上线两个月，管理层问效果与成本，团队答不上来。

**做法**：接入 Langfuse 全链路 trace；建四个面板（性能/成本/质量/业务）：P99 延迟、单会话成本、差评率、转人工率、每周 100 条抽样（judge 初判加人工复核）的幻觉命中率；设三条告警（日预算超 80%、P99 超 5 秒、差评率环比涨 30%）。

**效果**：两周后能给出数字——问题解决率 61%、单会话成本 0.18 元、最大短板是检索命中率（Top1 相关分低于 0.6 的会话差评率是其他的 4 倍）；优化排序从此有据。

### 案例 B：一次「变慢事故」的定位

**场景**：某 SaaS 助手 P99 从 4.2 秒涨到 7.8 秒，无任何报错。

**回放**：trace 显示 LLM 调用耗时不变（2.1 秒），retrieve 步从 300 毫秒涨到 5 秒；再下钻命中「知识库批量导入 2 万份新文档后向量库索引未重建」。

**效果**：定位 15 分钟，修复（重建索引）后恢复；若无 trace，这类「无报错劣化」要靠逐层肉眼排查数天。

### 案例 C：坏例沉淀成回归集

**场景**：某金融问答助手一个月内用户点踩 340 次。

**做法**：点踩 trace 全量回放，归因标签统计：检索未命中 45%、答非所问 25%、幻觉 18%、格式错误 12%；每周把修复后的坏例脱敏入库，三个月沉淀 220 条带标签的回归用例。

**效果**：随后两次提示词改版中，回归集提前拦下 6 处劣化；同类坏例复发率下降约 70%。

## 8. 常见坑

1. **只观测不回放**。只存耗时与 token、不存输入输出摘要，出错时无法定位是检索还是生成的锅；最小记录集一项不能少。
2. **全量记录不采样**。高 QPS 下存储成本指数上涨；错误与坏例必采，正常样本按比例采。
3. **只看均值不看分位**。均值 1 秒、P99 8 秒的体验是灾难；延迟必须看 P95/P99。
4. **质量指标缺失**。只盯延迟成本的绿灯，质量已漂移三周无人知——「正常返回」不等于「回答正确」。
5. **trace 不做脱敏**。用户手机号、身份证全量落库，观测系统成为最大数据泄露面；入库前必须清洗。
6. **无保留期策略**。生成明细留档无限增长；按敏感级定保留期（如 Generation 层 30 天、Span 层 90 天）。
7. **多轮对话不聚合**。没有 session_id，看不清「第 3 轮开始跑偏」这类会话级问题。
8. **告警只有基础设施**。预算燃尽、质量突降没有告警，只有 CPU 告警——LLM 特有风险全部裸奔。
9. **坏例只收集不闭环**。点踩数据躺在后台；坏例必须归因、修复、转回归用例，否则只是成本。
10. **采样丢掉了坏例**。均匀采样把点踩样本也丢了；质量触发采样必须独立于比例采样。
11. **trace 格式绑死平台**。用某平台私有 SDK 深度埋点，换后端等于重埋；按 OTel 约定打点，后端可换。
12. **只测新增不管回流**。回归集不随坏例更新，护栏逐渐失真；坏例库是评估集的活水（3.5 展开）。

6. 给 10 条 trace 打归因标签（检索未命中/幻觉/格式错误），统计分布并写出修复优先级建议。
7. 把 6.1 的日志格式改写为 OTel `gen_ai.*` 属性命名，对比两者字段映射，列出缺口。
8. 设计一份 trace 数据保留策略：区分 Span 层与 Generation 层的保留期与脱敏规则，写成半页制度。

## 10. 小结

- LLM 可观测性 = **给不确定的输出装仪表盘**：传统 APM 看「通没通」，这里还要看「答得好不好、贵不贵」。
- 三层数据模型：**Trace（一次请求）→ Span（一步）→ Generation（LLM 调用明细）**，父子关系构成可回放的链路树。
- 最小记录集：每步记**工具调用/token/耗时/输入输出摘要**，加 trace_id、parent_span_id、session_id 三键；缺一项回放就断链。
- 三类核心指标：**性能（分位延迟）、成本（token/预算）、质量（拒绝率/幻觉抽样/差评率/转人工率）**——质量指标是 LLM 特有新增项。
- 高 QPS 采样原则：**错误与坏例必采，正常样本按比例采，被丢样本留聚合计数**。
- 选型三分法：**托管平台求快（LangSmith）、自托管求控（Langfuse）、开放约定求不绑（OTel `gen_ai.*`）**，可叠加使用。
- 终局是闭环：**trace 回放定位坏例 → 归因修复 → 脱敏沉淀为回归集 → 3.5 评估体系消费**。
- 记住三个定位问题：慢在哪一步、钱花在哪、质量差在哪层——trace 是唯一能同时回答三者的工具。
- 观测标准（OTel）应与框架选型（3.3）一起定，它直接决定你的绑定深度。
