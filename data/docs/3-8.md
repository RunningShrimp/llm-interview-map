# 讲解 3.8 安全、合规与权限

> 说明：1.2b 解决「注入骗 Agent 说话」，2.9 给过 Agent 安全的总览；本篇解决「限制 Agent 做事」——最小权限、权限衰减、子 Agent 授权、高危人审、PII 脱敏、审计四要素与合规趋势，输入侧与权限侧合起来才是 Agent 安全全貌。
> 4.3 数据分析 Agent 的沙箱与只读账号是本篇的实操落地，3.10 的人机协同会展开审批工作流的产品形态。

## 1. 定位

L3 工程层第 8 个知识点，回答大纲里的关键问题：**如何做到最小权限与可审计？**

依赖链：1.2b（Prompt 注入防护）处理输入侧——攻击者通过内容操控模型；本篇处理权限侧——即使模型被操控，它能造成的破坏也被权限边界框住。3.1（架构与接口设计）的接入层与数据层是本篇权限模型落地的两个位置：鉴权在接入层，数据隔离在数据层。

向后支撑：4.3（数据分析 Agent，生成的 SQL/Python 必须进隔离沙箱、只读账号、白名单、超时——本篇原则的代码执行场景实操）、3.10（人机协同，高危审批工作流的产品化）、2.8（多 Agent 协作，子 Agent 授权是协作架构的安全约束）。

## 2. 一句话定义

Agent 能读私有数据、执行代码、修改外部系统，安全模型必须从「防说错话」升级为「防做错事」：按任务动态授予最小权限、任务结束权限衰减、子 Agent 单独授权、高危操作人工审批、PII 在数据与日志双重脱敏、全链路留痕到能 5 分钟内答出「谁、做了什么、影响多大、谁批的」。

## 3. 为什么需要

一个反直觉的事实：**不做任何配置时，Agent 的默认权限是「无限」的**。它以运行环境身份跑，能读的文件、能调的网络、能执行的命令一概继承——Agent 以服务账号运行，而服务账号在数据库里往往是全能的。很多团队的第一次 Agent 事故都源于此：不是模型「决定」作恶，而是它被注入误导（1.2b 的攻击面）或逻辑跑偏（4.9 的软故障）后，手里恰好握着万能钥匙。

传统 LLM 应用（问答、摘要）最坏结果是说错话；Agent 的最坏结果是**做成错事**：删库、转账、对外群发。风险等级完全不同：

| 维度 | 传统 LLM 应用 | Agent |
|---|---|---|
| 最大风险 | 输出错误内容 | 执行破坏性动作 |
| 攻击面 | 输入文本 | 输入文本 + 工具 + 环境 + 子 Agent 链 |
| 权限模型 | 基本不需要 | 必须显式设计 |
| 审计要求 | 日志留档即可 | 全链路结构化留痕、可倒查 |
| 合规范围 | 内容合规 | 数据保护 + 操作合规 + 责任链 |

**Agent 安全的第一课是「先假设它什么都做得到，再一层层收权」，而不是「它应该不会有问题吧」。**

## 4. 核心原理

### 4.1 最小权限原则（Least Privilege）

给 Agent 干活像给实习生配工牌：不会把公司大门钥匙、财务章和全部密码做成一张万能工牌，而是给一张「今天下午、只能进 3 楼档案室、只能查不能拿」的临时卡。落地三层：

| 层 | 手段 | 反例 |
|---|---|---|
| 身份层 | Agent 用独立服务身份，与用户身份绑定（代行授权），绝不复用 root 或业务写账号 | Agent 拿数据库管理员账号跑批 |
| 能力层 | 只读账号优先；工具白名单；命令/SQL 白名单与参数化模板 | 允许 Agent 自由拼 SQL 直连生产库 |
| 数据层 | 行级/列级权限（按角色只看本品类）、敏感字段默认脱敏 | 全表开放查询，手机号明文返回 |

### 4.2 权限衰减（Permission Decay）

临时凭证随任务推进与时间收缩，任务结束自动失效——杜绝「一次授权终身有效」的万能工牌：

- **按任务授权**：授权范围 = 当前任务所需的最大集合，不是 Agent 系统的全集。
- **时间盒**：凭证带 TTL（如 30 分钟），超时自动失效；长任务滚动续期并留痕。
- **单调收缩**：任务进行中权限只减不增——数据导出完成后的下载凭证用完即焚。
- **显式回收**：任务完成、失败、取消三条路径都要触发凭证吊销，失败路径最常被漏。

### 4.3 子 Agent 不继承权限

2026 年的高频追问：「主管 Agent 有权查财务，它派生一个『翻译报表为英文』的子 Agent，子 Agent 该继承什么权限？」答案是**只获得本次翻译所需的最小权限（拿到已脱敏的文本），不接触数据库连接**。

「子 Agent 继承父权限」是最典型的反模式：它把攻击面放大到每个分支节点——任一子 Agent 被注入，攻击者就拿到了财务库权限。正确做法是父 Agent 完成数据读取后，把**脱敏结果**作为数据传给子 Agent；子 Agent 的授权只覆盖文本处理这一步。权限随任务树传播时逐层收窄，不是逐层复制。

### 4.4 高危操作人工审批

删除、付款、对外发送类动作必须挂起等人批准，且审批要带明确范围：

| 级别 | 动作示例 | 控制 |
|---|---|---|
| 低危 | 查询、计算、生成文本 | 自动执行，留痕 |
| 中危 | 写内部缓存、创建草稿、调用付费 API（小额） | 配额内自动，超配额告警 |
| 高危 | 删数据、转账付款、对外发送、改生产配置 | 挂起人审：审批人确认范围（哪个库/哪批数据/多少金额）后放行 |

审批设计三要素：**范围明确**（审批的是「test_db.orders 限定 2025 年的 3207 行」，不是「删点数据」）；**审批留痕**（谁在何时批准了什么范围）；**最小执行**（放行后仍以临时凭证执行，影响行数回写审计）。

### 4.5 PII 脱敏：数据与日志双重脱敏

PII（Personally Identifiable Information，个人身份信息）的泄露重灾区不是数据库，而是**日志与 Trace**——它们被广泛广播、长期保存、权限宽松。

- **入模型前脱敏**：身份证、手机号、地址在进入 Prompt 前替换为占位符或 token 化引用，需要原文时由受控服务反查。
- **入日志前脱敏（双重脱敏的第二重）**：查询参数、Prompt、响应在落盘前过脱敏管道。审计日志本身要脱敏，否则审计系统会成为最大泄露源——这一点能主动说出来，方案才算完整。
- **合规底线**：训练/评估数据要过合规审查；用户数据的使用要与其授权范围一致。

### 4.6 审计四要素

可审计性 = 结构化留痕 + 可检索。每次敏感操作必须能回答四问：

| 要素 | 记录内容 | 反查问题 |
|---|---|---|
| 人 | 发起用户（真实身份，经 SSO 绑定）、执行 Agent 实例 | 谁发起的？ |
| 动作 | 工具名 + 完整参数（SQL 语句、API 参数） | 让 Agent 做了什么？ |
| 范围 | 影响的数据范围：库表、行数、金额、接收方 | 影响了多少数据？ |
| 审批 | 审批人、审批时间、批准的范围、审批意见 | 谁批准的？ |

合规检查的实战问法：「上个月 15 号，是谁批准 Agent 删除了生产库的哪批数据？」——四要素齐全且能按时间检索，几分钟内答出，才算过线。邮件抄送和截图无法结构化检索，本质等于没有审计。

### 4.7 合规趋势

监管在追着 Agent 能力跑，三个方向要盯：

- **GDPR（欧盟通用数据保护条例）**：数据最小化（只收集任务必需）、目的限定、被遗忘权（用户可要求删除，Agent 系统的记忆与日志要支持定向清除）、数据保护影响评估（DPIA）对高风险自动化处理是硬要求。
- **个人信息保护法（个保法，中国）**：知情同意、最小必要、敏感个人信息单独同意、自动化决策的透明度与拒绝权；Agent 处理个人信息属于「自动化决策」范畴。
- **趋势口径**：Agent 时代监管焦点从「内容」转向「行为与责任链」——谁授权、谁批准、谁担责；2026 年面试已出现「Agent 时代监管」类开放题，答法是把 4.2~4.6 的机制映射到法规条款，而不是背法条。

## 5. 架构 / 流程

一次高危操作的完整生命周期（每环都有留痕，出事可倒查）：

```text
┌──────────────────────────────────────────────────────────┐
│ ① 接入与鉴权（接入层）                                     │
│    用户经 SSO 登录 → 角色解析 → 与 Agent 服务身份绑定       │
│    授权 = f(角色, 任务类型)：按任务动态生成权限集            │
├──────────────────────────────────────────────────────────┤
│ ② 执行前校验（权限中间件，每次工具调用都过）                 │
│    身份 → 能力（白名单）→ 数据范围（行/列级）→ 危级判定      │
│    低/中危：放行执行，留痕                                  │
│    高危：拦截 → 生成审批工单（动作+参数+影响范围预估）        │
├──────────────────────────────────────────────────────────┤
│ ③ 人工审批                                                 │
│    审批人确认范围（test_db.orders，限定 2025 年）→ 批准      │
│    批准记录入审计日志（审批人/时间/范围）                    │
├──────────────────────────────────────────────────────────┤
│ ④ 最小执行（数据层）                                       │
│    以限时只读+限定范围的临时凭证执行                         │
│    SQL 语句与影响行数（3207 行）写入审计日志                 │
│    结果经脱敏管道返回；日志侧同管道再脱敏一次（双重脱敏）     │
├──────────────────────────────────────────────────────────┤
│ ⑤ 回收与归档                                               │
│    任务结束（完成/失败/取消）→ 临时凭证自动失效             │
│    审计记录归档 180 天，支持按人/时间/动作检索               │
└──────────────────────────────────────────────────────────┘
     权限曲线：环境默认（全部）→ 按任务裁剪 → 衰减 → 归零
     （单调递减，任何一步都不可逆向上跳）
```

## 6. 代码 / 工具

### 6.1 权限校验中间件

```python
"""Agent 工具调用的权限中间件：最小授权 + 高危拦截 + 权限衰减。"""
import time
import secrets
from dataclasses import dataclass, field


@dataclass
class Permission:
    """一次任务授权：范围明确、带 TTL、可吊销。"""
    scopes: set                     # 允许的能力，如 {"db:read", "sql:template"}
    data_scope: dict                # 数据范围，如 {"db": "test_db", "table": "orders", "year": 2025}
    max_rows: int = 10_000          # 单次影响行数上限
    ttl_seconds: int = 1800         # 时间盒：超时自动失效
    expires_at: float = field(default_factory=lambda: time.time() + 1800)

    def alive(self) -> bool:
        return time.time() < self.expires_at

    def shrink(self, scopes: set):
        """权限衰减：任务推进中只减不增。"""
        self.scopes &= scopes


class PermissionDenied(Exception):
    pass


class ApprovalRequired(Exception):
    """高危操作：挂起等人工审批，携带完整上下文供审批人确认范围。"""
    def __init__(self, action: str, params: dict, scope_hint: str):
        self.action, self.params, self.scope_hint = action, params, scope_hint
        super().__init__(f"高危操作待审批：{action}，范围：{scope_hint}")


HIGH_RISK_ACTIONS = {"db:delete", "db:update", "payment:execute", "email:send_bulk"}


def issue_permission(scopes, data_scope, ttl_seconds=1800, max_rows=10_000) -> Permission:
    """按任务动态授权：只给本任务所需的最大集合，绝不给全集。"""
    return Permission(scopes=set(scopes), data_scope=data_scope,
                      ttl_seconds=ttl_seconds,
                      expires_at=time.time() + ttl_seconds, max_rows=max_rows)


def enforce(perm: Permission, action: str, params: dict) -> dict:
    """每次工具调用前的校验入口：衰减检查 → 能力 → 数据范围 → 危级。"""
    if not perm.alive():
        raise PermissionDenied("授权已过期（权限衰减）")

    if action not in perm.scopes:
        raise PermissionDenied(f"能力不在授权范围：{action}")

    if action.startswith("db:"):
        for k, v in perm.data_scope.items():                    # 数据范围硬校验
            if k in params and params[k] != v:
                raise PermissionDenied(f"越界访问 {k}={params.get(k)}，授权仅限 {v}")

    if action in HIGH_RISK_ACTIONS:
        scope_hint = f"{perm.data_scope.get('db')}.{perm.data_scope.get('table')} " \
                     f"限定 {perm.data_scope.get('year')} 年，上限 {perm.max_rows} 行"
        raise ApprovalRequired(action, params, scope_hint)      # 挂起人审，不放行直接执行

    return {"ok": True, "action": action}


def run_task():
    """父任务：查财务数据 → 派子 Agent 翻译（子 Agent 不继承数据库权限）。"""
    perm = issue_permission(scopes={"db:read", "db:delete"},     # 本任务上限
                            data_scope={"db": "test_db", "table": "orders", "year": 2025},
                            ttl_seconds=1800)

    rows = enforce(perm, "db:read", {"db": "test_db", "table": "orders", "year": 2025})
    rows["sql"] = "SELECT ... LIMIT 1000"                        # 参数化模板，非自由拼 SQL

    perm.shrink({"db:read"})                                     # 读取完成后收走删除权限
    try:
        enforce(perm, "db:delete", {"db": "test_db"})            # 已被 shrink，直接拒绝
    except PermissionDenied as e:
        print(f"[衰减生效] {e}")

    try:
        enforce(perm, "db:delete", {"db": "prod_db"})            # 越界库
    except PermissionDenied as e:
        print(f"[越权拦截] {e}")

    sanitized = mask_pii("客户张三 13800138000 订单 2025-001")    # 子 Agent 只拿脱敏文本
    child_perm = issue_permission(scopes={"text:translate"},     # 子 Agent 单独最小授权
                                  data_scope={}, ttl_seconds=300)
    enforce(child_perm, "text:translate", {})
    print(f"[子 Agent] 权限：{child_perm.scopes}，输入：{sanitized}")
```

### 6.2 审计日志与双重脱敏实现

```python
"""审计日志：四要素结构化留痕 + 可检索 + PII 双重脱敏（数据面与日志面各过一次管道）。"""
import json
import time
import re
import hashlib

PII_PATTERNS = [
    (re.compile(r"1[3-9]\d{9}"), "[PHONE]"),                          # 手机号
    (re.compile(r"\d{17}[\dXx]"), "[IDCARD]"),                        # 身份证
    (re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+"), "[EMAIL]"),              # 邮箱
]


def mask_pii(text: str) -> str:
    """脱敏管道：数据进模型前、日志落盘前各调用一次（双重脱敏）。"""
    for pattern, repl in PII_PATTERNS:
        text = pattern.sub(repl, text)
    return text


class AuditLog:
    """四要素：人 / 动作 / 范围 / 审批。结构化、可检索、不可静默篡改。"""

    def __init__(self, sink: list):
        self.sink = sink                       # 生产中替换为 WORM 存储/追加式日志服务

    def record(self, actor: str, agent_id: str, action: str, params: dict,
               scope: dict, approved_by: str | None, result: dict):
        entry = {
            "ts": time.time(),
            "actor": actor,                                    # 要素一：人（真实用户）
            "agent_id": agent_id,
            "action": action,                                  # 要素二：动作
            "params": json.loads(mask_pii(json.dumps(params, ensure_ascii=False))),
            "scope": scope,                                    # 要素三：范围（库表/行数/金额）
            "approved_by": approved_by,                        # 要素四：审批（高危必填）
            "result": {"affected_rows": result.get("affected_rows", 0),
                       "status": result.get("status")},
            "digest": None,
        }
        entry["digest"] = hashlib.sha256(                      # 链式摘要：防静默篡改
            json.dumps(entry, sort_keys=True).encode()).hexdigest()
        self.sink.append(entry)
        return entry

    def query(self, actor: str | None = None, action: str | None = None,
              since: float | None = None) -> list:
        """合规反查：「上个月 15 号谁批准删了什么」要能按人/动作/时间秒级检索。"""
        hits = self.sink
        if actor:
            hits = [e for e in hits if e["actor"] == actor]
        if action:
            hits = [e for e in hits if e["action"] == action]
        if since:
            hits = [e for e in hits if e["ts"] >= since]
        return hits


audit = AuditLog(sink=[])

# 高危操作：审批通过后执行，四要素齐全落盘
audit.record(actor="ops_wang", agent_id="agent-da-01",
             action="db:delete", params={"sql": "DELETE FROM orders WHERE year=2025"},
             scope={"db": "test_db", "table": "orders", "year": 2025, "rows": 3207},
             approved_by="lead_li", result={"affected_rows": 3207, "status": "ok"})

# 日志侧验证：手机号已脱敏，即使日志库被拖也不泄露
audit.record(actor="ops_wang", agent_id="agent-da-01",
             action="db:read", params={"q": "张三 13800138000 的订单"},
             scope={"db": "test_db", "table": "orders"},
             approved_by=None, result={"affected_rows": 3, "status": "ok"})

print(json.dumps(audit.query(action="db:delete"), ensure_ascii=False, indent=1))
# 审计系统的注意点：params 里的 PII 已被第二重管道脱敏——审计日志本身不能成为泄露源。
```

task_types:
  data_analysis:

  queryable_by: [actor, action, time_range]

## 7. 案例

### 案例 A：数据分析 Agent 的导出管控

**场景**：一家电商的数据分析 Agent 要向运营开放「查询并导出订单数据」。

**权限模型**：运营经 SSO 登录按角色授权——普通运营只查本品类聚合数据，负责人可查明细；Agent 用独立只读账号；查询走白名单参数化模板，不允许自由拼 SQL 直连。**高危控制**：导出超一万行或含手机号字段自动升级人工审批，导出文件加水印并记录接收人。**脱敏**：手机号与地址默认脱敏展示，日志与 Trace 中查询参数先脱敏再落盘。**审计**：每次查询记录发起人、时间、查询模板与参数、返回行数、是否触发审批，日志不可篡改、保存 180 天、可按人与时间检索。

**效果**：上线后越权查询拦截 11 次（均为角色范围外的品类），合规审查一次通过；审计反查任意一次导出的「人/动作/范围/审批」在 1 分钟内完成。

### 案例 B：删除过期数据的审计链

**场景**：Agent 接到「删除过期测试数据」指令，动作命中高危清单被拦截。

**链路**：审批队列生成工单，值班工程师确认范围（test_db.orders，限定 2025 年）并批准；执行时以只读加限时删除的临时凭证运行，删除语句与影响行数（3207 行）写入审计日志；任务结束临时凭证自动失效，记录归档 180 天。

**效果**：三个月后审计抽查，从「谁批的、删了哪批、影响多少行」到完整证据链还原用时 4 分钟。若当时权限是「服务账号直连」，这条链路将无从谈起——删除可能直接命中生产库。

### 案例 C：子 Agent 注入事故（反例复盘）

**场景**：一家金融科技公司的主管 Agent 负责财报分析，它派生一个「摘要报表」子 Agent；初期实现里子 Agent 直接继承父任务全部工具权限。某次报表附件被注入恶意指令，子 Agent 被误导调用财务库连接尝试导出。

**拦截与复盘**：因为子 Agent 走了独立授权改造后（只拿到脱敏文本、无数据库 scope），注入指令在校验层被拒；改造前的老版本则依赖「子 Agent 不做坏事」的侥幸。

**效果与教训**：改造后同类注入全部拦截在能力校验层。教训写在复盤结论第一条：**权限随任务树逐层收窄，继承就是把攻击面复制到每个分支。**

## 8. 常见坑

1. **默认权限放任**。不配置时 Agent 继承运行环境全部能力；第一课是先收权，不是先信任。
2. **Agent 复用业务账号或 root**。越权无从界定、审计无从归因；独立服务身份是底线。
3. **授权一次终身有效**。凭证无 TTL、任务结束不回收；时间盒加三路径吊销（完成/失败/取消）。
4. **子 Agent 继承父权限**。攻击面复制到每个分支，任一节点被注入全线失守；按子任务单独最小授权。
5. **父传子传原文**。子 Agent 只需要脱敏结果；传数据库连接或全量原文等于传钥匙。
6. **高危操作靠 Prompt 约束**。Prompt 可被注入绕过；删除、付款、外发必须走代码层的挂起人审。
7. **审批不含范围**。「批准删除」不等于「批准删除 test_db.orders 的 2025 年数据」；审批粒度必须到库表与行数。
8. **日志记了 Prompt 明文**。日志与 Trace 是泄露重灾区；落盘前必须过脱敏管道。
9. **只脱敏数据不脱敏日志**。审计系统自己成为最大泄露源——双重脱敏缺一不可。
10. **审计不可检索**。日志存在但按人/时间查不出来，合规检查等于没过；结构化四要素加检索索引。
11. **审计可篡改**。可改写的日志在追责时不被采信；追加式存储加链式摘要。
12. **越权只拦不报**。每次拦截都应告警并计数——拦截率本身是最重要的安全信号。
13. **合规当成法条背诵**。把最小化、留痕、审批映射到 GDPR/个保法条款的机制设计才是面试与实战的正确答法。
14. **沙箱外执行生成代码**。Agent 生成的 SQL/Python 必须进隔离沙箱（只读账号、白名单、超时）——4.3 是本篇的执行场景落地。

## 9. 练习

1. 用 6.1 的中间件跑通三条路径：正常读取、衰减后拒绝、越界库拒绝；再触发一次高危审批，观察工单里的范围提示。
2. 给 Permission 增加「滚动续期」：长任务到期前校验任务仍在活跃状态才续期，并记审计。
3. 用 6.2 的脱敏管道测 10 组真实格式数据（手机号、身份证、邮箱混排），验证召回率；补一种你业务里的敏感格式。
4. 实现审计反查接口：给定「上月 15 号」与操作类型，1 秒内返回完整四要素；故意篡改一条记录，验证摘要校验能否发现。
5. 把 6.3 的 YAML 扩展一个任务类型（如「邮件营销」），明确它的 scopes、审批策略与脱敏字段，并说明每条的理由。
6. 复现案例 C：搭一个父 Agent 加子 Agent 的最小链路，分别在「继承权限」与「单独授权」两种模式下注入同一条恶意指令，对比结果。
7. 写一份合规映射表：把最小权限、权限衰减、双重脱敏、审计四要素分别对应到 GDPR 与个保法的具体原则，每行一句话理由。
8. 审计你们现有项目的一个 Agent：列出它当前持有的全部凭证与工具，标注哪些超出「当前任务所需」，写收权清单。

## 10. 小结

- Agent 安全模型从「防说错话」升级为「防做错事」；与 1.2b 的输入侧防护合起来才是全貌。
- **默认权限是无限的**：先假设 Agent 什么都做得到，再一层层收权——身份、能力、数据三层落地最小权限。
- **权限衰减**：按任务授权、TTL 时间盒、单调收缩、三路径吊销；杜绝万能工牌。
- **子 Agent 不继承权限**：权限随任务树逐层收窄，父传子传脱敏结果而非连接与原文；继承是最典型反模式。
- **高危操作人审**：删除、付款、外发挂起；审批必须带范围（库表/行数/金额），审批记录留痕。
- **PII 双重脱敏**：入模型前一次、入日志前一次；审计日志本身要脱敏，否则审计系统成为最大泄露源。
- **审计四要素**：人、动作、范围、审批——结构化、可检索、防篡改，合规反查要能分钟级作答。
- **合规趋势**：GDPR 与个保法把焦点从内容转向行为与责任链——最小化、目的限定、被遗忘权、自动化决策透明度。
- 代码层的校验中间件加声明式策略，是把原则变成工程事实的唯一方式；Prompt 约束不能替代权限控制。
- 这些机制在 4.3（数据分析 Agent 沙箱）实操化，在 3.10（人机协同）产品化，在 2.8（多 Agent 协作）成为架构约束。
