## 1. 定位

AI 工程化层第 8 个知识点，属于“信任与合规基础设施”。  
它解决本锚点的核心问题：**Agent 能做事，但如何保证它只做该做的事、只碰该碰的数据、留下该留的记录？**——也就是如何做到最小权限与可审计。

与 1.7 的分工：1.7 是应用层安全入门，讲单应用的提示注入（Prompt Injection）防护、密钥管理、成本与延迟；本篇把它升级为工程化层的体系工程——认证授权体系、数据隔离、审计链路、PII 治理、内容安全管线、供应链与合规框架，重复的基础结论收敛为一句指路：注入的攻防细节见 1.7，Agent 安全的评估口径见 2.9，红队实战见 4.8。

前置：1.7 应用层安全、3.1 架构与接口设计（安全组件挂在架构的哪些边界上）。  
后续：3.9 发布门禁、4.3 沙箱执行、4.8 红队检验。

## 2. 一句话定义

安全、合规与权限，是通过身份认证、访问控制、数据隔离、审计追踪、内容安全、供应链管控与合规检查等机制，确保 Agent 系统在合法、合规、可控、可审计的边界内运行的工程体系。

简化公式：

```text
信任 = 认证（你是谁） + 授权（你能做什么） + 隔离（你看不到别人的）
     + 审计（你做了什么） + 合规（你符合规定）
```

## 3. 为什么需要

Demo 阶段只关心“能不能用”；生产阶段有十类事故：

- **越权**：普通用户诱导 Agent 调用管理员工具，查看他人订单。
- **数据泄露**：多租户（Multi-tenancy）系统，A 公司检索到 B 公司文档。
- **提示注入**：用户覆盖系统指令，Agent 执行恶意操作。
- **PII 泄露**：日志、输出、缓存中含手机号、身份证。
- **合规违规**：GDPR、个保法、行业法规，违规罚款。
- **审计缺失**：监管要求所有操作可追溯，出事无法举证。
- **供应链攻击**（Supply Chain Attack）：第三方模型、插件、MCP Server 带后门。
- **内容安全**：输出违法、有害、歧视内容。
- **成本攻击**：恶意用户刷接口，成本爆炸（预算兜底见 3.7）。
- **模型滥用**：Agent 被用来批量生成垃圾内容、诈骗素材。

| 维度 | Demo 阶段 | 生产阶段 |
|---|---|---|
| 身份 | 用户自报，或者干脆没有 | 认证系统签发，不可自称 |
| 权限 | 能拿到所有工具 | 按角色、作用域、时效收缩 |
| 数据 | 单租户全部可见 | 多租户强制隔离 |
| 日志 | 排错用，想删就删 | 审计留痕，不可篡改，保留 1–7 年 |
| 上线检查 | 跑通即可 | 合规审查 + 红队 + 内容安全 |

**类比**：

```text
没有安全 = 一栋没有门禁、没有监控的办公楼：任何人进任何楼层、翻任何文件柜，
           出了事查不到人
有安全   = 刷卡进大堂（认证）、按权限开楼层（授权）、访客只能进指定会议室（作用域）、
           全程监控且事后可回放（审计）、消防年检定期过（合规）
```

## 4. 核心原理

### 4.1 安全体系全景

```text
┌──────────────────────────────────────────────┐
│ 身份层    认证（AuthN）：你是谁               │
│           授权（AuthZ）：你能做什么           │
│           会话管理：登录状态与过期            │
├──────────────────────────────────────────────┤
│ 数据层    数据分级：公开 / 内部 / 机密 / PII   │
│           数据隔离：多租户、行级、文档级       │
│           加密：传输 + 存储；脱敏：PII 处理    │
├──────────────────────────────────────────────┤
│ 应用层    输入过滤：注入检测                  │
│           输出过滤：内容安全                  │
│           工具权限：白名单 + 角色 + 风险分级   │
│           人工审批：高风险操作                │
│           沙箱：代码执行（4.3 展开）          │
├──────────────────────────────────────────────┤
│ 审计层    操作日志 / 访问日志 / 合规报告 / 告警 │
├──────────────────────────────────────────────┤
│ 供应链层  模型来源 / 插件与 MCP 审核          │
│           依赖扫描 / 密钥管理                 │
└──────────────────────────────────────────────┘
```

### 4.2 认证（Authentication，AuthN）

一句话原则：**身份不能由用户声称，必须由认证系统证明。**

| 方式 | 说明 | 适用 |
|---|---|---|
| API Key | 静态密钥，服务间调用 | 须配合 IP 白名单与定期轮转 |
| OAuth 2.0 | 授权框架，令牌可撤销 | 第三方登录、Agent 代表用户访问 |
| JWT | 无状态令牌（JSON Web Token），自带角色与过期 | 微服务、Agent 会话 |
| SSO | 单点登录（Single Sign-On），接企业身份源 | 企业内部 |
| mTLS | 双向证书认证 | 高安全服务间 |
| 生物识别 | 指纹/人脸 | 端侧高安全场景 |

Agent 特有的一点：Agent 代表用户行事时，令牌要携带**代理身份（on-behalf-of）**——既是用户 u1 的授权，也是 Agent 服务自身的身份；出事时审计要能同时回答“哪个用户授权的、哪个服务执行的”。

关键原则：

- 身份字段（user_id、roles、tenant_id）只从 token 解出，绝不从请求体读。
- Token 必须有过期时间；敏感操作叠加二次验证。
- 签发与校验的完整代码见 6.1。

### 4.3 授权（Authorization，AuthZ）

| 模型 | 判定依据 | 灵活性 | 维护成本 | 典型用法 |
|---|---|---|---|---|
| RBAC（基于角色） | 用户 → 角色 → 权限 | 低到中 | 低 | 工具级权限基线 |
| ABAC（基于属性） | 用户/资源/环境属性规则 | 高 | 中 | 数据级判断（本人、同租户） |
| ReBAC（基于关系） | 实体关系图（所有者、成员） | 高 | 高 | 文档协作类复杂关系 |
| PBAC（基于策略） | 集中策略引擎，策略可热更新 | 最高 | 中到高 | 动态策略、外部授权服务 |

叠加原则：**RBAC 定工具级（能不能调这个工具），ABAC 定数据级（能对哪条数据调），二者叠加而不是二选一。** 判定顺序固定：先白名单、再角色、再属性、再阈值，任何一步失败即拒绝（完整链路见 §5，实现见 6.1 与 6.2）。

### 4.4 最小权限：角色、作用域、时效

正面回答本锚点关键问题的上半句。最小权限（Principle of Least Privilege）= **默认拒绝（Deny by Default）+ 三个收缩维度**：

| 机制 | 收缩什么 | 怎么做 |
|---|---|---|
| 角色基线 | 能用哪些工具 | 每个角色只挂完成任务所需的最小工具集，工具按风险分级（见 4.9） |
| 作用域（Scope） | 能碰哪些数据 | 参数级限制（只能退本租户订单、金额上限）+ 查询强制注入过滤（见 4.5） |
| 时效（TTL） | 权限活多久 | 按任务签发短时凭证（scoped token），任务结束或超时自动失效 |

**权限衰减**（Privilege Attenuation）：权限随任务生灭，不是随账号常驻。

```text
任务授权时间线：
t0 任务创建    scope = {tools: [search_orders], data: tenant_a/u1 的订单, ttl: 30min}
t1 执行中      只能调 search_orders，只能查 u1 的订单
t2 派生子任务  子 Agent 只继承子任务所需的最小子集（不是父 Agent 全量）
t3 完成/超时   scope 立即失效，旧凭证再调用一律 401
```

**类比**：最小权限就是酒店的房卡——只能开你住的楼层和房间（作用域），退房立刻失效（时效），员工卡能开的门更多但也按岗位发（角色）。

**面试高频问法**：“如何给 Agent 设计最小权限？子 Agent 该不该继承父任务的全部工具权限？”共识口径：默认拒绝，权限按任务动态授予——角色定基线、作用域限数据、时效限存活；子 Agent 只继承子任务所需的最小子集，全量继承是最常见的反模式，一次提示注入就能借子 Agent 放大成全局越权。

### 4.5 数据隔离

| 级别 | 说明 | 隔离度 | 成本 |
|---|---|---|---|
| 共享表 + tenant_id | 所有租户一张表，查询带过滤 | 低 | 低 |
| 独立 Schema | 每租户一个 Schema | 中 | 中 |
| 独立数据库 | 每租户一个库 | 高 | 高 |
| 独立实例 | 每租户一套存储 | 最高 | 最高 |

两条铁律：

- **过滤条件必须由服务端注入**，不能来自模型生成的查询参数——模型输出是待验证数据，不是可信输入。
- **应用层过滤 + 数据库行级安全（RLS，Row-Level Security）双层兜底**：应用层漏了，数据库还能拦住。

向量库隔离——写入时打标（检索侧强制过滤见 6.4）：

```python
# 写入时打标：tenant_id 与权限标签跟着文档走
collection.add(
    documents=[content],
    metadatas=[{
        "tenant_id": "company_a",
        "dept": "hr",
        "permission": ["hr_admin", "hr_user"],
    }],
    ids=[doc_id],
)
```

数据库行级安全（PostgreSQL）：

```sql
CREATE POLICY tenant_isolation ON documents
    USING (tenant_id = current_setting('app.tenant_id')::uuid);

ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
```

### 4.6 PII 与数据分级

数据分级与处理（PII，Personally Identifiable Information，个人身份信息）：

| 级别 | 例子 | 进入 Agent 前 | 存储与审计 |
|---|---|---|---|
| 公开 | 产品介绍、帮助文档 | 无限制 | 常规记录 |
| 内部 | 流程文档、周报 | 权限控制 | 记录访问者 |
| 机密 | 财务、合同 | 加密 + 严格权限，默认不进上下文 | 高风险标记 + 审批 |
| PII | 姓名、电话、身份证、卡号 | 脱敏（Masking）或假名化 | 加密存储，禁止明文入日志 |

脱敏实现（内容安全管线复用它，见 6.5）：

```python
import re

class PIIMasker:
    """正则脱敏：进入模型、写入日志前统一处理。"""
    PATTERNS = {
        "phone":     (r"1[3-9]\d{9}", "[手机]"),
        "id_card":   (r"\d{17}[\dXx]", "[身份证]"),
        "email":     (r"[\w.-]+@[\w.-]+", "[邮箱]"),
        "bank_card": (r"\d{16,19}", "[银行卡]"),
        "name":      (r"(?<=姓名：)[^\s]+", "[姓名]"),
    }

    def mask(self, text: str) -> str:
        for pattern, repl in self.PATTERNS.values():
            text = re.sub(pattern, repl, text)
        return text

    def detect(self, text: str) -> list:
        return [name for name, (pattern, _) in self.PATTERNS.items()
                if re.search(pattern, text)]
```

合规框架（截至 2026 年的主流口径，条款以官方文本为准）：

| 法规/框架 | 关注点 | 对 Agent 系统的直接要求 |
|---|---|---|
| GDPR（欧盟） | 个人数据 | 知情同意、被遗忘权（可删除）、数据可携带（可导出）、默认脱敏 |
| 个保法（中国） | 个人信息 | 告知同意、最小必要、敏感信息单独同意、境内存储与跨境评估 |
| HIPAA（美国医疗） | 医疗数据 | 受保护健康信息的访问控制与审计留痕 |
| PCI DSS | 支付卡数据 | 卡号加密存储、传输加密，严禁明文进日志 |
| EU AI Act（欧盟，2024 年生效，义务分阶段适用至 2027 年） | AI 系统风险分级 | 高风险用途的文档、日志与人工监督义务 |
| 生成式 AI 服务管理暂行办法（中国，2023 年施行） | 生成内容 | 内容合规、数据来源合法、服务备案 |

### 4.7 审计与可审计性

正面回答本锚点关键问题的下半句。**可审计的完整定义：能一句话回答——谁在何时让 Agent 以什么权限对什么资源做了什么、结果如何、谁批准的。** 这句话落地成审计事件模型：

| 字段 | 示例 | 回答的问题 |
|---|---|---|
| trace_id / run_id | abc123 / run-456 | 哪一次执行（与 3.4 的全链路 trace 串联） |
| timestamp | 2026-01-15T10:30:00Z | 何时 |
| user_id / tenant_id | u1 / company_a | 谁发起、属于哪个租户 |
| agent_id / tool | agent-cs / initiate_refund | 让哪个 Agent 用什么工具做什么 |
| roles / scope | ["admin"] / tenant_a:orders | 以什么身份与作用域 |
| resource | order:12345 | 对什么对象 |
| args（脱敏后） | {"amount": 1000, "reason": "质量问题"} | 具体怎么做的 |
| result / risk_level | success / high | 结果与风险定级 |
| approval | {"approved_by": "admin1"} | 谁批准的 |
| ip / user_agent | 10.0.0.1 / Mozilla/5.0 | 从哪发起 |
| prev_hash / hash | sha256… | 是否被篡改 |

审计原则：

- **完整性**：关键操作成败都记，越权尝试也记。
- **不可篡改**：只插不改（无更新接口），哈希链或 WORM 存储兜底。
- **可追溯**：trace_id 串起一次执行的全部工具调用（见 3.4）。
- **可查询**：支持按用户、时间、操作、租户检索。
- **保留期**：按合规要求保留，行业惯例 1–7 年。

**面试高频问法**：“Agent 要执行删除数据库这类高风险操作，审批和审计链路怎么设计？日志里的 PII 怎么处理？”共识口径：事前——高风险工具默认不进白名单，进白名单必须挂审批门，审批请求带参数快照、超时升级且超时视为拒绝；事中——执行前后双写审计事件，参数与审批人一并入链；事后——审计日志只插不改、哈希链防篡改，PII 落日志前统一脱敏、敏感字段加密存储。实现见 6.3。

### 4.8 内容安全

| 防线 | 位置 | 检查项 | 拦下后 |
|---|---|---|---|
| 输入过滤 | 进入 Agent 前 | 注入模式（“忽略之前指令”等）、禁入话题 | 拒绝请求，返回 400 |
| 输出过滤 | 返回用户前 | 敏感词、内容审核（Moderation）API、PII 外泄 | 兜底话术替换 |
| 工具防线 | 每次工具调用 | 白名单、角色、参数阈值 | 拒绝执行 + 审计（见 4.9） |
| 生成内容标识 | 输出侧 | 按监管要求标注 AI 生成 | 附加标识 |

要点：过滤是**概率性的**（正则和审核模型都有漏报），所以它必须与权限硬门禁叠加——注入话术绕过了过滤器，也不应导致越权，因为授权判定根本不看内容，只看身份与策略。实现见 6.5。

### 4.9 工具风险分级与人工审批

| 风险级 | 判定 | 示例工具 | 门禁 | 审计 |
|---|---|---|---|---|
| 低 | 只读、影响面小 | search_orders、get_order_detail | 白名单直接放行 | 常规记录 |
| 中 | 写操作、影响可控 | create_order | 限参（数量上限）+ 配额 | 记录参数 |
| 高 | 涉及资金、删除 | initiate_refund | 人工审批 + 金额阈值 | 双写：请求 + 批准人 |
| 极高 | 不可逆、影响面大 | delete_account、批量删除 | 双人审批，或默认禁止自动化 | 记录 + 实时告警 |

审批设计三要点：

- 审批请求带**参数快照**，批准的是这份参数，不是“随便执行”。
- **超时升级、超时视为拒绝**，不能挂起无限等。
- 每次决策（批准/拒绝/超时）都留痕入审计；运行时中断复用 2.5 的 WAITING_HUMAN 状态与检查点恢复。

### 4.10 供应链安全

| 风险点 | 说明 | 缓解 |
|---|---|---|
| 模型来源 | 不可信渠道的模型权重可能带后门 | 只用可信厂商与官方渠道，记录模型版本 |
| 插件/MCP Server | 恶意工具描述可诱导模型调用、外传数据 | 审核 + 白名单 + 最小数据暴露 |
| 依赖包 | 依赖投毒 | pip-audit 等定期扫描，锁定版本 |
| API Key | 硬编码泄露 | 密钥管理服务 + 定期轮转 |
| 第三方 API | 数据出境与合规 | 合规审查 + 数据分级出口管控 |

密钥管理三档：不硬编码是底线；环境变量是及格；密钥管理服务（如 Vault、云厂商 Secrets Manager）+ 定期轮转是生产标准。截至 2026 年，MCP（Model Context Protocol）已成为工具接入的主流协议之一，第三方 MCP Server 的审核与白名单是供应链防线的新增重点。扫描命令见 6.6。

### 4.11 安全开发流程

```text
1. 威胁建模：识别资产、威胁、脆弱性
2. 安全设计：认证、授权、隔离、加密
3. 安全编码：输入校验、输出过滤、参数化查询
4. 安全测试：SAST、DAST、红队
5. 安全部署：密钥管理、最小权限、网络隔离
6. 安全监控：审计、告警、异常检测
7. 应急响应：预案、演练、复盘
```

## 5. 架构 / 流程

防御纵深（Defense in Depth）：五段防线层层过滤，任何一层失守都还有下一层。

```text
┌──────────────────────────────────────────┐
│  用户请求                                 │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  接入层                                   │
│  ├─ 认证（JWT/OAuth）                    │
│  ├─ 限流                                 │
│  ├─ 输入过滤（注入检测）                 │
```

一次工具调用要过的五道门（任一环节失败即拒绝并写审计）：

```text
LLM 决策调用 tool(args)
   → ① 白名单：工具是否登记？
   → ② 角色：用户角色是否允许该工具？
   → ③ 作用域：参数里的资源是否在本租户/本人范围内？
   → ④ 风险：风险级与阈值是否触发人工审批？
   → ⑤ 审计：无论成败，写一条完整审计事件
   → 全部通过 → 执行；任一失败 → 拒绝 + 告警
```

### 6.1 认证与授权中间件（权限中间件）

```python
import jwt
from datetime import datetime, timedelta, timezone
from fastapi import FastAPI, Request, HTTPException

app = FastAPI()
SECRET = "change-me"  # 生产环境放密钥管理服务（见 4.10），不要硬编码

# ---------- 认证：JWT 签发与校验 ----------
def create_token(user_id: str, roles: list, tenant_id: str) -> str:
    payload = {
        "sub": user_id,
        "roles": roles,               # 角色基线：权限的静态部分
        "tenant_id": tenant_id,       # 作用域：数据隔离的依据
        "iat": datetime.now(timezone.utc),
        "exp": datetime.now(timezone.utc) + timedelta(hours=1),  # 时效：1 小时过期
    }
    return jwt.encode(payload, SECRET, algorithm="HS256")

def verify_token(token: str) -> dict:
    try:
        return jwt.decode(token, SECRET, algorithms=["HS256"])
    except jwt.ExpiredSignatureError:
        raise HTTPException(401, "Token 已过期")
    except jwt.InvalidTokenError:
        raise HTTPException(401, "Token 无效")

# ---------- 授权：RBAC 管工具级，ABAC 管数据级，叠加判定 ----------
ROLE_PERMISSIONS = {
    "user":  {"run_agent", "search_orders", "create_order"},
    "admin": {"run_agent", "search_orders", "create_order", "initiate_refund"},
}

def check_rbac(user: dict, action: str) -> bool:
    allowed = set().union(*(ROLE_PERMISSIONS.get(r, set()) for r in user["roles"]))
    return action in allowed

def check_abac(user: dict, resource: dict) -> bool:
    if resource.get("tenant_id") != user["tenant_id"]:
        return False  # 跨租户一律拒绝
    return resource.get("user_id") == user["user_id"] or "admin" in user["roles"]

# ---------- 权限中间件：认证 → 授权 → 脱敏 → 审计一条链 ----------
class SecurityMiddleware:
    def __init__(self, masker, auditor):
        self.masker = masker    # PII 脱敏器（见 4.6）
        self.auditor = auditor  # 审计器（见 6.3）

    async def authenticate(self, request: Request) -> dict:
        token = request.headers.get("Authorization", "").removeprefix("Bearer ")
        payload = verify_token(token)
        return {"user_id": payload["sub"], "roles": payload["roles"],
                "tenant_id": payload["tenant_id"]}

middleware = SecurityMiddleware(masker=PIIMasker(), auditor=AuditLogger(db))

@app.post("/v1/agent/run")
async def run_agent(request: Request, body: AgentRunRequest):
    user = await middleware.authenticate(request)   # 1. 认证：身份只信 token
    if not check_rbac(user, "run_agent"):           # 2. 工具级授权
        await middleware.auditor.log({"user_id": user["user_id"],
                                      "action": "run_agent", "result": "denied"})
        raise HTTPException(403, "无权限")
    safe_input = middleware.masker.mask(body.input)  # 3. 输入脱敏
    result = await agent.run(safe_input, user=user)  # 4. 执行：内部再过 6.2 工具守卫
    await middleware.auditor.log({                   # 5. 审计：成败都记
        "user_id": user["user_id"], "tenant_id": user["tenant_id"],
        "action": "run_agent", "input": safe_input, "result": "success",
    })
    return result
```

### 6.2 工具权限守卫与人工审批

```python
TOOL_POLICIES = {
    # 风险分级：低风险放行 / 高风险审批 / 极高风险默认禁止自动化
    "search_orders":    {"roles": ["user", "admin"], "risk": "low"},
    "get_order_detail": {"roles": ["user", "admin"], "risk": "low"},
    "initiate_refund":  {"roles": ["admin"], "risk": "high",
                         "threshold": {"amount": 500}},  # 超过 500 元必须审批
    "delete_account":   {"roles": ["admin"], "risk": "critical",
                         "requires_approval": True},
}

class ToolGuard:
    """工具守卫：白名单 → 角色 → 参数阈值 → 审批，任何一步失败即拒绝。"""
    def __init__(self, policies: dict, approval_service):
        self.policies = policies
        self.approval = approval_service

    async def execute(self, user: dict, tool: str, args: dict) -> dict:
        policy = self.policies.get(tool)
        if policy is None:  # 1. 白名单：没登记的工具一律拒绝
            raise PermissionError(f"工具未登记: {tool}")
        if not set(user["roles"]) & set(policy["roles"]):  # 2. 角色检查
            raise PermissionError(f"无权限调用 {tool}")

        needs = policy["risk"] in ("high", "critical")    # 3. 阈值 + 审批
        for key, limit in policy.get("threshold", {}).items():
            if args.get(key, 0) > limit:
                needs = True
        if needs:
            decision = await self.approval.request(
                user=user, tool=tool, args=args,
                reason=f"高风险操作: {tool}",
            )
            if not decision["approved"]:
                raise ApprovalDenied(decision["reason"])

        return await execute_tool(tool, args)  # 4. 审批通过才真正执行
```

### 6.3 审计日志（哈希链防篡改）

```python
import hashlib
import json

class AuditLogger:
    """审计日志：只插不改 + 哈希链防篡改。
    每条事件的 hash 覆盖自身内容与前一条的 hash，改任何一条都会断链。"""
    def __init__(self, db):
        self.db = db
        self.prev_hash = "GENESIS"

    async def log(self, event: dict) -> None:
        event = {**event, "timestamp": now_iso()}
        event["prev_hash"] = self.prev_hash
        event["hash"] = self._hash(event)
        await self.db.insert("audit_logs", event)  # 只允许插入，无更新接口
        self.prev_hash = event["hash"]

    async def query(self, user_id: str = None, action: str = None) -> list:
        filters = {k: v for k, v in
                   {"user_id": user_id, "action": action}.items() if v}
        return await self.db.find("audit_logs", filters)

    async def verify_integrity(self) -> bool:
        prev = "GENESIS"
        for log in await self.db.find("audit_logs", {}):
            stored = log.pop("hash")
            if log["prev_hash"] != prev or self._hash(log) != stored:
                return False  # 链断了 = 有篡改
            prev = stored
        return True

    def _hash(self, event: dict) -> str:
        content = json.dumps({k: v for k, v in event.items() if k != "hash"},
                             sort_keys=True, ensure_ascii=False)
        return hashlib.sha256(content.encode()).hexdigest()
```

### 6.4 数据隔离检索

```python
class SecureRetriever:
    """检索强制过滤：租户与权限条件在查询层注入，取回后二次校验。"""
    def __init__(self, vector_store):
        self.vector_store = vector_store

    async def retrieve(self, query: str, user: dict, top_k: int = 5) -> list:
        # 1. 查询层强制注入过滤条件，模型与 Agent 都无法绕过
        results = await self.vector_store.query(
            query_texts=[query],
            n_results=top_k * 3,  # 多取一些，过滤后可能不足
            where={"$and": [
                {"tenant_id": user["tenant_id"]},
                {"permission": {"$in": user["roles"]}},
            ]},
        )
        # 2. 二次校验：不信任过滤结果，逐条再核一次元数据
        kept = []
        for doc, meta in zip(results["documents"][0], results["metadatas"][0]):
            if meta.get("tenant_id") == user["tenant_id"] and \
               set(meta.get("permission", [])) & set(user["roles"]):
                kept.append(doc)
        return kept[:top_k]
```

### 6.5 内容安全（输入/输出双过滤器）

```python
class ContentModerator:
    """内容安全：敏感词 → 审核模型 → PII 外泄，三道检查。"""
    def __init__(self, moderation_api=None, pii_masker=None):
        self.moderation_api = moderation_api
        self.pii_masker = pii_masker

    async def check(self, text: str, is_output: bool = False) -> tuple:
        if self._has_sensitive_words(text):  # 1. 敏感词
            return False, "含敏感词"
        if self.moderation_api:              # 2. 内容审核 API
            result = await self.moderation_api.check(text)
            if result["flagged"]:
                return False, f"内容审核不通过: {result['categories']}"
        if is_output and self.pii_masker.detect(text):  # 3. 输出侧拦 PII 外泄
            return False, "输出含 PII"
        return True, ""

    def _has_sensitive_words(self, text: str) -> bool:
        return any(w in text for w in load_sensitive_words())

moderator = ContentModerator(moderation_api, PIIMasker())

@app.post("/v1/agent/run")
async def run_agent(body: AgentRunRequest):
    ok, reason = await moderator.check(body.input)  # 输入审核
    if not ok:
        raise HTTPException(400, reason)
    result = await agent.run(body.input)
    ok, _ = await moderator.check(result["answer"], is_output=True)  # 输出审核
    if not ok:
        result["answer"] = "抱歉，我无法回答这个问题。"  # 兜底话术
    return result
```

## 7. 案例

### 案例 A：越权访问拦截（某电商客服 Agent）

**攻击**：普通用户在对话里构造话术，诱导 Agent 调用 `delete_account`。

**防护链路**：

1. JWT 认证，身份从 token 解出，构造的“我是管理员”无效。
2. RBAC 检查：`delete_account` 只允许 `admin` 角色。
3. 检查失败返回 403，同时写入审计事件并触发告警。

**示意数字**：上线首月拦截普通会话中的管理类工具调用 47 次（多数是好奇心探测，3 次疑似批量探测），成功越权 0 次；越权告警平均 15 分钟内有人响应。

### 案例 B：多租户数据泄露修复（某企业知识库 SaaS）

**问题**：灰度期 A 公司用户反馈“搜到了别家公司的文档”。

**排查**：审计日志定位到一条检索路径未带 `tenant_id` 过滤，代码审查确认 `where` 条件在某个新加的检索分支上漏拼，跨租户命中约 0.4%。

**修复**：

1. 检索层由中间件统一注入租户过滤，禁止业务代码自行拼接。
2. 补 200 条跨租户不可见的单元测试，进 CI。
3. PostgreSQL 行级安全作为兜底。

**示意数字**：修复后 3 万次跨租户回归检索 0 条返回；上线后 RLS 又兜底拦下 2 次应用层遗漏。

### 案例 C：PII 泄露合规整改（某金融科技公司客服 Agent）

**问题**：日志抽检发现约 12% 的条目含手机号、身份证号，违反个保法最小必要原则。

**整改**：

1. 全链路日志出口统一走脱敏器（4.6 的 PIIMasker）。
2. 审计库中确需保留的 PII 字段加密存储。
3. 建立 PII 数据地图，每周自动扫描泄露。
4. 上线用户数据导出与删除入口，支撑被遗忘权。

**示意数字**：三个月后抽检 PII 命中率从 12% 降到 0；用户导出/删除请求平均 3 天闭环，年度合规审计通过。

## 8. 常见坑

1. **身份由用户声称**。  
   “我是管理员”不能信，身份字段只从认证系统签发的 token 解出。

2. **只在前端做权限**。  
   前端可绕过，后端每个入口必须重新校验。

3. **工具权限不检查**。  
   模型说要调就调，等于把越权决定权交给模型；必须过工具守卫（6.2）。

4. **数据隔离只靠应用层**。  
   应用层漏拼一个过滤就泄露；数据库行级安全兜底。

5. **日志含 PII**。  
   合规风险；落日志前统一脱敏，审计库敏感字段加密。

6. **审计日志可篡改**。  
   合规不通过；只插不改 + 哈希链或 WORM 存储。

7. **密钥硬编码**。  
   仓库一旦泄露密钥即泄露；用密钥管理服务并定期轮转。

8. **供应链不设防**。  
   第三方模型、插件、依赖包都可能带后门；pip-audit/trivy 定期扫描 + SBOM + 版本锁定。

9. **MCP Server 不审核**。  
   恶意 MCP 可借工具描述诱导模型外传数据；白名单 + 审核 + 最小数据暴露。

10. **不做内容安全**。  
    输出有害内容是品牌与监管双重风险；输入输出双过滤器 + 兜底话术。

11. **高风险操作无人工审批**。  
    资金、删除类操作必须挂审批门，超时视为拒绝。

12. **不做红队测试**。  
    不知道安全边界在哪；定期红队，系统化方法见 4.8。

13. **合规要求不清楚**。  
    GDPR、个保法、行业法规必须设计前对齐，EU AI Act 类分级义务要提前评估。

14. **不做数据地图**。  
    不知道 PII 在哪就无从保护；先盘家底再谈治理。

15. **子 Agent 全量继承父权限**。  
    一次注入被放大成全局越权；子 Agent 只继承子任务所需的最小子集。

16. **安全是事后补的**。  
    事后补的成本是设计期的十倍量级；从威胁建模开始前置。

## 9. 练习

1. 实现 JWT 认证 + RBAC 授权（参考 6.1）。验收：伪造 roles 的请求被 403，过期 token 被 401。
2. 实现 ABAC：用户只能访问自己的订单。验收：构造 20 组跨用户请求全部拒绝。
3. 实现多租户数据隔离：向量库过滤 + 数据库行级安全。验收：跨租户检索 0 条，RLS 能拦住应用层遗漏。
4. 实现 PII 脱敏器：手机号、身份证、邮箱、银行卡。验收：100 条样本 0 漏报。
5. 实现审计日志：记录、查询、哈希链防篡改（参考 6.3）。验收：篡改任意一条能被 `verify_integrity` 检出。
6. 实现工具权限检查：角色 + 风险分级 + 阈值审批（参考 6.2）。验收：超 500 元退款必须审批才能执行。
7. 实现内容安全过滤：输入拦注入、输出拦有害与 PII。验收：20 条注入样本的拦截率有量化数字。
8. 实现人工审批流：请求、通知、审批、恢复全链路，复用 2.5 的 WAITING_HUMAN 中断。
9. 配置供应链扫描：pip-audit + trivy + gitleaks 进 CI。验收：HIGH 以上漏洞阻断构建。
10. 设计一个红队测试方案，覆盖注入、越权、泄露、成本攻击、滥用五类攻击，输出报告与修复清单。

## 10. 小结

- 安全体系五层：**身份、数据、应用、审计、供应链**，层层设防、层层兜底。
- 认证：身份不可声称；**JWT、OAuth、SSO、mTLS**；Agent 代表用户要携带代理身份。
- 授权：**RBAC 定工具级、ABAC 定数据级**，ReBAC/PBAC 处理复杂关系与动态策略。
- 最小权限三机制：**角色基线 + 作用域收窄 + 时效衰减**；默认拒绝，子 Agent 只继承最小子集。
- 可审计：能回答**谁在何时让 Agent 以什么权限对什么做了什么、谁批准的**；字段模型落地，哈希链防篡改。
- 数据隔离：**多租户、行级、文档级**；服务端注入过滤，数据库 RLS 兜底。
- PII：**分级、脱敏、加密、合规**；GDPR、个保法、EU AI Act、生成式 AI 管理办法口径提前对齐。
- 内容安全：**输入拦注入、输出拦有害与 PII 外泄**；过滤是概率性的，不能替代权限硬门禁。
- 工具安全：**白名单、角色、风险分级审批、沙箱**；审批带参数快照，超时视为拒绝。
- 供应链：**模型来源、插件与 MCP 审核、依赖扫描、SBOM、密钥管理**。
- 这些能力直接支撑：3.9 CI/CD、版本管理与发布、4.3 数据分析 Agent、4.8 评估与红队。
