## 1. 定位

## 2. 一句话定义

Embedding（嵌入）是把一段文本映射成固定长度实数向量的技术：**语义越接近的文本，向量在空间中的位置越接近**，于是「判断两段话像不像」从语言问题变成了几何问题——算两个向量的距离。

向量数据库（Vector Database）则负责存这批向量，并用近似最近邻索引（ANN，Approximate Nearest Neighbor）在亿级向量中毫秒级找出「离查询最近的 K 个邻居」。两者合起来就是现代语义检索、RAG、推荐与 Agent 记忆的地基。

## 3. 为什么需要

传统关键词搜索有三个绕不开的硬伤：

1. **同义改写搜不到**。用户问「怎么把钱要回来」，文档标题是《退换货说明》——零关键词重合，BM25 这类基于词频的方法直接失手。
2. **跨表达粒度搜不到**。「东西坏了想退」与《售后政策》没有任何字面交集，但意思高度相关。
3. **不懂上下文**。「苹果」在手机评测里是公司，在菜谱里是水果，关键词匹配不分。

向量检索的价值对照：

| 维度 | 关键词检索（BM25） | 向量检索（Embedding） |
|---|---|---|
| 匹配依据 | 字面词项重合 | 语义距离 |
| 同义改写 | 搜不到 | 天然命中 |
| 专有名词/编号/代码 | 强项 | 弱项（需要混合检索兜底） |
| 跨语言 | 差 | 多语言模型可行 |
| 可解释性 | 高（命中词可见） | 低（距离是黑盒分数） |
| 索引成本 | 低 | 需要嵌入模型 + 向量索引 |

结论：**向量检索解决「按意思搜」，关键词检索解决「按字搜」，生产系统两者都要**——这是 4.6 混合检索的伏笔，1.4c 落地。

Embedding 的应用面远不止搜索：RAG 检索（1.4）、相似内容推荐、用户/商品聚类去重、异常检测、Agent 长期记忆（2.4）、多模态检索（图文同空间）。它是应用工程师使用频率最高的一块积木。

## 4. 核心原理

### 4.1 从 one-hot 到稠密语义向量

最早表示词的方法是 one-hot：词表里有 10 万个词，「退款」就是一个 10 万维、只有一维是 1 的向量。问题致命——任意两个词的 one-hot 向量都正交，距离完全相同，「退款」和「退货」没有任何关系可计算。

Word2Vec / GloVe 引入稠密词向量：用 300 维左右的小数向量表示一个词，通过「上下文相似词的向量也相似」训练出来，于是出现「国王 - 男人 + 女人 ≈ 女王」这类线性关系。但词向量解决不了句子级问题：一句 30 个词的话，直接平均词向量会稀释语义、丢掉词序。

现代 Sentence Embedding（句子嵌入）的通行做法：

1. 把整句话喂给一个 Encoder（多为 BERT 系双向编码器，对应 1.1 讲的 Encoder-only 家族）；
2. 对每个 token 的输出向量做池化（Pooling）——取 [CLS] 位向量或全 token 平均（mean pooling）；
3. 得到一个固定维度的句向量（如 384/768/1024 维）。

训练目标是对比学习（Contrastive Learning）：**正样本对（改写、问答对）拉近，负样本对推远**。这样训练出的空间里，语义距离就是坐标距离——「语义地图」的比喻由此而来：意思相近的话落在相邻街区。

### 4.2 相似度度量：余弦、点积、欧氏

三个候选度量：

| 度量 | 定义 | 值域 | 特点 | 典型场景 |
|---|---|---|---|---|
| 余弦相似度（Cosine） | 两向量夹角的余弦：dot(u,v)/(|u||v|) | [-1, 1] | 只看方向不管长度，抗「长短句」差异 | 语义检索的默认选择 |
| 点积（Dot Product） | 对应位相乘求和 | 不定 | 计算最快；向量未归一化时偏好长向量 | 推荐召回、注意力打分（0.4c） |
| 欧氏距离（L2） | 两点直线距离 | [0, +∞) | 对绝对位置敏感 | 聚类、可视化 |

关键工程事实：**向量做 L2 归一化（单位长度）后，点积 = 余弦相似度，且与欧氏距离单调等价**（欧氏距离越小 = 余弦越大）。所以主流向量库统一用「内积 + 归一化」实现余弦检索——点积计算最快，归一化消除了长度偏置，一举两得。

余弦相似度的经验读数（因模型而异，仅供校准直觉）：

| 相似度区间 | 语义关系 |
|---|---|
| 0.85 以上 | 高度相关，基本是同一话题的不同表述 |
| 0.70 ~ 0.85 | 相关，可进入候选 |
| 0.50 ~ 0.70 | 弱相关，通常要靠 Rerank 二次判断 |
| 0.50 以下 | 基本无关 |

阈值不是通用常数：不同模型的分数分布不同，必须用自己的数据画分布图再定，切忌照抄别人的 0.8。

### 4.3 嵌入模型与维度

选模型的四个轴：

1. **语言**：中文场景选中文/多语言模型（BGE、GTE、M3E、multilingual-e5），用英文模型处理中文召回会明显掉。
2. **维度**：常见 384（MiniLM 级）、768（BERT-base 级）、1024（BGE-large/M3 级），商用 API 有 1536/3072 等。维度越高表达力越强，但存储和计算线性变贵。
3. **领域**：通用模型在垂直领域（医疗、法律、客服工单）可能不够，可用领域语料微调或换领域模型。
4. **指令前缀**：部分模型（如 BGE、e5）要求查询侧加固定前缀（如「为这个句子生成表示以检索相关文章：」），漏掉会掉点——用模型卡上写的用法。

维度与代价的量级关系：

| 维度 | 存储量（100 万条，float32） | 精度趋势 | 适合 |
|---|---|---|---|
| 384 | 约 1.5 GB | 下限够用 | 端侧、原型、成本敏感 |
| 768 | 约 3 GB | 均衡 | 中小规模生产 |
| 1024 | 约 4 GB | 更高 | 主流生产默认 |
| 1536+ | 6 GB 起 | 更高，边际收益递减 | 商用 API、多模态 |

降维与压缩是大规模标配：主成分分析（PCA）截断、标量量化（SQ8，float32 转 int8，内存降到 1/4）、乘积量化（PQ，可压到 1/16~1/32，精度有损）。这些与 4.4 的索引一起构成「召回-延迟-内存」三角。

### 4.4 ANN 索引：HNSW 与 IVF 的三角权衡

向量库里如果有 N 条向量，查询时要找 Top-K 最近邻，暴力扫描（Flat 索引）要做 N 次距离计算——100 万条在毫秒到几十毫秒之间尚可，千万级以上延迟和成本都不可接受。近似最近邻（ANN）的思路：**牺牲少量召回率（比如 95%→99%），换取几个数量级的速度**。

两大主流索引：

**HNSW（Hierarchical Navigable Small World，分层可导航小世界图）**

- 把所有向量组织成一张多层图：顶层稀疏、只有少数「高速公路」节点，负责大步远跳；底层稠密包含全部节点，负责精找。
- 查询从顶层入口出发贪心跳跃：先在粗层跳到目标大致区域，逐层下沉细化，几十到几百次比较即锁定近邻。
- 关键参数：M（每节点连边数，常见 16~32，越大越准越费内存）、efConstruction（建图候选队列，200+ 常见）、efSearch（查询候选队列，越大召回越高延迟越高）。
- 优点：查询快、召回率高（轻松 95%+）；缺点：内存占用大（存图边）、建图慢、删除不便。

**IVF（Inverted File，倒排文件/聚类分桶）**

- 建索引时用 k-means 把向量聚成 nlist 个桶；查询时先算查询向量离哪些桶心最近，只搜最近的 nprobe 个桶。
- 关键参数：nlist（桶数，经验值为簇数约 sqrt(N) 量级）、nprobe（搜几个桶，越大越准越慢）。
- 常与 PQ 量化组合成 IVF-PQ：桶内向量再压缩存储，内存降到十分之一以下——超大规模（亿级）、内存受限场景的主力。
- 优点：内存省、可扩展；缺点：精度略低，桶边界附近的邻居可能漏掉。

三角权衡总结：

| 维度 | HNSW | IVF-Flat | IVF-PQ |
|---|---|---|---|
| 查询延迟 | 极低（毫秒级） | 低 | 中（多了量化解码） |
| 召回率 | 高 | 高（nprobe 足够时） | 有损 |
| 内存 | 大（向量+图边） | 中 | 极小（1/10 以下） |
| 建索引速度 | 慢 | 快 | 快 |
| 适用规模 | 百万~千万 | 千万 | 亿级/内存受限 |
| 一句话定位 | 内存充足时的默认选择 | 平衡款 | 省内存的规模化方案 |

面试口径：**HNSW 是「分层图跳跃」，IVF 是「聚类分桶」；HNSW 用内存换速度与召回，IVF（尤其 IVF-PQ）用精度换内存与扩展性。选哪个取决于规模、内存预算和延迟要求，没有万能答案。**

### 4.5 向量库选型：FAISS / Chroma / Qdrant / Milvus / pgvector

先分清两个概念：**向量索引（算法库）** 与 **向量数据库（工程产品）**。FAISS 是 Meta 开源的索引算法库——快、成熟，但不管理数据持久化、过滤、分布式，需要自己包一层；Qdrant/Milvus 等是在索引之上补齐存储、过滤、副本、监控的完整数据库。

| 库 | 形态 | 索引支持 | 元数据过滤 | 分布式 | 适合 |
|---|---|---|---|---|---|
| FAISS | 算法库 | Flat/HNSW/IVF/PQ 全家桶 | 无（自己做） | 无 | 研究、离线批处理、嵌入服务内部件 |
| Chroma | 轻量库/服务 | HNSW（内置默认） | 有 | 无 | 原型、Demo、小规模生产 |
| Qdrant | 独立数据库 | HNSW/量化 | 强（Payload 过滤） | 有 | 中型生产、过滤需求重的检索 |
| Milvus | 分布式数据库 | HNSW/IVF/DiskANN 等 | 强（分区+标量过滤） | 强 | 亿级向量、多租户、重运维 |
| pgvector | Postgres 扩展 | HNSW/IVFFlat | 有（SQL 全能力） | 随 PG | 已有 PG 栈、数据量中等、想一套库管所有 |

选型三问：

1. **数据量级**：十万以内 Chroma/pgvector 足够；千万级上 Qdrant/Milvus + HNSW；亿级看 Milvus 分布式或 IVF-PQ。
2. **要不要带过滤的检索**：生产检索几乎必然是「向量相似 + 元数据过滤」（部门、时间、权限），过滤能力和过滤语义（预过滤还是后过滤）直接决定选型——权限管控（1.4 案例 C）靠的就是这个。
3. **团队栈与运维预算**：已有 Postgres 且量不大，pgvector 的运维成本最低；云上托管版省人力但加费用；FAISS 自研包一层只有在特殊性能要求下才值得。

### 4.6 混合检索：概念铺垫

纯向量检索的两个已知短板：专有名词、订单号、产品编号、代码标识符这类「精确符号」语义向量反而不敏感；且领域外术语可能落在奇怪的位置。而关键词检索（BM25）恰好是精确匹配的强项。

混合检索（Hybrid Search）就是把两路召回合并：

```text
查询 ─┬─ BM25 关键词检索 ──→ Top-20（按字面）
      └─ 向量语义检索   ──→ Top-20（按意思）
              ↓ 两路结果合并去重
        RRF（Reciprocal Rank Fusion）按排名融合
              ↓
        Rerank 交叉编码器精排
              ↓
            Top-5 交给 LLM
```

RRF 的直觉：不看原始分数（两路分数量纲不同没法直接加），只看每路里的排名，排名越靠前贡献越大（贡献约 1/(排名+60)）。实现简单、效果稳，是工程默认选择。

本节只建立概念——切分、BM25、Rerank、评估的完整实操在 1.4b/1.4c 展开。

## 5. 架构 / 流程

完整的向量检索系统分离线与在线两条链路：

```text
┌────────────────────────────────────────────┐
│ 离线索引（一次构建，增量更新）               │
│                                            │
│ 文档 ─→ 清洗 ─→ 切分 chunk ─→ 嵌入模型      │
│                                 │          │
│                                 ↓          │
│                     向量 + 原文 + 元数据     │
│                    （来源/权限/时间/页码）    │
│                                 │          │
│                                 ↓          │
│                     向量库（HNSW/IVF 索引）  │
└────────────────────────────────────────────┘
                  ↓
┌────────────────────────────────────────────┐
│ 在线检索（每次查询，毫秒级）                 │
│                                            │
│ 用户查询 ─→ （查询重写，可选）               │
│         ─→ 同一嵌入模型 ─→ 查询向量          │
│         ─→ ANN 检索 Top-K                   │
│         ─→ 元数据预过滤（权限/时间/部门）     │
│         ─→ （Rerank 精排，可选）             │
│         ─→ Top-N 结果 + 相似度分数           │
└────────────────────────────────────────────┘
```

HNSW 查询的跳跃过程：

```text
第 2 层（稀疏，远跳）:   入口 A ────跳───→ B   （锁定大致区域）
                              │
第 1 层（中等密度）:           └─→ C ─→ D        （逼近邻域）
                                       │
第 0 层（全量，精找）:                  └─→ E ─→ F = Top-1
每次跳跃只比较当前节点的邻居，贪心走向离查询更近的节点；
比较次数几十~几百，替代百万级暴力扫描。
```

工程流程清单：

1. 离线：切分 → 嵌入（批量）→ 建索引（HNSW/IVF）→ 存元数据。
2. 在线：嵌入查询 → 过滤 → ANN → （Rerank）→ 返回。
3. 更新：新文档走增量 upsert；全量换模型必须重建索引——不同模型的向量不在同一个空间。

## 6. 代码 / 工具

### 6.1 sentence-transformers 嵌入 + 余弦相似度

```python
from sentence_transformers import SentenceTransformer
import numpy as np

# 1. 加载中文嵌入模型（首次运行会自动下载权重）
model = SentenceTransformer("BAAI/bge-small-zh-v1.5")

docs = [
    "退换货说明：签收后 7 天内可退，15 天内可换。",
    "退款时效：审核通过后 3-5 个工作日原路到账。",
    "会员积分规则：每消费 1 元累计 1 积分。",
    "新品上市：秋季新品奶茶系列本周五发售。",
]

# 2. 批量编码；normalize=True 做 L2 归一化，之后点积即余弦相似度
doc_emb = model.encode(docs, normalize_embeddings=True)
print("向量维度:", doc_emb.shape[1])   # 512 维

# 3. 查询编码与相似度计算
query = "怎么把钱要回来？"
q_emb = model.encode([query], normalize_embeddings=True)

# 点积 = 余弦（因为已归一化）
scores = doc_emb @ q_emb.T            # (4, 1)
for doc, s in sorted(zip(docs, scores.flatten()), key=lambda x: -x[1]):
    print(f"{s:.4f}  {doc}")

# 典型输出（量级示意）：
# 0.83  退款时效：审核通过后 3-5 个工作日原路到账。
# 0.76  退换货说明：签收后 7 天内可退，15 天内可换。
# 0.35  会员积分规则：每消费 1 元累计 1 积分。
# 0.31  新品上市：秋季新品奶茶系列本周五发售。
```

注意「怎么把钱要回来」与「退款时效」零字面重合却排第一——这就是语义坐标的价值。

### 6.2 FAISS 最小索引：精确检索与 IVF 近似检索

```python
import faiss
import numpy as np
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-small-zh-v1.5")
docs = [
    "退换货说明：签收后 7 天内可退。",
    "退款时效：3-5 个工作日到账。",
    "会员积分规则：每消费 1 元累计 1 积分。",
]
emb = model.encode(docs, normalize_embeddings=True).astype("float32")
d = emb.shape[1]

# ---- 方案 A：IndexFlatIP 精确检索（小规模直接用） ----
index_flat = faiss.IndexFlatIP(d)          # 内积度量
index_flat.add(emb)                        # 也可以直接传文档，见 6.1 的 Chroma 风格
q = model.encode(["怎么把钱要回来"], normalize_embeddings=True).astype("float32")
scores, ids = index_flat.search(q, k=2)    # Top-2
print("Flat:", list(zip(ids[0], scores[0])))

# ---- 方案 B：IndexIVFFlat 近似检索（大规模适用） ----
nlist = 8                                  # 聚成 8 个桶（真实场景约取 sqrt(N)）
quantizer = faiss.IndexFlatIP(d)           # 用内积做桶心分配
index_ivf = faiss.IndexIVFFlat(quantizer, d, nlist, faiss.METRIC_INNER_PRODUCT)

index_ivf.train(emb)                       # k-means 训练桶心（必须先 train 再 add）
index_ivf.add(emb)
index_ivf.nprobe = 3                       # 查询时只搜最近的 3 个桶：精度换速度的旋钮

scores, ids = index_ivf.search(q, k=2)
print("IVF :", list(zip(ids[0], scores[0])))
```

生产要点：emb 必须 `float32`；IVF 必须先 `train` 再 `add`；nprobe 从小往大调，用 Recall@K 对着 Flat 结果压测校准。HNSW 版本一行可换：`faiss.IndexHNSWFlat(d, 32, faiss.METRIC_INNER_PRODUCT)`，参数 M=32。

### 6.3 五个库的接入姿势速查

```text
FAISS   ：faiss.IndexFlatIP / IndexHNSWFlat / IndexIVFFlat —— 纯算法，自己管持久化
Chroma  ：chroma_client.get_or_create_collection("kb") → collection.add / query
Qdrant  ：client.upsert("kb", points=[...]) → client.search("kb", query_vector, query_filter)
Milvus  ：建 Collection（含 HNSW/IVF 索引参数）→ insert → search，支持分区级过滤
pgvector：CREATE EXTENSION vector → 列类型 vector(1024) → ORDER BY embedding <=> $1 LIMIT 5
```

原型期用 Chroma（一行建库），生产按 4.5 节三问选 Qdrant/Milvus/pgvector。

## 7. 案例

### 案例 A：电商客服搜索从关键词到向量

**场景**：某电商平台客服知识库约 8000 篇文档，用户搜索命中率长期在 60% 左右，投诉集中在「搜不到」：问「东西坏了想退」搜不到《售后政策》。

**改造**：

1. 文档按标题递归切分成 512 token 的块；
2. BGE 中文模型批量嵌入，Chroma 入库（原型）→ 迁 Qdrant（带权限过滤）；
3. 保留原 BM25 通道做双路召回，RRF 融合；
4. 用 500 条真实用户查询做抽样评测，定余弦阈值与 K 值。

**效果**：抽样命中率从 60% 提升到 88%；「同义改写类查询」（占比约四成）从几乎全失手到基本命中；未解决的 bad case 集中在订单号精确查询——那本来就是 BM25 的领地，双路正好互补。

### 案例 B：5000 万向量库的索引迁移

**场景**：某金融科技公司知识库扩到 5000 万段文档，检索 P99 延迟 200ms，目标 50ms 以内，同时内存预算不能翻倍。

**方案**：从单机 HNSW 迁到 Milvus 分布式 + 按部门分区（partition）；权限过滤改为分区级预过滤，先缩小候选集再搜索；HNSW 的 efSearch 用 Recall@10 曲线校准，从默认值降到召回与延迟的平衡点；内存吃紧的冷数据分区换 IVF-PQ，存储压到约 1/10。

**效果**：P99 从 200ms 降到 40ms 左右，Recall@10 从 98% 微降到 96%（业务可接受），内存控制在原预算内。复盘结论：**降延迟的第一杠杆不是换硬件，是预过滤缩小候选集 + 用压测数据调参数**。

### 案例 C：Agent 长期记忆复用同一套技术

**场景**：一个个人研究助手的 Agent，需要记住用户几周前提过的偏好（「只看 arXiv 综述」「引用要给 DOI」）。

**做法**：把每条记忆事件（「用户在某日表示偏好综述」）嵌入后存入向量库；新一轮对话时用当前请求做查询，取 Top-3 历史记忆注入系统提示。这就是 2.4 讲的记忆检索：**长期记忆 = 语义地图上的存与取**，与 RAG 检索共用 0.7 的全部技术，只是存的内容从文档换成了记忆事件。

## 8. 常见坑

1. **查询和文档用不同嵌入模型**。两个模型的空间完全不同，距离无意义。对策：同一任务锁死同一模型，版本一起升级。
2. **中文场景用了纯英文模型**。召回明显劣化。对策：按数据语言选 BGE/GTE/multilingual 系列。
3. **漏掉模型要求的指令前缀**。部分模型查询侧必须加固定前缀。对策：照模型卡用法写，封装进统一的 encode 函数。
4. **没有归一化就比相似度**。未归一化向量的点积被长度污染，长文本天然占优。对策：统一 L2 归一化后再算内积。
5. **阈值照抄别人的 0.8**。不同模型分数分布不同。对策：用自己的数据画相似度分布直方图再定阈值。
6. **切分不当毁掉嵌入**。块太大语义被稀释，太小上下文断裂。对策：256–1024 token 起步，10%–20% overlap（1.4b 细讲）。
7. **百万级还用暴力扫描**。Flat 索引在千万级延迟不可接受。对策：HNSW 起步，亿级上 IVF-PQ/分布式。
8. **ANN 参数从不校准**。默认参数不代表业务最优。对策：用 Flat 结果当金标，画 Recall@K-延迟曲线再定 efSearch/nprobe。
9. **检索时不做元数据过滤**。多租户与权限场景会数据泄露。对策：存储时写入权限/部门字段，检索时预过滤。
10. **换模型不重建索引**。新旧向量混在一个空间，检索结果随机劣化。对策：模型升级=全量重嵌入+重建索引，用别名灰度切换。
11. **只看最终答案不看检索指标**。不知道该修检索还是修生成。对策：先建 Recall@K/Hit Rate 的检索评测集。
12. **把向量检索当万能**。精确匹配（订单号、代码）和强时效数据（价格库存）不是它的领地。对策：BM25 双路 + 工具查询兜底。
13. **忽略过滤语义**。后过滤（先取 K 再滤）在强过滤条件下会丢结果甚至返回空。对策：选支持预过滤的库并验证。

1. 用 sentence-transformers 对 10 对句子算余弦相似度，手工标注哪些「语义相同、字面不同」，验证模型排序是否符合直觉。
2. 把 6.1 的脚本改成读入本地 txt 文件并按段落切分入库，用 5 个自造问题测试命中率。

4. 用 FAISS 生成 10 万随机向量，对比 IndexFlatIP 与 IndexIVFFlat（nprobe=1/8/32）的 Recall@10 与查询耗时，画出权衡曲线。
5. 同一批文档分别用 384 维和 1024 维模型嵌入，比较存储占用、建索引时间与检索质量。

7. 安装 rank_bm25，实现 BM25 与向量双路召回 + RRF 融合，找一个「只有双路才能查到」的查询案例。
8. 把一个小型 FAQ 库接入 2.4 风格的「记忆查询」：每次输入新问题，返回最相关的 3 条历史记录并打印相似度。

## 10. 小结

- Embedding = 文本变坐标：**语义越近，向量越近**，「理解意思」变成「计算距离」。
- 相似度默认用**归一化后点积**（等价余弦）；阈值必须用自己数据校准。
- 句向量由 Encoder + 池化得到；模型按**语言、维度、领域、用法（前缀）**四轴选。
- 千万级以上必须上 ANN：**HNSW 图跳跃（快、准、吃内存）vs IVF 分桶（省内存、可 PQ 压缩）**——召回、延迟、内存的三角权衡，用压测数据定参数。
- 向量库选型三问：**量级、过滤需求、团队栈**；原型 Chroma，生产 Qdrant/Milvus/pgvector。
- 生产检索标配：**向量 + 元数据预过滤 + 双路混合检索 + Rerank**。
- 同一套技术直接支撑 1.4 RAG、1.4c 检索优化与 2.4 Agent 长期记忆——语义地图是整个知识工程的地基。
