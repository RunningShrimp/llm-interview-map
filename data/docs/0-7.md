## 2. 一句话定义

向量与嵌入基础，是把文本映射为高维稠密向量，并通过相似度度量实现语义检索与匹配的工程方法。

简化公式：

```text
文本 x → 嵌入模型 f(x) → 稠密向量 v（384–3072 维）
查询向量与文档向量算相似度 → 取 Top-K → 语义检索
```

## 3. 为什么需要

做 AI Agent，你一定会遇到：

- **RAG**：用户问题怎么从知识库中找到相关文档？
- **记忆**：Agent 怎么记住并召回历史信息？
- **去重**：两条文本是否语义重复？
- **分类**：把用户意图映射到已知类别？
- **推荐**：找相似内容？
- **评估**：答案和标准答案语义接近吗？

这些问题的共同解法：**嵌入 + 相似度检索**。

传统关键词检索（BM25）只能匹配字面，嵌入能匹配**语义**：

```text
用户问：“怎么退钱？”
知识库写：“退款流程说明”
关键词检索：匹配不到“退钱”（字面不一致）
嵌入检索：“退钱”与“退款”语义接近，能召回
```

类比：关键词检索像只按书名找书的旧书店——书名对不上就找不到；向量检索像给每本书标了“内容坐标”的图书馆地图，“怎么退钱”和“退款流程”在这张地图上挨着，走过去就能拿到。

两类检索的系统对比：

| 维度 | BM25 关键词检索 | 向量语义检索 |
|---|---|---|
| 匹配对象 | 字面 token | 语义 |
| 同义改写（退钱/退款） | 召回差 | 强 |
| 精确匹配（编号、代码、专名） | 强 | 弱 |
| 可解释性 | 强（能指出命中词） | 弱（相似度是黑盒分数） |
| 依赖 | 分词与倒排索引 | 嵌入模型 |
| 离线成本 | 低 | 需批量嵌入 |

结论：生产系统通常**两者混合**（见 4.9，工程细节见 1.4）。

## 4. 核心原理

### 4.1 嵌入（Embedding）是什么

嵌入是把离散对象（词、句、文档、图片）映射为**稠密向量（Dense Vector）**：

```text
"退货政策" → [0.12, -0.98, 0.33, ..., 0.07]  （如 1536 维）
```

特点：

- 维度通常 384 / 768 / 1024 / 1536 / 3072。
- 语义相近的文本，向量距离近。
- 向量是模型学出来的，不是人工定义。
- **同一个模型才能比较向量**——不同模型的向量空间互不兼容。

向量怎么学出来的：嵌入模型用**对比学习（Contrastive Learning）**训练——把语义相似的句对（如问题与对应答案）在向量空间里拉近，把不相似的推远；训练覆盖足够广之后，“语义相近 = 向量相近”就成了这个空间的几何性质，也因此能泛化到训练时没见过的问题上。

### 4.2 从词嵌入到句嵌入

| 层级 | 说明 | 代表 |
|---|---|---|
| 词嵌入 | 单个词的向量 | Word2Vec、GloVe |
| 上下文词嵌入 | 同词不同语境不同向量 | BERT |
| 句/段嵌入 | 整句/整段一个向量 | Sentence-BERT、OpenAI Embedding |
| 文档嵌入 | 整篇文档一个向量 | 同上，但需先切分 |

RAG 用的是**句/段/文档级嵌入**。

### 4.3 嵌入模型的选择

| 模型 | 维度 | 特点 |
|---|---|---|
| OpenAI text-embedding-3-small | 1536 | 便宜、够用 |
| OpenAI text-embedding-3-large | 3072 | 更强、更贵，支持降维 |
| BGE-M3 | 1024 | 开源、多语言、稠密+稀疏+多向量 |
| GTE | 768-1024 | 开源、中文好 |
| Cohere Embed | 1024 | 多语言、检索优化 |
| Jina Embeddings | 768-1024 | 长文本友好 |

选型考虑：

- **语言**：中文优先 BGE、GTE、Cohere。截至 2026 年，开源中文嵌入的主流选择仍是 BGE 系与 GTE 系；MTEB 等榜单排名迭代很快，选型以当期榜单加自建评测为准（趋势观察）。
- **成本**：开源自托管 vs API 按量付费。
- **维度**：维度越高通常越准，但存储与检索成本随之上涨；text-embedding-3 系列支持 Matryoshka 式降维——先按高维存，需要时截断到低维，精度只小幅下降。
- **长度**：模型有最大输入长度（如 512 / 8192 token）。
- **是否需要稀疏/混合检索**：BGE-M3 一个模型同时输出稠密、稀疏与多向量三种表示。

### 4.4 相似度度量

三种常见度量（点积与范数的基础运算见 0.1）：

| 度量 | 公式 | 值域 | 特点 |
|---|---|---|---|
| 余弦相似度（Cosine Similarity） | cos(a,b) = a·b / (‖a‖‖b‖) | [-1, 1] | 只看方向，最常用 |
| 点积（Dot Product） | a·b | 无界 | 受向量长度影响，计算最快 |
| 欧氏距离（Euclidean Distance, L2） | ‖a-b‖ | [0, +∞) | 看绝对距离 |

三者的关系（推导）：

- 向量归一化（Normalization，除以自身模长）后，余弦相似度 = 点积。
- 归一化后：‖a-b‖² = ‖a‖² + ‖b‖² - 2a·b = 2(1 - cos(a,b))，即欧氏距离与余弦相似度单调对应，排序结果一致。

工程建议：

- 文本检索默认用**余弦相似度**。
- 向量库常要求先归一化，然后用内积（IP）加速——数学上等价于余弦。
- 一定看清向量库默认用哪种度量（有的默认 L2），度量与索引不匹配会静默排错序。

面试高频问法：“为什么文本检索默认用余弦相似度而不是欧氏距离？”共识口径：文本嵌入的向量模长受文本长度、信息量影响并不稳定，余弦只比较方向，对模长波动更鲁棒；而归一化之后两者单调等价，所以这是稳定性与工程惯例的选择，不是严格的能力差异。

### 4.5 向量数据库

向量数据库（Vector Database）存储向量并支持近似最近邻（ANN, Approximate Nearest Neighbor）检索。

| 向量库 | 形态 | 特点 | 适用 |
|---|---|---|---|
| FAISS | 本地库 | Meta 出品，纯检索库，快 | 单机、进程内嵌入 |
| Chroma | 轻量库 | 原型友好，API 简单 | Demo、小项目 |
| Qdrant | 服务 | Rust 实现，性能好，过滤强 | 生产、中大规模 |
| Weaviate | 服务 | 功能全，内置混合检索 | 生产 |
| Milvus | 服务 | 大规模、分布式 | 亿级向量 |
| Pinecone | 云服务 | 全托管，省运维 | 不想自己运维 |
| pgvector | PostgreSQL 扩展 | 和业务库一体 | 已有 PG 技术栈 |
| Redis Vector | Redis 扩展 | 低延迟 | 已有 Redis |

选型考虑：

- 数据量：<10 万条用 FAISS/Chroma 就够；百万级以上上 Qdrant/Milvus。
- 运维能力：无人运维选 Pinecone。
- 已有 PostgreSQL：pgvector 最省事，一个库同时放业务数据和向量。
- 需要混合检索与元数据过滤：Qdrant、Weaviate、Milvus 支持好。

面试高频问法：“百万级向量，FAISS、Milvus、pgvector 怎么选？”共识口径：先按运维成本再按性能选——单机内存放得下且不需要服务化，用 FAISS；要服务化、多租户、过滤与高可用，用 Milvus/Qdrant；数据量不大且团队已有 PG 技术栈，pgvector 最省事。

### 4.6 ANN 索引

精确检索（暴力搜索）是 O(n)：每个查询都要与全库向量逐个比距离，10 万条还能扛，千万条就太慢。  
ANN 用“近似”换速度：以很小的召回损失，换数量级的延迟下降。

常见索引：

| 索引 | 原理 | 查询复杂度 | 内存 | 精度 | 特点 |
|---|---|---|---|---|---|
| Flat | 暴力搜索，逐一比较 | O(n) | 高 | 精确解 | 最准、最慢 |
| IVF | 聚类分桶，查询只扫部分桶 | O(√n) 量级 | 中 | 高（可调） | 快，需训练与调参 |
| HNSW | 分层近邻图，贪心游走 | 近 O(log n) | 高 | 很高 | 快且准，内存开销大 |
| PQ | 乘积量化（Product Quantization）压缩向量 | 低 | 低 | 中 | 省内存，精度略降 |

机制直觉：

- **IVF** 像快递分拣：先对全库向量做 k-means 聚类分成若干桶（省、市、网点），查询时先找离查询最近的 nprobe 个桶，只在桶内暴力搜。代价是落在聚类边界附近的向量可能被漏掉。
- **HNSW** 像问路：建一张多层近邻图，上层是“高速公路”（节点稀疏、边长），底层是“小路”（节点稠密、边短）；查询从顶层贪心走向目标，逐层下沉，最后在底层精确定位。建图成本高、内存占用大，但查询又快又准。

工程建议：

- 小数据（<10 万）：Flat，精确解且够快。
- 中大数据：HNSW，事实上的默认选择。
- 内存受限：IVF + PQ 组合（如 IVF1024,PQ64）。
- 参数：`ef_search`（HNSW）、`nprobe`（IVF）控制精度-速度权衡——调大更准但更慢。

### 4.7 切分（Chunking）

文档太长，既超过嵌入模型的输入长度，也不适合整体嵌入——太长的文本会被压成一个“什么都像”的向量。要切分：

类比：切分像把教材做成知识卡片——每张卡片必须是一句完整的知识点；把一句话撕成两半，两张半句卡片谁也检索不准。

| 策略 | 说明 | 适用 |
|---|---|---|
| 固定长度 | 按 token/字符切 | 简单通用 |
| 递归切分 | 按段落→句子→词逐级 | 推荐默认 |
| 语义切分 | 按语义边界切 | 质量高，成本高 |
| 按结构切 | 按标题、章节切 | 结构化文档 |

关键参数：

- `chunk_size`：如 256–1024 token。
- `chunk_overlap`：如 10%–20%，防止边界信息丢失。

原则：

- 太小：语义不完整，检索碎片化。
- 太大：噪音多，嵌入不聚焦。
- 加 metadata：来源、标题、时间、权限——它们是后续过滤与引用的钩子。

父子切分（小块检索、大块返回）等进阶策略在 1.4 展开。

### 4.8 检索流程

```text
1. 离线：文档 → 切分 → 嵌入 → 归一化 → 存入向量库
   ↓
2. 在线：用户问题 → 嵌入（同一模型）→ ANN 检索 Top-K
   ↓
3. 可选：重排（Rerank）
   ↓
4. 拼接上下文 → 交给 LLM 生成（组装细节见 1.4）
```

### 4.9 混合检索与重排（预告）

纯向量检索的弱点：

- 对精确关键词、编号、代码不敏感。
- 对领域专有名词可能不准。

改进：

- **混合检索（Hybrid Search）**：BM25（关键词）+ 向量（语义），两路结果做排名融合（如 RRF）。
- **重排（Rerank）**：用交叉编码器（Cross-Encoder）把查询和文档放在一起重新打分，精度高于双编码器（Bi-Encoder）的独立召回分。

流程：

```text
查询 → BM25 Top-20 + 向量 Top-20 → 合并去重 → Rerank → Top-5 → LLM
```

重排模型：BGE-Reranker、Cohere Rerank、Jina Reranker。

RRF 融合、查询重写与完整工程细节见 1.4。

### 4.10 检索质量指标

| 指标 | 含义 |
|---|---|
| Recall@K | 前 K 个结果覆盖了多少相关文档 |
| Precision@K | 前 K 个里有多少相关 |
| MRR | 第一个相关文档的排名倒数 |
| NDCG | 考虑排序位置的增益 |
| Hit Rate | 至少命中一个相关的比例 |

示例：相关文档共 3 篇，Top-5 检索结果命中其中 2 篇，则 Recall@5 = 2/3 ≈ 0.67。

RAG 最关心 **Recall@K**：先保证召回，再优化精度。没召回的文档，后面的重排和生成都没有机会补救。

## 5. 架构 / 流程

从文本到检索的完整链路：

```text
┌─────────────────────────────────────────────┐
│  离线索引（Indexing）                        │
│  文档 → 清洗 → 切分 → 嵌入 → 归一化 → 存储   │
│  （向量 + 原文 + metadata + ANN 索引）       │
└─────────────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────┐
│  在线检索（Retrieval）                       │
│  查询 → 嵌入（同一模型）→ 归一化             │
│       → ANN 检索 Top-K → metadata 过滤       │
│       → 可选 Rerank → Top-k' 返回            │
└─────────────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────┐
│  下游消费                                    │
│  RAG：上下文拼装 → LLM → 答案 + 引用（1.4）  │
│  记忆：历史信息写入与召回（2.4）             │
└─────────────────────────────────────────────┘
```

## 6. 代码 / 工具

### 6.1 生成嵌入（OpenAI API）

```python
from openai import OpenAI
import numpy as np

client = OpenAI(api_key="YOUR_KEY")

def embed(texts: list[str]) -> np.ndarray:
    """批量把文本变成 1536 维向量"""
    response = client.embeddings.create(
        model="text-embedding-3-small",
        input=texts,
    )
    return np.array([d.embedding for d in response.data])

texts = [
    "退货政策是什么",
    "退款流程说明",
    "如何申请换货",
    "今天天气真好",
]

vectors = embed(texts)
print(vectors.shape)  # (4, 1536)
```

### 6.2 余弦相似度与归一化

```python
def cosine_similarity(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

query = "怎么退钱"
query_vec = embed([query])[0]

scores = [cosine_similarity(query_vec, v) for v in vectors]
ranked = sorted(zip(texts, scores), key=lambda x: -x[1])

for text, score in ranked:
    print(f"{score:.4f}  {text}")

# 归一化后点积 = 余弦：大规模计算前统一归一化，用矩阵乘加速
normed = vectors / np.linalg.norm(vectors, axis=1, keepdims=True)
q = query_vec / np.linalg.norm(query_vec)
scores_fast = normed @ q
```

预期输出：「退货政策」「退款流程」得分明显高于「今天天气真好」。

### 6.4 FAISS 最小示例（Flat 与 HNSW）

```python
import faiss
import numpy as np

dim = 1536
vecs = vectors.astype("float32")   # 复用 6.1 的嵌入结果 (n, dim)

# 方案一：精确检索。归一化 + 内积（IP）= 余弦相似度
faiss.normalize_L2(vecs)
flat = faiss.IndexFlatIP(dim)
flat.add(vecs)

q = embed(["怎么退钱"]).astype("float32")
faiss.normalize_L2(q)
scores, ids = flat.search(q, 2)    # Top-2
print(ids, scores)

# 方案二：数据量大时用 HNSW（近似，快）
hnsw = faiss.IndexHNSWFlat(dim, 32)  # 每个节点 32 个邻居
hnsw.add(vecs)
scores, ids = hnsw.search(q, 2)
```

## 7. 案例

### 案例 A：电商 RAG 知识库检索

**场景**：某电商知识库 1000 篇文档，切分成约 5000 块。用户问：“退款要多久到账？”

**做法**：

1. 问题用 text-embedding-3-small 嵌入为 1536 维向量。
2. 向量库 HNSW 索引检索 Top-20（单次延迟约 10ms 量级）。
3. BGE-Reranker 重排取 Top-5。
4. 拼接上下文交给 LLM 生成。

**示意效果**：召回“退款时效说明”，LLM 回答“3-5 个工作日”并标注来源；加重排后 Top-5 内正确率从约 70% 提升到约 90%，端到端延迟只增加不到 200ms。

### 案例 B：工单语义去重

**场景**：客服沉淀了 1000 条工单，想合并重复问题。

**做法**：

1. 每条工单嵌入。
2. 两两计算余弦相似度。
3. 相似度 > 0.9 归为一类。

**示意效果**：1000 条工单聚成约 200 类，热门问题一目了然；能识别“登录不上”和“无法登录”这类字面不同、语义相同的表述——字符串精确匹配做不到这一点。

### 案例 C：混合检索解决编号查询

**场景**：用户问“错误码 E1024 怎么解决？”，运维知识库里有大量错误码文档。

**做法与示意效果**：纯向量检索会召回语义相近但编号不同的文档（E1023、E1042 混进 Top-5，命中率仅约 40%）；改为 BM25 + 向量混合检索后，BM25 精确锁定“E1024”的字面命中，向量补充语义相关内容，Top-5 命中率提升到约 95%。

## 8. 常见坑

1. **查询和文档用不同模型嵌入**。  
   向量空间不一致，检索完全失效。必须同一模型；换模型就要全量重建索引。

2. **忽略归一化**。  
   用点积但不归一化，向量模长会干扰相似度排序。统一先归一化，再用内积。

3. **度量与索引不匹配**。  
   向量库默认 L2 而你按余弦理解分数，排序会静默出错。接入时先看清默认度量再选索引。

4. **切分太大或太小**。  
   太大噪音多、嵌入不聚焦，太小语义碎。建议 256–1024 token + 10%–20% overlap，并用评测集挑参数。

5. **不加重排**。  
   Top-K 向量检索的排序精度有限。Rerank 用交叉编码器重新打分，能显著提升排序质量。

6. **只靠向量，不用关键词**。  
   编号、代码、专有名词是纯向量检索的盲区。用 BM25 混合检索兜底。

7. **不做元数据过滤**。  
   多租户、权限、时间范围必须靠 metadata 过滤；检索后再过滤会因 Top-K 截断而漏结果。

8. **不看 Recall@K**。  
   检索没召回，LLM 再强也白搭。先建评测集监控召回率，再优化其他环节。

9. **嵌入模型不支持中文**。  
   用英文为主的模型处理中文，效果差很多。中文场景选 BGE、GTE、Cohere。

10. **向量库选型过度**。  
    10 万条以下用 FAISS/Chroma 就够，不必上 Milvus。先按运维成本选，再按性能选。

11. **忽略成本**。  
    查询侧每次都要嵌入（API 按量计费），存储侧高维向量占内存。批量嵌入与降维是两个省钱抓手。

12. **不更新索引**。  
    知识库变了、向量库没更新，就会检索到旧内容。文档变更要联动增量重嵌入。

13. **把嵌入当万能**。  
    嵌入捕捉语义相似，不擅长逻辑推理、数值比较、否定关系。这些交给 LLM 或工具。

## 10. 小结

- 嵌入 = 文本 → 稠密向量，语义相近则向量相近；向量由对比学习训出，只能在同一模型的向量空间内比较。
- 相似度：**余弦最常用**；归一化后余弦 = 点积，且与欧氏距离单调对应。
- 嵌入选型：中文优先 BGE / GTE / Cohere；维度越高越准也越贵，text-embedding-3 系列支持降维。
- 向量库：**FAISS/Chroma 入门，Qdrant/Milvus 生产，pgvector 复用已有 PG 最省事**。
- ANN 索引：**小数据 Flat，中大数据 HNSW，内存紧张 IVF+PQ**；用 `ef_search`/`nprobe` 调精度-速度权衡。
- 切分：**256–1024 token + 10%–20% overlap** 是常用起点，务必带 metadata。
- 检索：**向量召回 + 混合检索 + Rerank** 是生产标配（工程细节见 1.4）。
- 评估：**先看 Recall@K，再看 Precision、MRR、NDCG**。
- 本篇只讲“向量本身”；把这些组件组装成完整系统是下一步的事。
- 这些能力直接支撑：1.4 RAG、2.4 记忆、3.2 数据与知识工程。
