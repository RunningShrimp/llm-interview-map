# 讲解 2.2 规划 Planning

> 说明：2.1 定义了 Agent 四件套，本篇展开其中「规划」这一件：把模糊目标拆成带依赖、可校验的执行计划。计划如何被逐步执行是 2.5 ReAct 循环的主题，执行失败的反思修正见 2.6，拆分后的子任务分给多个 Agent 协作在 2.8 展开。

---

## 1. 定位

L2 第二章，Agent 从「能循环」到「能干成事」的关键。它回答一个问题：**拿到「调研竞品并写报告」这种模糊目标，怎么变成机器可执行、可校验、可重来的步骤清单？**

前置：2.1（Agent 定义——规划是四件套之一，Planner/Executor 分工建立在「模型决定下一步」的框架上）、1.3（结构化输出——计划必须落成可解析的 JSON，规划才谈得上工程化）。后续：2.5 用 ReAct 循环执行计划并处理轨迹，2.6 的 Reflection 是重规划的思想源头之一，2.8 的多 Agent 协作中「怎么拆任务」直接决定团队结构。面试中「Agent 如何处理复杂任务」的标准答案起点就是任务分解，往下追问必然落到 Plan-and-Execute 与 ReWOO 的取舍。

## 2. 一句话定义

规划 = 把模糊目标拆成**带依赖关系与完成判据的子任务清单**。主流范式两条：**Plan-and-Execute** 先由 Planner 生成完整计划、Executor 照单执行，失败回炉重规划；**ReWOO** 规划阶段不看工具观察结果，一次排完所有调用、批量并行、由 Solver 汇总——LLM 调用从 n 次降到约 2 次。

## 3. 为什么需要

没有规划的 Agent 只会 ReAct 式边想边做，长任务上暴露三个问题：

1. **跑偏**。每一步只看当前观察做局部决策，十步之后早已偏离初始目标。城市里靠路牌开车，开一段看一段，容易绕晕。
2. **上下文膨胀**。每步的思考与观察都堆进上下文，token 成本线性上涨，且触发「中间遗忘」（1.5 提过的 lost-in-the-middle）。
3. **无法并行**。边想边做的串行节拍，把本可并行的独立子任务（同时搜竞品 A、B、C）也排成了队。

规划对症下药：先在地图上把整趟行程排好、标清先后依赖（先加油才能上山），再照单执行。代价是**计划本身可能错**——路上封路就得重规划。所以规划的完整闭环是「拆解-执行-校验-重规划」，而不是「拆解-执行」两步。

一个来自装修工头的直觉：瓦工贴完砖发现防水没做，正确做法不是骂瓦工重贴，而是回炉计划本身——拆单时漏了防水工序。**错误答案通常意味着错误计划**：重规划要回到 Planner 层，在 Executor 层重复重试只会原地翻车。

## 4. 核心原理

### 4.1 任务分解三要素

一个合格的计划由三种信息构成，缺一不可：

1. **子任务**：目标拆成粒度均匀、单步可执行的最小单元。每个子任务应能被一次工具调用或一次短生成完成；需要两个工具接力才能完成的，说明还没拆透。
2. **依赖关系**：谁先谁后、谁的结果是谁的输入。依赖决定了执行顺序与可并行性——无依赖的子任务可以并行跑。
3. **完成判据**：每个子任务「怎么算做完」。判据是 Executor 的验收标准和 Verifier 的校验依据——**缺判据的计划没法校验失败**，也就无从重规划。

以「调研三个竞品的定价并写对比报告」为例：

| 子任务 | 依赖 | 完成判据 |
|---|---|---|
| T1 检索竞品 A 定价页 | 无 | 拿到含价格数字的页面内容 |
| T2 检索竞品 B 定价页 | 无 | 同上 |
| T3 检索竞品 C 定价页 | 无 | 同上 |
| T4 抽取三家定价为结构化表格 | T1,T2,T3 | 表格含每家的套餐名与价格字段 |
| T5 写对比报告初稿 | T4 | 覆盖三家、含结论段 |

三要素的自检口诀：**子任务看得清单步动作，依赖说得清输入来源，判据答得出怎么算完**。判据最容易被漏——「检索竞品定价」不算合格子任务，「拿到含价格数字的页面」才是。

### 4.2 Plan-and-Execute

两段式架构：Planner 一次生成完整计划，Executor 逐步执行，Verifier 校验，失败回炉 Planner。

```text
目标 → Planner（一次拆解+依赖排序）→ Executor（逐步照单执行）
              ▲                            │
              │            结果不达标        ▼
              └────── Verifier（校验判据）◀──┘
```

与 ReAct 的本质区别：ReAct 每一步都让 LLM 看着全部历史做决策（决策 n 次，上下文越来越大）；Plan-and-Execute 把「决定做什么」集中到 Planner 一次完成，Executor 只负责「怎么做」，上下文被隔离在子任务粒度。

收益：

- **长任务不跑偏**：计划是全局的，执行时始终对齐初始目标。
- **上下文可控**：每个子任务只携带与自己相关的上下文，不背全部历史。
- **可校验可重入**：计划是显式数据结构，哪个子任务失败一清二楚，重规划有明确着力点。

代价：计划质量依赖 Planner 能力；环境变化快时计划过时，需要重规划机制兜底。

### 4.3 ReWOO

ReWOO（Reasoning WithOut Observation）：规划阶段**不看工具观察结果**，一次性生成全部调用计划（子任务可用占位符引用前序结果），然后由 Worker 批量执行（可并行），最后 Solver 汇总作答。

```text
ReAct：      想A→做A→看A → 想B→做B→看B → 想C→做C→看C → 答案   （n 轮 LLM）
ReWOO：      Planner 一次排完 A/B/C（含占位引用）
             → Worker 并行：做A ∥ 做B ∥ 做C                    （0 轮 LLM）
             → Solver 汇总出答案                                （1 轮 LLM）
```

三项收益：

1. **省 token**：LLM 决策轮从 n 次降到约 2 次（规划 1 次 + 汇总 1 次）；任务步数越多省得越多。
2. **可并行**：无依赖的子任务真正同时执行，端到端延迟显著下降。
3. **计划可审计**：完整计划先于执行生成，可以在执行前人工审查或干跑校验。

一项代价：**中途无法根据观察调整计划**——观察被推迟到 Solver，执行中发现的意外（搜索结果为空、页面失效）只能等汇总后触发整体重规划。所以 ReWOO 适合「路径可预判、检索型为主」的任务；环境高度动态时退回 Plan-and-Execute。

### 4.4 三范式对比

| 维度 | ReAct | Plan-and-Execute | ReWOO |
|---|---|---|---|
| 决策时点 | 每步 | 集中在 Planner | 集中在 Planner（不看观察） |
| LLM 决策轮 | ≈ n 次 | 1 + 执行中若干 | ≈ 2 次 |
| 可并行性 | 无 | 依赖图内可并行 | 天然并行 |
| 应变能力 | 最强 | 中（可重规划） | 弱（事后整体重规划） |
| 上下文压力 | 大（全历史） | 小（子任务隔离） | 最小 |
| 适用任务 | 路径高度动态、单步灵活 | 长任务、目标明确 | 检索型、可预判、步数多 |
| 主要风险 | 绕晕、成本高 | 计划过时 | 计划错则全盘错 |

选型口诀：**ReAct 管单步灵活性，Plan-and-Execute 管长任务不跑偏，ReWOO 管省 token 高并行**。按任务形状选，不追新。

### 4.5 重规划 vs 重试

执行失败时的两条路，选错就是原地翻车：

- **重试（Retry）**：同一计划、同一子任务，换个参数再跑一遍。适用于**瞬时故障**：网络超时、限流 429、偶发解析失败。判据：错误是随机的、环境没变、上次失败原因与计划无关。
- **重规划（Replan）**：回到 Planner 层修计划本身——调整子任务、补漏、换路径。适用于**计划性缺陷**：子任务拆错、依赖遗漏、判据不可满足、环境已变化。判据：同一路径重试两次仍失败，或失败原因指向计划结构。

工程上的标准闭环：Executor 失败 → 先按瞬时故障重试（带上限，如 2 次）→ 仍失败则把失败上下文回传 Planner 重规划 → 重规划也连续失败则升级人工。重规划提示词里必须带上「原计划 + 失败子任务 + 失败原因」，否则 Planner 会重复犯同样的错。

| 信号 | 处置 |
|---|---|
| 超时、429、网络错误 | 重试（指数退避，带上限） |
| 同一子任务重试 2 次仍失败 | 重规划 |
| 判据校验不通过且原因结构性 | 重规划 |
| 计划依赖的外部条件消失 | 重规划 |
| 重规划连续 2 次仍失败 | 升级人工 |

### 4.6 多 Agent 场景的任务拆分

拆分质量决定多 Agent 系统的成败（2.8 的正式主题，这里给规划视角的三条原则）：

1. **按产出物拆，不按角色腔调拆**。每个子 Agent 对应一个可校验的交付物（定价表、用户口碑摘要、报告终稿），而不是「乐观者」「批评者」式的人格扮演——交付物才能挂判据。
2. **拆到接口清晰为止**。子任务间的输入输出是显式数据（结构化 JSON），不是共享一团对话历史。接口清晰才能并行、才能单测、才能替换。
3. **控制上下文隔离与传递**。每个子 Agent 只携带自己子任务需要的上下文；汇总层（主管或 Solver）只收交付物与判据结果，不收全部过程——否则多 Agent 退化成一个大上下文的单 Agent，只剩成本劣势。

对应到计划结构：多 Agent 计划就是在计划 JSON 的每个子任务上多一个 `assignee` 字段，主管按依赖图调度，可并行的节点同时派发。

### 4.7 规划失败模式

| 失败模式 | 现象 | 对策 |
|---|---|---|
| 过度规划 | 简单任务拆出十几个子任务，成本翻倍 | 计划里加步数预算；Planner 提示词声明「能一步完成就别拆」 |
| 欠规划 | 子任务粗到单步执行不了 | 要求子任务单步可完成，判据可机器校验 |
| 幻觉依赖 | 引用不存在的子任务或字段 | 计划生成后程序校验：ID 引用闭合、依赖无环 |
| 判据不可校验 | 「尽量全面」「写好一点」 | 判据必须是可判定的布尔或结构条件 |
| 计划僵化 | 环境已变仍死守原计划 | Verifier 持续校验，触发即重规划 |
| 计划漂移 | 每次重规划越改越偏 | 重规划只允许修改失败分支，全量重排在多数场景是反模式 |
| 死循环重规划 | 规划-失败-重规划无限循环 | 重规划次数上限 + 升级人工 |

## 5. 架构 / 流程

Plan-and-Execute 完整闭环（含 ReWOO 变体与重规划回环）：

```text
┌────────────────────────────────────────────────────┐
│ Planner                                            │
│  输入：目标 + 可用工具清单 + 上下文摘要               │
│  输出：计划 JSON（子任务/依赖/判据/指派）              │
│  程序预检：ID 闭合、依赖无环、步数不超预算             │
└────────────────────────────────────────────────────┘
                        │ 合法计划
                        ▼
┌────────────────────────────────────────────────────┐
│ Scheduler（调度）                                   │
│  按依赖图计算就绪集；无依赖子任务并行派发              │
│  [ReWOO 变体：全部子任务带占位符一次派发，Worker 并行] │
└────────────────────────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────┐
│ Executor（逐子任务执行）                             │
│  瞬时故障 → 重试（上限 2 次，指数退避）                │
│  产出：子任务结果 + 结构化观察                        │
└────────────────────────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────┐
│ Verifier（校验完成判据）                             │
│  通过 → 下一子任务；全部通过 → Solver 汇总输出        │
│  不通过（结构性失败）→ 回传 Planner 重规划            │
└────────────────────────────────────────────────────┘
                        │
                        ▼  重规划回环（带上限，超限升级人工）
        Planner ←── 失败子任务 + 失败原因 + 已完成结果
```

单子任务的生命周期：

```text
pending ──依赖满足──▶ ready ──派发──▶ running ──▶ done（判据通过）
                                       │
                                       ├─ 瞬时失败 ─▶ retrying（≤2 次）
                                       │                  │ 超限
                                       └─ 结构失败 ─▶ replan（回 Planner）
```

## 6. 代码 / 工具

### 6.1 Planner 提示词模板

规划质量的上限在提示词。三要素（子任务/依赖/判据）和防过度规划都写进约束：

```text
# 角色
你是任务规划器（Planner）。把用户目标拆解为可执行的计划。
你只负责规划，不执行任何工具。

# 可用工具
{tools_with_schema}

# 规划规则
1. 每个子任务必须单步可完成：一次工具调用，或一次不超过 500 字的生成。
2. 每个子任务必须给出完成判据（success_criteria）：
   可机器判定的布尔条件或结构要求，禁止「尽量」「较好」等模糊表述。
3. 依赖用子任务 ID 表示，只允许引用已定义的子任务，不得成环。
4. 无依赖的子任务必须标注为可并行（parallel_group）。
5. 控制粒度：能用一步完成的目标不要拆；总步数不超过 {max_steps}。
6. 不确定工具是否可用时，生成一个「探测类」子任务先行确认，不要假设。

# 输出格式
只输出 JSON，schema 见 plan_schema，不要输出任何其他文字。

# 用户目标
{goal}

# 已知上下文（可选）
{context}

# 失败重规划时附加
原计划：{original_plan}
失败子任务：{failed_task_id}
失败原因：{failure_reason}
已完成结果摘要：{completed_summary}
要求：只修改必要的子任务，保持其余计划不变。
```

### 6.3 调度与校验的最小实现

```python
def validate_plan(plan: dict) -> list:
    """程序预检：ID 闭合、依赖无环、步数预算"""
    errors, ids = [], {t["id"] for t in plan["tasks"]}
    for t in plan["tasks"]:
        errors += [f"{t['id']} 引用了不存在的 {d}"
                   for d in t["depends_on"] if d not in ids]
    # 拓扑排序判环
    seen, stack = set(), set()
    def dfs(tid, tasks_by_id):
        if tid in stack:
            errors.append(f"依赖成环: {tid}"); return
        if tid in seen: return
        seen.add(tid); stack.add(tid)
        for d in tasks_by_id[tid]["depends_on"]:
            dfs(d, tasks_by_id)
        stack.discard(tid)
    by_id = {t["id"]: t for t in plan["tasks"]}
    for tid in by_id: dfs(tid, by_id)
    if len(plan["tasks"]) > plan.get("max_steps", 30):
        errors.append("步数超预算")
    return errors

def ready_tasks(plan: dict) -> list:
    """依赖全部 done 的子任务即就绪，可并行派发"""
    by_id = {t["id"]: t for t in plan["tasks"]}
    return [t for t in plan["tasks"]
            if t["status"] == "pending"
            and all(by_id[d]["status"] == "done" for d in t["depends_on"])]

def run_plan(plan: dict, executor, verifier, replanner, max_replans: int = 2):
    replans = 0
    while any(t["status"] != "done" for t in plan["tasks"]):
        for t in ready_tasks(plan):                    # 就绪集天然可并行
            t["status"] = "running"
            result = executor(t)                       # 内部含重试上限
            ok, reason = verifier(t, result)           # 校验完成判据
            if ok:
                t["status"] = "done"; t["result"] = result
            elif t.get("retries", 0) < 2:
                t["retries"] += 1; t["status"] = "pending"   # 瞬时故障：重试
            else:
                t["status"] = "failed"; t["failure"] = reason
                if replans >= max_replans:
                    return plan, "escalate_to_human"          # 升级人工
                plan = replanner(plan, t["id"], reason)        # 结构失败：重规划
                replans += 1
                break                                          # 重排后回到调度
    return plan, "completed"
```

## 7. 案例

### 案例 A：长任务跑偏的治理

**场景**：某咨询团队的竞品调研 Agent 用纯 ReAct 实现，任务「调研 5 个竞品并写报告」经常在 15 步之后跑偏——搜完竞品 3 就开始写报告，漏掉 2 家，且上下文已膨胀到 4 万 token。

**改造**：换 Plan-and-Execute。Planner 一次生成 11 个子任务（5 检索 + 4 抽取 + 校验 + 报告），检索类子任务按并行组同时派发，每个子任务只携带自己的判据与输入。

**效果**：任务完成度从「平均覆盖 3.2 家」升到 5 家全覆盖；端到端延迟从 4 分 30 秒降到 1 分 50 秒（并行收益）；上下文峰值从 4 万 token 降到 8 千（子任务隔离）；token 成本降 60%。核心收益不是省 token，是**不跑偏**。

### 案例 B：ReWOO 砍掉批量检索的成本

**场景**：一家金融科技公司的舆情监控 Agent，每小时对 20 个关键词做检索汇总。ReAct 版每轮决策都带全量历史，单小时任务消耗 18 万 token。

**改造**：换 ReWOO——Planner 一次生成 20 个带占位符的检索子任务，Worker 并行执行（0 次 LLM 决策），Solver 一次汇总。异常处理：检索结果为空的子任务标记后进入一次重规划补查。

**效果**：LLM 决策轮从约 21 次降到 2 次，单小时 token 消耗降 82%；并行执行让耗时从 6 分钟压到 50 秒。代价如实记录：某次某关键词源站改版，ReWOO 无法中途换源，等汇总后整体重规划补查，比 ReAct 慢一轮——这是选择 ReWOO 时接受的应变税。

### 案例 C：重试救不了的错误计划

**场景**：某电商售后 Agent 的计划里有个隐藏缺陷：子任务「查询退款资格」依赖「订单状态」，但 Planner 把两个子任务标成了无依赖可并行。执行时退款资格查询拿到的是下单前的旧状态，判据偶然通过，最终给出错误退款方案。团队最初当成偶发 bug 反复重试，失败率稳定在 12% 不降。

**定位与治理**：把失败轨迹回传 Planner 重规划时，Planner 指出依赖缺失；同时在 validate_plan 预检里加了「字段血缘检查」——子任务参数引用的字段必须来自其 depends_on 子任务的产出。

**效果**：失败率从 12% 降到 0.4%（剩余为真实瞬时故障）。复盘结论就是本篇的核心命题：**错误答案通常意味着错误计划——先问计划对不对，再问执行好不好**。

## 8. 常见坑

1. **子任务拆得太粗**。
   一步干不完三个动作，Executor 无所适从。子任务必须单步可完成。

2. **判据缺失或模糊**。
   「尽量全面」没法校验，失败无从谈起。判据必须是可机器判定的条件。

3. **依赖没标或标错**。
   该串行的并行走，拿到半成品输入。计划生成后程序预检依赖闭合与无环。

4. **把重试当重规划**。
   计划性缺陷重试两次结果一样。瞬时故障重试，结构性失败回炉 Planner。

5. **过度规划**。
   简单任务拆十步，成本和失败面同步放大。提示词里写明步数预算与「能一步就别拆」。

6. **ReWOO 用在动态环境**。
   观察被推迟，中途应变能力为零。路径可预判才用 ReWOO，否则退回 Plan-and-Execute。

7. **ReAct 用在长任务**。
   步数一多就跑偏加膨胀。长任务先规划再执行，ReAct 留给单步灵活场景。

8. **重规划全量重排**。
   每次重排越改越偏。只修改失败分支，保持其余计划稳定。

9. **重规划不带失败上下文**。
   Planner 看不到失败原因，重蹈覆辙。回传原计划、失败子任务与原因。

10. **重规划不设上限**。
    规划-失败循环烧钱无底。重规划次数上限，超限升级人工。

11. **多 Agent 按人格拆而不是按交付物拆**。
    「乐观者/批评者」没法挂判据。按可校验的交付物拆，接口用结构化数据。

12. **多 Agent 共享一整团上下文**。
    退化成成本更高的单 Agent。上下文按子任务隔离，汇总层只收交付物。

13. **计划不做程序预检**。
    幻觉 ID、循环依赖直接进调度器炸掉。先跑 validate_plan 再执行。

14. **把计划写死在提示词里**。
    计划应是可解析、可修改的数据结构，不是一段散文。落成 JSON，让调度器消费。

## 10. 小结

- 规划 = 拆子任务 + 标依赖 + 定判据；**缺判据的计划没法校验失败**，也就没法重规划。
- **Plan-and-Execute**：Planner 一次拆解，Executor 照单执行，Verifier 校验——长任务不跑偏、上下文可控。
- **ReWOO**：规划不看观察，一次排完、并行执行、Solver 汇总——决策轮从 n 次降到约 2 次，代价是中途不能应变。
- 选型口诀：**ReAct 管单步灵活，Plan-and-Execute 管长任务，ReWOO 管省 token 高并行**。
- **重规划不等于重试**：瞬时故障重试（带上限），结构性失败回炉 Planner——错误答案通常意味着错误计划。
- 重规划要带失败上下文、只改失败分支、设次数上限，超限升级人工。
- 多 Agent 拆分三原则：**按交付物拆、接口结构化、上下文隔离**（展开在 2.8）。
- 计划是一等数据结构：JSON Schema 定形，程序预检（ID 闭合、无环、步数）后才进调度。
- 高频失败模式：过度/欠规划、幻觉依赖、判据模糊、计划僵化、重规划死循环——都有对应护栏。
- 规划产出的计划由 2.5 的 ReAct 循环逐步执行；执行中学到的教训如何沉淀，见 2.6 反思。
