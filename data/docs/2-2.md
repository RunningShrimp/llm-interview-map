# 讲解 2.2 规划 Planning

> 说明：前置 2.1 讲了 Agent 是什么，本篇讲 Agent 的“大脑第一步”：**如何把模糊目标拆成可执行的步骤、决定行动顺序，并在执行中动态调整**。

## 1. 定位

Agent 核心层第 2 个知识点，属于“决策与任务分解”。  
它解决本锚点的核心问题：**用户给了一个模糊目标，Agent 如何把它变成可执行的步骤序列，并在环境变化时调整计划？**

- 直接前置：2.1（先分清“下一步由谁决定”，才谈得上“怎么定计划”）。
- 直接后续：2.5 执行循环与状态机（计划的运行时消费方）、2.6 反思（重规划信号的来源）。
- 相邻但不展开：工具调用见 2.3，单 Agent 架构选型见 2.7，多 Agent 协作见 2.8。

**与 2.5 的边界**：本篇回答“计划长什么样、怎么生成、怎么改”；2.5 回答“计划怎么跑、怎么停、怎么恢复”。一句话——本篇产出计划，2.5 消费计划。

## 2. 一句话定义

规划（Planning），是 Agent 把高层目标分解为可执行步骤、显式安排依赖与顺序、按复杂度选择处理方式（路由），并根据执行反馈动态修正计划的能力。

简化公式：

```text
规划 = 目标澄清 + 任务分解 + 依赖排序 + 可执行化 + 动态调整
```

## 3. 为什么需要

没有规划，Agent 会遇到：

- **目标太大**：用户说“帮我做市场调研”，Agent 不知道从哪开始。
- **步骤混乱**：先查数据还是先定框架？顺序错了浪费成本。
- **无法并行**：明明可以同时查三个来源，却串行执行。
- **不会调整**：第一步失败了，还按原计划走。
- **重复劳动**：做了 A 又做 B，发现 B 依赖 A 的结果，得重做。
- **无法解释**：用户问“你打算怎么做”，Agent 答不上来。

无规划与有规划的对比：

| 维度 | 没有规划（走一步看一步） | 有规划（先拆解再执行） |
|---|---|---|
| 长任务 | 容易跑偏，做几步忘了目标 | 计划锚定目标，不丢主线 |
| 成本 | 每步把全量历史重复喂给 LLM | 规划一次，执行不必逐步重复上下文 |
| 并行 | 天然串行 | 无依赖步骤可并行 |
| 可解释 | 事后难以复盘 | 计划即清单，可审查、可对齐 |
| 失败恢复 | 一步失败往往全盘重来 | 局部重规划，保留已完成成果 |

**类比 1（装修）**：

```text
没有规划 = 装修队进门就砸墙，边干边想，管线埋完才想起没定插座位置
有规划   = 先出图纸（分解），排工序（水电→瓦工→木工，依赖排序），
           每道工序有验收标准（可执行化），业主改需求就出变更单（重规划）
```

**类比 2（年夜饭）**：“办一桌年夜饭”是典型的模糊目标。先澄清（几位客人、有无忌口、几点开席），再分解（冷菜、热菜、汤、主食），再排序（炖汤最先下锅、热炒临上桌前），最后可执行化（每道菜绑定具体菜谱与锅具）。缺一步都出事：不澄清，客人忌口全踩雷；不排序，汤好了菜凉了；不做可执行化，菜谱写着“适量”“少许”，照样没法开工。

## 4. 核心原理

### 4.1 正面回答关键问题：模糊目标 → 可执行步骤的四步法

本锚点的关键问题是“如何把模糊目标拆成可执行步骤”，正面答案就是下面这个四步法，本节之后的所有小节都是它的展开。

**第一步：目标澄清（Goal Clarification）**。模糊目标缺三样东西：范围、约束、成功标准。澄清就是把它们显式化——范围（哪个市场、什么时间段、给谁看）、约束（预算、时限、数据口径）、成功标准（一份 8 页报告，还是一组结论要点）。做法：能问用户就问；不能问，就在规划提示词（Prompt）里先要求补一个“成功标准 + 假设”字段，先补全再分解。

**第二步：任务分解（Task Decomposition）**。把澄清后的目标拆成子任务（方法见 4.4），判据是 MECE（相互独立、完全穷尽，Mutually Exclusive and Collectively Exhaustive）加原子性（一步能被一个工具完成）。

**第三步：依赖排序（Dependency Ordering）**。标出每个子任务依赖谁的输出，构成有向无环图（Directed Acyclic Graph, DAG）；无依赖的步骤排入同一层，可并行执行。

**第四步：可执行化（Executable Mapping）**。每个原子步骤绑定三件事：用什么工具、传什么参数、怎样算完成（验收标准）。没绑定工具与验收标准的步骤只是愿望，不是步骤。

贯穿示例（“帮我做一份新能源汽车市场调研报告”）：

```text
澄清：2024 年中国乘用车市场 / 读者是管理层 / 3 天内 / 成功标准 = 结论先行的 8 页报告

分解 + 排序 + 可执行化，一次到位的结构化计划：
1. 搜销量与增速数据     工具: web_search  验收: 拿到 2024 全年数字   depends_on: []
2. 搜主要厂商市场份额   工具: web_search  验收: Top5 份额数字       depends_on: []
3. 搜政策变化           工具: web_search  验收: 至少 3 条政策        depends_on: []
   （1/2/3 互不依赖 → 同层可并行）
4. 汇总为对照表         工具: python      验收: 数字口径一致        depends_on: [1,2,3]
5. 生成报告             工具: write_doc   验收: 8 页、结论先行      depends_on: [4]
```

### 4.2 规划的层次

```text
Level 1: 目标理解     → 用户到底要什么？
Level 2: 任务分解     → 拆成哪些子任务？
Level 3: 步骤排序     → 先做什么，后做什么？
Level 4: 资源分配     → 用哪个工具，花多少预算？
Level 5: 动态调整     → 执行中怎么改计划？
```

四步法覆盖 Level 1-4；Level 5（动态调整）即 4.7 的重规划。

### 4.3 规划的三个时机

| 时机 | 说明 | 代表范式 |
|---|---|---|
| 执行前规划 | 先制定完整计划再执行 | Plan-and-Execute、ReWOO |
| 执行中规划 | 边想边做，每步决策 | ReAct |
| 执行后重规划 | 失败或环境变化后修正计划 | Replanning（校验后回环给 Planner）；Reflexion 可作触发器（见 2.6） |

**执行前规划**：

```text
目标 → 完整计划 → 逐步执行 → 完成
```

优点：结构清晰，可并行。缺点：计划可能过时。

**执行中规划**：

```text
目标 → 观察 → 决策 → 行动 → 观察 → 决策 → ...
```

优点：灵活，适应性强。缺点：容易短视，可能死循环。

**混合模式**：

```text
先粗规划 → 执行中细化 → 失败后重规划
```

这是生产推荐方案。

### 4.4 任务分解（Task Decomposition）

**方法 1：LLM 直接分解**

```text
目标：帮我分析这份财报并给出投资建议。

分解：
1. 读取财报文件
2. 提取关键财务指标（营收、利润、现金流）
3. 计算同比/环比增长率
4. 与行业平均水平对比
5. 分析风险和机会
6. 生成投资建议
```

**方法 2：思维链分解（Chain-of-Thought, CoT）**

```text
请一步一步思考，把目标分解为可执行步骤。
```

**方法 3：最少到最多提示（Least-to-Most Prompting）**

```text
先分解成子问题，再从最简单的子问题开始逐个解决。
```

**方法 4：递归分解**

```text
大任务 → 子任务 → 子子任务 → ... → 可执行原子操作
```

四种分解策略对比：

| 分解方法 | 怎么做 | 适合 | 风险 |
|---|---|---|---|
| LLM 直接分解 | 一次提示词输出步骤清单 | 结构清晰的任务 | 默认不带依赖信息，需补排序 |
| 思维链（CoT） | “一步一步思考”，边推理边拆 | 推理密集型任务 | 分解藏在推理里，机器难解析 |
| Least-to-Most | 先拆子问题，从最简单开始逐个解决 | 可递归拆解的难题 | 子问题拆错则整链错 |
| 递归分解 | 逐层下钻到原子操作 | 深层嵌套的大目标 | 层数深时上下文膨胀 |

**分解原则**：

- **MECE**：相互独立，完全穷尽。
- **可执行**：每步都能用工具完成。
- **可验证**：每步有明确的完成标准。
- **粒度适中**：太粗无法执行，太细浪费 token。

### 4.5 计划表示

**自然语言**：

```text
1. 先查销售数据
2. 再按地区分析
3. 最后生成报告
```

优点：灵活。缺点：难解析。

**结构化 JSON**：

```json
{
  "goal": "分析销售下降原因",
  "steps": [
    {"id": 1, "action": "load_data", "args": {"file": "sales.csv"}, "depends_on": []},
    {"id": 2, "action": "aggregate", "args": {"by": "month"}, "depends_on": [1]},
    {"id": 3, "action": "aggregate", "args": {"by": "region"}, "depends_on": [1]},
    {"id": 4, "action": "compare", "args": {"metric": "sales"}, "depends_on": [2, 3]},
    {"id": 5, "action": "generate_report", "args": {}, "depends_on": [4]}
  ]
}
```

优点：可解析、可并行、可验证。缺点：需要 Schema 约束。

**DAG（有向无环图）**：

```text
     ┌─→ [2] 按月聚合 ─┐
[1] ─┤                  ├─→ [4] 对比 ─→ [5] 报告
     └─→ [3] 按地区聚合 ┘
```

优点：显式依赖，可并行。缺点：实现复杂。

三种表示对比：

| 表示 | 可解析 | 可并行 | 实现成本 | 适用 |
|---|---|---|---|---|
| 自然语言清单 | 差 | 差 | 低 | 快速原型、给人看 |
| 结构化 JSON | 好 | 好（依赖显式） | 中 | 生产默认 |
| DAG 对象 | 好 | 好（图算法） | 高 | 复杂依赖、多 Agent 分工 |

**工程建议**：

> 生产 Agent 用**结构化计划 + DAG 依赖**，便于并行和恢复。

### 4.6 规划范式

**范式 1：Plan-and-Execute（规划-执行）**

两阶段：Planner（规划器）先拆子任务、明确依赖，生成一份完整计划；Executor（执行器）逐步执行。它针对 ReAct 的两大痛点——长任务**跑偏**（做着做着忘了目标）与**上下文膨胀**（每步重复喂全量历史）。

```text
Plan（一次性规划）→ Execute（逐步执行）
```

流程：

```text
1. 用户给目标
2. LLM 生成完整计划（含依赖）
3. 按计划逐步执行
4. 每步结果反馈
5. 失败或环境变化 → 重新规划
```

优点：结构清晰，可并行，成本可控。缺点：计划可能过时，不适合高度动态环境。

**范式 2：ReAct（推理-行动交替，边想边做）**

```text
Thought → Action → Observation → Thought → ...
```

优点：灵活，适应性强。缺点：短视，容易死循环，难以并行。  
完整 ReAct 循环实现与死循环防护见 2.5，本篇不展开。

**范式 3：ReWOO（Reasoning WithOut Observation，无观察推理）**

按 ReWOO 论文（2023 年提出，IBM 2025 年有官方技术解读）的口径，它把**规划与观察解耦**，由三个模块组成：

```text
Planner：一次性生成全部计划，用占位变量 #E1、#E2… 表示未来的工具输出，
         后续步骤直接引用 #E1；规划阶段不看任何真实观察
Worker ：逐条（或按依赖并行）执行工具调用，把结果填回 #E1、#E2…
Solver ：拿到全部变量值后，一次性综合出最终答案
```

与 Plan-and-Execute 的区别：Plan-and-Execute 每步执行后通常把观察喂回 LLM 再决定下一步；ReWOO 的计划一次成型、批量执行，执行中间不回 LLM。

优点：可并行，token 与 LLM 调用次数大幅降低。缺点：失去中间反馈——步骤 B 真实依赖步骤 A 的实际结果时，规划期的假设可能落空，只能靠重规划兜底；不适合“观察决定分支”的任务。

**面试高频问法**：「ReWOO 为什么省 token？」共识口径：ReAct 每一步都把累积的 Thought/Action/Observation 全量塞回提示词再调一次 LLM，调用次数等于步数、上下文越滚越大；ReWOO 全程只有 Planner 一次加 Solver 一次共两次 LLM 调用，执行中间不调 LLM，提示词也不随执行膨胀，所以 token 显著下降（示意量级见案例 D）。

**范式 4：LLMCompiler（LLM 编译器）**

```text
规划 → 生成 DAG → 并行执行 → 汇总
```

优点：显式依赖，最大化并行。缺点：实现复杂。

**范式 5：Tree of Thoughts（ToT，思维树）**

```text
生成多个候选计划 → 评估 → 选最优 → 展开
```

优点：适合复杂推理。缺点：成本极高。

**面试高频问法**：「ReAct 与 Plan-and-Execute 的核心区别是什么？」共识口径（社区题库，2025）：ReAct 赢在单步灵活性，Plan-and-Execute 赢在长任务不跑偏，Reflection 赢在输出质量（见 2.6）；按任务长度与环境确定性选型，生产常用混合模式。

**范式对比**：

| 范式 | 规划时机 | 并行 | 适应性 | 成本 |
|---|---|---|---|---|
| Plan-and-Execute | 执行前 | 中 | 中 | 中 |
| ReAct | 执行中 | 低 | 高 | 中高 |
| ReWOO | 执行前（与观察解耦） | 高 | 低 | 低 |
| LLMCompiler | 执行前 | 高 | 中 | 中 |
| ToT | 执行前 | 低 | 高 | 极高 |

截至 2026 年，主流编排框架（如 LangGraph）的官方教程仍以 Plan-and-Execute 与 ReAct 为两种基础范式；“规划与观察进一步解耦”（ReWOO 式批量执行）在并发批量任务中的推广属于趋势观察。

### 4.7 重规划（Replanning）

执行中遇到以下情况需要重规划：

- 工具调用失败
- 结果与预期不符
- 发现新信息
- 计划步骤不可行
- 超预算/超时

**重规划触发条件**：

```python
def should_replan(state) -> bool:
    if state.last_error:                                  # 上一步报错
        return True
    if state.steps_executed > state.plan_length * 1.5:    # 实际步数远超计划，计划已失真
        return True
    if state.new_info_changes_goal:                       # 新信息改变了目标前提
        return True
    return False
```

**核心纪律：错误答案通常意味着错误计划**。校验器（Verifier）发现结果不对时，正确动作是回环给 Planner 重新规划，而不是反复重试 Executor——同一个计划重跑十次，错的还是错的（共识口径：Hugging Face Agents Course 认证项目实践与 LangGraph 官方 Plan-and-Execute 教程都强调这个回环）。

**重规划策略**：

| 策略 | 说明 | 代价 |
|---|---|---|
| 局部重规划 | 只改失败的步骤及其后继 | 低，优先用 |
| 全局重规划 | 重新生成整个计划 | 高，目标变更时才用 |
| 回溯 | 回到上一个检查点重跑 | 中（检查点机制见 2.5） |
| 降级 | 用简单方案替代失败步骤 | 低，精度可能受损 |

**分工提示**：重规划“该不该做、怎么改”在本篇；改完后循环怎么继续、状态怎么回滚归 2.5；“哪里错了、为什么错”的反思信号来自 2.6。

### 4.8 规划中的路由（Routing）

不是所有任务都需要完整规划。路由决定“用哪种处理方式”，是规划系统的第一道闸门：

```text
用户输入
   ↓
路由判断
   ├─ 简单任务 → 直接回答
   ├─ 中等任务 → 单步工具调用
   ├─ 复杂任务 → Plan-and-Execute
   └─ 超复杂 → 多 Agent 协作（见 2.8）
```

**路由策略**：

| 档位 | 判据（示意） | 处理方式 | 预期延迟 |
|---|---|---|---|
| simple | 一问一答，无需外部信息 | 直接回答，不进规划 | 秒级 |
| medium | 需要 1-2 次工具调用 | 单步工具调用 | 数秒 |
| complex | 多步且步骤间有依赖 | Plan-and-Execute | 数十秒 |
| very_complex | 跨领域、需分工或大量并行 | 多 Agent 协作（见 2.8） | 分钟级 |

**路由实现**：

```python
ROUTE_PROMPT = """判断以下任务的复杂度：
- simple: 直接回答即可
- medium: 需要 1-2 个工具
- complex: 需要多步规划
- very_complex: 需要多 Agent 协作

任务：{task}
输出：simple / medium / complex / very_complex
"""
```

### 4.9 规划的评估

| 指标 | 含义 |
|---|---|
| 计划可执行率 | 计划中步骤能成功执行的比例 |
| 计划完成率 | 完整完成目标的比例 |
| 步数效率 | 实际步数 / 最优步数 |
| 重规划次数 | 平均重规划次数 |
| 并行度 | 可并行步骤的比例 |
| 成本 | 规划 + 执行的 token 消耗 |
| 延迟 | 端到端时间 |

### 4.10 规划的常见失败

| 失败 | 原因 | 解法 |
|---|---|---|
| 计划太粗 | 分解不够细 | 要求原子步骤 |
| 计划太细 | 过度分解 | 限制步数 |
| 顺序错误 | 依赖没理清 | 用 DAG |
| 不可执行 | 步骤无法用工具完成 | 工具对齐 |
| 死循环 | 重规划无终止 | 最大重规划次数 |
| 跑偏 | 目标理解错 | 目标确认 |
| 成本爆炸 | 步骤太多 | 预算限制 |
| 无法恢复 | 没有检查点 | 状态持久化 |

### 6.1 任务分解提示词模板 + 计划数据结构

```python
DECOMPOSE_PROMPT = """你是一个任务规划器（Planner）。把目标分解为可执行步骤。

要求：
1. 先补全“成功标准”；目标模糊时，列出你做的假设
2. 每步必须能由一个工具完成（原子步骤），并写明验收标准
3. 如实标注 depends_on：本步骤依赖哪些前置步骤的输出
4. 无依赖的步骤会被并行执行
5. 总步数控制在 3-10 步；超出说明应先拆目标

可用工具：{tools}

输出 JSON：
{{"goal": "...", "success_criteria": "...", "steps": [
  {{"id": 1, "action": "...", "tool": "...", "args": {{...}},
    "depends_on": [], "acceptance": "怎样算完成"}}
]}}

目标：{goal}
"""
```

计划数据结构与静态校验：

```python
from dataclasses import dataclass, field

@dataclass
class Step:
    id: int
    action: str                    # 动作描述
    tool: str = ""                 # 绑定的工具名（可执行化的关键）
    args: dict = field(default_factory=dict)
    depends_on: list = field(default_factory=list)   # 前置步骤 id
    acceptance: str = ""           # 验收标准

@dataclass
class Plan:
    goal: str
    success_criteria: str = ""
    steps: list = field(default_factory=list)

def validate_plan(plan: Plan) -> list:
    """静态校验：每步绑定工具、依赖存在、无环。返回错误清单，空列表即通过"""
    errors, ids = [], {s.id for s in plan.steps}
    for s in plan.steps:
        if not s.tool:
            errors.append(f"步骤 {s.id} 未绑定工具")
        for d in s.depends_on:
            if d not in ids:
                errors.append(f"步骤 {s.id} 依赖不存在的步骤 {d}")
    # 拓扑排序：消费不完说明存在环
    indeg = {s.id: len(s.depends_on) for s in plan.steps}
    queue = [i for i, d in indeg.items() if d == 0]
    seen = 0
    while queue:
        cur = queue.pop()
        seen += 1
        for s in plan.steps:
            if cur in s.depends_on:
                indeg[s.id] -= 1
                if indeg[s.id] == 0:
                    queue.append(s.id)
    if seen != len(ids):
        errors.append("计划存在循环依赖")
    return errors
```

### 6.2 Plan-and-Execute 执行引擎

```python
import asyncio
import json
from openai import AsyncOpenAI

client = AsyncOpenAI()  # 密钥从环境变量读取

async def plan(goal: str, tools: list) -> dict:
    """Planner：用 6.1 的模板生成结构化计划"""
    response = await client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user",
                   "content": DECOMPOSE_PROMPT.format(goal=goal, tools=tools)}],
        response_format={"type": "json_object"},
        temperature=0,
    )
    return json.loads(response.choices[0].message.content)

async def execute_plan(plan: dict, tool_map: dict) -> dict:
    """Executor：按依赖分层执行，同层无依赖步骤并行"""
    results, completed = {}, set()

    while len(completed) < len(plan["steps"]):
        # 可执行步骤 = 未完成 且 依赖全部满足
        ready = [s for s in plan["steps"]
                 if s["id"] not in completed
                 and all(d in completed for d in s.get("depends_on", []))]
        if not ready:
            raise RuntimeError("计划存在循环依赖或无法继续")

        # 同层并行执行；未绑定工具的步骤跳过（占位）
        tasks = [tool_map[s["tool"]](**s.get("args", {}))
                 if s.get("tool") in tool_map else asyncio.sleep(0)
                 for s in ready]
        outputs = await asyncio.gather(*tasks, return_exceptions=True)

        for step, output in zip(ready, outputs):
            results[step["id"]] = output
            completed.add(step["id"])

    return results

async def plan_and_execute(goal: str, tool_map: dict) -> dict:
    """两阶段串联：先规划一次，再按依赖执行"""
    plan_data = await plan(goal, list(tool_map.keys()))
    results = await execute_plan(plan_data, tool_map)
    return {"plan": plan_data, "results": results}
```

### 6.3 ReWOO 风格：一次规划 + 占位变量

```python
import re

REWOO_PLANNER_PROMPT = """为目标制定完整计划。你看不到任何工具返回结果，
用 #E1、#E2、… 表示未来的工具输出，后续步骤可直接引用这些变量。

工具：{tools}
目标：{goal}
按行输出计划，格式：序号. 工具名(参数) -> #E编号
"""

async def rewoo_run(goal: str, tool_map: dict) -> str:
    # 1) Planner：一次生成完整计划（此时没有任何观察）
    plan_text = await plan_by_llm(REWOO_PLANNER_PROMPT.format(
        goal=goal, tools=list(tool_map)))
    results = {}

    # 2) Worker：逐条执行工具，把 #E1、#E2 … 替换成真实结果（中间不调 LLM）
    for idx, (tool_name, args_text) in enumerate(parse_plan(plan_text), start=1):
        args_text = re.sub(r"#E(\d+)",
                           lambda m: str(results.get(f"#E{m.group(1)}", "")),
                           args_text)
        results[f"#E{idx}"] = await tool_map[tool_name](**parse_args(args_text))

    # 3) Solver：一次性综合全部证据（全程第 2 次 LLM 调用）
    return await plan_by_llm(
        f"根据计划与全部工具输出，综合回答目标。\n"
        f"计划：{plan_text}\n证据：{json.dumps(results, ensure_ascii=False)}\n目标：{goal}")

# plan_by_llm / parse_plan / parse_args 为 LLM 调用与计划解析封装，实现同 6.2
```

### 6.4 重规划

```python
REPLAN_PROMPT = """原计划执行失败，请重新规划。

原目标：{goal}
原计划：{plan}
已执行步骤及结果：{executed}
失败原因：{error}

注意：错误答案通常意味着错误计划——优先修改计划结构，
而不是原样重复失败步骤；已完成且结果正确的步骤请保留。

请生成新的计划，输出 JSON：
{{"goal": "...", "steps": [...], "reason": "重规划原因"}}
"""

async def replan(goal: str, plan: dict, executed: dict, error: str) -> dict:
    response = await client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": REPLAN_PROMPT.format(
            goal=goal, plan=plan, executed=executed, error=error
        )}],
        response_format={"type": "json_object"},
        temperature=0,
    )
    return json.loads(response.choices[0].message.content)

async def plan_execute_with_replan(goal: str, tool_map: dict, max_replans: int = 3):
    """带重规划的完整循环：失败回环 Planner，最多重规划 max_replans 次"""
    plan_data = await plan(goal, list(tool_map.keys()))

    for attempt in range(max_replans):
        try:
            results = await execute_plan(plan_data, tool_map)
            return {"plan": plan_data, "results": results}
        except Exception as e:
            if attempt == max_replans - 1:
                raise  # 重规划次数用尽，向上抛出
            plan_data = await replan(goal, plan_data, {}, str(e))
```

### 6.5 用 LangGraph 编排规划节点

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict

class PlanState(TypedDict):
    goal: str
    plan: list
    current_step: int
    results: list
    error: str

def planner_node(state: PlanState) -> PlanState:
    # 生成完整计划，Prompt 与数据结构见 6.1
    plan = plan_sync(state["goal"])
    return {**state, "plan": plan["steps"], "current_step": 0}

def executor_node(state: PlanState) -> PlanState:
    step = state["plan"][state["current_step"]]
    result = execute_step(step)
    return {
        **state,
        "results": state["results"] + [result],
        "current_step": state["current_step"] + 1,
    }

def should_continue(state: PlanState) -> str:
    if state.get("error"):
        return "replan"   # 错误答案通常意味着错误计划 → 回环 Planner
    if state["current_step"] >= len(state["plan"]):
        return "end"
    return "execute"

# replan_node 实现见 6.4；检查点与中断恢复等状态机细节见 2.5
graph = StateGraph(PlanState)
graph.add_node("planner", planner_node)
graph.add_node("executor", executor_node)
graph.add_node("replan", replan_node)
graph.set_entry_point("planner")
graph.add_edge("planner", "executor")
graph.add_conditional_edges("executor", should_continue, {
    "execute": "executor",
    "replan": "replan",
    "end": END,
})
graph.add_edge("replan", "executor")

app = graph.compile()
```

## 7. 案例

### 案例 A：研究报告 Agent（Plan-and-Execute + 并行）

**目标**：“调研 2024 年新能源汽车市场，输出报告。”

**做法**（Plan-and-Execute）：

```text
Plan:
1. 搜索行业报告
2. 提取关键数据（销量、增长率、市场份额）
3. 搜索主要厂商动态
4. 搜索政策变化
5. 整合分析
6. 生成报告

Execute:
1 → 2 → (3, 4 并行) → 5 → 6
```

**示意效果**：步骤 3、4 无依赖，并行执行，端到端时间约缩短 40%；计划先展示给用户确认，报告结构返工从平均 2 轮降到 0-1 轮。

### 案例 B：数据分析 Agent 重规划

**目标**：“分析销售下降原因。”

**原计划**：

```text
1. 读取 sales.csv
2. 按月聚合
3. 按地区聚合
4. 对比
```

**执行到步骤 1 失败**：文件不存在。

**重规划**（校验失败回环给 Planner，而不是原地重试同一个读取）：

```text
1. 列出数据目录，找到实际文件名
2. 读取文件
3. 按月聚合
4. 按地区聚合
5. 对比
```

**示意效果**：自动恢复，无需人工干预；本次重规划 1 次、新增 1 个探测步骤，恢复耗时约 10 秒。若只做重试，同一错误会重复 3 次后以失败告终。

### 案例 C：路由避免过度规划

**输入**：“今天天气怎么样？”

**路由判断**：simple（单事实问答，无需多步外部信息）。  
**处理**：直接调用天气工具，不做完整规划。  
**示意效果**：延迟从约 5 秒降到 1 秒，token 成本降低约 80%——对简单任务而言，Planner 的一次完整调用纯属浪费。

### 案例 D：同一任务，ReWOO 与 ReAct 的成本对比

**任务**：“查三家候选供应商的公开报价，汇总成比价表。”（3 路独立查询 + 1 次汇总）

**ReAct**：每步把全量历史塞回提示词，6 次 LLM 调用，累计约 12k token（示意）。  
**ReWOO**：Planner 一次加 Solver 一次共 2 次调用，3 路查询并行，累计约 3k token（示意）。  
**示意效果**：token 约降 75%，端到端延迟约降 60%（并行收益）。代价：若某一路查询返回空，ReWOO 不能当场改道，只能整体重规划一次；ReAct 可即时调整。这正是 4.6 对比表中“适应性低”的含义。

## 8. 常见坑

1. **所有任务都做完整规划**。简单任务直接回答即可——先路由，再决定是否规划，否则延迟和成本白涨。
2. **计划太粗**。“分析数据”不是可执行步骤——细到“读取 CSV、计算均值”，用验收标准倒逼粒度。
3. **计划太细**。50 个步骤 token 爆炸且容易出错——控制在 3-10 步，超出先拆目标。
4. **忽略依赖关系**。不标 depends_on，顺序错误或无法并行——生成计划后先跑静态校验（依赖存在、无环）。
5. **不做重规划**。一步失败整个任务失败——把重规划作为默认路径，而不是异常分支。
6. **重规划无终止**。无限重规划，成本失控——设最大重规划次数（如 3 次）与总预算熔断。
7. **校验失败只会重试执行**。错误答案通常意味着错误计划——校验不过要回环给 Planner，而不是反复重跑 Executor。
8. **规划与工具不匹配**。计划里的步骤没有对应工具，无法执行——把工具清单喂给 Planner，生成后校验工具名。
9. **不做目标确认**。目标理解错，计划全错——四步法第一步先澄清范围、约束、成功标准。
10. **忽略并行机会**。可并行的步骤串行执行，延迟高——依赖排序后同层步骤并行。
11. **计划不持久化**。中断后无法恢复，只能重新规划——计划与已完成步骤落盘（检查点见 2.5）。
12. **不评估计划质量**。不知道计划好不好，无法优化——统计可执行率、完成率、步数效率并做回归。
13. **过早用 ToT**。树搜索成本极高，普通任务用不上——只有单路径规划反复失败时才考虑。

## 10. 小结

- 规划 = 目标澄清 + 任务分解 + 依赖排序 + 可执行化 + 动态调整；四步法就是“模糊目标拆成可执行步骤”的正面答案。
- 三个时机：执行前规划、执行中规划、执行后重规划。
- 主流范式：Plan-and-Execute（长任务防跑偏）、ReAct（单步灵活）、ReWOO（规划与观察解耦、省 token）、LLMCompiler（DAG 并行）、ToT（多候选计划）。
- ReWOO 省 token 的根因：Planner 与 Solver 各一次调用、执行中间不调 LLM、提示词不随执行膨胀。
- 重规划纪律：错误答案通常意味着错误计划——校验失败回环给 Planner，并设最大重规划次数。
- 路由先行：简单任务不规划，复杂任务才规划；能用固定工作流解决的不上自由规划（与 2.1 的 Agent/工作流边界一脉相承）。
- 计划表示：自然语言 → 结构化 JSON → DAG；生产用结构化计划 + 显式依赖。
- 关键工程件：依赖校验、并行执行、重规划终止、预算限制、计划持久化。
- 这些能力直接支撑：2.5 执行循环与状态机、2.6 反思。
