## 1. 定位

L3 工程层第 7 个知识点，回答大纲里的关键问题：**如何平衡效果、成本、延迟？**

它的依赖链清晰：0.4c（Self-Attention 与 QKV）解释了为什么生成每个字都要「重看全文」；3.6（部署与扩展）给了把算力用满的引擎；本篇回答经济侧的三件事——**为什么慢（机理）、怎么量化（黄金信号）、怎么降（四板斧）**。

向后支撑：3.4（可观测性，黄金信号是其中推理指标的特化）、4.9（部署与运维，黄金信号演化为告警清单）、4.4（浏览器 Agent，步级成本累积问题）。与 1.1c（采样参数）的关系：max_tokens、温度等参数在本篇的账本里直接变现为成本数字。

## 2. 一句话定义

LLM 推理是自回归（Autoregressive）逐字接龙：每写一个 token 都要把前面全部内容重新看一遍——这决定了它越长越慢、越贵；工程上的全部努力（KV Cache、PagedAttention、缓存、路由、压缩、批处理）都是在给这笔「逐字税」打折，而黄金信号（TTFT、每 token 延迟、单请求成本、缓存命中率）负责证明折扣真的生效。

## 3. 为什么需要

三个真实的痛：

1. **慢是生成方式决定的**。用户粘贴 2 万字文档要等 8 秒才见第一个字，长回答后半段肉眼可见变慢——不理解机理的团队会去「优化网络」，方向全错。
2. **贵是慢的镜像**。占用算力的时间就是钱：输入长、输出长、重复算，三样都直接写进账单。不加约束的 Agent 循环一个月能烧出七位数账单（见第 7 节案例）。
3. **没有信号就没有管理**。成本与延迟不进看板，优化就是盲调：降了 30% 成本还是劣化了 20% 质量都发现不了。

Demo 与生产的分界线，就是这组数字是否存在、是否被看。

## 4. 核心原理

### 4.1 推理两阶段与逐字税

推理分两段，瓶颈完全不同：

| 维度 | Prefill（预填充） | Decode（解码） |
|---|---|---|
| 做什么 | 整段通读输入，算出第一个 token | 逐个生成后续 token |
| 计算特征 | 一次大批量矩阵乘，compute-bound | 每步一个 token，memory-bandwidth-bound |
| 决定什么 | TTFT（Time To First Token，首 token 时间） | TPOT（Time Per Output Token，每 token 延迟） |
| 输入越长 | 首字等待越久（烧开水） | 背包越重，每步越慢 |
| 输出越长 | 不影响 | 总耗时 = TPOT × 输出长度，线性涨 |

「逐字税」的机理：自回归每生成一个 token，都要对全部已有序列做注意力（0.4c 的 QKV 计算）——没有缓存时，写第 N 个 token 要重算前 N-1 个 token 的 K/V，单步 O(n)、整段 O(n²)。写 500 字的回答，等于把前 499 字重读了 500 遍。这不是 bug，是生成方式的固有代价。

用户体感拆解：**长问题卡在等首字（prefill 通读），长回答卡在越写越慢（decode 背包变重）**。产品抱怨「转圈 8 秒像坏了」，基本都花在首字之前。

### 4.2 KV Cache：以显存换速度

KV Cache 把历史 token 的 Key/Value 矩阵缓存下来，每步生成只算新 token 的 Q/K/V，注意力直接读缓存对历史做加权——把「每步重抄全书」变成「翻笔记」，decode 提速数量级。

三个高频细节：

- **缓存的是 K 和 V 两份，Q 不缓存**：当前步的 Q 只对自己有用，历史 Q 不再参与计算。
- **显存公式**：KV 大小 = 2 × 层数 × KV头数 × head_dim × 序列长 × 精度字节 × 并发。7B MHA（32 层、32 头、128 维）fp16 下每 token 约 512 KB，4K 上下文单路 2.1 GB。
- **代价是显存**：长上下文大并发下 KV 轻松反超权重——所以 KV 的结构压缩（MQA 全头共享、GQA 分组共享、MLA 低秩潜压缩）与数值压缩（KV fp8/int8）是模型选型时的成本科目。

### 4.3 PagedAttention：消灭碎片

KV Cache 本身有管理问题：传统做法按最大长度预留连续显存——请求来了预租一整层楼，实际只住一半房间，空房不能给别人（内部碎片）；分配多了还不连续（外部碎片）；利用率常低于 40%。

PagedAttention（vLLM 核心）借鉴操作系统虚拟内存：把 KV Cache 切成固定大小的 block（钟点房），按需分配、逻辑连续物理离散（映射表）、退房立刻转新客，Copy-on-Write 支持并行采样共享。利用率提到 90% 以上，同卡并发翻数倍，吞吐提升 2~4 倍。附赠能力是前缀缓存（Prefix Caching）：相同前缀的请求共享物理块，长系统提示只存一份。

### 4.4 黄金信号

四个信号分列盯住延迟、成本、效率三条线，任何一个失守都代表系统性问题：

| 信号 | 定义 | 健康参考 | 异常意味着 |
|---|---|---|---|
| TTFT | 请求发出到首 token 的延迟 | 在线对话 1~2 秒内（长输入按 prefill 速率另算） | prefill 瓶颈 / 输入失控 / 队列堆积 |
| 每 token 延迟（TPOT，按 token 分列看分布） | 生成阶段每个 token 的平均与 P99 耗时 | 数十毫秒级；后段不应显著劣化 | 显存带宽打满 / KV 过长 / batch 过大 |
| 单请求成本 | （输入 token 单价×输入 + 输出单价×输出）/ 每次调用，自建按卡时折算 | 按业务设预算上限并告警 | Agent 循环失控 / 重复调用 / 路由失误 |
| 缓存命中率 | 命中前缀/语义缓存的请求占比 | 客服 FAQ 类 30%~50%，开放创作类低属正常 | 前缀没归一 / 缓存键设计错误 / 该缓存没缓存 |

可靠性侧再加两条配套：超时与重试策略（指数退避，防雪崩）、降级路径（换小模型 / 排队提示）。这些信号的采集与 Trace 关联在 3.4 展开，告警阈值设计在 4.9。

### 4.5 降本四板斧

| 板斧 | 原理 | 典型降幅 | 陷阱 |
|---|---|---|---|
| 缓存（前缀 + 语义） | 相同/相似请求不重算：前缀缓存共享系统提示计算；语义缓存按向量相似度直接返回历史答案 | 总成本的 15%~40%（取决于命中率） | 陈旧答案、相似但不同质的问题被错答——要阈值 + 时效 + 兜底 |
| 模型路由 | 意图分类分流：简单任务到 7B 级小模型（成本约 1/10），复杂任务才走大模型 | 40%~60%（简单请求占大头时） | 路由错误伤质量——必须配置信度评估与 cascade 兜底（低置信升级大模型） |
| 上下文压缩 | 历史摘要替代全文、滑窗截断、提示词精简、输出 max_tokens 上限 | token 量降 20%~40% | 压掉关键信息导致回答退化——压缩比要配质量回归 |
| 批处理 | 非实时任务转 Batch API 约 5 折；自建推理用连续批处理填满 GPU | 该部分成本减半 | 只适用于离线任务；在线对话硬凑大 batch 会拖垮 TTFT |

组合拳通常省 50%~80%。铁律：**每斧都要过质量关**——golden set 回归 + 灰度对比，成本与质量双指标看板同屏看，只报省钱不报质量的优化都是埋雷。

## 5. 架构 / 流程

一次请求的延迟分解与全链路降本流水线：

```text
【延迟分解：一次请求的时间都花在哪】

用户请求 ──→ [网络+排队] ──→ [Prefill 通读输入] ──→ [Decode 逐字生成] ──→ 完成
                │                    │                     │
             限流/负载均衡      决定 TTFT              决定 TPOT×输出长度
             （队列堆积会       输入越长越久            KV Cache 在这里生效：
              毁掉 TTFT）       前缀缓存可跳过          历史只算一次，之后读缓存
                                                       PagedAttention 让并发塞得下

【全链路成本优化流水线：请求先过四道闸，能省则省】

  请求
   ↓
① 缓存闸：精确缓存？→ 语义缓存命中？──是──→ 直接返回（成本≈0）
   ↓ 未命中
② 路由闸：意图分类/复杂度评估 ──简单──→ 小模型（成本 1/10）
   ↓ 复杂                            └─低置信─→ 升级大模型（cascade 兜底）
   ↓
③ 压缩闸：历史摘要 / 滑窗 / 提示精简 / 输出上限
   ↓
④ 批处理闸：实时？──否──→ Batch API 队列（半价，24h 内）
   ↓ 实时
   调用大模型 ──→ 双指标看板（成本 + 质量）──→ 回归与灰度验证
```

## 6. 代码 / 工具

### 6.1 KV Cache 演算脚本

```python
"""KV Cache 演算：公式、单路占用、并发总账、以及三层压缩后的对比。"""

def kv_bytes(num_layers, kv_heads, head_dim, seq_len, bytes_per=2, batch=1):
    """2 份（K 与 V）× 层数 × KV 头数 × head_dim × 序列长 × 字节 × 并发。"""
    return 2 * num_layers * kv_heads * head_dim * seq_len * bytes_per * batch


GB = 1024**3

# 基线：7B MHA（32 层、32 KV 头、128 维），fp16，4K 上下文
base = kv_bytes(32, 32, 128, 4096)
print(f"MHA fp16  4K 单路 KV：{base / GB:.2f} GB")          # ≈ 2.15 GB
print(f"16 路并发合计     ：{kv_bytes(32, 32, 128, 4096, batch=16) / GB:.1f} GB")
print(f"对比：7B fp16 权重 14 GB —— 长上下文多并发下 KV 反超权重\n")

# 三层压缩对比
variants = [
    ("GQA（8 组 KV 头，LLaMA-2/3 系）", dict(kv_heads=8)),
    ("KV 量化 fp8（字节减半）",          dict(bytes_per=1)),
    ("GQA + fp8 叠加",                  dict(kv_heads=8, bytes_per=1)),
    ("GQA + fp8 + 滑窗截到 1K 上下文",   dict(kv_heads=8, bytes_per=1, seq_len=1024)),
]
for name, kw in variants:
    size = kv_bytes(32, kw.get("kv_heads", 32), 128,
                    kw.get("seq_len", 4096), kw.get("bytes_per", 2), 16)
    print(f"{name:32s}：{size / GB:6.2f} GB（基线的 {size / (kv_bytes(32, 32, 128, 4096, batch=16)):.1%}）")

# decode 阶段的算力账：为什么缓存能加速数量级
n = 4096
no_cache_flops = sum(2 * i for i in range(1, n + 1))        # 无缓存：每步重算全部历史
with_cache_flops = 2 * n                                     # 有缓存：每步只算新 token
print(f"\n4K 序列注意力重算量对比：无缓存 {no_cache_flops / 1e9:.1f} GFLOPs vs 有缓存 {with_cache_flops / 1e6:.1f} MFLOPs"
      f"（约 {no_cache_flops / with_cache_flops:.0f} 倍差距）")
```

### 6.2 单请求与月度成本核算脚本

```python
"""成本核算：单请求成本公式、月账单推演、四板斧各自砍掉多少。"""

def request_cost(prompt_tokens, completion_tokens, in_price, out_price):
    """API 计费：输入输出分列单价（$/1M token）。自建推理按 卡时成本/卡时吞吐 折算。"""
    return prompt_tokens / 1e6 * in_price + completion_tokens / 1e6 * out_price

def monthly_bill(qps_avg, prompt_tokens, completion_tokens,
                 in_price, out_price, days=30):
    per_req = request_cost(prompt_tokens, completion_tokens, in_price, out_price)
    return per_req * qps_avg * 86400 * days

# 基线：Agent 应用，每次调用 16K 输入 + 2K 输出，白天均值 2 QPS
# 单价取主流旗舰模型量级（$/1M）：输入 3、输出 15；小模型约 1/20：输入 0.15、输出 0.6
IN, OUT = 3, 15
base = monthly_bill(2, 16384, 2048, IN, OUT)
big_base = base                       # 大模型承担 100% 流量
print(f"基线月账单：${base:,.0f}")

# 板斧一：模型路由——70% 简单请求走小模型，30% 留在大模型
big = 0.3 * big_base
small = 0.7 * monthly_bill(2, 16384, 2048, 0.15, 0.6)
routed = big + small
print(f"路由后    ：${routed:,.0f}（省 {1 - routed / base:.0%}）")

# 板斧二：语义缓存——大模型请求中 35% 直接命中（成本≈0，仅缓存服务费按 5% 计）
big = big * (1 - 0.35) + big * 0.35 * 0.05
cached = big + small
print(f"加缓存后  ：${cached:,.0f}（相对基线省 {1 - cached / base:.0%}）")

# 板斧三：上下文压缩——历史摘要把输入 16K 砍到 8K（大小模型同降）
big = 0.3 * monthly_bill(2, 8192, 2048, IN, OUT) * (1 - 0.35 + 0.35 * 0.05)
small = 0.7 * monthly_bill(2, 8192, 2048, 0.15, 0.6)
compressed = big + small
print(f"加压缩后  ：${compressed:,.0f}（相对基线省 {1 - compressed / base:.0%}）")

# 板斧四：20% 流量是离线任务，转 Batch API 半价
final = compressed * (1 - 0.2 * 0.5)
print(f"加批处理  ：${final:,.0f}（总降幅 {1 - final / base:.0%}）")
# 典型输出：总降幅 80% 以上（路由 -67% → 缓存 -77% → 压缩 -84% → 批处理 -86%）。
# 每一步都要配 golden set 回归——省下的钱不能从质量里扣。
```

## 7. 案例

### 案例 A：$2M 账单降 60% 的复盘框架

**场景**：一家 SaaS 公司的 Agent 产品月账单冲到 200 万美元量级，被财务叫停。复盘按固定框架走：

1. **解剖账单**：拉 Trace 按「调用方 × 场景 × 模型档位」三维透视。典型发现：大模型占成本 90% 以上；输入 token 占单请求成本大头（长系统提示 + 全量历史每轮重发）；30% 以上请求高度重复；部分 Agent 循环无输出上限，单次任务生成 10 万 token。
2. **止血（当天）**：max_tokens 硬上限、按用户日预算熔断、循环步数上限——先止失控，不谈优化。
3. **四板斧（两周）**：意图路由把 65% 简单请求切到小模型；语义缓存吃掉 30% 重复请求；历史摘要把输入砍 40%；评测与质检跑批全部转 Batch 半价。
4. **质量护栏**：每项上线过 golden set 回归与 5% 灰度，解决率与满意度双指标不劣化才算数。

**效果**：总降幅约 60%（账单 $2M 量级降到 $0.8M 量级），质量指标持平。框架的价值在于可复用：任何团队的账单优化都走「解剖—止血—四板斧—护栏」四步，而不是从「换个便宜模型」开始。

### 案例 B：客服 AI 月账单降一半

**场景**：客服 AI 月账单 50 万元，要求降一半且质量不降。

**方案**：先 Trace 定位——大模型占 90%、重复率高。语义缓存（向量相似 + 7 天时效 + 置信阈值防错答）命中 30~40%，省 15~20 万；意图分流让 FAQ 与物流查询等 60% 简单请求走微调 7B，再省 10~15 万；系统提示精简 + 前缀缓存 + 历史摘要把输入 token 砍 30%；质检回放转 Batch。

**效果**：总降幅 50%~65%，解决率与满意度持平。语义缓存的置信兜底（低置信回大模型）是质量不塌的关键。

### 案例 C：长文档总结的 8 秒首字

**场景**：产品抱怨「AI 总结粘贴长文档后转圈 8 秒才出第一个字，用户以为坏了」。

**诊断**：8 秒基本全花在 prefill——长文档要整段通读才能出首字，输入越长水烧得越久。

**立刻能做的**：流式进度反馈（「正在阅读文档…已读取 60%」，内容没出但焦虑消失）；分段摘要再汇总（每段千字分别总结，每段首字等待都短）。**长期**：如果用户只关心文档里的几个点，检索相关段落替代全文投喂，输入 token 与延迟同降。

**效果**：感知首响从 8 秒降到 1 秒级（流式反馈），实际总耗时降约 30%（分段路径）。

## 8. 常见坑

1. **把慢归因于网络或机器**。机理是逐字接龙：长输入卡 prefill、长输出卡 decode，先分阶段定位再动手。
2. **只看平均延迟不看分位**。用户投诉来自 P99；TTFT 与 TPOT 必须分列看分布。
3. **输出长度不加上限**。总耗时 = TPOT × 输出长度，没有 max_tokens 上限的 Agent 循环就是无底洞。
4. **历史全量重发**。多轮对话把全部历史每轮重发，输入成本线性爆炸；用摘要、滑窗或增量式上下文管理。
5. **以为缓存只有精确匹配**。前缀缓存（引擎层共享）与语义缓存（应用层相似命中）是两件事，长系统提示场景前缀缓存是白捡的收益。
6. **语义缓存不设时效与阈值**。相似但不同质的问题命中陈旧答案，比不缓存更糟：阈值 + 时效 + 低置信兜底三件套缺一不可。
7. **路由没有兜底**。小模型答不了的硬答，质量塌方；cascade（低置信升级大模型）是路由的标配而非可选项。
8. **在线对话硬凑大 batch**。批越大吞吐越高但单请求延迟越涨，TTFT 先崩；在线与离线要分开定 batch 策略。
9. **自建推理不算卡时账**。自建成本 = 卡时成本 ÷ 有效吞吐，引擎选型（3.6）直接决定分母，别拿 API 单价直接比。
10. **降本不看质量**。只报省钱不报质量回归的优化，等于把成本转嫁给用户投诉。
11. **KV Cache 概念混淆**。缓存的是 K 和 V 两份，Q 不缓存；「为什么能加速」要答「免重算历史 K/V」，不是「压缩了权重」。
12. **长回答后半段变慢当成 bug 排查**。这是 decode 背包变重的固有现象，优化方向是压缩上下文与 KV，不是查服务器。
13. **预算护栏后置**。账单失控后才想熔断；预算阈值告警与用户级配额是上线第一天的配置。
14. **把 Batch API 用于实时任务**。Batch 是离线半价通道，24 小时返回，塞实时需求是事故。

## 10. 小结

- 推理慢是生成方式决定的：**自回归逐字接龙，单步 O(n)、整段 O(n²)**；长问题卡 TTFT，长回答卡 TPOT。
- 两阶段瓶颈不同：**prefill 是 compute-bound，decode 是 memory-bandwidth-bound**——优化手段要分开选。
- KV Cache：**缓存历史 K/V（Q 不缓存）免重算**，显存换速度；公式 2×层数×KV头数×head_dim×序列长×字节×并发，长上下文下反超权重。
- PagedAttention：**分页 block + 按需分配 + 逻辑物理映射**，利用率 40% 以下提到 90%+，同卡吞吐翻数倍；附赠前缀缓存共享。
- 黄金信号四件套：**TTFT、TPOT（按 token 分列）、单请求成本、缓存命中率**——没有信号就没有管理。
- 降本四板斧：**缓存（前缀+语义）、模型路由（配 cascade 兜底）、上下文压缩、批处理**，组合通常省 50%~80%。
- 铁律：**每斧过质量关**——golden set 回归 + 灰度 + 成本质量双指标看板。
- $2M 账单复盘框架：**解剖账单 → 止失控（上限/熔断）→ 四板斧 → 质量护栏**，顺序不可乱。
- 体感优化有时比性能优化便宜：流式输出与进度反馈把 8 秒焦虑变成 1 秒安心。
- 这些能力向后支撑：3.4 的 Trace 体系、4.9 的黄金信号告警、4.4 的步级成本控制。
