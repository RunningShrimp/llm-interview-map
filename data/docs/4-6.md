# 讲解 4.6 多 Agent 协作系统

> 说明：2.8 讲了多 Agent 的角色分工与通信，2.8b 回答了「何时真的优于单 Agent」并给出三条件与约 15× token 的账；4.6 把这套团队论搬上真实项目，以研究/写作团队为主案例走完全流程。  
> 系统化之后如何注册、发现、治理多个 Agent，是 4.7 平台架构的主题。

---

## 1. 定位

L4 应用层第 6 个锚点，回答一个工程问题：**确定要多 Agent 之后，怎么把研究、写作这类真实任务组织出质量，又管住 token 账单和失败风险？**

前置依赖：2.8b（三条件判据、15× token、单 Agent 优先的反方论证）——本篇默认读者已接受「能单则单」的前提，只讨论拆了之后怎么做好。2.8（角色分工、通信与监督）提供角色与通信的词汇表。  
后续去向：4.7 把「一个团队」升级为「一个平台」——注册发现、权限审计、灰度发布；4.8 的红队会专门攻击多 Agent 间的注入传播。

## 2. 一句话定义

多 Agent 协作系统是把一个任务拆给多个角色化、带独立上下文的 Agent，由主管（Orchestrator）拆单、并行执行、汇总成稿、评审修订后交付的系统；配套 token 预算封顶与失败兜底，用组织成本（约 15× token）换取并行速度、上下文隔离与专业深度。

## 3. 为什么需要

单 Agent 做深度研究或长文写作时的三个硬伤：

| 单 Agent 的问题 | 机制 | 多 Agent 的对应解法 |
|---|---|---|
| 上下文污染 | 检索中间噪音、草稿旧版本全部挤进同一窗口，后期推理质量下降 | 每个 Agent 独立上下文，只装自己任务需要的 |
| 串行慢 | 三个子课题依次查，墙钟时间 = 三段之和 | 并行执行，墙钟 ≈ 最慢一段 |
| 角色串扰 | 同一窗口既当检索员又当编辑，提示词互相稀释 | 专职专职：检索 Agent、评审 Agent 各自提示词干净 |

代价同样清楚（2.8b 的账）：Anthropic 公开过其多 Agent 研究系统的工程经验——多 Agent 系统耗 token 约为单 Agent 聊天的 **15 倍**量级。买来的是并行与隔离，卖掉的是成本与简单。

**所以判断永远先行：三条件是否成立。** 条件不成立，本篇所有工程技巧都是在给错误的架构烧钱。

## 4. 核心原理

### 4.1 三条件：什么任务值得上多 Agent

| 条件 | 含义 | 研究任务上的体现 |
|---|---|---|
| 任务可分解 | 能拆成互不依赖的子任务 | 市场规模 / 主要玩家 / 定价策略，三问独立 |
| 读多写少 | 子任务大量读外部信息，几乎不写共享状态 | 各查各的资料，不抢着改同一份稿 |
| 上下文可隔离 | 子任务的中间过程不需要全局可见 | 检索的原始页面噪音不必进主稿窗口 |

三条都成立才拆。深度研究、多源报告生成、大规模代码库并行调查是典型命中区；需要共享可变状态、强顺序依赖的任务（多轮谈判、状态机类交易流程）不命中。

### 4.2 15× token：钱花在哪、何时值

Anthropic 的多 Agent 研究系统经验里，token 消耗结构大致是：

```text
主管拆单（少量）＋ 3 个子 Agent 并行检索（大头，原始页面反复进出上下文）
＋ 汇总（中等）＋ 评审（中等）＋ 修订（少量） ≈ 单 Agent 直答的 15 倍量级 token
```

值不值的判据：

| 任务 | token 量级 | 15× 值不值 |
|---|---|---|
| 「X 是什么」事实问答 | 小 | 不值，单 Agent 直答 |
| 深度研究/尽调报告 | 大，且价值密度高 | 值：并行省时间、隔离提质量 |
| 简单摘要改写 | 小 | 不值，直接给 LLM |
| 关键决策的多视角论证 | 中 | 值：错误成本远高于 token 成本 |

工程结论：**15× 不是劝退指标，是定价指标**——任务价值密度高、时间敏感、错误代价大时才付这个价，并且用预算封顶把 15× 压成可控的 10×。

### 4.3 结构化通信：任务书与结果卡

Agent 之间不传「自由对话」，传结构化消息。任务书四件套：

| 字段 | 作用 |
|---|---|
| objective | 目标一句话，防跑偏 |
| questions | 问题清单，框定检索范围 |
| output_format | 交付格式（Markdown 结构 / JSON schema），汇总才能拼 |
| budget | token 上限，接近即收敛，超限熔断 |

结果卡与之对称：结论列表（每条带来源 URL 与引文）、覆盖情况（哪些问题没查到）、消耗 token 数。**汇总即验收**：主管按任务书逐项核对结果卡，没来源的结论退回，不带病拼稿。

### 4.4 研究团队五步流程

```text
① 主管拆单 → ② 子 Agent 并行检索 → ③ 汇总成稿 → ④ 评审 → ⑤ 修订交付
```

细节在 5 节展开。两个非显然要点：

- **并行的授权来自条件二**：只读外部资料、不写共享状态，才敢同时开三路；一切写入共享稿件的环节收口给主管。
- **评审是独立 Agent 而不是主管兼职**：评审提示词只对「事实、来源、覆盖度」负责，与「赶进度」的主管视角天然制衡。

### 4.5 token 预算控制

三层护栏：

| 层 | 机制 | 动作 |
|---|---|---|
| 任务级 | 任务书写明 budget（如 12000 token） | 达到 80% 收敛输出，100% 强制收尾 |
| 编排级 | 全局总预算 + 已消耗计数器 | 总量耗尽停止派新单，只做汇总交付 |
| 策略级 | 模型分级路由 | 子 Agent 检索用小模型，主管/评审用强模型 |

预算必须随任务书下发并在结果卡回收，主管才知道每一单的性价比，下一轮拆单可以据此调整份数与预算分配。

### 4.6 失败兜底

| 失败 | 表现 | 兜底策略 |
|---|---|---|
| 子任务超时 | 截止时间内未交件 | 降级：收部分结果，终稿标注缺口 |
| 子任务失败 | 报错 / 输出非法 | 有限次重派（换提示词或换模型）；仍败则跳过并标注 |
| 预算耗尽 | 全局预算触顶 | 熔断：停止派单，用已有材料收工 |
| 主管失败 | 单点故障 | 主管状态外置（黑板），可重建后续跑 |

原则与 4.5 的死信队列同源：**绝不无限等待，绝不静默丢失，缺什么就明说**。「部分结果 + 缺口标注」交付给用户，好过卡死或假装完整。

### 4.7 单 vs 多 Agent 对比实验设计

决定是否多 Agent 化，靠对照实验不靠感觉：

1. **固定测试集**：20-50 个真实任务（研究问题、报告题目），冻结不变。
2. **两个被试**：同一模型底座；单 Agent（一份长提示词 + 全部工具）vs 多 Agent（主管 + N 子 Agent）。
3. **控制变量**：同样的外部资料源、同样的输出格式要求、同样的评审标准（用独立评审 Agent 或人评双盲）。
4. **记录四类指标**：质量分（事实正确率、来源覆盖率、完整性）、墙钟时间、token 总消耗、失败率/需人工干预率。
5. **决策规则事先写死**：例如「质量提升 ≥ 15% 且预算可承受 10× token，才采用多 Agent」。

典型结果形态：简单任务上多 Agent 质量持平但 token 翻一个数量级；复杂任务上质量显著领先且时间减半。结论按任务分桶，不要追求全局唯一答案。

## 5. 架构 / 流程

研究团队一次完整运行（预算刻度示意，总预算 40000 token）：

```text
课题：调研 A 市场竞争格局
│
▼
① 主管拆单（消耗 ~3%，强模型）
│   写三份任务书：
│   T1 市场规模（budget 12000）
│   T2 主要玩家（budget 12000）
│   T3 定价策略（budget 12000）
│   全局预算池扣减登记
│
▼
② 子 Agent 并行检索（消耗 ~45%，小模型）
│   T1 ─┐
│   T2 ─┼─ 三个独立上下文，只读外部资料
│   T3 ─┘   各自记录来源 URL + 引文
│   [超时哨兵] T3 到点未交 → 部分结果 + 缺口标注
│
▼
③ 主管汇总成稿（消耗 ~25%）
│   按任务书格式逐张验收结果卡
│   无来源结论退回，不带病拼稿
│
▼
④ 评审 Agent 核查（消耗 ~12%，强模型）
│   逐条核对：结论有来源？数字一致？三问覆盖全？
│   产出问题清单：如「玩家 B 份额无来源」「T3 缺口未在稿中标注」
│
▼
⑤ 修订交付（消耗 ~15%）
    评审意见回流对应子 Agent 补查（受剩余预算约束）
    主管合成终稿 + 缺口声明 + 消耗账单
```

## 6. 代码 / 工具

### 6.1 多 Agent 编排骨架（任务书 + 并行 + 预算 + 兜底）

```python
import time, concurrent.futures as cf
from dataclasses import dataclass, field, asdict

@dataclass
class TaskCard:                      # 任务书：结构化通信的核心
    id: str
    objective: str
    questions: list[str]
    output_format: str
    budget: int                      # token 上限，超限熔断
    timeout_s: float = 60.0

@dataclass
class ResultCard:                    # 结果卡：与任务书对称回收
    task_id: str
    findings: list[dict]             # [{claim, source, quote}]
    gaps: list[str] = field(default_factory=list)   # 没查到的要明说
    tokens_used: int = 0
    status: str = "ok"               # ok / degraded / failed
    error: str | None = None

class Orchestrator:
    def __init__(self, worker_fn, global_budget: int = 40000):
        self.worker_fn = worker_fn   # 子 Agent：模型+工具的组合
        self.global_budget = global_budget
        self.spent = 0

    def _guard(self, card: TaskCard, remaining: int) -> TaskCard:
        # 预算收敛：子任务预算不超过全局剩余，触顶只降不升
        card.budget = min(card.budget, remaining)
        return card

    def run(self, cards: list[TaskCard]) -> list[ResultCard]:
        results = []
        with cf.ThreadPoolExecutor(max_workers=len(cards)) as pool:   # 条件二成立才敢并行
            futs = {pool.submit(self.worker_fn, self._guard(c, self.global_budget - self.spent)): c
                    for c in cards}
            for fut, card in futs.items():
                try:
                    res = fut.result(timeout=card.timeout_s)          # 超时哨兵
                    self.spent += res.tokens_used
                except cf.TimeoutError:
                    res = ResultCard(card.id, findings=[], gaps=[card.objective + " 超时未完成"],
                                     status="degraded", error="timeout")   # 降级不阻塞
                except Exception as e:
                    res = ResultCard(card.id, findings=[], gaps=["执行失败，缺口见任务书"],
                                     status="failed", error=str(e))
                results.append(res)
        return results

def worker(card: TaskCard) -> ResultCard:      # 真实实现里调用 LLM + 检索工具
    time.sleep(2)                              # 模拟检索耗时
    return ResultCard(card.id,
        findings=[{"claim": "市场规模约 80 亿", "source": "https://r/1", "quote": "..."}],
        gaps=["细分定价数据无公开来源"],
        tokens_used=9000)

orch = Orchestrator(worker_fn=worker, global_budget=40000)
cards = [TaskCard("T1", "市场规模", ["总量?增速?"], "markdown", 12000),
         TaskCard("T2", "主要玩家", ["份额前五?"], "markdown", 12000),
         TaskCard("T3", "定价策略", ["定价模式?"], "markdown", 12000)]
for r in orch.run(cards):
    print(r.task_id, r.status, r.gaps)
```

### 6.2 任务书 / 结果卡 JSON 模板（评审与汇总共用协议）

### 6.3 评审 Agent 的提示词模板

```text
你是研究报告的评审员，只负责核查，不负责重写。
对照以下任务书逐条检查结果卡：
1. 每条 finding 是否有 source 与 quote？无来源的结论直接判不通过。
2. quote 是否真的支持 claim？数字、口径是否一致？
3. 任务书 questions 是否逐条被覆盖？未覆盖项是否已写入 gaps？
输出 JSON：{"pass": bool, "issues": ["..."]}
不允许为了通过而降低标准；发现疑似编造来源，标记为 fabrication。
```

## 7. 案例

### 案例 A：市场研究团队（主案例）

某咨询团队用主管 + 3 子 Agent + 1 评审的结构做行业尽调报告。改造前单 Agent 串行：一份 30 页报告要 4 小时，且后期窗口塞满检索噪音，事实错误率约 12%。改造后：三路并行 + 评审对照任务书逐条核来源，墙钟时间降到约 70 分钟，终稿事实错误率降到约 3%，token 消耗为单 Agent 的 11 倍——用任务书预算封顶把 15× 压到 11×，客户按报告计费，账算得过来。

### 案例 B：写作团队的评审-修订闭环

某内容平台的「选题→初稿→核稿→终稿」流水线。早期没有独立评审，主编（主管）兼赶进度兼核稿，漏网错误随发布流出。引入专职评审 Agent 后，评审只对照「事实、来源、体例」三张清单，问题清单回流对应环节修订，修订次数上限 2 次、超限转人工。返工率从约 20% 降到 6%，人工终审工作量减少一半以上。

### 案例 C：对比实验决定架构

某工程效能团队为「大库代码调查」任务做了 4.7 节风格的对照实验：40 个真实调查题，单 Agent vs 主管+4 子 Agent。结果分桶：10 个简单题上多 Agent token 12×、质量持平；30 个复杂题上质量分 +22%、墙钟 -60%。最终按题路由：简单题走单 Agent，复杂题走多 Agent，整体成本只有全量多 Agent 方案的约三成。教训写进团队规范：**对比实验的结论必须分桶，不许全局一刀切**。

## 8. 常见坑

1. **三条件没验证就拆**。任务有强顺序依赖或共享可变状态，多 Agent 只会把成本翻上去；先过 2.8b 判据。
2. **任务书写不清就派单**。目标、问题清单、格式、预算缺一项，子 Agent 必跑偏；四件套写全再派。
3. **子 Agent 自由对话协调**。聊天式通信让上下文爆炸且不可复现；通信用任务书/结果卡这类结构化消息。
4. **并行去写同一份稿**。写入冲突立刻出现覆盖与错乱；共享稿只有主管能写，子 Agent 只读外部资料。
5. **不设 token 预算**。15× 直接照单全收；任务书带预算，80% 收敛、100% 熔断。
6. **主管兼职评审**。既赶进度又核稿等于不核；评审必须独立，且只对质量清单负责。
7. **汇总不做验收**。无来源结论混进初稿，评审压力后置；汇总即验收，不合格当场退回。
8. **子任务失败无限重试**。重试要有上限，仍败就降级为部分结果 + 缺口标注。
9. **降级交付不标注**。缺口悄悄吞掉，用户以为报告完整；缺什么必须在终稿明说。
10. **超时不设哨兵**。一个子 Agent 卡死拖住全局；每个任务书带 deadline，超时收残件。
11. **拿单点任务评多 Agent**。在全求唯一答案的任务上测，当然亏；测试集要按复杂度分桶。
12. **对比实验不控变量**。底座模型、资料源、评审标准不一致，结论无效；一次只变架构这一维。
13. **忽略错误传播**。上游一个小错经多环节放大；每个交接点做结构化校验（4.7 平台治理同样强调此点）。

## 9. 练习

1. 用 6.1 骨架跑一个真实研究题：拆 3 份任务书，检查各结果卡的来源覆盖率。
2. 给 Orchestrator 加全局预算熔断：spent 超过 80% 时拒绝派新单并只做汇总。
3. 实现降级交付：把 degraded 任务的 gaps 写进终稿末尾的「缺口声明」小节。
4. 写评审 Agent 并接入流程，统计它拦截了多少条无来源结论。
5. 做一次单 vs 多对照实验：20 道题、双盲评分，按复杂度分桶给出质量/token/时间三维结论。
6. 把子 Agent 的 worker 换成真实 LLM 调用，实测 token 结构，对比 15× 量级差在哪里。
7. 给主管加状态外置（黑板模式）：进程重启后能从黑板恢复继续汇总，不重跑已完成的子任务。
8. 构造一个写入冲突场景（两个子 Agent 同时改同一文档），验证收口给主管后冲突消失。

## 10. 小结

- 多 Agent 化是笔交易：**约 15× token 买并行与上下文隔离**，是否划算由任务价值密度决定。
- 三条件判据：**可分解、读多写少、上下文可隔离**，缺一条就留在单 Agent。
- 结构化通信：**任务书四件套（目标/问题/格式/预算）下发，结果卡（结论+来源+缺口+消耗）回收**。
- 研究团队五步：**主管拆单 → 并行检索 → 汇总即验收 → 独立评审 → 修订交付**。
- 预算三层护栏：任务级封顶、编排级总闸、策略级模型分级路由。
- 失败兜底三招：**超时降级为部分结果 + 缺口标注、有限重派、预算触顶熔断**——绝不无限等待、绝不静默丢失。
- 评审必须独立于主管，对照清单核查事实、来源与覆盖度，意见回流形成闭环。
- 架构决策靠对照实验：固定测试集、控制变量、按复杂度分桶看质量/时间/成本三维结论。
- 错误在交接链上会放大，每个交接点设结构化校验。
- 团队之后是平台：注册发现、权限审计与成本治理在 4.7 展开。
