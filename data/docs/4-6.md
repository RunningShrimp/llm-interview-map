# 讲解 4.6 多 Agent 协作系统

> 说明：前置 2.8 讲清了多 Agent 的协作范式原理（监督（Supervisor）、并行、辩论、层级怎么选、通信有哪几种）；本篇把它落成一个可运行的实战项目——一个"调研-写作"多 Agent 团队，聚焦角色设计、任务分发、结果汇聚、成本控制，并用 A/B 对比正面回答关键问题：通信成本是否值得。后续 4.7 把这类系统平台化（多租户、治理、复用）。

## 1. 定位

实战层第 6 个知识点，属于"分布式智能实战"，直接前置是 2.8 多 Agent 协作。
它解决一个核心问题：**如何用多个各有所长的 Agent 协作完成单 Agent 搞不定的任务，并用数据证明它比单 Agent 更好？**

与 2.8 的分工边界：2.8 讲"范式原理"——拓扑、通信、辩论为什么有效、何时优于单 Agent 的判据；本篇讲"工程落地"——角色怎么设、任务怎么派、结果怎么汇、成本怎么控、效果怎么证明。全篇用同一个贯穿项目（"调研 AI Agent 市场并写一份报告"的研究-写作团队）把机制串起来。

后续承接：4.7 生产级 Agent 平台是直接后继（本篇的共享状态、trace、成本口径都会被平台层复用）；4.8 评估与红队、4.9 部署与运维继续深化评估与稳定性。

## 2. 一句话定义

多 Agent 协作系统（Multi-Agent System, MAS），是把复杂任务分解给多个具有不同角色、工具、Prompt 的 Agent，通过主管（Supervisor）协调、共享状态（Shared State）、消息传递等机制协同完成目标，并通过 A/B 对比证明其相对单 Agent 增益的实战系统。

简化公式：

```text
多 Agent 系统 = 多个单 Agent + 协调者（Supervisor） + 共享状态 + 通信 + 终止控制 + 评估对比
```

## 3. 为什么需要

单 Agent 在以下场景会力不从心：

- **上下文窗口不够**：研究报告要读 50 篇文档，一个 Agent 塞不下——检索噪声、原文摘录、草稿互相污染。
- **能力冲突**：同一个 Prompt 难以同时擅长研究和写作；要求堆得越多，每项越平庸。
- **无法并行**：多源检索串行执行，延迟成倍上涨。
- **缺少制衡**：自己写自己审，生成时漏掉的边界条件，自检时大概率还是看不见。
- **多视角缺失**：单一 Agent 容易思维定势，重大决策只有一种声音。
- **职责不清**：一个 Agent 既查数据又写报告又做审核，出错难定位、难回归。

**类比 1（自由职业者 vs 内容工作室）**：

```text
单 Agent = 一个接私活的全栈自由职业者：又调研又写稿又校对，
           一天只有 8 小时（上下文窗口），资料摊满一桌，很快找不到重点
多 Agent = 一个内容工作室：主编拆题派活，研究员/分析师/撰稿人各干各的，
           互不打扰，每人只交一页摘要，主编合稿
```

**"不做会怎样"对比表**：

| 场景 | 硬扛的单 Agent | 拆成多 Agent |
|---|---|---|
| 50 篇文献做综述 | 摘要互相覆盖，后半程遗忘前半程 | 每个研究员各读一册，只回摘要 |
| 生成 + 审查 | 自检发现不了自己的盲区 | Writer 与 Critic 上下文隔离 |
| 5 个数据源调研 | 串行 5 段延迟 | 并行 1 段延迟 + 一次汇总 |
| 高风险决策建议 | 单一视角，置信度虚高 | 正反方辩论 + 裁决 |

**但注意**：

> 多 Agent 不是默认选择。**先单 Agent，遇瓶颈再上多 Agent。**瓶颈判据见 2.8 的四判据（可并行性、上下文隔离、制衡、成本收益为正），本篇 4.9 给实战决策树。

## 4. 核心原理

### 4.1 贯穿项目与四种实战模式

本篇所有机制都挂在同一个项目上：**"调研 AI Agent 市场并写一份报告"**。先选模式（范式细节见 2.8）：

| 模式 | 结构 | 适用 | 相对单 Agent 成本 | 用在本项目的哪一段 |
|---|---|---|---|---|
| Supervisor | 主管 + Worker | 任务分发 | 3–5x | 总控：目标模糊、需要动态派活 |
| 并行分工 | 多 Worker + 汇总 | 多源检索 | 2–4x | 检索阶段：3 个来源并行查 |
| 辩论（Debate） | 正反方 + 裁决 | 决策 | 5–10x | 结论评审：进不进市场的建议 |
| 流水线（Pipeline） | A → B → C | 顺序任务 | 2–3x | 写作阶段：大纲→初稿→审校 |

实战常是组合体：Supervisor 做总控，检索段内部并行，写作段走流水线，关键结论过一轮辩论。

### 4.2 Supervisor 模式（最常用）

```text
        ┌──────────────┐
        │  Supervisor  │
        │   （主管）    │
        └──────┬───────┘
               │ 分配任务
     ┌─────────┼─────────┐
     ↓         ↓         ↓
  Researcher  Analyst  Writer
     │         │         │
     └─────────┼─────────┘
               ↓
          汇总结果
```

**Supervisor 职责**：

- 理解目标
- 分解任务
- 选择 Worker
- 检查结果
- 决定继续/完成

**Worker（工作者）职责**：

- 接收任务
- 使用专属工具
- 返回结果（摘要，不是过程全文）

**任务分发三策略**：

| 策略 | 做法 | 风险 |
|---|---|---|
| 按角色说明书匹配 | Supervisor 读每个 Worker 的职责声明派活 | 声明写差了就派错 |
| 轮询 | 依次派给空闲 Worker | 忽略能力差异 |
| 自愿认领 | Worker 从看板认领任务 | 争抢或推诿，需要仲裁 |

实战默认第一种：把每个 Worker 的职责、工具、输入输出写成一页"角色说明书"，Supervisor 只按说明书匹配，不做自由发挥。

### 4.3 角色设计

```python
ROLES = {
    "researcher": {
        "system": "你是研究员，负责检索和总结信息。只返回事实和来源。",
        "tools": ["search_web", "search_docs"],
    },
    "analyst": {
        "system": "你是分析师，负责数据分析和推理。基于事实给出洞察。",
        "tools": ["execute_sql", "execute_python"],
    },
    "writer": {
        "system": "你是写作者，负责撰写报告。结构清晰，语言专业。",
        "tools": [],
    },
    "critic": {
        "system": "你是审查员，负责找出报告中的错误、遗漏、不合理之处。",
        "tools": [],
    },
}
```

**角色设计模式表**（配角色时先对号入座，再写 Prompt）：

| 模式 | 角色配置 | 解决什么 | 本项目示例 |
|---|---|---|---|
| 生成-审查对（Maker-Checker） | 生成者 + 独立审查者 | 制衡，抓错误 | Writer + Critic |
| 流水线岗位 | 按工序各设一个 | 顺序质量累积 | 大纲→初稿→审校 |
| 辩论席位 | 正方 + 反方 + 裁决（Judge） | 多视角 | 支持方 + 反对方 + 裁决者 |
| 路由-执行 | Router + 各领域专家 | 简单任务不进团队 | 意图分类 + 专家 |
| 主-子 Agent | Lead + SubAgent | 上下文隔离 | 主研究员 + 3 个检索子 Agent |

**设计原则**：

- **职责单一**：一个 Agent 只做一件事。
- **能力匹配**：角色需要什么工具就配什么，多余的工具有注入风险。
- **Prompt 差异化**：不同角色用不同 System Prompt，强调各自的边界。
- **边界清晰**：知道什么该做、什么不该做、输出什么格式。

### 4.4 共享状态设计

```python
class SharedState:
    def __init__(self, goal: str):
        self.goal = goal
        self.plan = []
        self.results = {}       # {task_id: result}
        self.messages = []      # Agent 间消息
        self.artifacts = {}     # 中间产物
        self.current_round = 0
        self.max_rounds = 5

    def add_result(self, task_id: str, result):
        self.results[task_id] = result

    def add_message(self, sender: str, receiver: str, content: str):
        self.messages.append({
            "sender": sender,
            "receiver": receiver,
            "content": content,
            "timestamp": now(),
        })

    def to_context(self) -> str:
        return json.dumps({
            "goal": self.goal,
            "results": self.results,
        }, ensure_ascii=False)
```

**设计要点**：

- **唯一事实源**：所有中间结果只认 `results`，Worker 不私藏结论。
- **to_context 是成本闸门**：下发给 Worker 的上下文只带 goal + 已有结果，不带原始过程——这是控制通信成本的第一道闸。
- **可序列化**：状态随时能落盘，为检查点、重放、4.7 的平台化治理铺路。

### 4.5 通信机制与开销拆解

| 方式 | 说明 | 适用 |
|---|---|---|
| 共享状态 | 所有 Agent 读写同一状态 | 小规模 |
| 消息传递（Message Passing） | Agent 之间发消息 | 大规模 |
| 黑板（Blackboard） | 共享黑板，订阅变更 | 复杂协作 |

**共享状态实现**：

```python
class SharedStateStore:
    def __init__(self):
        self.states = {}

    async def get(self, workflow_id: str) -> SharedState:
        return self.states.get(workflow_id)

    async def update(self, workflow_id: str, key: str, value):
        state = self.states[workflow_id]
        setattr(state, key, value)
```

**一次通信的 token 账（示意推导）**：

```text
单个 Worker 一轮的输入 = 系统提示（约 0.3K）
                      + 任务描述（约 0.5K）
                      + 下发上下文（goal + 已有结果摘要，随轮数增长）

N 个 Worker × R 轮 → 上下文重放随轮数线性放大
粗算：5 个 Worker × 4 轮 × 平均 3K 输入 ≈ 60K token，还没算输出与工具结果
```

类比 2（开会成本）：多 Agent 的通信开销像开会——3 人团队每完成一步都要拉群同步，会议时长（消息 token）随人数和轮数上涨；好的 Supervisor 像项目经理，只让每人交"一页纪要"（结果摘要），不许在群里刷屏全文（原始过程）。

Anthropic 官方复盘其多 Agent 研究系统（《How we built our multi-agent research system》，2025）：多 Agent 的 token 消耗约为单 Agent 会话的 15 倍，主要来自子 Agent 并行探索与结果回传。这是"通信成本"目前最硬的公开数据。

**面试高频问法**："主 Agent 和子 Agent 的通信链路是怎样的？"共识口径分四步：任务下发（结构化 task + 裁剪后的上下文）→ 子 Agent 独立循环执行（带自己的工具与轨迹）→ 结果回传（只回结论摘要，不回过程全文）→ 状态合并（写入共享状态，触发下一轮决策）。追问"为什么用子 Agent 而不是把能力做成 Tool"的判据见 2.8。

### 4.6 终止条件

```python
def should_terminate(state: SharedState) -> tuple[bool, str]:
    if state.current_round >= state.max_rounds:
        return True, "达到最大轮数"
    if state.goal_achieved:
        return True, "目标完成"
    if state.cost > state.budget:
        return True, "预算超限"
    if state.rounds_since_progress >= 3:
        return True, "无进展"
    return False, ""
```

设计要点与 2.5 的单 Agent 终止控制同源：硬熔断（轮数、预算）放在每轮入口第一件事检查；软检测（无进展）看连续几轮结果指纹是否不变；终止要带回执（是否终止 + 原因），让调用方区分"完成"与"失败"。

### 4.7 成本控制

多 Agent 成本是单 Agent 的数倍（示意量级）：

| 模式 | 相对单 Agent 成本 |
|---|---|
| 流水线 | 2–3x |
| 并行 | 2–4x |
| Supervisor | 3–5x |
| 辩论 | 5–10x |

研究型（探索密集）系统按 Anthropic 口径可达约 15x token。

**控制手段**：

- 限制轮数与 Worker 数量
- 简单任务不进团队：入口 Router 分流到单 Agent 旁路
- 缓存 Worker 结果（同题检索直接命中）
- 通信裁剪：只下发 goal + 摘要，只回传摘要
- 小模型做简单 Worker，大模型只给 Supervisor 和 Writer
- 按需切换单/多模式：论文《Single-agent or Multi-agent? Why Not Both?》（arXiv:2505.18286，2025）的混合架构在问答基准上提升 1.1–12% 精度，同时省约 88% 成本——路由混合是成本控制的最强手段

### 4.8 评估对比：正面回答"通信成本是否值得"

本锚点的关键问题，分三步正面回答。

**第一步：把成本算清楚。**成本 = 消息 token（任务下发 + 结果回传 + 状态同步）× 轮次放大系数 + 并行重复探索。参考区间：流水线 2–3x、并行 2–4x、Supervisor 3–5x、辩论 5–10x，研究型系统约 15x（token 口径，不含延迟——延迟取决于最慢分支）。

**第二步：把收益判据摆出来。**Claude 官方博客《Building multi-agent systems: When and how to use them》（2026）与 Anthropic 工程复盘（2025）给出的三条件，满足越多越值得：

| 判据 | 含义 | 本项目对应 |
|---|---|---|
| 任务可并行 | 子任务独立、各自耗时数十秒以上 | 3 路检索并行 |
| 探索型、读多写少 | 多路径搜索的覆盖率收益大于重复探索成本 | 市场调研正是读多写少 |
| 需要专业化分工或上下文隔离 | 噪声隔离、生成-审查分离 | 研究噪声不进写作上下文 |

**第三步：用 A/B 评估证明。**必须做单 Agent 与多 Agent 的 A/B 对比：

```python
async def compare_single_vs_multi(task: str) -> dict:
    single_result = await single_agent.run(task)
    multi_result = await multi_agent.run(task)

    return {
        "single": {
            "answer": single_result["answer"],
            "cost": single_result["cost"],
            "latency": single_result["latency"],
            "quality": await judge_quality(task, single_result["answer"]),
        },
        "multi": {
            "answer": multi_result["answer"],
            "cost": multi_result["cost"],
            "latency": multi_result["latency"],
            "quality": await judge_quality(task, multi_result["answer"]),
        },
    }
```

**对比维度**：

| 维度 | 单 Agent | 多 Agent |
|---|---|---|
| 质量 | 基准 | 是否提升？提升多少？ |
| 成本 | 基准 | 增加多少倍？ |
| 延迟 | 基准 | 增加还是降低（并行）？ |
| 成功率 | 基准 | 是否提升？ |
| 可解释性 | 单轨迹 | 多轨迹，trace 是否更清晰？ |

**上线判据（一句话）**：质量提升 × 任务价值 > 成本倍数 × 单次成本，且延迟可接受——**多 Agent 必须在评估集上赢过单 Agent 才允许上线**；赢不了就退回单 Agent，或改用混合路由只让复杂任务进团队。

**面试高频问法**："多 Agent 系统比单 Agent 贵多少？什么条件下才值得上？"共识口径：贵 2–10 倍，研究型可到约 15 倍 token；值得的三条件是可并行、探索型读多写少、需要分工或上下文隔离；且必须拿出 A/B 数据证明质量或成功率收益覆盖成本，否则不上。

### 4.9 何时该用多 Agent（决策树）

```text
单 Agent 能完成吗？
├─ 能 → 用单 Agent
└─ 不能 → 瓶颈在哪？
    ├─ 上下文不够 → 多 Agent 分工（上下文隔离）
    ├─ 能力单一 → 多 Agent 专业化
    ├─ 需要并行 → 多 Agent 并行
    ├─ 需要多视角 → 多 Agent 辩论
    └─ 需要监督 → 生成-审查对
```

**该用**：

- 任务需要多种专业能力
- 需要并行处理
- 需要多视角/辩论
- 单 Agent 上下文不够

**不该用**：

- 单 Agent 能搞定
- 任务简单、实时性要求高
- 成本敏感且任务价值低

2026 年的主流做法是"路由混合"：入口一个 Router（可理解为医院分诊台——感冒直接开药走快速通道，疑难杂症才组织多科室会诊），简单任务走单 Agent 旁路，复杂任务才进团队。这也呼应 4.7 的混合架构数据（省约 88% 成本）。

### 4.10 多 Agent 的失败模式

| 失败 | 原因 | 解法 |
|---|---|---|
| 无限循环 | 无终止条件 | 最大轮数 + 无进展检测 |
| 通信爆炸 | 消息太多、拓扑全连接 | 限制拓扑（星型/分层） |
| 责任不清 | 角色重叠 | 明确职责说明书 |
| 互相推诿 | 无协调者 | 加 Supervisor |
| 成本失控 | 多 Agent 多调用 | 预算硬熔断 |
| 无法收敛 | 辩论无终点 | 固定轮数 + 裁决机制 |
| 状态冲突 | 并发写 | 按 task_id 分片 + 锁/版本控制 |
| 调试困难 | 轨迹复杂 | 全链路 trace（Trace） |

错误还会沿通信链放大：单步成功率 95% 的组件，串到第 8 次交互端到端只剩约 66%（复合失败率直觉，见 2.9）——每加一条通信边就多一条错误放大路径。

## 5. 架构 / 流程

一个带路由与评估闭环的研究-写作团队全景：

```text
┌──────────────────────────────────────────────┐
│ 用户目标："调研 AI Agent 市场并写一份报告"      │
└──────────────────┬───────────────────────────┘
                   ↓
┌──────────────────────────────────────────────┐
│ Router（任务路由 / 分诊台）                    │
│ ├─ 简单任务 → 单 Agent 旁路（不进团队）       │
│ └─ 复杂任务 → 进入多 Agent 团队               │
└──────────────────┬───────────────────────────┘
                   ↓
┌──────────────────────────────────────────────┐
│ Supervisor：分解 → 派发 → 验收 → 汇总         │
│ 终止检查：轮数 / 预算 / 目标完成 / 无进展      │
└────────┬──────────────┬──────────────┬───────┘
         ↓              ↓              ↓
  ┌────────────┐ ┌────────────┐ ┌────────────┐
  │ Researcher │ │  Analyst   │ │   Writer   │
  │ 3 路并行检索│ │ SQL/Python │ │ 大纲→初稿  │
  └──────┬─────┘ └──────┬─────┘ └──────┬─────┘
         └──────────────┼──────────────┘
                        ↓
┌──────────────────────────────────────────────┐
│ 共享状态：goal / results（按 task_id）/ 消息   │
│ 唯一事实源，可序列化，支撑检查点与重放          │
└──────────────────┬───────────────────────────┘
                   ↓
┌──────────────────────────────────────────────┐
│ Critic 审查 → 不通过则回派 Writer 修订         │
└──────────────────┬───────────────────────────┘
                   ↓
```

### 6.2 Agent 基类

```python
class BaseAgent:
    def __init__(self, name: str, system_prompt: str, tools: dict = None, model: str = "small-model"):
        self.name = name
        self.system_prompt = system_prompt
        self.tools = tools or {}
        self.model = model  # 简单角色可配小模型，控制成本

    async def execute(self, task: str, context: str = "") -> dict:
        messages = [
            {"role": "system", "content": self.system_prompt},
            {"role": "user", "content": f"上下文：\n{context}\n\n任务：\n{task}"},
        ]
        cost = 0.0

        for _ in range(5):  # 单 Agent 内部工具循环上限
            response = await chat(messages, tools=self.tools, model=self.model)
            msg = response
            cost += getattr(response, "cost", 0.0)  # 按实际 usage 计费

            if not msg.tool_calls:
                return {
                    "agent": self.name,
                    "output": msg.content,   # 只回结论，过程留在本地 messages
                    "cost": cost,
                }

            messages.append(msg)
            for tc in msg.tool_calls:
                result = await execute_tool(tc.function.name, tc.function.arguments)
                messages.append({
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": json.dumps(result, ensure_ascii=False),
                })

        return {"agent": self.name, "output": "未完成", "cost": cost}
```

### 6.3 Supervisor 实现（多角色编排核心）

```python
class SupervisorAgent:
    def __init__(self, workers: dict[str, BaseAgent]):
        self.workers = workers
        self.state = SharedState(goal="")

    async def run(self, goal: str, max_rounds: int = 5, budget: float = 0.5) -> dict:
        self.state.goal = goal

        for round_num in range(max_rounds):
            self.state.current_round = round_num + 1

            # 0. 硬熔断：预算
            done, reason = should_terminate(self.state)
            if done:
                break

            # 1. 决定下一步（任务分发）
            next_tasks = await self._plan_next()
            if not next_tasks:
                break

            # 2. 并行执行
            results = await self._execute_tasks(next_tasks)

            # 3. 更新共享状态
            for task, result in zip(next_tasks, results):
                self.state.add_result(task["id"], result)

            # 4. 检查是否完成
            if await self._is_complete():
                break

        # 5. 汇总（汇聚阶段）
        return await self._aggregate()

    async def _plan_next(self) -> list:
        prompt = f"""你是主管。根据目标和当前进展，决定下一步分配给哪些 Worker。

目标：{self.state.goal}
已完成：{json.dumps(self.state.results, ensure_ascii=False)}
可用 Worker：{list(self.workers.keys())}

输出 JSON：{{"tasks": [{{"id": "...", "worker": "...", "description": "..."}}]}}
如果已完成，输出 {{"tasks": []}}。"""

        response = await chat([{"role": "user", "content": prompt}], temperature=0)
        data = json.loads(response.content)
        return data.get("tasks", [])

    async def _execute_tasks(self, tasks: list) -> list:
        async def run_one(task):
            worker = self.workers[task["worker"]]
            # 只下发裁剪后的上下文（goal + 已有结果），不塞过程全文
            return await worker.execute(task["description"], self.state.to_context())

        return await asyncio.gather(*[run_one(t) for t in tasks])

    async def _is_complete(self) -> bool:
        prompt = f"""目标：{self.state.goal}
当前结果：{json.dumps(self.state.results, ensure_ascii=False)}

目标是否已完成？只输出 yes 或 no。"""

        response = await chat([{"role": "user", "content": prompt}], temperature=0)
        return "yes" in response.content.lower()

    async def _aggregate(self) -> dict:
        prompt = f"""根据以下结果，生成最终答案。

目标：{self.state.goal}
结果：{json.dumps(self.state.results, ensure_ascii=False)}"""

        response = await chat([{"role": "user", "content": prompt}], temperature=0.3)
        return {"answer": response.content, "state": self.state.results}
```

```python
class DebateAgent:
    def __init__(self, name: str, position: str):
        self.name = name
        self.position = position

    async def argue(self, topic: str, history: list) -> str:
        prompt = f"""你是辩论者 {self.name}，立场：{self.position}。

主题：{topic}
历史发言：
{chr(10).join(f"{h['name']}: {h['content']}" for h in history)}

请发表你的观点（200 字以内）："""
        response = await chat([{"role": "user", "content": prompt}], temperature=0.7)
        return response.content

async def debate(topic: str, rounds: int = 3) -> str:
    debaters = [
        DebateAgent("正方", "支持"),
        DebateAgent("反方", "反对"),
    ]
    history = []

    for _ in range(rounds):        # 固定轮数，保证收敛
        for d in debaters:
            arg = await d.argue(topic, history)
            history.append({"name": d.name, "content": arg})

    judge = BaseAgent("judge", "你是裁决者，根据辩论给出结论。")
    return await judge.execute(f"主题：{topic}\n辩论：{history}")

result = await debate("AI Agent 会取代人类工作吗？")
```

### 6.7 单 vs 多对比评估

```python
async def compare_agents(task: str, single_agent, multi_agent) -> dict:
    # 单 Agent
    single_start = time.time()
    single_result = await single_agent.run(task)
    single_latency = time.time() - single_start

    # 多 Agent
    multi_start = time.time()
    multi_result = await multi_agent.run(task)
    multi_latency = time.time() - multi_start

    # 质量评估（LLM-as-Judge，judge 校准见 4.8）
    single_quality = await judge_quality(task, single_result["answer"])
    multi_quality = await judge_quality(task, multi_result["answer"])

    return {
        "single": {
            "quality": single_quality,
            "latency": single_latency,
            "cost": single_result.get("cost", 0),
        },
        "multi": {
            "quality": multi_quality,
            "latency": multi_latency,
            "cost": multi_result.get("cost", 0),
        },
        "quality_lift": multi_quality - single_quality,
        "cost_ratio": multi_result.get("cost", 1) / max(single_result.get("cost", 1), 0.0001),
        "latency_ratio": multi_latency / single_latency,
    }

async def eval_suite(tasks: list) -> dict:
    # 在固定评估集上跑均值，避免单题巧合；win_rate 是上线判据的直接输入
    runs = [await compare_agents(t, single_agent, multi_agent) for t in tasks]
    return {
        "avg_quality_lift": sum(r["quality_lift"] for r in runs) / len(runs),
        "avg_cost_ratio": sum(r["cost_ratio"] for r in runs) / len(runs),
        "win_rate": sum(1 for r in runs if r["quality_lift"] > 0) / len(runs),
    }
```

## 7. 案例

### 案例 A：研究报告团队（Supervisor + 并行 + 流水线，主案例）

**场景**：某科技媒体团队要做"调研 AI Agent 市场并写报告"，此前由单个 Agent 一把梭，报告常漏数据源、引用错年份。

**做法**：Supervisor 总控；检索段 3 个 Researcher 并行（网页/论文/新闻），只回事实与来源；Analyst 用 Python 做趋势分析；Writer 按大纲→初稿两段流水线成稿；Critic 审查后回派修订；入口 Router 把"只查一个数字"类简单请求分流到单 Agent 旁路。

```text
Supervisor
   ├─ Researcher ×3：三源并行检索（只回事实+来源）
   ├─ Analyst：趋势与份额分析（Python 沙箱执行）
   ├─ Writer：大纲 → 初稿
   └─ Critic：审事实、审结构 → 不通过回派 Writer
```

**对比实验（50 题固定评估集，示意性量级）**：

| 维度 | 单 Agent | 多 Agent |
|---|---|---|
| 质量（10 分制） | 7.2 | 8.5 |
| 延迟 | 45s | 90s |
| 成本 | $0.03 | $0.12 |
| 成功率 | 75% | 92% |

**结论**：质量提升 18%、成功率提升 17 个百分点，成本 4 倍、延迟 2 倍。对单篇报告价值数百美元的业务，这笔交易成立；对日常快讯，Router 分流走单 Agent。

### 案例 B：代码生成流水线（生成-审查对）

**场景**：某内部工具团队让 Agent 写数据清洗脚本，单 Agent 一次性生成后直接交付，跑不通的脚本要人工返工。

**做法**：流水线 + 制衡——Planner 出实现方案，Coder 写码，Tester 在沙箱跑测试（沙箱设计见 4.3），Reviewer 对边界条件与可读性给意见，不过关回派 Coder。

```text
Planner → Coder → Tester（沙箱执行） → Reviewer → 通过交付
                        ↑__________________|  不通过回派
```

**示意数字**：单 Agent 一次通过率约 55%；加 Tester + Reviewer 后一次通过率 78%；单次生成成本约 2.8 倍、耗时约 3 倍。但"直到跑通"的端到端成本反而从约 4.2 倍降到约 2.1 倍——制衡角色把返工轮次打了下来，这是"成本高但总成本反而低"的典型样本。

### 案例 C：辩论决策（多视角制衡）

**场景**：一家金融科技公司用 Agent 辅助"该不该进入某细分市场"类决策，单 Agent 建议总偏乐观。

**做法**：辩论 + 裁决——正方 Agent 列进入理由与机会规模，反方 Agent 列风险与失败案例（两轮攻防），裁决 Agent 综合双方输出结构化建议（结论/置信度/关键假设/触发复查的条件）。

**示意数字**：回放 50 个历史决策问题，单 Agent 建议与事后专家共识的一致率约 64%，辩论 + 裁决约 76%；单题成本约 6 倍。结论：只在高价值、高风险决策上启用辩论模式，日常决策不配这种预算。

## 8. 常见坑

1. **过早多 Agent**。  
   单 Agent 能搞定的任务上多 Agent，纯付协调税。先单后多，出现 2.8 四判据的明确瓶颈再拆。

2. **不做 A/B 对比就上线**。  
   "感觉更好"不是证据。构建固定评估集，量化质量/成本/延迟/成功率，赢过单 Agent 才上线。

3. **角色重叠**。  
   两个 Agent 干同一件事，互相覆盖还抢状态。一岗一责，职责写进角色说明书。

4. **通信爆炸**。  
   所有 Agent 两两互通，消息量随连接数平方上涨。限制拓扑：星型（都过 Supervisor）或分层。

5. **全量上下文下发给每个 Worker**。  
   把整个历史塞给所有 Worker，token 随轮数雪崩。下发前裁剪：只带 goal + 相关结果摘要。

6. **无终止条件**。  
   辩论或互相纠错无限进行。最大轮数 + 预算 + 无进展检测三重兜底。

7. **Supervisor 瓶颈**。  
   所有决策串行过主管，并行度归零。可并行的任务打包同轮派发，Supervisor 只做"分派与验收"。

8. **结果直接拼接汇聚**。  
   把 N 个 Worker 的全文原样拼给汇总者，立刻超窗。先各自摘要，再分层归并（Map-Reduce 式汇总）。

9. **状态并发写冲突**。  
   多个 Worker 同时写同一字段，互相覆盖。按 task_id 分片写入 + 版本号或锁。

10. **调试困难**。  
    轨迹交错，出问题不知道是哪个 Agent 哪一步错。全链路 trace：每条消息带 sender/receiver/轮次/token 数。

11. **成本失控**。  
    调用次数是单 Agent 的 N 倍还不设上限。预算硬熔断 + 轮数上限 + 简单 Worker 用小模型。

12. **辩论无法收敛**。  
    正反方各说各话，没有终点。固定轮数后强制进入裁决 Agent。

13. **所有任务都进团队**。  
    一句话问答也走全套流程，延迟成本双输。入口加 Router，简单任务走单 Agent 旁路。

14. **框架锁定**。  
    深度绑定某框架的私有抽象。状态、消息、终止自实现，框架只当执行引擎（选型见 3.3）。

15. **权限不隔离**。  
    多 Agent 权限叠加，一个 Worker 被提示注入后横向扩散。每个 Agent 最小权限，高危工具只授予特定角色。

## 9. 练习

1. 实现 Supervisor 模式最小版：1 个主管 + 3 个 Worker（researcher/analyst/writer），跑通"调研一个主题并写 500 字摘要"。验收：固定目标下 5 次运行都能正常终止且产出非空。
2. 给系统加终止条件：最大轮数 + 预算 + 连续 2 轮无进展。验收：构造一个"Worker 永远说没做完"的场景，系统仍能停并返回原因。
3. 实现并行分工：3 个检索 Agent 并行查不同来源 + 1 个汇总 Agent。对比串行版本的延迟差。
4. 实现辩论模式：正反方各 2 轮 + 裁决者。验收：对"该不该上多 Agent"辩一次，输出含结论与关键假设的结构化裁决。
5. 实现通信裁剪：Worker 回传只带 200 字摘要 + 来源列表，Supervisor 只下发 goal + 摘要。对比全量下发的 token 消耗，记录节省比例。
6. 用 LangGraph 重写 6.3 的 Supervisor 拓扑（图编排，参考 3.3），接入 checkpointer 支持中断恢复。
7. 构建 20 题固定评估集，跑单 vs 多 A/B，报告质量、成本、延迟、成功率四列数字与 win_rate。
8. 设计多 Agent 客服系统：Router + 分类/处理/审查/升级四角色，画出状态流转图并标出人工介入点。
9. 给每条 Agent 间消息加 trace（sender/receiver/轮次/token），实现一次失败任务的回放定位。
10. 分析题：给出三个真实任务（天气问答、文献综述、年报数据核对），判断各自该走单 Agent、多 Agent 还是混合路由，逐条写明判据。

## 10. 小结

- 多 Agent 系统 = **多个单 Agent + 协调者 + 共享状态 + 通信 + 终止控制 + 评估对比**。
- 四种实战模式：**Supervisor、并行分工、辩论、流水线**——按任务形态选用并可组合。
- 角色设计：**职责单一、能力匹配、Prompt 差异化、边界清晰**；生成与审查必须分上下文。
- 通信：**共享状态、消息传递、黑板**三种；实战关键是**裁剪**——只传 goal 与摘要，不传过程全文。
- 终止：**最大轮数、预算、目标完成、无进展**四重条件，硬熔断放在每轮入口。
- 成本口径：**单 Agent 的 2–10 倍，研究型系统约 15 倍 token**；混合路由可省约 88% 成本。
- 通信成本是否值得：**三条件判收益（可并行、探索型读多写少、需分工/隔离），A/B 评估证收益**——多 Agent 必须在评估集上赢过单 Agent 才上线。
- 核心原则：**先单 Agent，遇瓶颈再上多 Agent；上线前必须有对比数据。**
- 这些能力直接支撑：4.7 生产级 Agent 平台（平台化复用与治理）、4.8 评估与红队、4.9 部署与运维。
