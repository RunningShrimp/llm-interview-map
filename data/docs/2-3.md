## 1. 定位

Agent 四件套（2.1）中的第三件，也是 Agent 与普通聊天机器人（Chatbot）的分水岭：**Chatbot 只会说话，Agent 能动手**。

它解决一个根本问题：**LLM 的知识是冻结的、不会精确计算、不能执行动作——如何让它安全、可靠地驱动外部系统？**

后续展开：

面试定位：**「工具调用失败怎么处理？如何防死循环？」「什么是 MCP？」是 Agent 方向的高频必答题**，答法就是本篇的防护四件套与三层协议定位。

## 2. 一句话定义

工具使用（Tool Use）是让 LLM 通过结构化调用（Function Calling）与外部系统交互的机制：**模型只负责决策——调什么工具、传什么参数；系统负责执行、校验与安全边界**。工程上的完整含义是四层能力之和：工具设计 + 参数校验 + 错误回传 + 防失控。

## 3. 为什么需要

LLM 有三个与生俱来的短板：

1. **知识截止**：训练数据有截止日期，不知道今天的股价、汇率、库存。
2. **不会精确计算**：算大数乘法、查数据库、排序一万条记录，都不该靠参数记忆硬算。
3. **不能执行动作**：改工单、发邮件、下单出票，模型没有「手」。

没有工具，Agent 的天花板是「会聊天的百科全书」。接上工具后，新的问题面随之而来——**工具层是 Agent 生产事故的最大来源**：

- 模型会**幻觉参数**：编造不存在的枚举值、拼错日期格式。
- 会**选错工具**：描述写得烂，模型拿搜索工具去查内部数据库。
- 会**无限重试**：接口超时后一遍遍原样重调，重试风暴一晚烧掉上万元 API 费。
- 会**死循环**：「失败→道歉→再查→再失败」原地打转，直到把上下文撑爆。

三类系统的能力与风险对比：

| 维度 | 纯 LLM 对话 | LLM + 工具 | LLM + 工具 + 防护 |
|---|---|---|---|
| 实时数据 | 无 | 有 | 有 |
| 执行动作 | 无 | 有 | 有，且带安全边界 |
| 失败处理 | 无此概念 | 失败即崩或幻觉 | 结构化回传 + 换路 |
| 成本可控性 | 天然有界 | 可能失控烧钱 | 双阈值强制终止 |
| 生产可用 | 是（但能力弱） | 否（定时炸弹） | 是 |

结论：**「demo 能跑」与「生产敢上」之间的距离，几乎全部落在工具层工程上。**

## 4. 核心原理

### 4.1 工具设计四原则

工具描述（Tool Description）就是模型的「API 文档」——模型看不见代码，只看得见描述。工具选错、参数写错，九成是描述的锅。

| 原则 | 内容 | 违反后果 | 反例 → 正例 |
|---|---|---|---|
| 功能清晰 | 一个工具一个职责；命名动宾式（`get_weather`）；语义不重叠 | 模型分不清该调谁，随机选 | `do_stuff` → `query_order_by_id` |
| 参数精简 | 能从上下文推导的不传；必填最小化；用枚举约束取值 | 参数多了幻觉面变大 | 传 12 个字段 → 只传 `order_id` |
| 描述充分 | 写清功能、每个参数含义、适用场景、返回示例、何时**不该**用 | 选错工具、传错参数 | 「查询订单」→「按订单号查物流状态；不知道单号时先调 search_order」 |
| 返回可读 | 结构化输出（JSON）、字段名自解释、超长可截断、带状态码 | 模型读不懂返回，编结果 | 返回原始 HTML → 返回 `{"status": "ok", "eta": "2天"}` |

补充两条工程纪律：

- **幂等性标注**：写操作尽量支持幂等键（Idempotency Key），模型重试不会重复出票。
- **粒度取舍**：粒度太细（`set_temp`、`set_mode`、`set_timer` 三个工具）让模型拼装易错；粒度太粗（一个万能 `execute`）让模型乱传参。中等粒度、场景化封装最优。

### 4.2 参数幻觉与校验

模型生成的参数本质是「概率采样」，不是「程序赋值」——它可能编造枚举值、混用日期格式、把字符串传成数字。防线是三层校验：

| 校验层 | 手段 | 拦截的问题 | 失败后动作 |
|---|---|---|---|
| Schema 层 | 按 JSON Schema 校验类型、必填、枚举 | 类型错、缺字段、编造枚举值 | 结构化错误回传，模型自修 |
| 语义层 | 取值范围、跨字段规则、业务约束 | 出发日期早于今天、成人数 > 9 | 回传原因 + 合法范围提示 |
| 执行层 | 预检查（Pre-check）、幂等键、数据库约束 | 订单不存在、库存已空、重复提交 | 按工具错误分类回传 |

关键认知：**校验失败不是终点，是反馈信号**。正确姿势是把「哪错了、合法值是什么」结构化地回传给模型，让它修一次；同一参数连续修 2 次仍失败，说明模型拿不到正确信息，应终止或转人工，而不是无限循环「修错」。

参数「自修链路」：

```text
模型生成参数 → Schema 校验失败（date 格式错）
→ 回传 {code:"INVALID_PARAM", field:"date", expect:"YYYY-MM-DD", got:"9月3号"}
→ 模型重生成 "2026-09-03" → 通过 → 执行
```

### 4.3 错误回传与自修（Error Feedback & Self-Repair）

工具失败后的 Observation 决定了 Agent 的下一步。三条铁律：

1. **严禁空串**。模型看到空结果会自行脑补「查询成功但无数据」甚至编造内容——这是幻觉事故的直接来源。
2. **严禁整段堆栈**。异常堆栈是给工程师看的，对模型是噪音，还会挤爆上下文。
3. **必须结构化**：错误码 + 人话原因 + 下一步建议。

统一错误结构（全站所有工具共用）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ok` | bool | 是否成功；错误处理逻辑的第一判断位 |
| `code` | string | 机器可读错误码，如 `TIMEOUT` / `INVALID_PARAM` / `UPSTREAM_5XX` |
| `message` | string | 一句话人话原因，进上下文给模型看 |
| `retriable` | bool | 是否可重试——瞬时错误 true，参数错/权限错 false |
| `suggestion` | string | 给模型的行动建议，如「改用备用接口」/「请向用户确认单号」 |
| `data` | any | 成功时的载荷；失败时省略 |

自修的前提是**错误分类**：瞬时错误（超时、限流）可重试；确定性错误（参数错、权限不足、资源不存在）重试无意义，必须换路或向用户求证。把 `retriable` 和 `suggestion` 写进错误结构，就是把「接线员的常识」制度化。

### 4.4 死循环防护四件套

Agent 循环的终止动力来自「观察到成功」——观察持续失败时，模型没有内建的「放弃」机制，必须靠外部工程刹车。四件套按层级排布：

| 机制 | 所在层 | 触发条件 | 动作 |
|---|---|---|---|
| 重试上限 + 指数退避 | 工具层 | 同一工具连续失败 2~3 次 | 停止重试，返回结构化错误 |
| 重复指纹熔断 | 工具层 | 同一（工具名+参数 hash）重复出现 N 次（通常 2~3） | 注入「该方法已失败请换策略」；再犯则本轮禁用该工具 |
| 步数 / 预算双阈值 | 循环层 | 最大步数（如 12 步）或 token/费用预算任一触达 | 强制终止，汇总已有进展转人工或降级 |
| 人工在环 | 业务层 | 不可逆动作（出票、退款、删除）失败或高影响决策 | 暂停，转人工确认后继续 |

要点展开：

- **指数退避（Exponential Backoff）**：第 1 次等 1s、第 2 次 2s、第 3 次 4s，配合抖动（Jitter）避免重试风暴打挂上游。
- **指纹熔断**：对 `hash(tool_name + canonical(json(args)))` 计数。单纯的步数上限拦不住「换着花样重复同一失败」的循环，指纹才拦得住。
- **双阈值是最后刹车**：它们不依赖模型自觉，是唯一保证「必然终止」的机制。提示词里写「请不要循环」是软约束，不能替代硬阈值。
- **熔断之后不是弃单**：汇总「已完成什么、卡在哪、建议怎么办」交人工——先保可用，再保完美。

### 4.5 并行工具调用

主流模型 API 支持一次返回多个 `tool_calls`。系统并发执行后，把结果按 `call_id` 对齐回填。

| 判据 | 适合并行 | 必须串行 |
|---|---|---|
| 数据依赖 | 三个独立航班查询 | 后一步参数依赖前一步返回值 |
| 副作用 | 只读操作（查询、搜索） | 写操作（下单、转账、删除） |
| 资源约束 | 各自独立接口 | 同一接口有并发/限流限制 |
| 一致性 | 无顺序要求 | 后一步需依据前一步结果决策 |

工程注意：

- **依赖判断交给模型 + 系统 双保险**：模型在 Thought 里声明「这三个查询互不依赖」；系统侧对同一工具的写操作强制串行。
- **超时统一**：并行组整体设 deadline，任一失败按错误分类处理，不因一个超时拖死整组。
- **结果对齐**：按 `tool_call_id` 回填，错位回填是常见低级事故。

### 4.6 MCP：工具接入标准化

MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年开源的模型连接工具/数据源的开放标准，被称为「AI 应用的 USB-C」。

**它解决的核心问题是集成的乘法爆炸**：M 个应用 × N 个工具，两两对接需要 M×N 套私有集成；标准协议之后，每个工具实现一次 MCP Server、每个应用装一个 MCP Client，变成 M+N 个标准模块。

```text
没有 MCP：2 个应用 × 5 个工具 = 10 套定制集成（每接一个重复开发）
有   MCP：2 个 Client + 5 个 Server = 7 个标准模块（新工具上架即全家可用）
```

两大角色：

- **MCP Server**：工具方。把能力封装为标准化的工具描述 + 调用接口，对外声明「我有什么」。
- **MCP Client**：应用方。运行在 AI 应用（Host）内，连接一个或多个 Server，动态发现（Discover）其能力并代理调用。

三大原语（Server 对外声明的能力类型）：

| 原语 | 含义 | 例子 |
|---|---|---|
| tools | 可被模型调用的工具 | `create_ticket`、`run_query` |
| resources | 可被读取的数据资源 | Wiki 页面、监控指标、文件内容 |
| prompts | 预置的提示模板 | 「按模板生成周报」 |

与相邻协议的分工——三层各管一段：

| 协议 | 连接对象 | 解决的问题 | 层级 |
|---|---|---|---|
| Function Calling | 模型 ↔ 单次调用 | 怎么下单（参数怎么传、格式怎么定） | 交互层 |
| MCP | 模型 ↔ 工具/数据源 | 工具从哪来（发现、描述、接入标准化） | 生态层 |
| A2A | Agent ↔ Agent | 智能体之间怎么互联协作 | 协作层 |

MCP 与 Function Calling **不冲突**：经 MCP 接入的工具，最终仍以 Function Calling 的形式被模型调用。MCP 管「上架与货架」，FC 管「下单流程」。

安全边界（接入第三方 Server 必做）：

- Server 白名单，而非全开放。
- 按请求者身份透传权限（Server 用用户自己的权限查数据，不越权代取）。
- 工具描述经安全审计，防「描述投毒」（恶意 Server 在描述里注入诱导指令）。
- 写操作强制人工确认；全量调用审计留痕；敏感字段在 Server 侧脱敏。

## 5. 架构 / 流程

一次受保护的工具调用全链路：

```text
┌────────────────────────────────────────────────────┐
│  模型（决策层）                                     │
│  读工具描述 → 生成 tool_calls（可多个=并行）          │
└────────────────────────────────────────────────────┘
                     ↓ tool name + args
┌────────────────────────────────────────────────────┐
│  客户端（执行层）                                   │
│  1. 注册表查找工具（不存在→UNKNOWN_TOOL 错误回传）    │
│  2. 参数三层校验（Schema→语义→预检查）               │
│     失败→INVALID_PARAM 错误回传，模型自修（限 1~2 次）│
│  3. 指纹检查：同（工具+参数）重复超限→熔断            │
│  4. 执行：超时控制 / 并行编排 / 幂等键                │
└────────────────────────────────────────────────────┘
                     ↓ 统一错误结构 { ok, code, message,
                        retriable, suggestion, data }
┌────────────────────────────────────────────────────┐
│  循环层（防护层，2.5 展开）                          │
│  错误按 retriable 决定重试/换路；                    │
│  步数 / token 预算双阈值；触达即强制终止              │
│  不可逆动作 → 人工在环                               │
└────────────────────────────────────────────────────┘
```

MCP 接入形态：

```text
┌─ AI 应用（Host）──────────────┐
│  模型  ←→  MCP Client         │
└──────────────┬────────────────┘
               │ 标准协议（stdio / HTTP）
   ┌───────────┼───────────┬──────────────┐
   ↓           ↓           ↓              ↓
MCP Server   MCP Server   MCP Server    MCP Server
(数据库)     (日历)        (内部工单)     (第三方搜索)
 tools        tools        tools         tools
 resources   resources
```

接入清单（新工具上线七步）：写四要素描述 → 定义参数 Schema → 实现统一错误结构 → 注册进注册表 → 单测（正常/参数错/超时三例）→ 权限与幂等评审 → 接入轨迹监控与告警。

## 6. 代码 / 工具

### 6.1 工具注册表（注册、校验、分发）

```python
import json, hashlib
from jsonschema import validate, ValidationError

TOOL_REGISTRY = {}   # name -> {"schema":..., "fn":..., "description":...}

def tool(description, schema):
    """装饰器：注册工具，绑定描述与参数 Schema"""
    def deco(fn):
        TOOL_REGISTRY[fn.__name__] = {
            "description": description, "schema": schema, "fn": fn,
        }
        return fn
    return deco

@tool(
    description="按订单号查询物流状态。仅当用户提供了订单号时使用；"
                "不知道单号时先调 search_order。",
    schema={
        "type": "object",
        "properties": {"order_id": {"type": "string"}},
        "required": ["order_id"],
    },
)
def get_logistics(order_id: str):
    return {"status": "transit", "eta": "2天"}

def validate_args(name, args):
    """Schema 层校验：失败抛 INVALID_PARAM"""
    try:
        validate(instance=args, schema=TOOL_REGISTRY[name]["schema"])
    except ValidationError as e:
        return ToolError("INVALID_PARAM",
                         f"参数不合法: {e.message}",
                         retriable=False,
                         suggestion="按 Schema 修正参数后重试")
    return None

def fingerprint(name, args):
    """（工具+参数）指纹：供死循环熔断计数"""
    canonical = json.dumps(args, sort_keys=True, ensure_ascii=False)
    return hashlib.md5(f"{name}:{canonical}".encode()).hexdigest()

def dispatch(name, args, fp_counter=None, FP_LIMIT=3):
    """分发执行；fp_counter 为跨轮指纹计数器"""
    if name not in TOOL_REGISTRY:
        return ToolError("UNKNOWN_TOOL", f"工具 {name} 不存在",
                         retriable=False,
                         suggestion=f"可用工具: {list(TOOL_REGISTRY)}")
    err = validate_args(name, args)
    if err:
        return err
    fp = fingerprint(name, args)
    if fp_counter is not None:
        fp_counter[fp] = fp_counter.get(fp, 0) + 1
        if fp_counter[fp] > FP_LIMIT:
            return ToolError("LOOP_DETECTED", "同一调用已重复多次",
                             retriable=False,
                             suggestion="请更换策略或转人工")
    try:
        return TOOL_REGISTRY[name]["fn"](**args)
    except TimeoutError:
        return ToolError("TIMEOUT", "上游接口超时", retriable=True,
                         suggestion="稍后重试或改用备用接口")
```

### 6.2 统一错误结构（结构化回传）

```python
from dataclasses import dataclass, asdict

@dataclass
class ToolError:
    code: str          # 机器可读错误码
    message: str       # 一句话人话原因（进上下文）
    retriable: bool    # 是否可重试
    suggestion: str    # 给模型的行动建议

    def to_observation(self) -> str:
        """作为 Observation 回传给模型——严禁空串与堆栈"""
        return json.dumps(
            {"error": asdict(self)}, ensure_ascii=False
        )

def to_observation(result) -> str:
    """成功/失败统一包装为 Observation"""
    if isinstance(result, ToolError):
        return result.to_observation()
    return json.dumps({"ok": True, "data": result},
                      ensure_ascii=False)

# 用法示例：失败时的 Observation 长这样
# {"error": {"code": "INVALID_PARAM",
#            "message": "参数不合法: 'order_id' is a required property",
#            "retriable": false,
#            "suggestion": "按 Schema 修正参数后重试"}}
```

from mcp.server import Server

app = Server("ticket-system")

@app.tool(description="创建内部工单。title 不超过 50 字；"
                      "severity 取值 P0|P1|P2。创建后不可自行删除。")
def create_ticket(title: str, severity: str, owner: str):
    # Server 持系统凭证，但按请求者 owner 的权限执行（权限透传）
    assert severity in ("P0", "P1", "P2"), "severity 必须是 P0/P1/P2"
    ticket = db.insert(title=title, severity=severity, owner=owner)
    return {"ticket_id": ticket.id, "status": "created"}

@app.resource("wiki://{path}")
def read_wiki(path: str) -> str:
    return wiki.render(path)   # 只读资源：供 Client 检索引用

## 7. 案例

### 案例 A：客服 Agent 重试风暴治理

**场景**：某电商客服 Agent，高峰期订单接口超时。失败被当成空串回传，模型不知道失败，原样重调；又没有步数上限。事故当晚单会话最高重试 60 余次，一晚烧掉上万元 token 费，且无一单真正解决。

**治理**（防护四件套逐层落地）：

1. 工具层：超时 3s + 指数退避，同一（工具+参数）连续失败 2 次即熔断，回传 `TIMEOUT` + 建议「改用备用票源接口」。
2. 循环层：最大步数 12、单会话 token 预算上限，触达强制终止。
3. 业务层：出票失败即停转人工。
4. 监控层：步数 P95、失败率、单会话成本三条告警；上线前用故障注入演练验证阈值真的会触发。

**效果**：单会话步数 P95 从 15 降到 6，异常成本从「一晚万元级」压到百元级，接口超时场景下任务完成率反而从 40% 升到 78%——因为模型拿到结构化错误后真的会换路。

### 案例 B：M×N → M+N 的集成改造

**场景**：一家金融科技公司有 5 个内部系统（工单/CRM/Wiki/监控/HR），此前为 2 个 AI 应用做过定制集成，共 10 套私有对接代码，新增一个系统平均要 2 周。

**改造**：5 个系统各实现一个 MCP Server（核心能力映射为 tools、只读数据暴露为 resources、统一鉴权与 Schema）；2 个应用各接一个 MCP Client 动态发现工具；生产环境 Server 白名单 + 写操作人工确认 + 全量审计。

**效果**：10 套集成变 5+2=7 个标准模块；新系统接入从 2 周缩到 2 天；权限越权事件归零（按请求者身份透传权限）。

### 案例 C：并行调用提速

**场景**：研究助手需要对比三个竞品的最新融资信息，原实现串行调用三次搜索。

**改造**：模型在 Thought 中声明三个查询互不依赖，一次输出三个 `tool_calls`；系统并发执行，按 `call_id` 对齐回填。

**效果**：端到端延迟从约 12s 降到 5s，token 成本不变。教训：第二次迭代时把「写收藏夹」也并行了，导致两个写操作竞争冲突——写操作从此强制串行。

## 8. 常见坑

1. **工具描述只写一句话**。模型选错工具、传错参数的根因。写全四要素：功能、参数、适用场景、返回示例，并注明「何时不该用」。
2. **语义重叠的工具**。`get_user` 和 `query_user` 并存，模型随机选。合并或用描述明确分工。
3. **参数表过大**。十几个必填字段，幻觉面指数增大。能推导的不传，必填最小化，取值用枚举。
4. **失败回传空串或堆栈**。空串诱发幻觉，堆栈污染上下文。统一结构化错误：码 + 原因 + 建议。
5. **所有错误都重试**。参数错、权限错重试一万次也一样。按 `retriable` 分类：瞬时错误才重试。
6. **重试没有上限和退避**。立刻原样重打上游，等于对故障接口发起第二次攻击。指数退避 + 连续 2~3 次即停。
7. **只有步数上限，没有指纹检测**。模型会「换着花样」重复同一失败调用。对（工具+参数）做指纹，重复超限熔断。
8. **把提示词约束当防线**。「请不要循环」是软约束。终止保证只能来自硬阈值：步数 + token/费用预算。
9. **校验失败直接终止**。Schema 校验失败应先结构化回传让模型自修一次；连续修不动再终止——直接弃单浪费了自修机会。
10. **写操作不设幂等键**。模型重试导致重复出票、重复退款。所有写操作带幂等键或做预检查。
11. **不可逆动作放行无确认**。出票、退款、删除必须人工在环；失败即停，不自动「再试一次」。
12. **并行了写操作或依赖调用**。写写竞争、后一步依赖前一步返回值时并行会出错。并行只用于无依赖的只读调用。
13. **MCP 全开放接入第三方 Server**。描述投毒、越权代取、敏感数据经手。白名单 + 权限透传 + 写确认 + 审计。
14. **工具结果不做截断与摘要**。一个搜索返回 2 万字直接进上下文，轨迹立刻膨胀。超长结果在执行层截断或摘要后再回传。

## 9. 练习

1. 给 5 个假想工具（查天气/查订单/搜索/发邮件/计算器）写四要素描述，互相评审语义是否重叠。
2. 实现一个工具注册表：装饰器注册 + JSON Schema 校验 + 未知工具与参数错误的统一回传。
3. 构造一个「必然超时」的假接口，验证指数退避 + 重试上限 + 指纹熔断的完整触发链路。
4. 故意让模型生成非法枚举值，观察错误回传后它能否自修；对比回传空串时的行为差异。
5. 把三个独立查询改成并行 `tool_calls`，测量端到端延迟变化；再验证写操作被强制串行。
6. 用官方 SDK 写一个最小 MCP Server（一个 tool + 一个 resource），在任意 MCP Client 里接入并调用。
7. 为 MCP 接入设计安全清单：白名单、权限透传、写确认、审计日志四项逐一落地。
8. 做一次故障注入演练：随机挂掉 30% 的工具调用，统计步数分布、成本分布与终止原因，确认双阈值生效。

## 10. 小结

- 工具使用 = 模型决策 + 系统执行；模型只管「调什么、传什么」，校验、执行、安全边界全在系统侧。
- 工具描述是模型唯一的「文档」，**功能清晰、参数精简、描述充分、返回可读**四原则定成败。
- 参数是概率采样，必须三层校验：Schema → 语义 → 执行层；校验失败结构化回传让模型自修。
- 错误回传三铁律：**严禁空串、严禁堆栈、必须结构化**（码 + 原因 + 建议 + retriable）。
- 死循环防护四件套：**重试上限退避、步数/预算双阈值、重复指纹熔断、人工在环**——硬阈值是唯一保证终止的机制。
- 并行调用只用于无依赖的只读操作，结果按 `call_id` 对齐回填。
- MCP 把 M×N 私有集成变 M+N：工具方做 Server、应用方装 Client，三大原语 tools/resources/prompts。
- 三层协议分工：FC 管「怎么调」，MCP 管「从哪来」，A2A 管「Agent 怎么互联」。
- 生产清单：幂等键、写确认、白名单、审计、轨迹监控、故障注入演练。
- 这些能力由 1.3 的调用协议支撑，并在 2.4 记忆、2.5 执行循环中与记忆和循环控制合流。
