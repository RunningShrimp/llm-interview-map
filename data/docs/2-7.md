# 讲解 2.7 单 Agent 架构模式

> 说明：2.6 给 Agent 装上了反思兜底，单 Agent 的能力件已集齐——本篇把它们组装成**整体架构**：工具型、RAG 型、工作流型、自主型四大模式怎么选。  
> 「工作流还是自主」的精细判据在 2.7b 展开；单 Agent 也扛不住时升级到 2.8 多 Agent；落地为服务架构是 3.1 的事。

---

## 1. 定位

S2 与 S3 的交汇点。前置：2.6 反思（自主型的质量兜底层）、1.4b RAG 最小链路（RAG 型的组件来源）、2.2-2.5（规划/工具/记忆/循环——自主型的发动机零件）。

它回答工程上最先遇到的架构问题：**拿到一个 LLM 需求，该搭成什么样？**

后续走向：2.7b 给「工作流 vs 自主」的判据清单；2.8 多 Agent 是更贵的一档；3.1 服务架构是选型之后的工程底座；4.1 最小可用 Agent 原型从这里起步。

## 2. 一句话定义

单 Agent 架构模式是把「LLM + 组件 + 控制流」组织起来的固定配方：**工具型**一次调用、**RAG 型**先查再答、**工作流型**代码定路径、**自主型**模型定路径——四者是组件与自由度的递进，不是高级与否之分。

选型的第一步不是选框架，是**画任务形状**：

```text
一次调用能办 → 工具型；要先查资料 → RAG 型；
路径固定可画流程图 → 工作流型；路径开放要边做边定 → 自主型
```

## 3. 为什么需要

同一个「让 AI 干活」，四种架构的成本、可控性、适用边界差一个数量级：

1. **成本差**：工具型一次 LLM 调用；自主型每一步都是一次决策调用，一个 10 步任务的 token 与延迟可能差 10 倍以上。
2. **可控性差**：工作流的路径由代码写死，出事看日志定位到节点；自主型的路径由模型现场生成，调试像大雾里找路。
3. **翻车面差**：模式选错不是「效果差一点」，是根本跑不通——给固定报表任务上自主 Agent，等于为用不上的灵活性买单；给开放调研任务上工具型，单发调用直接不够用。

医院分诊类比：量个体温开盒药就走（工具型）；疑难杂症先翻病历文献再下诊断（RAG 型）；入职体检按固定套餐走完（工作流型）；跨科会诊边查边改方案（自主型）。**不存在最先进，只存在最合身。**

## 4. 核心原理

### 4.1 四大模式总览

| 维度 | 工具型 | RAG 型 | 工作流型 | 自主型 |
|---|---|---|---|---|
| 组件构成 | LLM + 函数调用 | LLM + 检索器 + 知识库 | 代码骨架 + 节点内 LLM | LLM + 工具 + 记忆 + 循环 + 反思 |
| 路径由谁定 | 单发，无路径 | 固定（检索→生成） | 代码预先定义 | 模型现场决定 |
| 循环/记忆 | 无 | 无 | 无（或节点级） | 有（2.5 循环 + 2.4 记忆 + 2.6 反思） |
| 适用场景 | 天气/汇率/查库存等一问一答 | 企业知识问答、文档客服 | 审批链、报表、数据管道 | 调研、修 bug、多源汇总等开放任务 |
| 成本 | 最低 | 低-中 | 中（只在必要节点调模型） | 最高 |
| 可控可测 | 最好 | 好 | 最好（路径可审计） | 最差（必须配熔断） |
| 典型翻车点 | 任务超 5 步就力不从心 | 检索不到/检索错→答非所问 | 需求一变就改代码 | 死循环、成本失控、不可预测 |

### 4.2 工具型：一次调用

LLM 听懂请求、选一个工具、调用一次、组织回答。没有循环、没有记忆、没有反思——本质是 1.3b Function Calling 的直接产品化。

- 甜点区：答案由一次外部调用决定，LLM 只负责「听懂 + 选工具 + 说人话」。
- 价值：延迟最低、最好测试（工具选对与否可离线评测）、每请求成本最省。
- 边界：任务需要多步协作、中途要判断时，单发力不从心——该升级了。

### 4.3 RAG 型：先查再答

在工具型之上加一条检索链路：检索知识库 → 拼上下文 → 生成带引用的回答。组件流就是 1.4b 的最小 RAG 链路嵌进 Agent 外壳。

- 甜点区：答案存在于固定资料中、要求知识新鲜、可溯源、权限过滤。
- 命门在检索质量：生成端只能忠于检索结果，**查错了就一路错到底**。
- 工程要点：引用编号、检索质量闸门（相关度太低就答「资料不足」转人工）、知识库更新机制。

### 4.4 工作流型：代码定路径

路径由代码预先定义，LLM 只是流水线上的工人，在节点内干活。企业生产环境的主力模式。

- 甜点区：路径能画成流程图——分支可穷举、步骤事先写得出来。
- 价值：可控、可测、可审计（3.8 的审计要求靠它兜底），LLM 调用只发生在必要节点。
- 边界：需求一变就要改代码；没覆盖到的分支直接卡死——灵活性为 0。

### 4.5 自主型：模型定路径

模型自己决定下一步：ReAct 循环（2.5）执行、记忆（2.4）维持状态、反思（2.6）质量兜底、步数/预算熔断（2.3）防失控。自由度最大，成本与风险也最大。

- 甜点区：路径没法预先写出——调研、修 bug、跨多源汇总，下一步取决于上一步的观察。
- 必配三件：步数熔断、预算护栏、人工在环。缺一个都不该上生产。

### 4.6 四范式选型口诀

架构模式之下还有一层「范式」选择——自主型内部用什么控制流跑。四个经典范式：

| 范式 | 机制 | 强项 | 弱点 | 口诀 |
|---|---|---|---|---|
| ReAct | Thought→Action→Observation 逐轮循环 | 单步灵活，每步可依据观察调整 | 长任务易跑偏；每步都要过模型 | 单步灵活看 ReAct |
| Plan-and-Execute | Planner 先出全量计划，Executor 照单执行 | 长任务有全局图，不跑偏 | 计划赶不上变化，需重规划机制 | 长任务不跑偏看 Plan-and-Execute |
| ReWOO | Planner 一次性生成变量代换的计划，工具结果不回传给 LLM，最后统一求解 | token 省、可并行 | 中途纠错弱 | 省钱并行选 ReWOO |
| Reflection/Reflexion | 执行后自评反思，教训入记忆重试 | 输出质量兜底 | 每轮多花钱 | 输出质量靠 Reflection |

组合用法：ReAct 出灵活性、Plan-and-Execute 出骨架、Reflection 兜质量——**质量这条线通常并入自主型架构的讨论**，即「自主型 = ReAct + Reflection」是面试标准答案。

### 4.7 工作流还是自主：先过判据

2.7b 的核心判据一句话：**任务路径能画成流程图（分支可穷举）就用工作流；画不出、下一步取决于执行中途的观察，才上自主 Agent。**

LangChain 官方劝退清单——以下情况别上 Agent：

| 信号 | 更合适的方案 |
|---|---|
| 路径可穷举，能画流程图 | 工作流 / 纯代码 |
| 一次调用能解决 | 直接 API / 工具型 |
| 要确定性输出 | 模板 + 校验规则 |
| 高频、成本敏感 | 规则自动化 |
| 信息能装进一个上下文 | 单 Agent 别拆 |

补充两条默认原则：**默认先工作流，压不住了再升级**（升级方向永远比降级好做）；**多数生产系统是混合体**——工作流骨架 + 关键节点留 LLM 自由度 + 人工闸门兜底，不是二选一。

### 4.8 模式组合

四模式是配方不是阵营，生产系统常见组合配方：

| 组合 | 结构 | 典型场景 |
|---|---|---|
| 工作流骨架 + RAG 节点 | 固定步骤中某一步是「检索→生成」 | 工单自动处理：分类（代码）→ 查知识库（RAG）→ 生成回复 |
| 工作流骨架 + 自主节点 | 大流程固定，个别环节开放 | 内容生产：选题（代码）→ 调研（自主 ReAct）→ 成稿（模板） |
| 工具型前置 + 自主型兜底 | 先试单发，失败升级循环 | 客服：常见问题一次调用；复杂问题转自主处理 |
| 自主型 + Reflection | ReAct 循环外挂反思兜底 | 研究助手、修 bug Agent 的标准形态 |

## 5. 架构 / 流程

四模式的自由度谱系（从左到右：越来越自由，越来越贵，越来越难测）：

```text
 自由度低 ←──────────────────────────────────────→ 自由度高
 成本低                                            成本高
 可控好                                            可控差

 ┌─────────┐   ┌─────────┐   ┌──────────┐   ┌──────────┐
 │ 工具型   │   │ RAG 型  │   │ 工作流型 │   │ 自主型    │
 │ 单发调用 │   │ 检索→生成│   │ 代码定路径│  │ 模型定路径│
 └─────────┘   └─────────┘   └──────────┘   └──────────┘
  1 次 LLM      2 次 LLM       N 个节点中      每步 1 次 LLM
  （部分免调）   （检索+生成）   少数节点调 LLM   + 反思轮
```

选型决策树：

```text
拿到需求
  │
  ├─ 一次调用能解决？ ──是──→ 工具型（直接 API）
  │
  ├─ 答案在固定资料里？ ──是──→ RAG 型（+ 引用 + 检索闸门）
  │
  ├─ 路径能画成流程图？ ──是──→ 工作流型（节点校验 + 降级路径）
  │
  └─ 路径写不出来、要边做边定？
        ├─ 是 → 自主型（ReAct + 反思 + 步数/预算熔断 + 人工在环）
        └─ 拿不准 → 工作流起步，长尾留自主节点（混合体）
```

## 6. 代码 / 工具

### 6.1 RAG 型 Agent 骨架

```python
"""RAG 型 Agent 骨架：检索 → 检索闸门 → 带引用生成 → 兜底。
比工具型多一条检索链路；比自主型便宜一个数量级，知识问答的主力形态。"""

import json
import chromadb
from openai import OpenAI

client = OpenAI(api_key="YOUR_KEY")
MODEL = "gpt-4o-mini"
col = chromadb.Client().get_or_create_collection("kb")

# ---- 离线：文档入库（真实项目用 1.4 的切分+嵌入，这里示意） ----
col.add(
    documents=["退货政策：签收后 7 天内可退。",
               "退款时效：3-5 个工作日到账。"],
    metadatas=[{"source": "policy.md", "page": 1},
               {"source": "policy.md", "page": 2}],
    ids=["doc1", "doc2"])

def retrieve(query: str, k: int = 5) -> list:
    res = col.query(query_texts=[query], n_results=k)
    return [{"text": d, "meta": m}
            for d, m in zip(res["documents"][0], res["metadatas"][0])]

def retrievable(query: str, docs: list) -> bool:
    """检索质量闸门：相关度不够就别硬答——RAG 型的第一道反思点"""
    joined = "\n".join(d["text"][:200] for d in docs)
    resp = client.chat.completions.create(
        model=MODEL, temperature=0,
        response_format={"type": "json_object"},
        messages=[{"role": "user", "content":
            f"问题：{query}\n资料：\n{joined}\n"
            '资料能否回答该问题？回 JSON：{"answerable": bool}'}])
    return json.loads(resp.choices[0].message.content)["answerable"]

def answer(query: str) -> str:
    docs = retrieve(query)
    if not retrievable(query, docs):
        return "知识库中没有相关资料，建议转人工。"      # 兜底比瞎编强
    context = "\n".join(f"[{i+1}] {d['text']}" for i, d in enumerate(docs))
    resp = client.chat.completions.create(
        model=MODEL, temperature=0,
        messages=[
            {"role": "system", "content":
                "只根据资料回答，标注引用编号；资料不足就说资料不足，不许编造。"},
            {"role": "user", "content": f"资料：\n{context}\n\n问题：{query}"}])
    return resp.choices[0].message.content

print(answer("退货后多久能收到退款？"))
# 根据资料 [2]，退款需要 3-5 个工作日到账。
```

```python
"""工作流型：路径由代码定死，LLM 只在节点内干活；每节点带校验与降级。"""

def weekly_report(day: str) -> dict:
    raw   = extract_from_warehouse(day)              # 步骤 1：拉数（纯代码）
    clean = clean_rows(raw)                           # 步骤 2：清洗（纯代码）
    draft = llm_node(                                 # 步骤 3：LLM 节点
        prompt="把以下数据写成 5 段周报，只使用给定数据",
        payload=clean)
    ok, why = validate_report(draft, clean)           # 步骤 4：规则校验
    if not ok:
        draft = llm_node(                             # 修复轮：把问题喂回去
            prompt=f"周报有以下问题，请修正：{why}",
            payload=clean)
    return publish(draft)                             # 步骤 5：发布（纯代码）
```

### 6.3 自主型骨架（ReAct + 反思 + 熔断）

```python
def autonomous_agent(goal: str, max_steps: int = 15,
                     max_reflect_rounds: int = 3) -> str:
    memory = load_memory()                            # 2.4 记忆
    for r in range(max_reflect_rounds):               # 2.6 反思熔断
        result, steps = react_loop(                   # 2.5 ReAct 循环
            goal, tools=TOOLBOX, memory=memory,
            step_budget=max_steps)                    # 2.3 步数熔断
        verdict = evaluate(goal, result)              # 硬验证器优先
        if verdict["pass"]:
            return result
        lesson = reflect(goal, steps, verdict["why"]) # 2.6 经验沉淀
        memory.add("open_task", lesson)
    return escalate_to_human(goal, result)            # 全熔断：人工在环
```

## 7. 案例

### 案例 A：企业客服的知识问答（RAG 型为主 + 工具型子能力）

**场景**：某电商平台客服机器人，日均 2 万请求，80% 是「订单到哪了」「退货政策」类问题。

**架构**：查订单走工具型（一次 API 调用）；政策问答走 RAG 型（内部文档 + 混合检索 + 引用）；两条线之外不到 5% 的复杂咨询转人工闸门。

**效果**：自动解决率 78%，政策类答案引用准确率 96%，单请求平均成本自主型方案的约八分之一——用任务形状选架构，便宜且可控。

### 案例 B：周报机器人（工作流型，不上自主）

**场景**：团队周报，数据源固定三张表、每周步骤完全一致。有人提议「上自主 Agent 才专业」。

**决策**：路径能画成流程图，选工作流——拉数、清洗纯代码；成稿一个 LLM 节点；规则校验不过把问题喂回修复轮。三范式口诀逐条对照：不需要单步灵活（ReAct 用不上）、没有跑偏问题（Plan-and-Execute 用不上）、输出质量靠模板加校验（Reflection 让规则干了）。

**效果**：上线三个月零事故，单次成本自主方案的约十分之一；后来数据源换成不可预测的外部 API，才把「取数」环节升级为自主节点——按需局部升级。

### 案例 C：研究助手（自主型，ReAct + Reflection）

**场景**：咨询公司的行业调研助手：给定主题，产出带来源的调研纪要，路径无法预先写出。

**架构**：ReAct 循环驱动（搜索→读网页→记要点→决定下一步）；记忆存放中间发现；反思兜底——每轮结束评估「要点是否都有来源、主题是否覆盖完整」，不达标带着教训再跑一轮；步数上限 20、预算上限 0.5 美元、超限转人工。

**效果**：调研纪要初稿可用率约 70%，单篇平均成本 0.3 美元；反思环节贡献了约 12 个点的可用率提升，代价是成本翻倍——值不值看任务对质量的容忍度。

## 8. 常见坑

1. **为了「先进」上自主 Agent**。架构是手段不是勋章，固定路径任务上自主等于为用不上的灵活性买单。对策：先画任务形状再选型。
2. **跳过任务形状直接选框架**。先有结论再找理由，选型必然拧巴。对策：四问决策树走一遍（单发？查资料？路径固定？路径开放？）。
3. **RAG 型不设检索闸门**。检索到垃圾也硬答，幻觉全算在模型头上。对策：相关度不足就回「资料不足」并转人工。
4. **RAG 型不做引用**。答案不可追溯，用户不敢用。对策：强制引用编号，元数据存来源页码。
5. **工作流节点没有校验与降级**。LLM 节点输出直接进下一步，一处烂尾全线烂尾。对策：每节点配校验规则 + 失败降级路径。
6. **自主型没有步数/预算熔断**。死循环烧钱到天亮。对策：步数上限 + token 预算双阈值，超限上报。
7. **自主型不加反思兜底**。跑完就是终点，错不纠。对策：硬验证器 + 反思循环，2.6 全套。
8. **工具太多不分组**。几十个工具全塞给模型选，选择准确率明显下降。对策：按任务阶段分组暴露，或工具检索（RAG 选工具）。
9. **四模式当互斥阵营**。非要「纯工作流」或「纯自主」。对策：生产系统多为混合体——工作流骨架 + 开放节点 + 人工闸门。
10. **拿「步骤多」当「需要自主」的信号**。步骤多但路径固定，照样是工作流。对策：只看「分支能否穷举」，不看步骤数量。
11. **模式切换不跑评估**。从工作流换自主（或反之）没有回归数据，好坏全凭感觉。对策：同一评测集对比成功率、成本、延迟再切换。
12. **确定性输出任务用自主型**。格式要求严格的任务（合同抽取、报表）用模板+校验远比让模型自由发挥稳。对策：查 LangChain 劝退清单第三条。
13. **忽略升级方向的不对称性**。先简后繁容易，先繁后简基本不可能落地。对策：默认从工作流起步。

1. 把同一个「查库存并回答」需求分别用工具型和工作流型实现，对比成本、延迟与代码量。
2. 用 6.1 骨架搭一个 RAG 型 Agent，然后故意往知识库放一篇过时文档，观察检索闸门和引用机制如何兜底。
3. 给周报机器人写规则校验函数：数字必须来自源数据、段落必须为 5 段，校验失败自动触发修复轮。
4. 实现一个带步数熔断的 ReAct 循环，故意构造一个会死循环的工具，验证熔断生效。
5. 对同一个任务分别用 ReAct 和 Plan-and-Execute 跑 10 次，统计 token 消耗与最终答案质量差异。
6. 把 ReWOO 的「计划不回传中间结果」改造成代码，对比 ReAct 的 token 账单。
7. 按第 4.8 节的组合配方，把「工作流骨架 + 自主节点」拼成一个文档处理流水线，标清每个节点的模式归属。
8. 用 LangChain 劝退清单审查你手头的一个 Agent 项目，写出哪些环节应该降级为工作流。

## 10. 小结

- 四模式按自由度递进：**工具型（单发）→ RAG 型（先查再答）→ 工作流型（代码定路径）→ 自主型（模型定路径）**。
- 选型第一步是**画任务形状**，不是选框架：单发/查资料/路径固定/路径开放，一一对应。
- RAG 型命门在**检索质量**：检索闸门 + 引用 + 知识库更新，生成端只忠于检索结果。
- 工作流型是**生产主力**：可控、可测、可审计，LLM 只在必要节点干活。
- 自主型必配三件：**步数/预算熔断、反思兜底、人工在环**——缺一个不上生产。
- 四范式口诀：**ReAct 管单步灵活、Plan-and-Execute 管长任务不跑偏、ReWOO 管省钱并行、Reflection 管输出质量**。
- 工作流 vs 自主一句话判据：**路径能画成流程图就别上 Agent**（分支可穷举性）。
- LangChain 劝退四条：路径可穷举、单次调用可解、要确定性输出、高频成本敏感。
- 默认先工作流：**升级方向永远比降级好做**；多数生产系统是混合体。
- 模式切换必须过评估：同一评测集比成功率、成本、延迟。
