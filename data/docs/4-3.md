## 1. 定位

L4 实战层第 3 个锚点，回答关键问题：**如何安全执行代码与查询？**

前置依赖：

- 2.3 工具使用 Tool Use：参数校验、错误回传自修——本篇所有「校验层」的机制母版。
- 3.8 安全、合规与权限：最小权限、按任务动态授权、审计留痕——本篇权限线的原则来源。

下游去向：

- H8 Agent 沙箱与可靠执行：把「一次性容器」展开成完整选题，E2B/Firecracker/gVisor 的隔离强度与冷启动取舍。
- 4.10 作品集：一个带沙箱与审计的数据分析 Agent，是「安全设计能力」的最佳展品。

它解决一个根本问题：**数据分析 Agent 的核心矛盾是「能力越强越危险」——让模型写 SQL 和 Python 并执行，效率提升十倍的前提是，最坏情况也被锁死在隔离间里。** 这是 2026 年出现频率很高的原文真题：「Agent 生成的 SQL/代码需要执行，如何设计沙箱环境、权限隔离，避免越权操作、注入攻击？」

## 2. 一句话定义

数据分析 Agent = 翻译官 + 审计员：把自然语言问题翻译成 SQL/Python（注入 Schema 与业务口径），代码与查询先过白名单/AST 校验，再进一次性沙箱以只读账号执行（带超时、行数、内存上限），最后把结果讲成人话并写明数据范围、口径与局限；所有数值必须来自执行结果——查不到就说查不到，严禁编数字。

## 3. 为什么需要

类比：柜员窗口 vs 直接进金库。让 Agent 直连生产数据库，等于让一位能力超强但偶尔听错话的实习生直接进金库点钞——他说「我理解你是要全部删除」时没人拦得住。正确设计是柜员窗口：他只能在窗口（沙箱）办业务，递进来的单据（SQL）先被审核（白名单与只读权限），能取的钱有额度上限（行数/资源限制），每笔业务都有回执（审计日志）。

直连方案与五道防线方案的对比：

| 维度 | 直连生产库 | 五道防线 |
|---|---|---|
| 误删数据 | 一次 UPDATE 无 WHERE 就是事故 | 只读账号：物理上无写权限，想删也删不了 |
| 注入攻击 | 模型拼接的 SQL 直接命中 | AST 校验拒绝多语句/危险结构 |
| 越权查询 | 薪资表、全量表随便看 | 白名单表集与用户角色绑定 |
| 拖垮数据库 | 一个无 LIMIT 全表扫描全站卡顿 | 超时 + 行数上限 + 禁全表扫描 |
| 事后追责 | 查无对证 | 审计日志 5 分钟定位到人 |

最关键的认知：**「让模型在提示词里保证只写安全 SQL」不算防线。** 提示词约束是概率性的——模型偶尔会忽略指令，尤其在复杂问题或注入诱导之下；安全底线必须由代码层的权限/校验兜底。这是面试原题「为什么靠提示词审查不够」的答案内核，也是本篇贯穿始终的哲学：模型当「能力强但偶尔听错话的实习生」，安全不靠自觉，靠窗口与柜台这些确定性结构。

## 4. 核心原理

### 4.1 翻译层：自然语言 → SQL/Python

Agent 的前半身份是翻译官。翻译质量的上限不在模型，在**注入了什么上下文**：

| 注入内容 | 作用 | 缺失后果 |
|---|---|---|
| 表结构 Schema（表/字段/类型/主外键） | 模型知道能查什么、怎么连 | 幻觉字段名，查询报错 |
| 业务口径（指标定义：复购率=？退款计不计入？） | 翻译符合公司定义而非通用定义 | 数字「对」但口径错，误导决策 |
| 示例问答对（few-shot：问→标准 SQL） | 对齐方言与惯例 | 方言错误、风格混乱 |
| 当前用户角色与可见范围 | 翻译时就不碰越权表 | 靠校验层兜底，来回返工 |
| Schema 变更日志 | 字段改名/下线及时同步 | 查询突然大面积失败 |

两个实操要点：一是给 Schema 与口径比给原始数据更准——模型不需要看数据本身，需要看数据的「地图」；二是 **Schema 变更要同步进提示词**，把 Schema 当 Prompt 的一部分做版本管理，否则每次表结构变更都是一次线上事故。

### 4.2 五道防线总览

| 防线 | 属性 | 拦住什么 | 失效时的后果 |
|---|---|---|---|
| ① 只读账号 | 代码层硬防线，与模型聪明程度无关 | DELETE/UPDATE/DDL——最坏情况也改不了数据 | 无此层 = 一切上层防线形同虚设 |
| ② 白名单/AST 校验 | 代码层硬防线 | 注入、跨表越权、「顺带」访问敏感字段 | 越权与注入长驱直入 |
| ③ 沙箱执行 | 隔离层 | 恶意代码、死循环、外传数据 | 主机被生成代码直接攻击 |
| ④ 资源上限 | 稳定性层 | 全表扫描拖垮库、导出千万行 | 单个查询放倒整个系统 |
| ⑤ 审计日志 | 追溯层 | （拦不住但能查）出事 5 分钟定位到人 | 事故变悬案 |

分层纪律：每层各司其职——「能不能查某张表」是白名单/权限层，「代码在哪跑」是沙箱层，「跑多久跑多重」是资源层，「谁干的」是审计层。混着讲等于都没讲清。

### 4.3 只读账号：第一道硬防线

- Agent 使用独立的数据库账号，**只授 SELECT**，物理上无 UPDATE/DELETE/DDL 权限。这与模型聪明程度无关、与提示词无关——是权限系统层面的确定性保证。
- 账号与用户身份绑定：Agent 以「当前用户的代理身份」查询，不同角色用不同账号或行级权限（RLS，Row-Level Security），运营查不到薪资表不是靠校验层拦，而是这个账号本来就没有那张表的授权——两层叠加，纵深防御。
- 测试库与生产库分开配账号与连接串，连接配置里写死库名，杜绝「模型把 FROM 写成生产库」。

### 4.4 白名单与 AST 校验

优先级从高到低：

1. **预定义参数化查询模板**：运营点单（选模板、填参数），SQL 主体由人写好并审过，模型只填占位参数。最安全，适合高频固定报表。
2. **受限自由查询 + AST 校验**：需要灵活探索时，对模型生成的 SQL 做抽象语法树（AST，Abstract Syntax Tree）级校验，过了才放行。关键规则：

| 校验规则 | 拦截的攻击/事故 |
|---|---|
| 只允许 SELECT，拒绝 INSERT/UPDATE/DELETE/DROP/ALTER/GRANT 及多语句 | 写操作与注入 |
| 解析 AST 上的表名，限定在角色可见表集合内 | 越权访问（薪资表、日志表） |
| 列级白名单，敏感列（salary/id_card）按角色拒绝 | 字段级越权 |
| 强制 LIMIT 且设上限，无 LIMIT 自动注入或拒绝 | 失控大结果集 |
| 拒绝注释截断、十六进制编码、拼接可疑结构 | 绕过类注入手法 |
| 执行前 EXPLAIN 检查执行计划，禁全表扫描 | 拖垮数据库 |

为什么必须是 AST 而不是关键词过滤：关键词「黑名单」能被注释、大小写、编码、嵌套子查询轻松绕过；AST 拿到的是语句的结构本身，绕无可绕。这是「白名单优先于自由查询」的工程含义。

### 4.5 一次性容器沙箱与资源上限

Python 线的核心纪律：**模型生成的代码是不可信输入，绝不进主机直接跑。**

| 机制 | 做法 | 拦截 |
|---|---|---|
| 一次性容器/微 VM | 每次执行新建容器，执行完即销毁 | 状态残留、横向渗透、指纹沉淀 |
| 网络隔离 | 默认 `--network none`，或仅白名单出口 | 死循环外联、数据外传、下载恶意包 |
| 文件系统 | 只挂载白名单目录；根文件系统只读 | 读写主机任意文件 |
| 资源配额 | 内存/CPU/PID 上限 | fork 炸弹、内存耗尽 |
| 超时强杀 | 硬超时（如 15 秒）到点 kill | 死循环 |
| 产物回传 | 执行产物（图表文件等）经扫描后回传 | 借产物夹带数据 |

选型梯度（详见 H8）：裸容器 < gVisor 类用户态沙箱 < Firecracker/E2B 类微 VM（microVM），隔离强度递增、冷启动开销递增。数据探索类任务的共识是「一次性容器 + 断网 + 配额」起步，平台化后再上微 VM 池。

### 4.6 结果解释带前提 + 幻觉数字红线

Agent 的后半身份是审计员。结果解释不是「把表格念一遍」，而是带着前提的翻译：

```text
结论：……（先说人话结论）
数据范围：基于哪些表、什么时间范围、什么过滤条件
口径说明：指标是怎么定义的（复购率=？退款订单计不计入？）
局限：没覆盖什么（线下渠道？样本量？）
下一步：如需换口径对比，我可以重跑
```

不带前提的解释是危险的：一个口径错误的精确数字，比一个粗略数字更能误导决策。**数字对但口径错，是最隐蔽的分析事故。**

幻觉数字红线：Agent 严禁「编」数字——所有数值必须来自查询结果，查不到就说「库里没有这个指标/该时间范围无数据」。落地两件事：一是 Prompt 硬约束 + 输出校验（答案中的数字必须能在执行结果中找到，见 4-2 的数值回验思路）；二是评估时专测「数据库里没有的指标」类问题——这类问题答得越流畅越可疑。

## 5. 架构 / 流程

一次自然语言查数的完整链路，五道防线标注在位：

```text
用户问题：「上季度华东区复购率最高的三个品类？」
   │
   ▼
┌────────────────────────────────────────────────┐
│ 翻译层（4.1）                                    │
│ Schema + 业务口径 + few-shot + 用户角色 → LLM     │
│ 输出：SQL（或 Python 分析代码）                    │
└────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────────────────────────────┐
│ 校验层（防线②）AST 校验                           │
│ 只读语句？表在白名单？列在白名单？LIMIT 合规？     │
│   └─ 不过 → 结构化错误回传 LLM 自修（≤2 次）      │
│       仍不过 → 拒答 + 记 badcase                  │
└────────────────────────────────────────────────┘
   │ 通过
   ▼
┌────────────────────────────────────────────────┐
│ 执行层（防线①③④）                                │
│ 只读账号 + EXPLAIN 计划检查                       │
│ 一次性容器（断网/只读挂载/配额）+ 超时 15s 强杀    │
│ 返回行数 ≤ 上限，脱敏后回传                       │
└────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────────────────────────────┐
│ 解释层（4.6）                                    │
│ 数值回验（答案中的数字 ∈ 执行结果）                │
│ 结论 + 数据范围 + 口径 + 局限 + 下一步             │
└────────────────────────────────────────────────┘
   │
   ▼
审计日志（防线⑤）：谁、何时、什么 SQL、返回多少行 —— 全部落盘可检索
```

## 6. 代码 / 工具

### 6.1 SQL AST 校验器

```python
# sql_guard.py —— AST 级白名单校验：结构上封死越权与注入
import sqlglot
from sqlglot import exp

ALLOWED_TABLES = {"orders", "order_items", "products", "users_profile"}
ALLOWED_COLUMNS = {                       # 列级权限：与用户角色绑定（示例：运营角色）
    "orders": {"id", "user_id", "amount", "status", "region", "created_at"},
    "products": {"id", "name", "category", "price"},
    "order_items": {"order_id", "product_id", "qty", "price"},
    "users_profile": {"id", "region", "register_at"},   # 无 salary / id_card
}
FORBIDDEN = (exp.Insert, exp.Update, exp.Delete, exp.Drop, exp.Alter,
             exp.Create, exp.Grant, exp.Command)          # 只读：禁 DML/DDL/命令
MAX_LIMIT = 1000

def validate_sql(sql: str) -> tuple[bool, str]:
    try:
        stmts = sqlglot.parse(sql, read="mysql")
    except sqlglot.errors.ParseError as e:
        return False, f"SQL 解析失败：{e}"
    if not stmts:
        return False, "空查询"
    if len(stmts) > 1:                                    # 多语句=典型注入形态
        return False, "禁止多语句"
    stmt = stmts[0]
    if isinstance(stmt, FORBIDDEN):
        return False, "只允许 SELECT"
    if not isinstance(stmt, exp.Select):
        return False, "只允许 SELECT"
    for t in stmt.find_all(exp.Table):                    # ① 表白名单
        if t.name.lower() not in ALLOWED_TABLES:
            return False, f"越权表：{t.name}"
    for c in stmt.find_all(exp.Column):                   # ② 列白名单
        tbl = c.table or _resolve_table(stmt, c.name)
        if tbl and c.name.lower() not in ALLOWED_COLUMNS.get(tbl.lower(), set()):
            return False, f"越权或不存在列：{tbl}.{c.name}"
    if not stmt.args.get("limit"):                        # ③ 强制 LIMIT
        return False, f"必须带 LIMIT ≤ {MAX_LIMIT}"
    lim = stmt.args["limit"].expression.name
    if not lim.isdigit() or int(lim) > MAX_LIMIT:
        return False, f"LIMIT 超上限（≤ {MAX_LIMIT}）"
    return True, "ok"

def _resolve_table(stmt, col_name: str) -> str | None:
    """无表前缀的列：在 FROM/JOIN 里找唯一包含该列的表。"""
    owners = [t.name for t in stmt.find_all(exp.Table)
              if col_name.lower() in ALLOWED_COLUMNS.get(t.name.lower(), set())]
    return owners[0] if len(owners) == 1 else None

# 校验失败的正确姿势：不终止任务，把错误回传让模型自修（2.3 的机制母版）
if __name__ == "__main__":
    bad = "SELECT name, salary FROM employees; DROP TABLE orders"
    ok, msg = validate_sql(bad)
    print(ok, msg)   # False 禁止多语句 —— 注入与越权一条都过不去
```

### 6.2 一次性容器沙箱执行器

```python
# sandbox_runner.py —— 生成代码进一次性容器：断网、配额、超时强杀、用完即毁
import subprocess, tempfile, os, uuid, shutil, json

IMAGE = "python:3.12-slim"
TIMEOUT_SEC, MEM, CPUS, PIDS = 15, "512m", "1.0", "128"

def run_generated_code(code: str, inputs: dict | None = None) -> dict:
    """每次执行 = 新建临时目录 + 新建容器，跑完销毁。主机只与产物交互。"""
    workdir = tempfile.mkdtemp(prefix=f"sbx-{uuid.uuid4().hex[:8]}")
    try:
        for name, content in (inputs or {}).items():     # ① 输入文件落白名单目录
            with open(os.path.join(workdir, name), "w") as f:
                f.write(content)
        with open(os.path.join(workdir, "main.py"), "w") as f:
            f.write(code)
        cmd = [
            "docker", "run", "--rm",                     # ② 用完即毁
            "--name", f"sbx-{uuid.uuid4().hex[:8]}",
            "--network", "none",                         # ③ 默认断网：封外传通道
            "--memory", MEM, "--cpus", CPUS,             # ④ 资源配额
            "--pids-limit", PIDS,                        #    防 fork 炸弹
            "--read-only", "--tmpfs", "/tmp:size=64m",   # ⑤ 根文件系统只读
            "-v", f"{workdir}:/work:ro",                 # ⑥ 输入只读挂载
            "-w", "/work", IMAGE, "python", "main.py",
        ]
        try:
            p = subprocess.run(cmd, capture_output=True,
                               timeout=TIMEOUT_SEC, text=True)
            result = {"ok": p.returncode == 0,
                      "stdout": p.stdout[-4000:], "stderr": p.stderr[-2000:]}
        except subprocess.TimeoutExpired:
            result = {"ok": False, "error": f"超时 {TIMEOUT_SEC}s 强杀"}
        audit_log(user="agent", stage="sandbox", **result)   # ⑦ 审计留痕（防线⑤）
        return result
    finally:
        shutil.rmtree(workdir, ignore_errors=True)       # ⑧ 现场清理，不留状态

if __name__ == "__main__":
    print(run_generated_code("import pandas as pd; print(pd.__version__)"))
```

## 7. 案例

### 案例 A：某电商运营自助查数平台

**场景**：运营每天提几十个取数需求，数据组排期 2 天起步；上线数据分析 Agent 自助查数。

**实施**：模板查询（Top 20 高频报表）+ 受限自由查询双轨；只读账号按角色分 4 档；SQL 过 AST 校验，Python 进一次性容器；全部执行留审计。

**效果**（示意量级）：常规取数从 2 天人力排期降到 3 分钟自助；AST 校验日均拦截越权/危险 SQL 约 40 次（主要是误碰日志表与无 LIMIT 查询）；上线一年零数据写入事故、零越权成功案例。

### 案例 B：一次越权拦截复盘

**症状**：某运营同学问「按部门看人均薪酬分布」，校验层返回「越权表：salary_view」。

**排查**：模型在翻译时把「薪酬」匹配到了库名相似的人事表——翻译层不知道角色边界，是校验层拦下的。暴露的问题：Schema 注入里没标角色可见范围，模型每必然要撞一次墙。

**修复**：给每个角色注入「可见表清单」进翻译层；校验失败的错误信息结构化（指明可见表），让模型自修成「该指标无数据权限」的如实回答。

**效果**：此类往返从日均 40 次降到 3 次以内。教训：**校验层是最后的墙，不是唯一的墙——翻译层就应知道角色边界，防线要纵深，不要单点。**

### 案例 C：幻觉数字红线的评估

**场景**：专测「数据库里没有的指标」类问题（如「查看 IP 属地转化率」——库中无 IP 字段）。

**基线**：不加约束时，模型 18% 的问题给出流畅但编造的数字（如「转化率 12.3%」），这是最危险的失败——错得自信。

**治理**：Prompt 硬约束（「结果集中没有的数字一律不得出现」）+ 数值回验（答案中的数字必须能在执行结果中找到）+ 查不到的标准话术（「当前数据范围没有该指标，可选的相近指标是……」）。

**效果**：编造数字率从 18% 压到 1.2%，残余案例全部进入回归集。红线检查进了每次改版的必跑评估。

## 8. 常见坑

1. **把提示词当防线**。对策：「只写安全 SQL」是概率性软约束，安全属性必须落在代码层硬防线。
2. **关键词黑名单代替 AST 校验**。对策：注释、编码、嵌套子查询都能绕关键词；AST 校验结构本身。
3. **只校验不回传**。对策：校验失败把结构化错误回传让模型自修，直接终止会逼用户换问法。
4. **沙箱有网络**。对策：默认断网或白名单出口，否则生成的代码可以外传数据、下载恶意包。
5. **无超时**。对策：硬超时强杀，死循环是最常见的「软事故」。
6. **返回行数无上限**。对策：强制 LIMIT + 上限 + EXPLAIN 禁全表扫描，单个查询能放倒整库。
7. **容器复用**。对策：一次性执行用完即毁，状态残留会污染下次结果并扩大渗透面。
8. **Schema 变更不同步**。对策：Schema 进 Prompt 做版本管理，表结构变更必须触发 Prompt 更新与回归。
9. **结果解释不带前提**。对策：结论必须配数据范围、口径、局限——口径错的精确数字最误导。
10. **允许 Agent 编数字**。对策：数值回验 + 「查不到就说查不到」话术，专测库里没有的指标。
11. **测试库生产库混用**。对策：连接配置写死库名、分开配账号，杜绝「模型把 FROM 写成生产库」。
12. **无审计日志**。对策：谁、何时、什么 SQL、返回多少行全部落盘——出事 5 分钟定位到人。
13. **Agent 用超级管理员账号图省事**。对策：只读账号是第一道硬防线，权限最小化从账号开始。

## 10. 小结

- 核心矛盾：**能力越强越危险**——把模型当「能力强但偶尔听错话的实习生」，安全靠窗口与柜台，不靠自觉。
- 翻译层注入四件套：**Schema、业务口径、few-shot、用户角色**；Schema 变更要同步进 Prompt。
- 第一道硬防线是**只读账号**：与模型聪明程度无关的、代码层的权限底线。
- 白名单优先于自由查询；自由查询必须过 **AST 校验**：只读、表白名单、列白名单、强制 LIMIT、拒注入结构。
- 生成的 Python 是不可信输入，必须进**一次性容器/微 VM**：断网、只读挂载、资源配额、超时强杀、用完即毁。
- **资源上限**保的是数据库与系统：超时、行数上限、禁全表扫描。
- 结果解释必须**带前提**：数据范围、口径、局限——口径错的精确数字比粗略数字更危险。
- **幻觉数字是红线**：所有数值来自执行结果，查不到就说查不到；评估专测库里没有的指标。
- 提示词约束是软约束，面试原题「为什么靠提示词审查不够」的答案内核就在这一句。
- 审计日志是追溯底线：谁、何时、什么 SQL、返回多少行，出事 5 分钟定位到人。
- SQL 线四层：只读账号→白名单/AST→资源上限→审计；Python 线：一次性沙箱。共同哲学：硬防线在代码层。
- 沙箱选型深挖（容器 vs gVisor vs Firecracker/E2B）在 H8；权限原则来源在 3.8。
