## 1. 定位

Agent 四件套的「总线」：规划、工具、记忆都在循环里被逐步消费。它解决一个根本问题：**如何让 Agent 一步步逼近目标，同时保证循环必然终止、失败可恢复、失控有刹车？**

前置依赖：

- 2.2 规划 Planning：任务拆解结果就是循环的「待办清单」。
- 2.3 工具使用 Tool Use：循环的每一拍 Action 都是一次受防护的工具调用；四件套防护是循环层的地基。
- 2.4 记忆 Memory：循环每一步从记忆取上下文，把中间结论写回去。

后续展开：

- 2.6 反思与自我修正：循环结束后的自我评估回路。
- 2.7 单 Agent 架构模式：ReAct、Plan-and-Execute 等范式在架构层的对比。
- 3.3 编排框架与运行时：LangGraph 等图编排的生产化。
- 2.9 Agent 评估与安全：轨迹评估与安全审计。

面试定位：**「什么是 ReAct？工作流程是怎样的？」是 Agent 方向的第 1 号敲门题**；延伸追问必然是失败模式与防失控——正好是本篇两大半。

## 2. 一句话定义

执行循环（Agent Loop）是 Agent 的基本运行节拍：**思考（Thought）→ 行动（Action）→ 观察（Observation）循环推进，直到得出最终答案或触发终止条件**。状态机（State Machine）是它的工程化形态：把「当前处于哪一步、允许去哪一步」显式建模，配合 checkpoint（检查点）实现中断恢复——**循环负责前进，状态机负责可控**。

## 3. 为什么需要

LLM 单次调用是「一口气答完」，但复杂任务做不到：

1. **信息不全**：后面的路取决于前面的结果——不查名单就不知道该跟踪谁，不比价就不知道订哪班。
2. **单次调用无法执行动作**：查、算、写需要多步外部交互。
3. **错误需要反馈修正**：第一步的失败信息要能改变第二步的决策。

ReAct（Reasoning + Acting，2022 年提出）的核心洞察：**让推理决定行动、让行动结果修正推理，交替推进**。只推理不行动是纸上谈兵，只行动不推理是无头苍蝇。

但裸循环有三种必然失控（机制根源见 4.4）：

| 失控 | 表现 | 后果 |
|---|---|---|
| 永不终止 | 失败→重试→失败→重试 | 烧钱、超时、拖垮上游 |
| 轨迹膨胀 | 轨迹涨到几万字 | 注意力稀释、忘记目标、原地打转 |
| 信号污染 | 空串/堆栈/重复观察被当真 | 每一步决策被误导 |

结论：**没有终止条件的循环就是事故**。生产级执行循环 = ReAct 节拍 + 硬性终止 + 轨迹管理 + 状态机恢复，缺一不可。

## 4. 核心原理

### 4.1 ReAct 循环节拍

三拍循环，每一拍是一次 LLM 调用或一次工具执行：

| 拍 | 角色 | 产生者 | 常见形态 |
|---|---|---|---|
| Thought | 当前处境分析 + 下一步决策依据 | 模型生成 | 「市值是实时数据，应调用搜索」 |
| Action | 具体调用：工具名 + 参数 | 模型生成 | `web_search({"query": "特斯拉 最新市值"})` |
| Observation | 真实执行结果 | **系统回填，禁止模型编造** | 「返回：约 1.1 万亿美元（今日收盘）」 |

三个实操要点：

- **格式化提示词**：固定 Thought/Action/Observation 字段 + 1~2 个完整 few-shot 示例 + 停止符；明确声明「Observation 由系统填充，禁止自己编造」。让模型自己填 Observation 是幻觉事故的直接来源。
- **现代实现 = Function Calling + 循环**：原生工具调用 API 里，Action 变成结构化 `tool_calls`，Thought 变成 `assistant` 消息内容，Observation 变成 `tool` 角色消息——格式化文本协议的工程化替代。
- **每拍要过防护**：Action 出来先过 2.3 的参数校验与指纹熔断，Observation 回来按 `retriable` 决定换路——循环层不做防护，等于裸奔。

### 4.2 终止三条件

| 条件 | 触发信号 | 终止后动作 |
|---|---|---|
| 得出答案 | 模型输出 Final Answer / 不再发起工具调用 | 正常返回，落轨迹 |
| 达到上限 | 最大步数（如 12 步）或 token/费用预算任一触达 | **强制终止**，汇总已有进展转人工或降级 |
| 触发人工 | 不可逆动作待确认 / 指纹熔断后仍无路可走 / 失败超限 | 暂停等待人工输入，或转工单 |

机制层认知（面试采分点）：**循环的终止动力来自「观察到成功」——观察持续失败时，模型没有内建的「放弃」机制，只有外部阈值能保证终止**。所以提示词里写「请不要循环」是软约束；步数/预算双阈值是不依赖模型自觉的硬刹车，也是唯一「必然终止」的保证。

### 4.3 轨迹管理与裁剪

轨迹（Trajectory）= 累积的 Thought + Action + Observation 序列，既是上下文也是复盘材料。任务 20 步、每步观察 2000 字，轨迹就到几万字——**轨迹管理不是优化项，是正确性前提**。

| 手段 | 做法 | 解决什么 |
|---|---|---|
| 目标前置 | 目标固定在系统提示最前部，每 K 步重申一次 | 目标漂移 |
| Observation 摘要 | 超过 N 轮的观察压成一句关键结论（保留数值/错误码/状态） | 轨迹膨胀 |
| 状态外置 | 维护结构化「任务清单/已完成项」状态块，每轮固定注入最前部 | 忘记进度、重复已做动作 |
| 失败显式标记 | 失败工具在后续轮次以「此前已失败」标记再次出现 | 引用失败工具、重入失败路径 |
| 大结果截断 | 超长工具返回在执行层截断/摘要后再入轨迹 | 单拍撑爆窗口 |
| 轨迹落盘 | 每拍完整写入轨迹存储（供 2.9 评估与 3.4 追踪） | 无法复盘调优 |

裁剪原则：**裁内容不裁结论**——旧观察的原文可删，但其关键结论（成功/失败、数值、错误码）必须以摘要或状态块形式保留，否则模型会「忘了做过什么」而重复劳动。

### 4.4 失败模式与机制根源

L2 会用循环，工程师要能从机制层解释失控（与 2.3 四件套一一对应）：

| 失败模式 | 机制根源 | 工程刹车 |
|---|---|---|
| 死循环（不终止） | 终止动力来自观察成功；持续失败时模型无「放弃」机制 | 最大步数 + 预算双阈值；重复指纹熔断 |
| 跑偏（目标漂移） | 轨迹变长稀释注意力，早期目标被挤到低效区（lost in the middle） | 目标固定前置 + 阶段性重申；状态外置 |
| 工具反复失败 | 失败被当普通结果回传，模型原样重试 | 结构化错误回传 + retriable 分类 + 重试上限退避 |
| 重复劳动 | 模型对「已完成状态」失去感知 | 状态块注入 + 已完成项打勾 |
| 信号污染 | 模型无法区分「空结果」与「工具故障」 | 系统显式标注失败；严禁空串/堆栈 |
| 不可逆误操作 | 写动作在错误路径上被执行 | 不可逆动作强制人工在环 |

诊断口诀：重复已做动作 = 状态感知丢失；引用失败工具 = 失败信号被淹没；原地打转 = 终止动力缺失。**机制层的病要靠机制层的药**——换更强模型不是解法。

### 4.5 状态机与图编排

裸 `while` 循环的问题是「所有步骤共用一条无差别的路径」：无法表达「订票必须先查后订」「失败只能回到重规划节点」。状态机把流程显式建模：

- **状态（State/Node）**：规划、执行、校验、等待确认、汇总……每个节点职责单一。
- **边（Edge）**：节点间的合法转移，含条件边（校验通过 → 执行；失败 → 重试或转人工）。
- **图编排（Graph Orchestration）**：LangGraph 等框架把状态机做成「节点 = 函数、边 = 转移逻辑」的图，共享一个显式的状态对象。

三种流程控制形态的取舍：

| 形态 | 结构 | 适合 | 风险 |
|---|---|---|---|
| 固定工作流 | 代码写死的步骤链 | 流程确定的场景（表单处理） | 不灵活，改流程要改代码 |
| 状态机 / 图 | 显式节点 + 条件边 | 步骤可枚举、需审批与恢复的流程 | 建模成本 |
| 自治循环 | 模型自主决定下一步 | 开放任务（研究、探索） | 失控面最大，防护要求最高 |

**Checkpoint（检查点）机制**（以 LangGraph 为例）：每执行完一个节点，把完整状态（消息、中间变量、步数计数）持久化到存储。三个直接收益：

1. **中断恢复**：进程崩溃、超时被杀后，从最近 checkpoint 加载状态继续跑，不必从头重来。
2. **人工介入挂起**：跑到需确认的节点时把图停住（interrupt），状态已落盘；人工批准后从该节点恢复。
3. **时间旅行调试**：回放到任意历史 checkpoint，复现与修改决策（配合 3.4 可观测性）。

### 4.6 中断恢复与人工介入

人工在环（Human-in-the-Loop）在循环里有两个标准挂点：

| 挂点 | 触发 | 恢复动作 |
|---|---|---|
| 审批型中断 | 不可逆动作（出票/退款/删除）待执行 | 人工批准 → 恢复执行；拒绝 → 回到重规划或终止 |
| 求助型中断 | 工具反复失败 / 熔断触发 / 步数触顶 | 汇总进展 + 卡点 + 建议转人工；人工补信息后继续 |

恢复的关键工程点：

- **幂等恢复**：checkpoint 恢复后，已成功的工具调用不能重打（用 2.3 的幂等键与完成标记）。
- **状态一致性**：恢复时先校验外部世界（订单是否已创建），再决定从哪一步继续。
- **人工输入也是 Observation**：审批结果以结构化 Observation 回注轨迹，模型据此继续，而不是开新会话。

## 5. 架构 / 流程

带防护与状态机的执行循环全图：

```text
                 ┌──────────────────────────────┐
                 │  初始化：目标 + 工具清单 + 记忆注入 │
                 └──────────────┬───────────────┘
                                ↓
        ┌───────────────────────────────────────────┐
        │           ReAct 主循环                     │
        │                                           │
        │  Thought ← 模型（读目标/状态块/轨迹摘要）     │
        │     ↓                                     │
        │  Action  → [校验] → [指纹熔断] → 工具执行    │
        │     ↓              失败: 结构化错误回传       │
        │  Observation（系统回填，摘要压缩后入轨迹）     │
        │     ↓                                     │
        │  [终止检查] ──答案──→ Final Answer          │
        │     │ 步数/预算触顶 → 强制终止 → 汇总转人工    │
        │     │ 不可逆动作 → 挂起 → 人工确认 → 继续     │
        │     └ 否则回到 Thought                      │
        └───────────────────────────────────────────┘
                                ↓ 每拍落盘
                 ┌──────────────────────────────┐
                 │ Checkpoint 存储：状态 + 轨迹    │
                 │ 中断恢复 / 时间旅行 / 复盘评估   │
                 └──────────────────────────────┘
```

状态机视角的节点转移清单：

```text
PLAN ──(有子任务)──→ EXECUTE ──(成功)──→ VERIFY
 │                                            │
 │(直接可答)──→ ANSWER                 (通过)──┴──→ 下一个子任务 / ANSWER
 │                                            │
 └────────────── (失败≤2次) ────── REPLAN ←─(失败>2次)
                                   │
                          (仍失败/触顶) → ESCALATE（转人工）
```

## 6. 代码 / 工具

### 6.1 ReAct 主循环 + 步数熔断

```python
import json
from docs2_3 import TOOL_REGISTRY, dispatch, to_observation  # 2.3 的注册表

MAX_STEPS = 12          # 硬刹车 1：步数上限
BUDGET_TOKENS = 60_000  # 硬刹车 2：token 预算

def react_loop(question: str, llm_call, used_tokens=0):
    messages = [
        {"role": "system", "content": (
            "你是任务执行 Agent。逐步思考并调用工具完成任务。"
            "Observation 由系统回填，禁止自己编造。"
            "信息足够时输出 Final Answer。")},
        {"role": "user", "content": question},
    ]
    fp_counter = {}     # （工具+参数）指纹计数，见 2.3
    history = []        # 轨迹：[(thought, action, obs)]，供落盘与复盘

    for step in range(1, MAX_STEPS + 1):
        # 终止条件 2：预算触达 → 强制终止
        if used_tokens >= BUDGET_TOKENS:
            return finalize(history, reason="预算耗尽", escalate=True)

        resp = llm_call(messages, tools=list(TOOL_REGISTRY))
        used_tokens += resp.usage.total_tokens

        # 终止条件 1：模型给出最终答案
        if not resp.tool_calls:
            return {"answer": resp.content, "steps": step,
                    "history": history, "escalated": False}

        thought = resp.content or "(silent)"   # Thought 拍
        for call in resp.tool_calls:           # Action 拍（支持并行）
            result = dispatch(call.name, json.loads(call.arguments),
                              fp_counter=fp_counter)
            obs = to_observation(result)       # Observation 拍：系统回填
            obs = compress(obs, max_chars=800) # 超长观察摘要，控轨迹膨胀
            messages.append(tool_msg(call.id, obs))
            history.append({"step": step, "thought": thought,
                            "action": f"{call.name}({call.arguments})",
                            "observation": obs})
        # 循环尾部：每拍落 checkpoint（伪码）
        # checkpoint.save(step, messages, used_tokens, fp_counter)

    # 终止条件 2：步数触达 → 强制终止，汇总转人工
    return finalize(history, reason="达到最大步数", escalate=True)

def finalize(history, reason, escalate):
    summary = "\n".join(f"[{h['step']}] {h['action']} -> {h['observation']}"
                        for h in history[-5:])   # 近 5 拍进展
    return {"answer": None, "escalated": escalate,
            "reason": reason,
            "handoff": f"已完成进展：\n{summary}\n卡点：{reason}"}
```

### 6.2 轨迹裁剪与状态外置

```python
def build_context(question, done_list, trajectory, keep_recent=5):
    """每拍组装上下文：目标前置 + 状态块 + 压缩轨迹 + 近期原文"""
    traj_digest = "\n".join(
        f"- {t['action']}: {digest(t['observation'])}"   # 旧观察压成一行结论
        for t in trajectory[:-keep_recent])
    recent = "\n".join(render(t) for t in trajectory[-keep_recent:])
    checklist = "\n".join(
        f"{'[x]' if d['done'] else '[ ]'} {d['task']}" for d in done_list)
    return f"""[目标] {question}        ← 固定最前，防目标漂移
[任务状态]                        ← 状态外置，防重复劳动
{checklist}
[早前轨迹摘要]
{traj_digest or '（无）'}
[最近 {keep_recent} 拍]
{recent}"""
```

### 6.3 LangGraph 状态机：checkpoint + 人工中断

```python
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.checkpoint.memory import MemorySaver

def plan(state):        # 规划节点：拆子任务写入 state["tasks"]
    ...
def execute(state):     # 执行节点：取下一子任务调工具
    ...
def check(state):       # 终止判断：全部完成 / 步数触顶
    ...
def ask_human(state):   # 审批节点：不可逆动作前挂起
    ...

g = StateGraph(MessagesState)
g.add_node("plan", plan); g.add_node("execute", execute)
g.add_node("check", check); g.add_node("ask_human", ask_human)

g.add_edge(START, "plan")
g.add_edge("plan", "execute")
g.add_conditional_edges("execute", check, {
    "continue": "execute",        # 还有子任务 → 继续执行
    "need_approval": "ask_human", # 不可逆动作 → 人工挂起
    "done": END,                  # 完成 → 终止
})
g.add_edge("ask_human", "execute")  # 批准后从断点恢复执行

app = g.compile(checkpointer=MemorySaver())   # 每节点后自动落 checkpoint

# 运行：interrupt 时挂起等待；人工批准后同 thread_id 恢复
cfg = {"configurable": {"thread_id": "run-42"}}
result = app.invoke({"messages": [...]}, cfg)
# 崩溃后恢复：同 thread_id 重新 invoke，从最近 checkpoint 继续
```

## 7. 案例

### 案例 A：订票 Agent 的死循环截停

**场景**：某差旅 Agent 高峰期查航班接口超时，失败被当普通文本回传，模型「道歉→再查→再超时」打转；单会话最高 60 余步，一晚烧掉万元级 token。

**治理**：结构化错误回传（`TIMEOUT` + 建议「改用备用票源」）；同一调用指纹连续 2 次熔断；最大步数 12 + 单会话 token 预算双阈值；出票前强制人工确认。

**效果**：单会话步数 P95 从 15 降到 6；超时场景任务完成率从 40% 升到 78%（模型拿到建议后真的换路）；异常成本压到百元级。

### 案例 B：30 步长任务的「健忘症」修复

**场景**：某数据分析 Agent 跑 30+ 步长任务，后半程开始重复已做过的查询、引用早已失败的工具，产出前后矛盾。

**诊断**：长轨迹稀释注意力——早先的成功观察被挤出有效窗口，模型对「已完成状态」失去感知。

**修复**（三条机制层药方）：状态外置——结构化任务清单每轮注入上下文最前部；轨迹压缩——超过 5 拍的观察压成一行结论（保留数值与错误码）；失败显式标记——失败工具在后续轮次以「此前已失败」标注并配合熔断防重入。

**效果**：同批长任务回归，重复动作率从约 35% 降到 4%，平均步数从 34 降到 21，产出一致性显著改善。

### 案例 C：图编排的中断恢复

**场景**：一家金融科技公司的报表 Agent 跑批约 40 分钟，此前裸 while 循环实现：夜间上游抖动导致中途崩溃，只能整单重跑，且资金调拨类动作缺人工闸口。

**改造**：迁移到 LangGraph——plan/execute/check/ask_human 四节点 + 条件边；每节点后自动 checkpoint；资金调拨节点设为 interrupt 挂起等审批；崩溃后同 thread_id 从最近检查点恢复，幂等键防止已成功调用重打。

**效果**：单点故障重跑率从约 20% 降到近 0，平均节省 30 分钟级返工；调拨动作 100% 经人工审批；轨迹落盘后 bad case 可逐节点回放定位。

## 8. 常见坑

1. **没有最大步数**。失败动作上无限循环烧钱。步数 + 预算双阈值是唯一保证终止的硬刹车。
2. **让模型自己编 Observation**。它会把想象结果当真继续推进。Observation 必须由系统回填真实执行结果。
3. **轨迹只增不裁**。几万字轨迹稀释注意力，忘记目标、重复劳动。旧观察摘要化 + 状态外置 + 近期保原文。
4. **目标只在开头说一次**。轨迹一长目标就被淹没。目标固定在系统提示最前，每 K 步重申。
5. **失败回传空串或堆栈**。模型无法区分「没结果」与「工具坏了」。结构化错误 + 显式失败标记。
6. **只截断不保留结论**。裁掉旧观察原文却连关键数值一起丢了。裁内容不裁结论，摘要里必须留数值/错误码/状态。
7. **熔断后直接弃单**。应汇总「已完成什么、卡在哪、建议怎么办」转人工，而不是静默失败。
8. **不可逆动作不设人工闸口**。出票、退款、删除必须挂起审批；拒绝后回重规划，不是换个说法再执行一次。
9. **恢复后重复执行已完成调用**。缺幂等键与完成标记，checkpoint 恢复变重复扣款。恢复前先对外部世界做一致性校验。
10. **每拍都全量重发整条轨迹**。成本与延迟线性爆炸。用摘要 + 状态块控制每拍上下文规模。
11. **开放任务用固定工作流硬套**。步骤无法枚举时图会退化成巨大的状态爆炸；开放探索任务用自治循环 + 强防护，确定流程才用图。
12. **无轨迹落盘**。失控后无从复盘「哪一步开始偏」。每拍完整落盘，接 3.4 追踪与 2.9 评估。
13. **把「换更强模型」当解法**。失控是机制问题不是智力问题——阈值、熔断、状态外置这些工程刹车换任何模型都要装。

## 9. 练习

1. 手写一个三拍 ReAct 循环跑通「查天气 → 决定穿衣建议」，观察每拍的 Thought/Action/Observation。
2. 给循环加双阈值：把 MAX_STEPS 设为 3，构造一个 5 步任务，验证强制终止与 handoff 汇总。
3. 实现（工具+参数）指纹计数，让模型重复调用同一失败工具，观察熔断注入「请换策略」后的行为变化。
4. 对比实验：同一 15 步任务，「全量轨迹」vs「摘要+滑窗+状态块」两种上下文组装，统计步数与口径一致率。
5. 用 LangGraph 搭四节点图（plan/execute/check/ask_human），在写动作前挂起，模拟批准与拒绝两条路径。
6. 制造一次中途崩溃（kill 进程），用同一 thread_id 从 checkpoint 恢复，验证幂等：已成功的调用不重打。
7. 把一个固定流程任务分别用「写死的函数链」和「状态机图」实现，对比改需求（加一步审批）时的改动成本。
8. 收集 10 条失控轨迹（死循环/跑偏/重复劳动），按 4.4 的失败模式分类归因，写出各自的机制根源与刹车。

## 10. 小结

- ReAct = Reasoning + Acting：**Thought→Action→Observation** 循环至 Final Answer，推理决定行动、观察修正推理。
- Observation 由**系统回填**真实结果，格式化提示词 + few-shot + 停止符是基本盘；现代实现 = Function Calling + 循环。
- **终止三条件**：得出答案 / 达到步数与预算上限 / 触发人工——终止动力来自观察成功，失败时只有外部阈值保证终止。
- **轨迹管理是正确性前提**：目标前置、旧观察摘要、状态外置、失败显式标记、大结果截断、全程落盘。
- 失败模式有机制根源：不终止（无放弃机制）、跑偏（注意力稀释）、反复失败（失败语义丢失）、重复劳动（状态感知丢失）——机制层的病用机制层的药。
- 状态机/图编排把「可控」显式化：节点单一职责、条件边限定转移、非法路径不存在。
- **Checkpoint 三收益**：中断恢复、人工挂起、时间旅行调试；恢复必须配幂等键与一致性校验。
- 人工在环两个挂点：审批型（不可逆动作前）与求助型（熔断/触顶后），人工输入以 Observation 回注轨迹。
- 生产循环 = ReAct 节拍 + 2.3 四件套防护 + 双阈值硬刹车 + checkpoint 可恢复 + 轨迹可复盘。
