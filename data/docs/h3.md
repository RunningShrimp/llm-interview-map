## 1. 定位

S4 前沿层第 3 个锚点（deps：1-5、2-4）。站点状态口径：**面试出现中**，且是 H 层证据最强考点之一——2026 年出现多个独立专项面试指南（其中一份直言 context engineering 已出现在「几乎所有高级 ML/AI 工程面试」中），Anthropic 官方工程博客与 Cookbook 已把三原语做成 API 级实践（2026-03）。

它回答 Agent 岗的新主考题：**长任务 Agent 为什么越干越糊涂？怎么系统性治理？**

四个支柱：

1. **概念层**：与提示词工程的边界——超集关系，不是同义词。
2. **方法层**：三原语（压缩 compaction / 记忆工具 / 子代理隔离）+ just-in-time 检索。
3. **诊断层**：长任务上下文衰退的机制，以及「越用越慢」类真题的原理拆解。
4. **前沿层**：记忆工程化成为生产学科（Mem0《State of AI Agent Memory 2026》口径），Claude Code 的落地实践。

前置：1.5 的「关键信息放头尾」是单轮内的注意力管理，本篇把它推广到数十步的任务全程；2.4 的短期窗口+长期向量库是本篇「记忆工具」原语的原理地基。

## 2. 一句话定义

Context Engineering（上下文工程）是取代「提示词工程」的体系化学科：系统性地管理模型每一步看见的全部信息——系统提示、对话历史、工具结果、检索内容、外部记忆——用压缩、记忆外置、子代理隔离、按需取回四种手段，让长任务 Agent 在有限上下文窗口内不迷路。

## 3. 为什么需要

上下文窗口不是内存条，塞满不等于能用。三个硬约束：

1. **稀缺**：窗口再大也是有限资源，长任务的工具输出、文件内容、报错日志会以指数速度吃掉它。
2. **注意力衰减**：超长上下文中部信息的利用率显著下降（lost in the middle，TACL 2024，1.5 的锚点结论）；关键约束淹没在第 4 万 token 与完全不在窗口里，效果差不多。
3. **成本与延迟线性上涨**：每步都带着全量历史跑一遍前向，token 越积越多，越用越慢、越用越贵。

典型症状（社区与面试反复出现的真题式问题——「编程 Agent 为什么用得越久响应越慢、越干越糊涂」）：

```text
第 1 步：目标清晰，动作利落
第 20 步：开始重复读已经读过的文件
第 35 步：忘了用户最初要什么，开始「自由发挥」
第 50 步：上下文爆满，要么截断报错，要么被平台自动裁剪——
         裁掉的偏偏是第 1 步的需求描述
```

根因：**上下文是稀缺资源，而默认行为（全部历史原样保留）是对它最挥霍的用法。**Context Engineering 的立场是像管理内存一样管理上下文：分级、换页、垃圾回收——这就是「Engineering」的含义。

边界感也要有：三五步的简单任务不需要这套体系——硬给一个 5 步任务上子代理隔离和记忆外置，纯增加延迟与复杂度。启动信号是三条中任意一条：任务步数会超过 20；单步工具结果可能超万 token；任务需要跨会话延续。满足才上工程，否则提示词工程仍然是性价比最高的工具。

| 维度 | Prompt Engineering | Context Engineering |
|---|---|---|
| 管理对象 | 一条指令怎么写 | 模型每一步的全部输入 |
| 范围 | 系统提示、任务描述、少样本示例 | + 历史、工具结果、检索内容、记忆文件 |
| 时间尺度 | 单次调用 | 任务全程（几十上百步）+ 跨会话 |
| 核心技能 | 措辞、结构化、示例选择 | 预算分配、压缩、外置、隔离、按需供给 |
| 失效模式 | 指令歧义、格式错 | 目标漂移、历史膨胀、关键信息被裁剪 |
| 时代定位 | 聊天时代的主技能 | Agent 时代的主战场 |

**关系口径：上下文工程是提示词工程的超集。提示词只管「怎么说」，上下文工程管「每步看见什么」——提示词写得再好，第 50 步时它被挤掉也没用。**

算一笔成本账（Agent 与聊天机器人的经济学差异）：聊天机器人一次对话 = 一次输入计费；Agent 跑 50 步，每步都携带全量历史重新计费，输入 token 总量是 O(步数 × 历史长度) 的累积——历史线性增长时，总输入成本按平方级上涨。这解释了两个现象：一是「越用越慢、越用越贵」不是错觉而是复利；二是上下文工程的每一项手段（压缩控长、引用代替内容、缓存友好前缀）都直接对应账单曲线的斜率。

## 4. 核心原理

### 4.1 三原语

Anthropic 工程体系（官方博客 + Cookbook）把长任务上下文治理归纳为三个可 API 化的原语，外加一条检索原则：

| 原语 | 解决什么 | 机制 | 代价 |
|---|---|---|---|
| Compaction 压缩 | 窗口临满 | 历史折叠为结构化摘要（目标/已完成/未完成/决策），带干净书桌继续干 | 摘要有损；压缩时机与保留策略要调 |
| 记忆工具外置 | 跨步、跨会话的关键事实 | 重要事实写外部文件（memory tool），按需读回；窗口外持久 | 多一次工具往返；要设计读写时机 |
| 子代理隔离 | 海量中间产物污染主上下文 | 子代理在独立上下文翻完资料山，只向主 Agent 回传报告 | 子代理可能漏细节；要写好任务说明 |
| Just-in-time 取回（检索原则） | 预加载浪费与噪音 | 不预读大文档，只存引用（路径+行号），用到时精确读取 | 需要模型知道「有什么可取」（目录/索引） |

三原语各自对应一类「丢失」：

```text
压缩   → 解决「窗口装不下」：折叠历史，保住任务主干
记忆   → 解决「窗口留不住」：重要事实越过窗口边界存活
隔离   → 解决「窗口不该装」：脏活在别处干，主上下文只收结论
取回   → 解决「窗口不用先装满」：按需供给胜过预加载
```

### 4.2 压缩（Compaction）的工程细节

1. **触发时机**：窗口占用阈值（常见 80%–90%）或按步数/时间兜底触发；压缩本身是一次 LLM 调用，要设防抖。
2. **摘要结构化**：不是「随便总结」，而是固定四段——原始需求（逐字保留约束）、已完成项与关键决策、未完成项、当前焦点与风险。自由摘要几乎必然丢需求。
3. **压缩前外置**：把不能丢的细节（路径、行号、报错原文、用户显式偏好）先写入记忆文件，再压历史——摘要是有损的，文件是无损的。
4. **保留最近原文**：摘要 + 最近若干轮原文一起重建上下文，避免「刚发生的事」也在摘要里失真。
5. **失败信号**：压缩后若模型开始重复已完成动作，说明摘要丢了进度账——检查结构是否覆盖「已完成项」。

两个反模式（面试说得出即加分）：

1. **高频小压缩**：每几步就压一次，摘要叠摘要，失真复利累积，最后模型对着「摘要的摘要的摘要」干活。对策：设最小压缩间隔与最小释放量（一次至少释放 30% 占用才值得压）。
2. **裁剪式治理**：不压摘要，直接按条数丢最旧消息——最旧的位置恰恰是原始需求所在，等于系统性删除目标。Anthropic 工程博客点名的失败形态之一。对策：永远先摘要后丢弃，且需求逐字保留进摘要。

### 4.3 记忆工具：窗口外的第二大脑

与 2.4 的 RAG 式长期记忆的区别：记忆工具是 **Agent 主动读写的笔记本**（显式 write/read 操作），不是被动检索的向量库。设计要点：

- 写入有明确时机：用户表达偏好、做出关键决策、发现重要事实时立即落盘。
- 内容结构化：按主题分文件（偏好、项目状态、环境信息），别写成一团日志。
- 读回靠自觉+提醒：系统提示里告诉模型「开工前先读 plan/记忆文件」，否则它不会读。
- 生命周期：会话结束不清空才叫记忆；每次会话都重建的那叫草稿。

读写时机的一组经验法则：

1. **写**：用户表达偏好（「以后都用 TypeScript」）、关键决策拍板、发现可复用事实（环境信息、报错解法）——三类事件触发写入，其余别写（写太多读不回来）。
2. **读**：会话冷启动读一次（恢复上下文）；执行与记忆主题相关的操作前读一次（改代码前读项目约定）；别每步都读——记忆是外存不是寄存器，反复全量读取等于把外置的成本又搬回窗口。
3. **改**：新事实与旧记忆冲突时覆盖而非追加（用户口味变了就更新），保留时间戳便于过期治理（见 4.6 的偏好衰减）。

### 4.4 子代理隔离与 just-in-time 取回

**子代理隔离**（对应 2.7 多 Agent 分工的上下文动机）：主 Agent 让子代理执行「搜索 20 个网页」「通读 30 个文件找引用」这类重上下文操作。子代理的原始内容（几万字）全部留在它自己的上下文里死掉，只有 1–2k 的结论报告回到主 Agent。规则：**上下文在谁那里膨胀，谁负责压缩成结论。**

隔离不是免费的，取舍判据有三：子代理总数与串并行度（每个都是独立 LLM 会话，token 总成本可能不降反升，买的是主上下文的干净）；任务可委托性（目标清晰、验收可描述的操作才适合外包，需要主 Agent 亲自判断的不能派）；信息完整性风险（子代理可能漏掉主任务真正需要的细节，报告里要带「查了什么、没查什么」的边界声明）。一句话判据：**中间产物巨大且最终只需结论的操作才隔离**，普通工具调用留在主循环。

**Just-in-time 取回**：预加载整个代码库或全部文档是反模式——绝大部分内容永远用不到，却持续消耗注意力与预算。正确姿势是让引用常驻（文件路径+行号范围+一句话说明），内容用到时才读。它对 H4 的 Agentic RAG 是同一思想：检索不是一次性注入，而是任务过程中按需发生的工具调用。

落地前提常被忽略：just-in-time 依赖「模型知道有什么可取」。没有目录、索引或引用清单，模型连「该读哪个文件」都问不出来，按需取回退化成盲目试探。所以引用清单本身是常驻层的一等公民——花几十 token 登记「有什么在哪」，省下的是每次数万 token 的盲读。

### 4.5 长任务上下文衰退的机制拆解

「越用越慢、越用越糊涂」的面试级解释，四条机制叠加：

| 症状 | 机制 | 对策 |
|---|---|---|
| 响应越来越慢 | 历史线性增长 → 每步 prefill token 增长；缓存命中率下降 | 压缩控长 + 稳定前缀利用提示缓存 |
| 重复读同一文件 | 早期读过的内容被裁剪/稀释，模型不记得已读 | 记忆外置 + 引用清单常驻 |
| 忘记最初需求 | 需求在最旧的窗口位置，被裁剪或沉入低注意力区 | 摘要里逐字保留需求 + plan 文件常驻 |
| 动作开始发散 | 工具结果噪音累积，有效指令占比下降 | 子代理隔离脏活 + 定期清理 |
| 成本越跑越贵 | 每步全量历史计费（输入 token 按步累积） | 预算监控 + 及时压缩 |

面试答法顺序：先给症状分类，再逐条给机制（prefill 增长、注意力衰减、裁剪策略伤头、噪音占比），最后给四原语对位方案——**结构化回答本身就是「懂上下文工程」的证明。**

「越慢」还有一条容易被漏掉的机制——**提示缓存（prompt caching）失效**：平台的缓存按前缀匹配，若每步都改写历史开头（比如把最新摘要插在前面），缓存全量失效，每步按未命中价全价重算。工程对策：常驻层（系统提示、记忆索引）放最前且保持字节级稳定，动态内容一律追加在尾部；压缩重建上下文时尽量保持前缀不变（摘要追加而非重写）。这一条是「延迟与成本双优」的关键杠杆，也是多数人从「越用越慢」现场排查里学到的第一课。

现场排查清单（拿到一个「越用越糊涂」的 Agent 时按序过一遍）：

1. 历史长度曲线：每步输入 token 是否线性/超线性增长？→ 定位是否缺压缩。
2. 原始需求位置：需求还完整出现在窗口里吗？在哪一个位置？→ 定位裁剪与注意力风险。
3. 重复动作指纹：是否有重复读同一文件、重复执行同一命令？→ 定位记忆/进度账缺失。
4. 缓存命中率：平台侧缓存是否命中？前缀是否被每步改写？→ 定位「贵而慢」的原因。
5. 噪音占比：工具结果垃圾（超长日志、无关内容）占窗口比例多少？→ 定位是否需要隔离与清理。

### 4.6 记忆工程化与 Mem0 2026 报告口径

Mem0 发布《State of AI Agent Memory 2026》年度报告，行业口径要点：Agent 记忆已从「技巧集合」升级为**生产工程学科**——出现年度报告、专项基准（含 BEAM 偏好衰减基准：衡量记忆随时间的衰减与更新）与运维实践。对本锚点的意义：

1. 「压缩/记忆/隔离/取回」不再是高级技巧，而是与缓存、限流同级的**生产基础设施**话题。
2. 记忆需要评测：偏好会过时（用户去年喜欢 A 今年喜欢 B），衰减与更新策略要进基准、进回归。
3. 面试延伸：被问「记忆系统怎么做」时，先分「会话内（压缩）/跨会话（记忆文件）/大规模（向量库+2.4 原理）」三层，再谈评测——比直接背 Mem0 结论更显功底。

报告口径里最值得展开的一点是**偏好衰减（preference decay）**：记忆不是只增不减的资产，用户偏好会过时——去年「要详细解释」的用户今年可能只要结论。BEAM 类基准把「记忆随时间的衰减与更新」变成可评测对象，对应到工程就是三个问题：多久复审一次旧偏好、冲突时信新还是信旧、多久没有访问的记忆可以退役。这与 8 节坑 14（记忆当传家宝）互为正反面。

### 4.7 Claude Code 实践

| 模式 | Claude Code 中的落地 |
|---|---|
| Compaction | 会话接近窗口上限自动压缩历史为结构化摘要，保留目标与进度后继续 |
| 计划外置 | plan.md/TODO 文件：任务列表落盘，完成一项更新一项，模型每步可重读目标 |
| 项目记忆 | CLAUDE.md 常驻：项目约定、构建命令、代码风格进每次会话 |
| 子代理 | Task 工具派发子代理做大范围搜索/探索，主会话只收结论 |
| Just-in-time | 默认不整库预读，按 Grep/Glob 定位后精确读取行号范围 |

产品化观察（面试引用时的话术价值）：Claude Code 证明了四原语不需要花哨架构——一个阈值触发的摘要、几个落盘的 Markdown 文件、一个派发子任务的工具，就撑起了小时级任务的可用性。上下文工程的门槛不在技术复杂度，而在**纪律**：什么进常驻层、什么外置、什么丢弃，每一步都要有明确规则并坚持执行。这也是它适合作为面试题的原因——答得好坏差异极大，且无法靠背名词蒙混。

## 5. 架构 / 流程

长任务 Agent 的上下文生命周期（四原语各就各位）：

```text
任务开始
   ↓
[注入] 系统提示 + 常驻记忆（CLAUDE.md / plan.md / 用户偏好文件）
       引用清单：路径+行号+一句话说明（不装内容本身）
   ↓
[循环] 每步：模型看见 = 常驻层 + 摘要层 + 最近 N 轮原文 + 本步工具结果
   │
   ├─ 重上下文操作（搜索/通读/探索）──→ 子代理隔离：脏活在独立上下文干，
   │                                     主上下文只收 1–2k 结论报告
   ├─ 大文件引用 ──→ just-in-time：用到时按路径+行号精确读取，读完即弃
   ├─ 关键事实出现 ──→ 记忆工具：立即写外部文件（窗口外持久）
   ↓
[监控] 窗口占用、每步输入 token、缓存命中率
   ↓ 占用 > 80%
[压缩] 先外置「不能丢」的细节 → 历史折叠为四段结构化摘要
       → 摘要 + 最近若干轮原文 = 干净书桌，继续干活
   ↓
[收尾] 任务总结回写记忆文件 → 下次会话冷启动即带经验
```

选型速查（什么症状用什么原语）：

```text
窗口快满了？                → compaction
事实要跨步/跨会话存活？      → 记忆工具外置
中间产物巨大且只需结论？     → 子代理隔离
内容大但按需才用？          → just-in-time 取回
全都有一点？                → 组合拳（生产 Agent 的常态）
```

预算分配的经验起点（20 万 token 窗口的参考切法，示意）：常驻层（系统提示+记忆索引+计划文件）压在 5% 以内且全程稳定；摘要层（任务摘要）控制在 5%–10%；最近原文保留 10%–15%；剩余预算留给当步工具结果与思考空间——任何一层越界挤占思考与工具结果，都会先表现为动作质量下降，再表现为截断报错。切法本身要进评测：改预算配比必须跑同一批任务对比，不许凭感觉。

## 6. 代码 / 工具

### 6.1 上下文压缩策略实现

```python
from dataclasses import dataclass, field

COMPACT_PROMPT = """把以下 Agent 历史压缩为四段，总量不超过 800 token：
1. 原始需求：用户最初目标，逐字保留关键约束与验收标准
2. 已完成项与关键决策：每条一行，附理由
3. 未完成项：下一步动作，可执行粒度
4. 当前焦点与风险：正在进行什么、有什么坑
禁止丢弃：文件路径、行号、报错原文、用户显式偏好。"""

@dataclass
class CompactionManager:
    """窗口预算管理：阈值触发压缩，压缩前先外置关键事实。"""
    max_tokens: int = 200_000
    compact_at: float = 0.80                    # 占用超 80% 触发
    messages: list = field(default_factory=list)
    memory_path: str = "agent_memory.md"

    def used_tokens(self, count) -> int:        # count: 粗略 token 计数函数
        return sum(count(m["content"]) for m in self.messages)

    def maybe_compact(self, count, llm_summarize) -> bool:
        if self.used_tokens(count) < self.max_tokens * self.compact_at:
            return False
        # 1) 压缩前：把不可丢的细节先外置（摘要是有损的，文件是无损的）
        self._persist_key_facts(llm_summarize)
        # 2) 历史折叠为结构化摘要（四段结构，不是自由总结）
        summary = llm_summarize(self.messages, COMPACT_PROMPT)
        # 3) 摘要 + 最近 6 轮原文 = 干净书桌
        recent = self.messages[-6:]
        self.messages = [{"role": "user",
                          "content": f"[任务摘要·自动压缩]\n{summary}"}] + recent
        return True

    def _persist_key_facts(self, llm_summarize) -> None:
        facts = llm_summarize(self.messages,
                              "仅提取：路径/行号/报错原文/用户显式偏好，逐条列出。")
        with open(self.memory_path, "a", encoding="utf-8") as f:
            f.write(f"\n## 自动外置 {self._now()}\n{facts}\n")

    @staticmethod
    def _now() -> str:
        from datetime import datetime
        return datetime.now().strftime("%Y-%m-%d %H:%M")
```

主循环接入（伪代码）：

```python
mgr = CompactionManager()
mgr.messages.append({"role": "user", "content": load_plan("plan.md")})

while not task_done:
    mgr.maybe_compact(count_tokens, llm_summarize)   # 每步先查预算
    action = agent.step(mgr.messages)                # 正常干活
    mgr.messages.append(action)
```

### 6.2 子代理隔离与 just-in-time 取回

```python
def delegate_search(query: str) -> str:
    """子代理隔离：重上下文操作在全新上下文里翻资料山，只回传报告。"""
    sub = Agent(
        system="你是检索专员：只做检索与核实，报告不超过 300 字，"
               "给出结论 + 来源路径/链接 + 置信度。原始内容不要复述。",
        context=fresh_context(),                 # 与主 Agent 完全隔离
        tools=[web_search, read_file, grep],
    )
    sub.run_until_done(query)                    # 几万字原始内容死在子上下文
    return sub.final_report(max_chars=2000)      # 主 Agent 只收 2k 结论

def jit_read(ctx, path: str, lines: tuple | None = None) -> str:
    """just-in-time：引用常驻，内容用到才读，读完即弃。"""
    span = f" L{lines[0]}-{lines[1]}" if lines else " 全文"
    ctx.note(f"[引用登记] {path}{span}")          # 路径常驻主上下文（极便宜）
    return read_file_slice(path, lines)          # 内容只进当步工具结果，下步可被压缩
```

两段代码的组合拳才是生产形态：主循环每步先查窗口预算（6.1），重上下文操作派子代理（6.2），关键事实随手外置，大文件按行号即用即取——四个原语在同一会话里各管一段，互不替代。单独落地任何一个原语都能缓解症状，但「越用越糊涂」是四种丢失机制的叠加，治理也要叠加。

### 6.3 计划外置模板（plan.md）

```markdown
# plan.md（模型每步可重读目标，不依赖长历史回忆）
## 目标
- 把 orders 模块从单体重构为独立服务（用户 2026-09-12 提出）
- 验收标准：全部现有测试通过；接口响应 P99 < 200ms
## 进度（完成打勾）
- [x] 梳理 orders 依赖（结论：3 处外部调用，见 memory/depends.md）
- [ ] 抽出 OrderRepository 接口
- [ ] 迁移单元测试
## 关键决策
- 用适配器层兼容旧表结构（理由：避免双写迁移风险）
## 风险
- 报价逻辑与 promotions 服务隐式耦合：改动前先跑集成测试
```

要点：目标逐字保留用户原话（防漂移）；进度打勾（防重复劳动）；关键决策带理由（防反复推翻）；风险显式化（防踩坑）。四原语里「记忆外置」最廉价也最见效的一招，就是它。

## 7. 案例

### 案例 A：编程 Agent 的重构任务治理

**场景**：某软件团队的 AI 编程助手跑 2 小时的服务重构任务，症状：重复读文件、中途偏离需求、第 40 步后响应明显变慢。

**改造**：窗口占用 80% 触发 compaction（四段结构化摘要）；重构计划外置 plan.md 逐步打勾；「找全部引用」类操作改子代理执行只回传文件+行号清单；代码不再整库预读，改 Glob 定位后按行号读取。

**效果**（示意量级）：步骤成功率 55% 提升到 82%；目标漂移（中途偏离需求的次数）从 7 次降到 1 次；单任务平均输入 token 下降 40%，尾部步骤延迟回到首步的 1.5 倍以内（此前是 6 倍）。

### 案例 B：深度研究 Agent 的隔离改造

**场景**：一家咨询公司的深度研究 Agent，单任务要检索 30+ 网页，主上下文在第 15 个网页后爆满，报告后半部分质量骤降。

**改造**：按研究子问题拆 4 个子代理并行检索，各自在独立上下文读完全部网页，各回传 1.5k 结构化报告（结论+来源+置信度）；主 Agent 只聚合报告；全部原始网页 URL 写入记忆文件备查。

**效果**：单任务可容纳的信息源从 15 个提升到 40+；报告事实性错误率下降一半；主上下文占用稳定在 30% 以内——**上下文在谁那里膨胀，谁负责压缩成结论，这条规则立住了。**

### 案例 C：长会话客服的记忆外置

**场景**：某电商 VIP 客服 Agent 处理跨 3 小时的售后工单（多次转接、多轮举证），用户重复陈述背景，Agent 偶尔遗忘已承诺的补偿方案。

**改造**：承诺类语句实时写入记忆文件（含时间与工单号）；每 20 轮做一次轻量压缩；新转接坐席（或会话恢复）先读记忆文件再开工。

**效果**：重复陈述率下降 60%；「遗忘已承诺事项」类投诉降为零样本出现；压缩触发的额外成本约占会话成本 5%——远低于重复沟通与投诉处理的开销。复盘关键句：客服场景的「必须外置」信息极其明确——承诺、金额、时限、工单号，识别这四类的正则比任何摘要模型都可靠；**能用规则写盘的别交给模型总结**，这条原则在治理类改造里屡试不爽。

## 8. 常见坑

1. **把 Context Engineering 当提示词工程的新名字**。只优化指令文本不管历史与工具结果；对策：按「每步看见什么」盘点全部输入源。
2. **盲目相信大窗口**。窗口大不等于注意力可用，中部信息照样丢失（lost in the middle）；对策：关键约束进常驻层与摘要层，不赌位置。
3. **压缩用自由摘要**。模型随总结随丢需求与约束；对策：四段结构化摘要 + 「禁止丢弃」清单。
4. **压缩前不外置**。有损摘要直接覆盖历史，细节永久丢失；对策：先写记忆文件再压缩。
5. **记忆只写不读**。落盘了但系统提示不提醒模型读，等于没写；对策：开工先读记忆/计划，写进系统提示。
6. **记忆不分主题一坨日志**。检索与模型阅读都困难；对策：按主题分文件、带时间戳、定期清理过期偏好。
7. **子代理任务说明太模糊**。回传报告缺关键细节，主 Agent 还得重查；对策：限定报告结构（结论/来源/置信度/字数）。
8. **子代理拆太碎**。简单查询也派子代理，往返开销大于收益；对策：只有「中间产物巨大且只需结论」才隔离。
9. **预加载整库/全部文档**。噪音与成本双杀；对策：引用常驻 + just-in-time 精确读取。
10. **不监控窗口预算**。到截断报错才发现爆了；对策：占用率、每步输入 token、缓存命中率三个指标常驻看板。
11. **压缩时机太晚**。占用 95% 才压，裁剪已经先动手砍掉了头部需求；对策：80% 左右主动压，别让平台替你裁。
12. **压缩后不验证**。模型开始重复已完成动作才知道摘要丢了进度；对策：压缩后跑一次进度核对（对照 plan.md 打勾项）。
13. **忽略缓存友好性**。每步改写前缀导致提示缓存全失效，延迟成本双涨；对策：常驻层放前缀且保持稳定，动态内容靠后。
14. **把记忆当传家宝**。什么都存，过期偏好污染当前决策；对策：偏好带衰减与更新策略（参考 BEAM 类基准思路），定期退役。

## 10. 小结

- Context Engineering 是提示词工程的**超集**：管模型每一步看见的全部信息——指令只是其中一块。
- 根本立场：**上下文是稀缺资源，像管理内存一样管理它**（分级、换页、回收）。
- 三原语：**压缩**（窗口装不下）、**记忆工具**（窗口留不住）、**子代理隔离**（窗口不该装）。
- 第四模式：**just-in-time 取回**——引用常驻、内容按需，预加载是反模式。
- 压缩三铁律：结构化四段摘要、压缩前先外置、摘要+最近原文重建。
- 「越用越慢」四机制：prefill 随历史增长、注意力中部衰减、裁剪伤头、噪音占比上升——四原语逐条对位。
- 子代理规则一句话：**上下文在谁那里膨胀，谁负责压缩成结论。**
- 记忆外置最廉价的形态是 plan.md：目标逐字保留、进度打勾、决策带理由、风险显式化。
- 行业口径：**Mem0《State of AI Agent Memory 2026》确认记忆已从技巧升级为生产工程学科**（含 BEAM 偏好衰减基准）。
- Claude Code 实践映射：自动 compaction、plan.md、CLAUDE.md、Task 子代理、按行号读取——四原语的产品化样板。
- 效果必须可度量：步骤成功率、目标漂移率、每步输入 token 三指标，改造前后对比。
- 面试安全答法：先分症状、再讲机制、后给原语对位——结构本身就是能力证明。
