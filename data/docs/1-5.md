# 讲解 1.5 记忆与上下文管理

> 说明：本篇前置 1.1b（上下文长度与成本、延迟的联动）与 0.5（上下文窗口从哪来），聚焦多轮对话中「记什么、忘什么、放哪儿」的工程实操。  
> Agent 级记忆的持久化与检索调度在 2.4 展开，长任务上下文的压缩与子代理隔离在 H3（Context Engineering）深入，「只把相关的给 AI」的检索化路线通向 1.4 RAG。

## 1. 定位

S1 应用层第 5 个知识点，回答本锚点的关键问题：**多轮中该记住什么、忘掉什么？**

1.1/1.2 解决「怎么问」，1.3 解决「怎么接」，本锚点解决「怎么在多轮里保持连贯且不爆成本」。它是 2.1 Agent 定义、2.4 记忆机制的直接前置，也是 H3 Context Engineering 的入门篇。

两个常被混用的词先分清：

- **上下文管理（Context Management）**：管理单次请求里塞进窗口的内容——历史、检索结果、系统提示的取舍与摆放。
- **记忆（Memory）**：跨请求的状态持久化——本次会话的结论、历史会话沉淀的用户偏好。

本篇以多轮对话为场景讲上下文管理，并给出短期/长期记忆分层的雏形；2.4 把分层做完，H3 讲长任务的极端场景。

## 2. 一句话定义

上下文管理是在有限窗口与有限预算下，决定「哪些信息进入模型上下文、以什么形态（原文/摘要/检索结果）、放在什么位置」的工程决策。核心口诀：**近期留原文、远期做摘要、相关的检索出来、关键信息放头尾**。

## 3. 为什么需要

三个约束逼出这门手艺：

1. **窗口有限**。即使 128K 窗口，300 轮客服对话加上系统提示早就超了。
2. **窗口 ≠ 有效长度**。标称 128K 是「装得下」，不是「用得上」——利用率随长度与位置衰减。
3. **成本与延迟联动**。输入 token 按量计费且逐 token 进入注意力计算，「全塞进去」是最常见的账单爆炸与响应变慢原因（回看 1.1b，延伸在 1.7）。

「会议记录本」类比（站内 1-5 考点）：300 轮对话像一本厚记录本，窗口就那么几页。三种处理：撕掉最早几页（滑动窗口，快但丢历史）、把旧内容浓缩成一页纪要（摘要压缩，保大意丢细节）、把最相关的几页复印放最前（检索式选取）。工程上三招组合。

## 4. 核心原理

### 4.1 窗口 ≠ 有效长度

| 概念 | 含义 | 工程含义 |
|---|---|---|
| 标称窗口 | 模型能接受的最大 token 数 | 只决定「装不装得下」 |
| 有效利用长度 | 信息真正被利用的长度 | 远小于标称值，随总长衰减 |
| 位置利用率 | 同一信息在不同位置的可用程度 | U 形：头尾高、中部低 |
| 上下文成本 | 输入 token 计费 + 注意力计算延迟 | 与每轮携带的历史长度成正比 |

推论：把大窗口当「无限内存」用，效果时好时坏且越来越贵。窗口大小是模型参数，上下文质量是工程责任。

### 4.2 lost in the middle 与位置工程

TACL 2024 的 lost-in-the-middle 研究给出关键发现：**关键信息埋在长上下文中部时，模型利用率明显下降；放开头和结尾表现最好**——一条 U 形曲线。这与人类「摊满考桌的资料，开头结尾记得牢、中间走神」高度相似。

| 放置位置 | 利用率 | 放什么 |
|---|---|---|
| 上下文开头（系统提示附近） | 高 | 系统提示、硬约束、全局规则 |
| 长上下文中部 | 最低 | 次要背景、低优先级资料 |
| 结尾、紧邻用户问题 | 最高 | 最相关的检索结果、当前轮关键信息 |

位置工程口诀：**系统提示放开头，最相关的资料贴着问题放，次要背景填中部。** 这是零成本的免费优化——不换模型、不加服务，只挪位置。

RAG 场景直接复用：召回 Top-5 重排后，相关性最高的一两条放结尾（紧邻问题），其余按相关性向中部递减排布。

### 4.3 多轮历史管理四策略

| 策略 | 做法 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| 全量塞入 | 每轮带上全部历史 | 零信息损失 | 成本线性涨、超窗、中部遗忘 | 短会话（约 10 轮内） |
| 滑动窗口 | 只保留最近 N 轮原文 | 实现最简、成本恒定 | 丢早期关键信息 | 轮数可控的会话 |
| 摘要压缩 | 旧历史浓缩成纪要 | 保大意、控长度 | 丢细节、摘要自身有偏差 | 长会话 |
| 检索式选取 | 历史入库，按当前问题召回 | 精准、可扩展 | 多一套索引与延迟 | 超长会话、跨会话 |

生产标配是组合拳：**最近 10 轮原文 + 更早历史滚动摘要 + 与当前问题相关的历史按需检索**。

摘要压缩的两个触发时机：

- 阈值触发：历史 token 超过阈值（如窗口的 60%）压缩一次，省调用。
- 每 N 轮触发：节奏固定，实现简单。

压缩保真原则：用户身份、订单号、金额、日期、已承诺的结论这类「硬信息」原样保留；寒暄与过程性内容丢弃。摘要本身也是一次 LLM 调用，用小模型、低温即可。

### 4.4 短期 vs 长期记忆分层

| 层 | 内容 | 载体 | 生命周期 | 示例 |
|---|---|---|---|---|
| 工作记忆（本轮） | 当前请求的上下文：system + 摘要 + 近期轮 + 检索结果 | 请求体 | 单次请求 | 本轮问题加刚召回的资料 |
| 短期记忆（本会话） | 会话内全部轮次与状态 | 服务端会话存储（Redis/DB） | 会话期间 | 300 轮客服对话原文 |
| 长期记忆（跨会话） | 沉淀的用户偏好、事实、结论 | 向量库/KV 存储 | 持久 | 「偏好经济舱、靠窗」 |

数据流：短期记忆是长期记忆的原料池；会话结束或达成条件时，经过**写入过滤**的结论晋升为长期记忆；每轮请求时，长期记忆按相关性检索注入上下文。1.4 的向量检索在此复用——检索的对象从文档换成记忆。

### 4.5 记忆写入过滤

不是所有对话都值得记住。无过滤的写入让长期记忆变成噪音堆，检索时反而污染上下文。

写入过滤器（每条候选记忆过一遍）：

1. **价值判断**：稳定事实/偏好/结论才记。「用户是会员、要开发票」记；「好的谢谢」丢。
2. **时效判断**：永久有效（偏好）还是有时效（「本周三请假」到期归档）？
3. **冲突处理**：新信息与旧记忆矛盾时，新覆盖旧并留版本痕迹（用户改了收货地址）。
4. **敏感过滤**：PII、凭据类信息脱敏或不入库。
5. **去重合并**：同主题记忆合并成一条，控制长期记忆规模。

一句话：**记忆系统的质量取决于忘掉什么，不取决于记下什么。**

## 5. 架构 / 流程

一轮多轮对话的上下文组装流水线：

```text
用户新输入
   ↓
┌──────────────────────────────────────────────┐
│ 历史管理器                                     │
│  短期记忆（会话存储）                           │
│   ├─ 最近 N 轮 ──────────→ 原文直接进上下文     │
│   └─ 更早历史 → 超阈值？→ 滚动摘要（LLM 压缩）  │
│  长期记忆（向量库）                             │
│   └─ 按当前问题检索 Top-K 相关记忆 ──┐          │
└──────────────────────────────────────────────┘
   ↓ 组装（位置工程）
┌──────────────────────────────────────────────┐
│ 最终上下文                                     │
│  [开头] system：角色/规则/硬约束                │
│  [中部] 全局摘要 + 相关历史检索结果 + 次要背景   │
│  [结尾] 最近几轮原文 + 用户新输入               │
│         （最相关的资料紧邻问题放）               │
└──────────────────────────────────────────────┘
   ↓
LLM 生成 → 回复用户 → 本轮写入短期记忆
   ↓ 会话结束 / 条件触发
写入过滤（价值/时效/冲突/敏感/去重）→ 晋升长期记忆
```

## 6. 代码 / 工具

### 6.1 滑动窗口 + 滚动摘要压缩

```python
from openai import OpenAI

client = OpenAI(api_key="YOUR_KEY")
SUMMARY_TRIGGER_TOKENS = 3000     # 历史超过此阈值触发压缩
KEEP_RECENT_TURNS = 6             # 压缩时保留最近 N 轮原文

def rough_token(text: str) -> int:
    return max(1, len(text) // 2)          # 中文粗估：2 字符约等于 1 token

class Conversation:
    """短期记忆：全量存服务端；进上下文的只有近期原文 + 滚动摘要。"""
    def __init__(self, system: str):
        self.system = system
        self.history: list[dict] = []       # 短期记忆：全部轮次
        self.rolling_summary: str = ""      # 远期摘要

    def add(self, role: str, content: str):
        self.history.append({"role": role, "content": content})
        self._compact_if_needed()

    def _compact_if_needed(self):
        total = rough_token(self.rolling_summary) + \
                sum(rough_token(m["content"]) for m in self.history)
        if total < SUMMARY_TRIGGER_TOKENS:
            return
        old, recent = self.history[:-KEEP_RECENT_TURNS], self.history[-KEEP_RECENT_TURNS:]
        if not old:
            return
        # 用小模型把旧历史并入滚动摘要；硬信息要求原样保留
        text = "\n".join(f"{m['role']}: {m['content']}" for m in old)
        prompt = ("把以下对话并入既有纪要，输出一段摘要。"
                  "订单号、金额、日期、已承诺结论必须原样保留。\n"
                  f"既有纪要：{self.rolling_summary or '（无）'}\n对话：\n{text}")
        resp = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            temperature=0)
        self.rolling_summary = resp.choices[0].message.content
        self.history = recent               # 旧历史已被摘要取代

    def build_messages(self) -> list[dict]:
        msgs = [{"role": "system", "content": self.system}]     # 开头：系统提示
        if self.rolling_summary:                                 # 中部：远期摘要
            msgs.append({"role": "system",
                         "content": f"此前对话纪要：\n{self.rolling_summary}"})
        return msgs + self.history                               # 结尾：近期原文

# 使用
conv = Conversation(system="你是电商客服，基于历史与纪要回答。")
while True:
    user = input("> ")
    conv.add("user", user)
    resp = client.chat.completions.create(
        model="gpt-4o-mini", messages=conv.build_messages(), temperature=0.3)
    reply = resp.choices[0].message.content
    conv.add("assistant", reply)
    print(reply)
```

### 6.2 检索式历史召回 + 头尾放置组装

```python
def assemble_context(conv: Conversation, query: str,
                     memory_store, top_k: int = 3) -> list[dict]:
    """按当前问题从长期记忆召回相关历史，按相关性升序放中部，
    使最相关的自然落在最靠近结尾（紧邻问题）的位置。"""
    hits = memory_store.search(query, top_k=top_k)   # 向量检索历史记忆
    hits = sorted(hits, key=lambda h: h["score"])    # 分数低的放前
    mid = "\n".join(f"[相关历史] {h['text']}" for h in hits)
    msgs = conv.build_messages()
    if mid:
        msgs.insert(1, {"role": "system", "content": mid})  # 检索结果放中部
    return msgs

def write_to_long_term(memory_store, candidates: list[dict]):
    """会话结束时的写入过滤：五件套过一遍才入长期记忆。"""
    for c in candidates:
        if not c.get("valuable"):            # 价值：闲聊不记
            continue
        text = mask_pii(c["text"])           # 敏感：脱敏
        memory_store.upsert(                 # 冲突：同主题覆盖并留版本
            topic=c["topic"], text=text,
            expires_at=c.get("expires_at"))  # 时效：到期归档
```

### 6.3 上下文组装模板（位置工程速查）

```text
最终请求的消息序列：
  1. system（开头）    角色 + 规则 + 硬约束（稳定不变）
  2. system（中部）    跨会话相关记忆 Top-K（相关性升序排列）
  3. system（中部）    本会话滚动纪要（硬信息原样保留）
  4. user/assistant   最近 N 轮原文（时间升序）
  5. user（结尾）      用户新输入；如带检索资料，最相关一条紧贴其后
```

## 7. 案例

### 案例 A：300 轮客服会话改造

**场景**：某电商平台智能客服，长会话动辄 200-300 轮，全量塞历史导致账单失控，且早期的承诺经常被「忘掉」。  
**做法**：最近 6 轮原文 + 旧历史滚动摘要（订单号、金额、承诺原样保留）+ 订单号类实体单独存结构化槽位；摘要超 3000 token 阈值触发压缩。  
**效果**：单会话平均输入 token 从约 8 万降到 9 千，成本降约 89%；「前面说过的承诺被忘掉」类投诉下降约七成。

### 案例 B：200 页 PDF 问答的位置修复

**场景**：一家法律科技公司把 200 页合同全文塞进上下文做问答，效果时好时坏，单次几十万 token。  
**诊断**：一是把大窗口当检索器用——相关段落只有几段，却被 200 页噪音淹没；二是相关段落常落在中部，正撞 lost in the middle 的低谷，所以时好时坏。  
**改造**：切块建向量索引，只召回 Top-5；重排后最相关块紧邻问题放结尾，全文摘要作背景层放中部；要求回答标注来源页码。  
**效果**：单次请求 token 从约 40 万降到 6 千，准确率因去噪与位置优化反而从 71% 升到 88%。完整 RAG 链路在 1.4 展开。

### 案例 C：跨会话记忆的写入过滤

**场景**：某旅行助手 App 沉淀用户偏好，最初全量入库，一个月后检索命中率烂掉——记忆库里塞满「好的」「谢谢」。  
**改造**：写入过滤五件套（价值/时效/冲突/敏感/去重），只存稳定偏好与事实，新偏好覆盖旧偏好并留版本。  
**效果**：长期记忆条目从 12 万降到 1.8 万，偏好类检索命中率从约 40% 升到 83%，个性化推荐采纳率显著上升。

## 8. 常见坑

1. **把标称窗口当有效长度**。装得下不等于用得上，超长上下文的利用率衰减明显。
2. **全量塞历史**。成本线性增长、延迟变慢、中部遗忘三连击；短会话之外一律上策略。
3. **只砍不摘要**。纯滑动窗口把关键承诺连同早期轮次一起丢掉，用户会觉得 AI 失忆。
4. **摘要丢硬信息**。订单号、金额、日期、承诺结论必须在摘要中原样保留。
5. **关键信息埋中部**。检索结果按随手顺序塞，正撞 U 形低谷；最相关的要贴着问题放。
6. **系统提示放错位置或被冲淡**。系统提示放开头，别把大量动态内容混进系统提示。
7. **长期记忆不过滤**。闲聊全入库，检索时噪音污染上下文——记忆质量取决于忘掉什么。
8. **记忆冲突不处理**。用户改了地址，新旧两条并存，模型随机取一条。
9. **敏感信息直接入库**。PII 与凭据要脱敏或不存。
10. **摘要每轮都做**。压缩本身是 LLM 调用，按阈值触发而非每轮触发。
11. **多用户共享一份记忆**。用户 A 的偏好注入用户 B 的上下文是事故；记忆必须按租户/用户隔离。
12. **不看成本曲线**。上下文长度与账单、首 token 延迟直接挂钩（1.1b/1.7），策略调整必须连成本一起评估。

## 9. 练习

1. 实现一个纯滑动窗口对话类，测 50 轮会话的 token 消耗曲线。
2. 加上滚动摘要，验证订单号等硬信息在 100 轮后仍能被正确引用。
3. 构造「关键条款放中部 vs 放结尾」的对比实验，各跑 10 次统计命中率差异。
4. 把 6.2 的检索式召回接上向量库，对比「无检索注入」与「Top-3 注入」的多轮一致性。
5. 实现写入过滤的冲突处理：用户两次说不同收货地址，验证记忆更新与版本留痕。
6. 对同一会话分别用全量、滑窗、滑窗+摘要三种策略，画出成本与回答质量两条曲线。
7. 给摘要压缩加触发阈值参数，扫描 1000/3000/6000 token 三档，选性价比最高的一档。
8. 复现一个「时好时坏」的长文档问答案例，把最相关段落从中部挪到结尾，量化提升。

## 10. 小结

- 窗口三条约束：**装得下 ≠ 用得上、利用率随位置衰减、成本延迟与长度联动**。
- lost in the middle：关键信息**头尾表现好、中部最差**（U 形曲线），TACL 2024 的经典发现。
- 位置工程口诀：**系统提示放开头，最相关资料紧邻问题放，次要背景填中部**——零成本免费优化。
- 历史管理四策略：**全量、滑动窗口、摘要压缩、检索式选取**；生产标配三招组合：近期原文 + 远期摘要 + 按需检索。
- 摘要压缩要点：**阈值触发、硬信息原样保留**；摘要用小模型低温即可。
- 记忆三层：**工作记忆（本轮上下文）、短期记忆（会话存储）、长期记忆（向量库/KV）**。
- 写入过滤五件套：**价值、时效、冲突、敏感、去重**——记忆质量取决于忘掉什么。
- 上下文管理是 1.4 RAG「只把相关的给 AI」的同源思想；Agent 级调度在 2.4，长任务压缩与子代理隔离在 H3。
