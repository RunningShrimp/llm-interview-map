# 讲解 2.6 反思与自我修正

> 说明：前置 2.5 讲了执行循环怎么转、工具失败怎么兜底（重试、降级、中断恢复）。  
> 2.6 讲 **Agent 怎么知道自己错了、怎么改**：自我批评、反思记忆、验证器、修正路径。  
> 反思机制怎么嵌进单 Agent 架构放在 2.7 展开，2.6 聚焦「反思」本身。

---

## 1. 定位

Agent 核心层第 6 个知识点，属于「自我纠错能力」。  
它解决一个核心问题：**Agent 执行过程中会犯错（工具选错、参数错、推理错、结果不对），如何让它自己发现错误并修正，而不是一路错到底？**

与 2.5 的分工：2.5 的错误恢复处理**操作层失败**——工具超时、限流、网络抖动，用固定策略（重试、降级）就能恢复，不需要理解错误；2.6 的反思处理**认知层错误**——选错方法、推错结论、格式不对，必须先分析「为什么错」，才知道「怎么改」。重试的上限、退避、熔断实现见 2.5，本篇只在修正路径里引用。  
它是 2.5 的直接后续（执行循环给出反思的触发点），也是 2.7 单 Agent 架构（Reflexion 是四大单 Agent 模式之一）和 2.9 Agent 评估与安全的直接前置。

## 2. 一句话定义

反思与自我修正（Reflection & Self-Correction），是 Agent 在执行过程中或执行后，对自身的输出、推理、行动进行审视、批评、验证，并据此调整行为、重试或重规划的机制。

简化公式：

```text
反思 = 审视输出 + 发现错误 + 生成改进
自我修正 = 反思结果 → 行动调整 → 重新执行（必要时把教训写入记忆）
```

## 3. 为什么需要

没有反思的 Agent：

- **一错到底**：第 1 步参数错了，后面全错，但 Agent 不知道。
- **重复失败**：同一个工具调用失败 5 次，每次的失败方式一模一样。
- **幻觉累积**：编造了一个数据，后面基于它继续编。
- **不会改进**：同样的任务做 100 次，第 101 次还是犯同样的错。
- **无法验证**：输出看起来合理，但事实错误。
- **不会换方法**：A 方法失败了，不知道试试 B 方法。
- **经验不沉淀**：错误发生了，但没有变成下次可用的教训。

朴素重试救不了认知层错误——同样的输入原样再来一次，大概率得到同样的错：

| 维度 | 朴素重试 | 反思重试 |
|---|---|---|
| 重试时携带 | 原任务，原样再来 | 原任务 + 语言化教训 |
| 失败分析 | 无 | 有（批评先生成「为什么错」） |
| 跨尝试记忆 | 无 | 有（教训存入记忆，机制见 2.4） |
| 同类错误复发 | 高，每次从零开始 | 低，下次带教训执行 |
| 额外成本 | 低 | 中（批评 + 反思各一次调用） |
| 适用对象 | 瞬时故障：超时、限流 | 认知错误：方法、参数、推理 |

**类比 1（学生与错题本）**：

```text
没有反思 = 埋头做题、从不检查的学生，错了也不知道
有反思   = 做完检查、错了记进错题本的学生
错题本   = Reflexion 的反思记忆：下次遇到同类题，先翻一遍再动笔
```

**类比 2（门禁卡）**：刷不开再刷一次，是重试；连刷三次都失败，退一步看看是拿错卡了还是刷反了方向，是反思。重试不改变任何信息，反思改变了「下一次怎么做」。

## 4. 核心原理

### 4.1 关键问题的正面回答：怎么判断错了、怎么修正

「如何判断错了并修正」拆成两半：**错误检测**（信号从哪来）和**修正路径**（检测到之后走哪条路）。

**错误检测的三路信号**：

| 信号来源 | 判错方式 | 能发现 | 发现不了 |
|---|---|---|---|
| 验证器（Verifier）：规则 / 工具 | Schema 校验、正则、编译、单测、搜索核实、代码执行 | 格式错、计算错、可形式化判定的事实错 | 语义与偏好类问题 |
| 批评模型（Critic）：LLM 自我批评或独立批评模型 | 按检查清单审输出与执行轨迹 | 逻辑矛盾、遗漏、跑偏 | 自我欺骗（模型认为自己对） |
| 人类信号：用户纠正 / 拒绝 / 投诉 | 显式反馈与隐式负反馈 | 最准，是最后防线 | 慢、贵、覆盖低（闭环设计见 3.10） |

**修正路径的分级**：

```text
错误信号（验证器 / 批评 / 人类）
        ↓ 按「错在哪一层」分级
  ├─ 输出层小问题（格式、措辞）→ 修正后重试（带错误反馈）
  ├─ 行动层问题（工具、参数）  → 换工具 / 改参数重调用
  ├─ 计划层问题（步骤、顺序）  → 重规划（Replanning，见 2.2）
  ├─ 反复出现的同类错误        → 反思注入：教训写入记忆
  └─ 无法解决 / 超出权限       → 升级人工（Escalation）
```

原则：**错误在哪一层，修正就发生在哪一层**。参数错了去重规划是过度反应；计划错了只改参数是隔靴搔痒。

面试高频问法：「Agent 执行失败了，你的系统怎么发现错了、怎么修正？」——按本节口径答：先讲三路检测信号，再讲分级修正路径，最后补成本控制（见 4.9）。

### 4.2 反思的三个层次

```text
Level 1: 输出反思（Output Reflection）
  → 检查最终输出是否正确、完整、符合要求
  → 例：答案是否回答了问题？格式对不对？

Level 2: 过程反思（Process Reflection）
  → 检查推理步骤、工具调用、计划是否合理
  → 例：为什么选了这个工具？参数对不对？

Level 3: 策略反思（Strategy Reflection）
  → 检查整体方法、策略、模式是否最优
  → 例：这个任务应该用 Plan-Execute 还是 ReAct？
```

层次越高，改动越大、成本越高：输出反思改几个字，过程反思改若干步，策略反思推倒重来。默认从 Level 1 起判，问题反复出现才升级到更高层。

### 4.3 反思的时机

| 时机 | 做什么 | 代表 |
|---|---|---|
| 执行前 | 检查计划是否合理 | Plan 审查 |
| 执行中 | 每步后检查结果 | Self-Refine、逐步验证 |
| 执行后 | 检查最终输出 | Reflexion、终审 |
| 失败后 | 分析失败原因 | CRITIC、失败反思 |
| 跨任务 | 从历史经验学习 | 经验回放、教训库 |

```text
执行前：Plan 生成后 → 审查计划 → 发现问题 → 改计划再执行
执行中：Step 执行后 → 检查结果 → 不对 → 立即调整重试（纠错最快，调用最密）
执行后：任务完成后 → 检查输出 → 不满意 → 带反思重跑（一次看全局）
失败后：Step 失败  → 分析原因 → 生成教训 → 存记忆，下次避免
```

时机选择是成本问题：执行中反思纠错最早但每步都花调用；执行后反思一次看全局，但错误可能已污染多步。高价值任务两者都要，普通任务只做执行后。

### 4.4 反思的核心范式

**范式 1：Self-Refine（2023 年论文提出）**

```text
生成初稿 → 自我批评 → 按批评改进 → 再批评 → 再改进 → 通过或到轮数上限
```

要点：批评与改进在**同一次尝试内**循环，改进只看当轮的批评，不跨尝试积累。  
适用：写作、代码生成、翻译——输出质量导向、单步可完成的任务。

**范式 2：Reflexion（2023 年论文提出）——本篇主角**

```text
执行 → 评估（成功/失败）→ 失败则反思生成教训 → 教训存入记忆 → 带教训重试 → 循环
```

机制要点（面试口径）：

1. 反思的单位是**一次完整尝试**，不是单个步骤。
2. 反思结论是语言化的经验文本（「下次先按地区拆分再下结论」），存入记忆，下一次尝试注入 Prompt。
3. 与纯重试的本质区别：**有语言化经验沉淀**——第 N 次尝试站在前 N-1 次失败的肩膀上；纯重试每次从零开始。
4. 与 ReAct 的区别：ReAct 在单次尝试内交替「思考-行动-观察」；Reflexion 在多次尝试之间沉淀记忆。两者常组合使用（见 2.7）。

面试高频问法：「什么是 Reflexion？和 ReAct 的区别是什么？怎么提升 Agent 自我纠错能力？」——答：Reflexion 定义 + 与 ReAct 的单位差异（尝试内 vs 尝试间）+ 提升纠错的工程手段（验证器、教训记忆、最大轮数、升级人工）。

**范式 3：CRITIC（2023 年论文提出）**

```text
生成 → 调外部工具验证（搜索、计算器、代码执行）→ 按验证结果修正 → 循环
```

要点：错不错由工具说了算，不靠模型自觉。变体「验证反思」：生成中发现某事实拿不准，主动触发搜索核实再决定输出，而不是盲写——这是幻觉校正的常用手段；RAG 场景同源的 Self-RAG 式「检索 → 自评 → 修正」循环见 1.4。  
适用：事实性任务、计算任务。

**范式 4：Constitutional AI（Anthropic，2022 年提出）**

```text
定义一组原则（宪法）→ 生成 → 对照原则检查 → 违反则修正 → 输出
```

要点：批评标准是显式原则清单，不是模型自由发挥。  
适用：安全、合规、价值观对齐。

**范式 5：验证器（Verifier）模式**

```text
主模型生成 → 独立验证器（规则 / 另一模型 / 测试）检查 → 通过输出 / 不通过打回
```

适用：代码、数学、结构化输出——存在客观对错标准的任务。

**五范式对比**：

| 范式 | 循环粒度 | 反思对象 | 跨尝试记忆 | 典型场景 |
|---|---|---|---|---|
| Self-Refine | 单次尝试内 | 输出质量 | 无 | 写作、代码、翻译 |
| Reflexion | 跨尝试 | 失败原因 | 有（教训库） | 多步任务、代码修复 |
| CRITIC | 单次尝试内 | 事实正确性 | 无 | 事实核查、计算 |
| Constitutional AI | 单次尝试内 | 安全合规 | 无 | 安全对齐 |
| Verifier | 单次尝试内 | 可形式化判定 | 无 | 代码、数学、JSON |

选型口诀（业界共识）：单步灵活性找 ReAct、长任务跑偏找 Plan-Execute、输出质量找 Reflection——三者可叠加不互斥，完整对比见 2.7。截至 2026 年，主流编排框架（如 LangGraph）都把反思节点作为常见模式提供，图编排基础见 2.5 与 3.3。

### 4.5 错误检测的实现方式：验证器选型

| 实现方式 | 怎么做 | 优点 | 局限 | 成本 |
|---|---|---|---|---|
| 规则验证 | Schema、正则、类型检查 | 确定、快、零额外调用 | 只查形式，查不了语义 | 极低 |
| 工具验证 | 搜索核实、执行代码、跑测试 | 客观，能到事实级 | 依赖工具覆盖面 | 中 |
| LLM 自我批评 | 模型按检查清单审输出/轨迹 | 通用，无需外部设施 | 自我欺骗、批评空泛 | 中 |
| 多模型交叉验证 | 多模型生成 + 投票 / 一致性 | 独立性强 | 贵、慢，且可能同源同错 | 高 |
| 人类信号 | 用户纠错、审批拒绝 | 最准 | 慢、贵、不可扩展 | 高 |

组合原则：**能用规则的不要用模型，能用工具的不要用自我批评，人类信号留作兜底**。实现代码见第 6 节。

### 4.6 反思的内容：检查清单与 Prompt 模板

| 维度 | 检查项 |
|---|---|
| 正确性 | 事实是否正确？计算是否准确？ |
| 完整性 | 是否回答了所有问题？是否遗漏？ |
| 相关性 | 是否切题？是否跑偏？ |
| 格式 | 是否符合要求？JSON 是否合法？ |
| 逻辑 | 推理是否连贯？有无矛盾？ |
| 安全性 | 是否有害？是否泄露？ |
| 效率 | 是否用了最少步骤？成本是否合理？ |
| 风格 | 是否符合品牌调性？ |

**反思 Prompt 模板**：

```text
你是一个严格的审查员。请审查以下 Agent 执行过程。

目标：{goal}
计划：{plan}
执行结果：{results}
最终输出：{output}

请从以下维度审查：
1. 正确性：输出是否正确？
2. 完整性：是否完成目标？
3. 效率：是否有更优路径？
4. 安全性：是否有风险？

输出 JSON：
{
  "passed": true/false,
  "issues": [{"type": "...", "description": "...", "severity": "..."}],
  "suggestions": ["..."],
  "next_action": "accept|retry|replan|escalate"
}
```

`next_action` 字段是反思与修正的接口：批评不能只说「不好」，必须给出可执行的下一步动作。

### 4.7 自我修正策略

根据反思结果，按错误类型选择修正策略：

| 问题类型 | 修正策略 |
|---|---|
| 格式错误 | 重试 + 加格式约束 |
| 参数错误 | 反馈错误信息 + 重新调用 |
| 事实错误 | 检索验证 + 修正 |
| 推理错误 | 重新推理 + 显式推理链 |
| 工具选错 | 重新选择工具 |
| 计划不合理 | 重规划（见 2.2） |
| 目标理解错 | 向用户澄清目标 |
| 无法解决 | 升级 / 转人工 |

注意：这里的重试必须**带反馈**（错误信息或教训）——不带反馈的重试只是掷骰子；纯操作层的退避重试与上限控制见 2.5。

**修正循环**：

```python
async def self_correct(task: str, max_iterations: int = 3) -> str:
    output = await generate(task)
    for i in range(max_iterations):
        critique = await critique_output(task, output)   # 批评：结构化 JSON
        if critique["passed"]:
            return output                                # 通过即出
        # 重试带反馈：把 issues 与 suggestions 一起喂回去
        output = await refine(task, output, critique["suggestions"])
    return output                                        # 到上限返回最后版本
```

### 4.8 反思与记忆的结合

反思结果应写入记忆，避免重复犯错——这是 Reflexion 的核心，也是「错题本」的工程对应物（记忆系统全貌见 2.4）：

```python
class ReflectiveMemory:
    def __init__(self):
        self.lessons = []  # 教训库

    def add_lesson(self, task_type: str, error: str, lesson: str):
        self.lessons.append({
            "task_type": task_type,
            "error": error,
            "lesson": lesson,
            "timestamp": now(),
        })

    def get_relevant_lessons(self, task_type: str) -> list:
        return [l for l in self.lessons if l["task_type"] == task_type]

# 使用：任务开始前取同类教训，注入 Prompt
lessons = memory.get_relevant_lessons("查订单")
```

**教训示例**：

```text
教训 1：调用 search_orders 时，status 只能用枚举值。
教训 2：退款金额 > 500 需要人工审批。
教训 3：用户说「那个订单」时，需要先检索历史订单再确认指代。
```

好的教训有三个特征：具体（能直接执行）、可迁移（同类任务通用）、可验证（下次能检查是否遵守）。空泛的「下次仔细点」没有价值。

### 4.9 反思的成本与收益

**成本**：

- 额外的 LLM 调用（批评 + 改进，每轮 2 次）
- 更长的延迟（通常 1–3 倍）
- 更高的 token 消耗

**收益**：

- 更高的准确率、更少的错误外流
- 更好的鲁棒性
- 从错误中学习（教训可跨任务复用）

**权衡表**：

| 场景 | 是否反思 | 深度 |
|---|---|---|
| 高价值任务（资金、代码、合规） | 是 | 多轮反思 + 独立验证器 |
| 普通任务 | 是 | 一轮轻量反思 |
| 简单任务（改写、分类） | 否 | 只做规则校验 |
| 实时交互（对话中） | 轻量 | 规则 + 快速自检 |
| 离线批处理 | 充分 | 全链路反思 + 交叉验证 |

**反思触发条件**（什么时候值得反思）：验证失败、连续 2 次相同失败、高价值任务终审、用户负反馈。不要每步无条件反思，成本会吞掉收益（成本工程见 3.7）。

**经验值**：

- 反思 1–2 轮通常收益最大。
- 超过 3 轮收益递减。
- 必须设最大轮数与预算双上限，防止无限循环（终止条件见 2.5）。

### 4.10 反思的失败模式

| 失败 | 原因 | 解法 |
|---|---|---|
| 反思无效果 | 批评太泛 | 具体化检查项（见 4.6） |
| 越改越差 | 过度修正 | 设轮数上限，保留最好版本 |
| 自我欺骗 | 模型认为自己对 | 用独立验证器或更强模型批评 |
| 成本失控 | 无限反思 | 预算 + 轮数双限制 |
| 不学教训 | 没写入记忆 | 反思结果持久化（见 4.8） |
| 批评不准确 | 批评模型弱 | 用同等或更强模型批评 |
| 循环反思 | 无终止条件 | 最大轮数 |

### 4.11 反思与其他组件的关系

```text
┌──────────────────────────────────────────┐
│                 反思                      │
│  ├─ 输入：执行结果、输出、上下文          │
│  ├─ 处理：批评、验证、分析                │
│  └─ 输出：问题、建议、教训                │
└──────────────────────────────────────────┘
       ↑              ↓              ↑
       │              │              │
   ┌───┴───┐    ┌─────┴─────┐   ┌───┴───┐
   │ 执行  │    │  修正策略  │   │ 记忆  │
   │ 循环  │    │ 重试/重规划│   │ 教训  │
   │ (2.5) │    │  (4.7)    │   │ (2.4) │
   └───────┘    └───────────┘   └───────┘
```

## 5. 架构 / 流程

一个完整的反思与自我修正系统：

```text
┌──────────────────────────────────────────┐
│  执行                                     │
│  ├─ 生成输出                             │
│  └─ 记录过程（轨迹，可回溯）             │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  反思（三路信号并行）                     │
│  ├─ 输出检查（格式、完整性）             │
│  ├─ 事实验证（搜索、计算、测试）         │
│  ├─ 逻辑检查（一致性）                   │
│  ├─ 安全审查（合规、有害）               │
│  └─ 效率评估（步数、成本）               │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  判断（按错误层级分级，见 4.1）           │
│  ├─ 通过？→ 输出                         │
│  ├─ 输出层小问题？→ 修正重试             │
│  ├─ 行动层问题？→ 换工具/改参数          │
│  ├─ 计划层问题？→ 重规划                 │
│  └─ 无法解决？→ 升级/转人工              │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  修正                                     │
│  ├─ 局部修正（改参数、换工具）           │
│  ├─ 全局修正（重规划）                   │
│  └─ 学习（教训写入记忆）                 │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  重新执行                                 │
│  └─ 带修正信息与历史教训，重试           │
└──────────────────────────────────────────┘
```

### 6.1 Self-Refine 实现

```python
import json

async def generate(task: str) -> str:
    """生成初稿（llm.chat 为项目内的模型调用封装）"""
    return await llm.chat([{"role": "user", "content": task}], temperature=0.7)

async def critique(task: str, output: str) -> dict:
    """自我批评：按检查清单审输出，结构化返回（清单见 4.6）"""
    prompt = f"""请审查以下输出，找出问题。
任务：{task}
输出：{output}
检查：1. 是否回答了问题？2. 是否有事实错误？3. 是否遗漏关键信息？4. 格式是否符合要求？
输出 JSON：{{"passed": true, "issues": ["..."], "suggestions": ["..."]}}"""
    resp = await llm.chat([{"role": "user", "content": prompt}], temperature=0)
    return json.loads(resp)

async def refine(task: str, output: str, suggestions: list) -> str:
    """按批评建议改进输出"""
    tips = "\n".join(f"- {s}" for s in suggestions)
    return await llm.chat(
        [{"role": "user", "content": f"任务：{task}\n原输出：{output}\n按以下建议改进：\n{tips}"}],
        temperature=0.7,
    )

async def self_refine(task: str, max_iterations: int = 3) -> str:
    """Self-Refine 主循环：生成 → 批评 → 改进，最多 max_iterations 轮"""
    output = await generate(task)
    for i in range(max_iterations):
        c = await critique(task, output)
        if c["passed"]:
            print(f"第 {i+1} 轮通过")
            return output                          # 通过即出
        print(f"第 {i+1} 轮发现问题: {c['issues']}")
        output = await refine(task, output, c["suggestions"])
    return output                                  # 到上限返回最后版本
```

### 6.2 Reflexion 循环最小实现

```python
class ReflexionAgent:
    """Reflexion 最小实现：执行 → 评估 → 反思 → 带教训重试"""

    def __init__(self, llm, max_attempts: int = 3):
        self.llm = llm
        self.max_attempts = max_attempts
        self.reflections = []          # 反思记忆（教训库），跨尝试累积

    async def run(self, task: str) -> dict:
        result = None
        for attempt in range(self.max_attempts):
            result = await self._execute(task)              # 1. 执行（带历史教训）
            evaluation = await self._evaluate(task, result) # 2. 评估成败
            if evaluation["success"]:
                return {"result": result, "attempts": attempt + 1}
            lesson = await self._reflect(task, result, evaluation)  # 3. 反思
            self.reflections.append(lesson)                 # 4. 教训写入记忆
            print(f"第 {attempt+1} 次失败，教训：{lesson}")
        return {"result": result, "attempts": self.max_attempts, "failed": True}

    async def _execute(self, task: str) -> str:
        # 关键：把历史教训注入 Prompt，下一次尝试「站在前几次失败的肩膀上」
        lessons = "\n".join(f"- {r}" for r in self.reflections)
        prompt = f"任务：{task}\n\n历史教训（务必避免重蹈覆辙）：\n{lessons}\n\n请执行任务。"
        return await self.llm.chat([{"role": "user", "content": prompt}])

    async def _evaluate(self, task: str, result: str) -> dict:
        # 生产建议：优先用验证器（测试/规则）评估，LLM 评估仅作补充（见 4.5）
        prompt = (f"评估任务是否完成。\n任务：{task}\n结果：{result}\n"
                  f'输出 JSON：{{"success": false, "reason": "..."}}')
        return json.loads(await self.llm.chat(
            [{"role": "user", "content": prompt}], temperature=0))

    async def _reflect(self, task: str, result: str, evaluation: dict) -> str:
        # 反思输出一条可执行教训：错在哪、下次怎么改（好教训的标准见 4.8）
        prompt = (f"分析失败原因并生成教训。\n任务：{task}\n结果：{result}\n"
                  f"失败原因：{evaluation['reason']}\n输出一条简洁教训（下次如何避免）：")
        return await self.llm.chat([{"role": "user", "content": prompt}], temperature=0)
```

### 6.3 CRITIC 实现（工具验证）

```python
async def critic_loop(task: str, max_iterations: int = 3) -> str:
    """CRITIC：生成 → 工具验证 → 修正，错不错工具说了算"""
    output = await generate(task)
    for _ in range(max_iterations):
        issues = []
        for fact in await extract_facts(output):       # 1. 抽取待验证事实
            hit = await search(fact["claim"])          # 2. 搜索核实
            if not hit["confirmed"]:
                issues.append({"type": "fact_error",
                               "claim": fact["claim"], "evidence": hit["evidence"]})
            if fact.get("calculation"):                # 3. 计算复核
                actual = await calculate(fact["calculation"])
                if actual != fact["expected"]:
                    issues.append({"type": "calc_error", "claim": fact["calculation"],
                                   "expected": fact["expected"], "actual": actual})
        if not issues:
            return output                              # 全部通过
        output = await fix_issues(task, output, issues)  # 4. 按证据修正
    return output
```

### 6.4 验证器与执行循环集成

```python
import re

def is_valid_json(output: str) -> bool:     # 规则：必须是合法 JSON
    try:
        json.loads(output)
        return True
    except json.JSONDecodeError:
        return False

def no_pii(output: str) -> bool:            # 规则：不得含手机号/身份证号
    return not re.search(r"\d{11}|\d{18}", output)

async def agent_with_reflection(goal: str, max_steps: int = 10):
    """把反思嵌进 2.5 的执行循环：每步轻审，失败分级修正，教训入库"""
    state, lessons = AgentState(goal=goal), []
    while state.current_step < max_steps:
        action = await decide(state)
        result = await execute(action)
        state = update(state, action, result)

        if should_reflect(state):                        # 触发条件见 4.9
            # 规则验证 + LLM 批评，产出结构化 verdict 与 next_action
            critique = await critique_step(
                state, action, result, rules=[is_valid_json, no_pii])
            if not critique["passed"]:
                if critique["action"] == "retry":        # 行动层：改参数重试
                    continue
                elif critique["action"] == "replan":     # 计划层：回 2.2 重规划
                    state.plan = await replan(state, critique)
                    state.current_step = 0
                elif critique["action"] == "escalate":   # 无法解决：转人工
                    return await escalate(state)
            if critique.get("lesson"):                   # 教训入库，下次注入
                lessons.append(critique["lesson"])

        if is_done(state):
            break

    final = await critique_final(state)                  # 终审（Level 1 反思）
    return {"result": state, "reflections": lessons}
```

### 案例 A：代码生成 Self-Refine（某工具库团队内部评测，数字为示意量级）

**任务**：「写一个 Python 函数，判断字符串是否为回文。」

**第 1 轮**：

```python
def is_palindrome(s):
    return s == s[::-1]
```

**批评**：未处理大小写；未处理空格和标点；未处理空字符串。

**第 2 轮**：

```python
import re

def is_palindrome(s: str) -> bool:
    cleaned = re.sub(r'[^a-zA-Z0-9]', '', s).lower()
    return cleaned == cleaned[::-1]
```

**通过**：边界用例 8/8 全过（第 1 轮仅 3/8）。  
**规模数据**：60 题代码生成评测集上，首轮单测通过率 71%，加至多 3 轮 Self-Refine 后 89%；平均每题多 1.6 次调用、延迟约 2.3 倍。收益主要来自前 2 轮，第 3 轮只贡献约 1 个百分点——印证「1–2 轮收益最大」。

### 案例 B：数据分析 Reflexion（某电商周报场景，数字为示意量级）

**任务**：「分析销售数据，找出下降原因。」

**第 1 次尝试**：

- 执行：读取数据 → 按月聚合 → 发现 3 月下降
- 评估：失败——只发现了现象，没有回答「为什么」
- 反思：「只看了总量。下次先按地区、产品、渠道拆分，再下结论。」

**第 2 次尝试（带教训）**：

- 执行：读取 → 按月 → 按地区 → 按产品 → 定位华东 A 产品下滑
- 评估：成功——有现象、有原因、可行动

**教训写入记忆**：「分析销售下降时，先按多个维度拆分再下结论。」  
**规模数据**：接入教训库并允许至多 3 次尝试后，这类分析任务的一次通过率从 55% 升到 82%；教训库沉淀 40 余条后，同类任务首轮通过率也升到 74%——教训在跨任务起作用，这才是 Reflexion 与纯重试的差距。

### 案例 C：事实核查 CRITIC（内容平台抽检，数字为示意量级）

**任务**：「总结爱因斯坦的成就。」

**输出 v1**：「爱因斯坦 1921 年获得诺贝尔化学奖，提出了相对论。」

**验证**：

**规模数据**：50 条含 10 处事实错误的生成摘要，CRITIC 拦下 9 处（漏掉的 1 处为冷门时间细节）；修正后人工抽检错误率从 20% 降到 2%，代价是每条多 2–4 次搜索调用、延迟约 1.8 倍。

## 8. 常见坑

1. **反思无终止条件**：无限反思，成本失控。设最大轮数 + 预算双上限（见 2.5）。
2. **批评太泛**：「写得不好」没有指导意义。批评要具体到「缺少数据支撑」这一级，用检查清单约束（见 4.6）。
3. **过度修正**：越改越差。设轮数上限，保留评分最高的版本而不是最后版本。
4. **自我欺骗**：模型认为自己是对的。引入独立验证器或更强的批评模型（见 4.5）。
5. **不写入记忆**：反思完就忘，下次还犯。教训持久化并注入后续 Prompt（见 4.8）。
6. **反思成本超过收益**：简单任务也多轮反思。按任务价值定反思深度（见 4.9 权衡表）。
7. **验证器不可靠**：验证器本身出错，错把对的改错。多验证器交叉，验证器要进评测。
8. **只反思输出、不反思过程**：过程错了，输出对了也是运气。把工具选择、参数、计划纳入反思范围（Level 2/3，见 4.2）。
9. **忽略延迟**：反思通常增加 1–3 倍延迟。实时场景只留规则校验 + 快速自检。
10. **不做 A/B 对比**：不知道反思到底有没有提升效果。上线前后对比准确率与成本，方法见 1.6 与 3.5。
11. **批评模型太弱**：弱模型批评强模型，批评不准。批评用同等或更强模型，或用规则/工具替代。
12. **不区分错误类型**：格式错误和逻辑错误用同一招。按 4.7 的类型-策略表分类处理。
13. **反思结果不结构化**：自然语言教训难以程序化使用。批评输出 JSON，含 next_action。
14. **忽略人工介入**：有些错误反思解决不了，还在空转。到上限就升级/转人工，闭环设计见 3.10。

## 9. 练习

1. 实现 Self-Refine：生成 → 批评 → 改进，最多 3 轮。验收：批跑 20 个写作任务，对比首轮与末轮的清单得分。
2. 实现 Reflexion 最小循环（参考 6.2）：失败 → 反思 → 带教训重试。验收：打印每次尝试注入的教训，确认第 3 次尝试能看到前 2 次的教训。
3. 实现 CRITIC：用搜索/计算工具验证含 10 处事实错误的 20 条摘要。验收：报告拦截率与误伤率。
4. 给 Agent 加验证器：JSON Schema + PII 正则 + 事实抽查三层。验收：各层分别拦截的错误数。
5. 实现教训库：反思结果按 task_type 存取，下次同型任务自动注入。验收：同类错误复发率对比。
6. 对比实验：同一任务集跑「无反思 / 纯重试 / 反思重试」三版，对比成功率、调用次数、延迟。验收：一张三列对比表。
7. 实现多模型交叉验证：3 个模型生成 + 多数投票。验收：记录投票分歧比例与最终正确率的关系。
8. 实现反思的终止条件：最大轮数 + token 预算 + 连续失败熔断。验收：构造一个必然失败的任务，确认系统按时停机。
9. 设计一份覆盖正确性、完整性、格式、安全四维度的检查清单，并让批评模型严格按清单输出 JSON。验收：批评结果可被程序解析并路由到 retry/replan/escalate。
10. 评估反思的 ROI：选一个线上任务，量化「准确率提升 vs 成本增加」，给出是否保留反思的建议。验收：一页结论，含数字。

## 10. 小结

- 反思 = **审视输出 + 发现错误 + 生成改进**；自我修正 = 反思结果驱动**行动调整 + 重新执行**。
- 判断错了靠三路信号：**验证器、批评模型、人类信号**；修正按错误层级走：**修正重试 / 换法 / 重规划 / 反思注入 / 升级人工**。
- 三个层次：**输出反思、过程反思、策略反思**——层次越高改动越大，默认从低层起判。
- 核心范式：**Self-Refine、Reflexion、CRITIC、Constitutional AI、Verifier**。
- Reflexion 的本质：**反思结论作为语言化经验存入记忆，下一次尝试带经验执行**；与纯重试的区别就在「有没有经验沉淀」。
- 验证器选型原则：**规则优先于工具，工具优先于自我批评，人类信号兜底**。
- 关键工程：**最大轮数、预算限制、结构化反思（JSON + next_action）、教训写入记忆、A/B 量化**。
- 核心原则：**高价值任务多反思，简单任务不反思；反思必须有终止条件。**
- 这些能力直接支撑：2.7 单 Agent 架构、2.9 Agent 评估与安全、3.5 评估体系与实验管理。
