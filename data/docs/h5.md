# 讲解 H5 A2A 协议与多 Agent 互操作

> 说明：2.3b 讲了 MCP——Agent 与工具之间的标准接入层；2.8 讲了同一进程内多 Agent 的协作模式。本篇上移一层：跨框架、跨组织的 Agent 之间如何互相发现、委托任务、回报状态，标准答案就是 A2A（Agent-to-Agent）协议。  
> 平台内部的多 Agent 编排（主管-工人、通信协议栈）在 4-7 展开，A2A 管的是平台之外的水平协作。

---

## 1. 定位

H 层第 5 个锚点（deps：2-3b）。站点状态口径：**趋势观察**（考点卡口径）——协议事实层面进展迅猛：v1.0 已定稿并进入主流云平台、出现企业生产部署，但本站按从严原则标注其考察成熟度，面试考察以「与 MCP 怎么分工」一类概念题为主、尚在成形中。考点卡来源标注为「A2A 官方 v1.0（Linux Foundation 2026-03）/ 卡码」。

必须掌握的事实口径（2026 官方信息，引用时注意版本）：

1. **v1.0 定稿**：A2A 于 2026-03 在 Linux Foundation 正式定稿 v1.0（随后有 v1.0.1 修订）——此前由 Google 于 2025-04 发起、同年捐入 Linux Foundation 做厂商中立治理。
2. **生态规模**：2026-04 协议发布一周年时，官方口径为 **150+ 组织参与**，协议进入主流云平台并有企业生产部署案例。
3. **Signed Agent Cards**：v1.0 引入签名 Agent Card——能力名片可附签名，防篡改、防冒充，这是从「声明式发现」走向「可验证发现」的关键一步。

它回答的前沿面试问题是：**「MCP 和 A2A 都是协议，有什么区别？为什么 MCP 解决不了 A2A 要解决的问题？」**——答分点在垂直/水平分工与协议抽象层级，本篇 4.5 节专述。

## 2. 一句话定义

A2A 是一个开放的 Agent 互操作协议：每个 Agent 在标准位置暴露一张能力名片（Agent Card），其他 Agent（或客户端）据此发现它、用结构化 Task 委托任务、按生命周期状态回报进度与产物——让不同框架、不同厂商的 Agent 像对等组织一样协作，委托方无需知道对方的内部实现。

## 3. 为什么需要

### 3.1 集成地狱重现

Agent 生态爆发后，问题回到三十年前企业软件的老路：你的 Agent 用框架 X，合作伙伴的差旅 Agent 用框架 Y，第三方的数据分析 Agent 是某云厂商闭源服务。要协作，每两方都得做一次私有集成——N 个 Agent 需要 N x (N-1)/2 条定制对接线，模型、工具、消息格式、鉴权全对不上。协议把 N x (N-1)/2 压成 N：每方实现一次 A2A，即可与所有实现方互通。

两个类比（本站考点卡口径）：

- **Agent 界的 HTTP**：各家 Agent 像早期孤岛式即时通讯软件——互相加不了好友。A2A 之于 Agent，如 HTTP 之于网站：统一的能力名片、任务委托、消息格式，任何符合协议的 Agent 都能与任何其他 Agent 协作，不管底层框架。
- **外包协作合同**：MCP 像公司给员工配的标准工具台（内部怎么接工具）；A2A 像公司之间的外包合同（对等组织如何委托任务）——甲方把任务连同验收标准发给乙方，乙方用自己的团队（自己的模型、自己的工具）完成，按协议回报进度与产物。

### 3.2 为什么 MCP 解决不了 A2A 的问题

这是本题的核心采分点。MCP 不是「差一点的 A2A」，而是抽象层级不同的另一层协议：

| 维度 | MCP | A2A |
|---|---|---|
| 连接对象 | Agent ↔ 工具/资源（垂直） | Agent ↔ Agent（水平，对等） |
| 角色模型 | Client-Server：工具是被动能力，被调用即返回 | 对等协作：远端 Agent 是自主执行者，有自己的状态与策略 |
| 交互形态 | 一次工具调用，同步取结果 | 长任务生命周期：可运行数分钟到数天，异步推进 |
| 能力声明 | 工具的参数 schema（怎么调这个函数） | Agent Card（我是谁、擅长什么任务域、怎么找我、怎么鉴权） |
| 过程透明度 | 调用方完全掌控执行 | Opaque（不透明协作）：内部模型/工具/流程对委托方黑盒 |
| 多轮交互 | 工具不反问调用方 | input-required 状态：远端可挂起等用户补充信息 |
| 典型问题 | 「我的 Agent 怎么接上你的数据库」 | 「我的 Agent 怎么把订票任务外包给你的 Agent」 |

具体论证「为什么不够」：

1. **工具没有自主性**。MCP Server 是被动的函数集合，被调用、执行、返回；A2A 的远端是一个完整的 Agent——它自己规划、自己用工具、自己处理异常。把一个 Agent 当 MCP 工具暴露，等于要求委托方接管它的全部内部编排，跨组织做不到也不该做。
2. **没有任务生命周期**。MCP 调用是请求-响应，几分钟的长任务没有「处理中/需要补件/已完成/失败」的状态机，委托方无法跟踪、无法挂起恢复。
3. **没有能力发现的对等语义**。MCP 的工具列表回答「你有哪些函数」；A2A 的 Agent Card 回答「你是谁、能承包什么任务、如何建立信任」——这是组织间协作需要的商业语义，不是函数签名。
4. **信任与责任模型不同**。Agent 间委托涉及鉴权、责任边界、审计留痕——外包合同条款；工具调用只涉及函数执行正确性。

结论：**MCP 管垂直的工具接入，A2A 管水平的 Agent 协作——互补而非竞争**。同一个 Agent 完全可以既用 MCP 接自己的工具，又用 A2A 接受外部委托。

## 4. 核心原理

### 4.1 Agent Card：能力名片与发现机制

每个 A2A Server 在约定位置暴露 Agent Card（JSON 文档），这是发现的起点：

- **标准位置**：`https://<host>/.well-known/agent.json`（well-known URI 约定，与 OAuth、ACME 同一路数）。
- **签名（v1.0 重点）**：Signed Agent Cards 允许名片附带签名，客户端可验证卡片未被篡改、确实来自声明的主体——跨组织场景里防冒充的信任锚。
- **发现路径**：直接已知 URL 拉取；或经注册表/目录服务聚合检索（企业内部可自建 Agent 目录）。

名片核心字段一览：

| 字段 | 内容 | 委托方用它做什么 |
|---|---|---|
| protocolVersion | 协议版本（如 1.0） | 兼容性校验，版本不符拒绝对接 |
| name / description | 名称与能力自述 | 粗筛：这个 Agent 管不管我的需求域 |
| url | A2A 服务端点 | 后续 message/send 的目标地址 |
| capabilities | 能力开关（流式、推送通知） | 决定轮询还是订阅的实现方式 |
| authentication | 鉴权方案声明 | 我方凭据管理是否支持该方案 |
| skills | 技能清单（id/描述/标签/示例） | 精筛：具体任务匹配到哪个技能 |

工程要点：名片声明的是「能力边界即接口」——委托方只依赖名片描述做决策，能力是否名实相符要靠沙箱验证（见第 8 节坑 4）。

### 4.2 Task：任务生命周期与委派

A2A 的核心数据模型是 Task（任务对象），有独立 ID 与状态机：

```text
submitted（已提交）→ working（执行中）→ completed（已完成）
                          |
                          ├→ input-required（等待补充信息，挂起）
                          └→ failed（失败）/ canceled（取消）
```

委派流程四步：

1. **发现**：拉取对方 Agent Card，确认技能匹配、鉴权可行。
2. **发送**：向对方端点发 `message/send`（或流式 `message/stream`），消息里带任务意图与结构化上下文（行程、偏好、预算上限、验收标准）。
3. **生命周期管理**：用 `tasks/get` 轮询或订阅通知跟踪状态；`input-required` 时桥接我方用户补信息再续；长任务可注册推送回调（push notification）。
4. **交付**：`completed` 后取回 Artifact（产物，如行程单文件）并归档计费。

关键设计：**支持长任务与多轮补信息**——这正是 MCP 单次调用模型缺失的能力，也是「外包合同」类比里「按阶段汇报、缺材料找甲方要」的协议化。

### 4.3 Opaque 协作：能力边界即接口

A2A 明确规定委托方不假设对方的内部实现：对方用什么模型、什么框架、什么工具，一概黑盒。收益：

- 双方可各自独立升级内部实现，接口不变即合约不变。
- 厂商中立：框架 X 与框架 Y 互通不需要任何一方迁就。
- 责任清晰：内部怎么做是乙方的事，合约看输入输出与验收标准。

代价是信任必须外置：签名名片验证身份、沙箱任务验证能力、留痕审计验证行为——协议给通道，信任靠配套。

### 4.4 传输与消息形态

核心形态是 HTTPS 上的 JSON-RPC 消息（`message/send`、`tasks/get` 等方法），v1.0 提供多传输绑定并保持消息语义一致；流式场景用 SSE 持续推送状态更新，长任务可配推送通知回调。鉴权在 HTTP 层完成（API key、OAuth 等，名片中声明），协议本体不另造身份体系。

### 4.5 协议格局：A2A / MCP / ACP / ANP

2026 社区讨论常四者并列，定位各有侧重（按考点卡与研究口径，ACP/ANP 细节以官方文档为准）：

| 协议 | 发起方 | 定位 | 一句话差异 |
|---|---|---|---|
| MCP | Anthropic，开放规范 | Agent↔工具/资源（垂直接入） | 管设备：标准工具台 |
| A2A | Google 发起，Linux Foundation 治理 | Agent↔Agent（水平协作，跨组织） | 管外包：能力名片+任务生命周期 |
| ACP | IBM/BeeAI 等推动 | Agent 间通信（REST、低门槛） | 走纯 HTTP/REST 的轻量替代路线，强调离线/进程间场景 |
| ANP | 开源社区 | 去中心化 Agent 网络 | DID（去中心化身份）为根的开放互联网路线 |

判读：MCP 已是事实标准；A2A v1.0 定稿后进入主流云平台，是跨组织互操作的主导候选；ACP/ANP 代表不同取舍（轻量化 vs 去中心化），生态仍早期。面试表态建议：**讲清 MCP/A2A 分工为主，ACP/ANP 一句话带过并诚实标注成熟度**。

## 5. 架构 / 流程

一次跨厂商协作的完整时序（对应本站考点卡 demo 的三步）：

```text
 主 Agent（框架 X，我方）                差旅 Agent（框架 Y，合作方）
        |                                        |
        |  ① 发现：GET /.well-known/agent.json    |
        |--------------------------------------->|
        |  ← Agent Card：技能"订票/订酒店"、        |
        |    鉴权 OAuth、支持流式与推送             |
        |  （验签名，确认能力与边界）                |
        |                                        |
        |  ② 委托：message/send                    |
        |--------------------------------------->|
        |    task: "预订 9/10 北京→上海，          |
        |     靠窗经济舱，预算上限 1500"            |
        |     验收：出票成功 + 行程单               |
        |                                        |
        |  ③ 状态回报（SSE / tasks/get 轮询）       |
        |<------- working（查询航班中）------------|
        |<------- input-required（需护照信息）-----|
        |------- 补充信息（多轮续传）-------------->|
        |<------- completed + Artifact 行程单 -----|
        |                                        |
        |  ④ 验收产物 → 归档、计费、审计留痕         |
```

分层视角：单个 Agent 内部是 2.7 的架构 + MCP 接工具；Agent 之间是 A2A 的名片与任务；两者叠加才是完整的多 Agent 互操作栈。

### 6.2 委派流程示例（发现 → 委托 → 生命周期管理）

```python
import json
import requests

class A2AClient:
    """最小 A2A 客户端：发现、委托、跟踪生命周期。
    生产实现请用官方 SDK；此处展示协议语义。"""

    def __init__(self, base_url: str, token: str):
        self.base = base_url.rstrip("/")
        self.headers = {"Authorization": f"Bearer {token}"}
        self._id = 0

    # ---- 第 1 步：发现（拉取并校验能力名片）----
    def discover(self) -> dict:
        card = requests.get(
            f"{self.host_origin()}/.well-known/agent.json", timeout=5
        ).json()
        # 生产环境：验签名（Signed Agent Cards）+ 核对鉴权方案是否支持
        assert card["protocolVersion"].startswith("1."), "协议版本不匹配"
        return card

    def host_origin(self) -> str:
        return self.base.split("/a2a")[0]

    def has_skill(self, card: dict, keyword: str) -> bool:
        return any(keyword in s["name"] or keyword in s["description"]
                   for s in card.get("skills", []))

    # ---- 第 2 步：委托任务（JSON-RPC message/send）----
    def send(self, text: str, task_id: str | None = None) -> dict:
        self._id += 1
        payload = {
            "jsonrpc": "2.0", "id": self._id, "method": "message/send",
            "params": {
                "message": {
                    "role": "user",
                    "parts": [{"type": "text", "text": text}],
                    "taskId": task_id,           # 续传时带同一 taskId
                    "messageId": f"m-{self._id}",
                },
            },
        }
        return requests.post(self.base, json=payload,
                             headers=self.headers, timeout=30).json()

    # ---- 第 3 步：跟踪生命周期（tasks/get 轮询）----
    def wait_terminal(self, task_id: str, max_polls: int = 30) -> dict:
        for _ in range(max_polls):
            state = self.get_task(task_id)
            s = state["status"]["state"]
            if s == "input-required":            # 远端要补信息 → 桥接我方用户
                answer = ask_our_user(state["status"]["message"])
                state = self.send(answer, task_id=task_id)   # 同 taskId 续传
                continue
            if s in ("completed", "failed", "canceled"):
                return state
        raise TimeoutError("任务未在轮询窗口内到达终态")

    def get_task(self, task_id: str) -> dict:
        self._id += 1
        payload = {"jsonrpc": "2.0", "id": self._id,
                   "method": "tasks/get", "params": {"id": task_id}}
        return requests.post(self.base, json=payload,
                             headers=self.headers, timeout=10).json()["result"]

def ask_our_user(remote_question: dict) -> str:
    print("远端 Agent 需要：", remote_question)
    return input("> ")

# ---- 完整委派 ----
client = A2AClient("https://travel.example.com/a2a", token="OAUTH_TOKEN")
card = client.discover()
assert client.has_skill(card, "机票"), "对方名片没有订票技能"

resp = client.send(
    "预订 9/10 北京→上海经济舱靠窗，预算上限 1500 元；"
    "验收标准：出票成功 + 交付行程单。"
)
task_id = resp["result"]["id"]
final = client.wait_terminal(task_id)

if final["status"]["state"] == "completed":
    artifacts = final.get("artifacts", [])      # 行程单等产物
    print("交付产物：", [a["name"] for a in artifacts])
    # 第 4 步：归档、计费、审计留痕（task_id 全程可追溯）
else:
    print("任务失败：", final["status"])
```

### 6.3 自检清单：接一个外部 Agent 前必做

```text
[ ] 拉取 Agent Card 并验证签名/域名一致性
[ ] 核对鉴权方案与我方凭据管理方式
[ ] 用沙箱任务实测能力（名片≠实测能力，见坑 4）
[ ] 约定任务超时、重试与取消策略
[ ] 明确敏感字段最小化披露清单（证件号等）
[ ] 合同明确责任边界（出错谁担责）与审计留痕方案
```

## 7. 案例

### 案例 A：跨厂商差旅集成

**场景**：某公司自研客服 Agent（框架 X），需要接入合作伙伴差旅 Agent（框架 Y）帮客户订票。此前评估过两条路：为对方做一次私有 API 集成（约 4 人周，且对方换版本就重做）；按 A2A 对接（双方各实现一次，名片+任务模型对齐）。

**实施**：沙箱环境先发 50 个测试任务验证对方真实能力与响应格式；生产上处理 input-required 桥接（护照信息由我方用户补）；completed 后验收行程单 Artifact 并计费归档；任务全程留痕可审计。

**效果**：集成周期从预估 4 人周缩到 1.5 人周；后续接入第二家差旅供应商时复用同一客户端，边际成本接近零——**多厂商异构接入时标准化收益才真正显现**。

### 案例 B：企业内部多团队 Agent 互联

**场景**：一家金融科技公司内部有五个团队各自的 Agent（客服、风控、合规、数据、运维），原来互不通信，跨域需求靠人工转发工单。

**实施**：内部建 Agent 目录（聚合各团队的 Agent Card），主客服 Agent 通过 A2A 把「该笔交易是否命中风控规则」委托给风控 Agent，把「引用哪条合规条款」委托给合规 Agent；长任务（批量报表）走异步任务+推送通知。

**效果**：跨域请求平均处理时长从小时级降到分钟级；每个 Agent 的边界由名片声明，职责冲突显著减少。这是 4-7 平台架构在跨团队维度的延伸。

### 案例 C：冷静判断——什么时候不用 A2A

**场景**：某团队只有一个外部合作方，被「上协议」的号召推着做了三个月 A2A 对接，期间对方协议实现还在频繁变更。

**修正与教训**：合作方仅此一家时，双方约定的私有 API 更快更稳；协议的价值在多方异构生态。技术选型先问**参与方数量与异构程度**——这是考点卡架构题里「成熟度判断」的采分点。2026 年的合理姿态：跟踪 v1.0 生态落地速度，多厂商场景优先采用，单点合作场景不必赶早。

## 8. 常见坑

1. **把 A2A 和 MCP 当竞争方案**。  
   一个连工具（垂直）一个连 Agent（水平），答成替代关系直接丢分。

2. **名片即信任**。  
   名片可以夸大甚至被冒充。签名验证+沙箱实测，两者都做。

3. **把远端 Agent 当函数调**。  
   忽视任务生命周期，长任务不做轮询/推送，超时无兜底。按状态机写集成。

4. **input-required 没有桥接设计**。  
   远端挂起等补件，我方无人处理，任务永久挂起。桥接我方用户或默认策略必须有。

5. **敏感信息过度披露**。  
   委托消息里顺手带上全套用户数据。最小化披露，按需传字段。

6. **无超时无取消**。  
   对方 Agent 挂了，我方跟着挂。每个任务设超时、可取消、可重试。

7. **不做留痕审计**。  
   跨组织协作出纠纷时拿不出证据。taskId、消息、产物全程归档。

8. **跳过沙箱验证直连生产**。  
   名片说支持≠真支持。上线前用测试任务验证响应格式与异常行为。

9. **责任边界口头约定**。  
   出票出错谁担责没写进合同。协议管通道，责任靠合同。

10. **版本不锁定**。  
    对方升级协议版本导致字段变更。发现时校验 protocolVersion，兼容策略前置。

11. **单合作方硬上协议**。  
    参与方只有一家时私有 API 更快。先问生态规模再选型。

12. **忽略推送通知能力协商**。  
    名片声明 capabilities 才能用推送；不核对就按推送写，运行期报错。

## 10. 小结

- A2A 是 **Agent 互联的开放标准**：能力名片（Agent Card）+ 任务生命周期（Task）+ 不透明协作（Opaque），类比「Agent 界的 HTTP」+「组织间外包合同」。
- 事实口径：**2026-03 于 Linux Foundation 定稿 v1.0，150+ 组织参与，新增 Signed Agent Cards，进入主流云平台**。
- Agent Card 发现：标准位置 **/.well-known/agent.json**，名片声明技能、鉴权、能力开关；v1.0 起可签名防篡改防冒充。
- 任务生命周期：**submitted → working → input-required → completed/failed/canceled**，支持长任务、多轮补信息、流式与推送通知。
- 与 MCP 的分工（标准采分点）：**MCP 管 Agent↔工具（垂直接入），A2A 管 Agent↔Agent（水平协作）**——互补而非竞争。
- MCP 解决不了 A2A 的问题，因为抽象层级不同：**工具是被动函数，Agent 是自主执行者**；长任务状态机、能力发现的对等语义、信任与责任模型，都是工具调用层没有的。
- 格局：**MCP 已是事实标准，A2A v1.0 是跨组织互操作主导候选，ACP（REST 轻量）/ANP（DID 去中心化）为不同取舍路线**，生态早期。
- 本站状态口径：**趋势观察**——协议事实进展迅猛，考察以概念分工题为主，引用时注明版本与时间点。
- 工程铁律：**名片≠实测能力**，签名验证+沙箱验证+最小化披露+留痕审计，一个都不能省。
- 选型冷静剂：**参与方数量与异构程度决定收益**——多厂商场景上协议，单点合作私有 API 更快。
- 与站内衔接：垂直接入层回看 2-3b，平台内编排看 4-7，A2A 补上的是平台之外的水平协作层。
