# 讲解 3.1 架构与接口设计

> 说明：2.7 解决了编排层内部「单 Agent 用什么架构模式」的选型问题；本篇把镜头拉远，解决 Agent 作为一个服务如何上生产——五层参考架构、AI 网关、同步异步边界、接口契约与容量规划。  
> 编排框架选型与防锁定在 3.3，可观测层的完整工程体系在 3.4 展开，部署与推理服务化在 3.6，最小权限与审计在 3.8，五层架构在真实业务约束下的完整推演在 4.7b。

## 1. 定位

AI 工程化阶段（S4）的第一篇架构课。它回答的问题：**当一个 Agent 要从笔记本 demo 变成 2000 人使用的服务，系统该怎么分层、边界怎么画、接口怎么定、容量怎么算？**

前置依赖只有 2.7——编排层里住着什么模式（工具型/RAG 型/工作流型/自主型），决定了编排层内部形态；但无论内部选什么模式，外层的服务架构是同一套。本篇与后续的关系：3.4 把可观测层展开成 Trace/指标/告警体系，3.6 从模型侧讲部署与显存，3.9 讲发布流程，4.7b 把本篇五层放进完整业务全案。本篇给的五层是后面所有篇目的地图。

## 2. 一句话定义

Agent 服务架构，是把系统拆成**接入（鉴权限流）→ AI 网关（密钥/路由/护栏/成本归因）→ 编排（Agent 循环）→ 数据（RAG/记忆/工具）→ 可观测（Trace/指标）**五层，层间用接口与事件解耦；接口设计遵循「长任务异步化、契约先行、错误结构统一」，容量规划从模型侧配额（TPM/RPM）开始而非服务器台数——每层的存在理由都能用「删掉它会坏什么」自测。

## 3. 为什么需要

反面教材先看三行代码的架构：业务函数里直接 `openai.chat.completions.create(...)`。半年后的三个下场：

1. **密钥散落**：厂商 Key 出现在 8 个仓库的环境变量里，泄露面不可控，轮换一次密钥要发 8 个服务。
2. **账单黑箱**：月底账单翻了三倍，没人说得清 token 花在哪个业务、哪个团队。
3. **换模型地震**：换一家供应商要改 40 处代码，回归全量业务。

这些痛点分别指向缺失的层：密钥治理与成本归因缺 **AI 网关**，出事定位不到人缺 **接入层** 的鉴权与 trace_id，回归成本爆炸缺 **编排层** 的边界隔离。架构图的本质是痛点的对账表——每个真实痛点都应该能指到一个具体层。

| 痛点 | 缺的层 | 该层的职责 |
|---|---|---|
| 恶意用户打爆服务、出事无法定位到人 | 接入层 | 鉴权、限流、配额、trace_id 生成 |
| Key 散落、换模型改 N 处、账单无法归因 | AI 网关 | 密钥集中、模型路由、护栏执行、成本归因 |
| 业务与 Agent 逻辑耦合、改动全量回归 | 编排层 | Agent 循环、规划、工具调用、状态管理 |
| 数据无版本无权限、换嵌入模型全库重建 | 数据层 | 向量库、记忆、工具注册表、权限过滤 |
| 线上坏了只能「重启试试」、迭代盲飞 | 可观测层 | Trace、指标、告警、回归数据集沉淀 |

## 4. 核心原理

### 4.1 五层参考架构

| 层 | 核心职责 | 关键设计决策 | 删掉它会坏什么 |
|---|---|---|---|
| 接入层 | 鉴权、限流、配额、trace_id | SSO 统一认证；按用户/部门限流；trace_id 全链路透传 | 一个恶意用户打爆全服务；出事无法定位到人 |
| AI 网关 | 密钥、路由、护栏、成本 | 按任务分级路由；单请求成本核算；降级熔断 | Key 泄露面大；换模型改 N 处；成本失控无护栏 |
| 编排层 | Agent 循环、状态、工具 | 长任务异步化；步数/预算双熔断；工具统一错误结构 | 业务和 Agent 逻辑耦成一坨，任何改动全量回归 |
| 数据层 | 向量库、记忆、工具注册表 | 按部门命名空间隔离；权限前置过滤；工具带最小权限标签 | 越权访问无防线；换嵌入模型即全库重建 |
| 可观测层 | Trace、指标、告警、回归 | 每步落盘可回放；成本/延迟按维度聚合；p95 告警 | 故障只能盲猜；没有评估护栏的任何迭代都是盲飞 |

两点补充口径。其一，有些资料画成六层，把**模型服务**（各厂商 API 或自托管推理）单独成层排在网关之后——本质相同，模型侧是网关的下游依赖，本篇按 3-1 考点口径画五层。其二，层间通信用接口与事件解耦：同步调用走契约化 HTTP/gRPC，任务完成、成本超限这类通知走事件，编排层不感知下游实现。

### 4.2 AI 网关：四件事

AI 网关是 2026 年 Agent 架构的标准件，它与传统 API 网关的区别正是以下四件事：

1. **密钥集中管理**：厂商 Key 只存在于网关，应用侧拿凭证找网关，Key 轮换不发版。
2. **模型路由**：按任务分级把请求路由到不同模型——FAQ 类路由到廉价模型保成本，复杂推理路由到强模型保质量；换模型从「改 40 处代码」变成「路由表改一行」。
3. **护栏执行点**：预算上限、内容审核、限流熔断统一在网关生效——全应用一处配置、改策略不用发版；护栏放在业务代码里则每个调用点都要记得检查，必然漏。
4. **成本归因**：token 级计量按调用方（用户/部门/功能）打标聚合，账单从黑箱变成看板。

| 维度 | 传统 API 网关 | AI 网关 |
|---|---|---|
| 管理对象 | HTTP 接口 | 模型调用 |
| 路由依据 | URL/头部 | 任务类型、成本档位、可用性 |
| 计量单位 | 请求数 | token 数 × 模型单价 |
| 护栏内容 | 频控、WAF | 预算、内容审核、模型降级 |
| 降级手段 | 备用实例 | 备用模型厂商 |
| 观测重点 | QPS、错误率 | token 消耗、每请求成本、TPM 限额水位 |

### 4.3 同步异步边界：长任务 task_id

判断标准一句话：**超过 30 秒的任务不要同步等**。Agent 任务常见 3~8 分钟（深度调研、报告生成），同步 HTTP 挂着等有三个死法：连接被代理超时切断、超时后结果丢失且无法重试、并发上不去（连接被占死）。

| 任务时长 | 接口形态 | 示例 |
|---|---|---|
| < 2 秒 | 同步请求/响应 | FAQ 问答、单轮改写 |
| 2~30 秒 | 同步 + 流式（SSE） | RAG 回答、单 Agent 短任务 |
| > 30 秒 | 异步任务化 | 深度调研、批量分析、报告生成 |

异步任务化的标准件：

- 提交接口立刻返回 `task_id`（HTTP 202），客户端轮询 `GET /tasks/{id}` 或订阅回调/WebSocket 推送；
- 任务状态机：queued → running → done / failed，状态与结果**持久化**（Redis/DB），进程重启不丢；
- 支持取消、超时、重试语义；结果保留 TTL；
- 幂等键防重复提交。

### 4.4 接口契约与错误结构

契约先行：请求/响应 Schema、错误码表、超时语义先写文档再写代码。两条铁律：

**工具与内部服务统一错误结构**，让编排层可以统一处理：

```json
{
  "ok": false,
  "error": {
    "code": "ORDER_NOT_FOUND",
    "message": "订单 A9999 不存在",
    "retryable": false,
    "trace_id": "t-7f3a"
  }
}
```

`retryable` 字段决定编排层行为：true 则带错误回传模型自修或退避重试，false 直接止损（2.3 的错误回传自修机制依赖这个字段）。

**对外错误码表分层**：4xx 客户端错（参数、权限、配额）、429 限流（带 Retry-After）、5xx 服务端错、504 上游模型超时。错误码是契约的一部分，增删要走评审——客户端会写 switch-case 依赖它。

### 4.5 架构自测法：删掉它会坏什么

每个组件回答两问：

1. **删掉它会坏什么？** 答不出 → 大概率是冗余层（PPT 架构），砍掉。
2. **换成别的实现要改几处？** 答不出（或答「很多」）→ 过度耦合，加接口边界。

反过来自查：每个真实痛点都应该能指到一个具体层——成本失控找网关、定位不到人找接入层 trace、越权找数据层。这套对账既是设计方法，也是面试答法：讲架构不说「我画了五层」，而说「每层删掉会坏什么」。

### 4.6 容量规划从模型配额开始

传统服务容量规划算服务器；Agent 服务流量涨十倍，先满的通常不是你的代码，而是**模型侧的 TPM/RPM 限额**。账要从模型配额算起：

```text
单任务 token 消耗 T（输入+输出，含每步重复携带的上下文）
峰值并发 C（或 QPS × 平均任务时长）
需要 TPM ≈ T × 任务完成速率 × 安全系数(1.5~2)
对照厂商限额 → 不够则：申请提额 / 多账号池化（网关做）/ 路由分流到小模型
```

示意：单任务平均 30K token，峰值每分钟完成 40 个任务，需要 TPM ≈ 30K × 40 × 1.5 = 180 万——远超常见默认限额。这就是为什么扩容设计先谈配额与路由，再谈服务副本数；服务层无状态化之后，副本本来就是随时可加的。

## 5. 架构 / 流程

五层架构与一次异步任务的完整流转：

```text
┌─────────────────────────────────────────────────────────┐
│ 接入层    鉴权 → 限流 → 生成 trace_id → 挂用户标识         │
└────────────────────────┬────────────────────────────────┘
                         ↓ POST /v1/agent/tasks
┌─────────────────────────────────────────────────────────┐
│ AI 网关   密钥代管 │ 按任务路由模型 │ 预算护栏 │ 成本打标  │
└────────────────────────┬────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────────┐
│ 编排层    立即返回 task_id(202) → 任务入队                 │
│   worker: Agent 循环(2.5/2.7) ←→ 工具(统一错误结构)        │
│   每步检查: 步数熔断 / 预算熔断 / 危险操作确认              │
└──────────┬──────────────────────────────┬───────────────┘
           ↓ 读/写                        ↓ 每步落盘
┌─────────────────────────┐  ┌────────────────────────────┐
│ 数据层                   │  │ 可观测层                    │
│ 向量库(权限隔离) 记忆     │  │ Trace 回放 │ 指标看板        │
│ 工具注册表(最小权限标签)  │  │ 成本归因 │ p95 告警 │ 回归集 │
└─────────────────────────┘  └────────────────────────────┘

异步任务时序：
客户端 ──POST──▶ 接入层 ──▶ 编排层 ──202 {task_id}──▶ 客户端
客户端 ──GET /tasks/{id}──▶ queued/running(轮询或推送)
完成   ──GET──▶ done + result（结果持久化，支持断线回查）
```

## 6. 代码 / 工具

### 6.1 FastAPI 异步任务接口

长任务任务化的最小骨架：提交即返回 task_id，状态机 + 结果持久化，统一错误结构。

```python
"""main.py — Agent 长任务异步接口（FastAPI）"""
import uuid
import asyncio
from enum import Enum
from datetime import datetime, timezone
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI(title="agent-api")

# 生产环境换 Redis/DB 持久化，这里用内存字典示意
TASKS: dict[str, dict] = {}


class TaskStatus(str, Enum):
    queued = "queued"
    running = "running"
    done = "done"
    failed = "failed"


class TaskRequest(BaseModel):
    goal: str = Field(..., min_length=1, max_length=2000)
    max_steps: int = Field(15, ge=1, le=50)          # 步数护栏
    budget_cents: int = Field(50, ge=1, le=1000)     # 成本护栏
    idempotency_key: str | None = None               # 防重复提交


@app.post("/v1/agent/tasks", status_code=202)
def submit_task(req: TaskRequest):
    if req.idempotency_key:
        hit = next((t for t in TASKS.values()
                    if t.get("idem") == req.idempotency_key), None)
        if hit:
            return {"ok": True, "data": _accepted(hit["task_id"])}  # 幂等命中

    task_id = uuid.uuid4().hex
    TASKS[task_id] = {
        "task_id": task_id, "status": TaskStatus.queued,
        "result": None, "error": None,
        "idem": req.idempotency_key,
        "created_at": datetime.now(timezone.utc).isoformat(),
    }
    asyncio.get_event_loop().create_task(_run(task_id, req))
    return {"ok": True, "data": _accepted(task_id)}


def _accepted(task_id: str) -> dict:
    return {"task_id": task_id, "status": TaskStatus.queued,
            "poll_url": f"/v1/agent/tasks/{task_id}"}


async def _run(task_id: str, req: TaskRequest):
    TASKS[task_id]["status"] = TaskStatus.running
    try:
        result = await agent_loop(goal=req.goal,
                                  max_steps=req.max_steps,
                                  budget_cents=req.budget_cents)
        TASKS[task_id].update(status=TaskStatus.done, result=result)
    except Exception as exc:
        TASKS[task_id].update(status=TaskStatus.failed, error={
            "code": "AGENT_FAILED", "message": str(exc),
            "retryable": True,
        })


async def agent_loop(goal: str, max_steps: int, budget_cents: int) -> dict:
    """编排层的 Agent 循环（示意）；每步过步数/预算双熔断"""
    steps, cost = [], 0
    for i in range(max_steps):
        # ... 调用 AI 网关路由的模型 + 工具，略
        cost += 3
        if cost > budget_cents:
            raise RuntimeError(f"预算超限: {cost} > {budget_cents}")
        steps.append({"i": i + 1, "cost_cents": cost})
    return {"answer": f"任务完成: {goal[:20]}...", "steps": steps, "cost_cents": cost}


@app.get("/v1/agent/tasks/{task_id}")
def get_task(task_id: str):
    task = TASKS.get(task_id)
    if task is None:
        raise HTTPException(status_code=404, detail={
            "ok": False,
            "error": {"code": "TASK_NOT_FOUND", "message": "任务不存在",
                      "retryable": False},
        })
    data = {"task_id": task_id, "status": task["status"],
            "created_at": task["created_at"]}
    if task["status"] is TaskStatus.done:
        data["result"] = task["result"]
    if task["status"] is TaskStatus.failed:
        data["error"] = task["error"]
    return {"ok": True, "data": data}
```

### 6.3 接口契约文档骨架

契约先行的落地产物（OpenAPI 之外的补充约定）：

```text
POST /v1/agent/tasks          提交任务 → 202 {task_id, poll_url}
GET  /v1/agent/tasks/{id}     查询状态/结果 → 200 {status, result|error}
POST /v1/agent/tasks/{id}/cancel  取消 → 200；已完成任务返回 409

超时语义：网关到模型 p99 超时 60s；任务总超时 15min（可配）
幂等：请求带 Idempotency-Key，24h 内去重
限流：429 + Retry-After；按用户 10 并发 / 按部门 TPM 配额
错误码表：
  INVALID_ARGUMENT(400, no)  QUOTA_EXCEEDED(429, yes)
  TASK_NOT_FOUND(404, no)    UPSTREAM_TIMEOUT(504, yes)
  BUDGET_EXCEEDED(402, no)   AGENT_FAILED(500, yes)
```

## 7. 案例

### 案例 A：客服 Agent 的五层改造

某电商客服团队起初在业务后端直连模型，半年后：换模型要改 40 处代码、Key 在 8 个仓库、月账单涨三倍但说不清去向。改造为五层：接入层接 SSO 并按部门限流；AI 网关统一三家模型，FAQ 类请求路由到廉价模型（占流量 70%），编排层长任务异步化；数据层按部门命名空间隔离检索。效果：换模型变成路由表改一行并当年完成两次厂商切换；账单按部门/功能归因后砍掉两类无效调用，月成本降 38%；一次线上故障凭 trace_id 在 10 分钟内定位到某工具超时引发的级联失败。

### 案例 B：深度调研 Agent 异步化

一家金融科技公司的调研 Agent 单次运行 3~8 分钟。最初同步接口把 HTTP 超时设为 10 分钟：网关 60 秒就切断，用户重试造成重复计算，高峰期连接池占死。改造为异步任务化：提交返回 task_id，状态机持久化到 Redis，前端轮询 + 完成推送；配幂等键后重试不再重复计算；编排层加步数 15 步、预算 $0.5 双熔断。结果：p95「提交响应」降至 120ms，任务完成率从 74% 升到 96%（超时丢结果清零），月 API 浪费成本降约 25%。

### 案例 C：流量十倍的容量推演

某企业助手计划从 200 人推广到 2000 人。团队先算模型账：当前峰值 TPM 已用到默认限额的 80%，流量十倍必然先撞限额。措施按序落：网关申请限额提升并池化多账号；意图分类后 70% 请求路由到小模型（其 TPM 充裕）；高频问答加语义缓存（3.7c 的四板斧之一）。最终推广后模型侧水位稳定在 65%，而服务层副本数只从 2 加到 3——验证了「容量规划从模型配额开始」：先满的从来不是你的服务器。

## 8. 常见坑

1. **模型调用写进业务代码**。  
   Key 散落、账单黑箱、换模型地震；第一刀永远是引入 AI 网关层。

2. **同步接口等长任务**。  
   分钟级任务挂 HTTP 必然超时丢结果；task_id + 状态机 + 持久化是唯一正解。

3. **任务状态只存内存**。  
   进程一重启任务全丢；状态与结果必须持久化，支持断线回查。

4. **没有幂等键**。  
   用户重试造成重复执行，副作用类任务（下单、退款）会出真实事故。

5. **护栏放在业务代码里**。  
   每个调用点各自检查必然漏；预算、内容护栏统一放网关，一处生效。

6. **成本不归因**。  
   只看总账单无法优化；token 计量必须按用户/部门/功能打标。

7. **接口契约后补**。  
   先写代码后补文档，错误码漂移、客户端 switch-case 全崩；契约先行并走评审。

8. **错误结构不统一**。  
   有的抛异常有的返回字符串，编排层无法统一判断 retryable；统一 {ok, data|error}。

9. **用「看起来全」证明该分层**。  
   层的存在理由是「删掉会坏什么」，答不出的是 PPT 架构；换实现要改很多处的是耦合。

10. **容量只算服务器**。  
    流量涨十倍先满的是模型 TPM 限额；先算配额与路由，再算副本。

11. **trace_id 不全链路透传**。  
    各层各自记日志无法串联，故障定位退回盲猜；入口生成、逐层透传。

12. **数据层权限后置**。  
    检索完再靠 prompt 别泄露必泄露；权限过滤必须在检索层前置（呼应 3.2/3.8）。

13. **编排层直接依赖具体框架 API**。  
    框架升级即全量改动；编排层内部再留抽象边界，防锁定（3.3 展开）。

## 9. 练习

1. 用 FastAPI 实现异步任务接口：提交返回 task_id，轮询查状态，任务状态落 Redis。
2. 给任务接口加幂等键：同一 Idempotency-Key 重复提交返回同一个 task_id。
3. 画你当前项目的分层图，对每层回答「删掉它会坏什么」与「换实现要改几处」，找出冗余层与耦合点。
4. 写一个最小 AI 网关：统一密钥、按 task_type 路由到两个 mock 模型、记录每次调用的 token 与成本。
5. 把 1.7 中你算过的成本账升级为网关归因报表：按「功能 × 模型」聚合单日 token 与费用。
6. 给一个 5 分钟级 Agent 任务设计错误码表：至少覆盖参数错、配额超、上游超时、预算超四类，标注 retryable。
7. 做一次容量推演：给定单任务 30K token、峰值每分钟 40 个任务，计算所需 TPM 并给出三条扩容路径。
8. 故障演练：随机 kill 掉 worker 进程，验证进行中任务能否从队列恢复或明确标失败，而不是永久卡在 running。

## 10. 小结

- 五层参考架构：**接入（鉴权限流 trace_id）→ AI 网关（密钥路由护栏成本）→ 编排（Agent 循环）→ 数据（权限隔离）→ 可观测（Trace 告警）**，层间接口与事件解耦。
- AI 网关四件事：**密钥集中、模型路由、护栏执行点、token 级成本归因**——正是它区别于传统 API 网关的地方。
- 同步异步边界：**超 30 秒的任务异步化**，task_id + 状态机 + 持久化 + 幂等键。
- 接口契约先行：Schema、错误码表、超时语义先写文档；工具统一 **{ok, data|error}**，retryable 驱动自修或止损。
- 架构自测法两问：**删掉它会坏什么？换成别的实现要改几处？** 前者滤冗余，后者测耦合。
- 容量规划从模型配额开始：**TPM 账先行**，路由与缓存是扩容的第一杠杆，副本是最后手段。
- 每个真实痛点都应指到一个具体层：成本失控找网关、定位不到人找接入层、越权找数据层。
- 可观测层在 3.4 展开成完整体系，部署与推理容量在 3.6，五层全案推演在 4.7b。
