## 1. 定位

AI 工程化层第 1 个知识点，属于「系统设计入口」。  
它集中回答本锚点的关键问题：**系统如何分层、解耦、扩展？**——即把 Agent 原型从「一个脚本」升级为「一个可维护、可扩展、可部署的生产系统」。

直接前置：2.7 单 Agent 架构模式。  
后续承接：3.3-3.10 全部工程化专题（编排框架 3.3、可观测 3.4、评估 3.5、部署 3.6、成本 3.7、安全 3.8、CICD 3.9、人机协同 3.10），以及 4.5 工作流自动化 Agent、4.7 生产级 Agent 平台两个全案。本篇只定骨架，专题深入一律指路后文。

## 2. 一句话定义

架构与接口设计，是定义 AI 系统的分层结构、服务边界、通信方式、数据流向和扩展点，使系统在变化中保持可维护、可替换、可演进的工程方法。

简化公式：

```text
好的架构 = 分层清晰 + 接口稳定 + 依赖单向 + 可替换 + 可观测
```

## 3. 为什么需要

原型阶段：

```python
# 一个文件搞定
def agent(query):
    docs = search(query)
    answer = llm(query, docs)
    return answer
```

生产阶段的八项要求，这段原型代码一项都接不住：

- **模型要换**：GPT → Claude → 本地模型，不能改业务代码。
- **工具要加**：从 3 个工具到 30 个，不能改 Agent 核心。
- **数据要隔离**：多租户（Multi-tenancy）、权限、审计。
- **流量要扩展**：从 10 QPS 到 1000 QPS。
- **故障要降级**：主模型挂了，备用模型接管。
- **要能观测**：每次调用、每步决策、每笔成本都要可追踪（深入见 3.4）。
- **要能回滚**：Prompt、模型、工具版本要能切换（深入见 3.9）。
- **要能协作**：多个团队开发不同模块，接口要稳定。

**类比 1（整体）**：

```text
没有架构 = 一个手工作坊，所有工序挤在一张桌上，改一道工序全店停工
有好架构 = 一条流水线，每道工序独立工位、可替换、可监控，换一台设备不停产
```

**类比 2（接口）**：接口标准就像家用插座——电器厂商和电网各造各的，但都遵守同一套插座规格，于是任何电器能插任何一面墙。没有接口约定的系统，每接一个新工具都要「剪断电线重新接线」，接 30 个工具就是 30 次带电作业。

## 4. 核心原理

### 4.1 分层架构（Layered Architecture）

**经典五层架构**：

```text
┌──────────────────────────────────────────┐
│  L5 接入层（API Gateway / UI / SDK）      │
│  ├─ 认证、限流、路由                      │
│  └─ 请求/响应格式                         │
├──────────────────────────────────────────┤
│  L4 编排层（Agent Orchestration）         │
│  ├─ 工作流、状态机、多 Agent 协调         │
│  └─ 任务调度、终止控制                    │
├──────────────────────────────────────────┤
│  L3 能力层（Capabilities）                │
│  ├─ LLM 调用、工具执行、检索              │
│  ├─ 记忆读写、反思验证                    │
│  └─ 每个能力独立封装                      │
├──────────────────────────────────────────┤
│  L2 基础设施层（Infrastructure）          │
│  ├─ 日志、Trace、监控                     │
│  ├─ 缓存、队列、存储                      │
│  └─ 配置、密钥管理                        │
├──────────────────────────────────────────┤
│  L1 外部依赖（External）                  │
│  ├─ LLM API、向量库、数据库               │
│  └─ 第三方 API、消息队列                  │
└──────────────────────────────────────────┘
```

**分层原则**：

- **依赖单向**：上层依赖下层，下层不依赖上层，禁止跨层直连。
- **接口稳定**：层间通过接口通信，不直接依赖实现。
- **每层可替换**：换 LLM 不影响编排层，换编排不影响接入层。
- **横切关注点（Cross-Cutting Concerns）**：日志、监控、安全贯穿所有层，不属于任何一层。

### 4.2 服务边界划分（Service Boundary）

**按职责划分**：

| 服务 | 职责 | 独立部署？ |
|---|---|---|
| API Gateway | 认证、限流、路由 | 是 |
| Agent Service | Agent 编排、决策 | 是 |
| LLM Service / AI 网关 | 模型调用、路由、重试 | 是 |
| Tool Service | 工具注册、执行、权限 | 是 |
| RAG Service | 检索、重排 | 是 |
| Memory Service | 记忆读写 | 是 |
| Eval Service | 评估、监控 | 是 |
| Observability | 日志、Trace、指标 | 是 |

**三种组织形态对比**：

| 维度 | 单体 | 模块化单体（Modular Monolith） | 微服务 |
|---|---|---|---|
| 部署单元 | 1 个进程 | 1 个进程（内部分层/分模块） | 多个独立服务 |
| 团队协作 | 2-3 人小团队 | 中型团队，按模块分工 | 多团队，按服务归属 |
| 扩展方式 | 整体扩容 | 整体扩容，模块可独立优化 | 按服务独立扩展 |
| 故障隔离 | 一挂全挂 | 进程内隔离（弱） | 服务级隔离（强） |
| 运维成本 | 低 | 低-中 | 高（网关/服务发现/链路追踪全套） |
| 适用阶段 | 原型验证 | 日请求十万级以内的生产 | 大流量、多团队、需独立伸缩 |

**划分原则**：

- **高内聚（High Cohesion）**：一个服务只做一件事。
- **低耦合（Low Coupling）**：服务间通过接口通信，不共享数据库。
- **独立部署**：一个服务升级不影响其他。
- **独立扩展**：按需扩展某个服务，而不是整体扩容。

**什么时候拆分**：

```text
单体 → 模块化单体 → 微服务
  ↑          ↑          ↑
原型阶段   生产主流    出现独立扩展/独立故障域需求时
```

**面试高频问法**：「Agent 系统从单体还是微服务起步？」共识口径：从模块化单体起步——单进程内先做到分层清晰、模块间只走接口；等出现独立扩展需求（LLM 网关要单独扩容、检索服务要单独换硬件）再逐个拆出服务。判断标准见 4.2 对比表，反例是一上来十几个微服务，联调、部署、排障成本先压垮小团队。资深信号是每个组件都能说清「删掉它会坏什么」。

### 4.3 AI 网关（AI Gateway）：LLM 调用的统一边界

LLM 调用是全系统最贵、最不稳定、变化最快的外部依赖：按 token 计费、有 TPM/RPM 限额、经常超时、供应商不断出新模型。截至 2026 年，生产架构普遍在应用与模型提供方之间加一层 AI 网关，作为「应用与模型提供方之间的受控边界」，这已成为系统设计轮的标准考点（依据：dev.to《How to Choose an AI Gateway in 2026》、skphd 端到端生产架构问答集，2026）。

类比：AI 网关 = 公司总机。所有对外通话先过总机，统一登记（计量）、转接（路由）、录音（审计），任何部门不许直拨外线——谁打了多久、打给谁、花了多少钱，一处看得清清楚楚。

| 职责 | 说明 | 对应专题 |
|---|---|---|
| 统一接入 | 多家模型统一成一种 API 格式 | 换模型不改业务代码 |
| 模型路由与降级 | 按任务档位路由（fast/balanced/powerful）+ 失败降级链 | 见 3.7 |
| 限流与配额 | 按 Key/租户限流，超配额熔断 | 成本失控的第一道防线 |
| 护栏（Guardrail）执行 | Prompt 注入检测、PII 脱敏、内容过滤 | 见 3.8 |
| 计量计费 | token 用量与单请求成本，按租户/应用归因 | 见 3.7 |
| 缓存 | 精确缓存 + 语义缓存（Semantic Cache） | 重复请求降本 |
| 可观测 | 每次调用的 trace、成本、护栏事件 | 见 3.4 |

实现选择：开源自建（如 LiteLLM，把上百家模型统一为 OpenAI 兼容格式，自带路由/预算/限流）、云厂商托管网关，或在 LLM Service 内自研薄层。小团队常从「进程内 LLM Service 抽象」（见 6.4）起步，流量上来再独立成网关服务——演进思路与 4.2 一致。

**面试高频问法**：「AI 网关和传统 API 网关的区别？为什么把护栏放在网关层而不是每个应用里？」共识口径：传统网关管「转发 + 认证 + 限流」，不理解请求内容；AI 网关额外理解模型语义——流式响应转发、token 计量、语义缓存、模型路由与降级、护栏检查。护栏放网关层的理由：一处升级全局生效、新应用接入即受保护、护栏事件集中审计；放进每个应用则规则漂移、漏配难查、审计分散。

### 4.4 接口设计

**API 设计原则**：

| 原则 | 说明 |
|---|---|
| 稳定 | 接口一旦发布，尽量不变；变则走版本 |
| 版本化 | `/v1/agent/run`，破坏性变更升 `/v2/` |
| 幂等（Idempotent） | 相同请求可重复执行，不产生重复副作用 |
| 明确 | 输入输出 Schema 清晰（Pydantic / JSON Schema） |
| 错误规范 | 统一错误码和格式，错误信息可指导重试 |
| 分页 | 列表接口支持分页 |
| 限流 | 每个接口有配额 |
| 超时 | 明确超时时间，不让调用方无限等 |
| 异步 | 长任务返回 task_id |

**四种接口风格对比**：

| 风格 | 通信方向 | 典型用途 | 优点 | 代价 |
|---|---|---|---|---|
| REST（同步请求/响应） | 客户端拉 | 提交任务、查状态、管理接口 | 简单、通用、易缓存 | 长任务占连接，无中间过程 |
| 流式 / SSE（Server-Sent Events） | 服务端单向推 | token 级输出、执行过程事件 | HTTP 友好、首字延迟低、自动重连 | 单向、连接持续占用 |
| WebSocket | 双向 | 多人协同、实时对话式交互 | 全双工、低延迟 | 状态管理复杂、网关兼容性要验证 |
| Webhook（回调） | 服务端推给第三方 | 异步任务完成通知外部系统 | 免轮询、跨组织集成 | 需公网端点、需验签与重试设计 |

**RESTful API 示例**：

```http
POST /v1/agent/run
{
  "input": "帮我查订单 12345",
  "session_id": "sess_abc",
  "user_id": "u1",
  "config": {
    "max_steps": 10,
    "timeout": 60,
    "budget": 0.5
  }
}

Response:
{
  "task_id": "task_xyz",
  "status": "completed",
  "answer": "订单 12345 已发货...",
  "trajectory": [...],
  "usage": {
    "steps": 3,
    "tokens": 1500,
    "cost": 0.003,
    "latency_ms": 2500
  }
}
```

**异步任务 API**：

```http
POST /v1/agent/tasks
→ {"task_id": "task_xyz", "status": "pending"}

GET /v1/agent/tasks/task_xyz
→ {"task_id": "task_xyz", "status": "running", "progress": 0.5}

GET /v1/agent/tasks/task_xyz
→ {"task_id": "task_xyz", "status": "completed", "result": {...}}
```

**流式 API（SSE）**：

```http
POST /v1/agent/stream
→ SSE:
data: {"type": "thought", "content": "我需要查订单"}
data: {"type": "action", "content": "search_orders(12345)"}
data: {"type": "observation", "content": "订单已发货"}
data: {"type": "answer", "content": "订单 12345 已发货"}
data: {"type": "done"}
```

### 4.5 同步、异步与流式：通信模式选型

四种通信模式对比（含事件驱动，机制见 4.6）：

| 维度 | 同步 | 异步（task_id + 轮询/回调） | 流式（SSE） | 事件驱动 |
|---|---|---|---|---|
| 响应方式 | 阻塞等完整结果 | 立即返回 task_id | 边生成边推送 | 发布事件，订阅方各自消费 |
| 适用 | 快任务（< 30s） | 长任务（> 30s）、批量 | 对话、实时交互 | 监控/审计/评估等旁路 |
| 连接占用 | 高（全程占用） | 低（提交即返回） | 中（占用但持续有产出） | 低（异步消费） |
| 超时风险 | 容易超时 | 基本无 | 需心跳保活 | 需处理事件积压 |
| 实现复杂度 | 低 | 中（任务存储/队列） | 中 | 高（消息总线） |
| 典型场景 | 查询类 API | 深度报告生成 | 聊天逐字输出 | tool.called → 审计 |

**决策规则**：

```text
任务 < 30s        → 同步
任务 > 30s        → 异步（task_id + 队列）
实时交互/逐字输出 → 流式（SSE）
旁路消费          → 事件驱动（不进主流程）
```

### 4.6 事件驱动架构（Event-Driven Architecture, EDA）

**核心思想**：服务之间通过事件通信，而不是直接调用。

```text
Agent Service
    ↓ 发布事件
Event Bus（Kafka / Redis Streams / RabbitMQ）
    ↓ 订阅
┌─────────┬─────────┬─────────┐
│ 评估服务 │ 监控服务 │ 审计服务 │
└─────────┴─────────┴─────────┘
```

**事件类型**：

```python
events = [
    {"type": "task.started", "task_id": "...", "user_id": "..."},
    {"type": "step.completed", "task_id": "...", "step": 1, "tool": "search_orders"},
    {"type": "tool.called", "task_id": "...", "tool": "refund", "args": {...}},
    {"type": "task.completed", "task_id": "...", "cost": 0.003},
    {"type": "task.failed", "task_id": "...", "error": "..."},
]
```

**优势**：

- 解耦：生产者不需要知道消费者是谁。
- 可扩展：加新消费者不影响现有系统。
- 可观测：所有事件可记录、可回放（回放沉淀评估集的闭环见 3.4、3.5）。
- 异步：不阻塞主流程。

### 4.7 人机协同接口（Human-in-the-Loop, HITL）

Agent 不是完全自主的，高风险动作必须有暂停点（策略深入见 3.10）：

```text
Agent 执行
    ↓
高风险操作？
    ├─ 是 → 暂停，保存检查点，等待人工审批
    │         ↓
    │      人工审批
    │         ├─ 批准 → 从检查点恢复继续
    │         └─ 拒绝 → 终止/降级
    └─ 否 → 继续
```

**审批接口**：

```http
POST /v1/agent/approvals
{
  "task_id": "task_xyz",
  "action": "initiate_refund",
  "args": {"order_id": "12345", "amount": 1000},
  "risk_level": "high",
  "reason": "退款金额超过 500 元"
}

Response:
{
  "approval_id": "appr_abc",
  "status": "pending",
  "expires_at": "2024-01-15T11:00:00"
}

POST /v1/agent/approvals/appr_abc/decide
{
  "decision": "approved",
  "approved_by": "admin1",
  "comment": "确认退款"
}
```

检查点与恢复机制在 2.5 已展开，本篇只约束接口形态：发起审批要带完整上下文（动作、参数、风险原因），决策要留痕（谁、何时、依据）。

### 4.8 配置、版本与多环境

**配置化**：

```yaml
# config/agent.yaml
agent:
  version: "1.2.0"
  llm:
    default: gpt-4o-mini
    fallback: claude-3-5-haiku
  tools:
    - search_orders
    - get_weather
  limits:
    max_steps: 20
    timeout: 300
    budget: 5.0
  prompts:
    version: "v1.2.0"
```

**版本管理**：

| 对象 | 版本策略 |
|---|---|
| API | URL 版本 `/v1/` |
| Prompt | 文件版本 `prompts/v1.2.0/` |
| 模型 | 固定版本号 `gpt-4o-2024-08-06` |
| 工具 | 语义化版本 `search_orders@1.2.0` |
| 配置 | Git 管理 + 环境变量 |

**多环境**：开发（dev）→ 预发（staging）→ 生产（prod），三套环境各自独立的 API Key、数据库、向量库、监控；相同的代码、不同的配置。发布与回滚管线见 3.9。

### 4.9 降级与容错（Fallback）

```text
正常路径：主模型 → 主工具 → 主检索
    ↓ 失败
降级 1：备用模型
    ↓ 失败
降级 2：缓存结果
    ↓ 失败
降级 3：友好错误 + 人工介入
```

**实现**：

```python
async def resilient_call(primary, fallbacks: list):
    try:
        return await primary()
    except Exception as e:
        for fallback in fallbacks:
            try:
                return await fallback()
            except Exception:
                continue
        raise
```

可靠性体系（重试、熔断、超时预算的完整展开）见 3.7。

### 4.10 解耦手段与扩展路径

关键问题「分层、解耦、扩展」在此收口：分层见 4.1，本节给解耦手段清单与扩展路径。

| 解耦手段 | 解开什么耦合 | 一句话做法 |
|---|---|---|
| 分层 | 业务逻辑 vs 基础设施 | 上层只依赖下层接口，不跨层调用 |
| 服务抽象（LLM Service） | 业务 vs 某家模型 | Provider 接口 + 路由表（见 6.4） |
| 工具注册表 | Agent 核心 vs 具体工具 | 注册 + JSON Schema 声明，动态发现 |
| 事件总线 | 主流程 vs 监控/审计/评估旁路 | 发布订阅，生产者不知道消费者（见 6.5） |
| 配置外置 | 代码 vs 环境与参数 | 配置文件 + 环境变量（见 4.8） |
| 依赖注入（Dependency Injection, DI） | 组件 vs 组件的构造过程 | 依赖从外部注入，替换与测试零改动（见 6.6） |

**扩展路径**（流量从 10 QPS 到 1000 QPS，按序启用）：

```text
1. 垂直扩展：加 CPU / 内存 / 连接池——最先做，收益直接
2. 无状态水平扩展：API 与编排服务多副本 + 负载均衡
3. 缓存：语义缓存消化重复请求（命中 30%-60% 常见）
4. 队列削峰：同步转异步，高峰流量进队列排队
5. 按服务异构扩展：网关单独扩容、检索加副本、重排上 GPU
6. 模型分级路由：简单请求走小模型，复杂请求走大模型
```

先定位瓶颈再扩：模型侧瓶颈看 TPM 限额与排队，编排侧瓶颈看 CPU 与连接数——扩错层等于白花钱（部署与伸缩深入见 3.6，成本杠杆见 3.7）。

### 4.11 架构演进路线

```text
阶段 1：单体脚本
  └─ 一个文件，快速验证

阶段 2：模块化单体
  └─ 分层清晰，接口稳定

阶段 3：服务化
  └─ 核心服务独立部署

阶段 4：微服务 + 事件驱动
  └─ 高扩展、高可用

阶段 5：平台化
  └─ 多租户、工具市场、自助配置
```

> **不要跳过阶段。** 每个阶段解决当前瓶颈，不要过度设计。

### 6.3 FastAPI 服务骨架（同步 + SSE 流式）

```python
from fastapi import FastAPI, HTTPException, Depends
from fastapi.responses import StreamingResponse

app = FastAPI(title="Agent API", version="1.0.0")

async def stream_agent(request: AgentRunRequest):
    """SSE 流式输出：thought / action / observation / answer 四类事件"""
    async for event in agent_orchestrator.run_stream(request):
        yield f"data: {event.json()}\n\n"      # SSE 协议：事件之间空一行
    yield 'data: {"type": "done"}\n\n'

@app.post("/v1/agent/run", response_model=AgentRunResponse)
async def run_agent(
    request: AgentRunRequest,
    user = Depends(authenticate),          # 认证中间件
    _ = Depends(rate_limit),               # 限流中间件
):
    if not has_permission(user, "run_agent"):
        raise HTTPException(403, "无权限")

    try:
        if request.stream:                 # 流式分支：直接透传生成器
            return StreamingResponse(
                stream_agent(request),
                media_type="text/event-stream",
            )

        result = await agent_orchestrator.run(   # 同步分支：等完整结果
            input=request.input,
            user_id=request.user_id,
            session_id=request.session_id,
            max_steps=request.max_steps,
            timeout=request.timeout,
            budget=request.budget,
        )
        return AgentRunResponse(**result)

    except BudgetExceeded as e:
        raise HTTPException(429, f"预算超限: {e}")
    except TimeoutError:
        raise HTTPException(504, "任务超时")
    except Exception:
        logger.exception("agent_run_failed")    # 原始堆栈进日志，不给客户端
        raise HTTPException(500, "内部错误")

@app.get("/v1/agent/tasks/{task_id}", response_model=TaskStatusResponse)
async def get_task(task_id: str, user = Depends(authenticate)):
    task = await task_store.get(task_id)
    if not task:
        raise HTTPException(404, "任务不存在")
    if task.user_id != user.id:            # 越权检查：任务只能本人查
        raise HTTPException(403, "无权访问")
    return TaskStatusResponse(**task.to_dict())

@app.post("/v1/agent/tasks/{task_id}/cancel")
async def cancel_task(task_id: str, user = Depends(authenticate)):
    task = await task_store.get(task_id)
    if not task or task.user_id != user.id:
        raise HTTPException(404, "任务不存在")
    await task.cancel()
    return {"status": "cancelled"}
```

### 6.4 LLM Service 抽象（AI 网关的进程内雏形）

```python
from abc import ABC, abstractmethod

class LLMProvider(ABC):
    """所有模型提供方实现同一接口，业务代码不感知具体厂商"""
    @abstractmethod
    async def chat(self, messages: list[dict], **kwargs) -> str: ...

class OpenAIProvider(LLMProvider):
    async def chat(self, messages, **kwargs):
        response = await openai_client.chat.completions.create(
            model=kwargs.get("model", "gpt-4o-mini"),
            messages=messages,
            temperature=kwargs.get("temperature", 0.7),
        )
        return response.choices[0].message.content

class ClaudeProvider(LLMProvider):
    async def chat(self, messages, **kwargs):
        response = await anthropic_client.messages.create(
            model=kwargs.get("model", "claude-3-5-sonnet"),
            messages=messages,
            max_tokens=kwargs.get("max_tokens", 1024),
        )
        return response.content[0].text

class LLMService:
    """路由表决定「哪档任务用哪家模型」；换供应商只改这张表"""
    def __init__(self):
        self.providers = {
            "openai": OpenAIProvider(),
            "claude": ClaudeProvider(),
        }
        self.routing = {
            "fast": ("openai", "gpt-4o-mini"),        # 意图识别等轻任务
            "balanced": ("openai", "gpt-4o"),
            "powerful": ("claude", "claude-3-5-sonnet"),  # 复杂推理
        }

    async def chat(self, messages, tier="fast", **kwargs):
        provider_name, model = self.routing[tier]
        provider = self.providers[provider_name]
        return await provider.chat(messages, model=model, **kwargs)
```

### 6.5 事件总线

```python
import asyncio
from collections import defaultdict

class EventBus:
    def __init__(self):
        self.subscribers = defaultdict(list)

    def subscribe(self, event_type: str, handler):
        self.subscribers[event_type].append(handler)

    async def publish(self, event_type: str, data: dict):
        for handler in self.subscribers[event_type]:
            asyncio.create_task(handler(data))   # 异步分发，不阻塞主流程

event_bus = EventBus()

# 订阅方各自独立，加一个消费者不改生产者
async def on_tool_called(data):
    await audit_log.record(data)

async def on_task_completed(data):
    await metrics.record_cost(data["cost"])

event_bus.subscribe("tool.called", on_tool_called)
event_bus.subscribe("task.completed", on_task_completed)

# 发布
await event_bus.publish("tool.called", {
    "task_id": "task_xyz",
    "tool": "refund",
    "args": {"order_id": "12345"},
})
```

## 7. 案例

### 案例 A：从脚本到服务（某 3 人内部工具团队，示意数字）

```text
阶段 1 脚本：main.py 一个文件，命令行问答，周均手动跑 30 次
阶段 2 模块化：拆成 llm.py / tools.py / agent.py / config.py
阶段 3 API 服务：FastAPI + 分层结构 + 配置管理，QPS 从 5 到 60
阶段 4 服务化：API Gateway → Agent Service → LLM / Tool / RAG Service，QPS 到 200
阶段 5 事件驱动：Agent Service → Event Bus → 评估 / 监控 / 审计
```

复盘（示意数字）：两次换模型供应商（一次涨价、一次限流）只改网关路由表，业务代码 0 改动、当天完成；发布频率从月更到周更；一次主模型区域故障靠备用模型接管，用户侧只感受到延迟升高。

### 案例 B：多租户隔离（SaaS 平台，60+ 企业客户，示意数字）

**需求**：SaaS 平台，多个企业客户共用一套 Agent 服务。

**架构**：

```text
请求 → API Gateway（识别 tenant_id）
    → Agent Service（注入 tenant 上下文）
    → RAG Service（按 tenant 过滤）
    → Memory Service（按 tenant 隔离）
```

**关键**：

- 每个请求带 `tenant_id`，全链路透传。
- 向量库用 metadata 过滤，数据库行级隔离。
- 审计日志按租户分组。

示意效果：改造前压测曾出现约 0.2% 的跨租户检索串扰（tenant 上下文没传到向量库过滤层）；tenant_id 贯穿 + 存储层强制过滤上线后回归为 0；「看到别家报价单」类客户工单从月均 2-3 单降到 0。

### 案例 C：人机协同审批（客服退款，示意数字）

**流程**：

```text
1. Agent 决定调用 refund(amount=1000)
2. 金额 > 500，触发审批
3. 保存检查点，暂停任务
4. 通知管理员
5. 管理员审批
6. 批准 → 恢复任务；拒绝 → 终止
```

**接口**：

```http
POST /v1/agent/approvals
POST /v1/agent/approvals/{id}/decide
GET  /v1/agent/approvals?status=pending
```

示意效果：上线首月发起审批 37 次，人工拒绝 5 次——其中 3 次是 Agent 把退款金额多算一个零；平均等待审批 6 分钟。对比灰度的无审批版本曾发生 1 次错误全额退款，损失约等于审批环节一个月的人力成本。

## 8. 常见坑

1. **一开始就微服务**。对策：原型从模块化单体起步，出现独立扩展需求再拆（见 4.2 对比表）。
2. **业务逻辑与 LLM 调用耦合**。对策：换模型要改业务代码说明越界了；用 LLM Service / AI 网关抽象隔离。
3. **工具硬编码在 Agent 核心里**。对策：加一个工具就改一次核心；用注册表 + JSON Schema 动态注册。
4. **接口没有版本化**。对策：一次改动打断所有下游；从 `/v1/` 起步，破坏性变更升 `/v2/`。
5. **同步处理长任务**。对策：连接挂满、网关超时；长任务转异步 task_id + 队列（见 4.5）。
6. **没有降级方案**。对策：主模型一挂全站不可用；备用模型 + 缓存 + 友好错误三级兜底（见 4.9）。
7. **配置写死在代码里**。对策：换个环境就改代码；配置文件 + 环境变量 + 多环境隔离（见 4.8）。
8. **监控、审计、评估耦合在主流程**。对策：主流程越加越慢、越改越险；用事件总线剥离到旁路（见 4.6）。
9. **不做多租户隔离**。对策：数据串扰是最贵的事故；tenant_id 全链路透传 + 存储层强制过滤。
10. **高风险操作没有人工审批接口**。对策：错误动作无法拦截；审批门 + 检查点暂停，决策留痕（见 3.10）。
11. **日志格式不统一**。对策：各服务各写各的，聚合排查困难；统一结构化日志 + trace_id 贯穿（见 3.4）。
12. **不用依赖注入**。对策：组件互相构造，测试只能连真实服务；依赖注入 + mock 单测（见 6.6）。
13. **dev 与 prod 共用配置甚至共用 Key**。对策：测试流量打进生产模型、账单混算；多环境物理隔离。
14. **忽略向后兼容**。对策：接口一改旧客户端全崩；新增字段保持可选，废弃字段留缓冲期。
15. **没有架构图与决策记录**。对策：团队理解全靠口口相传；维护架构文档，每个决策写清「为什么」。

## 10. 小结

- 架构 = **分层 + 服务边界 + 接口 + 通信 + 扩展点**。
- 五层架构：**接入层、编排层、能力层、基础设施层、外部依赖**；依赖单向、层间只走接口。
- **AI 网关是 LLM 调用的统一边界**：统一接入、路由降级、护栏、计量、缓存——一处升级，全局生效。
- 接口设计：**稳定、版本化、幂等、Schema 明确、错误统一**；REST 管同步、SSE 管流式、Webhook 管回调。
- 通信选型：**短任务同步、长任务异步、实时交互流式、旁路消费事件驱动**。
- 事件驱动：**解耦、可扩展、可回放**，把监控/审计/评估从主流程剥离。
- 人机协同：**高风险操作保存检查点、暂停等待审批、决策留痕**。
- 解耦六手段：**分层、服务抽象、工具注册表、事件总线、配置外置、依赖注入**。
- 扩展按序走：**垂直 → 无状态水平 → 缓存 → 队列削峰 → 异构扩展 → 模型分级**，先定位瓶颈层再动手。
- 工程铁律：**从模块化单体起步，按瓶颈演进；不跳阶段、不过度设计。**
- 这些能力直接支撑：3.2-3.10 全部工程化专题，以及 4.5 工作流自动化 Agent、4.7 生产级 Agent 平台。
