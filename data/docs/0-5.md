## 1. 定位

基础层第 5 个知识点，属于「模型能力认知」。
0.4 让你理解 Transformer 的内部结构，0.5 让你理解 **LLM 是怎么被训练出来的、为什么有能力、为什么会犯错、边界在哪里**。

rodmap 给本篇的关键问题是：**能力、幻觉、上下文窗口从哪来？**——先分节拆解，§4.12 集中正面回答。

它是从「模型结构」过渡到「模型应用」的桥梁，直接支撑 0.6 提示工程基础、0.7 向量与嵌入基础、1.1 LLM API 与模型选型、1.4 RAG。

## 2. 一句话定义

LLM 基础，是理解大语言模型（LLM，Large Language Model）从预训练到对齐的训练流程、自回归推理机制、采样策略、能力边界与幻觉根源的最小知识集合。

简化公式：

```text
LLM 基础 = 训练流程（预训练 → SFT → 对齐）
         + 推理机制（token → 自回归 → 采样）
         + 边界认知（能力上限 / 幻觉根源 / 上下文窗口）
```

## 3. 为什么需要

做 Agent，你每天都在和 LLM 的「脾气」打交道：

- **为什么模型会一本正经地胡说八道？** → 它本质是概率续写器，不是事实数据库。
- **为什么同一个问题问两次答案不同？** → 采样策略引入随机性。
- **为什么上下文一长就变傻？** → 注意力分散 + 位置编码外推问题。
- **为什么工具调用要低温？** → 需要确定性输出。
- **为什么有的模型便宜有的贵？** → 参数规模、训练成本、推理成本不同。
- **什么时候该微调？** → 需要理解预训练、SFT、对齐的分工。

这些问题不搞清楚，Agent 开发就是盲人摸象。懂与不懂的差距，最先体现在线上排查效率：

| 线上现象 | 不懂原理的排查方式 | 懂原理的排查方式 |
|---|---|---|
| 输出忽对忽错 | 反复改提示词（Prompt）碰运气 | 先固定采样参数，再逐项归因 |
| 多轮对话后「失忆」 | 把历史全量塞回去硬试 | 查窗口占用，改摘要压缩或检索式记忆 |
| 模型编造事实 | 归结为「模型不行」换模型 | 区分知识截止与幻觉，接 RAG 或工具 |
| JSON 偶发解析失败 | 无脑加重试次数 | temperature=0 + Schema 校验 + 定向重试 |

## 4. 核心原理

### 4.1 训练三阶段：预训练 → SFT → 对齐

```text
阶段 1: 预训练（Pre-training）
  数据: 海量文本（万亿 token 量级的网页、书籍、代码）
  目标: 预测下一个 token（自监督，不需要人工标注）
  结果: 学会语言规律、世界知识、推理能力
  类比: 学生泛读百科全书

阶段 2: 监督微调（SFT，Supervised Fine-Tuning）
  数据: 人工标注的指令-回答对（十万到百万级）
  目标: 学会听懂指令、按格式回答
  结果: 从"续写器"变成"助手"
  类比: 学生做专项练习册

阶段 3: 对齐（Alignment，RLHF / DPO）
  数据: 人类偏好排序
  目标: 让输出符合人类价值观、更有用、更安全
  结果: 更听话、更安全、更少有害输出
  类比: 学生参加社会实践，学会什么该说什么不该说
```

关键认知：

- **预训练**决定了模型的知识上限。
- **SFT**决定了模型听不听话。
- **RLHF/DPO**决定了模型安不安全、有没有用。
- 你用的 API 模型，通常已经走完这三步。

规模共识：参数量、数据量、算力同步放大，能力可预期提升（Scaling Law，缩放定律）是过去几年业界的基本共识；SFT 与对齐并不新增知识，而是把基座模型（Base Model）的潜在能力激发成「可用能力」。

### 4.2 对齐方法：RLHF（PPO）、DPO、GRPO 与 LoRA

RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）的经典实现是 PPO，分三步：

```text
RLHF（PPO 路线）三步：
1. 训练奖励模型（RM，Reward Model）
   人类对同一问题的多个回答做排序 → RM 学会给回答打分
2. 用 PPO（Proximal Policy Optimization，近端策略优化）更新 LLM
   让模型采样出的回答拿到更高的奖励分
3. 加 KL 散度惩罚
   防止模型为讨好 RM 而漂离原模型太远（reward hacking，钻奖励空子）
```

DPO（Direct Preference Optimization，直接偏好优化）的思路是把上面三步压成一步：不训奖励模型、不做在线采样，直接在偏好对（好回答 A、差回答 B）上定义损失，让模型增大 A 相对 B 的生成概率。

| 维度 | RLHF（PPO 路线） | DPO |
|---|---|---|
| 奖励模型 | 需要单独训练 | 不需要，偏好对直接当训练信号 |
| 优化方式 | 在线强化学习：采样→打分→更新 | 离线：偏好对上做类似分类的损失 |
| 工程复杂度 | 高（策略、参考、奖励、价值多模型协同） | 低（策略 + 参考两个模型即可） |
| 训练稳定性 | 易跑偏，需要精细调参 | 更稳定，容易复现 |
| 效果上限 | 通常更高（在线探索充分） | 略低于调优好的 PPO，性价比高 |
| 数据要求 | 偏好标注 + 采样算力 | 只需偏好对 |

GRPO（Group Relative Policy Optimization，组相对策略优化）是 PPO 的变体：去掉价值网络，对同一问题采样一组回答，用组内相对奖励当基线，训练开销更低，DeepSeek 系列模型将其带成主流话题。

微调侧的配套常识是 LoRA（Low-Rank Adaptation，低秩适配）：冻结原权重，只在旁路训练两个低秩矩阵，可训练参数常不到全量的 1%，显存和存储成本降一个量级，是应用侧微调的默认起点，属于参数高效微调（PEFT，Parameter-Efficient Fine-Tuning）家族。

**面试高频问法**：「DPO 和 PPO 的区别是什么？RLHF、DPO、GRPO 之间是什么关系？」业界共识口径：RLHF 是「用人类偏好做对齐」的范式总称；PPO 是其经典在线实现，效果上限高但工程重；DPO 是离线简化，免奖励模型、稳定易复现；GRPO 是 PPO 的去价值网络变体，用组内相对奖励做基线。追问「为什么 SFT 之后还需要对齐」——SFT 只能模仿人类写出的好答案，学不到「两个答案哪个更好」的偏好序，也压不住有害输出；对齐阶段把偏好本身变成优化目标。

### 4.3 token：模型处理与计价的最小单位

- 分词器（Tokenizer，见 0.4）把文本切成子词单元，词表通常在几万到十几万量级。
- 经验量级：英文约 4 个字符折合 1 个 token；中文一个汉字通常 1-2 个 token，新一代分词器已优化到接近 1:1；代码因缩进和符号密集，token 密度更高。具体数字以所用模型的分词器实测为准（§6.1）。
- token 同时决定三件事：**成本**（API 按 token 计价）、**窗口占用**（输入输出都算 token）、**延迟**（生成耗时随输出 token 数近似线性增长）。
- 工程纪律：成本和窗口的估算必须按 token 算，不能按字数估。

### 4.4 自回归生成（Autoregressive）

LLM 生成文本的方式：

```text
输入: "今天天气"
→ 预测下一个 token: "真" (概率 0.4)
→ 拼回输入: "今天天气真"
→ 预测下一个 token: "好" (概率 0.6)
→ 拼回输入: "今天天气真好"
→ 预测下一个 token: "。" (概率 0.8)
→ 遇到结束符，停止
```

特点：

- **逐个 token 生成**，不能并行。
- 每个 token 都依赖前面所有 token。
- 生成长度越长，耗时越长，成本越高。

这就是为什么：

- 流式输出（Streaming）体验好：不用等全部生成完。
- 长回答更贵：token 数线性增长。
- 首 token 延迟（TTFT，Time To First Token）和总延迟是两个不同指标：前者决定「多快看到第一个字」，后者决定「多快拿到完整结果」。

类比：像老式电传打字机逐字吐出新闻稿，而不是整版报纸一次性印好——你可以边看边处理，但整篇出来的时间取决于总字数。

### 4.5 采样策略：从概率分布到具体 token

模型每步输出的是整个词表上的概率分布，采样决定选哪个 token。先看三代解码策略：

| 解码策略 | 做法 | 特点 | 适用 |
|---|---|---|---|
| 贪心（Greedy） | 每步取概率最高的 token | 确定但容易重复、呆板 | 分类、抽取等有标准答案的任务 |
| 束搜索（Beam Search） | 同时维护 k 条最优候选序列 | 整体更优，但开放式生成文本乏味 | 翻译、摘要等近标准答案任务 |
| 采样（Sampling） | 按概率随机抽取，配合温度/top-p/top-k 裁剪 | 多样、随机度可控 | 开放式生成的主流选择 |

采样内部的常用参数：

| 参数 | 作用 | 典型值 | 影响 |
|---|---|---|---|
| Temperature | 调整分布陡峭程度 | 0.0-1.0 | 低=确定，高=随机 |
| Top-p | 从累积概率前 p 中采样 | 0.9-0.95 | 控制候选集大小 |
| Top-k | 从概率最高的 k 个中采样 | 40-50 | 限制候选数量 |
| Repetition Penalty | 惩罚重复 token | 1.0-1.2 | 减少复读机 |
| Max Tokens | 最大生成长度 | 按需 | 控制成本和延迟 |

类比：temperature=0 像每次进餐厅只点「销量第一」；高温像闭着眼从整本菜单随机点——可能惊喜，也可能点出一桌怪菜。

工程建议：

- 工具调用、结构化输出：`temperature=0`（此时退化为贪心解码，输出基本确定）。
- 创意写作：`temperature=0.7-1.0`。
- 代码生成：`temperature=0-0.3`。
- 对话：`temperature=0.5-0.7`。
- 纪律一：temperature 与 top-p 都在放大或收缩随机性，一般固定其中一个、只调另一个。
- 纪律二：换了模型默认参数不一定继承，迁移时重新校准采样配置。

### 4.6 上下文窗口（Context Window）

模型一次能「看到」的最大 token 数。

```text
上下文窗口 = 输入 token + 输出 token
```

常见规模（截至 2026 年，示意量级）：上一代模型 4K-32K；当前闭源 API 普遍 128K-1M（GPT-4o 128K、Claude 系列 200K 级、Gemini 系列百万级）；开源模型多为 8K-256K，长窗口在持续追赶。

类比：窗口像一张固定大小的办公桌——桌子再大，一次也只能摊开这么多资料；摊得越多，翻找某一页越慢，压在中间那份还最容易被忽略。

关键认知：

- **窗口不是越大越好**：中间信息容易被忽略（中间遗忘，Lost in the Middle）。
- **窗口占用有成本**：输入 token 越多，越贵越慢。
- **超出窗口会被截断**：关键信息可能丢失。
- **窗口 ≠ 有效利用**：128K 窗口不代表能有效利用 128K。

### 4.7 幻觉（Hallucination）

LLM 幻觉的根源：

```text
LLM 本质: P(下一个 token | 前文)
目标: 生成"最像"的文本，不是"最真"的文本
结果: 不知道时会编一个"看起来合理"的答案
```

类比：像一个从不肯说「不知道」的老同学——不管你问什么他都能接上话，讲得头头是道，但细节未必真发生过。

幻觉类型：

| 类型 | 例子 |
|---|---|
| 事实性幻觉 | 编造不存在的论文、人物 |
| 忠实性幻觉 | 总结时偏离原文 |
| 上下文幻觉 | 忽略给定文档，自己编 |
| 工具幻觉 | 编造不存在的工具调用 |

缓解手段：

- RAG（Retrieval-Augmented Generation，检索增强生成，见 1.4）：提供事实依据。
- 工具调用（Function Calling）：查数据库、搜索引擎。
- 引用要求：让模型标注来源。
- 低温采样：减少随机性。
- 验证器：二次检查关键事实。
- 明确说「不知道」：用 Prompt 约束行为边界。

**面试高频问法**：「幻觉能不能彻底消除？」共识口径：不能根除、只能缓解——它源自「最大化像、不保证真」的概率续写目标，这个目标同时也是模型流畅能力的来源；工程上靠 RAG 供事实、工具查证、Prompt 约束、低温采样、后置验证器，把发生率压到业务可接受范围。

### 4.8 能力边界

LLM 擅长：

- 语言理解与生成
- 总结、改写、翻译
- 代码生成与解释
- 常识推理
- 少样本学习（在提示词里给几个示例即可上手新任务）

LLM 不擅长：

- 精确计算（大数乘法、日期计算）
- 实时信息（知识截止日期）
- 长链推理（多步数学证明）
- 事实核查（容易编造）
- 空间推理、因果推理
- 长期记忆（每次对话独立，默认不记得上次）

Agent 的意义：

> **用工具、RAG、记忆、规划，弥补 LLM 的短板。**

### 4.9 知识截止与实时性

- 模型训练数据有截止日期（Knowledge Cutoff）。
- 截止日期后的事件，模型不知道；硬问它会用旧知识外推，是幻觉高发区。
- 解决方案：RAG、搜索工具、API 调用（天气、行情、库存等实时源）。
- 工程纪律：涉及时效信息的问题，默认「模型不知道」，把实时性交给工具层。

### 4.10 模型规模与 MoE

| 规模 | 代表 | 特点 |
|---|---|---|
| 小模型（<10B） | Llama 3.2 3B、Qwen 2.5 7B | 便宜、快、适合简单任务 |
| 中模型（10B-100B） | Llama 3.1 70B、Qwen 2.5 72B | 平衡 |
| 大模型（>100B） | GPT-4 级、Claude、Gemini 旗舰 | 强、贵、慢 |
| MoE（Mixture of Experts，混合专家） | Mixtral、DeepSeek 系列 | 总参数量大但每 token 激活少，性价比高 |

工程建议：

- 不是所有任务都要大模型。
- 路由策略：简单任务用小模型，复杂任务用大模型。
- 成本、延迟、效果三者权衡。

### 4.11 开源 vs 闭源

| 维度 | 闭源 API | 开源模型 |
|---|---|---|
| 效果 | 通常最强 | 追赶中 |
| 成本 | 按 token 付费 | 自托管，固定成本 |
| 隐私 | 数据出域 | 可本地部署 |
| 可控性 | 低 | 高 |
| 运维 | 无 | 需要 GPU、部署能力 |
| 微调 | 有限 | 自由（LoRA 全家桶可用） |

### 4.12 集中回答：能力、幻觉、上下文窗口从哪来

**能力从哪来**：预训练数据的广度与质量决定知识上限，参数规模决定容量（Scaling Law 共识）；SFT 与对齐不增加知识，而是把潜在能力激发成可用能力；用强化学习激发长链推理的「推理模型」是近年主线（趋势观察）。

**幻觉从哪来**：训练目标是「续写得更像」，从不奖励「不知道时承认不知道」；叠加知识截止（训练之后的事只能编）与采样随机性。根子在目标函数，所以只能缓解、不能根除。

**上下文窗口从哪来**：上限由位置编码（Positional Encoding，见 0.4）能表达的范围和训练时见过的序列长度决定；能不能用好受推理工程制约——注意力计算量随长度平方增长，KV 缓存（KV Cache）显存随长度线性增长，所以厂商标称的是「塞得进」，不是「都用得好」。

由此引出一个高频选型题：知识该进参数、进检索库，还是直接塞上下文：

| 维度 | 微调（SFT/LoRA） | RAG（见 1.4） | 长上下文直接塞 |
|---|---|---|---|
| 适合改变什么 | 风格、格式、领域行为 | 事实、私有知识、易变知识 | 一次性文档分析 |
| 知识更新 | 重新训练 | 更新文档即可 | 无需更新，每次现塞 |
| 可追溯性 | 差 | 好（可引用来源） | 好（原文就在输入里） |
| 成本结构 | 一次训练 + 低推理成本 | 检索 + 中等输入成本 | 超长输入，token 成本最高 |
| 延迟 | 最低 | 中 | 最高（注意力开销） |
| 典型风险 | 过拟合、灾难性遗忘 | 检索失败、噪声混入 | 中间遗忘、成本爆炸 |

共识口径：**改行为用微调，补知识用 RAG，一次性分析用长上下文**；三者不互斥，生产系统常组合使用。

## 5. 架构 / 流程

### 5.1 三阶段训练流水线

```text
┌──────────────────────────────────────────────────────────────┐
│ 阶段 1  预训练（Pre-training）                                 │
│ 数据：数万亿 token 的网页 / 书籍 / 代码，无需人工标注            │
│ 目标：预测下一个 token（自监督）                                │
│ 产物：基座模型——会语言、有知识、能推理，但不会「听话」            │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│ 阶段 2  监督微调（SFT）                                        │
│ 数据：十万到百万级人工标注的指令-回答对                          │
│ 目标：仍是预测下一个 token，但学的是「指令 → 应答」格式           │
│ 产物：指令模型——听得懂指令、按角色和格式回答                      │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│ 阶段 3  对齐（RLHF-PPO / DPO / GRPO）                          │
│ 数据：人类偏好排序 / 偏好对（A 比 B 好）                        │
│ 目标：把「人类觉得更好」变成优化目标                             │
│ 产物：对齐模型——更有用、更安全、更符合预期                       │
└──────────────────────────────────────────────────────────────┘
                              ↓
        发布为 API 或开源权重 → 你在 1.1 里调用的模型，
        通常已经走完全部三步
```

### 5.2 从用户输入到模型输出

```text
1. 用户输入: "帮我总结这篇文章"
   ↓
2. 分词: 文本 → token 序列
   ↓
3. 拼接上下文: system prompt + 历史 + 用户输入
   ↓
4. 检查上下文窗口: 超长则截断/压缩
   ↓
5. Transformer 前向传播（见 0.4）:
   ├─ 嵌入 + 位置编码
   ├─ N 层 Transformer Block
   └─ 输出层 → 词表概率分布
   ↓
6. 采样: 根据 temperature/top-p 选 token
   ↓
7. 拼回输入，重复直到结束符或 max_tokens
   ↓
8. 解码: token 序列 → 文本
   ↓
9. 返回给用户（可流式）
```

## 6. 代码 / 工具

### 6.1 tiktoken：token 计数与成本估算

```python
import tiktoken

# 分词器与模型绑定：新一代模型用 o200k_base，旧一代用 cl100k_base
enc = tiktoken.get_encoding("o200k_base")

zh = "大语言模型把文本切成 token 再处理。"
en = "Large language models split text into tokens."

print(len(enc.encode(zh)))  # 中文 token 数（量级示意：约十几个）
print(len(enc.encode(en)))  # 英文 token 数（量级示意：约 10）

# 成本估算：按输入 token 计价，单价以厂商文档为准（此处为示意值）
text = "一段要发往 API 的长文本。" * 200
tokens = len(enc.encode(text))
price_per_mtok = 0.15  # 示意单价：美元 / 百万 token
print(f"{tokens} tokens, 输入成本约 {tokens / 1e6 * price_per_mtok:.6f} 美元")
```

注意：tiktoken 对应 OpenAI 系分词器，其他厂商用自己的分词器或在线计数工具；跨模型迁移时 token 数会变，成本估算要重跑。

### 6.2 调用 API：采样参数长什么样

```python
from openai import OpenAI

client = OpenAI(api_key="YOUR_KEY")

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "你是一个简洁的助手。"},
        {"role": "user", "content": "用一句话解释什么是 LLM。"},
    ],
    temperature=0.7,   # 随机度：低温确定，高温发散
    max_tokens=100,    # 输出上限：同时兜住成本与延迟
    top_p=0.9,         # 核采样：只从累积概率前 90% 的候选里取
)

print(response.choices[0].message.content)
print("Token 使用:", response.usage)  # 实际消耗的输入/输出 token 数
```

### 6.3 对比不同 temperature

```python
# client 沿用 6.2 的定义
def ask(prompt: str, temperature: float) -> str:
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
        temperature=temperature,
        max_tokens=50,
    )
    return response.choices[0].message.content

prompt = "给我一个创业点子，一句话。"

for t in [0.0, 0.7, 1.5]:
    print(f"--- Temperature={t} ---")
    for _ in range(2):
        print(ask(prompt, t))
```

观察：

- T=0：每次几乎一样。
- T=0.7：有变化但合理。
- T=1.5：可能跑偏、不连贯。

### 6.4 流式输出

```python
stream = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "写一首关于 AI 的短诗。"}],
    stream=True,  # 逐 chunk 返回，首字出现时间大幅提前
)

for chunk in stream:
    if chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="", flush=True)
```

## 7. 案例

### 案例 A：幻觉导致 Agent 编造工具

**场景**：某本地生活服务 Agent 上线初期，用户问「帮我查一下明天北京的天气」。Agent 并没有接入天气工具，但 LLM 仍然生成了 `get_weather` 调用，参数 `city="北京"`、`date="明天"` 全是编的。工具调用直接失败，用户看到报错。埋点显示，工具调用失败里约 8% 属于「调用了不存在的工具」。

**做法**：

- 工具白名单校验：调用前检查函数名是否在注册表中。
- 开启 Function Calling 的严格模式（结构化工具调用，见 1.3）。
- 系统提示明确：「没有可用工具时，直接告知无法查询，不要模拟调用」。
- 采样参数固定 `temperature=0`。

**效果**：两周后编造类调用占比降到 0.5% 以下，无工具时模型改为明确告知「我无法查询实时天气」（示意性数字）。

### 案例 B：多轮对话撑爆上下文窗口

**场景**：某电商客服 Agent，平均每轮往返约 2K token，对话进行到 20 轮时输入约 4-6 万 token，超过所用模型 32K 窗口，历史被静默截断——模型忘了开头确认过的订单号，开始答非所问。

**做法**：

- 滑动窗口：只保留最近 8 轮原文。
- 摘要压缩：更早的历史压缩成约 300 token 的滚动摘要。
- 槽位记忆：订单号、会员等级等关键事实单独存字段，每轮注入（记忆管理的系统做法见 1.5）。

**效果**：单轮输入稳定在 8K 以内，单次调用成本下降约 60%，「失忆」类客诉基本消失（示意性数字）。

### 案例 C：Temperature 导致 JSON 解析失败

**场景**：某表单信息抽取服务，输出需要严格 JSON。`temperature=1.0` 时模型偶尔输出带注释、尾逗号或裸字段名的 JSON，下游 `json.loads` 失败率约 3%。

**做法**：`temperature=0` + 启用 JSON 输出模式 + Pydantic Schema 校验 + 校验失败定向重试一次。

**效果**：解析失败率降到 0.1% 以下，重试带来的额外成本可忽略（示意性数字）。

### 案例 D：模型分层路由控成本

**场景**：某电商客服系统全量走旗舰模型，月账单难以承受。流量分析发现：意图分类和 FAQ 直接命中两类请求占约 70%，任务本身不需要强推理。

**做法**：分类与 FAQ 切换到 7B 级小模型本地部署，仅复杂售后纠纷走旗舰 API，中间用置信度路由兜底回退。

**效果**：整体 token 成本下降约 70%，平均响应延迟从约 3 秒降到约 1.2 秒，人工抽检的用户可见质量基本持平（示意性数字）。

## 8. 常见坑

1. **以为模型知道一切**。
   知识有截止日期，实时信息要接工具。

2. **以为模型会精确计算**。
   大数乘法、日期计算容易错，用代码解释器或计算工具。

3. **忽略上下文窗口**。
   超长输入被截断，关键信息丢失；多轮场景要先做占用预算。

4. **Temperature 设太高**。
   结构化输出、工具调用必须低温。

5. **盲目追求大模型**。
   简单任务用小模型，成本可降一个量级。

6. **不做 token 估算**。
   多轮 Agent 的 token 成本是复利增长，历史越滚越贵。

7. **以为流式输出只是体验优化**。
   它还能显著降低首 token 延迟，提升感知速度。

8. **忽略模型版本差异**。
   同系列的大小版本在能力、成本、上下文上限上都不同，升级版本要跑回归。

9. **把幻觉当 bug 修**。
   幻觉是 LLM 的固有特性，要靠 RAG、工具、验证器等系统工程压低，不存在「修一次就好」。

10. **不读模型文档**。
    不同模型的采样参数范围、上下文窗口、定价都不同，迁移配置必须逐项核对。

11. **temperature 与 top_p 同时大幅调高**。
    两处随机性叠加，输出失控且无法归因；固定一个、只调另一个。

12. **max_tokens 设得太小**。
    输出被拦腰截断，JSON 缺右括号必然解析失败；要给足输出预算并检测 finish_reason 是否为截断。

13. **关键信息塞在上下文中段**。
    中间遗忘使中段内容最容易被忽略；重要指令放系统提示，关键文档放首尾。

## 10. 小结

- 训练三阶段：**预训练定知识上限，SFT 定指令服从，对齐定安全与有用**。
- 对齐方法谱系：**RLHF（PPO）在线强但重，DPO 离线简而稳，GRPO 是去价值网络的 PPO 变体**。
- 微调常识：**LoRA 只训低秩增量，成本降一个量级，是应用侧默认起点**。
- 推理机制：**自回归，逐个 token 生成**；长即慢即贵，TTFT 与总延迟是两个指标。
- 采样策略：**Temperature 定随机度，Top-p/Top-k 定候选集**；结构化输出必低温，二参数别同时大调。
- 上下文窗口：**输入输出共享额度，大窗口不等于用得好**，警惕中间遗忘与截断。
- 幻觉：**源于概率续写本质，只能缓解不能根除**，靠 RAG、工具、约束、验证器压制。
- 能力边界：**擅长语言与模式，不擅长精确计算、实时信息、事实核查**——Agent 用工具、记忆、规划补短板。
- 选型口径：**简单任务小模型、结构化输出低温；改行为用微调、补知识用 RAG、一次性分析用长上下文**。
- 这些能力直接支撑：0.6 提示工程基础、0.7 向量与嵌入基础、1.1 LLM API 与模型选型、1.4 RAG。
