# 讲解 1.6 LLM 应用评估与可观测性

> 说明：前置 1.1-1.5 讲完模型选型、Prompt、结构化输出、RAG 与记忆，1.6 回答下一层问题：**这套应用到底好不好、为什么不好**——离线/在线评估、LLM-as-Judge、指标体系、日志与基础追踪。  
> 这是从“Demo 能跑”到“生产可靠”的分水岭。  
> 全链路追踪平台与评估/实验管理平台在 3.4 可观测性与追踪、3.5 评估体系与实验管理展开，Agent 特有的评估见 2.9；本篇聚焦 LLM 应用层的最小评估与可观测能力。

## 1. 定位

LLM 应用层第 6 个知识点，属于“质量保障体系”。  
它解决一个核心问题：**LLM 输出不确定、多步链路复杂、主观性强，如何量化效果、定位问题、持续迭代？**

对这个问题先给正面拆解，本篇全部内容都在回答它的两半：

```text
如何量化效果？
  = 评估集（Eval Set） + 指标体系 + 评估方法
  = 离线评估（评估集上跑分） + 在线评估（真实流量与用户反馈）

如何定位问题？
  = 可观测性三支柱：日志（Logging） + 链路追踪（Tracing） + 指标（Metrics）
  = 分层评估：端到端分数下降时，用组件级评估定位是检索、生成还是工具环节坏了
```

**评估告诉你“好不好”，可观测性告诉你“为什么”。两个都缺，迭代就是盲调。**

类比一家餐厅：评估集像**试菜员**——每道改了配方的菜都要过一遍固定的打分表，才能端给客人；可观测性像**后厨监控**——客人投诉菜太咸时，你能回放录像看到是哪一步盐放多了。只有试菜员没有监控，你知道菜不好但不知道为什么；只有监控没有试菜员，你能还原过程却无法系统性对比新旧配方。

前置：1.1-1.5（选型、Prompt、结构化输出、RAG、记忆，它们提供被评估的对象）。  
后续：直接支撑 2.9 Agent 评估与安全、3.4 可观测性与追踪、3.5 评估体系与实验管理。

## 2. 一句话定义

LLM 应用评估与可观测性，是通过构建评估集、定义指标、用人工/规则/LLM-as-Judge 打分（离线），结合真实流量与用户反馈（在线），并依靠日志、追踪、指标记录每次调用，从而量化 LLM 应用效果并定位问题的工程体系。

简化公式：

```text
评估与可观测性 = 评估集 × 指标 × 评估方法（离线 + 在线）   ← 回答“好不好”
              + 日志 × 追踪 × 指标（三支柱）             ← 回答“为什么”
```

## 3. 为什么需要

传统软件测试靠断言：

```python
assert add(1, 2) == 3
```

LLM 应用把断言的基础全拆了：

- **输出不确定** → 同一输入多次调用结果不同，无法写死期望值。
- **主观性强** → 回答“好不好”没有唯一标准答案。
- **多步链路** → RAG 检索、工具调用、记忆注入（见 1.4、1.5），任何一环出错都污染最终结果，且互相掩盖。
- **迭代频繁** → Prompt 一改，行为全变。
- **黑盒依赖** → 厂商模型更新，你不知道变了什么。

| 维度 | 传统软件测试 | LLM 应用评估 |
|---|---|---|
| 正确性判定 | 断言，非对即错 | 打分/判断，是程度问题 |
| 期望输出 | 唯一且确定 | 多个可接受答案，或无标准答案 |
| 一次变更的影响 | 可静态分析影响面 | Prompt/模型/检索任一改动全局生效，需全量回归 |
| 回归范围 | 单元测试精确定位 | 依赖评估集覆盖度 |
| 问题定位 | 栈追踪 | 依赖专门记录的调用链路（trace） |
| 成本维度 | 基本可忽略 | token、延迟随调用量线性变化 |

不做评估与可观测性的实际后果：

- Prompt 改了，不知道是变好还是变坏。
- 用户投诉回答错，不知道是检索问题还是生成问题。
- 成本突然涨了，不知道哪里 token 用多了。
- 模型升级后回归失败，不知道哪些 case 受影响。

（这四个场景的完整复盘见 §7 案例。）

**评估是“知道好不好”，可观测性是“知道为什么”。**

## 4. 核心原理

### 4.1 评估的四个层次

```text
Level 1: 单元测试       → 格式、校验、解析（断言仍然适用）
Level 2: 组件评估       → RAG 检索、工具调用单独跑分
Level 3: 端到端评估     → 任务成功率、回答质量
Level 4: 在线评估       → 用户反馈、A/B 测试
```

| 层次 | 评估对象 | 典型指标 | 主要方法 |
|---|---|---|---|
| L1 单元测试 | 输出格式与解析 | 格式合规率、解析成功率 | 断言、规则 |
| L2 组件评估 | 检索、工具调用、记忆 | Recall@K、工具调用准确率 | 规则 + 评估集 |
| L3 端到端评估 | 最终回答/任务结果 | 准确率、忠实度、任务成功率 | 规则 + LLM-as-Judge + 人工 |
| L4 在线评估 | 真实用户表现 | 满意度、投诉率、留存 | A/B 测试、反馈分析 |

分层的目的不是流程好看，是**归因**：端到端分数下降时，从上往下逐层排查——L3 掉分而 L2 检索正常，问题大概率在生成环节；L2 掉分则先修检索，别急着动 Prompt。类比服装厂质检：先验布料（组件），再验裁剪（组装），最后验成衣（端到端），布料不合格就别怪裁缝。

### 4.2 离线评估 vs 在线评估

| 维度 | 离线评估 | 在线评估 |
|---|---|---|
| 数据 | 固定评估集，可控、可复现 | 真实流量，分布随时间漂移 |
| 速度 | 快，分钟级跑完一轮 | 慢，需积累流量达到统计显著性 |
| 风险 | 无用户风险 | 直接影响用户，必须灰度 |
| 指标 | 代理指标（准确率、忠实度） | 业务指标（满意度、转化、投诉率） |
| 成本 | 低（评估集跑一遍） | 高（真实调用量 × 实验时长） |
| 主要作用 | 迭代筛选、回归门禁 | 终极验证、发现评估集盲区 |

标准节奏：**离线先过滤明显退化 → 小流量灰度在线验证 → 全量发布**。离线分数是发布的必要条件，不是充分条件。

面试高频问法：**离线评估分数涨了，线上效果没动甚至变差，怎么办？** 共识口径：先查两个错位——评估集分布与真实流量漂移（旧 case 覆盖不了新场景）、离线代理指标与业务目标错位（忠实度涨了，但用户要的是简洁）。对策：把线上 bad case 回流进评估集，重新校准离线指标与线上指标的相关性，然后再谈优化。

### 4.3 评估集（Eval Set）

评估集 = 输入 + 期望输出 + 元数据。

```python
eval_set = [
    {
        "input": "退货后多久能收到退款？",
        "expected": "3-5 个工作日",
        "context": "退款时效：3-5 个工作日到账。",
        "tags": ["退货", "退款"],
    },
    {
        "input": "怎么申请换货？",
        "expected": "15 天内可换，联系客服",
        "context": "换货说明：15 天内可换。",
        "tags": ["换货"],
    },
]
```

**构建原则**：

- **代表性**：覆盖真实用户场景。
- **多样性**：不同问法、长度、难度。
- **独立性**：不能和调参用的样例重叠。
- **可扩展**：从 bad case 持续补充。
- **规模**：起步 50–100 条，生产 500+。

工程口径补充：

- 起步阶段 20–200 条即可形成可用的**黄金评估集（Golden Set）**，但要**版本化**：评估集进 git，改评估集和改代码一样走 review，否则分数没可比性（实验管理展开见 3.5）。
- **独立性是最常被违反的**：用来调 Prompt 的样例绝不能进评估集，否则数据泄漏（Data Leakage），分数虚高，上线就翻车。
- 增长来源三路：bad case 回流（见 4.10）、线上日志抽样、人工构造边界 case。

### 4.4 评估指标体系

**客观指标**：

| 指标 | 适用 | 说明 |
|---|---|---|
| 准确率 | 分类、抽取 | 完全匹配比例 |
| F1 | 分类 | 精确率和召回率调和 |
| BLEU / ROUGE | 翻译、摘要 | n-gram 重叠 |
| 格式合规率 | JSON 输出 | 符合 Schema 比例 |
| 检索 Recall@K | RAG | 前 K 个含相关文档 |
| 工具调用准确率 | Agent | 工具名、参数正确 |

**主观指标**：

| 指标 | 说明 |
|---|---|
| 忠实度（Faithfulness） | 答案是否基于上下文 |
| 答案相关性 | 是否回答了问题 |
| 有用性 | 用户是否觉得有帮助 |
| 安全性 | 是否有害、偏见、泄露 |
| 语气风格 | 是否符合品牌调性 |

**工程指标**：

| 指标 | 说明 |
|---|---|
| TTFT（Time To First Token） | 首 token 延迟，流式体验的关键 |
| 总延迟 | 完整响应时间 |
| P95 / P99 | 长尾延迟 |
| Token 消耗 | 输入 + 输出 |
| 成本 | 每次调用费用 |
| 错误率 | 失败请求比例 |

指标选择三原则：

- **与任务对齐**：抽取任务看 F1，客服问答看解决率，别全押在“judge 打分好不好看”上。
- **北极星 + 护栏**：定一个质量北极星指标，再配护栏指标（Guardrail Metrics）——成本、延迟、安全合规是护栏，质量涨 5% 但成本涨 3 倍或有害率上升，都不能发布。
- **可复算**：同一版本重跑，指标波动应可解释（固定随机种子、控制温度），否则对比无意义。

### 4.5 评估方法：人工 / 规则 / LLM-as-Judge / 混合

| 方法 | 成本 | 速度 | 语义能力 | 一致性 | 适用 |
|---|---|---|---|---|---|
| 人工评估 | 高 | 慢 | 最强 | 中（标注者间有差异） | 小规模、高价值、主观指标、终审 |
| 规则评估 | 极低 | 极快 | 无 | 完全一致 | 格式、关键词、正则、数值断言 |
| LLM-as-Judge | 低 | 快 | 强 | 较高（有偏差，需校准） | 大规模语义质量、忠实度、两版对比 |
| 混合评估 | 中 | 中 | 强 | 高 | 生产推荐 |

**人工评估**：准确，但贵、慢。适合小规模、高价值、主观指标。形式：打分（1–5）、排序、二元判断。

**规则评估**：快、便宜。适合格式、关键词、正则。局限：无法评估语义，但凡是能写成规则的，就不要浪费 judge。

**LLM-as-Judge（以 LLM 为裁判）**：用强模型给被评估输出打分，是规模化语义评估的主力，偏差与校准见 4.6 专门展开。

**混合评估**：

```text
规则评估（格式、硬约束） + LLM-as-Judge（语义质量） + 人工抽检（校准与终审）
```

这是生产推荐方案：规则拦住确定性问题，judge 覆盖语义面，人工守住 judge 的漂移。

### 4.6 LLM-as-Judge 深入：打分方式、偏差与校准

原理：用一个（通常更强的）judge 模型，按给定评分标准对输出打分或做判断。judge 给出的是**代理判断**，不是真值——它的可靠性完全取决于校准程度。

**三种打分方式**：

| 方式 | 做法 | 优点 | 局限 |
|---|---|---|---|
| 绝对打分（Absolute Scoring） | 对单个回答按 1–5 打分 | 可跨版本跟踪，成本低 | 分数不稳，judge 在“3 分还是 4 分”上摇摆 |
| 成对比较（Pairwise Comparison） | 两个回答二选一 | 判别比打分稳定，适合对比两版 Prompt | 只能相对排序，n 个候选 O(n²) 调用 |
| 量规打分（Rubric） | 预先写清每档分数的具体标准 | 显著提升稳定性与一致性 | rubric 要人工写好并随任务演化 |

经验口径：**对比两版系统用 pairwise，跨版本长期跟踪用绝对打分，两者都尽量挂 rubric。**

**四类系统偏差与缓解**：

| 偏差 | 现象 | 缓解 |
|---|---|---|
| 位置偏差（Position Bias） | pairwise 时系统性偏好先出现的答案 | 交换 A/B 顺序跑两次，结论不一致记平局 |
| 冗长偏差（Verbosity Bias） | 偏好更长的答案，哪怕信息量相同 | rubric 明确“信息量相同时更简洁者胜” |
| 自我偏好（Self-preference） | judge 偏好与自己同家族模型的输出风格 | judge 与被评估模型异源，定期人工抽检核查 |
| 漂移（Drift） | judge 模型升级或静默更新后打分尺度变化 | 用固定 golden set 定期重校准，监控 judge 分数分布 |

**校准流程（judge 上线前必须走完）**：

1. 人工标注一个小型 golden set（50–100 条，两人独立标注、分歧仲裁）。
2. judge 对同一批打分，计算与人工的一致率（Agreement Rate）或 Cohen's Kappa（科恩 Kappa 系数，剔除随机一致）。
3. 一致率不达门槛（经验值 80% 以上，示意）就改 rubric、换 judge 模型，达标后才允许批量使用。
4. 运行期保留 5%–10% 人工抽检（示意比例），持续监控 judge 与人工的一致性，发现漂移立即重校准。

**适用与不适用**：

- 适合：大规模语义质量评估、RAG 忠实度与相关性、两版输出的 pairwise 排序、bad case 初筛。
- 不适合或慎用：
  - 有确定性判定的（JSON 合法性、字段抽取匹配）——断言更准更便宜。
  - 数值精确计算与事实核验——judge 自己也会算错、也会幻觉。
  - 高风险终判（医疗、法律、金融内容能否上线）——judge 只能初筛，终审必须人工。
  - judge 与被评估模型同源且未做自我偏好校准。

面试高频问法：**「LLM-as-Judge 可靠吗？」** 共识口径：可靠是有前提的。它在 pairwise 与 rubric 模式下与人工一致性可以做得很高，但存在位置、冗长、自我偏好三类系统偏差，且会随 judge 模型升级漂移；生产口径是“先校准、后使用、常抽检”——golden set 上与人工一致性达标才启用，运行中保留人工抽检并定期重校准。未经校准的 judge 分数不能作为发布依据。

### 4.7 可观测性三支柱

| 支柱 | 说明 | 工具 |
|---|---|---|
| 日志（Logging） | 记录事件 | Python logging、JSON 结构化日志 |
| 链路追踪（Tracing） | 还原一次请求的完整链路 | OpenTelemetry、LangSmith、LangFuse |
| 指标（Metrics） | 聚合统计与告警 | Prometheus、Grafana、Datadog |

**Tracing 核心概念**：

```text
Trace: 一次完整请求
  ├─ Span: 用户输入
  ├─ Span: RAG 检索
  │    ├─ Span: 嵌入
  │    └─ Span: 向量检索
  ├─ Span: LLM 调用
  └─ Span: 输出校验
```

每个 Span 记录：开始时间、耗时、输入、输出、token、错误。有了它，“回答错了”才能变成“检索 span 里 Top-5 只有 1 篇相关”。

划界：本篇只到应用层最小埋点；全链路 trace 规范、采样策略、跨服务串联、会话回放与平台选型在 3.4 可观测性与追踪展开，实验管理与 CI 回归门禁在 3.5 展开。趋势观察：OpenTelemetry 社区截至 2026 年已推出生成式 AI 语义约定（gen_ai semconv），不同框架的 trace 字段正在走向互通。

### 4.8 日志设计

结构化日志（Structured Logging）：

```python
import logging
import json

logger = logging.getLogger("llm_app")

logger.info(json.dumps({
    "event": "llm_call",
    "trace_id": "abc123",
    "model": "gpt-4o-mini",
    "input_tokens": 500,
    "output_tokens": 200,
    "latency_ms": 1200,
    "cost": 0.0002,
    "user_id": "u1",
}))
```

**必须记录**：

- trace_id：串联一次请求的所有环节。
- 模型、参数。
- 输入/输出 token。
- 延迟。
- 成本。
- 错误信息。
- 工具调用。

**不能记录**：

- API Key。
- 用户 PII（Personal Identifiable Information，个人身份信息；必须记录时先脱敏）。
- 完整敏感文档。

### 4.9 监控与告警

关键监控面板：

```text
1. 请求量：QPS、日请求数
2. 延迟：P50、P95、P99
3. 错误率：4xx、5xx、超时
4. 成本：日消耗、单次成本
5. Token：输入/输出分布
6. 质量：评估分数、用户反馈
7. 缓存命中率
8. 限流触发次数
```

告警规则：

- P99 延迟 > 5s。
- 错误率 > 1%。
- 日成本 > 预算。
- 评估分数下降 > 5%。
- judge 分数分布突变（judge 模型可能漂移，提示重校准）。

### 4.10 Bad Case 收集与回流

```text
用户反馈（点赞/点踩/投诉）
    ↓
记录 bad case（输入、输出、上下文、trace）
    ↓
分类：检索问题？生成问题？工具问题？
    ↓
修复：调 Prompt / 改检索 / 换模型
    ↓
加入评估集，防止回归
```

回流是评估集的血液：没有回流的评估集会逐渐失去代表性，模型再好也是在旧场景上过拟合。

### 4.11 A/B 测试

对比两个版本：

```text
版本 A（50% 流量） vs 版本 B（50% 流量）
    ↓
指标对比：准确率、延迟、成本、用户反馈
    ↓
统计显著性（Statistical Significance）检验
    ↓
全量发布优胜版本
```

注意：

- 样本量要够，结论才显著。
- 指标要提前定好，防止事后挑对自己有利的指标。
- 避免同时改多个变量，否则无法归因。

### 4.12 评估驱动开发流程

```text
 1. 定义任务和指标
 2. 构建评估集
 3. 跑基线
 4. 改一个变量
 5. 跑评估
 6. 对比：变好？变坏？
 7. 保留提升，回滚退化
 8. 记录实验
 9. 上线灰度
10. 收集反馈，补充评估集
```

## 5. 架构 / 流程

**生产级 LLM 应用可观测性架构**：

```text
┌──────────────────────────────────────────┐
│  用户请求                                 │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  应用层                                   │
│  ├─ trace_id 生成                         │
│  ├─ Span 埋点                             │
│  └─ 结构化日志                            │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  LLM / RAG / 工具调用                     │
│  ├─ 记录 token、延迟、成本                │
│  └─ 记录输入输出（脱敏）                  │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  可观测平台                               │
│  ├─ Logging: ELK / Loki                   │
│  ├─ Tracing: LangFuse / LangSmith / OTel  │
│  └─ Metrics: Prometheus + Grafana         │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  评估与迭代                               │
│  ├─ 离线评估集                            │
│  ├─ 在线 A/B 测试                         │
│  └─ Bad case 回流                         │
└──────────────────────────────────────────┘
```

**评估驱动迭代闭环**（4.12 流程的循环视角）：

```text
   ① 定义指标（北极星 + 护栏）
          ↓
   ② 构建评估集（golden set，版本化）
          ↓
   ③ 跑基线，记录版本与分数
          ↓
   ④ 只改一个变量 → 跑评估 → 对比
          ↓
   ⑤ 保留提升 / 回滚退化，记录实验
          ↓
   ⑥ 灰度上线 → A/B 验证 → 收集反馈与 bad case
          │
          └──→ 回流补充评估集、按 trace 归因修复 ──→ 回到 ②④，进入下一轮
```

没有闭环的评估是“一次性考试”，有闭环的评估才是“持续体检”：每一次上线都在给下一轮迭代生产数据。

### 6.1 评估集构建脚本

```python
import json
import hashlib
from datetime import date

def build_eval_set(manual_cases: list[dict], bad_cases: list[dict]) -> list[dict]:
    """合并人工种子 case 与线上 bad case，生成可版本化的评估集。
    每条带唯一 id 与入库日期，便于去重和 git 管理。"""
    merged = []
    for c in manual_cases + bad_cases:
        merged.append({
            # 以输入文本的哈希作为去重 id
            "id": hashlib.md5(c["input"].encode("utf-8")).hexdigest()[:8],
            "input": c["input"],
            "expected": c.get("expected", ""),   # 主观题可为空，交给 judge
            "context": c.get("context", ""),
            "tags": c.get("tags", []),
            "source": c.get("source", "manual"), # manual / bad_case
            "added": str(date.today()),
        })

    seen, deduped = set(), []
    for case in merged:
        if case["id"] not in seen:
            seen.add(case["id"])
            deduped.append(case)
    return deduped

# 线上 bad case：来自用户点踩日志，人工补 10 分钟期望输出后即可入库
bad_cases = [
    {
        "input": "异地退货运费谁承担？",
        "context": "退货政策：质量问题卖家承担运费，其他情况买家承担。",
        "expected": "质量问题卖家承担，其他情况买家承担",
        "tags": ["退货", "运费"],
        "source": "bad_case",
    },
]

eval_set = build_eval_set(manual_cases=eval_set, bad_cases=bad_cases)
with open("eval_set_v3.json", "w", encoding="utf-8") as f:
    # 评估集文件入 git，变更走 review，保证分数跨版本可比
```

### 6.2 最小评估脚本

```python
import asyncio

async def evaluate(prompt_template: str, eval_set: list[dict]) -> dict:
    results = []
    for case in eval_set:
        output = await call_llm(prompt_template.format(**case))
        correct = case["expected"] in output
        results.append({
            "input": case["input"],
            "expected": case["expected"],
            "output": output,
            "correct": correct,
        })

    accuracy = sum(r["correct"] for r in results) / len(results)
    return {"accuracy": accuracy, "details": results}
```

### 6.3 LLM-as-Judge：绝对打分与去位置偏差的 pairwise

```python
import json

JUDGE_PROMPT = """你是一个评估专家。请根据以下标准给回答打分（1-5分）。

标准：
1. 忠实度：回答是否基于上下文，没有编造。
2. 相关性：回答是否切题。
3. 完整性：是否覆盖关键信息。

上下文：{context}
问题：{question}
回答：{answer}

输出 JSON：{{"faithfulness": int, "relevance": int, "completeness": int, "reason": str}}
"""

async def judge(context: str, question: str, answer: str) -> dict:
    """绝对打分：适合跨版本跟踪单一系统的质量。"""
    prompt = JUDGE_PROMPT.format(context=context, question=question, answer=answer)
    response = await call_llm(prompt, temperature=0)
    return json.loads(response)

PAIRWISE_PROMPT = """你是评估专家。对比同一问题的两个回答，按以下标准选出更好的一个：
1. 忠实度：是否基于上下文，没有编造。
2. 相关性：是否切题。
3. 简洁：信息量相同时，更简洁的更好。

上下文：{context}
问题：{question}
回答A：{answer_a}
回答B：{answer_b}

输出 JSON：{{"better": "A" 或 "B" 或 "tie", "reason": str}}
"""

async def judge_pairwise(context: str, question: str, a: str, b: str) -> str:
    prompt = PAIRWISE_PROMPT.format(
        context=context, question=question, answer_a=a, answer_b=b
    )
    return json.loads(await call_llm(prompt, temperature=0))["better"]

async def judge_pairwise_debiased(context: str, question: str, a: str, b: str) -> str:
    """交换 A/B 顺序各跑一次，消除位置偏差：
    两次结论一致才采纳，不一致记 tie。调用成本 x2，换来结论可信。"""
    r1 = await judge_pairwise(context, question, a, b)
    r2 = await judge_pairwise(context, question, b, a)
    if r1 == "A" and r2 == "B":
        return "A"
    if r1 == "B" and r2 == "A":
        return "B"
    return "tie"

def agreement_rate(judge_labels: list[str], human_labels: list[str]) -> float:
    """judge 上线前的校准门槛：与人工标注的一致率。"""
    assert len(judge_labels) == len(human_labels)
    hit = sum(j == h for j, h in zip(judge_labels, human_labels))
    return hit / len(judge_labels)

# 在 100 条人工标注的 golden set 上跑 agreement_rate，
# 达到门槛（如 0.8，示意）才允许 judge 批量上岗；上线后每月重校准防漂移
```

### 6.6 简单监控指标

```python
from prometheus_client import Counter, Histogram, start_http_server

REQUEST_COUNT = Counter("llm_requests_total", "Total LLM requests", ["model", "status"])
REQUEST_LATENCY = Histogram("llm_request_latency_seconds", "LLM latency", ["model"])
TOKEN_USAGE = Counter("llm_tokens_total", "Total tokens", ["model", "type"])

            response = await call_llm(model, messages)
            REQUEST_COUNT.labels(model=model, status="success").inc()
            TOKEN_USAGE.labels(model=model, type="input").inc(response.usage.prompt_tokens)

            return response
        except Exception:
            REQUEST_COUNT.labels(model=model, status="error").inc()
            raise
```

## 7. 案例

### 案例 A：RAG 系统上线后用户投诉

**场景**：某电商智能客服，RAG 上线两周，用户反馈“回答不准”。  
**排查**（靠 trace 分层归因）：

1. 查 Trace：检索耗时 2s，LLM 耗时 1s，链路正常但质量可疑。
2. 查检索 Span 的输出：Top-5 里只有 1 篇相关——组件级问题，不是生成问题。
3. 定位：切分太大，语义不聚焦。

**修复**：调小 chunk_size，加 Rerank。  
**效果**：检索 Recall@5 从 0.6 升到 0.9，端到端回答准确率从 65% 提升到 82%，相关 bad case 一周内清零。

### 案例 B：Prompt 改动导致回归

**场景**：新 Prompt 上线后，JSON 解析失败率从 0.5% 升到 3%，监控告警触发。  
**排查**：

1. 对比新旧 Prompt 在同一评估集上的结果：格式合规率从 99.3% 掉到 96.8%。
2. 抽查失败 case：新 Prompt 少了格式示例，模型偶尔输出带解释文字的 JSON。

**修复**：加 Few-shot 格式示例，离线评估恢复 99.2% 后重新灰度上线。  
**教训**：没有格式合规率监控和评估集回归，这次事故要等用户投诉才发现。

### 案例 C：成本突然飙升

**场景**：日成本从 $50 涨到 $200，无人变更。  
**排查**：

1. 看 Metrics：Token 消耗增加 4 倍，请求量持平。
2. 看 Trace：多轮会话的输入 token 随轮次线性上涨。
3. 定位：代码 bug，历史消息没截断，第 10 轮对话把前 9 轮全文塞进上下文。

**修复**：加滑动窗口截断历史，日成本回落到 $55。  
**要点**：成本告警（日消耗超预算）让问题在当天暴露，而不是月底账单。

### 案例 D：LLM-as-Judge 上线前校准

**场景**：一家金融科技公司的合规问答系统，每次 Prompt 迭代需人工评估 200 条，评估拖慢迭代到两周一次。  
**做法**：

1. 人工标注 100 条 golden set（两人独立标注，分歧样本仲裁）。
2. 第一版 judge：无 rubric、直接绝对打分，与人工一致率 72%，低于 80% 门槛，不许上岗。
3. 第二版：写 rubric 明确每档标准，对比场景改用交换顺序的 pairwise，一致率升到 89%。
4. 上线后每周保留 20 条人工抽检；某次 judge 模型升级后分数整体上浮，抽检发现漂移，重新校准。

**效果**：评估周期从 2 周缩到 1 天，Prompt 迭代频率翻倍，且两次漂移都被抽检机制拦截。

## 8. 常见坑

1. **只测几个例子就上线**。  
   对策：评估集至少 50 条，生产 500+；案例 D 的经验是 100 条 golden set 就能支撑 judge 校准。

2. **用调参样例做评估**。  
   数据泄漏，评估虚高。评估集必须独立，调参样例一律不进评估集。

3. **只看平均分，不看长尾**。  
   P95/P99 延迟、最差 case 更重要，平均值会掩盖 5% 用户的灾难体验。

4. **把 LLM-as-Judge 当绝对真理**。  
   judge 有位置、冗长、自我偏好三类偏差且会漂移。先在 golden set 上校准一致率，运行中保留人工抽检。

5. **pairwise 不交换顺序**。  
   位置偏差会让结论随呈现顺序翻转。交换 A/B 跑两次，不一致记平局。

6. **judge 与被评估模型同源还不知情**。  
   自我偏好会系统性抬分。judge 选异源模型，或用人工抽检对冲。

7. **不做版本管理**。  
   评估结果无法对比，不知道哪版好。评估集、Prompt、评估结果三者都版本化（实验管理见 3.5）。

8. **不记录 trace_id**。  
   出问题无法串联链路，排查只能靠猜。第一天就埋点。

9. **日志含敏感信息**。  
   PII、API Key 不能进日志，必须记录时先脱敏，否则评估系统自己变成合规事故。

10. **只监控技术指标，不监控质量**。  
    延迟低但回答错，用户照样不满意。质量指标（评估分数、点踩率）必须上面板。

11. **没有 Bad Case 回流**。  
    同样的错误反复出现。点踩/投诉进评估集，修复后固化为止回归用例。

12. **评估指标不统一**。  
    每次评估标准不同，分数没有可比性。指标与 rubric 固化在代码里，变更走 review。

13. **忽略成本指标**。  
    效果好了但成本爆炸，商业上不可行。成本是护栏指标，超阈值一票否决。

14. **不做 A/B 测试，或一次改多个变量**。  
    凭感觉上线可能变差；多变量改动无法归因。一次一个变量，离线评估后再灰度。

15. **评估集不更新**。  
    用户场景变了，评估集过时，离线分数与线上表现脱节。定期用线上 bad case 刷新。

16. **把可观测性当事后工作**。  
    上线后补埋点的成本是初期的数倍。trace_id 和结构化日志在第一行业务代码时就该有。

## 9. 练习

1. 为你的 RAG 系统构建 20 条评估集，用 6.1 的脚本去重并写入 json 文件，纳入 git 管理，计算准确率。
2. 实现规则 + LLM-as-Judge 双通道：规则查格式合规率，judge 打忠实度分，对 10 个回答各跑一遍，人工复核两者分歧的样本。
3. 实现 6.3 的 pairwise 评估：先不交换顺序跑 20 对，再交换顺序复跑，统计两次结论的翻转率（翻转率高说明位置偏差严重）。
4. 人工标注 30 条 golden set，计算 judge 与你的一致率；再给 judge 加 rubric，观察一致率变化。
5. 接入 LangFuse 或 OpenTelemetry，记录一次包含检索和生成的完整 trace，并能根据 trace 说出每段耗时和 token。
6. 用 Prometheus 记录请求量、延迟直方图、token 消耗，配置“日成本超预算”和“P99 延迟超 5s”两条告警规则。
7. 收集 10 个 bad case，按“检索/生成/工具”三类归因，写出每类的修复动作，并把全部 case 补进评估集。
8. 对比两个 Prompt 版本在评估集上的表现：报告准确率差值，并用置换检验或 bootstrap 估计该差值是否显著。
9. 设计一个监控面板，包含 6 个关键指标（至少覆盖质量、延迟、成本三个维度），说明每个指标的告警阈值与理由。

## 10. 小结

- 评估 = **评估集 + 指标 + 方法**；量化效果靠离线评估集跑分 + 在线真实流量验证，先离线过滤、再灰度上线。
- 可观测性 = **日志 + 追踪 + 指标**；定位问题靠 trace 分层归因：端到端掉分时，组件级评估指出是检索、生成还是工具坏了。
- 评估方法四档：**人工（准而贵）、规则（快而死）、LLM-as-Judge（规模化语义评估）、混合（生产标配）**。
- LLM-as-Judge 三种打分方式各有分工：**跨版本跟踪用绝对打分，两版对比用 pairwise，都要挂 rubric**。
- judge 的可靠来自校准：**golden set 上与人工一致率达标才启用，交换顺序消位置偏差，运行期人工抽检防漂移**。
- 指标体系三层：**客观指标、主观指标、工程指标**；用“北极星 + 护栏”组合，质量不能以成本和安全为代价。
- 生产标配：**结构化日志 + trace + 监控告警 + bad case 回流**，且埋点从第一行代码开始。
- 核心原则：**先量化，再优化；先评估，再上线**；评估驱动开发 = 改一个变量、跑评估、对比、保留提升、回滚退化。
- 这些能力直接支撑：2.9 Agent 评估与安全、3.4 可观测性与追踪、3.5 评估体系与实验管理（并在 3.9 CI/CD 中作为回归门禁复用）。
