## 1. 定位

S1 应用层收官知识点，回答关键问题：**如何量化效果与定位问题？**

前五个锚点把应用搭起来——1.1 选型、1.1b 参数、1.2 提示、1.3 结构化、1.5 上下文——本锚点回答「怎么知道它变好了还是变坏了」。评估与可观测是 LLM 应用从 demo 走向生产的分水岭：没有金标集，每次改提示词都是赌博；没有 trace，线上 bad case 只能靠猜。

它是 1.7 成本与安全的认知前置，也是 2.9 RAG 评估、3.4 可观测性、3.5 评估体系的入门层。0.6b 讲过「改 prompt 要评测」，本篇把「评测」从一句话纪律变成一套可落地的工具链。

## 2. 一句话定义

LLM 应用评估是「建金标集 + 定指标 + 每次改动必跑」的回归测试纪律；主观维度用 LLM-as-Judge（让一个更强的模型按评分标准当裁判）量化，但裁判有系统性偏差，必须与人工标注校准后采信；可观测性用 trace（调用链）、日志与成本归因回答「线上到底发生了什么、钱花在哪、错出在哪一步」。

## 3. 为什么需要

LLM 输出不确定，「改一版感觉更好」不可信，原因有三：

1. **安慰剂效应**。改的人期待变好，就会看出变好——「我觉得好了」是工程里最危险的一句话。
2. **提示词是全局变量**。改一句可能救了 A 场景、毁了 B 场景——不跑全集根本看不见回归。
3. **无法归因**。没有指标与 trace，线上出错时分不清是检索没召回、生成跑偏还是参数填错。

「新药临床试验」类比：自己喝一口感觉「好像更有劲」不算数——那是安慰剂效应。临床试验的做法是固定一批病例（金标集）、规定疗效判定标准（rubric，评分标准）、给药前后各测一遍（基线 vs 改版对比）。LLM 应用同理。

## 4. 核心原理

### 4.1 金标集构建（20-200 条）

金标集（golden set，评测集）是版本化的固定测试用例集合，评估的地基。规模经验值 **20-200 条**：太小抓不住回归（漏检风险高），太大每轮跑不动（迭代变慢）。起步 30-50 条即可开跑，随业务长大。

| 用例类型 | 占比建议 | 示例 |
|---|---|---|
| 主流程用例 | 约 60% | 常规退货咨询、常规字段抽取 |
| 边界用例 | 约 20% | 超长输入、字段缺失、枚举外取值 |
| 历史坏例 | 约 20% | 线上翻过车的 case 沉淀入库 |
| 对抗用例 | 按需 | 提示注入、诱导话术（与 1.2b、4.8 呼应） |

构建要点：

- 每条含：输入、期望（精确答案/字段断言/评分标准）、标签（场景/难度/来源）。
- 与代码一起版本化管理（git 或评测平台），坏例只增不删。
- 覆盖度优先于数量：先保证主要场景与历史翻车点都有代表。

### 4.2 客观指标 vs 主观指标

| 维度 | 判定方式 | 指标示例 | 工具 |
|---|---|---|---|
| 客观（有标准答案） | 代码精确判 | 字段抽取准确率、格式合法率、必含关键词、正则命中、引用页码正确 | 断言/单测式脚本 |
| 主观（无标准答案） | LLM-as-Judge 打分 | 相关性、语气、忠实度、可读性、完整性 | 裁判模型 + rubric |
| 业务结果 | 线上统计 | 解决率、复问率、转人工率、采纳率 | 数据仓库 |

分层原则：**能代码判的绝不请裁判，能裁判的绝不只靠人肉**；客观层先行——客观分不过关的版本，主观分没有意义。

忠实度（faithfulness，答案是否基于给定资料）处于中间地带：RAG 场景用「答案中每个断言能否被引用支撑」的规则加 judge 混合判定，专用工具链在 2.9（RAGAS）展开。

### 4.3 LLM-as-Judge：绝对打分 vs 两两对比

| 方式 | 做法 | 优点 | 风险 | 适用 |
|---|---|---|---|---|
| 绝对打分 | 按 rubric 逐条给 1-5 分 | 可跟踪趋势、可设阈值 | 打分偏松、分数飘、区分度差 | 版本间趋势监控 |
| 两两对比（pairwise） | 只答「A 好 or B 好」 | 相对判断更稳、更符合模型能力 | 位置偏差：偏爱先出场 | 版本 A/B 定胜负 |

pairwise 的标准姿势：**同一对回答交换顺序各判一次，两次结论一致才算数**——用对称性对冲位置偏差；两次不一致记平局。

rubric 前置是打分质量的第一决定因素：维度拆细（相关性/忠实度/语气各一票）、每档给锚点描述（5 分=完全正确且引用规范；3 分=正确但漏引用）、要求先给理由再给分、输出结构化 JSON 便于统计。

### 4.4 裁判的三种偏差

| 偏差 | 表现 | 缓解 |
|---|---|---|
| 位置偏差（position bias） | 偏爱先出场的答案 | pairwise 交换顺序测两遍 |
| 冗长偏差（verbosity bias） | 偏爱更长的答案，即使没多说信息 | rubric 写明「以信息量而非长度计分」 |
| 自我偏好（self-preference） | 偏爱与裁判自身风格一致的输出 | 换异源裁判模型、人工抽检 |

工程含义：裁判分数是「带系统误差的测量仪器读数」——不校准直接用于发版决策，等于用没对零的秤称重。

### 4.5 人工校准与漂移

裁判采信流程：

```text
抽 20-50 条裁判已打分的样本 → 人工独立打分 → 算一致率（一致比例或秩相关）
→ 一致率 ≥ 80%：采信裁判；不足：先修 rubric 再下结论
→ 换裁判模型 / 改 rubric / 模型服务端升级后：重新校准（judge 会 drift）
```

校准不是一次性动作：裁判模型升级、rubric 改动、业务口径变化都会让旧校准失效。把「一致率」本身做成一个持续要盯的指标。

### 4.6 线上指标

离线金标集管「发版前有没有变坏」，线上指标管「真实用户买不买账」：

| 指标 | 定义 | 信号含义 |
|---|---|---|
| 解决率 | 无需转人工或复问即终结的会话占比 | 核心业务指标 |
| 复问率 | 用户对同一问题换说法重问的比例 | 回答没说到点上的强信号 |
| 转人工率 | 会话升级人工的比例 | 异常升高=系统性退化 |
| 负反馈率 | 点踩/差评占比 | 快速但稀疏 |
| 采纳率 | 生成内容被用户采用的比例（写作/代码类） | 最接近真实价值 |

灰度发布是两层之间的桥：评测过关先放 10% 流量，观察一周线上失败率与复问率，无回归再全量。

### 4.7 可观测入门：trace / 日志 / 成本归因

可观测性回答三个问题：**发生了什么、为什么错、钱花在哪**。

- **Trace（调用链）**：一次请求的全部环节——检索了什么、拼了什么上下文、调了哪个模型、参数多少、返回什么。LLM 应用特有的「软故障」（不报错但跑偏）只有 trace 能定位。工具：LangSmith、Langfuse、OpenTelemetry 语义约定。
- **结构化日志**：每轮记录输入摘要、输出摘要、模型、参数、token 数、耗时、工具调用与结果；脱敏后落库。
- **成本归因**：按用户/场景/版本/模型维度聚合 token 与费用。账单爆炸时能定位到「哪个场景哪个版本在烧钱」，而不是对着总账单发呆。

三件套的最小实现：请求入口生成 trace_id，贯穿检索→组装→生成→校验各环节，日志全带 trace_id——出问题一键还原完整链路。体系化在 3.4 深化。

### 4.8 评测驱动迭代纪律

```text
改动（prompt/模型/参数/检索）= 一次发版
→ 冻结基线分数 → 跑金标集 → 分数 + 坏例分析
→ 主观维度 judge 打分（已校准）→ 通过阈值 → 灰度 → 全量
→ 任一环倒退：分析 → 迭代 → 重跑；上线后回流的 bad case 入金标集
```

三条铁律：

1. **没跑评测的改动不上线**——哪怕「就改了一个词」。
2. **倒退即回滚**——新版本整体更好但关键用例倒退超阈值，先回滚再研究。
3. **bad case 入集**——线上每翻一次车，金标集多一条免疫记录，评估集随业务一起进化。

## 5. 架构 / 流程

评估与可观测的闭环：

```text
                ┌────────────────────────────┐
                │       金标集（版本化）        │
                │ 主流程+边界+历史坏例 20-200 条 │
                └────────────┬───────────────┘
                             ↓ 每次改动必跑
┌───────────────┐   ┌────────────────────────────┐
│ 客观层：代码断言 │ → │ 分数报表（版本对比、回归标红）  │
│ 主观层：Judge   │ → │ 校准：人工抽检 20-50 条对一致率 │
└───────────────┘   └────────────┬───────────────┘
                             ↓ 阈值判定
      通过 → 灰度 10% → 线上指标（解决率/复问率）→ 全量
                             ↓
┌────────────────────────────────────────────┐
│ 线上可观测：trace_id 贯穿 检索→组装→生成→校验  │
│ 结构化日志 + 成本归因（按用户/场景/版本聚合）   │
└────────────────────────────────────────────┘
                             ↓ 线上 bad case
               回流入金标集（免疫记录 +1）
```

## 6. 代码 / 工具

### 6.1 金标集评测脚本（客观断言 + 可选 judge）

```python
import json, re
from dataclasses import dataclass
from openai import OpenAI

client = OpenAI(api_key="YOUR_KEY")

@dataclass
class Case:
    qid: str
    input: str
    expect_contains: list[str]     # 必含关键词
    expect_regex: str | None       # 可选格式断言
    tags: list[str]

def load_golden(path="golden_set.jsonl") -> list[Case]:
    cases = []
    for line in open(path, encoding="utf-8"):
        d = json.loads(line)
        cases.append(Case(d["qid"], d["input"], d.get("expect_contains", []),
                          d.get("expect_regex"), d.get("tags", [])))
    return cases

RUBRIC = """5=完全正确、引用规范、无编造；4=正确但有小瑕疵；
3=基本正确但漏关键信息或漏引用；2=部分正确且有事实错误；1=答非所问或编造。"""

def judge(query: str, answer: str, rubric: str) -> dict:
    """主观维度裁判：先理由后分数，输出 JSON 便于统计。"""
    prompt = f"""你是严格的评测员，按评分标准独立打分。
评分标准：
{rubric}
只依据标准打分，不受答案长度影响，长的答案不加分。
输出 JSON：{{"reason": "一句话理由", "score": 1-5}}
用户问题：{query}
待评回答：{answer}"""
    resp = client.chat.completions.create(
        model="gpt-4o", messages=[{"role": "user", "content": prompt}],
        temperature=0, response_format={"type": "json_object"})
    return json.loads(resp.choices[0].message.content)

def evaluate(cases: list[Case], pipeline, use_judge=False) -> dict:
    scores = []
    for c in cases:
        answer = pipeline(c.input)
        hard_ok = all(k in answer for k in c.expect_contains) and \
                  (c.expect_regex is None or re.search(c.expect_regex, answer))
        soft = judge(c.input, answer, RUBRIC) if use_judge else None
        scores.append({"qid": c.qid, "hard_pass": hard_ok,
                       "judge": soft["score"] if soft else None})
    hard_rate = sum(s["hard_pass"] for s in scores) / len(scores)
    judged = [s["judge"] for s in scores if s["judge"]]
    j_avg = sum(judged) / max(1, len(judged))
    return {"hard_pass_rate": round(hard_rate, 3), "judge_avg": round(j_avg, 2)}

# 纪律：每次改 prompt / 换模型 / 调参数后跑一遍，分数说话
cases = load_golden()
print(evaluate(cases, pipeline=my_rag_pipeline, use_judge=True))
```

### 6.2 两两对比 Judge 模板（交换顺序对冲位置偏差）

```text
模板（pairwise judge，同一对回答跑两遍）：
  你是评测裁判。给定用户问题与两份回答 A、B，只依据以下标准判断哪份更好：
  rubric：忠实度（是否只基于给定资料）> 完整性 > 简洁。
  以信息量计分，不因长度加分。
  输出 JSON：{"winner": "A"|"B"|"tie", "reason": "一句话理由"}
  第一遍：按给定 A/B 顺序判。
  第二遍：同一对回答交换 A/B 位置再判一次。

汇总口径：
  两次 winner 指向同一份回答 → 该回答胜；不一致 → 记 tie（位置偏差改判无效）
  胜率 = 新版胜场 / (胜 + 负场次)，tie 不计
  发版判定：胜率 ≥ 60% 且金标集关键用例无倒退 → 新版可灰度
```

## 7. 案例

### 案例 A：换便宜模型的换版决策

**场景**：一家合同抽取 SaaS 老板要求把模型换成更便宜的新模型。  
**做法**：冻结旧模型基线（字段准确率 96.2%、单次成本 0.004 美元）；新模型跑同一金标集（120 条，含 30 条历史坏例）；阈值写死——关键字段（金额/日期/违约条款）倒退超 2 个百分点一票否决；主观维度 judge 打分并抽 30 条与人工对齐，一致率 87% 采信。  
**结果**：新模型金额字段准确率倒退 3.1 个百分点，触发一票否决；改用「普通条款用新模型、关键字段用旧模型」的路由方案，成本降 38% 且基线不破。

### 案例 B：Judge 校准救了一次错误发版

**场景**：某客服团队用 judge 给两个版本打分，新版平均 4.3 对旧版 4.1，准备全量。  
**发现**：抽 30 条人工复核发现一致率只有 61%——裁判把更长但答非所问的回答打了高分（冗长偏差）。  
**修正**：rubric 加「以信息量而非长度计分」并拆维度重打，新版掉到 3.8；交换顺序复测后维持 3.8。旧版继续在线。  
**教训**：裁判未校准的分数不能作为发版依据。

### 案例 C：成本归因定位账单爆炸

**场景**：某知识库问答产品月账单环比涨 2.7 倍，业务量只涨 20%。  
**做法**：按场景/版本聚合 token 成本，trace 显示某次「优化」误改配置，让单次请求召回块从 5 个膨胀到 40 个；叠加 lost in the middle，成本涨的同时回答质量同步下滑（回看 1.5）。  
**修复**：修配置 + 上单请求 token 上限护栏；月成本回落，解决率回升 6 个百分点。  
**要点**：没有按维度归因，这口锅会背在「模型变贵」上。

## 8. 常见坑

1. **「试了三个问题都更好」就上线**。三个样本既漏回归也可能只是运气；改动必跑金标集。
2. **金标集只有主流程用例**。边界与历史坏例缺席，回归恰好发生在没覆盖的地方。
3. **坏例修完就删**。历史坏例是免疫记录，只增不删。
4. **让模型自己评自己**。没有外部锚点，等于没有评估。
5. **judge 不写 rubric 直接打分**。标准不前置，分数没有可比性。
6. **pairwise 固定顺序**。放大位置偏差；同一对必须交换顺序测两遍。
7. **judge 分数直接信**。偏松、飘、有三种系统偏差；先抽 20-50 条与人工对一致率。
8. **换裁判模型不重新校准**。judge 会 drift，旧校准随换模型失效。
9. **只做离线评测不做灰度**。离线过了也可能在线翻车，10% 灰度观察一周是标配。
10. **只盯平均分不看分布**。平均分掩盖关键用例倒退；逐条对比加关键字段一票否决。
11. **日志没有 trace_id**。bad case 无法还原链路，复盘只能靠猜。
12. **成本只看总账单**。不按场景/版本归因，爆炸源头找不到。
13. **评估集一成不变**。业务变了集没变，分数再高也与线上表现脱节。

## 10. 小结

- **金标集 20-200 条**：主流程+边界+历史坏例，版本化、只增不删，是评估的地基。
- **改动=发版**：换提示词/换模型/调参数必跑评测，分数说话；「我觉得好了」最危险。
- **指标分层**：客观代码判、主观 judge 判、业务线上看；能代码判的不请裁判。
- **Judge 两式**：绝对打分看趋势（偏松）、两两对比定胜负（更稳）；pairwise 必须交换顺序。
- **三种偏差**：位置、冗长、自我偏好；rubric 前置 + 交换顺序 + 异源裁判缓解。
- **校准纪律**：抽 20-50 条与人工对一致率，达到约 80% 才采信；换裁判或 rubric 后重新校准。
- **线上指标**：解决率、复问率、转人工率、采纳率；离线把关 + 灰度验证 + 全量。
- **可观测三件套**：trace（还原链路）、结构化日志、成本归因（按场景/版本聚合）。
- **迭代闭环**：bad case 回流金标集，评估集随业务进化。
