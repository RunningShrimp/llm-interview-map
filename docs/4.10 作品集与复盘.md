# 讲解 4.10 作品集与复盘

> 说明：前置 4.1–4.9 完成了从单 Agent 原型（4.1）到部署运维（4.9）的九类实战项目。  
> 4.10 是实战层的收尾，也是**从“会做”到“能证明自己会做”的关键一步**：把项目整理成可展示、可复现、可讲述的作品集，并通过复盘把经验沉淀成可复用的方法论。  
> 这套方法与模板将在 5.7 阶段 6 综合项目与作品中完整落地。

---

## 1. 定位

实战层第 10 个知识点，属于“能力沉淀与表达”。  
它回答本锚点的核心问题：**如何让别人相信我能做？**

答案是一条证据链。别人无法验证你的能力，只能验证你的证据：

```text
可运行代码（证明做过） + 量化指标（证明有效）
+ 架构图与选型理由（证明想清楚） + 复盘叙事（证明深度）
= 可信的能力证明
```

面试视角下，这条证据链落在两件事上：用 STAR 法则（Situation-Task-Action-Result，情境-任务-行动-结果）组织项目讲述，以及扛住面试官的逐层追问（深挖防御），见 4.1。

与 5.7 的分工：**本篇讲作品集与复盘的方法论、模板和自测法；5.7 是综合项目的实战阶段规划**——用本篇的方法端到端做一个生产级项目。前置：4.1–4.9；后续：5.7。

## 2. 一句话定义

作品集（Portfolio）与复盘（Retrospective），是把 Agent 项目的目标、架构、技术选型、指标、踩坑、改进整理成可展示、可复现、可讲述的文档与代码，并通过系统复盘把经验提炼为可复用方法论的过程。

简化公式：

```text
作品 = 可运行的代码 + 清晰的文档 + 量化的指标 + 可讲述的故事
复盘 = 目标回顾 + 结果对比 + 原因分析 + 经验提炼 + 下一步行动
```

## 3. 为什么需要

不做作品集与复盘，4.1–4.9 的九个项目等于白做：

- **面试讲不清**：做过但说不明白，面试官两句追问就判断为“没做过”。
- **无法复现**：过几个月连自己都忘了怎么跑起来。
- **经验流失**：踩过的坑，下一个项目再踩一遍。
- **无法对比**：没有基线，不知道哪个方案更好、优化有没有效果。
- **无法演进**：不知道进步在哪，能力停在原地。
- **团队无法复用**：项目做完就烂尾，同事只能重做一遍。
- **作品零散**：六个仓库没有一个完整的故事线。
- **能力无法证明**：说“我会做 Agent”，但拿不出任何证据。

**对比**：

| 维度 | 不做作品集与复盘 | 做了作品集与复盘 |
|---|---|---|
| 面试 | STAR 展开到一半被追问穿 | 指标、权衡、踩坑信手拈来 |
| 复现 | clone 下来跑不起来 | 一键脚本，README 五分钟上手 |
| 经验 | 同一个坑踩第二遍 | 坑记录一次，之后永久绕行 |
| 迭代 | “感觉变好了” | 前后基线对比，效果量化 |
| 影响 | 项目烂尾在硬盘里 | 文章、分享、简历持续放大 |

**类比 1**：

```text
做项目 = 造了一辆车
作品集 = 拍好照片、写好说明书、录好试驾视频
复盘   = 分析油耗、故障、改进点，下次造更好的车
```

## 4. 核心原理

### 4.1 证据链：能力如何被证明

“如何让别人相信我能做”的正面回答是分层证据。声明不可信，证据才可信：

| 层级 | 证据 | 证明什么 | 面试官如何验证 |
|---|---|---|---|
| L0 声明 | 简历写“熟悉 Agent 开发” | 什么都证明不了 | 一句追问即穿 |
| L1 代码 | 可运行仓库 + 一键脚本 | 真的做过 | clone 下来跑一遍 |
| L2 指标 | 成功率 / 延迟 / 成本 / 安全基线 | 真的有效 | 追问数字的口径与来源 |
| L3 架构图 + 设计决策 | 分层、数据流、选型理由 | 真的想清楚了 | “删掉这层会坏什么” |
| L4 复盘叙事 | 目标 vs 结果、踩坑、教训 | 有深度、在成长 | 按 STAR 逐层深挖 |

作品集的工程，就是把每个项目从 L0 做到 L4。

**面试高频问法 1**：“讲讲你的项目”怎么组织？共识口径：一句话定位（做什么、给谁用）→ STAR 展开（背景约束 → 你的任务 → 关键行动 → 量化结果）→ 主动交出权衡与踩坑。最后一步最重要：先自己说出每个选型的代价，别等面试官追问。面试官验证项目真实性的方式就是逐层追问——背景是真实约束还是自己想象的？行动是你做的还是团队做的？结果有没有数字支撑？

**面试高频问法 2**：“如果把你的 XX 层去掉，系统会坏在哪？”这是检验权衡表达的经典深挖。讲前自测：对架构里的每个组件问一句“删掉它会坏什么”；答不上来，说明它只是组件堆砌，会被读作背题。

**类比 2**：一家餐厅证明厨艺，靠的不是招牌上写“本店大厨水平很高”，而是端得上桌的菜（可运行代码）、菜谱和食材溯源（文档与架构图）、食客与评审的打分（量化指标）、以及后厨的复盘笔记（这盘咸了、下次放几分盐）。

### 4.2 作品集的核心要素

每个项目按八项要素整理，缺一项就掉一层可信度：

| 要素 | 说明 | 对应章节 |
|---|---|---|
| 问题定义 | 解决什么问题，给谁用，为什么需要 Agent | 4.1–4.7 |
| 架构设计 | 分层、组件、数据流 | 3.1 |
| 技术选型 | 为什么选这个模型 / 框架 / 工具，代价是什么 | 3.3 |
| 关键指标 | 成功率、延迟、成本、安全 | 3.5、4.8 |
| 踩坑与改进 | 遇到什么问题，怎么解决 | 4.1–4.9 |
| 可运行代码 | README + 一键运行 | 3.9 |
| 演示 | 截图、视频、在线 Demo | — |
| 复盘 | 目标 vs 结果，经验提炼 | 4.10 |

### 4.3 作品集的结构

一个作品集仓库的推荐结构（六个项目分别对应 4.1–4.7 的实战类型）：

```text
agent-portfolio/
├── README.md                    # 总览：故事线 + 项目索引 + 指标速览
├── projects/
│   ├── 01-order-agent/          # 单 Agent 原型（4.1）
│   │   ├── README.md
│   │   ├── src/
│   │   ├── eval/
│   │   ├── docs/
│   │   │   ├── architecture.md      # 架构图 + 数据流
│   │   │   ├── design-decisions.md  # 选型理由 + 代价
│   │   │   ├── metrics.md           # 量化指标 + 口径
│   │   │   └── retrospective.md     # 复盘
│   │   └── demo/
│   ├── 02-rag-agent/            # 检索增强生成（RAG）知识库（4.2）
│   ├── 03-data-agent/           # 数据分析（4.3）
│   ├── 04-browser-agent/        # 浏览器 / 计算机使用（4.4）
│   ├── 05-workflow-agent/       # 工作流自动化（4.5）
│   └── 06-multi-agent/          # 多 Agent 协作 + 平台（4.6、4.7）
├── blog/                        # 技术文章
├── talks/                       # 分享材料
└── resume/                      # 简历项目描述
```

顶层 README 用一条故事线把六个项目串起来：从单 Agent 原型，到 RAG、工具增强，再到多 Agent 与平台化——每个项目解决上一代方案留下的问题。

### 4.4 量化指标体系

每个项目必须有量化指标，没有数字的“效果不错”等于没有效果：

| 类别 | 指标 |
|---|---|
| 功能 | 任务成功率、工具准确率、答案准确率 |
| 性能 | P50/P95/P99 延迟、TTFT（Time To First Token，首字延迟）、吞吐 |
| 成本 | 单次成本、日成本、成本归因 |
| 安全 | 红队（Red Team）通过率、越权拦截率、注入抵抗率（红队方法见 4.8） |
| 质量 | 忠实度、相关性、用户满意度 |
| 效率 | 平均步数、缓存命中率 |

**指标呈现的好坏对比**：

| 差的写法 | 问题 | 好的写法 |
|---|---|---|
| “效果不错” | 无法证伪 | “答案准确率 60% → 85%（200 题评估集）” |
| “延迟很低” | 没有口径 | “P95 延迟 4.2s（1000 次采样）” |
| “成本很低” | 没有单位 | “单次成本 $0.008，日成本 $24（日均 3000 次）” |
| “很安全” | 没有边界 | “红队 120 条用例拦截 118 条，漏掉的 2 条已修复并回归” |

**对比基线**（没有对比的指标是孤例，有了基线才是证据）：

```text
单 Agent vs 多 Agent
纯向量检索 vs 混合检索
大模型 vs 小模型（同任务成本/质量对比）
优化前 vs 优化后
```

### 4.5 复盘框架：KPT / STAR / GRAI

三个框架一张表选清楚：

| 框架 | 步骤 | 适用场景 |
|---|---|---|
| KPT | Keep（保持）/ Problem（问题）/ Try（尝试） | 技术项目迭代，**推荐默认** |
| STAR | Situation（情境）/ Task（任务）/ Action（行动）/ Result（结果） | 面试叙事、简历描述 |
| GRAI | Goal（目标）/ Result（结果）/ Analysis（分析）/ Insight（洞察） | 深度根因分析 |

**推荐**：技术项目用 KPT + 指标对比（模板见 6.3）；STAR 留给面试和简历；GRAI 用于重大失败后的一次性深挖。

### 4.6 复盘的八个核心问题

无论用哪个框架，复盘都要能回答这八问：

```text
1. 目标是什么？达成了吗？
2. 关键指标是多少？和预期差多少？
3. 哪些做对了？为什么对？
4. 哪些做错了？为什么错？
5. 最大的坑是什么？怎么解决的？
6. 如果重做，会怎么改？
7. 有什么可复用的经验？
8. 下一步做什么？
```

### 4.7 演示材料与技术文章

**截图**（成本最低，优先做全）：

- 架构图与数据流图
- 交互界面
- Trace 调用链（可观测性见 3.4）
- 监控 Dashboard
- 评估报告

**视频**：2–3 分钟 Demo，展示核心流程，突出一个亮点（如高风险操作的人工审批）。

**在线 Demo**：Hugging Face Spaces、Streamlit Cloud 或自建 Demo 站，让面试官无需环境就能点开。

**技术文章**：把项目写成文章是放大器，结构固定为：

```text
标题：如何构建一个生产级 XXX Agent

1. 问题背景（谁有痛点，现状如何）
2. 方案设计（架构 + 选型理由）
3. 关键技术点（2–3 个，讲透）
4. 踩坑与解决（最有含金量的部分）
5. 效果数据（前后对比）
6. 经验总结（可复用的结论）
```

发布渠道：个人博客、掘金 / 知乎 / Medium、GitHub README、技术社区。

### 4.8 简历项目描述

简历是作品集的压缩版，用 STAR + 量化成果：

```text
项目名：电商客服 Agent 平台
角色：核心开发
时间：2024.01–2024.06

背景（S/T）：客服团队每天处理 5000+ 咨询，人工成本高，
目标把可自动解决的比例提到 70% 以上。

行动（A）：
- 基于 LangGraph + GPT-4o 构建多 Agent 客服系统
- 集成 RAG 知识库（混合检索 + 重排（Rerank））
- 实现工具调用（查订单、退款、转人工）
- 高风险操作人工审批 + 全链路审计

结果（R）：
- 自动解决率 75%，人工成本降低 40%
- P95 延迟 4.2s，单次成本 $0.008
- 红队通过率 98%，零数据泄露
```

写完做 4.1 的“删掉这层会坏什么”自测，确保每个技术点都经得起追问。

### 4.9 复盘驱动成长

复盘的价值不在单个项目，在跨项目的复利：

```text
项目 1 → 复盘 → 经验 1
项目 2 → 复盘 → 经验 2
项目 3 → 复盘 → 经验 3
         ↓
    方法论沉淀
         ↓
    下一个项目更好
```

**经验分类**（复盘产出按这五类归档）：

| 类型 | 例子 |
|---|---|
| 技术经验 | RAG 切分 512 token 是好的起点 |
| 工程经验 | 工具必须幂等（Idempotency），否则重试会重复下单 |
| 产品经验 | 用户更在意回答是否带引用来源 |
| 团队经验 | 评估集要和业务方共建 |
| 踩坑经验 | 提示词（Prompt）改动必须跑回归评估 |

```text

└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  整理代码                                 │

└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  整理文档                                 │
│  ├─ 架构图                               │

└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  复盘                                     │
│  ├─ 目标 vs 结果                         │
```

关键点：这条流水线是**边做边走**的，不是项目结束后一次性补——踩坑当场记录、指标当次评估就存档，最后一周只做组装。

### 6.1 项目 README 模板（可复制）

每个项目的 README 都用同一个骨架，保证任何人 10 分钟能看懂、能跑通：

```markdown

## 一句话介绍

- 现在怎么解决的？
- 为什么需要 Agent？
```

### 6.2 一键运行脚本

别人 clone 后能不能跑起来，是 L1 证据的分界线：

```bash
#!/bin/bash
# run.sh —— 一键运行，任何环节失败立即退出
set -e

echo "=== Agent 项目一键运行 ==="

# 1. 检查依赖
if ! command -v python &> /dev/null; then
    echo "请安装 Python 3.11+"
    exit 1
fi

# 2. 创建虚拟环境（已存在则复用）
if [ ! -d "venv" ]; then
    python -m venv venv
fi
source venv/bin/activate

# 3. 安装依赖
pip install -r requirements.txt

# 4. 检查配置
if [ ! -f ".env" ]; then
    cp .env.example .env
    echo "请编辑 .env 填入 API Key"
    exit 1
fi

# 5. 索引知识库（RAG 项目需要）
python -m src.rag.indexer

# 6. 跑冒烟评估，确认环境正常
python -m eval.smoke

# 7. 启动
python -m src.main
```

### 6.3 复盘模板（可复制）

复盘文档固定放 `docs/retrospective.md`，用 KPT + 指标对比：

```markdown
# 项目复盘：XXX Agent

## 1. 目标回顾
- 原目标：XXX
- 成功标准：XXX

## 2. 结果对比
| 指标 | 目标 | 实际 | 差距 |
|---|---|---|---|
| 任务成功率 | 90% | 92% | +2% |
| P95 延迟 | 10s | 8.5s | -1.5s |
| 单次成本 | $0.01 | $0.008 | -20% |

## 3. 做得好的（Keep）
- 混合检索 + Rerank 显著提升召回
- 幂等设计避免了重复退款
- 全链路 Trace 让问题定位很快

## 4. 遇到的问题（Problem）
- 切分策略调了 5 次才找到最优
- 多轮对话查询重写效果不稳定
- 成本初期超预算 3 倍

## 5. 下次改进（Try）
- 一开始就建评估集，用数据驱动切分
- 查询重写加 Few-shot 示例 + 验证器
- 上线前先做成本模拟

## 6. 关键经验（进入个人经验库）
- RAG 切分 512 token + 10% overlap 是好的起点
- 工具必须幂等，否则重试会出事故
- 评估集是迭代的基础设施
```

```python
    """生成达标状态：mode='gt' 越大越好，mode='lt' 越小越好。"""
    ok = actual > target if mode == "gt" else actual < target
    return "达标" if ok else "未达标"
```

## 8. 常见坑

1. **不做作品集**。  
   做过但说不清，等于没做过。项目完成一周内启动整理。

2. **README 太简单**。  
   只有“怎么运行”，没有问题、方案、指标。用 6.1 模板补全。

3. **没有量化指标**。  
   说“效果不错”但没有数据。每个项目至少给出功能、性能、成本、安全各一项。

4. **指标没有口径**。  
   只写数字不写评估集大小、采样方式、对比基线。每个数字标注口径。

5. **不做复盘**。  
   踩过的坑再踩一遍。项目结束 48 小时内完成复盘，趁记忆新鲜。

6. **复盘太笼统**。  
   “做得不错，继续努力”没有价值。用 4.6 八问逐条回答，落到具体事。

7. **不记录踩坑**。  
   过几个月自己都忘了。边做边记，issue 或日志形式均可。

8. **不做演示**。  
   别人不知道怎么用。至少给截图，最好有 2 分钟视频。

9. **代码不可运行**。  
   别人 clone 下来跑不起来。提供 6.2 的一键运行脚本并实际测一遍。

10. **被深挖就穿**。  
    只会背架构，答不上“删掉这层会坏什么”。讲前对每个组件做删层自测。

11. **不写文章**。  
    经验只在自己脑子里。每个拿得出手的项目写一篇，影响力放大十倍。

12. **简历堆技术名词**。  
    没有背景、行动、成果。用 STAR + 量化数字。

13. **作品零散**。  
    六个仓库没有一个故事线。按 4.3 结构组装，顶层 README 串联。

14. **忽略失败项目**。  
    失败的经验同样宝贵。记录失败原因与教训，面试中反而是加分项。

15. **不做版本管理**。  
    代码散乱、无演进历史。Git + 清晰 commit message（见 3.9）。

16. **不更新作品集**。  
    做完就放着。每完成一个迭代或复盘，同步更新指标与文章。

17. **不做分享**。  
    经验不传播就不产生影响力。做一次内部分享或社区分享。

18. **忽略可复现性**。  
    别人无法验证你的数字。提供评估集样例、配置、脚本，让结论可复跑。

## 9. 练习

1. 为 4.1 的订单 Agent 写完整 README（用 6.1 模板）。验收：同伴 clone 后 10 分钟内跑通。
2. 为 4.2 的 RAG Agent 画架构图与数据流图。验收：不看代码能讲清一次请求的完整路径。

5. 为 4.5 的工作流 Agent 写复盘文档（用 6.3 模板）。验收：4.6 八问全部有具体回答。
6. 为 4.6 的多 Agent 系统写一篇技术文章。验收：含至少 2 个“关键决策 + 代价”。

## 10. 小结

- 作品 = **可运行的代码 + 清晰的文档 + 量化的指标 + 可讲述的故事**。
- 证据链回答“如何让别人相信我能做”：声明不可信，**代码 → 指标 → 架构图 → 复盘**才可信。
- 作品集要素：**问题、方案、选型、指标、踩坑、复盘**，逐层对应 L1–L4 证据。
- README 模板：**一句话介绍、背景、方案、指标、亮点、踩坑、运行、演示、复盘**。
- 复盘框架：**KPT（项目迭代）、STAR（面试叙事）、GRAI（根因分析）**。
- 复盘八问：**目标达成吗？指标差多少？做对什么？做错什么？下次怎么改？**
- 量化指标：**功能、性能、成本、安全、质量、效率**，每个数字带口径与对比基线。
- 演示材料：**截图、2–3 分钟视频、在线 Demo**。
- 技术文章：**背景 → 方案 → 关键决策 → 踩坑 → 效果 → 经验**。
- 简历描述：**STAR + 量化成果**，讲前做“删掉这层会坏什么”自测。
- 核心原则：**不做作品集等于没做，不做复盘等于白做。**
- 这些能力直接支撑：5.7 阶段 6 综合项目与作品集。
