# 讲解 2.7 单 Agent 架构模式

> 说明：2.1–2.6 依次讲完 Agent 的定义与范式、规划、工具、记忆、执行循环、反思——零件都齐了。  
> 2.7 是 2 层收束篇：把零件**组装成四类可落地的单 Agent 架构模式**（工具型、RAG 型、工作流型、自主型），并正面回答「何时用简单工作流，何时用自主 Agent」。  
> 多 Agent 协作放在 2.8，系统级分层与接口设计放在 3.1，实战组装见 4.1 与 4.5。

---

## 1. 定位

Agent 核心层第 7 个知识点，属于「架构选型与组装」，是 2.1–2.6 六个组件篇的收束。  
它解决一个核心问题：**组件都有了，如何把它们组合成一个可落地、可维护、可扩展的单 Agent 系统？**

锚点关键问题「何时用简单工作流，何时用自主 Agent」的正面回答集中在 4.7（四维决策表 + 决策树）。

它是 2.8 多 Agent 协作、2.9 Agent 评估与安全、3.1 架构与接口设计的直接前置。

## 2. 一句话定义

单 Agent 架构模式，是在明确任务特征、成本约束、可靠性要求的前提下，为「LLM + 工具 + 检索 + 记忆 + 循环 + 反思」这套组件选择组合方式与控制权归属的工程架构范式。

简化公式：

```text
单 Agent = 任务特征 × 组件选择 × 循环形态 × 工程约束
```

控制权归属是关键变量：流程由**代码预定义**（工作流型）还是交给**模型动态决策**（自主型）——2.1 讲的 Agent 与固定工作流的边界，在本篇落地为具体选型。

## 3. 为什么需要

知道所有组件，不等于会组装。选型失败的六种典型：

- **过度设计** → 简单查询也走规划 + 反思，延迟和成本白白翻倍。
- **设计不足** → 固定业务流交给自由循环，步骤漂移、无法验收。
- **组件不匹配** → 有记忆不读写、有工具不接，只增加成本不改善决策。
- **无法演进** → 原型直线代码，换模型、加工具都要改主流程。
- **难以调试** → 组件耦合，出问题定位不到是哪一层。
- **无法复用** → 每个 Agent 从头写，重复劳动、质量参差。

| 症状 | 根因 | 后果（示意量级） |
|---|---|---|
| 查天气也跑完整规划-执行-反思 | 过度设计 | 延迟从秒级涨到分钟级，token 成本翻 10 倍 |
| 周报生成全靠自由循环 | 设计不足 | 格式漂移，验收不过率超三成 |
| 记忆组件上线但从不命中 | 组件不匹配 | 只加延迟和存储，决策没变好 |
| 无分层无路由，一条路径服务所有请求 | 无法演进 | 每加一个能力就改一次主流程 |
| 工具调用散落在各节点 | 难以调试 | 故障无法归因到组件 |
| 五个 Agent 五套循环实现 | 无法复用 | 重复劳动，行为不一致 |

**类比一（造车）**：

```text
知道引擎、轮子、方向盘 ≠ 会造车。
家用车、货车、赛车共用同一个零件库，差别在底盘——为什么任务配什么底盘。
Agent 架构模式，就是单 Agent 系统的底盘设计。
```

**类比二（餐厅）**：快档口是工作流型——菜单固定、流程固定，出餐快、可复制，但点不了菜单外的菜；现炒小馆是工具型——师傅按单取料加工，几步出餐；私人大厨是自主型——你只给预算和口味，他自己定菜单、采购、烹饪，能力强但贵、慢，还得有人验收账单。给什么客流配什么店型，就是架构选型。

## 4. 核心原理

### 4.1 从组件到模式：四类架构总览

四类模式不是新机制，而是 2.1–2.6 组件的不同组合方式：

```text
2.1 边界 ─┐
2.2 规划 ─┤   工具型   = LLM + 工具 + 简单循环（循环骨架见 2.5）
2.3 工具 ─┤   RAG 型   = 检索 + 生成 + 可选工具（检索管线见 1.4）
2.4 记忆 ─┼→ 工作流型 = 代码预定义流程 + LLM 节点 + 状态机（见 2.5）
2.5 循环 ─┤   自主型   = 规划（2.2）+ 工具（2.3）+ 记忆（2.4）+ 循环（2.5）+ 反思（2.6）
2.6 反思 ─┘   混合型   = 路由 + 上面四类的组合（生产形态，见 4.9）
```

与推理范式的关系一句话说清：ReAct、Plan-and-Execute、ReWOO、Reflexion（见 2.2、2.6）是**循环内部**的推理范式；本篇四类是**系统层面**的架构模式——推理范式主要决定自主型内部的循环形态，架构模式决定整个系统的控制权归属，两层不要混。截至 2026 年，主流编排框架（如 LangGraph）的官方教程已把 ReAct、Plan-and-Execute 等做成可直接复用的图模板（趋势观察，转述口径），框架细节见 3.3。

### 4.2 模式一：工具型 Agent（Tool-Use Agent）

**结构**：

```text
用户输入
   ↓
LLM 决策（工具调用 / Function Calling）
   ├─ 信息不够 → 调用工具 → 结果回填 → 回到 LLM 决策（循环 1–5 步）
   └─ 信息足够 → 生成最终回答
```

**适用**：客服查单（订单、物流）、信息查询（天气、汇率）、简单计算、单笔 API 操作——**意图明确、一两步工具就能拿到答案**的任务。

**风险**：多步任务短视，走一步看一步（升级路径：自主型）；工具选错与参数幻觉要靠 Schema 校验 + 重试兜底（见 2.3、1.3）；循环不设上限会死循环（终止条件见 2.5）。

参考实现见 6.1 的 ToolAgent。

### 4.3 模式二：RAG 型 Agent

RAG（检索增强生成，Retrieval-Augmented Generation）型 Agent 把「答案从哪来」从模型参数换成了可更新的语料库：

**结构**：

```text
用户输入
   ↓
查询重写（Query Rewriting，可选）
   ↓
混合检索（向量 + BM25）→ 重排（Rerank）取 top 5
   ↓
上下文组装（资料 + 问题）
   ↓
LLM 生成 + 引用
   ↓
（可选）工具补充实时数据
```

**适用**：企业知识库问答、文档助手、客服 FAQ、研究综述——**知识密集、答案在私有语料里**的任务。

**风险**：检索质量决定上限（切分、混合检索、重排的完整管线见 1.4，本篇不重复展开）；需要实时数据或写操作时无解（升级路径：加工具或转混合型）；输出不带引用就无法验收。

参考实现见 6.1 的 RAGAgent。

### 4.4 模式三：工作流型 Agent（Workflow Agent）

**结构**：

```text
用户输入
   ↓
节点 1：意图分类 / 参数抽取（LLM 或规则）
   ↓
条件分支
   ├─ 分支 A → 节点 2A → …
   └─ 分支 B → 节点 2B → …
   ↓
输出（关键节点可挂人工审批）
```

**适用**：客服工单处理、退款审批流、数据 ETL、标准化报告生成——**步骤可枚举、有 SOP、要审计**的业务流程。

**风险**：流程外请求处理不了（要留兜底分支或升级混合型）；业务变更需要改流程定义；节点内的 LLM 仍会参数幻觉，照样要校验（见 1.3）。

LangGraph 编排实现见 6.3。

### 4.5 模式四：自主型 Agent（Autonomous Agent）

**结构**：

```text
目标
   ↓
规划（见 2.2）→ 执行 → 观察 → 反思（见 2.6）
   ↑                          ↓
   └────── 重规划（Replanning）┘（判定计划不可行时回环）
   ↓
循环直到完成，或触发熔断（最大步数 / 预算 / 超时，见 2.5）
   ↓
输出（结果 + 执行轨迹）
```

**适用**：研究助手、复杂数据分析、多步问题求解、跨系统自动化——**路径未知、必须边做边决定下一步**的开放任务。

**风险**：成本高（单任务 token 消耗可达工作流型的 10 倍量级）、延迟高；会跑偏、会死循环，全靠终止条件与反思兜底；错误难归因，必须记录完整轨迹（见 3.4）。内部循环形态按任务选 ReAct（动态环境）或 Plan-and-Execute（长任务防跑偏），选型口径见 2.2。

代码骨架：

```python
async def autonomous_agent(goal: str, max_steps: int = 20, budget: float = 5.0) -> dict:
    state = AgentState(goal=goal, max_steps=max_steps, budget=budget)

    while not should_terminate(state):          # 终止条件：完成/步数/超时/预算，见 2.5
        # 1. 规划：没有计划、或计划被判定不可行时（重新）生成
        if not state.plan:
            state.plan = await plan(goal)

        # 2. 执行当前步骤并记录
        step = state.plan[state.current_step]
        result = await execute_step(step, state)
        state.step_results[step["id"]] = result

        # 3. 反思：判定结果是否可信、计划是否仍可行
        critique = await critique_step(state, step, result)
        if not critique["passed"]:
            if critique["action"] == "replan":  # 错误答案通常意味着错误计划，见 2.2
                state.plan = await replan(state, critique)
                state.current_step = 0
                continue
            if critique["action"] == "retry":
                continue

        state.current_step += 1
        if state.current_step >= len(state.plan):
            break

    return {"result": state.step_results, "steps": state.current_step}
```

### 4.6 四类模式对比

| 维度 | 工具型 | RAG 型 | 工作流型 | 自主型 |
|---|---|---|---|---|
| 控制权 | 模型（短循环） | 代码为主 | 代码（固定流程） | 模型（动态决策） |
| 复杂度 | 低 | 低 | 中 | 高 |
| 成本 | 低 | 中 | 低 | 高 |
| 延迟 | 低 | 中 | 低 | 高 |
| 灵活性 | 中 | 低 | 低 | 高 |
| 可靠性 | 高 | 高 | 高 | 中 |
| 可调试性 | 易 | 易 | 易 | 难 |
| 典型步数 | 1–5 | 1–3 | 固定节点数 | ≤20（须熔断） |
| 适用任务 | 明确查询/操作 | 知识问答 | 标准业务流 | 开放复杂任务 |

为什么自主型的可靠性只有「中」：复合失败率——单步成功率 95% 的组件，8 步串联后端到端只剩约 66%（0.95 的 8 次方，示意量级；社区评估指南多源一致，2026）。步数越多，越需要反思与重规划兜底（见 2.6、2.9）。

**面试高频问法**：「ReAct / Plan-and-Execute / Reflection / Multi-Agent 各自适用什么场景？」（社区题库常见问法，2025）——先按 2.2、2.6 口径答推理范式，再落回本篇：推理范式决定循环内部怎么走，架构模式决定系统控制权在代码还是模型手里；Multi-Agent 是另一个维度（角色分工），见 2.8。

### 4.7 关键问题的正面回答：何时用简单工作流，何时用自主 Agent

四个判据，逐条问自己：

| 判据 | 问自己 | 偏工作流 | 偏自主 Agent |
|---|---|---|---|
| 任务确定性 | 步骤能否事先枚举成 SOP？ | 能枚举、有现成流程 | 路径未知、边做边定 |
| 步数 | 典型任务几步？ | ≤5 步且每步清晰 | 8 步以上、步骤间有依赖 |
| 容错成本 | 一步做错代价多大？ | 高（写操作、资金、不可逆）→ 固定路径 + 审批 | 低（只读探索、可回滚）→ 可放权 |
| 可观测要求 | 审计与合规要求多强？ | 强合规、每步要可审计 | 允许看轨迹复盘即可 |

结论口径：**步骤可枚举 + 容错成本高 → 工作流；路径未知 + 只读为主 → 自主型；两者混杂 → 混合型路由。** 社区与官方博客的共识判据同向：读多写少的任务留在单 Agent 简单架构（LangChain 官方博客《How and when to build multi-agent systems》与 Phil Schmid《Single vs Multi-Agent System?》，2025，转述口径）；重写入、高容错成本的操作一律固定路径加人工审批。

选型决策树：

```text
任务步骤能否事先枚举成 SOP？
├─ 能 → 是否需要外部知识？
│   ├─ 否 → 纯代码工作流（LLM 只用在个别节点）
│   └─ 是 → 工作流 + RAG 节点
└─ 不能 → 需要行动，还是只要答案？
    ├─ 只要答案、知识在库里 → RAG 型（1–3 步）
    ├─ 要行动、步数 ≤5 且路径清晰 → 工具型
    └─ 要行动、步数多且路径未知 → 自主型（规划 + 反思 + 熔断）

任何分支：高风险写操作 → 一律加人工审批（见 3.10）
任务类型混杂 → 混合型路由（见 4.9）
```

**面试高频问法**：「给你一个新业务，你会怎么给 Agent 选架构？什么时候上自主 Agent？」共识口径：不先问「用多强的模型」，先问任务确定性与容错成本——步骤可枚举就固化成工作流；只有路径未知、以只读探索为主的任务才放权自主 Agent；从最简单的架构起步，用基线评估（见 2.9）证明不达标再逐级升级，多 Agent 是最后选项（判据见 2.8）。

### 4.8 组件选择矩阵

不同模式需要哪些组件：

| 组件 | 工具型 | RAG 型 | 工作流型 | 自主型 | 混合型 |
|---|---|---|---|---|---|
| LLM | 必需 | 必需 | 必需 | 必需 | 必需 |
| 工具 | 必需 | 可选 | 必需 | 必需 | 必需 |
| 检索 | 不需要 | 必需 | 可选 | 可选 | 必需 |
| 规划 | 不需要 | 不需要 | 不需要 | 必需 | 必需 |
| 记忆 | 可选 | 可选 | 可选 | 必需 | 可选 |
| 执行循环 | 简单 | 简单 | 不需要（顺序执行） | 复杂 | 按路由而定 |
| 反思 | 不需要 | 不需要 | 不需要 | 必需 | 可选 |
| 状态机 | 不需要 | 不需要 | 必需 | 必需 | 必需 |

读法：只加「必需」的；「可选」等指标证明需要再加（各组件机制见 2.2–2.6 与 1.4，本篇不重复展开）。

### 4.9 混合型 Agent（Hybrid Agent）：四模式的组合形态（生产推荐）

**结构**（工作流骨架 + Agent 节点）：

```text
用户输入
   ↓
复杂度路由（轻量 LLM 分类，见 6.2）
   ├─ FAQ / 知识问答 → RAG 型
   ├─ 查订单 / 查物流 → 工具型
   ├─ 退款 / 审批 → 工作流型（含权限检查）
   ├─ 开放复杂任务 → 自主型（带熔断）
   └─ 高风险 / 低置信度 → 人工
```

特点：分层处理、成本优化（简单任务不陪跑贵路径）、可靠性高（人工兜底）。生产系统的默认形态。

类比（医院分诊台）：护士按病情分诊——感冒去普通门诊（工作流型，量大、流程固定），拍片去检查科（工具型，按单取结果），疑难杂症组织专家会诊（自主型，路径未知），危重走绿色通道直通手术室（人工兜底）。分诊台就是路由器，分错台就是路由错误。

路由实现见 6.2。

### 4.10 架构设计六原则

1. **从简单开始**：先工作流 → 工具型 → RAG 型 → 自主型，每次升级要有指标证据，不达标就退回。
2. **按需引入组件**：需要知识加检索、需要行动加工具、需要多步加规划、需要持久加记忆、需要纠错加反思（对照 4.8 矩阵）。
3. **分层解耦**：接入 / 编排 / 能力 / 基础设施四层分离，跨层只走接口（分层参考架构见 5.2，接口设计见 3.1）。
4. **可观测优先**：每个组件有 trace、每个决策有日志、每次工具调用有记录（见 3.4）。
5. **可降级**：主模型失败降备用模型、检索失败退直接 LLM、工具失败用缓存、Agent 失败转人工（见 3.7）。
6. **可演进**：组件可替换（换模型、换向量库）、流程可配置、提示词（Prompt）可版本化。

## 5. 架构 / 流程

### 5.1 四类模式结构总图

同一个接入层与公共底座，四条执行路径——「组件相同、架构不同」的直观图：

```text
工具型               RAG 型               工作流型              自主型
输入                 输入                 输入                  目标
 ↓                   ↓                    ↓                     ↓
LLM 决策             查询重写（可选）      意图分类/参数抽取      规划（2.2）
 ↓                   ↓                    ↓                     ↓
工具调用 ×1–5 步     检索 + 重排           固定节点 + 条件分支    执行 + 观察（2.5）
 ↓                   ↓                    ↓                     ↓
LLM 汇总回答         上下文组装 + 生成     输出（可挂审批）       反思 + 重规划（2.6）
                     + 引用                                     ↓
                                                            熔断检查 → 输出
─────────────────────────────────────────────────────────────────────
公共底座：记忆（2.4）｜检查点（2.5）｜日志与 trace（3.4）｜降级（3.7）｜预算控制
```

## 6. 代码 / 工具

### 6.1 统一框架：工具型与 RAG 型

```python
import json
from abc import ABC, abstractmethod

class BaseAgent(ABC):
    """所有模式的基类：只注入能力，不绑定流程——流程形态由子类决定。"""
    def __init__(self, llm, tools=None, retriever=None, memory=None):
        self.llm = llm
        self.tools = tools or {}        # 工具注册表：名字 → 异步函数（与 Agent 解耦）
        self.retriever = retriever
        self.memory = memory

    @abstractmethod
    async def run(self, input: str) -> dict:
        ...

class ToolAgent(BaseAgent):
    """工具型：LLM 决策 + 工具调用，简单循环（1–5 步）。"""
    async def run(self, input: str) -> dict:
        messages = [{"role": "user", "content": input}]
        for _ in range(5):                          # 最大步数熔断
            response = await self.llm.chat(messages, tools=self.tools)
            msg = response.choices[0].message
            if not msg.tool_calls:                  # 不再调工具 → 生成最终回答
                return {"answer": msg.content}
            messages.append(msg)
            for tc in msg.tool_calls:               # 执行本轮全部工具调用
                result = await self.tools[tc.function.name](
                    **json.loads(tc.function.arguments))
                messages.append({
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": json.dumps(result, ensure_ascii=False),
                })
        return {"answer": "已达最大步数，转人工。"}

class RAGAgent(BaseAgent):
    """RAG 型：检索 + 生成，带引用输出。"""
    async def run(self, input: str) -> dict:
        docs = await self.retriever.retrieve(input, top_k=5)   # 检索管线见 1.4
        context = "\n".join(f"[{i+1}] {d['content']}" for i, d in enumerate(docs))
        answer = await self.llm.chat([
            {"role": "system", "content": "只根据资料回答，并标注引用编号。"},
            {"role": "user", "content": f"资料：\n{context}\n\n问题：{input}"},
        ])
        return {"answer": answer, "sources": docs}
```

### 6.2 复杂度路由与混合型

```python
ROUTE_PROMPT = """判断任务复杂度，只输出一个词：
- rag：知识问答，查资料就能答
- tool：需要查订单/物流等工具调用，1–3 步内完成
- workflow：标准业务流程（退款、审批）
- complex：开放任务，需要多步规划

任务：{task}
"""

class Router:
    """复杂度路由：轻量模型 + temperature=0，输出限定在受控词表。"""
    def __init__(self, llm):
        self.llm = llm

    async def classify(self, task: str) -> str:
        response = await self.llm.chat(
            [{"role": "user", "content": ROUTE_PROMPT.format(task=task)}],
            temperature=0,
        )
        return response.strip().lower()

class HybridAgent(BaseAgent):
    """混合型：路由分发到各子 Agent，人工兜底。"""
    def __init__(self, *args, router=None, sub_agents=None, **kwargs):
        super().__init__(*args, **kwargs)
        self.router = router
        self.agents = sub_agents

    async def run(self, input: str) -> dict:
        mode = await self.router.classify(input)
        agent = self.agents.get(mode)
        if agent is None:                       # 路由失败或低置信 → 人工兜底
            return {"answer": "", "escalate": "human", "reason": mode}
        return await agent.run(input)
```

### 6.3 工作流型：LangGraph 图编排

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class WorkflowState(TypedDict):
    input: str
    intent: str
    order_id: str
    result: dict

def classify(state: WorkflowState):
    return {"intent": classify_intent(state["input"])}     # LLM 节点：意图分类

def extract_order(state: WorkflowState):
    return {"order_id": extract_order_id(state["input"])}  # LLM 节点：参数抽取

def handle_refund(state: WorkflowState):
    # 写操作：生产上先过权限检查与人工审批（见 3.10）
    return {"result": process_refund(state["order_id"])}

def handle_query(state: WorkflowState):
    return {"result": get_order_detail(state["order_id"])}  # 读操作

def route_by_intent(state: WorkflowState) -> str:
    return state["intent"]

graph = StateGraph(WorkflowState)
graph.add_node("classify", classify)
graph.add_node("extract", extract_order)
graph.add_node("refund", handle_refund)
graph.add_node("query", handle_query)

# 截至 2026 年的推荐写法：显式从 START 连边（set_entry_point 已废弃，与 2.5 口径一致）
graph.add_edge(START, "classify")
graph.add_edge("classify", "extract")
graph.add_conditional_edges("extract", route_by_intent, {
    "refund": "refund",   # 分支 A：退款流程
    "query": "query",     # 分支 B：查询流程
})
graph.add_edge("refund", END)
graph.add_edge("query", END)

app = graph.compile()
```

```python
import yaml

def build_agent(config_path: str) -> BaseAgent:
    """按配置组装 Agent：模式 = 组件组合方式的预设。"""
    config = yaml.safe_load(open(config_path, encoding="utf-8"))["agent"]

    llm = LLMClient(config["llm"])
    tools = load_tools(config["tools"])                       # 从注册表加载
    retriever = (build_retriever(config["rag"])
                 if config["rag"]["enabled"] else None)
    memory = build_memory(config["memory"])

    agents = {
        "rag": RAGAgent(llm, retriever=retriever),
        "tool": ToolAgent(llm, tools),
        # workflow / autonomous 的构建同理
    }
    if config["mode"] == "hybrid":
        return HybridAgent(llm, tools, retriever, memory,
                           router=Router(llm), sub_agents=agents)
    return agents[config["mode"]]
```

## 7. 案例

### 案例 A：客服 Agent 架构选型（某电商，混合型）

**需求**：查订单、查物流、退款、FAQ；退款要权限控制；复杂投诉转人工。

**做法**：混合型。路由分发——FAQ 走 RAG 型（带引用）、查询走工具型、退款走工作流型（权限检查 + 人工审批）、复杂投诉直接转人工（结构见 4.9 的路由图）。

**效果（数字为示意量级）**：上线后请求分布约为 FAQ 70%、查询 25%、退款 4%、人工 1%；简单问答首响从「全走自主型」试点的约 20–40 秒压到 3 秒内，推理成本下降约一个数量级；退款链路因固定流程 + 审批，上线后未发生资损事故。

### 案例 B：研究助手（某金融科技投研团队，自主型）

**需求**：给定调研主题，多源检索、阅读、交叉验证、产出综述。

**做法**：自主型——规划（拆 6–10 个子问题）→ 逐题检索/阅读 → 反思验证（来源冲突、证据不足时触发补检索）→ 汇总生成；全程带 20 步与预算双熔断。

**效果（数字为示意量级）**：单任务平均 15–25 步、消耗数十万 token，成本约为一次 RAG 问答的 20–50 倍；在内部 50 题评测集上，加规划 + 反思后报告可用率从纯 ReAct 的约 55% 提升到约 78%。结论：自主型的能力要用熔断和评估兜住，否则成本先于质量失控。

### 案例 C：从工作流演进到自主型（某内容平台周报系统）

**阶段 1**：固定工作流（分类 → 检索 → 生成），覆盖约 60% 请求——格式稳定，但复杂选题处理不了。  
**阶段 2**：加工具型 Agent 支持多工具查询，覆盖到约 85%——多步任务仍搞不定。  
**阶段 3**：加规划 + 反思，自主型兜底复杂选题，覆盖约 95%。

**教训**：每一次升级都被「上一档覆盖不了的请求占比」驱动，而不是一开始就上自主型——按需演进，用数据说话（评估方法见 2.9）。

## 8. 常见坑

1. **过度设计**：简单查询也上规划 + 反思，延迟和成本翻倍。从最简单可行的架构起步，指标不达标再升级。
2. **设计不足**：步骤可枚举的业务交给自由循环，漂移且无法验收。有 SOP 就固化成工作流。
3. **组件堆砌**：检索、记忆、反思全开，系统复杂难维护。按 4.8 矩阵只加必需组件。
4. **不做路由**：一条路径服务所有请求，简单任务陪跑贵路径。混合型按复杂度分流（见 6.2）。
5. **读写不分离**：查询和写操作混在一条路径，权限难控制。读可放权，写走固定流程 + 审批。
6. **没有降级**：主路径失败就整体失败。主模型 → 备用 → 缓存 → 人工逐级兜底（见 3.7）。
7. **状态不持久化**：中断后无法恢复，只能重跑。关键节点写检查点（见 2.5）。
8. **不记 trace**：出问题无法定位到组件与步骤。每个决策、每次工具调用都记录（见 3.4）。
9. **提示词硬编码**：无法版本化与 A/B 测试。提示词外置并纳入版本管理（见 3.9）。
10. **工具与 Agent 耦合**：换工具要改 Agent 代码。用注册表 + Schema 解耦（见 2.3）。
11. **不做成本控制**：自主型单任务成本可达工作流型的 10 倍量级。步数、超时、预算三重熔断。
12. **忽略安全**：工具越权、提示注入、数据隔离全裸奔。最小权限 + 审计 + 沙箱（见 2.9、3.8）。
13. **过早多 Agent**：单 Agent 能解决的不上多 Agent。先单后多，判据见 2.8。
14. **不做评估**：架构选型是否合理全凭感觉。先建基线，做轨迹级评估再谈优化（见 2.9）。

## 10. 小结

- 四类模式一句话：**工具型 = LLM + 工具短循环；RAG 型 = 检索 + 生成；工作流型 = 代码预定义流程；自主型 = 规划 + 工具 + 记忆 + 循环 + 反思。**
- 选型正面答案：**四问定乾坤——任务确定性、步数、容错成本、可观测要求；步骤可枚举 + 高容错成本选工作流，路径未知 + 只读探索才放权自主型。**
- 组件按需引入：对照 4.8 矩阵只加必需项，「可选」等指标证明需要再加。
- 混合型 = 路由 + 四类组合，是生产默认形态；高风险写操作一律人工审批（见 3.10）。
- 推理范式（ReAct / Plan-and-Execute / ReWOO / Reflexion）管循环内部，架构模式管系统控制权——两层不混（见 2.2、2.6）。
- 六原则：**从简单开始、按需引入、分层解耦、可观测优先、可降级、可演进。**
- 默认从最简单架构起步：「先工作流、默认单 Agent」是社区与官方博客共识口径（2025），多 Agent 是最后选项（见 2.8）。
- 核心认知：**架构为任务服务，不是越复杂越好；每次升级都要有评估数据背书。**
- 这些能力直接支撑：2.8 多 Agent 协作、2.9 Agent 评估与安全、3.1 架构与接口设计、4.5 工作流自动化 Agent（实战）。
