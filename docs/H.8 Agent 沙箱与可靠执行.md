## 2. 一句话定义

Agent 沙箱是一个隔离、一次性、可复现的受控执行环境：Agent 生成的代码与命令只允许在容器或微虚拟机（microVM）里运行——破坏被限制在环境内部，资源消耗被封顶，任务结束即销毁，需要的结果经显式通道扫描后回传，全程留痕可审计——它是 Agent 从「建议者」升级为「执行者」的安全基石。

简化公式：

```text
可靠执行 = 隔离（逃不出去） + 限制（耗不垮） + 可恢复（毁得掉重来） + 可观测（出事说得清）
```

## 3. 为什么需要

推导链只有三步，但每一步都硬：

1. **Agent 的输出是概率性输出**：它可能算错路径（`rm -rf` 打错目录）、装错依赖包、写出死循环，甚至被提示词注入（Prompt Injection）诱导执行恶意命令——模型层没有「意图可靠性」保证。
2. **输出会变成动作**：一旦接上工具与执行环境，「生成的一段文本」立刻变成「主机上的一条命令」。不可信输出直接等于不可信动作。
3. **主机上的错误不可逆**：删掉的文件不会回来、泄出去的数据收不回来、打爆的资源拖垮的是邻居。直接在主机执行，等于把全家钥匙交给一个刚认识、还偶尔犯糊涂的装修队。

痛点清单：

- **错误爆炸半径不可控** → 一次路径算错就是全盘损失
- **环境互相污染** → 上一个任务的残留让下一个任务莫名失败
- **问题无法复现** → 排障时环境早被改得面目全非
- **资源被吃穿** → 死循环、fork 炸弹（Fork Bomb）、内存打爆拖垮宿主机
- **数据单向流出** → 一段 `curl` 就能把上下文里的敏感数据送出去
- **出事无法定责** → 分散的日志回答不了「它到底执行了什么、耗了多少资源」

| 维度 | 主机直接执行 | 沙箱执行 |
|---|---|---|
| 错误爆炸半径 | 整台主机及其数据 | 容器/VM 内部，销毁即归零 |
| 可逆性 | 删了就是删了 | 环境用完即弃，重跑一次即可 |
| 可复现性 | 主机状态被污染，难复现 | 从干净快照启动，问题可稳定复现 |
| 多任务干扰 | 状态残留互相污染 | 一任务一环境，天然隔离 |
| 资源占用 | 无上限，死循环烧穿宿主 | CPU/内存/时间硬上限，超限即杀 |
| 审计 | 分散在各处日志 | 代码、资源用量、输出、扫描结论集中留痕 |
| 权限面 | 进程权限即用户权限 | 禁网/白名单、只读文件系统、降权用户 |

类比：主机直接执行 = 把家里钥匙整套交给刚认识的装修队；沙箱 = 只开放一间指定的房间、只给指定的工具、干完锁门清点——哪怕他们把房间拆了，损失也只有一间。一句话：**隔离不提升模型智力，它把不可靠输出的代价变成可承受的**——这也是「可靠执行」中「可靠」二字的工程含义：不是不出错，而是错了也兜得住、回得来、说得清。

## 4. 核心原理

### 4.1 三属性：隔离、一次性、可复现

| 属性 | 含义 | 工程手段 | 反面案例 |
|---|---|---|---|
| 隔离 | 逃不出去：网络、文件系统、进程、权限全面受限 | 禁网/出口白名单、只读根文件系统、降权用户、seccomp | 容器里挂载宿主机 Docker socket 加全量凭证 |
| 一次性（Ephemeral） | 用完即毁：不跨任务保留任何状态 | 任务结束强制销毁，不复用容器 | 多用户复用同一容器造成交叉泄漏 |
| 可复现 | 从干净快照重启，问题可定位 | 基础镜像版本化、快照与恢复、环境即代码 | 排障时环境已被下一次任务改掉 |

三者是乘法关系：只做隔离不做一次性，状态残留会慢慢磨穿隔离；只做一次性不留快照，排障无从下手；只留快照不隔离，快照本身就是泄漏源（见 4.5 的快照纪律）。

### 4.2 隔离强度谱系：从进程级到云沙箱与本地策略

| 档位 | 代表技术 | 隔离原理 | 冷启动 | 运行开销 | 适用 |
|---|---|---|---|---|---|
| 进程级 | 受限子进程（命名空间 + seccomp + 资源上限）、WASM 运行时近似此档 | 共享宿主内核，仅软限制 | 毫秒级 | 最低 | 本地开发、自家高可信代码 |
| 容器 | Docker / containerd | 命名空间（Namespace）+ 控制组（cgroups），仍共享内核 | 秒级 | 低 | 默认档：内部工具、单租户代码执行 |
| 用户态内核 | gVisor（Google 开源，用户态实现的 Linux 内核层） | 在进程与内核间拦截、过滤系统调用，系统调用暴露面大幅收窄 | 秒级（略慢于容器） | 中（syscall 密集场景损耗明显） | 半可信代码、多租户 SaaS |
| microVM | Firecracker（AWS 开源，Lambda/Fargate 同源技术） | KVM 轻量虚拟机，独立内核 + 最小设备模型 | 百毫秒级（官方口径最小启动约 125 毫秒） | 中 | 云端高并发代码执行、强多租户 |
| 完整 VM / 物理机 | KVM 全量虚拟机、裸金属 | 硬件虚拟化完整实现 | 分钟级 | 最高 | 极高风险、强合规 |
| 云沙箱（托管） | E2B、Modal、Daytona 等 | 把上述档位外包成 API：底座是 microVM 或 gVisor 容器（见 4.10） | 服务商承诺亚秒级（快照池化） | 中（含服务溢价） | 无基础设施团队、快速接入 |
| 本地策略 | macOS sandbox-exec、Linux bubblewrap/命名空间封装、Windows AppContainer | 操作系统级策略声明，无独立内核，靠系统调用拦截 | 毫秒级 | 低 | 编码 Agent 的本地执行闸门（H.6 的权限四层在本地落地即此档） |

读法一：**隔离强度与轻便性是一对交换**。类比现金押运——收银台的零钱抽屉（进程级）、网点金库（容器）、跨城运钞车（gVisor）、跨国装甲专机（microVM）：按押运金额配安保等级，不为买瓶水雇专机（过度隔离白白付出延迟与成本），也不能用抽屉放一百万（档位不足）。按风险选档：跑自己写的单元测试，容器足够；跑用户上传的任意脚本，至少 gVisor/microVM；处理不可信来源的文件与代码，microVM 起步。

读法二：**容器共享内核是档位分界线**。容器与进程级都跑在宿主内核上——一个内核漏洞就是共同的逃逸面（容器逃逸，Container Escape）；gVisor 收窄系统调用面，microVM 干脆换一个内核。这就是「不可信代码至少 gVisor/microVM」的底层依据。

**面试高频问法**：「容器和 microVM 怎么选？」共识口径：先看信任等级——共享内核意味着内核漏洞即逃逸面，多租户/不可信代码用独立内核；再看密度与冷启动——microVM 牺牲一点内存与启动开销换强隔离，Firecracker 快照把冷启动压回亚秒；最后看运维成本——自建 microVM 池工程量大，托管云沙箱（E2B 类）是用钱换运维。

### 4.3 资源限制：五维硬上限

资源限制回答「就算代码是坏的，也耗不垮机器」。五个维度缺一不可：

| 维度 | 不限制的后果 | 限制手段 | 典型取值（示意） |
|---|---|---|---|
| CPU | 死循环烧满核，邻居任务全部变慢 | cgroups CPU 配额（cpu.max）、RLIMIT_CPU | 0.5-2 核 |
| 内存 | 大对象分配打爆宿主或触发全局 OOM | cgroups 内存上限（memory.max）、RLIMIT_AS | 256MB-2GB |
| 进程数 | fork 炸弹进程数指数膨胀 | pids 上限（pids.max）、RLIMIT_NPROC | 32-128 |
| 文件系统/磁盘 | 垃圾文件写满磁盘、大文件拖垮 I/O | 只读根 + tmpfs 容量上限 + 磁盘配额 | 可写区 64-512MB |
| 时间（墙钟） | 卡在 I/O 或睡眠上的任务永不返回 | 墙钟超时（Wall-clock Timeout）强杀 | 30-300 秒 |

两个工程口径：

1. **CPU 时间与墙钟时间不是一回事**：`RLIMIT_CPU` 只数计算时间，`sleep 10000` 不耗 CPU 却永远挂着——所以必须有墙钟超时兜底（对应 2.5 的终止条件：应用层检查之外，执行层再设一道独立熔断）。
2. **cgroups 与 RLIMIT 各有位置**：cgroups（Control Groups）是内核级资源组限制，容器场景在运行时参数里下；RLIMIT 是进程级资源上限，无容器的子进程包装器在启动前下（见 6.1）。两层叠加，防的是「容器配额没配齐」的缝隙。

类比：资源上限像健身房私教课——到点必须下课，器械是共享的，不能因为你一个人想练就把全场占一天；沙箱的「课时长」就是墙钟超时，「器械数」就是 CPU 与内存配额。

### 4.4 文件系统与网络策略

文件系统四条纪律：

- **根只读**：容器根文件系统设为只读，脚本删不掉、改不掉系统文件。
- **唯一可写区**：只挂一个容量受限的 tmpfs（内存盘）工作目录，一切写入被圈在里面。
- **最小挂载**：绝不挂载 Docker socket、宿主凭证目录、SSH 密钥；数据按需注入、用完即取。
- **降权与裁剪**：以非 root 用户运行、清空能力位（Linux Capabilities，cap_drop=ALL）、开 no-new-privileges、屏蔽敏感内核路径（/proc/sys 等）。

网络两条路线：

| 路线 | 做法 | 适用 |
|---|---|---|
| 禁网（默认） | network_disabled 或空白网络命名空间 | 绝大多数代码执行任务：分析、转换、生成图表 |
| 出口白名单（Egress Allowlist） | 经代理出去，只放行声明过的域名，DNS 固定，其余全拒并告警 | 确需拉包、查 API 的任务 |

禁网一石三鸟：数据传不出去（防外传）、恶意载荷下不来（防投毒）、回连 Shell 连不上（防反向控制）。白名单是「必须联网」时的收窄妥协，不是默认态。

### 4.5 快照与回滚

快照（Snapshot）与回滚（Rollback）解决「一次性」与「低延迟、可排障」的矛盾。三层机制，由轻到重：

| 机制 | 原理 | 量级 | 用途 |
|---|---|---|---|
| 镜像分层 + 写时复制（Copy-on-Write，overlayfs） | 镜像层只读、可写层记差异，起容器只建薄薄一层 | 秒级建环境 | 基础镜像版本化，环境即代码 |
| 容器检查点（CRIU） | 把进程树整体冻结落盘，可恢复继续跑 | 秒级 | 长任务的中间态保存 |
| microVM 快照（Firecracker Snapshot） | 整机内存 + 设备状态落盘；恢复即续跑；可从一份快照 fork 出多份 | 启动约 125 毫秒、快照恢复毫秒级 | 预热环境池化、亚秒级拉起 |

回滚的两种粒度，工程上要分清：

- **任务级回滚（销毁重来）**：出问题直接销毁环境、从干净快照重建。最可靠、最常用——因为环境回到初始态，与 Agent 重新生成的代码天然对得上账。
- **步级回滚（快照恢复）**：长任务执行到第 N 步失败，从第 N-1 步的环境快照恢复再试。要谨慎：环境回到过去，但 Agent 的对话上下文没有回滚，两边状态对不上，容易越修越乱。生产建议：优先任务级重建，步级回滚只用于环境昂贵（如装好大型依赖）的场景。

与 2.5 的关系：2.5 的检查点存的是 Agent 状态（可序列化的目标、计划、已完成步骤——JSON 就能装下）；本篇的快照存的是整个执行环境（内存、进程、文件系统——GB 级二进制）。应用层重启续跑配执行层干净重建，是完整的恢复故事。

快照纪律：**快照只含干净基础环境**——凭证、客户数据一律运行时注入。含着密钥的快照被复用，等于把密钥复印了发给每个任务。

类比：一次性环境像酒店客房——退房即彻底清扫换床品（销毁清盘），上一位客人落下的东西不会出现在你的房间（无状态残留）；长驻容器像长租公寓，上一任租户装的针孔摄像头你很难发现（残留状态磨穿隔离）。快照池则是「提前铺好的干净客房」，客人到即住，毫秒级完成入住。

### 4.6 产物回传与扫描

沙箱追求「用完即弃」，因此**需要持久化的东西必须显式导出**，其余全部丢弃：

- **显式通道**：只开放约定导出目录（如 `/sandbox/out`），容器内其他改动一概不回传。
- **扫描管道**：导出物过三道——恶意文件扫描（病毒/脚本特征）、敏感信息扫描（密钥、内部数据指纹）、格式校验（只允许声明的产物类型，如 PNG/CSV）。
- **丢弃即安全**：脚本写到导出目录之外的内容，随容器销毁自然蒸发——这比「事后清理」可靠得多。

类比：产物通道像机场海关申报——从隔离区出来只有一条申报通道，行李全部过 X 光与嗅探（三道扫描）；没申报的物品留在隔离区，随销毁处理，根本到不了境内。

### 4.7 执行审计与日志

沙箱方案「只装不留痕」等于白装——出事时无法回答「执行了什么、用了多少资源、结果去哪了」。审计（Audit）留痕四要素：

| 留痕项 | 内容 | 用途 |
|---|---|---|
| 代码与命令 | 执行的完整代码/命令内容（版本化存档） | 定责、复现 |
| 输出 | stdout/stderr（截断存档） | 排障、回填分析 |
| 资源用量 | 峰值 CPU/内存、时长、进程数 | 成本核算、异常检测 |
| 扫描与告警结论 | 产物扫描结果、异常事件清单 | 安全事件闭环 |

告警事件清单（出现即记录并推送）：联网尝试、敏感路径读取、超时强杀、fork 异常增长、导出物扫描命中。三条工程纪律：

1. **审计日志独立存放**：不放在沙箱可达的存储里，只增不可改（append-only），防的是「出事的证据被出事的进程改掉」。
2. **与全链路追踪合流**：沙箱事件作为执行类 span 挂进 3.4 的 trace，一次任务从 LLM 决策到命令执行到产物扫描全程可回放——这正是 2.9 评估 Agent 可靠性时需要的证据链。
3. **审计要能回答三类问题**：出了什么事（告警）、怎么发生的（轨迹）、影响多大（资源用量与产物去向）。

### 4.8 可靠执行四要素与失败模式对策

把前四节收拢成一个可背、可查、可验收的框架——**可靠执行四要素**：

| 要素 | 含义 | 工程手段（本篇对应节） | 缺失后果 |
|---|---|---|---|
| 隔离（Isolation） | 坏动作出不去 | 档位谱系 + 文件系统/网络策略（4.2/4.4） | 一次失误变全盘事故 |
| 限制（Limitation） | 坏动作耗不垮 | 五维资源硬上限（4.3） | 死循环与炸弹拖垮宿主 |
| 可恢复（Recoverability） | 毁得掉、回得来 | 一次性环境 + 快照/回滚（4.5） | 排障无从下手、任务卡死 |
| 可观测（Observability） | 出事说得清 | 审计留痕 + 告警（4.7） | 无法定责、无法复盘 |

失败模式与对策表（上线前逐行自查）：

| 失败/攻击模式 | 典型表现 | 对策（所属要素） |
|---|---|---|
| 死循环/长任务 | CPU 占满、永不返回 | 墙钟超时强杀 + CPU 配额（限制） |
| fork 炸弹 | 进程数指数膨胀 | pids 上限 + 进程数告警（限制+可观测） |
| 内存打爆 | OOM 或拖垮邻居任务 | 内存硬上限 cgroups memory.max（限制） |
| 数据外传 | 脚本尝试上传上下文数据 | 禁网/出口白名单 + 外传尝试告警（隔离+可观测） |
| 路径穿越（Path Traversal）/乱写 | 写导出目录之外、读敏感路径 | 只读根 + 唯一可写 tmpfs + 显式导出（隔离） |
| 容器逃逸 | 利用内核漏洞或特权操作越界 | 升档 gVisor/microVM + cap_drop + seccomp（隔离） |
| 供应链投毒 | 安装恶意依赖/技能包 | 白名单 + 安装前审查 + 沙箱兜底（隔离+治理） |
| 状态残留泄漏 | 复用环境读到他人数据 | 一次性环境 + 强制销毁（可恢复） |
| 僵尸容器堆积 | 超时不清理耗尽宿主资源 | finally 强制销毁 + 池巡检（运维） |
| 审计缺失 | 出事无法定责与复盘 | 四要素全留痕 + 独立 append-only 存储（可观测） |

**面试高频问法**：「Agent 执行代码怎么保证安全？」（借道 4.3 已有真题先例）标准答法四层递进：提示词约束（体验层）→ 静态校验（拦截层）→ 权限模型（准入层，2.3/3.8）→ 沙箱隔离 + 资源限制（兜底层，本篇）；再补一句档位谱系与选型（4.2），从场景答案上升到体系答案。

### 4.9 与工具权限模型的关系

权限与沙箱是两道前后咬合的闸门，不是二选一：

| 维度 | 工具权限模型（2.3/3.8） | 沙箱（本篇） |
|---|---|---|
| 管什么 | 能调用什么工具、传什么参数、要不要人工在环（Human-in-the-loop） | 放行之后，执行能碰到什么资源 |
| 位置 | 准入：调用发生之前 | 兜底：执行过程之中 |
| 实现 | 白名单、RBAC、审批流、审计 | namespace/microVM、cgroups、网络策略 |
| 典型失效 | 提示词注入骗过审批，或参数合法但语义恶意 | 权限放行后代码行为失控（这不该由权限管） |
| 口径 | 权限决定「门开多大」 | 沙箱决定「门后的房间多结实」 |

分工逻辑：权限模型不可能穷尽判断「这段代码会干什么」——图灵完备的代码行为不可静态审全（4.3 已论证：SQL 审得住、Python 审不住）；所以权限负责「该不该跑」，沙箱负责「跑了也出不了事」。H.6 的编码 Agent 权限四层（只读/确认/审批/沙箱）就是这个分工在本地形态的落地：前三层是权限闸门，最后一层把执行交给沙箱。

### 4.10 2026 年格局与供应链延伸

托管沙箱格局（趋势观察期，口径性对比，具体能力与数字以各厂商最新文档为准，选型必实测）：

| 维度 | E2B | Modal | Daytona | 自建（Docker 池/Firecracker 池） |
|---|---|---|---|---|
| 定位 | 开源的 AI 代码执行沙箱 | AI 无服务器算力平台 | 开发环境即服务 | 全自控基础设施 |
| 隔离底座 | microVM（Firecracker 系） | gVisor 隔离的容器 | 容器/VM 工作区 | 自选档位 |
| 冷启动 | 主打低延迟，官方口径低于 200 毫秒，支持快照/暂停恢复 | 秒级弹性扩缩 | 主打秒级起环境 | 取决于工程：预热池可压到亚秒 |
| GPU 透传 | 非主打（面向代码执行） | 丰富，主流 GPU 按需分配 | 有限，视产品线 | 可配，但运维重 |
| 快照恢复 | 有（环境状态可暂停恢复） | 有镜像层缓存/快照能力 | 有（工作区快照） | Firecracker 快照自研 |
| 适合 | 快速给 Agent 加代码执行能力 | 训练/推理与代码执行混合负载 | Agent 开发工作区场景 | 强合规、数据不出域、成本敏感 |

选型口诀：**先问数据能不能出域**——能出域优先托管服务（快、省运维），不能出域只剩自建；再按负载选底座——纯代码执行选 E2B 类，要 GPU 选 Modal 类，长驻开发环境看 Daytona 类。

安全焦点转移（截至 2026 年社区口径）：

| 旧焦点 | 新焦点 |
|---|---|
| 提示词注入防御 | 工具与代码执行的安全（本篇沙箱） |
| 输出内容审查 | 上下文暴露控制（敏感数据不进不可信上下文） |
| 单体应用权限 | MCP/工具权限收敛与调用审计（3.8 的延伸） |
| 模型自带安全 | 工具/技能供应链安全 |

**技能（Skills）与工具供应链**是沙箱话题的自然延伸：技能包（如 Agent Skills 的 SKILL.md 生态）本质是「提示词+脚本+工具权限」的组合，供应链风险与 npm 恶意包同构——一个带恶意脚本的技能包被 Agent 安装执行，沙箱是最后一道闸。已有安全扫描报告给出量级口径：3,984 个技能中 36.82% 存在问题（MintMCP《Secure AI Agents in Production》厂商报告，2026，单一来源，引用时需注明）。落地纪律四条：技能与工具白名单化、安装前审查（脚本行为+权限申请）、来源可信验证、执行仍走沙箱。

## 5. 架构 / 流程

一个生产级「Agent 代码执行」管线——四要素在图上各就各位：

```text
Agent 生成代码/命令
        |
┌───────▼────────────────────────────────┐
│ 执行准入（权限模型：2.3/3.8 的辖区）      │
│  静态检查（危险 API/网络调用指纹）        │

│     ↓ 拉起                              │

│     ↓ 领取                              │
│  一任务一环境：                          │
│   禁网/出口白名单 ｜ 只读根+tmpfs 可写区  │

│   降权用户 ｜ cap_drop ｜ seccomp        │
└───────┬────────────────────────────────┘

        ▼
┌─────── 销毁与审计（4.5/4.7）─────────────┐
│  强制销毁容器/VM（清盘，不留状态）        │
│  留痕：代码+输出+资源用量+扫描结论        │
│  （独立 append-only 存储，挂入 3.4 trace）│
│  告警：试联网/读敏感路径/超时/fork 异常   │
└───────────┬────────────────────────────┘
            ▼
    成功 → 产物与日志交付 Agent
    失败 → 任务级回滚（从快照重建重试）
           或 步级回滚（环境快照恢复，慎用）
```

生命周期与回滚路径（一句话版）：

```text
创建（从版本化镜像/快照）→ 预热（池化温环境）→ 执行（五维资源硬上限）
→ 产物显式导出（三道扫描）→ 销毁（强制，含清盘）→ 审计（全量留痕）

失败时：优先任务级回滚（销毁+从干净快照重建）
仅在环境昂贵时用步级回滚（CRIU/快照恢复执行前状态）
```

读图要点：准入层是 2.3/3.8 的辖区，沙箱池往后是本篇的辖区——权限管门、沙箱管房间；产物通道是唯一的数据回流路径，扫描不过就进不了下游；审计不在流程终点，而是横向覆盖执行、导出、销毁全程。

## 6. 代码 / 工具

### 6.1 进程级执行包装器：OS 资源硬限制

对应谱系最低档（毫秒级启动，仅限自家高可信代码；与 4.3 的「字符串校验子进程」不同，这里讲的是操作系统级硬限制，两者应叠加）：

```python
# process_sandbox.py —— 进程级执行包装器：RLIMIT 资源上限 + 墙钟超时 + 输出截断
import resource
import subprocess
import sys


def _apply_limits(mem_mb: int = 512, cpu_seconds: int = 30, nproc: int = 64):
    """返回一个在子进程内执行的函数，把资源上限落在子进程上。"""
    def _set():
        # 地址空间上限：大对象分配直接失败，而不是拖垮宿主
        resource.setrlimit(resource.RLIMIT_AS, (mem_mb * 1024 * 1024,) * 2)
        # CPU 时间上限：死循环在核内时间耗尽后被内核终止
        resource.setrlimit(resource.RLIMIT_CPU, (cpu_seconds, cpu_seconds))
        # 进程数上限：fork 炸弹到此为止
        resource.setrlimit(resource.RLIMIT_NPROC, (nproc, nproc))
        # 核心转储关闭：崩溃不留盘
        resource.setrlimit(resource.RLIMIT_CORE, (0, 0))
    return _set


def run_with_limits(code: str, wall_timeout: int = 60,
                    max_output: int = 20000) -> dict:
    """执行一段 Python 代码，返回退出码、输出（截断）。"""
    proc = subprocess.Popen(
        [sys.executable, "-I", "-c", code],   # -I 隔离模式：不加载用户环境与站点包
        stdout=subprocess.PIPE, stderr=subprocess.PIPE,
        text=True, preexec_fn=_apply_limits(),   # 关键：限制在子进程启动前生效
    )
    try:
        out, err = proc.communicate(timeout=wall_timeout)  # 墙钟超时：含卡 I/O 的时间
        return {"exit_code": proc.returncode,
                "stdout": out[:max_output], "stderr": err[:max_output]}
    except subprocess.TimeoutExpired:
        proc.kill()                           # 超时强杀：防睡眠与卡 I/O 的任务
        out, err = proc.communicate()
        return {"exit_code": 124, "stdout": out[:max_output],
                "stderr": "[wall-clock timeout] " + err[:max_output]}


if __name__ == "__main__":
    # 样本：内存打爆（被 RLIMIT_AS 拦截，而非拖垮宿主）
    r = run_with_limits("x = [0] * 10**9")
    print(r["exit_code"], r["stderr"][-100:])
```

### 6.2 Docker 容器沙箱执行器（生产默认档）

4.3 的 6.5 给过「容器即参数」的极简版；这里是完整执行器：隔离 + 五维上限 + 产物显式导出 + 强制销毁。

```python
# docker_sandbox.py —— 一次性容器沙箱：隔离+资源上限+产物导出+销毁
import io
import tarfile
import uuid

import docker


def run_in_sandbox(code: str, timeout: int = 60,
                   mem_limit: str = "512m", cpus: float = 1.0) -> dict:
    """在一次性容器里执行代码，返回退出码、日志与显式导出的产物。"""
    client = docker.from_env()
    workdir = "/sandbox"
    container = client.containers.create(
        image="python:3.12-slim",
        command=["python", "-c", code],
        name=f"sandbox-{uuid.uuid4().hex[:8]}",
        network_disabled=True,             # 隔离：切断数据外传与回连
        mem_limit=mem_limit,               # 限制：内存
        nano_cpus=int(cpus * 1e9),         # 限制：CPU 配额
        pids_limit=64,                     # 限制：防 fork 炸弹
        read_only=True,                    # 文件系统：根只读
        tmpfs={workdir: "size=64m"},       # 唯一可写区：64MB 内存盘（磁盘上限）
        user="65534:65534",                # 降权：nobody 运行
        cap_drop=["ALL"],                  # 裁剪：清空全部能力位
        security_opt=["no-new-privileges"],
    )
    try:
        container.start()
        try:
            result = container.wait(timeout=timeout)
        except Exception:
            container.kill()               # 墙钟超时强杀：防死循环与卡 I/O
            result = {"StatusCode": 124}
        logs = container.logs(stdout=True, stderr=True).decode(errors="replace")
        artifacts = _export(container, f"{workdir}/out")   # 只回传导出目录
        return {"exit_code": result["StatusCode"], "logs": logs,
                "artifacts": artifacts}    # 审计：连同资源用量一起落盘（见 4.7）
    finally:
        container.remove(force=True)       # 一次性：用完即毁


def _export(container, path: str) -> dict:
    """把导出目录打包取回，交由扫描管道（恶意文件/敏感信息/格式白名单）。"""
    bits, _ = container.get_archive(path)
    tar = tarfile.open(fileobj=io.BytesIO(b"".join(bits)))
    out = {}
    for m in tar.getmembers():
        if m.isfile():
            out[m.name] = tar.extractfile(m).read()
    return out


if __name__ == "__main__":
    r = run_in_sandbox(
        "with open('/sandbox/out/hello.txt','w') as f: f.write('ok')\n"
        "print('done')"
    )
    print(r["exit_code"], r["logs"], list(r["artifacts"]))
```

### 6.3 E2B 云端托管沙箱调用

```python
# e2b_demo.py —— E2B：创建一次性微 VM、执行、产物回传、自动销毁
# pip install e2b-code-interpreter（SDK 接口以官方最新文档为准）
from e2b_code_interpreter import Sandbox


def analyze() -> str:
    with Sandbox(timeout=120) as sbx:          # 一次性微 VM 环境
        # 1. 注入数据（运行时注入，不进快照——见 4.5 快照纪律）
        sbx.files.write("/home/user/data.csv",
                        "city,sales\nhangzhou,120\nshanghai,98\n")

        # 2. 在沙箱里执行模型生成的分析代码
        code = (
            "import pandas as pd, matplotlib\n"
            "matplotlib.use('Agg')\n"
            "import matplotlib.pyplot as plt\n"
            "df = pd.read_csv('/home/user/data.csv')\n"
            "df.plot.bar(x='city', y='sales', figsize=(6,4))\n"
            "plt.tight_layout()\n"
            "plt.savefig('/home/user/out/chart.png')\n"
            "print(df.describe())"
        )
        execution = sbx.run_code(code)
        print(execution.logs.stdout)           # 文本输出：describe 结果

        # 3. 产物显式回传（回传后仍应过本地扫描管道）
        chart = sbx.files.read("/home/user/out/chart.png", format="bytes")
        with open("chart.png", "wb") as f:
            f.write(chart)
    # with 退出即销毁：本地与云端都不留运行状态
    return "chart.png"


if __name__ == "__main__":
    analyze()
```

## 7. 案例

### 案例 A：数据分析 Agent 的脚本执行架构（四要素落地）

**场景**：一家金融科技公司的数据分析 Agent 要执行用户上传的 Python 脚本自动出图表，涉及多租户数据（4.3 场景的沙箱底座由本篇体系接管）。

**做法**：按四要素落地——隔离：每脚本一个容器（禁网、只读根文件系统、降权用户、cap_drop）；限制：2 核 2GB、可写区 256MB、120 秒墙钟硬上限，超时强杀；可恢复：环境全部从版本化快照拉起，失败即销毁重建；可观测：全量留痕并告警异常行为（约 0.3% 的脚本有联网尝试，全部被禁网拦截并记录）。

**效果**：温环境池把冷启动从约 8 秒压到 1.2 秒；上线一年零跨租户数据事故。关键决策是**拒绝容器复用**——性能换安全的交易不做。

### 案例 B：Coding Agent 平台的微 VM 化

**场景**：某研发效能团队的 Coding Agent 平台（H.6 的测试循环形态），每个 PR 要在干净环境跑构建与测试，高峰并发约 200 任务，容器现起冷启动约 22 秒，体验与成本双差。

**做法**：底座换 Firecracker microVM，把预热好的基础环境（语言工具链、常用依赖）打成快照；任务从快照拉起后克隆仓库执行，结束销毁。

**效果**：环境就绪时间从 22 秒降到约 0.9 秒；同等并发下宿主机数量降约七成（快照共享基础层 + 更小的运行时开销）；每个 PR 天然获得干净可复现环境，flaky 环境问题归零。印证 4.5 的结论：快照让「一次性」与「低延迟」兼得。

### 案例 C：一次交叉污染事故复盘

**场景**：某 SaaS 团队为省资源让多用户复用同一批长生命周期容器。用户 A 的脚本把中间数据缓存到工作目录，用户 B 的脚本遍历目录时读到 A 的数据——数据泄漏。

**定责与整改**：审计日志还原了完整链路（这正是 4.7 留痕的价值：谁、何时、读了哪个路径）。整改三条：一人（一任务）一容器、销毁前强制清盘、产物只走扫描后的导出通道；容器复用策略整体下线。

**结果**：吞吐下降约 15%，用池化温环境补回。教训：**复用容器跑不同用户的任务是数据泄漏的经典通道，这条性能优化永远不做**。

## 8. 常见坑

1. **主机直接跑 Agent 生成的命令**。  
   一次算错路径的 `rm -rf` 就不可逆。任何模型输出一律进沙箱。

2. **容器挂载 Docker socket 与全量凭证**。  
   等于把宿主机 root 交给沙箱内进程。最小挂载、按需注入、短时凭证。

3. **沙箱能访问外网**。  
   禁网优先；确需联网走域名白名单出口，防数据外传与下载恶意载荷、防回连。

4. **复用容器跑不同用户的任务**。  
   交叉污染是数据泄漏的经典通道。一任务一环境，销毁前清盘。

5. **无资源上限或只限 CPU**。  
   死循环、fork 炸弹、内存打爆、磁盘写满各有各的死法；CPU/内存/PID/磁盘/墙钟五维硬上限缺一不可（见 4.3）。

6. **只限 CPU 时间不限墙钟时间**。  
   `sleep` 与卡 I/O 不耗 CPU 却永远挂着。communicate(timeout=...) 墙钟强杀兜底。

7. **产物不扫描直接回传**。  
   恶意文件或带密钥的导出物流进下游。扫描三道：恶意文件、敏感信息、格式白名单。

8. **只装沙箱不留审计**。  
   出事无法回答「执行了什么、用了多少资源」。代码+输出+资源用量+扫描结论全留痕，独立 append-only 存储。

9. **把长生命周期容器当沙箱**。  
   状态残留慢慢磨掉隔离假设。一次性+快照拉起，别恋战。

10. **隔离档位选错**。  
    用户上传的任意脚本只给了进程级软限制。按风险选档：不可信代码至少 gVisor/microVM（见 4.2）。

11. **冷启动不优化**。  
    秒级到十秒级的现起毁掉体验。预热池+快照恢复，目标亚秒。

12. **快照里带敏感状态**。  
    含凭证/客户数据的快照被复用即泄漏。快照只含干净基础环境，敏感物运行时注入。

13. **步级回滚用得太随意**。  
    环境回到过去、上下文没回，两边对不上账越修越乱。优先任务级重建（见 4.5）。

14. **技能/依赖不做供应链审查**。  
    技能包与 npm 包同构，恶意脚本随安装进环境。白名单+安装前审查+沙箱执行兜底（业界扫描口径：3,984 技能 36.82% 有问题，单一来源需标注）。

15. **把提示词防护当全部安全**。  
    注入防得住措辞防不住执行。安全重心在工具与代码执行面，沙箱是最后闸（与 2.3/3.8 的权限闸门前后咬合）。

16. **超时后不清理**。  
    僵尸容器堆积吃光资源。finally 强制销毁+池巡检兜底。

## 10. 小结

- 核心逻辑：**Agent 输出是概率性的，隔离不提升智力，而是把不可靠输出的代价变成可承受的**——这是 Agent 从建议者变执行者的门票。
- 三属性：**隔离（逃不出去）、一次性（用完即毁）、可复现（快照重启）**，三者是乘法关系，缺一磨穿另外两个。
- 隔离谱系：**进程级 → 容器 → gVisor 用户态内核 → Firecracker microVM → 完整 VM**，外加云托管（外包档位）与本地策略（OS 闸门）两个变体——按风险选档，不可信代码至少 gVisor/microVM。
- 资源限制五维：**CPU/内存/进程数/磁盘/墙钟时间**硬上限；CPU 时间替代不了墙钟超时，cgroups 与 RLIMIT 各守一层。
- 可靠执行四要素：**隔离（出不去）、限制（耗不垮）、可恢复（毁得掉重来）、可观测（说得清）**——上线前按失败模式对策表逐行自查。
- 快照工程：**预热池+Firecracker 快照**让一次性与低延迟兼得；回滚优先任务级重建，步级回滚慎用；快照只含干净环境，敏感物运行时注入。
- 产物与审计纪律：**显式导出通道+三道扫描（恶意文件/敏感信息/格式白名单），其余随销毁丢弃**；留痕四要素进独立 append-only 存储，挂入 3.4 的全链路 trace。
- 与权限模型的分工：**权限（2.3/3.8）管准入「门开多大」，沙箱管执行「房间多结实」**——提示词约束→静态校验→权限→沙箱四层递进，任何单层都不够。
- 选型与格局：**E2B（代码执行）、Modal（GPU 弹性）、Daytona（开发环境）、自建池**——先问数据能否出域；2026 年安全重心已从提示词转向工具/代码执行、上下文暴露与 MCP 权限审计，技能供应链与沙箱合流。
- 铁律：**禁止复用容器跑不同用户的任务**——交叉污染是数据泄漏的经典通道；状态口径为趋势观察，面试借道 4.3 真题先例，按「四要素+档位谱系」作答即覆盖真题口径。
- 这些能力直接支撑：4.7 生产级 Agent 平台与 4.9 部署运维的执行底座，H.6 编码 Agent 的测试循环与 H.7 计算机使用的执行隔离——并就此收束 H 层（H.1-H.8）：推理扩展、RLVR 对齐、上下文工程、Agentic RAG、A2A 互操作、编码智能体、计算机使用、沙箱可靠执行八问合拢，回接 5.5-5.7 的工程化与综合项目路径。
