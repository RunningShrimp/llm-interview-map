## 1. 定位

Agent 核心层第 3 个知识点，属于"行动能力"。2.1 的公式里，Agent = LLM + 工具 + 记忆 + 循环 + 目标，本篇负责其中"工具"一环：**Agent 有了目标和计划，如何真正与外部世界交互，把决策变成行动？**

锚点关键问题更进一步：**如何安全、可靠地调用外部系统？** 本篇 4.6 用"五层防御"集中正面回答：参数校验、超时重试、幂等、最小权限、审计。

前置：1.3（Function Calling 接口机制）、2.1（Agent 定义与范式）。  
后续：2.5 执行循环（工具结果如何回到循环）、3.3 编排框架（MCP 深入）、4.4 浏览器与计算机使用 Agent（GUI 类工具）。

## 2. 一句话定义

工具使用（Tool Use），是 Agent 通过定义、选择并调用外部函数、API、服务，并对每次调用做校验、错误处理与权限控制的工程机制，用来完成 LLM 无法直接完成的任务。

简化公式：

```text
Agent 能力 = LLM 原生能力 + 工具扩展能力
```

## 3. 为什么需要

LLM 本身有硬伤：

| LLM 不能做 | 工具能解决 |
|---|---|
| 实时查询天气 | 调用天气 API |
| 精确计算 | 调用计算器 |
| 查数据库 | 执行 SQL |
| 发邮件 | 调用邮件 API |
| 操作网页 | 浏览器工具 |
| 读写文件 | 文件系统工具 |
| 生成图片 | 图像生成 API |
| 查最新新闻 | 搜索引擎 |
| 执行代码 | 代码沙箱 |
| 支付转账 | 支付 API（需审批） |

反过来，工具接不好，行动能力就是负资产。没有工具治理的 Agent 上线后通常这样翻车：

- **参数幻觉频发** → 模型编造参数值、自创枚举，下游系统接连报错。
- **越权调用** → 模型说调什么就调什么，用户没授权的操作也照做。
- **工具一多就选错** → 30 个工具全塞给模型，选择准确率雪崩。
- **错误无人接管** → 工具一挂 Agent 卡死，不会重试也不会降级。
- **结果塞爆上下文** → 一次返回几万 token，后续推理全部变形。

**核心认知**：

> LLM 是大脑，工具是手脚。没有工具，Agent 只能"说"；有了工具，Agent 才能"做"。

**类比**：

```text
LLM 单独 = 一个博学但只能动嘴的顾问：什么都能分析，什么都干不了
Agent + 工具 = 同一个顾问配上查资料的助手、计算器和系统账号：
               说"查"就有人查，说"办"就真有人去办
```

## 4. 核心原理

### 4.1 工具的生命周期

```text
1. 定义（Define）    → 函数名、描述、参数 Schema
2. 注册（Register）  → 加入工具列表
3. 选择（Select）    → LLM 决定用哪个
4. 调用（Invoke）    → 解析参数，执行函数
5. 校验（Validate）  → 参数校验、权限检查
6. 执行（Execute）   → 实际运行
7. 返回（Return）    → 结果格式化
8. 记录（Log）       → 日志、trace、成本
9. 错误处理（Handle）→ 重试、降级、反馈
```

其中"模型怎么输出 tool_calls、结果怎么回填 messages"属于 Function Calling 的接口时序，1.3 已逐步拆解；整个循环怎么转、何时终止见 2.5。本篇聚焦 Agent 工程侧的四个问题：怎么定义（4.2）、怎么选（4.4）、怎么兜错（4.5）、怎么防越权（4.6）。

### 4.2 工具定义的最佳实践

Schema 的语法基础（JSON Schema 字段、Pydantic 生成）见 1.3，这里讲 Agent 侧的差异：**工具定义就是写给模型看的 API 文档**——模型选不选这个工具、参数传得对不对，八成取决于这段定义。

**类比**：工具描述 = 新员工的岗位说明书。只写"处理订单"没人会用；写清"干什么、什么时候来找我、要带什么信息、会返回什么"，新员工（模型）第一天就能上手。

**1. 命名清晰**：

```text
好：search_orders, get_weather, send_email
差：func1, do_stuff, helper
```

**2. 描述要写透**——同一个工具的三种描述写法，效果差一个量级：

| 写法 | 描述示例 | 效果 |
|---|---|---|
| 差 | "查订单" | 模型不知道何时该用，参数含义靠猜 |
| 中 | "查询订单列表" | 会用，但和 get_order_detail 分不清 |
| 好 | "根据用户 ID 和可选状态查询订单列表。用户询问订单状态、历史订单时使用；查单个订单详情用 get_order_detail。返回订单 ID、金额、状态、创建时间" | 何时用、何时不用、返回什么都明确，参数幻觉显著减少 |

"好"写法的完整 Schema（枚举 + 必填 + 默认值三件套）：

```json
{
  "name": "search_orders",
  "description": "根据用户 ID 和可选状态查询订单列表。用户询问订单状态、历史订单时使用；查单个订单详情用 get_order_detail。返回订单 ID、金额、状态、创建时间。",
  "parameters": {
    "type": "object",
    "properties": {
      "user_id": {"type": "string", "description": "用户唯一标识"},
      "status": {
        "type": "string",
        "enum": ["pending", "shipped", "delivered", "cancelled"],
        "description": "订单状态筛选，不传则返回全部"
      },
      "limit": {"type": "integer", "minimum": 1, "maximum": 50, "default": 10}
    },
    "required": ["user_id"],
    "additionalProperties": false
  }
}
```

**3. 参数设计原则**：

- **扁平优先**：嵌套越深，模型越容易出错。
- **枚举优先**：用 `enum` 限制选项，减少幻觉。
- **必填明确**：`required` 标记必填项。
- **默认值合理**：可选参数给默认值。
- **类型严格**：整数就是 integer，不要用 string。
- **描述具体**：每个参数都要有 description，写清单位与格式。

**4. 返回值设计**：

```json
{
  "success": true,
  "data": {},
  "error": null,
  "metadata": {"latency_ms": 120}
}
```

原则：结构化便于 LLM 理解；控制大小，避免几万 token；错误信息要可执行（见 4.5）；敏感信息脱敏。

> 面试高频问法：「工具描述怎么写才稳？」共识口径：写清**何时用、何时不用（与相邻工具的边界）、每个参数的含义与单位、返回什么**，再配合枚举、必填、默认值收紧 Schema。描述本质上是给模型看的 Prompt，不是写给人看的注释。

### 4.3 工具分类

| 类型 | 说明 | 例子 |
|---|---|---|
| 查询类 | 只读，无副作用 | 搜索、查天气、查订单 |
| 计算类 | 纯计算 | 计算器、单位转换 |
| 写入类 | 有副作用 | 发邮件、创建订单 |
| 操作类 | 改变外部状态 | 删除、转账、部署 |
| 通信类 | 与外部交互 | API 调用、消息推送 |
| 代码类 | 执行代码 | Python 沙箱、SQL |
| 浏览器类 | 网页操作 | 点击、填表、截图 |

**按风险分级**：

```text
低风险：查询、计算 → 可直接执行
中风险：写入、通信 → 需校验 + 幂等
高风险：删除、转账 → 需人工审批
```

### 4.4 工具选择策略

**策略 1：全量传入** —— 所有工具都传给 LLM。

- 优点：简单，无路由损耗。
- 缺点：工具多了模型选择困难，token 消耗大。
- 适用：工具 < 10 个。

**策略 2：分组路由** —— 按任务类型分组，先路由再传工具：

```text
用户输入 → 意图分类 → 选择工具组 → 只传入该组工具
```

**策略 3：检索式选择** —— 用嵌入（Embedding）把用户输入与每个工具的描述向量化，检索最相关的 top-k 个传入（实现见 6.4）。

**策略 4：分层工具** —— 一级只给少量通用工具（search、calculate），二级工具通过一级工具动态发现，用一次额外调用换取选择面可控。

**工程建议**：

> 单次传入工具不超过 20 个；超过就用路由或检索。同时把工具间的边界写进描述（见 4.2），否则路由对了照样选错。

### 4.5 工具调用错误处理

**错误分类与处理策略**：

| 错误 | 原因 | 可重试 | 处理 |
|---|---|---|---|
| 参数错误 | 模型传错类型、缺字段、编造枚举值 | 否 | 校验拒绝，错误反馈给 LLM 修正后重调 |
| 权限错误 | 用户无权限 | 否 | 拒绝并告知用户 |
| 超时 | 工具执行慢 | 是 | 超时上限 + 指数退避重试 + 降级 |
| 服务错误 | 外部 API 故障 | 有限次 | 重试 + 熔断 |
| 业务错误 | 订单不存在等 | 否 | 返回明确错误给 LLM 转述 |
| 限流 | 调用太频繁 | 是 | 退避重试，尊重限流响应头 |

**参数幻觉（hallucinated arguments）**：模型编造不存在的枚举值、猜参数格式，是工具调用最高频的失败模式。三层防线：Schema 收紧（enum、required、additionalProperties:false）；入口校验直接拒绝，不进业务系统；错误反馈自修正——把错误讲清楚回给模型，多数一轮就能改对：

```python
tool_result = {
    "success": False,
    "error": "参数 status 必须是 pending/shipped/delivered/cancelled 之一，你传了 'unknown'",
    "suggestion": "请重新选择正确的 status",
}
```

**重试与幂等**：可重试的错误用指数退避（Exponential Backoff），连续失败达到阈值就熔断（Circuit Breaker）、走降级。写入类工具天然不幂等（Idempotency），**重试前必须带幂等键（Idempotency Key）**，否则超时重试一次就是重复扣款：

```python
async def call_with_retry(tool, args: dict, max_retries: int = 3):
    key = make_idempotency_key(tool.name, args)    # 写入类工具先生成幂等键
    for attempt in range(max_retries):
        try:
            return await tool(args, idempotency_key=key)
        except RetryableError:                      # 超时/限流/5xx：退避后重试
            await asyncio.sleep(2 ** attempt)       # 1s / 2s / 4s
        except NonRetryableError as e:              # 参数/权限/业务错误：不重试
            return {"success": False, "error": str(e)}
    return {"success": False, "error": "重试耗尽，已熔断降级"}
```

**类比**：幂等键 = 收银台的小票号。网络卡了重刷一次，收银系统认出是同一张小票，不会扣两次钱。

### 4.6 工具权限与安全：五层防御

锚点关键问题的正面回答：**如何安全、可靠地调用外部系统？** 核心原则一句话：**模型输出永远只是建议，不是授权**。五层防御，每层挡不同的风险：

| 防御层 | 机制 | 挡住什么 |
|---|---|---|
| 1. 参数校验 | JSON Schema / Pydantic 在入口校验类型、范围、枚举、必填 | 参数幻觉、类型错误打进业务系统 |
| 2. 超时与重试 | 每个工具有超时上限；可重试错误指数退避，超阈值熔断降级 | 外部系统抖动拖死整个 Agent |
| 3. 幂等 | 写入类工具带幂等键，重试不产生重复副作用 | 重试导致重复扣款、重复下单 |
| 4. 最小权限 | 白名单（Allowlist）+ 角色权限（RBAC）+ 高危审批 + 沙箱 | 越权调用、破坏面扩大 |
| 5. 审计 | 每次调用留痕：谁、调了什么、参数、结果、耗时，可回放 | 出问题无法定责、无法排查 |

第 4 层展开成四种权限模型，按工具风险选型：

| 权限模型 | 判定依据 | 适用工具 | 开销 |
|---|---|---|---|
| 静态白名单 | 工具在不在允许列表 | 只读查询类 | 最低 |
| 角色权限（RBAC，Role-Based Access Control） | 用户角色 × 工具授权矩阵 | 常规业务工具 | 低 |
| 阈值审批（人在回路，Human-in-the-Loop） | 高风险或金额超阈值，人确认后再执行 | 退款、删除、转账 | 高，引入等待 |
| 沙箱（Sandbox） | 代码/文件/SQL 在受限环境执行 | 代码执行类（见 4.3） | 中 |

白名单与 RBAC 的实现已内嵌在 6.1 的 Tool 类里（permissions 字段 + 入口检查）；审批的典型写法：

```python
HIGH_RISK_TOOLS = {"refund", "delete_account", "transfer"}

async def execute_with_approval(tool_name: str, args: dict, user):
    if tool_name in HIGH_RISK_TOOLS:
        approval = await request_human_approval(tool_name, args, user)
        if not approval:
            return {"success": False, "error": "人工审批未通过"}
    return await execute_tool(tool_name, args)
```

**Schema 校验不等于安全**：参数合法不等于意图安全。`refund(order_id, amount)` 每个字段都通过校验，仍可能是"给别人的订单退款"——校验管格式，权限与对象归属校验管"该不该做"。

> 面试高频问法：「有 Schema 为什么还会不安全？」共识口径：Schema 只保证参数格式合法，不判断调用意图与对象归属；提示注入的诱导、越权对象、合法范围内的恶意操作，都要靠最小权限 + 归属校验 + 高危审批兜底。注入攻防见 2.9，系统级认证授权审计见 3.8。

### 4.7 MCP（Model Context Protocol）：工具接入的标准化

MCP 是 Anthropic 2024 年 11 月开源发布的**标准化工具接入协议**。

**核心思想**：

```text
传统：每个 Agent 自己定义工具，M 个应用 × N 个工具 = M×N 份胶水代码
MCP：工具以标准协议暴露，任何支持 MCP 的 Agent 都能接入
```

**架构**：

```text
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  MCP Client │ ←→  │  MCP Server │ ←→  │  外部系统   │
│  (Agent 侧) │     │  (工具提供) │     │  (API/DB)   │
└─────────────┘     └─────────────┘     └─────────────┘
```

**MCP Server 提供三类能力**：Tools（可调用的函数）、Resources（可读取的数据）、Prompts（预定义提示模板）。

**工具定义侧的实务**——工具方实现一次 Server，工具的发现（list_tools）与调用（call_tool）都走标准协议；Agent 侧拿到标准 Schema 后可直接转成模型的 tools 参数：

```python
# 工具方：用 MCP Server 把工具暴露给任何支持 MCP 的 Agent
from mcp.server import Server
from mcp.types import Tool, TextContent

server = Server("knowledge-base")

@server.list_tools()                  # 发现：Agent 启动时拉取工具清单
async def list_tools() -> list[Tool]:
    return [
        Tool(
            name="search_docs",
            description="搜索知识库",
            inputSchema={
                "type": "object",
                "properties": {
                    "query": {"type": "string"},
                    "top_k": {"type": "integer", "default": 5},
                },
                "required": ["query"],
            },
        )
    ]

@server.call_tool()                   # 调用：参数与结果走标准协议
async def call_tool(name: str, arguments: dict) -> list[TextContent]:
    if name == "search_docs":
        results = await do_search(arguments["query"], arguments.get("top_k", 5))
        return [TextContent(type="text", text=json.dumps(results, ensure_ascii=False))]
```

**价值**：标准化（一次开发、多处使用）、解耦（工具与 Agent 独立演进）、生态（社区共享现成 Server）。

两个定位认知：

- **MCP 不取代 Function Calling**：FC 是模型侧的调用机制，MCP 解决工具供给侧的"从哪来、Schema 谁维护、如何被发现"。截至 2026 年，主流模型厂商与编排框架大多已提供 MCP 支持。
- **协议标准化不等于安全自动成立**：MCP 只管"接得上"，鉴权、审计、沙箱仍由应用与网关层负责（见 3.8）。

框架层的深入对比（MCP 与 LangGraph 等编排框架的关系、与 A2A 协议的分工）见 3.3；MCP 能否成为统一的"工具 USB 口"属趋势观察，落地时按官方文档核实当前版本。

### 4.8 工具结果处理

**1. 结果截断**：

```python
def truncate_result(result: str, max_tokens: int = 2000) -> str:
    tokens = encode(result)
    if len(tokens) > max_tokens:
        return decode(tokens[:max_tokens]) + "\n...[截断]"
    return result
```

**2. 结果摘要**：

```python
async def summarize_result(result: str, max_length: int = 500) -> str:
    if len(result) < max_length:
        return result
    return await call_llm(f"请把以下内容压缩到 {max_length} 字以内：\n{result}")
```

**3. 结果结构化**：按工具定制返回字段，只回模型需要的列——查订单只回 id/status/amount，不把整行数据库记录丢回去。

一句话：**回给模型的每一段工具结果都在消耗上下文预算**，上下文管理策略见 1.5。

### 4.9 并行工具调用与 DAG 调度

当多个工具调用无依赖时，并行执行：

```python
import asyncio

async def execute_parallel(tool_calls: list, tool_map: dict):
    async def run_one(tc):
        fn = tool_map[tc.function.name]
        args = json.loads(tc.function.arguments)
        try:
            return await fn(**args)
        except Exception as e:
            return {"error": str(e)}

    tasks = [run_one(tc) for tc in tool_calls]
    return await asyncio.gather(*tasks)
```

**收益**：

```text
串行：3 个工具 × 500ms = 1500ms
并行：max(500ms) = 500ms
```

并行与依赖的总原则：**无依赖并行、有依赖按 DAG（Directed Acyclic Graph，有向无环图）编排**——每轮取出"依赖已全部完成"的就绪步骤并行跑，其余等待。判断依赖的依据很简单：后一个调用是否用到前一个调用的结果参数。工具级如此，步骤级同理（DAG 执行器实现见 2.5）。

### 4.10 工具评估

| 指标 | 含义 |
|---|---|
| 工具选择准确率 | 选对工具的比例 |
| 参数准确率 | 参数正确的比例 |
| 调用成功率 | 执行成功的比例 |
| 平均调用次数 | 完成任务用几次工具 |
| 错误恢复率 | 失败后能恢复的比例 |
| 延迟 | 工具执行时间 |
| 成本 | 工具调用成本 |

**评估方法**：

```python
eval_cases = [
    {"input": "北京天气怎么样？", "expected_tool": "get_weather", "expected_args": {"city": "北京"}},
    {"input": "查一下我的订单", "expected_tool": "search_orders", "expected_args": {"user_id": "u1"}},
]

def evaluate_tool_selection(agent, cases):
    correct_tool = 0
    correct_args = 0
    for case in cases:
        result = agent.run(case["input"])
        if result.tool_name == case["expected_tool"]:
            correct_tool += 1
            if result.args == case["expected_args"]:
                correct_args += 1
    return {
        "tool_accuracy": correct_tool / len(cases),
        "args_accuracy": correct_args / len(cases),
    }
```

注意：只看最终答案会漏掉中间的工具调用错误，轨迹级评估（Trajectory Evaluation）见 2.9。

## 6. 代码 / 工具

### 6.1 工具注册与执行框架

```python
import json
import asyncio
from typing import Callable
from pydantic import BaseModel

class Tool:
    def __init__(
        self,
        name: str,
        description: str,
        func: Callable,
        args_model: type[BaseModel],
        risk_level: str = "low",
        permissions: list[str] = None,
    ):
        self.name = name
        self.description = description
        self.func = func
        self.args_model = args_model
        self.risk_level = risk_level
        self.permissions = permissions or ["user"]

    def to_openai_schema(self) -> dict:
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": self.args_model.model_json_schema(),
            }
        }

    async def execute(self, args: dict, user_role: str) -> dict:
        # 第 4 层防御：权限检查（模型说调不等于用户被授权调）
        if user_role not in self.permissions:
            return {"success": False, "error": f"无权限调用 {self.name}"}

        # 第 1 层防御：参数校验（不合法直接拒绝，不进业务系统）
        try:
            validated = self.args_model(**args)
        except Exception as e:
            return {"success": False, "error": f"参数错误: {e}"}

        # 执行（真实系统在此接入第 2/3 层：超时、重试、幂等键）
        try:
            result = await self.func(**validated.model_dump())
            return {"success": True, "data": result}
        except Exception as e:
            return {"success": False, "error": str(e)}


class ToolRegistry:
    def __init__(self):
        self.tools: dict[str, Tool] = {}

    def register(self, tool: Tool):
        self.tools[tool.name] = tool

    def get_schemas(self, tool_names: list[str] = None) -> list[dict]:
        names = tool_names or list(self.tools.keys())
        return [self.tools[n].to_openai_schema() for n in names if n in self.tools]

    async def execute(self, tool_name: str, args: dict, user_role: str) -> dict:
        tool = self.tools.get(tool_name)  # 白名单：没注册的工具一律拒绝
        if not tool:
            return {"success": False, "error": f"工具 {tool_name} 不存在"}
        return await tool.execute(args, user_role)
```

### 6.3 完整的 Agent + 工具循环

工具结果（含错误信息）回填给模型，形成"调用 → 反馈 → 自修正"闭环；循环本身的时序细节见 1.3、终止控制见 2.5：

```python
async def agent_with_tools(
    user_input: str,
    registry: ToolRegistry,
    user_role: str = "user",
    max_steps: int = 10,
) -> str:
    messages = [{"role": "user", "content": user_input}]
    schemas = registry.get_schemas()

    for step in range(max_steps):
        response = await client.chat.completions.create(
            model="gpt-4o-mini",
            messages=messages,
            tools=schemas,
            tool_choice="auto",
            temperature=0,
        )
        msg = response.choices[0].message

        if not msg.tool_calls:          # 模型不再调工具 = 给出最终回答
            return msg.content

        messages.append(msg)

        # 本轮多个工具调用无依赖时并行执行
        async def run_tool(tc):
            args = json.loads(tc.function.arguments)
            result = await registry.execute(tc.function.name, args, user_role)
            return tc.id, result

        results = await asyncio.gather(*[run_tool(tc) for tc in msg.tool_calls])

        for tool_call_id, result in results:
            messages.append({           # 结果或错误信息都回给模型
                "role": "tool",
                "tool_call_id": tool_call_id,
                "content": json.dumps(result, ensure_ascii=False),
            })

    return "达到最大步数。"
```

### 案例 B：工具选择优化

**问题**：Agent 有 30 个工具，经常选错。

**优化**：

1. 按任务分组：订单组、支付组、账户组、FAQ 组。
2. 先意图分类，再传入对应组的工具。
3. 每组不超过 8 个工具。
4. 相邻工具的边界写进描述（见 4.2）。

**效果（示意数字）**：工具选择准确率从 65% 提升到 92%，单次请求消耗在工具 Schema 上的 token 约降一半。

### 案例 C：工具错误自动恢复

**场景**：`search_orders` 参数 `status` 被模型传了 `"unknown"`。

**处理**：

## 8. 常见坑

1. **工具描述太简单**。  
   模型不知道何时用、怎么用、和谁区分，容易选错。按 4.2 对比表的"好"写法补齐何时用、边界、返回结构。

2. **参数 Schema 太宽松**。  
   不加 enum、required、additionalProperties:false，模型自由发挥，参数错误率高。逐字段收紧。

3. **工具太多不路由**。  
   30 个工具全传入，选择困难、token 翻倍。超过 20 个就分组路由或检索（见 4.4）。

4. **不做参数校验**。  
   模型传错类型直接打到下游，业务系统崩溃。入口 Pydantic 校验，不合法不执行（见 1.3）。

5. **不做权限检查**。  
   模型说调用就调用，越权风险大。白名单 + RBAC，权限在业务侧判定（见 4.6、6.1）。

6. **高风险操作无审批**。  
   退款、删除、转账直接执行，出事无法挽回。加人工审批与金额阈值（Human-in-the-Loop）。

7. **非幂等工具盲目重试**。  
   超时重试一次就重复扣款、重复下单。写入类工具先带幂等键再重试（见 4.5）。

8. **把 Schema 校验当安全**。  
   参数合法不等于意图安全，合法的退款请求也能退别人的订单。加对象归属校验与高危审批（见 2.9）。

9. **工具结果太大**。  
   一次返回几万 token，上下文爆炸、成本飙升。截断、摘要、按需裁剪字段（见 4.8）。

10. **可并行的工具串行执行**。  
    三个无依赖查询排队跑，延迟三倍。用 asyncio.gather 并行（见 4.9）。

11. **不处理工具失败**。  
    工具挂了 Agent 卡死。按可重试分类处理：退避重试、熔断、降级（见 4.5）。

12. **不做工具调用日志**。  
    出问题无法追踪是谁、传了什么参数。每次调用留审计字段并接 trace（见 3.4）。

13. **工具版本不管理**。  
    改了工具行为，线上 Agent 行为悄悄变化。工具定义与实现变更走版本化与回归（见 3.9）。

14. **沙箱不安全**。  
    代码执行工具没隔离，可能执行恶意代码、读写敏感目录。限时限网限目录（见 4.3）。

15. **忽略 MCP 标准化**。  
    每个工具单独适配一遍 Agent，重复劳动。用 MCP 一次暴露、多处接入（见 4.7、3.3）。

16. **把工具当万能**。  
    工具解决执行问题，不解决决策问题。决策质量靠规划与模型能力（见 2.2），加工具修不了决策。

## 10. 小结

- 工具 = Agent 的手脚：LLM 原生能力之外的行动力，全部来自工具扩展。
- 生命周期：**定义 → 注册 → 选择 → 调用 → 校验 → 执行 → 返回 → 记录 → 错误处理**。
- 工具定义 = 写给模型的 API 文档：**命名清晰、描述写透（何时用/边界/返回）、参数扁平、枚举优先、Schema 严格**。
- 工具选择：**全量 → 分组路由 → 检索式 → 分层**，单次传入不超过 20 个。
- 五层防御正面回答"如何安全、可靠地调用外部系统"：**参数校验、超时重试、幂等、最小权限、审计**。
- **Schema 校验不等于安全**：参数合法不等于意图安全，归属与意图靠权限层和审批兜底。
- 错误处理：**可重试分类、错误反馈自修正（治参数幻觉）、指数退避、熔断降级**。
- 性能：**无依赖并行 + DAG 依赖编排、结果截断与摘要**。
- 标准化：**MCP 解决工具供给侧，不取代 Function Calling**；框架深入见 3.3。
- 评估：**选择准确率、参数准确率、调用成功率、错误恢复率**；轨迹级评估见 2.9。
- 这些能力直接支撑：2.5 执行循环与状态机、3.3 编排框架与运行时、4.4 浏览器与计算机使用 Agent。
