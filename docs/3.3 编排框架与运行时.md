# 讲解 3.3 编排框架与运行时

> 说明：2.5 讲清了执行循环与状态机的原理，3.1 定了系统的分层与接口边界。  
> 3.3 讲**承载它们的"胶水"**：编排框架与运行时——用什么框架、怎么选、怎么不被锁死。  
> 选型结论会在 3.9 的发布管线与 4.x 实战篇（如 4.6 多 Agent 协作系统、4.7 生产级 Agent 平台）直接落地。

---

## 1. 定位

AI 工程化层第 3 个知识点，属于"工具选型与运行时基础设施"（选修锚点，建议掌握程度：会用）。
它解决一个核心问题：**Agent 的循环、状态、工具、记忆、多 Agent 协作，用自研代码写，还是用框架？用哪个框架？怎么避免被框架锁定？**

与 2.5 的分工：循环与状态机的**原理**（为什么需要 while、检查点、终止条件）归 2.5；本篇讲**用什么框架承载**这些原理，以及运行时工程——部署形态、检查点存储（Checkpointer）、中断恢复、人工介入在框架中的落地。

前置：2.5 执行循环与状态机、3.1 架构与接口设计。后续：3.9 CI/CD、版本管理与发布，以及 4.x 实战篇。

## 2. 一句话定义

编排框架与运行时（Orchestration Framework & Runtime），是把执行循环、状态管理、工具集成、多 Agent 协调、持久化与恢复做成可复用工程基础设施的软件层，让开发者聚焦业务逻辑，不必每个项目从零实现底层机制。

简化公式：

```text
编排框架 = 执行引擎 + 状态管理 + 工具集成 + 持久化 + 可观测性
```

## 3. 为什么需要

自研 Agent 循环的痛点（每条都是 2.5 手写示例里"没写就翻车"的点）：

- **重复造轮子**：每个项目都写一遍 while 循环、状态管理、重试逻辑。
- **状态管理复杂**：中断恢复、检查点、并发控制，手写容易出错。
- **工具集成繁琐**：每个工具都要适配 JSON Schema、参数校验、错误处理（见 1.3、2.3）。
- **多 Agent 协调难**：通信、路由、终止条件，从零实现成本高（见 2.8）。
- **缺乏可观测性**：没有 trace、没有指标，出问题难定位（见 3.4）。
- **难以扩展**：加一个工具要改核心代码，改一个模型要动多处。
- **框架锁定风险**：选了某个框架，业务逻辑和它深度耦合，换框架成本极高。

自研 vs 框架对比：

| 维度 | 自研循环 | 成熟框架 |
|---|---|---|
| 首版速度 | 慢，先写循环/检查点/重试 | 快，核心能力开箱即用 |
| 状态持久化 | 全部手写，容易漏边界情况 | Checkpointer / Session 内置 |
| 中断恢复与人工介入 | 自行设计存档与恢复 | interrupt / 审批原语现成 |
| 可观测性 | 自建埋点 | 与主流 trace 平台预集成 |
| 学习与升级成本 | 无框架 API，但底层机制自己背 | 要学框架抽象，升级要跟进 |
| 锁定风险 | 无 | 有，需抽象层缓解 |
| 适合 | 极简场景、深度定制、学原理 | 大多数生产场景 |

判断口径：循环步数少（3 步以内）、无持久化与人工介入需求 → 自研 while 足够（写法见 2.5）；需要检查点、恢复、多 Agent、长任务 → 框架收益显著。

**类比 1（自研 vs 框架）**：

```text
自研 Agent 循环 = 自己造发动机：曲轴、喷油、散热，每个零件都要设计
编排框架       = 买成熟的发动机总成：你只管踩油门和换机油
```

**类比 2（框架锁定）**：

```text
锁定   = 装修全用某品牌的异形定制柜：入住顺手，十年后想换，尺寸只匹配原厂
防锁定 = 当年坚持标准尺寸柜体：门板坏了，谁家的都能配上
```

## 4. 核心原理

### 4.1 编排框架的五大能力

| 能力 | 说明 | 原理出处 |
|---|---|---|
| 执行循环 | 驱动 Agent 的 while 循环 | 2.5 |
| 状态管理 | 保存、恢复、检查点 | 2.5 |
| 工具集成 | 工具注册、Schema 生成、执行 | 2.3 |
| 多 Agent 协调 | 角色、通信、路由 | 2.8 |
| 可观测性 | Trace、日志、指标 | 3.4 |

框架没有发明新原理——它把 2.5 的循环、检查点、终止条件做成了标准件。这也是本篇与 2.5 的分界：原理归 2.5，标准件的形状与选型归本篇。

### 4.2 主流框架格局（截至 2026 年）

| 框架 | 抽象模型 | 状态与持久化 | 多 Agent | 学习曲线 | 锁定风险 | 适用场景 |
|---|---|---|---|---|---|---|
| **LangGraph** | 状态图（StateGraph） | 强，Checkpointer 内置 | 强 | 中高 | 中：模型无关，但 API 绑定 LangChain 生态 | 生产级复杂 Agent |
| **LlamaIndex Workflows** | 事件驱动（Event-driven） | 中强，Context + 事件流 | 中 | 中 | 中：与 LlamaIndex 检索生态亲和 | RAG + 文档处理 |
| **OpenAI Agents SDK** | Agent + Runner + Handoff | 中，Session 会话级 | 中 | 低 | 中高：多模型可用，但官方生态最顺 | 快速原型、多 Agent 交接 |
| **CrewAI** | 角色团队（Crew/Task） | 中 | 强 | 低 | 中 | 角色分工协作 |
| **AutoGen / Microsoft Agent Framework** | 对话驱动 → 统一框架 | 中 | 强 | 中 | 中：并入微软官方主线 | 研究、复杂对话、.NET 生态 |
| **Dify** | 可视化编排 | 强 | 中 | 低 | 高：平台绑定，导出受限 | 低代码场景 |

时效核对（截至 2026 年，以下均为公开信息）：

- **OpenAI**：实验性项目 Swarm 已于 2025 年 3 月归档，官方指向 Agents SDK（来源：OpenAI 官方仓库与社区迁移指南，2025）。看到 2024 年前后的 Swarm 教程，直接按 Agents SDK 口径更新。
- **Microsoft**：AutoGen 与 Semantic Kernel 于 2025 年 10 月宣布合并为 Microsoft Agent Framework——AutoGen 的简洁 Agent 抽象 + Semantic Kernel 的企业特性（会话状态管理、类型安全），此后是微软系的官方主线（来源：Microsoft DevBlogs 公告，2025；Microsoft Learn 文档更新至 2026 年 8 月）。
- **LangGraph**：复杂 Agent 生产编排的事实主力之一；本篇代码按其当前 API 口径写（START 显式连边、Checkpointer 用上下文管理器初始化）。
- **趋势观察**：轻量类型安全框架（如 PydanticAI）、云厂商自带框架（如 Google ADK）、TypeScript 系编排（如 Mastra）在 2026 年选型讨论中出现频率上升，格局仍在演化，未成定局。

一句话结论：**框架层是快变量，概念层是慢变量**。循环、状态、检查点、协议这些概念十年不变；具体框架两三年一轮换。把原理（2.5）学扎实，用哪个框架都上手快。

### 4.3 LangGraph 核心概念

LangGraph 用**状态图（StateGraph）**建模 Agent 工作流：把 2.5 的状态机画成一张显式的图。

**三个核心抽象**：

```text
State（状态）：图的全局状态，节点可读写
Node（节点）：一个执行步骤，可以是 LLM 调用、工具执行、条件判断
Edge（边）  ：节点之间的流转，固定边或条件边（Conditional Edge）
```

**最小示例**（按 2026 年 API 口径）：

```python
from langgraph.graph import StateGraph, START, END
from typing import TypedDict

class State(TypedDict):
    messages: list
    intent: str    # 路由用的意图字段要写进 State：LangGraph 按定义合并状态

def classify(state: State) -> State:
    """分类节点：判断用户意图"""
    intent = classify_intent(state["messages"][-1])
    return {"intent": intent}

def handle_query(state: State) -> State:
    """处理查询节点"""
    result = search(state["messages"][-1])
    return {"messages": state["messages"] + [result]}

def handle_complaint(state: State) -> State:
    """处理投诉节点"""
    result = escalate(state["messages"][-1])
    return {"messages": state["messages"] + [result]}

def route(state: State) -> str:
    """条件边：根据意图路由"""
    return state.get("intent", "query")

graph = StateGraph(State)
graph.add_node("classify", classify)
graph.add_node("query", handle_query)
graph.add_node("complaint", handle_complaint)

# 截至 2026 年的推荐写法：START 显式连边（set_entry_point 已废弃）
graph.add_edge(START, "classify")
graph.add_conditional_edges("classify", route, {
    "query": "query",
    "complaint": "complaint",
})
graph.add_edge("query", END)
graph.add_edge("complaint", END)

app = graph.compile()
```

**关键特性**：

| 特性 | 说明 |
|---|---|
| 状态持久化 | Checkpointer 支持中断恢复 |
| 条件边 | 动态路由 |
| 循环 | 支持 while 循环（边可以指回任意节点） |
| 并行 | Send API 支持 map-reduce |
| 子图 | 图可以嵌套，便于团队分工复用 |
| 人工介入 | interrupt 暂停等待审批（HITL，见 3.10） |

**持久化与恢复示例**：

```python
from langgraph.checkpoint.sqlite import SqliteSaver  # 需单独安装 langgraph-checkpoint-sqlite

# from_conn_string 返回上下文管理器，必须用 with（截至 2026 年）
with SqliteSaver.from_conn_string("checkpoints.db") as memory:
    app = graph.compile(checkpointer=memory)

    config = {"configurable": {"thread_id": "user-123"}}
    result = app.invoke({"messages": ["你好"]}, config)

    # 同一 thread_id 再次 invoke，即从最近检查点恢复（中断恢复）
    result = app.invoke({"messages": ["继续"]}, config)
```

这就是 2.5 手写 FileCheckpointer 的框架版：同一个"存档点"思想，存储引擎从 SQLite 换 Postgres 只需换一行。

### 4.4 LlamaIndex Workflows 核心概念

LlamaIndex Workflows（1.0 起）是**事件驱动（Event-driven）**的轻量级编排框架。

**核心抽象**：

```text
Event（事件）    ：步骤之间的通信载体
Step（步骤）     ：一个处理函数，消费事件、产生事件
Workflow（工作流）：步骤的集合
Context（上下文）：跨步骤共享状态
```

**示例**：

```python
from llama_index.core.workflow import (
    Workflow, StartEvent, StopEvent, Event, step, Context
)

class RetrievedEvent(Event):
    """自定义事件：检索完成，携带文档"""
    docs: list

class RAGWorkflow(Workflow):
    @step
    async def retrieve(self, ctx: Context, ev: StartEvent) -> RetrievedEvent:
        # 检索：RAG 原理见 1.4，此处只看编排
        docs = await retrieve_docs(ev.query)
        await ctx.set("query", ev.query)
        return RetrievedEvent(docs=docs)

    @step
    async def generate(self, ctx: Context, ev: RetrievedEvent) -> StopEvent:
        # 生成：消费 RetrievedEvent，产出最终结果
        answer = await generate_answer(await ctx.get("query"), ev.docs)
        return StopEvent(result=answer)

workflow = RAGWorkflow(timeout=60)
result = await workflow.run(query="退货政策是什么？")
```

**关键特性**：

| 特性 | 说明 |
|---|---|
| 事件驱动 | 步骤之间通过事件解耦 |
| 异步优先 | 原生 async 支持 |
| 并行 | 多个步骤可并行 |
| 循环 | 支持 while 循环 |
| 子工作流 | 工作流可以嵌套 |
| 人机协同 | 支持暂停等待审批 |

**与 LangGraph 的区别**：

| 维度 | LangGraph | LlamaIndex Workflows |
|---|---|---|
| 核心抽象 | 状态图 | 事件驱动 |
| 状态管理 | 显式 State + Reducer | Context + Event |
| 控制流可见性 | 图结构一眼看全 | 控制流隐式藏在事件订阅里 |
| 学习曲线 | 中高 | 中 |
| RAG 集成 | 一般 | 强（原生接 LlamaIndex 检索） |
| 多 Agent | 强 | 中 |

选择口径：要"流程一眼可见、精确控制每一步"选 LangGraph；要"步骤松耦合、以数据管线为主"选 Workflows。

### 4.5 OpenAI Agents SDK 核心概念

OpenAI Agents SDK 是 OpenAI 官方的轻量级 Agent 框架（2025 年发布，取代已归档的 Swarm）。

**核心抽象**：

```text
Agent     ：一个 LLM + 指令 + 工具
Runner    ：驱动 Agent 执行循环
Handoff（交接）  ：Agent 之间的任务转移
Guardrail（护栏）：输入输出安全检查
Session（会话）  ：持久化对话状态
```

**多 Agent 交接**（完整示例见 6.3）：

```python
triage = Agent(
    name="分诊",
    instructions="判断用户问题类型，路由到对应专家。",
    handoffs=[order_agent, refund_agent],
)

result = await Runner.run(triage, "我要退款")
print(result.last_agent.name)  # refund_agent
```

**关键特性**：

| 特性 | 说明 |
|---|---|
| 轻量 | 代码量少，快速上手 |
| Handoff | 原生多 Agent 交接 |
| Guardrail | 输入输出安全检查（原理见 3.8） |
| Session | 对话状态持久化 |
| Trace | 内置可观测性 |

代价：抽象层次低，复杂状态流转要自己在框架外搭；深度使用 OpenAI 生态能力时，迁移成本会升高。

### 4.6 MCP 协议

MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年提出的**标准化工具接入协议**；2025 年 12 月，Anthropic 将其捐赠给 Linux Foundation 旗下新设立的 Agentic AI Foundation（与 Block、OpenAI 共同创建），转入中立治理（来源：Anthropic 官方公告，2025 年 12 月）。截至 2026 年，主流框架均已支持。

**核心思想**：

```text
传统：每个 Agent 自己定义工具，每个工具适配不同 Agent
MCP ：工具以标准协议暴露，任何支持 MCP 的 Agent 都能用
```

**类比**：

```text
MCP 之前 = 早期电脑外设：打印机用并口、键盘用 PS/2、鼠标用串口，每种外设配一种线
MCP 之后 = USB 统一接口：外设厂商做一次 USB 设备，所有电脑都能用
```

**架构**：

```text
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  MCP Host   │ ←→  │  MCP Server │ ←→  │  外部系统   │
│  (Agent)    │     │  (工具提供) │     │  (API/DB)   │
└─────────────┘     └─────────────┘     └─────────────┘
```

**MCP Server 提供三类东西**：

- **Resources**：可读取的数据。
- **Prompts**：预定义提示词模板。
- **Tools**：可调用的函数。

**示例**：

```python
# MCP Server 端：实现一次
from mcp.server import Server

server = Server("my-tools")

@server.tool()
async def search_docs(query: str, top_k: int = 5) -> str:
    """搜索知识库"""
    results = await do_search(query, top_k)
    return format_results(results)

# Agent 端：通过 MCP Client 调用
from mcp.client import Client

async with Client("my-tools") as client:
    tools = await client.list_tools()
    result = await client.call_tool("search_docs", {"query": "退货政策"})
```

**MCP 的价值**：

- **标准化**：一次开发，多处使用。
- **解耦**：工具和 Agent 独立演进。
- **生态**：社区可共享 MCP Server，工具市场成为可能。

### 4.7 A2A 协议

A2A（Agent-to-Agent，Agent 间通信协议）是 Google 于 2025 年提出的跨组织 Agent 协作协议；同年 6 月交由 Linux Foundation 中立治理，截至 2026 年公开支持组织超过 150 家（来源：Linux Foundation 公告，2025 年 6 月；A2A 项目公告，2026 年 4 月）。

**核心思想**：

```text
MCP 解决 Agent ↔ 工具
A2A 解决 Agent ↔ Agent
```

**架构**：

```text
Agent A（客户端）→ A2A 协议 → Agent B（服务端）
```

**核心概念**：

| 概念 | 说明 |
|---|---|
| Agent Card | Agent 的数字名片，描述能力，供发现 |
| Skill | Agent 可执行的特定功能 |
| Task | 一次协作任务 |
| Message | Agent 之间的消息 |

**Agent Card 示例**：

```json
{
  "name": "退款处理 Agent",
  "description": "处理电商退款请求",
  "skills": [
    {
      "id": "process_refund",
      "name": "处理退款",
      "description": "根据订单 ID 发起退款",
      "input_modes": ["text", "json"],
      "output_modes": ["json"]
    }
  ],
  "auth": {"type": "oauth2"}
}
```

**A2A 的价值**：

- **跨平台**：不同厂商的 Agent 可以协作。
- **标准化**：统一的发现、通信、协调机制。
- **安全**：内置认证和授权。

现状判断：MCP 已是事实标准并大规模落地；A2A 声势大、实际生产落地仍在早期（趋势观察）。跨组织协作场景值得跟进，单团队内部优先把 MCP 用好。

### 4.8 协议关系图

```text
┌──────────────────────────────────────────┐
│                应用层                     │
│  Agent 业务逻辑                           │
└──────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────┐
│                编排层                     │
│  LangGraph / LlamaIndex Workflows /      │
│  OpenAI Agents SDK / Agent Framework     │
└──────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────┐
│                协议层                     │
│  MCP（Agent↔工具）  │  A2A（Agent↔Agent）│
└──────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────┐
│                能力层                     │
│  LLM / 工具 / 检索 / 记忆                │
└──────────────────────────────────────────┘
```

分层要点：编排层管"流程怎么走"，协议层管"双方怎么对话"。工具接入与跨 Agent 协作尽量压到协议层（标准、与框架无关），业务流程留在编排层（选型可换）。

### 4.9 框架选型决策树

```text
你的场景是什么？
├─ 需要复杂状态图 + 生产级可靠性（检查点/恢复/审批）
│   → LangGraph
├─ 以 RAG / 文档处理为主
│   → LlamaIndex Workflows
├─ 快速原型 + 多 Agent 交接
│   → OpenAI Agents SDK
├─ 角色分工明确的团队协作
│   → CrewAI
├─ 研究型、对话驱动的多 Agent / .NET 生态
│   → Microsoft Agent Framework（原 AutoGen / Semantic Kernel）
├─ 低代码、可视化
│   → Dify
└─ 循环 3 步以内、无持久化、想彻底掌控
    → 自研（写法见 2.5）
```

**面试高频问法**：「你为什么选 / 不选 LangGraph？LangGraph、OpenAI Agents SDK、自研循环怎么选？换框架要改多少代码？」共识口径：先讲需求——是否需要显式状态图、人工介入、长任务持久化；再讲代价——学习曲线中高、与 LangChain 生态耦合；最后给分层结论——重状态机用 LangGraph，轻任务用 Agents SDK，极简场景自研。能答出"删掉这个框架会坏什么"（丢检查点、丢 interrupt、丢可视化调试）是资深信号。

### 4.10 避免框架锁定

锚点关键问题的正面回答。锁定不是"不用框架"，而是**换框架时哪些资产必须扔掉**；目标是把"必须扔掉的部分"压到最小。

**原则 1：业务逻辑与框架解耦**

```python
# 不推荐：业务逻辑写在 LangGraph 节点里
def node(state):
    result = business_logic(state["input"])  # 业务规则散落在节点里
    return {"result": result}

# 推荐：业务逻辑独立成服务，框架只做编排
class BusinessService:
    def process(self, input: str) -> dict:  # 纯业务逻辑，可单测
        ...

def langgraph_node(state):
    return {"result": business_service.process(state["input"])}
```

**原则 2：用接口抽象框架**

```python
class AgentRuntime(ABC):
    @abstractmethod
    async def run(self, input: str) -> dict:
        pass

class LangGraphRuntime(AgentRuntime):
    async def run(self, input: str) -> dict:
        return await self.app.ainvoke({"input": input})

class CustomRuntime(AgentRuntime):
    async def run(self, input: str) -> dict: ...  # 自研循环，写法见 2.5
```

**原则 3：配置驱动**

```yaml
runtime:
  framework: langgraph  # 一行切换实现
  config:
    checkpoint: sqlite
    max_steps: 20
```

**原则 4：可迁移的资产用标准格式**

- 提示词（Prompt）存文件、入版本库，不硬编码在框架代码里（版本管理见 3.9）。
- 工具用标准 JSON Schema 或直接走 MCP，不依赖框架私有装饰器。
- 状态用标准数据结构（dict / JSON），不依赖框架特有类型。
- 观测数据按 OpenTelemetry 语义约定（Semantic Conventions）导出：截至 2026 年，OTel 的 gen_ai.* 约定已完成标准化并被主流观测平台广泛支持，"观测走 OTel 标准"是企业防锁定的共识做法（详见 3.4）。

**迁移成本评估表（选型时就要算，不是迁移时才算）**：

| 评估维度 | 低迁移成本信号 | 高迁移成本信号 |
|---|---|---|
| 业务逻辑位置 | 独立 Service，节点只做转发 | 规则散落在节点/装饰器里 |
| 状态定义 | 标准 dict + JSON Schema | 框架特有 State 类与 Reducer |
| 工具定义 | 标准 Schema / MCP | 框架私有类型与注册机制 |
| 观测数据 | OTel gen_ai.* 标准导出 | 只进框架自家平台 |
| 评估集 | 框架无关的输入/期望输出对（见 3.5） | 与框架对象深度绑定 |
| 团队技能 | 掌握 2.5 原理，能换框架重写 | 只会某个框架的 API |

**面试高频问法**：「怎么避免被某个编排/观测框架锁定？标准在哪？」共识口径是四层防锁：业务逻辑独立成模块；运行时用自有接口（AgentRuntime）包装；工具与协作走开放协议（MCP / A2A）；观测走 OTel gen_ai.* 标准导出。再加一条：评估集（见 3.5）框架无关——换框架后跑同一套评估集，行为一致才算迁移成功。

## 5. 架构 / 流程

一个框架无关的 Agent 运行时分层：业务层只认识抽象层，适配层把抽象翻译给具体框架。

```text
┌──────────────────────────────────────────┐
│  业务层                                   │
│  Agent 业务逻辑、Prompt、工具定义          │
└──────────────────────────────────────────┘
                  ↓ 只调用抽象层接口
┌──────────────────────────────────────────┐
│  抽象层（自研，刻意做薄）                 │
│  ├─ AgentRuntime 接口（run / resume）    │
│  ├─ ToolRegistry 接口（注册 / 查找）     │
│  ├─ StateStore 接口（检查点存取）        │
│  └─ Observability 接口（OTel 导出）      │
└──────────────────────────────────────────┘
                  ↓ 被适配层实现
┌──────────────────────────────────────────┐
│  适配层                                   │
│  ├─ LangGraphAdapter                     │
│  ├─ LlamaIndexAdapter                    │
│  └─ CustomAdapter（自研循环，见 2.5）    │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  框架层                                   │
│  LangGraph / LlamaIndex / OpenAI SDK /   │
│  Microsoft Agent Framework               │
└──────────────────────────────────────────┘
```

要点：抽象层刻意做薄——只定义接口、不含逻辑；否则它会膨胀成"自研框架"，防锁定变成造锁定。

## 6. 代码 / 工具

### 6.1 LangGraph 完整示例（Plan-Execute-Replan）

2.5 的混合循环（规划 → 执行 → 必要时重规划）用 LangGraph 落地：

```python
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.sqlite import SqliteSaver  # 需单独安装 langgraph-checkpoint-sqlite
from typing import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    messages: Annotated[list, operator.add]  # Reducer：多节点结果追加而非覆盖
    plan: list
    current_step: int
    results: dict
    error: str

def planner(state: AgentState):
    plan = generate_plan(state["messages"][-1])
    return {"plan": plan, "current_step": 0, "results": {}}

def executor(state: AgentState):
    step = state["plan"][state["current_step"]]
    try:
        result = execute_step(step)
        return {
            "results": {**state["results"], step["id"]: result},
            "current_step": state["current_step"] + 1,
        }
    except Exception as e:
        return {"error": str(e)}

def should_continue(state: AgentState) -> str:
    if state.get("error"):
        return "replan"
    if state["current_step"] >= len(state["plan"]):
        return "end"
    return "execute"

def replan(state: AgentState):
    new_plan = generate_plan(state["messages"][-1], error=state["error"])
    return {"plan": new_plan, "current_step": 0, "error": ""}

graph = StateGraph(AgentState)
graph.add_node("planner", planner)
graph.add_node("executor", executor)
graph.add_node("replan", replan)

# START 显式连边（2026 年口径，set_entry_point 已废弃）
graph.add_edge(START, "planner")
graph.add_edge("planner", "executor")
graph.add_conditional_edges("executor", should_continue, {
    "execute": "executor",
    "replan": "replan",
    "end": END,
})
graph.add_edge("replan", "executor")

# Checkpointer 必须用 with 初始化（2026 年口径）
with SqliteSaver.from_conn_string("checkpoints.db") as memory:
    app = graph.compile(checkpointer=memory)
    config = {"configurable": {"thread_id": "task-123"}}
    result = app.invoke({"messages": ["分析销售数据"]}, config)
```

对照 2.5 手写循环：终止条件变成条件边的返回值，检查点变成 checkpointer，循环本身消失在图结构里——代码量减半，能力翻倍。

### 6.2 LlamaIndex Workflows 示例（研究型任务）

```python
import asyncio
from llama_index.core.workflow import (
    Workflow, StartEvent, StopEvent, Event, step, Context
)

class PlannedEvent(Event):
    """自定义事件：规划完成，携带信息源列表"""
    sources: list

class ResearchWorkflow(Workflow):
    @step
    async def plan(self, ctx: Context, ev: StartEvent) -> PlannedEvent:
        # 规划：决定用哪些信息源
        plan = await generate_plan(ev.topic)
        await ctx.set("topic", ev.topic)
        return PlannedEvent(sources=plan["sources"])

    @step
    async def search(self, ctx: Context, ev: PlannedEvent) -> StopEvent:
        # 并行检索 + 汇总
        topic = await ctx.get("topic")
        results = await asyncio.gather(*[
            search(source, topic) for source in ev.sources
        ])
        report = await generate_report(topic, results)
        return StopEvent(result=report)

workflow = ResearchWorkflow(timeout=120)
result = await workflow.run(topic="AI Agent 市场")
```

### 6.4 同一任务、两种框架

任务：客服分诊——"查订单"走订单工具，"退款"走退款 Agent。同一个需求，两种承载方式：

```python
# 实现 A：LangGraph——路由是图里一条显式的条件边（classify 节点同 4.3）
def route(state: State) -> str:
    return "refund" if "退款" in state["messages"][-1] else "order"

graph = StateGraph(State)
graph.add_node("order", order_node)
graph.add_node("refund", refund_node)
graph.add_edge(START, "classify")
graph.add_conditional_edges("classify", route, {"order": "order", "refund": "refund"})

# 实现 B：OpenAI Agents SDK——路由是 LLM 决定的一次 Handoff
triage = Agent(name="分诊", instructions="判断问题类型并交接。",
               handoffs=[order_agent, refund_agent])
result = await Runner.run(triage, user_question)
```

| 维度 | LangGraph 实现 | OpenAI Agents SDK 实现 |
|---|---|---|
| 路由由谁决定 | 代码里的条件边，确定性 | LLM 判断 Handoff，概率性 |
| 改路由的成本 | 改 route 函数，可单测 | 改分诊 Agent 指令，需回归测试 |
| 状态可见性 | 显式 State，每步可检查点 | 隐式在 Runner 内部，Session 粒度 |
| 适合 | 规则明确、要审计的生产流程 | 对话开放、路由本身需要智能 |

这是选型的最小实验：拿你的真实任务在两个框架各写一遍，答案往往自己浮现。

### 6.5 框架抽象层

把 4.10 的原则落成代码（接口保持最小）：

```python
from abc import ABC, abstractmethod
from uuid import uuid4

class AgentRuntime(ABC):
    @abstractmethod
    async def run(self, input: str, config: dict = None) -> dict:
        pass

    @abstractmethod
    async def resume(self, checkpoint_id: str) -> dict:
        pass

class LangGraphRuntime(AgentRuntime):
    def __init__(self, app):
        self.app = app

    async def run(self, input: str, config: dict = None) -> dict:
        config = config or {"configurable": {"thread_id": str(uuid4())}}
        result = await self.app.ainvoke({"input": input}, config)
        return {"result": result, "thread_id": config["configurable"]["thread_id"]}

    async def resume(self, checkpoint_id: str) -> dict:
        config = {"configurable": {"thread_id": checkpoint_id}}
        return await self.app.ainvoke(None, config)

class CustomRuntime(AgentRuntime):
    """自研实现：直接包 2.5 的 AgentRuntime"""
    async def run(self, input: str, config: dict = None) -> dict: ...
    async def resume(self, checkpoint_id: str) -> dict: ...
```

## 7. 案例

### 案例 A：从自研循环迁移到 LangGraph

**场景**：某电商客服团队的自研循环跑了 3 个月，积累了约 1200 行运行时代码（循环、检查点、重试、埋点），新成员接手困难。

**自研循环的形状**：

```python
async def agent_loop(goal):
    state = {"goal": goal, "step": 0}
    while state["step"] < 10:
        action = await decide(state)
        result = await execute(action)
        state = update(state, action, result)
    return state
```

**问题**：中断恢复、并行、可观测性都要自己实现，每项都是隐性成本。

**迁移做法**：decide / execute / update 三个函数原样保留（业务逻辑本就解耦，原则见 4.10），只把外层换成图 + checkpointer：

```python
graph = StateGraph(State)
graph.add_node("decide", decide_node)
graph.add_node("execute", execute_node)
graph.add_edge(START, "decide")
graph.add_conditional_edges("decide", should_continue)
graph.add_edge("execute", "decide")

app = graph.compile(checkpointer=SqliteSaver.from_conn_string("cp.db"))
```

**示意性效果**：运行时层代码从约 1200 行降到 300 行以内（保留的 decide / execute + 适配代码）；检查点、恢复、trace 改用框架内置；新工具接入从改 3 处代码变成注册 1 个节点。

### 案例 B：混合架构的对比研究

一项 2025 年公开的多框架对比研究（学术预印本，数字为示意性引用）给出三类框架的取舍：

- CrewAI：任务分配得分高约 34%，但计划适应性弱。
- AutoGen：计划适应性强约 28%，但 token 成本高。
- LangChain（链式）：最灵活，但计算开销增加约 42%。

**混合方案**：LangGraph 做状态管理和路由 + CrewAI 做角色分工——成功率 96.1%，token 消耗降低 76.2%，延迟降低约 14.5 倍。

**启示**：框架选型不是单选题；用"抽象层 + 协议"（4.10）组合多个框架的长处是可行路径。但组合本身也是复杂度，要有明确的量化收益再上。

### 案例 C：MCP 标准化工具接入

**场景**：某金融科技公司内部 6 个 Agent 项目，各自维护同一批内部工具（查账户、查流水、开工单）的适配代码。

**问题**：每接入一个新工具，平均 3-5 天适配 × 6 个项目；工具接口一变，6 处都要改。

**MCP 方案**：

```text
工具方：实现一次 MCP Server（内部工具网关）
Agent 方：6 个项目统一通过 MCP Client 调用
变更时：只改 MCP Server 一处，Agent 项目无感
```

**示意性效果**：新工具上线从约 3 周（6 个项目各自适配）缩短到 3 天内（实现一个 Server）；工具接口变更的联调范围从 6 处降到 1 处。

## 8. 常见坑

1. **盲目追新框架**。  
   框架半年一换，业务逻辑跟着重写。先立抽象层（4.10），再考虑换框架。

2. **业务逻辑写死在框架里**。  
   规则散落在节点和装饰器里，换框架等于全部重写。业务逻辑独立成可单测的模块。

3. **不评估框架成熟度与维护状态**。  
   选了停止维护的框架，遇到 bug 没人修（Swarm 归档、AutoGen 并入 Agent Framework 都是先例）。选型前看维护频率、issue 响应、社区规模。

4. **忽略状态持久化**。  
   长任务中断后无法恢复，只能整个重来。生产环境 checkpointer 是标配，不是可选项。

5. **不用 MCP 标准化工具**。  
   每个工具在每个项目里重复适配。内部工具优先封装成 MCP Server，一次实现多处复用。

6. **多 Agent 过度设计**。  
   单 Agent 加好工具能搞定的事，上了多 Agent 框架，延迟和成本翻倍。先单 Agent（见 2.7），证明不够再升级多 Agent（见 2.8）。

7. **不评估 token 成本**。  
   不同框架的对话轮次与上下文管理差异巨大，多 Agent 对话式框架的 token 消耗可达图式的数倍。选型阶段就用同一任务实测 token 用量（见 3.7）。

8. **忽略框架的调试体验**。  
   状态图可视化、trace、断点调试缺失，出问题只能逐行 print。把"怎么调试"当成选型硬指标（可观测性见 3.4）。

9. **不考虑部署复杂度**。  
   依赖树庞大、需要常驻进程的框架，部署和运维成本翻倍。评估依赖数量、冷启动时间、与现有基建的兼容（见 3.6）。

10. **框架版本不固定**。  
    升级框架后行为悄悄变化，线上回归。锁版本 + 灰度升级 + 评估集回归（见 3.9）。

11. **不抽象运行时接口**。  
    业务代码直接调用框架 API，处处耦合。用 AgentRuntime 一类的薄接口隔离（4.10 原则 2）。

12. **观测数据只进框架自家平台**。  
    trace 存在厂商私有格式里，换框架时观测历史全部作废。按 OTel gen_ai.* 标准导出到自主可控的后端（见 3.4）。

13. **把 A2A 当成眼前必需品**。  
    单组织内部强行上跨组织协议，平添复杂度。A2A 面向跨厂商协作场景；内部优先把 MCP 用好。

14. **把框架当银弹**。  
    框架只解决编排问题，不解决提示词质量、数据质量、模型能力。先修好这三样，框架才能发挥作用（见 1.4、3.2）。

15. **不评估框架的扩展性**。  
    原型单机跑得动，生产并发下 checkpointer 成瓶颈。压测并发、持久化、多租户隔离后再上线。

## 9. 练习

1. 用 LangGraph 实现带检查点的 Agent 循环。验收：杀掉进程后用同一 thread_id 再 invoke，能从断点继续。
2. 用 LlamaIndex Workflows 实现"检索 → 生成"RAG 工作流（两个 step、一个自定义事件）。验收：打印事件流，确认两步解耦。
3. 用 OpenAI Agents SDK 实现"分诊 → 专家"交接。验收：10 条测试 query 至少 9 条落到正确的 last_agent。
4. 设计 AgentRuntime 抽象层，让同一段业务代码能在 LangGraph 和自研运行时下运行。验收：切换只改一行配置。
5. 实现一个 MCP Server，暴露 3 个工具。验收：另一个项目的 Agent 不改工具代码即可调用。
6. 同一任务（客服分诊）分别用 LangGraph 和 OpenAI Agents SDK 实现（参考 6.4），对比代码量、路由可控性、调试体验，写 300 字结论。
7. 用 LangGraph 的 interrupt 实现人工审批：高风险操作暂停，批准后继续。验收：拒绝路径能正确终止并留痕。
8. 设计配置驱动的运行时（YAML 指定 framework 字段，参考 4.10 原则 3）。验收：改配置即在两个实现间切换。
9. 用同一套评估集（10 个输入/期望输出对）测你的 Agent 在两个框架下的成功率与 token 消耗，记录差异并解释原因。
10. 写一份迁移方案：把 2.5 的自研循环迁移到任一框架，列出保留、删除、新增的模块清单与理由。

## 10. 小结

- 编排框架 = **执行引擎 + 状态管理 + 工具集成 + 持久化 + 可观测性**；原理全部来自 2.5，框架只是标准件实现。
- 主流格局（截至 2026 年）：**LangGraph（状态图）、LlamaIndex Workflows（事件驱动）、OpenAI Agents SDK（轻量，Swarm 已归档）、CrewAI（角色团队）、AutoGen 与 Semantic Kernel 并入 Microsoft Agent Framework**。
- 协议层：**MCP（Agent↔工具，已交 Linux Foundation 旗下基金会中立治理）、A2A（Agent↔Agent，150+ 组织支持，生产落地仍在早期）**。
- 选型口径：**重状态图 → LangGraph；RAG → Workflows；快速原型与交接 → OpenAI SDK；角色分工 → CrewAI；循环 3 步以内且无持久化 → 自研**。
- 自研 vs 框架的本质：**用学习成本和锁定风险，换持久化、恢复、观测的成熟能力**；判断依据是检查点、人工介入、多 Agent、长任务的需求强度。
- 防锁定四层：**业务逻辑独立、运行时接口抽象、工具与协作走开放协议（MCP / A2A）、观测走 OTel gen_ai.***；迁移成本在选型时就要评估。
- 概念是慢变量，框架是快变量：**框架是工具，不是架构，业务逻辑不要和框架耦合。**
- 这些能力直接支撑：**3.9 CI/CD、版本管理与发布，以及 4.x 实战篇（如 4.6 多 Agent 协作系统、4.7 生产级 Agent 平台）**。
