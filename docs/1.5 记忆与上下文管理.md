# 讲解 1.5 记忆与上下文管理

> 说明：1.4 RAG 解决“外部知识从哪来”，本篇解决“**对话状态与历史信息怎么管**”：多轮对话、短期/长期记忆、摘要压缩、检索式记忆入门。  
> Agent 化的记忆系统（工作/情节/语义记忆分层架构、记忆管理器、记忆与规划/工具/反思的联动）在 2.4 Agent 记忆展开，本篇是它的地基。

---

## 1. 定位

LLM 应用层第 5 个知识点，属于“状态管理”。  
它解决一个核心问题：**LLM 本身无状态（Stateless），每次调用都是独立的，如何让它记住对话历史、用户偏好、任务进展？**

前置：1.4 RAG——检索式记忆直接复用它的向量检索与查询重写能力（见 1.4、0.7）。  
后续：直接支撑 2.1 Agent 定义与范式、2.4 Agent 记忆；2.5 执行循环、2.7 单 Agent 架构经由 2.4 间接依赖本篇；记忆效果如何量化在 1.6 展开。

与 2.4 的划界，一句话：**“单次调用里怎么管好上下文”看本篇，“为长任务 Agent 怎么设计记忆系统”看 2.4**。本篇讲 LLM 应用层的多轮对话状态、窗口策略、摘要压缩、检索式记忆入门；工作/情节/语义/程序记忆的完整分层与记忆管理器架构归 2.4。

## 2. 一句话定义

记忆与上下文管理，是在 LLM 上下文窗口限制下，有选择地保存、压缩、检索和注入历史信息，让应用具备多轮连贯性和个性化能力的工程方法。

简化公式：

```text
每轮送入 LLM 的上下文 = 固定指令 + 画像（常驻） + 相关记忆（检索）
                     + 历史摘要（压缩） + 最近对话（窗口） + 当前输入
记忆管理的全部工作   = 决定每一项放什么、放多少、何时更新、何时丢弃
```

## 3. 为什么需要

LLM API 是无状态的：

```text
调用 1：用户说“我叫张三” → LLM 知道
调用 2：用户说“我叫什么？” → LLM 不知道，因为没有历史
```

要让它“记住”，必须把历史消息一起传进去：

```python
messages = [
    {"role": "user", "content": "我叫张三"},
    {"role": "assistant", "content": "你好，张三！"},
    {"role": "user", "content": "我叫什么？"},
]
```

但这样会带来新问题：

- **窗口有限** → 上下文窗口（Context Window）以 token 计，多轮对话很快超限。
- **成本线性增长** → 每轮都带全部历史，单次请求 token 随轮数线性涨，整场会话累计随轮数平方涨。
- **噪音干扰** → 无关历史稀释关键信息，指令跟随质量下降。
- **中间遗忘** → 长上下文中间部分的信息容易被忽略（Lost in the Middle 现象，Liu et al.，2023）。
- **跨会话丢失** → 关掉页面，下次对话全忘了。
- **个性化缺失** → 每次都要重新自我介绍。

**类比 1：记忆系统 = 医院的病历制度。** 没有病历的医生，复诊病人每次都要重述病史、重做检查；有病历（长期记忆）+ 本次主诉（当前输入）+ 最近一次检查单（短期记忆），医生三句话就能接上上次的诊疗。记忆管理就是给 LLM 建“病历制度”——该归档的归档，该带进诊室的带进诊室。

记忆与 RAG 常被混为一谈。两者共享嵌入与向量检索技术（见 1.4），但归属不同：

| 维度 | 记忆（本篇） | RAG（见 1.4） |
|---|---|---|
| 信息归属 | 用户/会话私有 | 全局共享知识 |
| 产生方式 | 对话过程中实时写入 | 离线批量入库 |
| 生命周期 | 随用户变化、需支持删除 | 随知识库更新 |
| 检索键 | 用户 ID + 当前问题 | 当前问题 |
| 典型内容 | 偏好、事件、任务状态 | 文档、政策、FAQ |
| 合规重点 | PII、被遗忘权 | 权限过滤 |

记忆与上下文管理，就是同时解决上面六个问题的工程方法。

## 4. 核心原理

### 4.1 记忆的分类

按时间跨度：

| 类型 | 说明 | 例子 |
|---|---|---|
| 短期记忆（Short-Term Memory） | 当前会话的对话历史 | 最近几轮消息 |
| 长期记忆（Long-Term Memory） | 跨会话持久化信息 | 用户偏好、历史订单 |
| 工作记忆（Working Memory） | 当前任务相关的临时信息 | 正在处理的订单号 |

按内容类型：

| 类型 | 说明 | 例子 |
|---|---|---|
| 情节记忆（Episodic Memory） | 具体事件和经历 | “用户上周投诉过物流” |
| 语义记忆（Semantic Memory） | 事实和知识 | “用户是 VIP 会员” |
| 程序记忆（Procedural Memory） | 技能和流程 | “用户喜欢先看摘要” |

1.5 主要讲**短期记忆 + 基础长期记忆**；完整的记忆分层架构与记忆读写体系在 2.4 展开。

**类比 2：摘要压缩 = 会议纪要。** 一场两小时的会，缺席的同事不会去听完整录音（全量历史），而是看 3 句纪要（历史摘要）+ 最后十分钟的待办确认（最近消息）。摘要记忆做的就是这件事：有损，但把“结论和待办”留住了。

### 4.2 上下文窗口管理策略

五种策略，公式与取舍：

**策略 1：全量保留**

```python
messages = system + all_history + current_input
```

- 优点：信息完整，实现最简单。
- 缺点：很快超限，成本随轮数平方级累积。
- 适用：短对话、原型验证。

**策略 2：滑动窗口（Sliding Window）**

```python
messages = system + history[-N:] + current_input
```

- 优点：简单，token 上限恒定。
- 缺点：窗口外信息全部丢失。
- 适用：一般对话。

**策略 3：摘要压缩（Summarization）**

```python
messages = system + summary_of_old + history[-N:] + current_input
```

- 优点：保留长期信息，token 上限恒定。
- 缺点：摘要有损，需要额外一次 LLM 调用。
- 适用：长对话、客服。

**策略 4：检索式记忆（Retrieval-Based Memory）**

```python
relevant_history = retrieve(query, history_store)
messages = system + relevant_history + current_input
```

- 优点：按需召回，天然支持跨会话。
- 缺点：依赖向量库，检索不准会召回噪音。
- 适用：长期助手、Agent。

**策略 5：分层记忆**

```text
工作记忆：当前任务，全量保留
短期记忆：最近 N 轮，滑动窗口
长期记忆：摘要 + 检索，持久化
```

- 优点：兼顾完整性和成本。
- 缺点：实现复杂。
- 适用：生产级系统。

五种策略横向对比（量级推导：每轮一问一答约 400 token，30 轮会话）：

| 策略 | 每轮携带历史 | 30 轮累计输入 | 早期信息保留 | 复杂度/额外开销 | 适用 |
|---|---|---|---|---|---|
| 全量保留 | 400×(n−1)，线性涨 | 约 17.4 万 | 完整 | 最低 | 短对话、原型 |
| 滑动窗口 5 轮 | ≤2000，恒定 | ≤6 万（降约 65%） | 窗口外全丢 | 低 | 一般对话 |
| 摘要 + 窗口 5 轮 | ≤2300，恒定 | ≤6.9 万 | 有损保留 | 中，压缩时一次 LLM 调用 | 长对话、客服 |
| 检索式 top-3 | 约 200–500 | 约 1.5 万以内 | 按需召回，不保证 | 高，向量库 + 检索延迟 | 长期助手 |
| 分层混合 | 各层可控 | 可控 | 组合保留 | 最高 | 生产系统 |

推导要点：全量保留的累计输入是 400×(1+2+…+29)≈17.4 万 token，平方级增长；摘要版每轮只多带约 300 token 摘要，换来 30 轮后仍知道第 1 轮说了什么。**摘要比同尺寸窗口略贵，买到的是信息保留；比全量便宜，靠的是把线性增长压平。**

趋势观察（截至 2026 年）：主流 API 普遍提供提示词缓存（Prompt Caching），对重复前缀的输入按折扣计费，全量历史命中缓存后成本压力下降。但两点不变——上下文越长中间遗忘越明显、首 token 延迟随长度上升，压缩与检索仍是标配（缓存与计费口径见 1.7、3.7）。

**面试高频问法：「长对话怎么不丢关键信息？」** 共识口径：不是一味换更大窗口的模型，而是分层处理——关键信息结构化沉淀（画像/任务状态）、早期对话摘要、最近若干轮保原文、长期记忆按需检索；同时讲清 token 成本与信息保留的权衡，就是上面这张表。

### 4.3 短期记忆实现

**1. 消息列表（滑动窗口）**：

```python
class ConversationBuffer:
    def __init__(self, max_turns: int = 10):
        self.messages = []
        self.max_turns = max_turns

    def add(self, role: str, content: str):
        self.messages.append({"role": role, "content": content})
        # 只保留最近 N 轮（一轮 = user + assistant 两条）
        if len(self.messages) > self.max_turns * 2:
            self.messages = self.messages[-self.max_turns * 2:]

    def get(self) -> list[dict]:
        return self.messages
```

**2. 摘要记忆**：

```python
class SummaryMemory:
    def __init__(self, max_recent: int = 5):
        self.summary = ""   # 早期对话的滚动摘要
        self.recent = []    # 最近几轮原文
        self.max_recent = max_recent

    def add(self, role: str, content: str):
        self.recent.append({"role": role, "content": content})
        if len(self.recent) > self.max_recent * 2:
            self._compress()

    def _compress(self):
        old = self.recent[:-self.max_recent * 2]
        prompt = f"请把以下对话压缩成简洁摘要，保留关键信息：\n{old}\n\n已有摘要：{self.summary}"
        self.summary = call_llm(prompt)
        self.recent = self.recent[-self.max_recent * 2:]

    def get(self) -> list[dict]:
        messages = []
        if self.summary:
            messages.append({"role": "system", "content": f"历史摘要：{self.summary}"})
        messages.extend(self.recent)
        return messages
```

**3. 摘要 + 最近消息混合**：生产最常用的方式——早期对话进摘要、最近几轮保原文，兼顾成本与细节（可直接运行的完整实现见 6.1，摘要模板见 6.2）。

### 4.4 长期记忆实现

**1. 用户画像（User Profile）存储**：

```python
class UserProfile:
    def __init__(self, user_id: str):
        self.user_id = user_id
        self.data = {}

    def update(self, key: str, value: str):
        self.data[key] = value
        # 持久化到数据库

    def get_context(self) -> str:
        return "\n".join(f"- {k}: {v}" for k, v in self.data.items())
```

**2. 向量化记忆**：把每条记忆存入向量库、按语义检索，原理同 RAG 的向量检索（见 0.7、1.4），完整实现见 6.3。

**3. 结构化记忆**：

```python
class StructuredMemory:
    def __init__(self):
        self.facts = []       # 事实
        self.preferences = {} # 偏好
        self.events = []      # 事件

    def add_fact(self, fact: str):
        self.facts.append(fact)

    def set_preference(self, key: str, value: str):
        self.preferences[key] = value

    def add_event(self, event: str, timestamp: str):
        self.events.append({"event": event, "time": timestamp})
```

### 4.5 该记住什么、该忘掉什么（本锚点的核心问题）

一句话判定原则：**以后还会用到的写入，用过即弃的不写入；会被反复引用的结构化沉淀，转瞬即逝的留在窗口里自然滑出。**

该记（写入白名单）：

| 类别 | 例子 | 为什么 |
|---|---|---|
| 用户偏好 | “回答简洁点”“用中文交流” | 每轮都影响输出 |
| 事实约束 | 会员等级、地址、过敏原、设备型号 | 约束后续所有建议 |
| 任务状态 | 进行到第几步、已确认/待确认项 | 多轮任务的断点 |
| 长期目标 | “我在准备 10 月的考试” | 跨会话个性化 |
| 显式指令 | “记住我常用这个账号” | 用户明确授权，优先级最高 |

该忘（不写入或主动淘汰）：

| 类别 | 例子 | 为什么 |
|---|---|---|
| 寒暄客套 | “你好”“谢谢” | 零信息量 |
| 过期事实 | 上个月的订单号、已完结的任务状态 | 留着会与新事实冲突 |
| 冗余复述 | 同一偏好的第 N 次表达 | 浪费存储与检索空间 |
| 一次性敏感信息 | 验证码、一次性密码 | 绝不该存，合规红线 |
| 可查系统的信息 | 订单详情、库存实时数据 | 记忆只存“指针”（订单号），详情实时查工具或数据库 |

写入前的判定四问（写入路径的过滤器）：

1. 以后会用到吗？——不会，不记。
2. 是稳定事实还是瞬时情绪？——寒暄和情绪波动不记，稳定偏好才记。
3. 会过期吗？——会，打时间戳，纳入衰减淘汰。
4. 换个会话还成立吗？——只在当前任务成立，留在短期记忆，不入长期。

代价不对称原则：**记错的代价大于不记**。不记，用户最多重说一遍；记错（用户搬家后还用旧地址），系统直接输出错误结果。所以更新与冲突处理（见 4.7）不是可选项，是写入策略的另一半。

**面试高频问法：「多轮对话中记忆该怎么设计？该记住什么、忘掉什么？」**（面试鸭/牛客出现过同型题；英文变体："How would you design a memory system that remembers user preferences across sessions?"，The Interview Guys 2026）答法框架：白名单写入（偏好/事实/任务状态）→ 过滤噪音（寒暄/过期/冗余）→ 分层读取（画像常驻 + 检索 + 窗口）→ 更新与合规删除兜底。

### 4.6 记忆写入与读取策略

写入策略——不是所有信息都值得记住：

| 策略 | 说明 |
|---|---|
| 全量写入 | 每轮都存，简单但噪音多 |
| 规则写入 | 关键词触发，如“记住”“我喜欢” |
| LLM 判断 | 让 LLM 判断是否值得记 |
| 定期总结 | 每隔 N 轮总结一次 |
| 用户显式 | 用户主动要求记住 |

示例：LLM 判断是否值得记

```python
EXTRACT_PROMPT = """从以下对话中提取值得长期记住的信息。
只提取用户偏好、重要事实、长期目标。
如果没有值得记住的，输出 NONE。

对话：
{conversation}

提取结果（JSON 数组，每项包含 type、content）：
"""
```

读取策略：

| 策略 | 说明 |
|---|---|
| 全量注入 | 所有记忆都放进 Prompt，简单但超限 |
| 检索注入 | 根据当前问题检索相关记忆 |
| 分层注入 | 用户画像常驻，事件按需检索 |
| 摘要注入 | 把记忆压缩成摘要 |

推荐组合：

```text
用户画像（常驻） + 检索相关记忆（按需） + 最近对话（滑动窗口）
```

### 4.7 记忆更新与遗忘

**更新**：

- 事实变化：用户搬家，更新地址。
- 偏好变化：用户口味变了。
- 冲突处理：新信息覆盖旧信息，或让 LLM 判断以哪个为准。

**遗忘**：

- 时间衰减（Time Decay）：旧记忆权重降低，长期不被引用的排序靠后。
- 容量限制：超过 N 条，淘汰最旧/最不重要。
- 主动删除：用户要求删除（合规要求）。
- 隐私合规：GDPR 被遗忘权（Right to be Forgotten），PII 类记忆必须可删、可导出。

### 4.8 上下文压缩技巧

**1. 消息摘要**：

```text
把 10 轮对话压缩成 3 句话。
```

**2. 关键信息提取**：

```text
从对话中提取：用户意图、已确认信息、待办事项。
```

**3. 工具结果压缩**：

工具返回 5000 token JSON，只保留关键字段再入上下文。

**4. RAG 上下文压缩**：

检索 20 篇文档，用 LLM 压缩成 5 条要点再拼接（见 1.4）。

**5. 结构化状态**：

```json
{
  "user_intent": "退款",
  "order_id": "12345",
  "confirmed": ["退货原因", "退款方式"],
  "pending": ["等待用户确认金额"]
}
```

比自然语言历史更紧凑，且不易被“改写丢失”。

### 4.9 多轮对话中的查询重写（Query Rewriting）

用户说“那退款呢？”，单独拿去检索会失败。  
结合历史重写：

```python
REWRITE_PROMPT = """根据对话历史，把用户最新问题重写为独立完整的问题。

历史：
{history}

最新问题：{question}

重写后的问题："""
```

重写后：“退货后多久能收到退款？”——再做检索就能命中“退款时效”。这是多轮 RAG 的标准前置步骤（详见 1.4）。

### 4.10 记忆的评估

| 指标 | 含义 |
|---|---|
| 记忆准确率 | 记住的信息是否正确 |
| 召回率 | 需要时是否能召回 |
| 相关性 | 召回的记忆是否相关 |
| 一致性 | 多轮中信息是否一致 |
| 成本 | 记忆存储和检索成本 |
| 延迟 | 记忆读写延迟 |

记忆评估是 LLM 应用评估体系的一支，指标设计与评测工具在 1.6 展开（成本与延迟的完整治理见 3.7）。

**术语趋势（截至 2026 年）**：业界开始把“记什么、忘什么、上下文里放什么、按什么顺序组织”统称为上下文工程（Context Engineering）。英文面试题库已出现专项（如 The Interview Guys 2026《Top 10 Context Engineer Interview Questions》、Weaviate 博客《Context Engineering: LLM Memory and Retrieval for AI Agents》），中文一手面经尚未形成独立题面——作为趋势口径了解即可，答题用本篇的分层口径完全覆盖。

## 5. 架构 / 流程

先看单轮视角：每一轮对话，上下文如何流转（读路径 → 生成 → 写路径）：

```text
第 n 轮：用户输入“那退款呢？”
        ↓
┌─ 读路径 ─────────────────────────────────┐
│ ① 查询重写：结合最近 K 轮 → 独立完整问题   │
│ ② 组装上下文（自上而下注入）：              │
│    system 指令                             │
│    + 用户画像（常驻）                      │
│    + 相关长期记忆（向量检索 top-k）         │
│    + 历史摘要（压缩产物）                  │
│    + 最近 N 轮原文（滑动窗口）             │
│    + 当前输入                              │
└──────────────┬───────────────────────────┘
               ↓
          LLM 生成回答
               ↓
┌─ 写路径 ─────────────────────────────────┐
│ ③ 值得记吗？判定四问（见 4.5）             │
│    是 → 提取（type、content）→ 入库        │
│         ├─ 偏好/事实 → 画像或向量库        │
│         └─ 事件 → 带 timestamp 存储        │
│ ④ 窗口超限？→ 触发摘要压缩（见 6.2 模板）  │
│ ⑤ 记忆冲突？→ 新值覆盖旧值或 LLM 仲裁      │
└──────────────────────────────────────────┘
               ↓
        进入第 n+1 轮（循环）
```

再看系统视角，一个生产级记忆系统的分层：

```text
┌──────────────────────────────────────────┐
│  写入路径                                 │
│  对话 → 判断是否值得记 → 提取 → 存储      │
│         ├─ 短期：消息列表                 │
│         ├─ 长期：向量库 / 数据库          │
│         └─ 画像：结构化存储               │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  存储层                                   │
│  ├─ 短期：Redis / 内存                    │
│  ├─ 长期：向量库 + PostgreSQL             │
│  └─ 画像：关系数据库                      │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  读取路径                                 │
│  当前问题 → 检索相关记忆 → 组装上下文     │
│         ├─ 用户画像（常驻）               │
│         ├─ 相关记忆（检索）               │
│         └─ 最近对话（滑动窗口）           │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  LLM 调用                                 │
│  压缩后的上下文 → 生成回答                │
└──────────────────────────────────────────┘
```

### 6.1 多轮记忆管理最小实现（滑动窗口 + 摘要）

```python
from openai import OpenAI

client = OpenAI(api_key="YOUR_KEY")

class ConversationMemory:
    """短期记忆：最近 N 轮保原文，更早的滚动压缩成摘要"""

    def __init__(self, max_recent_turns: int = 5):
        self.summary = ""
        self.recent = []
        self.max_recent_turns = max_recent_turns

    def add(self, role: str, content: str):
        self.recent.append({"role": role, "content": content})
        if len(self.recent) > self.max_recent_turns * 2:
            self._compress()

    def _compress(self):
        old = self.recent[:-self.max_recent_turns * 2]
        text = "\n".join(f"{m['role']}: {m['content']}" for m in old)
        prompt = f"""请把以下对话压缩成简洁摘要，保留关键信息（用户偏好、事实、待办）：

已有摘要：{self.summary}

新对话：
{text}

更新后的摘要："""
        response = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            temperature=0,
        )
        self.summary = response.choices[0].message.content
        self.recent = self.recent[-self.max_recent_turns * 2:]

    def get_messages(self, system_prompt: str) -> list[dict]:
        messages = [{"role": "system", "content": system_prompt}]
        if self.summary:
            messages.append({"role": "system", "content": f"历史摘要：{self.summary}"})
        messages.extend(self.recent)
        return messages

# 使用
memory = ConversationMemory(max_recent_turns=3)
memory.add("user", "我叫张三，是 VIP 会员")
memory.add("assistant", "你好张三！")
# ... 多轮后自动压缩
```

### 6.2 摘要压缩模板

摘要质量决定信息保留率，模板要把“保留什么、丢什么、冲突怎么办”说死：

```text
【对话摘要压缩模板】

你是对话摘要器。把“新增对话”合并进“已有摘要”，输出更新后的摘要。

保留（必须有）：
1. 用户偏好（语言、风格、称呼）
2. 事实约束（会员等级、地址、过敏原、订单号等数字）
3. 未解决的待办与未确认项

丢弃（必须删）：
1. 寒暄、感谢等客套
2. 已完结且无后续影响的细节
3. 与已有摘要重复的内容

冲突规则：新旧信息冲突时，以新信息为准并覆盖旧值。

输出限制：不超过 {max_sentences} 句话。

已有摘要：{summary}
新增对话：{recent_text}
更新后的摘要：
```

### 6.3 向量长期记忆

```python
import chromadb
import uuid

class LongTermMemory:
    """长期记忆：向量库存储，按 user_id 隔离检索"""

    def __init__(self):
        self.collection = chromadb.Client().create_collection("memory")

    def add(self, text: str, user_id: str, memory_type: str = "fact"):
        self.collection.add(
            documents=[text],
            metadatas=[{"user_id": user_id, "type": memory_type}],
            ids=[str(uuid.uuid4())],
        )

    def retrieve(self, query: str, user_id: str, top_k: int = 3) -> list[str]:
        results = self.collection.query(
            query_texts=[query],
            n_results=top_k,
            where={"user_id": user_id},  # 用户隔离：只检索本用户记忆
        )
        return results["documents"][0]

# 使用
ltm = LongTermMemory()
ltm.add("用户喜欢用中文交流", user_id="u1", memory_type="preference")
ltm.add("用户上个月投诉过物流", user_id="u1", memory_type="event")

relevant = ltm.retrieve("用户有什么偏好？", user_id="u1")
print(relevant)
```

### 6.5 完整记忆系统（分层组装）

```python
class AgentMemory:
    """画像常驻 + 长期记忆检索 + 短期记忆窗口，三层组装"""

    def __init__(self, user_id: str):
        self.user_id = user_id
        self.short_term = ConversationMemory(max_recent_turns=5)
        self.long_term = LongTermMemory()
        self.profile = {}

    def add_turn(self, role: str, content: str):
        self.short_term.add(role, content)

    def update_profile(self, key: str, value: str):
        self.profile[key] = value

    def remember(self, text: str, memory_type: str = "fact"):
        self.long_term.add(text, self.user_id, memory_type)

    def build_context(self, query: str, system_prompt: str) -> list[dict]:
        messages = [{"role": "system", "content": system_prompt}]

        # 第一层：用户画像（常驻）
        if self.profile:
            profile_text = "\n".join(f"- {k}: {v}" for k, v in self.profile.items())
            messages.append({"role": "system", "content": f"用户画像：\n{profile_text}"})

        # 第二层：相关长期记忆（按需检索）
        relevant = self.long_term.retrieve(query, self.user_id)
        if relevant:
            memory_text = "\n".join(f"- {m}" for m in relevant)
            messages.append({"role": "system", "content": f"相关记忆：\n{memory_text}"})

        # 第三层：短期记忆（摘要 + 最近消息，去掉已加过的 system）
        messages.extend(self.short_term.get_messages(system_prompt)[1:])

        return messages
```

## 7. 案例

### 案例 A：客服多轮对话

**问题**：用户对话 30 轮，上下文超限。

**方案**：

- 最近 5 轮全量保留。
- 更早的对话压缩成摘要（模板见 6.2）。
- 订单号、退款金额等关键信息结构化存储（见 4.8）。
- 用户画像常驻。

**效果**（示意）：单轮输入 token 从 1.2 万降到 3000 以内，整场会话 token 消耗降低约 70%；第 1 轮反馈的问题在第 30 轮追问时仍可答出——关键信息零丢失靠的是结构化沉淀，不是靠窗口。

### 案例 B：个人助手长期记忆

**场景**：用户每天使用，希望助手记住偏好。

**方案**：

- 每轮对话后，LLM 判断是否有值得记的信息（EXTRACT_PROMPT）。
- 偏好、事实存入向量库，按 user_id 隔离。
- 每次对话检索相关记忆注入（top-3，约 200 token）。

**效果**（示意）：使用三个月后画像与记忆库累计 60 余条；用户说“老样子”，助手能解析为“大杯热美式、少糖”——内部用 20 条指代用例做评测，命中 17 条；而没有任何记忆的基线版本全部答非所问。

### 案例 C：多轮 RAG 查询重写

```text
用户：退货政策是什么？
助手：签收后 7 天内可退。
用户：那退款呢？
```

“那退款呢？”直接检索命中率极低。重写为“退货后多久能收到退款？”再检索，命中“退款时效：3-5 个工作日到账”。一次重写约多花 300 token、增加一次小模型调用，换来检索命中（详见 1.4 的多轮 RAG）。

## 8. 常见坑

1. **全量历史塞进 Prompt**。  
   很快超限，成本随轮数平方涨。必须压缩或检索，按 4.2 的对比表选策略。

2. **摘要丢关键信息**。  
   摘要 Prompt 要明确保留：偏好、事实、待办、数字；数字类（订单号、金额）最好结构化另存，不依赖摘要转述。

3. **不区分短期和长期**。  
   所有信息都存一处，无法分层管理，也做不了差异化淘汰。短期管窗口、长期管检索。

4. **记忆写入无策略**。  
   什么都记，噪音多，检索不准。用判定四问（见 4.5）过滤。

5. **记忆读取不检索**。  
   全部注入，上下文超限，关键信息被稀释。画像常驻 + 相关检索 + 窗口保底。

6. **不做用户隔离**。  
   多用户共享记忆库，A 能检索到 B 的记忆，等于数据泄露。所有读写带 user_id 过滤。

7. **不处理记忆冲突**。  
   用户搬家了，旧地址还在库里，模型在两个地址间摇摆。新值覆盖旧值，或 LLM 仲裁。

8. **忽略隐私合规**。  
   记忆含 PII，要支持删除、导出、加密；GDPR 被遗忘权是硬要求。

9. **摘要调用太频繁**。  
   每轮都摘要，成本和延迟上升。按阈值触发（如超过 N 轮才压一次）。

10. **不评估记忆效果**。  
    不知道记住没有、召回准不准。按 4.10 的指标建评测集，定期回归。

11. **忽略多轮查询重写**。  
    “那退款呢？”单独检索失败。先重写再检索（见 4.9）。

12. **记忆库不更新**。  
    用户信息变了，记忆还是旧的。写入路径要能更新，不是只追加。

13. **工具结果全量存**。  
    工具返回 5000 token 直接入库，浪费存储还拉低检索精度。先裁剪保留关键字段。

14. **把记忆当 RAG**。  
    记忆是用户/会话相关，RAG 是知识相关（见 §3 对比表），混存会导致跨用户泄露与检索污染。

15. **以为开了 Prompt Caching 就不用压缩**。  
    缓存只降低重复前缀的费用，不解决超限、中间遗忘和延迟问题。压缩与检索仍是标配（趋势观察，见 4.2）。

## 10. 小结

- LLM 无状态，记忆靠**上下文注入**实现——每轮把该带的带上，其余靠存储与检索。
- 记忆分类：**短期、长期、工作；情节、语义、程序**（完整分层架构见 2.4）。
- 窗口策略演进：**全量 → 滑动窗口 → 摘要 → 检索式 → 分层混合**，核心权衡是 token 成本 vs 信息保留。
- 生产标配：**画像常驻 + 历史摘要 + 最近消息窗口 + 检索式长期记忆**。
- 该记：**用户偏好、事实约束、任务状态、长期目标、显式指令**；该忘：**寒暄、过期事实、冗余复述、一次性敏感信息**。记错的代价大于不记。
- 写入要过滤（规则/LLM 判定），读取要分层（常驻 + 检索 + 窗口），更新要覆盖冲突，遗忘要支持时间衰减与用户删除。
- 压缩四板斧：**消息摘要、关键信息提取、工具结果裁剪、结构化状态**；多轮检索前先做**查询重写**。
- 记忆是用户/会话相关，RAG 是知识相关：共享向量检索技术，但归属、生命周期、合规要求都不同；评估口径见 1.6。
- 工程底线：**用户隔离、冲突处理、隐私合规（被遗忘权）、效果评估**；缓存降成本但不替代压缩。
- 这些能力直接支撑：2.1 Agent 定义与范式、2.4 Agent 记忆，并经 2.4 支撑 2.5 执行循环、2.7 单 Agent 架构。
