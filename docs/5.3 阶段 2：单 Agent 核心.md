> 5.x 是学习路径篇，不讲新知识，讲**阶段作战计划**：本篇把 2 层核心知识组队成一条可执行顺序，带你分四个迭代做出阶段项目“工具型研究助手”，并给出里程碑自检表与卡点解法。

## 1. 定位

学习路径的第 3 个阶段，属于“从 LLM 应用到 Agent”的跨越期。  
它解决一个核心问题：**如何让 LLM 不再只回答一次，而是通过循环、工具调用（Function Calling / Tool Use）、记忆、状态机（State Machine），自主完成多步任务？**

对学习者，它是一份阶段作战计划：学什么、按什么顺序学、做什么项目、怎么验收。  
对知识地图，2.1–2.7 是“兵种”，5.3 负责把它们编成“作战序列”，再用一个项目把知识串起来。5.2 的产出是“稳定调用的 LLM 应用”，5.3 的产出是“能多步执行、能从失败里恢复的单 Agent”——后者是 5.4 RAG 与工具增强、5.6 多 Agent 与生产的直接地基。

本阶段口径（与知识地图一致）：

| 项 | 内容 |
|---|---|
| 前置 | 5.2 阶段 1：LLM 应用入门（稳定调用、结构化输出、基础评估） |
| 目标 | 掌握工具调用、规划（Planning）、记忆（Memory）、状态机 |
| 项目 | 工具型研究助手 |
| 里程碑 | 能多步执行、调用工具、记录轨迹（Trajectory）、处理失败 |
| 后续 | 5.4 阶段 3：RAG 与工具增强 |

## 2. 一句话定义

阶段 2 单 Agent 核心，是掌握单 Agent 的五个核心组件（LLM + 工具 + 记忆 + 循环 + 目标，见 2.1），能够独立设计并实现一个可运行、可调试、可终止的单 Agent 系统——工具型研究助手——的工程实践阶段。

简化公式：

```text
阶段 2 = 工具调用 + 规划 + 记忆 + 执行循环 + 状态机 + 终止控制
```

## 3. 为什么需要

阶段 1 的 LLM 应用是“单次调用 + 结构化输出”。  
但真实任务往往需要多步：

- **查询需要多轮**：先查订单，再查物流，再判断。
- **工具需要组合**：搜索 + 计算 + 查询 + 写入。
- **状态需要维护**：第 3 步要用第 1 步的结果。
- **失败需要恢复**：工具超时后重试或换方法。
- **流程需要终止**：什么时候算完成，什么时候放弃。

没有 Agent 核心能力：

- **只能做单步任务**：复杂任务搞不定。
- **无法组合工具**：每个工具单独调用，靠人串流程。
- **状态丢失**：多步之间信息断裂。
- **无法恢复**：一步失败整个任务失败。
- **无法终止**：要么不完成，要么死循环（Infinite Loop）。

“阶段 1 应用 vs 阶段 2 单 Agent”对比：

| 维度 | 阶段 1：LLM 应用 | 阶段 2：单 Agent |
|---|---|---|
| 调用次数 | 一次请求一次回答 | 多步循环，步数由任务与终止条件决定 |
| 工具 | 最多辅助生成输出 | 工具是执行主体：搜索、计算、写入由工具完成 |
| 状态 | 无状态，或只有对话历史 | 工作记忆显式维护目标、计划、步骤结果 |
| 失败 | 调用失败重试一次即止 | 四级恢复：重试 → 换参数 → 重规划 → 降级输出 |
| 终止 | 天然终止（拿到回答即结束） | 必须显式设计，否则死循环或过早放弃 |
| 适用任务 | 输入输出模式固定的任务 | 步骤不可预知、需要组合工具的任务 |

一句话说：阶段 1 = 会使用单个工具；阶段 2 = 会按计划组合工具，完成一个完整任务。两个类比，具体到场景：

```text
装修：  阶段 1 = 你打电话问师傅“这面墙能不能砸”，问一次答一次；
        阶段 2 = 请了位包工头，你只交底“三个月后入住”，他自己排工序、调工种、
        验每道环节——包工头就是 Agent，施工进度表是规划，工序验收单是状态机，
        “三个月交房”是终止条件。
改稿：  没有终止条件的 Agent = 让一个追求完美的实习生“改到满意为止”，他会改一整晚；
        有终止条件的 Agent = 明确告诉他“最多三稿，第三稿必须交”——max_steps、
        重规划上限与完成判定，就是给 Agent 的交稿纪律。
```

### 4.5 里程碑自检表：本阶段学完能做什么

把里程碑“能多步执行、调用工具、记录轨迹、处理失败”拆成可逐项打分的自检表，全部达到合格口径才算通过：

| 自检项 | 合格口径 | 不合格信号 | 对应锚点 |
|---|---|---|---|
| 多步执行 | Agent 能按计划连续执行 3 步以上，第 3 步能取到第 1 步的结果 | 只会单次调用 LLM，多步之间信息断裂 | 2.5 |
| 工具调用 | 定义 3–5 个工具（Pydantic 校验 + 写清何时用），模型能选对、传对参数 | 模型频繁选错工具或传错参数导致崩溃 | 2.3 |
| 规划与重规划 | 目标能分解为 3–10 步 JSON 计划；关键步骤失败后能生成新计划且不重复已完成步骤 | 计划只有 1 步或 20 步不可执行；一失败整任务报废 | 2.2 |
| 记忆分工 | 工作记忆存目标/计划/步骤结果，短期记忆管消息窗口，互不混装 | 全部信息堆进一个消息列表，越跑越长 | 2.4 |
| 状态与终止 | 有状态机雏形；有最大步数、重规划上限与完成判定三个开关 | 死循环，或不知道何时算完成 | 2.5 |
| 轨迹记录 | 每步记录动作/工具/参数/结果/耗时，落盘可回放，出问题按轨迹定位 | 出问题只能加 print 重猜 | 本篇 §6、3.4 |
| 失败处理 | 工具失败不崩溃：分类（可重试/不可重试）→ 重试 → 换方法 → 重规划，逐级递进 | 一律无脑重试，或一失败就终止 | 2.3、2.6 |

配套的 10 个关键问题（口头全部答清即达标）：

1. Agent 和工作流的边界在哪？
2. 什么时候用 ReAct，什么时候用 Plan-Execute？
3. 工具怎么定义才不容易选错？
4. 工具调用失败怎么处理？
5. 工作记忆和短期记忆怎么分工？
6. 执行循环怎么防止死循环？
7. 状态机怎么设计才不过度复杂？
8. 中断后怎么恢复？
9. 反思什么时候有用，什么时候浪费？
10. 五种单 Agent 架构怎么选？

**面试高频问法**：阶段 2 学完，以下三问应能给出共识口径的回答——“ReAct 和 Plan-and-Execute 怎么选？”（步骤少且不可预知、需要边看边走的探索型任务用 ReAct；步骤可预知、计划需要人事先审查或可并行的任务用 Plan-Execute；生产系统常取混合——先出计划、执行中允许局部自主、失败触发重规划，机制见 2.5）；“Agent 和工作流的边界在哪？”（步骤由代码写死的是工作流，步骤由模型在运行时决定的是 Agent；能用工作流解决的不要上 Agent，判断框架见 2.1）；“工具是不是越多越强？”（不是——工具越多选择准确率越容易被稀释，常见实践是从 3–5 个高内聚工具起步，描述写清何时用与何时不用，机制见 2.3）。

### 4.6 高频卡点与解法速查

| 卡点 | 典型症状 | 第一时间解法 | 深入锚点 |
|---|---|---|---|
| 工具选择混乱 | 模型总选错工具、瞎传参数 | 减到 3–5 个工具；描述写清何时用/何时不用；参数加 Pydantic 校验 | 2.3 |
| JSON 解析失败 | 规划输出不是合法 JSON，解析即崩 | 用结构化输出接口（response_format / JSON Schema），解析失败带错误重问一次 | 1.3、2.2 |
| 死循环 | 反复调用同一个工具不收敛 | 设最大步数 + 重复动作检测 + 显式完成判定 | 2.5 |
| 上下文爆炸 | 多步之后消息超出上下文窗口 | 工作记忆只存状态摘要，短期记忆用滑动窗口（Sliding Window） | 2.4、1.5 |
| 一步失败全盘报废 | 某工具超时，整任务终止 | 失败分级：可重试的退避重试，不可重试的换方法或重规划 | 2.3、2.6 |
| 成本失控 | 一次研究跑几十次调用，账单吓人 | 记录每步 token；设总步数与 token 预算上限 | 1.7、2.9 |
| 重规划无限套娃 | 失败→重规划→再失败，循环往复 | 重规划次数上限（如 2 次），超限改为降级输出 | 2.2、2.5 |
| 轨迹没法看 | 日志记了一堆但读不懂 | 统一轨迹格式（步骤/工具/参数/结果/耗时），落盘 JSONL | 本篇 §6、3.4 |
| 过度设计 | 两步的固定任务也上完整 Agent | 能用工作流就用工作流，Agent 留给步骤不可预知的任务 | 2.1、2.7 |

### 6.2 迭代一：定义工具与注册表

先让“Agent 有手脚”：工具带 Pydantic 参数校验，注册表统一管理与执行。

```python
# tools/registry.py —— 工具注册表：注册、出 schema、带校验地执行
from pydantic import BaseModel
from typing import Callable

class Tool:
    def __init__(self, name: str, description: str, func: Callable, args_model: type[BaseModel]):
        self.name = name
        self.description = description  # 描述写清“何时用/何时不用”，模型靠它选工具
        self.func = func
        self.args_model = args_model    # Pydantic 模型：模型传错参数在这里拦截

    def to_schema(self) -> dict:
        # 转成主流对话 API 的工具 schema 格式（function calling 标准形态）
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": self.args_model.model_json_schema(),
            }
        }

class ToolRegistry:
    def __init__(self):
        self.tools = {}

    def register(self, tool: Tool):
        self.tools[tool.name] = tool

    def get_schemas(self) -> list[dict]:
        return [t.to_schema() for t in self.tools.values()]

    async def execute(self, name: str, args: dict) -> dict:
        # 统一返回 {"success": ..., "data"/"error": ...}，错误不抛出、交给上层决策
        tool = self.tools.get(name)
        if not tool:
            return {"success": False, "error": f"工具 {name} 不存在"}
        try:
            validated = tool.args_model(**args)      # 参数校验：非法参数在这里报可读错误
            result = await tool.func(**validated.model_dump())
            return {"success": True, "data": result}
        except Exception as e:
            return {"success": False, "error": str(e)}
```

```python
# tools/search.py / calculate.py / summarize.py —— 三个最小工具
from pydantic import BaseModel, Field

class SearchArgs(BaseModel):
    query: str = Field(description="搜索关键词")
    top_k: int = Field(default=5, ge=1, le=20)  # 越界值（如 99）直接被拦截

async def search_web(query: str, top_k: int = 5) -> list:
    # 演示用模拟数据；接真实搜索 API 的做法见 2.3
    return [
        {"title": f"关于 {query} 的结果 {i}", "snippet": f"...{query}..."}
        for i in range(top_k)
    ]

class CalculateArgs(BaseModel):
    expression: str = Field(description="数学表达式")

async def calculate(expression: str) -> float:
    # 白名单校验后求值，仅演示；生产建议用 ast 安全求值（见 2.3）
    allowed = set("0123456789+-*/.() ")
    if not all(c in allowed for c in expression):
        raise ValueError("表达式含非法字符")
    return eval(expression, {"__builtins__": {}}, {})

class SummarizeArgs(BaseModel):
    texts: list[str] = Field(description="待总结文本列表")
    max_length: int = Field(default=200, description="摘要最大长度")

async def summarize(texts: list[str], max_length: int = 200) -> str:
    # 工具内调用 LLM 做总结；chat 为 5.2 的带重试封装（见 1.1）
    from llm import chat
    combined = "\n".join(texts)
    prompt = f"请把以下内容总结到 {max_length} 字以内：\n{combined}"
    return await chat([{"role": "user", "content": prompt}])
```

迭代一验收：注册 3 个工具后，传入 `top_k=99` 能被拦截并返回可读错误；调用不存在的工具返回“工具不存在”而非抛异常。

### 6.3 迭代二：规划、记忆与执行循环

```python
# planner.py —— 规划与重规划：输出 JSON 计划，低温保证稳定
import json
from llm import chat

PLANNER_PROMPT = """你是一个任务规划器。
把目标分解为可执行步骤，输出 JSON：
{{"steps": [{{"id": 1, "action": "...", "tool": "...", "args": {{}}}}]}}

可用工具：{tools}
目标：{goal}

只输出 JSON。"""

async def plan(goal: str, tools: list[str]) -> list:
    # 规划用低温：同一目标多次规划结果应基本一致
    response = await chat(
        [{"role": "user", "content": PLANNER_PROMPT.format(goal=goal, tools=tools)}],
        temperature=0,
        response_format={"type": "json_object"},  # 结构化输出，见 1.3
    )
    return json.loads(response)["steps"]

REPLAN_PROMPT = """原计划执行失败，请重新规划。

目标：{goal}
原计划：{plan}
失败原因：{error}

输出新计划 JSON：{{"steps": [...]}}"""

async def replan(goal: str, plan_data: list, error: str) -> list:
    # 重规划同样低温 + JSON 模式；新计划不应重复已成功完成的步骤
    response = await chat(
        [{"role": "user", "content": REPLAN_PROMPT.format(goal=goal, plan=plan_data, error=error)}],
        temperature=0,
        response_format={"type": "json_object"},
    )
    return json.loads(response)["steps"]
```

```python
# memory.py —— 双通道记忆：working 管任务状态，history 管对话窗口
from collections import deque

class Memory:
    def __init__(self, max_turns: int = 10):
        # 短期记忆：滑动窗口，只保留最近 max_turns 轮，防止撑爆上下文
        self.history = deque(maxlen=max_turns * 2)
        # 工作记忆：Agent 的“工序卡”——目标、计划、进度、每步结果
        self.working = {
            "goal": None,
            "plan": [],
            "current_step": 0,
            "step_results": {},
        }

    def add_message(self, role: str, content: str):
        self.history.append({"role": role, "content": content})

    def set_goal(self, goal: str):
        self.working["goal"] = goal

    def set_plan(self, plan_data: list):
        self.working["plan"] = plan_data

    def record_step(self, step_id: int, result):
        self.working["step_results"][step_id] = result
        self.working["current_step"] += 1

    def get_working(self) -> dict:
        return self.working

    def get_messages(self) -> list[dict]:
        return list(self.history)
```

```python
# agent.py —— Plan-Execute 主循环：规划 → 逐步执行 → 失败重规划 → 汇总
import json
import time
from llm import chat
from tools.registry import ToolRegistry
from tools.retry import execute_with_retry  # 迭代四：工具层失败分级重试
from memory import Memory
from planner import plan, replan
from trajectory import new_entry

SYSTEM_PROMPT = """你是一个研究助手。
你可以使用工具搜索、计算、总结。
按计划执行，每步记录结果。
如果工具失败，尝试其他方法或重规划。
"""

class ResearchAgent:
    def __init__(self, registry: ToolRegistry, max_steps: int = 15, max_replans: int = 2):
        self.registry = registry
        self.max_steps = max_steps      # 终止开关 1：最大步数，防死循环
        self.max_replans = max_replans  # 终止开关 2：重规划上限，防“失败→重规划”套娃
        self.memory = Memory()
        self.trajectory: list[dict] = []

    async def run(self, goal: str) -> dict:
        self.memory.set_goal(goal)
        self.trajectory = []
        replans_used = 0

        # 1. 规划
        plan_data = await plan(goal, list(self.registry.tools.keys()))
        self.memory.set_plan(plan_data)

        # 2. 执行循环：用 while 而不是递归重规划，轨迹不丢失、深度可控
        while True:
            for step in plan_data:
                # 断点续跑：已完成的步骤直接跳过（重规划后不重复执行）
                if step["id"] in self.memory.working["step_results"]:
                    continue
                # 终止开关 3：达到步数上限，停止执行、降级汇总
                if len(self.trajectory) >= self.max_steps:
                    return await self._summarize(goal, truncated=True)

                started_at = time.monotonic()  # 步骤开始时间：轨迹里的耗时从这算
                result = await self._execute_step(step)
                self.memory.record_step(step["id"], result)
                self.trajectory.append(new_entry(step, result, started_at))  # 迭代三接入

                # 3. 关键步骤失败 → 重规划；超上限则降级输出而不是崩溃
                if not result.get("success") and step.get("critical"):
                    if replans_used >= self.max_replans:
                        return await self._summarize(goal, truncated=True)
                    plan_data = await replan(goal, plan_data, result.get("error"))
                    self.memory.set_plan(plan_data)
                    replans_used += 1
                    break  # 跳出 for，带新计划回到 while 顶部
            else:
                # for 正常跑完：全部步骤执行完毕，进入汇总
                return await self._summarize(goal)

    async def _execute_step(self, step: dict) -> dict:
        tool_name = step.get("tool")
        if not tool_name:
            # 无工具步骤：当作“纯思考/整理”步骤，记录动作说明即可
            return {"success": True, "data": step.get("action")}
        args = step.get("args", {})
        return await execute_with_retry(self.registry, tool_name, args)  # 失败分级在工具层处理

    async def _summarize(self, goal: str, truncated: bool = False) -> dict:
        results = self.memory.working["step_results"]
        note = "（注意：因步数或重规划上限被截断，基于已有结果作答并说明局限。）" if truncated else ""
        prompt = f"""根据以下执行结果，回答目标。

目标：{goal}
结果：{json.dumps(results, ensure_ascii=False)}
{note}
请给出完整回答："""
        answer = await chat([{"role": "user", "content": prompt}])
        return {
            "answer": answer,
            "trajectory": self.trajectory,
            "steps": len(self.trajectory),
            "truncated": truncated,  # 降级标志：报告生成不等于任务完美完成
        }
```

迭代二验收：给一个 3 步目标，助手先打印计划再逐步执行，第 3 步能取到第 1 步的结果；把 `max_steps` 设为 2 重跑，任务在第 2 步后降级汇总，而不是死循环或崩溃。

### 6.4 迭代三：轨迹记录

轨迹是调试与复盘的唯一依据（生产级追踪见 3.4），格式统一、每步一行 JSONL：

```python
# trajectory.py —— 统一轨迹格式并落盘 JSONL，出问题能按步回放
import json
import time
from pathlib import Path

def new_entry(step: dict, result: dict, started_at: float | None = None) -> dict:
    started_at = started_at if started_at is not None else time.monotonic()
    return {
        "step": step["id"],
        "action": step["action"],          # 这一步想做什么
        "tool": step.get("tool"),          # 用了哪个工具（纯思考步骤为 null）
        "args": step.get("args"),          # 传了什么参数
        "success": result.get("success", False),
        "error": result.get("error"),      # 失败原因：定位问题的第一现场
        "duration_ms": round((time.monotonic() - started_at) * 1000),
    }

def dump_jsonl(trajectory: list[dict], path: str = "trajectory.jsonl") -> None:
    # 追加写：每次任务一段，复盘时逐行回放
    with Path(path).open("a", encoding="utf-8") as f:
        for entry in trajectory:
            f.write(json.dumps(entry, ensure_ascii=False) + "\n")
```

一次任务的轨迹示例（示意）：

```text
{"step": 1, "action": "检索市场规模数据", "tool": "search_web", "args": {"query": "... 市场规模 2024"}, "success": true, "error": null, "duration_ms": 1830}
{"step": 2, "action": "补充机构口径",     "tool": "search_web", "args": {"query": "... 市场报告"},   "success": true, "error": null, "duration_ms": 1620}
{"step": 3, "action": "计算增长率",       "tool": "calculate",  "args": {"expression": "45.6*1.35"}, "success": true, "error": null, "duration_ms": 4}
{"step": 4, "action": "总结素材",         "tool": "summarize",  "args": {"texts": ["..."]},          "success": true, "error": null, "duration_ms": 5210}
{"step": 5, "action": "汇总生成报告",     "tool": null,         "args": null,                        "success": true, "error": null, "duration_ms": 6480}
```

迭代三验收：每行至少含 step/tool/args/success/duration_ms 五个字段；人为让第 3 步失败，能只看 JSONL 说出“卡在哪一步、为什么”。

### 6.5 迭代四：失败处理与重规划

失败处理是四级阶梯：工具内重试 → 换参数/换方法 → 重规划 → 降级输出。前两级在工具层，后两级在循环层（§6.3 已内置）。

```python
# tools/retry.py —— 工具层失败分级：可重试退避重试，不可重试立刻上抛
import asyncio

RETRYABLE = ("timeout", "connection", "rate_limit", "超时", "限流")  # 可重试的错误特征

async def execute_with_retry(registry, name: str, args: dict, max_retries: int = 3) -> dict:
    for attempt in range(max_retries):
        result = await registry.execute(name, args)
        if result.get("success"):
            return result
        err = str(result.get("error", "")).lower()
        if not any(k in err for k in RETRYABLE):
            return result              # 不可重试（参数非法、工具不存在）：直接上抛规划层
        await asyncio.sleep(2 ** attempt)  # 指数退避（Exponential Backoff）：1s → 2s → 4s
    return result                      # 重试耗尽：交给 Agent 决定换方法或重规划
```

循环层的三条兜底（§6.3 代码已实现，此处点名）：

- **重规划上限**：`max_replans=2`，重规划两次仍失败就降级，杜绝无限套娃。
- **步数上限**：`max_steps=15`，任何异常路径最终都会停。
- **降级输出**：截断时仍基于已有结果出报告，并带 `truncated` 标志说明局限——失败不是终止，而是触发恢复。

基础反思（reflector.py 的最小形态）：执行后校验结果是否合理——搜索结果为空、数值离谱、摘要为空串，都算失败，触发换关键词重试一次；Self-Refine、Reflexion 等完整机制见 2.6，原型期不展开。

迭代四验收：把 search_web 改成前两次必超时，任务仍能完成且轨迹里能看到两次退避重试；把某步标成 `critical` 并让它必失败，能看到一次重规划与“不重复已完成步骤”。

## 7. 案例

### 案例 A：跑通一次完整调研

**场景**：学员完成四个迭代后，输入目标“调研 2024 年 AI Agent 市场规模，给出估算与依据”，验证四项里程碑。

**做法**：

```text
Step 1: search_web("AI Agent 市场规模 2024")   → 5 条结果，2 条含数字口径
Step 2: search_web("AI Agent 市场报告")        → 补充 1 家机构口径
Step 3: calculate("45.6 * 1.35")               → 按复合增长率推算下一年规模
Step 4: summarize([...])                       → 3 段素材压成 200 字要点
Step 5: 汇总生成报告                           → 结论 + 估算依据 + 数据来源
```

**示意数字效果**：一次任务 5 步，其中 3 步触发 LLM（规划、总结、汇总），输入输出合计约 1.6 万 token，用低价模型单次成本约 0.05 美元；轨迹 JSONL 共 5 行、总耗时约 15 秒；同一目标连跑 3 次，2 次结论一致（规划温度设 0）。

### 案例 B：从 ReAct 升级到 Plan-Execute

**场景**：学员先用 ReAct 循环做助手，目标超过 8 步就跑偏——第 6 步重复第 2 步的搜索，还理直气壮地又总结了一遍。

**ReAct 版本**：

```text
Thought → Action → Observation → Thought → ...
```

问题：边走边看，步骤多时容易丢失全局目标。

**Plan-Execute 版本**：

```text
Plan → Execute Step 1 → Execute Step 2 → ...
```

改进：结构清晰，可并行，可重规划。

**示意数字效果**：在 10 个测试目标的小评估集上，ReAct 版约 3 个跑偏、平均约 12 步；Plan-Execute 版跑偏降到 1 个以内、平均约 7 步，token 花费下降约四成；且计划可人事先审查，失败可定位到具体步骤。

### 案例 C：一次工具失败的自救

**场景**：运行研究助手，search_web 连续超时。

**处理**：

1. 重试 3 次（指数退避）。
2. 仍失败，返回错误。
3. Agent 反思：换个搜索词。
4. 重新执行。
5. 成功。

**示意数字效果**：在 20 次任务的小评估集中，工具层失败共 6 次：4 次靠退避重试成功、1 次换关键词后成功、1 次触发重规划后成功；无一次整任务崩溃，平均每次自救多花约 6 秒。关键结论：工具失败不是终止，而是触发反思和重试。

## 8. 常见坑

1. **工具太多，模型选错**。对策：从 3–5 个高内聚工具起步，选错率稳定后再加，机制见 2.3。
2. **工具描述不清，模型不知道何时用**。对策：描述写“何时用/何时不用”，具体到触发条件而不是功能罗列。
3. **参数不校验，模型传错参数工具就崩**。对策：所有参数走 Pydantic 模型，越界与缺字段在入口拦截。
4. **不做最大步数限制，Agent 死循环**。对策：循环必须带 max_steps 硬上限，超限降级输出。
5. **不做终止条件，不知道什么时候算完成**。对策：显式写完成判定（目标已答/计划跑完），并与步数上限、重规划上限组成三个开关。
6. **规划太粗或太细**。对策：控制在 3–10 步——太粗无法执行，太细浪费 token，见 2.2。
7. **不做重规划，一步失败整个任务失败**。对策：关键步骤失败触发 replan，且带次数上限防套娃。
8. **记忆不管理，历史无限增长**。对策：短期记忆用滑动窗口，工作记忆只存状态摘要，见 2.4。
9. **不做轨迹记录，出问题无法定位**。对策：每步记 step/tool/args/success/耗时，JSONL 落盘，见 §6.4。
10. **不做反思，错了不知道、一路错到底**。对策：加最小校验器（结果为空/数值离谱即失败），深入见 2.6。
11. **过度设计，简单任务用复杂架构**。对策：能工作流就工作流，Agent 留给步骤不可预知的任务，边界见 2.1、2.7。
12. **不评估，不知道 Agent 好不好**。对策：至少配 10 条评估集（目标 + 期望要点），跑完看成功率，见 2.9。
13. **不做错误处理，工具失败就崩溃**。对策：注册表统一捕获、统一返回结构，失败分级处理，见 §6.5。
14. **不做日志，无法调试**。对策：复用 5.2 的日志骨架，每步调用落盘，出问题先看轨迹再改代码。
15. **不写 README，项目无法复现**。对策：按“环境—安装—运行—验收”四段写清，同学 10 分钟能跑起来才算合格。

## 9. 练习

1. 定义 3 个工具，带 Pydantic 参数；验收：传入 `top_k=99` 被拦截并返回可读错误。
2. 实现工具注册表，支持注册、查询、执行；验收：调用不存在的工具返回“工具不存在”而非抛异常。
3. 实现工具失败重试（指数退避）；验收：模拟前两次失败第三次成功，总等待约 3 秒（1+2）。
4. 实现任务分解，输出 JSON 计划；验收：给 3 个不同目标，计划均为 3–10 步且每步能映射到已有工具。
5. 实现重规划：失败后生成新计划；验收：故意让第 2 步失败，新计划绕开失败路径且不重复第 1 步。
6. 实现工作记忆，记录每步结果；验收：任一步后打印 `get_working()`，能看到目标、计划、当前步与已完成结果。
7. 实现 ReAct 循环；验收：一个 3 步任务全程 Thought/Action/Observation 交替，且能自然终止。
8. 实现 Plan-Execute 循环；验收：同一 3 步任务先打印计划再执行，实际步数与计划一致。
9. 加最大步数和终止条件；验收：把 max_steps 设为 2 跑 5 步任务，第 2 步后降级汇总，不报错、不死循环。
10. 加轨迹记录；验收：trajectory.jsonl 每行含 step/tool/args/success/duration_ms 五个字段。
11. 加基础反思：检查结果是否合理；验收：构造“搜索结果为空”的步骤，Agent 能识别并换关键词重试一次。
12. 构建 10 条评估集（目标 + 期望要点）；验收：跑完输出成功率，且能指出失败任务卡在哪一步。
13. 写 README、录 Demo；验收：同学按 README 10 分钟内跑起来，Demo 视频不超过 3 分钟。
14. 自答 §4.5 的 10 个关键问题并录音回听；验收：每题 60 秒内讲清，讲不清的回锚点补课。

## 10. 小结

- 阶段 2 = **工具调用 + 规划 + 记忆 + 执行循环 + 状态机 + 终止控制**，对应知识地图 2.1–2.7，概念细节一律回锚点。
- 组队顺序：**2.1 → 2.3 → 2.2 → 2.4 → 2.5 → 2.6 → 2.7**——先工具后规划，先循环后反思，先单 Agent 后多 Agent，先原型后工程化。
- 里程碑口径：**能多步执行、调用工具、记录轨迹、处理失败**，逐项对照 §4.5 自检表打分，不合格回锚点补课。
- 最小项目：**工具型研究助手**，按四个迭代交付——定义工具、规划与执行循环、轨迹记录、失败处理。
- 终止三开关：**最大步数 + 重规划上限 + 完成判定**，缺任何一个都可能在真实任务里死循环或无限套娃。
- 失败处理是四级阶梯：**工具内重试 → 换参数换方法 → 重规划 → 降级输出**——失败不是终止，而是触发恢复。
- 高频卡点集中在**工具选择、JSON 解析、死循环、上下文爆炸、成本失控**五类，解法见 §4.6 速查表。
- 架构纪律：能用工作流解决的不上 Agent，工具从 3–5 个起步——这是面试“边界与取舍”类问题的共识口径。
- 时间预算：有阶段 1 基础 **3–4 周**；多 Agent（2.8）与系统评估安全（2.9）不在本阶段展开，分别留给 5.6 与 5.5。
- 这些能力直接支撑：**5.4 阶段 3：RAG 与工具增强**（私有知识库、检索评估、引用与权限过滤）。
