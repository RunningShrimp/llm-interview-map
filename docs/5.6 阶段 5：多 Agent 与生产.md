## 1. 定位

学习路径的第 6 个阶段，属于“从单 Agent 到多 Agent 生产系统”的跨越期。  
它解决一个核心问题：**当单 Agent 搞不定复杂任务时，如何用多个 Agent 协作把它做对做好，并在生产环境中控制成本、延迟与可靠性？**

对学习者，它是一份阶段作战计划：学什么、按什么顺序学、做什么项目、怎么验收。  
对知识地图，2.8 与 4.6 是“兵种”，5.6 负责把它们编成“作战序列”，用一个多 Agent 项目把知识串起来，4.7 负责最后的平台化收束。它是 5.7 综合项目与作品集的直接前置——5.7 的端到端项目，默认你会组队、会通信、会评估、会上线。

本阶段口径（与知识地图一致）：

| 项 | 内容 |
|---|---|
| 目标 | 多 Agent 协作与平台化 |
| 项目 | 多 Agent 内容/研究团队 |
| 里程碑 | 角色清晰、通信可控、评估证明优于单 Agent |
| 前续 | 5.5 阶段 4：AI 工程化 |

## 2. 一句话定义

阶段 5 多 Agent 与生产，是把多 Agent（Multi-Agent）协作范式、角色设计、通信协调与终止控制组队起来，把多 Agent 系统带上生产——可观测、成本可控、权限隔离、可部署——并用 A/B 对比数据证明它优于单 Agent，最后按平台化思路收束的工程实践阶段。

简化公式：

```text
阶段 5 = 多 Agent 协作 + 生产部署 + 成本控制 + 评估对比 + 平台化
验收口径 = 角色清晰 + 通信可控 + 用 A/B 数据证明优于单 Agent（三项缺一不可）
```

## 3. 为什么需要

单 Agent 在生产中会遇到瓶颈，任务越复杂越明显：

- **上下文不够**：复杂任务需要多源信息与长中间产物，一个 Agent 的上下文窗口（Context Window）塞不下。
- **能力冲突**：一个提示词（Prompt）难以同时擅长研究、分析、写作——指令互相稀释，样样通样样松。
- **无法并行**：多源检索只能串行做，延迟随信息源数量线性增长。
- **缺少制衡**：自己写自己审，错误自己发现不了。
- **职责不清**：一个 Agent 既查数据又写报告，出错难定位、难复现。
- **成本不透明**：不知道哪个环节花了多少钱，账单只看到一个总数。
- **难以扩展**：加一个能力要改整段提示词，牵一发动全身。

“硬拆 vs 按方法拆”对比：

| 维度 | 任务一复杂就硬拆多 Agent | 先过阶段 5 的方法再拆 |
|---|---|---|
| 质量 | 角色不清互相干扰、互相改稿，可能不如单 Agent | 角色单一、边界清晰，各司其职 |
| 通信 | 消息满天飞，轮数越多越乱 | 拓扑受限：只走 Supervisor 与共享状态 |
| 成本 | 调用次数翻几倍，账单失控 | 按角色配模型、缓存、限轮数，压进 3 倍内 |
| 可靠性 | 无终止条件，偶发无限循环烧穿预算 | 三重终止条件 + 预算告警 |
| 结论 | “感觉更好”，说不清值不值 | A/B 数据四项成表，值得与否有据 |
| 整体节奏 | 上手快一周，之后天天救火 | 慢半周建机制，之后加角色不改架构 |

两个类比，具体到场景（外加一句总括）：

```text
独行侠与车队：阶段 4 = 一个能上高速的独行侠司机；阶段 5 = 一支各司其职的车队——
              领航车（Supervisor）规划路线，侦查、维修、驾驶分工，但车队越大，
              对讲机通话（通信）越贵，不设收车时间（终止条件）就永远到不了终点。
报社编辑部：  单 Agent = 一个记者采访、写稿、审校全包，深度报道质量看运气；
              多 Agent = 主编派研究员、分析师、撰稿人、审校各管一段，产出稳定——
              但小快讯也开一次编委会，纯属浪费钱。
装修工程队：  小活（换水龙头）= 单 Agent；大活（整屋翻新）= 项目经理按工序派工，
              水电先行（流水线）、墙面吊顶并行（分工并行）、验收不合格返工（审查制衡）。
```

### 4.3 学习顺序与依赖（周计划表）

顺序的依据只有一条链：先有理论心智模型（2.8）再动手，动手直接复用实战骨架（4.6）；团队“能干活”之后先看得见（trace、成本）再判得出（A/B 评估）；评估证明值得之后，才谈部署与平台化收束（4.7）——把平台化放最后，是防止过早抽象。

| 步骤 | 锚点 | 为什么排在此时 | 产出物 | 参考时长 |
|---|---|---|---|---|
| 1 | 2.8 多 Agent 协作（理论） | 先建立范式、角色、通信、终止的完整心智模型，避免瞎试 | 口头讲清六种范式与各自适用场景 | 3–5 天 |
| 2 | 4.6 多 Agent 协作系统（实战） | 项目骨架直接复用其 Supervisor 与共享状态设计 | 跑通 Supervisor + 2 个 Worker 最小版 | 4–6 天 |
| 3 | 项目迭代一至三（本篇 §6） | 角色定义 → 通信协议 → Supervisor 汇聚，先让团队“能干活” | 4 Worker 内容团队可运行 | 1 周 |
| 4 | 3.4 / 3.7 回看 + 4.6 成本控制 | 多 Agent 的 trace 与成本归因复用 5.5 底座，重点补“多 Agent 特有的归因口径” | 全链路 Trace + 按 Agent 成本看板（迭代四） | 3–5 天 |
| 5 | 1.6 / 3.5 回看 + 项目迭代五 | A/B 对比是本阶段灵魂：判分口径、样本量、值得判据都要练 | 单 vs 多对比报告（30 条评估集） | 3–5 天 |
| 6 | 4.7 生产级 Agent 平台（收束） | 从“一个系统”到“一类系统”：注册、网关、治理 | K8s 部署上线 + Agent 注册表（迭代六） | 3–5 天 |

```text

   ↓

   ↓

   ↓

   ↓

   ↓
迭代六：平台化收束（4.7）+ K8s 部署（3.6 回看）
   ↓
验收：§4.5 三项里程碑逐项打分 → 5.7
```

五条原则：

- **先单后多**：单 Agent 能搞定的不上多 Agent。
- **先简单后复杂**：从流水线开始，再到 Supervisor、辩论。
- **先评估后上线**：必须做单 vs 多对比，数据说话。
- **先成本后规模**：多 Agent 成本是单 Agent 的数倍，预算线先划好。
- **先安全后开放**：每个 Agent 最小权限，越权拦截留痕。

### 4.5 里程碑自检表：角色清晰、通信可控、评估证明优于单 Agent

把三项里程碑拆成可逐项打分的自检表，全部达到合格口径才算通过。特别强调：**第三项必须用 A/B 数据证明，“感觉更好”不算数——这是本阶段的灵魂。**

| 自检项 | 合格口径 | 不合格信号 | 对应锚点 |
|---|---|---|---|
| 角色职责单一 | 每个 Agent 一句话说清“只做什么、不做什么”，提示词差异化 | 角色 Prompt 互相抄袭，两个 Agent 输出雷同 | 2.8、4.6 |
| 工具最小配置 | 每个 Agent 只挂其角色白名单内的工具 | 所有 Agent 共用一套工具全集 | 2.8、3.8 |
| 通信拓扑受限 | 只走 Supervisor 与共享状态（Shared State），Worker 之间不私聊 | 任意两个 Agent 互相发消息，消息数随轮数暴涨 | 2.8、4.6 |
| 状态下发收敛 | 下发给 Worker 的上下文只带目标与已有结论，不带全量过程 | 每轮把全部历史塞给所有 Agent，token 疯涨 | 4.6 |
| 有终止条件 | 轮数硬上限 + 计划为空 + 完成判定，三重保险 | 辩论或审查循环停不下来 | 2.8、4.6 |
| 有 A/B 数据 | 同一评估集、同一判分口径，质量分、成功率、成本比、延迟比四项成表 | 只报质量不报成本，或只有一条任务的结果 | 4.6、1.6、3.5 |
| 值得判据明确 | 质量提升超过阈值且成本比可接受，才下“值得上线”的结论 | 结论是“感觉更好”，无判据 | 4.6、3.7 |
| 轨迹可回放 | 凭一个 trace_id 能回放整次协作：哪一轮、谁、调了什么工具、花了多少 | 只有最终答案，过程是黑箱 | 3.4 |

配套的 10 个关键问题（口头全部答清即达标）：

1. 什么时候该用多 Agent，什么时候不该？
2. Supervisor、辩论、并行、流水线怎么选？
3. 角色怎么划分才不重叠？
4. 共享状态和消息传递怎么选？
5. 多 Agent 怎么避免无限循环？
6. 多 Agent 成本怎么控制在 3 倍以内？
7. 怎么做单 Agent vs 多 Agent 的 A/B 对比？
8. 多 Agent 的 Trace 怎么设计才能回放整次协作？
9. 多 Agent 怎么做权限隔离？
10. 多 Agent 系统怎么部署、扩展，何时该平台化？

**面试高频问法**：阶段 5 学完，以下两问应能给出共识口径的回答——“什么时候该用多 Agent？”（任务可分解为需要不同专长、不同工具或不同视角的子任务，且并行或制衡能带来可测量的质量收益时；单 Agent 加好提示词与工具能解决的，一律不上多 Agent）；“多 Agent 一定比单 Agent 好吗？”（不一定：通信与协调成本随 Agent 数量超线性增长，质量提升必须用同一评估集的 A/B 数据证明，且成本比、延迟比同时可接受才算真的更好——这正是本阶段里程碑的第三项）。

### 4.6 高频卡点与解法速查

| 卡点 | 典型症状 | 第一时间解法 | 深入锚点 |
|---|---|---|---|
| 过早上多 Agent | 单 Agent 基线都没测就拆团队 | 先测单 Agent 基线，质量或成功率确实不达标再拆 | 2.8、4.6 |
| 角色重叠 | 两个 Agent 输出雷同、互相改稿 | 重写角色卡：职责单一、边界清晰、提示词差异化 | 2.8、4.6 |
| 通信爆炸 | 每轮消息数随轮数近乎平方增长 | 限制拓扑：一切经 Supervisor 与共享状态 | 2.8 |
| 无限循环 | 辩论、互相审查停不下来 | 轮数硬上限 + 完成判定双保险 | 2.8、4.6 |
| 成本失控 | 多 Agent 账单是单 Agent 5 倍以上 | 小模型分工 + 缓存 + 限轮数 + 并行，先归因再优化 | 4.6、3.7 |
| Trace 断裂 | 出问题看不出是哪个 Agent 错 | 统一 trace 上下文，从 Supervisor 根 span 贯穿到每个 Worker 与工具 | 3.4 |
| 规划输出解析失败 | Supervisor 的 JSON 计划解析报错 | 温度 0 + 结构化输出 + 解析失败重试兜底 | 1.3 |
| 权限混乱 | Writer 也能调 SQL 工具 | 工具白名单按角色配置，越权拦截并留审计痕 | 3.8、4.7 |
| A/B 对比不公平 | 一边温度 0 一边 0.7，样本只有一条 | 同评估集、同判分、同温度，跑 3 次取均值 | 1.6、3.5 |
| 过早平台化 | 3 个 Agent 就要建注册中心与网关 | 先交付系统再抽象平台，多个系统出现后再平台化 | 4.7 |

```python
    },

AGENT_PERMISSIONS = {
    "researcher": ["search_web", "search_docs"],
    "analyst": ["execute_sql", "execute_python"],
    "writer": [],
    "critic": [],
}

def check_agent_tool_permission(agent_name: str, tool: str) -> bool:
    return tool in AGENT_PERMISSIONS.get(agent_name, [])

async def execute_with_agent_permission(agent_name: str, tool: str, args: dict):
    if not check_agent_tool_permission(agent_name, tool):
        raise PermissionError(f"Agent {agent_name} 无权调用 {tool}")  # 拦截并留审计痕
    return await execute_tool(tool, args)
```

### 6.3 迭代二：通信协议——Agent 基类与共享状态

```python
# agents/base.py —— Worker 基类：最多 5 步工具调用，产出带成本的结构化结果
import json

class BaseAgent:
    def __init__(self, name: str, system_prompt: str,
                 tools: dict | None = None, model: str = "gpt-4o-mini"):
        self.name = name          # 角色名，与 ROLES / AGENT_PERMISSIONS 对齐
        self.system_prompt = system_prompt
        self.tools = tools or {}  # 只挂该角色白名单内的工具
        self.model = model        # 按角色配模型：简单角色用小模型省钱

    async def execute(self, task: str, context: str = "") -> dict:
        messages = [
            {"role": "system", "content": self.system_prompt},
            {"role": "user", "content": f"上下文：\n{context}\n\n任务：\n{task}"},
        ]
        for _ in range(5):  # 工具循环硬上限：防单个 Worker 内部转圈
            response = await llm.chat(messages, tools=self.tools, model=self.model)
            if not response.tool_calls:  # 模型不再要工具，视为完成
                return {"agent": self.name, "output": response.content,
                        "cost": response.cost}
            messages.append(response.message)
            for tc in response.tool_calls:  # 逐个执行工具并把结果喂回
                result = await execute_with_agent_permission(self.name, tc.name, tc.args)
                messages.append({"role": "tool", "tool_call_id": tc.id,
                                 "content": json.dumps(result, ensure_ascii=False)})
        return {"agent": self.name, "output": "未完成（达到工具步数上限）"}
```

```python
# orchestration/state.py —— 共享状态：唯一事实源 + 成本闸门（设计见 4.6）
import json

class SharedState:
    def __init__(self, goal: str = "", max_rounds: int = 3):
        self.goal = goal
        self.results = {}              # {task_id: result}，唯一事实源，Worker 不私藏结论
        self.current_round = 0
        self.max_rounds = max_rounds   # 终止条件之一：轮数硬上限

    def add_result(self, task_id: str, result: dict) -> None:
        self.results[task_id] = result

    def to_context(self) -> str:
        # 成本闸门：只下发目标 + 已有结论，不带全量过程消息
        return json.dumps({"goal": self.goal, "results": self.results},
                          ensure_ascii=False)
```

验收：连续跑 3 轮，下发给 Worker 的上下文长度基本不随轮数线性膨胀。

### 6.4 迭代三：汇聚——Supervisor 协调循环

Supervisor（监督者）模式是多 Agent 最常用的协作范式：一个主管决定每轮派谁做什么，Worker 只干活、回报结果。

```python
# orchestration/supervisor.py —— Supervisor：规划 → 并行执行 → 汇聚，三重终止条件
import asyncio
import json
from agents.base import BaseAgent
from observability.tracing import MultiAgentTracer
from llm import chat
from state import SharedState

class SupervisorAgent:
    def __init__(self, workers: dict[str, BaseAgent], tracer: MultiAgentTracer):
        self.workers = workers
        self.state: SharedState | None = None
        self.tracer = tracer

    async def run(self, goal: str, max_rounds: int = 3) -> dict:
        self.state = SharedState(goal=goal, max_rounds=max_rounds)
        with self.tracer.start_span("multi_agent_run") as span:
            span.set_attribute("goal", goal)
            for round_num in range(max_rounds):          # 终止条件 1：轮数硬上限
                self.state.current_round = round_num + 1
                with self.tracer.start_span(f"round_{round_num + 1}") as round_span:
                    next_tasks = await self._plan_next()  # 1. 规划：这一轮派谁做什么
                    if not next_tasks:
                        break                             # 终止条件 2：计划为空
                    results = await self._execute_tasks(next_tasks)  # 2. 并行执行
                    for task, result in zip(next_tasks, results):    # 3. 汇聚进共享状态
                        self.state.add_result(task["id"], result)
                        round_span.add_event("task_completed", {
                            "task_id": task["id"], "worker": task["worker"],
                            "cost": result.get("cost", 0)})
                    if await self._is_complete():         # 终止条件 3：完成判定
                        break
            return await self._aggregate()                # 4. 汇总最终答案

    async def _plan_next(self) -> list[dict]:
        prompt = f"""你是主管。根据目标和当前进展，决定下一步分配给哪些 Worker。
目标：{self.state.goal}
已完成：{json.dumps(self.state.results, ensure_ascii=False)}
可用 Worker：{list(self.workers.keys())}
输出 JSON：{{"tasks": [{{"id": "...", "worker": "...", "description": "..."}}]}}
如果已完成，输出 {{"tasks": []}}。"""
        response = await chat([{"role": "user", "content": prompt}], temperature=0)
        return json.loads(response.content).get("tasks", [])

    async def _execute_tasks(self, tasks: list[dict]) -> list[dict]:
        async def run_one(task: dict) -> dict:
            worker = self.workers[task["worker"]]
            return await worker.execute(task["description"], self.state.to_context())
        # 同轮任务并行执行：延迟取决于最慢分支，而不是所有任务之和
        return await asyncio.gather(*[run_one(t) for t in tasks])

    async def _is_complete(self) -> bool:
        prompt = f"""目标：{self.state.goal}
当前结果：{json.dumps(self.state.results, ensure_ascii=False)}
目标是否已完成？只输出 yes 或 no。"""
        response = await chat([{"role": "user", "content": prompt}], temperature=0)
        return "yes" in response.content.lower()

    async def _aggregate(self) -> dict:
        prompt = f"""根据以下结果生成最终答案。
目标：{self.state.goal}
结果：{json.dumps(self.state.results, ensure_ascii=False)}"""
        response = await chat([{"role": "user", "content": prompt}], temperature=0.3)
        return {"answer": response.content, "state": self.state.results}
```

验收：给定主题走完“研究 → 分析 → 写作 → 审查”，3 轮内终止并产出成稿。

### 6.5 迭代四：可观测——全链路 Trace 与成本归因

多 Agent 出问题时的第一问永远是“哪一轮、哪个 Agent、哪个工具错了、花了多少钱”——没有 trace 和成本归因就只能猜。

```python
# observability/tracing.py —— 多 Agent 全链路 Trace：一棵 span 树回放整次协作
from opentelemetry import trace

tracer = trace.get_tracer("multi-agent")

class MultiAgentTracer:
    def start_span(self, name: str):
        # 从 multi_agent_run 根节点贯穿到每个 round、agent、tool，形成一棵树
        return tracer.start_span(name)

    def record_agent_call(self, agent_name: str, input_text: str,
                          output_text: str, cost: float):
        with tracer.start_as_current_span(f"agent_{agent_name}") as span:
            span.set_attribute("agent", agent_name)
            span.set_attribute("input", input_text[:200])   # 截断，防存储爆炸
            span.set_attribute("output", output_text[:200])
            span.set_attribute("cost", cost)

    def record_tool_call(self, tool: str, args: dict, result: dict, latency: float):
        with tracer.start_as_current_span(f"tool_{tool}") as span:
            span.set_attribute("tool", tool)
            span.set_attribute("latency", latency)
            span.set_attribute("success", result.get("success", False))
```

```python
# observability/cost.py —— 成本归因：按 Agent / 按轮 / 按任务三个口径记账
from collections import defaultdict

class MultiAgentCostTracker:
    def __init__(self):
        self.cost_by_agent = defaultdict(float)
        self.cost_by_round = defaultdict(float)
        self.cost_by_task = defaultdict(float)

    def record(self, agent: str, round_num: int, task_id: str, cost: float):
        self.cost_by_agent[agent] += cost
        self.cost_by_round[round_num] += cost
        self.cost_by_task[task_id] += cost

    def report(self) -> dict:
        return {
            "total": sum(self.cost_by_agent.values()),
            "by_agent": dict(self.cost_by_agent),  # 谁最费钱，一眼看出
            "by_round": dict(self.cost_by_round),  # 轮数是否过多，一眼看出
            "top_tasks": sorted(self.cost_by_task.items(), key=lambda x: -x[1])[:10],
        }
```

验收：凭一个 trace_id，10 分钟内回答“这次协作哪一轮、哪个 Agent、哪个工具最贵”。

### 6.6 迭代五：单 vs 多 A/B 对比评估（本阶段灵魂）

A/B 对比（A/B Testing）的实验设计先写清楚，再跑数：

| 对比维度 | 怎么测 | 判读口径 |
|---|---|---|
| 质量分 | 同一评估集（30 个主题），LLM 评审（LLM-as-Judge）按事实、深度、结构打 1–10 分，各跑 3 次取均值 | 提升 > 0.5 分才算显著更好 |
| 成功率 | 完成判定通过且无事实硬伤的比例 | 多 Agent 应高出 10 个百分点以上 |
| 成本比 | 双方 token 花费之比 | 3 倍内为合格，超过 5 倍重新设计 |
| 延迟比 | 端到端耗时之比（并行执行后应远低于轮数 × 单轮耗时） | 内容生产类 ≤ 3 倍 |
| 结论 | 四项成表，写明“值得 / 不值得 / 什么场景值得” | 没有数据的“感觉更好”不算结论 |

```python
# eval/compare.py —— 单 vs 多 A/B：同一任务、同判分口径，产出决策字段
import time

async def compare_single_vs_multi(task: str, single_agent, multi_agent) -> dict:
    single_start = time.time()
    single_result = await single_agent.run(task)   # 单 Agent 基线（Baseline）
    single_latency = time.time() - single_start

    multi_start = time.time()
    multi_result = await multi_agent.run(task)     # 多 Agent 团队
    multi_latency = time.time() - multi_start

    single_quality = await judge_quality(task, single_result["answer"])
    multi_quality = await judge_quality(task, multi_result["answer"])
    single_cost = single_result.get("cost", 0)
    multi_cost = multi_result.get("cost", 0)

    return {
        "single": {"quality": single_quality, "latency": single_latency,
                   "cost": single_cost},
        "multi": {"quality": multi_quality, "latency": multi_latency,
                  "cost": multi_cost},
        "quality_lift": multi_quality - single_quality,      # 质量提升
        "cost_ratio": multi_cost / max(single_cost, 0.0001),  # 成本比
        "latency_ratio": multi_latency / max(single_latency, 0.001),
        # 单条任务的值得判据：质量提升 > 0.1（1–10 分制）且成本比 < 5，两条件同时满足
        "worth_it": (multi_quality - single_quality > 0.1)
                    and (multi_cost / max(single_cost, 0.0001) < 5),
    }
```

注意：生产决策看整评估集上四项指标的均值与分布，不用单条任务的 worth_it 下结论。

验收：30 个主题跑完，报告含质量分、成功率、成本比、延迟比四组对比数字与明确结论。

## 7. 案例

### 案例 A：多 Agent 内容生产团队（主案例）

**场景**：一家科技自媒体要做深度行业文章。单 Agent 版本（一个好提示词 + 检索工具）在复杂主题上事实错漏多、结构松散。

**做法**：Supervisor + 4 Worker——Researcher 并行检索 3 个信息源，Analyst 提炼趋势与论据，Writer 成稿，Critic 审查；不合格打回重写一轮，最多 3 轮。

**示意数字效果**（30 个主题的评估集，各跑 3 次取均值）：

| 维度 | 单 Agent | 多 Agent | 判读 |
|---|---|---|---|
| 质量分（1–10） | 7.2 | 8.5 | +1.3 分，显著更高 |
| 成功率 | 75% | 92% | +17 个百分点 |
| 延迟 | 45s | 90s | 2 倍，可接受 |
| 成本 | $0.03 | $0.12 | 4 倍，需判是否值得 |

**结论**：质量提升约 18%、成功率显著提高，代价是 4 倍成本与 2 倍延迟——深度文章是高价值任务，值得；短快讯类任务继续走单 Agent。

### 案例 B：把成本从 5 倍压进 3 倍

**场景**：一位学员的首版多 Agent 团队跑完评估，成本达到单 Agent 的 5 倍，超出预算线。

**做法**（四项优化，前两项贡献最大）：

1. 简单 Worker 换小模型：Critic、Researcher 用低价小模型，Writer 保留强模型。
2. 缓存 Researcher 结果：同一主题的检索结果按查询缓存，命中不再调用。
3. 最大轮数从 5 收到 3：消灭大部分“空转轮”。
4. 同轮任务并行执行：延迟取决于最慢分支而非任务之和。

**示意数字效果**：成本比从 5.0 降到 2.8，落进 3 倍预算线；P95 延迟（P95 Latency）从 150s 降到 95s；质量分基本不变（8.5 → 8.4）——优化成本不必牺牲质量，关键是先归因再动手。

### 案例 C：权限隔离拦下越权调用

**场景**：红队测试中，Writer 收到的“参考资料”里混入了提示注入（Prompt Injection）内容，随后试图调用 execute_sql 查询数据库。

**做法**：工具白名单按角色配置（writer 的权限列表为空），越权调用在 Worker 基类内被 PermissionError 拦截，事件写入审计日志与 trace；Supervisor 下一轮把该任务改派给有权限的 Analyst。

**示意数字效果**：20 次越权尝试全部被拦截、拦截记录 100% 留痕；凭 trace 定位到注入源约 10 分钟——同类问题在没有 trace 时靠翻日志约 2 小时。多 Agent 的攻击面比单 Agent 更大，注入会沿通信扩散，权限隔离是必须项而非加分项。

## 8. 常见坑

1. **过早多 Agent**。对策：先测单 Agent 基线，质量或成功率确实不达标再拆团队——单 Agent 能搞定的不上多 Agent。
2. **不做 A/B 对比就上线**。对策：上线前用同一评估集跑单 vs 多，质量、成功率、成本、延迟四项成表，没有数据就没有结论。
3. **角色重叠**。对策：重写角色卡，职责单一、边界清晰、提示词差异化；两个 Agent 做同样的事，砍掉一个。
4. **通信爆炸**。对策：限制拓扑——Worker 之间不私聊，一切经 Supervisor 与共享状态。
5. **无终止条件**。对策：轮数硬上限 + 计划为空 + 完成判定，三重保险防无限循环。
6. **成本失控**。对策：多 Agent 调用次数是单 Agent 的数倍，先按 Agent 归因找出大头，再上小模型、缓存、限轮数。
7. **Trace 断裂**。对策：从 Supervisor 根 span 贯穿到每个 Worker 与工具，全链路一棵树，否则出问题只能猜。
8. **成本不归因**。对策：按 Agent、按轮、按任务三个口径记账，报表能直接指出最贵的角色与最贵的轮。
9. **权限不隔离**。对策：每个 Agent 最小权限的工具白名单，越权拦截并写审计日志。
10. **部署复杂化**。对策：多 Agent 逻辑收敛为一个服务、用统一网关对外，K8s 与扩缩写法见 3.6。
11. **调试靠 print**。对策：轨迹复杂时用 trace 回放逐轮分析，定位到具体 Agent 与工具再改。
12. **上线后不做持续评估**。对策：评估集每周回归一次，角色或提示词任何改动都重跑对比。
13. **忽略延迟**。对策：同轮无依赖任务并行执行，延迟取决于最慢分支而非轮数之和。
14. **不做安全**。对策：多 Agent 攻击面更大，注入会沿通信扩散，输入过滤 + 权限隔离双管齐下（见 3.8）。
15. **过早平台化**。对策：先把一个系统交付上线，出现第二个、第三个系统再抽平台，按 4.7 的演进路线走。

## 9. 练习

1. 不看资料手画六种协作范式（流水线、分工并行、辩论、监督、层级等）的拓扑图并各举一个适用场景；验收：10 分钟内画全、讲清。
2. 实现 Supervisor 模式，带 4 个 Worker；验收：给定主题 3 轮内产出完整文章。
3. 实现辩论模式：正方 + 反方 + 裁决者，最多 2 轮；验收：输出三方观点与最终裁决。
4. 实现并行分工：3 个 Researcher 同时检索不同信息源再汇总；验收：总延迟低于串行版的一半。
5. 实现共享状态与消息传递（Message Passing）两种通信方式并对比；验收：写清各自适用规模与成本差异。
6. 给多 Agent 系统加三重终止条件；验收：构造一个“永远完不成”的任务，系统在硬上限处停下。
7. 实现多 Agent 全链路 Trace；验收：凭一个 trace_id 回放“哪一轮、谁、调了什么工具、花了多少钱”。
8. 实现按 Agent 的成本归因；验收：report() 能指出最贵的 Agent 与最贵的一轮。
9. 做单 Agent vs 多 Agent 的 A/B 对比；验收：30 条评估集，质量、成功率、成本比、延迟比四项成表并有结论。
10. 实现多 Agent 权限隔离；验收：Writer 调 execute_sql 被拦截且审计有记录。
11. 部署多 Agent 到 K8s 并配 HPA；验收：压测下副本自动扩缩，且可灰度发布与回滚。
12. 写 README 与对比报告；验收：一位同学按 README 复现，并看懂报告中“值得与否”的结论。
13. 回答 §4.5 的 10 个关键问题并录音回听；验收：每题 60 秒内讲清，讲不清的回锚点补课。

## 10. 小结

- 阶段 5 = **多 Agent 协作 + 生产部署 + 成本控制 + 评估对比 + 平台化**，知识来源是 2.8（理论）、4.6（实战）、4.7（平台化）。
- 组队顺序：**2.8 → 4.6 → 项目六迭代 → 3.4 / 3.7 / 3.8 / 3.6 回看（复用 5.5 底座）→ 4.7 平台化收束**。
- 里程碑三项：**角色清晰、通信可控、评估证明优于单 Agent**——第三项是本阶段灵魂，必须用 A/B 数据说话，逐项对照 §4.5 自检表打分。
- 最小项目：**多 Agent 内容/研究团队**（Supervisor + Researcher / Analyst / Writer / Critic），六个迭代交付：角色定义 → 通信协议 → 汇聚 → 可观测 → A/B 评估 → 平台化收束。
- 核心原则：**先单后多、先简单后复杂、先评估后上线、先成本后规模、先安全后开放。**
- 时间预算：**有阶段 4 基础 3–4 周**，有多 Agent 经验 2–3 周，零多 Agent 经验 4–5 周。
- 高频卡点集中在 **过早多 Agent、角色重叠、通信爆炸、无限循环、成本失控** 五类，解法见 §4.6 速查表。
- 面试共识口径：多 Agent 不是默认更优——任务可分解、子任务需要不同专长或视角、质量收益大于数倍成本时才用，且结论必须来自同评估集的 A/B 数据。
- 这些能力直接支撑：**5.7 阶段 6：综合项目与作品集**（端到端独立交付、指标与演示、可复现文档与复盘）。
