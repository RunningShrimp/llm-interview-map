# 讲解 H.5 A2A 协议与多 Agent 互操作

> 说明：前置 2.3（工具使用：Agent 怎么安全调用外部函数）、2.8（多 Agent 协作：同一系统内的编排拓扑与协作范式）、3.3（编排框架与运行时：MCP 协议与框架选型）——三篇分别管「单 Agent 怎么用工具」「系统内怎么协作」「工程栈怎么选」，都没有回答「跨框架、跨组织的 Agent 之间怎么互操作」。

> 后续：多租户、工具市场、审计这些平台化治理边界在 4.7 展开；远端 Agent 不可信时的沙箱隔离与可靠执行在 H.8；沙箱之外的安全体系口径见 3.8。

## 1. 定位

H 层（前沿层）第 5 个锚点，星级 4，直接前置 2.3（工具使用；MCP 的深入对比在 3.3 展开）。

站点状态口径：**面试出现中**——截至 2026 年，4 个独立中文题库设 A2A 专项题：小林面试笔记、知乎 118 题（第 79 题标注「2026 新题」）、卡码 Agent 题库第 8 题、面试鸭（题库，2025-2026）。考点卡来源口径为「A2A 官方 v1.0（Linux Foundation 2026-03）/ 卡码」。考察以概念题为主，已确证的高频原题是：

**「MCP 和 A2A 都是协议，有什么区别？为什么 MCP 解决不了 A2A 要解决的问题？」**（卡码笔记原题面，2025-2026）

必须掌握的事实口径（截至 2026 年，引用时注意版本与时间点）：

1. **发起与治理**：A2A 由 Google 于 2025-04 发起，2025-06 捐入 Linux Foundation（Linux 基金会）做厂商中立治理。

4. **Signed Agent Cards**：v1.0 引入签名 Agent Card——能力名片可附签名，防篡改、防冒充，这是从「声明式发现」走向「可验证发现」的关键一步。

## 2. 一句话定义

A2A 是一个开放的 Agent 互操作协议：每个 Agent 在标准位置暴露一张能力名片（Agent Card），其他 Agent（或客户端）据此发现它、用结构化任务（Task）委托工作、按生命周期状态回报进度与产物——让不同框架、不同厂商的 Agent 像对等组织一样协作，委托方无需知道对方的内部实现。

简化公式：

```text
A2A = Agent Card（发现） + Task 生命周期（委托与跟踪） + Opaque 协作（黑盒边界）
效果：N 个异构 Agent 的对接成本从 N x (N-1)/2 条私有集成，压成 N 份协议实现
```

## 3. 为什么需要

### 3.1 集成地狱重现

Agent 生态爆发后，问题回到三十年前企业软件的老路。痛点清单：

- **框架割裂** → 你的 Agent 用框架 X，合作伙伴的差旅 Agent 用框架 Y，第三方的数据分析 Agent 是某云厂商闭源服务，消息格式、任务模型、鉴权全对不上。
- **两两定制** → 每两方协作就得做一次私有集成：N 个 Agent 需要 N x (N-1)/2 条定制对接线，第 N+1 个加入时再改 N 条。
- **能力不可发现** → 对方是 Agent 还是普通 API？擅长什么任务域？怎么建立信任？全靠口口相传的接口文档。
- **长任务无法跟踪** → 订一张机票要几分钟到几小时，私有 API 的请求-响应模型没有「处理中/需补件/已完成」的状态语义。
- **责任无法追溯** → 跨组织委托出了错，谁发起的、发给了谁、带了什么数据、返回了什么，拿不出证据链。
- **厂商锁定** → 深度绑定某家平台的私有 Agent 接口，换供应商等于重做一遍集成。

协议把 N x (N-1)/2 压成 N：每方实现一次 A2A，即可与所有实现方互通——这与 HTTP 统一网站接入、SMTP 统一邮件互通是同一个经济学。

| 维度 | 逐对私有集成 | 标准 协议接入 |
|---|---|---|
| 首次接入成本 | 较低（只做一家） | 较高（实现协议全套语义） |
| 第 2..N 家边际成本 | 每家都接近重做 | 接近零（复用同一客户端） |
| 供应商可替换性 | 差，锁定深 | 好，名片一换即切换 |
| 能力发现 | 无，靠文档 | 标准化（Agent Card） |
| 长任务/补件/取消 | 每家各造一遍 | 协议内置（Task 状态机） |
| 审计留痕 | 各家格式不一 | taskId 全程可追溯 |

两个类比（站点考点卡口径，具体到场景）：

- **Agent 界的 HTTP**：各家 Agent 像早期孤岛式即时通讯软件——互相加不了好友，A 公司的用户给 B 公司的用户发消息要装两个客户端。A2A 之于 Agent，如 HTTP 之于网站：统一的能力名片、任务委托、消息格式，任何符合协议的 Agent 都能与任何其他 Agent 协作，不管底层框架。
- **外包协作合同**：MCP 像公司给员工配的标准工具台（内部怎么接工具，员工从统一的工具柜取用）；A2A 像公司之间的外包合同（对等组织如何委托任务）——甲方把任务连同验收标准发给乙方，乙方用自己的团队（自己的模型、自己的工具）完成，按协议回报进度与产物；乙方内部怎么干活，甲方无权过问，只验收结果。

### 3.2 为什么 MCP 解决不了 A2A 的问题

这是本题的核心采分点，也是最容易答错的地方。MCP 不是「差一点的 A2A」，而是抽象层级不同的另一层协议：

| 维度 | MCP | A2A |
|---|---|---|
| 连接对象 | Agent ↔ 工具/资源（垂直） | Agent ↔ Agent（水平，对等） |
| 角色模型 | Client-Server：工具是被动能力，被调用即返回 | 对等协作：远端 Agent 是自主执行者，有自己的状态与策略 |
| 交互形态 | 一次工具调用，同步取结果 | 长任务生命周期：可运行数分钟到数天，异步推进 |
| 能力声明 | 工具的参数 schema（怎么调这个函数） | Agent Card（我是谁、擅长什么任务域、怎么找我、怎么鉴权） |
| 过程透明度 | 调用方完全掌控执行 | Opaque（不透明协作）：内部模型/工具/流程对委托方黑盒 |
| 多轮交互 | 工具不反问调用方 | input-required 状态：远端可挂起等用户补充信息 |
| 典型问题 | 「我的 Agent 怎么接上你的数据库」 | 「我的 Agent 怎么把订票任务外包给你的 Agent」 |

（MCP 的完整机制——Tools/Resources/Prompts 三类供给、USB 统一接口类比——见 3.3 的 4.6 节，此处不重复展开。）

具体论证「为什么 MCP 不够」，四条：

1. **工具没有自主性**。MCP Server 是被动的函数集合，被调用、执行、返回；A2A 的远端是一个完整的 Agent——它自己规划、自己用工具、自己处理异常。把一个 Agent 当 MCP 工具暴露，等于要求委托方接管它的全部内部编排，跨组织做不到也不该做。
2. **没有任务生命周期**。MCP 调用是请求-响应，几分钟的长任务没有「处理中/需要补件/已完成/失败」的状态机，委托方无法跟踪、无法挂起恢复、也无法取消。
3. **没有能力发现的对等语义**。MCP 的工具列表回答「你有哪些函数」；A2A 的 Agent Card 回答「你是谁、能承包什么任务、如何建立信任」——这是组织间协作需要的商业语义，不是函数签名。
4. **信任与责任模型不同**。Agent 间委托涉及鉴权、责任边界、审计留痕——外包合同的条款；工具调用只涉及函数执行正确性。

结论：**MCP 管垂直的工具接入，A2A 管水平的 Agent 协作——互补而非竞争**。同一个 Agent 完全可以既用 MCP 接自己的工具，又用 A2A 接受外部委托；截至 2026 年，主流云平台与编排框架普遍同时支持两者。

## 4. 核心原理

### 4.1 五个核心对象

A2A 的数据模型围绕五个对象展开，一张表看全：

| 对象 | 是什么 | 关键内容 | 谁生产/消费 |
|---|---|---|---|
| Agent Card | 能力名片（JSON 文档） | 协议版本、技能清单、端点、鉴权方案、能力开关 | Server 发布，Client 发现时消费 |
| Task | 任务对象，协作的基本单位 | 全局唯一 taskId、状态机、交互历史 | Client 发起，Server 推进 |
| Message | 任务内的一轮消息 | role（user/agent）、parts（内容块列表） | 双方交替生产 |
| Part | 消息的内容块 | 文本块、文件块、数据块（结构化 JSON） | 双方 |
| Artifact | 任务产物 | 出票后的行程单、生成的报告等最终交付物 | Server 生产，Client 验收 |

两个设计要点：

- **Part 模型让消息可混合承载自然语言与结构化数据**——委托指令用文本块说清意图，预算上限、日期约束用数据块带结构化字段，机器可校验、可回放。
- **Artifact 与 Message 分离**——过程中的沟通（「正在查询航班」）是 Message，最终交付物（行程单文件）是 Artifact，验收与计费只认 Artifact。

### 4.2 Agent Card：能力名片与发现机制

每个 A2A Server 在约定位置暴露 Agent Card，这是发现的起点：

- **标准位置**：`https://<host>/.well-known/agent.json`（well-known URI 约定，与 OAuth、ACME 证书验证同一路数——把「去哪找元数据」也标准化）。
- **签名（v1.0 重点）**：Signed Agent Cards 允许名片附带签名，客户端用发布方公钥验证卡片未被篡改、确实来自声明的主体——跨组织场景里防冒充的信任锚。
- **发现路径**：直接已知 URL 拉取；或经注册表/目录服务聚合检索（企业内部可自建 Agent 目录，把各部门的 Card 聚合起来统一检索）。

名片核心字段一览：

| 字段 | 内容 | 委托方用它做什么 |
|---|---|---|
| protocolVersion | 协议版本（如 1.0） | 兼容性校验，版本不符拒绝对接 |
| name / description | 名称与能力自述 | 粗筛：这个 Agent 管不管我的需求域 |
| url | A2A 服务端点 | 后续 message/send 的目标地址 |
| version | 名片自身版本 | 缓存失效判断，感知对方升级 |
| capabilities | 能力开关（流式、推送通知） | 决定轮询还是订阅的实现方式 |
| authentication | 鉴权方案声明 | 我方凭据管理是否支持该方案 |
| skills | 技能清单（id/描述/标签/示例） | 精筛：具体任务匹配到哪个技能 |

工程要点：名片声明的是「能力边界即接口」——委托方只依赖名片描述做决策，能力是否名实相符要靠沙箱验证（见第 8 节坑 2）。类比：名片如外卖平台的商家页——菜单（skills）、资质公示（签名）、配送范围（能力边界）都写在页面上，协议保证页面真实（签名可验），不保证菜好吃（能力要实测）。

### 4.3 Task：任务生命周期与状态机

A2A 的核心数据模型是 Task，有全局唯一 ID 与状态机：

```text
submitted（已提交）→ working（执行中）→ completed（已完成）
                          |
                          ├→ input-required（等待补充信息，挂起）
                          └→ failed（失败）/ canceled（取消）
```

状态转移与双方职责对照：

| 状态 | 含义 | 谁触发 | 委托方该做什么 |
|---|---|---|---|
| submitted | 任务已受理，尚未开工 | Server 收到消息即置 | 记录 taskId，启动跟踪 |
| working | 执行中（对方在自己规划、调工具） | Server | 轮询/订阅更新，不催单 |
| input-required | 挂起，等补充信息 | Server | 桥接我方用户补信息，同 taskId 续传 |
| completed | 完成，产物就绪 | Server | 验收 Artifact，归档计费 |
| failed | 失败 | Server | 取失败原因，决定重试/换家/上报 |
| canceled | 取消 | Client 发起 | 走取消流程，清理本地状态 |

委派流程四步：

1. **发现**：拉取对方 Agent Card，确认技能匹配、鉴权可行、协议版本兼容。
2. **发送**：向对方端点发 `message/send`（或流式 `message/stream`），消息里带任务意图与结构化上下文（行程、偏好、预算上限、验收标准）。
3. **生命周期管理**：用 `tasks/get` 轮询或订阅通知跟踪状态；input-required 时桥接我方用户补信息再续；长任务可注册推送回调（push notification，推送通知，如 Webhook）。
4. **交付**：completed 后取回 Artifact 并归档计费；失败则按预案处理（重试、换供应商、上报）。

关键设计：**支持长任务与多轮补信息**——这正是 MCP 单次调用模型缺失的能力，也是「外包合同」类比里「按阶段汇报、缺材料找甲方要」的协议化。

### 4.4 Opaque 协作：能力边界即接口

A2A 明确规定委托方不假设对方的内部实现：对方用什么模型、什么框架、什么工具，一概黑盒。收益：

- 双方可各自独立升级内部实现（换模型、换框架），接口不变即合约不变。
- 厂商中立：框架 X 与框架 Y 互通不需要任何一方迁就。
- 责任清晰：内部怎么做是乙方的事，合约看输入输出与验收标准。

代价是信任必须外置：签名名片验证身份、沙箱任务验证能力、留痕审计验证行为——协议给通道，信任靠配套（本篇 4.6 节展开）。

与 2.8 的对照值得记牢：2.8 的多 Agent 协作里，编排者看得见每个成员的内部状态（共享状态、黑板、消息总线）；A2A 里委托方只看得见状态机与产物。**你控制所有参与者时用编排，你不控制对方时用协议**——这是两种多 Agent 形态的本质分水岭，也是本篇 4.8 节选型判断的第一性依据。

### 4.5 传输与消息形态

- **消息格式**：核心形态是 HTTPS 上的 JSON-RPC 消息（`message/send`、`message/stream`、`tasks/get`、`tasks/cancel` 等方法）；v1.0 提供多传输绑定并保持消息语义一致。
- **鉴权**：在 HTTP 层完成（API key、OAuth 2.0 等，名片中声明），协议本体不另造身份体系。

三种任务跟踪方式的取舍（长任务集成的实现决策）：

| 跟踪方式 | 机制 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 轮询（tasks/get） | 定时拉取任务状态 | 实现最简单，无回调依赖 | 有延迟、空轮询浪费 | 对接初期、不支持流式的对方 |
| 流式（message/stream） | SSE（Server-Sent Events，服务器推送事件）持续推送 | 过程实时可见，体验最好 | 占用长连接 | 秒级到分钟级任务的实时反馈 |
| 推送通知（push notification） | 委托方注册回调，状态变更被主动通知 | 不占连接，适合小时级任务 | 要暴露回调端点、验签 | 批量报表等超长任务 |

工程默认：**先轮询跑通语义，再按对方 capabilities 与任务时长升级到流式或推送**。

### 4.6 安全考量：协议给通道，信任靠配套

跨组织 Agent 协作的攻击面比工具调用宽：远端不可信、名片可被冒充、委托内容本身可携带恶意指令。威胁与对策一张表：

| 威胁 | 场景 | 对策 |
|---|---|---|
| 名片冒充 | 假冒合作方 Agent 发布名片，骗取委托 | Signed Agent Cards 签名验证 + 域名/来源核对 |
| 名片夸大 | 声称支持的技能实际做不到 | 沙箱任务实测后再放量 |
| 越权调用 | 凭据 scope 过大，远端可动不该动的资源 | 最小授权 scope，按任务域发凭据 |
| 数据过度披露 | 委托消息顺手带上全套用户数据 | 最小化披露，证件号等敏感字段按需传 |
| 间接提示注入（Indirect Prompt Injection） | 委托文本里夹带「忽略之前指令」类内容，污染远端执行 | 内容过滤 + 远端侧权限最小化 + 高危动作人工确认（1.7 与 3.8 口径） |
| 传输窃听篡改 | 明文传输任务与产物 | 强制 HTTPS/TLS |
| 抵赖与纠纷 | 出错后双方各执一词 | taskId、消息、产物全程留痕归档（3.4 口径） |
| 供应链传导 | 上游 Agent 被攻破，坏结果污染下游决策 | 产物校验、异常结果隔离、不盲信 Artifact |

面试高频问法：「A2A 场景下的安全怎么考虑？」——分层作答：身份层（签名名片、OAuth）、授权层（最小 scope）、内容层（注入过滤）、审计层（全链路留痕）；一句话收尾：**协议管互操作，不管信任——信任是工程与合同的配套**。

### 4.7 协议格局：A2A / MCP / ACP / ANP

2026 年社区讨论常四者并列，定位各有侧重（ACP/ANP 细节以官方文档为准，生态仍早期）：

| 协议 | 发起方与治理 | 定位 | 一句话差异 |
|---|---|---|---|
| MCP | Anthropic 开放规范，2025-12 捐入 Linux Foundation 旗下基金会 | Agent↔工具/资源（垂直接入） | 管设备：标准工具台（USB 统一接口类比，见 3.3） |
| A2A | Google 2025-04 发起，Linux Foundation 治理 | Agent↔Agent（水平协作，跨组织） | 管外包：能力名片 + 任务生命周期 |
| ACP | IBM/BeeAI 等推动 | Agent 间通信（REST、低门槛） | 走纯 HTTP/REST 的轻量替代路线，强调离线/进程间场景 |
| ANP | 开源社区 | 去中心化 Agent 网络 | DID（Decentralized Identifier，去中心化身份标识符）为根的开放互联网路线 |

判读：MCP 已是事实标准；A2A v1.0 定稿后进入主流云平台，是跨组织互操作的主导候选；ACP/ANP 代表不同取舍（轻量化 vs 去中心化）。面试表态建议：**讲清 MCP/A2A 分工为主，ACP/ANP 一句话带过并诚实标注成熟度**。

### 4.8 何时用、何时不用：互操作方案选型

这是考点卡架构题里「成熟度判断」的采分点。选型只问两个问题：**参与方数量**与**异构程度**（组织、框架、供应商是否受你控制）。

| 方案 | 适用条件 | 不适用 | 成本特征 |
|---|---|---|---|
| 2.8 的内部编排（LangGraph、Agents SDK 等） | 同一组织、同一代码库，你控制所有参与者 | 跨组织、对方不受你控制 | 低 |
| 私有 API 集成 | 单一稳定合作方，长期关系 | 多厂商、多框架、供应商会更换 | 每家一次性中高 |
| MCP | 给 Agent 接工具/数据/提示模板 | Agent 对 Agent 的任务委托 | 低且标准化 |
| A2A | 多厂商/多框架/跨组织，委托关系，长任务需跟踪 | 单合作方、内部编排、秒级同步调用 | 协议实现一次，边际趋零 |
| 消息队列/事件总线 | 组织内异步解耦、事件驱动 | 需要 Agent 语义（名片、状态机、补件） | 中 |

决策树：

```text
参与者都在你的控制之下（同组织同代码库）？
├─ 是 → 2.8 的内部编排，不需要 A2A
└─ 否 → 跨了组织边界，对方是什么？
    ├─ 对方是工具/数据（被动能力）→ MCP（3.3）
    └─ 对方是 Agent（自主执行者）→
        ├─ 只有一个合作方且任务秒级同步 → 私有 API 足够
        └─ 多厂商/多框架，任务长、需补件与验收 → A2A
```

三条经验判据（截至 2026 年的工程共识口径）：

1. **多数内部系统不需要 A2A**——单组织内的多 Agent 协作用 2.8 的编排即可，协议的收益（厂商中立、对等发现）在组织边界内体现不出来。
2. **参与方 ≥3 且异构时收益转正**——第二家、第三家供应商接入的边际成本接近零，这是 N x (N-1)/2 → N 的直接体现。
3. **秒级同步调用不必上 A2A**——一次查询、一次翻译，普通 API 或 MCP 工具调用更轻；A2A 的价值在长任务、多轮补件、需要验收与留痕的委托关系。

## 5. 架构 / 流程

一次跨厂商协作的完整时序：

```text
 主 Agent（框架 X，我方）                差旅 Agent（框架 Y，合作方）
        |                                        |
        |  ① 发现：GET /.well-known/agent.json    |
        |--------------------------------------->|
        |  ← Agent Card：技能"订票/订酒店"、        |
        |    鉴权 OAuth、支持流式与推送             |
        |  （验签名，确认能力与边界）                |
        |                                        |
        |  ② 委托：message/send（含验收标准）       |
        |--------------------------------------->|
        |    task: "预订 9/10 北京→上海，          |
        |     靠窗经济舱，预算上限 1500"            |
        |     验收：出票成功 + 行程单               |
        |                                        |
        |  ③ 状态回报（SSE / tasks/get 轮询）       |
        |<------- working（查询航班中）------------|
        |<------- input-required（需护照信息）-----|
        |------- 补充信息（同 taskId 续传）------->|
        |<------- completed + Artifact 行程单 -----|
        |                                        |
        |  ④ 验收产物 → 归档、计费、审计留痕         |
```

分层视角：单个 Agent 的完整互操作栈——垂直与水平两层叠加：

```text
┌──────────────────────────────────────────────────────────┐
│  组织边界 A                                      组织边界 B │
│  ┌──────────────────────────┐      ┌───────────────────┐  │
│  │ 主 Agent（框架 X）         │      │ 差旅 Agent（框架 Y）│  │
│  │  ├ 执行循环与状态机（2.5）  │      │  ├ 执行循环（2.5）  │  │
│  │  ├ 记忆（2.4）             │      │  ├ 规划（2.2）      │  │
│  │  └ MCP Client             │      │  └ MCP Client      │  │
│  │       │ 垂直接入层（3.3）   │      │     垂直接入层      │  │
│  └───────┼────────────────────┘      └─────────▲─────────┘  │
│          │                                     │            │
│          └────── A2A 水平协作层 ────────────────┘            │
│           （Agent Card 发现 + Task 状态机 + Artifact）        │
└──────────────────────────────────────────────────────────┘
```

要点：Agent 内部是 2.7 的单 Agent 架构 + MCP 接工具（垂直）；Agent 之间是 A2A 的名片与任务（水平）；**两层叠加才是完整的多 Agent 互操作栈**。目录聚合、计费、审计这些治理能力，在 4.7 的平台层完成。

### 6.2 委派客户端：发现 → 委托 → 生命周期管理（Python）

```python
import time
import requests

class A2AClient:
    """最小 A2A 客户端：发现、委托、跟踪生命周期。
    生产实现请用官方 SDK；此处展示协议语义。"""

    def __init__(self, base_url: str, token: str):
        self.base = base_url.rstrip("/")
        self.headers = {"Authorization": f"Bearer {token}"}  # HTTP 层鉴权
        self._id = 0  # JSON-RPC 请求 id

    # ---- 第 1 步：发现（拉取并校验能力名片）----
    def discover(self) -> dict:
        origin = self.base.split("/a2a")[0]                  # 名片在源站根路径
        card = requests.get(
            f"{origin}/.well-known/agent.json", timeout=5
        ).json()
        # 生产环境：验签名（Signed Agent Cards）+ 核对鉴权方案是否支持
        assert card["protocolVersion"].startswith("1."), "协议版本不匹配"
        return card

    @staticmethod
    def has_skill(card: dict, keyword: str) -> bool:
        return any(keyword in s["name"] or keyword in s["description"]
                   for s in card.get("skills", []))

    # ---- 第 2 步：委托任务（JSON-RPC message/send）----
    def send(self, text: str, task_id: str | None = None) -> dict:
        self._id += 1
        payload = {
            "jsonrpc": "2.0", "id": self._id, "method": "message/send",
            "params": {
                "message": {
                    "role": "user",
                    "parts": [{"type": "text", "text": text}],  # 文本内容块
                    "taskId": task_id,           # 续传时带同一 taskId
                    "messageId": f"m-{self._id}",
                },
            },
        }
        return requests.post(self.base, json=payload,
                             headers=self.headers, timeout=30).json()

    # ---- 第 3 步：跟踪生命周期（tasks/get 轮询）----
    def get_task(self, task_id: str) -> dict:
        self._id += 1
        payload = {"jsonrpc": "2.0", "id": self._id,
                   "method": "tasks/get", "params": {"id": task_id}}
        return requests.post(self.base, json=payload,
                             headers=self.headers, timeout=10).json()["result"]

    def wait_terminal(self, task_id: str, max_polls: int = 30,
                      interval: float = 2.0) -> dict:
        for _ in range(max_polls):
            state = self.get_task(task_id)
            s = state["status"]["state"]
            if s == "input-required":            # 远端要补信息 → 桥接我方用户
                answer = ask_our_user(state["status"]["message"])
                state = self.send(answer, task_id=task_id)   # 同 taskId 续传
                continue
            if s in ("completed", "failed", "canceled"):
                return state
            time.sleep(interval)                 # 轮询间隔，避免打爆对方
        raise TimeoutError("任务未在轮询窗口内到达终态")  # 兜底：超时转取消

def ask_our_user(remote_question: dict) -> str:
    print("远端 Agent 需要：", remote_question)
    return input("> ")

# ---- 完整委派 ----
client = A2AClient("https://travel.example.com/a2a", token="OAUTH_TOKEN")
card = client.discover()
assert client.has_skill(card, "机票"), "对方名片没有订票技能"

resp = client.send(
    "预订 9/10 北京→上海经济舱靠窗，预算上限 1500 元；"
    "验收标准：出票成功 + 交付行程单。"
)
task_id = resp["result"]["id"]
final = client.wait_terminal(task_id)

if final["status"]["state"] == "completed":
    artifacts = final.get("artifacts", [])      # 行程单等产物（Artifact）
    print("交付产物：", [a["name"] for a in artifacts])
    # 第 4 步：归档、计费、审计留痕（task_id 全程可追溯）
else:
    print("任务终态：", final["status"])
```

### 6.3 服务端最小骨架（FastAPI 示意）

客户端之外，被委托方（A2A Server）的协议义务同样清楚：暴露名片、受理任务、推进状态机、交付产物。

```python
from fastapi import FastAPI, Request

app = FastAPI()
TASKS = {}  # 生产环境换持久化存储；重启不丢任务是底线（见坑 7）

@app.get("/.well-known/agent.json")
def agent_card():
    return CARD  # 6.1 的名片；生产环境附签名字段

@app.post("/a2a")
async def a2a_endpoint(req: Request):
    """JSON-RPC 统一入口：按 method 分发到协议方法"""
    body = await req.json()
    method, params = body["method"], body.get("params", {})

    if method == "message/send":                 # 委托或续传
        msg = params["message"]
        task_id = msg.get("taskId")
        if task_id is None:                      # 新任务：受理即 working
            task_id = new_task_id()
            TASKS[task_id] = {"status": {"state": "working"},
                              "history": [msg]}
            dispatch_to_agent(task_id, msg)      # 交给内部执行循环（2.5）
        else:                                    # 续传：解除 input-required
            resume_task(task_id, msg)
        return rpc_ok(body["id"], TASKS[task_id])

    if method == "tasks/get":                    # 状态查询
        return rpc_ok(body["id"], TASKS[params["id"]])

    if method == "tasks/cancel":                 # 取消
        TASKS[params["id"]]["status"]["state"] = "canceled"
        return rpc_ok(body["id"], TASKS[params["id"]])
    return rpc_err(body["id"], -32601, "method not found")

# 内部 Agent 执行完一个阶段后回调：
def on_stage_done(task_id: str, state: str, artifact: dict | None = None):
    """working / input-required / completed / failed 四类回报；
    completed 时把 Artifact（行程单）挂到任务上，等 tasks/get 取回。"""
    TASKS[task_id]["status"]["state"] = state
    if artifact:
        TASKS[task_id]["artifacts"] = [artifact]
```

实现要点：Server 侧的核心是把「内部执行循环的状态」翻译成「协议状态机的状态」——内部怎么规划、怎么调工具（Opaque）委托方一概不关心，它只认六个协议状态与最终 Artifact。

### 6.4 自检清单：接一个外部 Agent 前必做

```text
[ ] 拉取 Agent Card 并验证签名/域名一致性
[ ] 核对鉴权方案与我方凭据管理方式
[ ] 用沙箱任务实测能力（名片≠实测能力，见坑 2）
[ ] 约定任务超时、重试与取消策略
[ ] 明确敏感字段最小化披露清单（证件号等）
[ ] 合同明确责任边界（出错谁担责）与审计留痕方案
[ ] capabilities 协商：对方不支持流式/推送时回退到轮询
```

## 7. 案例

### 案例 A：跨厂商差旅集成

**场景**：某公司自研客服 Agent（框架 X），需要接入合作伙伴差旅 Agent（框架 Y）帮客户订票。此前评估过两条路：为对方做一次私有 API 集成（约 4 人周，且对方换版本就得重做）；按 A2A 对接（双方各实现一次，名片与任务模型对齐）。

**做法**：沙箱环境先发 50 个测试任务验证对方真实能力与响应格式；生产上处理 input-required 桥接（护照信息由我方用户补充，敏感字段只传乘机所必需的）；completed 后验收行程单 Artifact 并计费归档；任务全程留痕可审计。

**效果（示意数字，复盘口径）**：集成周期从预估 4 人周缩到 1.5 人周；上线后 3 个月接入第二家差旅供应商，复用同一客户端、只改名片地址与凭据，边际成本接近零——**多厂商异构接入时标准化收益才真正显现**，这正是本篇 4.8 节判据 2 的实例。

### 案例 B：企业内部多团队 Agent 互联

**场景**：一家金融科技公司内部有五个团队各自的 Agent（客服、风控、合规、数据、运维），技术栈各异——两家用 LangGraph、一家用厂商托管服务、两家自研，原来互不通信，跨域需求靠人工转发工单。

**做法**：内部建 Agent 目录（聚合各团队的 Agent Card），主客服 Agent 通过 A2A 把「该笔交易是否命中风控规则」委托给风控 Agent，把「引用哪条合规条款」委托给合规 Agent；长任务（批量报表）走异步任务 + 推送通知；每个团队各自维护名片，升级内部实现不改接口。

**效果（示意数字）**：跨域请求平均处理时长从约 4 小时降到约 15 分钟（人工转发环节被协议化委托取代）；每个 Agent 的边界由名片声明，职责冲突类工单下降约六成。注意这里的判断细节：五团队分属不同技术栈、彼此不控制对方实现——已满足「多方 + 异构」判据，组织内部也值得上协议；若五团队同框架同代码库，2.8 的编排更省。

### 案例 C：冷静判断——什么时候不用 A2A

**场景**：某团队只有一个外部合作方，被「上协议」的号召推着做了约 3 个月 A2A 对接，期间对方协议实现还在频繁变更，联调反复返工。

**修正与教训**：合作方仅此一家、任务又是秒级同步调用时，双方约定的私有 API 更快更稳；协议的价值在多方异构生态。技术选型先问**参与方数量与异构程度**（本篇 4.8 节）——这是考点卡架构题里「成熟度判断」的采分点。2026 年的合理姿态：跟踪 v1.0 生态落地速度，多厂商场景优先采用，单点合作场景不必赶早。

## 8. 常见坑

1. **把 A2A 和 MCP 当竞争方案**。  
   一个连工具（垂直）一个连 Agent（水平），答成替代关系直接丢分；正确口径是互补叠加。

2. **名片即信任**。  
   名片可以夸大甚至被冒充。签名验证 + 沙箱实测，两者都做。

3. **把远端 Agent 当函数调**。  
   忽视任务生命周期，长任务不做轮询/推送，超时无兜底。按状态机写集成。

4. **input-required 没有桥接设计**。  
   远端挂起等补件，我方无人处理，任务永久挂起。桥接我方用户或默认策略必须有。

5. **敏感信息过度披露**。  
   委托消息里顺手带上全套用户数据。最小化披露，按需传字段。

6. **无超时无取消**。  
   对方 Agent 挂了，我方跟着挂。每个任务设超时、可取消（tasks/cancel）、可重试。

7. **服务端任务不持久化**。  
   Server 重启丢任务，委托方轮询永远等不到终态。任务状态落库是底线。

8. **不做留痕审计**。  
   跨组织协作出纠纷时拿不出证据。taskId、消息、产物全程归档（3.4 口径）。

9. **跳过沙箱验证直连生产**。  
   名片说支持不等于真支持。上线前用测试任务验证响应格式与异常行为。

10. **责任边界口头约定**。  
    出票出错谁担责没写进合同。协议管通道，责任靠合同。

11. **版本不锁定**。  
    对方升级协议版本导致字段变更。发现时校验 protocolVersion，兼容策略前置。

12. **单合作方硬上协议**。  
    参与方只有一家时私有 API 更快。先问生态规模再选型（本篇 4.8 节）。

13. **用 A2A 做同进程内部编排**。  
    同一代码库里的多 Agent 协作套上协议开销（HTTP 往返、状态机翻译），白付复杂度。内部编排回 2.8，协议留给组织边界。

14. **忽略间接注入面**。  
    委托文本本身可夹带注入指令，污染远端执行并随产物回传。内容过滤 + 远端最小权限 + 高危动作人工确认。

15. **不协商 capabilities 就按流式写**。  
    对方名片没开 streaming/pushNotifications，客户端按 SSE 写死，运行期报错。读 capabilities 并写好轮询回退。

## 10. 小结

- A2A 是 **Agent 互联的开放标准**：能力名片（Agent Card）+ 任务生命周期（Task）+ 不透明协作（Opaque），类比「Agent 界的 HTTP」+「组织间外包合同」。
- 事实口径（截至 2026 年）：**Google 2025-04 发起、2025-06 捐入 Linux Foundation，2026-03 定稿 v1.0（随后 v1.0.1），一周年 150+ 组织参与、进入主流云平台与企业生产部署**。
- Agent Card 发现：标准位置 **/.well-known/agent.json**，名片声明技能、鉴权、能力开关；v1.0 起可签名（Signed Agent Cards）防篡改防冒充。
- 任务生命周期：**submitted → working → input-required → completed/failed/canceled**，支持长任务、多轮补信息（同 taskId 续传）、流式（SSE）与推送通知。
- 与 MCP 的分工（标准采分点）：**MCP 管 Agent↔工具（垂直接入），A2A 管 Agent↔Agent（水平协作）**——互补而非竞争，同一 Agent 可以两层都挂。
- MCP 解决不了 A2A 的问题，因为抽象层级不同：**工具是被动函数，Agent 是自主执行者**；长任务状态机、能力发现的对等语义、信任与责任模型，都是工具调用层没有的。
- 安全分层口径：**签名名片（身份）+ 最小授权（权限）+ 注入过滤（内容）+ 全程留痕（审计）**；协议管通道，信任靠配套与合同。
- 格局：**MCP 已是事实标准，A2A v1.0 是跨组织互操作的主导候选，ACP（REST 轻量）/ ANP（DID 去中心化）为不同取舍路线**，生态早期、诚实标注成熟度。
- 选型冷静剂：**参与方数量与异构程度决定收益**——多厂商、跨组织、长任务委托上 A2A；单点合作用私有 API；组织内部的协作回 2.8 的编排。
- 与站内衔接：垂直接入层回看 2.3 与 3.3，系统内协作看 2.8，平台化治理看 4.7——A2A 补上的是平台之外的水平协作层；远端不可信时的沙箱与可靠执行在 H.8。
- 这些能力直接支撑：4.7 生产级 Agent 平台、H.8 Agent 沙箱与可靠执行。
