# 讲解 3.10 人机协同与反馈闭环

> 说明：3.4 可观测性与追踪给出全链路 Trace，3.5 评估体系给出验证改版的手段，本篇站在两者之上回答：系统上线后，**人该在哪些节点介入、反馈怎么回流，才能越用越好**。  
> 与 2.5 的分工：2.5 的 WAITING_HUMAN 解决「循环怎么暂停、怎么恢复」，本篇解决「什么值得暂停、审批怎么设计、数据怎么回流」。  
> 后续 4.5 工作流自动化 Agent 把审批落进企业流程，4.7 生产级 Agent 平台把这套闭环平台化。

## 1. 定位

AI 工程化层第 10 个知识点，也是 AI 工程化层的收尾。  
它解决的核心问题：**人在哪些节点介入最有效？以及如何设计人机分工、收集反馈、标注数据、持续迭代，让 Agent 在真实使用中不断改进，而不是上线即巅峰？**

- 直接前置：3.4 可观测性与追踪（反馈回流依赖完整 Trace 与 Bad case 定位）、3.5 评估体系与实验管理（改进是否有效依赖评估集验证）。
- 后续承接：4.5 工作流自动化 Agent（审批是企业工作流的一等公民）、4.7 生产级 Agent 平台（反馈闭环是平台的标配能力）。
- 边界：本篇讲人机分工与反馈闭环的**设计**（审批策略、反馈采集、数据回流、持续学习）；单步执行怎么挂起与恢复属于 2.5 的执行循环与状态机。

## 2. 一句话定义

人机协同与反馈闭环，是在 Agent 系统的关键节点引入人工判断（审批、确认、审核），收集用户反馈（Feedback）与标注数据，通过持续学习循环，让系统在真实场景中不断优化的工程体系。

简化公式：

```text
反馈闭环（Feedback Loop） = 人工介入 + 反馈收集 + 标注回流 + 分析改进 + 验证再上线
```

## 3. 为什么需要

全自动 Agent 的局限：

- **高风险操作不能自动**：退款、删除、转账，错了不可逆。
- **边界情况处理不了**：训练数据没覆盖的场景，Agent 会犯错。
- **主观判断需要人**：语气、品牌调性、敏感话题。
- **用户不信任**：全自动决策，用户不敢用。
- **错误无法纠正**：Agent 错了，没人能改。
- **不会从错误中学习**：同样错误反复出现。
- **反馈无处可去**：用户点踩，但没人处理。
- **上线即巅峰**：上线后效果固定，不会变好。

**类比 1**：

```text
全自动 Agent   = 一家不允许员工提问、不允许客户投诉的公司
人机协同 Agent = 一家员工可求助上级、客户可投诉、每起投诉都进复盘会的组织
```

**类比 2**：

```text
审批门   = 银行柜员的大额取现授权：柜员（Agent）自己能办小额业务，
           超过额度必须请主管（人）放行——额度就是风险阈值
反馈闭环 = 导航 App 的路况上报：一个用户上报封路，地图更新，
           所有用户都绕行——个体反馈变成全局改进
```

## 4. 核心原理

### 4.1 人机协作模式

| 模式 | 说明 | 适用 |
|---|---|---|
| 人在环内（Human-in-the-Loop, HITL） | 人参与每一步决策 | 高风险、低容错 |
| 人在环上（Human-on-the-Loop, HOTL） | 人监督，异常时介入 | 中等风险 |
| 人不在环（Human-out-of-the-Loop） | 全自动 | 低风险、高容错 |
| 人做决策（Human-in-Command） | 人做最终决策 | 战略决策 |
| 混合模式 | 按风险分级路由 | 生产推荐 |

**混合模式示例**：

```text
低风险操作（查询、计算）        → 全自动
中风险操作（写入、通知）        → 自动 + 事后审计
高风险操作（退款、删除）        → 人工审批
极高风险（转账、合规对外动作）  → 人工决策
```

### 4.2 介入点选型：人在哪些节点介入最有效

这是本锚点的关键问题，正面回答：介入点沿执行时间轴分布，**越靠前拦截能力越强，延迟与人力代价也越高**，选型就是在风险 × 成本 × 延迟之间找平衡。

| 介入点 | 机制 | 拦截能力 | 延迟代价 | 人力成本 | 典型适用 |
|---|---|---|---|---|---|
| 行动前审批 | 高危动作执行前必须人批（审批门） | 强：错误不会发生 | 高：用户等待 | 高 | 不可逆操作：转账、删除、对外发送 |
| 行动中确认 | 长任务的关键步骤逐个放行 | 强 | 高 | 高 | 多步任务的敏感分支 |
| 结果后审核 | 先执行，事后人工/规则审计抽检 | 弱：错误已发生，可止损 | 低：异步 | 低 | 可回滚、低风险高频操作 |
| 持续反馈 | 用户对结果点赞点踩，回流改进 | 无：只影响未来版本 | 几乎无 | 低 | 全场景标配 |

选型推导：

```text
单次错误损失 × 不可逆程度 高   → 越早介入（行动前 / 行动中）
操作频率高 × 单次损失低        → 结果后审核（抽检为主）
中间地带                      → 风险触发式审批（规则/置信度决定是否升级，见 4.3）
任何介入点之上                → 叠加持续反馈（不影响本次结果，只让下次更好）
```

**面试高频问法**：「什么操作必须人工审批，什么可以自动执行？」共识口径分三档：只读、可逆、可回滚的操作自动执行；写内部状态但可撤销的操作自动执行 + 事后审计；不可逆或影响外部世界（资金、删除数据、对外通信、合规敏感）的操作必须人审，并在档内再按金额/影响范围分级——小额自动、大额人审。

### 4.3 升级触发：什么时候把人拉进来

风险触发式审批的核心是升级（Escalation）判定，五个条件任一命中即挂起任务：

```python
def should_escalate(state: AgentState) -> bool:
    # 1. 置信度低
    if state.confidence < 0.7:
        return True
    # 2. 高风险操作
    if state.next_action in HIGH_RISK_TOOLS:
        return True
    # 3. 金额超阈值
    if state.next_action == "refund" and state.args.get("amount", 0) > 500:
        return True
    # 4. 连续失败
    if state.consecutive_failures >= 2:
        return True
    # 5. 用户主动要求
    if state.user_requested_human:
        return True
    return False
```

### 4.4 HITL 审批工作流

一套完整的审批工作流（Approval Workflow）有三个必备构件（截至 2026 年社区设计资料的共识口径，如 StackAI 2026 年的审批工作流指南）：

| 构件 | 说明 | 缺了会怎样 |
|---|---|---|
| 审批门（Approval Gate） | 高风险动作前挂一道门，Agent 暂停、等待人类决定 | 高危操作直接执行，出错不可逆 |
| 升级策略（Escalation） | 超时未审批 → 升级到上级 / 换通道提醒 / 默认拒绝 | 审批积压，用户无限等待 |
| 决策留痕（Decision Logging） | 每次审批记录：谁、何时、批了什么、依据什么 | 出事无法审计追溯（见 3.8 合规） |

**审批策略对比**——审批不等于全审，四种策略人力成本递减：

| 策略 | 做法 | 人力成本 | 风险覆盖 | 延迟 | 适用 |
|---|---|---|---|---|---|
| 全审 | 每次都人批 | 最高 | 全覆盖 | 高 | 上线初期、极高危操作 |
| 风险触发 | 规则/置信度触发才审（4.3） | 中 | 覆盖已知风险 | 中 | 生产主流 |
| 抽审 | 事后随机抽样审核 | 低 | 统计性覆盖 | 无（事后） | 低风险高频操作 |
| 预授权 | 事先授权范围，范围内自动 | 一次性 | 范围内全覆盖 | 无 | 信任建立后的稳定期 |

典型演进路径：上线初期全审 → 审批通过率稳定后切到风险触发 → 逐步放大预授权范围 + 抽审兜底。**审批通过率是最重要的放权信号**：某类审批连续通过率高于 95%，就该考虑降档。

**审批执行方式**：

| 方式 | 说明 | 延迟 |
|---|---|---|
| 同步审批 | 暂停等待，批完继续 | 高 |
| 异步审批 | 先挂起任务，审批后恢复 | 低 |
| 预审批 | 批量预授权 | 最低 |
| 自动审批 | 规则直接通过 | 无 |

实现层面：自研用「暂停 + 轮询/回调 + 状态持久化」三件套（完整实现见 6.1）；截至 2026 年，主流编排框架已内置等价原语——LangGraph 的 interrupt()/checkpoint 机制即可实现「暂停等人、恢复继续」，对应 2.5 状态机里的 WAITING_HUMAN 状态。

趋势观察：HITL 审批工作流在 2026 年的社区设计资料中已充分沉淀，但专门的面试题库尚未成形，考察频率呈上升趋势。

### 4.5 反馈收集

**反馈信号类型**：

| 类型 | 说明 | 采集成本 | 价值 |
|---|---|---|---|
| 显式反馈（Explicit Feedback） | 点赞/点踩/评分 | 高（用户要动手） | 高 |
| 隐式反馈（Implicit Feedback） | 点击、停留、复制、重写 | 低（自动埋点） | 中 |
| 文本反馈 | 评论、投诉 | 高 | 高（信息量最大） |
| 行为反馈 | 是否采纳、是否人工修改 | 低 | 高（最接近真实满意度） |
| 对比反馈 | A/B 二选一哪个好 | 中 | 高（偏好数据，可直接微调） |

**反馈入口设计**（原则：入口越轻，反馈率越高；带原因选项，反馈才可分类）：

```text
每条回答下方三个按钮：[有帮助] [没帮助] [详细反馈]

点踩后弹出原因单选：
- 答案错误
- 信息不全
- 格式问题
- 语气不当
- 其他（文本框补充）
```

### 4.6 标注与数据回流

**标注流程**：

```text
1. 收集 bad case（点踩 + 低置信度 + 审批拒绝的轨迹）
2. 去重、按失败类型分类
3. 分发给标注员
4. 标注（修正答案、标注错误原因）
5. 质量检查（多人一致性）
6. 加入评估集或训练集
```

**标注类型**：

| 类型 | 说明 | 去向 |
|---|---|---|
| 修正标注 | 修正错误答案 | 评估集 |
| 原因标注 | 标注错误类型（检索/生成/工具/规划） | 分析归因 |
| 偏好标注 | A/B 哪个好 | 微调 |
| 相关性标注 | 文档是否相关 | RAG 评估（见 1.4） |

两条回流纪律：第一，标注结果必须回流到 3.5 的评估集——每个被修复的 bad case 都应变成一条回归用例，防止同类问题在后续改版中复发。第二，标注与评审分工（截至 2026 年的常见做法）：LLM-as-judge 跑全量初筛（分钟级千条），人工只抽检校准 judge 与人评的一致性——机器管覆盖、人管校准（见 3.5）。

### 4.7 主动学习

主动学习（Active Learning）的核心思想：标注预算有限时，优先标注模型最不确定的样本。

```python
class ActiveLearner:
    def __init__(self, model, pool, budget: int = 100):
        self.model = model
        self.pool = pool
        self.budget = budget

    def select_samples(self) -> list:
        # 1. 计算不确定性
        scored = []
        for sample in self.pool:
            confidence = self.model.predict_confidence(sample)
            scored.append((sample, confidence))

        # 2. 选置信度最低的
        scored.sort(key=lambda x: x[1])
        return [s for s, _ in scored[:self.budget]]
```

**不确定性来源**：模型置信度低、多次采样结果不一致、检索相似度低、用户反馈负面。四类信号都可作为「值得花人工」的选样依据。

### 4.8 持续学习循环

六个阶段构成闭环，每转一圈，系统变好一点：

```text
生产运行 ─→ 数据收集 ─→ 分析 ─→ 改进 ─→ 验证 ─→ 回到生产
（交互反馈） （bad case  （分类归因 （Prompt/  （评估集回归、
             低置信样本） 优先级）   知识/微调） 灰度发布）
```

各阶段职责：

- 生产运行：正常服务用户，顺带产生 Trace、反馈、异常记录（见 3.4）。
- 数据收集：bad case、低置信度样本、用户反馈、异常轨迹入池。
- 分析：失败分类（检索/生成/工具/规划）、逐步归因、优先级排序。
- 改进：按优先级选择 Prompt 优化、知识库更新、工具修复、微调。
- 验证：先加入评估集跑回归（见 3.5），再灰度发布（见 3.9）。
- 回到生产：闭环转动，进入下一轮。

**面试高频问法**：「用户反馈和人工标注怎么流回训练/评估集，让系统越用越好？」共识口径：反馈先结构化（类型 + 原因 + 关联 Trace），低置信与负反馈样本经主动学习筛选后进入标注队列；标注结果分两路回流——修正答案进评估集做回归门禁，偏好对进训练集做微调；每轮改进必须过评估集回归再灰度，否则「改进」无法证明。

### 4.9 人机协同的评估

| 指标 | 说明 |
|---|---|
| 人工介入率 | 需要人工的比例（越低自动化越充分） |
| 审批通过率 | 审批通过比例（放权信号） |
| 审批延迟 | 从请求到决策的时间 |
| 反馈率 | 用户反馈比例 |
| 反馈采纳率 | 反馈被处理的比例 |
| 改进周期 | 从反馈到改进上线的时间 |
| 自动化率 | 无需人工完成的比例 |
| 人机一致性 | 人与 Agent 判断一致的比例（可反推哪些审批能放权） |

### 4.10 最佳实践

1. **按风险分级**：低风险全自动，中风险自动 + 审计，高风险人审，极高风险人决策。
2. **人在关键节点**：不要每一步都让人参与，只在关键节点介入。
3. **反馈要闭环**：用户反馈必须有人处理，否则用户不再反馈。
4. **数据要回流**：每个 bad case 都要变成改进的输入。
5. **自动化优先**：能用规则自动处理的不要人工；审批通过率稳定后主动放权。
6. **透明**：用户知道什么时候是 AI、什么时候是人。

## 5. 架构 / 流程

一个完整的人机协同与反馈闭环系统：

```text
┌────────────────────────────────────────────────┐
│ 生产运行                                         │
│  Agent 执行 ─风险路由─┬─ 低风险 → 自动执行        │
│                      ├─ 中风险 → 自动+事后审计   │
│                      └─ 高风险 → 审批门（暂停）  │
│  用户交互：提问 / 反馈（点赞、点踩、评论）        │
└────────────────────────────────────────────────┘
      │ Trace（见 3.4）             │ 反馈信号
      ↓                             ↓
┌────────────────────────────────────────────────┐
│ 数据管道                                         │
│  Trace 收集 / 反馈收集 / Bad case 识别           │
│  / 低置信样本（主动学习候选池）                  │
└────────────────────────────────────────────────┘
                    ↓
┌────────────────────────────────────────────────┐
│ 分析与标注                                       │
│  失败分类 → 归因 → 优先级 → 人工标注（回流）     │
└────────────────────────────────────────────────┘
                    ↓
┌────────────────────────────────────────────────┐
│ 改进                                             │
│  Prompt 优化 / 知识库更新 / 工具修复 / 微调      │
└────────────────────────────────────────────────┘
                    ↓
┌────────────────────────────────────────────────┐
│ 验证与发布（见 3.5、3.9）                        │
│  评估集回归 → 灰度 → 全量 → 回到生产运行（闭环） │
└────────────────────────────────────────────────┘
```

## 6. 代码 / 工具

### 6.1 审批工作流（审批门 + 超时升级 + 决策留痕）

```python
import asyncio
import time
from enum import Enum
from uuid import uuid4
from datetime import datetime, timezone

def now() -> str:
    return datetime.now(timezone.utc).isoformat()

class ApprovalStatus(Enum):
    PENDING = "pending"
    APPROVED = "approved"
    REJECTED = "rejected"
    TIMEOUT = "timeout"

class ApprovalRejected(Exception):
    pass

class ApprovalTimeout(Exception):
    pass

class ApprovalService:
    def __init__(self, store, notifier):
        self.store = store
        self.notifier = notifier

    async def request_approval(self, task_id: str, action: str,
                               args: dict, user: dict, reason: str) -> dict:
        """审批门：创建请求并通知审批人（留痕从入库开始）"""
        approval_id = str(uuid4())
        await self.store.save("approvals", {
            "id": approval_id,
            "task_id": task_id,
            "action": action,
            "args": args,
            "user_id": user["id"],
            "reason": reason,
            "status": ApprovalStatus.PENDING.value,
            "created_at": now(),
        })
        await self.notifier.send(
            to="admin",
            subject=f"待审批: {action}",
            body=f"任务 {task_id}\n操作: {action}\n参数: {args}\n原因: {reason}",
            approval_id=approval_id,
        )
        return {"approval_id": approval_id, "status": "pending"}

    async def decide(self, approval_id: str, decision: str,
                     approver: str, comment: str = ""):
        """决策留痕：谁、何时、批了什么、依据什么"""
        approval = await self.store.get("approvals", approval_id)
        if approval["status"] != "pending":
            raise ValueError("审批已完成，禁止重复决策")
        await self.store.update("approvals", approval_id, {
            "status": decision,
            "approver": approver,
            "comment": comment,
            "decided_at": now(),
        })

    async def wait(self, approval_id: str, timeout: int = 3600) -> dict:
        """等待决策；超时升级：过半无人处理换通道提醒，再超时默认拒绝"""
        start = time.time()
        reminded = False
        while time.time() - start < timeout:
            approval = await self.store.get("approvals", approval_id)
            if approval["status"] != "pending":
                return approval
            if not reminded and time.time() - start > timeout / 2:
                await self.notifier.send(
                    to="admin_backup", subject="审批超时升级",
                    approval_id=approval_id,
                )
                reminded = True
            await asyncio.sleep(5)
        await self.store.update("approvals", approval_id, {
            "status": ApprovalStatus.TIMEOUT.value,
        })
        return {"status": "timeout"}

approval_service = ApprovalService(store, notifier)

# 使用：高风险操作先过审批门
async def execute_with_approval(task_id: str, action: str,
                                args: dict, user: dict):
    req = await approval_service.request_approval(
        task_id=task_id, action=action, args=args, user=user,
        reason=f"高风险操作: {action}",
    )
    decision = await approval_service.wait(req["approval_id"])
    if decision["status"] == "approved":
        return await execute_tool(action, args)
    if decision["status"] == "rejected":
        raise ApprovalRejected(decision.get("comment"))
    raise ApprovalTimeout()  # 超时默认不执行（fail-safe）
```

### 6.3 Bad Case 分析

```python
from collections import defaultdict

class BadCaseAnalyzer:
    def __init__(self, llm):
        self.llm = llm

    async def analyze(self, bad_case: dict) -> dict:
        trace = bad_case["trace"]
        prompt = f"""分析以下 Agent 执行失败的原因。

用户输入：{trace['input']}
执行轨迹：{json.dumps(trace['steps'], ensure_ascii=False)}
最终输出：{trace['output']}
用户反馈：{bad_case.get('feedback', '无')}

请分析：
1. 失败类型：检索/生成/工具/规划/其他
2. 根因
3. 改进建议
4. 优先级：高/中/低

输出 JSON。
"""
        result = await self.llm.chat(prompt, temperature=0)
        return json.loads(result)

    async def batch_analyze(self, bad_cases: list) -> dict:
        results = []
        for case in bad_cases:
            analysis = await self.analyze(case)
            results.append({**case, "analysis": analysis})

        # 按失败类型统计，决定改进优先级
        by_type = defaultdict(int)
        for r in results:
            by_type[r["analysis"]["failure_type"]] += 1
        return {"total": len(results), "by_type": dict(by_type), "results": results}
```

### 6.4 标注任务管理

```python
class AnnotationManager:
    def __init__(self, store):
        self.store = store

    async def create_task(self, trace: dict, instruction: str) -> str:
        task_id = str(uuid4())
        await self.store.save("annotation_tasks", {
            "id": task_id, "trace": trace, "instruction": instruction,
            "status": "pending", "annotations": [], "created_at": now(),
        })
        return task_id

    async def submit(self, task_id: str, annotator: str, result: dict):
        task = await self.store.get("annotation_tasks", task_id)
        task["annotations"].append({
            "annotator": annotator, "result": result, "timestamp": now(),
        })
        await self.store.update("annotation_tasks", task_id, task)

    async def resolve(self, task_id: str) -> dict:
        """三人标注 + 多数投票，控制标注质量"""
        task = await self.store.get("annotation_tasks", task_id)
        if len(task["annotations"]) < 3:
            return None
        votes = defaultdict(int)
        for ann in task["annotations"]:
            votes[ann["result"]["label"]] += 1
        winner = max(votes, key=votes.get)
        await self.store.update("annotation_tasks", task_id, {
            "status": "resolved", "result": winner,
        })
        return {
            "label": winner,
            "confidence": votes[winner] / len(task["annotations"]),
        }
```

### 6.5 持续学习循环

```python
class ContinuousLearningLoop:
    def __init__(self, feedback_service, analyzer,
                 annotation_manager, eval_store):
        self.feedback = feedback_service
        self.analyzer = analyzer
        self.annotation = annotation_manager
        self.eval_store = eval_store

    async def run_cycle(self, since: str):
        # 1. 收集 bad case
        bad_cases = await self.feedback.get_bad_cases(since)
        print(f"收集到 {len(bad_cases)} 个 bad case")

        # 2. 批量分析
        analysis = await self.analyzer.batch_analyze(bad_cases)
        print(f"分析完成: {analysis['by_type']}")

        # 3. 高优先级进标注队列
        high_priority = [c for c in analysis["results"]
                         if c["analysis"]["priority"] == "高"]
        for case in high_priority:
            await self.annotation.create_task(
                trace=case["trace"],
                instruction="修正答案并标注错误类型",
            )

        # 4. 回流评估集：修复的 bad case 变成回归用例
        for case in high_priority:
            await self.eval_store.add_case({
                "input": case["trace"]["input"],
                "expected": case["analysis"].get("correct_answer"),
                "tags": [case["analysis"]["failure_type"]],
            })

        return {
            "bad_cases": len(bad_cases),
            "high_priority": len(high_priority),
            "by_type": analysis["by_type"],
        }
```

## 7. 案例

### 案例 A：电商退款 Agent 人工审批（风险触发式）

某电商平台的售后 Agent，退款审批策略两个月内完成一次演进：

```text
第 1 个月：所有退款全部人工审批 → 通过率 97%，但审批队列天天积压
第 2 个月：切风险触发——单笔 ≤ 200 元自动退，> 200 元进审批门
第 3 个月：触发审批的量降到 8%，通过率仍 95% 以上
```

**效果**（示意量级）：日均 1200 笔退款请求中约 8% 进入人工审批，平均审批延迟从全审时期的排队半小时降到 6 分钟；误退款率与全审时期持平，人力投入降为原来的十分之一。审批通过率稳定在 95% 以上，成为下一步把自动额度从 200 元放大到 500 元的放权依据。

### 案例 B：反馈驱动 RAG 改进（反馈闭环）

某企业知识库问答 Agent，靠用户点踩驱动 RAG 迭代：

```text
1. 用户点踩某条回答，原因勾选「答案错误」
2. bad case 入队，关联 Trace 还原现场（见 3.4）
3. 分析归因：检索没召回 2026 版新政策文档，旧版本文档占了首位
4. 修复：调切分粒度 + 加重排（Rerank，见 1.4）
5. 该问题加入评估集，回归通过后灰度发布（见 3.9）
```

**效果**（示意量级）：上线前四周点踩率 5.2%，归因中「检索失败」占六成；迭代两个月后点踩率降到 1.8%，首批沉淀的 80 个 bad case 全部进入回归集，同类问题复现归零。

### 案例 C：主动学习降低标注成本

**问题**：标注预算只够标 500 条，未标注样本池有 10000 条，怎么选？

**方案**：

```text
1. 用当前模型对 10000 条样本预测置信度
2. 选置信度最低的 500 条（最不确定 = 最有标注价值）
3. 人工标注这 500 条
4. 标注结果加入训练/评估集，重新评估
```

**效果**（示意量级）：标注量减少 95%（10000 → 500），在低置信样本上的准确率提升与随机标注 5000 条相当——同样预算花在模型最没把握的地方，收益最大。

## 8. 常见坑

1. **全自动，无人工介入**。高风险操作出错不可逆。按风险分级，高危动作必须过审批门。

2. **人工介入太多**。效率低、用户等待，审批人疲劳后开始无脑点通过。只在关键节点介入，用通过率数据主动放权。

3. **反馈无闭环**。用户点踩没人处理，两周后没人再反馈。给反馈队列设处理时限，每条负面反馈必须有处理记录。

4. **反馈不分类**。所有反馈混在一起，无法归因。入口就带原因选项（答案错误/信息不全/语气不当）。

5. **不做 Bad Case 回流**。同样的错误反复出现，修过还会复发。每个修复的 bad case 都进评估集做回归用例。

6. **标注质量无控制**。标注员水平参差，脏标注污染训练集。三人标注 + 多数投票 + 一致性抽检。

7. **不做主动学习**。随机标注，预算花在模型已经会的样本上。优先标注低置信度样本。

8. **审批延迟高**。用户等 1 小时，体验崩塌。异步审批 + 分级额度 + 超时升级换通道。

9. **审批无审计**。谁批的、什么时候批的，无法追溯。决策留痕从请求入库那一刻开始（见 3.8 合规）。

10. **超时无默认策略**。审批人失联，任务永久挂起。超时升级 + 默认拒绝（fail-safe），绝不默认放行。

11. **人机职责不清**。人和 Agent 互相推诿，出错互相甩锅。写清边界：Agent 建议、人决策、系统记录。

12. **用户不知道对面是 AI**。信任与合规双重问题。透明告知，审批等待时说明在等人处理。

13. **反馈收集太少**。只有 1% 用户反馈，样本严重偏差。主动询问 + 简化入口 + 补隐式反馈。

14. **不做改进验证**。改了不知道是否变好，甚至改坏。改进必须过评估集回归再上线（见 3.5）。

15. **改进周期太长**。反馈到修复要 1 个月，用户早就流失。按周跑闭环（6.5 的 run_cycle），优先修高频问题。

16. **忽略隐式反馈**。只看点赞点踩，忽略复制、重写、放弃等行为数据。显式 + 隐式两条腿走路。

## 9. 练习

1. 实现 6.1 的审批工作流，跑通「请求 → 通知 → 通过/拒绝 → 恢复执行」全流程。验收：拒绝路径不执行工具。
2. 给审批加超时升级：过半换通道提醒，超时默认拒绝。验收：无人审批时任务在超时后安全终止。
3. 实现 6.2 的反馈收集：点赞、点踩（带原因单选）、文本反馈三类入口。验收：每条反馈都能关联到 trace_id。
4. 实现 bad case 自动收集与 6.3 的批量分析，按失败类型（检索/生成/工具/规划）输出统计。验收：对 20 条构造样本分类正确率不低于 80%。
5. 实现 6.4 标注任务管理：创建、提交、三人多数投票裁定。验收：两人一致时能出结果，三人各不相同时报错转人工裁定。
6. 实现 4.7 的主动学习选样：对样本池按置信度排序取最低 N 条。验收：与随机选 N 条对比，标注后评估提升更明显。
7. 串联 6.5 持续学习循环：收集 → 分析 → 标注 → 回流评估集。验收：一个 bad case 修复后能在回归中挡住同类改版。
8. 实现 4.3 的升级触发：置信度、风险工具、金额阈值、连续失败、用户要求五条件。验收：每个条件单独触发都能挂起任务。
9. 设计人机协同 Dashboard（参考 6.6），覆盖审批、反馈、回流、标注四组指标。验收：能从看板直接回答「本周自动化率是多少」。

## 10. 小结

- 人机协同模式：**HITL（人在环内）、HOTL（人在环上）、全自动、按风险分级的混合模式**。
- 介入点选型：**行动前审批、行动中确认、结果后审核、持续反馈**，按风险 × 成本 × 延迟权衡——错误损失越大、越不可逆，介入越早。
- 升级触发：**置信度低、高风险工具、金额超限、连续失败、用户要求**。
- HITL 审批工作流三构件：**审批门、超时升级、决策留痕**；策略从全审演进到风险触发、抽审、预授权，审批通过率是放权信号。
- 反馈收集：**显式、隐式、文本、行为、对比**五类信号，入口越轻反馈率越高。
- 标注与回流：**修正、原因、偏好、相关性**四类标注，结果必须回流评估集做回归用例。
- 主动学习：**优先标注最不确定的样本**，同等预算收益最大。
- 持续学习循环：**生产 → 收集 → 分析 → 改进 → 验证 → 再上线**，改进必须过评估集回归。
- 关键指标：**介入率、审批通过率、审批延迟、反馈率、改进周期、自动化率**。
- 核心原则：**按风险分级、反馈要闭环、数据要回流、自动化优先、对用户透明**。
- 这些能力直接支撑：4.5 工作流自动化 Agent、4.7 生产级 Agent 平台。
