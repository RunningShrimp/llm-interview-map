# 讲解 4.7 生产级 Agent 平台

> 说明：3.1-3.10 补齐了单系统的工程能力（接口、数据、编排、可观测、评估、部署、成本、安全、发布、人机协同），4.1-4.6 又把它们逐个用到六类 Agent 上。  
> 4.7 做实战层的收束：把这些能力**平台化**——多租户（Multi-tenancy）、工具市场、统一网关、监控、计费、权限治理。核心问题不再是「怎么再做一个 Agent」，而是：**怎么让 10 个团队、100 个 Agent、1000 个工具在一个平台上安全、高效、可治理地运行？**（后续 4.9 讲平台的部署运维，4.10 讲沉淀进作品集）

---

## 1. 定位

实战层第 7 个知识点，属于「平台化与治理」，是 3 层全部工程能力的收束点。  
它解决一个核心问题：**如何把零散的 Agent 能力整合成可复用、可治理、可扩展的生产级平台，支撑多团队、多租户、多场景？**——即「如何平台化复用与治理」，答案三句：

- **复用靠抽象**：把工具、RAG、记忆、评估做成平台能力，业务团队只写业务逻辑；工具一次开发、全平台复用（工具市场是复用的载体）。
- **治理靠集中**：权限、审计、配额、预算收口到平台层，业务想绕也绕不过去。
- **节奏靠演进**：按团队数与项目数分阶段，从项目制到共享库再到平台，不一步到位。

**与 3.x 的划界**：单系统的可观测归 3.4、评估归 3.5、部署与扩展归 3.6、成本归 3.7、安全归 3.8、发布归 3.9。本篇不重复这些机制本身，讲的是把它们**聚合成一个多租户平台**时的分层、隔离与治理。

前置：3 层全部（3.1-3.10）。后续：4.9 部署与运维、4.10 作品集与复盘；4.8 评估与红队与平台的评估聚合能力互为配合。

## 2. 一句话定义

生产级 Agent 平台，是把 Agent 运行时、工具市场、知识管理、评估体系、权限治理、监控计费、多租户隔离等能力平台化，让业务团队能自助创建、部署、运营 Agent 的基础设施（Infrastructure）。

简化公式：

```text
Agent 平台 = 运行时 + 工具市场 + 知识管理 + 评估 + 治理 + 计费 + 多租户
```

## 3. 为什么需要

**面试高频问法**：「公司里多个团队都要做 Agent，你作为平台团队怎么支撑？」共识口径不是替每个团队写 Agent，而是提供运行时、工具市场、治理三条底座让业务自助；衡量指标是「一个新团队从接入到第一个 Agent 上线的天数」和「工具复用率」。这正引出项目制与平台制的差别：

| 维度 | 项目制 | 平台制 |
|---|---|---|
| 开发效率 | 每个项目从头搭 | 复用平台能力 |
| 一致性 | 各自为政 | 统一标准 |
| 治理 | 难 | 集中治理 |
| 成本 | 重复建设 | 规模效应 |
| 安全 | 参差不齐 | 统一安全 |
| 可观测 | 各自埋点 | 统一监控 |
| 迭代 | 慢 | 快 |

**没有平台会怎样**：

- **重复建设** → 每个团队从头实现工具调用、记忆、RAG。
- **工具孤岛** → A 团队写的搜索工具 B 团队用不了，接口、鉴权各不相同。
- **安全参差** → 权限、审计各自实现，水平取决于恰好谁在写。
- **成本黑洞** → 花费无法归因到团队、Agent、工具，优化无从下手。
- **版本混乱** → 模型、Prompt、工具版本各自为政，无法统一升级与回滚。
- **评估割裂** → 每个项目一套口径，Agent 之间无法横向对比。
- **隔离靠自觉** → 多租户隔离散落在各业务代码里，一处遗漏就是数据泄露。

**类比 1（供电）**：

```text
项目制 = 每个部门自己买发电机：功率、电价、维护各管各的
平台制 = 建一座电厂 + 一张电网：统一供电、统一计费、统一检修
```

**类比 2（打印店）**：没有工具市场 = 每间办公室自己买打印机、自己修、自己谈耗材；有工具市场 = 楼里一间文印室——统一采购、统一维护、按张计费、刷卡授权。

## 4. 核心原理

### 4.1 平台的分层架构

```text
┌──────────────────────────────────────────┐
│  用户层                                   │
│  Web Console / API / SDK / CLI            │
├──────────────────────────────────────────┤
│  应用层                                   │
│  Agent Builder / 工作流编排 / 调试台      │
├──────────────────────────────────────────┤
│  能力层                                   │
│  Agent Runtime / RAG / Memory / Tools     │
├──────────────────────────────────────────┤
│  治理层                                   │
│  权限 / 审计 / 配额 / 计费 / 合规         │
├──────────────────────────────────────────┤
│  基础设施层                               │
│  LLM Gateway / Vector DB / Queue / Cache  │
├──────────────────────────────────────────┤
│  可观测层                                 │
│  Trace / Metrics / Logs / Eval            │
└──────────────────────────────────────────┘
```

每层「聚合什么」与对应前置（划界：机制本身在前置篇讲透，本篇只讲聚合）：

| 层 | 平台要做的聚合 | 机制详见 |
|---|---|---|
| 应用层 | Agent Builder、编排、调试台对多租户开放 | 3.3 编排框架与运行时 |
| 能力层 | 运行时、RAG、记忆、工具统一供给 | 1.4 RAG、2.3 工具使用 |
| 治理层 | 权限、审计、配额、计费、合规集中收口 | 3.8 安全、合规与权限 |
| 基础设施层 | 网关、向量库、队列、缓存、密钥、沙箱池 | 3.6 部署与扩展、3.7 成本 |
| 可观测层 | 全平台 Trace / Metrics / Logs / Eval 汇聚 | 3.4 可观测、3.5 评估 |

一条基础设施补充：**沙箱池**。数据分析、代码类 Agent 需要隔离执行环境（沙箱机制见 4.3「数据分析 Agent」一篇），平台把「按需创建、用完即毁」的沙箱池（如 Firecracker microVM，冷启动百毫秒级；E2B 官方文档 2026）做成基础设施能力——截至 2026 年属趋势观察，尚无常设面试真题（推断）。

### 4.2 多租户架构

**租户（Tenant）隔离级别对比**：

| 级别 | 说明 | 隔离度 | 成本 | 适用场景 |
|---|---|---|---|---|
| 共享一切 | 共享库、共享表、共享向量库 | 低 | 低 | 内部互信团队、原型期 |
| 共享基础设施 + 逻辑隔离 | 所有查询强制 tenant_id 过滤 | 中 | 中 | 内部平台主流选择 |
| 共享集群 + 独立命名空间 | K8s namespace / 独立 schema | 高 | 中高 | 重点客户、较强合规要求 |
| 独立部署 | 每租户一套完整栈 | 最高 | 高 | 金融、医疗等强合规大客户 |

选择逻辑：从上往下成本跳升，默认逻辑隔离，个别租户按合规与付费能力升级。注意逻辑隔离必须配租户级限流，否则一个租户的突发流量会拖垮所有租户（噪声邻居问题）。

**机制推导：一次请求的租户传播链路**。隔离不是「记得带 tenant_id」，而是让「不带」变得不可能：

```text
请求带 JWT（含 tenant_id）→ 网关验签识别租户 → 中间件写入请求上下文（contextvars）
  → 数据层强制注入过滤（业务代码删不掉）→ 审计日志带 tenant_id 落盘
任何一环缺失 = 隔离失效
```

**实现要点**：

```python
class TenantContext:
    def __init__(self, tenant_id: str, user_id: str, roles: list):
        self.tenant_id = tenant_id
        self.user_id = user_id
        self.roles = roles

# 所有数据访问强制带 tenant_id
class TenantAwareStore:
    async def query(self, ctx: TenantContext, query: str):
        return await self.db.find({
            "tenant_id": ctx.tenant_id,   # 强制过滤，不接受调用方覆盖
            "query": query,
        })
```

**向量库隔离**（RAG 场景同理，见 1.4、4.2「RAG 知识库 Agent」）：

```python
collection.query(
    query_texts=[query],
    where={"tenant_id": ctx.tenant_id},  # 元数据过滤，检索层隔离
)
```

**面试高频问法**：「在设计企业内部的 AI Agent 时，你如何实现多租户权限控制、数据隔离以及全链路合规审计？」共识口径分三段：隔离上，中间件注入 tenant_id + 数据层强制过滤双保险，不依赖业务自觉；权限上，RBAC（Role-Based Access Control，基于角色的访问控制）定粗粒度、ABAC（Attribute-Based Access Control，基于属性的访问控制）定金额/风险等细粒度；审计上，模型调用、工具调用、数据访问三类事件全量落日志，带租户与用户标识、追加写不可篡改。企业级系统设计真题还会叠加性能约束（如 P95 ≤ 3s）与 ACL 过滤（2026），即隔离不能以明显牺牲延迟为代价。

### 4.3 工具市场

**核心思想**：工具一次开发，全平台复用。

```text
┌──────────────────────────────────────────┐
│  工具市场                                 │
│  ├─ 官方工具（搜索、计算、天气）          │
│  ├─ 企业工具（CRM、工单、审批）           │
│  ├─ 团队工具（业务专用）                  │
│  └─ 第三方工具（MCP Server）              │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  工具注册                                 │
│  ├─ Schema 定义                           │
│  ├─ 权限配置                              │
│  ├─ 限流配置                              │
│  ├─ 版本管理                              │
│  └─ 文档                                  │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  Agent 引用                               │
│  Agent 按需选择工具，平台统一执行          │
└──────────────────────────────────────────┘
```

截至 2026 年，第三方工具接入的主流形态是 MCP（Model Context Protocol，模型上下文协议）Server：平台做一层 MCP 代理，统一鉴权、限流与审计，而不是让每个 Agent 直连外部服务（趋势观察：MCP 生态扩张很快，但企业侧的审计口径尚未完全统一，未核实）。

**上架治理**：市场不是想发就发。上架要走审核（Schema 合法性、权限最小化、风险分级）、灰度（先内部试用再全量）、可下架（出事一键停用），缺一不可，否则市场退化成无治理的代码堆。

**工具定义标准**：

```yaml
# tools/search_web.yaml
name: search_web
version: 1.2.0
description: 搜索网页信息
category: search
author: platform-team
schema:
  type: object
  properties:
    query:
      type: string
      description: 搜索关键词
    top_k:
      type: integer
      default: 5
  required: [query]
permissions:
  roles: [user, admin]
  rate_limit: 100/hour
risk_level: low
endpoint: /v1/tools/search_web   # 平台内部路由，不暴露真实地址
```

### 4.4 统一 LLM Gateway

**职责**：

| 职责 | 实现要点 |
|---|---|
| 模型路由 | 按 tier（快/强）、负载、成本选模型 |
| 限流熔断与重试降级 | 租户级 + 模型级令牌桶；超时换供应商，非关键请求降级到小模型 |
| 成本统计 | 按 tenant / user / agent / model 四维归因 |
| 缓存 | 语义缓存（Semantic Cache）命中直接返回 |
| 密钥管理 | Agent 无密钥，网关掌密钥 |

「对接多家大模型官方 API 时，如何设计统一调用网关屏蔽接口差异」是真实高频面经题（网易 AI 应用开发岗，2026）。共识口径就是上表：适配器统一接口抹平厂商差异，密钥只放网关，路由按档位选模型，失败重试换供应商，成本按租户归因。

```python
class LLMGateway:
    def __init__(self):
        self.providers = {}
        self.router = ModelRouter()
        self.cache = SemanticCache()
        self.cost_tracker = CostTracker()

    async def chat(self, ctx: TenantContext, messages: list, tier: str = "fast") -> dict:
        # 1. 缓存查询
        cached = await self.cache.get(messages)
        if cached:
            return cached

        # 2. 路由
        model = self.router.select(tier, messages)

        # 3. 限流
        if not await self.rate_limit(ctx.tenant_id, model):
            raise RateLimitExceeded()

        # 4. 调用
        response = await self.providers[model].chat(messages)

        # 5. 成本统计（按租户归因）
        cost = self.cost_tracker.record(
            model=model,
            input_tokens=response.usage.prompt_tokens,
            output_tokens=response.usage.completion_tokens,
            tenant_id=ctx.tenant_id,
            user_id=ctx.user_id,
        )

        # 6. 缓存
        await self.cache.set(messages, response)

        return {**response, "cost": cost}
```

### 4.5 权限与治理

**RBAC 与 ABAC 对比**：

| 维度 | RBAC | ABAC |
|---|---|---|
| 思路 | 人 → 角色 → 权限 | 属性条件表达式（租户、金额、风险等级） |
| 表达力 | 弱，但直观好审 | 强，能表达「金额 ≤ 500 免审」 |
| 变更成本 | 组织调整要改角色映射 | 改策略表达式即可 |
| 平台实践 | 定粗粒度（谁能用什么工具） | 定细粒度（什么条件下要审批） |

**实现**：

```python
class PolicyEngine:
    def __init__(self):
        self.policies = load_policies()

    def check(self, ctx: TenantContext, action: str, resource: dict) -> bool:
        for policy in self.policies:
            if policy.matches(action, resource):
                if not policy.allows(ctx):
                    return False
        return True

# 策略示例：RBAC 定角色，ABAC 定条件
policies = [
    {
        "action": "tool:search_orders",
        "roles": ["user", "admin"],
        "condition": "resource.tenant_id == ctx.tenant_id",
    },
    {
        "action": "tool:refund",
        "roles": ["admin"],
        "condition": "resource.amount <= 500",
    },
    {
        "action": "tool:refund",
        "roles": ["admin"],
        "condition": "resource.amount > 500",
        "requires_approval": True,   # 高危动作转人工，见 3.10 人机协同
    },
]
```

治理还有第三根柱子：**审计（Audit）**。模型调用、工具调用、数据访问三类事件全量落日志，每条带 tenant_id、user_id、动作、资源、时间戳与 trace_id，追加写不可篡改——没有审计，权限只是「防君子」。

### 4.6 配额与计费

**配额（Quota）维度**：

| 维度 | 说明 |
|---|---|
| 请求数 | 每日/每月请求上限 |
| Token | 每日/每月 token 上限 |
| 成本 | 每日/每月成本上限 |
| 工具调用 | 每工具调用上限 |
| 并发 | 同时请求数 |
| 存储 | 向量库、日志存储 |

配额要配**预算告警**：用到 80% 告警、100% 熔断，而不是月底才在账单上发现超标（成本治理的完整方法论见 3.7）。

**计费模型**：

```python
class BillingEngine:
    def __init__(self):
        self.pricing = {
            "llm": {"gpt-4o-mini": {"input": 0.15, "output": 0.60}},  # 每百万 token 单价
            "tool": {"search_web": 0.001},
            "storage": {"vector": 0.0001},
        }

    def calculate(self, usage: dict) -> float:
        cost = 0
        cost += usage["llm"]["input_tokens"] * self.pricing["llm"][usage["llm"]["model"]]["input"] / 1_000_000
        cost += usage["llm"]["output_tokens"] * self.pricing["llm"][usage["llm"]["model"]]["output"] / 1_000_000
        for tool, count in usage.get("tools", {}).items():
            cost += count * self.pricing["tool"].get(tool, 0)
        return cost
```

计费的意义不只是收钱（内部平台是「记账不收款」）：**成本归因到部门，是推动优化的前提**——看不到哪个 Agent 烧钱，就没人有动力换小模型、加缓存。

### 4.7 版本与发布

**平台级版本管理**：

```text
Agent 版本：
├─ 模型版本
├─ Prompt 版本
├─ 工具版本
├─ 知识库版本
└─ 配置版本

平台支持：
├─ 灰度发布（Canary Release）
├─ A/B 测试
├─ 一键回滚
└─ 版本对比
```

一次 Agent 发布 = 五类制品版本的整体快照。单系统的 CI/CD 与发布机制见 3.9；平台要做的是把「任意两个版本可对比、可回滚」变成对所有租户一致的默认能力。

### 4.8 可观测与评估

**统一 Trace**：

```text
所有 Agent 的 trace 汇聚到平台
→ 统一查询
→ 统一告警
→ 统一评估
→ Bad Case 回流
```

单系统怎么埋 Trace 见 3.4、评估体系见 3.5；平台做的是跨租户、跨 Agent 的聚合。一个业界参照：89% 的组织有可观测，但只有 52% 在跑离线评估（LangChain《Agent Evals》白皮书，2026）——差距正是平台要填的：把评估从自觉动作变成默认动作。

**平台级评估**：

```python
class PlatformEval:
    async def evaluate_agent(self, agent_id: str, dataset_id: str) -> dict:
        agent = await self.registry.get_agent(agent_id)
        dataset = await self.eval_store.get_dataset(dataset_id)
        return await evaluate(agent, dataset)

    async def compare_agents(self, agent_a: str, agent_b: str, dataset_id: str) -> dict:
        result_a = await self.evaluate_agent(agent_a, dataset_id)
        result_b = await self.evaluate_agent(agent_b, dataset_id)
        return compare(result_a, result_b)
```

### 4.9 开发者体验

**自助式 Agent 创建**：

```text
1. 选择模板（RAG / 工具 / 工作流 / 多 Agent）
2. 配置 Prompt
3. 选择工具（从工具市场）
4. 选择知识库
5. 配置权限
6. 测试
7. 发布
```

**调试台**：

- 实时查看 trace
- 单步调试
- Prompt 版本对比
- 工具调用模拟
- 评估集运行

开发者体验（Developer Experience）是平台的「产品力」：治理再严，如果创建一个 Agent 要走两周流程，业务就会绕开平台自己搭——治理被架空。

### 4.10 平台演进路线

演进节奏由团队规模与项目数决定，五个阶段：

| 阶段 | 特征 | 触发升级的信号 | 典型动作 |
|---|---|---|---|
| 1 项目制 | 每个项目独立搭 | 第 2-3 个重复轮子出现 | 直接开干，最快交付 |
| 2 共享库 | 提取 LLM Client、工具注册等公共组件 | 接入成本高、版本漂移 | 内部包 + 模板工程 |
| 3 平台化 | 统一运行时、工具市场、自助创建 | 团队数大于 5、Agent 数大于 20 | 建运行时与市场，治理先行 |
| 4 生态化 | 第三方工具、MCP 市场、跨团队协作 | 外部伙伴要求接入 | 开放协议、上架审核 |
| 5 自治化 | 自助创建、自动优化、自动治理 | 规模大到人工治理跟不上 | 策略自动生成、异常自愈（趋势观察） |

**工程建议**：

> **从项目制开始，遇到重复建设再平台化。**  
> 不要一开始就建大平台，容易过度设计。

### 4.11 自建、采购与开源

| 维度 | 自建 | 采购商用平台 | 开源框架自托管 |
|---|---|---|---|
| 初期成本 | 高（人月计） | 低（订阅费） | 中 |
| 长期成本 | 取决于团队能力 | 按量计费，规模大后变贵 | 中（要养运维） |
| 定制自由度 | 最高 | 低 | 高 |
| 多租户/治理成熟度 | 自己踩坑 | 开箱即用 | 看项目成熟度 |
| 锁定风险 | 无 | 高 | 低 |
| 适用 | 平台是核心竞争力 | 快速验证、非核心场景 | 大多数企业的中间态 |

共识口径：先用开源或采购验证需求，但治理与数据层的抽象始终留在自己手里，避免深度锁定（呼应第 8 节坑 7）。截至 2026 年商用与开源 Agent 平台都在快速迭代，选型结论按季度复核（趋势观察）。

### 6.2 统一运行时

```python
class AgentRuntime:
    def __init__(self, gateway, tools, rag, memory, policy, billing, tracer):
        self.gateway = gateway
        self.tools = tools
        self.rag = rag
        self.memory = memory
        self.policy = policy
        self.billing = billing
        self.tracer = tracer

    async def run(self, ctx: TenantContext, agent_id: str, input: str) -> dict:
        # 1. 加载 Agent 定义
        agent_def = await registry.get(agent_id)

        # 2. 权限检查（治理前置）
        if not self.policy.check(ctx, "run_agent", {"agent_id": agent_id}):
            raise PermissionError("无权限")

        # 3. 配额检查
        if not await self.billing.check_quota(ctx):
            raise QuotaExceeded()

        # 4. 创建 trace
        with self.tracer.start_trace(agent_id, ctx) as trace:
            # 5. 执行 Agent
            agent = build_agent(agent_def, self.gateway, self.tools, self.rag, self.memory)
            result = await agent.run(input, ctx)

            # 6. 记录成本
            await self.billing.record(ctx, result["usage"])

            # 7. 记录 trace
            trace.end(result)

        return result
```

```python
class ToolMarket:

            "published_at": now(),

        })
        return tool_id

    async def search(self, query: str, category: str = None) -> list:
        filters = {"status": "published"}
        if category:
            filters["category"] = category
        return await self.store.find("tools", filters)

    async def get(self, tool_id: str) -> dict:

    async def subscribe(self, tenant_id: str, tool_id: str):
        # 订阅制：租户能用哪些工具是显式授权的，不是默认全开
        await self.store.save("subscriptions", f"{tenant_id}:{tool_id}", {

            "subscribed_at": now(),
        })
```

### 6.4 多租户中间件与数据访问

先看中间件——隔离的「第一道锁」放在请求入口，而不是散在业务代码里：

```python
import contextvars

# 请求级租户上下文：全平台任何一层都能取到，业务代码无法伪造
_tenant_ctx: contextvars.ContextVar = contextvars.ContextVar("tenant_ctx", default=None)

def get_tenant_context() -> "TenantContext":
    ctx = _tenant_ctx.get()
    if ctx is None:
        raise RuntimeError("缺少租户上下文：请求未经过多租户中间件")
    return ctx

class TenantMiddleware:
    """多租户中间件：验 JWT -> 解出租户 -> 注入请求上下文。

    放中间件层而非业务代码：业务想绕也绕不过（下游都依赖
    get_tenant_context），且一处实现全平台生效、新服务零成本接入。
    """

    def __init__(self, app, jwt_verifier):
        self.app = app
        self.jwt_verifier = jwt_verifier

    async def __call__(self, scope, receive, send):
        if scope["type"] != "http":
            return await self.app(scope, receive, send)

        headers = dict(scope["headers"])
        token = headers.get(b"authorization", b"").decode().removeprefix("Bearer ")
        claims = await self.jwt_verifier.verify(token)  # 验签失败抛 401

        _tenant_ctx.set(TenantContext(
            tenant_id=claims["tenant_id"],
            user_id=claims["sub"],
            roles=claims.get("roles", []),
            quotas=claims.get("quotas", {}),
        ))
        return await self.app(scope, receive, send)
```

数据访问——与中间件配套的「第二道锁」（两道锁缺一不可：中间件保证上下文存在且可信，仓储层保证有上下文也必须过滤）：

```python
class TenantAwareRepository:
    def __init__(self, db):
        self.db = db

    async def find(self, ctx: TenantContext, collection: str, query: dict) -> list:
        # 强制注入 tenant_id，不接受调用方传入的同名键
        query["tenant_id"] = ctx.tenant_id
        return await self.db.find(collection, query)

    async def insert(self, ctx: TenantContext, collection: str, doc: dict):
        doc["tenant_id"] = ctx.tenant_id
        doc["created_by"] = ctx.user_id
        return await self.db.insert(collection, doc)

    async def update(self, ctx: TenantContext, collection: str, doc_id: str, updates: dict):
        # 只能更新自己租户的数据
        doc = await self.db.get(collection, doc_id)
        if doc["tenant_id"] != ctx.tenant_id:
            raise PermissionError("不能跨租户更新")
        return await self.db.update(collection, doc_id, updates)
```

### 6.5 计费与配额骨架

```python
class QuotaManager:
    """配额骨架：Redis 计数器，按 租户×资源×天 维度累加。"""
    def __init__(self, redis):
        self.redis = redis

    async def check(self, ctx: TenantContext, resource: str, amount: int = 1) -> bool:
        quota = ctx.quotas.get(resource, {}).get("daily", float("inf"))
        key = f"quota:{ctx.tenant_id}:{resource}:{today()}"
        used = int(await self.redis.get(key) or 0)
        return used + amount <= quota

    async def consume(self, ctx: TenantContext, resource: str, amount: int = 1):
        key = f"quota:{ctx.tenant_id}:{resource}:{today()}"
        await self.redis.incrby(key, amount)
        await self.redis.expire(key, 86400 * 2)  # 两天过期，跨天后自然重置

class BillingEngine:
    def __init__(self, store):
        self.store = store

    async def record(self, ctx: TenantContext, usage: dict) -> float:
        cost = self.calculate(usage)  # 定价计算见本篇 4.6 小节
        await self.store.insert("billing", {
            "tenant_id": ctx.tenant_id,
            "user_id": ctx.user_id,
            "usage": usage,
            "cost": cost,
            "timestamp": now(),
        })
        return cost

    async def report(self, ctx: TenantContext, period: str) -> dict:
        records = await self.store.find("billing", {
            "tenant_id": ctx.tenant_id,
            "timestamp": {"$gte": period_start(period)},
        })
        return {
            "total_cost": sum(r["cost"] for r in records),
            "by_model": group_by(records, "usage.llm.model"),
            "by_tool": group_by(records, "usage.tools"),
            "by_user": group_by(records, "user_id"),
        }
```

工程细节：`check` 与 `consume` 之间有并发窗口，严格场景用 Lua 脚本把「读 + 判 + 加」做成原子操作；记账失败不能阻断业务（先本地落盘，异步补偿入库）。

## 7. 案例

### 案例 A：企业内部 Agent 平台

**场景**：某电商公司，10 个部门、50 个 Agent、200 个工具，此前各部门独立建设。

**做法**：

```text
统一网关 → Agent Runtime → 工具市场 → LLM Gateway
            ↓
        治理层（权限/配额/计费/审计）
            ↓
        可观测（Trace/Metrics/Eval）
```

分两期落地：一期只上运行时 + LLM Gateway（先解决密钥散落与重复接入），二期再上治理层（权限、配额、计费）。

**效果**（示意性数字，复盘口径）：

- 新 Agent 创建从 2 周缩短到 2 天（模板 + 工具市场贡献最大）。
- 工具复用率约 80%：200 个工具里约 160 个被两个以上团队使用。
- 成本归因到部门后，砍掉重复的高价模型调用，月度总成本降约 40%。
- 全量工具调用有审计记录，一次通过内部安全审计。

### 案例 B：SaaS 多租户 Agent 平台

**场景**：一家做客服 Agent 的 SaaS 公司，100 家企业客户，各自独立配置 Agent。

**关键设计**：

1. 租户隔离：默认逻辑隔离（所有数据强制 tenant_id）；3 家金融客户付费升级到独立部署。
2. 配额：每租户独立配额（请求、token、并发三维），80% 告警、100% 熔断。
3. 计费：按 token + 工具调用计费，月度账单按维度出报表。
4. 工具市场：平台提供基础工具，租户可上传自有工具（走同一套审核）。
5. 审计：每租户独立审计视图，客户可自查自己租户的全部调用记录。

**效果**（示意性数字）：上线一年支撑 100 租户、零跨租户数据泄露；三次「忘带 tenant_id」的代码缺陷都被中间件与仓储层的强制过滤拦下，未出事故；头部租户检索 P95 稳定在 3 秒以内（对标企业级检索平台的通行口径）。

### 案例 C：从项目制到平台制

**场景**：一家金融科技公司内部 Agent 能力的演进复盘（约一年半，示意）。

- **阶段 1（第 1-3 月）**：三个团队各写各的 Agent，重复建设严重，第二个 RAG 轮子出现时触发演进。
- **阶段 2（第 4-6 月）**：提取公共库（LLM Client、Tool Registry），以内部包形式共享。
- **阶段 3（第 7-12 月）**：建统一运行时和工具市场，新团队接入从两周降到两天。
- **阶段 4（第 13-16 月）**：加治理层（权限、配额、计费），通过合规审查。
- **阶段 5（第 17 月起）**：开放自助创建，平台团队从「替业务写」转为「保平台稳」。

**教训**：按需演进，不要一步到位。同期另一个团队在第 2 个月就想建「全公司统一平台」，三个月只输出了规划文档与半成品门户——被业务需求追着建的平台活了下来，凭空规划的平台没有（示意性复盘）。

## 8. 常见坑

1. **一开始就建大平台**。  
   过度设计，业务还没验证先养一支平台团队。从项目制开始，出现第二个重复轮子再抽象。

2. **多租户隔离不彻底**。  
   隔离散在业务代码里，一处遗漏就泄露。中间件注入 + 数据层强制过滤双保险。

3. **工具市场无治理**。  
   恶意或劣质工具上架，全平台暴露。审核 + 白名单 + 版本管理 + 可一键下架。

4. **无配额**。  
   一个租户突发流量刷爆平台，殃及所有租户。配额 + 租户级限流，80% 告警 100% 熔断。

5. **无计费**。  
   成本无法归因，优化无从下手。按租户、Agent、模型、工具多维度记账。

6. **无审计**。  
   出了事查不到谁干的，合规过不了。模型调用、工具调用、数据访问三类事件全量审计。

7. **平台锁定**。  
   业务与平台深度耦合，想迁迁移不动。核心抽象留接口层，业务代码不直接摸平台内部。

8. **开发者体验差**。  
   创建一个 Agent 要两周流程，业务绕开平台自己搭，治理被架空。自助式 + 模板 + 调试台。

9. **无版本管理**。  
   Agent、工具、Prompt 版本混乱，升级即事故。版本是五类制品的整体快照，统一管理。

10. **无评估**。  
    不知道 Agent 好不好，全凭感觉上线。平台级评估 + A/B 对比做成默认动作。

11. **无灰度**。  
    新版本直接全量，出问题波及所有租户。灰度发布 + 一键回滚。

12. **无监控**。  
    平台挂了半小时才知道。统一 Trace + Metrics + 分级告警。

13. **平台团队闭门造车**。  
    做出来的能力没人用，自己做自己的。和业务团队共建，用「接入天数」「复用率」考核平台。

14. **忽略平台自身成本**。  
    平台本身烧钱，规模越大亏得越多。网关缓存、批处理、小模型路由都是平台侧优化点。

15. **不做安全**。  
    平台集中了所有密钥与数据，是最高价值攻击目标。密钥集中管理、最小权限、沙箱隔离。

## 9. 练习

1. 画出一个多租户 Agent 平台的分层架构图（六层），每层标出一个治理点。验收：能对着图讲清一次请求依次穿过哪些层、在哪层可能被拒绝。
2. 实现 TenantContext 与 TenantAwareRepository。验收：构造两个租户的数据互查不到；漏传上下文时直接抛错而非静默返回空。
3. 实现多租户中间件：从 JWT 解出租户，写入 contextvars。验收：把业务代码里所有手工传 tenant_id 的参数删掉，隔离仍然成立。
4. 实现工具市场：发布、搜索、订阅、下架。验收：同一工具的两个版本并存，Agent 固定引用旧版本时不受新版本发布影响。
5. 实现 LLM Gateway：路由、缓存、限流、成本统计。验收：同一问题二次请求命中缓存零成本；账单能按租户/用户/模型三个维度聚合。
6. 实现 PolicyEngine（RBAC + ABAC）：金额 ≤ 500 自动放行、> 500 转人工审批。验收：用 6 组「角色 × 金额」用例全部判定正确。
7. 实现 QuotaManager 与 BillingEngine。验收：配额耗尽后请求被拒并返回剩余额度与重置时间；月度账单能按部门出报表。
8. 实现 Agent Registry：注册、版本、灰度发布、回滚。验收：灰度 10% 流量发现错误率上升后，一键回滚到上一版本。
9. 实现平台级评估：同一数据集对比两个 Agent 版本。验收：输出一张含成功率、平均成本、P95 延迟的对比表。
10. 把以上组件拼成一个最小平台，并为每个组件写一条「删掉它会坏什么」。验收：能据此回答面试官对任意组件的追问。

## 10. 小结

- Agent 平台 = **运行时 + 工具市场 + 知识管理 + 评估 + 治理 + 计费 + 多租户**。
- 分层：**用户层、应用层、能力层、治理层、基础设施层、可观测层**；与 3.x 的边界是「单系统能力归 3.x，平台级聚合归本篇」。
- 平台化复用与治理的正面答案：**复用 = 能力抽象 + 工具市场；治理 = 集中权限/审计/预算；演进 = 按团队规模与项目数分阶段**。
- 多租户：**隔离级别按需选择（默认逻辑隔离），tenant_id 强制过滤，中间件 + 数据层双保险**。
- 工具市场：**一次开发、全平台复用；上架审核、版本管理、权限配置、可下架**。
- LLM Gateway：**路由、缓存、限流、熔断、成本统计；Agent 无密钥、网关掌密钥**。
- 治理：**RBAC 定粗粒度 + ABAC 定细粒度，配额 80% 告警 100% 熔断，三类事件全量审计**。
- 评估：**统一 Trace、平台级评估、A/B 对比，把评估从自觉动作变成默认动作**。
- 核心原则：**按需演进，从项目制到平台制；平台是手段，不是目的。**
- 这些能力直接支撑：4.9 部署与运维、4.10 作品集与复盘。
