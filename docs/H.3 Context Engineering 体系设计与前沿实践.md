## 2. 一句话定义

Context Engineering（上下文工程）是取代「提示词工程」的体系化学科：系统性地管理模型每一步看见的全部信息——系统提示、对话历史、工具结果、检索内容、外部记忆——用压缩、记忆外置、子代理隔离、按需取回四种手段，让长任务 Agent 在有限上下文窗口内不迷路。

简化公式：

```text
上下文工程 = 对模型每步全部输入的系统性管理
每步输入   = 系统提示 + 常驻记忆 + 历史摘要 + 最近原文 + 当步工具结果 + 按需检索
全部工作   = 决定每一项放什么、放多少、何时压缩、何时外置、何时隔离、何时取回
```

## 3. 为什么需要

上下文窗口不是内存条，塞满不等于能用。三个硬约束：

1. **稀缺** → 窗口再大也是有限资源，长任务的工具输出、文件内容、报错日志会以指数速度吃掉它。
2. **注意力衰减** → 超长上下文中部信息的利用率显著下降（Lost in the Middle，Liu et al.，2023；TACL 2024 刊出，1.5 已引用其结论）；关键约束淹没在第 4 万 token 与完全不在窗口里，效果差不多。
3. **成本与延迟线性上涨** → 每步都带着全量历史跑一遍前向，token 越积越多，越用越慢、越用越贵。

第 2 条值得展开一层：**标称窗口不等于有效上下文（Effective Context）**。模型卡片上的「支持 20 万 token」说的是装得下，不是用得好。工程共识口径是：检索类「大海捞针」（needle-in-a-haystack）测试接近满分，不代表真实长任务可用——真实任务里没有明确的目标串，信息以需要推理的形式散布在噪音中。真正的瓶颈是**注意力稀释（Attention Dilution）**：窗口里有效指令的占比越低，指令跟随质量越差。一个直观的量化视角是「信噪占比」——当 19 万 token 的历史与工具垃圾里混着 800 token 的真实约束时，模型的实际行为更接近「在噪音里猜指令」。这也是「盲目相信大窗口」成为 8 节头号坑的原因。

把同一条消息放进不同信噪比的窗口，效果差异（示意量级，工程复盘口吻）：

| 场景 | 窗口内容 | 约束的占比 | 表现 |
|---|---|---|---|
| 第 1 步 | 500 token 系统提示 + 300 token 需求 | 约 38% | 指令跟随准确 |
| 第 10 步 | + 2 万 token 历史与工具结果 | 约 1.6% | 偶尔忽略细节约束 |
| 第 40 步 | + 16 万 token 历史与工具结果 | 约 0.5% | 约束形同虚设，动作发散 |
| 第 40 步（治理后） | 常驻层 + 1 万摘要 + 2 万原文 | 约 3%–5% | 回到第 10 步的水准 |

这张表也解释了为什么四模式的收益都能在「占比」上对账：裁剪和隔离砍掉分母（噪音），压缩砍掉分母（历史），常驻层与记忆索引抬高分子（约束常在）。

典型症状（社区与面试反复出现的真题式问题——「编程 Agent 为什么用得越久响应越慢、越干越糊涂」）：

```text
第 1 步：目标清晰，动作利落
第 20 步：开始重复读已经读过的文件
第 35 步：忘了用户最初要什么，开始「自由发挥」
第 50 步：上下文爆满，要么截断报错，要么被平台自动裁剪——
         裁掉的偏偏是第 1 步的需求描述
```

根因一句话：**上下文是稀缺资源，而默认行为（全部历史原样保留）是对它最挥霍的用法。**

**类比 1：上下文工程 = 给模型配一个操作系统级的内存管理员。** 内存条再大，操作系统照样要做分页：内核与常驻进程钉在内存里（系统提示+记忆索引），活跃进程优先分配（最近原文+当步工具结果），不活跃页面换出到磁盘（压缩外置+记忆文件），数据按缺页中断调入而不是开机全量加载（即时取回）。没有页面置换算法的操作系统内存再大也会耗尽——没有上下文管理的 Agent 窗口再大也会腐化。「Engineering」的含义正在于此：分级、换页、回收，每一样都要有明确规则。

| 维度 | Prompt Engineering | Context Engineering |
|---|---|---|
| 管理对象 | 一条指令怎么写 | 模型每一步的全部输入 |
| 范围 | 系统提示、任务描述、少样本示例 | + 历史、工具结果、检索内容、记忆文件 |
| 时间尺度 | 单次调用 | 任务全程（几十上百步）+ 跨会话 |
| 核心技能 | 措辞、结构化、示例选择 | 预算分配、压缩、外置、隔离、按需供给 |
| 失效模式 | 指令歧义、格式错 | 目标漂移、历史膨胀、关键信息被裁剪 |
| 时代定位 | 聊天时代的主技能 | Agent 时代的主战场 |

**关系口径：上下文工程是提示词工程的超集。提示词只管「怎么说」，上下文工程管「每步看见什么」——提示词写得再好，第 50 步时它被挤掉也没用。** 这一句就是 InterviewsVector 那道原题的满分开头：先给超集关系，再给管理对象与时间尺度的差异，最后落到「聊天时代 vs Agent 时代」——概念辨析题答的是层次感。

算一笔成本账（Agent 与聊天机器人的经济学差异）：聊天机器人一次对话 = 一次输入计费；Agent 跑 50 步，每步都携带全量历史重新计费，输入 token 总量是 O(步数 × 历史长度) 的累积——历史线性增长时，总输入成本按平方级上涨。这解释了两个现象：一是「越用越慢、越用越贵」不是错觉而是复利；二是上下文工程的每一项手段（压缩控长、引用代替内容、缓存友好前缀）都直接对应账单曲线的斜率。

边界感也要有：三五步的简单任务不需要这套体系——硬给一个 5 步任务上子代理隔离和记忆外置，纯增加延迟与复杂度。启动信号是三条中任意一条：任务步数会超过 20；单步工具结果可能超万 token；任务需要跨会话延续。满足才上工程，否则提示词工程（0.6、1.2）仍然是性价比最高的工具。

## 4. 核心原理

### 4.1 先盘点输入源：上下文工程的层次差异从哪来

提示词工程只盯着六个输入源中的一个。上下文工程的第一步是把每步输入的全部来源摆上桌，逐源问一句「它怎么失控、拿什么治理」：

| 输入源 | 默认行为 | 失控方式 | 治理原语 |
|---|---|---|---|
| 系统提示 | 常驻 | 层级混乱、频繁改动毁掉缓存前缀 | 分层 + 稳定前缀（4.9） |
| 对话历史 | 原样累积 | 线性膨胀 → 腐化（4.7） | 压缩 Compaction |
| 工具结果 | 原样入窗 | 单步上万 token 的日志噪音 | 裁剪 + 引用化（4.9、6.2） |
| 检索内容 | 一次性预载 | 大部分用不到却全程占预算 | 即时取回 Just-in-time |
| 外部记忆 | 不接，或全量注入 | 要么丢失要么淹没 | 记忆工具 + 按需读回 |
| 任务状态 | 靠历史回忆 | 摘要有损，进度账丢失 | 结构化笔记外置（plan.md） |

这张表是「超集关系」的具体化：提示词工程优化第一行，上下文工程管理全部六行。也是 8 节坑清单的索引——每一条坑都能在「失控方式」列找到原型。

### 4.2 上下文预算：窗口是账本，先做切分再谈手段

把窗口当预算管理，是上下文工程区别于「打补丁」的第一特征。20 万 token 窗口的参考切法（示意量级，实际按任务调）：

| 层 | 内容 | 预算占比 | 稳定性要求 |
|---|---|---|---|
| 常驻层 | 系统提示 + 记忆索引 + 计划文件 | 5% 以内 | 全程字节级稳定（保缓存） |
| 摘要层 | 任务四段摘要 | 5%–10% | 仅压缩时更新 |
| 最近原文 | 最近若干轮消息 | 10%–15% | 滑动更替 |
| 工作区 | 当步工具结果 + 推理空间 | 剩余 70%–80% | 每步更替 |

三条使用纪律：

1. **任何一层越界，先表现为动作质量下降，再表现为截断报错**——所以预算监控要看占用率曲线而不是等报错。
2. **常驻层的稳定本身就是收益**：提示缓存（Prompt Caching）按前缀匹配计费，常驻层字节级稳定意味着每步的大头输入走缓存折扣价（详见 4.7 的缓存机制）。
3. **切法要进评测**：改预算配比必须跑同一批任务对比步骤成功率与目标漂移率，不许凭感觉——配比是超参数，不是审美。

### 4.3 四大模式总览：Anthropic 口径的三原语加一条检索原则

Anthropic 工程体系（官方工程博客 + Cookbook，2026-03 已 API 化）把长任务上下文治理归纳为三个可 API 化的原语，外加一条检索原则：

| 原语 | 解决什么 | 机制 | 代价 |
|---|---|---|---|
| 压缩 Compaction | 窗口临满 | 历史折叠为结构化摘要（目标/已完成/未完成/决策），带干净书桌继续干 | 摘要有损；压缩时机与保留策略要调 |
| 记忆工具外置 | 跨步、跨会话的关键事实 | 重要事实写外部文件（memory tool），按需读回；窗口外持久 | 多一次工具往返；要设计读写时机 |
| 子代理隔离 | 海量中间产物污染主上下文 | 子代理在独立上下文翻完资料山，只向主 Agent 回传报告 | 子代理可能漏细节；要写好任务说明 |
| 即时取回 Just-in-time | 预加载浪费与噪音 | 不预读大文档，只存引用（路径+行号），用到时精确读取 | 需要模型知道「有什么可取」（目录/索引） |

四个模式各自对应一类「丢失」，这是记忆它们的最稳框架：

```text
压缩     → 解决「窗口装不下」：折叠历史，保住任务主干
记忆     → 解决「窗口留不住」：重要事实越过窗口边界存活
隔离     → 解决「窗口不该装」：脏活在别处干，主上下文只收结论
即时取回 → 解决「窗口不用先装满」：按需供给胜过预加载
```

面试答法建议直接用这四行做骨架：先报四个「丢失类型」，再逐个给原语——分类框架比名词罗列高一个层次。

### 4.4 压缩（Compaction）的工程细节

1. **触发时机**：窗口占用阈值（常见 80%–90%）或按步数/时间兜底触发；压缩本身是一次 LLM 调用，要设防抖（最小压缩间隔、最小释放量）。
2. **摘要结构化**：不是「随便总结」，而是固定四段——原始需求（逐字保留约束）、已完成项与关键决策、未完成项、当前焦点与风险。自由摘要几乎必然丢需求。
3. **压缩前外置**：把不能丢的细节（路径、行号、报错原文、用户显式偏好）先写入记忆文件，再压历史——摘要是有损的，文件是无损的。
4. **保留最近原文**：摘要 + 最近若干轮原文一起重建上下文，避免「刚发生的事」也在摘要里失真。
5. **失败信号**：压缩后若模型开始重复已完成动作，说明摘要丢了进度账——检查四段结构是否覆盖「已完成项」。

两个反模式（面试说得出即加分）：

1. **高频小压缩**：每几步就压一次，摘要叠摘要，失真复利累积，最后模型对着「摘要的摘要的摘要」干活。对策：设最小压缩间隔与最小释放量（一次至少释放 30% 占用才值得压）。
2. **裁剪式治理**：不压摘要，直接按条数丢最旧消息——最旧的位置恰恰是原始需求所在，等于系统性删除目标。Anthropic 工程博客点名的失败形态之一。对策：永远先摘要后丢弃，且需求逐字保留进摘要。

### 4.5 记忆工具：窗口外的第二大脑

与 2.4 的 RAG 式长期记忆的区别：记忆工具是 **Agent 主动读写的笔记本**（显式 write/read 操作），不是被动检索的向量库。官方形态（Anthropic 记忆工具口径）：一个由客户端托管的文件目录，Agent 通过命令查看、创建、编辑、删除其中的 Markdown 文件——记忆就是文件，持久化由客户端负责，窗口内外以「文件存在」的方式解耦。

设计要点：

- 写入有明确时机：用户表达偏好、做出关键决策、发现重要事实时立即落盘。
- 内容结构化：按主题分文件（偏好、项目状态、环境信息），别写成一团日志。
- 读回靠自觉加提醒：系统提示里告诉模型「开工前先读 plan 与记忆文件」，否则它不会读。
- 生命周期：会话结束不清空才叫记忆；每次会话都重建的那叫草稿。

读写时机的一组经验法则：

1. **写**：用户表达偏好（「以后都用 TypeScript」）、关键决策拍板、发现可复用事实（环境信息、报错解法）——三类事件触发写入，其余别写（写太多读不回来）。
2. **读**：会话冷启动读一次（恢复上下文）；执行与记忆主题相关的操作前读一次（改代码前读项目约定）；别每步都读——记忆是外存不是寄存器，反复全量读取等于把外置的成本又搬回窗口。
3. **改**：新事实与旧记忆冲突时覆盖而非追加（用户口味变了就更新），保留时间戳便于过期治理（见 4.8 的偏好衰减）。

记忆文件的组织方式（按主题分文件，一个可直接照抄的起点）：

| 文件 | 内容 | 写入时机 | 生命周期 |
|---|---|---|---|
| preferences.md | 用户显式偏好（语言、风格、命名习惯） | 用户表达偏好的当步 | 长期，带时间戳与衰减复审 |
| project.md | 项目约定、构建命令、目录结构要点 | 发现即写，冲突覆盖 | 项目存续期 |
| state/plan.md | 当前任务的目标、进度、决策、风险 | 每完成一步更新 | 单任务，完成后归档 |
| facts/xxx.md | 环境信息、报错解法等可复用事实 | 发现即写 | 长期，低频复审 |

### 4.6 子代理隔离与即时取回

**子代理隔离**（上下文动机见 2.8 多 Agent 协作）：主 Agent 让子代理执行「搜索 20 个网页」「通读 30 个文件找引用」这类重上下文操作。子代理的原始内容（几万字）全部留在它自己的上下文里死掉，只有 1–2k 的结论报告回到主 Agent。规则：**上下文在谁那里膨胀，谁负责压缩成结论。**

隔离不是免费的，取舍判据有三：子代理总数与串并行度（每个都是独立 LLM 会话，token 总成本可能不降反升，买的是主上下文的干净）；任务可委托性（目标清晰、验收可描述的操作才适合外包，需要主 Agent 亲自判断的不能派）；信息完整性风险（子代理可能漏掉主任务真正需要的细节，报告里要带「查了什么、没查什么」的边界声明）。一句话判据：**中间产物巨大且最终只需结论的操作才隔离**，普通工具调用留在主循环。

**即时取回（Just-in-time Retrieval）**：预加载整个代码库或全部文档是反模式——绝大部分内容永远用不到，却持续消耗注意力与预算。正确姿势是让引用常驻（文件路径+行号范围+一句话说明），内容用到时才读。

**类比 2：即时取回 = 图书馆的闭架书库。** 开架书店把所有书摊在走道里（预加载全部文档），找书靠肉眼扫（注意力衰减）；闭架图书馆只给你一张索书号目录卡（引用常驻，几十 token），你要哪本，管理员按号取出那一本（按需精确读取），看完收回（读完即弃）。目录卡是常驻层的一等公民，书本身永远不常驻。

落地前提常被忽略：即时取回依赖「模型知道有什么可取」。没有目录、索引或引用清单，模型连「该读哪个文件」都问不出来，按需取回退化成盲目试探。所以引用清单本身是常驻层的必要组成——花几十 token 登记「有什么在哪」，省下的是每次数万 token 的盲读。它与 H4（Agentic RAG）是同一思想：检索不是一次性注入，而是任务过程中按需发生的工具调用。

### 4.7 长任务上下文腐化（Context Rot）：机制拆解

工程社区把长任务中「越用越慢、越干越糊涂」的复合退化统称为 context rot（上下文腐化）——不是单一 bug，而是四条机制叠加：

| 症状 | 机制 | 对策 |
|---|---|---|
| 响应越来越慢 | 历史线性增长 → 每步预填充（Prefill）token 增长；缓存命中率下降 | 压缩控长 + 稳定前缀利用提示缓存 |
| 重复读同一文件 | 早期读过的内容被裁剪/稀释，模型不记得已读 | 记忆外置 + 引用清单常驻 |
| 忘记最初需求 | 需求在最旧的窗口位置，被裁剪或沉入低注意力区 | 摘要里逐字保留需求 + plan 文件常驻 |
| 动作开始发散 | 工具结果噪音累积，有效指令占比下降 | 子代理隔离脏活 + 裁剪 + 定期清理 |
| 成本越跑越贵 | 每步全量历史计费（输入 token 按步累积） | 预算监控 + 及时压缩 |

「越慢」还有一条容易被漏掉的机制——**提示缓存失效**：平台的缓存按前缀匹配，若每步都改写历史开头（比如把最新摘要插在前面），缓存全量失效，每步按未命中价全价重算。工程对策：常驻层（系统提示、记忆索引）放最前且保持字节级稳定，动态内容一律追加在尾部；压缩重建上下文时尽量保持前缀不变（摘要追加而非重写）。这一条是「延迟与成本双优」的关键杠杆，也是多数人从「越用越慢」现场排查里学到的第一课。

面试答法顺序（对应那道 Claude Code 真题）：先给症状分类，再逐条给机制（预填充增长、注意力衰减、裁剪策略伤头、噪音占比上升、缓存失效），最后给四原语对位方案——**结构化回答本身就是「懂上下文工程」的证明。**

答题骨架（可直接套用的三段式）：

```text
第一段 分类：「越用越慢」是复合退化（context rot），分慢、糊、贵三类症状
第二段 机制：慢 = prefill 线性增长 + 缓存失效；糊 = 注意力稀释 + 裁剪伤头；
           贵 = 每步全量历史计费（输入随步数平方级累积）
第三段 对位：压缩控长（保缓存前缀）、裁剪与隔离降噪音、常驻层钉住需求、
           plan.md 保进度账——最后补一句监控指标（占用率/每步 token/缓存命中率）
```

现场排查清单（拿到一个「越用越糊涂」的 Agent 时按序过一遍）：

1. 历史长度曲线：每步输入 token 是否线性/超线性增长？→ 定位是否缺压缩。
2. 原始需求位置：需求还完整出现在窗口里吗？在哪一个位置？→ 定位裁剪与注意力风险。
3. 重复动作指纹：是否有重复读同一文件、重复执行同一命令？→ 定位记忆/进度账缺失。
4. 缓存命中率：平台侧缓存是否命中？前缀是否被每步改写？→ 定位「贵而慢」的原因。
5. 噪音占比：工具结果垃圾（超长日志、无关内容）占窗口比例多少？→ 定位是否需要裁剪与隔离。

### 4.8 记忆工程化与 Mem0 2026 报告口径

Mem0 发布《State of AI Agent Memory 2026》年度报告，行业口径要点：Agent 记忆已从「技巧集合」升级为**生产工程学科**——出现年度报告、专项基准（含 BEAM 偏好衰减基准：衡量记忆随时间的衰减与更新）与运维实践。对本锚点的意义：

1. 「压缩/记忆/隔离/取回」不再是高级技巧，而是与缓存、限流同级的**生产基础设施**话题。
2. 记忆需要评测：偏好会过时（用户去年喜欢 A 今年喜欢 B），衰减与更新策略要进基准、进回归。
3. 面试延伸：被问「记忆系统怎么做」时，先分「会话内（压缩）/跨会话（记忆文件）/大规模（向量库，原理见 2.4）」三层，再谈评测——比直接背 Mem0 结论更显功底。

报告口径里最值得展开的一点是**偏好衰减（Preference Decay）**：记忆不是只增不减的资产，用户偏好会过时——去年「要详细解释」的用户今年可能只要结论。BEAM 类基准把「记忆随时间的衰减与更新」变成可评测对象，对应到工程就是三个问题：多久复审一次旧偏好、冲突时信新还是信旧、多久没有访问的记忆可以退役。这与 8 节坑 14（记忆当传家宝）互为正反面。

### 4.9 工程落地清单：三件低成本高收益的事

四大模式之外，日常工程里最先该做的是三件「脏活」——它们不性感，却是改造一个失控 Agent 的第一周就能见效的动作：

**第一件：系统提示分层。** 把所有指令写进一个系统提示是常见起点，失控方式有两种：项目约定改动频繁（毁缓存），全局红线与任务细节混写（模型分不清优先级）。分三层，按变更频率排布：

| 层 | 内容 | 变更频率 | 位置与缓存影响 |
|---|---|---|---|
| 全局层 | 角色定义、安全红线、输出格式约定 | 极低（按季度） | 最前缀，字节级稳定 |
| 项目层 | 项目约定、构建命令、代码风格（CLAUDE.md 类） | 低（按周） | 次前缀，随项目稳定 |
| 任务层 | 本任务目标、验收标准、当前计划 | 高（按任务） | 动态段，放靠后追加 |

**第二件：工具结果裁剪（Tool Output Trimming）。** 工具结果是长任务里最大的噪音源——一次 `ls -R` 或超长日志就是数万 token。三个手法按优先级用：字段白名单（只保留本次决策需要的字段，其余丢弃）；头尾截断（日志类保留头部错误与尾部摘要，中段折叠为省略计数）；引用化（内容替换为「路径+行号+一句话说明」，需要时再取回，见 4.6）。完整代码见 6.2。

**第三件：结构化笔记。** plan.md 一类进度文件（模板见 6.4）：目标逐字保留、进度打勾、决策带理由、风险显式化。它是「记忆外置」原语里最廉价也最见效的一招——不依赖任何框架，一个 Markdown 文件就消灭了「目标漂移」和「重复劳动」两个最大症状。

改造顺序（把三件活排进四大模式之前，按成本收益排序）：

| 顺序 | 动作 | 实现成本 | 典型收益 |
|---|---|---|---|
| 1 | 工具结果裁剪 | 低 | 直接砍掉最大噪音源 |
| 2 | 结构化笔记 plan.md | 低 | 目标不再漂移、进度不再丢 |
| 3 | 系统提示三层分层 | 低 | 缓存稳定 + 指令优先级清晰 |
| 4 | 阈值触发压缩 | 中 | 长会话必需，防截断 |
| 5 | 子代理隔离 | 中 | 重上下文任务的主上下文保护 |
| 6 | 记忆工具 + 衰减治理 | 高 | 跨会话场景才需要，别提前上 |

### 4.10 Claude Code 实践：四模式的产品化样板

| 模式 | Claude Code 中的落地 |
|---|---|
| 压缩 Compaction | 会话接近窗口上限自动压缩历史为结构化摘要，保留目标与进度后继续 |
| 计划外置 | plan.md / TODO 文件：任务列表落盘，完成一项更新一项，模型每步可重读目标 |
| 项目记忆 | CLAUDE.md 常驻：项目约定、构建命令、代码风格进每次会话 |
| 子代理 | Task 工具派发子代理做大范围搜索/探索，主会话只收结论 |
| 即时取回 | 默认不整库预读，按 Grep/Glob 定位后精确读取行号范围 |

产品化观察（面试引用时的话术价值）：Claude Code 证明了四模式不需要花哨架构——一个阈值触发的摘要、几个落盘的 Markdown 文件、一个派发子任务的工具，就撑起了小时级任务的可用性。上下文工程的门槛不在技术复杂度，而在**纪律**：什么进常驻层、什么外置、什么丢弃，每一步都要有明确规则并坚持执行。延伸一个 2026 年的中文题库动向（代码随想录面经汇总）：「Harness Engineering」已成为独立考察词——Agent 的能力边界很大程度来自 harness（脚手架：循环、工具、上下文管理）而非模型本身，而上下文工程正是 harness 里权重最高的那一块。这也是它适合作为面试题的原因——答得好坏差异极大，且无法靠背名词蒙混。

## 5. 架构 / 流程

长任务 Agent 的上下文生命周期（四模式各就各位）：

```text
任务开始
   ↓
[注入] 系统提示（三层：全局/项目/任务） + 常驻记忆（CLAUDE.md / plan.md / 用户偏好文件）
       引用清单：路径+行号+一句话说明（不装内容本身）
   ↓
[循环] 每步：模型看见 = 常驻层 + 摘要层 + 最近 N 轮原文 + 本步工具结果（裁剪后）
   │
   ├─ 重上下文操作（搜索/通读/探索）──→ 子代理隔离：脏活在独立上下文干，
   │                                     主上下文只收 1–2k 结论报告
   ├─ 大文件引用 ──→ 即时取回：用到时按路径+行号精确读取，读完即弃
   ├─ 关键事实出现 ──→ 记忆工具：立即写外部文件（窗口外持久）
   ↓
[监控] 窗口占用、每步输入 token、缓存命中率
   ↓ 占用 > 80%
[压缩] 先外置「不能丢」的细节 → 历史折叠为四段结构化摘要
       → 摘要 + 最近若干轮原文 = 干净书桌，继续干活（前缀保持不变）
   ↓
[收尾] 任务总结回写记忆文件 → 下次会话冷启动即带经验
```

窗口内部的预算分层（4.2 的切法画成图，常驻层钉在最前）：

```text
┌───────────────────────────── 上下文窗口（示意 20 万 token）─────────────┐
│ [常驻层 ≤5%]  系统提示(全局/项目) + 记忆索引 + plan.md   ← 字节级稳定    │
│ [摘要层 5–10%] 任务四段摘要（压缩时追加更新）                             │
│ [最近原文 10–15%] 最近若干轮消息（滑动窗口）                             │
│ [工作区 ~75%] 当步工具结果（裁剪后） + 推理空间     ← 每步更替           │
└────────────────────────────────────────────────（动态内容一律尾部追加）─┘
     ↑ 前缀稳定 → 提示缓存命中；头部膨胀/改写 → 缓存全失效（4.7）
```

压缩触发瞬间，窗口内容的重建前后对比（前缀保持不变是缓存命中的关键）：

```text
压缩前（占用 82%）                          压缩后（占用约 30%）
┌────────────────────────┐                ┌────────────────────────┐
│ [常驻层] 系统提示+索引   │ ← 字节不变      │ [常驻层] 系统提示+索引   │
│ [历史] 16 万 token 原文  │                │ [摘要] 四段结构化 1 万    │
│   ├ 需求（在第 1 条）    │   先外置细节     │   ├ 需求逐字保留          │
│   ├ 大量工具结果噪音     │   → memory.md   │   ├ 已完成/决策/未完成    │
│   └ 最近 6 轮           │                │ [最近原文] 6 轮约 1.2 万  │
└────────────────────────┘                └────────────────────────┘
                                            工作区余量恢复 → 任务继续
```

选型速查（什么症状用什么原语）：

```text
窗口快满了？                → 压缩 compaction
事实要跨步/跨会话存活？      → 记忆工具外置
中间产物巨大且只需结论？     → 子代理隔离
内容大但按需才用？          → 即时取回 just-in-time
工具结果全是噪音？          → 裁剪（先做这个，成本最低）
全都有一点？                → 组合拳（生产 Agent 的常态）
```

## 6. 代码 / 工具

### 6.1 压缩模板与 CompactionManager

```python
from dataclasses import dataclass, field

COMPACT_PROMPT = """把以下 Agent 历史压缩为四段，总量不超过 800 token：
1. 原始需求：用户最初目标，逐字保留关键约束与验收标准
2. 已完成项与关键决策：每条一行，附理由
3. 未完成项：下一步动作，可执行粒度
4. 当前焦点与风险：正在进行什么、有什么坑
禁止丢弃：文件路径、行号、报错原文、用户显式偏好。"""

@dataclass
class CompactionManager:
    """窗口预算管理：阈值触发压缩，压缩前先外置关键事实。"""
    max_tokens: int = 200_000
    compact_at: float = 0.80                    # 占用超 80% 触发
    min_release: float = 0.30                   # 一次压缩至少释放 30% 才值得压（防抖）
    keep_recent: int = 6                        # 压缩后保留最近 6 轮原文
    messages: list = field(default_factory=list)
    memory_path: str = "agent_memory.md"

    def used_tokens(self, count) -> int:        # count: 粗略 token 计数函数
        return sum(count(m["content"]) for m in self.messages)

    def maybe_compact(self, count, llm_summarize) -> bool:
        used = self.used_tokens(count)
        if used < self.max_tokens * self.compact_at:
            return False
        before = used
        # 1) 压缩前：把不可丢的细节先外置（摘要是有损的，文件是无损的）
        self._persist_key_facts(llm_summarize)
        # 2) 历史折叠为结构化摘要（四段结构，不是自由总结）
        summary = llm_summarize(self.messages, COMPACT_PROMPT)
        # 3) 摘要 + 最近 6 轮原文 = 干净书桌
        recent = self.messages[-self.keep_recent:]
        self.messages = [{"role": "user",
                          "content": f"[任务摘要·自动压缩]\n{summary}"}] + recent
        after = self.used_tokens(count)
        assert (before - after) / before >= self.min_release, "释放量不足，检查摘要质量"
        return True

    def _persist_key_facts(self, llm_summarize) -> None:
        facts = llm_summarize(self.messages,
                              "仅提取：路径/行号/报错原文/用户显式偏好，逐条列出。")
        with open(self.memory_path, "a", encoding="utf-8") as f:
            f.write(f"\n## 自动外置 {self._now()}\n{facts}\n")

    @staticmethod
    def _now() -> str:
        from datetime import datetime
        return datetime.now().strftime("%Y-%m-%d %H:%M")
```

主循环接入（伪代码）：

```python
mgr = CompactionManager()
mgr.messages.append({"role": "user", "content": load_plan("plan.md")})

while not task_done:
    mgr.maybe_compact(count_tokens, llm_summarize)   # 每步先查预算
    action = agent.step(mgr.messages)                # 正常干活
    mgr.messages.append(action)
```

### 6.2 工具结果裁剪：最大噪音源的第一道闸

```python
MAX_TOOL_TOKENS = 4_000          # 单个工具结果的入窗上限（示意值）

def trim_tool_result(tool_name: str, result: dict | str,
                     need_fields: tuple = ()) -> str:
    """三手法按优先级：字段白名单 → 头尾截断 → 引用化。"""
    # 手法 1：字段白名单——结构化结果只留本次决策需要的字段
    if isinstance(result, dict):
        kept = {k: result[k] for k in need_fields if k in result}
        dropped = len(result) - len(kept)
        text = repr(kept)
    else:
        text, dropped = str(result), 0

    if count_tokens(text) <= MAX_TOOL_TOKENS:
        return text if not dropped else f"{text}\n[已裁掉 {dropped} 个无关字段]"

    # 手法 2：头尾截断——日志类保头（错误现场）保尾（结论与统计）
    head, tail = text[: MAX_TOOL_TOKENS * 2], text[-MAX_TOOL_TOKENS:]
    skipped = len(text) - len(head) - len(tail)
    # 手法 3：引用化——全文落盘，窗口里只留引用，需要时按引用取回
    ref = dump_to_file(tool_name, text)      # 返回 "logs/2026-09-23/run42.log L1-8800"
    return (f"{head}\n...[中段 {skipped} 字符已省略，全文见 {ref}]...\n{tail}")

# 用法：查订单列表，只需要 id 与状态两个字段
trimmed = trim_tool_result("list_orders", raw_json,
                           need_fields=("order_id", "status"))
```

裁剪原则一句话：**工具结果是为「下一步决策」服务的，不为「将来可能的回顾」服务**——后者交给引用化与记忆文件。

### 6.3 子代理隔离与即时取回

```python
def delegate_search(query: str) -> str:
    """子代理隔离：重上下文操作在全新上下文里翻资料山，只回传报告。"""
    sub = Agent(
        system="你是检索专员：只做检索与核实，报告不超过 300 字，"
               "给出结论 + 来源路径/链接 + 置信度 + 查了什么/没查什么。"
               "原始内容不要复述。",
        context=fresh_context(),                 # 与主 Agent 完全隔离
        tools=[web_search, read_file, grep],
    )
    sub.run_until_done(query)                    # 几万字原始内容死在子上下文
    return sub.final_report(max_chars=2000)      # 主 Agent 只收 2k 结论

def jit_read(ctx, path: str, lines: tuple | None = None) -> str:
    """即时取回：引用常驻，内容用到才读，读完即弃。"""
    span = f" L{lines[0]}-{lines[1]}" if lines else " 全文"
    ctx.note(f"[引用登记] {path}{span}")          # 路径常驻主上下文（极便宜）
    return read_file_slice(path, lines)          # 内容只进当步工具结果，下步可被压缩
```

两段代码的组合拳才是生产形态：主循环每步先查窗口预算（6.1），工具结果先过裁剪闸（6.2），重上下文操作派子代理（6.3），关键事实随手外置，大文件按行号即用即取——四个原语在同一会话里各管一段，互不替代。单独落地任何一个原语都能缓解症状，但「越用越糊涂」是四种丢失机制的叠加，治理也要叠加。

### 6.4 结构化笔记模板（plan.md）

```markdown
# plan.md（模型每步可重读目标，不依赖长历史回忆）
## 目标
- 把 orders 模块从单体重构为独立服务（用户 2026-09-12 提出）
- 验收标准：全部现有测试通过；接口响应 P99 < 200ms
## 进度（完成打勾）
- [x] 梳理 orders 依赖（结论：3 处外部调用，见 memory/depends.md）
- [ ] 抽出 OrderRepository 接口
- [ ] 迁移单元测试
## 关键决策
- 用适配器层兼容旧表结构（理由：避免双写迁移风险）
## 风险
- 报价逻辑与 promotions 服务隐式耦合：改动前先跑集成测试
```

要点：目标逐字保留用户原话（防漂移）；进度打勾（防重复劳动）；关键决策带理由（防反复推翻）；风险显式化（防踩坑）。四原语里「记忆外置」最廉价也最见效的一招，就是它。

## 7. 案例

### 案例 A：编程 Agent 的重构任务治理

**场景**：某软件团队的 AI 编程助手跑 2 小时的服务重构任务，症状：重复读文件、中途偏离需求、第 40 步后响应明显变慢。

**改造**：按 4.9 的顺序落地——先做工具结果裁剪（构建日志头尾截断、列表类只留文件名与行号）；再上 plan.md 外置（重构计划逐步打勾）；系统提示分三层（团队红线/项目约定/任务验收）；然后窗口占用 80% 触发压缩（四段结构化摘要）；「找全部引用」类操作改子代理执行只回传文件+行号清单；代码不再整库预读，改 Glob 定位后按行号读取。

**效果**（示意量级）：步骤成功率 55% 提升到 82%；目标漂移（中途偏离需求的次数）从 7 次降到 1 次；单任务平均输入 token 下降 40%，尾部步骤延迟回到首步的 1.5 倍以内（此前是 6 倍）。复盘关键句：前三步（裁剪、笔记、分层）没花一天就拿下大半收益，压缩与子代理是在任务变长之后才真正需要的。

### 案例 B：深度研究 Agent 的隔离改造

**场景**：一家咨询公司的深度研究 Agent，单任务要检索 30+ 网页，主上下文在第 15 个网页后爆满，报告后半部分质量骤降。

**改造**：按研究子问题拆 4 个子代理并行检索，各自在独立上下文读完全部网页，各回传 1.5k 结构化报告（结论+来源+置信度+边界声明）；主 Agent 只聚合报告；全部原始网页 URL 写入记忆文件备查。

**效果**（示意量级）：单任务可容纳的信息源从 15 个提升到 40+；报告事实性错误率下降一半；主上下文占用稳定在 30% 以内——**上下文在谁那里膨胀，谁负责压缩成结论，这条规则立住了。**

### 案例 C：长会话客服的记忆外置

**场景**：某电商 VIP 客服 Agent 处理跨 3 小时的售后工单（多次转接、多轮举证），用户重复陈述背景，Agent 偶尔遗忘已承诺的补偿方案。

**改造**：承诺类语句实时写入记忆文件（含时间与工单号）；每 20 轮做一次轻量压缩；新转接坐席（或会话恢复）先读记忆文件再开工。

**效果**（示意量级）：重复陈述率下降 60%；「遗忘已承诺事项」类投诉降为零样本出现；压缩触发的额外成本约占会话成本 5%——远低于重复沟通与投诉处理的开销。复盘关键句：客服场景的「必须外置」信息极其明确——承诺、金额、时限、工单号，识别这四类的正则比任何摘要模型都可靠；**能用规则写盘的别交给模型总结**，这条原则在治理类改造里屡试不爽。

## 8. 常见坑

1. **把 Context Engineering 当提示词工程的新名字**。只优化指令文本不管历史与工具结果；对策：按 4.1 的六源盘点表逐项检查输入。
2. **盲目相信大窗口**。窗口大不等于注意力可用，中部信息照样丢失（lost in the middle）；对策：关键约束进常驻层与摘要层，不赌位置。
3. **压缩用自由摘要**。模型随总结随丢需求与约束；对策：四段结构化摘要 + 「禁止丢弃」清单。
4. **压缩前不外置**。有损摘要直接覆盖历史，细节永久丢失；对策：先写记忆文件再压缩。
5. **记忆只写不读**。落盘了但系统提示不提醒模型读，等于没写；对策：开工先读记忆/计划，写进系统提示。
6. **记忆不分主题一坨日志**。检索与模型阅读都困难；对策：按主题分文件、带时间戳、定期清理过期偏好。
7. **子代理任务说明太模糊**。回传报告缺关键细节，主 Agent 还得重查；对策：限定报告结构（结论/来源/置信度/边界声明/字数）。
8. **子代理拆太碎**。简单查询也派子代理，往返开销大于收益；对策：只有「中间产物巨大且只需结论」才隔离。
9. **预加载整库/全部文档**。噪音与成本双杀；对策：引用常驻 + 即时取回精确读取。
10. **工具结果原样入窗**。超长日志与全量 JSON 一步吃掉数万 token 预算；对策：字段白名单、头尾截断、引用化三手法（6.2）。
11. **不监控窗口预算**。到截断报错才发现爆了；对策：占用率、每步输入 token、缓存命中率三个指标常驻看板。
12. **压缩时机太晚**。占用 95% 才压，裁剪已经先动手砍掉了头部需求；对策：80% 左右主动压，别让平台替你裁。
13. **压缩后不验证**。模型开始重复已完成动作才知道摘要丢了进度；对策：压缩后跑一次进度核对（对照 plan.md 打勾项）。
14. **忽略缓存友好性**。每步改写前缀导致提示缓存全失效，延迟成本双涨；对策：常驻层放前缀且保持稳定，动态内容靠后。
15. **系统提示一坨混写**。全局红线、项目约定、任务细节全塞一段，改一处毁整个缓存前缀；对策：三层分层（全局/项目/任务），按变更频率排布。
16. **把记忆当传家宝**。什么都存，过期偏好污染当前决策；对策：偏好带衰减与更新策略（参考 BEAM 类基准思路），定期退役。

## 10. 小结

- Context Engineering 是提示词工程的**超集**：管模型每一步看见的全部信息——指令只是六分之一个输入源。
- 根本立场：**上下文是稀缺资源，像操作系统管内存一样管理它**——常驻、换页（压缩）、回收（清理）、按需调页（即时取回）。
- 四大模式对四类丢失：**压缩**（窗口装不下）、**记忆工具**（窗口留不住）、**子代理隔离**（窗口不该装）、**即时取回**（窗口不用先装满）。
- 压缩三铁律：结构化四段摘要、压缩前先外置、摘要+最近原文重建；两个反模式：高频小压缩、裁剪式治理。
- 上下文腐化（context rot）五机制：预填充随历史增长、注意力中部衰减、裁剪伤头、噪音占比上升、缓存失效——四模式逐条对位。
- 预算分层：常驻层 5% 以内且字节级稳定，工作区留给当步工具结果——切法是超参数，改动必须进评测。
- 子代理规则一句话：**上下文在谁那里膨胀，谁负责压缩成结论。**
- 落地优先级：先做三件低成本的事——工具结果裁剪、plan.md 结构化笔记、系统提示三层分层——再上压缩、隔离与记忆工具。
- 记忆外置最廉价的形态是 plan.md：目标逐字保留、进度打勾、决策带理由、风险显式化。
- 行业口径：**Mem0《State of AI Agent Memory 2026》确认记忆已从技巧升级为生产工程学科**（含 BEAM 偏好衰减基准）。
- Claude Code 实践映射：自动压缩、plan.md、CLAUDE.md、Task 子代理、按行号读取——四模式的产品化样板，也是 Harness Engineering 的核心。
- 效果必须可度量：步骤成功率、目标漂移率、每步输入 token 三指标，改造前后对比。
- 面试安全答法：先分症状、再讲机制、后给模式对位——结构本身就是能力证明。
- 这些能力直接支撑：H4（Agentic RAG 的按需检索）、H6（AI Coding 智能体的 Harness 设计），以及 2.8 多 Agent 协作的子代理分工、3.7 成本与延迟治理。
