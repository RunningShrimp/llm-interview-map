# 讲解 3.4 可观测性与追踪

> 说明：前置 1.6 讲应用层评估入门（指标 + LLM-as-judge），前置 3.1 的分层架构把「观测」列为独立一层；本篇从 Agent 视角升级为**生产可观测体系**——Agent 多步、多组件、多工具，一次请求可能产生几十个 span。  
> 聚焦四个问题：如何还原完整轨迹、如何定位问题、如何归因成本、如何发现异常。  
> 坏例回流评估集见 3.5，观测数据变成发布门禁见 3.9，值班与故障处置见 4.9。

## 1. 定位

AI 工程化层第 4 个知识点，属于「系统可见性基础设施」。  
它回答本锚点的核心问题：**出错时如何还原完整轨迹——把「不知道哪里错了」变成「5 分钟内定位根因」**。

与 1.6 的分工：1.6 是评估入门，讲「离线怎么打分」（评估指标、LLM-as-judge）；本篇是生产可观测体系，讲「线上发生了什么怎么看见」（结构化日志、分布式追踪、span 树、token 与成本遥测、回放调试、告警）。两者首尾相接：可观测把线上坏例（Bad Case）捞出来，评估把坏例消化成回归用例（见 3.5）。

前置：1.6（评估入门）、3.1（架构分层，观测是其中一层）。  
后续承接：3.5（评估体系）、3.9（CI/CD 与发布）、4.9（运维保障）；内容上另与 3.7（成本与延迟优化）、3.10（反馈闭环）强联动。

## 2. 一句话定义

可观测性与追踪，是通过日志（Logging）、指标（Metrics）、链路追踪（Tracing）三大支柱，对 Agent 的每一步决策、每一次工具调用、每一笔成本进行记录、聚合和可视化，使系统行为可还原、可定位、可归因的工程体系。

简化公式：

```text
可观测性 = Logging（发生了什么） + Metrics（整体怎么样） + Tracing（为什么发生）
```

## 3. 为什么需要

Agent 系统比普通 LLM 应用复杂一个量级：

- **多步执行**：一次请求可能 5–20 步，哪步错了？
- **多组件**：LLM、工具、检索、记忆、反思，谁的问题？
- **多模型**：路由到不同模型，哪个模型拖慢了？
- **多工具**：工具调用失败，是参数错还是服务挂？
- **成本放大**：一次任务 10 次 LLM 调用，钱花在哪？
- **延迟叠加**：串行 5 步，每步 2 秒，P99（99 分位延迟）就是 10 秒。
- **状态复杂**：记忆、计划、工作状态，哪一步状态错了？
- **难以复现**：同输入不同轨迹，怎么调试？
- **多 Agent**：Agent 之间通信，谁传给谁什么？

**没有 vs 有的对比**（每个场景在 §7 都有完整复盘）：

| 故障场景 | 没有可观测性 | 有可观测性 |
|---|---|---|
| P99 延迟 3s 涨到 15s | 翻代码猜瓶颈，排查一两天 | 面板锁定慢工具，trace 定位到 span，半小时出根因 |
| 日成本 $50 涨到 $200 | 只知道账单涨了 | 按维度归因，Top-1 直接指到某类请求 |
| 用户投诉「Agent 答错了」 | 无法复现，同输入不同轨迹 | 拿 trace_id 回放轨迹，逐步看到哪步错 |
| 凌晨工具服务挂了 | 早上用户反馈才知道 | 告警分钟级触达值班（见 4.10） |

**类比一（追踪 = 物流单号）**：

```text
没有可观测性 = 黑色快递箱：签收时才发现东西碎了，碎在哪一程无从查起
有可观测性 = 全程物流跟踪：每到一个中转站扫码记一笔（span），单号（trace_id）全程不变
```

**类比二（回放 = 棋谱复盘）**：

```text
回放 trace = 棋谱复盘：每一步落子都有记录，输了这局（坏例）能指出第几手走错
没有回放   = 只知道输了，双方都记不清走过哪几步
```

## 4. 核心原理

### 4.1 可观测性三支柱

| 支柱 | 回答的问题 | 数据形态 | 典型工具 | Agent 场景例子 |
|---|---|---|---|---|
| Logging | 发生了什么？ | 离散事件 | ELK、Loki | 一次工具调用的参数与返回 |
| Metrics | 整体怎么样？ | 聚合数值 | Prometheus、Grafana | 工具失败率、日成本曲线 |
| Tracing | 为什么发生？ | 调用链 | OTel、Langfuse、LangSmith | 一次请求的完整 span 树 |

**三者关系**（一次故障排查的标准动线）：

```text
Metrics 发现异常（P99 延迟上升）
    ↓
Tracing 定位根因（某工具调用变慢）
    ↓
Logging 查看细节（工具返回了错误）
```

类比：Metrics 是体检报告的汇总页（看整体趋势），Tracing 是一次完整就诊的流程单（挂号→检查→诊断→取药），Logging 是每项检查的原始化验单（看单点细节）。

### 4.2 Agent 的 Trace 结构

一次 Agent 请求把每个操作记录为一个跨度（Span），所有 span 通过父子关系挂成一棵树。Agent 每一轮执行循环（见 2.5）天然对应一组子 span：

```text
Trace: agent_request (trace_id=abc123)
├─ Span: input_processing (5ms)
│   ├─ Span: auth (2ms)
│   └─ Span: rate_limit (1ms)
├─ Span: planning (800ms)
│   └─ Span: llm_call (gpt-4o, 800ms)
│       ├─ input_tokens: 500
│       └─ output_tokens: 200
├─ Span: step_1 (1200ms)
│   ├─ Span: llm_decision (600ms)
│   └─ Span: tool_call: search_orders (600ms)
│       ├─ args: {user_id: "u1"}
│       └─ result: {orders: [...]}
├─ Span: step_2 (900ms)
│   ├─ Span: llm_decision (500ms)
│   └─ Span: tool_call: get_order_detail (400ms)
├─ Span: reflection (600ms)
│   └─ Span: llm_call (600ms)
└─ Span: output_formatting (50ms)

Total: 3555ms, Cost: $0.008, Steps: 2
```

**关键字段**：

| 字段 | 说明 |
|---|---|
| trace_id | 一次请求的唯一标识 |
| span_id / parent_span_id | 本操作标识 / 父操作标识，二者构成树形结构 |
| name | 操作名称 |
| start_time / end_time / duration | 时间戳与耗时 |
| input / output | 输入输出 |
| model | 模型名 |
| tokens | token 数（输入/输出分列） |
| cost | 成本 |
| status / error | 成功/失败、错误信息 |
| prompt_version | 提示词（Prompt）版本号，坏例归因到具体改动（见 3.9） |
| metadata | 自定义标签（用户、租户、任务类型） |

### 4.3 Span 类型与语义约定

Agent 中的 span 类型：

| 类型 | 说明 | 例子 |
|---|---|---|
| request | 顶层请求 | agent_request |
| llm | LLM 调用 | llm_call |
| tool | 工具调用 | tool_call: search_orders |
| retrieval | 检索 | vector_search |
| memory | 记忆读写 | memory_read |
| reflection | 反思 | critique |
| planning | 规划 | plan_generation |
| routing | 路由 | model_routing |
| approval | 人工审批 | human_approval |

每类 span 的差异化必记字段：

| Span 类型 | 必记字段 |
|---|---|
| llm | 模型名、完整输入与补全、输入/输出 token、采样参数、prompt 版本 |
| tool | 工具名、入参、返回（超长截断）、状态码、耗时、错误详情 |
| retrieval | 查询语句、命中文档 ID 与相似度分数、Top-K |
| memory | 读写类型、命中的记忆条目 |

**语义标准化**：截至 2026 年，OpenTelemetry 的生成式 AI 语义约定（Semantic Conventions）以 `gen_ai.*` 前缀落地并经 CNCF 标准化，主流平台均已兼容（来源：OpenTelemetry 官方语义约定文档；n1n.ai 平台对比文，2026）。按标准属性埋点，换观测平台不用改业务代码：

| 通用概念 | OTel 属性 | 示例值 |
|---|---|---|
| LLM 提供方 | gen_ai.system | openai / anthropic |
| 模型名 | gen_ai.request.model | gpt-4o |
| 操作类型 | gen_ai.operation.name | chat / execute_tool |
| 输入 token | gen_ai.usage.input_tokens | 500 |
| 输出 token | gen_ai.usage.output_tokens | 200 |

### 4.4 分布式追踪与上下文传播

当 Agent 拆成多个服务（甚至多个 Agent 互调）时，链路追踪升级为分布式追踪（Distributed Tracing），trace 要跨服务、跨进程不断：

```text
API Gateway (span: request)
    ↓ trace 上下文传递
Agent Service (span: agent_run)
    ↓ trace 上下文传递
LLM Service (span: llm_call)
    ↓
Tool Service (span: tool_call)
```

**关键机制是上下文传播（Context Propagation）**：`trace_id` 和 `parent_span_id` 必须随请求传到下游。HTTP 场景用标准 header（W3C Trace Context 规范）：

```text
traceparent: 00-{trace-id 32 位十六进制}-{parent-span-id 16 位}-{flags}
```

```python
# 上游：把当前 trace 上下文放进 HTTP header
headers = {
    "traceparent": f"00-{trace_id}-{current_span_id}-01",
}

# 下游：解析出来作为本地 span 的父节点，链路就接上了
trace_id, parent_span_id = parse_traceparent(request.headers["traceparent"])
```

三种容易断链的场景与对策：

| 场景 | 传播方式 |
|---|---|
| HTTP 同步调用 | 标准 header（traceparent） |
| 消息队列 / 异步任务 | trace 上下文序列化进消息属性，消费者取出后再起子 span |
| 多 Agent 互调（见 2.8） | Agent 间消息体携带 trace 上下文，子 Agent 的 span 挂到同一棵树 |

### 4.5 还原完整轨迹的三件套

本锚点的关键问题「出错时如何还原完整轨迹」，正面答案是一套三件套：

```text
还原完整轨迹 = 上下文传播（trace_id 贯穿全程）
            + 分层记录（span 树记下每个 LLM / 工具调用的输入输出）
            + 可回放（沿 trace 逐步重演）
```

**推导：一次标准排查的完整路径**：

```text
1. 入口拿到 trace_id（来源：用户反馈工单、告警详情、日志检索，三者必居其一）
2. 按 trace_id 聚合所有 span，按 parent_span_id 重建 4.2 那棵树
3. 自顶向下逐层看 input/output，第一个 output 异常或 status=ERROR 的 span 即疑点
4. 用疑点 span 的 span_id 去日志里检索，看当时的报错细节与上下文
5. 归因到五类之一：检索给了错内容 / 工具返回错数据 / 提示词与上下文组装问题 /
   模型生成问题（幻觉、格式）/ 状态与参数错误
6. 修复后把该 trace 收进回归集（见 3.5），防止同类错误复发
```

**回放的两种模式**：

| 模式 | 做法 | 优点 | 局限 |
|---|---|---|---|
| 记录回放 | 读当时落库的 span 记录逐步展示 | 快、确定性、零额外成本 | 只能看到当时行为，验证不了新改动 |
| 重新执行 | 测试环境用记录的输入重跑一遍 | 能验证修复、对比新旧版本 | LLM 非确定性，轨迹可能不同；要花 token |

收集与回放的实现见 4.11。

**面试高频问法**：「线上 Agent 答错了怎么查？」共识口径分三步——先定位（用户反馈带出 trace_id → 看 span 树 → 找第一个异常 span），再归因（读该 span 的 input/output，区分检索错、工具错、还是模型生成错），后闭环（修复、坏例入回归集）。加分点：能说出「记录回放」与「重新执行」的区别，以及 prompt 版本号要落在 span 上（见 3.9）。

### 4.6 结构化日志

结构化日志（Structured Logging）指机器可解析的日志格式，不是写给人看的自由文本：

```json
{
  "timestamp": "2024-01-15T10:30:00.123Z",
  "level": "INFO",
  "service": "agent-service",
  "trace_id": "abc123",
  "span_id": "span456",
  "event": "tool_call",
  "tool": "search_orders",
  "args": {"user_id": "u1"},
  "duration_ms": 600,
  "status": "success",
  "user_id": "u1",
  "tenant_id": "company_a"
}
```

**原则**：

- **JSON 格式**：便于解析和检索。
- **包含 trace_id 与 span_id**：既能串联链路，也能从 trace 一键跳到日志。
- **包含关键字段**：模型、工具、token、成本、延迟。
- **不含敏感信息**：API Key、PII 必须脱敏——写入前过一层脱敏函数（字段白名单 + 正则打码手机号、邮箱、sk- 开头的 Key）。
- **统一字段名**：所有服务一致，否则聚合分析对不上。
- **级别有纪律**：按下表使用，DEBUG 生产默认关闭。

**日志级别**：

| 级别 | 用途 |
|---|---|
| DEBUG | 详细调试信息 |
| INFO | 关键事件（请求、工具调用） |
| WARNING | 可恢复的问题（重试、降级） |
| ERROR | 错误（工具失败、LLM 超时） |
| CRITICAL | 严重错误（服务不可用） |

### 4.7 指标（Metrics）

**Agent 关键指标**（按五层组织）：

```text
# 请求层

agent_request_duration_seconds{quantile}

# LLM 层
llm_calls_total{model, status}

# 工具层

agent_steps_total{task_type}

# 安全层

```

**黄金信号（Golden Signals）**：谷歌 SRE 四大黄金信号（延迟、流量、错误、饱和）在 LLM 场景的通用扩展：

| 黄金信号 | Agent 场景指标 | 为什么关键 |
|---|---|---|
| 延迟 | P50/P95/P99 请求耗时、TTFT（首字延迟）、单步耗时 | Agent 延迟是多步叠加，只看平均值会掩盖尾部 |
| 流量 | QPS、活跃 trace 数、在途步数 | 容量规划与限流依据 |
| 错误 | 请求失败率、工具失败率、LLM 超时率、用户点踩率 | 直接衡量质量 |
| 饱和 | token 消耗（输入/输出分列）、单请求成本、缓存命中率、队列长度 | 成本与容量同步失控的预警 |

（来源：黄金信号为 Google SRE 经典口径；TTFT、token 分列、单请求成本、缓存命中率为 LLM 场景扩展，见 MortalJobs《LLMOps 面试指南》2026。埋点代码见 6.4。）

**网关层观测（趋势观察）**：随着 AI 网关成为架构标配（见 3.1），网关侧观测清单在 2026 年逐渐成形——护栏（Guardrail）拦截事件、MCP 工具活动、请求追踪、成本监控四项是选型清单的常客（来源：dev.to《How to Choose an AI Gateway in 2026》）。

### 4.8 成本归因

**按维度归因**：

```text
成本归因维度：
├─ 按模型：gpt-4o vs gpt-4o-mini
├─ 按用户：哪个用户花最多
├─ 按租户：哪个客户成本最高
├─ 按任务类型：哪类任务最贵
├─ 按步骤：规划 vs 执行 vs 反思
└─ 按工具：哪个工具调用最频繁
```

做法：每次 LLM 调用在 span 上记录 token 与单价，再按标签（用户/租户/任务类型）聚合出报表，完整实现见 6.5。成本优化的手段（缓存、路由、级联）在 3.7 展开，本篇只解决「钱花在哪」的度量问题——度量不清，优化无从下手。

### 4.9 采样策略

**面试高频问法**：「高 QPS 下 trace 全量上报会有什么问题？怎么做采样？」共识口径：全量上报有三重代价——上报与存储成本随 QPS 线性增长、批量导出可能拖慢请求路径、后端查询越来越慢。主流答案是尾部采样（Tail-based Sampling）：先在本机缓冲完整 trace，结束后按规则决定去留——错误与慢请求全采，正常请求抽 1%–10%。

| 维度 | 头部采样（Head-based） | 尾部采样（Tail-based） |
|---|---|---|
| 决策时机 | 请求入口、trace 开始前 | trace 结束后，看过完整结果 |
| 资源开销 | 低，不采的直接不记 | 高，需缓冲整条 trace |
| 错误样本 | 会丢（入口时不知道后面会不会错） | 可 100% 保留 |
| 适用 | 纯容量控制 | Agent 调试与坏例收集 |

一套常用的采样规则（示意）：

```text
- status = ERROR       → 保留 100%
- duration > 5s        → 保留 100%
- 用户点踩 / 人工标记   → 保留 100%
- 其余正常请求         → 保留 10%（趋势分析够用）
保留策略：trace 存 30 天（TTL，存活时间），坏例永久，指标只存聚合值
```

类比：机场安检。对每位旅客开箱细查（全量 trace）成本不可接受；对高危行李（错误、超时）全检、普通行李抽查，安全与通行效率兼得。

### 4.10 异常检测与告警

**告警规则**（指标 + 阈值 + 分级）：

| 指标 | 阈值 | 级别 |
|---|---|---|
| P99 延迟 | > 10s | P1 |
| 错误率 | > 1% | P1 |
| 越权尝试 | > 0 | P1 |
| 成功率下降 | > 5% | P1 |
| 日成本 | > 预算 80% | P2 |
| 工具失败率 | > 5% | P2 |
| 注入检测 | > 10/小时 | P2 |
| 缓存命中率下降 | > 20% | P3 |

**分级响应**：

```text
P1：电话 / 短信，15 分钟内响应 —— 错误率、P99、越权
P2：IM 群，当天处理 —— 成本、工具失败率、注入检测
P3：日报周报，不叫人 —— 缓存命中率、慢趋势
```

**异常检测**（静态阈值之外，用统计基线兜住「缓慢劣化」这类静态阈值发现不了的问题）：

```python
def detect_anomaly(metric: str, window: int = 60) -> bool:
    recent = get_recent_values(metric, window)          # 最近 1 分钟
    baseline = get_baseline(metric, window * 10)        # 前 10 分钟基线
    mean = statistics.mean(baseline)
    std = statistics.stdev(baseline)
    current = statistics.mean(recent)
    # 偏离基线超过 3 个标准差即异常
    return abs(current - mean) > 3 * std
```

### 4.11 Bad Case 收集与回放

**收集**：用户点踩、人工审核标记、规则命中（超长、超时、敏感词），三者都自动落库整条 trace：

```python
class BadCaseCollector:
    def __init__(self, store):
        self.store = store

    async def collect(self, trace_id: str, reason: str, user_feedback: str = None):
        trace = await self.store.get_trace(trace_id)
        await self.store.save_bad_case({
            "trace_id": trace_id,
            "reason": reason,
            "user_feedback": user_feedback,
            "trace": trace,          # 整条 span 树一起存，回放才有完整素材
            "collected_at": now(),
        })
```

**回放**：

```python
async def replay(trace_id: str):
    trace = await store.get_trace(trace_id)
    # 按时间序重演每一步
    for span in trace["spans"]:
        print(f"Step: {span['name']}")
        print(f"  Input: {span['input']}")
        print(f"  Output: {span['output']}")
        print(f"  Duration: {span['duration']}ms")
        print(f"  Cost: ${span['cost']}")
```

**闭环**：trace 平台 → 坏例筛选 → 回归数据集 → 评估门禁（见 3.5、3.9）。「生产 trace 沉淀回归集」是 LLMOps 面试常见考点（来源：MortalJobs《LLMOps 面试指南》2026），也是 3.10 反馈闭环的数据来源。

```python
                step_span.set_attribute("prompt_version", PROMPT_VERSION)
                result = await execute_step(step)
```

### 6.4 指标埋点

```python
from prometheus_client import Counter, Histogram
import time

llm_calls = Counter("llm_calls_total", "LLM calls", ["model", "status"])
llm_latency = Histogram("llm_latency_seconds", "LLM latency", ["model"],
                        buckets=[0.1, 0.5, 1, 2, 5, 10, 30])
llm_tokens = Counter("llm_tokens_total", "LLM tokens", ["model", "type"])
llm_cost = Counter("llm_cost_dollars", "LLM cost", ["model", "tenant"])
agent_steps = Histogram("agent_steps", "Steps per task",
                        buckets=[1, 2, 3, 5, 10, 20, 50])

async def monitored_llm_call(model: str, messages: list, tenant: str = None):
    """所有 LLM 调用必须收口到这里：指标、token、成本一次记齐"""
    start = time.time()
    try:
        response = await llm.chat(model, messages)
        llm_calls.labels(model=model, status="success").inc()
        llm_tokens.labels(model=model, type="input").inc(response.usage.prompt_tokens)
        llm_tokens.labels(model=model, type="output").inc(response.usage.completion_tokens)
        cost = calculate_cost(model, response.usage)
        llm_cost.labels(model=model, tenant=tenant or "unknown").inc(cost)
        return response
    except Exception:
        llm_calls.labels(model=model, status="error").inc()
        raise
    finally:
        llm_latency.labels(model=model).observe(time.time() - start)
```

### 6.5 成本归因

```python
class CostAttributor:
    def __init__(self):
        self.data = defaultdict(lambda: defaultdict(float))

    def record(self, model: str, input_tokens: int, output_tokens: int, labels: dict):
        cost = calculate_cost(model, input_tokens, output_tokens)
        for dim, value in labels.items():
            self.data[dim][value] += cost
        return cost

    def report(self, dimension: str, top_k: int = 10) -> list:
        items = sorted(self.data[dimension].items(), key=lambda x: -x[1])
        return items[:top_k]

# 使用：一次调用同时落到多个维度
attributor = CostAttributor()
attributor.record("gpt-4o", 500, 200, {
    "user_id": "u1",
    "tenant_id": "company_a",
    "task_type": "refund",
    "model": "gpt-4o",
})

print(attributor.report("user_id"))    # 哪个用户花最多
print(attributor.report("task_type"))  # 哪类任务最贵
```

### 6.6 Trace 中间件（请求入口注入上下文）

```python
from fastapi import Request
import uuid

@app.middleware("http")
async def trace_middleware(request: Request, call_next):
    # 有上游 trace 就接上（上下文传播），没有就新开一条
    trace_id = request.headers.get("traceparent", "").split("-")[1] or str(uuid.uuid4())

    duration = time.time() - start

    response.headers["X-Trace-Id"] = trace_id   # 返回给前端，投诉时可凭它查轨迹

        "trace_id": trace_id,
        "method": request.method,
        "path": request.url.path,
        "duration_ms": duration * 1000,
        "status": response.status_code,
    }})
    return response
```

## 7. 案例

### 案例 A：P99 延迟突增定位

**场景**：某电商客服 Agent，某天 P99 从 3s 涨到 15s，工单变多。  
**排查（30 分钟，走完三支柱动线）**：

1. **Metrics**：面板发现 `tool_latency{tool="search_orders"}` 分位数整体上移，其余工具正常。
2. **Tracing**：抽 5 条慢 trace，span 树显示 `search_orders` 平均 8s，占整条请求的大头。
3. **Logging**：用慢 span 的 span_id 检索日志，工具日志里数据库查询慢的记录密集出现。
4. **根因**：订单量涨了 3 倍，查询走的字段没有索引，全表扫描。

**修复与效果**：补索引后当天 P99 回落到 3.2s。复盘时把「P99 突增」做成了告警规则（见 4.10），同类问题下次 5 分钟内触达。

### 案例 B：成本突增归因

**场景**：一家金融科技公司的合规问答 Agent，日成本从 $50 涨到 $200。  
**排查**：

1. **成本归因**：按模型维度看，gpt-4o 的成本涨了 5 倍，其他模型平稳。
2. **Trace**：抽样该模型的 trace，发现某类请求输入 token 单次 4 万以上，异常。
3. **Logging**：日志显示 RAG 检索返回 50 篇文档，全部塞进了提示词（Prompt）。
4. **根因**：上周改检索配置时 Top-K 被误设为 50。

**修复与效果**：Top-K 从 50 改回 5，单次输入 token 降到 5 千以内，一周后日成本回落到 $60 附近；同时加了「单请求成本 > $0.05 即告警」的规则兜底。

### 案例 C：Bad Case 回放定位

**场景**：用户投诉退款 Agent 把退款金额算错（示意：影响当天 12 笔同类请求）。  
**排查**：

1. 从用户反馈工单拿到 trace_id，回放完整轨迹：

```text
Step 1: search_orders      → 成功
Step 2: get_order_detail   → 成功
Step 3: initiate_refund    → 失败（金额计算错误：把运费重复计入）
Step 4: 未重试，直接向用户返回错误信息
```

2. 根因：Step 3 的金额计算逻辑错误；且失败后没有重试与降级。
3. 修复：修正计算逻辑，失败时改为重试一次再降级转人工。

**修复与效果**：从投诉到定位 20 分钟。该 trace 连同另外 4 条同类坏例进入回归集，下一版评估中 5 条全部通过（修复前 5 条全挂），同类错误没有再上线。

## 8. 常见坑

1. **不做 trace**。  
   出问题无法定位，只能靠猜。trace 是 Agent 的刚需，先有 trace 再谈其他。

2. **trace_id 不跨服务传递**。  
   分布式链路当场断裂。用标准 header（traceparent）传递；过消息队列时把上下文放进消息属性。

3. **日志非结构化**。  
   自由文本无法检索和聚合。用 JSON 格式 + 统一字段名。

4. **日志含敏感信息**。  
   PII、API Key 泄进日志系统，事后擦不干净。写入前必须脱敏（白名单 + 正则打码）。

5. **只记录成功，不记录失败**。  
   失败信息才是排查的关键素材。失败请求要完整记录，且错误 trace 全量保留（见 4.9）。

6. **不记录输入输出**。  
   出问题无法复现和归因。记录 input/output，但要注意隐私脱敏与超长截断。

7. **指标太多，没有重点**。  
   面板几十条曲线，没人看得过来。围绕黄金信号收敛：延迟、流量、错误、饱和（见 4.7）。

8. **告警太多，疲劳**。  
   告警被静音，真出事反而没人理。只对关键指标告警，P1/P2/P3 分级处理。

9. **不做成本归因**。  
   不知道钱花在哪，优化无从下手。按模型/用户/租户/任务类型出报表（见 6.5）。

10. **不做 Bad Case 回流**。  
    同样的错误反复出现、反复修。坏例自动沉淀回归集（见 4.11、3.5）。

11. **采样一刀切（全量或入口随机丢）**。  
    全量成本爆炸，头部采样丢错误样本。改用尾部采样：错误与慢请求全采，正常抽样，配 TTL。

12. **不做数据保留策略**。  
    trace 无限增长，存储爆炸。trace 设 TTL（如 30 天），坏例永久，指标只存聚合值。

13. **不区分环境**。  
    dev 和 prod 数据混在一起，分析结果不可信。所有遥测打上 env 标签。

14. **忽略多 Agent 的 trace**。  
    Agent 之间通信不传上下文，链路在协作处断裂。Agent 间消息携带 trace 上下文（见 2.8）。

15. **不做可视化**。  
    数据存了但没人看，等于没存。配 Dashboard：延迟分位数、错误率、成本曲线、Top 慢工具。

16. **prompt 与模型版本不落 span**。  
    坏例无法归因到某次改动，回归对比也无从谈起。版本号写进 span 属性与指标标签（见 3.9）。

## 9. 练习

1. 用 OpenTelemetry 给现有 Agent 埋点，跑一次多步任务并导出 trace；验收标准：span 树里能看到每个工具调用及其耗时。
2. 集成 Langfuse（或 LangSmith），对比它与「纯 OTel + Grafana」方案在查看一次完整请求时的体验差异，各列两条优劣势。
3. 实现结构化日志：JSON 输出含 trace_id、model、tokens、cost；用 jq 按工具名聚合出 P95 耗时。
4. 用 Prometheus 埋 5 个关键指标（QPS、P99、失败率、token、成本），配一条告警规则并人为触发它一次。
5. 实现成本归因器：按用户、租户、任务类型出 Top-10 报表，找出占比最高的那一项。
6. 分别实现头部采样与尾部采样各一版，对比错误 trace 捕获率（尾部采样应接近 100%）。
7. 实现 Bad Case 收集：用户点踩自动落库整条 trace，并写脚本回放打印每步的 input/output。
8. 用 Grafana 搭一个 Agent 监控面板：延迟分位数、错误率、成本曲线、Top 慢工具四块。
9. 故障演练：给某个工具注入 500ms 人工延迟，只看面板和 trace（不看代码）定位是哪个工具。
10. 设计数据保留策略：trace 30 天、坏例永久、指标 1 年，按日均请求量估算存储规模。

## 10. 小结

- 可观测性三支柱：**Logging + Metrics + Tracing**，配合动线是 Metrics 发现异常 → Tracing 定位 → Logging 看细节。
- Trace 数据模型：**trace → span → 子 span**，关键字段 trace_id、span_id、parent_span_id、model、tokens、cost、status、prompt_version。
- Span 类型覆盖请求、LLM、工具、检索、记忆、反思、规划、路由、审批九类；截至 2026 年按 **OTel gen_ai.\* 语义约定**埋点是防锁定的标准答案。
- 分布式追踪的核心是**上下文传播**：traceparent 跨服务、跨队列、跨 Agent 不断链。
- 还原完整轨迹三件套：**上下文传播 + 分层记录 + 可回放**；回放分「记录回放」与「重新执行」两种。
- 结构化日志：**JSON、含 trace_id/span_id、统一字段、PII 脱敏**。
- 指标按请求、LLM、工具、Agent、安全五层组织，收敛到黄金信号：**延迟（TTFT）、流量、错误、饱和（token 分列、单请求成本、缓存命中率）**。
- 成本归因六维度：**模型、用户、租户、任务类型、步骤、工具**——度量不清就没有优化。
- 采样与告警：**尾部采样（错误全采、正常抽样）**，告警 P1/P2/P3 分级响应，避免疲劳。
- Bad Case 闭环：**收集 → 回放 → 根因 → 修复 → 回归集**，让线上问题变成评估资产（见 3.5、3.10）。
- 核心原则：**不能度量就不能优化；不能追踪就不能定位。**
- 这些能力直接支撑：3.5 评估体系（坏例回流回归集）、3.9 CI/CD 与发布（回归门禁）、4.9 运维保障（值班告警与故障处置）。
