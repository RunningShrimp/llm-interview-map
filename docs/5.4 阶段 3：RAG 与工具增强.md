# 讲解 5.4 阶段 3：RAG 与工具增强

> 说明：前置是 5.3 阶段 2（工具调用、规划、记忆、执行循环、状态机），知识本身一律指路对应锚点（0.7、1.4、1.5、2.4、2.7、2.9），本篇不重复展开。  
> 5.x 是学习路径篇，不讲新知识，讲**阶段作战计划**：本篇把检索增强生成（RAG，Retrieval-Augmented Generation）、记忆与评估的知识组队成一条可执行顺序，带你分六个迭代做出阶段项目“知识库问答 Agent”，并给出里程碑自检表与卡点解法。  
> 这个阶段的核心是：**让 Agent 不只是“会调工具”，还能“基于私有知识回答”**——把 RAG、记忆、工具三者组合成一个有引用、可评估、带权限的知识型 Agent。验收通过后进入 5.5 阶段 4：AI 工程化。

---

## 1. 定位

学习路径的第 4 个阶段，属于“从通用工具到私有知识”的增强期。  
它解决一个核心问题：**当任务需要私有知识、历史记忆、多源检索时，如何让 Agent 稳定地基于事实回答，并给出可追溯的引用？**

对学习者，它是一份阶段作战计划：学什么、按什么顺序学、做什么项目、怎么验收。  
对知识地图，0.7 与 1.4、1.5、2.4、2.7、2.9 是“兵种”，5.4 负责把它们编成“作战序列”，再用一个项目把知识串起来。5.3 的产出是“能多步执行的单 Agent”，5.4 的产出是“有私有知识、有记忆、有引用、可评估的知识型 Agent”——它是 5.5 AI 工程化的直接前置，也支撑 5.6 多 Agent 与生产、5.7 综合项目。

本阶段口径（与知识地图一致）：

| 项 | 内容 |
|---|---|
| 前置 | 5.3 阶段 2：单 Agent 核心（工具调用、规划、记忆、执行循环） |
| 目标 | 私有知识 + 记忆 + 检索评估 |
| 项目 | 知识库问答 Agent |
| 里程碑 | 有引用、检索指标、坏例分析、权限过滤 |
| 后续 | 5.5 阶段 4：AI 工程化 |

## 2. 一句话定义

阶段 3 RAG 与工具增强，是掌握文档处理、切分、嵌入（Embedding）、混合检索、重排（Rerank）、引用生成、记忆读写、检索评估，并能独立构建一个有引用、可评估、带权限过滤的知识库问答 Agent 的工程实践阶段。

简化公式：

```text
阶段 3 = RAG 全流程 + 混合检索 + Rerank + 记忆增强 + 工具增强 + 检索评估
```

## 3. 为什么需要

阶段 2 的 Agent 只能使用工具返回的数据。  
但真实任务大量依赖私有知识：

- **企业知识库**：政策、流程、产品手册。
- **历史对话**：用户偏好、过往问题。
- **多源检索**：网页、文档、数据库。
- **长文档问答**：合同、报告、论文。
- **引用溯源**：答案必须可追溯。

没有 RAG 与记忆增强，会怎样：

- **幻觉严重**：LLM 不知道私有知识，硬编。
- **知识过时**：模型训练数据截止，新知识不知道。
- **无法溯源**：答案错了不知道来源。
- **多轮失忆**：用户偏好、历史信息丢失。
- **检索不准**：纯向量检索对编号、代码、专有名词不敏感。

“阶段 2 vs 阶段 3”对比：

| 维度 | 阶段 2：单 Agent（无 RAG） | 阶段 3：知识型 Agent（RAG + 记忆） |
|---|---|---|
| 知识来源 | 模型参数 + 公开工具返回 | 私有文档库 + 记忆 + 工具，按需取用 |
| 私有问题 | “报销上限是多少”只能编或拒答 | 检索命中政策原文，答案有出处 |
| 答案可追溯 | 错了无法定位错在哪句话 | 引用 [1][2] 对回来源文档 |
| 知识更新 | 受训练数据限制，更新靠换模型 | 文档重新入库即生效，分钟级 |
| 多轮体验 | “那退款呢？”这类追问检索失败 | 查询重写 + 记忆，追问接得住 |
| 质量判断 | 凭感觉说“好像不错” | Recall@5、MRR、忠实度，数字说话 |

两个类比，具体到场景：

```text
退休老专家 vs 配了图书馆的老专家：
  没有检索增强生成（RAG）的 LLM 像一位退休的老专家——知识停在退休那天（知识截止时间，
  Knowledge Cutoff），记不清的地方会下意识脑补（幻觉，Hallucination），而且说不出出处。
  加上 RAG，等于给他配了图书馆和检索员：答之前先翻书，答完标注页码（引用）。

裸机助理 vs 有档案柜的助理：
  阶段 2 的 Agent 是一个只会打电话问外界的助理（工具）；阶段 3 的助理身后有公司的
  档案柜（知识库）、记得你上次说过的话（记忆），每句结论都能指给你看出自哪份文件。
```

|---|---|---|---|---|

```text

   ↓
1.4 RAG
   ↓
1.5 记忆与上下文管理
   ↓
2.4 记忆 Memory
   ↓
2.7 单 Agent 架构模式
   ↓
2.9 Agent 评估与安全
   ↓
项目：知识库问答 Agent（§6 六个迭代）
```

五条原则：

- **先索引，后检索**：离线索引是基础，索引脏了检索再花哨也没用。
- **先召回，后精度**：先保证 Recall，再优化 Precision。
- **先纯向量，后混合**：理解基础再上混合检索与 Rerank。
- **先单轮，后多轮**：先做单轮问答，再加记忆和查询重写。
- **先评估，后调优**：没有 Recall@K，调切分是盲调。

### 4.5 里程碑自检表：本阶段学完能做什么

把里程碑“有引用、检索指标、坏例分析、权限过滤”拆成可逐项打分的自检表，全部达到合格口径才算通过：

| 自检项 | 合格口径 | 不合格信号 | 对应锚点 |
|---|---|---|---|
| 有引用 | 答案带 [1][2] 编号且能对回真实来源；编号经程序校验真实存在 | 编号是装饰、点开对不上原文，或整段答案无引用 | 1.4、4.2 |
| 检索指标 | 有至少 20 条人工标注的评估集，能算 Recall@5 与 MRR；调优前后在同一评估集上回归比较 | 没有评估集，调参全凭感觉 | 1.4、1.6 |
| 坏例分析 | 失败案例能归因到层（检索没召回 / 生成不忠实 / 引用错位），给出对策并回归验证 | 只记“答错了”，不知道错在哪层 | 4.2 |
| 权限过滤 | 过滤发生在检索层 where 条件；双租户交叉渗透测试互相查不到对方文档 | 只在提示词里写“不要回答无权限内容” | 1.7、4.2 |
| 混合检索与 Rerank | BM25 + 向量 + RRF 融合跑通，Rerank 后 Top-5 明显变准 | 只用纯向量，编号类查询全挂 | 1.4 |
| 多轮重写 | “那退款呢？”能重写为独立完整问题再检索 | 直接拿原句检索，多轮命中靠运气 | 1.4、4.2 |
| 记忆分工 | 短期记忆管对话窗口，长期记忆按 user_id 隔离检索 | 记忆与知识库混装，用户偏好当知识存 | 1.5、2.4 |

配套的 10 个关键问题（口头全部答清即达标）：

1. 切分策略怎么选？chunk_size 和 overlap 怎么定？
2. 嵌入模型怎么选？中文场景推荐哪些？
3. 余弦相似度、点积、欧氏距离怎么选？
4. 混合检索怎么融合 BM25 和向量分数？
5. Rerank 模型怎么选？值得加吗？
6. 如何评估检索质量？Recall@K 怎么算？
7. 多轮对话中查询重写怎么做？
8. 记忆和 RAG 有什么区别？
9. 如何做多租户权限过滤？
10. RAG 的常见失败模式有哪些？

**面试高频问法**：阶段 3 学完，以下两问应能给出共识口径的回答——“RAG 和微调（Fine-tuning）怎么选？”（知识需要频繁更新、答案要可溯源、面向私有语料的问题用 RAG；要改变模型行为、风格或领域语言用微调；工程上常先上 RAG、不够再微调，两者不互斥）；“多租户场景为什么不能靠提示词做权限控制？”（资料一旦进入上下文就已经泄露，还可能被提示注入（Prompt Injection）利用——过滤必须发生在检索层，提示词约束只能作兜底，机制见 4.2 与 1.7）。

### 4.6 高频卡点与解法速查

| 卡点 | 典型症状 | 第一时间解法 | 深入锚点 |
|---|---|---|---|
| 切分不当 | 检索结果半句话断在中间，或一大段全是噪音 | 512 字符 + 10%–15% overlap 起步，按评估集回归调整 | 1.4 |
| 编号类查询查不到 | 问“工单 A-1024”纯向量检索落空 | 上 BM25 混合检索 + RRF 融合 | 1.4 |
| Top-5 不准 | 召回了但不相关，答案被带偏 | 候选扩到 20，Rerank 后取 5 | 1.4 |
| 两侧嵌入模型不一致 | 查询与文档用不同模型，检索结果不着边际 | 同一模型编码两侧，禁混用 | 0.7 |
| 多轮追问检索失败 | “那退款呢？”查不到相关文档 | 查询重写为独立完整问题再检索 | 1.4、4.2 |
| 答案不忠实 | 资料里没有却硬答 | 提示词约束“只根据资料回答”+ 温度 0 | 1.4、1.6 |
| 越权泄露 | A 租户检索到 B 租户文档 | 检索层 where 过滤 + 双租户渗透测试 | 1.7、4.2 |
| 评估集缺失 | 调参前后无法比较，全凭印象 | 先建 20 条标注集，再谈调优 | 1.6、2.9 |
| 记忆与 RAG 混装 | 用户偏好被当知识条目入库 | 记忆按 user_id 隔离，知识按 tenant_id 隔离 | 1.5、2.4 |

## 6. 代码 / 工具

### 6.1 项目总览：知识库问答 Agent

项目目标：

- 加载企业文档（Markdown/PDF）
- 切分、嵌入、建索引
- 混合检索 + Rerank
- 多轮对话 + 查询重写

- 权限过滤

六个迭代，每步都可独立运行、独立验收：切分入库 → 检索生成 → 引用 → 检索指标 → 坏例分析 → 权限过滤与工具化集成。

### 6.2 迭代一：切分入库

先有干净的索引，后面一切检索质量都建立在这。元数据（来源、租户、权限）随切片一起入库——后面引用与权限过滤全靠它。

```python
# rag/indexer.py —— 加载、切分、嵌入、入库（含权限元数据）
from pathlib import Path

import chromadb
from langchain_text_splitter import RecursiveCharacterTextSplitter
from sentence_transformers import SentenceTransformer

class KnowledgeIndexer:
    def __init__(self):
        self.client = chromadb.PersistentClient(path="./chroma_db")
        self.collection = self.client.get_or_create_collection("knowledge")
        self.embedder = SentenceTransformer("BAAI/bge-m3")  # 多语种嵌入，本地推理
        # chunk_size 按字符计（中文一字一符），512 字符约合几百 token；口径写进配置，全库统一
        self.splitter = RecursiveCharacterTextSplitter(
            chunk_size=512,
            chunk_overlap=64,  # 约 12% 重叠，防止关键句被切断
            separators=["\n\n", "\n", "。", "！", "？", " ", ""],
        )

    def index_documents(self, docs_dir: str, tenant_id: str = "default") -> int:
        chunks = []
        for file in Path(docs_dir).rglob("*.md"):
            content = file.read_text(encoding="utf-8")
            for i, chunk in enumerate(self.splitter.split_text(content)):
                chunks.append({
                    "id": f"{file.stem}_{i}",
                    "content": chunk,
                    "metadata": {
                        "source": file.name,           # 引用溯源用
                        "tenant_id": tenant_id,        # 租户隔离的锚点
                        "permission": ["user", "admin"],  # 角色权限，检索层过滤用
                    },
                })

        if not chunks:
            return 0

        embeddings = self.embedder.encode([c["content"] for c in chunks]).tolist()
        self.collection.add(
            ids=[c["id"] for c in chunks],
            embeddings=embeddings,
            documents=[c["content"] for c in chunks],
            metadatas=[c["metadata"] for c in chunks],
        )
        return len(chunks)
```

验收：对一个 20 篇文档的目录跑 `index_documents()`，返回切片数在数百量级；抽查任意切片，元数据三字段齐全。

### 6.3 迭代二：检索与生成

先纯向量跑通“能回答”，再升级为混合检索 + Rerank。分两步走，每步都能独立看到效果。

第一步，纯向量检索：

```python
# rag/retriever.py 初版 —— 纯向量检索，先跑通
def vector_search(self, query: str, user: dict, top_k: int = 5) -> list:
    query_vec = self.embedder.encode([query]).tolist()
    results = self.collection.query(
        query_embeddings=query_vec,
        n_results=top_k,
        where={"tenant_id": user["tenant_id"]},  # 权限过滤在检索层，不在提示层
    )
    return [
        {"id": did, "content": doc, "metadata": meta}
        for did, doc, meta in zip(
            results["ids"][0], results["documents"][0], results["metadatas"][0]
        )
    ]
```

跑到编号类查询（“工单 A-1024”“GB/T 19001”）会发现纯向量大面积落空——这就是要上混合检索的理由。第二步，升级为完整版：

```python
# rag/retriever.py 完整版 —— 向量 + BM25 + RRF 融合 + Rerank
import jieba
from rank_bm25 import BM25Okapi
from sentence_transformers import CrossEncoder

class HybridRetriever:
    def __init__(self, collection, embedder):
        self.collection = collection
        self.embedder = embedder
        self.reranker = CrossEncoder("BAAI/bge-reranker-base")  # 重排模型
        self.bm25 = None
        self.documents = []
        self._doc_map = {}  # id → 文档条目，RRF 融合后回取内容用

    def build_bm25(self, docs: list) -> None:
        """离线构建 BM25 索引；docs 用索引时的同一批切片，保证两套检索语料一致。"""
        self.documents = docs
        self._doc_map = {d["id"]: d for d in docs}
        tokenized = [list(jieba.cut(d["content"])) for d in docs]
        self.bm25 = BM25Okapi(tokenized)

    def _allowed(self, doc: dict, user: dict) -> bool:
        """权限判定：租户匹配且角色在文档 permission 列表内；向量侧与 BM25 侧共用。"""
        meta = doc["metadata"]
        return (meta["tenant_id"] == user["tenant_id"]
                and any(r in meta["permission"] for r in user["roles"]))

    def search(self, query: str, user: dict, top_k: int = 5) -> list:
        # 1) 向量检索：语义召回，where 条件保证无权限文档根本不进候选
        query_vec = self.embedder.encode([query]).tolist()
        vec_results = self.collection.query(
            query_embeddings=query_vec,
            n_results=20,
            where={
                "$and": [
                    {"tenant_id": user["tenant_id"]},
                    {"permission": {"$in": user["roles"]}},
                ]
            },
        )

        # 2) BM25 检索：词法匹配，补齐编号、专有名词类查询
        bm25_scores = self.bm25.get_scores(list(jieba.cut(query)))
        bm25_rank = sorted(range(len(bm25_scores)), key=lambda i: -bm25_scores[i])
        # BM25 侧没有 where 条件可用，必须手动做同样的权限过滤，否则融合阶段就会漏
        bm25_top = [i for i in bm25_rank
                    if self._allowed(self.documents[i], user)][:20]

        # 3) RRF（Reciprocal Rank Fusion，倒数排名融合）：只看排名不看分数，
        #    天然免疫向量分数与 BM25 分数量纲不一致的问题；k=60 是常用常数
        scores = {}
        for rank, doc_id in enumerate(vec_results["ids"][0]):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (rank + 60)
        for rank, idx in enumerate(bm25_top):
            doc_id = self.documents[idx]["id"]
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (rank + 60)
        top_ids = sorted(scores, key=scores.get, reverse=True)[:20]

        # 4) Rerank：粗召回 20 条，交叉编码器精排出 top_k 条
        candidates = [{
            "id": did,
            "content": self._doc_map[did]["content"],
            "metadata": self._doc_map[did]["metadata"],
        } for did in top_ids]
        pairs = [(query, c["content"]) for c in candidates]
        rerank_scores = self.reranker.predict(pairs)
        ranked = sorted(zip(candidates, rerank_scores), key=lambda x: -x[1])
        return [c for c, _ in ranked[:top_k]]
```

### 6.4 迭代三：引用生成

迭代二结束时暴露的问题：答案是对的，但无法溯源——错在哪句话、出自哪份文档都不知道。本迭代把引用变成硬约束。

```python
# rag/pipeline.py 完整版 —— 引用约束 + 结构化来源 + 编号校验
import re

from llm import chat

RAG_PROMPT = """你是一个知识库问答助手。
只根据以下资料回答。如果资料中没有答案，说“资料中没有相关信息”。
回答时标注引用编号，如 [1][2]。

资料：
{context}

问题：{question}
"""

async def rag_answer(query: str, retriever, user: dict) -> dict:
    docs = retriever.search(query, user, top_k=5)
    context = "\n".join(f"[{i+1}] {d['content']}" for i, d in enumerate(docs))
    answer = await chat(
        [{"role": "user", "content": RAG_PROMPT.format(context=context, question=query)}],
        temperature=0,  # 事实问答用低温，保证稳定
    )
    return {
        "answer": answer,
        "sources": [{"id": d["id"], "source": d["metadata"]["source"]} for d in docs],
        "citations_ok": verify_citations(answer, docs),  # 拦住模型编造的 [6]
    }

def verify_citations(answer: str, docs: list) -> bool:
    """校验答案里的引用编号都能对回本次检索的资料，越界即不通过。"""
    cited = {int(n) for n in re.findall(r"\[(\d+)\]", answer)}
    return all(1 <= n <= len(docs) for n in cited)
```

验收：抽查 10 条回答，每条引用编号点开能对回原文对应段落；人为诱导模型输出 [6]（资料只有 5 条）时 `citations_ok` 为 False。

### 6.5 迭代四：检索指标

没有指标的调优是盲调。先建评估集（人工标注“问题 → 应命中文档 ID”），再算 Recall@5 与 MRR。

评估集格式（20 条起步，覆盖语义类、编号类、多轮改写类）：

```text
# eval/retrieval_eval.json —— 每条：问题 + 应命中的文档 ID（人工标注）
[
  {"query": "年假有几天？", "relevant_ids": ["hr_policy_12", "hr_policy_13"]},
  {"query": "工单 A-1024 的处理时限？", "relevant_ids": ["ops_sop_08"]}
]
```

评估脚本：

```python
# eval/run_eval.py —— 同一评估集回归：调参前后各跑一次，指标可比
import json

def eval_retrieval(retriever, user: dict) -> dict:
    with open("eval/retrieval_eval.json", encoding="utf-8") as f:
        eval_set = json.load(f)
    hits, rr_sum = 0, 0.0
    for case in eval_set:
        docs = retriever.search(case["query"], user, top_k=5)
        doc_ids = [d["id"] for d in docs]
        # Recall@5：相关文档至少一个进入前 5 即算命中
        if any(rid in doc_ids for rid in case["relevant_ids"]):
            hits += 1
        # MRR：第一个命中的相关文档的排名倒数
        for rank, did in enumerate(doc_ids, start=1):
            if did in case["relevant_ids"]:
                rr_sum += 1 / rank
                break
    metrics = {"recall@5": hits / len(eval_set), "mrr": rr_sum / len(eval_set)}
    print(f"Recall@5: {metrics['recall@5']:.2%}  MRR: {metrics['mrr']:.3f}")
    return metrics
```

验收：同一评估集上跑出基线；切换“纯向量 → 混合 → 混合 + Rerank”三档配置，Recall@5 逐档上升且留有记录。生成侧评估（忠实度、引用准确率）用 RAGAS 评估见 1.4 与 1.6，此处不重复。

### 6.6 迭代五：坏例分析

指标告诉你“有多少坏”，坏例（Bad Case）分析告诉你“为什么坏”。坏例归因表：

| 坏例症状 | 先查哪层 | 常见归因 | 对策 |
|---|---|---|---|
| 答非所问，引用也不相关 | 检索层 | 没召回：切分不当或纯向量盲区 | 混合检索、调切分、查询重写 |
| 引用相关，答案却在编 | 生成层 | 不忠实：忽略上下文 | 强化“只根据资料回答”约束、温度 0 |
| 答案对，但编号对不上原文 | 引用层 | 编号错位或模型编造编号 | 编号校验 + 结构化 sources |
| 多轮追问突然失灵 | 查询层 | 原句是“那退款呢”这类省略句 | 查询重写为独立完整问题 |

坏例闭环四步，每步都有落盘记录：

```text
收集：评估集跑挂的案例 + 使用中的点踩，追加记入 eval/bad_cases.jsonl
      每行一个坏例：{"query", "symptom", "layer", "cause", "fix", "regression"}
归因：按上表先查检索层，再查生成层——先检索后生成，先便宜后昂贵（优先级口径见 4.2）
修复：一次只改一处，改动写进配置可回滚
回归：修复后同一评估集重跑；坏例转为回归用例，防止下一次调优把旧病调回来
```

验收：产出至少 5 条带归因的坏例记录；其中 2 条完成“修复 → 回归通过”的完整闭环。

### 6.7 迭代六：权限过滤与工具化集成

权限过滤的铁律：**在检索层，不在提示层**。资料一旦进入上下文就已经泄露，还可能被提示注入利用——恶意文档可以指示模型复述隔壁租户的内容。所以过滤条件必须在向量库查询的 where 里（迭代二已实现），并用渗透测试验证：

多轮对话的钥匙是查询重写——用户追问时省略主语，直接拿原句检索必然失灵：

```python
# query_rewriter.py —— 借助对话历史，把省略句补全为独立完整的问题
from llm import chat

REWRITE_PROMPT = """根据对话历史，把用户最新问题重写为独立完整的问题。

历史：
{history}

最新问题：{question}

重写后的问题："""

async def rewrite_query(question: str, history: list) -> str:
    if not history:
        return question  # 首轮无需重写，省一次调用
    history_text = "\n".join(f"{m['role']}: {m['content']}" for m in history[-5:])
    response = await chat(
        [{"role": "user", "content": REWRITE_PROMPT.format(
            history=history_text, question=question)}],
        temperature=0,
    )
    return response.strip()
```

记忆分双通道——短期记忆管对话窗口，长期记忆按 user_id 隔离：

```python
# memory/short_term.py —— 滑动窗口（Sliding Window）：只留最近 max_turns 轮
from collections import deque

class ShortTermMemory:
    def __init__(self, max_turns: int = 10):
        self.history = deque(maxlen=max_turns * 2)  # 一轮 = user + assistant 两条

    def add(self, role: str, content: str):
        self.history.append({"role": role, "content": content})

    def get(self) -> list[dict]:
        return list(self.history)

# memory/long_term.py —— 检索式长期记忆：写入与召回都按 user_id 隔离
import uuid

import chromadb

class LongTermMemory:
    def __init__(self):
        self.collection = chromadb.Client().get_or_create_collection("memory")

    def add(self, text: str, user_id: str, memory_type: str = "fact"):
        self.collection.add(
            documents=[text],
            metadatas=[{"user_id": user_id, "type": memory_type}],
            ids=[str(uuid.uuid4())],
        )

    def retrieve(self, query: str, user_id: str, top_k: int = 3) -> list[str]:
        results = self.collection.query(
            query_texts=[query],
            n_results=top_k,
            where={"user_id": user_id},  # 只检索该用户自己的记忆
        )
        return results["documents"][0] if results["documents"] else []
```

最后把重写、检索、记忆、生成拼成完整 Agent：

```python
# agent.py —— 知识库问答主流程
from llm import chat
from rag.pipeline import RAG_PROMPT
from query_rewriter import rewrite_query

class KnowledgeAgent:
    def __init__(self, retriever, short_memory, long_memory):
        self.retriever = retriever
        self.short_memory = short_memory
        self.long_memory = long_memory

    async def run(self, query: str, user: dict) -> dict:
        # 1. 查询重写：把“那退款呢”补全为独立问题
        rewritten = await rewrite_query(query, self.short_memory.get())

        # 2. 检索：混合检索 + Rerank + 权限过滤
        docs = self.retriever.search(rewritten, user, top_k=5)

        # 3. 长期记忆召回：用户偏好、历史事实
        memories = self.long_memory.retrieve(rewritten, user["id"])

        # 4. 上下文组装：资料与记忆分区，互不混装
        context = "\n".join(f"[{i+1}] {d['content']}" for i, d in enumerate(docs))
        if memories:
            context += "\n\n相关记忆：\n" + "\n".join(f"- {m}" for m in memories)

        # 5. 生成：引用约束 + 低温
        answer = await chat([
            {"role": "system", "content": RAG_PROMPT},
            {"role": "user", "content": f"资料：\n{context}\n\n问题：{query}"},
        ], temperature=0)

        # 6. 更新短期记忆，供下一轮重写使用
        self.short_memory.add("user", query)
        self.short_memory.add("assistant", answer)

        return {
            "answer": answer,
            "sources": [d["id"] for d in docs],
            "rewritten_query": rewritten,
        }
```

验收：连续 3 轮追问（政策 → 那退款呢 → 时效呢），每轮返回的 `rewritten_query` 都是完整问题，且第 2、3 轮检索仍能命中相关文档。

```text
[ ] 能实现短期记忆
[ ] 能实现长期记忆

```

## 7. 案例

### 案例 A：企业知识库问答（从裸检索到可用管道）

**场景**：某电商内部约 1000 份文档（政策、流程、产品手册），员工日常问“报销上限”“年假天数”，学员以这套语料做毕业项目。

**做法**（按迭代四的指标驱动，每步在同一评估集上回归）：

```text
基线：纯向量检索                      Recall@5 ≈ 0.60，编号类问题大面积失败
第 1 步：BM25 混合 + RRF 融合          Recall@5 ≈ 0.74（编号类问题基本恢复）
第 2 步：Rerank 精排（候选 20 取 5）    Recall@5 ≈ 0.82，Top-5 明显变准
第 3 步：切分微调 + 查询重写            Recall@5 ≈ 0.90，多轮追问不再失灵
```

**示意数字效果**：50 条人工标注评估集上，Recall@5 从 0.60 提到 0.90；人工抽检 100 条回答，答案准确率从约 60% 提到约 85%，幻觉率（资料里没有却硬答）从约 15% 降到约 3%。关键复盘：前三步都没换生成模型——检索层每提升一分，生成层的上限就抬高一分。

### 案例 B：多轮 RAG 查询重写

**场景**：学员做多轮问答测试，第二轮开始检索大面积失灵。

**现场**：

```text
用户：退货政策是什么？
助手：签收后 7 天内可退。
用户：那退款呢？
```

**做法**：直接拿“那退款呢？”检索必然落空——它没有主语。用 §6.7 的重写器，借助上一轮历史补全为“退货后多久能收到退款？”，再检索即命中“退款时效”章节。

**示意数字效果**：20 条多轮追问的小评估集上，无重写命中 9 条（45%），加重写后命中 16 条（80%）；代价是每轮多一次低价模型调用，延迟约 +0.4 秒。结论：多轮场景下查询重写是必选项，不是优化项。

### 案例 C：权限过滤渗透测试

**场景**：知识库同时接入 A、B 两家公司（各约 200 份文档），验收时的红线问题：A 的员工能不能问到 B 的文档。

**做法**：按 §6.7 把过滤条件写进检索层 where（tenant_id + permission），再写渗透测试：两套账号各发 20 条查询，断言结果全部属于本租户。

```python
where={
    "$and": [
        {"tenant_id": user["tenant_id"]},
        {"permission": {"$in": user["roles"]}},
    ]
}
```

**示意数字效果**：检索层过滤版本，双租户交叉 40 次查询，越权泄露 0 次；对照版本只把“不要回答无权限内容”写进提示词，同一批查询泄露 5 次——资料进入了上下文就等于泄露。结论：提示词约束只能兜底，不能当边界。

## 8. 常见坑

1. **切分太大或太小**。对策：太大噪音多、太小语义碎；从 512 字符 + 10%–15% overlap 起步，按评估集回归调整，机制见 1.4。
2. **只用向量检索**。对策：编号、代码、专有名词是纯向量的盲区，上 BM25 混合 + RRF 融合。
3. **不加 Rerank**。对策：向量 Top-K 精度有限；候选扩到 20、Rerank 取 5，Top-5 精度显著提升。
4. **嵌入模型选错**。对策：中文场景截至 2026 年常用 BGE、GTE、Cohere embed 系列；拿自己的语料小样验证后再定。
5. **查询和文档用不同嵌入模型**。对策：两侧向量空间不一致，检索直接失效；同一个模型编码两侧，禁混用。
6. **不做查询重写**。对策：多轮对话里“那退款呢”检索必挂；按 §6.7 重写为独立完整问题。
7. **提示词不约束**。对策：不要求“只根据资料回答”，模型就自由发挥；加引用编号约束并配合温度 0。
8. **不标注引用**。对策：答案不可追溯；输出 [1][2] 加 sources 列表，再用编号校验拦住编造。
9. **不做权限过滤**。对策：多租户场景直接泄露；过滤写在检索层 where 条件，加渗透测试验收。
10. **不评估检索**。对策：不知道是检索问题还是生成问题，调参全凭感觉；先建 20 条标注集，Recall@5 起步。
11. **Top-K 太大**。对策：上下文噪音多、成本高；5 条起步，配合 Rerank 使用。
12. **不更新索引**。对策：知识库变了检索还是旧内容；按文件修改时间增量入库，做法见 4.2。
13. **忽略元数据**。对策：来源、权限、时间都要随切片入库，否则引用溯源与权限过滤无从谈起。
14. **把 RAG 当万能**。对策：RAG 解决知识问题，不解决计算与实时数据，那两类交给工具（5.3 的能力）。
15. **记忆和 RAG 混用**。对策：记忆是用户/会话相关的，RAG 是知识相关的；分别按 user_id 与 tenant_id 隔离。

## 10. 小结

- 阶段 3 = **RAG 全流程 + 混合检索 + Rerank + 记忆增强 + 工具增强 + 检索评估**，对应知识地图 0.7、1.4、1.5、2.4、2.7、2.9，原理细节一律回 1.4 与 4.2。
- 组队顺序：**0.7 → 1.4 → 1.5 → 2.4 → 2.7 → 2.9**——先索引后检索，先召回后精度，先纯向量后混合，先单轮后多轮，先评估后调优。
- 里程碑口径：**有引用、检索指标、坏例分析、权限过滤**，逐项对照 §4.5 自检表打分，不合格回锚点补课。
- 最小项目：**知识库问答 Agent**，按六个迭代交付——切分入库、检索生成、引用、检索指标、坏例分析、权限过滤与工具化集成。
- 评估纪律：**没有评估集的调优是盲调**——指标告诉你有多少坏，坏例归因告诉你为什么坏，修复必须回归。
- 权限纪律：**过滤在检索层，不在提示层**——资料进入上下文即泄露，提示词约束只能兜底。
- 高频卡点集中在**切分、纯向量盲区、多轮失灵、越权泄露、无评估**五类，解法见 §4.6 速查表。
- 面试共识口径：RAG 与微调不互斥（知识更新与溯源用 RAG，行为与风格用微调）；多租户权限靠检索层过滤。
- 时间预算：有阶段 2 基础 **3–4 周**；生产化深度（增量更新、联合评估体系）在 4.2 与 3 层展开，本阶段不贪多。
- 这些能力直接支撑：**5.5 阶段 4：AI 工程化**（可观测、评估、部署、CI/CD、成本控制）。
