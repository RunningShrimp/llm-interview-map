# 讲解 2.1 Agent 定义与范式

> 说明：前置 1.3（结构化输出与 Function Calling）与 1.5（记忆与上下文管理）已经备好「工具调用」与「记忆」两块积木，从 2.1 起正式进入 Agent 核心层。  
> 本篇是全层总纲，回答三个问题：**Agent 是什么、Agent 与固定工作流的边界在哪、主流范式怎么选**。  
> 各组件的细节分散在 2.2–2.6 展开，多 Agent 与评估在 2.8、2.9；本篇只建立全局心智模型。

## 1. 定位

Agent 核心层第 1 个知识点，也是 2.2–2.9 全部知识点共用的「总纲」。它解决两个根本问题：

- **Agent 由什么组成**：给出公认的拆解方式（五要素），后续每个知识点各领走一块。
- **Agent 与固定工作流（Workflow）的边界在哪**：什么时候该用工作流，什么时候才值得上 Agent——这是本篇的关键问题，§4.3 用四维判断表集中回答。

前置：1.3（工具调用的机制基础）、1.5（记忆与上下文管理）。  
后续：2.2–2.9 全部知识点都以本篇为地基；3.3（编排框架与运行时）是它的工程化延伸。

## 2. 一句话定义

Agent 是一个以 LLM 为决策核心，能够感知环境、规划行动、调用工具、维护记忆、循环执行，直到完成目标的智能系统。

简化公式：

```text
Agent = LLM（大脑） + Tools（手脚） + Memory（记忆） + Loop（循环） + Goal（目标）
```

两个权威口径可以佐证这个公式：

- Hugging Face《AI Agents Course》（2025）：Agent 是能对环境进行推理与规划、并采取行动影响环境的 LLM——对应公式里的「大脑 + 循环」。
- Anthropic《Building Effective Agents》（2024）：Agent 是由模型动态决定自身流程与工具使用的系统——对应公式里的「谁来决定下一步」。

判断一个系统是不是 Agent，只看一条判据：**下一步做什么，是代码写死的，还是模型在运行时自己决定的**。

## 3. 为什么需要

固定工作流（Workflow）能覆盖大量场景：

```text
用户输入 → 分类 → 检索 → 生成 → 输出
```

但以下场景它力不从心，每条的本质都是「下一步说不死」：

- **步骤不固定**：不知道要几步才能完成 → 代码无法预写路径。
- **需要动态决策**：下一步做什么取决于上一步结果 → 分支组合爆炸。
- **需要外部交互**：查数据库、调 API、操作网页 → 单次生成无法闭环。
- **需要错误恢复**：失败了要换方法重试 → 预定义流程只会硬失败。
- **目标模糊**：用户说「帮我处理一下这个」→ 需要自己拆解成子目标。

按任务形态对照（数量为示意性量级）：

| 任务 | 步骤特征 | 推荐形态 |
|---|---|---|
| 情感分类 | 单步、无外部交互 | 工作流（上 Agent 属过度设计） |
| 文档摘要 | 单步、输入固定 | 工作流 |
| RAG 问答 | 基本固定：检索后生成 | 工作流为主，可局部 Agent 化检索 |
| 多步数据分析 | 步数取决于中间发现 | Agent |
| 网页操作 | 页面环境随时变化 | Agent |
| 复杂客服 | 意图多样、需多步验证 | 混合：简单走工作流，复杂走 Agent |
| 研究助手 | 目标开放、多源整合 | Agent |

**类比 1（跟团游 vs 包车老司机）**：跟团游是工作流——行程表提前排好，便宜、准点、可预期，但景点临时关闭只能干等；包车配一位老司机是 Agent——他根据实时路况、天气和你的体力临时改路线，代价是按小时计费，且出发前你拿不到精确路线。

**核心判断**（§4.3 展开成四维）：

> **步骤固定 → 工作流；步骤动态 → Agent。**

## 4. 核心原理

### 4.1 三分谱系：Chatbot / Workflow / Agent

用「谁决定下一步」这一条判据，可以把 LLM 应用排成一个谱系：

| 形态 | 谁决定下一步 | 反馈闭环 | 典型例子 |
|---|---|---|---|
| Chatbot | 无「下一步」概念，一问一答 | 无 | 裸聊天的 LLM、话术型客服机器人 |
| Workflow（工作流） | 代码预定义路径 | 固定的（如检索结果固定喂给生成） | 固定管道 RAG、分类到生成管道 |
| Agent | 模型在运行时动态决定 | 有：观察结果影响下一步 | 工具调用循环、自主研究助手 |

边界讨论：**检索增强生成（RAG）+ Chat 算不算 Agent？** 不算。管道里「先检索再生成」是代码写死的，模型没有决定权；只有当模型能自己决定「要不要检索、检索什么、检索完要不要再搜一次」时，才构成 Agent 化。

**面试高频问法**：「什么是 AI Agent？和普通 Chatbot 有什么区别？」——共识口径三段作答：① 先给定义（以 LLM 为决策核心，配工具、记忆、循环，朝目标推进）；② 再讲区别在两点——能否使用工具改变外部状态、能否根据反馈多步推进；③ 举一个例子收尾：Chatbot 只能「说」，Agent 能「做」——查库、下单、改文件。追问「Chatbot 加上插件是不是就变成 Agent」：若模型能自主决定何时调用插件并基于结果继续，就是 Agent 雏形；若插件由代码触发，仍是工作流。

### 4.2 Agent 的五个核心组件（导论）

五要素：Goal、LLM、Planning、Tools、Memory，由 Loop 串成整体（结构图见 §5）。本篇只给每个组件一句定位，细节全部后置，避免与后续章节重复：

| 组件 | 一句话职责 | 深入章节 |
|---|---|---|
| LLM | 决策核心：理解目标、推理、决定下一步 | 0.5 LLM 基础、1.1 API 与选型 |
| Goal | 目标定义与终止条件：什么时候算完成 | 本篇 §4.5、2.5 |
| Planning（规划） | 把模糊目标拆成步骤，必要时重规划 | 2.2 |
| Tools（工具） | 与外部世界交互的手脚：搜索、代码、API | 2.3（机制基础见 1.3） |
| Memory（记忆） | 状态与历史管理：跨步、跨会话 | 2.4（机制基础见 1.5） |
| Loop（循环） | 观察 → 决策 → 行动 → 更新 → 终止 | 2.5 |
| Reflection（反思，可选） | 执行后自我评估与修正 | 2.6 |

**类比 2（入职第一周的新员工）**：Agent 就像这位新员工——Goal 是拿到的任务单，LLM 是理解与推理能力，Tools 是公司配的电脑和系统权限，Memory 是他的笔记本，Loop 是「干一步、看结果、再干下一步」的工作节奏，Reflection 是每天下班前的十分钟复盘。

### 4.3 Agent 与工作流的边界（关键问题的正面回答）

先给全维度对比：

| 维度 | 固定工作流 | Agent |
|---|---|---|
| 控制流归属 | 代码写死 | 模型运行时决定 |
| 执行路径 | 可预先穷举 | 动态生成，跑之前不知道 |
| 可预测性 | 高 | 低（同一输入可能得到不同轨迹） |
| 调试方式 | 打断点、看日志 | 需要执行轨迹（trajectory）回放 |
| 成本 | 低，1–3 次 LLM 调用 | 高，token 常为工作流的 5–20 倍（示意量级） |
| 延迟 | 秒级 | 数十秒到分钟级 |
| 典型失败 | 单步失败，局部重跑即可 | 死循环、跑偏、成本爆炸 |
| 适用 | 分类、抽取、摘要、固定 RAG | 多步任务、动态环境、需要纠错 |

再给**四维判断表**——判断「该不该上 Agent」，逐维对照：

| 判断维度 | 偏向工作流 | 偏向 Agent |
|---|---|---|
| 确定性程度 | 步骤与顺序可提前穷举、写进代码 | 下一步依赖中间结果，无法预写 |
| 环境动态性 | 输入输出封闭，环境不变 | 需与外部系统交互，环境随时变（网页、实时数据） |
| 成本容错 | 预算与延迟敏感，多花一个量级 token 不可接受 | 完成任务的价值显著覆盖多步成本 |
| 可控性要求 | 强合规，每步都要可审计复现 | 允许一定探索，用护栏 + 人工审批兜底 |

**判定规则**：四维全偏左 → 工作流；全偏右 → Agent；中间态 → 混合架构。

**混合模式（生产系统的常态）**：

```text
外层工作流（路由、护栏、审计） + 内层 Agent（动态子任务）
```

客服例子：

```text
用户输入 → 意图分类（工作流）
    ├─ 简单问题 → 固定 RAG（工作流）
    ├─ 中等复杂 → 单 Agent 处理（多步工具验证）
    └─ 复杂投诉 → 多 Agent 协作（安抚 + 解决 + 升级）
```

**业界共识**：

> **能用工作流解决的，不要用 Agent。**  
> Anthropic《Building Effective Agents》（2024）主张从最简单的方案开始、仅在需要时逐步增加自主性；LangChain 官方博客（2025）在多 Agent 选型上持同样立场。Agent 是用复杂度和不确定性换灵活性，只在灵活性真正产生业务价值时引入。

**面试高频问法**：「你们的场景为什么用工作流（或 Agent）？」——直接套四维表逐项作答：先说确定性程度（步骤能否穷举），再说环境动态性（要不要与外部系统交互），然后算成本账（token 与延迟差一个量级），最后讲可控性（合规与审计要求）。面试官要的不是背定义，而是这套决策框架。

### 4.4 Agent 的自主性分级：反应式 / 规划式 / 反思式

按自主性（与成本）递增排序，Agent 有一个公认的分级谱系：

| 级别 | 形态 | 决策方式 | 代表范式 | 成本量级（示意） |
|---|---|---|---|---|
| L0 | 固定工作流 | 代码预定义路径 | DAG 编排 | 1× |
| L1 | 反应式（Reactive） | 每步根据观察即时决策，无全局计划 | ReAct | 3–10× |
| L2 | 规划式（Deliberative） | 先全局规划再执行，必要时重规划 | Plan-and-Execute、ReWOO | 5–15× |
| L3 | 反思式（Reflective） | 执行后自我评估，教训沉淀进记忆再重试 | Reflexion | 10–30× |
| L4 | 搜索式 | 多分支生成 + 评估 + 搜索回传，取最优路径 | ToT、LATS | 20–100× |
| L5 | 多 Agent 系统 | 多角色分工、通信、汇总 | AutoGen、CrewAI、MetaGPT | 更高，叠加协调开销 |

三级主干正好对应三类能力缺口：反应式缺全局观；规划式补上全局观但缺纠错；反思式补上纠错但仍在单路径上打转；L4 的搜索式用「多路径并行 + 评估择优」补掉最后一个缺口。注意级别不是越高越好，而是**按任务难度付费**——任务只有 L1 的复杂度却上 L3/L4，多付的成本不会变成收益。

### 4.5 Agent 的核心循环

所有 Agent 的本质都是这个循环：

```text
while not done:
    1. 观察当前状态（Observation）
    2. 思考下一步（Thought）
    3. 选择行动（Action）
    4. 执行行动（Execute）
    5. 获取结果（Result）
    6. 更新状态与记忆（Update）
    7. 判断是否完成（Check）
```

这就是 **ReAct 循环**的通用形式。循环的状态管理、终止条件、中断恢复是 2.5 的主题，此处只立骨架。

### 4.6 主流范式

**范式 1：ReAct（Reason + Act，2022）**

```text
Thought → Action → Observation → Thought → ... → Answer
```

- 边想边做，单步最灵活
- 每步都调 LLM，成本随步数线性增长
- 缺全局计划，容易短视与死循环
- 代表：ReAct 论文、LangChain Agent、各大模型的工具调用循环

**范式 2：Plan-and-Execute（Plan-and-Solve，2023）**

```text
Plan（一次性规划）→ Execute（逐步执行）→ Replan（按需重规划）
```

- 先规划再执行，结构清晰、无依赖步骤可并行
- 解决长任务的跑偏与上下文膨胀
- 规划可能过时，重规划有额外成本
- 代表：Plan-and-Solve 论文、LLMCompiler、ReWOO（规划阶段不看观察结果、省 token，详见 2.2）

**范式 3：Reflexion（2023）**

```text
执行 → 评估 → 反思（生成语言化教训）→ 存入记忆 → 带着经验重试
```

- 自我批评，从错误中学习
- 与「简单重试」的区别：教训沉淀为文本经验，影响下一轮行为
- 多轮执行，成本高
- 代表：Reflexion 论文（机制详见 2.6）

**范式 4：ToT 与 LATS（搜索式，2023）**

```text
ToT：生成多个候选思路 → 评估 → 选最优 → 继续展开（树状搜索）
LATS：把 ReAct 轨迹整体当作搜索节点，蒙特卡洛树搜索（MCTS）+ 反思反馈打分
```

- ToT 在「思考空间」里搜索；LATS 把 ReAct、规划、反思统一进一个搜索框架
- 适合复杂推理与可离线的慢思考
- 成本极高：每步多分支乘以多轮模拟
- 代表：ToT 论文、LATS（Language Agent Tree Search）论文

**范式 5：Function Calling Agent（工具调用，工程落地主流）**

```text
LLM 决定调用工具 → 运行时执行 → 结果返回 → 继续（或结束）
```

- 以工具调用为核心机制，是 1.3 的直接延伸
- 结构最简单、稳定性最高，生产系统的默认形态
- 代表：OpenAI Function Calling、MCP 工具接入协议（见 2.3、3.3）

**范式 6：Multi-Agent（多 Agent 协作）**

```text
多个 Agent 分工 → 通信 → 汇总
```

- 角色分工，适合超复杂任务与可并行的子任务
- 协调成本高，错误会跨 Agent 放大
- 代表：AutoGen、CrewAI、MetaGPT（详见 2.8）

### 4.7 四范式对比与选型

核心四范式的机制对比：

| 范式 | 一句话机制 | 解决什么问题 | 主要代价 | 适用 |
|---|---|---|---|---|
| ReAct | 边想边做，逐步反馈 | 单步决策灵活性 | 无全局观、易死循环 | 动态环境、工具密集 |
| Plan-and-Execute | 先全局规划，按需重规划 | 长任务跑偏、上下文膨胀 | 规划过时、重规划成本 | 多步任务、已知流程 |
| Reflexion | 评估后沉淀教训再重试 | 重复犯同类错误 | 多轮执行，token 翻倍 | 高价值任务、需纠错 |
| LATS | 树搜索 + 反思，多路径择优 | 单路径困在局部最优 | 成本最高 | 复杂推理、可慢思考 |

全谱系总表（含工作流与工程形态）：

| 范式 | 适用 | 成本 | 复杂度 | 稳定性 |
|---|---|---|---|---|
| 固定工作流 | 步骤明确 | 低 | 低 | 高 |
| Function Calling Agent | 工具调用 | 中 | 低 | 高 |
| ReAct | 动态决策 | 中 | 中 | 中 |
| Plan-Execute | 多步长任务 | 中高 | 中 | 中高 |
| Reflexion | 需要纠错 | 高 | 中 | 中 |
| ToT / LATS | 复杂推理 | 极高 | 高 | 中 |
| Multi-Agent | 复杂协作 | 高 | 高 | 低 |

选型阶梯：

```text
简单任务 → 工作流
中等任务 → Function Calling Agent
长链条任务 → Plan-Execute
高价值需纠错 → Reflexion（或作为子模块挂进其他范式）
复杂推理可慢思考 → ToT / LATS
复杂协作可并行 → Multi-Agent（先单后多，见 2.8）
```

### 4.8 Agent 的能力边界

**Agent 擅长**：

- 多步任务：拆解、执行、汇总
- 动态决策：根据中间结果调整路线
- 工具调用：把动作外包给确定性组件
- 错误恢复：失败后换路径重试
- 信息整合：多来源、多格式的汇聚

**Agent 不擅长**（括号内为工程对策）：

- 精确计算（交给代码工具）
- 实时信息（交给搜索、数据库工具）
- 长期一致性（交给外部记忆，见 2.4）
- 高可靠性（交给验证器 + 工作流兜底）
- 低成本（token 常为工作流的 5–20 倍，示意量级）

**关键认知**：

> Agent 不是万能的，它是**用 LLM 的不确定性换取灵活性**。  
> 需要确定性的地方，用工作流 + 工具 + 验证器，而不是更大的自主权。

### 4.9 Agent 的失败模式

| 失败 | 原因 | 解法 |
|---|---|---|
| 死循环 | 没有终止条件 | 最大步数 + 循环检测（见 2.5） |
| 跑偏 | 目标不清晰 | 明确目标 + 中间校验点 |
| 工具选错 | 工具描述不清 | 优化工具定义（见 2.3） |
| 幻觉工具 | 工具列表不明确 | 白名单 + 参数校验 |
| 成本爆炸 | 循环太多、无预算 | 步数限制 + 预算熔断 |
| 状态丢失 | 记忆没管理 | 结构化状态 + 持久化（见 2.4、2.5） |
| 无法恢复 | 没有检查点 | 状态持久化 + 断点续行 |
| 越权 | 权限没控制 | 工具权限分级 + 人工审批 |

### 4.10 Agent 的评估维度

| 维度 | 指标 |
|---|---|
| 任务成功率 | 完成目标的比例 |
| 步数效率 | 平均执行步数（同等质量下越少越好） |
| 工具调用准确率 | 工具名、参数的正确率 |
| 成本 | 每次任务 token 消耗 |
| 延迟 | 端到端时间 |
| 轨迹质量 | 中间步骤是否合理 |
| 安全性 | 是否越权、泄露 |
| 鲁棒性 | 异常输入、工具故障下的表现 |

一个必须建立的成本直觉——**复合失败率**：单步成功率 95% 的组件，连续 8 步的端到端成功率只剩约 66%（0.95 的 8 次方，社区评估综述常见的经验估算）。Agent 是链式系统，评估必须看轨迹级指标，只看最终答案会漏掉工具调用错误。2.9 详细展开。

### 4.11 Agent 定义口径的演进（截至 2026 年）

「什么是 Agent」这个定义本身经历过一次收敛：

```text
2023：AutoGPT、BabyAGI 开源热潮 →「全自主长任务」激进口径，落地遇冷（死循环、成本失控）
2024：Anthropic《Building Effective Agents》→ 工作流 / Agent 二分，「从简单开始」成为工程共识
2025：Hugging Face AI Agents Course 等教学体系 → 定义收敛为「LLM + 工具 + 循环」；MCP、OpenAI Agents SDK 等生态成型
2026：定义之争基本平息，重心转向评估（轨迹级）、安全（注入与越权）、Agent 互连协议
```

趋势观察：Agent 间协作协议——2025 年由 Google 联合多家厂商发起、后交由 Linux 基金会治理的 A2A 协议，以及国内社区推进的 ANP——截至 2026 年仍在快速演进，采用度未核实，细节见 2.8。协议生态不改变本篇的五要素拆解与边界判断。

## 6. 代码 / 工具

### 6.1 最小 Agent 骨架

```python
import json
from openai import AsyncOpenAI

client = AsyncOpenAI(api_key="YOUR_KEY")  # key 与模型按环境替换

# 工具 = 描述（给 LLM 看）+ 实现（给运行时调）
TOOL_SPECS = [search_docs_spec, calculate_spec]  # OpenAI tools 格式的 JSON Schema
TOOL_FUNCS = {"search_docs": search_docs, "calculate": calculate}

async def minimal_agent(goal: str, max_steps: int = 10) -> str:
    messages = [
        {"role": "system", "content": "你是一个 Agent，通过调用工具完成目标，完成后直接给出最终答案。"},
        {"role": "user", "content": f"目标：{goal}"},  # Goal
    ]

    for step in range(max_steps):  # Loop + 终止条件：最大步数
        response = await client.chat.completions.create(  # LLM 决策核心
            model="gpt-4o-mini",  # 示例模型，按需替换
            messages=messages,
            tools=TOOL_SPECS,
            tool_choice="auto",
            temperature=0,
        )
        msg = response.choices[0].message

        # 模型不再调用工具 = 认为任务完成，返回最终答案
        if not msg.tool_calls:
            return msg.content

        messages.append(msg)

        # 执行模型选择的工具，把结果喂回去（反馈闭环）
        for tc in msg.tool_calls:
            args = json.loads(tc.function.arguments)
            result = await TOOL_FUNCS[tc.function.name](**args)
            messages.append({
                "role": "tool",
                "tool_call_id": tc.id,
                "content": json.dumps(result, ensure_ascii=False),
            })

    return "达到最大步数限制，任务未完成。"
```

30 行代码就能看到全部五要素：goal 参数、LLM 决策、工具执行、messages 充当最简记忆、for 循环加 max_steps 构成 Loop 与终止条件。

### 6.2 工作流 vs Agent：同任务两种写法

```python
# 工作流：步骤由代码写死，便宜、可预测
async def workflow_qa(query: str) -> str:
    docs = await retrieve(query)          # 步骤 1：检索
    answer = await generate(query, docs)  # 步骤 2：生成
    return answer

# Agent：步骤由模型在运行时决定，灵活、更贵
async def agent_qa(query: str) -> str:
    return await minimal_agent(query)  # 模型自己决定查不查、查什么、查几次
```

### 6.3 Plan-and-Execute 简化实现

```python
async def plan_and_execute(goal: str) -> str:
    # 1. 规划：一次性生成计划
    plan_prompt = f"""把以下目标分解为 3-5 个步骤，输出 JSON 数组：
目标：{goal}
"""
    plan_response = await client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": plan_prompt}],
        response_format={"type": "json_object"},
        temperature=0,
    )
    plan = json.loads(plan_response.choices[0].message.content)["steps"]

    # 2. 执行：逐步执行，携带前序结果
    results = []
    for step in plan:
        result = await execute_step(step, context=results)  # 示意函数
        results.append({"step": step, "result": result})

    # 3. 汇总
    summary = await summarize(goal, results)  # 示意函数
    return summary
```

### 6.4 用 LangGraph 构建 Agent（图编排）

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict

class AgentState(TypedDict):
    messages: list
    steps: int

def should_continue(state: AgentState) -> str:
    if state["steps"] >= 10:              # 终止条件写进图
        return "end"
    last = state["messages"][-1]
    if hasattr(last, "tool_calls") and last.tool_calls:
        return "tools"
    return "end"

# 构建图：节点是动作，边是控制流
graph = StateGraph(AgentState)
graph.add_node("agent", call_model)       # LLM 决策节点
graph.add_node("tools", execute_tools)    # 工具执行节点
graph.set_entry_point("agent")
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", "end": END})
graph.add_edge("tools", "agent")          # 工具结果回到 LLM，形成循环

app = graph.compile()
```

截至 2026 年，LangGraph、OpenAI Agents SDK、CrewAI、AutoGen 仍是主流编排选择，但该生态变化快，选型前先做评估（见 3.3）。

## 7. 案例

### 案例 A：什么时候不用 Agent（反例）

**场景**：某电商要从用户评论中提取情感标签。

**错误做法**：上 Agent，让 LLM 每条评论先决定「要不要调工具、调哪个」。

**正确做法**：固定工作流，一次 LLM 调用完成。

```python
def classify(review: str) -> str:
    return call_llm(f"分类为正面/负面/中性：{review}")
```

**示意数字效果**：工作流版单条约 600 token、p50 延迟 0.8 秒；Agent 版平均 3 步、约 4000 token、延迟 4 秒以上，准确率没有提升，反而引入「选错工具」这个新错误面。**结论**：简单任务用工作流，成本低、延迟低、稳定。

### 案例 B：多步数据分析 Agent

**场景**：运营丢来一份原始销售数据，只说「分析下滑原因」——拆什么维度、看哪个月，事先不知道。

**做法**：上 Agent，让它根据中间发现决定下一步：

```text
Step 1: 读取 CSV 文件
Step 2: 计算各月销售额
Step 3: 发现 3 月环比下降 30% → 决定按地区拆
Step 4: 按地区拆分，发现华东区贡献了大部分降幅 → 决定按产品拆
Step 5: 按产品拆分，发现 A 产品销量暴跌
Step 6: 生成分析报告（含数据引用）
```

**示意数字效果**：6 步、约 13 次工具调用、2 次参数报错后自动修正，全程约 2 分钟出报告；若写成固定脚本，需要预先枚举所有拆分维度和分支，维护成本远高于让模型按发现动态拆。**为什么用 Agent**：步骤不固定，取决于中间发现——这正是 §4.3 四维里「确定性程度」偏 Agent 的典型。

### 案例 C：客服混合架构

**场景**：一家金融科技公司的在线客服，既要省钱又要兜住复杂case。

**做法**：外层工作流做意图分类与路由，内层按复杂度分流：

```text
用户输入
   ↓
意图分类（工作流）
   ├─ 查订单 → 固定 RAG（工作流）
   ├─ 退款 → 单 Agent（需多步验证：查订单、核对规则、执行）
   └─ 投诉 → 多 Agent（情绪安抚 + 问题解决 + 升级判断）
```

**示意数字效果**：上线后约 70% 流量走固定 RAG（单次约 1000 token、2 秒内返回），20% 走单 Agent（平均 6 步），10% 走多 Agent；整体成本比「全部走 Agent」的方案低约一个量级，复杂case 解决率反而更高。**结论**：生产系统通常是**工作流 + Agent 混合**，不是纯 Agent。

## 8. 常见坑

1. **过度 Agent 化**。  
   简单任务用工作流就够；Agent 平白增加成本与不确定性，先过 §4.3 四维表再决定。

2. **没有终止条件**。  
   Agent 会无限循环。必须设最大步数、超时、预算上限三重熔断。

3. **目标不清晰**。  
   Agent 不知道「做到什么程度算完」，必然跑偏。目标里写清交付物与完成判据。

4. **工具描述不清**。  
   Agent 选错工具或不知道何时用。把工具描述当提示词（Prompt）认真写，见 2.3。

5. **没有状态管理**。  
   多步任务中间结果丢失，Agent 重复劳动。用结构化状态 + 显式记忆，见 2.4、2.5。

6. **不做错误恢复**。  
   工具一失败就卡死。区分可重试与不可重试错误，配重试与替代工具。

7. **忽略成本**。  
   Agent 多步调用，token 消耗常是工作流的 5–20 倍（示意量级）。上线前算单位任务成本，设预算熔断。

8. **不记录轨迹**。  
   出问题无法调试，不知道哪一步错。每步记录 thought、action、observation。

9. **没有人工介入点**。  
   高风险操作（退款、删数据、对外发送）必须人工审批后再执行。

10. **把 Agent 当万能**。  
    Agent 不擅长精确计算、实时信息、高可靠性任务，这些交给工具与验证器。

11. **忽视评估**。  
    「看起来能跑」不等于可靠。成功率、步数、成本都要量化，先建基线再迭代，见 2.9。

12. **过早多 Agent**。  
    单 Agent 能解决的不要上多 Agent，协调成本与错误放大是真实代价。先单后多，见 2.8。

## 10. 小结

- Agent = **LLM + Tools + Memory + Loop + Goal**，可选第 6 要素 Reflection。
- 判别式只有一条：**下一步由谁决定**——代码写死是工作流，模型运行时决定是 Agent；Chatbot 既无工具也无反馈闭环。
- 边界四维判断：**确定性程度、环境动态性、成本容错、可控性要求**；四维全偏左选工作流，全偏右选 Agent，中间态选混合架构。
- 工程共识：**能用工作流就不用 Agent；先单 Agent 后多 Agent；先原型后工程化**。
- 自主性分级：**固定工作流 → 反应式 → 规划式 → 反思式 → 搜索式 → 多 Agent**，按任务难度付费。
- 核心四范式：**ReAct 管灵活单步、Plan-Execute 管长任务、Reflexion 管纠错、LATS 管搜索择优**；工程默认形态是 Function Calling Agent。
- Agent 的本质：**用不确定性换灵活性**；需要确定性的地方用工作流 + 工具 + 验证器。
- 关键约束：**最大步数、预算、权限、终止条件、人工介入**，缺一项都不算生产可用。
- 评估维度：**成功率、步数效率、工具准确率、成本、延迟、轨迹质量、安全性、鲁棒性**；牢记复合失败率（0.95 的 8 次方约等于 0.66，示意）。
- 截至 2026 年，定义之争已收敛，重心在轨迹级评估、安全与 Agent 互连协议（A2A、ANP，趋势观察）。
- 这些能力直接支撑：**2.2 规划、2.3 工具使用、2.4 记忆、2.5 执行循环与状态机、2.6 反思与自我修正、2.7 单 Agent 架构、2.8 多 Agent 协作、2.9 评估与安全**（即 2.2–2.9 全层）。
