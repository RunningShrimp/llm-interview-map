## 1. 定位

学习路径的第 2 个阶段（前续 5.1），属于"从单次调用到工程化应用"的过渡期。  
它解决一个核心问题：**如何让 LLM 调用稳定、可控、可评估，而不是"碰运气"式开发？**

对学习者，它是一份阶段作战计划：学什么、按什么顺序学、做什么项目、怎么验收，把 1 层工程能力练成肌肉记忆。  
对知识地图，1.1、1.2、1.3、1.6 是"兵种"，5.2 负责把它们编成"作战序列"。它是 5.3 的直接前置——单 Agent 的推理、工具调用、记忆，每一步都建立在稳定调用与结构化输出之上。

本阶段口径（与知识地图一致）：

## 2. 一句话定义

阶段 1 LLM 应用入门，是通过稳定 API 调用、结构化输出（Structured Output）、函数调用（Function Calling，亦称 Tool Use）、基础评估与日志可观测，把 LLM 从"玩具"变成"可靠组件"的工程实践阶段。

简化公式：

```text
阶段 1 = 稳定调用 + 结构化输出 + 基础评估 + 可观测 + 可维护
```

## 3. 为什么需要

阶段 0 能跑通 CLI，但离生产级应用还有六道缺口：

- **稳定性缺口** → 429 限流（Rate Limit）、超时、网络抖动频发，裸调用一崩整个流程就断。
- **结构化缺口** → 业务要的是 JSON 字段，模型给的是自然语言段落，程序无法可靠解析。
- **可控性缺口** → 工具调用参数无校验、失败无重试，错误一路裸奔到用户面前。
- **评估缺口** → 改了一版提示词（Prompt），只能"感觉变好了"，说不清变好还是变坏。
- **可观测缺口** → 每次调用没有日志、没有链路追踪（trace）、没有成本，出问题只能靠猜。
- **可维护缺口** → 模型名、Prompt、配置散落各处，换模型要改十几处。

"跳过 vs 先过"对比：

| 维度 | 跳过阶段 1 直接做 Agent | 先过阶段 1 再进阶 |
|---|---|---|
| 输出解析 | json.loads 频繁崩，靠 try/except 硬扛 | Schema 约束 + 校验 + 重试，解析失败率压到个位数 |
| 调优方式 | 凭感觉改 Prompt，改完不知道好坏 | 评估集跑分，每次改动有数字结论 |
| 故障排查 | 无日志无 trace，问题靠复现碰运气 | 看日志回放，分钟级定位 |
| 成本控制 | 月底看账单才知道超支 | 每次 token 落日志，日预算可控 |
| 换模型 | 改十几处调用点，牵一发动全身 | 只改 Client 一处配置 |
| 整体进度 | 看似直接上手 Agent，两周后被稳定性问题拖回原地 | 慢一周打地基，之后每个阶段都快 |

两个类比，具体到场景：

```text
运营车队：阶段 0 = 拿到驾照能上路；阶段 1 = 把车开成正规运营——装计价器（成本统计）、
          行车记录仪（日志）、出车检查单（校验）、爆胎换备胎预案（重试与降级），
          乘客（业务方）才敢坐你的车。
餐厅后厨：LLM = 手艺不错但状态会波动的大厨；JSON Schema + Pydantic = 出餐口的质检员，
          不合格的菜当场退回重做（校验失败 → 错误反馈 → 重试）；评估集 = 固定的试菜单，
          换菜谱（改 Prompt）先盲测打分，而不是凭老板一个人的舌头拍板。
```

- **先结构化，再智能**：输出不可靠，再聪明也没用。

### 4.5 里程碑自检表：本阶段学完能做什么

把里程碑"有校验、重试、日志；能比较两个 Prompt"拆成可逐项打分的自检表，全部达到合格口径才算通过：

| 自检项 | 合格口径 | 不合格信号 | 对应锚点 |
|---|---|---|---|
| 校验：格式层 | 能用 JSON Mode / 结构化输出约束整体是合法 JSON | 只在提示词里写"请输出 JSON" | 1.3 |
| 校验：字段层 | 类型错误、字段缺失、置信度越界能被 Pydantic 拦截 | json.loads 之后直接用，崩了才知道 | 1.3 |
| 重试：网络层 | 429 / 超时 / 5xx 走指数退避（Exponential Backoff），401 / 400 立刻暴露 | 遇错一律无差别重试三次 | 1.1 |
| 重试：语义层 | 校验失败时把错误信息反馈给模型定向修正 | 原样重发，三次得到同一个错 | 1.3 |
| 日志 | 每次调用记模型、token、延迟、重试次数；能从日志回放一次失败 | 只 print 最终结果 | 1.6 |
| 成本 | 能从日志统计出一段时间的 token 数与费用 | 月底看账单才知道花了多少 | 1.1、1.6 |
| 两 Prompt 对比 | 同一评估集跑 A/B，给出准确率与失败率并写明取舍结论 | 凭感觉说"新版本好像更好" | 1.2、1.6 |

配套的 10 个关键问题（口头全部答清即达标）：

1. 如何选择模型？什么任务用小模型？
2. 如何处理 429 和超时？
3. 如何做模型路由？
4. CoT 什么时候有用？
5. 如何防止提示注入？
6. JSON Mode 和 JSON Schema 有什么区别？
7. Function Calling 的完整循环是什么？
8. 如何用 Pydantic 校验 LLM 输出？
9. 如何构建评估集？

**面试高频问法**：阶段 1 学完，以下两问应能给出共识口径的回答——"JSON Mode 和 JSON Schema（结构化输出）有什么区别？"（JSON Mode 只保证返回的是能被解析的合法 JSON，不保证字段与类型满足业务要求；JSON Schema / Structured Outputs 把约束下沉到字段级；生产口径是三层防线——提示词给格式说明与示例、接口层开结构化约束、应用层 Pydantic 校验加错误反馈重试）；"改了一版 Prompt，怎么证明它变好了？"（固定评估集、每次只改一个变量、用准确率等量化指标对比，必要时在留出集上复核，而不是肉眼挑几条例子下结论）。

### 4.6 高频卡点与解法速查

| 卡点 | 典型症状 | 第一时间解法 | 深入锚点 |
|---|---|---|---|
| JSON 输出失控 | 时不时夹带解释文字，json.loads 崩 | 开 JSON Mode / 结构化输出 + Pydantic 校验 | 1.3 |
| 重试无效 | 校验失败原样重发，三次同样的错 | 把报错拼进对话反馈给模型，让它定向修正 | 1.3 |
| 字段幻觉 | 模型编造 Schema 里没有的字段或值 | Schema 收紧 + 字段 description 写清 + 校验拦截 | 1.3 |
| 评估缺位 | 改 Prompt 只能靠感觉 | 先攒 20 条带标准答案的评估集再调优 | 1.6 |
| 429 限流 | 批量跑评估时大面积失败 | 指数退避 + 降并发，评估脚本串行或小并发跑 | 1.1 |
| 成本失控 | 一晚上调 Prompt 烧几美元 | 小模型跑通再上大模型；每次改动记录 token | 1.1 |
| 提示注入 | 用户输入覆盖系统指令 | 输入与指令分区、转义、长度限制 | 1.2 |
| Prompt 管理混乱 | 改完不知道哪版好、无法回滚 | 提示词进独立文件 + 版本注册表 | 1.2 |

### 6.2 迭代一（v1）：裸调用跑通，先暴露问题

```python
# v1_extract_bare.py —— 验收：两条样例文本返回可解析 JSON；同时观察失败模式
import asyncio
import json
from openai import AsyncOpenAI  # pip install openai

client = AsyncOpenAI()  # 自动读取环境变量 OPENAI_API_KEY

EXTRACT_PROMPT = """从以下文本中抽取人物信息。
输出 JSON，字段：
- people: 人物列表，每人包含 name, age, city, occupation
- confidence: 置信度 0-1

只输出 JSON，不要解释。

文本：
{text}
"""

async def extract_v1(text: str) -> dict:
    response = await client.chat.completions.create(
        model="gpt-4o-mini",  # 示例模型名，以你所用服务商当前文档为准，选型见 1.1
        messages=[{"role": "user", "content": EXTRACT_PROMPT.format(text=text)}],
        temperature=0,
    )
    # 三个隐患：可能不是合法 JSON、字段可能缺、错一次整个流程就断
    return json.loads(response.choices[0].message.content)

if __name__ == "__main__":
    print(asyncio.run(extract_v1("张三，30 岁，住在北京，是一名工程师。")))
```

跑 20 条样例，记录失败模式（夹带解释文字、字段缺失、类型错误），这些就是 v2 要解决的问题。

### 6.3 迭代二（v2）：Pydantic 校验 + 错误反馈重试

```python
# schemas.py —— 把"输出必须长什么样"写成代码，字段说明同时给模型看
from pydantic import BaseModel, Field

class PersonInfo(BaseModel):
    name: str = Field(description="人名")
    age: int | None = Field(default=None, description="年龄")
    city: str | None = Field(default=None, description="城市")
    occupation: str | None = Field(default=None, description="职业")

class ExtractResult(BaseModel):
    people: list[PersonInfo]
    confidence: float = Field(ge=0, le=1)
```

```python
# extractor.py —— 校验 + 错误反馈重试：告诉模型哪里错了，而不是原样重发
import json
from pydantic import ValidationError
from llm import chat
from schemas import ExtractResult

EXTRACT_PROMPT = """从以下文本中抽取人物信息。
输出 JSON，字段：
- people: 人物列表，每人包含 name, age, city, occupation
- confidence: 置信度 0-1

只输出 JSON，不要解释。

文本：
{text}
"""

async def extract(text: str, max_retries: int = 3) -> ExtractResult:
    messages = [{"role": "user", "content": EXTRACT_PROMPT.format(text=text)}]
    for attempt in range(max_retries):
        response = await chat(
            messages,
            temperature=0,
            response_format={"type": "json_object"},  # JSON Mode：先保证整体合法，见 1.3
        )
        try:
            data = json.loads(response)
            return ExtractResult.model_validate(data)  # Pydantic：字段、类型、取值范围
        except (json.JSONDecodeError, ValidationError) as e:
            if attempt == max_retries - 1:
                raise
            # 错误反馈重试：把上次的输出与报错追加进对话，让模型定向修正
            messages += [
                {"role": "assistant", "content": response},
                {"role": "user", "content": f"上次输出不合法：{e}\n请严格按要求重新输出 JSON。"},
            ]
```

### 6.4 迭代三（v3）：统一 Client + 日志 + 评估

```python
# llm.py —— 统一 Client：模型分层路由、重试分类、结构化日志
import asyncio
import time
from openai import AsyncOpenAI, APIStatusError, APITimeoutError, APIConnectionError
from config import settings
from logger import get_logger

logger = get_logger()

class LLMClient:
    def __init__(self):
        self.models = {  # 模型分层与路由：简单任务走低价快速档，见 1.1
            "fast": settings.model_fast,        # 如 gpt-4o-mini
            "balanced": settings.model_balanced,  # 如 gpt-4o
        }
        self.client = AsyncOpenAI(
            api_key=settings.openai_api_key, timeout=settings.timeout
        )

    async def chat(self, messages, tier="fast", temperature=0,
                   response_format=None, max_retries=3) -> str:
        model = self.models[tier]
        for attempt in range(max_retries):
            start = time.time()
            try:
                resp = await self.client.chat.completions.create(
                    model=model, messages=messages,
                    temperature=temperature, response_format=response_format,
                )
                logger.info(
                    "llm_call model=%s attempt=%d in_tokens=%d out_tokens=%d latency_ms=%d",
                    model, attempt + 1,
                    resp.usage.prompt_tokens, resp.usage.completion_tokens,
                    round((time.time() - start) * 1000),
                )
                return resp.choices[0].message.content
            except (APITimeoutError, APIConnectionError):
                if attempt == max_retries - 1:
                    raise
                await asyncio.sleep(2 ** attempt)  # 超时/断连：退避后重试
            except APIStatusError as e:
                retryable = e.status_code == 429 or e.status_code >= 500
                if retryable and attempt < max_retries - 1:
                    await asyncio.sleep(2 ** attempt)  # 限流/5xx：可重试
                else:
                    raise  # 401/400 等：重试无意义，立刻暴露真实错误

llm = LLMClient()
chat = llm.chat
```

```python
# evaluator.py —— 在评估集上跑准确率，Prompt 好坏用数字说话（指标见 1.6）
import json
from extractor import extract

async def evaluate(eval_set_path: str) -> dict:
    with open(eval_set_path, encoding="utf-8") as f:
        eval_set = json.load(f)
    results = []
    for case in eval_set:
        try:
            result = await extract(case["text"])
            got = {p.name: p for p in result.people}
            expected = {p["name"]: p for p in case["expected_people"]}
            correct = (
                set(got) == set(expected)
                and all(got[n].age == e.get("age") and got[n].city == e.get("city")
                        for n, e in expected.items())
            )
            results.append({"case": case["id"], "correct": correct})
        except Exception as e:
            results.append({"case": case["id"], "correct": False, "error": str(e)})
    accuracy = sum(r["correct"] for r in results) / len(results)
    return {"accuracy": accuracy, "details": results}
```

## 7. 案例

### 案例 A：两周做出信息抽取器（学员复盘）

**场景**：刚通过 5.1 验收的学员，每天约 1.5 小时，按 §4.3 周计划推进。

**做法**：

```text
第 1 周：1.1 统一 Client + 1.2 三版抽取 Prompt（每版都在同一评估集上跑分）
第 2 周：1.3 校验与重试 → 1.6 评估脚本与日志 → 整合 v3 + 测试 + README
```

两周里的核心实验是两 Prompt 对比（同一 20 条评估集，其余条件全部不变）：

| 版本 | 唯一改动 | 准确率 | 解析失败率 | 单条成本 | 结论 |
|---|---|---|---|---|---|
| Prompt A（基线） | 角色任务约束 | 72% | 18% | $0.001 | 基线 |
| Prompt B | A + 2 个 Few-shot 示例 | 85% | 9% | $0.001 | 保留 B，A 留档可回滚 |

**示意数字效果**：总投入约 20 小时；准确率 72% 提到 85%，解析失败率从 18% 压到 9%，剩余失败由 v2 的错误反馈重试兜住，程序级最终成功率约 97%；API 花费约 3 美元（低价模型为主、事实抽取温度 0）。

### 案例 B：Prompt 从 78% 迭代到 92%

**场景**：另一位学员的抽取器已能稳定输出 JSON，开始专项调 Prompt。

**做法**（每次只改一个变量，同一评估集跑分）：

1. 基线：角色任务约束 → 78%
2. 加 2 个 Few-shot 示例 → 84%
3. 加"先摘原文短句、再填字段"的 CoT 引导 → 87%
4. 接口层开 JSON Mode → 90%
5. Pydantic 校验 + 错误反馈重试兜住剩余格式错误 → 92%

**示意数字效果**：单条成本从 $0.001 涨到 $0.002（示例与重试多了 token），换来准确率 +14 个百分点，属可接受交换；最终保留第 5 版，前四版进版本注册表，可随时回滚复现。

### 案例 C：JSON 输出助手在某电商客服上线

**场景**：某电商客服团队每天约 2000 条用户留言，要转成工单 JSON（类型、优先级、订单号）供下游系统消费；此前用正则与关键词抽取，约 30% 留言解析失败转人工。

**做法**：按本阶段项目搭"JSON 输出助手"——Pydantic 定义工单 Schema；接口层开 JSON Mode；校验失败错误反馈重试（最多 2 次）；每次调用落日志并统计 token；上线前用 200 条人工标注留言做评估集验收（达标线 95%）。

**示意数字效果**：上线后解析失败率降到 3%；人工只处理长尾，日均处理时长从约 4 小时降到 40 分钟；月度 token 成本约 60 美元，远低于节省的人工成本。

## 8. 常见坑

1. **不封装 LLM Client**。对策：所有调用收敛到一个 Client 类，换模型、加日志只改一处（见 1.1）。
2. **不处理 429 限流**。对策：指数退避重试，必要时降并发；写法见 5.1 §6.3。
3. **不设超时**。对策：给每次调用设超时（如 30 秒），超时归入可重试错误，避免服务被挂死。
4. **不记录 token 与成本**。对策：每次调用把 input/output token 写进日志，每天汇总一次费用，设预算告警。
5. **Prompt 硬编码在业务代码里**。对策：提示词进独立文件 + 版本注册表（§6.5），支持 A/B 与回滚。
6. **只靠提示词保证 JSON**。对策：接口层开 JSON Mode / 结构化输出约束，应用层用 Pydantic 校验，三层防线缺一不可（见 1.3）。
7. **不做 Pydantic 校验**。对策：把输出 Schema 写成模型类，解析后必须 model_validate，非法输出拦截在入口。
8. **重试只是原样重发**。对策：把校验错误拼进对话反馈给模型，让它定向修正；原样重发大概率得到同样的错。
9. **不做评估集**。对策：动手调 Prompt 前先攒 20 条带标准答案的样本，改动好坏用准确率说话（见 1.6）。
10. **评估集与调参集混用**。对策：样本按约 7:3 分成调参集与留出集（Holdout），最终结论只在留出集上认。
11. **不做防注入**。对策：用户输入与系统指令分区、对输入转义并限长，基础手法见 1.2。
12. **不做日志**。对策：每次调用记模型、token、延迟、重试次数；出问题先看日志再改代码。
13. **不做版本管理**。对策：Prompt、模型名、配置全部纳入版本，评估结果落盘，可复现"当时为什么选 v3"。
14. **不写测试**。对策：至少给抽取器与 Client 写 pytest 用例，改代码后跑一遍再提交。
15. **不写 README**。对策：按"环境—安装—运行—测试"四段写清，别人 10 分钟内跑起来才算合格。

## 9. 练习

1. 封装统一 LLM Client（fast / balanced 分层）；验收：切换档位只改一个参数，日志里能看到模型名。
2. 给 Client 加指数退避重试；验收：429 场景观察到 1s → 2s → 4s 退避，错误 Key 场景 1 秒内失败。

7. 用评估集对比两个 Prompt（A/B）；验收：产出一张对比表（准确率、解析失败率、单条成本）并写出取舍结论。
8. 实现 LLM-as-Judge 给开放式回答打分；验收：与人工打分在 10 条样本上方向一致（见 1.6）。
9. 加结构化日志与成本统计；验收：从日志算出"今天花了多少 token、多少钱"。
10. 搭 Prompt 版本注册表；验收：改一个 current 字段即可回滚到旧版本。
11. 写 README；验收：找一位同学按文档在 10 分钟内跑通评估脚本。
12. 自答 §4.5 的 10 个关键问题并录音回听；验收：每题 60 秒内讲清，讲不清的回锚点补课。

## 10. 小结

- 阶段 1 = **稳定调用 + 结构化输出 + 基础评估 + 可观测 + 可维护**，把 LLM 从"玩具"变成"可靠组件"。
- 组队顺序：**1.1 → 1.2 → 1.3 → 1.6 → 项目**；原则是先稳定再优化、先评估再调优、先结构化再智能。
- 里程碑口径：**抽取器有校验、有重试、有日志；能用评估集比较两个 Prompt 并给出数字结论**，逐项对照 §4.5 自检表打分。
- 最小项目：**信息抽取器 / JSON 输出助手**，按三个迭代交付——v1 裸调用、v2 校验与错误反馈重试、v3 日志与评估。
- 结构化输出三层防线：**提示词给格式与示例、接口层开 JSON Mode / 结构化约束、应用层 Pydantic 校验 + 重试**，缺一层就靠碰运气。
- 评估是调优的前提：**20 条评估集 + 每次只改一个变量**，改 Prompt 的好坏由准确率说了算，不靠感觉。
- 时间预算：**2–3 周**（有阶段 0 基础）；第 1 周 1.1 + 1.2，第 2 周 1.3，第 3 周 1.6 + 项目。
- 高频卡点集中在 **JSON 失控、重试无效、评估缺位、成本失控**四类，解法见 §4.6 速查表。
- 面试共识口径随身带：JSON Mode 与 JSON Schema 的区别、如何证明一版 Prompt 变好了。
- 验收不合格不硬闯：**能稳定调用、能结构化、能评估、能复现**，四项齐了再走。
- 这些能力直接支撑：**5.3 阶段 2：单 Agent 核心**。
