# 讲解 4.3 数据分析 Agent

> 说明：前置 2.3 讲清了工具怎么定义、怎么安全调用；3.8 给了权限、审计与合规的底座。  
> 本篇让 Agent 真正"会算"：查数据库（Text2SQL）、跑 Python（沙箱）、画图表，并把**如何安全执行代码与查询**当作第一设计约束。  
> 这些执行与沙箱能力，后续在 4.7 生产级 Agent 平台沉淀为平台基础设施。

---

## 1. 定位

实战层第 3 个知识点，属于"计算与执行型 Agent"。  
它解决本锚点的核心问题：**如何让 Agent 安全地执行代码与查询——查询数据库、运行 Python、生成图表，完成真实的数据分析任务？**

- 直接前置：2.3 工具使用（工具定义与调用）、3.8 安全合规与权限（最小权限与审计）。
- 后续承接：4.7 生产级 Agent 平台（沙箱池成为平台的"计算机"）。
- 同层相邻：4.4 浏览器 Agent、4.5 工作流自动化复用本篇的安全执行思路。

一句话点题：普通 Agent 的风险是"说错话"，数据分析 Agent 的风险是"执行错代码"——所以本篇一半篇幅在讲安全。

## 2. 一句话定义

数据分析 Agent，是在单 Agent 基础上集成 SQL 执行器、Python 沙箱、图表生成工具，使 Agent 能自主完成"理解问题 → 查数据 → 计算 → 可视化 → 解释"的分析闭环，同时保证执行安全的实战系统。

简化公式：

```text
数据分析 Agent = 单 Agent + SQL 工具 + Python 沙箱 + 可视化 + 安全边界
```

## 3. 为什么需要

LLM 本身不擅长精确计算：

- **大数运算会错**：心算 384217 × 9136 基本必错。
- **日期计算会错**：跨月、跨年、时区换算经常偏一天。
- **聚合统计不可靠**：让它"看数据估个总数"，误差不可控。
- **访问不了数据库**：训练语料里没有你公司的订单表。

但真实业务大量需要：

- **数据查询**："上个月销售额是多少？"
- **统计分析**："哪个地区增长最快？"
- **趋势判断**："最近三个月的趋势如何？"
- **异常检测**："哪些订单金额异常？"
- **可视化**："画一张销售趋势图。"

三种做法对比：

| 做法 | 正确性 | 时效 | 安全 | 可追溯 |
|---|---|---|---|---|
| 人工写 SQL 取数 | 高（人写人查） | 慢（排队数小时到数天） | 高 | 取决于流程 |
| 直接问 LLM（心算/编数据） | 低（幻觉、算错） | 快 | 无执行风险 | 无依据 |
| 数据分析 Agent | 中高（需评估兜底） | 快（分钟级） | 取决于安全设计 | 有 SQL 与轨迹可查 |

**类比**：

```text
普通 Agent     = 一个会说话的顾问：口才好，但你让他算全年的账，他会一本正经地算错
数据分析 Agent = 一个会用 Excel、会写 SQL、会跑 Python 的分析师：
                 数字从数据库里查出来，计算交给代码跑，结论附上 SQL 和图表
```

## 4. 核心原理

### 4.1 数据分析 Agent 的能力矩阵

| 能力 | 工具 | 风险 |
|---|---|---|
| 查数据库 | SQL 执行器 | 注入、越权、慢查询 |
| 数据处理 | Python 沙箱 | 恶意代码、资源耗尽 |
| 统计计算 | Python / SQL | 计算错误 |
| 可视化 | matplotlib / plotly | 文件写入 |
| 文件读写 | 受限文件系统 | 路径穿越 |
| 结果解释 | LLM | 幻觉 |

### 4.2 两种核心工具：执行路径的本质差异

**1. SQL 执行器**

```text
Agent 生成 SQL → 静态校验 → 只读执行 → 限行返回
```

关键约束：

- 只允许 SELECT，禁止 DDL / DML
- 限制返回行数、设置查询超时
- 表级白名单、参数化查询（Parameterized Query）

**2. Python 沙箱（Sandbox）**

```text
Agent 生成代码 → 静态校验 → 沙箱隔离执行 → 输出截断返回
```

关键约束：

- 禁止网络访问、文件系统只读（或限制目录）
- 限制 CPU / 内存 / 时间
- 禁止 `os.system`、`subprocess`，白名单导入

**为什么两者的安全设计完全不同**——这是理解本篇的钥匙：

| 维度 | SQL 执行器 | Python 沙箱 |
|---|---|---|
| 语言能力 | 声明式子集，语句类型可枚举 | 图灵完备（Turing Complete），写法无穷 |
| 静态校验 | 能审住：解析语法、只认 SELECT、查白名单表 | 审不住：危险写法无法穷尽（如 `getattr` 动态调用） |
| 出事的后果 | 查错数、拖慢库 | 任意代码行为：删文件、开网络、起进程 |
| 核心防线 | 权限（只读账号）+ 限额（行数/超时）+ 白名单 | 隔离执行 + 资源限制 + 输出过滤 |
| 兜底手段 | 数据库层权限拒绝 | 容器/微虚拟机边界 |

结论：SQL 路径**校验得住**，所以以"校验 + 权限"为主；Python 路径**校验不住**，所以必须"隔离兜底"。这一判断直接决定后面所有安全设计。

### 4.3 Text2SQL 管道：从问题到数据

自然语言转 SQL（Text-to-SQL，下称 Text2SQL）不是"一次生成"，而是一条带反馈的管道：

```text
用户问题
   ↓
Schema 检索（表少全给；表多时嵌入召回 Top-K 相关表）
   → 输出：表结构 + 字段注释 + 少量示例行
   ↓
SQL 生成（问题 + Schema + 少样本示例）
   ↓
静态校验（只读、单语句、白名单表、行数上限）
   ├─ 不通过 → 拒绝原因回填 → 重新生成
   └─ 通过 → 只读执行
   ↓
执行出错？（语法错 / 字段不存在 / 超时）
   ├─ 是 → 报错原文 + Schema 回填 → 重新生成（自修复，最多 N 次）
   └─ 否 → 结果（限行）→ 摘要回填上下文
```

**Schema 理解**是起点——Agent 必须先知道库里有什么：

```python
SCHEMA_PROMPT = """数据库 Schema：
表 orders：
- id (VARCHAR)
- user_id (VARCHAR)
- amount (DECIMAL)
- status (VARCHAR): pending/shipped/delivered/cancelled
- created_at (TIMESTAMP)

表 users：
- id (VARCHAR)
- name (VARCHAR)
- city (VARCHAR)
- level (VARCHAR): normal/vip
"""
```

**Schema 检索**：表上千张时全塞进提示词既贵又让模型选错表。做法是把表结构切块、向量化，按问题召回 Top-K 张相关表再生成——本质是给 Schema 建了一个小型 RAG（检索思路见 4.2）。

**自修复（Self-repair）**：执行报错是最强的纠错信号。"no such column: region" 这句报错回填给 LLM，它几乎总能改成正确字段名。示意口径：一次生成通过率约 70%，加两轮自修复后可到 90% 以上（见案例 A）。

类比：Text2SQL 自修复像新员工第一次跑 SQL 报"字段不存在"，第二次对照数据字典就改对了——报错本身就是最好的老师。

### 4.4 多步分析循环

单次查询回答不了复杂问题，需要多步循环（循环与终止控制的机制见 2.5）：

```text
用户问题
   ↓
理解意图 → 需要什么数据？
   ↓
查 Schema → 有哪些表、字段？
   ↓
生成 SQL / Python
   ↓
执行 → 结果
   ↓
结果够吗？
   ├─ 否 → 继续查询/计算
   └─ 是 → 分析 → 可视化 → 解释
   ↓
输出：结论 + 图表 + 依据（SQL 与数据可回溯）
```

### 4.5 安全边界：查询安全与代码安全

本锚点的关键问题"如何安全执行代码与查询"，正面回答是两套三件套加一个原则。

**查询安全（SQL 侧）= 权限 + 限额 + 白名单**：

| 手段 | 做法 | 拦住什么 |
|---|---|---|
| 权限 | 数据库只读账号（Read-only Account）+ 参数化查询 | 即使校验全被绕过，DROP/UPDATE 在数据库层被拒；注入失效 |
| 限额 | 行数上限（如 100 行）+ 查询超时（如 10s）+ 并发限制 | 慢查询拖垮库、百万行结果撑爆上下文 |
| 白名单 | 表级白名单，敏感表（工资、身份）不开放 | 越权查敏感数据从源头断掉 |

**代码安全（Python 侧）= 沙箱 + 资源限制 + 输出过滤**：

| 手段 | 做法 | 拦住什么 |
|---|---|---|
| 沙箱 | 容器/子进程隔离执行，文件系统只读、网络禁用 | 代码出不了沙箱：删不了宿主文件、传不出数据 |
| 资源限制 | CPU、内存、执行时长三限 | 死循环烧不掉机器、大对象撑不爆内存 |
| 输出过滤 | stdout 截断回填、产物只走白名单目录 | 大输出撑爆上下文、路径穿越写任意位置 |

**两层防御原则**：

```text
第一层：静态校验（快、便宜）→ 拦"看得见的危险"，但可被绕过
第二层：运行时隔离（慢、可靠）→ 兜"绕过校验的危险"
提示词审查不算防线——它是体验优化，不是安全边界
```

具体到代码：字符串黑名单拦 `import os`，但 `__import__("o"+"s")` 能绕过——所以第一层拦大部分省资源，第二层（容器 + 只读账号）保证绕过也出不了事。

**面试高频问法**："怎么防止 Agent 的 SQL 删库？""Agent 生成的 SQL/代码需要执行，如何设计沙箱环境、权限隔离，避免越权操作、注入攻击？"（业界共识口径）标准答法是四层递进：提示词约束（体验层）→ 静态校验（拦截层）→ 只读账号/表白名单（权限层）→ 容器隔离 + 资源限制（兜底层）；任何单层都不够，"删库"最终由只读账号兜底——即使前三层全失效，数据库也拒绝写。

### 4.6 沙箱实现层次

| 层次 | 方式 | 隔离度 | 性能 |
|---|---|---|---|
| L1 | 字符串校验 | 低 | 高 |
| L2 | 受限执行环境 | 中 | 高 |
| L3 | 子进程 + 资源限制 | 中高 | 中 |
| L4 | 容器隔离 | 高 | 中 |
| L5 | 微虚拟机（microVM，如 Firecracker） | 最高 | 低 |

常见方案选型对比：

| 方案 | 隔离边界 | 冷启动（示意量级） | 成本 | 典型用途 |
|---|---|---|---|---|
| 进程 + 资源限制 | 进程级，共享内核 | 毫秒级 | 低 | 原型、内部工具 |
| 容器（Docker + cgroups） | 内核命名空间 | 秒级 | 中 | 生产主流 |
| 沙箱容器运行时（gVisor 类） | 用户态内核拦截系统调用 | 秒级 | 中 | 容器逃逸加固 |
| 微虚拟机（Firecracker） | 硬件虚拟化 | 百毫秒级 | 中高 | 不可信代码、托管平台 |
| 云函数 | 厂商托管临时实例 | 秒级（有池化更低） | 按调用计费 | 没有基础设施团队时 |

**工程建议**：

- 原型：L2 + L3（子进程 + 超时即可跑通）。
- 生产：L4（Docker 容器 + 资源限制 + 网络禁用）。
- 高安全/对外服务：L5（microVM 级隔离）。

类比：沙箱分层像医院处理感染源——洗手消毒（L1 校验）拦日常风险；隔离病房（L4 容器）防扩散；负压实验室（L5 microVM）对付最危险的样本。你会对高危样本只做"洗手"吗？

趋势观察：截至 2026 年，E2B（基于 Firecracker，官方口径冷启动低于 200ms）、Modal 等托管代码沙箱已较成熟，自建 microVM 成本高时可考虑采购；选型前以官方文档实测为准。

### 4.7 错误恢复策略

执行环节的错误频率远高于纯文本 Agent，恢复策略要按错误类型分流（重试、降级的通用机制见 2.5）：

| 错误类型 | 典型现象 | 恢复策略 |
|---|---|---|
| SQL 语法错误 | syntax error 报错 | 报错原文回填，重新生成（自修复，最多 3 次） |
| 字段/表不存在 | no such column / table | 回填正确 Schema，重新生成 |
| 查询超时 | 执行超过时限被中断 | 提示 Agent 加过滤条件、拆分查询、加 LIMIT |
| 结果行数超限 | 返回被截断 | 提示改为聚合查询或缩小范围 |
| 代码运行时异常 | Python 抛异常 | 堆栈回填，重新生成代码 |
| 代码死循环/超时 | 沙箱超时被杀 | 告知超时原因，要求改写算法 |
| 权限拒绝 | 访问白名单外的表 | 拒绝并说明边界，不重试（重试无意义） |
| 连续失败 | 自修复 N 次仍失败 | 终止，返回部分结果 + 失败原因 |

要点：权限类错误**不重试**（重试只会更烦数据库），生成类错误**必回填**（报错是免费的高质量监督信号）。

### 4.8 结果解释与可视化

**结果解释**——把数字翻译成结论，但不得发明数字：

```python
EXPLAIN_PROMPT = """根据以下查询结果回答用户问题。

用户问题：{question}
SQL：{sql}
结果：{result}

要求：
1. 用自然语言解释结果，结论先行
2. 指出关键发现（最大/最小/异常项）
3. 不要编造结果中没有的数据；数字必须与结果一致
4. 附上你使用的 SQL 作为依据
"""
```

解释三原则：结论先行、数字与查询结果逐字对齐、附 SQL 可回溯。

**图表选型**——让图匹配问题形态：

| 问题形态 | 合适图表 |
|---|---|
| 对比（各地区销售额） | 柱状图 |
| 趋势（逐月走势） | 折线图 |
| 占比（品类构成） | 饼图 / 堆叠柱 |
| 分布（订单金额区间） | 直方图 |
| 相关（投放 vs 转化） | 散点图 |

图表生成代码见 6.7。

### 4.9 数据脱敏

分析结果常含个人敏感信息（PII，Personally Identifiable Information），脱敏（Data Masking）必须发生在**结果回填上下文之前**——否则 PII 已经进入对话历史，事后删不掉：

```python
def mask_result(rows: list) -> list:
    for row in rows:
        for key, value in row.items():
            if key in ["phone", "id_card", "email"]:
                row[key] = "[已脱敏]"
    return rows
```

更彻底的做法是敏感表直接不进白名单（见 4.5），脱敏是第二道网。

### 4.10 评估维度

| 维度 | 指标 |
|---|---|
| SQL 正确率 | 生成的 SQL 是否可执行、结果正确 |
| 代码正确率 | Python 代码是否运行成功 |
| 答案准确率 | 最终结论是否正确 |
| 步数效率 | 完成分析用几步 |
| 安全性 | 是否有越权、危险操作 |
| 延迟 | 端到端时间 |

评估集构建与对抗测试的体系化做法见 4.8 评估与红队。

### 4.11 与其他 Agent 的区别

| 维度 | 普通 Agent | 数据分析 Agent |
|---|---|---|
| 核心工具 | 查询 API | SQL + Python |
| 安全风险 | 中 | 高（代码执行） |
| 结果验证 | 文本匹配 | 数值验证（可对答案） |
| 错误恢复 | 重试 | 报错回填 + 重新生成代码 |
| 沙箱 | 不需要 | 必须 |

```text
┌──────────────────────────────────────────┐
│  用户问题                                 │
│  "上个月哪个地区销售额最高？"             │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  Agent 编排层                             │
│  ├─ 理解意图                             │

┌──────────────────────────────────────────┐
│  工具层                                   │
│  ├─ SQL 执行器（只读、超时、限行）        │

│  ├─ 图表生成                             │
│  └─ Schema 查询                          │
└──────────────────────────────────────────┘
                  ↓                ↑ 报错回填（自修复）
┌──────────────────────────────────────────┐
│  安全层（横向包裹所有工具调用）           │
│  ├─ SQL 白名单 + 只读账号                │
│  ├─ 代码校验 + 容器隔离                  │
│  ├─ 资源限制                             │
│  ├─ 数据脱敏                             │
│  └─ 审计日志（谁、何时、查了什么）       │
└──────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────┐
│  输出层                                   │
│  ├─ 结论                                 │
│  ├─ 数据表格                             │
│  ├─ 图表                                 │
│  └─ 分析过程（SQL + 执行轨迹可回溯）     │
└──────────────────────────────────────────┘
```

读图要点：安全层不是流水线的一站，而是横向包裹工具层的每一笔调用——任何执行路径都绕不开它；编排层与工具层之间有一条"报错回填"回环，这就是 4.3 的自修复在架构里的位置。

### 6.2 SQL 工具：校验 + 只读 + 白名单 + 限额

```python
import sqlite3
from pydantic import BaseModel, Field

class SQLQueryArgs(BaseModel):
    sql: str = Field(description="SELECT 查询语句")

FORBIDDEN = ["DROP", "DELETE", "UPDATE", "INSERT", "ALTER", "TRUNCATE", "GRANT"]
ALLOWED_TABLES = {"orders", "users"}          # 表级白名单：敏感表从这里就不可见
MAX_ROWS = 100                                 # 行数上限：防大结果撑爆上下文
QUERY_TIMEOUT = 10                             # 查询超时（秒）：防慢查询拖垮库

def validate_sql(sql: str) -> tuple[bool, str]:
    upper = sql.upper().strip()
    if not upper.startswith("SELECT"):
        return False, "只允许 SELECT"
    for kw in FORBIDDEN:
        if kw in upper:
            return False, f"禁止 {kw}"
    if ";" in sql.rstrip(";"):
        return False, "禁止多语句"
    import re
    for t in re.findall(r"(?:FROM|JOIN)\s+([a-zA-Z_]\w*)", upper):
        if t not in ALLOWED_TABLES:
            return False, f"表 {t} 不在白名单"
    return True, ""

async def execute_sql(sql: str, max_rows: int = MAX_ROWS) -> dict:
    ok, err = validate_sql(sql)
    if not ok:
        return {"success": False, "error": err}
    try:
        # 只读连接（mode=ro）：即使校验被绕过，数据库层也拒绝写入
        conn = sqlite3.connect("file:data/sample.db?mode=ro", uri=True)
        conn.row_factory = sqlite3.Row
        cursor = conn.execute(sql)
        rows = [dict(r) for r in cursor.fetchmany(max_rows)]
        conn.close()
        return {"success": True, "data": rows, "count": len(rows)}
    except Exception as e:
        return {"success": False, "error": str(e)}
```

生产上换成 MySQL / PostgreSQL 时，等价手段是：专用只读账号 + `statement_timeout` + 结果分页；SQLite 的 `mode=ro` 是同一思想的最小实现。

### 6.3 Text2SQL 管道：生成 + 自修复

```python
TEXT2SQL_PROMPT = """你是 SQL 专家。根据问题和 Schema 写一条 SQLite 查询。

Schema：
{schema}

规则：
1. 只输出一条 SELECT 语句，不要任何解释。
2. 只能使用这些表：{allowed_tables}。
3. 结果必须限制在 {max_rows} 行以内。

问题：{question}
"""

async def text2sql(question: str, max_retries: int = 3) -> dict:
    schema = get_schema_prompt()               # 表少全给；表多先嵌入检索 Top-K（见 4.3）
    messages = [{
        "role": "user",
        "content": TEXT2SQL_PROMPT.format(
            schema=schema,
            allowed_tables=", ".join(ALLOWED_TABLES),
            max_rows=MAX_ROWS,
            question=question,
        ),
    }]
    result = {}
    for _ in range(max_retries):
        sql = (await chat(messages)).strip()   # 生成 SQL
        result = await execute_sql(sql)        # 校验 + 只读执行（见 6.2）
        if result["success"]:
            return {"sql": sql, **result}
        # 自修复：把报错原文回填，让模型修正（报错是免费的监督信号）
        messages.append({"role": "assistant", "content": sql})
        messages.append({
            "role": "user",
            "content": f"执行失败：{result['error']}。请对照 Schema 修正后重新输出 SQL。",
        })
    return {"success": False, "error": "自修复重试耗尽", "last_error": result.get("error")}
```

### 6.4 Python 沙箱：子进程 + 校验 + 超时

```python
import subprocess
import tempfile
import os

FORBIDDEN_IMPORTS = ["os", "sys", "subprocess", "socket", "requests", "shutil", "pathlib"]
FORBIDDEN_CALLS = ["eval", "exec", "open", "__import__", "compile", "input"]

def validate_code(code: str) -> tuple[bool, str]:
    for imp in FORBIDDEN_IMPORTS:
        if f"import {imp}" in code or f"from {imp}" in code:
            return False, f"禁止导入 {imp}"
    for call in FORBIDDEN_CALLS:
        if f"{call}(" in code:
            return False, f"禁止调用 {call}"
    return True, ""

async def execute_python(code: str, timeout: int = 10) -> dict:
    ok, err = validate_code(code)
    if not ok:
        return {"success": False, "error": err}

    with tempfile.NamedTemporaryFile(mode="w", suffix=".py", delete=False) as f:
        f.write(code)
        path = f.name

    try:
        result = subprocess.run(
            ["python", path],
            capture_output=True,
            text=True,
            timeout=timeout,                        # 时间限制：死循环 10 秒被杀
            env={"PATH": "/usr/bin", "PYTHONPATH": ""},  # 最小环境变量
        )
        return {
            "success": result.returncode == 0,
            "stdout": result.stdout[:5000],          # 输出截断：防大输出撑爆上下文
            "stderr": result.stderr[:2000],
        }
    except subprocess.TimeoutExpired:
        return {"success": False, "error": "执行超时"}
    finally:
        os.unlink(path)
```

注意：这一层仍是 L3（子进程），字符串校验可被绕过（见 4.5），生产必须叠加 6.5 的容器层。

### 6.5 容器化沙箱（生产推荐）

```python
import docker

client = docker.from_env()

async def execute_in_container(code: str, timeout: int = 15) -> dict:
    try:
        container = client.containers.run(
            "python:3.11-slim",
            command=["python", "-c", code],
            mem_limit="256m",              # 内存限制：大对象撑不爆宿主
            cpu_period=100000,
            cpu_quota=50000,               # 0.5 CPU：算力封顶
            network_disabled=True,         # 网络禁用：数据传不出去
            read_only=True,                # 文件系统只读：删不了宿主文件
            remove=True,
            timeout=timeout,              # 时间兜底
            detach=False,
        )
        return {"success": True, "output": container.decode()[:5000]}
    except docker.errors.ContainerError as e:
        return {"success": False, "error": str(e)}
    except Exception as e:
        return {"success": False, "error": str(e)}
```

对照 4.5 的代码安全三件套：容器隔离（network_disabled + read_only）、资源限制（mem_limit + cpu_quota + timeout）、输出过滤（decode 后截断）——三个手段都在参数里。

### 6.6 Agent 集成

```python
SYSTEM_PROMPT = """你是一个数据分析助手。
你可以：
1. 查询数据库（execute_sql）
2. 执行 Python 代码（execute_python）
3. 生成图表（generate_chart）
4. 查看数据库 Schema（get_schema）

规则：
1. 先查看 Schema，再写 SQL。
2. SQL 只允许 SELECT。
3. 不要编造数据，结论必须来自查询结果。
4. 结果要解释清楚，并附上使用的 SQL。
5. 需要可视化时调用 generate_chart。
"""

class DataAnalysisAgent:
    def __init__(self, registry):
        self.registry = registry
        self.trajectory = []

    async def run(self, query: str, max_steps: int = 15) -> dict:
        messages = [
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": query},
        ]

        for step in range(max_steps):
            msg = await chat(messages, tools=self.registry.get_schemas())

            if not msg.tool_calls:
                return {
                    "answer": msg.content,
                    "steps": step + 1,
                    "trajectory": self.trajectory,
                }

            messages.append(msg)

            for tc in msg.tool_calls:
                args = json.loads(tc.function.arguments)
                result = await self.registry.execute(tc.function.name, args)

                self.trajectory.append({          # 审计：每步留痕，可回溯
                    "step": step + 1,
                    "tool": tc.function.name,
                    "args": args,
                    "result": result,
                })

                messages.append({
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": json.dumps(result, ensure_ascii=False)[:3000],
                })

        return {"answer": "分析未完成", "steps": max_steps, "trajectory": self.trajectory}
```

## 7. 案例

### 案例 A：某电商团队的取数 Agent

**场景**：运营每天提数十个临时取数需求（"上周各品类转化率"），分析师疲于奔命，排队一两天。

**做法**：部署本篇架构——Schema 嵌入检索（库里有 400+ 张表）+ Text2SQL 自修复（2 轮）+ 只读账号 + 表白名单（排除工资、身份类表）+ 图表输出。

**示意数字效果**：

- 周均约 300 次取数请求自助完成，分析师不再介入常规取数。
- SQL 一次生成通过率约 70%，加自修复后升至约 92%。
- 平均 6 步、端到端 40 秒出结果；单次取数从"提需求等 2 小时"变成"5 分钟内自己拿到"。

### 案例 B：沙箱拦截"删库"诱导

**场景**：红队演练。一部分样本诱导生成 `import os; os.system("rm -rf /")`，另一部分诱导生成 `DROP TABLE orders;`。

**做法与拦截过程**：

1. 静态校验：`os` 导入、`DROP` 语句直接被拒（第一层）。
2. 构造绕过校验的样本（如 `getattr` 动态拼 `os`）：进入容器执行（第二层）。
3. 容器内文件系统只读：`rm` 无处可删；网络禁用：即使有数据也传不出去。
4. SQL 侧 `DROP` 即使绕过校验，只读账号在数据库层拒绝。

**示意数字效果**：50 条攻击样本，静态校验拦下 44 条；6 条进入沙箱后全部无法越界；0 条造成实际影响。多层防御的意义不是每层都完美，而是**任何一层失效时下一层兜底**。

### 案例 C：注入与拖库防护

**场景**：恶意输入 `1' OR '1'='1` 试图拖库；同时用 `SELECT * FROM orders`（百万行表）试图撑爆上下文。

**做法**：

1. Agent 生成 SQL 用参数化查询，注入串只是普通参数值。
2. 校验层禁止多语句，`;` 截断攻击无效。
3. 数据库账号只读且仅白名单表可见。
4. 行数上限 100 + 超时 10 秒：大查询被截断为 100 行，上下文稳定。

**示意数字效果**：100 条注入类 payload 全部失效；百万行查询在 10 秒内被限额截断，Agent 上下文占用保持在 3 KB 量级（未加限额时同类查询回填约 200 MB 文本，任务直接失败）。

## 8. 常见坑

1. **不做 SQL 校验**。  
   可能执行 DROP、DELETE，必须白名单加只读账号双重拦截。

2. **不做代码校验**。  
   恶意代码可执行系统命令；静态校验拦大部分、容器隔离兜底，多层防护。

3. **沙箱不隔离**。  
   直接在主进程执行代码，`while True` 就能拖垮整个服务；至少子进程，生产用容器。

4. **不限制资源**。  
   死循环、内存爆炸烧掉机器；CPU、内存、超时三限缺一不可。

5. **不限制返回行数**。  
   查 100 万行直接撑爆上下文，任务失败还烧 token；行数上限加聚合引导。

6. **不做 Schema 检索**。  
   表太多全塞提示词，模型选错表还贵；用嵌入检索召回相关表（见 4.3）。

7. **结果不脱敏**。  
   查询结果含手机号、身份证号，随对话历史泄露；脱敏在回填上下文之前做。

8. **不验证结果**。  
   SQL 执行成功但口径错（如漏了退款单），答案错得理直气壮；关键数字用第二条 SQL 交叉验证。

9. **不让 Agent 看 Schema**。  
   瞎写字段名，首轮必错；先给 Schema 再生成。

10. **不做审计**。  
    谁查了什么、执行了什么代码，出事无法追溯；每步工具调用留痕（见 6.6）。

11. **沙箱可访问网络**。  
    恶意代码把库里的数据直接外传；网络禁用是硬要求。

12. **不做错误自修复**。  
    SQL 语法错一次就直接失败；报错回填重试，一次通过率显著提升（见 4.3）。

13. **只做单步查询**。  
    复杂问题一次查不出来；用多步循环（见 2.5 的循环与终止控制）。

14. **忽略可视化**。  
    只给一排数字，用户理解难；按问题形态选图（见 4.8）。

15. **不评估准确率**。  
    不知道 SQL 生成对不对就敢上线；先建评估集再谈效果（见 4.8 评估与红队）。

16. **把提示词当安全边界**。  
    一句"忽略之前的规则"就可能让模型放开限制；提示词是体验优化，安全必须落在校验层、账号层、隔离层（见 4.5）。

## 10. 小结

- 数据分析 Agent = **单 Agent + SQL 工具 + Python 沙箱 + 可视化 + 安全边界**。
- 核心工具：**SQL 执行器、Python 沙箱、Schema 检索、图表生成**。
- 两条执行路径本质不同：SQL 可静态审住，以校验加权限为主；Python 图灵完备审不住，必须隔离兜底。
- Text2SQL 是管道不是单次生成：**Schema 检索 → 生成 → 校验 → 执行 → 报错回填自修复**。
- 查询安全 = **权限（只读账号）+ 限额（行数/超时）+ 白名单（表）**。
- 代码安全 = **沙箱（容器隔离）+ 资源限制（CPU/内存/时间）+ 输出过滤（截断回填）**。
- 两层防御：静态校验拦看得见的危险，运行时隔离兜绕过的危险；提示词不算防线；"删库"由只读账号最终兜底。
- 沙箱层次：**字符串校验 → 受限执行 → 子进程 → 容器 → 微虚拟机**；原型 L2+L3，生产 L4，高安全 L5。
- 多步循环 + 错误分类恢复 + 评估集（SQL 正确率、答案准确率），是效果的可验证底座。
- 核心原则：**能查就不要算，能算就不要猜；代码执行必须隔离。**
- 这些能力直接支撑：4.7 生产级 Agent 平台（沙箱执行沉淀为平台的"计算机"基础设施）。
