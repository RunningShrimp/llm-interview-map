## 2. 一句话定义

计算机使用 Agent（Computer Use Agent，CUA）是让多模态模型直接操作图形界面（Graphical User Interface，GUI）的 Agent：截图→视觉理解界面→输出坐标与动作（移动、点击、输入、滚动）→执行→再截图验证，循环推进直到任务完成——不依赖目标软件提供 API，人能点的它就能点。

广义的**多模态 Agent（Multimodal Agent）**不止「看屏幕」一种输入：任务指令可以是文本、语音或图像附件，感知可以是屏幕、文档、图像的组合；CUA 是多模态 Agent 目前最大、最成熟的应用形态，本篇以它为主线展开。

简化公式：

```text
CUA = 多模态感知（截图/无障碍树 + 指令文本/语音/附件）
    + 决策（多模态模型理解 + grounding 定位 + 结构化动作输出）
    + 执行（鼠标键盘原语） + 验证（再截图对照预期）
    + 治理（步数预算 / 危险动作闸 / 录屏留痕）
```

## 3. 为什么需要

企业自动化的真实痛点是**覆盖率缺口**：绝大多数存量企业软件（ERP、财务系统、内部审批台）没有开放 API，或 API 覆盖不到全流程；RPA（Robotic Process Automation，机器人流程自动化）能录脚本，但界面一改版就断，且每个流程都要单独开发。

没有 CUA 这块拼图会怎样：

- **无 API 存量系统无法自动化** → 最后一块拼图永远是人工：老 ERP、政务网站、银行后台，接口永远不会为你开。
- **RPA 脆弱** → 界面一改版脚本全断，维护成本随流程数线性增长。
- **跨系统任务靠人肉搬运** → 在 A 系统抄数据、贴到 B 系统，复制粘贴既慢又易错且无法审计。
- **7×24 不可持续** → 人要下班，对账、监控、批处理不会。
- **桌面级任务无法触达** → 浏览器自动化（4.4）只够得着网页，本地客户端、行业软件、系统设置全在网外。

只要人能用这个软件，CUA 就能操作——它用「看屏幕」换来了近乎 100% 的场景覆盖。

| 维度 | API/工具调用 | RPA（脚本录制回放） | Computer Use Agent |
|---|---|---|---|
| 适用前提 | 系统提供接口 | 界面稳定、流程固定 | 只要人能操作即可 |
| 目标系统改造成本 | 需开发对接 | 流程梳理+脚本开发 | 近零（不改造目标系统） |
| 界面改版适应性 | 不受影响 | 改版即断，需重录 | 视觉理解有一定鲁棒性，仍需监控 |
| 泛化迁移 | 每个接口单独接 | 每个流程单独录 | 同一 Agent 可跨软件换任务 |
| 速度/成本 | 最快最省 | 快 | 慢（每步一次截图推理，秒级） |
| 可靠性 | 高 | 稳定流程下较高 | 最低（概率性点击） |
| 安全面 | 小（权限可收敛） | 中 | 大（够得着界面上所有按钮） |

**类比 1（三种进仓库的方式）**：API 像老员工凭工牌走员工通道直达货架——快、准，但前提是仓库认识你（有接口和权限）；RPA 像照着录像带模仿动作的机械臂，货架一重新摆放就撞墙；CUA 像一个看得懂指示牌的新员工，无论布局怎么改都能重新找到货位，但每一步都要停下来看一看、想一想——慢，偶尔走错，但什么仓库都进得去。

结论铁律：**有 API 优先 API，RPA 次之，GUI Agent 是最后手段**。它的价值不是替代前两者，而是补上「无 API 老系统」这块覆盖率为零的拼图——架构师的第一反应应是「为什么不用 API/RPA」，再选最重的锤子。

## 4. 核心原理

### 4.1 感知-决策-执行循环：ReAct 的屏幕版

```text
截图（Observe）→ 理解与定位（Think + Ground）→ 执行动作（Act）→ 截图验证（Verify）→ 循环
```

四拍拆解：

1. **感知**：整屏截图送入视觉语言模型（Vision-Language Model，VLM）；部分方案叠加 DOM 或无障碍树作为辅助感知（路线对比见 4.2）。多模态任务里，指令本身也可能是语音或图像附件（见 4.4）。
2. **理解与定位**：模型读图定位目标元素（grounding，见 4.3），并判断界面状态——有没有弹窗、是否加载中、上一步是否报错。
3. **决策输出**：动作类型+坐标/按键序列，经 1.3 的结构化输出约束为 JSON。常见动作空间：`click`、`double_click`、`type`、`key`、`scroll`、`screenshot`、`wait`、`terminate`。完整操作原语表与执行细节在 4.4，本篇不重复。
4. **验证**：动作后再截图，对照预期确认是否生效。验证是纠错的唯一来源——跳过验证等于让错误单向累积。

与 2.5 ReAct 的对应：截图是 Observation 的来源，动作输出是 Action，新截图即下一次 Observation。循环的终止条件、步数上限、死循环检测，全部沿用 2.5 的防护设计，只是对象换成了屏幕；失败后的恢复阶梯（原地重试→重新感知→回退→重规划→降级→人工接管）已在 4.4 讲透，本篇直接引用。

### 4.2 感知路线三分：截图、无障碍树、混合

4.4 在浏览器语境讲过「DOM 简化 vs 截图」；到了桌面级，问题更复杂——**桌面应用没有统一 DOM**，结构化感知要靠各平台的无障碍树（Accessibility Tree）：Windows 的 UI Automation、macOS 的 AX API、Linux 的 AT-SPI。这是「跨应用」的第一道门槛：同一个 Agent 要面对质量参差的结构化信息源。

| 维度 | 截图路线（纯视觉） | 无障碍树路线（结构化） | 混合路线 |
|---|---|---|---|
| 感知载体 | 屏幕像素 | 各平台无障碍 API 输出的元素树 | 截图 + 元素树/编号标注 |
| 通用性 | 最高：画得出来的都能看（Canvas、远程桌面、纯图标按钮） | 低：依赖应用无障碍实现质量，自绘控件常缺失 | 高：结构化缺失时视觉兜底 |
| 信息保真 | 有损：降采样吃掉小字，OCR（Optical Character Recognition，光学字符识别）错则全错 | 高：元素文本/角色/状态是精确值 | 高：互为校验 |
| 定位方式 | 像素坐标（grounding 难点，见 4.3） | 元素引用（按节点引用点击） | 编号引用为主、坐标兜底 |
| 成本/速度 | 贵且慢（大图多 token） | 便宜且快 | 中 |
| 代表场景 | Claude Computer Use（桌面直控）、远程/虚拟环境 | 桌面辅助技术生态、无障碍实现完善的企业应用 | Browser Use 等开源框架与自研系统 |

选型逻辑与 4.4 的浏览器版一致（能拿结构化就拿结构化，视觉兜底），桌面级新增两个事实：其一，**无障碍树覆盖率不可假设**——大量企业老应用、远程发布的应用、Canvas 重的前端根本没有可用树；其二，**截图是唯一永远可得的感知通道**，所以纯视觉路线是桌面级的通用底座，混合路线是生产主流。

### 4.3 Grounding：把「点那个按钮」翻译成像素坐标

**Grounding（视觉定位/接地）**指把自然语言指称（「提交按钮」「搜索框左边那个图标」）映射到屏幕上具体坐标的能力。它是 CUA 区别于普通工具调用的关键难点：工具调用返回结构化数据，grounding 返回的是连续空间里的一个点——错一厘米就是点错按钮。

**类比 2（电话指路）**：你打电话让朋友帮你点他屏幕上的「红色删除按钮」，你只能用语言描述位置（「右上角，搜索框左边那个」），朋友要把这句话翻译成鼠标位置。grounding 就是这层翻译；偏差不只来自听错话，还来自「朋友的屏幕分辨率和你以为的不一样」。

影响定位精度的四个因素：

- **分辨率与降采样**：截图送模型前常被压缩，小图标、密集表格里的坐标误差被放大。
- **缩放比与多显示器**：设备像素比（Device Pixel Ratio，DPR）、缩放设置、多屏布局让同一逻辑位置对应不同物理坐标，必须统一归一化坐标系。
- **元素外观歧义**：多个相似按钮、纯图标无文字、动态内容（悬浮菜单、自动补全）让指称不唯一。
- **界面动态性**：模型「想」完界面已经变了（弹窗、动画、懒加载），坐标基于过期帧。

提升定位的四类手段：

| 手段 | 做法 | 收益 |
|---|---|---|
| 归一化坐标系 | 全链路统一逻辑坐标，动作前重新截图 | 消除系统性偏移 |
| Set-of-Mark（SoM，标记集提示，Set-of-Mark Prompting，2023） | 在截图上给可交互元素画框编号，模型输出「点 3 号」 | 把开放定位降级为选择题，单步成功率显著提升 |
| 结构化辅助 | 无障碍树/DOM 元素引用替代坐标 | 定位变成查表，覆盖到的部分精度极高 |
| 专项后训练 | 用屏幕定位数据（指称-坐标对、点击轨迹）做 grounding 专项训练 | 模型原生定位精度提升，头部模型演进的主要动力 |

定位精度的独立评测已形成 ScreenSpot 类屏幕 grounding 基准家族（趋势观察口径：各家分数仍在快速刷新，引用时注明基准与口径）。工程上更实用的做法是自建定位测试集：拿自己目标系统的截图，标注「指称→真实坐标框」，定期回归模型的定位误差——grounding 误差是可测量的工程量，不是「模型玄学」。

### 4.4 多模态输入：屏幕 + 指令 + 语音

CUA 的「多模态」不止输出侧看屏幕，输入侧同样多模态。任务指令的四种入口：

| 输入模态 | 形态 | 典型场景 | 新增难点 |
|---|---|---|---|
| 文本指令 | 打字描述任务 | 企业工单、批量任务 | 无 |
| 语音指令 | 边看屏幕边说 | 消费级 Computer Use 主入口（2026）、现场运维 | 自动语音识别（Automatic Speech Recognition，ASR）错误、口语指称更含糊 |
| 图像/文档附件 | 发一张截图/发票/PDF | 「把这张发票录进系统」 | 先从附件抽取结构化字段（OCR/文档理解） |
| 屏幕共享实时流 | 持续看用户屏幕 | 远程协助类产品 | 隐私边界、帧选择（何时截图） |

语音入口值得单独说：它改变产品形态——「边看边说」让 CUA 从「写工单给机器人」变成「带实习生干活」。代价是指称歧义急剧上升：口语里大量「点那个」「就刚才那个」，全靠当前屏幕上下文消歧，这是 grounding 压力的另一个来源。工程对策两条：语音转文本后与截图**同帧绑定**（指令必须锚定在转写时刻的界面状态上）；指称无法消歧时反问而不是猜。

多模态输入组合也影响成本：语音与附件都增加前置处理步骤（ASR、OCR、文档解析），这些步骤的错误以「输入噪声」形式进入循环。多模态 Agent 的失败归因要能区分「没看懂屏幕」「没听懂指令」「定位错了」三类——日志里必须可分离，否则 bad case 归因会系统性失真。

### 4.5 桌面级与跨应用编排：与浏览器自动化（4.4）的分工

4.4 的主战场是浏览器标签页内；CUA 的主战场是**整块桌面**——多个应用、窗口、文件系统与系统级 UI 同时在场。这不是规模差异，是能力差异：

| 维度 | 浏览器自动化（4.4 主线） | 桌面级计算机使用（本篇主线） |
|---|---|---|
| 控制范围 | 单浏览器实例、页面 DOM | 整个操作系统会话：任意应用+窗口+文件+系统对话框 |
| 感知底座 | DOM/无障碍树可得（网页标配） | 无障碍树覆盖不可假设，截图是唯一保底 |
| 动作对象 | 页面元素 | 全局键盘鼠标（含应用切换、拖拽、系统快捷键） |
| 跨应用数据流 | 标签页间复制 | 剪贴板/文件系统作为跨应用总线 |
| 特有干扰 | 弹窗、iframe、反爬 | 系统通知、更新弹窗、多窗口遮挡、输入法、锁屏 |
| 安全边界 | 域名白名单可收敛 | 「够得着界面上所有按钮」——包括系统设置与删除入口 |
| 执行环境 | 容器/无头浏览器即可 | 通常需要完整虚拟机（隔离需求直接衔接 H.8） |

桌面级新增的三件事：

1. **窗口与应用管理**：任务图跨多个应用——先按 2.2 的规划把任务拆成「在哪个应用里做什么」的子目标序列，Agent 再逐个执行，期间要会切换应用、排列窗口、处理系统级「保存/放弃」对话框。
2. **跨应用数据搬运**：A 应用复制、B 应用粘贴，剪贴板与临时文件是事实上的跨应用总线——这既是能力（打通数据孤岛）也是风险（敏感数据落剪贴板/临时文件，治理要管）。
3. **系统级异常态**：系统更新弹窗、通知横幅、锁屏/屏保、输入法状态，这些浏览器世界不存在的干扰在桌面世界无处不在，异常态清单要按操作系统分别枚举。

**面试高频问法**：「Computer Use 类 Agent 什么场景适合用？与 API/RPA 怎么取舍？」共识口径：跨多个无 API 桌面系统的长流程（财务对账、跨系统录单）是甜点区；有 API 用 API、界面稳定流程固定用 RPA；CUA 补的是「无 API 且界面常变」的缺口，且必须配监督式部署（见 4.10）。

### 4.6 产品格局剧变（2025-2026）

引用产品案例前先对时间线——这是趋势观察期最容易翻车的地方：

| 时间 | 事件 | 影响 |
|---|---|---|
| 2024-10 | Anthropic 发布 computer use 能力（API beta） | GUI Agent 走进开发者视野 |
| 2025-01 | OpenAI 发布 Operator（CUA 模型驱动） | 托管式浏览器 Agent 面向消费者 |
| 2025-07 | OpenAI 发布 ChatGPT Agent | 通用 Agent 形态上线 |
| 2025-08-31 | Operator 关停，能力并入 ChatGPT Agent | 独立浏览器 Agent 产品线收束 |
| 2026-03 | Anthropic 推出面向消费者的 Claude Computer Use（Mac 桌面直控） | 从开发者 API 走向 C 端，语音/屏幕多模态入口成为标配 |
| 2026-06-03 | OpenAI 通知弃用 Agent Builder | 低代码 Agent 编排工具线收缩 |
| 2026-08-26 | Assistants API 关停（定档） | OpenAI 工具线整合，新接口体系成为主线 |

读法：格局从「多家独立产品并行」收敛为「少数通用 Agent 主线+模型能力 API」。面试引用案例时以最新格局为准——提 Operator 必须补一句「已并入 ChatGPT Agent」；引用 OpenAI 工具链时注意 Assistants API 已于 2026-08 关停、Agent Builder 已弃用。用 2025 年初的产品格局答题，等于暴露信息过期。

两家代表两种产品形态：OpenAI 把环境托管起来卖服务，Anthropic 把模型能力下放、让开发者自建循环与环境。

| 维度 | OpenAI CUA 线（Operator→ChatGPT Agent） | Anthropic Claude Computer Use |
|---|---|---|
| 提供形态 | 托管 Agent 产品（Operator 能力并入 ChatGPT Agent）；模型能力亦经 API 提供 | 模型能力以 computer use 工具形式经 API 提供（自 beta 起持续迭代），官方提供参考实现 |
| 宿主环境 | 浏览器类任务跑在 OpenAI 托管的虚拟浏览器里 | 开发者自建虚拟机/容器（官方参考实现基于 Docker 容器），可操控完整桌面 |
| 感知输入 | 截图（低分辨率优化吞吐） | 截图为主；配套 bash、文本编辑等辅助工具 |
| 集成方式 | 产品内对话即用；API 侧作为工具接入自有循环 | 自己写感知-决策-执行循环，灵活性高、工程量大 |
| 适合谁 | 面向消费者的通用任务（订票、购物、填表） | 企业内网系统、桌面软件等需要自定义执行环境的场景 |

### 4.7 端到端任务基准：OSWorld/WebVoyager 类与量级口径

CUA 的评测分两层：**单点能力**（grounding 精度，ScreenSpot 类）与**端到端任务成功率**（End-to-End Task Success Rate，给一个自然语言任务，看 Agent 能否在真实环境里做完）。后者才是产品口径，主流基准家族：

| 基准 | 环境 | 任务形态 | 口径要点 |
|---|---|---|---|
| OSWorld | 真实操作系统（多应用桌面） | 跨应用办公任务（文件、邮件、表格等） | 最接近桌面级 CUA；有 -Verified 变体（人工校验初始状态与成功判据） |
| WebVoyager | 真实网站 | 网页任务（搜索、订票、填表） | 浏览器 Agent 主口径；与 OSWorld 分数不可横比 |
| AndroidWorld 类 | 移动端模拟器 | 手机应用任务 | 移动 CUA 口径；触控手势动作空间 |

量级与趋势（截至 2026 年，趋势观察口径）：

- 2025 年初：主流模型在 OSWorld 上成绩普遍落在 **15%-38%** 区间——五分之四的任务做不完。
- 2026 年：头部方案爬升到 **72%-89%** 区间（含开源方案 Browser Use 宣称 89.1% WebVoyager 的社区口径；各厂商官方口径的具体模型版本号与分数迭代快，引用时以官方文档为准并注明基准名）。

从严解读三点：

1. **基准分不等于生产可用**：基准任务定义清晰、环境干净；生产任务更长、界面更脏、干扰更多。
2. **分数口径不可横比**：OSWorld 与 WebVoyager 任务集不同，是否 verified 口径不同，产品宣称与第三方复测之间也存在差距——引用时注明基准名。
3. **即便单任务 80%+，完全自主仍不成立**：长任务与高危场景必须保留人工闸，这是各家产品仍设监督机制的共同原因。

演进归因：视觉定位专项训练提升点击精度、推理模型带来的多步规划与自纠错、Set-of-Mark 类辅助感知、computer use 专项后训练——四股力量叠加，而非单一突破。

### 4.8 步级错误累积：CUA 的核心数学

**任务成功率 = 单步成功率的连乘**（步级错误累积，Step-level Error Accumulation）。

```text
单步 95% →  8 步任务  66% → 30 步任务  21% → 50 步任务 7.7%
单步 99% →  8 步任务  92% → 30 步任务  74% → 50 步任务 60%
```

与 2.9 的复合失败率（95%^8≈66%）是同一个公式，只是步数被 GUI 任务拉得更长。三个推论：

1. **任务长度是隐形杀手**：单步看着不错，乘到几十步就归零。拆子任务、加检查点是唯一解。
2. **验证步不是开销而是止损**：每步验证把「错误传染」变成「错误拦截」——点错后立刻发现回退，比 10 步之后发现重来便宜一个量级。
3. **步数预算是硬约束**：无上限循环的期望结局是死循环（反复点刷新、关不完的弹窗）。步数+token 双阈值刹车，是 2.5 防护设计在屏幕上的直接应用。

本篇对 4.8 只补一条 CUA 特有观察：**视觉验证的「通过」也可能是假的**——截图看起来对（页面渲染相似）但数据没提交成功。高危步骤的验证断言要落到数据侧（订单号存在、列表条目数变化），不能只看截图像不像。

### 4.9 生产化挑战：可靠性、速度、成本三角

CUA 的生产化卡在一个三角里，任意两项的改善都在挤压第三项：

| 挑战 | 表现 | 量级（示意） | 缓解手段 | 缓解的代价 |
|---|---|---|---|---|
| 可靠性 | 步级错误累积、grounding 概率误差、异常态长尾 | 见 4.8 连乘 | 每步验证+检查点+SoM | 步数与 token 增加 |
| 速度 | 每步一次「截图+推理」，端到端分钟级 | 单步 3-10 秒；30 步任务约 2-5 分钟（与人工操作同量级） | 降截图分辨率、独立子任务并行 | 分辨率降则 grounding 精度降；并行则编排复杂度升 |
| 成本 | 大图多 token，长任务成本随步数线性涨 | 单步截图输入数千 token；50 步任务的成本为等价 API 调用的数十倍量级（示意） | 结构化感知替代截图、界面指纹缓存 | 覆盖率降、工程量增 |

三角的工程含义：CUA 不适合高频任务——**它自动化的是「人工分钟级」的任务，省的是人力分钟，不是毫秒**。若一个任务每天跑一万次，CUA 的延迟与成本会吃掉全部收益，那该去推动开 API；若一个月跑一千次、每次省 8 分钟人工，CUA 的经济账才成立（案例 A 即此形状）。成本与延迟的体系化计算方法见 3.7。

**面试高频问法**：「Computer Use Agent 为什么还不能大规模无人值守？」共识口径：不是单点能力不足，是步级错误累积、grounding 概率误差、异常态长尾三者的乘积效应；对策不是等模型变强，而是监督式部署+危险动作人工闸+沙箱隔离（H.8）的组合工程。

### 4.10 部署模式：监督式而非全自动

| 模式 | 行为 | 适用 |
|---|---|---|
| 全自动 | 无人值守跑完全程 | 仅限只读、可逆、沙箱内任务 |
| 监督式（生产默认） | 每步可观测；危险动作挂起等人确认 | 大多数生产场景 |
| 半自动 | 低风险步骤自动，提交/支付类人工点击 | 资金、数据变更场景 |
| Shadow（影子模式） | 只记录计划动作不执行，人工复核准确率 | 引入期验证 |

安全三件套贯穿所有模式：**危险操作白名单+人工确认、全程录屏留痕、失败自动暂停转人工**。执行环境本身还要隔离（虚拟机/容器、最小权限账号、网络白名单）——那正是 H.8 的主题。

与 H.8 的衔接先立结论：**没有沙箱就没有监督式部署**。原因有三：其一，CUA 的动作面是「整个桌面」，不隔离就等于把管理员权限交给概率模型；其二，录屏与逐步留痕需要环境级 hook，只有受控环境能稳定提供；其三，检查点续跑要保存完整环境状态（窗口、会话、文件），只有可快照的沙箱环境做得到。沙箱技术选型（微虚机/容器/沙箱运行时、隔离强度与冷启动取舍）在 H.8 展开。

## 5. 架构 / 流程

多模态 Agent 的感知-决策-执行全景（桌面级 CUA 视角）：

```text
任务输入（多模态）
  ├ 文本指令 ├ 语音指令（ASR 转写） ├ 图像/文档附件（OCR/解析）
  └ 全部锚定到同一份任务上下文（与首帧截图同帧绑定）
        |
┌───────▼─────────────────────────────────────┐
│ 执行环境：隔离 VM/沙箱（H.8 主题）            │
│  ├ 完整桌面 + 多应用 + 文件系统               │
│  ├ 专用最小权限账号（非管理员）               │
│  └ 网络白名单                                │
└───────┬─────────────────────────────────────┘
        ▼
┌──── 感知-决策-执行循环（ReAct 变体）────────────────┐
│ 1 感知：整屏截图（永远可得）                       │
│   └ 叠加：无障碍树 / SoM 编号（可得时，见 4.2/4.3） │
│        ↓                                          │
│ 2 理解与定位：VLM 读图 → 界面状态判断 → grounding   │
│        ↓                                          │
│ 3 决策：动作+坐标（1.3 结构化输出约束 JSON）       │
│        ↓                                          │
│ 4 安全闸门：命中危险操作白名单？                   │
│   ├ 是 → 挂起 → 人工确认 / 拒绝                   │
│   └ 否 ↓                                          │
│ 5 执行：鼠标键盘原语（点击/输入/滚动/快捷键）       │
│        ↓                                          │
│ 6 验证：再截图对照预期；高危步骤加数据侧断言        │
│        ↓                                          │
│ 7 检查：完成？步数/token 预算？停滞检测？          │
│   └ 未完成且未熔断 → 回到 1；熔断 → 存档转人工     │
└──────────────┬────────────────────────────────────┘
               ▼
┌──── 治理层 ─────────────────────────────────────┐
│ 录屏留痕 ｜ 每步日志（截图+动作+决策理由）        │
│ 异常告警：界面改版 / 死循环 / 失败暂停           │
│ 复盘：轨迹回放 → bad case → 评估集回归（3.4）    │
└─────────────────────────────────────────────────┘
```

读图三点：第一，循环七拍里第 4 拍（安全闸）与第 6 拍（验证）是 CUA 区别于普通 Agent 循环（2.5）的新增固定环节；第二，多模态输入在进循环之前就要与任务上下文锚定，语音/附件的预处理错误是独立失败源，日志要可归因；第三，治理层不是可选项——趋势观察期的生产部署里，「可审计」与「能跑通」同等重要。

### 6.1 桌面级最小循环：截图→决策→动作（含坐标归一化）

```python
# cua_minimal.py —— 桌面级「截图-决策-动作」最小循环（简化骨架）
# 依赖：pip install pyautogui pillow
import pyautogui

SCREEN_W, SCREEN_H = pyautogui.size()   # 逻辑分辨率：全链路统一坐标系
MAX_STEPS = 25

def normalize(coord: tuple[int, int]) -> tuple[int, int]:
    """把模型输出的 0-1000 归一化坐标映射回屏幕像素。
    统一归一化是抗分辨率/DPR 变化的第一道防线（4.3）。"""
    x, y = coord
    return int(x / 1000 * SCREEN_W), int(y / 1000 * SCREEN_H)

def decide(screenshot_path: str, task: str, history: list[dict]) -> dict:
    """接多模态模型：截图+任务+历史 → JSON 动作（1.3 结构化输出约束）。
    输出示例：{"action": "click", "coordinate": [512, 300],
              "expect": "出现系统设置窗口"}"""
    raise NotImplementedError("接入多模态模型")

def run(task: str) -> None:
    history: list[dict] = []
    for step in range(MAX_STEPS):
        pyautogui.screenshot("screen.png")            # 1 感知：整屏截图
        action = decide("screen.png", task, history)   # 2+3 理解定位与决策
        if action["action"] == "terminate":
            break                                      # 终止出口，防"做完还在点"
        if action["action"] == "click":
            x, y = normalize(action["coordinate"])     # 归一化坐标回像素
            pyautogui.click(x, y)                      # 4 执行
        elif action["action"] == "type":
            # 中文输入不能 typewrite（键序映射不到），走剪贴板粘贴
            import pyperclip
            pyperclip.copy(action["text"])
            pyautogui.hotkey("command", "v")           # Windows 为 ctrl+v
        history.append({"step": step, "action": action})
        pyautogui.screenshot(f"verify_{step}.png")     # 5 验证：留档对照 expect
    # 生产实现必补：危险词闸、停滞检测、步数+token 双预算（见 6.4 与 4.10）

run("打开系统设置，把深色模式关闭")
```

浏览器实例的等价循环（Playwright 工具箱版）在 4.4 的代码节已成稿，此处不重复；桌面与浏览器的差异只在于动作通道（全局鼠标键盘 vs 页面 API）与感知保底（截图 vs DOM）。

### 6.2 无障碍树感知：把开放定位降级为选择题

```python
# a11y_perceive.py —— 无障碍树感知 + 元素引用动作（简化示意）
# 桌面级对应物：Windows UI Automation / macOS AX API / Linux AT-SPI，
# 形态同为「元素树 → 展平编号清单 → 按编号引用」。
from playwright.async_api import async_playwright

INTERACTIVE = {"button", "link", "textbox", "combobox", "menuitem", "tab"}

async def perceive(page) -> list[dict]:
    """提取无障碍树，输出带编号的可交互元素清单（Playwright 亦有
    ariaSnapshot 等新接口，输出形态类似）。"""
    snap = await page.accessibility.snapshot(interesting_only=True)
    elements: list[dict] = []

    def walk(node: dict) -> None:
        if node.get("role") in INTERACTIVE:
            elements.append({
                "ref": len(elements),                  # 编号即动作引用
                "role": node["role"],
                "name": (node.get("name") or "")[:40],  # 截断防超长
            })
        for child in node.get("children", []) or []:
            walk(child)

    walk(snap)
    return elements

async def act_by_ref(page, elements: list[dict], ref: int,
                     text: str | None = None) -> None:
    """按编号执行动作：定位精度来自树结构而非视觉坐标（4.3 的结构化辅助）。"""
    target = elements[ref]  # 生产实现：把 ref 解析回选择器/AX 节点并校验仍存在
    if target["role"] == "textbox":
        await page.get_by_role("textbox", name=target["name"]).fill(text or "")
    elif target["role"] in {"button", "link", "tab"}:
        await page.get_by_role(target["role"], name=target["name"]).click()
```

### 6.3 Set-of-Mark 叠加：给截图画框编号

```python
# som_overlay.py —— 在截图上给可交互元素画框编号（Set-of-Mark，4.3）
from PIL import Image, ImageDraw, ImageFont

def overlay(screenshot: str, boxes: list[dict], out: str = "som.png") -> str:
    """boxes: [{"bbox": [x1,y1,x2,y2], "label": "提交订单"}, ...]
    框来源可以是无障碍树/DOM 检测，也可以是检测模型。叠加后送模型，
    动作空间从"输出坐标"变成"输出编号"，开放定位降级为选择题。"""
    img = Image.open(screenshot).convert("RGB")
    draw = ImageDraw.Draw(img)
    font = ImageFont.load_default(size=16)
    for i, b in enumerate(boxes):
        x1, y1, x2, y2 = b["bbox"]
        draw.rectangle([x1, y1, x2, y2], outline="red", width=3)
        draw.text((x1, max(0, y1 - 18)), f"[{i}] {b['label']}",
                  fill="red", font=font)
    img.save(out)
    return out
```

### 6.4 computer use 工具风格的循环（Python 简化骨架）

```python
# cu_loop.py —— computer use 工具风格的感知-决策-执行循环（简化示意）
import json

MAX_STEPS = 25

def screenshot_b64(vm) -> str: ...      # 从隔离 VM/容器截屏并编码
def send_to_model(messages): ...        # 调多模态模型，附带 computer use 工具定义
def run_in_vm(vm, action: dict): ...    # 在 VM 里执行 click/type/key/scroll

def run_task(task: str, vm) -> str:
    messages = [{"role": "user", "content": task}]
    for _ in range(MAX_STEPS):
        resp = send_to_model(messages)                    # 模型基于最新截图决策
        for block in resp.content:
            if block["type"] == "tool_use" and block["name"] == "computer":
                action = block["input"]   # 如 {"action":"click","coordinate":[1120,640]}
                run_in_vm(vm, action)                     # 执行
                messages.append({"role": "assistant", "content": resp.content})
                messages.append({
                    "role": "user",
                    "content": [{
                        "type": "tool_result",
                        "tool_use_id": block["id"],
                        "content": screenshot_b64(vm),    # 新截图作为 Observation 回传
                    }],
                })
            elif block["type"] == "text" and "任务完成" in block.get("text", ""):
                return block["text"]
    return "步数预算耗尽，转人工"

if __name__ == "__main__":
    print(json.dumps({"result": run_task("把附件发票录入报销系统", vm=None)},
                     ensure_ascii=False))
```

## 7. 案例

### 案例 A：无 API 老报销系统的财务自动化

**场景**：某制造企业 3 套老财务系统均无 API，财务每月手工录入约 1200 笔报销单。

**实施**：阶段一 Shadow 模式 4 周——Agent 每步只输出「计划动作序列」，不实际执行，人工逐条复核；计划操作准确率从 71% 提到 93%（补界面锚点提示与示例轨迹）。阶段二半自动——读取、填表自动执行，最终提交动作保留人工点击；执行环境为独立虚拟机+专用只读账号，全程录屏。

**效果**：单笔处理时间从约 11 分钟降到 3 分钟；因提交必须人工确认，上线至今零资金误操作；步数预算耗尽自动转人工的比例约 6%，构成持续改进的 bad case 池。经济账形状即 4.9 所述：月千次、每次省 8 分钟，CUA 的成本占比可忽略。

### 案例 B：电商运营后台批量改价——界面改版翻车与恢复

**场景**：某电商团队用 CUA 每月批量调整约 500 个 SKU 的价格与库存页签。

**过程**：稳定运行 3 个月后运营后台改版，按钮布局变化；首次执行时每步验证截图与预期不符率飙到 100%，停滞告警 3 分钟内触发，系统自动暂停并降级为人工处理——没有错价上线。随后用新截图重校准定位提示（约 2 人日）恢复运行。

**结果**：结论是「界面改版不是事故而是常态」，可观测告警+降级预案必须作为部署的一部分设计，而不是事后补救。

### 案例 C：跨 4 个系统的客服工单流转——拆任务对抗步级错误累积

**场景**：某物流公司客服工单要在 4 个无 API 系统间查询、回填、流转，单任务平均约 47 步。端到端全自动首月任务成功率仅 68%——正是步级错误累积（单步约 99%，47 步连乘约 62%-68%）。

**改造**：把任务拆成 5 段子任务（查单、核对、填单、校验、流转），每段之间设截图检查点，失败从检查点续跑而非从头重试；跨系统提交动作保留人工确认。

**效果**：任务成功率提升到 91%，平均重试成本下降过半。验证 4.8 的推论：拆任务+检查点是长任务的唯一解。

### 案例 D：语音驱动的跨应用运维巡检——多模态输入与桌面直控

**场景**：某连锁零售的 IT 运维团队，值班工程师早上一句语音「跑一遍门店系统巡检」，Agent 在桌面上跨 4 个工具（监控台、VPN 客户端、工单系统、Excel）完成巡检并回填报告。

**做法**：语音经 ASR 转任务单，并与转写时刻的桌面截图**同帧绑定**（4.4 的对策）；跨应用步骤用窗口标题定位应用，数据经剪贴板搬运；Excel 汇总段无障碍树可得，改用元素引用而纯截图只用于监控台（自绘图表）；重启服务类动作挂人工确认。

**效果**：单次巡检从约 40 分钟人工降到约 12 分钟；语音指称消歧失败率初期约 8%，加入「无法消歧即反问」后降到 2% 以下；重启类操作 100% 人工确认。三类失败源（看错屏/听错话/定位错）在日志中可分离归因。

## 8. 常见坑

1. **有 API 却硬上 GUI**。
   CUA 慢、脆、安全面大，是兜底不是首选。先穷尽 API/RPA/导出文件三条路。
2. **跳过每步截图验证**。
   点错了到第 10 步才发现，只能全部重来。每步验证把错误传染变错误拦截。
3. **危险按钮不设闸**。
   「删除」「支付」被概率性点中就是事故。白名单+人工确认+录屏三件套缺一不可。
4. **界面改版无告警**。
   改版后静默点错。验证不符率异常即告警，并预置降级人工预案。
5. **坐标不抗分辨率变化**。
   截图缩放、DPR 不同导致系统性偏移。统一归一化，必要时用 Set-of-Marks 类辅助定位。
6. **假设无障碍树总是可得**。
   企业老应用、自绘控件、远程桌面常常没有可用树。感知层以截图保底，树只是增强。
7. **循环无步数与预算上限**。
   弹窗反复出现导致死循环烧钱。步数+token 双阈值，停滞检测强制终止。
8. **把基准分当生产可靠性**。
   80% 的单任务成功率在 47 步任务上不剩多少。用自己的任务集做 Shadow 实测。
9. **无 Shadow 期直接上生产**。
   首日就在真实数据上点按钮。先影子模式复核计划准确率，逐级放行。
10. **执行环境不隔离**。
    直控员工主机等于把管理员权限交给概率模型。独立 VM/容器+最小权限账号+网络白名单（H.8）。
11. **不留痕无法审计**。
    出事答不出「Agent 当时看到了什么、为什么点」。截图+动作+理由逐步落盘，全程录屏。
12. **异常态无处理**。
    弹窗、验证码、多标签页、系统通知一出现就卡死。识别已知异常态并定义处理策略，未知态暂停转人工。
13. **长任务无检查点**。
    第 40 步失败从第 1 步重来。拆子任务+检查点续跑。
14. **凭证权限过大**。
    用管理员账号跑 GUI Agent。专用账号最小权限，敏感页面不进任务范围。
15. **语音/附件输入不锚定界面状态**。
    转写时刻与截图时刻错位，口语指称「刚才那个」无处消歧。指令与截图同帧绑定，无法消歧就反问而不是猜。
16. **视觉验证只看「像不像」**。
    渲染相似但数据未提交，验证假通过。高危步骤断言落到数据侧（订单号、条目数变化）。
17. **引用产品格局过期**。
    还在把 Operator 当独立产品讲。Operator 已并入 ChatGPT Agent；Agent Builder 弃用、Assistants API 2026-08 关停。

## 9. 练习

1. 用 pyautogui 写最小循环：截图→由人扮演决策者（打印截图给键盘输入）→执行动作，跑通「打开系统设置改一个开关」。
2. 把决策函数接到任意多模态模型，完成一次静态表单填写，统计 20 次的单步成功率与任务成功率，验证连乘公式（4.8）。
3. 实现危险词白名单+人工确认闸：构造一个「提交」按钮场景，确认命中时流程挂起。
4. 故意把按钮位置改版（改 CSS 或挪窗口），验证「验证不符率」告警能触发。
5. 构造一个会反复弹窗的页面，观察无预算上限的循环行为，然后加步数+停滞检测对比。
6. 用无障碍树感知（6.2）替换 6.1 的纯截图感知跑同一任务，对比定位误差、token 成本与覆盖率（哪些元素树里没有）。
7. 给 6.1 加 SoM 叠加（6.3）：先从树/检测拿到元素框，再让模型按编号输出动作，对比纯坐标路线的单步成功率。
8. 同一任务分别用截图感知与 DOM/树感知实现，对比界面改版后两者的失效模式差异（衔接 4.4 的练习 6）。
9. 复刻 Shadow 模式：让 Agent 输出计划动作序列而不执行，人工标注 50 步的计划准确率，写一份可靠性边界评估备忘（趋势观察口径：明确说明这是开放讨论题素材而非真题背诵）。
10. 给第 2 题的任务加检查点续跑，对比拆分前后任务成功率与平均重试成本。

## 10. 小结

- 定义：**截图→理解→动作→再截图验证**的循环，鼠标键盘为手、多模态视觉为眼——不依赖 API 驱动任何软件。
- 定位铁律：**有 API 优先 API，RPA 次之，GUI Agent 是最后手段**——价值在补覆盖率，不在替代接口。
- 循环节拍就是 2.5 的 ReAct：截图是 Observation，动作是 Action，验证是纠错与止损的唯一来源；动作 JSON 靠 1.3 的结构化输出约束。
- 感知路线三分：**截图（通用保底）、无障碍树（精确但覆盖不可假设）、混合（生产主流）**——桌面级没有统一 DOM，是与浏览器路线（4.4）的分水岭。
- Grounding 是 CUA 特有关卡：把语言指称翻译成像素坐标；归一化、Set-of-Mark、结构化辅助、专项后训练四类手段，定位误差要当工程量量化回归。
- 多模态输入（屏幕+指令+语音+附件）改变产品形态也带来新失败源——指令与截图同帧锚定，失败归因要能区分看错屏/听错话/定位错。
- 形态两分：**OpenAI 托管产品线（Operator 已并入 ChatGPT Agent）vs Anthropic 能力下放（computer use 工具+自建循环）**。
- 格局剧变（2025-2026）：Operator 2025-08-31 关停并入 ChatGPT Agent；OpenAI 弃用 Agent Builder、Assistants API 2026-08-26 关停——引用案例以最新格局为准。
- 可靠性演进：**15-38%（2025 初，OSWorld）→ 72-89%（2026，含社区口径 89.1% WebVoyager）**——基准分不等于生产可用，口径不可横比。
- 核心数学：**任务成功率=单步成功率连乘**（95%^8≈66%）——拆子任务+检查点是长任务唯一解；视觉验证要补数据侧断言。
- 生产化三角：可靠性/速度/成本互相挤压——CUA 自动化的是「人工分钟级」任务；部署默认**监督式**（危险闸+录屏+失败转人工），引入路径 Shadow→半自动→逐级放行。
- 状态口径：**趋势观察**——社区热度高但截至 2026-09 未进确证真题，面试答机制+格局+诚实边界，不吹不贬；站内衔接：入门实操在 4.4，评估方法论回看 2.9，成本体系见 3.7。
- 这些能力直接支撑：H.8 Agent 沙箱与可靠执行——没有隔离执行环境，监督式部署就没有物理基础。
