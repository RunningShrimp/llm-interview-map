# 讲解 5.5 阶段 4：AI 工程化

> 说明：前置是 5.4 阶段 3（RAG 与工具增强），你手里已有一个带引用与检索评估的知识库问答 Agent 原型；工程化的知识原理一律指路 3 层锚点（重点 3.4–3.9），本篇不重复展开。  
> 5.x 是学习路径篇，不讲新知识，讲**阶段作战计划**：本篇把 3 层工程化知识组队成一条可执行的顺序，带你分六个迭代把原型部署成"带监控与评估的 Agent API"，并给出里程碑自检表与卡点解法。核心是从"能跑通"到"敢上线"。  
> 应用层的评估与可观测在 1.6、安全与成本在 1.7 有入门版本可对照；验收通过后进入 5.6 阶段 5：多 Agent 与生产。

## 1. 定位

学习路径的第 5 个阶段，对应知识地图的 3 工程化层（3.1–3.10），属于"从原型到生产"的工程化跨越期。  
它解决一个核心问题：**Agent 原型在本地能跑，但如何让它 7×24 稳定运行、可监控、可评估、可回滚、成本可控、安全合规？**

对学习者，它是一份阶段作战计划：学什么、按什么顺序学、做什么项目、怎么验收。  
对知识地图，3.1–3.10 是"兵种"，5.5 负责把它们编成"作战序列"，再用一个生产级项目把知识串起来。它是 5.6 多 Agent 与生产、5.7 综合项目与作品集的直接前置——5.6 的多 Agent 系统与 5.7 的作品集指标，全部跑在本阶段建好的观测、评估、发布底座上。

本阶段口径（与知识地图一致）：

| 项 | 内容 |
|---|---|
| 目标 | 可观测、评估、部署、CI/CD、成本控制 |
| 项目 | 部署一个带监控与评估的 Agent API |
| 里程碑 | 有 trace、评估集、灰度、回滚、预算告警 |
| 前续 | 5.4 阶段 3：RAG 与工具增强 |
| 后续 | 5.6 阶段 5：多 Agent 与生产 |

## 2. 一句话定义

阶段 4 AI 工程化，是把架构设计、可观测性、评估体系、部署扩展、成本控制、安全合规、CI/CD 与人机协同组队起来，独立把 Agent 原型变成可观测、可评估、可部署、可回滚、成本可控的生产系统的工程实践阶段。

简化公式：

```text
阶段 4 = 架构 + 数据 + 可观测 + 评估 + 部署 + 成本 + 安全 + CI/CD + 人机协同
交付口径 = 有 trace + 评估集 + 灰度 + 回滚 + 预算告警（五件套，缺一不可验收）
```

## 3. 为什么需要

原型和生产之间有一道鸿沟，跳过工程化直接上线会遇到：

- **本地能跑，线上崩**：并发一上来，内存、超时全部暴露——笔记本单进程扛不住真实流量。
- **出了问题不知道**：没有日志、链路追踪（Tracing）、监控，用户投诉了才知道挂了。
- **改了不知道好坏**：没有评估集、没有回归对比，每次改提示词（Prompt）都是赌博。
- **成本失控**：多轮 Agent 的 token 消耗按轮数复利增长，一个死循环能把日预算烧穿。
- **安全漏洞**：越权调用工具、提示词注入（Prompt Injection）、数据泄露。
- **无法回滚**：新版本出问题只能现场改代码"热修"，修的动作比坏的更危险。
- **合规不通过**：没有审计、没有权限控制，金融、医疗场景直接一票否决。
- **无法扩展**：流量一上来就崩，扩容靠人肉。

"跳过 vs 先过"对比：

| 维度 | 跳过工程化直接上线的原型 | 先过阶段 4 再上线 |
|---|---|---|
| 出故障 | 用户先发现，定位靠猜，恢复靠重启 | 告警先响，按 trace 定位，按预案回滚 |
| 改提示词 | 凭感觉改，改坏了不知道 | 评估集回归 + CI 门禁，坏改动进不了主干 |
| 发布 | 手工拷贝，全量切换，错了回不去 | 镜像版本化，灰度爬坡，一键回滚 |
| 成本 | 月底看账单才发现超支 | 按租户、模型归因，预算 80% 即告警 |
| 安全 | 任何人拿到接口就能调任何工具 | 认证 + 权限 + 审计，越权被拦截且留痕 |
| 整体节奏 | 上线快三天，之后天天救火 | 慢一周搭底座，之后迭代越来越快 |

两个类比，具体到场景：

```text
造车：  阶段 3 = 造出一辆能开的车（发动机 = LLM，方向盘 = 工具调用）；
        阶段 4 = 装仪表盘（可观测）、装导航与路考（评估）、装刹车和安全气囊（回滚与降级）、
        记油卡账单与限速提醒（预算告警）、上牌照买保险（安全合规）——不装这些，不敢上高速。
开餐厅：原型 = 在家做菜请朋友吃，咸淡自己尝；生产 = 开餐厅——后厨要有监控（trace），
        菜品要试吃打分（评估集），新品先在半页菜单试卖（灰度），卖砸了连夜换回老菜单（回滚），
        每天要盘成本流水（预算告警），后厨动火要有消防验收（安全合规）。
```

### 4.3 学习顺序与依赖（周计划表）

顺序的依据只有一条链：看不见就无法优化（3.4 先行），没有评估就是赌博（3.5 次之），灰度与回滚要有部署舞台（3.6），流量与账单随部署而来（3.7），CI/CD 把前四步串成发布链路收口（3.9 最后）。3.1 的架构思维提前一天读，防止返工；3.8 安全与 3.10 人机协同作为支撑模块随项目接入。

| 步骤 | 锚点 | 为什么排在此时 | 产出物 | 参考时长 |
|---|---|---|---|---|
| 1 | 3.4 可观测性与追踪 | trace 与指标是评估归因、成本归因、回滚判断的共同数据源 | 迭代一：每次请求有完整 trace 与 5 个关键指标 | 1 周 |
| 2 | 3.5 评估体系与实验管理 | 上线前必须有客观标尺；评估集是 CI 门禁的原料 | 迭代二：三层评估集与基线；迭代三：CI 门禁（提前接触 3.9） | 1 周 |
| 3 | 3.6 部署与扩展 | API 要从笔记本搬进集群，灰度与回滚才有舞台 | 迭代四：Docker + K8s + HPA 上线 | 1 周 |
| 4 | 3.7 成本、延迟与可靠性 | 流量与账单同时到来；成本归因依赖 3.4 的数据 | 成本看板 + 模型路由与缓存改造 | 1 周 |
| 5 | 3.9 CICD、版本管理与发布 | 版本化一切 + 评估门禁 + 灰度 + 回滚，集成收口 | 迭代五：灰度与自动回滚；迭代六：预算告警接入告警通道 | 1 周 |
| 6 | 3.1 / 3.8 / 3.10（支撑收口） | 架构复盘、安全加固、人机审批贯穿全程，最后统一验收 | 值班手册 + §4.5 自检表逐项通过 | 3–5 天 |

顺序图：

```text
3.4 可观测性与追踪
   ↓
3.5 评估体系与实验管理（提前接触 3.9 的自动化测试）
   ↓
3.6 部署与扩展
   ↓
3.7 成本、延迟与可靠性
   ↓
3.9 CICD、版本管理与发布（集成收口：灰度 + 回滚）
   ↓
项目：带监控与评估的 Agent API（§6，六个迭代）
```

五条原则：

- **先可观测，后优化**：看不见就无法优化。
- **先评估，后上线**：没有评估的变更就是赌博。
- **先安全，后开放**：权限与审计是底线。
- **先灰度，后全量**：灰度是保命符。
- **先成本，后规模**：成本不可控，规模越大越危险。

### 4.5 里程碑自检表：有 trace、评估集、灰度、回滚、预算告警

把五个里程碑拆成可逐项打分的自检表，全部达到合格口径才算通过：

| 自检项 | 合格口径 | 不合格信号 | 对应锚点 |
|---|---|---|---|
| 有 trace | 凭一个 trace_id 能取回单次请求的完整调用链（入口、规划、每个工具、每次 LLM 调用），含耗时与 token 用量 | 只有零散 print 日志，出问题靠猜 | 3.4 |
| 有关键指标 | 成功率、错误率、P95/P99 分位数延迟（Percentile Latency）、QPS、成本五项有面板与告警 | 面板只给汇报用，值班不看 | 3.4、3.7 |
| 有评估集 | 冒烟（Smoke）/核心（Core）/红队（Red Team）三层，条数、判分规则、通过线写进文档，能跑出与基线（Baseline）的对比 | 只有几个手测例子，判分靠感觉 | 3.5 |
| 有 CI 门禁 | 评估进 CI：指标跌破基线容忍带自动阻止合并，红队有独立通过线 | 评估靠自觉手动跑，改完直接合 | 3.5、3.9 |
| 有灰度 | 新版本按 1% → 5% → 25% → 100% 爬坡，每一档有明确放行判据（错误率、延迟、评估分） | 改完直接全量上线 | 3.6、3.9 |
| 有回滚 | 指标越线（如错误率 > 1%）一键或自动回滚到上一版本，且提示词、配置随之回退，演练过至少一次 | 出问题现场改代码热修 | 3.9 |
| 有预算告警 | 成本按租户、模型归因；日预算 80% 告警、100% 熔断，触发路径演练过 | 月底看账单才知道超了 | 3.7 |
| 高风险操作有审批（加分项） | 退款等高风险工具走人工审批并留痕 | 所有工具调用全自动放行 | 3.10 |

配套的 10 个关键问题（口头全部答清即达标）：

1. 如何设计 Agent 的分层架构？
2. 如何做多租户数据隔离？
3. 如何接入 Trace、Metrics、Logs？
4. 如何构建评估集并集成到 CI？
5. 如何做灰度发布和自动回滚？
6. 如何控制成本？模型路由怎么做？
7. 如何做权限控制和审计？
8. 如何版本化提示词、模型、知识库？
9. 如何设计人工审批流程？
10. 如何做故障降级和容量规划？

**面试高频问法**：阶段 4 学完，以下两问应能给出共识口径的回答——"Agent 上线前，你如何保证一次提示词变更不出事故？"（版本化提示词 → 评估集回归 → CI 门禁拦截 → 灰度爬坡 → 指标越线自动回滚，五道闸口层层设防；只答"代码评审 + 手工测一遍"不是合格答案）；"可观测性的三大支柱是什么？"（结构化日志（Logs）、指标（Metrics）、链路追踪（Traces），分别回答"当时发生了什么、现在整体健康吗、这一次请求慢在哪"；对 LLM 系统还要加第四问"钱花在哪"，即成本归因）。

### 4.6 高频卡点与解法速查

| 卡点 | 典型症状 | 第一时间解法 | 深入锚点 |
|---|---|---|---|
| trace 采不全或太贵 | 全量记录正文导致存储爆炸，只好全关 | 采样策略分级，默认只记元数据，Bad Case 才落全文 | 3.4 |
| 评估集越建越没用 | 追求条数、层次混杂，跑一次半天 | 三层分层：冒烟秒级、核心精而准、红队独立维护，判分口径写进文档 | 3.5 |
| CI 评估不稳定 | LLM 输出随机导致门禁时过时挂 | 温度设 0、判分规则化、多次取均值、基线留 5% 容忍带 | 3.5、1.6 |
| 本地能跑容器里跑不起来 | 依赖缺失、编码、路径问题 | 先在本地 docker build/run 验证再推集群，镜像保持最小 | 3.6 |
| K8s 排查无从下手 | CrashLoopBackOff 看不懂就卡住 | 三板斧：kubectl describe、kubectl logs、kubectl get events | 3.6 |
| 灰度没有判据 | 爬到 5% 不知道能不能继续放量 | 提前写死放行线：错误率、P95 延迟、核心评估分三选一越线即回退 | 3.9 |
| 回滚了但配置没回 | 只回滚镜像，提示词还是新的，等于没回 | 版本化一切，版本号覆盖镜像 + 提示词 + 配置，回滚脚本一并回退 | 3.9 |
| 告警太吵或太哑 | 值班疲劳到忽略告警，或出事没响 | 分级告警、按 SLO 触发，预算告警走独立通道 | 3.4、3.7 |
| 成本归因不清 | 只知道总额，不知道谁花的 | 按请求记 token 进 trace，按租户、模型聚合到指标 | 3.4、3.7 |
| 重试放大成本 | 上游限流时重试风暴把账单翻倍 | 指数退避 + 熔断 + 降级链，重试上限写进配置 | 3.7 |

### 6.2 迭代一：把 Agent 暴露成 API 并接入 trace

先让每次请求"看得见"：一条 trace 串起整次执行，三个原始指标推出五个关键数字（成功率、错误率、延迟、QPS、成本）。

```python
# src/observability/tracing.py —— OpenTelemetry 初始化：span 通过 OTLP 导出到收集器
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter()))  # 异步批量导出，不阻塞请求
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("agent")
```

```python
# src/observability/metrics.py —— 指标：请求计数、延迟分布、成本归因
from prometheus_client import Counter, Histogram

agent_requests = Counter("agent_requests_total", "请求计数", ["status", "model"])
agent_latency = Histogram(
    "agent_request_latency_seconds", "延迟分布",
    buckets=[0.1, 0.5, 1, 2, 5, 10, 30])  # 桶覆盖 P95/P99 关注区间
agent_cost = Counter("agent_cost_dollars_total", "成本归因", ["model", "tenant"])
```

```python
# src/api/main.py —— FastAPI 入口：健康检查 + Agent 接口，每次请求一条 trace
import time
from fastapi import FastAPI
from observability.tracing import tracer
from observability.metrics import agent_requests, agent_latency
from agent.runtime import KnowledgeQAAgent  # 5.4 完成的 Agent

app = FastAPI()
agent = KnowledgeQAAgent()

@app.get("/health")   # 存活探针：进程活着
async def health():
    return {"status": "ok"}

@app.get("/ready")    # 就绪探针：依赖（LLM、向量库）可用才放流量
async def ready():
    ok = await agent.ping()
    return {"status": "ready" if ok else "not_ready"}

@app.post("/v1/agent")
async def run_agent(req: dict):
    """跑一次 Agent，返回答案与 trace_id；生产环境建议另提供流式接口。"""
    question = req.get("question", "")
    start = time.perf_counter()
    with tracer.start_as_current_span("agent_run") as span:
        span.set_attribute("input.length", len(question))
        try:
            result = await agent.run(question)  # 内部每一步各开一个子 span
            span.set_attribute("steps", result.get("steps", 0))
            trace_id = format(span.get_span_context().trace_id, "016x")
            return {"answer": result["answer"], "trace_id": trace_id}
        except Exception as e:
            span.record_exception(e)            # 异常写入 trace，可回放
            raise
        finally:
            status = "ok"   # 简化示意：真实实现按返回/异常区分 status
            agent_requests.labels(status=status, model=agent.model).inc()
            agent_latency.observe(time.perf_counter() - start)
```

迭代一验收：在 Jaeger（或任意 OTLP 兼容后端）凭返回的 trace_id 看到一次多步执行的完整调用链与各步耗时；/health、/ready 返回 200。

### 6.4 迭代三：CI 门禁

把评估挂进持续集成/持续交付（CI/CD，Continuous Integration / Continuous Delivery）流水线：不是"记得跑"，而是"不跑过就合不进"。

```yaml
# .github/workflows/ci.yaml —— 每次 PR 自动跑三层评估，指标破线即失败
name: CI
on: [pull_request]

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt
      - run: python -m eval.smoke                          # 冒烟：全过才继续
      - run: python -m eval.core --baseline baseline.json  # 核心：不跌破基线容忍带
      - run: python -m eval.red_team                       # 红队：通过率 >= 95%
```

```python
# eval/gate.py —— 门禁判定：核心指标留 5% 容忍带，红队不设容忍带
def check_gate(results: dict, baseline: dict, threshold: float = 0.05) -> bool:
    failures = []
    for metric in ["success_rate", "tool_accuracy", "citation_rate"]:
        if results[metric] < baseline[metric] * (1 - threshold):
            failures.append(metric)      # 核心指标跌破基线的 95%
    if results["red_team_pass_rate"] < 0.95:
        failures.append("red_team")      # 红队单独设线
    return len(failures) == 0
```

提示词与配置同步版本化：prompts/ 目录纳入 git，改提示词与改代码走同一套 PR 评审——这是 3.9"版本化一切"的第一步（提前接触）。迭代三验收：故意改坏一条提示词提交 PR，CI 能拦截并给出下跌指标。

```python
# src/security/auth.py —— JWT 签发与校验：密钥走配置，不硬编码
import jwt  # pyjwt
from config import settings

def create_token(user_id: str, roles: list[str]) -> str:
    return jwt.encode({"sub": user_id, "roles": roles},
                      settings.jwt_secret, algorithm="HS256")

def verify_token(token: str) -> dict:
    """校验失败抛 jwt.InvalidTokenError，由中间件统一转 401。"""
    return jwt.decode(token, settings.jwt_secret, algorithms=["HS256"])
```

```python
# deploy/watchdog.py —— 自动回滚：灰度期错误率越线即回退，人只做事后复核
import subprocess
import urllib.request
import json

PROM = "http://prometheus:9090"
THRESHOLD = 0.01  # 放行判据：灰度组 5 分钟错误率 > 1% 即回滚

def canary_error_rate() -> float:
    q = ('sum(rate(agent_requests_total{track="canary",status="error"}[5m]))'
         ' / sum(rate(agent_requests_total{track="canary"}[5m]))')
    with urllib.request.urlopen(f"{PROM}/api/v1/query", data=q.encode()) as r:
        result = json.load(r)["data"]["result"]
    return float(result[0]["value"][1]) if result else 1.0  # 查不到数据按最坏处理

if __name__ == "__main__":
    if canary_error_rate() > THRESHOLD:
        subprocess.run(["kubectl", "rollout", "undo", "deployment/agent-canary"])
        # 回滚不只回镜像：提示词、配置随同一版本号一起回退（见 3.9"版本化一切"）
```

### 6.8 迭代六：预算告警与成本归因

按三步迭代实现：第一步只记账（record），跑两天看真实消耗；第二步定日预算、加 80% 告警；第三步加 100% 熔断。

```python
# src/cost.py —— 预算告警：记账 → 80% 告警 → 100% 熔断
import time
from observability.metrics import agent_cost

PRICE = {  # 每百万 token 单价（美元），示意值，随所选服务商定价更新
    "gpt-4o-mini": (0.15, 0.60),
    "gpt-4o": (2.50, 10.00),
}

class BudgetExceeded(Exception):
    """日预算耗尽：API 层捕获后返回降级话术，而不是继续烧钱。"""

class CostManager:
    def __init__(self, daily_budget: float = 20.0, alert_hook=print):
        self.daily_budget = daily_budget
        self.alert_hook = alert_hook      # 接告警通道：邮件 / IM / 值班群
        self.cost_today = 0.0
        self.day = time.strftime("%Y-%m-%d")

    def _reset_if_new_day(self):
        today = time.strftime("%Y-%m-%d")
        if today != self.day:             # 按自然日重置
            self.day, self.cost_today = today, 0.0

    def record(self, model: str, usage: dict, tenant: str = "default") -> float:
        """每次 LLM 调用后记账；80% 告警，100% 抛 BudgetExceeded 触发降级。"""
        self._reset_if_new_day()
        p_in, p_out = PRICE[model]
        cost = usage["prompt_tokens"] / 1e6 * p_in + usage["completion_tokens"] / 1e6 * p_out
        self.cost_today += cost
        agent_cost.labels(model=model, tenant=tenant).inc(cost)  # 成本归因进指标
        if self.cost_today > self.daily_budget * 0.8:
            self.alert_hook(f"[预算告警] 今日已花 ${self.cost_today:.2f}"
                            f"（预算 ${self.daily_budget}，已达 80%）")
        if self.cost_today > self.daily_budget:
            raise BudgetExceeded(f"今日 ${self.cost_today:.2f} 超预算 ${self.daily_budget}")
        return cost

cost_manager = CostManager(daily_budget=20.0)
```

接入方式：在 §6.2 的 finally 块里加一行 `cost_manager.record(agent.model, agent.last_usage)`；API 层捕获 BudgetExceeded 后走缓存或兜底话术。模型路由（Model Routing）与语义缓存（Semantic Caching）的进一步优化见 3.7 与案例 B。迭代六验收：把日预算临时调成 1 美元，当天能观察到 80% 告警与 100% 熔断各触发一次。

```text
第 3 周：3.6 + 迭代四 —— Docker + K8s + HPA，压测从单机 QPS 1 到集群 500（P99 < 5s）
第 4 周：3.7 —— 成本看板 + 模型路由（简单问题走低价模型）
第 5 周：3.9 + 迭代五 —— 灰度爬坡，期间一次候选版本被自动回滚，4 分钟内恢复
第 6 周：迭代六 + 收口 —— 预算告警、值班手册、§4.5 自检表逐项通过
```

**示意数字效果**：上线后日均 2000 次调用、P95 延迟 3.2 秒、错误率 0.4%；第 5 周一次提示词回归被 CI 门禁拦下（core 引用率 0.85 → 0.81）；月成本稳定在 600 美元以内，预算告警月中触发过一次并被及时处理。

### 案例 B：某电商客服 Agent 月账单从 5000 美元降到 500 美元

**场景**：一家电商公司的多轮客服 Agent（带工具调用）上线三个月，月账单涨到 5000 美元，被要求一个月内降下来且质量不能降。

**做法**（四根杠杆，按投入产出排序）：

1. 模型路由：意图分类后，简单任务走低价 mini 模型，此类流量成本降约 80%。
2. 语义缓存：高频问题命中缓存直接返回，命中率约 30%，这部分几乎零成本。
3. 上下文压缩：历史轮次摘要 + 只带相关片段，输入 token 减半（方法见 1.5、3.7）。
4. 输出限制：max_tokens 从 2000 收到 500，并要求回答分点，输出 token 明显下降。

**示意数字效果**：月账单从 5000 美元降到 500 美元，降 90%；core 评估集准确率 0.84 → 0.83，在 5% 容忍带内，质量未受实质影响。

### 案例 C：CI 门禁拦下一次提示词回归

**场景**：一位工程师修改检索提示词想提升召回率，按流程提交 PR。

**流程**：

```text
1. 开发者修改提示词
2. 提交 PR
3. CI 自动跑 Smoke + Core + Red Team
4. Core 准确率从 0.85 降到 0.82
5. CI 失败，阻止合并
6. 开发者定位到新提示词漏了引用要求，修复后 0.86 合并
```

**示意数字效果**：回归在合并前被发现，修复只花了半小时；该团队此后三个月 CI 门禁共拦下 4 次类似回归，无一例流到线上——若没有门禁，按以往经验至少一次会造成线上大面积错误答案。

## 8. 常见坑

1. **不做可观测性，出问题无法定位**。对策：第一件事先接 trace 与关键指标，再谈任何优化（见 3.4）。
2. **不做评估，改了不知道好坏**。对策：上线前建好三层评估集，任何变更先跑对比（见 3.5）。
3. **不灰度直接全量，一出问题全站不可用**。对策：1% → 5% → 25% → 100% 爬坡，每档写死放行判据（见 3.6、3.9）。
4. **不做回滚，出问题只能手动修**。对策：镜像 + 提示词 + 配置同版本号管理，回滚一条命令，并演练一次（见 3.9）。
5. **不做成本控制，账单爆炸**。对策：记账、80% 告警、100% 熔断三步走，模型路由分流简单任务（见 3.7）。
6. **不做权限，越权与数据泄露**。对策：JWT 认证 + 工具级 RBAC，默认拒绝（见 3.8）。
7. **不做审计，合规不通过**。对策：谁在何时用何工具调了什么、结果如何，全量落库（见 3.8）。
8. **不版本化，提示词、模型、知识库混着改**。对策：版本化一切，一次发布只动一个变量（见 3.9）。
9. **不做 CI/CD，发布靠手工**。对策：PR 触发测试与评估门禁，发布全脚本化（见 3.9）。
10. **不做降级，依赖挂了整体不可用**。对策：LLM 超时熔断后走缓存或规则兜底话术（见 3.7）。
11. **不做容量规划，峰值来了才扩容**。对策：HPA + 压测定容，为峰值预留余量（见 3.6、3.7）。
12. **不做人机协同，高风险操作无人把关**。对策：退款、删除等工具加人工审批节点（见 3.10）。
13. **不做故障演练，真故障手忙脚乱**。对策：每季度一次演练——模拟 LLM 故障、验证降级与回滚（见 3.7、4.9）。
14. **忽略安全，被注入攻击无响应**。对策：红队评估集进 CI，输入过滤 + 最小权限双保险（见 3.8、2.9）。
15. **过度设计，一开始就上微服务全家桶**。对策：单体 + 清晰模块边界起步，量级到了再拆（见 3.1）。

## 9. 练习

1. 画出你的 Agent 分层架构图（接入、编排、能力、基础设施）。验收：向同学讲清每层职责与一条请求的完整路径。
2. 用 FastAPI 把 5.4 的 Agent 暴露成 API（含 /health、/ready）。验收：curl 调用能返回答案，健康检查返回 200。
3. 接入 OpenTelemetry，记录完整 trace。验收：凭 trace_id 找回一次多步执行的全部子 span 与耗时。
4. 用 Prometheus 记录 5 个关键指标。验收：面板上能看到成功率、P95 延迟、成本三张图。
5. 构建 50 条核心评估集并跑出基线。验收：README 写明条数、判分规则、通过线。
6. 配置 CI 门禁。验收：故意改坏提示词提交 PR，CI 能拦截并指出下跌指标。
7. 写 Dockerfile + K8s Deployment + HPA。验收：压测下副本数自动从 2 扩到 8 再缩回。
8. 实现模型路由和语义缓存。验收：路由日志显示简单任务走了低价模型，缓存命中率可查。
9. 实现 JWT + RBAC + 审计。验收：user 角色调退款工具被拒且留痕，admin 角色放行。
10. 配置灰度发布：1% → 5% → 10% → 100%。验收：每一档有记录在案的放行判据。
11. 实现自动回滚：错误率 > 1% 触发。验收：向灰度组注入 5% 错误，一个观察窗口内自动回滚。
12. 实现预算告警。验收：把日预算调成 1 美元，当天观察到 80% 告警与 100% 熔断各一次。
13. 写值班手册并做一次故障演练（模拟 LLM 故障验证降级）。验收：一位没写过这个系统的同事能照手册值班。
14. 回答 §4.5 的 10 个关键问题并录音回听。验收：每题 60 秒内讲清，讲不清的回锚点补课。

## 10. 小结

- 阶段 4 = **可观测 + 评估 + 部署 + CI/CD + 成本控制**，底座是 3.1–3.10 的工程化知识。
- 组队顺序：**3.4 → 3.5 → 3.6 → 3.7 → 3.9** 五大主线按依赖推进，3.1、3.8、3.10 支撑收口——先看得见，再判得出，才上得去、退得回、花得起。
- 里程碑五件套：**有 trace、评估集、灰度、回滚、预算告警**，逐项对照 §4.5 自检表打分，不合格不进下一阶段。
- 最小项目：**部署一个带监控与评估的 Agent API**，六个迭代交付——trace 接入、评估集、CI 门禁、部署、灰度回滚、预算告警。
- 核心原则：**先可观测后优化，先评估后上线，先安全后开放，先灰度后全量，先成本后规模。**
- 时间预算：**顺利通过 5.4 需 4–6 周**，有后端经验 3–4 周，工程经验薄弱 6–8 周。
- 高频卡点集中在 **trace 缺失、评估抖动、灰度无判据、回滚不彻底、成本无归因** 五类，解法见 §4.6 速查表。
- 面试共识口径：一次提示词变更的安全链 = 版本化 → 评估门禁 → 灰度 → 自动回滚，五道闸口缺一不可。
- 这些能力直接支撑：**5.6 阶段 5：多 Agent 与生产**（多 Agent 系统的观测、评估与发布全部复用本阶段底座）。
