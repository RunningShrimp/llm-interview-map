# 讲解 1.3 结构化输出与 Function Calling

> 说明：1.1 会调 LLM API、1.2 见识了 Prompt 约束的局限之后，1.3 给出**更可靠的工程手段**：JSON Schema、结构化输出（Structured Outputs）、Function Calling、Pydantic 校验、重试、并行工具调用。  
> 本篇聚焦「让 LLM 的输出可被程序可靠消费、让工具调用安全可控」这个接口层问题；Agent 侧的完整工具使用与执行循环在 2.3 / 2.5 展开，RAG 的引用输出在 1.4 展开。

## 1. 定位

LLM 应用层第 3 个知识点，属于「LLM 与外部系统之间的接口层」。  
它解决一个核心问题：**如何让 LLM 的输出从「自然语言」变成「程序能可靠解析的结构化数据或工具调用」**。

这也是锚点关键问题「如何让 LLM 安全调用工具」的两半：先「可靠」（Schema 约束 + 校验），再「安全」（最小权限 + 确认 + 沙箱）。安全闸门在 4.12 集中正面回答。

依赖关系：直接前置是 1.1（会调 API）与 1.2（懂 Prompt 约束的天花板）；直接后续是 1.4 RAG（引用输出）、1.5 记忆（状态结构化）、2.1 Agent 定义与范式、2.3 工具使用，并顺承到 2.5 执行循环。

## 2. 一句话定义

结构化输出（Structured Outputs）与 Function Calling，是通过 JSON Schema 约束 LLM 输出格式，并让 LLM 以结构化方式请求调用外部函数的工程方法。

简化公式：

```text
结构化输出：LLM → 受 Schema 约束的 JSON → 程序直接 json.loads
Function Calling：LLM → 工具调用请求（函数名+参数）→ 程序校验执行 → 结果回传 → LLM 继续推理
```

## 3. 为什么需要

纯 Prompt 约束输出，在生产环境会遇到：

- **格式不稳定**：说好只输出 JSON，模型加一句「好的，这是结果」。
- **字段缺失**：偶尔少一个字段，下游 `json.loads` 后取键崩溃。
- **类型错误**：`age` 应该是整数，模型给了 `"三十"`。
- **嵌套错误**：数组里塞对象，对象里塞字符串，结构飘忽。
- **工具调用不可靠**：靠 Prompt 让模型「假装调用工具」，输出格式五花八门，解析困难。
- **无法并行**：多个工具调用要串行解析，效率低。
- **无法校验**：输出错了，不知道错在哪，只能盲目整体重试。

类比：纯 Prompt 约束像在饭馆**口头点菜**——「来几个下饭菜，别太辣」，厨房全凭理解，份量口味每次都漂；Schema 约束像**扫码点餐**——菜名、规格、忌口全是固定格子，填错格子连下单按钮都点不动。1.2 讲的是怎么把话说清楚，1.3 讲的是怎么把菜单做成表格。

两条路线的差距：

| 维度 | 纯 Prompt 约束 | 结构化输出 / Function Calling |
|---|---|---|
| 格式保证 | 无，靠模型自觉 | API 层强制（合法 JSON / 符合 Schema） |
| 字段与类型 | 常缺字段、类型漂移 | required / type / enum 锁定 |
| 解析方式 | 正则 + 清洗，脆弱 | json.loads 一次到位 |
| 工具调用 | 让模型输出「调用文本」再自己解析 | 原生 tool_calls 结构，带调用 ID 可追踪 |
| 校验与重试 | 失败只能整体重试 | 精确到字段的校验错误可回传修正 |
| 适用 | 原型、一次性脚本 | 生产链路 |

Function Calling 和结构化输出就是解决这些问题的**工程标准**。

## 4. 核心原理

### 4.1 从 Prompt 约束到 Schema 约束

**Prompt 约束**：

```text
请输出 JSON，包含 name、age、city 三个字段。
```

问题：模型可能输出 Markdown 代码块、加解释、字段名拼错。

**Schema 约束**：

```json
{
  "type": "object",
  "properties": {
    "name": {"type": "string"},
    "age": {"type": "integer"},
    "city": {"type": "string"}
  },
  "required": ["name", "age", "city"]
}
```

模型被**强制**按 Schema 输出，解析成功率大幅提升。区别不在「说得再清楚一点」，而在约束的**层级**：Prompt 是建议，Schema 是合同。

### 4.2 JSON Schema 基础

JSON Schema 是描述 JSON 结构的行业标准。

```json
{
  "type": "object",
  "properties": {
    "name": {"type": "string", "description": "人名"},
    "age": {"type": "integer", "minimum": 0, "maximum": 150},
    "tags": {"type": "array", "items": {"type": "string"}},
    "address": {
      "type": "object",
      "properties": {
        "city": {"type": "string"},
        "zip": {"type": "string", "pattern": "^[0-9]{6}$"}
      },
      "required": ["city"]
    }
  },
  "required": ["name", "age"],
  "additionalProperties": false
}
```

关键字段：

| 字段 | 作用 |
|---|---|
| type | 类型：object、array、string、number、integer、boolean、null |
| properties | 对象属性定义 |
| required | 必填字段 |
| enum | 枚举值，锁死可选项 |
| items | 数组元素定义 |
| minimum / maximum | 数值范围 |
| pattern | 字符串正则约束 |
| description | 字段说明，帮助模型理解该填什么 |
| additionalProperties | 是否允许额外字段 |

原则：**能锁的都锁上**。enum、required、additionalProperties: false 用得越狠，模型自由发挥的空间越小，下游解析越稳。

### 4.3 四种输出约束方式与演进

| 方式 | 说明 | 可靠性 | 适用 |
|---|---|---|---|
| Prompt 约束 | 自然语言要求 JSON | 低 | 原型 |
| JSON Mode | API 保证输出合法 JSON | 中 | 简单结构 |
| JSON Schema（Structured Outputs） | API 保证符合 Schema | 高 | 生产 |
| Function Calling | 模型输出工具调用结构 | 高 | 工具调用 |

演进脉络（截至 2026 年的公开口径）：OpenAI 2023 年 6 月推出 Function Calling，2023 年 11 月推出 JSON Mode，2024 年 8 月推出 Structured Outputs 并宣称对支持的 Schema 达到 100% 结构符合（OpenAI 官方博客，2024）；Anthropic 2024 年开放工具使用（Tool Use）API。此后主流厂商与开源推理框架普遍跟进**受限解码（Constrained Decoding）**——在解码阶段直接屏蔽不符合 Schema / 语法的 token（如 vLLM 的 guided decoding、llama.cpp 的 GBNF 语法约束），从概率上杜绝非法输出，这是上述 API 能力的底层支撑。

**JSON Mode**：

```python
response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "提取人物信息，输出 JSON"}],
    response_format={"type": "json_object"},
)
```

保证输出是合法 JSON，但不保证字段符合你的 Schema。注意：多数厂商要求消息里显式提到 JSON 字样，否则可能直接报错（各厂商约束细节不同）。

**JSON Schema（Structured Outputs）**：

```python
response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "提取人物信息"}],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "person",
            "schema": {
                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "age": {"type": "integer"},
                    "city": {"type": "string"}
                },
                "required": ["name", "age", "city"],
                "additionalProperties": False
            }
        }
    },
)
```

保证输出**严格符合 Schema**。生产环境信息抽取默认用它，Pydantic 校验做第二道保险（见 4.8）。

### 4.4 Function Calling 是什么

Function Calling（函数调用，各厂商亦称 Tool Use / 工具调用，机制等价，本文统称 Function Calling）让模型**不直接回答，而是输出一个结构化的函数调用请求**。

类比：模型的角色像**医生开化验单**——医生不亲自操作检验仪器，只开出结构化化验单（项目、样本、参数），检验科（你的程序）执行后把报告贴回病历（messages），医生再基于报告决定下一步。全程医生没碰过仪器。

流程：

```text
1. 你定义工具（函数名、参数 Schema）
2. 把工具列表传给 LLM
3. LLM 决定调用哪个工具、传什么参数
4. 你的代码执行工具
5. 把结果返回给 LLM
6. LLM 根据结果生成最终回答
```

模型侧发生了什么：模型本身**不执行任何函数**，它输出的只是「函数名 + 参数 JSON」的特殊格式文本，由 API 层解析成 `tool_calls` 字段返回。模型的能力来自厂商用工具调用样本做的监督微调（SFT, Supervised Fine-Tuning）——大量「用户问题 + 可用工具列表 + 正确的调用/不调用」配对数据，让模型学会选工具、填参数、不该调时拒绝。这也是各家模型工具调用能力参差不齐的原因：语料的数量与质量决定能力上限。

示例：

```python
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名"},
                    "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
                },
                "required": ["city"]
            }
        }
    }
]

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "北京今天天气怎么样？"}],
    tools=tools,
    tool_choice="auto",
)

tool_call = response.choices[0].message.tool_calls[0]
print(tool_call.function.name)       # "get_weather"
print(tool_call.function.arguments)  # '{"city": "北京", "unit": "celsius"}'
```

> 面试高频问法：「简述 Function Calling 的工作流程。」共识答法：不能只说「模型调用函数」——要点是模型**输出结构化调用请求**（函数名+参数 JSON），应用程序拦截、校验、执行，再把结果回传给模型继续生成；模型自始至终没有执行权。

### 4.5 工具定义的最佳实践

**1. 函数名清晰**：

```text
好：search_products, get_order_status
差：func1, do_stuff
```

**2. description 详细**：

```json
{
  "name": "search_products",
  "description": "根据关键词搜索商品。返回商品列表，包含名称、价格、库存。当用户询问商品信息时使用。"
}
```

description 是写给模型看的「使用说明书」：什么时候用、返回什么、什么时候不要用。写得越具体，模型选择越准。

**3. 参数 Schema 严格**：

- 用 `enum` 限制选项
- 用 `required` 标记必填
- 用 `description` 解释每个参数
- 用 `additionalProperties: false` 禁止额外字段

**4. 参数尽量扁平**：

嵌套太深模型容易出错，两层以内为佳。

**5. 工具数量适中**：

- 太少：能力不足
- 太多：模型选择困难，容易选错
- 建议：单次传入 5–20 个；更多时先分组，再用检索或路由挑出当次相关的子集（见 2.3）

### 4.6 tool_choice 控制

| 值 | 含义 |
|---|---|
| "auto" | 模型自己决定是否调用工具 |
| "none" | 不调用工具 |
| "required" | 必须调用某个工具 |
| {"type": "function", "function": {"name": "xxx"}} | 强制调用指定工具 |

典型用法：分类任务用强制指定工具，把输出「挤压」成固定结构，兼做结构化输出的一种手段。

### 4.7 并行工具调用

并行工具调用（Parallel Function Calling）让模型可以一次返回多个工具调用：

```python
tool_calls = response.choices[0].message.tool_calls
# [
#   {id: "call_1", function: {name: "get_weather", arguments: '{"city":"北京"}'}},
#   {id: "call_2", function: {name: "get_weather", arguments: '{"city":"上海"}'}}
# ]
```

工程处理：

```python
import asyncio

async def execute_tools(tool_calls):
    tasks = []
    for tc in tool_calls:
        fn = TOOL_MAP[tc.function.name]
        args = json.loads(tc.function.arguments)  # arguments 是字符串，先解析
        tasks.append(fn(**args))
    return await asyncio.gather(*tasks)
```

优势：多城市天气、多商品查询可以并发，延迟大幅降低（案例 B 有数字）。

### 4.8 Pydantic 校验与重试

即使有 Structured Outputs，LLM 输出也不可信（自部署模型、旧版本模型、复杂嵌套 Schema 下尤甚），必须程序侧校验：

```python
from pydantic import BaseModel, Field, ValidationError

class Person(BaseModel):
    name: str
    age: int = Field(ge=0, le=150)
    city: str

def parse_with_retry(raw: str, max_retries: int = 3) -> Person:
    for attempt in range(max_retries):
        try:
            return Person.model_validate_json(raw)
        except ValidationError as e:
            if attempt == max_retries - 1:
                raise
            # 把校验错误反馈给 LLM，让它只修正错处
            raw = fix_with_llm(raw, str(e))
    raise ValueError("解析失败")
```

校验失败的重试策略按代价从低到高排列：

| 策略 | 做法 | 适用 |
|---|---|---|
| 错误回传重试 | 把 ValidationError 信息作为消息回传，让模型修正后重新生成 | Schema 校验失败的首选 |
| 降随机性 | temperature 调到 0–0.2 | 格式随机漂移 |
| 补示例 | Few-shot 加 1–2 个正确输出样例 | 复杂嵌套结构 |
| 换强约束 | Prompt 约束升级为 JSON Mode / Structured Outputs | 根因是约束力不足 |
| 程序侧静默修复 | 兜底改写（如 "三十" → 30） | 可枚举的确定性错误 |
| 降级或人工 | 多次失败后降级到兜底回答、转人工 | 高价值业务链路 |

> 面试高频问法：「Function Calling 怎么保证参数正确？线上调用不稳定怎么办？」共识口径：三层防御——生成侧用 Structured Outputs / 严格 Schema 约束；执行侧用 Pydantic 校验兜底（模型输出永远不等于可信输入）；失败侧把校验错误回传重试，超限降级或转人工。权限校验永远在业务系统，不依赖模型自觉。

### 4.9 工具调用的完整循环

```text
1. 用户提问
   ↓
2. LLM 决定调用工具 → tool_calls
   ↓
3. 执行工具 → tool_results
   ↓
4. 把 tool_results 追加到 messages
   ↓
5. 再次调用 LLM
   ↓
6. 如果还有 tool_calls，重复 3-5
   ↓
7. 直到 LLM 返回最终回答
```

消息格式：

```python
messages = [
    {"role": "user", "content": "北京天气怎么样？"},
    {"role": "assistant", "tool_calls": [...]},
    {"role": "tool", "tool_call_id": "call_1", "content": '{"temp": 25}'},
]
```

要点：assistant 的 tool_calls 消息和对应的 tool 结果消息**必须成对保留在上下文里**，缺失或不配对会直接报错。循环的状态管理细节在 2.5 执行循环与状态机展开。

### 4.10 结构化输出 vs Function Calling

| 维度 | 结构化输出 | Function Calling |
|---|---|---|
| 目的 | 让输出符合 Schema | 让模型请求调用函数 |
| 输出 | 数据对象 | 工具调用请求 |
| 执行 | 不执行外部函数 | 需要执行外部函数 |
| 适用 | 抽取、分类、格式化 | Agent、工具调用 |
| 可靠性 | 高（Schema 层强制） | 高（但参数仍需校验） |

两者可以结合：先用 Function Calling 调工具，再用结构化输出格式化最终答案；2.1 的「Agent = LLM + 工具 + 循环」里，Function Calling 就是那条「工具」通道。

### 4.11 工具生态的标准化：MCP

没有标准时，每个应用接每个工具都要手写一份 Schema、一套鉴权，M 个应用 × N 个工具 = M×N 份胶水代码。

MCP（Model Context Protocol，模型上下文协议）2024 年 11 月由 Anthropic 开源发布，把「工具的定义、发现、调用」标准化为客户端-服务器协议：工具方实现一次 MCP Server（数据库、浏览器、文件系统等），任何支持 MCP 的应用都能接入。截至 2026 年，主流模型厂商与编排框架（LangGraph、OpenAI Agents SDK 等）大多已提供 MCP 支持，社区积累了大量现成 Server。

两个关键认知：

- **MCP 不取代 Function Calling**：FC 是模型侧的调用机制，MCP 解决的是「工具从哪来、Schema 谁维护、如何被发现」的供给侧问题，二者是上下游关系。框架层的对比在 3.3 编排框架与运行时展开。
- **协议标准化不等于安全自动成立**：MCP 只管「接得上」，鉴权、审计、沙箱仍由应用与网关层负责（见 3.8）。MCP 能否成为统一的「工具 USB 口」属于趋势观察，落地时按官方文档核实当前版本状态。

### 4.12 如何让 LLM 安全调用工具：四道闸门

锚点关键问题的正面回答。核心原则一句话：**模型输出永远只是建议，不是授权**。四道闸门缺一不可：

| 闸门 | 机制 | 要点 |
|---|---|---|
| 参数校验 | Pydantic / JSON Schema 校验参数 | 类型、范围、枚举、必填；不合法直接拒绝执行，不进入业务系统 |
| 最小权限 | 每个工具绑定最小权限集；按用户身份二次鉴权 | 模型说调什么不等于用户被授权调什么，权限在业务侧判定 |
| 确认机制 | 高危操作（支付、删除、群发、退款）先出确认单，人点头再执行 | Human-in-the-Loop（人在回路），金额/范围阈值触发 |
| 沙箱隔离 | 代码、SQL、文件类工具在受限环境执行 | 限时限网限目录，防提示注入后的破坏面（见 4.3 数据分析 Agent） |

配套三件事：

1. **限流与步数上限**：单次会话最大工具调用次数，防死循环与成本失控（见 1.7）。
2. **全量审计日志**：每次调用的参数、结果、耗时、决策留痕，出问题可回放（见 1.6 可观测性、3.4 追踪）。
3. **评估闭环**：工具选择准确率、参数正确率、端到端成功率要有指标和回归集（见 1.6）。

系统化的认证、授权、审计体系在 3.8 安全、合规与权限展开；这里先记住接口层的最小集：**校验、最小权限、确认、沙箱**。

## 5. 架构 / 流程

一个完整的工具调用系统，分层看：

```text
┌─────────────────────────────────────┐
│  工具注册层                          │
│  ├─ 函数定义 + JSON Schema           │
│  ├─ 权限/限流标注                    │
│  └─ 高危标记（需确认/需沙箱）        │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  LLM 调用层                          │
│  ├─ messages + tools                 │
│  ├─ tool_choice                      │
│  └─ 结构化输出 Schema                │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  工具执行层                          │
│  ├─ 参数解析（arguments 是字符串）    │
│  ├─ Pydantic 校验 + 鉴权             │
│  ├─ 确认闸门（高危操作）             │
│  ├─ 并发执行 + 沙箱隔离              │
│  └─ 错误处理 + 结果格式化            │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  循环控制层                          │
│  ├─ 最大步数 / 最大调用次数          │
│  ├─ 终止条件                         │
│  ├─ 人工审批                         │
│  └─ 审计日志                         │
└─────────────────────────────────────┘
```

单次工具调用的时序（FC 循环的最小单元）：

```text
用户              应用程序             LLM API           工具（业务系统）
 │                  │                   │                   │
 │──── 提问 ───────▶│                   │                   │
 │                  │── messages+tools ▶│                   │
 │                  │◀── tool_calls ────│                   │
 │                  │ [闸门1: 参数校验]  │                   │
 │                  │ [闸门2: 鉴权/确认] │                   │
 │                  │──── 执行 ───────────────────────────▶ │
 │                  │◀── tool_results ──────────────────── │
 │                  │── messages+结果 ─▶│                   │
 │                  │   （若再出 tool_calls，回到闸门）       │
 │                  │◀── 最终回答 ──────│                   │
 │◀── 回答 ─────────│                   │                   │
```

注意时序图里的关键位置：**闸门在应用程序一侧、工具之前**——LLM 与工具之间没有直连通道，这是安全设计的根基。

## 6. 代码 / 工具

### 6.1 完整的 Function Calling 循环

```python
import json
import asyncio
from openai import AsyncOpenAI

client = AsyncOpenAI(api_key="YOUR_KEY")

# 1. 定义工具
async def get_weather(city: str, unit: str = "celsius") -> dict:
    return {"city": city, "temp": 25, "unit": unit, "condition": "晴"}

async def search_products(keyword: str, limit: int = 5) -> dict:
    return {"products": [{"name": f"{keyword}商品{i}", "price": 100 + i} for i in range(limit)]}

TOOL_MAP = {
    "get_weather": get_weather,
    "search_products": search_products,
}

# 2. 工具 Schema（与 TOOL_MAP 一一对应）
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string"},
                    "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
                },
                "required": ["city"],
                "additionalProperties": False
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "search_products",
            "description": "搜索商品",
            "parameters": {
                "type": "object",
                "properties": {
                    "keyword": {"type": "string"},
                    "limit": {"type": "integer", "minimum": 1, "maximum": 20}
                },
                "required": ["keyword"],
                "additionalProperties": False
            }
        }
    }
]

async def run_agent(user_input: str, max_steps: int = 5) -> str:
    messages = [{"role": "user", "content": user_input}]

    for step in range(max_steps):
        response = await client.chat.completions.create(
            model="gpt-4o-mini",
            messages=messages,
            tools=TOOLS,
            tool_choice="auto",
            temperature=0,
        )
        msg = response.choices[0].message

        # 没有工具调用，返回最终答案
        if not msg.tool_calls:
            return msg.content

        # 追加 assistant 消息（与 tool 结果成对保留）
        messages.append(msg)

        # 并发执行所有工具调用
        tasks = []
        for tc in msg.tool_calls:
            fn = TOOL_MAP[tc.function.name]
            args = json.loads(tc.function.arguments)  # 先校验再执行，生产中应换 Pydantic
            tasks.append(fn(**args))
        results = await asyncio.gather(*tasks, return_exceptions=True)

        # 追加工具结果（异常也要转成文本回传，不能中断循环）
        for tc, result in zip(msg.tool_calls, results):
            content = json.dumps(result, ensure_ascii=False) if not isinstance(result, Exception) else f"错误: {result}"
            messages.append({
                "role": "tool",
                "tool_call_id": tc.id,
                "content": content,
            })

    return "达到最大步数，未能完成。"

# 运行
result = asyncio.run(run_agent("北京和上海的天气怎么样？"))
print(result)
```

### 6.2 用 Pydantic 生成 JSON Schema

一份 Pydantic 模型同时服务两处：生成给模型的 Schema、生成执行前的校验器，避免两处手工维护不一致。

```python
from pydantic import BaseModel, Field
import json

class WeatherArgs(BaseModel):
    city: str = Field(description="城市名")
    unit: str = Field(default="celsius", pattern="^(celsius|fahrenheit)$")

schema = WeatherArgs.model_json_schema()
print(json.dumps(schema, indent=2, ensure_ascii=False))
```

输出：

```json
{
  "properties": {
    "city": {"description": "城市名", "title": "City", "type": "string"},
    "unit": {"default": "celsius", "pattern": "^(celsius|fahrenheit)$", "title": "Unit", "type": "string"}
  },
  "required": ["city"],
  "title": "WeatherArgs",
  "type": "object"
}
```

### 6.3 结构化输出 + 校验双保险

```python
from pydantic import BaseModel, Field, ValidationError

class ProductInfo(BaseModel):
    name: str
    price: float = Field(ge=0)
    tags: list[str] = Field(default_factory=list)

def extract_product(text: str) -> ProductInfo:
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "从文本中提取商品信息。"},
            {"role": "user", "content": text},
        ],
        response_format={
            "type": "json_schema",
            "json_schema": {
                "name": "product_info",
                "schema": ProductInfo.model_json_schema(),
            }
        },
        temperature=0,
    )
    raw = response.choices[0].message.content
    return ProductInfo.model_validate_json(raw)  # 第二道保险
```

### 6.4 工具调用失败重试（指数退避）

```python
async def call_tool_with_retry(tool_name: str, args: dict, max_retries: int = 3):
    for attempt in range(max_retries):
        try:
            fn = TOOL_MAP[tool_name]
            return await fn(**args)
        except Exception as e:
            if attempt == max_retries - 1:
                return {"error": str(e)}   # 最终失败也返回结构化错误，回传给 LLM
            await asyncio.sleep(2 ** attempt)  # 1s、2s 指数退避
```

注意：重试只适用于**幂等**的读取类工具；支付、下单等不可幂等操作盲目重试会重复执行，需要幂等键保护或改走确认机制（见 4.12）。

## 7. 案例

### 案例 A：电商客服 Agent 工具集

**场景**：某电商平台客服 Agent，日均约 3 万次会话，要查订单、办退款、必要时转人工。

**做法**：

```text
工具列表：
1. search_orders(user_id, status) - 查询订单
2. get_order_detail(order_id) - 订单详情
3. initiate_refund(order_id, reason) - 发起退款（高危）
4. transfer_to_human(reason) - 转人工

规则：
- order_id 用 pattern 锁格式，refund_reason 用 enum 锁选项
- 退款金额 > 500 元：出确认单，用户二次确认后才执行
- 不编造订单信息，工具失败时如实告知用户
- 单会话最多 8 步，工具失败重试 2 次后转人工
```

**效果（示意）**：工具选择准确率从 89% 提到 97%；金额超限的退款 100% 走确认通道；上线一个季度越权退款 0 起。

### 案例 B：并行工具调用降延迟

**场景**：天气查询页面，用户一次问多城市。

**做法**：检测 `tool_calls` 数组长度大于 1 时，用 `asyncio.gather` 并发执行，结果按 `tool_call_id` 对齐回传。

用户问：「北京、上海、广州的天气怎么样？」

**效果（示意）**：

```text
串行：3 次工具调用 = 3 × 300ms = 900ms
并行：asyncio.gather ≈ 300ms（取最慢一个）
收益：该环节延迟降为原来的 1/3
```

### 案例 C：结构化输出解析失败修复

**场景**：一家金融科技公司的资料抽取管线，每天约 10 万份文档要抽成结构化字段入库。

**做法**：Structured Outputs 约束 + Pydantic 双保险；校验失败把错误回传重试。某天模型输出：

```json
{"name": "张三", "age": "三十", "city": "北京"}
```

Pydantic 校验失败：`age` 不是整数。处理链路：

1. 把错误反馈给 LLM：「age 字段必须是整数，请重新生成。」
2. temperature 已为 0，补一个正确输出的 Few-shot 示例。
3. 重试一次成功，剩余无法修复的进入人工队列。

**效果（示意）**：首次解析成功率约 99.2%，错误回传重试一次后累计约 99.9%，剩余约千分之一走人工，整条管线无人工阻塞。

## 8. 常见坑

1. **只用 Prompt 不用 Schema**。  
   生产环境必须用 JSON Schema / Structured Outputs / Function Calling，Prompt 约束只配原型。

2. **工具描述太简单**。  
   模型不知道何时用、怎么用，容易选错；description 写清「何时用、返回什么、何时不要用」。

3. **参数 Schema 太宽松**。  
   不加 enum、required、additionalProperties: false，模型会自由发挥；能锁的都锁上。

4. **工具太多**。  
   超过 20 个模型选择困难；分组、检索或路由后再传入（见 2.3）。

5. **不做参数校验**。  
   模型可能传错类型、缺字段、传非法值；执行前必须过 Pydantic 这道闸。

6. **不处理工具执行失败**。  
   工具可能超时、返回错误；要捕获后转成结构化错误文本回传给 LLM，而不是让循环崩掉。

7. **不限制循环次数**。  
   模型可能反复调用工具形成死循环；max_steps 与最大调用次数必须有。

8. **并行工具调用串行执行**。  
   白白浪费延迟；用 `asyncio.gather` 并发，结果按 `tool_call_id` 对齐。

9. **工具结果太大**。  
   返回完整 JSON 可能几万 token，挤爆上下文还烧钱；截断、摘要或只回关键字段。

10. **忽略权限控制**。  
    模型说要调不等于用户被授权调；权限必须在业务侧二次校验（见 4.12）。

11. **不记录工具调用日志**。  
    出问题无法追踪；参数、结果、耗时、调用 ID 全量留痕（见 1.6）。

12. **工具名和参数名用中文**。  
    部分模型支持，但英文函数名 + 中文 description 更稳定。

13. **把 arguments 当对象用**。  
    `tool_call.function.arguments` 是 JSON **字符串**，必须先 `json.loads`；直接当 dict 访问必报错。

14. **对不可幂等的工具盲目重试**。  
    支付、下单类工具重试可能重复扣款；先判断幂等性或加幂等键，高危操作走确认机制。

## 9. 练习

1. 定义一个 `get_weather` 工具（unit 用 enum 约束），用 Function Calling 完成「北京天气」查询，打印函数名与 arguments。验收：能正确解出 city。
2. 用 Pydantic 定义工具参数模型，`model_json_schema()` 生成 Schema 接入 tools，与手写 Schema 做 diff。验收：差异为空或每处差异都能解释。
3. 实现「北京、上海、广州」三地并行查询，用计时对比串行 vs 并行。验收：并行耗时约为串行的 1/3。
4. 用 `response_format=json_schema` 实现商品信息抽取器，构造 5 条脏输入（缺字段、类型错、多字段）测试 Pydantic 校验。验收：非法输入全部被拦截。
5. 实现校验错误回传重试（max_retries=3），统计重试前后解析成功率。验收：给出前后两个数字。
6. 给 Agent 加最大步数限制与超限兜底话术，构造一个会触发连续工具调用的输入。验收：步数用尽时返回兜底文案而非报错。
7. 设计一个含 5 个工具的客服 Agent，写出每个工具的 Schema 与 description，标注哪个是高危工具、需要什么确认机制。验收：高危工具的确认流程有文字描述。
8. 模拟模型传错参数（缺字段、类型错、非法枚举值）三类错误，验证「校验拒绝 + 错误回传修复」链路。验收：三类错误都有对应日志记录。

## 10. 小结

- 结构化输出 = 用 JSON Schema 把 LLM 输出锁进固定格式，程序可直接 `json.loads` 消费。
- Function Calling = LLM 不执行函数，只输出「函数名+参数」的结构化调用请求；执行权始终在应用侧。
- 演进路径：Prompt 约束（低）→ JSON Mode（中）→ Structured Outputs / Schema 约束（高），底层支撑是受限解码。
- 模型的 FC 能力来自工具调用语料的监督微调，能力参差是语料问题，不是玄学。
- 工具定义五要点：**清晰命名、详细描述、严格 Schema、参数扁平、数量适中**。
- 工程链路标配：**Pydantic 校验、错误回传重试、并行执行、最大步数、权限控制、全量日志**。
- 完整循环：**LLM → tool_calls → 校验执行 → tool_results → LLM → 最终回答**。
- 安全调用四道闸门：**参数校验、最小权限、确认机制、沙箱隔离**——模型输出永远只是建议，不是授权。
- 生态方向：MCP 把工具接入的供给侧标准化（趋势观察），鉴权与审计仍在应用侧。
- 这些能力直接支撑：1.4 RAG（引用输出）、2.1 Agent 定义与范式、2.3 工具使用、2.5 执行循环与状态机、3.8 安全与权限、4.3 数据分析 Agent（沙箱执行）。
