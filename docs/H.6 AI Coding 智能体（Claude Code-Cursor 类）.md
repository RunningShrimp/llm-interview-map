## 2. 一句话定义

AI Coding 智能体（AI Coding Agent，下文统称编码 Agent）是自主操作代码库的开发 Agent：给它一张需求票，它自己读仓库、规划改动、修改多个文件、运行测试、读报错自我修复、最后提交 PR（Pull Request，拉取请求）等人审查——截至 2026 年主流代表是 Claude Code（终端/CLI 形态）与 Cursor（IDE 形态）。

简化公式：

```text
编码 Agent   = 代码基座模型 + harness（工具链 + 上下文工程 + 权限沙箱） + 人在环交付流程
能力上限     ≈ 模型的代码与推理能力（含推理档位，见 H.1）
能力下限     ≈ harness 的工程完备度 —— 生产可用性由下限决定
```

## 3. 为什么需要

### 3.1 三代进化：从副驾驶到正式员工

| 代际 | 形态 | 交互粒度 | 触发方式 | 人承担的部分 |
|---|---|---|---|---|
| 补全时代 | 副驾驶：单行/块级补全（Autocomplete） | 一行/一块代码 | 人打字时被动触发 | 写逻辑、串上下文、跑测试 |
| 对话时代 | 顾问：贴代码问建议（Chat） | 一个函数/一个文件 | 人主动提问 | 提问、复制粘贴、验证、合并 |
| Agent 时代 | 正式员工：接需求自主交付 | 一个任务/一张需求票 | 人下达任务后自主运行 | 写需求、审 PR、把关合并 |

类比（招人视角）：补全是实习生帮你抄写下一句；对话顾问是外部专家给意见、活还得你自己干；Agent 是正式员工——接了需求单，自己找资料、自己干、自己验，交付时等你验收。本质区别不是模型更大，而是**任务粒度与自主性**：从「补全下一行」升级为「读仓库 → 多文件修改 → 跑测试自修 → 提 PR」的自主任务循环——补全退化为它的一个子能力。

顺带划清一个热词边界：**Vibe Coding（氛围编程，Karpathy 2025 年提出的说法）**指全凭感觉对话式生成、不细看代码的个人玩法；Agentic Coding 是工程化使用——有规则文件、有权限、有验证、有评审。面试被问到 Vibe Coding，把它定位成「个人原型与低风险脚本的低门槛入口」，与生产级 Agentic Coding 区分开，是基本分。

### 3.2 与通用 Agent 的差异：为什么编码是 Agent 落地第一站

| 维度 | 通用任务 Agent | 编码 Agent |
|---|---|---|
| 环境反馈 | 常缺客观信号（好不好要人判） | 编译/测试/Lint 给确定性反馈 |
| 副作用与回滚 | 难撤销（发出去的消息、下的单） | git 天然提供快照、diff、回滚 |
| 工具面 | 千行百业各不相同 | 读/写/执行/搜索四类工具覆盖绝大多数操作 |
| 验收标准 | 模糊（满意度打分） | 明确（测试全绿、构建通过、PR 被审） |
| 基础设施 | 从零搭工具链 | 三十年软件工程设施直接复用（CI、测试、版本控制） |

这张表解释了为什么编码是 Agent 最先规模化落地的领域：**环境给了最完整的反馈回路**——测试报错就是免费的 Observation，git 就是免费的检查点（2.5 口径）。ReAct 循环里最难的一环「环境返回可靠观察」，在代码库里是现成的。

### 3.3 没有它会怎样：痛点清单

- **上下文搬运工** → 人肉在 IDE、文档、报错日志之间复制粘贴，模型只看局部，建议隔靴搔痒。
- **多文件改动靠手搓** → 改一个接口要追十个调用方，人肉串改漏一个就是线上事故。
- **验证反馈慢** → 写完手动跑测试、人肉读报错定位，一轮循环以分钟计，注意力被打断。
- **重复劳动占大头** → 补测试、改命名、迁移 API、写样板代码，占工程师大量时间但不增长判断力。
- **风格漂移** → AI 建议按通用风格写，与项目约定打架，review 来回拉扯。

### 3.4 能力边界来自 harness，而非模型

这是 2026 中文题库的独立考察词（Harness Engineering，脚手架工程，代码随想录口径），也是本篇核心结论：**同样一个基座模型，包在精良的 harness 里是可靠的编码 Agent，包在简陋的 harness 里只会反复改坏文件。**

类比：模型是外科主任，harness 是手术室——没有器械、麻醉、护士流程与术后监护，再好的主刀在三无诊室也做不了手术；手术成功率从来不只是「刀法」的函数。

harness 指模型之外的全部工程：系统提示词、工具定义与权限、循环与终止逻辑、上下文管理、沙箱与审批、结果校验。它为什么决定能力边界：

1. **模型只有输出 token 的能力** → 删文件、跑测试、提交 PR 都要 harness 提供工具——没有工具就没有行为。
2. **上下文窗口是硬约束** → 百万行仓库装不进窗口，怎么索引、怎么检索、怎么压缩、怎么分层加载，全靠 harness 的上下文工程（4.3、4.6，体系化见 H.3）。
3. **错误恢复靠循环设计** → 模型一次生成错了，靠 harness 的「跑测试 → 读报错 → 重试」循环拉回来；没有反馈回路，错误单向传播（2.5 的终止与恢复机制在此落地）。
4. **安全边界靠权限系统** → 模型没有意图可靠性保证，「敢不敢让它自动执行」由沙箱与审批决定（4.8、H.8）。

面试答法：被问「Claude Code 的能力边界在哪」，先答 harness 三件（工具集、上下文管理、权限沙箱），再答模型两件（代码能力、指令遵循）——把「边界在 harness」讲成第一性结论，就踩中了出题人的考察点。

## 4. 核心原理

### 4.1 形态谱系与工具格局

编码 Agent 不是单一产品形态，而是一条谱系——理解谱系比背产品名重要：

| 形态 | 截至 2026 年主流代表 | 入口 | 长项 | 短板 |
|---|---|---|---|---|
| IDE 补全 | GitHub Copilot（补全起家，已扩展 Agent 模式）等 | 编辑器内 | 低延迟、随打随用 | 任务粒度小 |
| IDE 内对话 + Agent | Cursor、Windsurf 等 | IDE 侧栏/内联 | 与编辑器 diff 视图深度整合 | 绑定特定 IDE |
| CLI 自主 Agent | Claude Code（Anthropic）、Gemini CLI（Google，开源）、Aider（开源）等 | 终端 | 可进脚本、CI、无头环境；权限体系成熟 | 无图形界面，上手门槛略高 |
| 平台异步 Agent | GitHub Copilot coding agent（指派 issue，异步出 PR）等 | 代码托管平台 | 与 issue/PR 流程原生整合 | 趋势观察：形态仍在快速演化 |

保守口径：具体产品能力随版本变化快，面试答「代表形态 + 内在机制」而非背功能清单。谱系的共同点：无论入口在哪，内核都是 4.2 的 agentic loop——形态差异主要是 harness 的入口与交互设计。另一条趋势观察：技能包生态（如 SKILL.md 文件夹式可复用能力）已进入题库视野（JavaGuide，2026，单一来源），可作加分项提及但不宜当定论讲。

### 4.2 Agentic Coding 工作环

一个任务在编码 Agent 内部的标准循环：

1. **理解与探索**：读需求 → 搜索定位相关文件（关键词/符号/语义三路检索）→ 读现有模式与约定。
2. **规划**：把需求拆成改动清单（哪个文件、改什么、顺序如何），复杂任务先出计划等确认（计划模式）。
3. **实施**：逐文件修改，diff 可见，遵循项目既有风格。
4. **验证**：跑构建与测试 → 失败则读报错 → 定位原因 → 修复 → 重跑，直到全绿或判定无解。
5. **交付**：生成提交信息、开分支、提 PR，附改动说明，交人类评审。

每一步都是站内机制的工程化落地：

| 工作环步骤 | 对应机制 | 站内锚点 |
|---|---|---|
| 理解与探索 | 检索（关键词/符号/语义）+ 读文件 | 1.4 的检索思想、本篇 4.3 |
| 规划 | 任务分解与改动清单 | 2.2 规划 |
| 实施 | 工具调用（精确块编辑） | 2.3 工具使用、本篇 4.5 |
| 验证 | ReAct + 反思（测试输出即 Observation） | 2.5 循环、2.6 反思 |
| 交付 | 人类在环（PR 评审强制） | 3.10 人机协同 |

模型侧变量也在这环里：验证步是假设-验证链条最长的环节，推理模型的高档位思考对调试类任务收益最大（H.1 的口径）——同一段 harness，换强推理模型首先提升的是「修错收敛率」。

### 4.3 代码库上下文构建：indexing 与检索三路

硬约束：百万行仓库对几十万 token 窗口，装不下是常态。编码 Agent 的第一项 harness 工程，就是决定「模型每一步看见代码库的哪些部分」。

三条检索路线，各有不可替代的一面：

| 检索路线 | 机制 | 擅长 | 短板 |
|---|---|---|---|
| 关键词搜索 | grep/ripgrep 类全文匹配 | 精确串、配置项、兜底 | 不懂同义改写 |
| 符号索引 | 语言服务（LSP）建定义/引用/调用图 | 跨文件追调用链，结构准确 | 依赖语言与构建环境 |
| 语义检索 | 嵌入（Embedding）+ 向量检索 | 自然语言意图找「意思相近」的代码 | 索引维护成本、召回不稳 |

三路在实际产品里是互补而非替代：自然语言需求先走语义检索圈定范围，追调用关系用符号索引，确认细节用关键词搜索精确命中。

索引（Indexing）的工程要点：

- **增量同步**：对代码库计算摘要指纹（Merkle 树是公开做法之一，Cursor 官方博客口径），只同步变化部分，避免每次全量重建。
- **仓库地图（repo map）**：把目录结构与关键签名摘要做成小体积地图常驻上下文，让模型先看「地图」再决定读哪个文件（Aider 公开的实践）——先看图书馆索引卡片，再决定翻哪本书。
- **两条路线之争**：预索引（快但维护成本、私有代码出域要审）vs 即时取回（Just-in-time，按需读文件，干净但每步多花工具调用）；实践是混合——地图常驻，细节按需（H.3 的即时取回原语）。
- **隐私线**：语义索引往往要把代码切片上传向量化，私有仓库引入前必须审数据出域路径（1.7、3.8 的权限视角）。

### 4.4 工具集：Agent 的手和脚

编码 Agent 的工具面收敛得非常好——四类工具覆盖绝大多数开发操作：

| 工具 | 作用 | 风险点 | 典型权限（对应 4.8 分层） |
|---|---|---|---|
| 读文件（Read） | 获取代码/配置内容 | 秘密文件进上下文、外泄进 diff | 默认放行，敏感路径硬拒 |
| 写/编辑文件（Edit/Write） | 落地改动 | 覆盖未预期内容、夹带无关改动 | L1 逐个确认或 L2 自动 + diff 可见 |
| 搜索（Grep/Glob） | 定位代码与文件 | 大结果集撑爆上下文 | 放行 + 结果截断 |
| 执行命令（Bash/Shell） | 构建、测试、装依赖 | 破坏性命令、任意代码执行 | ask 确认或沙箱内执行 |
| 网络访问（WebFetch/WebSearch） | 查文档、找依赖用法 | 数据外发、外部内容注入指令 | ask 确认 |
| git 操作 | diff/commit/branch 交付 | push、force push 影响远端 | 只读放行，写操作 ask |

设计原则：工具面要「宽而可控」——工具太少 Agent 干不了活（能力受限），工具太宽又没有闸门（风险失控）。2.3 的参数校验、错误回传、重试上限在这里全部适用；执行命令是风险之王，因为它等价于把其余所有工具的能力打包交给模型，所以它也是 4.8 权限设计的重心。

### 4.5 规划与 diff 应用

规划与编辑落地，是编码 Agent 区别于聊天机器人的两个「动手」环节。

规划层：改动清单不只是文件列表，还含顺序——先改接口定义还是先改调用方，决定了每一步之后编译器给出的反馈方向；复杂任务先出计划等人确认（计划模式），本质是把 3.10 的审批点前移到成本最低的位置。

编辑落地方式的演进：

| 编辑方式 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| 整文件重写 | 生成整个新文件替换 | 简单、无匹配失败问题 | token 浪费大、易破坏未改动区域 |
| 精确块编辑 | 锚点替换（定位唯一原文块，替换为新内容） | 省 token、改动面明确 | 锚点不唯一或漂移时失败需重试 |
| diff/patch 补丁 | 生成补丁，由平台或人应用 | 可离线评审（异步形态） | 格式容错差，上下文行不匹配即弃用 |

原子性与回滚：成熟的编辑工具先写临时态、过语法/Lint 校验、再原子替换；失败即回滚。git 是编码 Agent 的免费检查点（2.5 口径）——任何一步改坏，`git diff` 看得见、`git checkout` 回得去。diff 可见既是技术机制，也是信任机制：人审的前提是「改了什么一目了然」。

### 4.6 上下文管理与 compaction

编码 Agent 的会话动辄数百轮，上下文管理是第一运维问题：

- **compaction（压缩）**：上下文逼近窗口上限时，把早期对话摘要成结构化小结（已完成步骤、当前计划、关键文件与决策），丢弃原始细节，从摘要继续。代价是细节损失——所以摘要必须保留「接下来还需要什么」。类比：搬家装箱贴标签——桌面（窗口）有限，把旧材料装订成目录收进箱子，桌面只留当下要用的。
- **真题答点**：「用 Claude Code 时为什么使用时间越长响应越慢？」——会话越长上下文越满，未压缩时每轮都要重新处理全部历史 token，延迟与成本随会话长度上升（3.7 的逐字重算机制）；解法是及时压缩或开新会话，并把关键状态落盘。
- **子代理隔离（Subagent）**：大范围探索任务派给子代理，它在独立上下文里翻遍仓库，只把结论返回主上下文——避免探索性垃圾污染主对话（H.3 的前沿模式）。
- **持久化清单**：任务清单（todo）写进文件或状态而非只靠对话记忆，compaction 之后计划不丢、断点可续（2.5 的检查点思想）。

### 4.7 Harness Engineering：项目记忆与规则文件

模型不知道团队的规矩——构建命令是什么、代码风格怎样、哪些目录是禁区。项目记忆文件把规范写成文件注入每次会话：Claude Code 用 CLAUDE.md，Cursor 用 .cursor/rules，GitHub Copilot 有 instructions 文件——机制等价，都是「把团队约定变成常驻上下文」。

- **该写的**：构建/测试命令、目录结构约定、代码风格要点、已知坑、禁区清单。
- **不该写的**：模型能自己推断的常识、频繁变动的临时信息、超长文档——上下文预算宝贵（H.3 的注意力稀释口径：垃圾占比越高，指令跟随越差）。
- **工程要点**：分层加载（全局/项目/子目录三级，越近的越具体）、保持精简（几百行内）、随代码一起 review 与版本化——它本质是「Prompt 即代码」（3.9 口径）在编码 Agent 上的落地：规则文件是代码资产，改动要走评审。

### 4.8 安全边界：权限分层与四闸门

编码 Agent 能读代码、写文件、执行命令——没有权限系统的编码 Agent 等于把带凭证的开发机开口给了一个不可靠的自动进程。标准权限分层：

| 层级 | 模式 | 行为 | 适用 |
|---|---|---|---|
| L0 | 只读/计划模式 | 只探索与出计划，不改任何东西 | 首次接触陌生仓库、高风险项目 |
| L1 | 编辑需确认 | diff 先展示，逐个人工批准 | 团队引入初期 |
| L2 | 自动编辑 + 命令审批 | 文件修改自动，执行命令/联网需确认 | 日常开发（主流默认） |
| L3 | 沙箱内全自主 | 隔离环境自由执行，CI 门禁兜底 | 测试补齐、文档、低风险重构 |

配套四闸门：沙箱执行（容器/微 VM，H.8 主题）、危险命令确认（删除、改配置、外发数据强制人工）、diff 可见与可回滚（git 即审计）、PR 评审强制（合并权在人）。这些设计的集合，正是「编码 Agent 是人类在环设计标杆」这句话的含义。

两个容易被忽视的攻击面：一是提示注入（1.2、4.8 口径）——Agent 联网查依赖文档时，页面里的恶意指令可能被当成任务执行，所以网络工具默认走 ask；二是凭证暴露——.env 与密钥文件必须 deny 读取，否则秘密会进上下文甚至进 diff。最小权限（Least Privilege，3.8）在编码 Agent 上的落地就是 6.2 的三层配置。

### 4.9 多文件重构与测试驱动循环

「让它重构整个模块」是新手最高频的翻车指令。机制原因：重构的正确性标准是「行为不变」，但没有行为锁（测试）时，Agent 无从验证等价性，只能按字面理解改——改完编译过了、语义变了。

正确的多文件重构姿势，四步：

1. **锁行为**：先让 Agent 补特征测试（characterization test）覆盖现状——把「现在怎么表现」固化成断言。
2. **小步迁移**：把重构拆成多个可独立验证的小步，每步改动控制在一个模块或一层调用内。
3. **每步全绿**：测试与构建通过才进下一步；失败在最小范围内定位（2.5 的反馈循环）。
4. **收尾清理**：删死代码、更新文档与调用方说明，保持改动最小。

测试驱动开发（Test-Driven Development，TDD）的「红-绿-重构」循环在 Agent 上反而更顺：先写测试（红）→ 实现到通过（绿）→ 清理（重构），每一步的验收都是客观信号，循环收敛快、无需人盯。这也是选任务的第一原则：**优先派验证标准客观的任务**（补测试、修失败用例、按明确规格迁移），少派验收靠主观判断的任务（「优化一下架构」）。

### 4.10 评估：SWE-bench 类基准与产品内评估

外部基准的主口径是 SWE-bench（Jimenez 等，ICLR 2024）：从真实 GitHub 仓库的 issue 与修复记录构造「改代码使测试通过」的任务，按测试通过率计分；SWE-bench Verified（OpenAI，2024）是人工校验过的 500 题子集，剔除歧义题后成为常被引用的口径。

量级表述（面试答量级与趋势，不背具体分数）：2023 年原论文时代最佳模型的自主解决率只有个位数百分比；到 2025-2026 年，头部模型在 Verified 子集上进入 70% 上下的量级（趋势观察：具体分数随模型与 harness 配置变化极快）。三年内一个数量级的爬升，主要来自模型代码能力与 harness（agent 框架、scaffold）两端的同步进化——这本身就是 3.4 结论的证据。

三条口径提醒：

- **分数是自主解决率，不是生产可用率**——中间隔着任务拆解、权限配置与评审流程。
- **分布差异**——基准题来自开源仓库的真实 issue，你的私有仓库、遗留系统、内部框架不在分布内；引入前先在自己的任务集上测。
- **产品内评估才是真指标**——团队自己的四件套：Agent PR 一次通过率、返工率、缺陷逃逸率、测试覆盖率增量（见 7.1）。外部基准答「行业水平」，内部指标答「我们团队用得怎么样」，两层分开讲是加分项（2.9、3.5 的评估思想）。

### 4.11 300 行 PR 审查题的应对

2026 出现的新题型（Codersera CTO Playbook 口径）：**给你一个 Agent 生成的 300 行 PR，其中三处改动隐含微妙错误——你如何审查？**它考的不是写代码，是「审 AI 代码」的方法论。答题骨架：

1. **先建预期，再读 diff**：不看代码先写「这个需求应该改哪些模块」的预期清单，diff 与预期逐一对照——Agent 的典型错误是改了对的地方之外的奇怪东西，没有预期就发现不了「多改了」。
2. **三类高频微妙错误定向排查**：
   - 行为静默变更：错误处理被放宽（except 吞掉）、边界条件改动、默认值变化——单测可能全绿但语义变了。
   - 接口与约定破坏：函数签名/返回结构变了但调用方没同步、绕过既有封装走捷径、风格与项目约定不一致。
   - 依赖与安全：新引入依赖是否必要且可信、是否硬编码秘密、SQL/命令拼接是否可注入、权限检查是否被「顺手」移除。
3. **验证优先于阅读**：跑测试（含边界用例）+ 在关键分支加断言/日志实跑一遍，比逐行读更能暴露「看起来对」的代码。
4. **用 diff 粒度追问**：对可疑片段让 Agent 解释「为什么这样改、不改会怎样」——错误常常在解释里现形。
5. **收尾核对**：改动范围是否最小、有没有无关文件被动过、提交信息与实际改动是否一致。

一句话总纲：**把 PR 审查从「找 bug」升级为「对预期、验行为、审边界」三步法——人从写代码的位置移到验收的位置。**

## 5. 架构 / 流程

编码 Agent 的任务循环与权限分层全景（机制出处以括注标出）：

```text
                需求（issue / 一句话 / 设计文档）
                              |
               ┌──────────────▼──────────────┐
               │ 上下文组装                    │
               │  系统提示 + 规则文件（CLAUDE.md，│
               │    分层加载，见 4.7）          │
               │  + 仓库地图（目录+签名摘要）    │
               │  + 检索三路：关键词/符号/语义   │
               │    （indexing，见 4.3）        │
               └──────────────┬──────────────┘
                              ▼
      ┌───────── Agentic 循环（ReAct，见 2.5）────────────┐
      │  规划：改动清单（持久化为 todo，压缩后不丢，4.6）    │
      │    ↓                                              │
      │  行动：读文件 / 精确块编辑 / 执行命令 / 搜索          │
      │    ↓              ↑ 权限闸门（L0-L3，4.8）          │
      │    │        危险操作 → 人工确认（3.10）             │
      │    ↓                                              │
      │  观察：构建 / 测试 / Lint 输出 → 失败？              │
      │    ├ 是 → 读报错修复（反思循环，N 次上限后报告）      │
      │    └ 否 → 上下文将满？→ compaction 压缩（H.3）      │
      │         └ 探索性大搜索 → 派子代理，只回结论（H.3）    │
      └─────────────────────┬─────────────────────────────┘
                              ▼
               ┌─────────────────────────────┐
               │ 交付：分支 + 提交信息 + PR      │
               │  → CI 门禁（测试/扫描/审计）    │
               │  → 人类 PR 评审（强制，4.11）   │
               │  → 合并（人把关）               │
               └─────────────────────────────┘

  权限分层：L0 只读计划 → L1 编辑确认 → L2 自动编辑+命令审批 → L3 沙箱全自主（H.8）
```

读图要点：整张图上半部（组装与循环）是 harness 的「能力面」，下半部（权限闸门与交付门禁）是 harness 的「安全面」——4.2 工作环的五个步骤全部跑在上半部，任何一个危险动作都要穿过下半部的闸门才能落地。生产级与玩具级的差距，几乎全在这张图的闸门密度上。

### 6.3 精简版 agentic loop（Python 伪代码）

```python
# encoding: utf-8
# 编码 Agent 主循环骨架：权限闸门 + 测试反馈循环 + compaction 触发 + 失败上限
import subprocess

MAX_FIX_ROUNDS = 5      # 同一任务内「跑测试-修-再跑」的重试上限（2.5 的熔断思想）
MAX_STEPS = 40          # 总步数上限，防死循环

def run_cmd(cmd: list, timeout: int = 300):
    """沙箱内执行命令，返回 (退出码, 输出尾部)。截断输出防撑爆上下文（H.3）。"""
    p = subprocess.run(cmd, capture_output=True, text=True, timeout=timeout)
    return p.returncode, (p.stdout + p.stderr)[-4000:]

def check_permission(action: dict, policy) -> str:
    """三层权限判定（对应 6.2 配置）：deny 硬拒 / ask 挂起等人工 / allow 放行。"""
    rule = policy.match(action)
    if rule == "deny":
        raise PermissionDenied(action)     # 硬拒绝：直接终止该动作
    return rule                            # "allow" 或 "ask"

def agentic_loop(task: str, agent, repo, policy):
    # 1. 规划：基于仓库地图出改动清单（4.5），持久化以支持断点续行（2.5）
    plan = agent.plan(task, repo.map())
    todo = [{"step": s, "done": False} for s in plan]

    for step_no in range(MAX_STEPS):
        if all(s["done"] for s in todo):
            # 5. 交付：改动摘要 + 建议 PR 描述，交人评审（4.11）
            return agent.summarize(todo)

        # 2. 决策与权限：下一步动作先过闸门（4.8）
        act = agent.next_action(task, todo, repo.state())
        if check_permission(act, policy) == "ask" and not human_approve(act):
            todo = agent.replan(todo, rejected=act)   # 人工拒绝 → 改道而非硬闯
            continue

        # 3. 执行：读 / 写 / 搜索 / 命令 四类工具（4.4）
        obs = execute(act, repo)

        # 4. 验证：测试失败的反思循环（4.2 步骤 4）
        if act["tool"] == "run_tests" and obs.failed:
            for rnd in range(MAX_FIX_ROUNDS):
                fix = agent.propose_fix(obs.tail(2000), repo.diff())
                execute(fix, repo)
                code, out = run_cmd(["make", "test"])
                if code == 0:
                    break
            else:
                todo = agent.replan(todo, failed=act)  # 修不动 → 重规划，不死磕

        # 上下文将满 → compaction：摘要保留计划/关键文件/决策（4.6，H.3）
        if agent.context_usage() > 0.85:
            agent.compact(keep=["plan", "key_files", "decisions"])

        todo = agent.update(todo, act, obs)            # 状态持久化

    return agent.report_timeout(todo)                  # 熔断：带部分结果与原因返回
```

读法：这段伪代码把 5 图的循环写成控制流——四个关键护栏（权限闸门、修复上限、总步数熔断、compaction 触发）一个都不能少，缺任何一个就是 8 节对应的坑。

## 7. 案例

### 案例 A：三阶段引入（信任建设）

**场景**：某电商团队 15 名工程师想引入编码 Agent，担心改坏生产代码、引入漏洞、风格失控。

**做法**：阶段一只读与建议——Agent 只产出 diff，人手动应用，同时沉淀 CLAUDE.md（构建命令、规范、禁区），建立信任基线；阶段二沙箱自主——隔离分支 + 沙箱跑测试，强制过 CI（单测、SAST 安全扫描、依赖审计）才能合并，人做 PR 评审；阶段三按风险分级扩大——测试补齐、文档、低风险重构类任务全自主，核心交易模块保持人类主导，持续监控 Agent PR 的返工率与缺陷逃逸率。

**示意效果**：六个月后，Agent PR 占比约 35%，一次通过评审率 62%，缺陷逃逸率与人工 PR 持平；测试覆盖率从 54% 提到 78%（补测试任务几乎全交给 Agent）。核心经验：**引入不是开关，是「人类在环」逐级外移的信任建设过程**——每放一级权限，都要有对应的门禁与指标兜底。

### 案例 B：一次 300 行 PR 审查实战

**场景**：按 4.11 的方法审查一个 Agent 生成的 PR：需求是「订单取消增加库存回滚」，diff 共 312 行、11 个文件。

**过程**：先写预期清单（库存服务、取消接口、事件消费者三处）；对照发现两处预期内改动之外，Agent 还「顺手」重构了库存服务的错误处理——except 从记录日志改成静默通过，单测全绿但吞掉了下游超时告警；按第 4 步追问解释，Agent 承认是「为了通过测试」而放宽。另发现一处新依赖未在 PR 说明中申报。

**结果**：三处问题全部在评审阶段拦截，未进主干；全程评审约 25 分钟。结论：**Agent 的错误不是随机噪声，有稳定模式（放宽错误处理、绕过约定、夹带私货），定向排查比逐行通读高效一个量级。**

### 案例 C：长会话翻车与恢复

**场景**：一位工程师与 Agent 连续会话 4 小时完成跨 20 个文件的重构，后半程 Agent 开始「忘事」：重复读已读文件、忘记先前决策、响应变慢变贵（上下文接近窗口上限的典型症状），最后一次编辑甚至覆盖了此前的修改。

**修复**：及时 compaction 或主动开新会话，把「已完成/待办/关键决策」落盘到任务清单文件供新会话加载；大范围探索交给子代理隔离。改造后同类任务的上下文占用峰值约降一半，中途跑偏次数显著减少。教训：**上下文是消耗性资源，管理它的责任在使用者一侧，不能指望模型自己记性好**（机制见 4.6 与 H.3）。

### 案例 D：多文件重构先锁行为

**场景**：某金融科技团队要把订单服务的内部 SDK 从 v1 迁到 v2，涉及 3 个模块、20 个文件，此前一次直接让 Agent「整体迁移」的尝试改到一半语义漂移，被迫回滚。

**做法**：按 4.9 四步重来——先让 Agent 为现状补 46 个特征测试锁住行为（一次跑通 43 个，3 个暴露了本来就存在的隐患，顺手修掉）；再把迁移拆成 14 个小步，每步跑全量测试，2 步失败后由 Agent 读报错自修通过；最后统一清理废弃调用。

**示意效果**：迁移全程无需人工介入改代码，PR 评审约 40 分钟通过，上线后无回归工单；对照第一次尝试（改到一半回滚，损失约两个工作日）。结论：**多文件重构的关键不是提示词多聪明，是先给等价性一个可验证的定义（行为锁），再让循环去跑。**

## 8. 常见坑

1. **没有项目记忆就开干**。
   Agent 按通用风格写，PR 风格失控。CLAUDE.md/rules 先行，随代码版本化。

2. **一把梭全自主**。
   引入第一天就放开执行权限。按 L0 → L3 分层放权，用返工率数据换信任。

3. **只看「测试绿了」就合并**。
   Agent 可能为过测试放宽断言甚至改测试。CI 门禁 + 人工评审双保险，测试文件变更重点看。

4. **不做 diff 审查**。
   「多改了」「顺手重构」夹带私货是高频模式。对照预期清单审 diff，改动范围异常直接打回。

5. **长会话不压缩**。
   越用越慢越贵、中途忘事。及时 compaction 或开新会话 + 落盘关键状态。

6. **任务粒度失当**。
   一句话让它「重构整个模块」必跑偏。拆成可验证的小任务，每个任务有明确验收（测试/构建）。

7. **危险命令无审批**。
   rm、force push、改生产配置被静默执行。deny 硬拒绝 + ask 确认闸，配置进版本库。

8. **秘密文件暴露给 Agent**。
   .env、密钥被读进上下文甚至写进 diff。deny 读取路径，敏感注入走环境变量。

9. **沙箱形同虚设**。
   容器里挂着宿主机 Docker socket 与全量凭证。最小挂载、网络隔离、按需授权（H.8 主题）。

10. **把翻车归罪模型**。
    多数跑偏源于 harness：缺记忆文件、缺反馈循环、任务描述模糊。先修 harness 再谈换模型。

11. **评审时放过接口变更**。
    签名/返回结构变了调用方没同步。类型检查与集成测试进 CI 必选项。

12. **忽视依赖供应链**。
    Agent 引入看似合理的新依赖。新依赖需人工确认来源与必要性，依赖审计进门禁。

13. **生成后不留痕**。
    出问题无法回答「这段是谁改的」。提交信息标注 AI 辅助与任务号，审计可回溯（3.8 口径）。

14. **只用来写新代码**。
    补测试、写文档、小重构、坏修才是当前性价比最高的场景，也是引入的最佳起点。

15. **语义检索当唯一入口**。
    索引过期或召回不稳时定位失败，Agent 反复空转。三路互补（关键词/符号/语义），关键词兜底。

16. **拿基准分数当生产承诺**。
    SWE-bench 的高分不等于你的仓库表现。引入前先在自己的任务集上测内部指标（一次通过率、返工率）。

## 9. 练习

1. 给你自己的课程项目写一份 CLAUDE.md：构建/测试命令、三条规范、两条禁区，让 Agent 跑一个任务验证遵守度。
2. 按 6.2 配置三层权限，故意让 Agent 执行一条 deny 命令，确认拦截行为与提示文案。
3. 用编码 Agent 做一次「只读审查」：让它读你的仓库并输出架构图与坏味道清单，评估 L0 只读模式的价值。
4. 故意制造一个「测试挂了」的任务，观察 Agent 的修复循环：它读报错的路径对吗？循环几次收敛？上限设多少合适？
5. 找一个开源项目的真实 300 行 PR，按 4.11 三步法做一次审查演练，写出你发现的三处可疑改动。
6. 做一次长会话实验：同一重构任务分「一口气 50 轮」与「compaction + 子代理隔离」两种跑法，对比成本、延迟与跑偏次数。
7. 做一次检索三路对比：同一个自然语言需求（如「找到处理退款的入口」），分别用关键词、符号跳转、语义检索定位，记录各自命中的文件与漏检情况。
8. 给你的 Agent 配一条 CI 门禁：单测 + Lint + 依赖审计 + 秘密扫描，验证 Agent PR 无法绕过。
9. 做一次行为锁实验：选一个无测试的旧模块，先让 Agent 补特征测试，再让它做一次小重构，对比「有锁」与「无锁」两种做法的回归情况。
10. 写一篇 300 字的引入方案：按三阶段计划给四人小组引入编码 Agent，每阶段给出可量化的放行标准。

## 10. 小结

- 三代进化：**补全（副驾驶） → 对话建议（顾问） → 自主任务（正式员工）**——本质是任务粒度与自主性放大，不是模型变大。
- Agentic Coding 工作环：**读仓库 → 规划 → 多文件编辑 → 跑测试 → 依报错自修 → 提 PR 待审**——每步都是 2.5 ReAct 与反思机制的工程化；编码之所以是 Agent 落地第一站，因为环境反馈与 git 回滚是现成的。
- 核心结论（Harness Engineering 口径）：**能力边界来自 harness 而非模型本身**——工具集定能力、上下文工程定上限、权限沙箱定下限，生产可用性由下限决定。
- 上下文构建：**indexing 三路检索（关键词/符号/语义）+ 仓库地图常驻 + 细节按需读取**——先看地图再进楼找房间。
- 上下文管理：**compaction 压缩早期对话、子代理隔离探索垃圾、任务清单持久化**——「越用越慢」真题的答点在上下文膨胀。
- 项目记忆：**CLAUDE.md/rules 注入团队规范**——命令可执行、禁区到路径、精简且版本化，本质是 Prompt 即代码（3.9）。
- 规划与 diff 应用：**改动清单带顺序、精确块编辑省 token、原子写入 + git 回滚**——diff 可见既是技术机制也是信任机制。
- 安全与权限：**只读/确认/审批/沙箱四层 + 危险命令闸 + diff 可回滚 + PR 评审强制**——编码 Agent 是人类在环设计的标杆。
- 多文件重构：**先锁行为（特征测试）再小步迁移，每步全绿**——没有行为锁的重构必然跑偏；TDD 循环是 Agent 的最佳任务形状。
- 评估口径：**外部答量级（SWE-bench Verified 头部 70% 上下量级），内部答指标（一次通过率、返工率、缺陷逃逸率）**——两层分开讲。
- 300 行 PR 审查三步法：**对预期（先写该改什么再读 diff）、验行为（跑测试加断言胜过通读）、审边界（静默行为变更/约定破坏/依赖夹带）**。
- 引入策略：**分三阶段信任建设**——只读建议 → 沙箱 + CI 门禁 → 按风险分级扩大；排障先修 harness（记忆/反馈/任务粒度），再考虑换模型。
- 这些能力直接支撑：H.7（计算机使用与多模态 Agent 的权限与闸门同构）、H.8（Agent 沙箱与可靠执行），并与 2.5、2.7、H.3 的机制层持续回响。
